## Verdict

1. **Logic must change before a re-run: yes.** The calculator prices required spend on `media_cost` alone (`queries/ti_xxx_advertiser_prefill_metrics.sql:32,95`) while its own cohort defaults, INCR-75, and AUDI-1204 all price on advertiser-facing spend (media + data + platform). Median CPM ratio across 670 overlapping advertisers is 3.105x (WGU 31357: $4.607 embedded vs $9.116 in `tickets/incr_75_eligible_advertisers/outputs/incr_75_advertiser_metrics.csv`), and required spend is linear in CPM (`ti_xxx_mde_calculator_prefill.html:798`). Selecting an advertiser and clicking CLEAR currently return budgets on two different spend definitions.

2. **Re-runnable as-is today: no.** `queries/ti_xxx_advertiser_prefill_metrics.sql:21` declares `agg_end` from `dw-main-silver.aggregates.agg__daily_sum_by_campaign`, which no longer exists (whole `agg__*` family gone, confirmed by `bq ls` 2026-08-19 in `tickets/incr_75_eligible_advertisers/summary.md` §9.5). The script fails at the DECLARE, before any CTE, so all 12 embedded fields fail to regenerate. Cost of the corrected run: reuse `tickets/incr_75_eligible_advertisers/queries/incr_75_advertiser_metrics.sql`, which already carries every fix, plus a raw-to-compact JSON transform that does not exist in the repo. Scan ~95.5 GB, ~$0.58 on-demand at $6.25/TiB, ~$0 marginal through `bq_run.sh` on the us-central1 reservation.

3. **Mode dashboard: not now.** The port is mechanical but real (57 `document.getElementById` rescopes, 497 CSS lines to scope under one root id, data-source swap, SQL flatten), and it buys exactly two things the gist lacks: an auth gate and a schedule. Neither is needed until churned-advertiser revenue goes into the array, and two Mode preconditions are unverified (schedule creation with a member API key; Mode's BigQuery billing project and reservation coverage).

## Re-run requirements

### Do not re-run the TI-1019 query

`queries/ti_xxx_advertiser_prefill_metrics.sql` is dead at line 21. Its 2026-08-11 commit (0b6fc895) amended comments only; lines 21 and 72 still read `dw-main-silver.aggregates.agg__daily_sum_by_campaign`.

### Use the INCR-75 fork as the delivering-cohort source

`tickets/incr_75_eligible_advertisers/queries/incr_75_advertiser_metrics.sql` (143 lines, 2026-08-19) already carries every correction the refresh needs, verified in the file:

- `summarydata.sum_by_advertiser_by_day` for monthly spend, window anchored on `CURRENT_DATE()` rather than a `MAX(day)` probe (the physical table requires a `day` partition filter, so a `MAX(day)` CTE is rejected).
- Spend as `media_spend + data_spend + platform_spend` on both the 30-day and monthly legs, so the CPM basis and the budget basis match.
- `distinct_ips_56d` (`APPROX_COUNT_DISTINCT`), which the extrapolation-free 8-week cross-check needs.
- `is_b2b` and `vertical_buckets` from `fpa_advertiser_verticals` type=0, which the CVR gate needs.
- `active` from `integrationprod.advertisers`.
- Single-statement, no `DECLARE`, so it is also the version a scheduled runner or Mode could execute.

One decision it forces: it drops the spend floor entirely (delivered-in-30d only), returning 1,859 advertisers against TI-1019's 879. Keep a floor for the picker or the list grows ~2.1x. TI-1019's floor was `HAVING SUM(a.spend_ip) > 1000` at line 64, on media_cost; the same $1,000 on advertiser-facing spend is a looser cut.

### Cohort definition change for lapsed advertisers (AUDI-1204)

Both AUDI-1204 queries are single-advertiser templates and need a cohort rewrite:

1. `queries/audi_1204_last_active.sql` selects `MAX(day)`, `MIN(day)`, `delivering_days`, `lifetime_spend` from `summarydata.sum_by_advertiser_by_day` for one `{{ADVERTISER_ID}}`. Add `GROUP BY advertiser_id` and drop the ID predicate to resolve last-active per advertiser in one pass. History floor is 2024-01-01 (the table's floor), so an advertiser whose last delivery predates 2024 is excluded outright. Rate metrics themselves reach back to the `cost_impression_log` floor of 2023-10-01 with no TTL, so extending further means repointing the last-active resolution at `cost_impression_log`.
2. `queries/audi_1204_lapsed_advertiser_metrics.sql` takes `{{WIN_START}}`, `{{WIN_END}}`, `{{WIN56_START}}`, `{{ADVERTISER_ID}}` and already emits `window_start` and `window_end` alongside the same 12 field names plus `distinct_ips_56d`, `is_b2b`, `active`. Convert to a cohort form driven by a per-advertiser literal window list.
3. Keep the two-step literal-window split. BigQuery does not prune partitions on a subquery-derived date: AUDI-1204 measured 39.5 GB collapsing to 5.5 GB estimated for one advertiser (logged runs executed at 4.2 and 4.5 GB), and `artifacts/audi_1204_run_metrics.py` dry-runs and aborts above 25 GB. What degrades at cohort scale is pruning tightness, because the pruned set becomes the union of every last-active window rather than 56 days.

### Re-pull the 879 incumbents in the same run

The 12 field names map 1:1 between the two queries, but four fields do not carry the same meaning: `spend30` and `cpm` (media_cost vs advertiser-facing) and `typical`/`maxMo` (frozen aggregate on media_spend vs `sum_by_advertiser_by_day` on advertiser-facing total). WGU shows the size of it: prefill `cpm` 4.607 / `spend30` $1,847,461 on 401.0M impressions against INCR-75 `cpm` 9.1164 / `spend_30d` $3,352,209 on 367.7M impressions, 9% more impressions and 45% less spend. `months` is capped at 8 for every incumbent by the frozen aggregate (WGU 8 vs 13). A merge without re-pulling produces one picker whose two cohorts differ ~2x on required budget for purely structural reasons.

### Check the monthly window before trusting `typical`

`incr_75_advertiser_metrics.sql:89-92` truncates a `CURRENT_DATE()`-anchored 365-day range to calendar months, so both boundary months are partial and 365 of the 1,859 CSV rows carry `active_months_count` = 13. `typical` is the median of those months and is the calculator's default budget basis (`ti_xxx_mde_calculator_prefill.html:1186`), so every prefilled budget moves on whether partial boundary months are dropped. The source swap fixes the dead table and the spend basis; it does not settle this. Decide it in the same pass.

### Fields to add

`lastActive`, `window_start`, `window_end` (lapsed rows), `ips56`, `is_b2b`, prospecting share, and visiting/converting IP counts for the stability gates. Drop `imps30` and `ips30`, which no code path reads.

### Transform and redeploy

No script exists for the raw-to-compact JSON transform (field renames, string-to-number, per-field rounding). It has to be written before any of this can be scheduled. Redeploy edits three lines: `:732` (Generated comment), `:733` (the array), `:734` (`window.DATA_PULL_DATE`, which renders into the header at `:1246`). Publish with `gh gist edit` so the filename, and therefore the githack URL, is unchanged.

### Security note on the gist URL

The gist is `public=false`, but an unauthenticated fetch of the live URL returns HTTP 200 with the full 221 KB file, byte-identical to the artifact. That is obscurity, not access control, and the link has already been shared into Slack (the ElevenLabs thread: Kale McNaney, Edgar von Trotha, Mike Dolt, cc Matt Brorby). The array already exposes 879 named advertisers, $12.78M of trailing-30d spend, and per-advertiser spend, peak month, CPM, visit rate and conversion rate. Adding churned rows publishes former-customer revenue and, in aggregate, the win-back target list MNTN would work. Both `summary.md:50` and `tickets/audi_1204_lapsed_advertiser_test_eligibility/summary.md` §8 record this as a consideration to settle before loading churned revenue, not as a blocker. The constraint on the fix: githack raw URLs embed the filename, so a same-URL redeploy keeps every already-shared link working and keeps the exposure, while an auth-gated host requires re-distributing the link.
