# What the debugger and optimizer actually do — function inventory, 2026-09-06

**"Both tools work and the core paths earn their keep, but about 45 of roughly 180 functions have never run, five safeguards currently fail silently, and there are two full copies of the code with three laptop schedules against the dead one - cut ~700 lines and three jobs, fix five small defects, and add nothing new until the savings engine produces one real number."**

## Is it too complicated?
"Yes, it has become too complicated - but the complexity is concentrated, not spread evenly, and the core is sound.\n\nThe numbers. Roughly 180 distinct functions across two tools. Around 45 have never been observed to run. 24 of 43 failure patterns have never matched anything. 5 of 15 optimizer detectors have never produced a finding, and 2 of those cannot, because the data they read is never collected. Two of the debugger's three deep dives are effectively idle: Databricks runs 11 times and returns nothing every time, Dataproc runs 3 times and throws away the answer it found. The optimizer publishes 9 file families a day from one run. Both tools exist in two copies, with three laptop schedules running the copy, one of which has downloaded 1.8 GB a day for eleven days and crashed before reading any of it.\n\nWhat is actually working. The core paths are lean and earn their keep: fetch, parse, classify, report, deliver, remember. 197 failures diagnosed in 15 days with a 3-second time-to-first-answer. 2,126 findings tracked across 13 sweeps with a state machine that correctly refused to declare 30 untouched DAGs fixed during a six-day outage. That guard alone justifies a lot of the machinery around it.\n\nWhere the complexity actually came from - three sources, in order of cost. First, duplicate deployment shapes: two full code copies, three laptop crons, a container image for an abandoned platform. That is pure overhead with no capability behind it. Second, speculative coverage: patterns, detectors and states written for failures that have not happened. Individually cheap, collectively they make the catalogue unreadable and hide the ones that matter. Third, and most expensive, measurement machinery built ahead of measurable results: a savings engine with confidence intervals that has measured zero savings in sixteen days, and a plan-analysis half that runs daily and prints the same negative sentence.\n\nThe real risk is not size, it is silent failure. Five separate paths currently fail without saying so: the Databricks dive swallows a missing credential behind a one-word key mismatch; the extraction canary builds its alarm threshold from the degraded stream it polices and can no longer fire at any input; the Confluence write drops rows permanently on any error and never retries; the retry guard on the failure listener never matches, doubling sweep volume; and the empty-sweep check sums both download paths so a total archive failure is masked. Each of these was built as a safeguard and is now a place where a fault hides.\n\nPosition: cut about 700 lines and three scheduled jobs, fix five one-to-ten-line defects, and do not add another surface until the savings engine produces one real number end to end. The tools are not over-built for the problem. They are over-built for the evidence currently available about the problem."

## The debugger, in the order a failure travels

1. FIRE THE SWEEP THE INSTANT A TASK FAILS. A small plugin runs inside the failing task's own process and asks Airflow to start one debugger run immediately. Trigger: Airflow's built-in 'task failed' hook, on every task in the deployment. Fires in prod, measured: 130 manual sweep runs, all started 3-5 seconds after the matching failure. Known defect: one of its five guards, 'skip a task that is about to retry', never actually matches because Airflow 3 does not tell the listener that state, so roughly twice as many sweeps run as intended. No wrong output results, just wasted runs.

2. RAPID SWEEP, EVERY 15 MINUTES. Reads failures that finished in the last 45 minutes, diagnoses each one, posts the answer to Slack. If the scheduler was paused it stretches the window back to where the last cycle stopped, capped at 6 hours. Trigger: a 15-minute schedule, plus the instant trigger above. Fires in prod: the cycle bookmark file in cloud storage was rewritten 14 minutes before I looked, and 55 of the last 197 diagnosed failures were answered here rather than waiting for the daily run.

3. DAILY SWEEP, 17:00 UTC. Re-reads every task that failed at any point during the previous day, including ones that later succeeded on a retry, diagnoses them all, posts anything the rapid sweep missed, and publishes the day's record. Trigger: a daily schedule. Fires in prod: 15 published day-reports covering 2026-08-20 to 2026-09-05, 197 diagnosed failures in total. This is the system of record and the only path that files tickets.

4. SCOPE THE SWEEP TO THE PAGING FLEET. Only looks at DAGs carrying one of twelve team or product tags, so pipelines nobody gets paged for stay invisible. Trigger: every sweep. Fires in prod, and is the only thing bounding either sweep. Small flaw: the tag match is case-sensitive, so three DAGs that hardcode a lowercase team name are skipped. Those three alert to a personal email rather than Slack or a pager, so no paging coverage is actually lost.

5. FETCH THE FAILED TASK'S LOG. Lists the failing tasks over Airflow's web API, picks the try that actually failed (for a task that later recovered, that is the try before the last one), downloads that try's log, and flattens Airflow's structured response into plain text. Trigger: start of every sweep. Fires in prod: all 197 diagnoses are built from text fetched this way. This is the tool's only input.

6. USE THE FILENAME AS THE IDENTITY RECORD. Airflow 3 log bodies rarely say which DAG or task they belong to, so each log is saved as a filename encoding time, DAG, task, try number and state, and the parser reads identity back off the name. Trigger: every log written. Fires in prod. Known defect: the state in the filename is the task's state right now, so a task that later recovered is stamped 'success' and the report then prints the wrong 'why was this log empty' explanation.

7. PARSE IDENTITY, ENGINE AND THE HANDLE THAT LEADS DEEPER. Pulls DAG, task, run and try out of the log, decides which compute engine ran the work, and extracts the one identifier that leads to the real cause: a Dataproc batch id, a Databricks run id, a Vertex pipeline run, or the target of a cross-DAG wait. Trigger: every diagnosis. Fires in prod. Worth knowing: 117 of 197 failures produce no engine at all, so most diagnoses never reach any of the deep dives below and are carried by pattern matching alone.

8. REJECT A KNOWN-BOGUS BATCH ID. When Airflow logged the Dataproc job id as literally 'None' or 'None-1', the parser throws the id away and records that the upstream step never minted one. Trigger: Dataproc logs with that pattern. Matches real production logs (two on 2026-08-17), but has not fired since the tool was deployed. Cheap and load-bearing: without it the tool would call the cloud API asking about a job called 'None-1' and report 'batch not found', hiding the real fault.

9. CLASSIFY AGAINST THE PATTERN CATALOGUE. Matches the log against 43 ordered regular expressions, first match wins, each returning a failure class, a likely cause, a fixability rating and a concrete remedy. Trigger: every diagnosis, and again on every upstream log walked. Fires in prod: 19 of the 43 have ever matched a real failure. The top four are task timeout (31), OpenAI file quota (11), Dataproc job died with no payload (8), and dbt model error (7).

10. KEEP THE CATALOGUE IN THE RIGHT ORDER. A loose pattern placed above a tight one would steal its matches, so four precedence pairs are fixed deliberately and a test fails the build if the order changes. Trigger: every classification. The mechanism cannot be observed in production (the record stores the winner, never the runner-up), but it is proven by test, and it exists because a loose pattern once caused a real human misdiagnosis.

11. DATAPROC BATCH DIVE. Describes the failed Dataproc job: state, its time-to-live, actual runtime, five performance settings, and the driver's own error text pulled from cloud logging or the staging bucket. Trigger: a Dataproc engine failure with a valid job id. Fires in prod, 3 of 197 failures. All three collected a real error and then published a non-answer telling the reader to go read the driver log the tool was already holding, because a boilerplate wrapper message wins the pattern match. This is a real defect, not a design limit.

12. STAGING-BUCKET DRIVER-OUTPUT FALLBACK. When cloud logging returns nothing, reads the job's driver output file directly from the staging bucket, and if permission is denied says so and names the access grant to request. Trigger: an empty cloud-logging read; also the last step of the Vertex dive. Verified working live against a real production job. It is the only source of error text once cloud logging expires after 7 days.

13. STRUCTURAL TIMEOUT DETECTION. Some Dataproc jobs are killed by a wall-clock limit and leave no error message at all, so the tool declares a timeout kill from shape alone: the job was cancelled and its runtime landed within 5% of its configured limit. Trigger: any Dataproc dive. Never appears in the published record, but re-running the code today fires it on 12 of a 25-job sample of real cancelled jobs, including two on a DAG the sweep already covers. It is the only working detector for this class, and it has no test.

14. DATABRICKS RUN DIVE. Fetches the failed Databricks run, isolates which task inside it failed, reads that task's error and stack trace, and pulls the cluster's termination reason. Trigger: a Databricks failure with a numeric run id. Runs in production at least 11 times and returns nothing every time: no Databricks credential is configured for the tool, and a one-word key mismatch in the code swallows that fact, so the report shows a bare link and an invented note saying the task was 'not terminal'. Two bugs, one of them a single word.

15. VERTEX AI DEEP DIVE. Walks six layers down from a failed Vertex pipeline: the pipeline record, the failed leaf step, the machine that ran it, that machine's log, the Dataproc jobs it launched, their driver output, and if the deepest error is a known decoy, the cluster-creation audit log. Deepest real error wins. Trigger: the log printed a Vertex pipeline link. Fires in prod, 7 of 197 failures, 4 of which produced answers no other path could reach (a missing model version, two quota exhaustions, a capacity stockout).

16. READ CLOUD LOGS IN THE RIGHT ORDER. Cloud logging returns newest-first and splits a stack trace across entries, so the tool reverses the list before hunting for the error. Trigger: every machine-log read in the Vertex dive. Proven on a real 92-entry production capture: read forward the tool finds nothing, read reversed it correctly identifies quota exhaustion.

17. REFUSE TO CALL A DECOY THE CAUSE. Three error patterns can only ever sit in front of the real cause (a cleanup handler's own 404, a Slack notifier failure, a job reattach). Each names what it hides and where to look next. Trigger: every report build. Fires in prod three times, and all three were false alarms: the failing task's whole job was posting to Slack, so the Slack error WAS the cause, and the report contradicted its own correct verdict two lines above. Needs a guard the sibling Slack renderer already has.

18. FOLLOW A DECOY TO THE AUDIT LOG. For one of those three decoys, the tool does not just warn, it resolves: it pulls the cluster name out of the 404 and reads the cloud audit log for why cluster creation was refused. Trigger: that specific decoy. Fired once, 2026-08-24, turning 'the cluster disappeared' into 'the request needed 145,500 units of disk and 74,280 were free'. That single firing is why it stays.

19. ASK WHAT A WAITED-FOR TASK ACTUALLY DID. A cross-DAG wait fails silently with no message, so instead of pattern matching the tool asks Airflow what the waited-for task really did and maps six answers to six verdicts. Trigger: the log names a wait target. Fires in prod: the 'the target failed' verdict appears in published reports, and two other verdicts fired on real logs before publishing began.

20. COMPARE AGAINST WHEN THE WAIT GAVE UP, NOT WHEN WE ASKED. Airflow answers with the state now, so a recovered target reads 'success' hours after the wait correctly failed. The tool compares the target's finish time against the moment the wait gave up and rewrites the verdict when the target moved on afterwards. Trigger: any resolved wait with a known failure timestamp. Confirmed firing on a real production log through the real code path; not yet observed in a published report.

21. NAME WHICH UPSTREAM TASK ACTUALLY FAILED. A task marked 'upstream failed' never ran, so its log is an empty stub. One extra call lists the other tasks in that run and names the ones that failed, so the report can say which task to look at. Trigger: an empty upstream-failed stub. Triggered once in 15 days and found nothing, so the naming line has never appeared in any published report. Guarded, tested, cheap; unproven.

22. WALK UPSTREAM TO THE TASK THAT ACTUALLY RAISED. Follows the dependency chain back to the first task with a real error, proving each hop is a genuine ancestor rather than a guess. Trigger: a failure whose own log carries no error. Fires in prod.

23. SETTLE THE FORK A PATTERN LEAVES OPEN. Some patterns identify a class but leave two possible causes. Eight small resolvers run one extra check to settle which. Includes computing a runtime trend for a timeout: is this job creeping toward its limit, and how many runs until it breaches. Trigger: a matched pattern with a registered resolver. Fires in prod.

24. BUILD THE ANSWER-FIRST REPORT. Assembles the headline verdict, the evidence, the remedy, the confidence rating, and links, then trims to length without gutting any single line. Trigger: every diagnosis. Fires in prod, 197 times.

25. ATTACH SIMILAR PAST INCIDENTS. Scores the diagnosis against a 24-incident history and attaches the closest matches. Trigger: every diagnosis. Fires heavily: 169 of 197 diagnoses cite a past incident. The catch: the incident file is a hand-copied snapshot that stopped moving on 2026-08-20, nothing syncs it, and the staleness alarm is set to 45 days so it will not warn until October. 86% of diagnoses cite history from a frozen file.

26. THREAD THE REPLY UNDER THE FAILURE'S OWN ALERT. Searches the alert channels for the alert about this exact run (matching on run id, never on names, which repeat) and replies in that thread. Trigger: every diagnosis. Fires, but rarely: 2 of 118 posted answers landed under their own alert. Most failing DAGs alert to channels the tool is not configured to read, so it searches up to 300 messages per diagnosis for nothing. On 2026-09-03 that was roughly 378 fruitless searches.

27. COLLAPSE THE REST INTO ONE DIGEST THREAD. Everything that could not be threaded is held back and posted at the end of the sweep as one parent message with one reply per group, repeats collapsed to a counted line. Trigger: end of every sweep. Fires in prod: on 2026-09-03 it turned 49 diagnoses into 1 parent plus 19 replies. It exists because per-failure posting was too noisy.

28. ANSWER EACH FAILURE EXACTLY ONCE. Writes a small marker file per answered failure, keyed by DAG, run, task and try, so the rapid and daily sweeps never answer the same thing twice. Trigger: read before every post, written after every successful one. Fires in prod: 62 markers, and I reproduced the naming scheme exactly against a live one. Without it every failure would get roughly four duplicate replies.

29. CARRY THE WINDOW ACROSS A SCHEDULER PAUSE. Records where each cycle stopped so the next one can stretch back over a gap. Trigger: every rapid cycle. The write fires every cycle; the stretch itself has never been needed in production, because it requires a gap longer than 45 minutes.

30. PUBLISH THE DAY'S RECORD. Writes the day's findings as a data file and a readable report and uploads both to cloud storage, using a hand-rolled upload because the standard command-line tool cannot authenticate inside these worker pods. Trigger: end of a daily sweep that diagnosed at least one failure. Fires in prod: 30 objects across 15 days. Cosmetic bug: the published data file always says its own upload list is empty.

31. ARCHIVE EVERY UNEXPLAINED LOG. Uploads the raw log of any failure that matched no pattern, so a new pattern can be written from real lines. Trigger: any daily sweep with an unmatched failure. Fires in prod: 79 logs over 10 days. But 75 of those 79 are tries that were retried and then succeeded, so the queue looks like a huge backlog when the genuinely unexplained terminal failures number four.

32. WATCH FOR EXTRACTION QUIETLY BREAKING. Compares today's unexplained rate against the last seven days and warns if it jumps. Trigger: every daily sweep with enough history. Runs every day, has never warned, and mathematically cannot: it builds its baseline from the same degraded stream it polices, that baseline has climbed to 68.5%, and its alarm threshold is now above 100%. Broken, not merely quiet.

33. FILE ONE JIRA BUG PER NEW FAILURE PAIR. For each DAG/task pair never seen before, files a bug, links it, and appends a row to the on-call playbook page in Confluence, all as a service account rather than a person. Trigger: once per daily sweep. Fires in prod: 56 tickets filed, playbook at version 16, last written 2026-09-06. Three flaws: the priority it computes never reaches Jira so everything lands as lowest priority; the duplicate check reads the pair back out of the ticket title, so renaming a ticket re-files it; and a closed ticket suppresses its pair forever.

34. THE PASTE-READY TROUBLESHOOTING PACK. Renders a full write-up with problem, matched evidence, known fix, code links and performance profile. Trigger: every single diagnosis, at least 197 times. Nothing in production reads it. Both sweeps store only the short report; no published file contains it. Only a hand-run command-line flag surfaces it.

35. THE PERFORMANCE ESCALATION BRIDGE. For slow-shaped Dataproc failures, downloads the Spark event log and runs the optimizer's analysis over it. Trigger: a failure matching one of three named patterns. Has never fired: two of the three patterns have never matched a real failure, and the third is misspelled and does not exist in the catalogue at all, so it can never match anything.

36. THE AI FALLBACK. When pattern matching finds nothing, the code tries to call a language model. Trigger: on by default from the command line. Cannot fire: the module it imports is deliberately not shipped, and company policy forbids the API key on a production worker. The import always fails and the code correctly degrades. About 35 lines exist to reach something that is not there.

## The optimizer, in the order a sweep runs

1. DAILY SWEEP, 09:00 UTC. One scheduled job runs the entire optimizer once a day: restore history, download logs, analyse, score, write nine files, post to Slack. Trigger: a daily schedule. Fires in prod: all nine outputs land together every morning, most recently 2026-09-06 at 09:18. This is the tool.

2. RUN AS A DEDICATED IDENTITY. Before any cloud call, the job switches to a purpose-built service account with narrow permissions instead of the deployment's own identity. Trigger: start of the sweep. Fires in prod, proved by a permission failure: when a billing grant was given to the wrong account, the billing query failed precisely because the sweep was running as the narrow account. Fixing the grant on the right account fixed the query.

3. REFUSE TO OVERWRITE HISTORY ON AN OLD RE-RUN. If someone re-runs an old day, the job blanks its storage location so it computes everything but publishes nothing, protecting that day's already-published files. Trigger: every run, active only when the run's date is two or more days stale. Never observed firing. Gap: the Slack post is not covered by this guard, so a stale re-run would still announce results.

4. RESTORE THE HISTORY FILES FIRST. Downloads the finding ledger and the stage-metrics history before doing anything. Both are republished under a fixed name, so without the restore each day would overwrite the entire history with one day's data, and the storage bucket has no version history to recover from. Trigger: every publishing sweep. Fires in prod: the ledger holds 2,126 rows across 13 days in a single 1.2 MB file, of which today's sweep contributed 251.

5. TELL 'MISSING' APART FROM 'UNREADABLE'. When restoring, a genuine 'file does not exist' means start fresh, but any other failure raises an error rather than silently pretending the file was absent. Trigger: the two restore calls. The happy path fires daily; the discriminating branches have never been exercised. Note this specific safeguard is only four days old.

6. LIST THE NEWEST 200 ARCHIVED LOGS. Pages the storage listing, keeps compressed Spark logs, sorts by creation time, takes the newest 200, and raises if listing itself fails rather than reporting an empty day. Trigger: every sweep. Fires in prod.

7. NEVER CUT A MULTI-PART LOG IN HALF. Some Spark logs are directories of parts. If the 200 cut-off lands inside one, the missing siblings are added back, because half a log parses as a complete short run and scores 'clean'. Trigger: every listing. Covered by test; the expansion has not been observed in production, where the count has always landed exactly at 200.

8. DOWNLOAD EACH LOG INDIVIDUALLY, AUTHENTICATED. One authenticated request per file, counting successes off disk rather than trusting exit codes. Trigger: every sweep, after listing. Fires in prod and was the fix for a real six-day outage: before this change the sweep was landing 6 of 200 files a day; after it, 200 of 200 with zero failures on four consecutive days.

9. COLLECT THE OTHER HALF OF THE FLEET FROM THE HISTORY SERVER. Most jobs write their logs to a temporary bucket rather than the archive, so a second path lists recent Dataproc jobs, admits the successful ones belonging to this team, and copies up to 150 of their logs. Trigger: every sweep. Fires in prod: exactly '150' every day for eleven consecutive days, which is the cap binding. 27 eligible jobs are dropped every sweep, and 22 more belonging to a sibling team are excluded by an over-strict name match.

10. PARSE THE SPARK EVENT LOG. Turns a compressed log into a structured run: jobs, per-stage task rollups, executors, configuration, SQL plans with per-operator metrics, and cached-data statistics. Trigger: once per log. Fires in prod and produces 95.7% of all findings. Three of its seven data surfaces feed nothing that has ever produced a finding.

11. STREAM MULTI-FRAME COMPRESSED LOGS. Real Spark logs are written in many compressed frames; a naive read returns only the first 58 bytes, which parses as an empty run and scores 'clean'. This streams across every frame without loading the file. Trigger: every compressed log part. Fires in prod: measured today, a 97 MB log expands to 1.8 GB, and files carry 500 to 2,182 frames each.

12. PICK THE RIGHT STAGE ATTEMPT AND RECOVER MISSING TASK COUNTS. Keeps only the final attempt of each stage, and when Spark never wrote a stage's completion record, rebuilds the task count from the tasks actually seen. Trigger: end of every parse. The recovery half fires on real logs (in one production log, 12 of 22 stages had no completion record). The retry-selection half has never had anything to do: zero retried stages in 29 sampled production logs.

13. COST EACH RUN IN EXECUTOR-HOURS. Sums each executor's live time to produce the cost unit used to rank findings. Trigger: every parsed log. Fires in prod. Caution when reading the digest: the ledger stores the day's total across all runs of a DAG, but the digest labels it 'in its worst run'. One published '4,425 executor-hours in its worst run' was a 13-run day total; the actual worst run was 1,136.

14. CRAWL THE FLEET AND RANK WORST-FIRST. Runs every detector on every log, catches per-log errors so one bad file cannot sink the sweep, and sorts jobs by high-impact findings first. Trigger: once per sweep. Fires in prod: 'Fleet optimization: 344 jobs scanned, 301 findings, 157 high-impact' on 2026-09-05.

15. SKIP LOGS IT CANNOT TRUST. Records rather than scores three kinds of log: still-in-progress, empty or truncated, and ones that error out. Trigger: per log. The empty-log guard fired 9 times in the first week; nothing has been skipped since 2026-08-26. Note a real blind spot: 461 permanently-in-progress logs sit in the archive and are simply never seen.

16. WRITE THE FULL BACKLOG REPORT. One line per job with its finding counts and worst issue, worst first. Trigger: every sweep. Fires in prod: 31 KB on 2026-09-05, 344 job lines, of which 218 are simply 'clean'.

17-26. THE TEN EVENT-LOG DETECTORS. Each looks for one specific waste pattern in a parsed run and prescribes a fix. Eight fire in production: uneven work distribution (skew), one slow task holding up a stage (straggler), spilling to disk, wrong shuffle partition count, time lost waiting for shuffle data, garbage-collection pressure, executors reserved but idle, and unstable shuffle fetches. Two have never fired and structurally cannot: preemption cost (the fleet runs serverless, which never reports preemption) and ineffective caching (needs a Spark setting the fleet does not enable, so its input is permanently zero). Two detectors account for 1,409 of 2,126 findings: shuffle wait and disk spill.

27. THE FIVE PLAN-TEXT DETECTORS. A second family reads the query plan rather than the metrics, looking for missing table statistics, a join that should be broadcast, oversized shuffles, a window operation forcing a full sort, and the same table scanned repeatedly. Trigger: every SQL query in every log, and every Databricks plan, on every sweep. None has ever produced a finding, on either path. The cause is upstream: the plan-parsing regular expressions were written against the Spark web UI's rendering, and neither of the two engines in use writes plans in that shape.

28. RECORD EVERY FINDING IN A DURABLE LEDGER. Appends each finding with a stable identity, so the same problem can be tracked across days. Trigger: every sweep. Fires in prod: 2,126 rows, 13 sweep dates, 15 distinct detector types.

29. TRACK EACH FINDING'S LIFE: NEW, RECURRING, CHRONIC, RESOLVED. A finding on its second sweep is 'recurring'; on its third, 'chronic'; absent for three sweeps, 'resolved'. Trigger: every sweep. Fires in prod: 308 recurring, 923 chronic, 54 applied. One documentation gap: the module's own comment lists seven states while the code writes nine.

30. FREEZE RESOLUTION ON A PARTIAL SWEEP. If any download failed, the sweep still reports findings but may not conclude anything stopped happening, because you cannot infer a fix from a job you never looked at. Trigger: every sweep. Fires in prod and has already earned its keep: during the six-day download outage the visible fleet fell from 65 DAGs to 20, and this guard is the only reason 30 untouched DAGs were not published as 'fixed'. Resolutions were zero on all six frozen days and 158 on the first healthy day after.

31. REFUSE TO PUBLISH A COMPLETELY EMPTY SWEEP. If nothing at all downloaded, the job fails rather than publishing. Trigger: every sweep. Never fired. Design weakness: it sums both download paths, so a total failure of the archive half is masked by the history-server half, which is exactly what happened during the six-day outage.

32. STAMP SHIPPED FIXES ONTO FINDINGS. A manifest links pull requests to findings so the ledger knows which problems had a fix applied and when. Trigger: every sweep, plus a hand-run command. Fires in prod: 87 findings carry a fix, across 8 pull requests.

33. KEEP MEASURING A FIXED JOB AFTER ITS FINDING DISAPPEARS. When a fix works, the finding vanishes and takes the hours with it, so the sweep writes an hours-only row to keep the after-measurement alive. Trigger: a DAG with a shipped fix and no finding this sweep. Fires in prod: 11 rows on 2026-09-04 and 09-05.

34. MEASURE SAVINGS WITH A STATISTICAL GATE. Compares executor-hours before and after each shipped fix, requiring three days of data on each side and a 90% confidence interval clear of zero before claiming any number. Trigger: every sweep. The report publishes daily; the measured savings total is zero and has always been zero. 64 tracked fixes, all 'watching', every hours-saved cell a dash. The current blocker is a cold start that will age out, but the next blocker will be that jobs with flat runtimes can never produce an interval at all.

35. COST PROFILING ON THREE MORE SURFACES. Separately measures BigQuery slot-hours by DAG and task, Kubernetes pod CPU and memory against what was reserved, and Databricks job costs in DBUs and dollars. Trigger: every sweep, each isolated so one failing does not stop the others. All three fire in prod, contributing 92 of 2,126 findings. Databricks is the newest, four days of data, and produced the single largest dollar finding.

36. WORK OUT WHAT A COMPUTE-HOUR ACTUALLY COSTS. Derives a blended rate from the billing export rather than hardcoding one, falling back to a default if the query fails. Trigger: every sweep. Fires in prod.

37. REPORT WHICH ACTIVE DAGS COULD NOT BE SEEN AT ALL. Lists every DAG in the deployment and marks which ones the sweep never got a log for. Trigger: every sweep. Fires in prod and is the honest counterweight to the fleet numbers.

38. WRITE THE DIGEST: WHAT CHANGED. Not a list of everything wrong, but what is new, what recurred, what is chronic, what stopped, and which shipped fix each change is attributed to. Trigger: every sweep. Fires in prod, published daily and posted to Slack as a parent message plus one thread reply per DAG, capped at the eight worst.

39. PUBLISH NINE FILE FAMILIES TO CLOUD STORAGE, IN TWO PASSES. Everything else first, then the digest, so the digest can cite the addresses of files already uploaded. Uses the older storage tool deliberately, because the newer one corrupts compressed files in transit. Trigger: end of every sweep. Fires in prod, daily, unbroken.

## Shared plumbing

1. SERVICE-ACCOUNT IMPERSONATION. All three scheduled jobs switch to a dedicated, narrowly-permissioned cloud identity before any cloud call, so neither tool ever runs as the deployment's own broad identity. Two separate accounts on purpose: the debugger needs read access to a second project for Vertex AI, the optimizer needs BigQuery and monitoring. Merging them would hand each tool access it does not use. Fires in prod. Not covered by any test, so a typo in an account name would ship silently and surface days later as a confusing permission error.

2. THE ONE CREDENTIAL THAT COULD NOT BE ELIMINATED. Moving both tools into Airflow removed every API key except one: the Astro deployment token, needed to list task instances and read task logs, which live in the vendor's store and cannot be reached by a task's own scoped credential. The debugger has no local alternative; its whole input depends on this. Absence is treated as a skip, not an error.

3. CLOUD STORAGE AS THE DATABASE. Neither tool has a database. Every piece of durable state is a file in one bucket: the debugger's day reports, delivery markers, cycle bookmark and unexplained-log archive; the optimizer's finding ledger, stage-metrics history, savings log and six dated reports. The optimizer downloads its own history at the start of each run and republishes it at the end, over the same filename, in a bucket with no version history.

4. HAND-ROLLED AUTHENTICATED UPLOADS. The standard command-line storage tool does not authenticate inside these worker pods, and its bulk-copy mode was landing 2 files out of 194. Both tools now mint a token and make direct API calls instead. One path still uses the old tool (the history-server log copy) and works only because it copies one directory at a time; treat it as borrowed time, not a proven exception.

5. SLACK DELIVERY, CREDENTIAL-GATED. Both tools post to Slack through the same token, both degrade to a logged no-op if the token or channel is missing, and neither ever raises from a Slack failure. Credentials are passed on standard input rather than the command line, so they never appear in a process list.

6. CREDENTIALS KEPT OUT OF PUBLISHED TEXT. Cloud tool errors often echo the authenticated account name; both tools scrub that before anything reaches a report.

7. PER-STEP FAILURE ISOLATION. Every optional sub-report in the optimizer, and every deep dive in the debugger, is wrapped so one failure degrades that section rather than the run. This is why the tools are robust and also why they can fail silently: several of the never-fires findings below are exactly this pattern swallowing a configuration error.

8. THE DEGRADATION GUARDS. Both tools carry a version of the same idea: when acquisition was incomplete, keep reporting but stop drawing conclusions from absence. The optimizer's version works and has been proven under a real outage. The debugger's equivalent, its extraction canary, is mathematically unable to fire.

9. THE TEAM DAG WRAPPER. All three scheduled jobs go through the shared team configuration so their own failures alert like any other pipeline. Verified that this wrapper does not silently drop the timeouts and retry settings each job sets.

10. DEDICATED CONTINUOUS INTEGRATION. Each package has its own test workflow, path-filtered so it runs only when that package changes, plus a separate check protecting the tag list the debugger filters on. This path-filtering is also why extracting shared code between the two packages is not a free win: shared code would sit outside both filters.

11. A SECOND COMPLETE COPY OF BOTH TOOLS. The workspace holds a full, drifted copy of each package alongside the deployed one. They are not forks of each other: the deployed bundle has ten modules the copy lacks, the copy has five the bundle lacks, and of the shared files most have drifted, one by 309 lines. Three scheduled laptop jobs run against the copy. One of them re-diagnoses the same failures the production job diagnoses and reaches a different verdict, with no reconciliation.

12. THREE LAPTOP SCHEDULED JOBS. A 10:00 diagnosis run (works, duplicates the production job, disagrees with it), an 11:00 optimizer run (downloads 1.8 GB and then crashes on startup, every run, for eleven days), and a noon gap check (works, and depends on modules that exist only in the workspace copy). None of these is documented as production, and all three are currently loaded and firing.

## Cut list, most simplification first

1. 1. THE LAPTOP OPTIMIZER CRON. What it is: a scheduled job that runs at 11:00 daily, lists and downloads the newest 200 Spark event logs, then dies at startup before reading any of them. Evidence it is dead: nine identical crashes in its log, each immediately after 'pulled 200 logs'; last useful output 2026-08-26; the production job has published every day since. The crash is a Python version mismatch, not a code bug - the schedule's search path resolves to an old system interpreter. Cost of removal: none in output. Roughly 1.8 GB of daily cloud egress stops. One command unloads it. Note that unloading it does not fix the underlying copy, which is also broken for hand-running.

2. 2. THE LAPTOP DIAGNOSIS CRON THAT DISAGREES WITH PRODUCTION. What it is: a 10:00 job running the workspace copy of the debugger over the same failures the production job diagnoses at 10:00 PT, producing a second, different verdict. Evidence: on 2026-09-05 it wrote 9 diagnoses to the production job's 14, 8 overlapping; on one shared failure it says 'late data / missing partition' where production says 'vendor OpenAI batch cohort', because the workspace copy lacks a pattern the deployed one has. Cost of removal: real and under-appreciated. Its accumulated raw log archive is the regression-test corpus, it is not committed to version control, and the production job uploads only unexplained logs, so this cannot be replaced by the deployed tool. Recommendation: point the laptop script at the deployed package rather than deleting the job. That ends the two-verdict problem and keeps the corpus.

3. 3. THE SECOND FULL COPY OF BOTH PACKAGES. What it is: complete, drifted duplicates of both tools in the workspace. Evidence of divergence: the deployed bundle has ten modules the copy lacks; the copy has five the bundle lacks; shared files differ by up to 309 lines. Cost of removal: this is a migration, not a delete. Three laptop scripts and fifteen ticket artifacts import the copy, and four modules exist only there. Sequence: fix the interpreter, move the four unique modules into the bundle or into standalone scripts, then collapse to one copy and repoint everything.

4. 4. THE TROUBLESHOOTING PACK AND THE PERFORMANCE BRIDGE BEHIND IT. What it is: a full paste-ready write-up assembled on every single diagnosis, plus the performance profiling that feeds one of its sections. Evidence: computed at least 197 times; no production path reads it; the string does not appear in any of 30 published files or in 301 local diagnosis files; the only automated caller declines it. The performance bridge behind it cannot fire at all - two of its three trigger patterns have never matched a real failure and the third is misspelled and does not exist in the catalogue. Cost of removal: about 100 lines plus a 70-line module and its tests. The pack is genuinely useful when run by hand from the command line, so make it something the command line calls rather than something built and discarded every time. The bridge does real work (it downloads an event log with a 300-second timeout) so it is the more valuable half to remove or repair.

5. 5. THE AI FALLBACK REMNANTS. What it is: a branch that tries to call a language model when pattern matching finds nothing. Evidence: the module it imports is deliberately not shipped, so the import always fails; company policy forbids the key on a production worker; both scheduled jobs disable it explicitly. Cost of removal: about 35 lines, safely, keeping the command-line flag and the parameter so a documented command and a passing test keep working. Also fix the package export list, which currently names the missing module and breaks a wildcard import.

6. 6. THE OWNER AND COMPUTE-UNIT COLUMNS ON EVERY LEDGER ROW. What it is: two fields on all 2,126 finding rows plus a second full pass over the ledger to compute a before-and-after cost comparison. Evidence: no caller has ever passed either value; both fields are empty on all 2,126 rows; the second pass skips every row and does nothing; the digest therefore always prints the literal word 'unowned'. It was flagged as dead in a code review, and shipped anyway. Cost of removal: two fields, two parameters, a daily full-ledger rescan, two always-blank report columns, three test call sites. Nothing downstream reads either column.

7. 7. THE DATABRICKS PLAN-ANALYSIS HALF. What it is: pulling the heaviest recent warehouse queries, asking the engine to explain them, and running five detectors over the result. Evidence: all four published reports end with the identical sentence 'No statement in the window produced a plan the detectors could read.' Cost of removal: about 75 lines exclusive to Databricks. The detectors themselves are not unvalidated - three pass against a real plan captured by hand, and one fired on real tables in a manual test - what has never worked is the automated plan acquisition. Recommendation: give it a two-week deadline to produce one real plan, then delete the half if it does not.

8. 8. THE CACHE-EFFECTIVENESS SURFACE. What it is: tracking cached data and evictions in the event-log parser, feeding one detector. Evidence: measured across 15 real production logs, zero of the required events appear, because the Spark setting that emits them is not enabled anywhere in the fleet. The detector has zero findings in 2,126 rows. Cost of removal: three parser fields, one detector, three tests, and it removes the capability from both tools. The alternative is enabling the Spark setting fleet-wide, which inflates log size against an archive where the download cap already binds and 6% of objects are already unreadable. Recommend deleting rather than enabling.

9. 9. THREE TRIVIALLY DEAD FUNCTIONS. What they are: the optimizer's single-post Slack sender (superseded, and in fact shipped dead in its first and only commit), a whole-word name matcher in the debugger's Slack module that was written in the same commit that rejected name matching, and a coverage file-writer with no caller that would additionally write to a nonsense path if anyone called it after publishing. Evidence: no caller in any commit in history, for any of the three. Cost of removal: 12, 3 and 7 lines. Zero.

10. 10. THE REST-API COVERAGE COLLECTOR. What it is: a second way to enumerate DAGs, over the web API, alongside the in-process one that actually runs. Evidence: the scheduled job hardcodes the local path; the API path is reachable only from a command line. Cost of removal: about 70 lines and two environment variables. Important caveat: two of its helpers and two of its environment variables are NOT dead - the live path falls back to them for the paused-DAG list on every sweep. Cut the collector, keep the helpers.

11. 11. THE CONTAINER IMAGE FOR AN ABANDONED PLATFORM. What it is: a Dockerfile packaging the optimizer for a container platform. Evidence: one commit, never modified, never built, no CI in that repository, and an explicit written decision in the improvements backlog saying the container path was built and deleted. Its own header comment describes secret-loading behaviour that does not exist in the code. Cost of removal: none. Do not delete the shell script beside it - that is the laptop job's program.

12. 12. THE PINNED-ADDRESS NETWORK BYPASS. What it is: about 135 lines routing around a home network's DNS blocker when reading cloud logs, including an address validator, a DNS shell-out and a second HTTP client. Evidence: it cannot succeed on a production worker, because the command it needs is not installed in the image and the credential type it needs is not the one the job uses. Zero mentions across all 15 published reports. Cost of removal: 135 lines and five tests. One shared helper inside that block must survive - the Vertex dive imports it for a live path.

13. 13. FOUR GENUINELY SPECULATIVE FAILURE PATTERNS. What they are: patterns for concurrent Delta writes, shuffle out-of-memory, shuffle fetch failure and schema drift. Evidence: no incident record, no live emitter in the codebase, no caller, no ordering role, no match in 3,743 real logs. Cost of removal: negligible. Do NOT cut the other ten commonly cited as dead - four have live callers or were written from real unexplained failures, three are tied to dated production incidents whose logs simply aged out of a 7-day retention window, and one exists specifically to exclude a benign message that once caused a human misdiagnosis.

## What a fresh full audit should settle

- Why do 117 of 197 failures produce no engine at all, and 49% produce no pattern match? Is that the fleet's real shape, or is the parser missing a common log format? This one number governs how much of the deep-dive machinery is worth keeping.
- Why did a Dataproc job that was killed by its time limit on a DAG the sweep already covers never become a diagnosed row? The detector works when re-run today. Something upstream of it is dropping the failure.
- Is a Databricks credential going to be provisioned for the debugger, or should that dive be deleted? It has run 11 times in production and returned nothing every time. The answer is one decision, not an investigation.
- What is the real target for time-to-answer? If minutes is right, the 15-minute schedule and the instant trigger are both justified. If an hour is fine, the recorded plan to stretch the schedule makes the instant trigger the thing to keep and the schedule the thing to relax.
- Should the Spark setting that emits cache statistics be enabled fleet-wide? Enabling it makes one detector live at the cost of larger event logs against a download cap that already binds. Not enabling it means deleting the detector. Either is fine; keeping both is not.
- What should the savings engine say about a job whose runtime never varies? Three tracked jobs are in that state and can never produce a confidence interval, so they will report 'unmeasurable' forever unless the design changes.
- Does the incident history the debugger cites on 86% of diagnoses get wired to sync, or does the staleness alarm come down from 45 days to about ten? It is currently seventeen days stale with no alarm and no sync path.
- How many of the 461 permanently-unfinished logs in the archive belong to the jobs that matter most? They are skipped silently, and if they skew toward long-running or crashed jobs the fleet numbers are biased in a way nothing currently measures.
- Which team owns the sibling DAGs the history-server filter excludes by an over-strict name match, and should they be included? That is 22 jobs a day, from the same repository, dropped every sweep.
- Should the two packages share their common Slack and storage helpers? The duplication is small (about 20 lines) but the two test workflows are path-filtered, so shared code would sit outside both and neither suite would run when it changed. This needs a CI decision before a refactor decision.
- Is anyone reading the digest? The six-day download outage printed 'Partial sweep' into the digest and the Slack post every day for six days and went unnoticed. That is an attention problem the tools cannot fix themselves, and it determines whether more alerting is worth building or whether it would be equally unread.

## Method

101 agents across four lanes (debugger functions, optimizer functions, shared plumbing, what is dead). Every function claim was checked by an independent default-refute verifier against the source line and against live prod evidence — the ledger, GCS artifacts, or a test that exercises it. A capability with no reproducible evidence of firing is marked as such rather than assumed working.
