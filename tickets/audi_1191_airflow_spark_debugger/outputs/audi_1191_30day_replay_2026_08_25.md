"no error text" and hides a real gap. Selecting the member with the *longest* error text instead
changed the gap analysis completely. A replay harness that silently samples the wrong member looks
identical to a clean result.

### 3c. The four gap classes, characterised

Reading those logs by hand groups them into four causes, each with a different fix.

**G1 — the exception never reaches the log.** `mntn_match_verticals_precache_v1_1/pre_cache_verticals`
(6) and `databricks_guid_geos/run_databricks_job` (2). Both end on
`[error] task Task failed with exception` with **no payload after it** — the traceback is absent
from the log entirely, not merely unmatched. No signature can fix this; the verdict has to become
"the exception did not serialise, fetch it from the owning system", and for the Databricks one the
run id extractor should be finding a handle and is not.

**G2 — a reschedule-mode sensor whose log ends mid-poke.**
`fangorn_inference_pipeline_run/wait_for_challenger_features` (216 KB, thousands of poke lines) and
the same shape elsewhere. The log's last line is `Rescheduling task, marking task as
UP_FOR_RESCHEDULE`, so the `AirflowSensorTimeout` the `sensor_timeout` signature looks for is in a
**different try**. The task is `failed`, the log looks like a healthy poke loop, and the classifier
correctly finds nothing. Needs a signature keyed on the poke loop plus the terminal state, not on a
timeout string.

**G3 — the task was killed by an Airflow control-plane outage, and this one is already root-caused.**
`audience_intent/wait_for_ipdsc_geo` at 2026-08-19 **06:38–06:39Z** sits exactly inside the
Astronomer database maintenance window (06:36:45–06:42:14Z) that produced 122 heartbeat
`500 Internal Server Error`s — Astronomer support ticket #98048. The task did not fail; its
heartbeat did. **This is the highest-value signature on the list**: Astronomer confirmed the class
recurs (they have an internal issue open for customer-managed maintenance windows), it hits many
tasks at once, and the correct verdict is "not your DAG, re-run once the instance is back" rather
than any code change. Detection: a cluster of tasks dying within seconds of each other with no
exception, or the `psycopg2.OperationalError` / PgBouncer signature if the log carries it.

**G4 — reporting defect, not taxonomy.** The `tpa_ipdsc_export` group (10 logs) DOES extract a
Dataproc batch handle, so it routes correctly — but the batch has aged out and the report surfaces
the raw `ERROR: (gcloud.dataproc.batches.describe) NOT_FOUND ... This command is authenticated as
malachi@mountain.com` string. That is both unhelpful and leaks a personal identity into the output.
It should read "batch expired, evidence no longer retrievable".
