# DeepSeek Harness Plugin System Theory: Cordis / "A Programming Paradigm for Spatiotemporal Composability"

Sources: paper PDF (Shi, Zhang, Cui; Peking University & DeepSeek-AI, draft, 88 pp.) at https://github.com/cordiverse/paper/raw/main/paper.pdf; repo README at https://github.com/cordiverse/cordis (self-describes as "A Meta-Framework of Spatiotemporal Composability", API "not yet stable", pointing to the paper and to the primer at https://deepseek-harness.github.io/deepseek-harness/reference/cordis-primer); tutorial at https://deepseek-harness.github.io/deepseek-harness/en/develop/cordis-tutorial/. DeepSeek Harness vendors Cordis as its plugin framework; "every capability — tools, LLM adapters, file access, the agent loop itself — is a plugin mounted into a shared context" (tutorial). Koishi (the paper's case study, §5.3) uses the term *plugin* for what the paper formalizes as *component*.

## 1. The two dimensions and their runtime mechanisms

The paper identifies two orthogonal dimensions of dynamic composition (§1.1):

**Temporal composability** = the ability to completely and safely revert a component's modifications to the shared environment upon removal. Mechanism: **revertible effects** (§3.1). An effect is modeled as a function `Γ → Γ × (Γ → Γ)`: applied to the current context it yields the modified context *plus an explicit inverse*. The runtime pairs the context with an **accumulator**: the effect context is `∂Γ := Γ × (Γ → Γ)` (Def 2), a pair (γ, φ) where φ is the composite of the inverses of all effects performed so far. `track(f,g)` applies f and composes g onto φ (Def 3, a monoid homomorphism, Thm 5); `recover` applies φ and resets it to id (Def 6); the **soundness invariant** is φ(γ) = γ₀ (Thm 7). The refined **witnessed effect functions** 𝔈\*Γ (Def 8) choose their inverse *per state*, with the witness constraint g(δ) = γ (the inverse reverts the effect at the state where it was applied); `effect` lifts 𝔈Γ to 𝔈∂Γ (Def 12) — undoing an effect is itself an effect, giving a self-similar ∂-tower. Reverting in LIFO order needs no assumptions (Thm 16); reverting out of order or across interleaved components requires **independence** — commuting transformation monoids (Def 17, 19; Thm 20; Cor 21: pairwise-independent effects can have their inverses applied in any permutation and still reach γ₀).

**Spatial composability** = the ability to declare, discover, and resolve inter-component dependencies reactively. Mechanism: **reactive coeffects** (§3.2). The coeffect context is a typed dependent partial function `Σ := (k : K) ⇀ V_k` (Def 22) — the paper explicitly formalizes IoC containers this way. Crucially, `set(k,v)` has type 𝔈\*Σ, i.e. *coeffect provision is itself a revertible effect* ("coeffect operations are effects, and effects are revertible" — the stated synergy of the two mechanisms, §3.2.1). A component declares a **coeffect specification** d ⊆ K (Def 25); the **satisfaction predicate** σ ⊨ d (all declared keys present, Eq 24) is decidable, and every context transition is classified by `notify_d(σ,σ')` as **activating / deactivating / neutral** (Def 26). The reactive invariant: an activating transition triggers execution of the component's effects (with full tracking); a deactivating one triggers recovery by applying the accumulator. Two extensions (§3.2.3): **coeffect isolation** (realm table ρ; the same key resolves to different bindings in different contexts — "runtime ad-hoc polymorphism", Def 28–29) and **coeffect interception** (a metadata monoid per key, merged right-biased so an enclosing context can override a component's declaration without modifying it, Def 30–31). Both use *derived realization*: they derive a child context, so recovery is just discarding it — no inverse to run (Def 27).

## 2. The unified context type; effect tracking, coeffect resolution, config reconciliation, HMR

**Unified context** (§3.3.1): `Γ∞ := μΓ. Γ × (Γ → Γ) × Σ` (Def 32) — current state, accumulator, and coeffect table in one recursive type. Since the type family V is unconstrained, *any* shared state is encoded as a dependency at a key: "Σ subsumes all shared mutable states, not just inter-component dependencies. Every interaction between a component and its environment passes through this single entity." The recursion gives hierarchical composition — a literal "plug-in" metaphor: loading = executing effects; unloading = recovering them without affecting other components; a parent aggregates its children's effects. Recovery is claimed only up to an **observational equivalence** ≃ assembled from per-key indistinguishability under each key's published operations (§3.3.2, Def 33–37) — e.g. heap layout after malloc/free and generative names lie outside the relation. This quotient is also what makes **independence** attainable: operations at distinct keys are independent outright (Thm 40), and a key is **commutative** when its own operations pairwise commute (Def 39) — a table of independently added/removed entries (event-listener registration) is; an ordered middleware chain is not. Theorem 42: components whose effects are coeffect-mediated at commutative keys are independent, which is what carries temporal composability to a whole system.

**Calculus (§4)**: a *component* is a triple (d, p, e) — dependency spec, **provision** (keys it may provide), and witnessed effect function (Def 43). A *fiber* is an instantiation carrying parent, own coeffect table σ, retirement flag, and lifecycle state (Def 44); the registry is a tree of fibers, and the coeffect context is *derived*, the union of Active fibers' tables (Eq 40) — one provider per key. The lifecycle compares each fiber's **committed view** ω (key → provider fiber recorded at activation) against its **target view** (Def 46, recomputed from the current state): any divergence drives a transition. States `Inactive | Reloading | Active | Unloading` with rules L-Begin/L-Iter/L-Finish (activation as an **effect iterator** — a reified delimited continuation, `yield`-shaped, allowing divert/partial rollback at iteration boundaries, §4.3.2), L-Divert/L-Raise (early exits), L-Leave/L-Unload (deactivation), plus orchestration rules O-Insert/O-Retire/O-Remove (§4.2–4.3). Key ordering machinery (§4.3.1): L-Leave stops the fiber providing (dependents recompute an unsatisfied target and begin their own teardown *while its bindings are all still in place*), and the guard ¬relied_n holds L-Unload — the actual running of inverses — until every consumer has deactivated, so a consumer can read the withdrawn dependency throughout its own teardown. Asynchrony is modeled by **inertia** (§4.3.3): once launched, an iteration lands; transitions run to completion then chain. Failure (§4.3.4): a raise routes through Unloading, so the fiber's effects are recovered, the error is recorded on the fiber (not propagated to the parent — siblings keep running), and the lifecycle is not re-entered from an error outcome. Metatheory (§4.4): preservation (Thm 59); **recovery exactness** (Thm 61: applying a fiber's accumulator yields, up to control fields, the state the interleaved steps of *other* fibers alone would have produced — running an inverse withdraws that fiber's contribution and nothing else); terminal recovery (Cor 62: a departed fiber leaves nothing behind); ordering (Thm 63) and resolution coherence (Thm 64: every iteration of one transition runs against a single resolution); progress (Thm 66: no deadlock, termination — the guard always releases, given acyclic dependency precedence and bounded iterators); **confluence** (Thm 73: the quiescent state is the one a from-scratch static assembly of the final configuration would have produced — unique normal forms; "licenses reasoning about a Cordis application as though it were statically assembled").

**Implementation mapping** (§5.1, Table 2): `ctx` realizes Γ∞. **Effect tracking** (§5.1.1): every context mutation flows through the single primitive `ctx.effect(callback)`; the callback is driven as an (async) iterator yielding inverses, folded into one dispose closure; an `armed` flag makes recovery fire at most once and halts in-flight iteration; the dispose is prepended onto the enclosing context's `ctx.dispose` (LIFO), so a child effect's inverse is itself an effect on the parent. **Coeffect resolution** (§5.1.2): three symbol slots — `@@store` (realm → value), `@@isolate` (key → realm), `@@intercept` (key → metadata); `ctx.get`/`ctx.set` resolve through k → ρ(k) → σ(ρ(k)); `ctx.set` is a `ctx.effect` call (auto-tracked, auto-recovered) and both install and removal call `notify`, which refreshes every live fiber whose `fiber.inject` names a changed key in the same realm. A binding counts as available only while its installing fiber is ACTIVE, so withdrawal is visible one step before it happens. `ctx.isolate(key, realm)` / `ctx.intercept(key, metadata)` derive child contexts; recovery = discarding them. **Lifecycle** (§5.1.3): `ctx.use(component, config)` creates a fiber; the registration itself is a tracked effect of the *parent* fiber, so unloading a parent cascades to children. `refresh` recomputes `fiber.target` (declared keys → providing fiber uids); `reload`/`unload` are mutually recursive and inertial; `reload` commits the resolved view (`fiber.committed`), runs `fiber.apply` via the same iterator engine with a guard testing target stability; `unload` first awaits all notified dependents reaching INACTIVE (the L-Unload guard), then awaits `fiber.dispose()`. Identifying bindings by provider **uid** (fresh, never reused) is what makes replacement propagate: a provider overwriting its own binding in place is *not* observed — it must withdraw and reinstall. **Context access** (§5.1.4): a TypeScript `Proxy` mediates `ctx[key]`, walking the fiber chain: returns the binding from the first fiber whose committed view holds the key; throws `INACTIVE_ACCESS` if a fiber declares it uncommitted, `UNDECLARED_ACCESS` at the root — enforcement of the coeffect spec at point of use (also framed as capability-based access control, §6.3).

**Config reconciliation** (§5.2.1): the loader turns a declarative **configuration tree** of entries `(id, url, isolate, intercept, config, disabled)` into fibers. An entry is a faithful spec because the support set (Def 67) reads exactly τ, π, d, p — all derivable from the entry. Reconciliation is incremental and per-field: `id`/`url` change → rebuild; `isolate` → realm reassignment (Algorithm 7 with per-key delimiter tags deciding whether a binding travels with the entry); `intercept` → updated in place, no reload; `config` → handed to the component to diff (a `@cordisjs/group` entry applies a keyed diff over child ids, recursing); `disabled` → unload/reload. Soundness of doing this incrementally is *supplied by the metatheory*: Thm 73 (final state depends only on final configuration, not the order of loader operations), Thm 66 (reconciliation completes), Cor 62 (rebuilding one entry leaves neighbors untouched), Thm 63 (no load order to arrange — a fiber whose keys aren't provided waits; dependencies constrain activation, not module fetch, so the loader loads modules concurrently).

**HMR** (§5.2.2): `@cordisjs/hmr` applies the revertible-effect pattern at the module level, in three phases: (1) module classification — a fixed point over the import graph seeded with changed files (`stashed`) and un-replaceable modules (`externals`), marking modules `accepted`/`declined` (import cycles left undecided default to declined); (2) stale-entry detection — an entry is stale iff its transitive import tree intersects `accepted`; (3) **transactional reload** — invalidate module caches (with backup), `entry.fiber.dispose()`, re-import by `url`, swap in a fresh fiber; on any import error, restore caches and rebuild every stale entry from backup. "HMR therefore needs no developer-annotated acceptance boundaries, as opposed to Webpack or Vite HMR" — because a fiber already bounds all of its component's effects and coeffects.

## 3. What this buys: why a Cordis plugin is safely hot-swappable and disposable

- **Disposal is structural, not authored**: every mutation goes through `ctx.effect` with an inverse; the composite inverse of a whole plugin is derived by composition, so "a component's teardown is derived from its loading rather than written alongside it" (§3.3.3). Koishi evidence: "even an inexperienced author obtains ordered cleanup for a plugin's context-mediated effects without writing an uninstall path" (§5.3).
- **Exactness**: Thm 61/Cor 62 guarantee running a plugin's accumulator withdraws *its* contribution and nothing else, even interleaved with other plugins' activity; a removed fiber leaves the state as if it had never run.
- **Safe replacement ordering**: dependents are deactivated before a provider's bindings are withdrawn (Thm 63) — teardown code can still read the dependency being withdrawn (e.g. a connection pool handing connections back). Reconfiguring a provider "reactivates only the dependents whose resolved dependency changed; a plugin whose dependency is unavailable stays inactive until it appears, without erroring" (§5.3).
- **As-if-static reasoning**: confluence (Thm 73) means any sequence of loads/unloads/replacements quiesces at the state a from-scratch assembly of the final config would produce — dynamic history leaves no trace.
- **Failure containment**: a failing activation is rolled back (effects recovered), recorded on that fiber alone, siblings unaffected, no blind retry (§4.3.4).
- **Contained restarts**: HMR re-applies edited plugins "while preserving cache state and live connections elsewhere in the system" (§5.3) — vs. the VSCode baseline where removing any of the 87/100 top extensions containing code requires restarting the whole extension host (§1.2.1).

## 4. Practical rules a plugin author must follow

Effects (§5.1.1, §3.3.3, §6.1, Def 48, primer):
- Perform every side effect *through the context* via `ctx.effect(callback)` (or helpers built on it: `ctx.on()`, `ctx.set`, `ctx.use`); the callback returns — or, as an iterator, yields per-step — the inverse. The primer's rule: "ensure every registration has a corresponding disposer from `ctx.effect()` or Cordis helpers."
- Supply a correct inverse for each *atomic* effect only; never hand-write teardown for composites — composition derives it. The **witness** (that the inverse actually reverts the effect) "is an obligation on the component author rather than a property the runtime verifies" (§5.1.1).
- Effects that cross the **system boundary** (§6.1) are not recoverable by inversion: *acquisitions* (open/malloc/fork) should install a revertible record inside the boundary; *emissions* (bytes written to a file, datagrams sent) act as id — only withholding (delay until commit) or compensation is available.
- Don't reach another component's context through closures or globals — an effect installed there leaks out of your lifecycle, a coeffect read there escapes your declaration (§6.7 names this the library-realization hazard).

Dependencies (§4.1, Def 43/48/60/69, §3.3.2, §5.1.3):
- Declare every key you read in `inject` (d); undeclared access throws; declared-but-inactive access throws. Read dependency values through the context; values you read are held fixed while you run (Thm 63(3)).
- Provide only keys listed in your provision (p); write no other key; one provider per key (single-source discipline). Be **total on your provision**: install every key you declare (Def 69 — required for confluence).
- If you provide a key, publish a **commutative interface** where possible (registries where entries add/remove independently — yes; an order-sensitive middleware chain — no); "commutativity of a key is a property of the interface that key publishes, so meeting it is an obligation on the component providing the key" (§3.3.2). Order that matters must be carried by a declared coeffect, not by effect sequencing.
- To propagate a changed provision, withdraw the binding and install afresh — in-place overwrites of your own binding are invisible to dependents (§5.1.3).
- No dependency cycles: a cycle leaves the components involved *permanently inactive* (detectable from declarations; decompose bidirectional interactions into core + integration components, §6.5). No unbounded self-registration (progress requires a bounded registration tree, §4.4.4).
- On config updates, diff against the previous payload and reload only on material change (§5.2.1).

## 5. Comparison with ordinary plugin systems (§1.2.1, §3.3.3, §7)

- **Lifecycle-hook plugin APIs (VSCode et al.)**: `deactivate` is a graceful-shutdown callback at host termination, not live removal; it "separates effect disposal from effect creation, violating locality of concern"; exports are untyped `any`; among the top 100 VSCode extensions only 7 declare `extensionDependencies` on non-built-ins. Cordis pairs each effect with its inverse at creation and types dependencies as coeffects.
- **Developer-authored cleanup** (OSGi/Eclipse/IntelliJ unload callbacks, Command-pattern undo, sagas, event sourcing): the inverse is "an unenforced duty, decoupled from the operation, so that a forgotten one leaks resources silently." React's `useEffect` comes closest but hooks can't be conditional/looped/nested, can't be async or iterators, so no composite inverses; Cordis effects are ordinary composable operations (§7.3).
- **DI containers / middleware context** (Spring, Guice, Angular, Inversify; Vue `provide/inject`, React Context): wire once at initialization; "when a provider is replaced or removed at runtime, existing dependents are neither deactivated nor re-initialized, and none offers lifecycle management." Spring's `getBean` is an untyped service locator. Cordis re-resolves reactively and drives lifecycle transitions off satisfaction changes (§7.4, §3.3.3).
- **OSGi Declarative Services / iPOJO / R-OSGi**: the closest precedent (provide/require with automatic activation on availability), but recovery is a hand-written *synchronous* deactivation callback; Cordis recovery is structural and its inertial Unloading state runs asynchronous teardown to completion before further change (§7.4).
- **FRP/signals**: value-level, glitch-free, synchronous; Cordis is component-level with asynchronous lifecycle and only per-transition resolution coherence — complementary, a coeffect can itself carry reactive values (§7.4).
- **Monadic effect systems (ZIO, Effect-TS)**: tracking requires writing inside the effect type; requirements are discharged by interpretation and stay stale when the service goes. Cordis overlays ordinary host code and re-resolves as providers come and go (§7.1). Effekt's capabilities and Granule's graded modal types are static/lexical; Cordis lifts effects and coeffects to runtime (§7.1).
- **DSU / Erlang `code_change` / webpack-Vite HMR**: migrate state forward with hand-written functions; Cordis instead reverts and reapplies (no migration functions, full unload supported), at the cost that a component's in-memory state doesn't survive a reload unless placed in a longer-lived dependency (§7.3).
- **AOP**: a coeffect is a *declared* mediation point vs. an oblivious pointcut — crosscutting reach is exactly the declared surface, and changes ride the component lifecycle (§7.2). **COP** shares only vocabulary: layers neither track/revert effects nor activate by dependency satisfaction (§7.2).
- The framing insight (§3.3.3): the context paradigm sits between explicit state threading (traceable, unergonomic) and implicit mutation (ergonomic, untraceable) — effects and coeffects both mediated by an explicit context, so "correctness that would otherwise rest on developer discipline becomes a structural property."

## 6. Stated limitations

- Recovery holds only up to observational equivalence ≃, not physical equality (heap layout, generative names) (§3.3.2); ≃ only sees state bound at keys — locations not reified as coeffects fall outside the theorems (§3.3.2 "two limits", §6.1).
- Inverse correctness is unverified by the runtime — an author-supplied obligation (§5.1.1).
- Emissions past the system boundary can only be withheld or compensated; the commutation metatheory does not automatically transfer to compensations (§6.1).
- Confluence excludes failure: whether a step raises depends on the state it ran against, so different schedules may differ in a fiber's failed/active status (though a failed fiber contributes nothing to the rest of the state) (§4.4.5).
- Mutual dependencies leave components permanently inactive; the decomposition fix can grow integration components quadratically — an authoring-burden cost (§6.5).
- Nominal (key-identity) linking only: interface drift and key collision are unsolved; current mitigation is npm peer dependencies, which relies on semver honesty and forbids multiple versions of one package (§6.6, named an open problem).
- Progress requires acyclic precedence, bounded iterators, finitely many fibers (no unbounded self-registration) (§4.4.4).
- Host-language requirements: closures, a module registry or dynamic unlinking, typed context extension (declaration merging/typeclasses/traits), and property-access interposition (Proxy/`__get__`); otherwise runtime reflection at the cost of type safety (§6.4). Language-level access control cannot sandbox untrusted code — an external sandbox is required (§6.3).
- Exclusive provider binding perturbs all consumers on a switch; the service-broker pattern is needed to absorb rolling updates (§6.2).
- Evaluation: the Koishi case study (4000+ community plugins) is a single ecosystem in a single host language, observational not controlled — "an existence-and-adoption result"; overhead and productivity effects unmeasured (§5.3). Koishi runs Cordis v3 while the paper describes v4 (§5.3 fn 4), and the repo warns the API "may change without notice" (https://github.com/cordiverse/cordis).
