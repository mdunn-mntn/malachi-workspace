# AUDI-1321 handoff — corrected plan for dt=2026-09-03 (2026-09-04, second pass)

This supersedes `audi_1321_handoff_2026_09_04.md`. That document's step 2 cannot work, and its
underlying model of the problem was wrong in a way that changes the fix.

## What the first handoff got wrong

**Its step 2 has no delivery path.** `OPENAI_FILE_MAX_AGE_HOURS` set on the Astro prod deployment's
Environment tab never reaches `delete_all_storage_files.py`. The rendered pod spec of the cleanup
task that actually ran (`GET .../taskInstances/batch_cleanup_1`, submit `scheduled__2026-09-03T09:00`)
is `env_vars` = run_date/env/yesterday, `env_from` = `[]`, `pod_template_file` = null. A
`KubernetesPodOperator` builds a fresh pod and copies nothing from the worker environment.
`MntnKubePodOperator` mounts exactly one key (`OPENAI_API_KEY`) out of the `env-secrets` secret,
which is why that variable has to be mapped explicitly even though it is already a deployment
variable. The same gap applies to `STORAGE_ALARM_MIN_FILES`: the deployed image reads it, nothing
passes it, so it has always fallen back to its default. Neither name appears anywhere in
`airflow-ti`. Confirmed against `origin/main`, not just the local checkout.

**Its premise that a window change alone would unblock the day was never tested against sizes.** One
day is ~1,014 input files at ~40 MB each (40.3 GB for dt=2026-09-02, 40.1 GB for dt=2026-09-03) plus
~46 GB of results. At a 48h window our entire footprint should sit near 100 GB. The project is at
2.5 TB. **Roughly 2.4 TB of the ceiling is not this pipeline's.** No retention value we choose
touches it.

**That does not matter for the unblock, which is the useful surprise.** `batch_submit` dies on the
first 40 MB `files.create`, so it needs about 40 GB of headroom, not 2.4 TB. Freeing dt=2026-09-02's
inputs is enough. That is exactly what the 2026-09-03 sweep did when it deleted 1,132 files and the
submit went green minutes later: it bought one day of headroom, not a clean account.

**A third defect explains why the sweep looked healthy.** The paging loop ended on any page shorter
than its 10,000 limit (`if too_young or len(files) < PAGE: break`), so it acts on a prefix of the
store rather than the store. On 2026-09-04 it reported 28 files four minutes before `batch_fetch`
downloaded and deleted 416 output files. The zero-delete alarm from #305 could never fire either:
its threshold is 10,000 files and `seen` never exceeded 4,623.

## Correction to the "known false failure" note

`batch_test.test_product_categorization` failing on a backfilled day is **not** always the wall-clock
`max_dt` test. On fetch `scheduled__2026-09-03T09:00` it was `product_categorization__record_count`,
and it was correct: `manual__recover3` wrote dt=2026-09-02 at 05:11 from a partial join, today's
`batch_fetch` then landed 415 more completed batches, and the partition was left at 12 files / 408 MiB
against ~53 / 4.0 GiB on a normal day. `product_categorization__max_dt` passed on that same run.
`product_categorization.py` is `incremental_strategy="append"` and raises `FileExistsError` while the
partition has data, so it cannot self-heal: the partition must be deleted first. Backed up to
`gs://mntn-data-archive-prod/_backups/audi_1321/product_categorization_dt=2026-09-02_20260904/`
(12 objects, 427,873,211 bytes), deleted, and the task cleared to rebuild.

**Check which assertion failed before marking that task success.** Marking it green is what let the
short partition through, and `keyword_ddp_reporting manual__consume_dt_2026-09-02` consumed it, so
that run needs repeating once the rebuild lands.
