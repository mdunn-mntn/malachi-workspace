## Cap-arm write path (B/C) — CONFIRMED feasible with new bidder code, NOT config-only

- **The cap is per-campaign, not per-household.** `do_fcap` builds each `Campaign` from the candidate's `CampaignModel`: `campaign_frequency_caps` / `campaign_group_frequency_caps` (`campaign/fcap.rs`). `check_freq_cap_threshold(campaign_frequency_caps, campaign_group_frequency_caps, impressions, now)` (`fcap/src/check.rs` L41) applies those caps *identically to every household* — **confirmed in code**.
- **The household enters only as a counter/recency key, never as a cap selector.** In `check_frequency_cap` (`fcap/src/lib.rs` L119) the household id is used solely to (a) fetch `recent_cgids` via `fetch_recency_for_all(&household_id)` and drop recently-seen CGIDs (`FrequencyCapReason::Recency`, L136–186 — per-household, but a suppression flag, NOT a cap selector), (b) key the Redis frequency store `rtb:frequency:{ip}:campaign_group_id=<cg>:campaign_id=<c>` (`fcap/src/connection/impression.rs::campaign_key`; per-key Redis err = fail-open), and (c) fetch that household's impression timestamps. Nothing maps a household → a cap value — **confirmed in code**.
- **The fcap key is ALWAYS the IP — even when `uses_mntn_id=true`.** `bidder-core/src/request.rs`: `enum HouseholdIdentifier` is `Ipv4` / `Ipv6` / `Both` only (L360–363) — **no MNTN-id variant** — and `household_id_for_fcap()` returns IPv4 (IPv6 fallback) in every arm (L398–405). `uses_mntn_id` drives candidate fetch + holdout routing, never the fcap key — **confirmed in code**. *(Favorable for the RCT: an IP-based arm hash is consistent with the always-IP fcap key. Scope §3's "MNTN-ID only when `uses_mntn_id`" is an upstream error to correct.)*
- **The DB→cache path cannot carry a per-household cap.** The cached `CampaignModel` (`bidder-core/src/campaign_model.rs`) exposes only `campaign_frequency_caps` / `campaign_group_frequency_caps` (+ `advertiser_id: u32` L35, `uses_mntn_id: bool` L58) — **no per-household cap field** (L31–70). So editing `bidder.frequency_caps` / the campaign-cache sync cannot assign different caps to different household buckets — that config is per-campaign/per-campaign_group only. **Config-only foreclosure = confirmed in code** (was "inferred").
- **Therefore B/C need a new bidder feature** in the fcap path: compute the household's bucket, map bucket→arm→cap, and pass the arm's cap into `check_freq_cap_threshold` in place of the configured cap. The insertion point is `do_fcap` (bins) before building each `Campaign`; `check.rs` (lib) needn't change. `advertiser_id` IS on `CampaignModel`, so the arm hash is computable there. Small, localized, `@SteelHouse/rtb`-owned — **inferred from the code above**.
- The holdout/`holdout_cids` path (below) can't carry the arm either — it's binary suppress/serve per campaign, not a 3-level cap.

## Suppression arm (H) — feasible as a new feature reusing the ghost path, distinct from the existing holdout

- **A live suppression+logging mechanism already exists.** The bidder reads per-household `holdout_cids` from the Aerospike household profile, routes them (`campaign.rs::route_holdouts_by_source`), splits held-out bids off the served set (`apply_response_cap_split_ghosts`, `campaign/bid_response_cap.rs`), and in `process_ghost_bids` tags the would-have-won survivors with `BidDroppedReason::GhostBid` (`to_log()` = `"ghost-bid"`), then **runs them through `do_fcap_bid_event(fcap, ghost_cgids, req)`** ("Fcap as if really bid — same intent as do_fcap_bid_event on served reals," `campaign.rs` L423–427) and writes a bid-event log for downstream lift — **confirmed in code**.
- **The existing ghost holdout DOES accrue counterfactual frequency — it is NOT "frequency-unaware."** Because held-out ghosts pass through `do_fcap_bid_event`, this MNTN/Rust leg writes the counterfactual to the fcap store and throttles the holdout like a served IP. The bias register accordingly notes bias **A1** (frequency-cap asymmetry) is **structurally REDUCED on the MNTN/Rust leg** (A1-present is the Beeswax/JVM leg) — **confirmed in register + code** (`ghost_bid_lift_bias_register.md`; `campaign.rs` L423–427).
- **But the existing ghost holdout is still the wrong instrument for this RCT** — for two reasons that have nothing to do with frequency-awareness: (i) it is a **binary suppress-ALL-held-out-campaigns** holdout — the *selection* is frequency-blind and it serves zero impressions on a held-out campaign, whereas arm H needs **cap-aware PARTIAL** suppression (serve up to the counterfactual cap, suppress+log only the would-be-over-cap impressions); and (ii) its assignment is a **fixed ~10% (design; empirically ~16%, 753K/(753K+3.95M)/day per `data_knowledge.md`) `MD5(advertiser:ip) mod 1000 < 100`** bucket computed **upstream** (Aerospike profile, `holdout_cids`), **not a per-test tunable** — **confirmed in code + KB**.
- **A cap-aware arm H is feasible but is a new feature.** It fits the same code path — reuse `GhostBid`, `apply_response_cap_split_ghosts` / `process_ghost_bids`, and the `do_fcap` counters — all `@SteelHouse/rtb`-owned, and must coordinate with the ghost-bid lift pipeline (Matt Brorby). Treat as optional/Phase-2, not a blocker on B/C — **inferred from the code + register**.

## Hash-consistency requirement (load-bearing for the B/C bucket computation)

- Scope §6 randomizes by **`FARM_FINGERPRINT(advertiser:ip) mod 1000`** (a BigQuery function). The existing bidder holdout uses **`MD5(advertiser:ip) mod 1000`** computed upstream. For the RCT's arm assignment to be valid, the **bidder-side bucket computation must bit-match the BQ-side analysis**. Options: **(a)** reimplement BigQuery's FarmHash-Fingerprint64 in the Rust bidder, or **(b)** use `MD5` on both sides. The RCT design (Step 2) and the bidder change must pick one before implementation — **flagged; unresolved**.
