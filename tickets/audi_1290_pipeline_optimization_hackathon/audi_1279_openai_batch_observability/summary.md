### 3.1 Design (recommended defaults; §"Decisions" lists what the user may override)
- **Alarm mechanism:** raise `DeadCohortError` inside the `batch_fetch` pod → task fails → existing routing posts Slack `#monitor-emr` + emails the ML squad after the 4 retries (each retry re-checks OpenAI, so a cohort that wakes up clears itself). No new Slack/PagerDuty wiring, no DAG change.
- **Dead cohort:** receipts for `dt=yesterday` non-empty, `was_submitted` all False, every batch's live status ∉ {`in_progress`, `finalizing`, `completed`} AND `request_counts.completed == 0`, AND the youngest `batch_submit_time` is ≥ `DEAD_COHORT_MIN_AGE_HOURS` old (env var, default **12**; the scheduled fetch always runs ~24 h after submit, so the threshold only guards a manually triggered early run). Below the threshold: print a WARNING line, do not fail. `expired` with `completed > 0` counts as progressed (partial output exists).
- **Status logging:** one line per batch at every check, in both scripts, `flush=True`: `batch=<id> file=<s3_filename> status=<status> submitted_utc=<t> age_h=<x.x> counts=<completed>/<failed>/<total> error=<code>: <message>` (error from `batch.errors.data[0]`, empty when none), plus one summary line `cohort dt=<D>: n=<N> in_progress=<a> finalizing=<b> completed=<c> validating=<d> failed=<e> expired=<f> cancelled=<g> retrieve_error=<h> flagged_now=<k>`. A `retrieve` exception (404, 401, network) becomes `status=retrieve_error error=<exception>` and never aborts the loop.
- **Transitioner flag:** also mark `was_submitted=True` on `finalizing` (OpenAI has accepted the batch; today only `in_progress`/`completed` flag).

### 3.5 Risks
- Daily red `batch_fetch` (and Slack `#monitor-emr` noise) every day the org-side outage continues; downstream `batch_post` already fails on those days, so no new data loss. Mitigation is AUDI-1301, not this PR.
- With `retries: 4` and backoff to 45 min the Slack post arrives 1-2 h after the first detection; each retry re-queries OpenAI, so a late-waking cohort self-clears.
- Slack text is generic (`Pod ... returned a failure`); the cause is in the task log. Follow-up (separate airflow-ti PR, not this ticket): add an `openai_dead_cohort` signature to `include/airflow_debugger/signatures.py` so the debugger's thread reply quotes the summary line.
- ~1,100 `batches.retrieve` calls per check already happen today; the fetcher's new pass adds a second ~1,100 only on dead days (alive days return early on `was_submitted.any()`).
- Unpinned SDK: a future major bump could rename fields; the guarded retrieve turns that into `retrieve_error` lines and a dead-cohort alarm rather than a crash, which is the safe failure.
- `image_pull_policy=Always`: a prod deploy after 09:00Z lands on the following day's run; two tasks in one run can straddle a deploy.
