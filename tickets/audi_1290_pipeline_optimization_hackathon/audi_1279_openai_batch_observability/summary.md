### 3.1 Design (recommended defaults; §"Decisions" lists what the user may override)
- **Alarm mechanism:** raise `DeadCohortError` inside the `batch_fetch` pod → task fails → existing routing posts Slack `#monitor-emr` + emails the ML squad after the 4 retries (each retry re-checks OpenAI, so a cohort that wakes up clears itself). No new Slack/PagerDuty wiring, no DAG change.
- **Dead cohort:** receipts for `dt=yesterday` non-empty, `was_submitted` all False, every batch's live status ∉ {`in_progress`, `finalizing`, `completed`} AND `request_counts.completed == 0`, AND the youngest `batch_submit_time` is ≥ `DEAD_COHORT_MIN_AGE_HOURS` old (env var, default **12**; the scheduled fetch always runs ~24 h after submit, so the threshold only guards a manually triggered early run). Below the threshold: print a WARNING line, do not fail. `expired` with `completed > 0` counts as progressed (partial output exists).
- **Status logging:** one line per batch at every check, in both scripts, `flush=True`: `batch=<id> file=<s3_filename> status=<status> submitted_utc=<t> age_h=<x.x> counts=<completed>/<failed>/<total> error=<code>: <message>` (error from `batch.errors.data[0]`, empty when none), plus one summary line `cohort dt=<D>: n=<N> in_progress=<a> finalizing=<b> completed=<c> validating=<d> failed=<e> expired=<f> cancelled=<g> retrieve_error=<h> flagged_now=<k>`. A `retrieve` exception (404, 401, network) becomes `status=retrieve_error error=<exception>` and never aborts the loop.
- **Transitioner flag:** also mark `was_submitted=True` on `finalizing` (OpenAI has accepted the batch; today only `in_progress`/`completed` flag).

## 6. Questions Answered
- **Q:** Is the OpenAI-side status reachable from the fetcher, or does the alarm fall back to Airflow timing? **A:** Reachable. `client.batches.retrieve(id)` returns `status`, `errors.data[]`, `request_counts` per receipt (openai 3.7.0 verified), so the alarm is OpenAI-side; the only Airflow-side input is the receipt's `batch_submit_time` for the age.
- **Q:** What does the alarm look like in the log? **A:** N lines `batch=... status=<status> ... error=<code>: <message>`, one `cohort dt=...` summary, then `openai_wrapper.batch_status.DeadCohortError: dead cohort dt=2026-01-01: 0 of 3 batches progressed 30.1h after submit (threshold 12.0h); first error: AuthenticationError: Error code: 401 - ...` (staged run, §4.4). Under threshold: `WARNING: cohort dt=... has 0 of 3 progressed but is only 30.1h old; below threshold 48.0h, not failing`.
- **Q:** Threshold? **A:** `DEAD_COHORT_MIN_AGE_HOURS`, default 12 (user decision). The scheduled fetch runs ~22-24 h after submit, so the default only guards a manual early run.
- **Q:** Does a batch that OpenAI accepted but has not finished count as alive? **A:** Yes: `in_progress`, `finalizing`, `completed`, or any status with `request_counts.completed > 0` (partial `expired` output). `validating` past the threshold counts as dead (the outage cohorts never left `validating`/`failed`).
- **Q:** Does `sys.path.insert(0, <repo>/openai)` in the test shadow the installed `openai` SDK? **A:** No; 16 tests pass with the SDK imported through `batch_base`. A regular site-packages package wins over a namespace directory in the import scan.
- **Q:** Can `malachi@mountain.com` write to `gs://mntn-data-archive-dev`? **A:** Yes (probe and 3 seed receipts written and deleted, §4.1e/§4.5).
- **Q:** Is the outage still live? **A:** Unknown as of 2026-09-03 06:51Z: the dead cohorts were deleted and re-submitted with new batch ids between 04:43Z and 05:41Z (§4.2); nothing here can read the new batches' status.
