Profile a Dataproc Serverless batch from its **Spark event log** when the Airflow task log + `dataproc batches wait` driver output only show the symptom (e.g. "batch was cancelled") not where the wall-clock went. Built for INC-005 (`tpa_mntn_id_export` hit its 3h TTL); the parser is saved at `on-call/incidents/INC-005/eventlog_profiler.py`.

**Steps:**
1. Find the event log: `gcloud dataproc batches describe <id> --region us-central1 --project mntn-prj-prod-00 --format="value(uuid,runtimeInfo.outputUri)"` → the event log is `gs://dataproc-temp-us-central1-<projnum>-<suffix>/<uuid>/spark-job-history/app-*.zstd` (`.inprogress` suffix if the batch was killed). It captures up to ~2 min before a TTL kill.
2. **Download** (heads-up on a macOS gotcha): `gcloud storage cp` can report throughput but write **no file** because Gatekeeper blocks gcloud's `gcloud-crc32c` checksum helper (popup "gcloud-crc32c Not Opened" → click **Done**, NOT Move to Trash, which deletes the helper). Route around it with the storage JSON API: `curl -sS --fail -H "Authorization: Bearer $(gcloud auth print-access-token)" "https://storage.googleapis.com/storage/v1/b/<bucket>/o/<URL-ENCODED-object>?alt=media" -o eventlog.zstd` (encode `/` as `%2F`).
3. **Decompress:** `zstd -d eventlog.zstd -o eventlog.json` (event log is JSON-lines, one Spark event per line; a 55MB zstd → ~1.2GB / ~300K events).
4. **Parse:** `python3 on-call/incidents/INC-005/eventlog_profiler.py eventlog.json` — streams the file and prints per-stage cumulative runtime, shuffle read/write, memory+disk spill, GC%, fetchWait%, task-dur p50/p95/max (skew), FetchFailed count by (stage,shuffle), executor add/remove + removal reasons, job durations, SQL execs.

**Discriminators it surfaces (memory vs compute vs shuffle vs recompute vs infra):** cpu% ≈ runtime → compute-bound; high gc% → GC/memory pressure; high **fetchWait%** + big memory/disk **spill** → shuffle I/O bound from under-partitioning; the **same call-site stage repeated N×** (e.g. 7-9 `json at ...` stages) → uncached-lineage recompute spiral; `executors removed=0` → no executor loss (rules out infra); task max/p50 ratio → skew. **Skew needs a data cross-check (2026-08-07):** duration max/p50 high while per-task read bytes are ~uniform (data ratio ~1x) AND the slow task's CPU is a tiny fraction of its wall (fetchWait 0, GC 0) → an **IO-stalled STRAGGLER on one node, not data skew** — fix is `spark.speculation=true` (quantile ~0.9), NOT salting (AUDI-1194 `intent_score_map`: 13.4x duration, 1.0x data, 5% CPU, 67-min tail; `airflow_optimizer` now has `straggler` + `idle_reserved_executors` detectors for this). Cross-check the batch's `runtimeInfo.approximateUsage.milliDcuSeconds` + `shuffleStorageGbSeconds` good-run vs bad-run (INC-005 fix cut both ~26×). TTL-kill reason is in `stateHistory` → `"Cancelling batch as ttl exceeded"` (the Airflow log omits it).

**Dynamic-allocation pinning (Spark 4, serverless, verified vs apache/spark v4.0.0 source 2026-08-07):** with `shuffleTracking.enabled` (mandatory without an external shuffle service), `ExecutorMonitor.timedOutExecutors()` categorically excludes executors whose shuffle blocks are referenced by a **live job** (`hasActiveShuffle`) — AQE final jobs register upstream shuffles for their whole duration, so a 1-task tail pins the ENTIRE fleet (240/240 held, 0 removed, in the intent_score_map run). `spark.dynamicAllocation.shuffleTracking.timeout` only applies AFTER all referencing jobs end → **it is NOT a mid-query release lever; don't recommend it for tail-pinning**. The real lever is killing the tail (speculation / skew fix). `executorIdleTimeout` is similarly moot while shuffles are live.

**zstd trap (hardening pass 2026-08-07):** real Spark event logs are MULTI-FRAME zstd streams (a 29KB log = 35 frames). A one-shot `ZstdDecompressor().decompress()` or default `stream_reader` returns ONLY frame 1 (~58 bytes) with no error → the log parses empty and looks "clean". Use `stream_reader(fh, read_across_frames=True)` or the `zstd -dc` CLI, and treat a nonzero CLI rc as corrupt, never as empty.

**Event-log shapes in `gs://mntn-data-archive-{env}/spark-events`:** single `app-<id>.zstd` files AND **v2 rolling dirs** `eventlog_v2_batch-<batch-uuid>/events_{1..N}_batch-<uuid>.zstd` (+ `appstatus_*` marker). The batch-fleet logs use the batch UUID (from `batches describe .uuid`), NOT an app- name — find them via the uuid. `airflow_optimizer.eventlog` parses all parts in numeric order (IMP-029 fixed 2026-08-07). macOS download gotcha #2: `gsutil -m cp` can hang forever at 0-byte `.gstmp` files (sliced downloads + LibreSSL) — use sequential `gsutil -o "GSUtil:check_hashes=never" -o "GSUtil:sliced_object_download_threshold=0" cp`. **Bulk (2026-08-26, 3,022 objects):** `gsutil -m cp -I` fed thousands of objects on stdin allocates `.gstmp` files and then sits at **0 B/s indefinitely**, while a single-object `gsutil cp` of the same 20 MB log finishes in 2s. Drive it with `xargs -P 12 -L 1` over one-object `gsutil cp` calls instead (~2.5 files/s, 3,022 objects in ~20 min). Two further traps hit the same day: launching the downloader twice leaves two `gsutil` processes racing on identical `.gstmp` names and BOTH stall at 0 bytes (check `ps -eo command | grep check_hashes` before blaming the network), and the `zstd` CLI **refuses a symlinked input** (`rc=1`), so never build a sample dir out of symlinks.

**Fetch-wait is a MAP-SIDE question, not a partition-sizing one (AUDI-1194 `site_network_hourly`, 2026-08-20).** High `fetchWait%` alone does NOT mean under-partitioning, and the reflex fix can be exactly backwards. Shuffle blocks are served by the executor that **wrote** them, so a reduce stage is rate-limited by how many map-side executors hold the output. Proof from one app: stage 9 waited **73%** on 4.2M blocks @1,753 B while stages 29/35 in the SAME app waited **1s** on 23.4M blocks @1,607 B — 5.5x more blocks, same size. Block count and size were not the cause. What differed: stage 9's map stage ran while dynamic allocation was still at `initialExecutors=50` and landed 90% of its output on **77 executors with one holding 24.6%**; the later map stages ran with 306-500 up and spread across ~480 with a **0.3%** max. Consistent across 4 logs (44-73% fetch wait, always the map stage that starts with exactly 50 executors). **So: before touching `spark.sql.shuffle.partitions`, measure the map-side spread — raising partitions when blocks are already ~1.7 KiB multiplies block count and makes it worse.** Measure it with `artifacts/audi_1194_shuffle_concentration.py` (per-stage `Shuffle Write Metrics.Shuffle Bytes Written` grouped by `Task Info.Executor ID`, plus executors alive at stage start). Caveat kept honest: a SECOND reducer of the same concentrated output waits ~0%, so first-read-cold vs warm is likely also in play and the event log cannot settle it — hence the fix ships as a one-hour `initialExecutors` experiment, not a prescription. Raw counters worth pulling directly: `Remote Blocks Fetched`, `Local Blocks Fetched`, `Remote Bytes Read`, `Fetch Wait Time`, `Executor Run Time`, `Executor CPU Time` (stage 9's CPU was 608s of 23,716s run = 2.6%, which is what rules out compute).

**AQE's coalesce floor on the batch fleet is registered cores at plan time, NOT the 64 MiB advisory size (AUDI-1274, verified 2026-09-02 from the 08-26 `guid_log_pivot_ip_vertical_id` / `guid_conv_log_pivot_ip_vertical_id` logs, Dataproc Serverless 2.3 / Spark 3.5.3).** The fleet leaves `spark.default.parallelism` unset and `spark.sql.adaptive.coalescePartitions.parallelismFirst` at its default `true`, so AQE's merge target for a coalesced shuffle is `max(minPartitionSize 1 MiB, min(advisoryPartitionSizeInBytes 64 MiB, total shuffle bytes / cores registered when the stage is planned))`. Proof: guid_log stage 3 coalesced to **728** partitions when 90 executors x 8 cores = 720 were registered; every stage planned at 100 executors landed on exactly **800**; a fixed 64 MiB target cannot produce both counts for equal-size shuffles, the core-count floor reproduces both exactly through the greedy merge (`ShufflePartitionsUtil.coalescePartitions`: contiguous map partitions merge while the running sum stays at or under target). Consequences: (a) **raising `spark.sql.shuffle.partitions` above the core count is a no-op for the coalesced count**, it only shrinks the granule AQE merges (8,000 map partitions of a 19.9 GiB shuffle = 2.55 MiB granules); (b) **the lever is `spark.sql.adaptive.advisoryPartitionSizeInBytes`**, which binds whenever it is below total/cores (16 MiB binds for every shuffle above 12.5 GiB at 800 cores); (c) this corrects the AUDI-1194 spec line for rows 10-11 that said AQE coalesces "about 8000 back to about 800 by the 64 MiB advisory size", right remedy, wrong mechanism (contradiction appended in `tickets/audi_1290_pipeline_optimization_hackathon/audi_1274_aqe_advisory_pivot/summary.md` §4 and in the spec's Row 10/11 evidence). Two more mechanics from the same logs: **AQE coalesces the co-partitioned inputs of one stage on their summed per-index size**, so the pivot stage's 27.8 + 21.3 GiB shuffles form 6.29 MiB granules and a 16 MiB target packs 2 per output = 4,000 tasks at 12.6 MiB compressed (bytes / target = 3,100 is only the floor of the greedy merge, quote a band, not one number); and **the optimizer parser does not see AQE nodes** (`spark_optimizer.eventlog` keeps only `SQLExecutionStart` plan info; the final adaptive plan arrives in `SparkListenerSQLAdaptiveExecutionUpdate`), so read the raw log for `AQEShuffleRead` metrics (`artifacts/audi_1274_aqe_probe.py` in the ticket folder).

**Event-log trick for AQE post-mortems:** count `SparkListenerExecutorAdded` events up to each `SparkListenerStageSubmitted` (net of `SparkListenerExecutorRemoved`, 0 in these logs) to get the cores registered at plan time; a coalesced partition count that tracks executors x cores rather than bytes / 64 MiB is the signature of the `parallelismFirst` floor. Script: `tickets/audi_1290_pipeline_optimization_hackathon/audi_1274_aqe_advisory_pivot/artifacts/audi_1274_exec_timing_probe.py`.

**Spark 3.5.3 byte-string syntax, checked without a JVM (2026-09-02):** the parser `JavaUtils.byteStringAs` lives in `spark-common-utils_2.12-3.5.3.jar` (not `spark-network-common` on 3.5) and accepts suffixes `b k kb m mb g gb t tb p pb`, so `16m` = 16 MiB is valid for `spark.sql.adaptive.advisoryPartitionSizeInBytes` (SQLConf's default literal is `64MB`). macOS `strings(1)` refuses `.class` files (it parses them as Mach-O); pull constant-pool text with a Python regex over the raw bytes of the class extracted from the pyspark wheel's jar.

**`spark.sql.files.maxPartitionBytes` cannot split a parquet row group, so check row groups per file before prescribing it for a read-stage spill (AUDI-1273, verified 2026-09-02 on Spark 3.5.3).** Spark's parquet reader assigns each row group to the file split that contains the row group's midpoint, so a cap smaller than a file's single row group yields one task that reads the whole file and one that reads zero rows. Probe: `tickets/audi_1290_pipeline_optimization_hackathon/audi_1273_max_partition_bytes/artifacts/audi_1273_split_probe.py` read one 60 MiB DS4 file locally at 32, 64 and 128 MiB caps and every run gave two partitions, one with all 1,318,363 rows and one with 0 (`outputs/audi_1273_split_probe_2026_09_02.txt`). Cheap pre-check without a JVM: read the parquet footer with pyarrow (`pq.ParquetFile(path).metadata.num_row_groups`) on one or two files per input. Three inputs measured 2026-09-02: `gs://mntn-data-archive-prod/ipdsc/dt=<date>/data_source_id=4/` is ~160 files of ~60 MiB with ONE row group each (1.32 M rows), so the knob is a no-op for `ipdsc_ds_67` (the Jira value of 32 MiB would only add ~160 empty tasks per pass); only a smaller `parquet.block.size` at the writer (the targeted-signal pipeline, `spark/data_source/populate_data_source.py`) or a join change helps. `ipdsc_site_network/site_network_hourly/dt=<date>/hh=*` (716 files/day, median 13 MiB, max 26 MiB, one row group each, the `ipdsc_ds_49` input) and `feature_store/feature_group_1_source/conv_log_ip/dt=<date>` (8 files/day, one row group each, 9-11 MiB since 08-20) sit below the cap, so there the cap only sets how many whole files pack into one task (with the 4 MiB `openCostInBytes` per file, ds49 goes from ~82 MiB/task at 128 MiB to ~45 MiB at 64 MiB) and the knob works. Rule: a read-stage `disk_spill` finding needs the input's file size AND row-group count before "lower maxPartitionBytes" goes in the fix text.

**Long runs that are FetchFailed storms, not stragglers (`site_network_hourly`, AUDI-1275, four logs read 2026-09-02).** Wall clock 2 min to 2 h 25 min across 40 batches, all SUCCEEDED. The long ones are shuffle-loss storms from dynamic-allocation scale-down (every executor removal reads "Executor decommission finished: spark scale down", `shuffleTracking.timeout=300s`): `app-20260901205120829-0863` had 8,244 `FetchFailed` task ends, stage 8 re-submitted 116 times, both hour jobs failed ("ShuffleMapStage 9 / 25 has failed the maximum allowable number of times: 4"), 0 bytes written, batch SUCCEEDED because the model swallows the per-hour exception. `app-20260902115131178-0350`: 3,134 FetchFailed; `app-20260902005143827-0954`: 2,115. Speculation duplicates a slow task on a live executor; it cannot repair a lost shuffle, so `straggler:*` keys that are fetch-wait tails stay flagged after the canary. Tell them apart per stage: a stage with `FetchFailed` task ends in the same log is a fetch-wait tail; stages without (11 and 13 in `0350`, 39 in `0954`) are the ones speculation can shorten. A stage re-attempt under FileOutputCommitter v2 can also leave task-committed files with no `_SUCCESS` (`dt=2026-09-02/hh=05`: 29 part files carrying two timestamps, 09:45 and 10:02 UTC, from `app-20260902085134727-0157`), the pre-existing partial-partition exposure a post-merge check must not blame on speculation. The storms are logged as IMP-104.

**The optimizer's straggler detector fires on fetch-wait tails too (`include/spark_optimizer/optimizations.py` L240-265, read 2026-09-02):** it flags a stage with >= 8 tasks, `skew_ratio` >= 5, max task >= 60 s and `data_skew_ratio` < 2, with no look at `FetchFailed` or fetch-wait time, so on `site_network_hourly` most `straggler:*` keys are shuffle-loss tails. Check the log's `FetchFailed` count per stage before prescribing speculation. Write-stage stragglers seen so far (`output_bytes > 0` on the flagged stage): `identity_targeted_signal` stage 3 (the Iceberg write itself, 634 tasks, 31.3 s median / 236.3 s max, 104.2 GB out) and `site_network_hourly` stage 39 on `app-20260902005143827-0954` (37 tasks, 4.0 s / 161.3 s, 0.53 GB); both writers discard the losing attempt, so a write-stage straggler does not by itself block speculation.

**A `.zstd.inprogress` event log still parses.** The driver never closed it (batch killed, or the log was read while the batch was live), so there is no `SparkListenerApplicationEnd`, but `include.spark_optimizer.eventlog._read_events` reads it up to the last complete event; `app-20260902085134727-0157.zstd.inprogress` gave the whole hh=05 write-failure story above. Per-app props and per-stage evidence extractor: `tickets/audi_1290_pipeline_optimization_hackathon/audi_1275_straggler_gcs_writers/artifacts/audi_1275_eventlog_props.py` (writes `audi_1275_app_props.csv` with the committer and speculation keys per log and `audi_1275_stage_evidence.csv` with tasks, median/max, `output_bytes` and FetchFailed per stage).

**JDBC-sourced small side of a join is planned as SortMergeJoin (no stats), then broadcast at runtime by AQE, but the planted `Exchange hashpartitioning(<join key>)` on the big side stays (AUDI-1276, verified Spark 3.5.3 on 15 prod logs + local replay).** Any downstream aggregate/window on a superset of the join key reuses that keyed partitioning (ClusteredDistribution satisfied by subset), so the keyed shuffle runs with inherited data skew. `spark.sql.adaptive.skewJoin` is enabled but only rewrites sort-merge and shuffled-hash joins at runtime, and every join here is already a `BroadcastHashJoin`, so it never fires. Fix: plan-time broadcast `F.broadcast(df)` on the JDBC DataFrame or `/*+ BROADCAST(alias) */` in SQL; this eliminates the keyed Exchange and the downstream aggregate shuffles on its full key instead (uniform, because the join key is not the cardinality bottleneck). Verified: local Spark plan check on synthetic JDBC-emulated data (stats-less join + broadcast) produces same outputs as pre-fix, aggregate shuffles on full key instead of join key, no keyed Exchange. Fallback if a hint cannot be placed: `spark.sql.requireAllClusterKeysForDistribution=true` forces the aggregate to shuffle on all its keys rather than reusing the join's keyed partitioning (config wider than the hint, job-wide).

**CTEs are not materialised: N references = N evaluations (shuffle write reused, read + aggregate repeated) (AUDI-1276, Spark 3.5.3 / Dataproc 2.3).** Proof: `ipdsc_42_monitor` SQL computed `comparison` CTE (count-distinct by category on a 40.1 GB shuffle) referenced by `all_rows` (union), `total_row` (aggregate), and final projection (ORDER BY). The shuffle write (stages 8 and 10, plan_ids 555 and 593) completed once (20.2 + 19.9 GB written total), but the read and count-distinct reran three times: stages 18 (job 12), 22 (job 13), 26 (job 14), sequential windows 359-704s / 705-1018s / 1018-1323s of a 1,331s run (72% of wall consumed by re-reading and re-aggregating the same 40 GB three times). Fix: split SQL into two batches: first batch runs `count(distinct)` over the shuffled data and `.cache()`s the result; second batch `.count()`s the cache (logs intermediate row count), registers a temp view, then runs remaining SQL (projections, ORDER BY) over the view. Both consumers read `InMemoryTableScan` from the cache, one pass per DAG run. **Event-log stage-to-SQL-operator mapping recipe (AUDI-1276, refined 2026-09-02).** Every Spark stage writes a `SparkListenerStageSubmitted` with a `stageId`, `stageInfo.rddInfo[].scope` names the `WholeStageCodegen (N)` block(s) the stage runs. The final adaptive plan for an execution arrives in `SparkListenerSQLAdaptiveExecutionUpdate.sparkPlanInfo`, which is a tree where each node carries `nodeName` (operator type), `simpleString` (parameters + join type, build side, keys), and (in v2 of the update) a reference to the codegen blocks. Link stages to executions via `SparkListenerJobStart.Properties['spark.sql.execution.id']` (execution ID) + the job's stage IDs. Script template at `tickets/audi_1290_pipeline_optimization_hackathon/audi_1276_join_skew/outputs/audi_1276_stage_map.py` parses all three, outputs per-stage `(execution_id, stage_id, codegen_blocks, operators_per_block, shuffle_key, runtime_join_strategy, max_task_s, skew_metrics)`; call sites for prod event logs: `SparkListenerStageCompleted` fired, stage info available immediately after, plan available on first use by that execution (allow streaming parse).
