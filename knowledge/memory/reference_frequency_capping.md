**IP frequency-capping (fcap) mechanics (codebase, 2026-07; corrected AUDI-1173 2026-07-28).** Caps set in `bidder.frequency_caps` / `dso.frequency_caps` as `(cap, duration_secs)` pairs, `object_type` ∈ {campaign, campaign_group}; enforced in `do_fcap` (SteelHouse/rtb-campaign-service) BEFORE the bid; Redis counters `rtb:frequency:{ip}:campaign_group_id=<cg>:campaign_id=<c>`. **The counter key is ALWAYS the IP** — `household_id_for_fcap()` always returns the IP; enum `HouseholdIdentifier` has only `Ipv4`/`Ipv6`/`Both`, **no MNTN-id branch**. `uses_mntn_id` drives **candidate fetch + holdout routing, NOT the fcap counter key** (supersedes the old "MNTN-ID only when `uses_mntn_id`" claim). **NO advertiser dimension / no rollup key** → no cross-advertiser cap; each campaign_group counts the IP independently. Config-table state: **`advertiser_frequency_caps` is EMPTY (0 rows)** — no advertiser-scoped cap exists in prod (the advertiser-rollup gap is a real CAPABILITY GAP, not a mis-set knob); `integrationprod.campaign_group_frequency_caps` + `dso_frequency_caps` are populated. **True rolling/sliding window** (`now-ts <= duration`, per request; no calendar reset). A **universal 1-imp/30min** default policy is appended to all campaigns (per-campaign counter, NOT a shared cross-advertiser counter). **Fails OPEN on Redis error** (caps silently stop enforcing) → delivered > configured. Client caps: `has_custom_frequency_caps` — a bandit must touch only the DEFAULT cap. Generations: in-bidder `fcap` crate (2-scope) migrating away from `ads-fcap-service` (4-tier primary/secondary/universal/dsp; 7 identity types, IP window deliberately shorter than device-ID).

**LIVE CAP CENSUS (BQ, 7 days ending 2026-08-26) — the gap is GRAIN, not tightness.** Caps are set on essentially every live campaign: **10,428 of 10,430** campaigns that delivered impressions carry a `dso_frequency_caps` row (10,422 universal, 9,129 secondary, 3,262 primary; only **4** uncapped at any tier), across 1,627 live advertisers / 3,539 campaign groups. `dso_frequency_caps` = 126,460 rows, columns `advertiser_id, campaign_group_id, campaign_id, cap, duration, secondary_cap, secondary_duration, dsp_cap, dsp_duration, universal_cap, universal_duration`. Most common live configs: **1 imp/day + 6 imps/30d (16.0%)**, 1 imp/3h + 24/3d (11.1%), 1 imp/14d (10.0%), 6 imps/15d (7.0%), 24 imps/day (6.6%); `LEAST()` across tiers normalized to 30d puts ~27% of live campaigns at ≤8 imps/30d. Advertiser-set custom caps stay rare: `campaign_group_frequency_caps` 1,255 rows / 462 groups (same count in the `ui_` surface), most common custom value 1 imp/30d (538 rows, 188 groups). **So do not argue "caps are nominal" — argue grain.** The worked example is WGU (31357): every campaign capped, yet 367,710,012 imps over 14,910,370 distinct IPs in 30d = **24.66 imps/IP**, the 98.4th percentile of 1,859 advertisers (median 3.36). N campaign_groups × M funnel stages multiply the configured cap by construction.

**CONTRADICTION — universal window 30min (code) vs 900s/15min (config), unresolved 2026-08-27.** The July codebase read above says the appended universal policy is 1 imp/30min. The config table says `universal_cap=1, universal_duration=900` on **10,324 of 10,428** live campaigns. Both kept. Hypothesis: different layers (synced config row vs a policy the crate appends at request time), or the default was retuned after the code read. **Settling check:** the universal-policy constant in the `fcap` crate vs `universal_duration` for the same campaign_id, or delivered same-IP inter-impression gaps measured against 900s and 1800s.

**A tight cap does not protect a narrowed pool — it converts the failure.** Where a cap binds against a gated high-intent pool at fixed budget, the documented response is ordered: frequency rises on existing HI to the cap → the pacing controller lowers the HHST gate to find fill ([[reference_hhst_pacing_lever]]) → under-delivery. Bid inflation on a thinner pool is NOT a documented path (the only recorded pricing rule is a rolling ~7d publisher CPM with no score term) — do not assert it. Applied to a very-high-spend advertiser this is the whole MM-suitability argument: [[reference_mm_wgu_suitability_argument]].

**Frequency-cap bandit = the better FIRST MAB (vs the HHST intent-gate bandit [[reference_hhst_efficiency_sizing]]).** Both optimize a diminishing-returns curve; frequency wins on MEASURABILITY: its causal reward is a household-randomized cap RCT (`MOD(ABS(CAST(CONCAT('0x',SUBSTR(TO_HEX(MD5(CONCAT(CAST(advertiser_id AS STRING),':',ip))),1,16)) AS INT64)),1000)` = MNTN's MD5(AID:ip)-16hex-mod-1000 convention, treatment buckets 100-999 disjoint from the 0-99 platform holdout), whereas HHST graduated lift needs a blocked GCS+Databricks build. Frequency addresses ALL delivery (bigger TAM); HHST only non-RTC prospecting. Sequence frequency first, HHST second (reuse the randomized-holdout lift infra). Ownership: the knob lives in the bidder (rtb-campaign-service = @SteelHouse/rtb), a partner team, not AUDI.

**Phase-0 sizing (7d, household=ip×advertiser, CORRELATIONAL — cannot justify a cap alone).** Prospecting (has_mm) $3.93M/7d, ~12% of spend at freq≥8 (~$2M/30d), per-HH visit rate plateaus ~1.1% across freq 4-20. Retargeting (funnel≥2) $1.39M/7d, ~31% of spend at freq≥8 (biggest pool, but warm-user visits are the LEAST incremental). **Leakage — magnitude RETRACTED (AUDI-1173):** the qualitative "no advertiser rollup → frequency LEAKS across campaign_groups" holds, but any per-`(ip, advertiser)` leakage-$ is **SHARED-IP CONFOUNDED** — apparent leakage rises monotonically with distinct-advertiser count per IP; ~76% of "leaked" impressions sit on IPs shared by 5+ advertisers (NAT/office IPs, not one household), and a naive high-threshold purge trips for only ~0.34% of households. So the earlier **4.8% households / 13% impressions** (and any derived $/30d) figures are **retracted** — unreliable without a real shared-IP (identity/household) purge. LOAD-BEARING CAVEAT: attributed visits-per-impression decline is PARTLY a mechanical last-touch ~1/n artifact — the honest RCT metric is **total visits per household + cost-per-household** (guid_log, [[reference_total_visit_signal]]), not attributed visits/imp.
