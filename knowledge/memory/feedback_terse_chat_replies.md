Conversational replies (not just Jira/deliverables) must be terse. Lead with the answer, then stop.

**Why:** User's work is highly technical and they usually don't have time to read thoroughly. Filler, preamble, and self-narration waste output tokens and bury the answer.

**How to apply:** Delete preamble ("Honest answer:", "Here's the thing:"), self-narration of what was/wasn't verified (unless it changes the next action), unoffered options, hedges, editorializing adjectives, em-dashes. Keep the direct answer first + essential caveats/blockers + one next-step question if the decision is genuinely theirs. Rule lives in `~/.claude/CLAUDE.md` § "Chat Response Style". Extends the [[feedback_terse_tickets]] Terse Comms Standard to chat.

**Reinforced hard 2026-07-29 (Matt-message drafting):** when drafting a message the user will SEND (Slack/email), it must be PURE CONTENT — the ask + the specifics, nothing else. Strip ALL meta-framing/context-scaffolding: no "I hit a definitional fork I want your call on", no "before it goes to X", no "quick one for you", no explaining why you're asking. It took 4 rounds to cut a Matt question down; the final good version was 4 sentences of pure substance (the ask, the three numbers, the yes/no). Same bar applies to my own chat replies: the user said "let's make sure we have responses more like that from now on." Draft at that terseness the FIRST time, don't iterate down to it.

**HARD CAP for CHAT RESPONSES (2026-08-03): every conversational reply stays under ~500 characters.** Going over requires the user's explicit approval FIRST — ask before extending, don't ship a long response then apologize. Only unprompted exception: content that genuinely can't compress (a required table, code, a multi-step diff), kept minimal. Default = a tight paragraph or ≤3 bullets; when unsure, answer short and offer to expand. In global CLAUDE.md Chat Response Style.

**HARD CAP for send-drafts (2026-07-29, second correction same day — "WAY too long... make sure this never happens again"):** a drafted Slack/email message the user will send must be **≤ ~6 sentences / ~600 chars**, BLUF, first sentence carries the answer or the ask. A 3-paragraph "explain how we did it" draft is a FAILURE even when every sentence is true. Method/context/validation the reader didn't ask for = CUT (it lives in the doc, not the message). Shape: answer/result line → the number(s) → the one question, and stop. If I catch myself writing a second paragraph of background, delete it. BLUF-test every draft before showing it: if sentence one alone doesn't deliver the point, rewrite. This has now been corrected 3+ times ("Verbose, dont" / "that is way better, more like that" / "WAY too long") — treat verbosity in a send-draft as a defect on par with a wrong number.

**5th correction (2026-08-11, standing instruction — "Our outputs are always incredibly long... make sure this never gets violated"):** the cap is now stated as **~500 chars / ~75 words** and carries an explicit tie-breaker: **err on the side of leniency rather than over explanation.** Under-explaining is the cheap error (user asks a follow-up); over-explaining is the expensive one (buries the answer, doesn't get read). Prefer bullets over prose, fragments over bullets. Banned unprompted: closing summaries, recaps of what was just said, "let me know if…" lines, introductory throat-clearing. **Correction protocol:** if the user says "Too long", rewrite in exactly two short sentences — no apology, no explanation, no meta. Each such correction permanently tightens the default rather than fixing one message.

**6th correction (2026-08-12) — root cause of repeated violations, and the fix.** User asked why the cap keeps getting missed. Three causes, all structural, none a config bug: (1) **Nothing enforces it.** `lint_comms.py` only fires via the Bash PreToolUse hook, so Jira/PR/commit text is checked but chat replies never pass through any gate. The chat cap is honor-system, unlike every other cap in the standard. (2) **Position.** The rule sat at line 82 of a 14k-char `~/.claude/CLAUDE.md`, below 13 numbered always-on behaviors that all push toward MORE output (write knowledge immediately, auto-capture, update self-review, ticket docs are living). Recency/primacy both worked against it. (3) `effortLevel: "xhigh"` in `~/.claude/settings.json` — higher reasoning effort correlates with longer prose. **Fix applied 2026-08-12:** the section was promoted to **RULE 0**, immediately after the file header and ABOVE "Always-On Behaviors", with an explicit precedence line: "This rule outranks everything below it. Nothing in this file is a license to write more. The rules below say what to DO; this one caps what to SAY. Rules that mention writing/documenting/sweeping/capturing produce files and commits, NOT longer chat replies." Also added a pre-send word count instruction. **The precedence clause is the load-bearing part** — the failure mode was never not-knowing the rule, it was the write-everything rules bleeding into chat verbosity.

**4th correction (2026-08-06, PS-8572 Slack draft): "way too many words! try and keep under 500 characters. especailly the bullets."** The ~500-char cap applies to DRAFTS I hand the user (Slack replies, list bullets) exactly as to chat. Bullets must be fragment-short (verdict + number, e.g. "Blocks on since April, verified"), not sentences. The user rewrote my draft themselves and kept only 3 of my 5 points at half the length. Draft at their final-version terseness the first time.

**7th correction (2026-08-17) — "all your responses are incredibly wordy... research how other people got you to keep your answers small, then implement."** Researched external practice and implemented four structural fixes, because the 6th correction's root cause (nothing enforces the chat cap) was still live.

1. **Enforcement loop, the missing gate.** `.claude/hooks/chat_brevity_meter.py` (Stop) parses the transcript, measures the final assistant text with fenced code and table rows exempted, and writes the verdict to `.claude/state/chat_brevity.json` + an append-only `chat_brevity_log.jsonl`. `.claude/hooks/brevity_pointer.py` (UserPromptSubmit, registered LAST so it lands closest to generation) prints a ~20-token pointer at the rule, and when the state file shows `over: true` it escalates to "LAST REPLY BREACHED at Nch/Nw, this one is a hard rewrite." A breach now tightens the next turn instead of vanishing. **Stop hooks must stay advisory (exit 0)** — `decision: block` makes the model keep going, i.e. write MORE, which is backwards.
2. **Position beats repetition.** The cap lived only at the top of a 16k-char CLAUDE.md loaded thousands of tokens before generation, while everything nearer the generation point (memory_recall injection, tool results, ultracode's "be exhaustive") argued for more words. External practice converges on a UserPromptSubmit pointer for exactly this: ~15 tokens that re-point attention rather than restate the rule.
3. **Named prohibitions beat "be concise."** Rewrote RULE 0 to ban behaviors by name and added the two that were missing: **no tool-call narration** ("I can see the calls") and the filler test **"any sentence that would fit unchanged in a different conversation is filler, cut it."** Also cut RULE 0's own prose — a verbose rule models verbose output.
4. **Named the real conflict.** `ultracode: true` and `effortLevel: "xhigh"` in `~/.claude/settings.json` both push toward exhaustive output, and ultracode's prompt literally says optimize for the most exhaustive answer. RULE 0 now carries the precedence line: **ultracode and xhigh govern how much WORK and THINKING, never how many WORDS — exhaustive work, terse report.** This is the analogue of the 6th correction's load-bearing clause (write-everything rules bleeding into chat), one layer up in the config.

Rejected: a custom output style (`~/.claude/output-styles/`). It replaces sections of the default Claude Code system prompt and would put this workflow's engineering behaviors at risk for a lever the hooks already provide. Also confirmed no `/focus` mode is active here, so no competing `focus_mode` prompt section to disable.
