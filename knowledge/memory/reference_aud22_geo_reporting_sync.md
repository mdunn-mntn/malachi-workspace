Tracking spike (Malachi): **AUDI-1189** (this sprint). Sean's investigation: **AUDI-1072**.

Mission-control **audit 22 "Geo Includes / Excludes" (FA022)** reconciles the last 24h of impressions against the audience Geo expressions and flags IPs served outside the targeted geo. It is a **recurring** violation class, not a one-off.

**Root cause (confirmed, re-verified 2026-07-30):** the `dw-main-bronze.geo.location_data` model has ZIP rows (`location_type_id=7`) where the scalar `metro_id` field disagrees with the metro sitting in that same row's `hierarchy` chain. It is a **per-row contradiction**: one geoname_id, one row, its own hierarchy array carries a different metro than its own scalar field (so NOT explainable by a ZIP spanning two metros). The audience/TPA-export side and the impression side read different fields, so the same IP resolves in-geo on one and out-of-geo on the other → a false violation. Source of truth = ad-buying-ui `ipdata` (`https://ad-buying-ui.prod.in.mountain.com/ui/ipdata?id=<IP>`), which agrees with the audience config. **Current example set (geo_version 1785110400), metro_id field vs hierarchy metro:** 01223 Wendell 543 Springfield-Holyoke MA vs 532 Albany NY; 17371 New Salem 566 Harrisburg PA vs 508 Pittsburgh PA; 66214 Piqua 616 Kansas City MO vs 603 Joplin; 92545 Mokelumne Hill 862 Sacramento CA vs 803 Los Angeles CA; 95245 Mokelumne Hill 862 Sacramento vs 803 LA. (Shareable diagnostic query lives in the AUDI-1072 ticket work / perf log label "aud22 5 ZIP mismatch shareable with metro names v2".) **Correction (2026-07-30):** the original AUDI-1072 example ZIPs **43221 and 45814 are NOT inconsistent** — each geoname row there has `metro_id` matching its hierarchy (43221 spans two geoname_ids, Columbus 535 and Arlington/Toledo 547, each internally consistent). Earlier notes citing "43221 metro_id=535 but hierarchy→638/Toledo" were imprecise; do NOT cite 43221/45814 as the defect. Metro/DMA 638 (Toledo) was the wrong value in the ORIGINAL example only, not a recurring signature.

**Which field the impression side reads (lizz, CIL owner):** for `campaign_template_id = 55` CIL geo comes from **win_logs** (auction_id join); for **all other** campaigns from `geo.network_locations` (bid_ip → network prefix → geo_version match → most-specific block). So aud22 on non-template-55 CGs compares network_locations-derived geo vs the audience expression.
