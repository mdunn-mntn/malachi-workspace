# core.advertiser_padding_overrides

## Purpose
Small **exception / override table**: stores a `padding` multiplier for the handful of advertisers that
need a non-default value. `padding` is a decimal (stored as a STRING, e.g. `"1.05"` = a +5% uplift);
`1.0`/no row = default (no padding applied). Reach for it when you need to know whether a given
advertiser has an operator-set padding override and what it is (with the `notes` field usually pointing
at the Jira ticket that requested it). Thin silver VIEW (`SELECT *`) over the Postgres CDC dimension
`bronze.integrationprod.core_advertiser_padding_overrides`. A parallel table
`core.campaign_padding_overrides` does the same at campaign grain (`campaign_id`), and a companion view
`core.advertiser_padding_overrides_vw` exists.

> The precise downstream consumer of `padding` (pacing/delivery buffer vs billing/spend inflation) is
> not documented in the prose knowledge base — treat the exact use as an actionable gap, not a claim.

## Grain & keys
- **Grain:** one row per advertiser that has a padding override. `advertiser_id` is unique (physical
  table is clustered on it). This is an override-only table, not a per-advertiser dimension — most
  advertisers have **no** row. Observed live: exactly **1 row** (advertiser 31966 = "Boll & Branch").
- **Key(s) / join columns:** `advertiser_id` (PK) → `advertisers.advertiser_id`.

## Column meanings (only the non-obvious ones)
- **`padding`** — decimal multiplier stored as a **STRING**, not a number. `"1.05"` = a +5% padding /
  uplift; `"1.0"` (or no row) = default. `CAST(padding AS NUMERIC)` before any arithmetic. Only values
  needing a non-default override are stored.
- **`notes`** — free-text operator note; in practice a Jira ticket reference explaining why the override
  was set (observed value `"PER-4384"`). Not a structured field.
- **`create_time` / `update_time`** — native `TIMESTAMP` of the **Postgres source row** (business
  create / last-modify). Both `2025-05-09` in the one observed row. These are NOT the replication time —
  see `datastream_metadata.source_timestamp`.
- **`datastream_metadata`** — standard Google Datastream CDC envelope. `uuid` = the change-event id;
  **`source_timestamp` is epoch MILLISECONDS** (anchor: `TIMESTAMP_MILLIS(source_timestamp)` →
  `2025-12-19`, matching the table's creation/backfill; `TIMESTAMP_MICROS` yields 1970 = wrong). It is
  the CDC/backfill event time, **not** the business `create_time` — do not conflate them.

## Joins & relationships
- **`advertiser_id` → `advertisers.advertiser_id`** (physical: `bronze.integrationprod.advertisers`, PK
  `advertiser_id`, ~38.4K rows). **1:1** — each override references exactly one advertiser; the
  advertiser is the parent, so this is a lookup with **no fan-out**. (`advertisers` is where you get
  `company_name` and the `deleted` / `is_test` hygiene flags — see Gotchas.)
- **Sibling:** `core.campaign_padding_overrides` — identical schema keyed by `campaign_id`
  (→ `campaigns`); the campaign-grain version of the same override mechanism.
- **Companion view:** `core.advertiser_padding_overrides_vw` (→ `core_advertiser_padding_overrides_vw`),
  documented separately.

## Gotchas
- **Override-only table.** Absence of a row = default (no padding). Never assume an advertiser is
  present — `LEFT JOIN` and `COALESCE(CAST(padding AS NUMERIC), 1.0)`. Currently only 1 row exists.
- **`padding` is a STRING.** Cast to NUMERIC before math; a raw string compare/sum is a bug.
- **No `deleted` / `is_test` columns.** Unlike most `core.*` CDC dims, this physical table has neither
  flag (schema is just `advertiser_id, padding, notes, create_time, update_time, datastream_metadata`).
  You cannot filter test / soft-deleted rows here — apply that hygiene by joining to `advertisers`
  (`deleted = FALSE AND is_test = FALSE`).
- **Two different time meanings.** `create_time`/`update_time` = Postgres business timestamps;
  `datastream_metadata.source_timestamp` = CDC replication time (ms epoch). In the observed row they
  differ by ~7 months (May 2025 business vs Dec 2025 backfill).
- Physical `numRows` here is reliable (real table, not a SQLMesh view) — 1 row, 86 bytes.

## Cost & partitioning notes
- **No partition** (not an event table); physical is a real `TABLE` **clustered on `advertiser_id`**,
  with no TTL. At 1 row / 86 bytes the clustering is immaterial. There is no partition filter to apply —
  this is a tiny lookup dim, `SELECT *` is trivially cheap.
- Dry-run/live figures (labeled per column set): selecting `advertiser_id, padding, notes,
  create_time, update_time, datastream_metadata.*` = **0 GB processed / 0.01 GB billed** (min tier).
  The `advertiser_id → advertisers` join processed **0.001 GB** — the cost is the `advertisers` side
  (~38.4K rows scanned), not this table.

## Example queries
```sql
-- Resolve an advertiser's effective padding (default 1.0 when no override row), with hygiene filter.
SELECT
  a.advertiser_id,
  a.company_name,
  COALESCE(CAST(p.padding AS NUMERIC), 1.0) AS effective_padding,
  p.notes
FROM `core.advertisers` a          -- (advertisers dim; not core.advertisers if unavailable, use bronze.integrationprod.advertisers)
LEFT JOIN `core.advertiser_padding_overrides` p
  ON p.advertiser_id = a.advertiser_id
WHERE a.deleted = FALSE AND a.is_test = FALSE
  AND p.advertiser_id IS NOT NULL   -- drop to see all advertisers with the default
```
