# core.pixel_integrations

## Purpose
Configuration dimension recording each advertiser's **e-commerce / pixel integration** — how their conversion pixel is wired up (Shopify app, Google Tag Manager, manual tag, etc.). It is a thin silver view (`SELECT *`) over the non-SQLMesh bronze CDC dim `dw-main-bronze.integrationprod.core_pixel_integrations`. Reach for it to answer "what integration method does advertiser X use?" and to **date MNTN-side pixel/config setup** via `create_time` (used in the WGU / conversion-drop forensics playbook to rule out MNTN-side changes — see `data_knowledge.md` "Rule out MNTN-side"). It is **config metadata only** — it carries no conversion events, no revenue, no impression data.

## Grain & keys
- **Grain:** one row per `pixel_integration_id` — a single integration record. Verified unique: 12,183 rows = 12,183 distinct `pixel_integration_id`.
- **Primary key:** `pixel_integration_id`. (Also the physical table's clustering key.)
- **Foreign keys:** `advertiser_id` → `core.advertisers` (many integrations : one advertiser — 12,183 rows span 10,380 advertisers, so some advertisers hold >1 integration). `pixel_integration_type_id` → `core.pixel_integration_types` (8-row enum). `user_id` would reference the creating user but is **100% NULL** here.

## Column meanings (only the non-obvious ones)
- **pixel_integration_type_id** — integration method; joins to `core.pixel_integration_types`. Live domain (SELECT DISTINCT via the types table, ordered by usage): `4=manual` (7,282, dominant), `6=gtm` (2,030), `1=shopify` (1,341), `7=sans-pixel` (1,017), `8=reset` (513). Three enum values exist but are **never used** in the data: `5=mntn-wordpress-plugin`, `2=magento`, `3=prestashop` (0 rows each). "manual" = a hand-placed tag rather than a platform integration.
- **tracking_status / conversion_status** — STRING status fields with an essentially **inert domain**: every row is either `'Not Done'` on BOTH (11,495 rows) or NULL on both (688 rows). No `'Done'` (or any other) value ever appears — do **not** treat these as a live tracking-health signal; they are effectively frozen placeholders.
- **access_token** — 100% NULL in this table (0 non-null of 12,183). Would hold an OAuth/API token for app integrations but is unpopulated in this CDC snapshot.
- **shop_base_url** — 100% NULL (0 non-null). Would hold the Shopify/store base URL but is unpopulated here.
- **user_id** — 100% NULL. No creating-user is recorded.
- **create_time** — TIMESTAMP the integration record was created; the **reliable** recency field. Range 2018-10-30 → 2026-07-18 (still growing daily).
- **update_time** — TIMESTAMP of last update, but **stale/frozen and mostly NULL**: NULL on ~74% of populated rows (9,034 of 11,495), and MAX(update_time) = **2023-09-21** — no row shows an update after Sep 2023. Prefer `create_time` for any recency logic; a low/absent `update_time` is why the WGU forensics concluded "pixel_integrations untouched" (the field simply stops advancing), not proof nothing changed client-side.
- **datastream_metadata** — Datastream CDC-capture metadata `STRUCT<uuid STRING, source_timestamp INT64>`. `source_timestamp` is **milliseconds** epoch — verified: `TIMESTAMP_MILLIS(source_timestamp)` == `create_time` to the second (e.g. 1784378575672 → 2026-07-18 12:42:55); `TIMESTAMP_MICROS` gives 1970. This is CDC-capture time (coincides with create for this insert-only table), **not** independent business time — use `create_time`.

## Joins & relationships
- **→ `core.advertisers`** on `advertiser_id`. Partner grain: one row per advertiser (1:1 key). Direction here is **N:1** (many integrations per advertiser: 12,183 → 10,380 advertisers). Joining advertiser→integrations **fans out** ~1.17× on average (a few advertisers hold several integration rows) — deduplicate or pick latest by `create_time` if you need one row per advertiser. `advertisers.company_name` is the reliable advertiser label.
- **→ `core.pixel_integration_types`** on `pixel_integration_type_id`. Partner grain: 8-row enum, one row per type_id → clean N:1, no fan-out.
- **Related pixel-config tables (per `data_catalog.md`):** `core.pixel_integration_types` (this table's enum), `ui_advertiser_pixel_infos` (pixel notes / conversion_point_url), `attr_advertiser_waypoints_event_mapping` + `attr_advertiser_selective_performance_config` (event-name classification), and pixel flags on `advertisers` (`populate_order_on_conversion`, `conv_pixel_opt_out`, `pixel_isolation`, `allow_duplicate_orders`). There is **no** separate `conversion_sources` table — conversion-source decode lives in `data_sources`.

## Gotchas
- **No `deleted` / `is_test` columns** — unlike most `integrationprod` dims, this table has neither soft-delete nor test flag. Every row is treated as live; there is no live-vs-deleted filter to apply.
- **`update_time` is a trap** — frozen at ≤ 2023-09-21 and NULL on most rows. Never use it to detect recent config changes; use `create_time`.
- **Inert status fields** — `tracking_status` / `conversion_status` only ever `'Not Done'` or NULL. They do not report integration health.
- **Three all-NULL columns** — `access_token`, `shop_base_url`, `user_id` are 100% NULL; do not build logic that expects them populated.
- **Unused enum values** — `magento`, `prestashop`, `mntn-wordpress-plugin` types exist in the enum but have zero integrations; `manual` dominates (~60%).
- **`update_time` UTC** — timestamps are UTC (bronze integrationprod convention); compare in UTC.

## Cost & partitioning notes
- **Unpartitioned** — physical `dw-main-bronze.integrationprod.core_pixel_integrations` has NO time partitioning; clustered on `pixel_integration_id`. There is no partition column to filter, and none is needed: the whole table is tiny.
- **Full `SELECT *` = 1,199,862 bytes (~1.14 MiB), dry-run confirmed** — the entire physical table (`bq show` numBytes matches exactly). Billed rounds up to the 10 MB on-demand minimum (~0.01 GB). Cost is negligible regardless of predicate.
- Prefer selecting only needed columns (skip the three all-NULL columns `access_token`, `shop_base_url`, `user_id`) for clarity, not for cost.
- `approx_logical_bytes` = 1,199,862 (physical `numBytes`, unpartitioned single table).

## Example queries
```sql
-- Integration method mix across advertisers
SELECT t.name AS integration_type, COUNT(*) AS n
FROM `dw-main-silver.core.pixel_integrations` pi
JOIN `dw-main-silver.core.pixel_integration_types` t USING (pixel_integration_type_id)
GROUP BY 1 ORDER BY n DESC;

-- When did an advertiser's pixel integration(s) get set up? (use create_time, not update_time)
SELECT pixel_integration_id, pixel_integration_type_id, create_time, update_time
FROM `dw-main-silver.core.pixel_integrations`
WHERE advertiser_id = 31357          -- WGU
ORDER BY create_time;
```
