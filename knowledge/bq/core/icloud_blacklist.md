# core.icloud_blacklist

## Purpose
Per-advertiser blacklist governing how iCloud / Apple Private Relay traffic is treated for a
handful of advertisers. A row's mere presence marks the advertiser as blacklisted; the three
BOOL columns scope WHICH subsystems the carve-out applies to — `verified_visits`,
`audience_targeting`, and `conversion_attribution`. Reach for it when you need to know whether an
advertiser has an iCloud/Private-Relay exception configured for visit verification, targeting, or
attribution. Extremely small operational config table (2 rows), not an analytics fact.

## Grain & keys
- **Grain:** one row per `advertiser_id` (a blacklisted advertiser). Currently 2 rows
  (advertiser_id 22607, 22955), both with all three flags `true` and `create_time` 2022-10-01.
- **Key(s) / join columns:** `advertiser_id` — primary key (physical table is clustered on it) and
  the sole foreign key.

## Column meanings (only the non-obvious ones)
- **verified_visits / audience_targeting / conversion_attribution** — per-subsystem scope flags for
  the iCloud blacklist. A `true` marks that the subsystem participates in the carve-out for this
  advertiser. Exact polarity (true = exclude iCloud traffic vs true = allow it) is NOT empirically
  distinguishable here: both existing rows are `true` on all three, so treat these as "which
  features the blacklist entry covers," and confirm the direction with the consuming code before
  relying on it. NULL semantics unknown (none observed).
- **create_time / update_time** — TIMESTAMP business times from the source Postgres row. Both rows
  were created 2022-10-01; `update_time` is populated on one row (2022-11-04) and NULL on the other
  (never updated after insert). These reflect the SOURCE record's lifecycle, not the BQ load time.
- **datastream_metadata.source_timestamp** — CDC-capture epoch in **MILLISECONDS**
  (`= UNIX_MILLIS(capture_time)`): `TIMESTAMP_MILLIS(1766121490417)` → 2025-12-19 05:18:10, which
  matches the physical table's Datastream backfill (`creationTime` 2025-12-19); `TIMESTAMP_MICROS`
  yields 1970 (wrong unit). This is the Datastream capture moment, NOT business time — use
  `create_time`/`update_time` for when the blacklist entry was actually set. Both rows share the
  same `source_timestamp` and `datastream_metadata.uuid` (single backfill batch).

## Joins & relationships
- **`advertiser_id` → advertisers dimension** (`dw-main-bronze.integrationprod.advertisers`, grain =
  1 row per advertiser). 1:1 from this table into advertisers; no fan-out. Used as a semi-/anti-join
  membership test: an advertiser is on the iCloud blacklist iff a row exists here for its id.
- **`v_icloud_blacklist`** — a sibling `v_*` view in silver.core (and its bronze
  `core_v_icloud_blacklist`) presumably wraps/derives from the same source; documented separately.
- Joining this into any per-advertiser fact is safe (at most one match per advertiser); the risk is
  the opposite direction — the table covers only 2 advertisers, so an INNER join silently drops
  everyone else. Use LEFT JOIN + `IS NOT NULL` (or `WHERE advertiser_id IN (...)`) to test membership.

## Gotchas
- **No `deleted` / `is_test` columns** — the standard integrationprod dimension filter does NOT apply
  here (those columns do not exist). There is no soft-delete flag; presence of the row is the state.
- **Only 2 rows.** Any flag semantics/polarity inference is under-determined (all-true on both rows).
- **Not partitioned, not time-series.** No date/partition column — do not attempt a date filter.
- **CDC mirror.** Physical is a Datastream-materialized TABLE (created 2025-12-19), so
  `datastream_metadata.source_timestamp` clusters at the backfill time regardless of the much older
  business `create_time` (2022). Order/window on `create_time`/`update_time`, never on
  `source_timestamp`, for business chronology.

## Cost & partitioning notes
- Physical `dw-main-bronze.integrationprod.core_icloud_blacklist` is an unpartitioned **TABLE**
  (2 rows, `numBytes` = 138), clustered on `advertiser_id`. The silver `core.icloud_blacklist` is a
  thin `SELECT * FROM` view over it (no SQLMesh).
- No partition filter exists or is needed. `SELECT *` from the view billed 0.01 GB (10 MB on-demand
  floor; measured, all 7 columns) — the whole table is effectively free to scan. There is no cost
  trap here; the only "filter to apply" is `WHERE advertiser_id = <id>` when checking a single
  advertiser (cluster prune, but immaterial at this size).
- `approx_logical_bytes` = 138 (real backing `numBytes` of the single physical table).

## Example queries
```sql
-- Is a given advertiser on the iCloud blacklist, and for which subsystems?
SELECT advertiser_id, verified_visits, audience_targeting, conversion_attribution,
       create_time, update_time
FROM `core.icloud_blacklist`
WHERE advertiser_id = 22955;

-- Membership test against an advertiser set (LEFT JOIN, never INNER — table covers only 2 ids)
SELECT a.advertiser_id, (b.advertiser_id IS NOT NULL) AS on_icloud_blacklist
FROM some_advertiser_set a
LEFT JOIN `core.icloud_blacklist` b USING (advertiser_id);
```
