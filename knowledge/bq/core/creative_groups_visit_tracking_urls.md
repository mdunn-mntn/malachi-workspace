# core.creative_groups_visit_tracking_urls

## Purpose
CDC dimension holding the optional "visit tracking URL" configured on a creative group — the destination/pixel URL fired to track a visit for that group's creatives. It is a sparse extension of `core.creative_groups`: only ~2,169 of ~945K creative groups have any tracking URL row here. Reach for it when you need the tracking-URL string (or its POST config) attached to a `creative_group_id`. Tiny lookup dim — no cost trap.

## Grain & keys
- **Grain:** one row per visit-tracking URL. `visit_tracking_url_id` is the primary key and is unique (2,169 rows = 2,169 distinct ids).
- **Key(s) / join columns:** PK `visit_tracking_url_id`; FK `creative_group_id` → `core.creative_groups.group_id`. A creative group has 0-2 tracking-URL rows (2,137 distinct groups over 2,169 rows; max 2 URLs per group), so `creative_group_id` is **not** unique here.

## Column meanings (only the non-obvious ones)
- **visit_tracking_url** — the configured tracking/destination URL string (full https URL with query params, e.g. UTM/campaign tags). This is the payload of the table.
- **create_time** — native `TIMESTAMP` (UTC) of when the row was created in the source Postgres. Spans 2023-10-03 → 2026-07-15 in current data. This is business time; prefer it over `datastream_metadata.source_timestamp`.
- **user_id** — internal MNTN Postgres user id of whoever created the row (103 distinct). NOT an advertiser id and NOT an end-user/visitor id.
- **is_post** — whether the tracking URL should be fired as an HTTP POST (vs GET). **Empirically dormant: every one of the 2,169 rows is `false`.** Treat non-false as effectively unused today.
- **request_body** — POST body to send when `is_post` is true. **Empirically dormant: NULL in 100% of rows** (goes hand-in-hand with `is_post=false`).
- **datastream_metadata.source_timestamp** — CDC-capture epoch in **milliseconds** (verified: `TIMESTAMP_MILLIS(source_timestamp)` reproduces `create_time`; `TIMESTAMP_MICROS` yields 1970). This is Datastream capture time, not business time — use `create_time` for business logic.
- **datastream_metadata.uuid** — Datastream per-change-event id; not a business key.

## Joins & relationships
- **`creative_group_id` → `core.creative_groups.group_id`** (parent PK `group_id`, ~945,751 rows, 1 row per group). This table → creative_groups is **N:1** (each URL row maps to exactly one group; a group maps to 0-2 URL rows). Joining creative_groups → this table is 1:N and can **duplicate** a creative-group row up to 2x — aggregate/dedupe if a group could carry two URLs. Because only ~2,169 groups have a row here, use a LEFT join from creative_groups (most groups have no tracking URL).
- No other documented FKs. `user_id` references the internal Postgres users dim (not modeled in core.*).

## Gotchas
- **No `deleted` / `is_test` columns.** The standard `deleted=FALSE AND is_test=FALSE` live-row filter does NOT apply here — those columns do not exist. Every row is treated as live.
- **`is_post` and `request_body` are dormant** — 100% `false` / NULL respectively. Do not build logic assuming POST tracking exists until data shows otherwise.
- **`creative_group_id` is not unique** — a handful of groups have 2 tracking URLs. Do not assume 1:1 with creative_groups.
- **Two timestamps, different meaning** — `create_time` is business creation time; `datastream_metadata.source_timestamp` (ms) is CDC capture time. They coincide closely but only `create_time` is guaranteed business-meaningful.
- Tiny CDC snapshot dim (~2.1K rows, ~502 KB) — reflects current source state, not an event history.

## Cost & partitioning notes
- **Unpartitioned** (confirmed via `bq show`: no time/range partitioning), clustered by `visit_tracking_url_id`, no TTL. There is no partition column to filter — the "always filter" rule does not apply.
- Whole-table scan is trivial: `SELECT *` over all 2,169 rows dry-runs at ~0.01 GB billed (min tier-1 slot). Full backing storage `numBytes` = 502,123 bytes (~490 KB). No cost trap regardless of column set.
- Clustering on `visit_tracking_url_id` only helps point-lookups by PK; for `creative_group_id` lookups the scan is effectively free at this size.

## Example queries
```sql
-- Tracking URL(s) for a creative group
SELECT visit_tracking_url_id, visit_tracking_url, is_post, create_time
FROM `dw-main-silver.core.creative_groups_visit_tracking_urls`
WHERE creative_group_id = 1168220;

-- Attach tracking URL to creative groups (LEFT: most groups have none; may fan out 2x)
SELECT cg.group_id, v.visit_tracking_url
FROM `dw-main-silver.core.creative_groups` cg
LEFT JOIN `dw-main-silver.core.creative_groups_visit_tracking_urls` v
  ON v.creative_group_id = cg.group_id;
```
