# core.products

## Purpose
The canonical lookup that maps `product_id` → MNTN product-line name. Reach for it to label
`campaign_groups.product_id` as **PTV** (1), **Select** (2), or **QuickFrame** (3) in reporting,
invoices, and any Select-vs-PTV segmentation. `product_id` is the org-wide source-of-truth stamp for
product line (set by the UI on `campaign_groups`, immutable in practice — see `data_knowledge.md`
§ "MNTN Product Identification"); this table just resolves the id to a human name. It is a tiny (3-row)
enum dim, not an event or fact table.

`core.products` is a thin silver **VIEW** = `SELECT * FROM dw-main-bronze.integrationprod.core_products`.
The physical is a real **TABLE** (not another view), Datastream-CDC-replicated from coredb's Postgres
`public.core_products`.

## Grain & keys
- **Grain:** one row per MNTN product line. Exactly 3 rows live (verified 2026-07-19).
- **Primary key:** `product_id` (INT64). Values: `1=PTV`, `2=Select`, `3=QuickFrame`.
- **Referenced by:** `campaign_groups.product_id` (N:1 → this dim). No inbound FK from this table to anything else.

## Column meanings (only the non-obvious ones)
- **`product_id`** — PK / product-line enum. Only 3 values exist: `1=PTV` (Performance TV, the main product),
  `2=Select` (MNTN's media marketplace / PMP product), `3=QuickFrame`. Cluster key (trivial at 3 rows).
- **`name`** — human label ("PTV" / "Select" / "QuickFrame"). This is the display string; do not parse it for logic — key off `product_id`.
- **`create_time` / `update_time`** — TIMESTAMP columns (NOT epochs). ⚠️ These reflect the **Datastream CDC
  replication/backfill moment**, not true product age: all 3 rows carry `2025-03-18 22:07:50`, whereas PTV
  campaign_groups exist since 2010 and Select since 2025-07-31. Do NOT use these to date when a product line launched.
- **`datastream_metadata`** — STRUCT<uuid STRING, source_timestamp INT64>. CDC bookkeeping.
  - `source_timestamp` — **milliseconds** epoch of the CDC capture: `source_timestamp = UNIX_MILLIS(cdc_capture_time)`
    (verified 2026-07-19 — `TIMESTAMP_MILLIS` yields plausible 2025-12/2026-03 dates; `TIMESTAMP_MICROS` yields 1970).
    This is CDC capture time, **not** business time — prefer `update_time`/`create_time` for anything semantic (and even those are replication-stamped here). PTV and QuickFrame share the same `source_timestamp` (captured in one CDC batch); Select was captured later.
  - `uuid` — CDC row change identifier.

## Joins & relationships
- **`campaign_groups.product_id` (INT64) → `core.products.product_id`** — the one real join. Direction is
  **N:1**: `campaign_groups` is the many-side (~120K+ PTV groups + ~378 Select groups), this dim is the 1-side.
  **Fan-out risk: none** — joining the 3-row dim onto campaign_groups is a safe enum decoration (each group maps
  to exactly one product line; `product_id` is immutable per group). Reverse direction (dim → campaign_groups)
  fans out massively and is never what you want.
- **QuickFrame (id 3) has zero campaign_groups attached** (as of 2026-05-05), so an inner join against
  campaign data will never surface id 3 in practice — it exists only in the lookup.
- The four `campaign_groups` replica variants (`campaign_groups`, `campaign_groups_raw`, `public_campaign_groups`,
  `public_campaign_groups_raw`) all agree on `product_id`; use `public_campaign_groups_raw` for pipelines,
  `campaign_groups` for analytics (see `data_knowledge.md`).

## Gotchas
- **No `deleted` / `is_test` columns.** Unlike most `integrationprod` dims, this table has neither — the usual
  `WHERE deleted=FALSE AND is_test=FALSE` live-row filter **does not apply here** (all 3 rows are live). AUTO:SCHEMA
  lists only 5 columns; there is nothing to soft-delete.
- **`create_time`/`update_time` are not product-age.** They are the CDC replication stamp (all `2025-03-18`),
  not when the product launched. Date product lines from `campaign_groups` history instead.
- **`datastream_metadata.source_timestamp` is milliseconds** (per this table); do not assume micros. It is CDC
  capture time, not a business event time.
- **`name` is a display string, not a stable code.** Key logic off `product_id`; a rename of the label would not change the id.

## Cost & partitioning notes
- **Whole table = 235 bytes / 3 rows** (physical `numBytes`, verified 2026-07-19). No partition, no TTL;
  clustered on `product_id` (irrelevant at 3 rows). `require_partition_filter=false`.
- **`SELECT *` is fine here** — dry-run for `SELECT *` = **235 bytes** upper bound. There is no partition to
  filter and no cost trap; the normal "always filter the partition, avoid SELECT *" rule does not apply to this
  enum dim. Actual billed cost hits the 10 MB minimum-billing floor regardless. Safe to join freely as a decoration table.

## Example queries
```sql
-- Label campaign_groups with product line (N:1 safe decoration join)
SELECT cg.campaign_group_id, cg.advertiser_id, p.name AS product_line
FROM `dw-main-bronze.integrationprod.campaign_groups` cg
JOIN `core.products` p USING (product_id)
WHERE cg.deleted = FALSE AND cg.is_test = FALSE;

-- Inspect the whole dim (235 bytes)
SELECT product_id, name FROM `core.products` ORDER BY product_id;
```
