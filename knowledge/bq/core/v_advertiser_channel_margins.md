# core.v_advertiser_channel_margins

## Purpose
Per-advertiser, per-channel margin/pricing configuration — the take-rate and CPM economics MNTN applies to an advertiser's spend on a given channel (CTV vs display). Reach for it to answer "what margins / target CPM / platform fee / data margin does advertiser X run on channel Y." It is the **enriched** (`v_`) form of the base `core.advertiser_channel_margins` dimension: the view scopes everything to **partner 8** (hardcodes `partner_id = 8`) and backfills a derived `ad_buying_cpm` from channel-level defaults when the advertiser row leaves it NULL. **SENSITIVE** — margin/rate columns are private take-rate data; document schema only, never export or reproduce values.

## Grain & keys
- **Grain:** one row per **(advertiser_id, channel_id)** margin config. Verified empirically: 5,866 rows = 5,866 distinct `advertiser_channel_margin_id` = 5,866 distinct (advertiser_id | channel_id) pairs. An advertiser appears **once per channel** (≤2 rows/advertiser; 3,170 distinct advertisers across only 2 channels).
- **Primary key:** `advertiser_channel_margin_id` (surrogate, unique).
- **Foreign keys:** `advertiser_id` → `core.advertisers.advertiser_id`; `channel_id` → channel dim (only 2 values live: 1=display, 8=CTV per MNTN convention).
- **`partner_id` is NOT a key here** — it is a constant literal `8` injected by the view (see Gotchas).

## Column meanings (only the non-obvious ones)
- **partner_id** — **hardcoded literal `8` for every row** by the view; it is NOT sourced from the base table (the base `core_advertiser_channel_margins` has no `partner_id` column at all). Do not treat it as real partner data — all 5,866 rows = 8. It exists so the row can be interpreted within partner 8's margin economics and to drive the `ad_buying_cpm` fallback join.
- **ad_buying_cpm** — `COALESCE(base.ad_buying_cpm, base.target_cpm * channel_default_budget_margin)`. When the advertiser-level row carries an explicit `ad_buying_cpm` it passes through; when NULL it is **derived** as `target_cpm × budget_margin` where `budget_margin` comes from the channel-level defaults (`core_v_channel_margins`, filtered to `partner_id = 8`). So this column may not equal the raw base value.
- **budget_margin / platform_fee / target_cpm / data_margin** — advertiser×channel take-rate/pricing values. `platform_fee`, `target_cpm`, `data_margin` are `CAST(... AS NUMERIC)` normalizations of the base columns; `budget_margin` passes through unchanged. **SENSITIVE** — values are private.
- **create_time / update_time** — native `TIMESTAMP` of the config row's create/last-update (from Postgres CDC). These are true `TIMESTAMP`, **not** epoch integers — no unit conversion needed. Use these for recency (the CDC `datastream_metadata` capture column is dropped by the view).
- **channel_id** — only 2 distinct values in the whole view (1=display, 8=CTV). Combined with `advertiser_id` it forms the grain.

## Joins & relationships
- **advertiser_id → core.advertisers** (`advertiser_id`, PK) — 1:1 lookup, no fan-out. Join here to get `company_name` (advertiser_name is unreliable elsewhere).
- **channel_id → channel dim** — 2 values (display/CTV); 1:1 lookup.
- **Internal LEFT JOIN (already applied by the view):** base `core_advertiser_channel_margins` LEFT JOIN `core_v_channel_margins` ON `channel_id` AND `partner_id = 8`. Confirmed **1:1 / no fan-out** empirically: view output (5,866 rows) equals base table rows (5,866), so the channel-margins lookup added no rows. It supplies only the `ad_buying_cpm` fallback.
- **Fan-out risk joining OUT of this table:** grain is (advertiser_id, channel_id), so an advertiser can have up to 2 rows. Joining this view to a per-advertiser table **on `advertiser_id` alone fans out up to 2×** — join on **advertiser_id AND channel_id** to stay 1:1.

## Gotchas
- **partner_id = 8 is a literal, not data.** Every row is 8. Do not group/filter as if it were a real partner key, and do not assume other partners exist in this view.
- **No `deleted` / `is_test` columns.** The base table `core_advertiser_channel_margins` has neither (schema: only IDs, timestamps, NUMERIC margins, and `datastream_metadata`). The standard core-dimension soft-delete filter `deleted=FALSE AND is_test=FALSE` **cannot be applied here** — there is no soft-delete/test exclusion available.
- **`datastream_metadata` (CDC capture RECORD) is dropped by the view.** Present on the base table, absent here. Use `create_time` / `update_time`, not CDC capture time, for recency.
- **`ad_buying_cpm` is partly derived** (COALESCE fallback), so it can differ from the raw base column when the base value is NULL.
- **SENSITIVE — take rates.** `budget_margin`, `data_margin`, `platform_fee`, `target_cpm`, `ad_buying_cpm` are private margin economics. Never export, share externally, or reproduce example rows containing these values (take rates are private per workspace policy).

## Cost & partitioning notes
- Tiny dimension — **no partition, no TTL, no `require_partition_filter`**. The physical base `core_advertiser_channel_margins` is **clustered on `advertiser_channel_margin_id`** (the PK) for point lookups; the silver view is not itself clustered. Whole-view scans are trivially cheap; no filter is required for cost reasons.
- `SELECT *` dry-run = **346,443 bytes (~0.33 MB, upper bound)** [full-row column set].
- Real backing storage: base table `core_advertiser_channel_margins` `numBytes` = **616,092 bytes (~0.6 MB)**; `numRows` = 5,866. The view and its lookup partners add no material physical storage.
- Resolution chain: `silver.core.v_advertiser_channel_margins` → `dw-main-bronze.integrationprod.core_v_advertiser_channel_margins` (view) → `sqlmesh__integrationprod.integrationprod__core_v_advertiser_channel_margins__839763578` (derived view: injects partner_id=8, LEFT JOINs channel margins) → base TABLE `dw-main-bronze.integrationprod.core_advertiser_channel_margins`.
