# core.creative_groups

## Purpose
Dimension of **creative groups** — a creative group is a named set of creatives (banners / video ads) that rotate and/or A/B-test *within a single campaign*. It sits one level below `campaigns` in the entity hierarchy (`advertisers → campaign_groups → campaigns → creative_groups → creatives`) and carries the rotation/escalation/frequency-cap config plus optional 3P impression-tracking pixels. Reach for it to resolve a `group_id` (a.k.a. creative-group id) to its campaign, its name, its control-group status, or its per-day impression caps. It is a thin silver **view** (`SELECT *`) over the Postgres CDC replica `dw-main-bronze.integrationprod.core_creative_groups`; there is no SQLMesh layer.

## Grain & keys
- **Grain:** one row per creative group. Verified 1:1 — `COUNT(*) = COUNT(DISTINCT group_id) = 950,780` (2026-07-29). It is a **current-state snapshot**, not change history (one live row per group_id, refreshed in place by CDC).
- **Primary key:** `group_id`. This is the id joined from impression/bid/creative tables as the creative-group id.
- **Foreign keys:** `campaign_id` → `core.campaigns.campaign_id` (always populated — 0 NULLs; 250,948 distinct campaigns, so **N creative groups : 1 campaign**). `parent_group_id` → self (`group_id`) for nested/child creative groups. `user_id` → users. UI-side FKs: `ui_creative_group_id`, `mycreative_group_id`, `mycreative_video_group_id`, `template_group_id`. `delivery_mode_id` → a delivery-mode lookup.
- **No `deleted` / `is_test` columns** on this table (unlike many integrationprod dims). Use `active` (BOOL) as the liveness proxy — 697,160 of 950,780 rows (73%) are active; inactive groups are retained in the snapshot, not tombstoned.

## Column meanings (only the non-obvious ones)
- **`group_id`** — PK, the creative-group id. Clustering key of the physical table.
- **`active`** — liveness flag; the substitute for the missing `deleted`/`is_test` columns. 73% true.
- **`is_control` / `control_percentage`** — A/B holdout config. `is_control` marks a control creative group (only 283 of 950,780 rows — rare; count unchanged since 2026-07-19). `control_percentage` is the INT % of traffic routed to control.
- **`weight`** — rotation weight (relative share of impressions vs sibling groups in the same campaign).
- **`imp_limit_day` / `imp_limit_user_day`** — frequency caps: max impressions per group per day / per user per day. NULL = uncapped.
- **`escalation_type_id` / `escalating_order` / `escalation_limit`** — escalation-sequence config (serve groups in order, escalate after a threshold). **Almost never used** — `escalation_type_id` is set on only 309 rows (NULL on 950,471 / 99.97%); domain when set is {1, 2}. `escalation_limit` is NULL for 950,721 rows; when set it is a small integer that looks like a minutes budget (e.g. 1440 = 1 day, 2880 = 2 days, 10080 = 1 week).
- **`delivery_mode_id`** — delivery-mode enum. Live domain (2026-07-29): NULL (811,467 / 85% — default), `2` (93,039), `1` (44,845), `3` (1,429). Domain = {1, 2, 3} + NULL.
- **`impression_tracking`** — free-text 3P impression-tracking pixel/script snippet (Moat, DoubleClick, AdSafe, Weborama, etc.), NOT an enum. NULL for 935,914 rows (98.4%); a handful of dirty values ("impression", "imoression"). `override_impression_tracking` / `override_visit_tracking` (BOOL) control whether this group's tracking overrides the campaign/advertiser-level tracking. `url_prefix` / `url_suffix` / `click_url` / `display_url` are click-through URL fragments.
- **`ui_creative_groups_version`** — short hex hash (e.g. `7397edb7`) versioning the UI-side creative-group config; changes when the group is edited in the UI. **Not** a partition/cluster key.
- **`ui_creative_group_schedule`** — serialized (JSON) dayparting/scheduling blob; mostly NULL.
- **`snapshot`** / **`dpp_filter`** / **`has_dynamic`** — dynamic-product-personalization (DPP) config (`dpp_id` STRING) and a dynamic-creative flag; mostly NULL/false.
- **`create_time` / `update_time`** — TIMESTAMP (application-layer, UTC). `update_time` is the correct freshness column; range 2017-02-01 → live (max seen 2026-07-20, i.e. real-time CDC). Prefer these over CDC metadata.
- **`datastream_metadata.source_timestamp`** — CDC-capture epoch in **milliseconds** (13-digit). Verified: `source_timestamp` 1784520367749 ≈ `UNIX_MILLIS(update_time)` 1784520367736 (captured ~13 ms after the app write). This is the WAL-event time, **not** business update time — use `update_time` instead. `datastream_metadata.uuid` = replication-event UUID.

## Joins & relationships
- **→ `core.campaigns`** on `campaign_id` (this table N : 1 campaigns). campaigns is the parent; each campaign has ~3.8 creative groups on average (950,780 / 250,948). Safe direction (no fan-out): joining creative_groups → campaigns. Reverse (campaigns → creative_groups) fans out ~4x.
- **→ `core.creative_groups_x_creatives`** (junction/bridge, `group_id` ↔ `creative_id`) **→ `core.creatives`**. This is the many-to-many path from a creative group to its member creatives; the bridge fans out (one group → many creatives), so expect multiplication on the creative side.
- **Self-join** on `parent_group_id` → `group_id` for nested/child creative groups (703,657 rows / 74% have NULL parent = top-level; the rest are children).
- **UI-side FKs** (`ui_creative_group_id`, `mycreative_group_id`, `mycreative_video_group_id`, `template_group_id`) point at MyCreative/UI creative tables — one row each direction; usually not needed for delivery analysis.
- Impression/bid logs reference the creative group by its id; join those `group_id`-like fields back here 1:N (log side is many).

## Gotchas
- **No `deleted` / `is_test` filter available** — the standard `WHERE deleted=FALSE AND is_test=FALSE` integrationprod hygiene does **not** apply here (columns don't exist). Filter on `active = TRUE` if you want live groups only, but note inactive ≠ deleted (old/paused groups are retained).
- **Current-state snapshot, not history** — CDC overwrites the row in place, so there is exactly one row per `group_id`; you cannot reconstruct past states from this table.
- **Do not use `datastream_metadata.source_timestamp` as update time** — it is the CDC capture epoch (ms), not the app update. Use `update_time`.
- **950K rows is large for a "dimension"** — it accumulates every creative group ever created since 2017 (73% active). Don't assume it's a tiny lookup; a `SELECT *` scans the whole ~329 MB.
- **`escalation_*` and DPP columns are effectively vestigial** (≥98% NULL) — don't build logic assuming they're populated.
- **`impression_tracking` is dirty free text** — contains real 3P pixel HTML plus typo/junk values; treat as opaque strings, not a controlled vocabulary.

## Cost & partitioning notes
- **Unpartitioned** (`timePartitioning: None` on the physical table) and **clustered on `group_id`**. There is no partition column to filter — instead **prune columns** and/or filter on the `group_id` cluster key for point/range lookups.
- Physical backing: `numRows` 950,780, `numBytes` 328,752,376 (~0.31 GiB) — the value in `approx_logical_bytes`.
- **Measured dry-run:** `SELECT *` = 328,752,376 B (~0.31 GiB, full-table read — no partition to prune). `SELECT group_id, campaign_id` ≈ 15 MB. → **column pruning is the only cost lever, and it is ~21× here.** Avoid `SELECT *`.
- No TTL (dimension table; rows persist).

## Example queries
```sql
-- Resolve creative groups for a campaign, live only, cheap column set:
SELECT group_id, name, weight, imp_limit_day, is_control, active
FROM `dw-main-silver.core.creative_groups`
WHERE campaign_id = @campaign_id AND active = TRUE;

-- Point lookup on the cluster key:
SELECT group_id, campaign_id, name, update_time
FROM `dw-main-silver.core.creative_groups`
WHERE group_id = @group_id;
```
