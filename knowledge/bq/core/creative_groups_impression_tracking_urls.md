# core.creative_groups_impression_tracking_urls

## Purpose
Dimension holding the **3rd-party impression-tracking pixel URLs** that are attached to a creative group. When MNTN serves an impression for a creative group, it fires these tracking URLs (typically 1×1 gif beacons) so external measurement/verification vendors — observed in the data: Innovid (`s.innovid.com/1x1.gif`), iSpot (`pi.ispot.tv/v2/*.gif`) — can independently count the impression. Reach for it to answer "which verification/tracking pixels does this creative group carry?" or to inventory 3P-measurement coverage across creatives. It is a small config/lookup dimension, **not** an event/impression-count table — it stores the URL *templates*, not fired impressions.

A thin silver view (`SELECT *`) over the bronze CDC dimension `dw-main-bronze.integrationprod.core_creative_groups_impression_tracking_urls` (no SQLMesh).

## Grain & keys
- **Grain:** one row per `impression_tracking_url_id` — a single tracking pixel URL configured on a creative group. Verified: 83,425 rows = 83,425 distinct `impression_tracking_url_id`, zero nulls.
- **Primary key:** `impression_tracking_url_id` (also the physical cluster key).
- **Foreign keys:** `creative_group_id` → `core.creative_groups.group_id` (N:1); `user_id` → the internal user who added the URL (audit; `core.users`-family). `creative_group_id` has 74,864 distinct values across 83,425 rows → a creative group carries 1–22 tracking URLs (avg 1.11).

## Column meanings (only the non-obvious ones)
- **impression_tracking_url** — the full tracking-pixel URL fired on impression (usually a 1×1 gif beacon with vendor macros/query params). This STRING is ~71% of the table's bytes. Never NULL in sampled data.
- **server_side** — TRUE = MNTN fires the pixel server-side; FALSE = client-side (in the ad/player). ~86% TRUE (71,809 / 83,425).
- **is_post** — whether the tracking call is an HTTP POST (with `request_body`) rather than a GET beacon. **Empirically always FALSE** in current data (0 rows TRUE); the POST variant is defined in schema but unused.
- **request_body** — POST payload body, used only when `is_post` = TRUE. **Empirically always NULL/empty** given `is_post` is never set.
- **create_time** — business creation timestamp of the URL config (plain TIMESTAMP, UTC). Range 2020-06-05 → present; this is the real config age, and predates the CDC backfill (see `datastream_metadata`).
- **user_id** — internal MNTN user who added the tracking URL (audit FK, not an advertiser/account id).
- **datastream_metadata.source_timestamp** — Datastream **CDC-capture** epoch in **milliseconds** (`= UNIX_MILLIS`). Confirmed: `TIMESTAMP_MILLIS(min)` → 2025-12-19 (matches the physical table's creationTime; MICROS → 1970). This is capture time, **not** business time — its min ≈ backfill date, so use `create_time` for row age, never `source_timestamp`.
- **datastream_metadata.uuid** — CDC change-event id (dedup/lineage), not a business key.

## Joins & relationships
- **`creative_group_id` → `core.creative_groups.group_id`** — partner grain: one row per `group_id` (945,751 rows, clustered by `group_id`). **This table → creative_groups is N:1 (safe, no fan-out).** The reverse — **creative_groups → this table is 1:N and fans out up to 22×** (a group can have 22 tracking URLs); if you join creative_groups to this table, expect one output row per tracking URL, so pre-aggregate (COUNT / STRING_AGG) or de-dupe if you want one row per group.
- **`user_id`** → internal user dimension (audit only); not needed for most analyses.
- Not an event table: do **not** join to impression/cost logs on `impression_tracking_url_id` to count fired impressions — this stores URL *config*, not events.

## Gotchas
- **No soft-delete / test columns.** This table has no `deleted`, `is_test`, or `active` column (unlike most `integrationprod` dims). You cannot filter to "live" rows here — every configured URL is present, including historical ones. Liveness must be inferred via the parent `creative_groups.active` if needed.
- **`is_post` / `request_body` are dead columns** in current data (always FALSE / NULL) — don't build logic that assumes they're populated.
- **`source_timestamp` ≠ row age.** It reflects CDC capture (min ≈ 2025-12-19 backfill), not when the URL was created. Use `create_time` for age/recency.
- **Unpartitioned** — there is no date partition to filter; the only cost lever is column selection (see below). Every query full-scans the table, but it is tiny (~22 MB).

## Cost & partitioning notes
- **Physical is an unpartitioned dimension TABLE** (not a view internally): 83,425 rows, ~22.7 MB, clustered by `impression_tracking_url_id`, no TTL. No partition column exists, so there is nothing to prune by date — the one lever is **avoid `SELECT *`** because the `impression_tracking_url` string dominates storage.
- Dry-run byte estimates (labeled by column set), all full-scan since unpartitioned:
  - `SELECT *` → **22,737,881 bytes (~21.7 MiB)** — full table.
  - `SELECT impression_tracking_url` (URL string only) → **16,247,961 bytes (~15.5 MiB)** — the URL alone is ~71% of the table.
  - `SELECT impression_tracking_url_id, creative_group_id` (the two keys) → **1,334,800 bytes (~1.27 MiB)** — ~17× cheaper than `SELECT *`.
- Clustering on `impression_tracking_url_id` helps point-lookups / key joins on that column; there is no benefit for `creative_group_id` filters (not a cluster key on this table).

## Example queries
```sql
-- Tracking-pixel inventory for a set of creative groups (N:1 join, no fan-out)
SELECT t.creative_group_id, t.impression_tracking_url, t.server_side
FROM `core.creative_groups_impression_tracking_urls` t
WHERE t.creative_group_id IN (1182797, 1182798, 1182799);

-- One row per creative group: count + list of tracking URLs (pre-aggregate to avoid 1:N fan-out)
SELECT creative_group_id,
       COUNT(*) AS n_tracking_urls,
       STRING_AGG(impression_tracking_url, ' | ') AS urls
FROM `core.creative_groups_impression_tracking_urls`
GROUP BY creative_group_id;
```
