# core.media_plan

## Purpose
The CTV **media plan** dimension. A media plan is MNTN's per-advertiser CTV publisher-allocation recommendation (which networks — CBS, HBO Max, NBC… — get what budget share) generated by the olympus media-planning service. This view is a thin `SELECT *` over the Postgres CDC mirror `bronze.integrationprod.core_media_plan`. Reach for it to (a) identify active-media-plan advertisers/campaign_groups, (b) read the accepted publisher allocation via `media_plan_publishers`, or (c) audit plan-vs-actual delivery. Launched Oct 2025 (earliest `create_time` 2025-10-02); still small (~1,600 rows).

## Grain & keys
- **Grain:** one row per **`media_plan_id`** — i.e. one *plan version*. Confirmed unique: 1,586 rows = 1,586 distinct `media_plan_id` (2026-07-19).
- **Primary key:** `media_plan_id`.
- **Foreign keys:** `advertiser_id` → `core.advertisers`; `campaign_group_id` → `core.campaign_groups`. Both are always populated (0 NULLs).
- **A campaign_group accumulates many plan *versions* over time** (each regeneration/manual edit is a new `media_plan_id`): up to 29 rows for one `campaign_group_id`. But **at most ONE is active** — `campaign_group_id` filtered to `media_plan_status_id = 3` is 1:1 (max active-plans-per-cg = 1, verified 2026-07-19). Older versions are retired to status 8. 70 distinct advertisers, 457 distinct campaign_groups across the 1,586 rows.

## Column meanings (only the non-obvious ones)
- **`media_plan_status_id`** — plan lifecycle state. Only three values exist; distribution as of 2026-07-19 (a CDC dimension, so counts drift as plans retire 3→8): **8 = retired/superseded/inactive** = 1,148 (the bulk; every prior version of a regenerated plan lands here), **3 = active** = 370 (the live plan; unique per campaign_group), **1 = draft** = 68. Sum = 1,586. No `deleted`/`is_test` column exists on this table — **status 8 is the soft-delete/retire mechanism**, not a boolean flag.
- **`deliverability_classification`** — categorical delivery risk: `high` / `medium` / `low`, or **NULL**. NULL is common (1,070 of 1,586 ≈ 67.5%, 2026-07-19) and is **concentrated on retired plans** (888 of the 1,070 NULLs are status 8), with nearly all drafts unclassified too (67 of 68 status-1 rows NULL); even active plans are often NULL (115 of 370 status-3 rows) — treat NULL as "unclassified," not as a risk level. Business rule (from prose): worst individual guardrail wins; an in-flight plan running >3 days and >90% target pace is upgraded to `high`.
- **`is_manual`** — TRUE = plan was manually created/edited by the user; FALSE = auto-generated by olympus. Manual plans tend to have NULL `regeneration_run_id`.
- **`regeneration_run_id`** — STRING batch id of the olympus regeneration run that produced this version. **NULL for 1,068 of 1,586 rows** (manual and older/pre-instrumentation plans); 38 distinct run ids otherwise. New column not in the older `data_catalog.md` prose.
- **`original_recommendations`** — JSON: the publisher recommendations with budget %s and rationale as first emitted by the planner (the *accepted/edited* per-publisher rows live in `core.media_plan_publishers`). This column is **98% of the table's bytes** (see Cost) — do not select it unless you need it.
- **`datastream_metadata.source_timestamp`** — INT64 epoch in **MILLISECONDS** (Datastream CDC source commit time). Verified: `TIMESTAMP_MILLIS(source_timestamp)` = 2026-07-03 06:06:23 ≈ `update_time` 2026-07-03 06:06:22; `TIMESTAMP_MICROS` yields 1970 (wrong). `datastream_metadata.uuid` is the CDC row uuid. Note: `create_time`/`update_time` are **native TIMESTAMP** columns — the millisecond unit applies only to this nested `source_timestamp`.

## Joins & relationships
- **`media_plan_id` → `core.media_plan_publishers.media_plan_id`** — partner grain: one row per (plan × publisher). This is **1:N fan-out** (3–29 publisher rows per plan, median 16, 2026-07-19; `max_networks` config was 25 pre-Feb-2026, 15 after — but observed counts run higher/lower than config, so use the empirical range). Joining here multiplies media_plan rows by the publisher count — aggregate on the publisher side or expect fan-out. **Note:** 35 plans (all status 8) have **zero** rows in `media_plan_publishers`, so an INNER JOIN silently drops them; all 370 active (status 3) and 68 draft (status 1) plans have publisher rows, so the canonical `status = 3` query is unaffected.
- **`advertiser_id` → `core.advertisers.advertiser_id`** — partner grain: one row per advertiser. media_plan→advertisers is **N:1 (safe)**: many plan versions map to one advertiser. Use `advertisers.company_name` for names (per workspace gotcha, `fpa_advertiser_verticals.advertiser_name` is unreliable).
- **`campaign_group_id` → `core.campaign_groups.campaign_group_id`** — partner grain: one row per campaign_group. media_plan→campaign_groups is **N:1 (safe)** (up to 29 plan versions to one cg). The reverse (campaign_groups→media_plan) fans out unless you filter `media_plan_status_id = 3`, which restores 1:1.
- **Plan-vs-actual delivery join:** `media_plan_publishers.name` matches `sum_by_ctv_network_by_day.domain` exactly ("CBS"="CBS", "HBO Max"="HBO Max"; cross-validated TI-748). When measuring delivery, scope impressions to the plan's `campaign_group_id` only (see Gotchas).

## Gotchas
- **No `deleted` / `is_test` columns** — unlike most `integrationprod` dims, this table has neither. Do NOT apply the usual `deleted=FALSE AND is_test=FALSE` filter (it will error). Filter on `media_plan_status_id` instead: `= 3` for active plans, exclude `8` to drop retired versions.
- **"Active media-plan advertisers" ≠ "beta list."** Being provisioned doesn't mean live — always require `media_plan_status_id = 3`. Canonical query: `SELECT DISTINCT advertiser_id FROM core.media_plan WHERE media_plan_status_id = 3`.
- **Version explosion per campaign_group:** each regeneration/edit adds a new `media_plan_id` (status 8 for the old one). Selecting all rows for a campaign_group returns history; take `media_plan_status_id = 3` (or `MAX(create_time)`) for the current plan.
- **Delivery-audit scoping:** when comparing plan vs actual, ONLY count impressions from campaigns in the plan's `campaign_group_id`. Including all advertiser campaigns produced wildly wrong "plan not followed" results that were actually ±3% on-plan (TI-748).
- **Per-publisher *scores* are NOT in BQ** — they're computed transiently in memory and stored as JSON in GCS (`media-plan-artifacts` bucket, `media-plan/{version}/{advertiser_id}/{plan_id}/response.json`): score_semantic, score_performance_*, score_quality, score_spendability, score_cpm_efficiency, score_scale, score_combined. BQ only has `original_recommendations` (budget %s + rationale) and the accepted rows in `media_plan_publishers`.
- **Config drift over time:** `max_networks` 18 (Oct 2025) → 25 → 15 (Feb 3 2026, PERML-412); `min_allocation` 1% → 0.5%. Plans before Feb 2026 have 25–26 publishers; after, 16. Publisher counts are not comparable across that boundary.

## Cost & partitioning notes
- **Not time-partitioned** (`timePartitioning = null` on the physical table); **clustered on `media_plan_id`**; no TTL (CDC dimension). Small: 1,586 rows / **9.42 MB** total backing storage (numBytes, 2026-07-19).
- **The one filter/projection that matters: avoid `SELECT *` — never pull `original_recommendations` unless needed.** Dry-run (2026-07-19), labeled by column set:
  - `SELECT *` (all 11 cols incl. JSON): **9,420,035 bytes (9.42 MB)**
  - `SELECT original_recommendations` (JSON only): **9,246,378 bytes (9.25 MB)** — the JSON alone is **98%** of the table.
  - `SELECT media_plan_id, advertiser_id, campaign_group_id, media_plan_status_id` (4 narrow INT cols): **50,752 bytes (~50 KB)** — a **~185x** reduction vs `SELECT *`.
- Since there's no partition column, "always filter the partition" doesn't apply; the effective lever is the **column projection** above plus filtering `media_plan_status_id` / clustering on `media_plan_id` (prunes when you filter/join by plan id). At ~9 MB, even a full scan is trivially cheap regardless.

## Example queries
```sql
-- Advertisers with a live media plan (never pull original_recommendations here)
SELECT DISTINCT advertiser_id
FROM `dw-main-silver.core.media_plan`
WHERE media_plan_status_id = 3;

-- Current plan per campaign_group + its accepted publisher allocation
SELECT mp.campaign_group_id, mp.media_plan_id, mp.deliverability_classification,
       p.name AS publisher, SAFE_CAST(p.percentage AS INT64) AS budget_pct
FROM `dw-main-silver.core.media_plan` mp
JOIN `dw-main-silver.core.media_plan_publishers` p USING (media_plan_id)  -- 1:N fan-out
WHERE mp.media_plan_status_id = 3
ORDER BY mp.campaign_group_id, budget_pct DESC;
```
