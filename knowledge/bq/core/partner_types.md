# core.partner_types

## Purpose
Enum lookup dimension that decodes `partner_type_id` into a human-readable partner category. It classifies the rows in `core.partners` (79 partners) into 3 buckets: Demand Side Partner (DSP), Supply Side Partner (SSP), and Mobile Attribution. Reach for it whenever you need the label for a `partner_type_id`, or to filter/group partners by category. It is a 3-row static reference table — not an event or fact table.

## Grain & keys
- **Grain:** one row per partner type (3 rows total — the full enum domain).
- **Primary key:** `partner_type_id` (INT64; also the sole cluster key on the physical table).
- **No `deleted` / `is_test` columns** — this table has neither, so the standard `deleted=FALSE AND is_test=FALSE` dimension filter does not apply here. All 3 rows are live by definition.

## Column meanings (only the non-obvious ones)
- **`partner_type_id`** — enum key. Live domain (verified `SELECT DISTINCT ... ORDER BY partner_type_id`):
  - `1` = Demand Side Partner (DSP)
  - `2` = Supply Side Partner (SSP)
  - `3` = Mobile Attribution
- **`name`** — the display label for the enum value (strings above). Not a slug/code; it's the full parenthetical name.
- **`datastream_metadata.source_timestamp`** — Datastream CDC **capture** epoch in **milliseconds** (verified: `TIMESTAMP_MILLIS(1766121490653)` = 2025-12-19 05:18:10 UTC, a plausible recent snapshot; `TIMESTAMP_MICROS` yields 1970, ruling out microseconds). This is NOT a business event time — it marks when CDC last snapshotted the row. All 3 rows share the identical `source_timestamp` and `uuid`, i.e. they were captured in one batch snapshot (there is no per-row `create_time`/`update_time` on this table to prefer instead).
- **`datastream_metadata.uuid`** — CDC batch/change identifier, shared across all 3 rows here.

## Joins & relationships
- **`core.partners`** (physical `bronze.integrationprod.core_partners`, ~79 rows) — `partners.partner_type_id` → `partner_types.partner_type_id`. This table is the **parent (the "1" side)**: each partner carries exactly one `partner_type_id`, so `partners ⋈ partner_types` is **1:1 from the partners side** and **1:N from the partner_types side** (one type → many partners). No fan-out when you join partners onto partner_types (you're only decoding a label). `core.partners` has its own `deleted`/`is_test`? — it does not expose those either; it has `partner_id, name, description, created_at, partner_type_id, datastream_metadata`.
- No other table in the batch keys off `partner_type_id` here; treat this purely as the decode dim for `partners`.

## Gotchas
- **Only 3 values ever.** If a query returns a `partner_type_id` not in {1,2,3}, it came from stale/joined data, not this table.
- **`source_timestamp` is CDC-capture, not business time** — do not use it to reason about when a partner type was created or changed. It is milliseconds, not the microseconds/nanoseconds used by some event tables; resolve per-column, per-table.
- **No soft-delete / test flags.** Do not add a `deleted=FALSE AND is_test=FALSE` filter here — those columns don't exist and the filter would error. This is a departure from most `core.*` dimensions.
- **`object_type` nuance:** `silver.core.partner_types` is a thin VIEW (`SELECT * FROM bronze.integrationprod.core_partner_types`); the physical is a real unpartitioned `TABLE`, clustered on `partner_type_id`.

## Example queries
```sql
-- decode partner category onto the partners dimension (no fan-out; partner_types is the parent)
SELECT p.partner_id, p.name AS partner_name, t.name AS partner_type
FROM `core.partners` p
JOIN `core.partner_types` t USING (partner_type_id)
ORDER BY p.partner_id
```
