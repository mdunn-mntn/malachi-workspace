# core.pixel_integration_types

## Purpose
Static enum lookup for the **e-commerce pixel integration** platform an advertiser wired their MNTN
conversion pixel through. Reach for it only to put a human-readable name on the
`pixel_integration_type_id` FK carried by `core.pixel_integrations` (per-advertiser e-commerce
integration rows). Thin silver view over the bronze CDC dimension `core_pixel_integration_types`.
This is the *integration-method* taxonomy (how the pixel was installed) — NOT the conversion-event
taxonomy; event/conversion classification lives elsewhere (`conversion_log.conversion_type`,
`core_advertiser_conversion_types`, `data_sources` id 23 = "MNTN Pixel").

## Grain & keys
- **Grain:** one row per pixel integration type (enum value). 8 rows live today.
- **Primary key:** `pixel_integration_type_id` (also the sole cluster key on the physical).
- **Live domain (SELECT DISTINCT, 2026-07-19):** 1=shopify, 2=magento, 3=prestashop, 4=manual,
  5=mntn-wordpress-plugin, 6=gtm, 7=sans-pixel, 8=reset.
- **No `deleted` / `is_test` columns** exist on this dim (only the 3 AUTO:SCHEMA columns) — the usual
  `deleted=FALSE AND is_test=FALSE` live-row filter does not apply; every row is live.

## Column meanings (only the non-obvious ones)
- **`pixel_integration_type_id`** — enum PK, values 1-8 (see live domain above). `4=manual` is the
  fallback "hand-installed / no platform" case; `7=sans-pixel` = no pixel; `8=reset` = reset state.
- **`name`** — lowercase slug of the platform (`shopify`, `magento`, `gtm`, ...). Display label; not a
  join key.
- **`datastream_metadata.source_timestamp`** — CDC-capture epoch in **MILLISECONDS**
  (= `UNIX_MILLIS(capture_time)`; `TIMESTAMP_MILLIS(1766121416352)` = 2025-12-19 05:16:56 UTC —
  `TIMESTAMP_MICROS` mis-decodes it to 1970). This is when the Datastream CDC job last snapshotted the
  row, **not** a business/create time. All 8 rows currently share one identical value = a full-table
  re-snapshot; do not treat it as a per-row event time. `datastream_metadata.uuid` is the CDC change id.
  There is no `create_time`/`update_time` column here to prefer instead (unlike `core_pixel_integrations`,
  which has both) — the timestamp is CDC-only.

## Joins & relationships
- **`core.pixel_integrations`** (partner, grain = one row per `pixel_integration_id`, i.e. per
  advertiser e-commerce integration) → `pixel_integrations.pixel_integration_type_id = pixel_integration_types.pixel_integration_type_id`.
  - FROM `pixel_integrations` TO this dim = **N:1, safe** (each integration has exactly one type; no fan-out).
  - FROM this dim TO `pixel_integrations` = **1:N, fans out** (one type → many advertiser integrations).
  - `pixel_integrations` also carries `advertiser_id`, `shop_base_url`, `tracking_status`,
    `conversion_status`, `create_time`/`update_time` — join there for the per-advertiser detail.
- No other FKs; this is a leaf lookup dim.

## Gotchas
- **Not the conversion-event taxonomy.** This names the *install method* (shopify/gtm/manual), not
  what event fired. For event/revenue classification use `conversion_log.conversion_type`,
  `core_advertiser_conversion_types`, or `data_sources` (id 23 = "MNTN Pixel"). Confusing the two is the
  main pitfall.
- **No soft-delete columns** — nothing to filter; all 8 rows are current. Rows are effectively static
  (added only when MNTN ships a new integration platform).
- **`source_timestamp` is CDC capture time, not business time**, and is shared across all rows — never
  use it to order or date individual types.

## Cost & partitioning notes
- **No partition, no TTL.** Physical `core_pixel_integration_types` is an 8-row / 517-byte TABLE
  clustered on `pixel_integration_type_id`. There is no cost trap and no partition filter to apply —
  a full `SELECT *` scans 517 logical bytes (billed at the 10 MB minimum: dry-run of all 3 columns
  billed 0.01 GB tier-1, essentially free). Load it whole and join.
- `approx_logical_bytes: 517` = `bq show` numBytes on the bronze physical.

## Example queries
```sql
-- Label an advertiser's e-commerce integrations with the platform name.
SELECT pi.advertiser_id, pi.pixel_integration_id, pit.name AS integration_type,
       pi.shop_base_url, pi.tracking_status
FROM `dw-main-silver.core.pixel_integrations` pi
JOIN `dw-main-silver.core.pixel_integration_types` pit
  USING (pixel_integration_type_id)
WHERE pi.advertiser_id = 31357
```
