# core.partners

## Purpose
Small reference dimension of MNTN's **integration/platform partners** — the demand platforms (DSPs/social),
supply-side exchanges (SSPs), and mobile-measurement partners MNTN transacts with. Reach for it to resolve a
`partner_id` (on `campaigns`, `core_private_marketplace_deals`, spend/bidder tables) to a human name/type.

**Do NOT confuse with `tpa.direct_data_partners`** — that is the DDP *data-vendor* billing/usage registry
(5x5, 33Across, Predactiv, …) keyed by `data_source_id`. `core.partners` is a different universe:
inventory/platform partners (e.g. **Sovrn / FMX = partner_id 68**, a PMP inventory partner — DS33 data-feed
decisions do not touch it). Two separate "partner" concepts; do not join or equate them.

## Grain & keys
- **Grain:** one row per integration/platform partner. 79 rows total (live).
- **Primary key:** `partner_id` (INT, currently 1–79; clustered).
- **Referenced by (FK in):** `campaigns.partner_id`, `core_private_marketplace_deals.partner_id`, plus
  `partner_id` in spend_log / bidder tables. This table is always the "one" side (N:1 lookup).

## Column meanings (only the non-obvious ones)
- **`partner_id`** — PK, small int (1–79). Clustered. The FK carried by `campaigns` / PMP-deal / spend / bidder
  rows.
- **`partner_type_id`** — enum, live domain `{1, 2, 3}` (from `SELECT DISTINCT`). Semantics inferred from the
  member names (no companion `*_partner_types` lookup dim was located — treat as descriptive):
  - **1 = demand platforms / social** (8 rows): Facebook, Trade Desk, Instagram, Pinterest, Snapchat, Twitter,
    Beeswax, Steelhouse.
  - **2 = supply-side exchanges / SSPs** (66 rows — the bulk): Telaria, SpotX, Magnite, FreeWheel, Samsung,
    Index Exchange, Xandr Monetize, Thirty Three Across, Sovrn/FMX, … This is the inventory-supply universe.
  - **3 = mobile-measurement partners (MMPs)** (5 rows): AppsFlyer, Adjust, Kochava, Branch, Singular.
- **`created_at`** — TIMESTAMP, the **business** creation time of the partner row (ranges back to 2018). Use
  this for partner age — NOT `datastream_metadata.source_timestamp`.
- **`name` / `description`** — human labels; `description` frequently NULL/blank.
- **`datastream_metadata.source_timestamp`** — CDC-capture epoch in **MILLISECONDS**
  (`TIMESTAMP_MILLIS(source_timestamp)` = 2025-12-19; MICROS gives 1970, so ms not µs). It is the Datastream
  **snapshot load time**, identical (`1766121437210`) across every row — NOT a per-row change time and NOT
  business time. `datastream_metadata.uuid` = Datastream row identifier.

## Joins & relationships
- **`campaigns.partner_id` → `core.partners.partner_id`** — N:1. `campaigns` is the fan-out side (many campaigns
  per partner); joining FROM `campaigns` onto `partners` is a safe lookup (partner_id is unique here, no fan-out).
- **`core_private_marketplace_deals.partner_id` → `partners.partner_id`** — N:1. Names the exchange partner on a
  PMP deal.
- **spend_log / bidder tables** carry `partner_id` as an exchange/platform FK (per prose); same safe N:1 lookup.
- No FK *out* of this table (it is a leaf lookup dim). Safe to left-join from any fact on `partner_id` without
  row multiplication.

## Gotchas
- **No `deleted` / `is_test` columns.** This CDC dim has only the 6 columns in AUTO:SCHEMA — the standard
  `deleted=FALSE AND is_test=FALSE` live-row filter **does not apply and will error** if added. All 79 rows are
  treated as live.
- **Not the DDP registry.** `core.partners` (inventory/platform partners, keyed `partner_id`) ≠
  `tpa.direct_data_partners` (data-vendor billing, keyed `data_source_id`). Same word, different table — never
  equate or join across them. Sovrn appears in BOTH worlds separately: `partner_id 68` here (PMP inventory) and
  `data_source_id 33` in the DDP registry (data feed) — distinct decisions.
- **`partner_type_id` labels are inferred** from member names, not from a lookup table; if precise type
  semantics matter, verify against `name` rather than trusting the 1/2/3 gloss.
- **`source_timestamp` is a single constant snapshot time**, not a change timestamp — do not use it to detect
  which partner rows changed when; use `created_at` for business time.

## Cost & partitioning notes
- **Unpartitioned, clustered on `partner_id`.** 79 rows / **7,326 bytes** physical (`bq show numBytes`). A full
  `SELECT *` dry-run = **7,326 bytes** (the whole table) — same-column-set as the physical size, i.e. nothing to
  prune. No partition filter is possible or needed; scan freely. Clustering on `partner_id` only helps
  point-lookups by id.
- **One filter to always apply:** none required (tiny lookup). If you only need id→name/type, project just the
  columns you need — but at 7 KB it is immaterial.

## Example queries
```sql
-- resolve a partner_id to name + type
SELECT partner_id, name, partner_type_id
FROM `dw-main-silver.core.partners`
WHERE partner_id = 68;   -- Sovrn / FMX (SSP inventory partner)

-- attach partner name to campaigns (safe N:1 lookup, no fan-out)
SELECT c.campaign_id, c.partner_id, p.name AS partner_name, p.partner_type_id
FROM `dw-main-silver.core.campaigns` c
LEFT JOIN `dw-main-silver.core.partners` p USING (partner_id)
WHERE c.deleted = FALSE AND c.is_test = FALSE;
```
