# core.campaign_group_padding_overrides

## Purpose
Manual override table: for the small set of campaign groups that need a non-default
**padding multiplier**, one row records the override factor plus a free-text note pointing at
the PER Jira ticket that requested it. It is an exceptions/allow-list — only 31 campaign groups
of the many thousands in the system have a row here. A campaign group with **no** row uses the
default padding (effectively no override). Reach for it when you need to know which campaign
groups were manually padded and by how much, and why (the PER ticket in `notes`).

## Grain & keys
- **Grain:** one row per `campaign_group_id` that has an override. 31 rows = 31 distinct
  `campaign_group_id` (verified: `COUNT(*) = COUNT(DISTINCT campaign_group_id) = 31`).
- **Primary key / join column:** `campaign_group_id` (unique here; the physical bronze table is
  clustered on it).
- **No surrogate id / version column** — one current row per campaign group (CDC-replicated
  current state, not history).

## Column meanings (only the non-obvious ones)
- **padding** — the override multiplier, stored as **text**, not a number. Observed values:
  `"1.01"`, `"1.05"`, `"1.1"`, `"1.10"`, `"5"`, `"1"`. Older rows read as small multipliers
  (1.01–1.10, i.e. a 1–10% pad); recent rows (Mar–Apr 2026) use bare `"5"` and `"1"`, so the
  encoding/scale is **not internally consistent** — always `CAST(padding AS FLOAT64)` and treat
  the unit as unverified from this table alone. The exact quantity the factor multiplies
  (budget vs bid vs pacing target) is set by the consuming pacing/bidder service, not knowable
  from this dimension; confirm downstream before assuming "budget padding".
- **notes** — free text; in practice the PER Jira ticket(s) that authorized the override
  (e.g. `"PER-1922"`, `"PER-5908 PER-5959"`, `"PER-6038 | PER-6070 | … | PER-6127"`). Provenance,
  not a machine field.
- **create_time / update_time** — Postgres business timestamps. `update_time` ≥ `create_time`
  when a row was later re-padded (e.g. cg 108364 created 2026-02-25, updated 2026-03-04). Use
  `update_time` for "last changed."
- **datastream_metadata.source_timestamp** — Datastream **CDC-capture** epoch in
  **MILLISECONDS** (`= UNIX_MILLIS(capture_time)`; verified: `TIMESTAMP_MILLIS(1766121426493)`
  → 2025-12-19, `TIMESTAMP_MICROS` → 1970, so ms not µs). This is replication time, **not**
  business time — most rows share `1766121426493` (the initial backfill/snapshot load, matching
  the physical table's creation time), with only later-edited rows carrying newer values. Prefer
  `create_time`/`update_time` for anything business-meaningful. `datastream_metadata.uuid` is the
  CDC row-change id.

## Joins & relationships
- **`campaign_group_id` → `dw-main-bronze.integrationprod.campaign_groups.campaign_group_id`**
  — the campaign group dimension. Partner grain: **1 row per campaign group** → this is a
  **1:1** join (both sides unique on `campaign_group_id`). **No fan-out risk.** All 31 rows
  match a live `campaign_groups` row (verified). This table is a **sparse subset**, so join it
  as a `LEFT JOIN` *from* `campaign_groups` and coalesce a missing `padding` to the default.
  Filter the `campaign_groups` side with `deleted=FALSE AND is_test=FALSE` for live campaign
  groups (those columns live on `campaign_groups`, not here).
- Sibling views on the same physical family: `core.campaign_group_padding_overrides_vw`
  (integrationprod `core_campaign_group_padding_overrides_vw`) is a view variant of the same
  data; this doc covers the base `SELECT *` view over the `core_…` table.

## Gotchas
- **No `deleted` / `is_test` columns here.** This dimension has neither — do not add the
  standard live-row filter to *this* table (it will error); apply it on the joined
  `campaign_groups` instead.
- **`padding` is a STRING with mixed formatting** (`"1.10"` vs `"1.1"`, and bare `"5"`/`"1"`).
  Never compare or aggregate it as text; `CAST(... AS FLOAT64)`. The numeric scale/unit is not
  self-describing — verify against the consuming service.
- **Not history.** One current row per campaign group; for as-of/version history use the
  archives family (`archives_campaign_group_archives`), not this table.
- **`datastream_metadata.source_timestamp` is CDC-capture time, not edit time** — most rows
  carry the one-time backfill timestamp. Don't use it as "when the override was set."
- **No prose oracle existed** for this table in `data_catalog.md` / `data_knowledge.md` at
  enrichment time — all claims here are from live schema + sampling.

## Cost & partitioning notes
- **No partition** (physical bronze table has `timePartitioning: None`) and **no TTL**. It is a
  tiny CDC dimension — **31 rows, 2744 bytes** total (`bq show numBytes`). There is no partition
  filter to apply and no scan-cost trap; a full read is a rounding error.
- Cost figures (all from `bash .claude/scripts/bq_run.sh --dry_run`):
  - `SELECT *` (all 6 columns) over the view → **2744 bytes** upper bound (whole table).
  - Any real query bills the **10 MB minimum**, so column pruning is irrelevant here.
- Physical is clustered on `campaign_group_id`, which helps the 1:1 join but is immaterial at
  this row count.

## Example queries
```sql
-- Current padding overrides with their authorizing PER ticket, live campaign groups only
SELECT
  p.campaign_group_id,
  CAST(p.padding AS FLOAT64) AS padding_factor,
  p.notes,
  p.update_time
FROM `core.campaign_group_padding_overrides` p
JOIN `dw-main-bronze.integrationprod.campaign_groups` g
  ON p.campaign_group_id = g.campaign_group_id
WHERE g.deleted = FALSE AND g.is_test = FALSE
ORDER BY p.update_time DESC;

-- Apply as an override on the campaign_groups side (default = no pad)
SELECT
  g.campaign_group_id,
  COALESCE(CAST(p.padding AS FLOAT64), 1.0) AS effective_padding
FROM `dw-main-bronze.integrationprod.campaign_groups` g
LEFT JOIN `core.campaign_group_padding_overrides` p USING (campaign_group_id)
WHERE g.deleted = FALSE AND g.is_test = FALSE;
```
