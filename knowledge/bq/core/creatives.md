# core.creatives

## Purpose
Master dimension for every creative (ad unit) in the platform: the served ad's metadata, HTML/JS ad markup, ad-server payload, physical size, media type, and its owning advertiser. Reach for it to resolve a `creative_id` seen in a log/spend table into a human-readable creative (name, size, media type, video length, CaaS id) or to identify control-group creatives. It is a slowly-changing dimension, not an event stream.

## Grain & keys
- **Grain:** one row per creative — **5,722,718 rows = 5,722,718 distinct `creative_id`** (verified 2026-07-19; exact 1:1, no duplicates).
- **Primary key:** `creative_id` (INT64). Also the sole cluster key on the physical table.
- **Foreign keys (both mandatory — 0 NULLs observed):** `advertiser_id` → `core.advertisers` / `integrationprod.advertisers`; `creative_size_id` → `core.creative_sizes`. Optional: `user_id` → creating UI user (~75% NULL), `caas_video_id` → Creative-as-a-Service video (populated on ~6.2K rows).

## Column meanings (only the non-obvious ones)
- **`media_type_id`** — enum for the creative's media type. **No lookup table exists** in `integrationprod` (no `media_types`/`core_media_types`), so treat the id as opaque. Observed domain (2026-07-19): `2` (5.05M ≈ 88%, the dominant value), `9` (591K), `0` (41.6K), `NULL` (28.9K), `8` (11.0K), `3`, `1`, `7`, `6`, `10`, `4`, `5` (all <500). Never hand-map to names without a source.
- **`length`** — video duration in **seconds** (e.g. 15, 30). >0 on ~584.7K rows (~10%, the video creatives); NULL/0 for display.
- **`adcode`** — the served ad HTML/JS markup. **Large STRING; storage hog.** `is_adcode` = TRUE (~99.5%) flags rows that carry adcode.
- **`adserver_payload`** — ad-server tracking/config payload. **Large STRING; storage hog** (see Cost).
- **`is_control_creative`** — TRUE for control-group creatives used in lift/holdout tests (only ~2,424 rows).
- **`active`** — creative currently in rotation. ~50% TRUE (2.85M). Distinct from `deleted`; an inactive creative is still a live row.
- **`approved`** — creative passed review (~99.96% TRUE).
- **`deleted`** — soft-delete flag, but **always FALSE in the live snapshot** (0 rows deleted). The CDC replica appears to physically drop deleted creatives rather than retain a soft-deleted tombstone. There is **no `is_test` column** on this table.
- **`creative_hash_id`** — **100% NULL** (defined but entirely unpopulated as of 2026-07-19). Do not rely on it as a key.
- **`user_id`** — UI user who created the creative; ~75% NULL (only ~25% attributed).
- **`caas_video_id`** — Creative-as-a-Service video id; populated on ~6,164 rows (CaaS-authored videos only).
- **`a2_version`** — internal Adbuilder/creative-schema version (small ints, e.g. 2).
- **`fb_*` columns** — Facebook/social ad fields (headline, text, description, cta, click_url, display_url, url prefix/suffix, `fb_social`). Populated only for social creatives; NULL/empty for standard display & CTV.
- **`creative_location` / `static_image_location`** — asset URIs (rendered creative / static image).
- **`create_time` / `update_time`** — TIMESTAMP in **UTC**. `create_time` always populated; **`update_time` NULL on ~21,130 legacy rows (~0.37%)** — these pre-date update_time tracking and were the root cause of the Apr 2026 PSA cache-refresh incident (see Gotchas).
- **`datastream_metadata.source_timestamp`** — Datastream **CDC-capture** epoch in **MILLISECONDS** (verified: `1784520367501` ≈ `UNIX_MILLIS(update_time)=1784520367498`, i.e. captured ~3ms after the row write). It is capture time, NOT business time — use `create_time`/`update_time` for business logic. `datastream_metadata.uuid` = CDC event UUID.

## Joins & relationships
Physical lineage: `advertisers → campaign_groups → campaigns → core_creative_groups → core_creative_groups_x_creatives → core_creatives`.

| Join | Partner | Key | Cardinality | Fan-out risk |
|------|---------|-----|-------------|--------------|
| Creative → Advertiser | `core.advertisers` | `advertiser_id` | **N:1** (many creatives per advertiser) | none from this side; advertisers is 1-row-per-`advertiser_id` (filter `deleted=FALSE AND is_test=FALSE`) |
| Creative → Size | `core.creative_sizes` | `creative_size_id` | **N:1** | none; `creative_sizes` is 1-row-per-`creative_size_id` lookup |
| Creative ↔ Creative Group | `core.creative_groups_x_creatives` (junction) | `creative_id` (+ `group_id`) | **1:N** (a creative can belong to multiple groups) | multiplies rows per creative; dedup on `creative_id` if you only need creative attributes |
| Creative → Impression/spend logs | `logdata.*` / `cost_impression_log` / `spend_log` | `creative_id` (STRING `creative_alt_id` in some Beeswax/win logs) | **1:N** (one creative → many impressions) | **severe** — never join the dim to raw logs without aggregating the log side to `creative_id` first |

## Gotchas
- **No date partition.** This is a non-partitioned CDC dimension (see Cost). There is no time column to range-filter for cost; scan cost is driven entirely by which **columns** you select.
- **`deleted` is a no-op filter here** — always FALSE (deleted creatives are physically absent). Applying `WHERE deleted=FALSE` is harmless but prunes nothing. **No `is_test` column** — do not attempt the usual `is_test=FALSE` dimension filter on this table (it will error).
- **`creative_hash_id` is 100% NULL** — a defined-but-unpopulated column; not a usable join key.
- **`update_time` can be NULL on legacy creatives (~0.37%).** Any pipeline that full-refreshes by filtering on `update_time` silently skips these rows — this caused the Apr 15-16 2026 PSA spike (NULL-`update_time` VAST rows frozen in cache, expired from 14-day Redis TTL). Impact was limited to old creatives; newer Select creatives populate `update_time`. Use `create_time` as a fallback when a non-null timestamp is required.
- **`update_time`/`create_time` are UTC** — samples read one calendar day ahead of PST local; account for the offset before date-bucketing.
- **`media_type_id` has no lookup table** in `integrationprod`; do not invent name mappings.
- **View freshness:** `core.creatives` is a thin silver view directly over the bronze CDC replica (no SQLMesh layer, so no versioned `sqlmesh__*` physical) — it tracks Postgres near-real-time via Datastream.

## Cost & partitioning notes
Physical `dw-main-bronze.integrationprod.core_creatives`: **TABLE, non-partitioned, clustered on `creative_id`, no TTL. ~5.72M rows, ~19.56 GB backing storage (`bq show` numBytes = 19,555,701,313).** `time_unit: milliseconds` in front-matter refers to `datastream_metadata.source_timestamp` (the only epoch-int column); `create_time`/`update_time` are native TIMESTAMP.

**The one rule: select only the columns you need — never `SELECT *`.** With no date partition, column projection is the sole cost lever. Dry-run figures (2026-07-19, each labeled by column set):

| Query (column set) | Dry-run bytes | Note |
|--------------------|---------------|------|
| `SELECT *` (all 32 cols) | **19.56 GB** | full table |
| `SELECT adcode, adserver_payload` (2 heavy STRINGs) | **17.95 GB** | these two columns alone ≈ 92% of all bytes — avoid unless truly needed |
| `SELECT creative_id` (1 narrow INT) | **45.78 MB** | ~427x cheaper than `SELECT *` |
| `SELECT * WHERE creative_id = <one>` | **19.56 GB (dry-run)** | dry-run upper bound does **not** reflect cluster pruning; `creative_id`-equality/range filters prune at runtime via the `creative_id` cluster, but the estimate stays at full-table |

Practical guidance: project `creative_id, name, advertiser_id, creative_size_id, media_type_id, active, approved, length` for lookups (tiny); pull `adcode`/`adserver_payload` only for the specific creatives you need, filtered on `creative_id` so clustering can prune at runtime.

## Example queries
```sql
-- Resolve creative_ids to metadata (cheap — no heavy STRING columns)
SELECT creative_id, name, advertiser_id, creative_size_id, media_type_id,
       active, approved, length, caas_video_id, update_time
FROM `dw-main-silver.core.creatives`
WHERE creative_id IN (6440195, 6440194);   -- creative_id filter prunes via cluster at runtime

-- Control-group creatives for a lift test
SELECT creative_id, advertiser_id, name
FROM `dw-main-silver.core.creatives`
WHERE is_control_creative = TRUE;
```
