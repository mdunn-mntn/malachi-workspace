# core.advertisers_visit_tracking_urls

## Purpose
Configuration dimension for **outbound visit-tracking URLs** an advertiser has set up. Each row is a URL that MNTN fires when a **visit** event occurs — either a GET redirect/pixel (`is_post=false`) or a server-to-server POST webhook (`is_post=true`) whose JSON body carries macro placeholders (`${aid}`, `${campaign_name}`, `${cagid}`, …) that MNTN substitutes at fire time. Sampled destinations include advertiser landing pages, `webhooks.fivetran.com`, and advertiser API webhook endpoints (e.g. `api.mtailor.com/webhooks/...`). Reach for it when you need to know which advertisers have visit-side postbacks/pixels configured and where those visits are being forwarded. Sibling table `core.advertisers_impression_tracking_urls` is the impression-side analog (same shape).

## Grain & keys
- **Grain:** one row per configured advertiser visit-tracking URL. 381 rows, 381 distinct `visit_tracking_url_id` (verified 2026-07-19).
- **Primary key:** `visit_tracking_url_id` (unique; also the physical clustering key).
- **Foreign keys:** `advertiser_id` → `advertisers` / `core.advertisers` (1:N — an advertiser may have several visit URLs; max 6 observed, 349 distinct advertisers over 381 rows). `user_id` → internal MNTN user who created the config (nullable; 1 NULL row).

## Column meanings (only the non-obvious ones)
- **`visit_tracking_url`** — the destination URL fired on a visit. May contain macro placeholders resolved at fire time. Not deduplicated across advertisers.
- **`is_post`** — HTTP method flag: `true` = fire as POST with `request_body`; `false` = fire as GET (redirect/pixel). Overwhelmingly GET: only 2 of 381 rows are POST (verified 2026-07-19). Never NULL.
- **`request_body`** — POST body template, JSON with macro placeholders (`${aid}`, `${cagid}`, `${campaign_name}`, …). **Populated only when `is_post=true`** — NULL for the 379 GET rows (the two non-NULL rows are exactly the two `is_post=true` rows).
- **`create_time`** — native TIMESTAMP (UTC) when the config row was created in the source Postgres DB. Ranges 2023-09-29 → 2026-07-14. This is a config-creation timestamp, **not** an event time — the table is a lookup dim, not an event log.
- **`user_id`** — internal MNTN user id that created the URL config (FK to the users dim). Nullable (1 NULL).
- **`datastream_metadata`** — CDC replication metadata (STRUCT). `uuid` = Datastream event UUID. `source_timestamp` = **epoch milliseconds** of the source Postgres change event: `TIMESTAMP_MILLIS(datastream_metadata.source_timestamp)` yields valid 2026 timestamps; micros/seconds interpretations give 1970/year-56115 (verified 2026-07-19). For rows loaded via initial backfill this reflects the backfill read time, not `create_time`, so the two can diverge by hours — use `create_time` for config-age analysis, `source_timestamp` only for CDC/replication debugging.

## Joins & relationships
- **`advertiser_id` → `advertisers` (`core.advertisers` / `bronze.integrationprod.core_advertisers`)** — partner grain 1 row per advertiser (advertiser_id is that table's PK). This dim → advertisers is **N:1** (safe). advertisers → this dim is **1:N** (up to 6 URLs/advertiser): joining FROM advertisers fans out rows — pre-aggregate this side (e.g. `ARRAY_AGG` or `COUNT`) if you don't want duplicate advertiser rows.
- **`user_id` → users dim** — N:1, safe; nullable so use LEFT JOIN.
- Sibling **`core.advertisers_impression_tracking_urls`** — identical schema for impression-side tracking; do not confuse the two. There is no shared key beyond `advertiser_id`.

## Gotchas
- **No `deleted` / `is_test` columns** — unlike most `core.*` CDC dims, this table has neither, so the standard `WHERE deleted=FALSE AND is_test=FALSE` filter does not apply (and would error). Datastream keeps only current-state rows (deletes are applied, not soft-flagged), so all 381 rows are live configs; no dedup needed (`visit_tracking_url_id` already unique).
- **`request_body` is NULL for GET rows** — filter on `is_post=true` before assuming a body exists.
- **`create_time` ≠ `source_timestamp`** — see column notes; the CDC timestamp is millis and can lag config creation for backfilled rows.
- Tiny dimension (381 rows). Do not treat visit *counts* as living here — this is only the URL *configuration*; actual visit events live in the visit/conversion logs.

## Cost & partitioning notes
- **Unpartitioned** (physical `core_advertisers_visit_tracking_urls` has `timePartitioning: null`), clustered by `visit_tracking_url_id`, no TTL. There is no partition filter to apply.
- Trivially cheap: whole table is ~56,928 logical bytes / 381 rows (`bq show numBytes`). A `SELECT *` full scan dry-runs at ~0.01 GB billed (tier-1 minimum; measured 2026-07-19, all columns). No cost trap — filter/aggregate normally.

## Example queries
```sql
-- Advertisers with a POST (server-to-server webhook) visit postback configured
SELECT advertiser_id, visit_tracking_url, request_body, create_time
FROM `dw-main-silver.core.advertisers_visit_tracking_urls`
WHERE is_post = TRUE;

-- URL count per advertiser (fan-out check before joining to advertisers)
SELECT advertiser_id, COUNT(*) AS n_visit_urls
FROM `dw-main-silver.core.advertisers_visit_tracking_urls`
GROUP BY advertiser_id
ORDER BY n_visit_urls DESC;
```
