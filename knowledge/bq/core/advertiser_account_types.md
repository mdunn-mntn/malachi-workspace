# core.advertiser_account_types

## Purpose
Maps an advertiser to a single **account-type classification** — a coarse business
categorization (B2B, Mobile, Ecommerce, Gaming, Agency, Local, …). It is a thin silver
VIEW over the Postgres CDC dimension `bronze.integrationprod.core_advertiser_account_types`.
Reach for it only when you need this legacy classification for one of the handful of
advertisers it covers; it is **not** an authoritative account-type field for the whole
advertiser base (see Gotchas — only 16 advertisers are present).

## Grain & keys
- **Grain:** one row per **advertiser**. Verified: 16 rows / 16 distinct `advertiser_id`,
  max 1 row per advertiser — `advertiser_id` is effectively the primary key.
- **Key(s) / join columns:**
  - `advertiser_id` — PK of this table; FK → `advertisers.advertiser_id`.
  - `account_type_id` — FK → `core_account_types.account_type_id` (enum lookup).
- **Composite cluster key** on the physical table is `(account_type_id, advertiser_id)`.

## Column meanings (only the non-obvious ones)
- **account_type_id** — enum FK into `bronze.integrationprod.core_account_types`. Full domain
  (live `SELECT DISTINCT`, 2026-07-19): `1`=Ecommerce, `2`=B2B, `3`=Mobile, `4`=Gaming,
  `5`=Transparent Pricing, `6`=Agency, `7`=Local, `8`=Mobile With Conversions. Only **3** of
  these appear in this table: `3` Mobile (9 advertisers), `2` B2B (5), `8` Mobile With
  Conversions (2). Join to `core_account_types.name` for the label.
- **create_time** — TIMESTAMP the classification row was created in the source Postgres DB
  (business event time). Observed range 2023-10 → 2024-09 — a legacy, no-longer-maintained set.
- **datastream_metadata.source_timestamp** — INT64 **epoch MILLISECONDS**, verified:
  `1766121446404 = TIMESTAMP_MILLIS → 2025-12-19 05:17:26 UTC`. This is the **Datastream CDC
  read/backfill timestamp**, not a business event — every row shares the same value (the
  one 2025-12-19 backfill snapshot, matching the physical table's creationTime). Do **not**
  use it as a change/activity time; use `create_time` for that.
- **datastream_metadata.uuid** — Datastream per-change row UUID (CDC plumbing), not a business key.

## Joins & relationships
- **→ `advertisers` (`bronze.integrationprod.advertisers`, silver `core.advertisers`)** on
  `advertiser_id = advertisers.advertiser_id`. Partner grain: one row per advertiser (PK
  `advertiser_id`). Direction **N:1** from this bridge → advertisers, **no fan-out** (this
  table is a strict subset — 16 of many thousands of advertisers). Apply the advertisers-side
  live filter `deleted = FALSE AND is_test = FALSE` on the advertiser dimension when joining.
- **→ `core_account_types`** (enum lookup, PK `account_type_id`, ~8 rows) on `account_type_id`.
  Partner grain: one row per account type. **N:1**, no fan-out. There is no silver `core.account_types`
  view — read the label from `bronze.integrationprod.core_account_types` directly.

## Gotchas
- **Sparse / near-empty legacy table.** Only 16 advertisers are classified here. Treating this
  as "the advertiser's account type" for arbitrary advertisers will return nulls for almost
  everyone. Not a source of truth for advertiser vertical/classification at scale.
- **No `deleted` / `is_test` columns on THIS table.** The dataset-wide "filter
  `deleted=FALSE AND is_test=FALSE`" rule for `core.*` dimensions does **not** apply here —
  those columns live on the partner `advertisers` dim, not on this bridge. Apply the filter on
  the advertisers side of any join instead.
- **source_timestamp ≠ activity time.** It is a single CDC-backfill instant (2025-12-19) for
  every row; only `create_time` reflects when the mapping was actually made.
- Most enum values (Ecommerce, Gaming, Transparent Pricing, Agency, Local) are **unused** in
  this table — do not assume a code appears just because it exists in `core_account_types`.

## Cost & partitioning notes
- **No partition, no TTL.** Physical is a tiny clustered dimension (16 rows, 1120 bytes).
  `SELECT * FROM core.advertiser_account_types` dry-runs at **1120 bytes** (all 4 columns,
  whole view — 2026-07-19). Effectively free; a full scan is fine — there is no partition to
  filter. Clustering `(account_type_id, advertiser_id)` helps point lookups but is immaterial
  at this size.
- `approx_logical_bytes: 1120` = real backing storage (`bq show numBytes`).

## Example queries
```sql
-- Advertiser classification with human-readable label
SELECT a.advertiser_id, adv.company_name, a.account_type_id, t.name AS account_type
FROM `dw-main-silver.core.advertiser_account_types` a
JOIN `dw-main-bronze.integrationprod.core_account_types` t USING (account_type_id)
JOIN `dw-main-bronze.integrationprod.advertisers` adv
  ON adv.advertiser_id = a.advertiser_id
 AND adv.deleted = FALSE AND adv.is_test = FALSE
ORDER BY a.account_type_id;
```
