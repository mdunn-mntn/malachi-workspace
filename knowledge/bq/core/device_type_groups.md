# core.device_type_groups

## Purpose
Static lookup dimension that names the five device-type *groups* MNTN buckets inventory into and stores each group's default budget-allocation weight. It is the **parent** of `core.device_types` (individual device types roll up to one group). Reach for it when you need the human-readable group name for a `device_type_group_id`, or the default share of budget/optimization each device class should receive. It is `dw-main-silver.core.device_type_groups`, a thin `SELECT *` view over the bronze CDC table `dw-main-bronze.integrationprod.core_device_type_groups` (a real TABLE, 5 rows).

## Grain & keys
- **Grain:** one row per device-type group. Exactly 5 rows (fixed enum; no partition, no history).
- **Primary key:** `device_type_group_id` — the physical table is clustered on it. Domain: `-1` UNKNOWN (sentinel), `1` MOBILE, `2` COMPUTER, `3` CONNECTED_TV, `4` TABLET.
- **Referenced by:** `core.device_types.device_type_group_id` (the only FK to this table in `integrationprod`).

## Column meanings (only the non-obvious ones)
- **device_type_group_id** — PK. `-1` is the UNKNOWN sentinel (unmapped/unclassified device), not a real device class. `1`=MOBILE, `2`=COMPUTER, `3`=CONNECTED_TV, `4`=TABLET (verified via `SELECT DISTINCT`, all 5 rows).
- **device_type_group_name** — uppercase enum label (`MAX 255`). One-to-one with the id.
- **optimization_default_ratio** — NUMERIC(3,2). Default share of budget/optimization allocated to each device group. Across the four real groups it **sums to 1.00** (MOBILE 0.15 + COMPUTER 0.05 + CONNECTED_TV 0.70 + TABLET 0.10); UNKNOWN = 0. CTV is weighted heaviest (0.70), consistent with MNTN's CTV-first inventory. Treat it as a fractional weight, not a percent.
- **budget_floor / budget_ceiling** — NUMERIC(4,3), per-group budget-allocation bounds (fractional ratio, max 9.999). **Currently NULL for all 5 rows** — configured but unused as of the snapshot; do not assume a value exists.
- **datastream_metadata** — CDC (Datastream) capture metadata, NOT business time. `uuid` = Datastream row identifier. `source_timestamp` is epoch **milliseconds** (verified: `1766121447007` → `TIMESTAMP_MILLIS` = `2025-12-19 05:17:27 UTC`; `TIMESTAMP_MICROS` gives 1970, wrong). Anchor: `source_timestamp = UNIX_MILLIS(cdc_capture_time)`. All 5 rows share the identical timestamp — this dim was loaded in a single Datastream snapshot, so `source_timestamp` reflects the backfill, not per-row edit time. This table has **no** `create_time`/`update_time` column, so `source_timestamp` is the only recency signal.

## Joins & relationships
- **core.device_types** — `device_types.device_type_group_id = device_type_groups.device_type_group_id`. This dim is the **parent (1 : N)**: each group has 1–4 device types (verified: UNKNOWN→1, MOBILE→2, COMPUTER→1, CONNECTED_TV→4, TABLET→1; 10 device types total). Joining *from* device_types *to* this table is safe (N:1, no fan-out); joining *from* this table *to* device_types fans out ×1–4.
- Any fact/impression table exposing a `device_type_id` should join through `core.device_types` first to reach the group; there is no direct `device_type_group_id` on event tables in `integrationprod`.

## Gotchas
- **No `deleted` / `is_test` columns** — the usual `WHERE deleted=FALSE AND is_test=FALSE` dimension filter does **not** apply here (columns don't exist). All 5 rows are the live domain; there are no soft-deletes.
- **`-1` UNKNOWN is a sentinel**, not a device class — exclude it when computing real device-mix distributions.
- **budget_floor / budget_ceiling are all NULL** — don't build logic assuming they're populated.
- **Fixed enum** — treat ids as stable constants; a 6th group appearing is a schema event worth noting.
- **`source_timestamp` is CDC-capture (ms), not edit time** — all rows equal because of a single snapshot load; don't read per-row change history into it.

## Cost & partitioning notes
- **No partition, no TTL** — 5 rows / **399 bytes** total (physical `numBytes`). Full `SELECT *` measured **0 GB processed / 0.01 GB billed (tier-1 minimum)** via `bq_run.sh` — effectively free; there is no partition filter to apply and none is needed.
- Clustered by `device_type_group_id`, but clustering is inert at 5 rows.
- Safe to `SELECT *` or `CROSS JOIN`/broadcast against large fact tables.

## Example queries
```sql
-- Resolve a device_type_group_id to its name + default weight
SELECT device_type_group_id, device_type_group_name, optimization_default_ratio
FROM `dw-main-silver.core.device_type_groups`
ORDER BY device_type_group_id;

-- Roll individual device types up to their group name
SELECT g.device_type_group_name, COUNT(*) AS n_device_types
FROM `dw-main-silver.core.device_types` t
JOIN `dw-main-silver.core.device_type_groups` g USING (device_type_group_id)
GROUP BY g.device_type_group_name;
```
