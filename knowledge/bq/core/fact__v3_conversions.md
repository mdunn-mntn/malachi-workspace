# core.fact__v3_conversions

## Purpose
A **frozen backfill fact of attributed conversions** — one row per conversion event that was matched to a *verified impression*, with the winning impression's geo/domain/campaign context already joined onto the conversion. Reach for it when you need conversion events pre-attributed to an impression (impression_time / impression_epoch / domain / channel already resolved) without re-running the join against impression + conversion logs yourself.

Two things to know before using it:
- **It is a static snapshot, not a live table.** The partition column `time` spans **2025-09-01 → 2026-02-28 only** (verified 2026-07-19; the physical last-modified date of "today" is a metadata touch, not new data). Do not use it for anything after Feb 2026 — it does not update.
- **It is definitionally narrow.** Every row is `from_verified_impression = TRUE` **and** `click_through = TRUE` (both constant across all 17.08M rows). It is *not* the full conversion universe — for that, use `ui_conversions` / `conversion_log`.

## Grain & keys
- **Grain:** one row per **attributed conversion event** (conversion already matched to one verified impression). Verified live: 17,076,596 rows total.
- **No single-column primary key.** `guid` is **not** unique (Jan 2026: 2,434,514 rows vs 1,296,722 distinct guids ≈ 1.9 rows/guid) and `order_id` repeats too. A row is identified by the combination of the conversion (guid / order_id / event_time) and its matched impression.
- **Cluster keys:** `advertiser_id`, then `guid` — filtering or grouping on `advertiser_id` (and secondarily `guid`) prunes cheaply within a day.
- **Foreign keys (all N:1 → core dims):** `advertiser_id`, `campaign_id`, `campaign_group_id`, `group_id`, `creative_id`, `channel_id`, `metro_id`, plus `(advertiser_id, conversion_type)` → the conversion-type registry.

## Column meanings (only the non-obvious ones)
- **`time`** — the **attribution / record timestamp** and the DAY partition column. `time >= event_time` for **100%** of rows: it is when the conversion was recorded/attributed, always at or after the actual conversion. Filter on this for cost.
- **`event_time`** — the **actual conversion event** (pixel-fire) timestamp. Reaches back to 2025-05-05 (months before the partition window) because late/backfilled conversions carry an old event time under a recent `time`. Use this, not `time`, for "when did the conversion happen."
- **`impression_time`** — timestamp of the verified impression this conversion was attributed to. Never NULL (fully attributed fact).
- **`impression_epoch`** — the same impression instant as an **INT epoch in MICROSECONDS** (verified: magnitude 1.76e15 → /1e6 = valid 2025 Unix seconds; carries millisecond resolution so the last 3 digits are always `000`). `TIMESTAMP_MICROS(impression_epoch) ≈ impression_time` (the TIMESTAMP col is second-truncated, so they can differ by sub-second).
- **`elapsed_time`, `impression_elapsed_time`** — STRING interval text (Postgres/GP style, e.g. `"28 days 17:12:12"`, `"53 days 05:34:11.754"`), the precomputed lag from the conversion / impression to the record. Not numeric — do not compare as numbers; recompute from timestamps if you need arithmetic.
- **`conversion_type`** — the raw pixel event-type string (`Purchase`, `Lead`, `app_submitted`, `Confirmation`, `ViewContent`, `Page View`, `quoteStarted`, …). **Un-normalized and per-advertiser** (`Purchase` and `purchase` coexist as separate values). **`-101` is the sentinel for a NULL/untyped pixel** (~86% of rows) — matches the `ui_conversions` rendering and the `core_advertiser_conversion_types` sentinel row; never treat `-101` as a real event type. Excluding sentinels: `NOT REGEXP_CONTAINS(conversion_type, r'^-[0-9]+$')`.
- **`order_amt`** — NUMERIC; **never NULL** (uses `0` for no value; ~30.6% of rows are `0`). Same digit-extraction / fabricated-revenue caveats as the rest of the conversion pipeline apply (see Gotchas).
- **`order_curr`** — only two values, `"USD"` and `"usd"` — case variants of the same currency, not two currencies. Lower-case before grouping.
- **`order_id`** — advertiser-supplied order identifier; also carries sentinels like `"FirstOrder"`. Not unique.
- **`from_verified_impression`** — **constant TRUE** table-wide. No filtering power here; it is a definitional property of this fact.
- **`click_through`** — **constant TRUE** table-wide. Despite the CTV skew, this flag never varies, so it does not distinguish click- vs view-through here.
- **`classic`** — classic-attribution flag; TRUE for only ~0.09% (15,922 rows).
- **`disputed`** — always FALSE (0 rows) in this snapshot.
- **`exchange_id`** — **constant NULL** table-wide (not populated).
- **`channel_id`** — `8` = CTV (majority, ~10.45M), **NULL for ~38%** (~6.6M, channel not resolved), `1` = display (negligible, ~3,988). Expect NULLs; this is a CTV-dominant fact.
- **`domain` / `subdomain`** — the CTV app / network name the impression ran on (`"Fox News"`, `"NBC"`), `subdomain` often `"com"` or NULL — display-legacy fields repurposed for CTV inventory naming.
- **Geo (`country`, `region`, `city`, `postal_code`, `metro_id`, `group_id`)** — missing values are string/int **sentinels** `"-4"` / `"-3"` (e.g. `city="-4"`, `country="-4"`, `metro_id="-4"`, `group_id="-3"`), not NULL. Filter these out rather than checking `IS NULL`.

## Joins & relationships
Every documented join is **N:1 from this fact to a `core.*` CDC dimension** (many conversion rows → one dim row); fan-out risk is on the *dimension* side only if the dim has duplicate keys — filter dims with `deleted=FALSE AND is_test=FALSE` where those columns exist.
- `advertiser_id` → **core.advertisers** (dim, 1 row/advertiser). Use `advertisers.company_name` for the label (`fpa_advertiser_verticals.advertiser_name` is empty since 2025-12). Safe N:1.
- `campaign_id` → **core.campaigns**; `campaign_group_id` → **core.campaign_groups** (the UI "campaign"); `creative_id` → **core.creatives**; `group_id` → creative-group / line-item dim. All N:1, safe (filter `deleted=FALSE AND is_test=FALSE`).
- `(advertiser_id, conversion_type)` → **core_advertiser_conversion_types** registry (auto-registered on first sighting; sentinel rows `-100`/`-101`). N:1.
- `channel_id`: `8`=CTV, `1`=display (per platform enum). `metro_id` → DMA/metro lookup.
- `guid` links to the conversion pipeline (`ui_conversions` / `conversion_log`), but is **not** a unique key here (repeats), so any join on `guid` alone fans out — join on the full conversion identity or aggregate first.

*Partner dimension tables are CDC `core_*` views not live-verified in this pass; the N:1 direction and `deleted/is_test` filter are the safe fan-out guidance (prose, live-unverifiable).*

## Gotchas
- **Frozen window:** data only exists for `time` in **2025-09-01 … 2026-02-28**. A `time`-filter outside that (e.g. the 1-day 2026-07 dry-run) scans **0 bytes** and returns nothing. Not a live/refreshing table.
- **Definitional constants — do not filter on them expecting variation:** `from_verified_impression` (always TRUE), `click_through` (always TRUE), `disputed` (always FALSE), `exchange_id` (always NULL). Adding `WHERE from_verified_impression` or `WHERE click_through` is a no-op.
- **`time` ≠ conversion time.** `time` is the record/attribution timestamp; the conversion actually happened at `event_time` (which can predate the partition window by months). Aggregate revenue by `event_time` for business reporting, but you must still **filter the partition on `time`** for cost.
- **`conversion_type` is dirty:** mixed case, per-advertiser free text, `-101` sentinel for NULL (~86%), and the same pipeline is subject to **pentest / injection junk** (fabricated `order_amt` from digit-extracted SQLi payloads, one-day bursts of many distinct injection-string `conversion_type`s). Sanity-check outlier advertisers/days before trusting revenue. See data_knowledge.md "Conversion pixel payload anatomy" and the pentest sections.
- **`order_amt` never NULL** — it uses `0`; `~30.6%` of rows are `0`. `WHERE order_amt IS NULL` matches nothing; use `order_amt = 0` / `> 0`.
- **`order_curr` case:** `"USD"` and `"usd"` are the same currency — normalize case.
- **Geo/group sentinels** are `"-4"`/`"-3"` strings/ints, not NULL.
- **`impression_epoch` is microseconds** (not ms like `bidder_bid_events`, not ns like `spend_log`) — use `TIMESTAMP_MICROS()`.

## Cost & partitioning notes
- **Partition:** `time` (TIMESTAMP, **DAY**). `require_partition_filter = false` (BQ won't force it) — **but always add a `time` range anyway**; a bare `SELECT *` scans the whole physical.
- **Cluster:** `advertiser_id`, `guid` — add `advertiser_id` predicates to prune within a day.
- **Small table:** physical `sqlmesh__core.core__fact__v3_conversions__4225468191` = 17,076,596 rows / **4,886,360,285 bytes (≈4.55 GiB)**. TTL: none (no partition expiration).
- **Measured dry-runs (labeled by column set):**
  - `SELECT *`, no filter (all 31 cols, all 152 partitions) → **4.886 GB** upper bound (= full numBytes).
  - `SELECT *` for one empty day (`time` in 2026-07) → **0 bytes** (prunes to nothing; confirms partition = `time`).
  - Actual scan of 4 timestamp cols across the whole window (MIN/MAX aggregate) → **0.254 GB billed, 152 partitions** — ~19x cheaper than `SELECT *` purely from column pruning. Column-select aggressively.
- The full physical is only ~4.9 GB, so an all-time scan is cheap-ish, but still prefer `time`-bounded + column-selected queries.

## Example queries
```sql
-- Daily click-through/verified conversions + revenue for an advertiser (report by event_time, prune on time)
SELECT DATE(event_time) AS conv_day,
       COUNT(*) AS conversions,
       COUNTIF(order_amt > 0) AS revenue_conversions,
       SUM(order_amt) AS revenue_usd
FROM `dw-main-silver.core.fact__v3_conversions`
WHERE time >= TIMESTAMP('2026-01-01') AND time < TIMESTAMP('2026-02-01')   -- partition prune (required window: 2025-09..2026-02)
  AND advertiser_id = 31297                                                -- cluster prune
  AND NOT REGEXP_CONTAINS(conversion_type, r'^-[0-9]+$')                   -- drop -101 sentinel
GROUP BY conv_day
ORDER BY conv_day;
```
