# core.r2_roles_x_advertisers

## Purpose
Access-control bridge for the "roles v2" (r2) permission system in the MNTN app (CHAPI/UI account
management). It records, for each advertiser account, the set of role definitions that are scoped/
available to it. Reach for it only for user-permission / account-admin questions — **not** an ad-serving,
bidding, or performance table. Each `(role_id, advertiser_id)` row means "role R exists within
advertiser A's scope."

## Grain & keys
- **Grain:** one row per `(role_id, advertiser_id)` pair — verified `COUNT(*) = COUNT(DISTINCT pair) = 234,705` (no duplicate pairs; re-verified 2026-07-29).
- **Composite natural key / join columns:** `(role_id, advertiser_id)` — these are also the two clustering keys.
- **Shape:** near-full cross product — 39,237 distinct advertisers × 6 role_ids ≈ 235K rows; every advertiser carries essentially the same ~6 roles (per-role counts 38,992–39,226 out of 39,237 advertisers). Low discriminating value across advertisers.

## Column meanings (only the non-obvious ones)
- **role_id** — FK → `roles.roles_id`. Observed domain is exactly 6 values: `1` Super Admin (scope=mntn, unlimited_power), `9` Growth Manager (scope=mntn), `10` Restricted (scope=mntn), `14` Advertiser Admin (scope=customer, assignable_to `{advertiser}`), `15` Campaign Manager (scope=customer, assignable_to `{advertiser}`), and `11` which has **no matching row in the current `roles` dim** (orphan — a removed/renamed role; still present on ~38,992 advertiser rows; re-verified 2026-07-29 that roles dim holds {1,9,10,14,15} and 11 is absent).
- **advertiser_id** — FK → `advertisers.advertiser_id` (`core_advertisers`).
- **create_time** — business creation time from Postgres (when the role↔advertiser link was created). Ranges 2015-09-02 → present; this is the column to use for row age. There is no `update_time`.
- **datastream_metadata.source_timestamp** — CDC-capture epoch in **milliseconds** (Datastream), NOT business time. Resolved empirically: `MAX(TIMESTAMP_MILLIS(source_timestamp)) = 2026-07-20 04:48:49` equals `MAX(create_time)` exactly, while `TIMESTAMP_MICROS` yields 1970. Its min (2025-12-19) is when the CDC stream/backfill began (= table creationTime), not row age — do not use it as a business timestamp.
- **datastream_metadata.uuid** — Datastream per-change row id (CDC bookkeeping).

## Joins & relationships
- **role_id → `roles` (`roles_id`)** — small lookup dim (~13 rows). 1:1 point lookup, no fan-out. **Use a LEFT JOIN**: role_id `11` is an orphan and an INNER JOIN silently drops ~38K rows.
- **advertiser_id → `advertisers` (`advertiser_id`)** — advertiser dim is 1 row per advertiser. From the advertiser side this bridge is **1:N (~6 rows per advertiser)**: joining `advertisers` → this table fans out ~6×. To avoid fan-out, either filter `role_id` to a single role or `SELECT DISTINCT advertiser_id` before joining.
- No time/partition join key; it is a static-ish dimension keyed only on the composite pair.

## Gotchas
- **No `deleted` / `is_test` columns** — the standard `core.*` dim filter (`deleted=FALSE AND is_test=FALSE`) does not apply; every row is treated as live. (The partner `roles` dim also has no `deleted` column.)
- **role_id 11 is an orphan** — not present in the current `roles` dimension. INNER-joining to `roles` drops those ~38K rows; use LEFT JOIN if you need all advertisers.
- **source_timestamp ≠ business time** — it is ms CDC-capture; its floor (2025-12-19) reflects CDC onboarding of this table, not the age of the links. Use `create_time` for age.
- **No `update_time`** — only `create_time`; row mutations surface only via CDC (`source_timestamp`).
- **Near-full cross product / low analytic value** — every advertiser has essentially the same role set, so this table answers "who can act on account A" (RBAC), not anything about ad delivery or performance.
- **Silver is a thin view** — `silver.core.r2_roles_x_advertisers` is `SELECT * FROM dw-main-bronze.integrationprod.core_r2_roles_x_advertisers` (no SQLMesh); all metadata below is the physical bronze TABLE.

## Cost & partitioning notes
- **Unpartitioned** physical TABLE (`timePartitioning: None`); `require_partition_filter` = false. There is no partition column to filter — do not fabricate one.
- **Tiny table:** 234,705 rows / **16,429,350 bytes (~15.7 MiB) backing storage** (`bq show` numBytes, 2026-07-29). Full scans are cheap and safe here.
- **Clustered by `(role_id, advertiser_id)`** — point lookups on either/both prune via clustering.
- Measured dry-run/live figures (label the column set): grain query over `role_id, advertiser_id, create_time, datastream_metadata` scanned **0.007 GB processed / 0.01 GB billed** (tier-1 minimum); the `role_id`-only GROUP BY scanned **0.003 GB / 0.01 GB billed**. A `SELECT *` full scan reads the whole ~15.4 MiB.
- The one thing to always do: filter/GROUP on the cluster keys (`role_id`, `advertiser_id`); no partition filter is needed or possible.

## Example queries
```sql
-- Roles scoped to a given advertiser, resolved to names (LEFT JOIN keeps orphan role 11)
SELECT x.advertiser_id, x.role_id, r.name, r.scope, x.create_time
FROM `dw-main-silver.core.r2_roles_x_advertisers` x
LEFT JOIN `dw-main-bronze.integrationprod.roles` r ON r.roles_id = x.role_id
WHERE x.advertiser_id = <advertiser_id>
ORDER BY x.role_id;

-- Advertisers that carry a specific role (no fan-out — single role_id)
SELECT DISTINCT advertiser_id
FROM `dw-main-silver.core.r2_roles_x_advertisers`
WHERE role_id = 14;  -- Advertiser Admin
```
