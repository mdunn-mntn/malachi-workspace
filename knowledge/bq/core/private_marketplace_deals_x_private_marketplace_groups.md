# core.private_marketplace_deals_x_private_marketplace_groups

## Purpose
Junction/bridge that resolves the **many-to-many** membership between MNTN's private-marketplace
**deals** (`core.private_marketplace_deals`) and private-marketplace **groups**
(`core.private_marketplace_groups`). Each row asserts "this deal belongs to this group." Reach for it
whenever you need to expand a group into its member deals (or a deal into every group it participates
in) — e.g. rolling up deal-level PMP supply/pricing to the group a campaign targets, or listing which
groups a given deal is bundled into. It carries no measures of its own; it is pure linkage.

Thin silver VIEW (`SELECT *`) over the CDC dimension `dw-main-bronze.integrationprod.core_private_marketplace_deals_x_private_marketplace_groups`. No SQLMesh.

## Grain & keys
- **Grain:** exactly one row per `(private_marketplace_deal_id, private_marketplace_group_id)` pair.
  Verified 2026-07-29: `n_rows = n_pairs = 1111`, no duplicate pairs.
- **Composite primary key:** `(private_marketplace_deal_id, private_marketplace_group_id)`.
- **Foreign keys:**
  - `private_marketplace_deal_id` → `core.private_marketplace_deals.private_marketplace_deal_id` (PK, unique).
  - `private_marketplace_group_id` → `core.private_marketplace_groups.private_marketplace_group_id` (PK, unique).
- **Cardinality (2026-07-29):** 1,111 memberships spanning 942 distinct deals and 143 distinct groups
  (avg ~1.18 groups per participating deal, ~7.8 deals per group).

## Column meanings (only the non-obvious ones)
- **`user_id`** — **100% NULL in this table** (1,111/1,111 NULL on 2026-07-29). Do not rely on it to
  attribute who created the membership; it is never populated here. (The named partner dims carry their
  own `user_id`/`audit_user_id`.)
- **`create_time` / `update_time`** — TIMESTAMP business columns (row insert / last CDC update). Both
  are real dates (min create 2023-06-30, max update current). Use these, not the metadata epoch, for
  business time.
- **`datastream_metadata.source_timestamp`** — Datastream CDC-capture epoch in **MILLISECONDS**
  (`TIMESTAMP_MILLIS(source_timestamp) == update_time`, diff 0s; `TIMESTAMP_MICROS` yields 1970 — wrong).
  This is capture time, NOT business time; prefer `update_time`. `datastream_metadata.uuid` = CDC change id.
- No `deleted` / `is_test` columns exist on this bridge — the usual `deleted=FALSE AND is_test=FALSE`
  dimension filter does **not apply**; every row is treated as live.

## Joins & relationships
- **→ `core.private_marketplace_deals`** on `private_marketplace_deal_id`. Partner grain = 1 row per
  deal (PK unique, 1,073 rows). Bridge-to-deals is N:1, so each bridge row resolves to exactly one deal —
  **no fan-out** joining this way. Going the other direction (deal → its memberships) is 1:N.
- **→ `core.private_marketplace_groups`** on `private_marketplace_group_id`. Partner grain = 1 row per
  group (PK unique, 146 rows). Bridge-to-groups is N:1 — each bridge row resolves to exactly one group,
  **no fan-out**. Group → its member deals is 1:N (avg ~7.8).
- **Fan-out warning:** this table *is* the many-to-many. Joining a deal to a group *through* it multiplies
  a deal row by its group-membership count (and vice versa). When you only need one side's attributes,
  join the bridge to that single partner (N:1, safe); when you need both, expect the product.

## Gotchas
- `user_id` is entirely NULL — see column meanings.
- The membership is not soft-deleted here (no `deleted` flag). A removed membership disappears as a hard
  CDC delete; there is no tombstone row to filter out, but also no way to see historical memberships.
- `datastream_metadata.source_timestamp` is milliseconds and is capture time, not business time — don't
  use it for "when was this deal added to the group" (use `create_time`).
- Small, slowly-changing dimension (~1.1K rows). Do not treat it as an event/log table; there is no date
  partition to filter and no TTL.

## Cost & partitioning notes
- **Unpartitioned** (physical `timePartitioning: None`), clustered on
  `(private_marketplace_group_id, private_marketplace_deal_id)`. There is no partition column to filter;
  clustering lets a `WHERE private_marketplace_group_id = …` prune the (already tiny) scan.
- Whole-table `SELECT *` dry-run = **86,658 bytes (~85 KB)** on 2026-07-29 (equals physical `numBytes`).
  Cost is negligible at any column set; no filter is required for safety. Selecting only the two id
  columns is smaller still but immaterial at this size.
- `approx_logical_bytes: 86658` = physical backing storage (`bq show numBytes`).

## Example queries
```sql
-- Expand a PMP group into its member deals (N:1 bridge→deals, safe)
SELECT g.name AS group_name, d.private_marketplace_deal_id, d.name AS deal_name, d.floor_price
FROM `core.private_marketplace_groups` g
JOIN `core.private_marketplace_deals_x_private_marketplace_groups` x
  USING (private_marketplace_group_id)
JOIN `core.private_marketplace_deals` d
  USING (private_marketplace_deal_id)
WHERE g.private_marketplace_group_id = 36;
```
