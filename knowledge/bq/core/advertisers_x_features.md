# core.advertisers_x_features

## Purpose
Bridge (junction) table that records which product features / feature-flags are attached to each advertiser and whether each is turned on (`active`). It mixes two kinds of "features":
- **Legacy core entitlements** (`core_features.source IS NULL`) — business capabilities gated per advertiser, e.g. `MULTI_TOUCH_ENABLED`, `CAMPAIGN_GROUP_FREQUENCY_CAPS_ENABLED`, `CONFIGURABLE_BLOCKING`, `LEGACY_BUDGET_MINIMUMS`, `DELIVERABILITY_WIDGET`. For these `active` tracks row presence closely.
- **Harness UI feature flags** (`core_features.source = 'harness'`) — LaunchDarkly/Harness-style front-end rollout toggles, e.g. `BottomsUpKeywords` (BUK, feature_id 1047), `MNTNMatched_v3` (1117), `IncrementalityV2ShowTab`, `TPAExpressionV2`, `CampaignSplitTesting`. For these a row is very often written with `active=FALSE`, so the row's mere existence says nothing — you MUST filter `active = TRUE`.

Reach for it to answer "does advertiser X have feature/flag Y enabled?" — always joining `feature_id` to `core.features` for the human name and filtering `active = TRUE`.

## Grain & keys
- **Grain:** one row per (`advertiser_id`, `feature_id`) pair — verified: 198,352 rows = distinct `advertisers_x_features_id` = distinct (advertiser_id, feature_id) pairs (no duplicate pairs). ~33,781 distinct advertisers × 80 distinct features in use (of 87 defined).
- **Surrogate PK:** `advertisers_x_features_id` (also the cluster key).
- **Natural/composite key:** (`advertiser_id`, `feature_id`) — unique.
- **Foreign keys:** `advertiser_id` → `core.advertisers` (base `bronze.integrationprod.advertisers`); `feature_id` → `core.features` (`bronze.integrationprod.core_features`).
- **Live-row filter:** this table has **no `deleted` / `is_test` columns** (unlike most `core_*` dims). Its enable/soft-toggle is `active BOOL` — filter `active = TRUE` for "feature enabled." `active` has no NULLs (131,325 TRUE / 67,027 FALSE).

## Column meanings (only the non-obvious ones)
- **`active`** — the enable toggle (BOOL, never NULL). TRUE = feature/flag enabled for this advertiser; FALSE = row exists but the feature is off. This is the effective soft-delete/disable mechanism; there is no `deleted` column. For Harness-sourced flags, FALSE is common (e.g. `TPAExpressionV2`: 6,588 rows, 1 active; `BottomsUpKeywords`: 5,409 rows, 32 active), so **never treat row presence as "enabled."**
- **`feature_id`** — FK to `core.features`; NOT an inline enum. Join to `core.features.name` for the label and `core.features.source` to tell legacy entitlements (NULL) from Harness UI flags (`'harness'`). `core.features.default_value` (BOOL) is the org-wide default when an advertiser has no explicit row.
- **`advertiser_id`** — FK to `core.advertisers`. Never NULL here.
- **`create_time` / `update_time`** — native TIMESTAMP (UTC), not epoch ints; no unit conversion needed. Reflect Postgres row create/last-update captured by CDC.
- **`datastream_metadata`** — STRUCT<uuid STRING, source_timestamp INT64>: Datastream CDC bookkeeping (change UUID + source commit time). `source_timestamp` is the only epoch column and is Datastream microseconds; it is plumbing, not business data — ignore for analysis.
- **`advertisers_x_features_id`** — surrogate PK, also the physical cluster key.

## Joins & relationships
- **`feature_id` → `core.features`** (PK `feature_id`, 87-row lookup) — N:1, no fan-out. Adds `name`, `description`, `source`, `default_value`. Always join for a readable feature name.
- **`advertiser_id` → `core.advertisers`** (PK `advertiser_id`; base `bronze.integrationprod.advertisers`) — N:1 from this table's side, no fan-out. Use `advertisers.company_name` for the advertiser label (`fpa_advertiser_verticals.advertiser_name` is unreliable/empty — see data_knowledge).
- **Fan-out warning (reverse direction):** joining `core.advertisers` (or any per-advertiser table) **TO** this table fans out ~5.9× (198,352 rows / 33,781 advertisers ≈ 5.87 feature rows per advertiser, more for well-configured advertisers). To test one specific feature, pre-filter this table to a single `feature_id` **and** `active = TRUE` before joining, or the advertiser row multiplies once per feature.

## Gotchas
- **Row-existence ≠ enabled.** The #1 trap: a Harness flag row is written with `active=FALSE`. `WHERE feature_id = 1047` (BottomsUpKeywords) returns 5,409 advertisers, but only 32 are actually on — you need `AND active = TRUE`.
- **No `deleted` / `is_test` columns.** The standard `core_*` live filter does not apply; use `active = TRUE` instead. There is no test-advertiser scrub column on this table — filter test advertisers by joining `advertisers.is_test = FALSE` if needed.
- **Absence is not "disabled by default."** If an advertiser has no row for a feature, the effective value is `core.features.default_value`, not FALSE. Some entitlements default TRUE (e.g. `MULTI_TOUCH_ENABLED`, `CAMPAIGN_GROUP_FREQUENCY_CAPS_ENABLED`, `DELIVERABILITY_WIDGET`). Compute effective state as `COALESCE(x.active, f.default_value)` via a LEFT JOIN from the advertiser universe.
- **Two feature-id namespaces.** Legacy entitlement ids are small (1, 4, 9, 18, 1024…); Harness flag ids are large auto-generated numbers (513334, 1558584, 1922839…). Don't assume a contiguous enum range.
- **CDC freshness.** Values mirror Postgres via Datastream; `update_time` reflects the last source change, not query time.

## Cost & partitioning notes
- **Unpartitioned** (physical `timePartitioning: None`), clustered by `advertisers_x_features_id` — a surrogate id, so clustering rarely helps analytical filters (they hit `advertiser_id` / `feature_id`). Tiny table: **~17.1 MB total (198,352 rows)** — every query is a full scan; there is no partition to prune. The one filter that always matters is the **semantic** `active = TRUE` (+ a `feature_id` predicate), not a cost filter.
- **Dry-run byte estimates (2026-07-19):** `SELECT *` (all 7 cols incl the `datastream_metadata` struct) = **17,145,928 bytes (~16.35 MiB)**; narrow `SELECT advertiser_id, feature_id, active` = **3,371,984 bytes (~3.22 MiB)** — ~5× cheaper. The struct + timestamps dominate width, so avoid `SELECT *`; select the 2–3 columns you need.
- `approx_logical_bytes` = physical `numBytes` = 17,145,928 (real backing storage of the single physical table).

## Example queries
```sql
-- Advertisers with BottomsUpKeywords (BUK) ACTUALLY enabled (not just present)
SELECT x.advertiser_id, a.company_name
FROM `dw-main-silver.core.advertisers_x_features` x
JOIN `dw-main-silver.core.advertisers` a USING (advertiser_id)
WHERE x.feature_id = 1047   -- BottomsUpKeywords
  AND x.active = TRUE;

-- Effective feature state across all advertisers (row override else org default)
SELECT a.advertiser_id,
       COALESCE(x.active, f.default_value) AS effective_enabled
FROM `dw-main-silver.core.advertisers` a
CROSS JOIN (SELECT feature_id, default_value FROM `dw-main-silver.core.features` WHERE name = 'MULTI_TOUCH_ENABLED') f
LEFT JOIN `dw-main-silver.core.advertisers_x_features` x
  ON x.advertiser_id = a.advertiser_id AND x.feature_id = f.feature_id;
```
