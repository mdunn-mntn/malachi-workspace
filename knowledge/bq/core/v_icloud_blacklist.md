# core.v_icloud_blacklist

## Purpose
Per-advertiser **allowance matrix** for how iCloud Private Relay traffic is handled, across three
features: **verified visits, audience targeting, and conversion attribution**. Reach for it to answer
"is advertiser X allowed to use iCloud Private Relay signal for verified visits / audience / conversions?"

This is a **derived whitelist view built from a blacklist base table**. The underlying data table
`bronze.integrationprod.core_icloud_blacklist` lists only the advertisers that carry an iCloud
restriction (currently **2 rows**). The view expands that to **all advertisers** and flips the polarity:

- Advertiser **not** in the base blacklist → all three flags default to **TRUE (allowed)**, with a
  hardcoded placeholder `create_time = '2022-10-01 12:34:56'` and `update_time = NULL`.
- Advertiser **in** the base blacklist → each view flag = `NOT base_flag`, i.e. the base "blacklisted"
  TRUE becomes view **FALSE (not allowed)**, carrying the base row's real `create_time`/`update_time`.

Net effect: in the **view**, `TRUE = allowed / iCloud handling enabled`, `FALSE = blocked` — the
opposite polarity of the base `core_icloud_blacklist` table.

## Grain & keys
- **Grain:** one row per `advertiser_id` — **every** advertiser in `public_advertisers` (verified live:
  view rows = distinct advertiser_id = `public_advertisers` count = **38,440**; only **2** advertisers
  have any flag FALSE).
- **Primary key:** `advertiser_id` (1:1 with the advertiser dimension — no duplicates).
- **Join column:** `advertiser_id` → `advertisers.advertiser_id` / any table's `advertiser_id`.

## Column meanings (only the non-obvious ones)
- **`verified_visits` / `audience_targeting` / `conversion_attribution`** — three independent boolean
  *allowance* flags (view polarity: **TRUE = allowed / iCloud handling enabled**, **FALSE = blocked**).
  These are the **inverse** of the identically-named columns in the base `core_icloud_blacklist` table,
  where TRUE means "blacklisted". In practice the base always stores all-TRUE (fully blacklisted) rows,
  so a listed advertiser shows all-FALSE in the view. Non-listed advertisers are all-TRUE.
- **`create_time`** — for non-blacklisted advertisers this is a **hardcoded literal**
  `'2022-10-01 12:34:56'` from the view's default-allow branch, **not** a real per-advertiser timestamp.
  Only the ~2 blacklisted rows carry the base table's genuine `create_time` (e.g. `2022-10-01 00:06:10`).
  Do not treat `create_time` as an advertiser onboarding date.
- **`update_time`** — **NULL** for all default-allow (non-listed) advertisers; populated only when the
  base blacklist row was edited (e.g. advertiser 22955: `2022-11-04 17:37:42`). NULL here means
  "never in the blacklist / never edited", not "unknown".
- Note: the base `core_icloud_blacklist` table also carries a `datastream_metadata` RECORD
  (`uuid`, `source_timestamp` INT — Datastream CDC-capture metadata). The view does **not** expose it,
  so there is no epoch-int column to decode in this view; both timestamps are native `TIMESTAMP`.

## Joins & relationships
- **`advertiser_id` → `public_advertisers` / `advertisers` (1:1).** The view is driven by a LEFT JOIN
  against `public_advertisers`, so it emits exactly one row per advertiser — a clean 1:1 lookup, **no
  fan-out** when joined to any advertiser-grained table on `advertiser_id`.
- **Base data:** `bronze.integrationprod.core_icloud_blacklist` (the 2-row blacklist) is the only
  real data source; the view materializes the rest from `public_advertisers`.
- **No `deleted` / `is_test` columns** exist on this view (or the base table) — the standard
  `deleted=FALSE AND is_test=FALSE` dimension filter does **not** apply and cannot be used here.

## Gotchas
- **Polarity is inverted vs. the base table.** `v_icloud_blacklist.verified_visits = TRUE` means
  *allowed*; `core_icloud_blacklist.verified_visits = TRUE` means *blacklisted*. Never mix the two.
  Filter the view for restrictions with `WHERE NOT verified_visits OR NOT audience_targeting OR NOT
  conversion_attribution`.
- **Default-allow, not default-deny.** 38,438 of 38,440 advertisers are all-TRUE by construction, not
  because they were explicitly whitelisted. Only presence in the base blacklist changes anything.
- **`create_time` is a literal for most rows** (see column meanings) — useless as a real date except
  for the handful of blacklisted advertisers.
- **View resolves to a SQLMesh view, not a physical table.** `bronze.integrationprod.core_v_icloud_blacklist`
  → `sqlmesh__integrationprod.integrationprod__core_v_icloud_blacklist__2166105455` (itself a VIEW doing
  the `public_advertisers LEFT JOIN core_icloud_blacklist … UNION ALL …`). All SQLMesh physical metadata
  reads `numRows:0 / numBytes:0` — ignore it; the real row count is driven by `public_advertisers`.
- **No partition column, no TTL.** This is a small dimension view; filtering `advertiser_id` does **not**
  prune bytes (see cost notes).

## Cost & partitioning notes
- **No partition, no clustering, no TTL** — small dimension view. There is no partition filter to apply.
- **Trivially cheap.** Full `SELECT *` (all 6 columns) dry-run = **307,566 bytes (~0.0003 GB)**; a
  single-advertiser `WHERE advertiser_id = …` lookup dry-run = **307,542 bytes** — essentially
  identical (same 3 non-index columns projected). **A WHERE on `advertiser_id` does not prune** because
  the view recomputes the whole `public_advertisers` UNION; the cost is dominated by scanning
  `public_advertisers`, not by the tiny 2-row blacklist. `SELECT *` is fine here.

## Example queries
```sql
-- Restriction lookup for one advertiser (allowance = TRUE)
SELECT advertiser_id, verified_visits, audience_targeting, conversion_attribution
FROM `dw-main-silver.core.v_icloud_blacklist`
WHERE advertiser_id = 22607;   -- all three FALSE = blocked

-- All advertisers with ANY iCloud restriction
SELECT advertiser_id, verified_visits, audience_targeting, conversion_attribution, update_time
FROM `dw-main-silver.core.v_icloud_blacklist`
WHERE NOT verified_visits OR NOT audience_targeting OR NOT conversion_attribution;
```
