# core.flight_billing_types

## Purpose
Authoritative flight → billing-type map: for each flight (`core_flight_id`) it stores the
`billing_type_id` that drives how the flight is billed (CPM model). This is the **current source of
truth** for flight-level billing type — it supersedes the legacy `advertisers.billing_type_id` column,
which the reporting team (BAE/ray) no longer uses in spend logic. Reach for it whenever you need to
know a flight's billing model (e.g. splitting PTV Fixed CPM from other flights) or to attribute spend
by billing type.

Rows are derived and upserted by the **Gary** service (`gary-ql`) after budget processing — the
SELECT/Premier UI does not pass billing type on flight creation; Gary maps it from the campaign group's
`product_id`. (`gary-ql/src/gql/types/Budget/UiToCore.ts#L1026-L1037`, `.../data/Budget.ts#L1813-L1905`.)

## Grain & keys
- **Grain:** one row per flight — `core_flight_id` is the primary key. Verified 1:1 on 2026-07-29:
  74,769 rows = 74,769 distinct `core_flight_id`, zero duplicates. No history/versioning — a flight's
  billing type is upserted in place (see `update_time`), so there is at most one live row per flight.
- **Primary key:** `core_flight_id` (also the physical clustering key).
- **Join column:** `core_flight_id` → the flights dimension; `billing_type_id` is the enum value
  (no accessible bronze lookup table — see Joins).

## Column meanings (only the non-obvious ones)
- **`core_flight_id`** — the flight's primary key; join key to the flights dimension. PK here (1:1).
- **`billing_type_id`** — the CPM billing-model enum. Live domain on 2026-07-29 is **{1, 2}**
  (`SELECT DISTINCT`): `1` = 61,859 flights (~83%), `2` = 12,910 flights (~17%).
  - `2` = **PTV Fixed CPM** (per prose oracle, Tony Chen 2026-06-02). As of 2026-06-02 MNTN SELECT
    campaigns *also* share `billing_type_id = 2` — they are treated as equivalent in the current
    billing pipeline but are behaviourally distinct and are slated to be separated.
  - `1` = the dominant/default billing type (majority of flights). **Not** documented in the prose
    oracle nor resolvable to a label — the prose-referenced lookup `core.billing_types` does **not**
    exist under that name in `bronze.integrationprod` (only `core_flight_billing_types` itself and the
    unrelated `billing_billing_type_change_requests` exist). Treat `1` as "standard / non-Fixed-CPM"
    but confirm the exact label with Gary/reporting before relying on it. (drift — see Changelog.)
  - `3` = proposed new ID for MNTN SELECT (native impression cap), **not yet live** as of 2026-06-02;
    absent from live data on 2026-07-19. Tracked in PER-6526 (Gary/MSS to map SELECT cgs to `3` by
    `product_id`; downstream PCS / Pacing Engine / PROUI to be audited).
- **`create_time` / `update_time`** — TIMESTAMP (UTC), business-time of the row's insert / last upsert.
  Use these, not `datastream_metadata.source_timestamp`, for "when did this flight's billing type
  change." Data spans `create_time` 2025-05-12 → `update_time` 2026-07-18 (max, as of sync).
- **`datastream_metadata`** — STRUCT<uuid STRING, source_timestamp INT64>. CDC-capture metadata, **not**
  business time. `source_timestamp` is **epoch MILLISECONDS** (verified 2026-07-19:
  `TIMESTAMP_MILLIS(source_timestamp)` equals `update_time` to the second; `TIMESTAMP_MICROS` yields
  1970). `uuid` is the Datastream change-event id. Selecting this STRUCT dominates scan bytes (see Cost).

## Joins & relationships
- **→ flights dimension** on `core_flight_id`. This table is the **child/1:1 attribute** side: each
  flight has at most one billing-type row, so a `flights LEFT JOIN flight_billing_types USING
  (core_flight_id)` is 1:1 — **no fan-out**. Flights with no row here simply have no assigned billing
  type. (Partner-table exact name/grain not live-verified here; the join key is unambiguous and the
  fan-out-safe direction is flights → this table 1:1.)
- **`billing_type_id` → lookup:** the prose oracle names `core.billing_types` as the reference
  table for billing-type definitions, but **no such table exists** in `bronze.integrationprod`
  (verified 2026-07-19). Enum meanings currently live only in prose/tickets, not a queryable dim.
- **NOT related:** `billing_billing_type_change_requests` (advertiser-level payment-method change
  requests, domain `{INVOICE, STRIPE}`) is a different concept — do not join it to resolve
  `billing_type_id`.
- **Supersedes:** the legacy `advertisers.billing_type_id` column. Prefer this table for spend/billing
  attribution.

## Gotchas
- **No `deleted` / `is_test` columns.** Unlike most `integrationprod` dimensions, this table has neither
  soft-delete flag — the standard `WHERE deleted=FALSE AND is_test=FALSE` filter does **not** apply
  (and would error). Rows are upserted in place; there is no soft-delete tombstone.
- **`billing_type_id = 1` is unlabeled** (83% of rows) — see Column meanings. Do not assume it means a
  specific product; the accessible lookup is missing.
- **PTV Fixed CPM and MNTN SELECT are currently indistinguishable** here — both are `billing_type_id = 2`
  until PER-6526 introduces `3`. Any analysis that needs to separate SELECT from PTV must fall back to
  `campaign_groups.product_id` (1=PTV / 2=Select / 3=QuickFrame) in the interim, not this column.
- **Upsert grain, not append:** `update_time` moves when Gary re-derives a flight's billing type; there
  is no change history in this table (use `billing_billing_type_change_requests` only for the unrelated
  payment-method audit trail).
- **Timestamps are UTC.** Convert to Arizona Time (ATZ) when reconciling against MNTN UI figures.

## Cost & partitioning notes
- **Unpartitioned, clustered on `core_flight_id`** (physical `dw-main-bronze.integrationprod.core_flight_billing_types`:
  74,769 rows, ~5.83 MB, `timePartitioning: None`). No TTL. There is no partition filter to apply —
  the whole table is tiny; a full scan is cheap.
- **The one lever that matters: prune `datastream_metadata`.** Dry-run 2026-07-29:
  `SELECT *` = **5,831,982 bytes (~5.83 MB)**; `SELECT core_flight_id, billing_type_id` = **1,196,304
  bytes (~1.20 MB)**. The `datastream_metadata` STRUCT is ~80% of the bytes, so avoid `SELECT *` when
  you only need the mapping (~4.9x cheaper). Both figures are labeled by their exact column set.
- When joining a large table to this dim, filter/join on `core_flight_id` (the cluster key) and select
  only the columns you need.

## Example queries
```sql
-- Flight → billing type mapping (cheapest useful projection; prunes datastream_metadata)
SELECT core_flight_id, billing_type_id
FROM `dw-main-silver.core.flight_billing_types`;

-- Distribution of billing types (verify the live domain before relying on enum values)
SELECT billing_type_id, COUNT(*) AS n_flights
FROM `dw-main-silver.core.flight_billing_types`
GROUP BY billing_type_id ORDER BY billing_type_id;
```
