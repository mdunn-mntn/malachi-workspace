# core.mobile_apps

## Purpose
Tiny lookup dimension that registers each advertiser's mobile app so app-install / mobile targeting
and reporting can key off a stable internal `mobile_app_id` instead of a raw store identifier. Reach
for it to resolve a `mobile_app_id` to its app-store id (Android package or iOS App Store id), owning
advertiser, and partner, or to enumerate which apps an advertiser has registered. It is a thin silver
view over the Postgres CDC dim `bronze.integrationprod.core_mobile_apps` — 125 rows total (2026-07-19),
so it is effectively free to scan.

## Grain & keys
- **Grain:** one row per registered mobile app (`mobile_app_id`). Verified 1:1 — 125 rows = 125
  distinct `mobile_app_id`.
- **Primary key:** `mobile_app_id` (also the cluster key on the physical).
- **Foreign keys:** `advertiser_id` → advertiser dimension; `partner_id` → `core.partners.partner_id`.
- **`app_id`** is the natural/store key but is NOT unique here: 125 rows carry only 121 distinct
  `app_id` values (the same store id can be registered under different advertisers/partners).

## Column meanings (only the non-obvious ones)
- **`mobile_app_id`** — internal surrogate PK for the registered app; the stable key other systems
  should reference (not `app_id`).
- **`app_id`** — the app-store identifier as a STRING, mixed across two conventions: Android reverse-DNS
  package names (`com.pof.android`, `com.pinger.textfree`) and iOS App Store numeric track ids prefixed
  with `id` (`id917554930`, `id435588892`). No separate platform column — infer platform from the
  format (`id<digits>` = iOS, dotted string = Android). Not unique (see Grain & keys).
- **`active`** — BOOL soft-status flag (this dim has NO `deleted`/`is_test` columns). 95 active / 30
  inactive at 2026-07-29. Filter `active = TRUE` for the live app set; there is no other liveness gate.
- **`advertiser_id`** — owning MNTN advertiser. 57 distinct advertisers own the 125 apps (one advertiser
  can register many apps).
- **`partner_id`** — data/integration partner that supplied the app. Only 4 distinct values present
  (7, 14, 15, 78); partner 7 dominates (80 rows).
- **`datastream_metadata`** — CDC envelope STRUCT. `.uuid` = Datastream change-event id;
  `.source_timestamp` = INT64 **milliseconds** since epoch of the CDC capture (confirmed:
  `TIMESTAMP_MILLIS(source_timestamp)` yields 2025-12-19 … 2026-05-28, sensible dates; microseconds
  would give 1970). This is CDC replication time, NOT app registration/business time — there is no
  create/update business-time column on this dim, so `source_timestamp` is only a rough
  last-CDC-touch signal.

## Joins & relationships
- **`partner_id` → `core.partners.partner_id`** — partners is 1:1 on `partner_id` (79 rows = 79 distinct
  PK, verified). mobile_apps→partners is **N:1**, no fan-out (safe). Reverse (partners→mobile_apps) is
  1:N.
- **`advertiser_id` → advertiser dimension (keyed one-row-per `advertiser_id`)** — the canonical MNTN
  advertiser key (physical `bronze.integrationprod.advertisers`; note there is NO `core.advertisers`
  view — use the advertiser dim wherever it is surfaced, e.g. join through `campaigns`/`advertisers`
  by `advertiser_id`, or `company_name` for a label). mobile_apps→advertisers is **N:1** (safe);
  advertisers→mobile_apps is 1:N (an advertiser may have several registered apps).
- `partner_id` → `core.partner_types` is one hop further via `core.partners.partner_type_id` if a
  partner category is needed.
- Because it's a 125-row lookup, it is a safe **build/broadcast side** in any join — it never fans out
  a fact table beyond the multiplicity already implied by its keys.

## Gotchas
- **No `deleted` / `is_test` columns.** The standard `deleted=FALSE AND is_test=FALSE` dim filter does
  NOT apply here — those columns don't exist. Use `active = TRUE` for the live set instead.
- **`app_id` is not unique** — 4 duplicate rows share a store id under different advertiser/partner.
  De-dup on `mobile_app_id`, not `app_id`, if you need a per-app row.
- **Mixed platform encoding in one column** — an `app_id` starting with `id` + digits is iOS; a dotted
  package string is Android. No boolean/enum distinguishes them.
- **`datastream_metadata.source_timestamp` is CDC time, not business time** (milliseconds). Do not use
  it to reason about when an app was added or last edited in the product.
- View is `SELECT *` passthrough of the physical, so silver types show as `INT64`/`BOOL` where the
  Postgres source is `INTEGER`/`BOOLEAN` — no semantic change.

## Cost & partitioning notes
- **Unpartitioned, clustered on `mobile_app_id`.** The physical `core_mobile_apps` is a plain TABLE
  (125 rows, `numBytes` = 11,120 = ~11 KB); `timePartitioning: None`, `clustering.fields:
  [mobile_app_id]`. No partition filter is possible or needed.
- **The one filter to always apply:** `active = TRUE` (correctness, not cost) — there is no partition
  to prune.
- **Measured cost (2026-07-19):** `SELECT *`-equivalent full scan of all 125 rows processed ~0 GB and
  billed 0.01 GB — i.e. it hits BigQuery's 10 MB minimum-billing floor regardless of columns selected.
  Column projection cannot make it cheaper; this table is effectively free.

## Example queries
```sql
-- Live apps for an advertiser, with platform inferred from app_id format
SELECT
  ma.mobile_app_id,
  ma.app_id,
  IF(STARTS_WITH(ma.app_id, 'id'), 'ios', 'android') AS platform_guess,
  p.partner_id
FROM `dw-main-silver.core.mobile_apps` ma
JOIN `dw-main-silver.core.partners` p USING (partner_id)   -- N:1, no fan-out
WHERE ma.active = TRUE
  AND ma.advertiser_id = @advertiser_id
ORDER BY ma.mobile_app_id;
```
