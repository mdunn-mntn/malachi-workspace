# core.campaign_x_audiences

## Purpose
Junction (bridge) table that maps a **campaign** to the **audience(s)** it targets. Thin silver
view — `SELECT * FROM dw-main-bronze.integrationprod.core_campaign_x_audiences` — over the bronze CDC
replica of the Postgres `campaign_x_audiences` table. Reach for it to answer "which audience(s) is
this campaign attached to?" or the reverse "which campaigns use this audience?".

**Legacy / frozen — read before using.** Business writes stopped: the newest `create_time` is
**2023-12-15**, the same freeze date as the sibling `core.audiences` dimension. This is the old
core-schema audience-attachment model; the **live** per-campaign audience/targeting mechanism is the
`audience_audience_segments` expression (see `bronze.integrationprod.audience_audience_segments` /
`silver.archives.audience_segment_archives` in `data_catalog.md`). Treat this table as a historical
record for campaigns created on or before Dec 2023 — do not use it to determine current targeting.

## Grain & keys
- **Grain:** one row per `campaign_x_audience_id` (surrogate PK; 76,498 rows all distinct).
- **Natural key:** `(campaign_id, audience_id)` — also unique across the table (distinct pairs =
  row count). A campaign attaches an audience at most once.
- **Foreign keys:** `campaign_id` → `bronze.integrationprod.campaigns.campaign_id`;
  `audience_id` → `core.audiences.audience_id`; `segment_id` → core-era audience segment (nullable).
- **No `deleted` / `is_test` columns** — the usual dimension soft-delete/test filters do NOT apply
  here (they don't exist). Filter on partner tables (`campaigns`, `audiences`) if you need those.

## Column meanings (only the non-obvious ones)
- **campaign_x_audience_id** — surrogate PK; also the cluster key. Unique per row.
- **campaign_id** — FK to `bronze.integrationprod.campaigns`. Never NULL (0 nulls). All 76,498 rows
  resolve to a live campaign (0% orphan). ~76,490 distinct campaigns → a handful (8) of campaigns
  carry more than one audience row.
- **audience_id** — FK to `core.audiences.audience_id`. Never NULL. 47,022 distinct → audiences are
  reused across many campaigns.
- **segment_id** — core-era audience-segment reference; **~15% NULL** (11,576 of 76,498). Present
  only when the attachment carried a specific segment. Not every campaign/audience pair has one. The
  matching `core.*` segment dimension is not in this dataset region (see Joins); treat `segment_id`
  as a historical core-schema id, not a live `audience_segments` targeting id.
- **user_id** — **100% NULL** (0 of 76,498 populated). Column is present but unused/never captured in
  this CDC replica. Do not rely on it for who-created attribution.
- **create_time** — business creation timestamp of the attachment (TIMESTAMP, not epoch). Range
  2019-03-22 → **2023-12-15** (frozen). This is the field to use for business time.
- **datastream_metadata.source_timestamp** — CDC-capture epoch in **MILLISECONDS**
  (`= UNIX_MILLIS(cdc_capture_time)`; raw 1766121489618 → `TIMESTAMP_MILLIS` = 2025-12-19, sane;
  `TIMESTAMP_MICROS` = 1970, nonsense). This is Datastream snapshot/replication time, **NOT** business
  time — it can be years after `create_time` (rows created 2023 were last CDC-captured 2025). Prefer
  `create_time` for anything analytical. `datastream_metadata.uuid` is the CDC row id.

## Joins & relationships
- **→ `bronze.integrationprod.campaigns`** on `campaign_id` (PK `campaign_id`, **not** `id`; there is
  no `silver.core.campaigns`). Partner grain **1 row per campaign** (548,673 rows, PK verified unique).
  Junction→campaigns is **N:1, no fan-out** (safe). Reverse campaigns→junction fans out only slightly
  (8 campaigns have >1 audience row); most campaigns have 0 rows here since the table is frozen.
- **→ `core.audiences`** on `audience_id` (PK `audience_id`). Partner grain **1 row per audience**;
  also LEGACY/FROZEN (writes stopped 2023-12-15). Junction→audiences is **N:1, no fan-out**. Because
  many campaigns share an audience, audiences→junction is **1:N** (fan-out — an audience can appear on
  many campaign rows).
- **→ segment dimension** on `segment_id` — the core-era `core_audience_segments` / `core_segments`
  physical does **not exist** in `integrationprod`, and `campaigns`/`audience_segments` are not in the
  `core` dataset either; this FK target is **live-unverifiable from this dataset region**. The live
  (non-core) targeting-expression tables are `bronze.integrationprod.audience_segments` /
  `audience_audience_segments` (schema differs — those carry `campaign_id` + `is_targeted`), but they
  are a different lineage, not the parent of this `segment_id`.
- Sibling: **`core.campaign_group_x_audiences`** is the campaign-**group**-level analog (bridge on
  `campaign_group_x_audience_id`); use it for group-level audience attachment.

## Gotchas
- **Frozen since 2023-12-15** — no rows for any campaign created after that. Do not use for current
  targeting; use the live `audience_audience_segments` expression instead.
- **`user_id` is 100% NULL** — unusable.
- **`segment_id` ~15% NULL** — a LEFT join, not INNER, if you need every attachment.
- **No `deleted`/`is_test`** — cannot filter test/soft-deleted rows here; do it on the joined
  `campaigns`/`audiences` rows.
- **`datastream_metadata.source_timestamp` is CDC time, not business time** (and in ms) — do not use
  it as a created/updated business timestamp; use `create_time`.
- **`campaign_id` PK is `campaign_id` not `id`** on the `campaigns` partner — a common wrong-key join.

## Cost & partitioning notes
- **Unpartitioned, un-TTL'd** physical TABLE (`timePartitioning: None`), clustered by
  `campaign_x_audience_id`. Tiny dimension: ~76.5K rows, ~6.19 MiB total. There is **no partition
  column to filter** — the one lever is **project only the columns you need** (avoid `SELECT *`).
- Dry-run figures (labeled by column set):
  - `SELECT *` (all 7 cols) → 6,486,220 bytes (~6.19 MiB) = full table.
  - `SELECT campaign_id, audience_id` (2 cols) → 1,223,968 bytes (~1.17 MiB) ≈ 5.3x cheaper.
- Cluster on `campaign_x_audience_id` only prunes point-lookups by PK; filtering by `campaign_id`
  still scans the full (small) table. At this size cost is negligible regardless.

## Example queries
```sql
-- Audiences attached to a given campaign (legacy attachments only, <= 2023-12-15)
SELECT campaign_id, audience_id, segment_id, create_time
FROM `dw-main-silver.core.campaign_x_audiences`
WHERE campaign_id = 186250;

-- Campaigns that reused a given audience (1:N fan-out from audiences)
SELECT audience_id, campaign_id, create_time
FROM `dw-main-silver.core.campaign_x_audiences`
WHERE audience_id = 80296
ORDER BY create_time DESC;
```
