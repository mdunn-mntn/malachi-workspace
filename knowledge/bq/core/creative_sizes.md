# core.creative_sizes

## Purpose
Tiny reference/ENUM dimension that describes each **creative size** — its pixel dimensions
(`width` x `height`), a human-readable `description` (e.g. "Medium Rectangle", "Leaderboard",
"HD Video"), and boolean **format flags** (`video`, `web`, `mobile`, `ctv`, `approve`). Reach for
it to label what an ad *is* (a 300x250 web display banner vs a 1920x1080 CTV video) by joining
`creatives.creative_size_id` -> `creative_sizes.creative_size_id`. It is a thin silver view over the
CDC-replicated Postgres dim `dw-main-bronze.integrationprod.core_creative_sizes` — 29 rows, no
SQLMesh, no partition. Use it as an enum lookup; do not treat it as event/fact data.

## Grain & keys
- **Grain:** one row per creative size (dimension + format combination). 29 rows live (2026-07-19).
- **Primary key:** `creative_size_id` (also the physical clustering key).
- **Fanned into by:** `creatives.creative_size_id` (N:1 — many creatives share one size).
- **No `deleted` / `is_test` columns** — the standard `deleted=FALSE AND is_test=FALSE` dim filter
  does **not** apply here (those columns don't exist on this dim; all 29 rows are live).

## Column meanings (only the non-obvious ones)
- **`creative_size_id`** — PK. **Bitmask-style integer, NOT a dense sequence.** Observed values are
  power-of-two / OR-of-bit combinations: 1, 2, 8, 20, 24, 39, 40, ... 16384, 32768, 65536, 131072,
  524288 (and combos like 24576 = 16384+8192, 49152 = 32768+16384, 98304). Do not assume contiguity
  or `MAX(id)+1` semantics.
- **`width` / `height`** — pixel dimensions of the creative slot (integers). `description` sometimes
  just restates them (e.g. "1920x1200", "640x480") and sometimes gives a named format
  ("Medium Rectangle" = 300x250, "Leaderboard" = 728x90, "HD Video" = 1920x1080).
- **`ctv`** — TRUE only for CTV-eligible video sizes. Live: **exactly 2 rows** — id 39
  (Vertical HD Video, 1080x1920) and id 93 (HD Video, 1920x1080). Everything else is FALSE.
- **`video`** — TRUE for video creatives: ids 39, 80, 93. Note **`video` is a superset of `ctv`**:
  id 80 ("640x360 Landscape Video") is `video=TRUE` but `ctv=FALSE` (a video display size, not CTV).
- **`web` / `mobile`** — display-surface eligibility flags. Not mutually exclusive (a size can be
  both, e.g. "Full Banner" 468x60 is web+mobile) and large video/interstitial formats are often
  both FALSE.
- **`approve`** — TRUE for **all 29 live rows** (no discriminating value in current data); treat as
  a legacy/always-on flag, not a filter.
- **`datastream_metadata.source_timestamp`** — CDC-capture epoch in **MILLISECONDS** (13-digit),
  anchor `source_timestamp = UNIX_MILLIS(cdc_capture_time)` -> use `TIMESTAMP_MILLIS(...)`.
  Verified: 1766121466544 -> 2025-12-19 (interpreting as MICROS wrongly yields 1970). This is the
  Datastream replication instant, **not** a business/creation time — do not use it as a size's
  "created" date. `datastream_metadata.uuid` is the CDC row identity.

## Joins & relationships
- **`creatives.creative_size_id` -> `creative_sizes.creative_size_id`** — the canonical join. Partner
  `core.creatives` grain = one row per creative; direction **creatives -> creative_sizes is N:1**
  (safe, no fan-out — each creative carries exactly one size). The reverse
  (`creative_sizes` -> `creatives`) is **1:N** and fans out heavily (one size maps to many
  thousands of creatives) — only expand that way with an aggregation.
- Any table exposing `creative_size_id` (e.g. impression/creative-level rollups) joins here N:1 the
  same way; this dim is always the "1" side.

## Gotchas
- **No soft-delete / test columns** — cannot filter `deleted`/`is_test` (they don't exist). All rows
  are live.
- **`approve=TRUE` everywhere** — not usable to filter to "approved sizes"; it discriminates nothing
  in current data.
- **`creative_size_id` is a bitmask, not sequential** — never infer counts or ranges from the id.
- **`source_timestamp` is CDC-capture time in ms**, not a business timestamp; don't treat it as when
  the size was defined.
- **Prose-vs-schema drift reconciled (2026-07-19):** `data_catalog.md` carries two headers for this
  dim — `## bronze.integrationprod.creative_sizes` (line ~1883, names the physical without the
  `core_` prefix) and `## bronze.integrationprod.core_creative_sizes` (line ~2039). The silver view
  `core.creative_sizes` resolves to **`core_creative_sizes`** (per the view definition below); that
  is the authoritative physical. Prose also omitted the `approve` column, now documented.

## Cost & partitioning notes
- **No partition, no filter required.** 29-row lookup dim (physical `numBytes` = 2610). Clustered on
  `creative_size_id` (useful only for point lookups; irrelevant at this size).
- **`SELECT *` is safe here** — a full-view scan reads ~2.6 KB logical but **bills the BigQuery 10 MB
  minimum** (measured: full `SELECT` of all 10 cols = 0.01 GB billed, 0 GB processed, sub-second).
  There is no cheaper column set worth optimizing; just select the columns you need.
- Load the whole table into memory and join it broadcast-style against larger fact/creative tables —
  never scan a big table to fetch a size label.

## Example queries
```sql
-- Full dim (safe — 29 rows, ~10 MB min bill)
SELECT creative_size_id, width, height, description, video, web, mobile, ctv
FROM `dw-main-silver`.core.creative_sizes
ORDER BY creative_size_id;

-- Label creatives with their size/format (N:1, no fan-out)
SELECT c.creative_id, c.advertiser_id, s.description, s.width, s.height, s.video, s.ctv
FROM `dw-main-silver`.core.creatives c
JOIN `dw-main-silver`.core.creative_sizes s USING (creative_size_id);

-- CDC capture time (source_timestamp is MILLISECONDS)
SELECT creative_size_id, TIMESTAMP_MILLIS(datastream_metadata.source_timestamp) AS cdc_capture_ts
FROM `dw-main-silver`.core.creative_sizes;
```
