# core.advertiser_conversion_types

## Purpose
Auto-registered registry of every distinct conversion `type` string an advertiser's tag has ever
sent. A row is **auto-created the instant a new `conversion_type` first appears in `conversion_log`** —
`create_time` = the first occurrence of that type in the log (verified to the second: WGU
`app_submitted` registry create_time `2025-09-30 22:57:04` == MIN(time) of the first log event).
Reach for it to **date client-side pixel/tag changes**: a new row means the advertiser's website tag
started sending a new `type` param — a CLIENT-side change, not an MNTN platform config action. No MNTN
table tracks advertiser-side pixel edits (confirmed by Kevin Cipriani 2026-07-08); this registry's
`create_time` plus the conversion_log shape is the only reconstruction path. Dashboarded as the CPD
"13 Pixel Health" query + scorecard flag (TI-1037).

## Grain & keys
- **Grain:** one row per `(advertiser_id, conversion_type, conversion_source_id)` triple. Verified
  live 2026-07-29: 149,014 rows, and both the surrogate PK and the triple have 149,014 distinct values
  — **zero duplicate triples**. Re-registration of an existing type under a new source_id is negligible
  (~26 pairs platform-wide).
- **Primary key:** `advertiser_conversion_type_id` (surrogate, unique).
- **Foreign keys:** `advertiser_id` → `integrationprod.advertisers.id` (but see 50M-namespace gotcha —
  many advertiser_ids here do NOT exist in the dim); `conversion_source_id` → `integrationprod.data_sources.id`.
- **No `deleted`, `is_test`, or `user_id` column** — this dim carries neither soft-delete nor test flag,
  so the usual `deleted=FALSE AND is_test=FALSE` core-dim filter does **not** apply here.

## Column meanings (only the non-obvious ones)
- **`conversion_type`** — the free-text `type` param the advertiser's tag sends (e.g. `app_submitted`,
  `Purchase`, `Lead`). NOT an enum. Never NULL in practice (0 NULLs live). Six **platform sentinels**
  masquerade as types (see Gotchas): `-100`, `-101`, `-102`, `-105`, `-106`, `-107`. `ui_conversions`
  renders untyped conversions as the string `'-101'`. Also polluted with client garbage / pentest
  payloads (see Gotchas). Exclude sentinels with `REGEXP_CONTAINS(conversion_type, r'^-[0-9]+$')` — the
  regex matches exactly the six sentinels and no genuine client/pentest type; never hard-code a pair.
- **`conversion_source_id`** — FK into `data_sources`, identifies the pipeline that produced the event.
  Each sentinel binds to a single source across unrelated advertisers: `-100`↔`-1` (legacy "MNTN Pixel"
  unnamed), `-101`↔`23` (post-2025-01-10 NULL→23 migration; `23`=`guid_log`, displays "MNTN Pixel" /
  "Website Event"), `-102`↔`31` (offline events), `-105/-106/-107`↔`328494/328496/328497`. `21` =
  "MNTN Conversion". `-1` and `23` both display to clients as "MNTN Pixel".
- **`create_time`** — native `TIMESTAMP` (UTC), = the FIRST time that type fired in `conversion_log`,
  not when anyone configured it. This is the **partition column** (DAY). Never NULL. Live range
  2023-04-13 → present. It records WHEN a new event fired, not WHO configured it.
- **`advertiser_conversion_type_id`** — surrogate PK; no business meaning beyond uniqueness.

## Joins & relationships
- **`advertiser_id` → `core.advertisers` / `integrationprod.advertisers` (grain: 1 row per advertiser).**
  Expected N:1 (many types per advertiser). **Fan-out caveat:** joins will DROP a large share of
  registry rows since Apr 2026 — the 50M-namespace flow registers advertiser_ids that don't exist in
  the dim (dim max ≈ 3.5M). Inner-join to `advertisers` to keep only real advertisers.
- **`conversion_source_id` → `integrationprod.data_sources` (grain: 1 row per source id).** N:1, safe;
  decodes source display names. There is **no separate `conversion_sources` table** — `data_sources` is
  the registry.
- **`conversion_type` ↔ `logdata`/`summarydata` conversion tables (`conversion_log`, `ui_conversions`).**
  This registry is the config/registry side; the log side (`conversion_log`) is 1:N per (advertiser,
  type). Use this table's `create_time` as the "type first seen" anchor; do NOT join on it for volume —
  it has one row per type, the log has one per event.
- Related pixel-config tables (context, not joins): `core_pixel_integrations`(+`_types`) = e-commerce
  integrations; `ui_advertiser_pixel_infos` = pixel notes/URLs; `attr_advertiser_waypoints_event_mapping`
  + `attr_advertiser_selective_performance_config` = event-name classification; `advertisers` pixel flags
  (`populate_order_on_conversion`, `conv_pixel_opt_out`, `pixel_isolation`, `allow_duplicate_orders`).

## Gotchas
- **Six sentinels, not two.** `-100`/`-101`/`-102`/`-105`/`-106`/`-107` are platform pseudo-types
  (verified 2026-07-08, TI-1037). Use `REGEXP_CONTAINS(conversion_type, r'^-[0-9]+$')` to exclude them.
- **50M+ advertiser_id namespace (since 2026-03-31).** An automated flow registers exactly one
  `'Purchase'` (source 23) per sequential advertiser_id in a **50M+ namespace that does NOT exist in
  `integrationprod.advertisers`** (dim max ≈ 3.5M), ~2,100–2,600/month. `COUNT(DISTINCT advertiser_id)`
  on this registry is inflated **~10–30×** from Apr 2026. Real new advertisers (classic IDs) almost
  never get a first-month Purchase registration (0.19%). Inner-join to `advertisers` before counting.
- **Junk / pentest pollution.** Because registration is automatic from the log, injection payloads leak
  in — WGU (31357) has ~74 SQL-injection/XSS/Burp-Collaborator (`oastify.com`) rows from a 2026-02-07
  pentest; trace-scale garbage elsewhere (`[object Object]`, `undefined`, `true`, epoch-millis strings).
- **Row explosion Apr/May 2026.** 12.6K/8.9K non-sentinel regs, ~76–79% classic-namespace, concentrated
  on ~90 advertisers — a fuzzing/pentest-shaped many-types-per-advertiser pattern, not organic growth.
- **`create_time` = first log occurrence, not config time.** A new row = a client-side tag change; MNTN
  did nothing. Don't read it as an MNTN action.
- **No soft-delete / no test flag.** There is no `deleted` or `is_test` column — rows are never removed;
  the two mass backfills (2023-11, 2024-09) are ~100% `-100` sentinel rows.
- **SQLMesh-materialized (not a bronze passthrough).** Unlike most `core.*` thin views, this silver view
  resolves to a SQLMesh **physical TABLE** that mirrors `bronze.integrationprod.core_advertiser_conversion_types`.
  Query the clean name `core.advertiser_conversion_types`.

## Cost & partitioning notes
- **Partition: `create_time` (DAY). Cluster: `advertiser_id, conversion_source_id`. `require_partition_filter`
  = false** (not enforced, but filter anyway). Tiny table (~7.17 MB), so cost is never a concern — but
  filtering `create_time` still prunes.
- **The one filter to always apply:** a `create_time` range when you only need recent registrations.
- Dry-run figures (2026-07-19, `bq_run.sh --dry_run`):
  - `SELECT advertiser_conversion_type_id` (one narrow col), **full table**: **1,181,800 bytes** (~1.18 MB).
  - Same one col, `WHERE create_time >= '2026-07-01'`: **39,120 bytes** (~39 KB) — **~30× prune**, empirically
    confirming `create_time` is the partition column.
  - `SELECT *`, full table: **~7.25 MB** = full backing storage (`numBytes` 7,251,969, 2026-07-29).
  - Same-column-set comparison (one narrow col, filtered vs not) is the valid prune diff; `SELECT *` is ~6×
    the one-column full scan — avoid `SELECT *`.

## Example queries
```sql
-- Date a new tag/pixel event for one advertiser (client-side change detection)
SELECT conversion_type, conversion_source_id, create_time
FROM `core.advertiser_conversion_types`
WHERE advertiser_id = @advertiser_id
  AND NOT REGEXP_CONTAINS(conversion_type, r'^-[0-9]+$')   -- drop the 6 sentinels
ORDER BY create_time DESC;

-- Recent real registrations (prune the partition, drop the 50M-namespace junk)
SELECT t.advertiser_id, t.conversion_type, t.create_time
FROM `core.advertiser_conversion_types` t
JOIN `core.advertisers` a ON a.id = t.advertiser_id   -- inner join drops 50M-namespace ids
WHERE t.create_time >= TIMESTAMP('2026-07-01')
ORDER BY t.create_time DESC;
```
