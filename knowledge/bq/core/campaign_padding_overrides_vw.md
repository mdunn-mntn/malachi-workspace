# core.campaign_padding_overrides_vw

## Purpose
Manual **campaign-level delivery/pacing override** dim. Each row records a non-default `padding`
multiplier for one campaign — a factor applied so the campaign delivers *above* its nominal
budget/goal (padding > 1.0 = over-deliver by that fraction; observed 1.05 = +5%, 1.4 = +40%). The
`notes` column carries the **PER-XXXX Jira ticket** that authorized the override, so the table doubles
as an audit trail of who/why an override exists. Reach for it to (a) list which campaigns run a
non-default pacing pad and (b) trace the justifying ticket. **Absence of a row = no override / default
padding** — the table only holds the exceptions, not every campaign. Sibling dim
`core.advertiser_padding_overrides` is the advertiser-scoped equivalent.

## Grain & keys
- **Grain:** one row per **overridden `campaign_id`** — an exceptions/override table, not a per-campaign
  fact. Only 2 rows live today (2026-07-19).
- **Primary key:** `campaign_id` (unique; also the physical cluster key). No surrogate id.
- **Foreign key:** `campaign_id` → `core.campaigns.id` (the campaign this override applies to).

## Column meanings (only the non-obvious ones)
- **`padding`** — delivery/pacing multiplier as a **decimal factor**, not a percent. `1.0` = no pad;
  `1.4` = deliver 40% above the nominal budget/goal. Stored as **STRING** in the raw CDC table
  (`core_campaign_padding_overrides.padding`) and `SAFE_CAST` to **NUMERIC** in the SQLMesh view chain —
  so a non-numeric raw value would surface as NULL rather than error (none observed). NOT a margin /
  take-rate; it is a pacing over-delivery buffer.
- **`notes`** — free-text; in practice the **PER-XXXX Jira ticket key** that authorized the override
  (e.g. `PER-5842`, `PER-2694`). Audit-trail field, not a system enum.
- **`create_time` / `update_time`** — native `TIMESTAMP` (UTC), business row-lifecycle times, not epoch
  ints. `update_time == create_time` when the row was never edited after insert.
- **(not exposed) `datastream_metadata`** — the raw CDC table carries a `datastream_metadata` RECORD
  (Datastream capture time), but the view chain **drops it**; silver consumers only ever see the 5
  columns in AUTO:SCHEMA.

## Joins & relationships
- **`campaign_id` → `core.campaigns.id`** — partner grain **1 row per campaign** (campaigns keyed on
  `id`). This side is 0-or-1 override per campaign, so `campaigns LEFT JOIN campaign_padding_overrides_vw
  USING-ish (id = campaign_id)` is **fan-out-safe** (never multiplies campaign rows). Use LEFT JOIN and
  `COALESCE(padding, 1.0)` to treat missing overrides as the default. (Live cross-check of `campaigns`
  deferred — large table; the safe/no-fan-out direction is the one used here.)
- **Sibling:** `core.advertiser_padding_overrides` is the advertiser-level analogue (join on
  `advertiser_id`); a campaign may inherit an advertiser pad even with no row here — reconcile both when
  reasoning about effective delivery padding.

## Gotchas
- **No `deleted` / `is_test` columns.** The usual `deleted=FALSE AND is_test=FALSE` dim filter does NOT
  apply here (columns absent) — every row is a live override. There is no soft-delete flag, so a source
  Postgres delete either removes the row or (unverifiable from this dim) could leave a stale one; treat
  the view as current-state snapshot from Datastream.
- **Exceptions-only table.** Most campaigns have NO row. Never inner-join and assume every campaign
  appears; a missing row means "default padding," which callers should model as `1.0`.
- **`padding` is a STRING in the raw table** cast to NUMERIC in the view — a malformed raw value becomes
  NULL (`SAFE_CAST`), silently, rather than failing. Guard against NULL when averaging.
- **Timestamps are UTC business times**, not CDC capture time; the CDC `datastream_metadata.source_timestamp`
  is not exposed downstream.
- **Tiny + volatile.** Only 2 rows today; row count can change any time an ops ticket adds/removes an
  override. Don't hard-code counts.

## Cost & partitioning notes
- **Physical:** `dw-main-bronze.integrationprod.core_campaign_padding_overrides` — a real TABLE
  (2 rows, **171 bytes** on disk), **unpartitioned**, clustered on `campaign_id`. The view chain is
  `silver.core.campaign_padding_overrides_vw` → bronze `core_campaign_padding_overrides_vw` (view) →
  `sqlmesh__integrationprod.integrationprod__core_campaign_padding_overrides_vw__3483922465` (view,
  does the `SAFE_CAST(padding AS NUMERIC)`) → the raw table.
- **No partition to filter** — it's a sub-1KB lookup dim; there is no cost trap and no partition-filter
  requirement. `SELECT *` of the full view billed the **10 MB minimum tier (0.01 GB billed / 0 GB
  processed; all 5 columns)** — effectively free. Just select it whole.
- Clustering on `campaign_id` is inert at 2 rows (noted for completeness, no pruning benefit).

## Example queries
```sql
-- All current campaign padding overrides (whole table — no partition filter needed)
SELECT campaign_id, padding, notes, create_time, update_time
FROM `dw-main-silver.core.campaign_padding_overrides_vw`
ORDER BY padding DESC;

-- Attach effective padding to campaigns, defaulting non-overridden campaigns to 1.0
SELECT c.id AS campaign_id, COALESCE(p.padding, 1.0) AS effective_padding, p.notes
FROM `dw-main-silver.core.campaigns` c
LEFT JOIN `dw-main-silver.core.campaign_padding_overrides_vw` p
  ON p.campaign_id = c.id;
```
