# core.features

## Purpose
The lookup/definition table for MNTN **feature flags** — named boolean toggles that gate advertiser- or product-level behavior (e.g. `MULTI_TOUCH_ENABLED`, `FLAT_CPM`, `EGO_CAMPAIGNS_DISABLED`, `MNTN_MATCHED_V2_5`). This table holds only the flag **definitions** (id, name, human description, default) — it does **not** say which advertisers have each flag on. Reach for it to (a) resolve a `feature_id` → human name/description, (b) read a flag's `default_value` (what an advertiser gets when it has no explicit assignment), or (c) enumerate the full set of flags in the platform. To answer "does advertiser X have feature Y", join to `core.advertisers_x_features` (the membership junction).

## Grain & keys
- **Grain:** one row per feature-flag definition (87 rows as of 2026-07-19).
- **Primary key:** `feature_id` (INT64; also the physical clustering key). IDs are sparse/non-dense — observed min 1, max 3,356,188 — do not assume a contiguous 1..N range.
- **Natural key:** `name` is effectively unique per flag but is human-authored and inconsistent (mostly `UPPER_SNAKE_CASE`, but some are free text like `"GUID impression search logic"`) — join on `feature_id`, not `name`.

## Column meanings (only the non-obvious ones)
- **`default_value`** (BOOL): the flag value an advertiser receives **when it has no explicit row** in `core.advertisers_x_features`. It is the fallback, not the current state of any advertiser. Distribution as of 2026-07-19: 13 flags default `true`, 74 default `false`.
- **`description`** (STRING): free-text human explanation of what the flag does (e.g. "If an advertiser is in this feature, they will continue to have access to MT (display) campaigns"). Semantics are prose-only — some flags read as "…ENABLED" but default `false`, others as "…DISABLED" — always read the description, don't infer polarity from the name.
- **`source`** (STRING, nullable): provenance of the flag definition. Observed domain (`SELECT DISTINCT`): `internal`, `tag`, `harness`, and `NULL`. `harness` = created via the feature-flag harness tooling; `NULL` for older/manually-seeded flags. Not a business-critical field.
- **`create_time`** (TIMESTAMP): **business** time the flag was defined (observed range 2025-02-11 → 2026-07-15). This is the timestamp to use for "when did this flag appear."
- **`datastream_metadata.source_timestamp`** (INT64): **milliseconds** since epoch — `= UNIX_MILLIS(cdc_capture_time)`; decode with `TIMESTAMP_MILLIS(...)` (verified: value 1766121490295 → 2025-12-19; `TIMESTAMP_MICROS` yields 1970, wrong). This is the Datastream **CDC capture** time, NOT business time — 57 distinct values across 87 rows, with a large cluster on the initial 2025-12-19 backfill snapshot and per-row values for rows changed later. Prefer `create_time` for business questions.
- **`datastream_metadata.uuid`** (STRING): Datastream change-record id (CDC plumbing), not a business key.

## Joins & relationships
- **`core.advertisers_x_features`** (membership junction; view over `dw-main-bronze.integrationprod.core_advertisers_x_features`, ~198,442 rows, ~17 MB, clustered on `advertisers_x_features_id`): **1:N** from `features` on `feature_id` — one feature definition maps to many advertiser assignments. Fan-out = number of advertisers assigned that flag (avg ≈ 2,280 rows/feature but heavily skewed; a popular flag can join to tens of thousands of advertiser rows). Junction columns: PK `advertisers_x_features_id`; FKs `advertiser_id` (→ `core.advertisers`) and `feature_id` (→ this table); `active` BOOL = whether the assignment is currently on; `create_time` / `update_time`. To get an advertiser's effective flag state: `LEFT JOIN advertisers_x_features … AND active = TRUE`, then `COALESCE(axf.active, features.default_value)`.
- **`core.advertisers`**: reached transitively through the junction on `advertiser_id` (1:N from advertisers → junction rows). Not joined directly from this table.

## Gotchas
- **This table has NO `deleted` and NO `is_test` column** (nor `update_time`). The usual integrationprod `deleted=FALSE AND is_test=FALSE` live-row filter does not apply here — there is no soft-delete on flag definitions. Membership de-activation is expressed as `active=FALSE` on the **junction**, not here.
- **Definitions ≠ membership.** A row existing here says the flag *exists*, not that any advertiser has it on. Never infer adoption from this table; that requires `advertisers_x_features` (with `active=TRUE`).
- **`default_value` is the fallback, not a live count.** An advertiser with no junction row inherits `default_value`; one with a junction row uses `active`. Don't report `default_value` as "% of advertisers on the flag."
- **Name polarity is unreliable** — read `description`, and note default is often `false` even for `*_ENABLED` names.
- **`source_timestamp` is CDC capture time, not business time** (see column meanings) — using it as "when the flag was created" is wrong for backfilled rows; use `create_time`.

## Cost & partitioning notes
- Physical table `dw-main-bronze.integrationprod.core_features`: **no partitioning**, **clustered on `feature_id`**, no TTL (it's a CDC dimension, not an event log). 87 rows, `numBytes` = 12,199 (~12 KB real backing storage).
- **Cost is negligible — a full scan is fine.** `SELECT *` over the view processes **12,199 bytes (~12 KB)** — measured via `bq_run.sh --dry_run`, all 7 columns (2026-07-19). There is no partition filter to apply; the clustering key `feature_id` only helps point-lookups, not scan cost at this size.
- Prefer this small dim as the **left/broadcast side** of any join with the ~198K-row `advertisers_x_features` junction.

## Example queries
```sql
-- Resolve feature_id -> name/description/default
SELECT feature_id, name, description, default_value
FROM `dw-main-silver.core.features`
ORDER BY feature_id;

-- Advertisers currently on a given flag (membership lives in the junction)
SELECT axf.advertiser_id
FROM `dw-main-silver.core.features` f
JOIN `dw-main-silver.core.advertisers_x_features` axf USING (feature_id)
WHERE f.name = 'FLAT_CPM' AND axf.active = TRUE;

-- Effective flag state for an advertiser (falls back to default when unassigned)
SELECT f.feature_id, f.name,
       COALESCE(axf.active, f.default_value) AS effective_value
FROM `dw-main-silver.core.features` f
LEFT JOIN `dw-main-silver.core.advertisers_x_features` axf
  ON axf.feature_id = f.feature_id AND axf.advertiser_id = @advertiser_id;
```
