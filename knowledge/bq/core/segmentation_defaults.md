# core.segmentation_defaults

## Purpose
The catalog of MNTN's **built-in default retargeting/segment presets** — the ready-made audience
templates a user can pick when building a retargeting audience (e.g. "Auto Default", "Cart",
"5+ PV", "High Intent C", "Ego", "1+ PV", "1+ Conversion"). Each row pairs a display `name` with a
retargeting rule string in the `expression` DSL. This is a static config/lookup dimension, not an
event or per-advertiser table: as of 2026-07-19 it holds **7 rows total** (created 2018–2022), so
reach for it only to (a) map a default preset id/name to its rule expression, or (b) understand the
canned segment templates offered in the product. Thin silver view over the bronze CDC dim
`dw-main-bronze.integrationprod.core_segmentation_defaults`.

## Grain & keys
- **Grain:** one row per default segmentation preset. 7 rows / 7 distinct ids (verified 2026-07-19).
- **Primary key:** `segmentation_default_id` (INT64, unique; also the physical cluster key).
- **Grouping id:** `segmentation_section_id` — a UI section grouping (soft FK, no partner table in
  `core`; see Joins). Observed domain over the full table = {1, 2}.

## Column meanings (only the non-obvious ones)
- **segmentation_section_id** — groups the presets into product UI sections. Not a partition of any
  business dimension you can join out of `core`; observed values are 1 (standard retargeting presets:
  ids 1,2,3,4,6,7) and 2 (Ego: id 5). Since the table is only 7 rows, {1,2} is the *complete* domain,
  not a sample.
- **expression** — the retargeting rule as a string in MNTN's segment-expression DSL. Tokens seen:
  `UserLastVisitTime`, `UserNumPageViews`, `UserNumVisits`, `UserNumConversions`, `UserCartQuantity`,
  `UserCartValue`, `UserPageViews contains "…"`, `UserCustomIdentifiers contains "…"`, combined with
  `AND`/`OR`. Time windows use a `value,unit` form, e.g. `UserLastVisitTime >= 30,day`. Casing of
  keywords is inconsistent across rows (both `AND` and `and` appear) — treat the string as opaque
  config, do not parse it as canonical SQL.
- **auto_append** — BOOL. TRUE only for the "Auto Default" preset (id 1); FALSE for all others.
  Flags the preset that is auto-applied by default rather than explicitly chosen.
- **created_at** — native TIMESTAMP of business creation (range 2018-02-21 → 2022-01-21). This is the
  real "when the preset was authored" time; use it, not the CDC capture time.
- **name** — display label, STRING(max 256). Non-unique in principle but distinct across the 7 rows.
- **datastream_metadata.source_timestamp** — INT64 **UNIX_MILLIS** of the Datastream CDC capture, NOT
  business time: `TIMESTAMP_MILLIS(1766121417007)` = 2025-12-19 05:16:57 UTC, and it is **identical on
  all 7 rows** (a single backfill snapshot; matches the physical table creationTime). Never use it as
  an event/created time — use `created_at`. `datastream_metadata.uuid` is likewise the batch uuid,
  identical across all rows.

## Joins & relationships
- **segmentation_default_id** (PK) — a template/lookup id. No confirmed inbound FK inside `core`;
  product code copies the `expression`/`name` into an advertiser's actual segment rather than storing
  a hard reference, so treat this as a reference/enum dim, not a join hub. 1:1 by id if you ever do
  join to it (7 rows, no fan-out).
- **segmentation_section_id** — expected FK to a `segmentation_sections`-style table, but **no such
  table exists** in `bronze.integrationprod` (verified 2026-07-19: only `segment_types` and
  `archives_audience_segment_archives` are segmentation-adjacent). Live-unresolvable soft FK; the
  {1,2} meaning above is the best available mapping.
- Because it is a 7-row static dim, this table is a safe (fan-out-free) lookup to join *from* the
  right in any query; it can never blow up cardinality.

## Gotchas
- **Not a partitioned/event table** — no `deleted` and no `is_test` columns exist here (unlike most
  `core_*` dims), so the standard `deleted=FALSE AND is_test=FALSE` live-row filter does **not** apply
  and cannot be added. All 7 rows are live config.
- **Static & tiny** — 7 rows since ~2022; do not expect new rows per advertiser or per day. If you
  see it "growing", that is a schema/product change worth noting, not normal churn.
- **`source_timestamp` is a snapshot, not history** — the CDC dim is a full-copy view, not an
  append-only change log; a single capture timestamp on every row. Do not diff it for change tracking.
- **`expression` casing/format is inconsistent** — parse defensively (see Column meanings).
