# core.private_marketplace_families

## Purpose
Static reference/lookup dimension of **21 CTV media "families"** — the parent
network/media-company brand that owns a chunk of private-marketplace (PMP) CTV
inventory (e.g. `Disney`, `NBC`, `Fox`, `Paramount (ViacomCBS)`, `Warner Bros.
Discovery`, `Hallmark Media (Crown Media)`, `Samsung`, `Sling`, `Tubi`, `Fubo`,
`DirecTV`, `Spectrum`). Reach for it to roll individual PMP **deals** up to the
media company behind them (e.g. "how much spend went to Disney-family inventory
across all its deals"). It is a small human-maintained enum, not an event table —
all 21 rows were seeded Apr–Jun 2023 and never modified since.

## Grain & keys
- **Grain:** one row per PMP media family (parent network/brand grouping). 21 rows total, IDs 1–21 contiguous.
- **Primary key:** `private_marketplace_family_id` (INT64; also the physical cluster key).
- **Referenced by (FK):** `core_private_marketplace_deals.private_marketplace_family_id` and its legacy sibling `private_marketplace_deals.private_marketplace_family_id`. No other integrationprod table references it.

## Column meanings (only the non-obvious ones)
- **`name`** — the media-family / parent-network brand string (e.g. `"Warner Bros. Discovery"`, `"Paramount (ViacomCBS)"`, `"Hallmark Media (Crown Media)"`). Free text, not an enum code; match case-insensitively (`LOWER(name) LIKE ...`) if filtering by brand.
- **`create_time` / `update_time`** — business TIMESTAMPs (UTC). All 21 rows have `update_time == create_time` (rows were seeded once, never edited), spanning 2023-04-20 → 2023-06-28. Do not treat `update_time` as a change feed here.
- **`datastream_metadata.source_timestamp`** — CDC-capture epoch in **MILLISECONDS** (verified: value `1766121437717` → `TIMESTAMP_MILLIS()` ≈ 2025-12-19; `TIMESTAMP_MICROS()` yields 1970, i.e. NOT microseconds). It is identical across all 21 rows (the Datastream snapshot/backfill instant), so it is **not** business time — use `create_time`/`update_time` for anything time-related.
- **`datastream_metadata.uuid`** — Datastream CDC row-version UUID; internal replication bookkeeping, not a business key.

## Joins & relationships
- **→ `core.private_marketplace_deals`** (partner grain: one row per PMP deal, ~1,072 rows). Relationship is **1 family : N deals**. Joining `families` INTO a deals query is a safe **1:1 lookup** (one family row per `private_marketplace_family_id`) — no fan-out. Going the other way (deals per family) fans out ~4.5x on average across the 94 populated deals.
- **FK is sparse on the deals side:** only **94 of 1,072** PMP deals (~9%) carry a non-NULL `private_marketplace_family_id`; the other ~91% are NULL. All 21 families are used by at least one deal. So a `families ⨝ deals` join covers only the family-tagged slice of PMP inventory — use `LEFT JOIN` from deals and expect most deals to have no family.
- **Not part of the group/level hierarchy.** `core_private_marketplace_groups` and `core_private_marketplace_levels` are a *separate* PMP construct (groups reference `private_marketplace_level_id`, where level ∈ {1=global, 2=advertiser, 3=campaign_group}); **neither references `private_marketplace_family_id`.** Family is a deal-tagging dimension only, orthogonal to the group/level budget-scope hierarchy.

## Gotchas
- **No `deleted` / `is_test` columns.** Unlike most integrationprod dims, this table has neither soft-delete nor test flag — so the standard `deleted=FALSE AND is_test=FALSE` filter does NOT apply (would error). All 21 rows are treated as live.
- **`source_timestamp` is CDC-capture time, not business time** — millisecond epoch, identical for every row (~2025-12-19 snapshot). Never use it to order or window by "when the family changed"; use `create_time`.
- **Static / frozen dim.** No new families since 2023-06-28 and no updates ever; do not build change-detection or freshness logic on it.
- **FK sparsity (see Joins):** ~91% of PMP deals have NULL `private_marketplace_family_id`, so family coverage of PMP inventory is partial — a family roll-up will silently drop most deals unless you account for the NULLs.
- **Two sibling deal tables** carry the family FK: the current `core_private_marketplace_deals` and a legacy `private_marketplace_deals`. Confirm which one your pipeline reads before joining.

## Example queries
```sql
-- The whole dim (it is only 21 rows)
SELECT private_marketplace_family_id, name
FROM `dw-main-silver`.core.private_marketplace_families
ORDER BY private_marketplace_family_id;

-- Roll PMP deals up to their media family (LEFT JOIN: ~91% of deals have no family)
SELECT f.name AS family, COUNT(*) AS deals
FROM `dw-main-silver`.core.private_marketplace_deals d
LEFT JOIN `dw-main-silver`.core.private_marketplace_families f
  USING (private_marketplace_family_id)
GROUP BY family
ORDER BY deals DESC;
```
