# core.blocked_ip_addresses

## Purpose
Per-advertiser IP exclusion blocklist. Each row is one IP that a specific advertiser
wants suppressed — fraud/bot IPs (e.g. Cheq lists), known existing customers,
employees, competitors, partners, or low-quality-install sources. Reach for it to
understand or reproduce advertiser-scoped IP exclusions used to remove traffic from
targeting/billing. It is a CDC dimension mirror (add/remove/edit reflected via
Datastream), not an event log.

## Grain & keys
- **Grain:** one row per `(advertiser_id, ip)` — verified: `COUNT(*) = COUNT(DISTINCT advertiser_id|ip) = 657,395` (2026-07-19). Adding `audience_upload_id` does not increase the distinct count, so the pair is the natural key.
- **Key(s):** composite `(advertiser_id, ip)`. Same IP can be blocked by many advertisers (253,495 distinct IPs across 330 advertisers), so `ip` alone is **not** unique.
- **Join columns:** `advertiser_id`, `ip`, `audience_upload_id`, `user_id`.

## Column meanings (only the non-obvious ones)
- **advertiser_id** — FK to `advertisers`; owner of this exclusion. Never NULL in practice (0/657,395 NULL). The block is scoped to this advertiser only.
- **ip** — the blocked IP as a raw string (IPv4/IPv6 text, not parsed). Never NULL. Compare/join against the string `ip` on log tables, not `ip_raw`.
- **description** — free-text, user-entered **batch label**, shared across every row loaded together (that's why counts cluster: "test" 290,551 rows, a Cheq list 41,388, "IP Block List 2/1/24 – 3/25/24" 10,000, etc.). Uncontrolled — values range from meaningful ("List of IPs blocked from Cheq in September 2022") to junk ("12", "www", "LOOKHEREJARED"). **Not a status flag** — the literal value `"test"` here is a description string, unrelated to any `is_test` column. NULL for 1,583 rows.
- **user_id** — FK to the users dimension; the internal/advertiser user who added the batch. NULL for 1,931 rows (legacy/system-loaded entries).
- **audience_upload_id** — FK to `integrationprod.audience_uploads`; set when the block originated from an IP-list upload (`audience_upload_type_id = 3`). NULL for 2,493 rows added directly (not via an upload).
- **create_time / update_time** — native `TIMESTAMP` (UTC), not epochs. `create_time` NULL for 1,912 rows; `update_time` NULL for 1,931 (co-NULL with `user_id`). On unchanged rows `update_time = create_time`.
- **datastream_metadata.source_timestamp** — Datastream **CDC-capture** epoch in **milliseconds** (verified: `TIMESTAMP_MILLIS(1784335176332) = 2026-07-18 00:39:36`, matching `create_time`; `TIMESTAMP_MICROS` yields 1970 = wrong unit). This is pipeline-capture time, **not** business time — prefer `create_time`/`update_time` for when the block was actually made. `datastream_metadata.uuid` is the CDC row id.

## Joins & relationships
- **advertiser_id → `advertisers` (core_advertisers)** — partner grain 1 row/advertiser (PK `advertiser_id`). Direction advertisers→blocked_ip is **1:N** (one advertiser has up to thousands of blocked IPs); joining this table onto `advertisers` fans **out** by blocked-IP count. Safe direction: look up the advertiser from a blocked-IP row (N:1, no fan-out).
- **audience_upload_id → `integrationprod.audience_uploads`** — partner grain 1 row/upload (PK `audience_upload_id`). 1:N (one IP-list upload → many blocked-IP rows). Use to attribute a block batch to its source CRM/IP upload. NULL where the block was entered directly.
- **user_id → users dimension** — 1 row/user; N:1 from here (many blocks per user), no fan-out looking up the user.
- **ip → log/event tables (impression/visit/bid logs)** — join on the string `ip` to apply the exclusion. Massive fan-out (an IP appears in millions of log rows) and these are large partitioned event tables — always constrain the log side by its own date partition first, then join. This table itself is not partitioned.

## Gotchas
- **No `deleted` / `is_test` columns exist** on this table (schema has only the 8 columns above), so the standard `deleted=FALSE AND is_test=FALSE` dimension filter **does not apply** and would error. The blocklist is maintained by physical presence — removing a block deletes the row rather than soft-flagging it.
- **`description = "test"` is not a test-row marker** — it's just a free-text label on 290,551 real rows. Do not filter it out as test data.
- **`ip` is not unique** — always key on `(advertiser_id, ip)`. An IP blocked by advertiser A tells you nothing about advertiser B.
- **`user_id`, `update_time`, and `create_time` are frequently NULL** (~1.9K–2.5K rows each) for legacy/system-loaded batches — don't assume audit columns are populated.
- **Use `create_time`/`update_time`, not `datastream_metadata.source_timestamp`, for business timing** — the latter is CDC-capture (ms epoch) and reflects pipeline replay, not when the advertiser added the block.

## Cost & partitioning notes
- **No partition** (`timePartitioning: None`) and **no TTL** — it's a small CDC dimension (657,395 rows, ~81.5 MB backing storage). There is no partition filter to apply; a full scan is cheap.
- **Clustered on `(ip, advertiser_id)`** — filtering or joining on `ip` and/or `advertiser_id` gets cluster pruning; lead with `ip` for point lookups.
- **The one habit:** avoid `SELECT *`. Labeled dry-runs (2026-07-19): `SELECT *` (all 8 cols incl the `description` free-text + `datastream_metadata` struct) = **81,486,875 B**; `SELECT advertiser_id, ip` = **15,940,136 B** (~5.1x cheaper). Project only the columns you need. `approx_logical_bytes: 81486875` = full backing storage (`numBytes`).

## Example queries
```sql
-- All IPs an advertiser blocks (cluster-pruned on advertiser_id)
SELECT ip, description, create_time
FROM `core.blocked_ip_addresses`
WHERE advertiser_id = @advertiser_id;

-- Block batches by source upload
SELECT audience_upload_id, description, COUNT(*) AS n_ips
FROM `core.blocked_ip_addresses`
WHERE advertiser_id = @advertiser_id AND audience_upload_id IS NOT NULL
GROUP BY audience_upload_id, description
ORDER BY n_ips DESC;
```
