# core.objectives

## Purpose
Tiny static ENUM/lookup dimension that maps the integer `objective_id` to a human label + description. It is the reference table for the campaign "objective" concept (Prospecting, Retargeting, Multi-Touch, etc.). Reach for it only to decode `objective_id` values found on `campaigns` (and historically on `campaign_groups`) — it holds no metrics and no time series. Thin silver view over the CDC-replicated Postgres dim `dw-main-bronze.integrationprod.core_objectives` (no SQLMesh).

## Grain & keys
- **Grain:** one row per `objective_id`. 7 rows total (ids 1–7), fully enumerated below.
- **Primary key:** `objective_id`.
- **Foreign-key target:** `campaigns.objective_id → core_objectives.objective_id` (many campaigns → one objective; see Joins).
- No `deleted` / `is_test` columns exist on this dim (unlike most integrationprod dims) — there is no soft-delete filter to apply; all 7 rows are live.

## Column meanings (only the non-obvious ones)
Full live domain (`SELECT DISTINCT ... ORDER BY objective_id`, 2026-07-19):

| objective_id | name | description | notes |
|---|---|---|---|
| 1 | Prospecting | CTV Prospecting | S1 CTV prospecting |
| 2 | Onsite | *(null)* | ads on the customer's own website; description is NULL |
| 3 | Prospecting | CTV Prospecting | duplicate of 1, not actively used |
| 4 | Retargeting | Retargeting | |
| 5 | Multi-Touch | Multi-Touch | S2 prospecting (newer naming) |
| 6 | Multi-Touch Full Funnel | Multi-Touch Full Funnel | MT+ = Stage 3 (newer naming) |
| 7 | Ego | Retargeting | employee/self targeting; `name`=Ego but `description`=Retargeting (mismatched — trust `name`) |

- **`name` vs `description`:** they can disagree — id 7 is `name='Ego'` yet `description='Retargeting'`. Prefer `name` for the objective label. `description` is NULL for id 2 (Onsite).
- **`datastream_metadata.source_timestamp`** = the Datastream CDC-capture epoch in **MILLISECONDS** (empirically confirmed: `1767985678995` → `TIMESTAMP_MILLIS` = 2026-01-09 19:07:58 UTC; `TIMESTAMP_MICROS` gives 1970, so it is NOT micros). Anchor: `source_timestamp = UNIX_MILLIS(cdc_capture_time)`. It is replication metadata, not business time — and there are no `create_time`/`update_time` columns here, so this dim carries no usable business timestamp. All 7 rows share one bulk-load timestamp.
- `datastream_metadata.uuid` = per-CDC-event id (Datastream internal), not a business key.

## Joins & relationships
- **`campaigns.objective_id` → `core_objectives.objective_id`** — the primary use. Partner grain: `campaigns` is one row per `campaign_id` (millions of rows), so this is **many-to-one** (many campaigns per objective). Joining `campaigns → objectives` is a safe small broadcast lookup (no fan-out). Joining the other direction (`objectives → campaigns`) fans out 7 → millions — never start from this dim to size anything.
- Historically the objective also appeared on `campaign_groups` (parent group = obj 1/channel 8, children = obj 5/6/channel 1) before the "TV Only" UI collapse — see Gotchas.
- Pairs with `campaigns.funnel_level` (the authoritative stage indicator) and `channels.channel_id` (8=CTV, 1=display) for stage/channel analysis.

## Gotchas
- **`objective_id` is UNRELIABLE as a stage indicator (Ray, 2026-03-11).** During the "TV Only" UI migration the UI stopped setting `objective_id` correctly and pivoted to `funnel_level`. ~48,934 "Beeswax Television Multi-Touch Plus" (S3/MT+) campaigns carry `objective_id=1` instead of `6`; ~43K S2 and ~43K S3 campaigns are similarly stuck at `objective_id=1`. **`campaigns.funnel_level` is authoritative for stage (1=S1, 2=S2, 3=S3, 4=Ego), NOT this table.**
- **Prospecting filter:** `objective_id IN (1, 5, 6)` (Ray) or the safer `objective_id NOT IN (4, 7)`. Both work because the mislabeled MT+ campaigns fall to `objective_id=1` (included either way). `IN (1,5,6)` additionally excludes Onsite (2) and the unused dup (3). `funnel_level ≠ prospecting`: retargeting (obj=4) campaigns exist at every funnel_level.
- **Two ids collapse to the same meaning:** 1 and 3 are both "Prospecting / CTV Prospecting" (3 is a not-actively-used duplicate); treat them equivalently. Id 7 (Ego) has a Retargeting description — decode by `name`, not `description`.
- Static reference data: all 7 rows loaded together (single `source_timestamp`); do not expect per-row change history here.

## Cost & partitioning notes
- **No partition, no TTL. 7 rows / 566 bytes physical** (`numRows=7`, `numBytes=566` from `bq show`). Clustered on `objective_id` (CDC-replication default; irrelevant at this size). There is no partition column to filter and no cost trap — a full `SELECT *` scans the whole table for essentially free.
- Dry-run of the full-enum query (all 4 logical columns, 7 rows): **0 GB processed / 0.01 GB billed** (tier-1 minimum). Any figure here is the billing floor, not a real scan cost.
- Practical guidance: it is cheaper to `SELECT objective_id, name FROM core.objectives` once and broadcast-join than to repeatedly decode inline; but at 566 bytes it does not matter either way.

## Example queries
```sql
-- Decode objectives on prospecting campaigns (many-to-one, safe)
SELECT c.campaign_id, c.funnel_level, o.objective_id, o.name AS objective
FROM `dw-main-silver.core.campaigns` c
JOIN `dw-main-silver.core.objectives` o USING (objective_id)
WHERE c.objective_id IN (1, 5, 6)   -- prospecting; but funnel_level is authoritative for stage
  AND c.deleted = FALSE AND c.is_test = FALSE
LIMIT 100
```
