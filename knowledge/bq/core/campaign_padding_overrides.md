# core.campaign_padding_overrides

## Purpose
Small **exception / override table**: stores a `padding` multiplier for the handful of campaigns that
need a non-default value. `padding` is a decimal stored as a STRING (e.g. `"1.4"` = a +40% uplift,
`"1.05"` = +5%); `1.0` / no row = default (no padding applied). Reach for it when you need to know
whether a given campaign has an operator-set padding override and what it is (with the `notes` field
usually pointing at the Jira ticket that requested it). Thin silver VIEW (`SELECT *`) over the Postgres
CDC dimension `bronze.integrationprod.core_campaign_padding_overrides`. This is the **campaign-grain**
twin of `core.advertiser_padding_overrides` (same schema, keyed by `advertiser_id`).

> The precise downstream consumer of `padding` (pacing/delivery buffer vs billing/spend inflation) is
> not documented in the prose knowledge base — treat the exact use as an actionable gap, not a claim.

## Grain & keys
- **Grain:** one row per campaign that has a padding override. `campaign_id` is unique (physical table is
  clustered on it). This is an override-only table, not a per-campaign dimension — the vast majority of
  campaigns have **no** row. Observed live: exactly **2 rows** (campaign 531697 padding `"1.4"`, and
  campaign 219898 padding `"1.05"`).
- **Key(s) / join columns:** `campaign_id` (PK) → `campaigns.campaign_id`.

## Column meanings (only the non-obvious ones)
- **`padding`** — decimal multiplier stored as a **STRING**, not a number. `"1.4"` = +40% padding /
  uplift, `"1.05"` = +5%; `"1.0"` (or no row) = default. `CAST(padding AS NUMERIC)` before any
  arithmetic. Only campaigns needing a non-default override are stored.
- **`notes`** — free-text operator note; in practice a Jira ticket reference explaining why the override
  was set (observed values `"PER-5842"`, `"PER-2694"`). Not a structured field.
- **`create_time` / `update_time`** — native `TIMESTAMP` of the **Postgres source row** (business
  create / last-modify). NOT the replication time — see `datastream_metadata.source_timestamp`. Observed:
  campaign 219898 created `2024-04-29`, campaign 531697 created `2026-02-12`.
- **`datastream_metadata`** — standard Google Datastream CDC envelope. `uuid` = the change-event id;
  **`source_timestamp` is epoch MILLISECONDS** (anchor: `TIMESTAMP_MILLIS(source_timestamp)` →
  `2026-02-12` / `2025-12-19` — sensible; `TIMESTAMP_MICROS` yields 1970 = wrong). It is the CDC /
  backfill event time, **not** the business `create_time` — do not conflate them (in the 219898 row they
  differ by ~20 months: Apr-2024 business create vs Dec-2025 backfill).

## Joins & relationships
- **`campaign_id` → `campaigns.campaign_id`** (physical: `bronze.integrationprod.campaigns`, PK
  `campaign_id`, ~548.7K rows / ~111 MB). **1:1** — each override references exactly one campaign; the
  campaign is the parent, so this is a lookup with **no fan-out**. (`campaigns` is where you get
  `name`, the authoritative `funnel_level`, and the `deleted` / `is_test` hygiene flags — see Gotchas.)
- **Sibling:** `core.advertiser_padding_overrides` — identical schema keyed by `advertiser_id`
  (→ `advertisers`); the advertiser-grain version of the same override mechanism. A campaign-group-grain
  variant (`core.campaign_group_padding_overrides` / `_vw`) also exists (skeleton).

## Gotchas
- **Override-only table.** Absence of a row = default (no padding). Never assume a campaign is present —
  `LEFT JOIN` and `COALESCE(CAST(padding AS NUMERIC), 1.0)`. Currently only 2 rows exist.
- **`padding` is a STRING.** Cast to NUMERIC before math; a raw string compare/sum is a bug.
- **No `deleted` / `is_test` columns.** Unlike most `core.*` CDC dims, this physical table has neither
  flag (schema is just `campaign_id, padding, notes, create_time, update_time, datastream_metadata`).
  You cannot filter test / soft-deleted rows here — apply that hygiene by joining to `campaigns`
  (`deleted = FALSE AND is_test = FALSE`).
- **Two different time meanings.** `create_time`/`update_time` = Postgres business timestamps;
  `datastream_metadata.source_timestamp` = CDC replication time (ms epoch). In the observed 219898 row
  they differ by ~20 months (Apr 2024 business vs Dec 2025 backfill).
- Physical `numRows` here is reliable (real table, not a SQLMesh view) — 2 rows, 171 bytes.

## Cost & partitioning notes
- **No partition** (not an event table); physical is a real `TABLE` **clustered on `campaign_id`**, with
  no TTL. At 2 rows / 171 bytes the clustering is immaterial. There is no partition filter to apply —
  this is a tiny lookup dim, `SELECT *` is trivially cheap.
- Live figure (labeled per column set): selecting `campaign_id, padding, notes, create_time,
  update_time, datastream_metadata.source_timestamp` (full table) = **0 GB processed / 0.01 GB billed**
  (min tier), 2 rows read. Any real cost in a join comes from the `campaigns` side (~548.7K rows), not
  this table.

## Example queries
```sql
-- Resolve a campaign's effective padding (default 1.0 when no override row), with hygiene filter.
SELECT
  c.campaign_id,
  c.name,
  COALESCE(CAST(p.padding AS NUMERIC), 1.0) AS effective_padding,
  p.notes
FROM `core.campaigns` c
LEFT JOIN `core.campaign_padding_overrides` p
  ON p.campaign_id = c.campaign_id
WHERE c.deleted = FALSE AND c.is_test = FALSE
  AND p.campaign_id IS NOT NULL   -- drop this line to see all campaigns with the default
```
