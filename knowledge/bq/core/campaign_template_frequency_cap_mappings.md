# core.campaign_template_frequency_cap_mappings

## Purpose
Small config dimension that stores the frequency-cap definition for each **campaign template**, broken out by the three cap-optimization modes (AUTOMATED / AGGRESSIVE / MANUAL). A campaign inherits its template's cap config; this table is where you look up "for template X in mode Y, how many impressions are allowed per how many seconds." Reach for it to explain or reconstruct the frequency-capping applied to a campaign's delivery. Thin silver `SELECT *` view over the bronze CDC dimension `dw-main-bronze.integrationprod.core_campaign_template_frequency_cap_mappings` (no SQLMesh).

## Grain & keys
- **Grain:** one row per `(campaign_template_id, frequency_cap_optimized)` — each template has exactly one row per optimization mode. Empirically 21 distinct templates × 3 modes = 63 rows, 0 duplicate (template_id, mode) pairs.
- **Composite primary key:** `(campaign_template_id, frequency_cap_optimized)` (also the physical clustering key).
- **Foreign key:** `campaign_template_id` → the campaign-template entity (see Joins — no dedicated `campaign_templates` dim is CDC'd into `integrationprod`; consumers reach it via `campaigns.campaign_template_id`).

## Column meanings (only the non-obvious ones)
- **frequency_cap_optimized** — the cap-optimization mode; enum domain (live `SELECT DISTINCT`, no `deleted` column so all values are live): `AGGRESSIVE`, `AUTOMATED`, `MANUAL`. Part of the composite key; a template has one config row per mode.
- **primary_impressions / primary_duration** — the primary (usually short-window) cap: allow at most `primary_impressions` impressions per `primary_duration` **seconds**. Duration is in whole seconds (observed 10800=3h, 86400=1d, 259200=3d, 2592000=30d, 1209600=14d). **Both are frequently NULL together** (e.g. every observed AGGRESSIVE row) — NULL primary = no primary-tier cap, only the secondary cap applies.
- **secondary_impressions / secondary_duration** — the secondary (usually long-window) cap, same units: `secondary_impressions` per `secondary_duration` seconds. Observed non-NULL on all sampled rows. A template can thus enforce a two-tier cap (e.g. 1 imp/day primary + 6 imp/30d secondary).
- **create_time / update_time** — business TIMESTAMPs (µs precision, UTC). `create_time` is identical across all templates *within a mode* but differs *between* modes (AUTOMATED 2025-04-14, AGGRESSIVE 2025-08-25, MANUAL 2025-10-22) — i.e. rows were seeded in batches when each mode was introduced. `update_time` varies per template-mode and reflects the last edit of that specific cap config.
- **datastream_metadata.source_timestamp** — Datastream **CDC-capture** epoch in **milliseconds** (`= UNIX_MILLIS`; `TIMESTAMP_MILLIS(1775708306534)` = 2026-04-09 04:18:26 UTC, matching the physical table's creationTime; `TIMESTAMP_MICROS` yields 1970 = wrong). **Identical (1775708306534) across all 63 rows** = a single full-table snapshot/backfill load, NOT per-row business time. Use `create_time`/`update_time` for change tracking, never this.
- **datastream_metadata.uuid** — Datastream per-change row identifier (CDC bookkeeping, not a business key).

## Joins & relationships
- **`campaigns.campaign_template_id` → this.`campaign_template_id`** — the consumer path. Partner grain: `campaigns` is one row per campaign (many campaigns share a template), so campaigns → this is **N:1 on template_id but 1:3 on rows** because each template has 3 mode rows. **Fan-out warning:** joining on `campaign_template_id` alone multiplies each campaign by 3 (AGGRESSIVE/AUTOMATED/MANUAL). Consumers must additionally filter `frequency_cap_optimized` to the intended mode. Note `campaigns` carries `frequency_cap_type_id` (INT) but **no** `frequency_cap_optimized` STRING column, so there is no direct mode column to equi-join on — the mode selection must come from business logic.
- **Sibling `dw-main-bronze.integrationprod.audience_segmentation_templates`** — also keyed on `campaign_template_id`; shares the same template entity but is a separate config facet (segmentation, not capping). Join 1:N possible; not related to cap math.
- **No `campaign_templates` dimension exists in `integrationprod`** — the parent template entity is not CDC'd into BQ under that name; `campaign_template_id` resolves only through the tables that carry it as a column (`campaigns`, `audience_segmentation_templates`, `archives_campaign_archives`, `valid_campaigns`, `public_campaigns`, `dso_valid_campaigns`).

## Gotchas
- **No `deleted` / `is_test` columns** — the standard `deleted=FALSE AND is_test=FALSE` dimension filter does **not** apply here (columns absent). Treat all 63 rows as live config.
- **1:3 fan-out** on the campaign join (see Joins) — the single most common mistake. Always constrain `frequency_cap_optimized`.
- **NULL primary tier is normal**, not missing data — it means "no primary cap, secondary only." Don't `COALESCE` it to 0 (0 impressions would mean "cap everything").
- **`datastream_metadata.source_timestamp` is not business time** — it's one snapshot capture instant repeated on every row; useless for detecting which config changed when. Use `update_time`.
- **Durations are seconds**, not ms/minutes — convert with `/86400` for days.

## Cost & partitioning notes
- **No partition, no TTL.** Physical is a 63-row / **6,165-byte** un-partitioned bronze TABLE (`bq show numBytes`), clustered on `(campaign_template_id, frequency_cap_optimized)` — clustering is immaterial at this size. There is no partition column to filter and no cost trap; a full `SELECT *` scans well under the 10 MB minimum (dry-run/billed **0.01 GB**, tier-1 minimum billing floor, for the whole-table sample above).
- The one thing to always do is **filter `frequency_cap_optimized`** — not for cost, but to avoid the 3× row fan-out on joins.

## Example queries
```sql
-- Cap config for one template in its AUTOMATED mode
SELECT campaign_template_id, frequency_cap_optimized,
       primary_impressions, primary_duration,
       secondary_impressions, secondary_duration
FROM `dw-main-silver.core.campaign_template_frequency_cap_mappings`
WHERE campaign_template_id = 15
  AND frequency_cap_optimized = 'AUTOMATED';

-- Attach the correct cap to campaigns (constrain the mode to avoid 3x fan-out)
SELECT c.id AS campaign_id, m.primary_impressions, m.primary_duration,
       m.secondary_impressions, m.secondary_duration
FROM `dw-main-silver.core.campaigns` c
JOIN `dw-main-silver.core.campaign_template_frequency_cap_mappings` m
  ON m.campaign_template_id = c.campaign_template_id
 AND m.frequency_cap_optimized = 'AUTOMATED';   -- pick the intended mode
```
