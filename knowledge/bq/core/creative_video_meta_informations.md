# core.creative_video_meta_informations

## Purpose
Metadata for the transcoded video files produced for each video **creative**. When a video creative is uploaded, the transcode pipeline produces multiple renditions of the same source at 1080p mp4 across an adaptive-bitrate (ABR) ladder; each rendition gets one row here with its bitrate, fps, duration, dimensions, and CDN URL. Reach for it to answer "what video files/renditions exist for creative X", to look up a creative's duration/fps, or to resolve a rendition URL. **Frozen table:** the newest `created_at` is 2024-03-29 — no rows have been added since, so it only covers legacy/pre-2024 video creatives (see Gotchas).

## Grain & keys
- **Grain:** one row per transcoded rendition = **(`creative_id` × `bitrate` rung)**. A creative carries 2–21 rows (median/mode 7, avg 7.0) — one per bitrate rung it was transcoded to. All rows are 1080p `video/mp4`.
- **Primary key:** `creative_video_meta_information_id` (verified unique: 777,461 distinct = 777,461 rows).
- **Foreign key:** `creative_id` → `core.creatives.creative_id` (111,033 distinct creatives; never NULL).
- **No soft-delete columns:** this dim has **no `deleted` and no `is_test`** column — the standard `WHERE deleted=FALSE AND is_test=FALSE` dimension filter does not apply here.

## Column meanings (only the non-obvious ones)
- **bitrate** — STRING, video bitrate in **kbps** of this rendition. Exactly 7 distinct rungs form the ABR ladder: `1000, 2000, 3000, 4500, 6000, 12000, 15000`. Each rung appears ~111,067 times (≈ once per creative). This is the column that distinguishes the multiple rows sharing one `creative_id`.
- **duration_in_sec** — FLOAT64, the source video duration in **seconds** (e.g. 15.08). This is the reliable duration field; 28 rows NULL (~0%).
- **duration** — STRING, **legacy/near-unused: 99.7% NULL** (774,897 / 777,461 NULL, only 32 distinct non-null values). Do **not** use for duration — use `duration_in_sec`.
- **fps** — NUMERIC(6,3), frames per second (e.g. 25, 29.970). 9 distinct values.
- **status** — BOOL, **effectively dead flag: never TRUE** (0 TRUE, 762,255 FALSE, 15,206 NULL). Not a usable active/approved indicator — do not filter on it for "live" renditions.
- **video_size** — STRING, always `"1080p"` (single value across all rows); `width`/`height` are always `1920`/`1080` correspondingly. No cardinality — not a useful filter.
- **file_type** — STRING, always `"video/mp4"` (single value). Not a useful filter.
- **url** — CDN base path of the rendition on the SteelHouse/MNTN storage CDN, e.g. `https://c.steelhousemedia.com/storage/transcode/video/{account}/{hash}/`. The concrete file typically appends the resolution+bitrate (e.g. `{hash}-1080_6000.mp4`, seen in `video_adcode`). Never NULL.
- **job_task_id** — STRING, transcode job/task reference; **~58% NULL** (451,198 rows). Sparse — do not assume present.
- **video_adcode** — JSON, **rare: only 343 rows non-null** (777,118 NULL). When present it is the full creative-builder ad template (output specs, `product_fields`/`element_fields`, placeholder `values` with VIDEO/LOGO URLs and animation params), not per-rendition metadata.
- **created_at** — TIMESTAMP, row/transcode creation time. Range 2018-08-22 → **2024-03-29 (max)**; the table is frozen (see Gotchas). This is the business time to use.
- **datastream_metadata.source_timestamp** — INT64 CDC-capture epoch in **milliseconds** (`= UNIX_MILLIS(capture_time)`; `TIMESTAMP_MILLIS` → 2025-12-19, `TIMESTAMP_MICROS` → 1970 nonsense). **MIN == MAX == 1766121446441** for every row — the whole table was captured in a single Datastream snapshot on 2025-12-19 05:17:26 UTC, so this is NOT per-row business time. Use `created_at` for anything time-related.

## Joins & relationships
- **`creative_id` → `core.creatives.creative_id`** — partner grain: `core.creatives` is **1 row per creative** (PK `creative_id`). Direction matters for fan-out:
  - `creatives` ⋈ this table **fans out ~7× per creative** (2–21 rows each). Aggregate/`DISTINCT` this table down to `creative_id` before joining, or you will multiply creative-level metrics by the rendition count.
  - this table → `creatives` is **N:1** (safe; each rendition maps to exactly one creative).
- No other FK. To get advertiser/campaign context, chain through `core.creatives` (`advertiser_id`, etc.).

## Gotchas
- **FROZEN since 2024-03-29** — `created_at` maxes at 2024-03-29 23:56:15 and no rows are newer. This dim does not reflect video creatives built after March 2024. Treat as legacy/historical only; confirm current-creative video metadata against a live source before relying on it.
- **`status` is never TRUE** — do not use it as an active/approved filter (all FALSE or NULL).
- **`duration` STRING is 99.7% NULL** — use `duration_in_sec` (FLOAT seconds).
- **No `deleted`/`is_test`** columns — the standard dimension liveness filter cannot be applied.
- **Fan-out:** ~7 rows per creative (one per bitrate rung). Any join from a creative-grain table multiplies rows — dedup/aggregate to `creative_id` first.
- **`datastream_metadata.source_timestamp` is a single snapshot value** (same for all rows) — never use it as event time.
- **Single-value columns** (`video_size`=1080p, `file_type`=video/mp4, `width`/`height`=1920/1080) carry no filtering signal.

## Cost & partitioning notes
- **No partition** (physical `core_creative_video_meta_informations` is an unpartitioned TABLE; `require_partition_filter=false`). **Clustered on `creative_video_meta_information_id`** (the PK) only — filtering by `creative_id` does NOT leverage clustering; filtering by the PK does.
- Small dim (~**181 MB** real backing storage, `numBytes` from `bq show`; 777,461 rows). Every query is a full scan — there is no partition filter to apply. Control cost by **selecting only needed columns**, not by row filters.
- Measured (labeled by column set, from `--dry_run`/actual `bq_run.sh`):
  - `COUNT(*)` + ~13 aggregated columns → **0.102 GB** processed.
  - single narrow column full scan (e.g. `file_type`, `video_size`) → **0.005–0.017 GB** processed.
  - `SELECT *` ≈ the 181 MB physical size.
- Prefer the silver view `core.creative_video_meta_informations` (thin `SELECT * FROM bronze.integrationprod.core_creative_video_meta_informations`, no SQLMesh).

## Example queries
```sql
-- All renditions for one creative (PK-clustered filter is cheapest lookup path)
SELECT creative_video_meta_information_id, bitrate, duration_in_sec, fps, url
FROM `core.creative_video_meta_informations`
WHERE creative_id = 5334000
ORDER BY SAFE_CAST(bitrate AS INT64);

-- Creative-level video specs WITHOUT fan-out (collapse the rendition ladder first)
SELECT creative_id,
       ANY_VALUE(duration_in_sec) AS duration_sec,
       ANY_VALUE(fps)             AS fps,
       COUNT(*)                   AS n_renditions
FROM `core.creative_video_meta_informations`
GROUP BY creative_id;
```
