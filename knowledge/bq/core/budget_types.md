# core.budget_types

## Purpose
Tiny enum lookup dimension that decodes a campaign group's **budget pacing type**. Reach for it to turn
`campaign_groups.budget_type_id` into a human label. `silver.core.budget_types` is a thin view
(`SELECT * FROM dw-main-bronze.integrationprod.core_budget_types`) over a Postgres CDC replica dim — no
SQLMesh. As of 2026-07-19 the domain is exactly three rows:

| budget_type_id | name | meaning |
|---|---|---|
| 1 | Monthly | budget paces/resets on a monthly cadence |
| 2 | Daily | budget paces/resets per day |
| 3 | Flighted | budget is a fixed total spent across the flight's start→end window |

## Grain & keys
- **Grain:** one row per budget type. Static enum — 3 rows total (verified 2026-07-19).
- **Primary key:** `budget_type_id` (INT64, unique; the physical is clustered on it).
- **Join column:** `budget_type_id` — referenced by `campaign_groups.budget_type_id` (and its public/silver
  equivalents). This is the only join key.
- **No `deleted` / `is_test` columns** on this table (many small enum dims lack them) — so the usual
  `deleted=FALSE AND is_test=FALSE` live-row filter does not apply here; all 3 rows are always live.

## Column meanings (only the non-obvious ones)
- **`budget_type_id`** — enum PK. Domain {1=Monthly, 2=Daily, 3=Flighted}. Do not hard-code the code→name
  map in application logic; join this table (values verified live 2026-07-19 via `SELECT DISTINCT`).
- **`name`** — human label for the pacing type. Note the exact live spelling is **`Flighted`** (not
  "Flight"), alongside `Monthly` and `Daily`.
- **`datastream_metadata`** — STRUCT<uuid STRING, source_timestamp INT64> stamped by the Datastream CDC
  pipeline. `source_timestamp` is a **millisecond** epoch (CDC-capture time), NOT business time:
  `TIMESTAMP_MILLIS(datastream_metadata.source_timestamp)` → 2026-01-14 16:58:42 UTC, whereas
  `TIMESTAMP_MICROS(...)` yields a 1970 nonsense value. All 3 rows carry the identical `uuid`
  (`073ab513-…`) and identical `source_timestamp` — a single bulk backfill snapshot, so this field
  cannot be used to order rows or infer per-row edit time.

## Joins & relationships
- **`campaign_groups.budget_type_id` → `budget_types.budget_type_id`** — the canonical join. `campaign_groups`
  is the **N side** (one budget type maps to many campaign groups); `budget_types` is the **1 side**
  (lookup). Enriching campaign groups with the label is a safe **N:1** left join — **no fan-out**, since
  `budget_type_id` is unique here.
- **Reverse direction fans out:** `budget_types → campaign_groups` is **1:N** (thousands of campaign groups
  per type). Never join outward from this dim to count/aggregate campaign-group facts without expecting the
  full campaign-group cardinality.
- `budget_type_id` pairs with `campaign_groups.budget` (total flight budget, NUMERIC): budget_type_id=3
  (Flighted) is the fixed-total case; 1/2 are recurring pacing windows.
- No other table references this dim.

## Gotchas
- **No soft-delete columns.** Unlike most `core_*` dims, this table has no `deleted`/`is_test` — do not add
  those predicates (they'll error). All rows are live.
- **Label drift vs prose.** `data_catalog.md` describes the domain as "(Daily, Flight, etc.)". Live values
  are `Monthly`, `Daily`, `Flighted` — reconciled 2026-07-19. "Flight" → "Flighted".
- **`datastream_metadata.source_timestamp` is CDC-capture time in ms, not business time**, and is identical
  across all rows (bulk backfill). It is useless for ordering or change detection here. There is no
  `create_time`/`update_time` on this dim.
- **Static enum** — treat the code→name map as effectively frozen; a net-new pacing type would appear as a
  4th row.

## Cost & partitioning notes
- **No partition, no TTL.** Physical `dw-main-bronze.integrationprod.core_budget_types` is a 3-row / 188-byte
  TABLE (`bq show`: numRows=3, numBytes=188, timePartitioning=None, clustering on `budget_type_id`, no
  expirationTime). There is no partition column to filter and no cost trap.
- **Cost is negligible.** `SELECT *` over all 3 rows dry-ran to 0 GB processed / 0.01 GB billed (tier-1
  floor) — the whole table is smaller than one BQ metadata page. `SELECT *` is fine here.
- Filter only if you want a specific type, e.g. `WHERE budget_type_id = 3`. Clustering on `budget_type_id`
  is immaterial at this size.

## Example queries
```sql
-- Decode a campaign group's budget pacing type (safe N:1 lookup, no fan-out)
SELECT cg.campaign_group_id, cg.budget, bt.name AS budget_type
FROM `dw-main-silver`.core.campaign_groups cg  -- or bronze.integrationprod.campaign_groups
LEFT JOIN `dw-main-silver`.core.budget_types bt USING (budget_type_id)
WHERE cg.deleted = FALSE AND cg.is_test = FALSE
LIMIT 100;

-- Inspect the full enum (whole table = 3 rows)
SELECT budget_type_id, name FROM `dw-main-silver`.core.budget_types ORDER BY budget_type_id;
```
