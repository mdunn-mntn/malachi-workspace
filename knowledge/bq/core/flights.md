# core.flights

## Purpose
The **authoritative flight schedule** — the source of truth for a campaign group's scheduled delivery windows (`start_time`/`end_time`), flight budget, and lifecycle status. A "flight" is a scheduled budget/date period for a campaign **group**. Reach for this table to: (1) reconstruct a group's flight timeline, (2) compute flight length for the short-flight (<72h → auto HHST=0) check, and (3) overlay flight boundaries onto spend/gate diagnostics (AUDI-1070). It holds **every flight ever set** for a group, so it is the history table — unlike `dso_campaign_group_flight_budgets` (current-only) and `campaign_groups.active_flight_id` (stale pointer).

Flights are set **manually by Prod Ops (Tofer)**, one per launch — officially since early 2025, informally for years before. Each budget/schedule **edit spawns a new flight row**.

## Grain & keys
- **Grain:** one row per **flight** (`flight_id` is unique — 1,004,790 rows = 1,004,790 distinct flight_id, verified 2026-07-19).
- **Primary key:** `flight_id` (also the physical cluster key).
- **Group FK:** `campaign_group_id` → `campaign_groups.campaign_group_id` **directly** (N:1 — a flight belongs to exactly one group; a group has many flights: 89,262 groups carry the 1M flights, ~11 flights/group avg (11.26), **max 1,565 flights** on cg 25997, verified 2026-07-19). Join advertiser via `campaign_groups.advertiser_id`.
- **UI alias:** `ui_flight_id` — the UI-facing flight identifier (distinct from internal `flight_id`).

## Column meanings (only the non-obvious ones)
- **`start_time` / `end_time`** — the scheduled flight window; **this is the authoritative schedule**. Native `TIMESTAMP` = UTC point-in-time (companion `silver.dso.campaign_group_flight` adds local-tz + name). Flight length = `TIMESTAMP_DIFF(end_time, start_time, HOUR)`. Beware **sentinel/placeholder values**: min `start_time` = `1969-12-31 23:00:00` (≈epoch 0) and max `end_time` = `2074-08-01` were observed — evergreen/placeholder flights, not real windows; filter or sanity-check bounds.
- **`status_id`** — flight lifecycle. **Only `3` and `8` observed**: `3` = active/completed (~72%: 721K rows), `8` = superseded/replaced (~28%: 283K rows). There is **no soft-delete column** on this table (no `deleted`/`is_test`) — `status_id=8` is the "no longer the live schedule" signal.
- **`budget`** — `NUMERIC`, the flight's budget in dollars (per-flight allocation); p50 ≈ $5,000, p99 ≈ $135K. **Caveat (parallel to the date sentinels):** ~186,100 of 1M rows have `budget=0` (116,079 of the 721K `status_id=3` flights), and `MAX(budget)` reaches garbage/sentinel magnitudes ($8.38B on `status_id=3`, $9.23B overall) — a naive `SUM`/`AVG(budget)` is skewed by both; filter zeros and cap outliers. No NULLs.
- **`budget_type_id`** — budget-cadence FK → `silver.core.budget_types` (physical `bronze.integrationprod.core_budget_types`), whose PK is `budget_type_id`: `1`=Monthly, `2`=Daily, `3`=Flighted. Flights carry only `1` (Monthly, 722,421 rows) and `3` (Flighted, 282,369). Do **not** join to `core_flight_billing_types` — that is a different per-flight junction keyed by `core_flight_id`+`billing_type_id` (billing_type, not budget cadence), and there is no `flight_billing_types` table.
- **`create_time` / `update_time`** — Postgres row create / last-modify timestamps (`TIMESTAMP`, UTC). Because each schedule/budget **edit spawns a new row**, `create_time` ≈ when that flight version was cut. NOTE: `campaign_groups.update_time` is a **computed** `GREATEST(child-flight update_time, cg raw update_time)` — flight edits here propagate up to the group row.
- **`user_id`** — the user who created/owns the flight row (Prod Ops operator).
- **`ui_flight_id`** — UI-layer flight id; use `flight_id` for internal joins (spend_log, active_flight_id).
- **`datastream_metadata`** — `STRUCT<uuid STRING, source_timestamp INT64>` — Datastream **CDC replication** metadata, not business data. `source_timestamp` = **UNIX_MILLIS** of the CDC event (verified: `TIMESTAMP_MILLIS(1784497735868)` = `2026-07-19 21:48:55` = `update_time` exactly). Do not use for flight scheduling.

## Joins & relationships
- **`flights.campaign_group_id` → `campaign_groups.campaign_group_id`** — partner grain **1:1** (`campaign_groups` = 129,350 rows = 129,350 distinct cg). This is **N:1 from flights → safe, no fan-out**; all 1,004,790 flights resolve to a group (100% match, verified 2026-07-19). This join adds `advertiser_id` and the group label `campaign_groups.name`; for the **advertiser** label, hop `advertiser_id` → `advertisers.company_name` (there is **no** `company_name` column on `campaign_groups` — its label column is `name`).
- **`campaign_groups` → `flights`** — the **reverse direction FANS OUT** (~11 flights per group; **up to 1,565** on cg 25997). Never expand a per-group query through flights without aggregating or picking one flight.
- **`campaign_groups.active_flight_id` → `flights.flight_id`** — the "current flight" pointer, but **STALE** (per Tofer/TI-1037). Prefer selecting the flight whose `start_time`/`end_time` covers your as-of date, not `active_flight_id`.
- **`spend_log.flight_id` → `flights.flight_id`** — attribute any spend to its flight window (N:1 from spend). Same for other delivery/cost tables carrying `flight_id`.
- **Companion: `silver.dso.campaign_group_flight`** — adds local-timezone start/end + flight name. **`dso_campaign_group_flight_budgets`** — CURRENT-only (single latest flight per group) but carries the REAL current `flight_id` + budget; use `core.flights` for **history**, DSO for the **live** budget/flight.

## Gotchas
- **NO `deleted` / `is_test` columns** — unlike most `integrationprod` dims, this table does **not** carry the soft-delete/test flags, so the standard `WHERE deleted=FALSE AND is_test=FALSE` dim filter **does not apply here** (the columns literally don't exist). Use `status_id` (3 vs 8) for lifecycle instead. *(This corrects the generic "filter deleted/is_test" dim rule for this table.)*
- **Continuous delivery ≠ one flight.** A group can deliver continuously yet be composed of many short back-to-back flights (Kindred High Pop = 114 flights, 38 ≤3d). Delivery-run gap detection (`sum_by_campaign_by_day`) shows ONE run while the flight view shows heavy fragmentation. **Do NOT infer flight length from consecutive active-days** — read `start_time`/`end_time`.
- **Each edit = a new row.** A budget or schedule tweak spawns a fresh flight row, so a `<72h` "flight" can be a mid-schedule edit, not a new launch. Cross-check before treating a short flight as a launch.
- **Short flights (≤3d / <72h) auto-set the HHST gate to 0** for deliverability (AUDI-1070). A `threshold=0` row is not necessarily an intentional gate-off — cross-check flight length first.
- **Manual coverage.** Flights are hand-entered by Prod Ops; formalized early 2025, so **older campaigns may have partial flight coverage**.
- **Sentinel dates** (see column meanings): `1969-12-31` starts / `2074-08-01` ends are placeholders, not real windows.
- **No SQLMesh, no view filter.** `silver.core.flights` = `SELECT * FROM bronze.integrationprod.core_flights` (thin view, no filter) → the view returns the full 1M-row CDC replica as-is.

## Cost & partitioning notes
- **NOT partitioned** (physical `core_flights` has `timePartitioning: None`) — there is no partition column to filter, and no TTL (full CDC history back to `create_time` 2010-11-19). The table is **clustered on `flight_id` only**, so **filter/join on `flight_id`** for cheap block-pruned point lookups. A `campaign_group_id` filter is **not** cluster-pruned (dry-run shows the same 31,854,056-byte scan as no filter) — it works, but gets no block skipping.
- **The one thing to always do: prune columns — avoid `SELECT *`.** The whole table is small, but the wide columns dominate:
  - `SELECT *` (all 12 cols incl `budget` NUMERIC + `datastream_metadata` STRUCT) — **142,380,932 bytes (~0.133 GiB)** per dry-run (2026-07-19) = a full scan of the entire table.
  - `flight_id, campaign_group_id, start_time, end_time` (4 cols) — **31,854,056 bytes (~30 MB)** per dry-run (same day). Column-set comparable: dropping the wide cols cuts the scan ~**4.5x**.
- `approx_logical_bytes` = **142,380,932** = `bq show` `numBytes` of the single physical table (`dw-main-bronze.integrationprod.core_flights`); no UNION, single backing table.

## Example queries
```sql
-- Flight timeline for a group (safe N:1 join to advertiser)
SELECT f.flight_id, f.start_time, f.end_time,
       TIMESTAMP_DIFF(f.end_time, f.start_time, HOUR) AS length_hours,
       f.budget, f.status_id, g.advertiser_id
FROM `dw-main-silver.core.flights` f
JOIN `dw-main-bronze.integrationprod.campaign_groups` g USING (campaign_group_id)
WHERE f.campaign_group_id = @cg_id
ORDER BY f.start_time;

-- Short-flight (<72h) check — do NOT infer length from active-days
SELECT flight_id, campaign_group_id, start_time, end_time
FROM `dw-main-silver.core.flights`
WHERE campaign_group_id = @cg_id
  AND TIMESTAMP_DIFF(end_time, start_time, HOUR) < 72;
```
