# core.media_plan_publishers

## Purpose
The publisher/network allocation lines of a **CTV media plan**. Each row is one recommended (or user-added/modified) network in a plan, carrying its budget-allocation **percentage**, ordinal **rank**, and the algorithm's **rationale**. Reach for it to reconstruct what MNTN recommended a customer spend per CTV network, to compare recommended vs. actual delivery, or to study the media-plan algorithm's output (olympus repo, Chris Addy). `silver.core.media_plan_publishers` is a thin passthrough VIEW over the Datastream-CDC copy of the Postgres source; there is no transformation — query it like the base dim.

## Grain & keys
- **Grain:** one row per **media plan x publisher slot** (a network within a plan). Confirmed: 23,903 rows = 23,903 distinct `media_plan_publisher_id` (PK, unique). 1,551 distinct `media_plan_id`; ~15.4 publisher rows per plan (min 3, max 29).
- **Primary key:** `media_plan_publisher_id` (also the physical cluster key).
- **Join back to the plan:** `media_plan_id` → `core_media_plan.media_plan_id` (many publisher rows : one plan).
- **Network identity:** `publisher_ids` (JSON array; empirically always a single element) → integer network/publisher id; `name` is the human label for the same network.

## Column meanings (only the non-obvious ones)
- **`percentage`** — budget-allocation share for this network within the plan, on a **0-100 scale** (NUMERIC, empirically whole numbers). **Not a 0-1 fraction.** Overall min 1 / max 92 / avg ~6.5, but the max is provenance-dependent: `RECOMMENDED` max **75** (avg 6.35), `USER_ADDED` max **92**, `USER_MODIFIED` max 85 — the 92 comes from a user override, not the algorithm. The olympus "cap 12% per network" is **not** a hard invariant here: **486 `RECOMMENDED` rows exceed 12%.** Per-plan the values sum to ~100 (median = 100 across 1,551 plans; min 90, max 100); some plans sum to ~90 where the ~10% **Flex** reserve is not materialized as its own row. **DRIFT vs prose:** old `data_catalog.md` called this `STRING (cast to INT)` — it is native NUMERIC, no cast needed.
- **`rank`** — ordinal priority within the plan, 1 = top (INT64, 1..29). **DRIFT vs prose:** old catalog called this `STRING (cast to INT)` — it is native INT64.
- **`publisher_ids`** — JSON **array** of network/publisher integer ids. Empirically **always a single element** across all 23,903 rows (e.g. `[93]`, `[217068]`); modeled as an array but currently 1:1 with the row. Never NULL. Use `JSON_QUERY_ARRAY(publisher_ids)[OFFSET(0)]` / `JSON_VALUE(publisher_ids,'$[0]')` to extract the id.
- **`name`** — human network label (e.g. "HBO Max", "Discovery Channel", "Paramount Streaming - News"). **Casing is inconsistent and drifts by plan vintage** — mostly mixed-case, all-caps for acronyms ("NBC","CBS"), but many recent plans are fully lowercase ("nbc","hbo max"). The lowercase runs are **intermittent, not a clean cutover**: 2026-04 is heavily lowercase (8,895/10,222 rows), **2026-05 reverted to all-uppercase** (0/599 lowercase), then 2026-06 and 2026-07 went lowercase again (2,755/3,951 and 4,361/5,639). Because it flips either way by vintage, always LOWER()-normalize before an equality join — see Joins.
- **`badge_state`** — provenance of the line: `RECOMMENDED` (23,582 rows — MNTN algorithm allocation the user accepted), `USER_ADDED` (166 — user added this network), `USER_MODIFIED` (155 — user changed the algorithm's line). Filter `badge_state='RECOMMENDED'` for algorithm-only analysis.
- **`is_manual`** — BOOL user-touched flag (273 true / 23,630 false, never NULL). Correlates with but is **not identical** to `badge_state`: most USER_ADDED/USER_MODIFIED rows are true, most RECOMMENDED are false, but there are exceptions (32 RECOMMENDED/true, 47 USER_ADDED/false). Treat `badge_state` as the authoritative provenance; `is_manual` as a secondary edit flag.
- **`rationale`** — LLM (Gemini 2.0 Flash) natural-language reasoning for the pick. Can be an **empty string** (not NULL) — e.g. recent plans have it blank.
- **`create_time` / `update_time`** — native TIMESTAMP (UTC), source-row lifecycle. Equal on unedited rows.
- **`datastream_metadata.source_timestamp`** — INT64 epoch in **milliseconds** (`TIMESTAMP_MILLIS` resolves to 2026; `TIMESTAMP_MICROS` gives 1970). This is the Datastream **CDC capture** time, **not** the row's commit time — it is close to but **not equal to `update_time`**: across all 23,903 rows `TIMESTAMP_MILLIS(source_timestamp) = update_time` is true for **0** of them (they differ by ~tens of ms, e.g. `.340` vs `.277625`), and they agree only ~38% of the time even when truncated to the whole second (9,060/23,903). Do **not** use it as an equi-join/filter key against `update_time`. `datastream_metadata.uuid` = Datastream CDC event id. This is the only integer-epoch column; the table's own time columns are native TIMESTAMP (hence `time_unit: timestamp`).

## Joins & relationships
- **`media_plan_id` → `bronze.integrationprod.core_media_plan`** (the plan header). Partner grain = **one row per plan** (verified: 1,586 rows = 1,586 distinct `media_plan_id`); this table averages **~15.4 rows per plan**, so joining plan → publishers **fans out ~15x** (min 3, max 29). Aggregate this side (or scope to one plan) before joining up.
- **`publisher_ids[0]` / `name` → CTV network dimension.** The integer in `publisher_ids` is the network/publisher id; `name` is its label. `name` matches `sum_by_ctv_network_by_day.domain` (cross-validated in TI-748, same publishers and rank order vs `cost_impression_log`) — **but only when casing agrees.** Many recent plans store lowercase names, so a naive `name = domain` equality **silently drops those plans**; normalize both sides (`LOWER(name) = LOWER(domain)`). Note `sum_by_ctv_network_by_day` is a VIEW over a **`day`-partitioned physical table with require_partition_filter=TRUE** (~415 GB unscoped): any join to it **must** carry a `day` filter or the query hard-errors — scope it to the window you need (a 7-day window ≈ 0.09 GB).
- **Delivery scoping (CRITICAL, TI-748):** to compare a plan against actual delivery, restrict impressions to the plan's campaign groups (`media_plan.campaign_group_id`) only. Joining a plan's publishers against *all* of an advertiser's impressions produces wildly wrong "plan not followed" conclusions (real deviation is ±3%, absorbed by the Flex reserve).

## Gotchas
- **No `deleted` / `is_test` columns.** Unlike most `integrationprod` dims, this table has neither — the standard `WHERE deleted=FALSE AND is_test=FALSE` filter does **not** apply and will error. All rows are live.
- **Publisher count is a config artifact, not a data-quality signal.** Olympus commit `555234f` (Feb 3 2026, PERML-412) changed `max_networks` 25→15, `min_networks` 15→10 and added a spend-capacity gate. This shifted the *typical* count but is **not** a clean per-plan rule: post-Feb-3, **16 is the mode (1,289 / 1,476 plans, ~87%)** with a real tail (6→67 plans, 15→60, 12→39, plus 4-27); pre-Feb-3, counts spread across **3-29** and 25-or-26 covers only ~33% (25/75 plans). So do **not** bucket on `n_pub==16` vs `==26` — bucket by `create_time` relative to **2026-02-03**. The TI-748 "16 beats 26" performance split tracks this config change.
- **Flex reserve is usually invisible here.** ~10% of budget is held for bidder real-time optimization and often is not a row, so per-plan `SUM(percentage)` is ~90-100. Do not treat a <100 sum as missing data.
- **Casing drift** (see above) — the single biggest join footgun; normalize case.
- **CDC latency:** rows land via Datastream from Postgres; `update_time` is the source commit time. (`datastream_metadata.source_timestamp` is the CDC *capture* time — close to `update_time` but never exactly equal, differing by ~tens of ms; see column notes.) No partition means no late-partition backfill concern, but a very recent plan edit may lag by the CDC interval.
- **Coverage window:** `create_time` starts 2025-10-02 (M1 media-plan beta, released 2025-10-20). No history before that; there is no soft-delete, so cancelled/regenerated plans may leave stale rows keyed to a `media_plan_id` — dedup by taking the latest plan per campaign group upstream.

## Cost & partitioning notes
- **Unpartitioned dim.** `timePartitioning: None`; clustered on `media_plan_publisher_id`. There is no partition column to filter — the "always filter the partition" rule does not apply here.
- Whole table is tiny (~6.4 MB / 23,903 rows), so a full scan is cheap. Scope with `WHERE media_plan_id IN (...)` or `badge_state=...` for clarity, not for cost. Clustering on `media_plan_publisher_id` only helps point lookups by PK, not `media_plan_id` filters.
- Dry-run figures (labeled by column set): **`SELECT *` (all 12 cols) = 6,420,858 bytes** (= full backing storage / `approx_logical_bytes`); **`SELECT media_plan_id` (1 col) = 191,224 bytes**. Column pruning helps ~34x but both are negligible in absolute terms. Avoid `SELECT *` mainly to skip the JSON/STRUCT columns you don't need.

## Example queries
```sql
-- Recommended allocation for one plan, top-to-bottom
SELECT rank, name, percentage, JSON_VALUE(publisher_ids,'$[0]') AS publisher_id
FROM `core.media_plan_publishers`
WHERE media_plan_id = 1729 AND badge_state = 'RECOMMENDED'
ORDER BY rank;

-- Case-safe join of plan networks to CTV delivery.
-- sum_by_ctv_network_by_day is partitioned by `day` with require_partition_filter=TRUE,
-- so the day filter is MANDATORY (the query hard-errors without it) and also caps cost
-- (~0.09 GB for this 7-day window vs a ~415 GB unscoped scan).
-- For a TRUE plan-vs-delivery comparison also scope impressions to the plan's campaign
-- groups (media_plan.campaign_group_id) — see "Delivery scoping" — since this joins
-- networks across all advertisers/plans.
SELECT p.media_plan_id, p.name, p.percentage, d.domain
FROM `core.media_plan_publishers` p
JOIN `dw-main-silver.summarydata.sum_by_ctv_network_by_day` d
  ON LOWER(p.name) = LOWER(d.domain)
WHERE p.badge_state = 'RECOMMENDED'
  AND d.day >= DATE_SUB(CURRENT_DATE(), INTERVAL 7 DAY);
```
