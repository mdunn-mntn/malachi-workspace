# geo.location_data

## Purpose
Canonical geo-location dimension for the native BigQuery geo pipeline: every place MNTN targets or
resolves — countries, regions/states, DMAs, cities, and postal codes — as one row, with an ancestry
path and a MaxMind/GeoNames id. Reach for it to turn a `location_id`, `geoname_id`, `metro_id`, or
`old_location_id` into a human name, ISO code, time zone, or parent, and to walk the geo hierarchy.
It is the BQ-native replacement for the legacy CoreDW `geo.locations` view. NOTE: the native BQ geo
pipeline (Sheetal → Nivas) is **not yet fully complete** — for production queries the current
authoritative CoreDW copy is `dw-main-bronze.analytics_curated.geo_location_data`. Confirm freshness
before relying on this view for prod.

## Grain & keys
- **Grain:** one row per `location_id`, within a single `geo_version` snapshot. Confirmed:
  709,980 rows = 709,980 distinct `location_id`; one distinct `geo_version` currently loaded.
- **Primary/natural key:** `location_id` (unique; the legacy `geo.locations.location_id` is
  definitionally unique and can be a PK).
- **Foreign / join columns:** `parent_location_id` → `location_data.location_id` (self-reference,
  immediate parent); `hierarchy` = ARRAY of ancestor `location_id`s root→self; `old_location_id`
  → legacy CoreDW location id; `geoname_id` → MaxMind/GeoNames id; `metro_id` → DMA metro id.

## Column meanings (only the non-obvious ones)
- `location_id` — stable unique id for this place; the join key everything else references.
- `location_type_id` — the tier of the location. Observed counts + inferred meaning (confirm exact
  labels against a `location_types` lookup): `2` = country (251 rows, `iso_code` populated), `3` =
  DMA/metro tier (210 rows, all have `metro_id`), `4` = metro sub-tier (210 rows, `metro_id` +
  `sub_location1`), `5` = region/state (4,364 rows, `sub_location1` only), `6` = city (277,049 rows;
  time_zone + sub1/sub2, some `metro_id`), `7` = postal/sub-city (427,896 rows; time_zone + sub1,
  no sub2). The 210/210 for tiers 3 and 4 matches the count of US DMAs.
- `parent_location_id` — immediate parent's `location_id`; NULL at the country root.
- `hierarchy` — ARRAY<INT64> of the full ancestry `location_id` path root→self (e.g. a city =
  `[country, region, …, self]`). NOT NULL; always ends with the row's own `location_id`.
- `location` — the place's own name ("Afghanistan", "Saint George").
- `sub_location1` / `sub_location2` — denormalized ancestor names for display: `sub_location1` ≈
  state/region (e.g. "Alaska"), `sub_location2` ≈ country name (e.g. "United States"). Populated
  only for lower tiers; NULL for countries/regions.
- `iso_code` — ISO code of the location itself (populated for countries/regions; NULL for cities).
- `country_iso_code` — 2-letter ISO country code of the row's country ancestor (e.g. "US").
- `time_zone` — IANA tz name (e.g. "America/Adak"); populated for cities/postal tiers only.
- `metro_id` — DMA (Designated Market Area) metro id; only some cities/postal rows carry one.
- `geoname_id` — MaxMind/GeoNames identifier for cross-referencing MaxMind geo feeds.
- `old_location_id` — the legacy CoreDW `geo.locations` id, for mapping to pre-migration data.
- `geo_version` — snapshot version encoded as **epoch seconds** of the snapshot date
  (currently `1785110400` = 2026-07-27). `geo_version_ts` is the same instant as a TIMESTAMP. A
  single version is loaded today; a full-history pipeline would add versions here.

## Joins & relationships
- **Self-join for hierarchy:** `parent_location_id` → `location_id` walks up one level; `hierarchy`
  gives the whole path in one array (UNNEST to explode, or `hierarchy[OFFSET(0)]` = country root).
- **Fan-out warning:** joining a fact table on a **coarse** tier (e.g. `country_iso_code` or
  `metro_id`) fans out — those are shared by many `location_id`s. Join on `location_id` (or
  `geoname_id`/`old_location_id`) for a 1:1 lookup; anything coarser is one-to-many.
- **MaxMind bridge:** `geoname_id` links to the `dw-main-silver.geo.*` MaxMind feeds
  (`maxmind_blocks_ipv4`, `network_locations`) for IP→geo resolution.
- **Legacy bridge:** `old_location_id` maps rows back to CoreDW `geo.locations` / analytics data
  keyed on the old id.

## Gotchas
- **Pipeline not complete.** Native BQ geo pipeline is WIP (Sheetal → Nivas). For production geo
  lookups use `dw-main-bronze.analytics_curated.geo_location_data` (the current CoreDW copy in BQ)
  until this view is blessed. Do NOT replicate `geo.locations` from intprod → BQ (circular).
- **`iso_code` vs `country_iso_code`.** `iso_code` is the location's own ISO (country/region rows);
  `country_iso_code` is always the country ancestor. For a US city, `iso_code` is NULL but
  `country_iso_code` = "US". Don't use `iso_code` to filter to a country — use `country_iso_code`.
- **`location_type_id` enum is inferred**, not confirmed against a `location_types` lookup. The tier
  labels above are derived from row counts + which columns populate; verify before hard-coding.
- **Single `geo_version`.** Only one snapshot is loaded; a `geo_version` filter is a no-op today but
  will matter once the pipeline versions history. Don't assume this is the latest without checking.
- **`metro_id` is sparse** — NULL for most rows and even for many cities (only ~30k of 277k cities).
- **View metadata lies.** The view reports itself unpartitioned; the resolved physical
  `sqlmesh__geo.geo__location_data__182671189` reports `numRows: 0` / no partition (stale SQLMesh
  metadata). Empirically the table is a small unpartitioned dimension (~710k rows, ~11 MB scanned
  for a few columns).

## Cost & partitioning notes
- **Unpartitioned dimension** (`partition_by: none`, `require_partition_filter: false`). No date
  filter to apply. The table is tiny — a `COUNT`/scan of a handful of columns reads ~11 MB; a full
  `SELECT *` is still small (~710k rows, 15 narrow columns). Safe to scan in full.
- No clustering. Filter on `location_id` / `location_type_id` / `country_iso_code` as needed;
  cost is dominated by which columns you project, not by pruning.
- Prefer joining fact tables to a **de-duplicated, tier-filtered** slice of this dimension (e.g.
  `WHERE location_type_id = 6` for cities) rather than the whole table, to keep join cardinality tight.

## Example queries
```sql
-- Resolve a location_id to its name, country, tz, and full ancestry path
SELECT location_id, location_type_id, location, sub_location1, sub_location2,
       country_iso_code, time_zone, metro_id, hierarchy
FROM `dw-main-silver.geo.location_data`
WHERE location_id = 142250;

-- All US cities in a DMA, with their state
SELECT location_id, location AS city, sub_location1 AS state, metro_id, time_zone
FROM `dw-main-silver.geo.location_data`
WHERE location_type_id = 6 AND country_iso_code = 'US' AND metro_id = 743
ORDER BY city;
```
