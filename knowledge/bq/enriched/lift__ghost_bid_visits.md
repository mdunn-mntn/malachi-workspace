# enriched.lift__ghost_bid_visits

## Purpose
Per-IP outcomes table for MNTN's always-on ghost-bid holdout lift measurement (BER-2250 / INCR line, owned by Matt Brorby). Each row is one prospecting-bid subject (an IP that received bids for a campaign on a day), tagged with the experiment `arm` — `submitted` (treatment: bid actually submitted, can win an impression) or `ghost` (holdout: bid logic ran and was logged but never submitted, so the IP is never exposed) — plus whether that IP subsequently **won** an impression, **visited**, and **converted** within a 7-day-from-first-bid window. It is the silver source that feeds the gold incrementality reports `dw-main-gold.reporting.lift__ghost_bid_results` (per campaign × stratum) and `…lift__ghost_bid_rollup` (per advertiser & campaign_group: ITT lift, SE, CI, z, MH stratified estimator). Reach for it to compute raw visit/conversion lift (submitted-arm rate vs ghost-arm rate) or to reconstruct/ audit the gold rollups from the underlying subjects; for a ready-made per-campaign estimate prefer the gold `…rollup` one-liner. Sibling `enriched.lift__ghost_bid_audiences` holds exposure only (real-vs-ghost bid counts per IP/day).

## Grain & keys
- **Grain:** one row per **`dt` × `advertiser_id` × `campaign_group_id` × `campaign_id` × `ip`**. Each such subject carries exactly **one** `arm` (verified: on 2026-07-15, distinct `(campaign_id, dt, ip, arm)` = distinct `(campaign_id, dt, ip)` = row count = 87,575,444), so `arm` does not add grain — it labels the subject. An IP recurs across campaigns and days (24.7M distinct IPs vs 87.6M rows on one day ≈ 3.5 campaigns/IP), so `ip` alone is NOT the key.
- **Natural key:** `(dt, campaign_id, ip)` (campaign_id nests advertiser_id and campaign_group_id).
- **Foreign keys / join columns:** `advertiser_id` → advertisers; `campaign_group_id` → `public.campaign_groups.campaign_group_id` (the PK column is `campaign_group_id`, NOT `id`; picks up `product_id`); `campaign_id` → campaigns; `ip` → household IP (the randomization unit).

## Column meanings (only the non-obvious ones)
- **`dt`** (DATE) — the entry/observation day for the subject (the partition column). The **first** `dt` of the accumulated window is a left-censored stock and must be excluded from lift math (see Gotchas). Anchor a clean cohort with `ROW_NUMBER() OVER (PARTITION BY advertiser_id, campaign_id, ip ORDER BY dt) = 1`.
- **`arm`** (STRING) — experiment arm, ∈ {`ghost`, `submitted`}. `submitted` = treatment (bid submitted to the exchange, IP can win/serve). `ghost` = holdout (bidding logic ran and was logged, bid never submitted, IP never exposed). Holdout is a **fixed ~10% platform-wide** slice (empirically ~9% of rows: 7.6M ghost vs 79.9M submitted on 2026-07-15) — it is NOT a per-test tunable, so power scales only with campaign size and pooling.
- **`won`** (BOOL) — EXPOSURE / compliance flag: did this (treatment-eligible) IP actually win an impression. **Always `FALSE` for the `ghost` arm** (verified: n_won=0 for ghost) because ghost bids are never submitted; on the `submitted` arm ~37% win (29.2M of 79.9M). `ip_compliance` in the gold `_results` ≈ this win fraction (~50% pooled) → households reached ≈ `ip_compliance × n_treatment`.
- **`visited` / `converted`** (BOOL) — did the IP visit / convert within a **hard-coded 7-day window from `first_bid_time`**. This 7-day, fixed-arm window is baked into the pipeline; it is a platform 7-day reference for total-visit lift and CANNOT be re-parameterized for a ≥30-day or custom-arm (cap-N) estimand (build that from `guid_log`). `first_visit_time` / `first_conv_time` are the timestamps of those events. "Visit" here = pixel-fire within the window, **not** a Reporting Verified Visit — the pipeline undercounts Reporting VV (see Gotchas).
- **`bid_count`** (INT64) — number of bids this IP received in the window. **Post-treatment collider** — it reflects the treatment (submitted subjects average more bids: 30.9 vs ghost 25.5), so never use it as an uplift feature or stratum for a causal comparison.
- **`household_score`** (INT64) — general household intent score (0–10000; −1/NULL = unscored). `submitted` avg ~3473 vs `ghost` ~2653 on the sample.
- **`eff_score`** (INT64) — gated / effective intent score (the score after threshold gating actually used at bid time). Averages ~8600–8730 on the sample; distinct from the raw `household_score`.
- **`is_new`** (BOOL) — new-visitor flag from the client-side JS pixel (advertiser page tag), NOT a server-derived identity. Known to disagree with server logic 41–56% of the time — treat as advisory, not authoritative.
- **`objective_id`** (INT64) — funnel objective; effectively always `1` (prospecting) here — the holdout is prospecting-only by construction (a held-out IP never wins → never leaves the prospecting pool into retargeting).
- **`partner_id`** (INT64) — bidder leg: `8` = Beeswax/JVM leg, `79` = MNTN Rust leg. The leg is **1:1 with product**: Select (product_id=2) delivers ~97% on Rust (79); PTV/non-Select (product_id=1) is ~100% Beeswax (8). No campaign_group is split across legs.

## Joins & relationships
- **`campaign_group_id` → `public.campaign_groups.campaign_group_id`** (dimension; PK column is `campaign_group_id`, not `id`) → picks up `product_id` (1=PTV / 2=Select / 3=QF). N:1, no fan-out.
- **`advertiser_id` → advertisers**, **`campaign_id` → campaigns** — standard dimension lookups (N:1). Prefer `advertisers.company_name` for display (the fpa/advertiser-name unreliability rule).
- **This table → gold `reporting.lift__ghost_bid_results` / `…lift__ghost_bid_rollup`** — the gold views are the aggregated ITT estimators computed FROM these subjects (already time-boxed with the entry-cohort + drop-left-censored logic, reproducing the windowed silver calc to the digit). For a per-campaign estimate use the gold rollup one-liner (`WHERE level='campaign_group' AND entity_id=<campaign_group_id>`), not a hand-rolled aggregation here.
- **Sibling `enriched.lift__ghost_bid_audiences`** — exposure only (real-vs-ghost bid counts per IP/day), no outcomes. Dev copies of the whole family exist as `enriched__dev_matthewbrorby.*` and `enriched__dev_mbrorby_incr66.*` (do not read prod lift from dev).
- **IP is the randomization unit but is reused across advertisers/campaigns** — cohort any analysis by `(advertiser_id, ip, window)`, never by IP alone (the same IP can be holdout for one advertiser and treatment for another).

## Gotchas
- **Drop the first window day (left-censoring).** `dt` = window minimum (currently ~2026-06-22) is a left-censored stock that inflates `ghost_frac` and can manufacture a spurious NEGATIVE lift. Use the entry-cohort anchor (`ROW_NUMBER() … = 1`); on the clean set `ghost_frac` → 0.10 and pooled visit lift ≈ +5%.
- **7-day window is fixed and immature at the edge.** The newest usable `dt` is ~7 days behind the data edge (the 7-day visit window must mature). The window cannot be lengthened without rebuilding from `guid_log`.
- **Data floor ≈ 2026-06-22, no backfill.** The table accumulates daily with **no TTL**, but source `bronze.raw.bid_price_log` has a ~10-day TTL, so pre-06-22 subjects are unrecoverable. Logging went live 2026-05-27; a true ≥30-day matured window only arrives ~late-July 2026.
- **`won` is definitionally FALSE for ghost.** Do not treat ghost win-rate as a control exposure rate — ghost is the never-exposed counterfactual. Lift = submitted visit-rate vs ghost visit-rate (1.20% vs 0.69% on the 2026-07-15 sample).
- **`bid_count` is a collider; `is_new` is a noisy client pixel.** Neither is safe as a causal feature/stratum.
- **Pipeline "visit" ≠ Reporting Verified Visit.** This pixel-fire count UNDERCOUNTS Reporting VV (~2.9x for non-Select/PTV, ~1.1x for Select). For a client-facing CPIV/CPIA, convert with `incremental_VV = Reporting_VV × rel_lift/(1+rel_lift)` rather than summing this table's visits.
- **Cross-campaign/band pooling must be inverse-variance-weighted** (`SUM(abs_itt/se²)/SUM(1/se²)`), not a naive count pool (which is Simpson-confounded). Applies when rolling these subjects up by score band.
- **SQLMesh physical metadata can read stale.** The view resolves to `sqlmesh__enriched.enriched__lift__ghost_bid_visits__2999749496`; the physical name carries a version hash and changes on model rebuilds — re-resolve via `INFORMATION_SCHEMA.VIEWS` rather than hard-coding it.

## Cost & partitioning notes
- **Always filter `dt`** (DATE, partition column, DAY granularity). `require_partition_filter: false` — the filter is NOT enforced, but skipping it scans the whole ~2.95B-row / ~320 GB table. Empirically: one day = **2.3 GB**, full scan (no filter) = **44.3 GB** for a single `ip` column — filtering `dt` prunes ~19x.
- **No clustering.** Filtering `advertiser_id` / `campaign_id` prunes rows but not bytes (only `dt` prunes bytes). One full day of `SELECT *`-equivalent aggregation over all 19 columns billed ~4.3 GB on 2026-07-15.
- **Wide-ish (19 cols).** A single `dt` day is ~87M rows; scope both `dt` AND explicit columns. Prefer the gold `…rollup` for per-campaign lift instead of re-aggregating 87M subjects/day here.

## Example queries
```sql
-- Raw visit lift for one campaign_group, entry-cohort anchored, left-censored day dropped
WITH subj AS (
  SELECT *,
         ROW_NUMBER() OVER (PARTITION BY advertiser_id, campaign_id, ip ORDER BY dt) AS rn
  FROM `dw-main-silver.enriched.lift__ghost_bid_visits`
  WHERE dt BETWEEN DATE '2026-06-23' AND DATE '2026-07-15'   -- exclude 06-22 stock; partition-pruned
    AND campaign_group_id = <CGID>
)
SELECT arm,
       COUNT(*)                              AS n,
       COUNTIF(visited)                      AS visits,
       SAFE_DIVIDE(COUNTIF(visited), COUNT(*)) AS visit_rate
FROM subj
WHERE rn = 1                                  -- one first-bid anchor per IP
GROUP BY arm;
-- lift = (submitted visit_rate / ghost visit_rate) - 1
```
