# aggregates.tpa_membership_updates_log_insegments

## Purpose
Daily materialized snapshot of **holdout-group IP memberships** in **MNTN Third Party** (`data_source_id = 3`) audience segments, expanded to **campaign grain**. Every row is a holdout IP — the `tags` array is always exactly `["holdout"]` (100% of rows, all sampled days). Reach for it to enumerate *which IPs sit in the holdout for a given campaign's DS3 segments* and *each IP's household/intent score* — the raw material for holdout / incrementality (lift) measurement. This is the **current** member of three sibling rollups (see Joins): `_uber` (event-level change log) and `_insegments__legacy` (retired, 0 rows).

## Grain & keys
- **Grain:** one row per **(date, advertiser_id, campaign_id, segment_id, ip)**. Verified exact — on a single-advertiser day slice (adv 38363, 2026-07-17) `COUNT(DISTINCT ip|campaign_id|segment_id)` = `COUNT(*)` = 38,643,675 (no duplicates). One IP recurs once per (campaign, segment) it is a holdout member of; ~2.25B rows/day.
- **Key / join columns:** `ip` (join to event tables), `(advertiser_id, campaign_id)` (→ campaigns), `segment_id` (→ DS3 segment). Physical partition = `date`; cluster = `date, advertiser_id, campaign_id`.

## Column meanings (only the non-obvious ones)
- **`ip`** — the holdout household IPv4 as a STRING. Join key to bid/impression/visit tables; mind the `ip` vs `ip_raw` convention on partner tables.
- **`date`** — DAY partition = the snapshot day. Native `DATE` (no epoch encoding anywhere in this table); `time_unit: date`. Intra-day change *timing* is not here — use the `_uber` sibling (`time` / `activity_time` TIMESTAMPs).
- **`segment_id`** — the DS3 audience segment the IP is a member of (~14.7K distinct segments/day). No verified DS3-segment name dimension found this pass (DS3 ≠ the DS35/DS16 catalogs in `tpa.categories`) — treat as an opaque id.
- **`score`** — graduated household / intent score for the IP in that segment, **range 1–10000** (higher = stronger). **NULL for a large, day-varying share of rows** (41.7% on 2025-09-01, 66.2% on 2026-03-01, 46.7% on 2026-07-17). NULL = *unscored membership*, NOT zero — do not `COALESCE(score,0)` for averages.
- **`tags`** — `ARRAY<STRING>`, **always exactly `["holdout"]`** (100% of rows across every sampled day; `ARRAY_LENGTH=0` count = 0). Flags the row as a holdout-group membership. (In the `_uber` sibling `tags` is a `RECORD` array, not a string array.)
- **`data_source_id`** — **uniformly `3` = "MNTN Third Party"** (authoritative name from `integrationprod.data_sources`). The base `tpa_membership_update_log` carries DS2 (MNTN First Party) + DS3; this view is the **DS3 branch only**. NOTE: DS3 "MNTN Third Party" is a coarse membership-log bucket — it is **not** DS35 (LiveRamp "3P" IP segments) and **not** DS19 (MNTN Matched / MM). Do not filter on it expecting other values.

## Joins & relationships
- **`ip` → event tables** (`logdata.cost_impression_log`, `visits`/`ui_visits`, `bidder_bid_events`): partner side has **many rows per ip**, and *this table also has many rows per ip* (one per campaign×segment). Joining on `ip` alone **fans out on BOTH sides** (M:N). Scope by `(advertiser_id, campaign_id, segment_id)` or `SELECT DISTINCT ip` first.
- **`(advertiser_id, campaign_id)` → `campaigns`** (1:N — a campaign has many rows here). `campaign_id` = the bidder campaign / line-item id, not the campaign group; roll up via `campaign_groups` if group grain is needed.
- **`segment_id` → DS3 segment metadata** — no confirmed DS3-segment name table in BQ (DS3 segment names live_unverifiable this pass; `tpa.categories` covers DS35/16/13/14/21, not DS3).
- **Sibling variants (all in `aggregates`, all VIEWs over `sqlmesh__aggregates` physicals):**
  - `tpa_membership_update_log_uber` — event-level membership CHANGE log; richer schema (adds `time`, `activity_time` TIMESTAMPs, `version` INT; `tags` = RECORD array). ~5.96B rows, ~473 GB, partition `date`, cluster `date, advertiser_id, campaign_id`. Use for *when* an IP entered/left a segment.
  - `tpa_membership_updates_log_insegments` — **THIS doc**; flattened daily per-campaign holdout snapshot (no timestamps). ~745.9B rows, ~50.4 TB. ~118× more rows than `_uber` because it expands membership across campaigns per day, not per change event.
  - `tpa_membership_updates_log_insegments__legacy` — **retired, 0 rows** (last modified 2026-06-17, no partition/cluster). Same 8-col shape as current. Always query the **non-`__legacy`** name.
  - `tmul_holdout_segments` — separate holdout-oriented view in the same dataset (related but distinct object).

## Gotchas
- **Holdout-only table.** Every row is a holdout member (`tags = ["holdout"]`, 100%). Do NOT read row counts / distinct-IP counts as total segment reach — this is the holdout slice, not the full targeted audience.
- **`score` is NULL ~half the time** (day-varying 42–66%). NULL = unscored, not 0.
- **`data_source_id` is constant (3).** No selectivity from filtering it; and "MNTN Third Party" (DS3) is a membership-log bucket, not the DS35/DS19 sources used elsewhere.
- **Severe `ip` fan-out** — one IP → many (campaign, segment) rows; ~2.25B rows/day. Never join on `ip` unscoped.
- **No timestamp / DATE granularity only.** For intra-day change timing use `_uber`.
- **Legacy sibling is empty** — `_insegments__legacy` returns nothing.
- **SQLMesh note:** unlike many SQLMesh physicals (which report numRows:0 / partition:None), this view resolves to a real physical whose metadata IS populated — partition/cluster/rows read directly off `bq show`.

## Cost & partitioning notes
- **ALWAYS `WHERE date = '<day>'`** (or a tight range). Partition prune is the dominant lever:
  - `SELECT ip` **no date filter** (one col, full history) = **9.86 TB** [dry-run] → `SELECT ip WHERE date = '<day>'` (one col, one day) = **58.6 GB** [dry-run] — ~180× reduction.
- **Add `advertiser_id = <AID>` to hit the cluster key:** a 5-col single-advertiser day slice billed **2.06 GB** vs **140.7 GB** for the same columns across all advertisers that day — ~68× [actual].
- **Reference figures (one recent full day = 2026-07-17, labeled by column set):**
  - `SELECT *` one day = **174.0 GB** upper bound [dry-run].
  - 6-col aggregate (`ip, advertiser_id, campaign_id, segment_id, score, data_source_id`) one day = **140.7 GB** [actual].
  - `data_source_id` only, 3 days = **89.0 GB** (~29.7 GB/day) [actual].
  - `tags` + `score` one day = **50.5 GB** [actual]; `tags` only one day = **40.4 GB** [actual]; `advertiser_id` only one day = **38.0 GB** [actual].
- ~2.25B rows/day; an unfiltered scan of even one column touches ~10 TB. Never omit the `date` filter.

## Example queries
```sql
-- Holdout IPs (with score) for one advertiser's campaigns on one day — cheap (date + cluster key)
SELECT ip, campaign_id, segment_id, score
FROM `aggregates.tpa_membership_updates_log_insegments`
WHERE date = '2026-07-17' AND advertiser_id = 38363;

-- DISTINCT holdout IPs for a campaign's segment (dedupe the campaign×segment fan-out before joining events)
SELECT DISTINCT ip
FROM `aggregates.tpa_membership_updates_log_insegments`
WHERE date = '2026-07-17' AND advertiser_id = 38363 AND campaign_id = 566599 AND segment_id = 617699;
```
