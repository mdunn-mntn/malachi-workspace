# aggregates.guid_identity_daily

## Purpose
Daily rollup of the MNTN identity graph's raw edges. It aggregates a day of bidder auction
logs into the device-to-device / device-to-network connections used as a **core input to the
MNTN household (identity) graph**. For each `guid`, it records the network + device identifiers
(`ip`, `original_ip`, `ga_client_id`, `ua_raw`) seen together that day and how many events
supported each linkage. Owned by the **Identity team** (Jack Barbey / Weiang Li / Alexander
Jerneck). It is a **leaf node in the SQLMesh DAG** — its downstream consumers are Spark/Databricks
jobs that build the household graph, not other SQLMesh models. Reach for it when you need the
raw guid↔device/IP linkages for a given day rather than the resolved household graph.

## Grain & keys
- **Grain:** one row per distinct **daily linkage**. The **exact unique key is the 6-tuple**
  (`guid`, `ip`, `original_ip`, `ga_client_id`, `ua_raw`, `email`) — verified on 2026-07-15:
  81,962,630 rows = 81,962,630 distinct 6-tuples. The **5-tuple without `email` is NOT unique**:
  distinct 5-tuple = 81,807,914, so **154,716 rows (0.19%) share an identical 5-tuple** and are
  distinguished only by `email`. (`phone` is 100% NULL — adding it changes nothing; the +phone
  distinct count stays at 81,807,914.) **NOT one row per (guid, day).** On 2026-07-15, 81.96M rows
  vs 51.17M distinct `guid` → a guid averages **~1.6 rows/day** (it appears once per distinct
  IP / GA-client / user-agent / email combination it was seen with). Distinct
  (guid, ip, original_ip, ga_client_id) = 80.25M ≈ 97.9% of rows; `ua_raw` splits that to 99.8%
  (81.81M), and `email` splits the final 0.19% to 100%. **COUNT(DISTINCT guid) ≠ row count, and
  COUNT(DISTINCT 5-tuple) ≠ row count either — dedup on the 6-tuple (or aggregate to guid grain)
  yourself if you need it.**
- **Partition key:** `day` (DATE, DAY partitioning) — always filter it.
- **Cluster keys:** `guid`, `ga_client_id` — filtering/joining on `guid` (or `guid` then
  `ga_client_id`) prunes cluster blocks.
- **Primary identity key:** `guid` (the identity-graph node id; ~0 NULL — 29 of 82M on the sample day).

## Column meanings (only the non-obvious ones)
- **day** — DATE partition (UTC). The aggregation day the linkage was observed.
- **guid** — MNTN identity-graph node id (the person/household-device identity). Effectively never
  NULL. Clustered.
- **ip** — network IP associated with the linkage. **Always populated** (0 NULL on the sample day).
- **original_ip** — the pre-resolution / raw IP before identity resolution; **~14.5% NULL**
  (11.9M of 82M on 2026-07-15). When NULL, only the resolved `ip` is known.
- **ga_client_id** — Google Analytics client id (cookie-scoped). Present on **~76%** of rows
  (62.6M of 82M). Second cluster key.
- **ua_raw** — raw User-Agent string; splits **most** of the residual grain — it separates the
  ~1.9% of otherwise-identical (guid, ip, original_ip, ga_client_id) tuples into multiple rows
  (takes distinctness from 97.9% to 99.8% of rows). It is **not** the finest split: `email` splits
  the final 0.19% (see Grain & keys).
- **phone / email** — PII identifiers, **sparsely populated**. On 2026-07-15 `email` was on only
  ~0.7% of rows (585,776) and `phone` was **100% NULL (0 rows)**. Note: despite the sparsity,
  `email` is the column that **completes the row-uniqueness key** — it distinguishes the 0.19% of
  rows that share a 5-tuple (see Grain & keys). That is a different use from a join key: `email` is
  still **too sparse (~0.7%) to be a reliable JOIN key** to other tables, and `phone` carries no
  information at all (100% NULL).
- **event_count** — total number of underlying auction/bidder events supporting this linkage that
  day. Never NULL. avg 3.76, max 149,255 on the sample day.
- **distinct_seconds** — count of distinct 1-second timestamps among those events. **Always
  ≤ `event_count`** (0 rows violate this); equals `event_count` on ~88% of rows (i.e. usually
  ≤1 event per second, occasionally more). avg 3.0, max 9,580.
- **seconds** — `ARRAY<TIMESTAMP>` (native TIMESTAMP, **not an epoch int** — no unit conversion
  needed) of the event timestamps for this linkage. This is the widest column; reading it dominates
  scan cost (see Cost). `ARRAY_LENGTH(seconds)` relates to `event_count`/`distinct_seconds`.

## Joins & relationships
- **Upstream source:** daily **bidder auction logs** (the model extracts device-to-device
  connections from a day of auction data). Sibling model `aggregates.augmentor_identity_daily`
  is the augmentor-sourced counterpart; both feed the identity graph.
- **Downstream:** Spark/Databricks household-graph jobs (no downstream SQLMesh dependency — hence
  a leaf node).
- **Join on `guid`** → other identity-graph artifacts keyed by guid. `guid` is the intended join
  key and is a cluster key, so guid-filtered joins are cheap. Partner grain varies; this table is
  1:N on guid (multiple linkage rows per guid per day) — dedup/aggregate to guid before a 1:1 join.
- **Join on `ga_client_id`** → GA/pixel-sourced tables that carry a GA client id. ~76% coverage,
  so expect NULL-key drops. Cluster key #2.
- **Join on `ip` / `original_ip`** → IP-keyed tables. **Fan-out warning:** joining this daily
  aggregate to any per-event log (`bidder_bid_events`, `cost_impression_log`, `visits`) on IP is
  **many:many** and will explode — this is already a daily rollup, one IP maps to many guids and
  vice-versa. Also note the workspace rule: **no IP→IP bridging in BQ** (graph resolution is
  external), so do not attempt IP-graph self-joins here.
- Partner tables were not live-joined for this pass (this is a terminal daily aggregate, not meant
  to be row-joined to raw logs); fan-out directions above are the safe warnings.

## Gotchas
- **Grain is finer than guid×day.** A guid appears in ~1.6 rows/day. `COUNT(*)` overcounts guids;
  `COUNT(DISTINCT guid)` undercounts rows. Aggregate explicitly for per-guid metrics.
- **The 5-tuple is not a unique key — the 6-tuple (incl. `email`) is.** Deduping on
  (guid, ip, original_ip, ga_client_id, ua_raw) over-collapses ~155K rows/day (0.19%). If you need
  the true row grain, dedup on the 6-tuple including `email` (see Grain & keys).
- **45-day TTL** (partition `expirationMs` = 3,888,000,000 ms). Partitions auto-expire ~45 days
  after `day`; there is **no long history here**. For older identity history use the GCS archive /
  augmentor Spark pipeline, not this table.
- **No enforced partition filter** (`require_partition_filter` = false) — nothing stops a full-table
  scan. Always add `WHERE day = …`. An unfiltered 2-column scan is ~164 GB; `SELECT *` unfiltered
  is ~1 TB.
- **`phone` empty, `email` sparse.** On 2026-07-15 phone was 100% NULL and email ~0.7%. Don't rely
  on PII columns being populated.
- **NULL profile (sample day):** `ip` 0% NULL, `guid` ~0% NULL, `ga_client_id` ~24% NULL,
  `original_ip` ~14.5% NULL.
- **Volume-explosion / freshness risk.** Since ~2026-05-28, bidder auction/bid volume grew +3–10x
  (SSP onboarding for the PTV migration, with more expected). This model runs ~6 h/day and **has
  been timing out**; a single SQLMesh model was reported attempting ~1.8 PB/day. **Verify the latest
  available `day` before trusting recent partitions** — the BQ SQLMesh build may lag, and the
  identity team is migrating this work to a Spark/GCS pipeline. Alerts were added to the job in
  June 2026 (earlier, as of 2026-05-18, no failure alerting was configured).
- **No-share advertiser filter (policy).** As of late-Apr 2026 the model was slated to join
  `public.advertisers` and exclude no-share advertisers (No-Share Advertiser Policy); confirm
  whether that filter is live before using this for data-usage-sensitive work.
- **`seconds` is native `ARRAY<TIMESTAMP>`** (UTC), not epoch integers — no `UNIX_*` conversion.

## Cost & partitioning notes
- **Partition = `day` (DAY), cluster = (`guid`, `ga_client_id`), TTL = 45 days.** The one filter to
  **always** apply: `WHERE day = DATE '…'` (or a `day` range). Confirmed empirically — same
  `day,guid` column set: **1 day = 3.77 GB vs all partitions = 163.8 GB** (~43x prune).
- **Avoid `SELECT *`** — the `seconds ARRAY<TIMESTAMP>` + `ua_raw` columns dominate. Per-day figures
  by column set (dry-run `totalBytesProcessed`, decimal GB, 2026-07-15 partition; billed rounds up
  to the same or marginally more):
  - `SELECT *`, 1 day: **22.57 GB** (22,574,448,385 B)
  - narrow IDs `(guid, ip, original_ip, ga_client_id)`, 1 day: **7.57 GB** (7,570,054,535 B)
  - `SELECT day, guid`, 1 day: **3.77 GB** (3,770,279,878 B)
  - two INT payload cols `(event_count, distinct_seconds)`, 1 day: **1.97 GB** (1,967,103,120 B)
  These differ ~11x across column sets — select only what you need; never read `seconds` unless
  required.
- `MAX(day)` over all partitions costs ~28.5 GB (scans the `day` column across every partition) — do
  not use it as a cheap freshness probe.
- Physical backing storage: ~981 GB / ~3.57B rows across the ~45 live partitions.

## Example queries
```sql
-- Per-guid daily footprint (collapse the finer linkage grain to guid×day)
SELECT day, guid,
       COUNT(*)                         AS linkage_rows,
       COUNT(DISTINCT ip)               AS ips,
       COUNT(DISTINCT ga_client_id)     AS ga_clients,
       SUM(event_count)                 AS events
FROM `aggregates.guid_identity_daily`
WHERE day = DATE '2026-07-15'
GROUP BY day, guid
LIMIT 100;
```
