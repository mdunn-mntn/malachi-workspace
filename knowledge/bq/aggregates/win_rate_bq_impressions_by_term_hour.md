# aggregates.win_rate_bq_impressions_by_term_hour

## Purpose
The **numerator** side of the keyword-level win-rate rollup. Counts **won impressions** (ads
actually served) bucketed by campaign x keyword-term x hour-of-day. Reach for it when you need
win rate = impressions / bids at term granularity — e.g. diagnosing which keyword terms are
losing auctions, or how win rate varies by hour of day. It is meaningless alone: it is a raw
impression count and only becomes "win rate" once divided by the matching bid count in the
sibling table `aggregates.win_rate_bq_bids_by_term_hour` on the same 4-tuple. SQLMesh-materialized
daily rollup; small (~437 MB, ~12.8M rows) with a 45-day partition TTL.

## Grain & keys
- **Grain:** one row per **(date, hh, campaign_id, term_id)** — empirically unique (0 duplicate
  tuples in a one-day sample of 273,817 rows). Each row is one campaign's won-impression count
  for one keyword term in one hour of one day.
- **Key(s) / join columns:** the full 4-tuple `(date, hh, campaign_id, term_id)` is the natural
  key and the exact join key to the bids (denominator) table.
- **NULL `term_id` is its own bucket**, not a rollup total — it is the no-keyword / term-not-attributed
  impressions for that campaign-hour (~57% of impression rows carry NULL term_id and hold large
  volumes). Do not treat it as a subtotal of the term rows.

## Column meanings (only the non-obvious ones)
- **`hh`** — hour of day, integer **0–23** (verified: min 0, max 23, 24 distinct in a one-day
  sample). NOT an epoch; it is the bucket of the impression's timestamp. Timezone is whatever the
  upstream serving log uses (assume UTC unless proven otherwise). There is no minute/second grain.
- **`term_id`** — the keyword/interest **term** identifier, stored as a **numeric STRING** (e.g.
  `"215410"`). It is **campaign-scoped**: the same numeric id can carry different meaning across
  campaigns, so never join or group on `term_id` alone — always pair it with `campaign_id`.
  **NULL** = the no-term / not-attributed-to-a-keyword bucket (see Grain & keys); `""` empty
  string does not occur (0 empty in sample).
- **`impressions`** — count of **won impressions** (ads served) for that campaign x term x hour.
  This is the win-rate **numerator**. Always ≥ 1 (rows with 0 impressions are not emitted).
- **`date`** — DATE (not timestamp); the partition column, DAY-grained.
- **`campaign_id`** — INT64 campaign identifier; join to `core`/`campaigns` dims by this.

## Joins & relationships
- **`aggregates.win_rate_bq_bids_by_term_hour`** (the win-rate **denominator**) — mirror schema
  `(date, hh, campaign_id, term_id, bids)`. Join on the full 4-tuple `(date, hh, campaign_id, term_id)`.
  **Grain 1:1, no fan-out either direction**: both tables are empirically unique on the 4-tuple
  (bids side: 0 duplicate tuples in 308,406-row one-day sample). `win_rate = impressions / bids`.
- **NOT every impression row has a matching bid row and vice versa** — inner-joining a one-day
  sample matched only 79,552 of 273,817 impression rows / 308,406 bid rows. Most of the shortfall
  is the NULL-`term_id` bucket (equality joins drop NULL=NULL — see Gotchas); the rest is genuine
  key non-overlap. Choose INNER vs LEFT deliberately.
- **`campaign_id` → campaign dims** (`silver.core.campaigns` / `bronze.integrationprod.core_campaigns`):
  N:1 from this table (many term-hour rows per campaign). No fan-out when this table is the left/many side.
- `term_id` has no clean standalone dim here; interpret it only within its `campaign_id`.

## Gotchas
- **NULL `term_id` silently drops from equi-joins.** `JOIN ... USING(term_id)` (or `a.term_id = b.term_id`)
  never matches NULL=NULL, so the ~57% of impression rows and ~71% of bid rows with NULL term_id
  vanish from a naive win-rate join. To include the no-keyword bucket, join with
  `IS NOT DISTINCT FROM` on `term_id`, or `COALESCE(term_id,'__none__')` on both sides, or aggregate
  to campaign×hour first.
- **Per-row win rate is NOT guaranteed ≤ 1.** The head of the distribution is sane (top rows
  win_rate 0.06–0.63), but many low-volume long-tail rows show `impressions > bids` (57,937 of
  79,552 joined rows) — timing/attribution skew between the two independently-materialized
  aggregations (an impression counted this day whose bid landed in an adjacent bucket, etc.).
  **Aggregate numerator and denominator BEFORE dividing** (SUM(impressions)/SUM(bids)); don't average per-row ratios.
- **45-day partition TTL** (`expirationMs` = 3,888,000,000 ms). Only ~45 daily partitions exist at
  any time — no long historical backfill lives here. For anything older, go upstream.
- **`hh` is hour-of-day, not a timestamp** — do not add it to `date` expecting an event time; it is
  a bucket label 0–23.
- **`term_id` is a STRING** — quote it in filters (`term_id = '215410'`), and remember it's
  campaign-scoped.

## Cost & partitioning notes
- **Partition:** `date` (DAY). **Cluster:** `hh, campaign_id, term_id` (in that order — filtering
  `hh`/`campaign_id` prunes clustered blocks). `require_partition_filter` is **false**, but always
  filter `date` anyway.
- **The one filter to always apply:** `WHERE date = '<day>'` (or a tight range).
- **Cost (all 5 columns):** full-table scan (no date filter) ≈ **457,950,538 bytes (~437 MB)**;
  single-day filter ≈ **9,677,333 bytes (~9.2 MB)** — same column set, so the date filter prunes
  **~47x**. The whole table is tiny, so even a full scan is cheap, but filter `date` by habit.
- `approx_logical_bytes: 457950538` = the physical backing table's real `numBytes` (single physical
  table, not a UNION), ~437 MB. `approx_rows: 12832936`.

## Example queries
```sql
-- Term-level win rate for one day, INCLUDING the no-keyword (NULL term) bucket.
SELECT i.campaign_id, i.term_id, i.hh,
       i.impressions, b.bids,
       SAFE_DIVIDE(i.impressions, b.bids) AS win_rate
FROM       `aggregates.win_rate_bq_impressions_by_term_hour` i
FULL JOIN  `aggregates.win_rate_bq_bids_by_term_hour`        b
  ON  i.date = b.date AND i.hh = b.hh AND i.campaign_id = b.campaign_id
  AND i.term_id IS NOT DISTINCT FROM b.term_id          -- NULL-safe: keeps the no-term bucket
WHERE COALESCE(i.date, b.date) = DATE_SUB(CURRENT_DATE(), INTERVAL 2 DAY)
ORDER BY i.impressions DESC
LIMIT 100;

-- Campaign x hour win rate (aggregate BEFORE dividing — avoids per-row ratio > 1).
SELECT i.campaign_id, i.hh,
       SUM(i.impressions) AS won_impr,
       SUM(b.bids)        AS bids,
       SAFE_DIVIDE(SUM(i.impressions), SUM(b.bids)) AS win_rate
FROM       `aggregates.win_rate_bq_impressions_by_term_hour` i
FULL JOIN  `aggregates.win_rate_bq_bids_by_term_hour`        b
  ON  i.date = b.date AND i.hh = b.hh AND i.campaign_id = b.campaign_id
  AND i.term_id IS NOT DISTINCT FROM b.term_id
WHERE COALESCE(i.date, b.date) = DATE_SUB(CURRENT_DATE(), INTERVAL 2 DAY)
GROUP BY 1, 2;
```
