# aggregates.augmentor_identity_daily

## Purpose
Daily per-identity rollup that feeds the **MNTN identity / household graph**. Owned by the Identity team
(Jack Barbey / Weiang Li / Alexander Jerneck). For each device identity observed on a given day
(keyed by IP / IPv6 / IFA) it collects the auction timestamps, domains, user-agents, networks, and
inventory sources seen — the raw material the graph builder uses to extract device-to-device
connections. Downstream consumers are **Spark jobs on Databricks**; there are **no downstream SQLMesh
dependencies**, which is why this appears as a leaf node in the SQLMesh DAG.

**CRITICAL current state (verified 2026-07-19 — reconciles prose):** the original BQ SQLMesh model was
**disabled** on 2026-06-08 after bidder volume grew +10–100× (late May 2026) and the job timed out
(~6 h/day). It was replaced by a **GCS/Spark pipeline** (Airflow DAG `augmentor_daily_gcs.py`, hourly
Dataproc batches → daily merge, ~40–50 min end-to-end). The `aggregates.augmentor_identity_daily`
view is now a thin pass-through:

```
aggregates.augmentor_identity_daily  (VIEW)
  → sqlmesh__aggregates.aggregates__augmentor_identity_daily__2089722211  (VIEW — unnests Parquet LIST arrays)
    → dw-main-bronze.external.augmentor_identity_daily__v1  (EXTERNAL Parquet, hive-partitioned on dt)
      → gs://mntn-data-archive-dev/identity/augmentor_identity_daily/*   ← EMPTY as of 2026-07-19
```

The GCS prefix currently matches **no files**, so any query against the view (or the external table)
**errors** with `Failed to expand table … matched no files`. **Treat the BQ view as non-functional**;
the live identity signal is consumed from GCS/Databricks directly, not through this view.

## Grain & keys
- **Grain (intended):** one row per **identity per day**. Identity = the device key observed
  (`ip` / `ipv6` / `ifa`); the arrays hold that identity-day's aggregated observations.
- **Key(s):** `day` + (`ip` / `ipv6` / `ifa`).
- **Currently unpopulated** — grain is documented from schema + pipeline design, not from live rows
  (the table errors on read). **Treat the single-key identity×day grain as tentative:** the closest
  analog, the sibling `guid_identity_daily`, turned out to be a **finer** multi-column linkage-tuple
  grain (~1.6 rows per entity per day), not one-row-per-entity-per-day. An identity could plausibly
  appear on multiple rows here too (e.g. an `ip`-keyed and an `ifa`-keyed row from the same auction),
  so verify actual grain once the table is repopulated before de-duping on it.

## Column meanings (only the non-obvious ones)
- **day** — DATE, the observation day. This is an **in-file Parquet data column**, NOT the hive
  partition. Filtering `day` does **not** prune GCS files (see Cost & partitioning). The real hive
  partition is `dt` (STRING), which the view drops.
- **ip / ipv6 / ifa** — the identity keys. `ipv6` is populated for IPv6 traffic (with `ip` NULL for
  IPv6 auctions — same split as bidder logs, IP lives in `device_ipv6`); `ifa` is the mobile/CTV
  device ad-ID. A row is keyed on whichever identity was observed.
- **seconds** — `ARRAY<TIMESTAMP>`. **Name is a misnomer:** these are native TIMESTAMP values (the
  individual auction observation times for the identity that day), **not** integer epoch seconds — no
  unit decode needed. (Time-unit is native TIMESTAMP; there are no integer-epoch columns in this table.)
- **domains / user_agents / networks / inventory_sources** — `ARRAY<STRING>` of the values observed
  for the identity that day (domains bid on, user-agents, networks/SSPs, inventory sources). The
  SQLMesh view flattens the upstream Parquet LIST straight through
  (`ARRAY(SELECT element FROM UNNEST(<col>.list))`) with **no DISTINCT/dedup** — whether the arrays
  hold distinct values depends on the upstream Spark/GCS job, not this view, so do not assume
  `ARRAY_LENGTH()` is a distinct count. Declared NON-nullable: the unnest yields an empty array,
  never NULL.

## Joins & relationships
- **silver.logdata.v_augmentor_log** — the per-bid-request bidstream log (one row per upstream bid
  eval; epoch in **milliseconds**). Conceptually the row-level source of the same identity signal.
  Fan-out: **1 daily identity row ↔ N per-request rows** (heavy). NOTE: the current GCS/Spark pipeline
  reads bidder **auction-log Parquet from GCS directly**, so this daily table is **not** a live
  BQ-downstream of `v_augmentor_log`. NOTE: `v_augmentor_log` has **no `day` column** (its time cols
  are `time` TIMESTAMP and `epoch` INTEGER) — enrich by joining `ip` + `DATE(v_augmentor_log.time) =
  augmentor_identity_daily.day` and expect heavy fan-out.
- **aggregates.guid_identity_daily** — sibling Identity-team model (guid-keyed device/network
  linkages extracted from **bidder auction logs**), also feeding the identity graph. Unlike this
  table it is **NOT** migrated to GCS — it is a live, populated BQ **TABLE** (~3.56B rows / ~976 GB,
  DAY-partitioned on `day`, 45-day TTL, clustered `(guid, ga_client_id)`) that queries normally.
  Its grain is **finer than identity×day**: one row per `(guid, ip, original_ip, ga_client_id,
  ua_raw)` daily linkage (~1.6 rows/guid/day) — see its own doc. Do not assume the augmentor and
  guid tables share grain or backing architecture.
- **Downstream:** Databricks/Spark identity-graph builder — no SQLMesh deps (leaf node).

## Gotchas
- **NON-FUNCTIONAL via BQ (2026-07-19):** view → external table → **empty GCS prefix**
  (`gs://mntn-data-archive-dev/identity/augmentor_identity_daily/*`). Every read errors
  `matched no files`. Confirmed empirically (dry-run + COUNT both failed).
- **Dev bucket:** output path is on **`mntn-data-archive-dev`** (a DEV bucket), not a prod archive.
  Staging/experimental — data may be transient, relocated, or written elsewhere. Do not build prod
  dependencies on this BQ view.
- **`day` ≠ `dt`:** the view exposes the in-file `day` (DATE) and **drops** the hive partition `dt`
  (STRING, e.g. `'2026-07-18'`). Filtering `day` does not prune GCS partitions.
- **`seconds` is TIMESTAMP, not epoch seconds** — the column name misleads.
- **Arrays are never NULL** (empty array instead) — SQLMesh unnest guarantee.
- **History:** was a monolithic BQ SQLMesh model timing out ~6 h/day; disabled after +10–100× bidder
  volume growth (late May 2026), migrated to hourly Dataproc + daily merge. For large auction-log
  aggregations, Identity's guidance is Spark/GCS over BQ SQLMesh (auction_events_agg scanned 13.2 TiB/hr
  and timed out in BQ).

## Cost & partitioning notes
- **Right now there is no cost surface:** any query **errors** (no files) → 0 useful bytes. Don't rely
  on this view; go to GCS/Databricks for the identity signal.
- **When populated, prune at the external layer:** the real hive partition is **`dt`** (STRING) on
  `dw-main-bronze.external.augmentor_identity_daily__v1` — filter `dt` **there** to prune GCS files.
  Through this view you only have `day`, an in-file column that does **not** prune.
- **`require_partition_filter` is NOT enforced** (external table).
- **Dry-run measurement (2026-07-19):** `SELECT day, ip … WHERE day = DATE '2026-07-18'` (2-column,
  filtered) — **could not be measured**: dry-run failed to expand the external table (matched no files),
  so no byte estimate exists. `approx_logical_bytes` = null (external table `numBytes` = 0, GCS prefix
  empty).
