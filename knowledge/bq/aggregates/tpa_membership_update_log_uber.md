# aggregates.tpa_membership_update_log_uber

## Purpose
Daily materialized **snapshot** of which IPs are members of each TPA (Third-Party Audience) segment,
per campaign. Despite the "update_log" name it is **not** an event/delta stream — each `date`
partition is a full re-listing of the current membership set (a fresh full snapshot written once per
day). Reach for it to answer "which IPs were in TPA segment S for campaign C on day D," to size a TPA
segment's IP footprint, or to reconstruct historical membership over time. It is the **richest of three
sibling variants** (`_uber`, `_insegments`, `_insegments__legacy`): `_uber` alone carries `time`,
`activity_time`, and `version`.

## Grain & keys
- **Grain:** one row per **(ip, campaign_id, segment_id)** within a `date` partition — a per-day
  membership snapshot. Verified on 2026-07-15: `COUNT(*)` = `COUNT(DISTINCT ip|campaign_id|segment_id)`
  = 36,585,423 (exactly equal → no duplicates on that combo).
- **Natural key:** `(date, ip, campaign_id, segment_id)`.
- **Join columns:** `ip` (to bid/impression/visit logs), `advertiser_id`, `campaign_id`,
  `segment_id` (to segment/audience dims), `data_source_id`.

## Column meanings (only the non-obvious ones)
- **ip** — the member IP (STRING, IPv4 observed). This is the membership subject, not a device. ~36.6M
  distinct IPs/day, ≈ the row count (an IP can appear in multiple segments/campaigns).
- **time / activity_time** — both TIMESTAMP and, in current data, **identical and uniform within a
  partition**: the daily snapshot instant `<date> 08:00:00 UTC` (= midnight US-Pacific). They are the
  batch snapshot timestamp, **not** per-row membership/activity times. `DATE(time) = DATE(activity_time)
  = date` for every row (verified 2026-07-15). Do not treat `time` as when the IP joined the segment.
- **version** — INT64 **millisecond epoch**, a segment/audience *version stamp* (not a per-row event
  time): `1741380888811` = `TIMESTAMP_MILLIS(...)` = 2025-03-07 20:54:48 UTC. Marks which version of the
  TPA segment definition produced the membership. `version = 0` = unversioned/default (a small residual
  count of rows). Same across all IPs sharing a segment on a given day.
- **data_source_id** — segment source id; **only `2` observed** (2026-07-15) → the TPA / third-party
  audience source. Not the DS4/DS8/DS13/DS19/DS46 prospecting/MM data-source taxonomy.
- **segment_id** — the TPA segment/audience the IP is a member of (campaign-scoped). Only a handful of
  distinct segments/day in current data (2–3 observed).
- **score** — INT64, **entirely NULL** in current data (unused in this variant; present for schema
  parity with the `_insegments` siblings).
- **tags** — `ARRAY<STRUCT<tag_value STRING>>`, **REQUIRED array but empty `[]`** in current data
  (never NULL — the array itself is non-nullable; its elements are absent).
- **date** — DATE **partition column** = the snapshot date = `DATE(time)`.

## Joins & relationships
- **Sibling variants (each a separate physical SQLMesh model; all thin `SELECT *` pass-through views):**
  - `_uber` (this table) — superset: adds `time`, `activity_time`, `version`.
  - `aggregates.tpa_membership_updates_log_insegments` — **current** slim variant. Columns:
    `ip, date, advertiser_id, campaign_id, segment_id, score, tags, data_source_id` (no time/version).
  - `aggregates.tpa_membership_updates_log_insegments__legacy` — **deprecated** predecessor of
    `_insegments` (identical column set; the `__legacy` suffix marks it superseded). Prefer the
    non-legacy one.
- **ip → bid/impression/visit logs** (`logdata.bidder_bid_events`, `logdata.cost_impression_log`,
  `logdata.visits`): partner grain is one row per **event**, so a join fans out **1:N** (one snapshot
  membership row → many events for that IP). Aggregate the event side first or the membership footprint
  will be over-counted.
- **segment_id / audience** dims (`bronze.integrationprod.audience_segments` / `audiences`): partner is
  ~1 row per segment → **N:1** (many member IPs per segment). Filter dims `deleted=FALSE AND
  is_test=FALSE`.
- **advertiser_id / campaign_id** → `integrationprod.advertisers` / `campaigns`: **N:1**, safe.

## Gotchas
- **Snapshot, not a change-log.** Name says "update_log" but every partition is a full membership
  re-listing. To detect membership *changes* you must diff consecutive `date` partitions yourself; there
  is no add/remove event semantics.
- **Currently populated for a SINGLE advertiser.** Every sampled day (2026-07-09..18 and re-checked
  2026-07-27) shows exactly `advertiser_id = 34411`, `data_source_id = 2`, with only a handful of
  campaigns/segments (3 on 2026-07-09..18, 2 on 2026-07-27). Do **not** assume this table covers all
  advertisers/segments — it is narrow right now. Re-check breadth before generalizing.
- **`score` is always NULL and `tags` always empty** in current data — don't build logic on them here.
- **`time`/`activity_time` are a single per-day constant** (08:00 UTC = midnight PT), not real per-IP
  timestamps — useless as an event clock; use `date`.
- **`version` is milliseconds, not seconds** and is a segment-version stamp, not a row timestamp.
- **NULL `date` partition exists** (`__NULL__`, 0 rows) — harmless but present in INFORMATION_SCHEMA.
- **SQLMesh view → physical hash** `...__556747428`; query the clean `aggregates.` name. Physical
  `numRows`/metadata are real here (not the SQLMesh 0-row trap).
- **Partition write lag:** partition `date=D` is (re)built by SQLMesh around **D+1 to D+2 00:45–01:00
  UTC**, so the latest day or two may be absent/partial early in the morning.

## Cost & partitioning notes
- **Partition:** DAY on **`date`** (empirically confirmed: single `ip` column, no filter =
  **90.2 GB** upper-bound dry-run vs one `date` day = **0.85 GB** → ~106× prune). **Always filter
  `date`.** `require_partition_filter` is **not enforced**, so an unfiltered query silently full-scans.
- **Cluster:** `[date, advertiser_id, campaign_id]` — adding `advertiser_id`/`campaign_id` predicates
  prunes further within a day (though only 1 advertiser exists today).
- **Backing storage (all columns, `bq show` numBytes):** ~501.8 GB / ~467 GiB across
  daily partitions from **2026-01-01 → present** (2026-07-28), ~6.33B rows (~30–37M rows/day).
- **Measured dry-runs (label = exact column set):**
  - `SELECT ip` no filter → 90.2 GB (upper bound). `SELECT ip WHERE date = 1 day` → 0.85 GB.
  - `COUNT DISTINCT advertiser_id/campaign_id/segment_id/data_source_id/time` over 8 days →
    13.15 GB billed (5 int/timestamp columns × 8 partitions).
- One filter to always apply: **`WHERE date BETWEEN DATE '2026-07-01' AND DATE '2026-07-15'`** (bound
  both sides). Avoid `SELECT *`
  (the `tags` array and both timestamps inflate scan cost vs the int keys).

## Example queries
```sql
-- IP membership footprint of each TPA segment for one day
SELECT campaign_id, segment_id, COUNT(DISTINCT ip) AS member_ips
FROM `aggregates.tpa_membership_update_log_uber`
WHERE date = DATE '2026-07-15'
GROUP BY campaign_id, segment_id
ORDER BY member_ips DESC;

-- Membership churn: IPs added between two snapshots (diff, since it's not a change-log)
SELECT COUNT(*) AS added_ips
FROM (
  SELECT ip FROM `aggregates.tpa_membership_update_log_uber`
  WHERE date = DATE '2026-07-15' AND segment_id = 299734
  EXCEPT DISTINCT
  SELECT ip FROM `aggregates.tpa_membership_update_log_uber`
  WHERE date = DATE '2026-07-14' AND segment_id = 299734
);
```
