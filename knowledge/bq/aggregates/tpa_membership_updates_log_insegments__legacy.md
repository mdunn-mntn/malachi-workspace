# aggregates.tpa_membership_updates_log_insegments__legacy

## Purpose
Daily "which IP is in which TPA (Third-Party Audience) segment" membership table — the flattened, in-segments-only projection of the TPA membership event stream. Use it to resolve, for a given day, the set of (advertiser, campaign, segment) memberships an IP belongs to plus its membership `score`, e.g. to attribute augmentor/bid activity back to a segment or to reconstruct audience composition on a historical date.

This `__legacy` object is a **backward-compatibility, full-history VIEW**. It is a `UNION ALL` of two branches:
1. **Live branch** — the go-forward SQLMesh model `aggregates.tpa_membership_updates_log_insegments` (physical `sqlmesh__aggregates.aggregates__tpa_membership_updates_log_insegments__4126169799`), filtered to `date >= '2025-09-11'`.
2. **Historical branch** — a frozen GCS-Parquet external table `dw-main-bronze.external.tpa_membership_updates_log_insegments_by_day_historical` covering **2025-08-31 .. 2025-09-10** only (11 days); it casts `date` STRING->DATE and parses `tags` STRING->`ARRAY<STRING>` via `JSON_VALUE_ARRAY`.

**Which is current:** prefer the **non-legacy** `tpa_membership_updates_log_insegments` for go-forward analysis — it is the live SQLMesh model. `__legacy` exists only to stitch the pre-2025-09-11 GCS backfill onto the live model so older full-history queries keep resolving; in practice it adds barely more coverage than the live physical (the physical already retains partitions back to 2025-09-01). The **`_uber`** sibling (`tpa_membership_update_log_uber`) is the finer-grained event log: it keeps `time`/`activity_time` TIMESTAMPs and a `version` column and is NOT limited to in-segment rows — `insegments` is the day-grain in-segment projection derived from that stream.

## Grain & keys
- **Grain:** one row per **(ip x segment_id x date)** IP-in-segment membership record — a per-day snapshot of segment membership, not a change event (no enter/leave timestamps here; that lives in `_uber`).
- **Key(s) / join columns:** `ip` (IP address, the identity key), `date` (partition + the "as-of day"), `segment_id`, `advertiser_id`, `campaign_id`, `data_source_id`. No single surrogate PK; the natural key is the (ip, date, advertiser_id, campaign_id, segment_id) tuple.

## Column meanings (only the non-obvious ones)
- **`ip`** — the IP address; the identity key for a TPA membership. This table is IP-keyed (no cookie/device id). There is no IP->IP bridging in BQ.
- **`date`** — DATE (calendar day), the partition column and the "as-of" day of the membership snapshot. On the historical branch this is derived by casting a STRING partition value; on the live branch it is a native partitioned DATE.
- **`segment_id`** — the TPA/audience segment the IP is a member of. Campaign-scoped audience segment id. ~14.7K distinct segments observed on a single day (2026-07-15).
- **`score`** — the membership/household score for this IP-in-segment, scaled **1..10000** (0..10000 family, same convention as RTC/AHS where 10000 = max). **Nullable** — observed NULL on `holdout`-tagged rows (holdout members carry the tag but no score).
- **`tags`** — `ARRAY<STRING>` of membership flags/labels; observed value **`"holdout"`** (marks IPs held out of activation — ties to the sibling `tmul_holdout_segments`). Empty array (not NULL) when no flags apply; the column is `NOT NULL` at the array level but individual arrays can be empty. On the historical branch this is JSON-parsed from a STRING.
- **`data_source_id`** — the DS the membership came from. Observed **only `3`** (third-party interest audiences) on the sampled day; the TPA family is documented as DS 2 + DS 3, so DS 2 may appear in other slices. Note DS 4 (CRM) does NOT flow through TPA membership tables — CRM is resolved via the identity graph, not here.
- **`advertiser_id` / `campaign_id`** — the advertiser/campaign that owns the segment targeting; also the 2nd/3rd cluster keys.

## Joins & relationships
- **`aggregates.tpa_membership_updates_log_insegments` (non-legacy, live)** — SAME physical table backs the recent branch of this view (1:1 on the shared date range); this `__legacy` view just adds the 2025-08-31..09-10 GCS backfill on top. Prefer the non-legacy name for go-forward work.
- **`aggregates.tpa_membership_update_log_uber`** — the upstream finer-grained event log (has `time`/`activity_time`/`version`). `insegments` is a day-grain projection of it; joining back to `_uber` is many-rows-per-day and NOT 1:1 — use it only when you need change timestamps/version.
- **`audience_segments` / `audiences`** (`bronze.integrationprod`) — join `segment_id` -> `audience_segments` to resolve the targeting expression and confirm advertiser ownership; filter `deleted=FALSE AND is_test=FALSE`. audience_segments is a dim (1 row per segment) so this join does not fan out; audiences are templates.
- **`advertisers` / `campaigns`** — `advertiser_id`/`campaign_id` join to the integrationprod dims (1:1, dim side) for names; `fpa_advertiser_verticals.advertiser_name` is unreliable — use `advertisers.company_name`.
- **`bronze.raw.augmentor_log` / bidder logs** — this table is the advertiser/segment attribution bridge for IP-keyed pre-bid logs that lack `advertiser_id`: join on `ip` (+ align `date`). **Fan-out warning:** an IP is typically in MANY segments/advertisers on a day (multiple rows per ip), so joining augmentor/bid rows on `ip` alone multiplies rows — join on `ip` AND `segment_id` (or aggregate this table to the grain you need first).

## Gotchas
- **Federated UNION view.** Because one branch is an external GCS-Parquet table, `--dry_run` byte estimates come back "accuracy is unknown because of federated tables or clustered tables", and the external branch cannot use BQ clustering/partition pruning the way the live physical does. For clean, prunable, cheaper scans of recent data, query the non-legacy `tpa_membership_updates_log_insegments` (or the physical) directly.
- **Boundary at 2025-09-11.** The live branch is filtered `date >= '2025-09-11'`; the historical branch is `2025-08-31..2025-09-10`. So 2025-09-01..09-10 comes from the frozen GCS backfill even though the live physical also has those partitions — the two branches are stitched, not overlapping. Total view coverage: **2025-08-31 -> present**.
- **`score` NULL on holdout rows.** Do not assume `score` is always populated — holdout-tagged members have NULL score. Filter/handle NULLs before averaging.
- **Huge daily volume.** ~2.5 B rows/day (2026-07-15), ~745.9 B rows total on the live branch. One IP appears once per (advertiser, campaign, segment) it belongs to, so per-IP row counts are large. Never scan without a `date` filter.
- **DS domain is narrow in practice.** Only `data_source_id = 3` was present on the sampled day; treat DS 2 as possible-but-verify rather than guaranteed. DS 4 (CRM) is absent by design.
- **`tags` semantics.** `tags` is an operational flag array (e.g. `holdout`), not free-form metadata; the sibling `tmul_holdout_segments` view is the holdout-focused cut.
- **Physical `numRows` is trustworthy here.** Unlike most SQLMesh physicals, the live insegments physical reports a real `numRows` (7.46e11) via `bq show`; the `__legacy` physical itself is a VIEW (numRows 0) — resolve through it.

## Cost & partitioning notes
- **The one filter to always apply: `WHERE date = '<day>'`** (or a tight `date BETWEEN`). Partition = `date` (DAY), cluster = `(date, advertiser_id, campaign_id)` on the live branch. `require_partition_filter` is not enforced (a no-filter scan is allowed) — so it is on YOU to add the `date` predicate. Add `advertiser_id`/`campaign_id` equality predicates too, to exploit clustering.
- Backing storage (live branch physical `__4126169799`, from `bq show` numBytes): **~50.4 TB / ~745.9 B rows across daily partitions** (2025-09-01 -> present; INFORMATION_SCHEMA total_logical_bytes was ~45.5 TB at 2026-07-19 enrichment — table has grown). No TTL (partitions retained indefinitely). The historical GCS-Parquet branch reports `numBytes 0` in `bq show` (external), so total logical bytes is not summable -> `approx_logical_bytes: null`.
- **Dry-run scan estimates (via `--dry_run`, labeled by column set — same-column-set only is comparable):**
  - `SELECT ip WHERE date='2026-07-15'` (1 col, 1 day): **~54.5 GB** (58,472,355,306 B).
  - `SELECT ip` (1 col, NO date filter, full view): **~14.8 TB** (16,287,540,112,308 B) — the `date` filter prunes ~**280x** for this column set.
  - `SELECT *` (all 8 cols, 1 day `2026-07-15`): **~161.8 GB** (173,748,766,323 B) — all-columns is ~3x the single-column scan; select only needed columns.
  - Actual run: `data_source_id + score + segment_id + advertiser_id` grouped, 1 day = **86.0 GB billed**. One day of this table is expensive; aggregate, don't row-scan.
- Estimates carry the federated-table "accuracy unknown" caveat. For repeated recent-data work, prefer the non-legacy `tpa_membership_updates_log_insegments` (pure partitioned+clustered physical, no external branch).

## Example queries
```sql
-- Segments/score an IP belongs to on a specific day (partition-pruned, clustered)
SELECT advertiser_id, campaign_id, segment_id, score, tags, data_source_id
FROM `dw-main-silver.aggregates.tpa_membership_updates_log_insegments__legacy`
WHERE date = '2026-07-15'
  AND ip = '<ip>';

-- Attribute IP-keyed pre-bid rows to segments (join on ip AND segment to avoid fan-out)
SELECT a.ip, m.advertiser_id, m.campaign_id, m.segment_id, m.score
FROM `dw-main-bronze.raw.augmentor_log` a
JOIN `dw-main-silver.aggregates.tpa_membership_updates_log_insegments__legacy` m
  ON m.ip = a.ip AND m.segment_id IN UNNEST(a.mntn_segments)
WHERE a.time >= '2026-07-15' AND a.time < '2026-07-16'
  AND m.date = '2026-07-15';
```
