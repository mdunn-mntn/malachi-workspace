# aggregates.pmp_impression_rates

## Purpose
A tiny **current-state snapshot** of impression availability, one row per PMP
(private-marketplace / deal-based) inventory deal. It answers "how much can each
PMP deal deliver, and how many distinct IPs does it reach?" — the deal-level inputs
to **PMP impression forecasting**. The olympus `inventory-forecast` app consumes a
sibling of this data for deliverability modeling. It is a lookup/dimension table,
not a fact/event table: 79 rows, ~4 KB, refreshed daily (the `yesterdays_inventory`
column signals a nightly rebuild). Reach for it when you need a deal's recent
delivery rate or reach, or to enrich bid/impression events with per-deal availability.

## Grain & keys
- **Grain:** one row per **`partner_deal_id`** (one PMP deal). Verified 79 rows =
  79 distinct `partner_deal_id`, zero NULL keys.
- **Key / join column:** `partner_deal_id` — the exchange-side deal identifier
  (STRING, e.g. `WAR-1MP-00729`, `NBC-MNT-00020`, `PLU-US-SS-MAG-MNTN-SELECT-PROCEDURAL-02`).
  Matches `partner_deal_id` on `core.private_marketplace_deals` exactly. The bid/win/
  impression logs also carry deal IDs (`bidder_bid_events.selected_pmp_deal_id`,
  `win_logs.deal_id`, `impression_log.deal_id`) but those are **exchange-prefixed**
  (e.g. `stv/…`, `pm/…`) — strip the `^[a-z]+/` prefix before matching (see Joins).

## Column meanings (only the non-obvious ones)
- **`partner_deal_id`** — exchange-side PMP deal ID (STRING), the grain key. Not the
  integer `private_marketplace_deal_id` PK; this is the human/exchange string ID.
- **`days_with_data`** — number of days in the trailing window that had impression
  data (observed only **2 or 7** on the current snapshot; effectively a 7-day rolling
  window). It likely drives the `avg_daily_impression_rate` denominator (see that column
  — inferred, not proven) and doubles as a data-completeness/recency gauge: a low value
  (e.g. 2) means the rate rests on a thin base and tends to be inflated.
- **`distinct_ips`** — count of distinct IPs reached/available on the deal over the
  window. Reach measure, not impressions. Wide range — observed **~8.6K to ~14.3M**
  (2026-07-19). Because this is a daily-overwrite snapshot the ceiling drifts, so do
  **not** hard-size off any pinned value.
- **`avg_daily_impression_rate`** — the deal's average daily impression rate over the
  window: a window impression-sum ÷ a ~7-day denominator. The minimum observed value
  0.1429 = exactly 1/7 is **consistent with** a 7-day window but does not uniquely prove
  the denominator is `days_with_data` vs a fixed 7 — the only rows that could distinguish
  them (the 3 with `days_with_data = 2`) carry whole-integer rates (16–22) that satisfy
  both. Treat the exact denominator as **inferred, not proven**. Small float, observed
  **0.14–22.0**. Empirically the deals with only 2 days of data carry the highest rates
  (thin base inflates them) — read alongside `days_with_data`.
- **`yesterdays_inventory`** — prior-day impression inventory count available on the
  deal (observed **~1.3K–178M**). Its presence is why the table is a daily-refreshed
  snapshot rather than a historical series.

## Joins & relationships
- **`partner_deal_id` → `core.private_marketplace_deals.partner_deal_id`** (PMP deal
  dimension; `silver.core` thin view over `bronze.integrationprod.core_private_marketplace_deals`).
  Verified **1:1**: all **79/79** deals match, and the full dimension is empirically
  unique on `partner_deal_id` (**1,072 rows = 1,072 distinct**), so an undeduped
  `LEFT JOIN` does not fan out. Gives deal `name`, `advertiser_id`,
  `campaign_group_id`, `floor_price`, `active`.
- **`partner_deal_id` → the bid/win/impression logs' deal fields** — there is **no
  `pmp_deal_id` column** on any of them (that name is wrong). The real columns are
  `logdata.bidder_bid_events.selected_pmp_deal_id` (scalar STRING; the chosen deal) or
  `pmp_deal_ids` (a **repeated RECORD** of candidate deals — needs `UNNEST`), and
  `logdata.win_logs.deal_id` / `logdata.impression_log.deal_id` (scalar STRING).
  **Domains do NOT match directly:** the log deal IDs carry an **exchange prefix**
  (e.g. `stv/NBC-MNT-00004`, `pm/PM-PSER-6773`) while `partner_deal_id` is unprefixed
  (`NBC-MNT-00020`). On a 2026-07-18 `win_logs` sample a direct `deal_id = partner_deal_id`
  join matched **0 of 172** distinct deals (170 were prefixed); stripping the prefix
  (`REGEXP_REPLACE(deal_id, r'^[a-z]+/', '')`) matched 24. **Always strip `^[a-z]+/`
  before joining.** **1:N** — one deal fans out to millions of bid/impression events, so
  use this 79-row table as a lookup, or aggregate events to deal grain *before* joining.
  Only these 79 deals are covered, so most events will not match.
- **Sibling (not a BQ join): `core.private_marketplace_deal_impression_rates_log`**
  (silver view over `bronze.integrationprod.core_private_marketplace_deal_impression_rates_log`)
  — the historical **log** this snapshot derives from (the deliverability-forecast source).
  Verified columns: `partner_deal_id`, `log_time`, `days_with_data`, `win_rate`,
  `adj_avg_daily_impression_rate`, `distinct_ips`, `avg_daily_impression_rate`,
  `yesterdays_inventory` (+ row id `private_marketplace_deal_impression_rate_id`,
  `datastream_metadata`). The log is a **superset**: this aggregates snapshot drops
  `win_rate`, `adj_avg_daily_impression_rate`, `log_time`, and the row id and keeps only
  the latest state per deal. `distinct_ips`/`yesterdays_inventory` are **not** unique to
  the BQ version — they exist in the log too.

## Gotchas
- **Snapshot, no history.** There is **no date/partition column** — the table is a
  current-state overwrite. Do not expect a time series or trend; each daily rebuild
  replaces the rows.
- **Tiny lookup table.** 79 rows / ~4 KB. It is a dimension, not a fact table.
- **Coverage is partial.** Only 79 PMP deals appear — not every active PMP deal is
  present. Absent deal ≠ zero inventory.
- **`days_with_data` skews the rate.** Rows with `days_with_data = 2` show the largest
  `avg_daily_impression_rate` values (thin denominator). Filter `days_with_data >= 7`
  (or a chosen threshold) when you need a stable rate.
- **Subset of the log, not column-parity.** This snapshot **drops** `win_rate`,
  `adj_avg_daily_impression_rate`, `log_time`, and the row id from the
  `..._deal_impression_rates_log` source; it does **not** add columns
  (`distinct_ips` / `yesterdays_inventory` exist in the log too). See Joins.
- **Physical is a plain TABLE.** The `silver` view is a thin `SELECT *` over the SQLMesh
  physical `aggregates__pmp_impression_rates__218890280`, which is unpartitioned,
  unclustered, no TTL.

## Cost & partitioning notes
- **No partition column exists**, so there is nothing to filter and no partition-pruning
  to do — this is the rare table where `SELECT *` is fine. The whole table is ~4 KB.
- Dry-run figures (labeled by column set):

## Example queries
```sql
-- Deals ranked by prior-day inventory, joined to deal name/config
SELECT r.partner_deal_id, d.name, r.avg_daily_impression_rate,
       r.days_with_data, r.distinct_ips, r.yesterdays_inventory
FROM `aggregates.pmp_impression_rates` r
LEFT JOIN `core.private_marketplace_deals` d USING (partner_deal_id)
WHERE r.days_with_data >= 7          -- stable rates only
ORDER BY r.yesterdays_inventory DESC;
```
