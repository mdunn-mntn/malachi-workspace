# aggregates.win_rate_bq_bids_by_term_hour

## Purpose
The **denominator half of an hourly, term-level win-rate pair.** Records the count of `bids`
for every campaign x targeting-term x hour x day. It is meant to be joined 1:1 to its sibling
`aggregates.win_rate_bq_impressions_by_term_hour` (the numerator = impressions won) so that
`win_rate = impressions / bids` can be computed at the (date, hh, campaign_id, term_id) grain.

Reach for it to analyze **bid volume and win rate by targeting term at hourly resolution** —
e.g. which BUK / behavior-keyword / audience-segment terms a campaign bids into by hour and how
often those bids convert to won impressions. Note the `bq` prefix's exact meaning (bidder / Beeswax /
BigQuery bid pipeline) is **not verified** — treat it as opaque, not a claim.

## Grain & keys
- **Grain:** exactly one row per **(date, hh, campaign_id, term_id)**. Verified: on 2026-07-18,
  `COUNT(*) == COUNT(DISTINCT key)` = 308,406 (term_id NULL folded to a sentinel in the check).
- **Key(s) / join columns:** the 4-tuple above. `term_id` is **nullable**, so any join on it must
  use a NULL-safe sentinel (e.g. `IFNULL(term_id,'~')`).
- `(campaign_id, term_id)` is effectively a campaign-scoped targeting term — verified 0 term_id
  values span more than one campaign on a sample day.

## Column meanings (only the non-obvious ones)
- **date** — partition column; the day the bids occurred. Rolling ~45-day retention (see Cost). Timezone not verified — assume UTC until confirmed.
- **hh** — hour of day, integer **0–23** (verified min 0 / max 23). Cluster field #1. Pairs with `date` to give the hourly bucket.
- **campaign_id** — bidder campaign identifier (observed values ~300K–650K). Cluster field #2. Joins to the `campaigns` dim for funnel_level / name / advertiser (dim join unverified but is the standard campaign id family).
- **term_id** — bidder **targeting-term identifier**, a *numeric-valued STRING* (e.g. `"215410"`, `"40730"`). Same identifier family as `terms_log_agg_min.term_id / picked_term_id`. Cluster field #3. Two NULL facts, both verified:
  - **Campaign-scoped:** a given term_id belongs to exactly one campaign (0 terms spanned >1 campaign on a sample day).
  - **NULL = a separate "no-term / unattributed" bucket, NOT a rollup total.** ~71% of daily rows have NULL term_id (220,339 / 308,406 on 2026-07-18). Verified: the NULL-bucket bids do **not** equal the sum of the campaign's non-NULL term bids (they diverge in both directions), so NULL is bids not attributed to any specific targeting term — its own bucket, not a subtotal.
- **bids** — count of bids for that campaign x term x hour. This is the **denominator** of the win-rate ratio; the sibling table's `impressions` is the numerator (wins). Exact bid semantics (bid submissions/responses vs. requests) not fully pinned; sampled win rates (impressions/bids) fall ~0.04–0.53, consistent with bids = bid responses submitted and impressions = auctions won.

## Joins & relationships
- **→ `aggregates.win_rate_bq_impressions_by_term_hour`** (identical shape, `impressions` in place of `bids`): join on all four keys `(date, hh, campaign_id, term_id)` with a NULL-safe term_id, then `win_rate = SAFE_DIVIDE(impressions, bids)`. 1:1 per key. **Use a LEFT JOIN bids→impressions** and `COALESCE(impressions,0)` — a bids row with no matching impressions row means 0 wins that hour (win rate 0), which is common.
- **campaign_id → `campaigns`** (many rows : 1 campaign) for funnel_level, name, advertiser.
- **term_id → targeting-term / `audience_segments` / `terms_log_agg_min`** term domain — same numeric term identifier family.
- **Fan-out:** none *within* the table (grain is unique per key). Joining out to `campaigns` is many-to-one and safe; only the impressions join must guard the nullable term_id.

## Gotchas
- **NULL term_id dominates (~71% of rows) and is its own bucket, not a rollup.** For term-level analysis filter `term_id IS NOT NULL`. A naive `SUM(bids) GROUP BY campaign_id` mixes the no-term bucket with the term buckets — for a true campaign total include NULL rows; for term totals exclude them. Do NOT treat the NULL row as "sum of terms."
- **term_id is STRING** though it looks numeric — compare/cast as string, and the impressions join needs a NULL-safe sentinel (nullable key).
- **This is the bids/denominator ONLY.** A win rate requires the impressions sibling; a bids row with no impression match = 0 wins → LEFT JOIN + COALESCE.
- **Rolling ~45-day retention** (partition expiration). Verified span on 2026-07-19: 2026-06-05 → 2026-07-19 = 45 partitions. Not usable for long-lookback trend work.
- **View is a passthrough** `SELECT *` over the physical table — querying the view == querying the table (no extra cost/logic). The impressions sibling has stray `__dev` physical variants; ignore them, query the silver view name.

## Cost & partitioning notes
- Partition `date` (DAY), **require_partition_filter is NOT enforced** — but always filter `date` anyway. Cluster `[hh, campaign_id, term_id]`, so filtering campaign_id / term_id after date prunes well.
- Whole table ≈ **13.4M rows / ~456 MB** across 45 daily partitions.
- **One-day slices are cheap:** a single-day aggregate scanned ~0.01 GB (~308K rows). Filtering to specific campaigns/terms stays in the low-MB range.
- **Avoid full scans:** a query that first computes `MAX(date)` scans all 45 partitions (~0.42 GB billed). Hardcode the date literal instead of deriving it in the same query.

## Example queries
```sql
-- Win rate by targeting term for a campaign-day, hourly
SELECT b.hh, b.term_id, b.bids, COALESCE(i.impressions,0) AS impressions,
       SAFE_DIVIDE(i.impressions, b.bids) AS win_rate
FROM `aggregates.win_rate_bq_bids_by_term_hour` b
LEFT JOIN `aggregates.win_rate_bq_impressions_by_term_hour` i
  ON b.date=i.date AND b.hh=i.hh AND b.campaign_id=i.campaign_id
 AND IFNULL(b.term_id,'~') = IFNULL(i.term_id,'~')
WHERE b.date = '2026-07-18' AND b.campaign_id = 629615
  AND b.term_id IS NOT NULL            -- drop the no-term bucket for term-level analysis
ORDER BY b.bids DESC;
```
