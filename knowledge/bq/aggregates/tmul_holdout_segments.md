# aggregates.tmul_holdout_segments

## Purpose
Flattened, DATE-partitioned **per-IP holdout (control-group) roster**, derived from the TPA
membership update log (`tmul` = **t**pa **m**embership **u**pdate **l**og). For every
advertiser x campaign x audience-segment, it enumerates the IPs that fall in that segment's
**holdout** group on each date, tagged `"holdout"`. This is the row-level control-group population
that MNTN holds back from bidding for **incrementality / holdout measurement** (the 10% holdout —
`MD5('{AID}:{IP}') mod 1000`, 0-99). Reach for it when you need the exact set of held-out IPs for an
advertiser/campaign on a given day (e.g. to confirm a holdout IP was never served, or to build an
ITT control cohort). It is a very large, expensive table — see Cost.

## Grain & keys
- **Grain:** one row per **(date, ip, advertiser_id, campaign_id, segment_id)** — a single
  holdout-group membership. Verified on WGU (advertiser 31357) / 2026-07-10:
  `COUNT(*) = COUNT(DISTINCT ip|campaign_id|segment_id) = 39,589,633` (no duplicates).
- **Key(s) / join columns:** `ip` (to impression/visit tables), `advertiser_id`, `campaign_id`,
  `segment_id`. `date` is the partition column and part of the grain.
- **Volume:** ~2.56B rows per day (2026-07-10 full-partition count); WGU alone that day = 39.6M rows
  across 11.5M distinct IPs and 112 campaigns (= 112 segments, 1:1).

## Column meanings (only the non-obvious ones)
- **`ip`** — dotted-quad IPv4 string (e.g. `"23.244.168.114"`), NOT an INET type. The held-out
  household IP. Join carefully to `ui_visits`/`cost_impression_log`, which carry `ip` vs `ip_raw`.
- **`date`** — native `DATE` (no epoch decoding needed). Partition key; the day this holdout
  membership was recorded. Front-matter `time_unit: none` (house convention for a DATE-partitioned
  table with no epoch column — same as `agg__daily_sum_by_campaign` / `pmp_impression_rates`; it is
  not a granularity).
- **`segment_id`** — the TPA/audience segment id whose holdout this IP belongs to. In practice one
  active segment per campaign (n_segments == n_campaigns == 112 for WGU/2026-07-10, paired 1:1).
- **`data_source_id`** — **uniformly 3** across the entire 2026-07-10 partition (2.56B rows, 1505
  advertisers; MIN=MAX=3). Not a useful discriminator in this view — only DS3 appears in this holdout
  roster. DS3 **is** decodable: it resolves to **"MNTN Third Party"** in the `audience.data_sources`
  registry (the silver view over `bronze.integrationprod.audience_data_sources`; 86,687 rows,
  `data_source_id` runs from -1 up, e.g. DS2="MNTN First Party", DS3="MNTN Third Party", DS4="CRM").
- **`score`** — INT64, **NULL for ~99% of rows** (2.53B of 2.56B on 2026-07-10). The only non-NULL
  value observed is **`10000`** (28.4M rows / 1,395 advertisers that day) — the household-score / RTC
  max-score sentinel (same 10000 seen in `household_score` / `realtime_conquest_score`). Likely flags
  held-out IPs that met the household-score bidding threshold (a "would-have-qualified" control), but
  that reading is inferred, not verified. **Do NOT treat `score IS NULL` as "not held out"** — the
  row's presence + `tags` already establish holdout membership; NULL just means no score sentinel.
- **`tags`** — `ARRAY<STRING>`, but **effectively the constant `["holdout"]`** — the only value
  present across the full 2026-07-10 partition. Must `UNNEST(tags)` to filter on it.

## Joins & relationships
- **`advertiser_id` -> `bronze.integrationprod.advertisers.advertiser_id`** — dim, advertiser side
  1:1; this table is the N side (many holdout rows per advertiser). Filter `deleted=FALSE AND
  is_test=FALSE` on the dim. Join for company_name.
- **`campaign_id` -> `bronze.integrationprod.campaigns.campaign_id`** — dim, campaign side 1:1; this
  table is the N side. Use `campaigns.funnel_level` (authoritative for stage), not `objective_id`.
- **`(campaign_id, segment_id)` -> `silver.audience.audience_segments (campaign_id, segment_id)`** —
  live-verified: all 112 holdout (campaign_id, segment_id) pairs for WGU/2026-07-10 match
  `audience_segments` **1:1** (no fan-out), every matched row `is_targeted = TRUE`. Join on the pair
  (segment_id alone is not unique across campaigns); `audience_segments` carries the segment's
  targeting `expression` JSON. One active segment per campaign here (112 pairs = 112 campaigns).
- **`ip` -> `cost_impression_log.ip` / `ui_visits.ip`** — plain string equality; `ip` here is already
  a dotted-quad IPv4 STRING, so **no transform** (do NOT wrap in `host(ip)` — that is Greenplum/INET
  syntax and errors in BigQuery). The key join for incrementality work (compare/exclude held-out IPs
  vs served impressions/visits). **Heavy fan-out**
  on both sides (an IP appears on many days/campaigns here and many impressions there); always bound
  by `date` + `advertiser_id` first, and mind the `ip` vs `ip_raw` distinction on the partner tables.

## Gotchas
- **Enormous + no forced partition filter.** `require_partition_filter` is NOT set, so an accidental
  unfiltered `SELECT *` scans the whole **42.9 TiB**. Always filter `date`, and add `advertiser_id`
  (cluster key) — one advertiser-day is ~2.4 GiB vs 152.6 GiB for a full-day `SELECT *`.
- **`tags` is a constant `["holdout"]`** (as of 2026-07-10) — don't build logic expecting other tag
  values. `UNNEST(tags)` does **not** inflate bytes scanned/billed — bytes are fixed by the columns
  read from the pruned partition (before UNNEST); UNNEST only multiplies rows in compute/shuffle.
  Verified: a full-day tag/ds/score group-by (with `UNNEST(tags)`) and the plain 3-column read both
  dry-run at the **identical** `64,152,004,305 B` (64.15 GB / 59.75 GiB).
- **`data_source_id` is always 3** here — filtering on it prunes nothing.
- **`score` is NULL for ~99% of rows** — see Column meanings; NULL != "not held out."
- **Distinct from the raw tmul tables.** This is NOT `bronze.raw.tpa_membership_update_log` (raw
  change-log: `dt`+`hh` STRING partitions, DS2+DS3, `in_segments`/`out_segments` RECORDs) nor
  `bronze.raw.tmul_daily` (14-day-TTL daily snapshot, `.list`/`.element` unnest). This `aggregates`
  view is a flattened, per-IP, DATE-partitioned holdout roster with **no TTL** and much longer
  history.
- **No TTL / partition expiration.** Data runs daily from **2025-09-23** (physical creation) through
  present (2026-07-18 confirmed), and keeps growing — hence 736B rows / 47 TB.
- **Cross-project physical.** The physical resolves through a link to `mntn-coredw-prod`:
  `INFORMATION_SCHEMA.VIEWS`/`.PARTITIONS` on the sqlmesh dataset error with a coredw-prod
  permission denial, but `bq show` and normal queries through the silver view work fine.

## Cost & partitioning notes
- **Partition `date` (DAY); cluster `date, advertiser_id, campaign_id`.** The one filter to always
  apply: `WHERE date = '<day>'` **plus** `AND advertiser_id = <AID>` whenever possible.
- Dry-run upper bounds, **one day (2026-07-10), labeled by exact column set**:
  - `SELECT *` (all 8 cols): **152.59 GiB** (163,840,958,394 B)
  - narrow (advertiser_id, campaign_id, segment_id, data_source_id, score, tags): **116.90 GiB**
  - `ip` only: **54.74 GiB** · `tags` only: **40.48 GiB** · `data_source_id` only: **38.10 GiB**
    (even a single column over one day is 38+ GiB — every full-day scan is expensive)
  - `SELECT *` one day **+ `advertiser_id = 31357`**: **2.36 GiB** (2,538,876,658 B) — 64x cluster prune
  - **no `date` filter**, `SELECT *`: **42.89 TiB** (47,162,511,139,880 B) — the full table
  - full-day tag/ds/score group-by (`UNNEST(tags)`): **59.75 GiB** (64,152,004,305 B) — same bytes
    as the plain 3-col read; UNNEST adds no scan cost
- Actual billed (real run): 7-col advertiser-day profile = **2.03 GB** — consistent (below the
  2.36 GiB `SELECT *` advertiser-day dry-run upper bound, since dry-run bounds on-demand bytes billed).
- `approx_logical_bytes` = physical `numBytes` = 47,162,511,139,880 B (42.9 TiB backing storage).

## Example queries
```sql
-- Held-out IPs for one advertiser/campaign on one day (cluster-pruned, ~2 GiB)
SELECT ip, campaign_id, segment_id, score
FROM `aggregates.tmul_holdout_segments`
WHERE date = DATE '2026-07-10'
  AND advertiser_id = 31357
  AND campaign_id = 457628;

-- Holdout roster size per campaign for an advertiser-day
SELECT campaign_id, segment_id, COUNT(DISTINCT ip) AS holdout_ips,
       COUNTIF(score = 10000) AS scored_ips
FROM `aggregates.tmul_holdout_segments`
WHERE date = DATE '2026-07-10' AND advertiser_id = 31357
GROUP BY campaign_id, segment_id;
```
