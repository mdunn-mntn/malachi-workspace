# aggregates.campaign_group_log_agg_min

## Purpose
Minute-by-minute pacing and bid-volume summary of the bidder, rolled up to the **campaign-group /
flight** level. Reach for it to answer "how was this campaign group pacing at 3:04pm?" — how many bid
requests it saw, how many it actually bid on vs. dropped (204), and how its cumulative flight-to-date
and day-to-date spend and impressions sat against their caps. It is the campaign-group sibling of the
finer `campaign_log_agg_min` (adds campaign_id) and `terms_log_agg_min` (per targeting term). Because
it is pre-aggregated to the minute, it is far cheaper than reconstructing pacing from raw
`bidder_bid_events`, and it is the go-to source for pacing/throttling diagnostics and spend-cap audits.

## Grain & keys
- **Grain:** one row per **(advertiser_id, campaign_group_id, flight_id, bid_time-minute)**. `bid_time`
  is a TIMESTAMP truncated to the minute (seconds always `00`, verified on a full day sample).
- **Key(s) / join columns:** `advertiser_id`, `campaign_group_id`, `flight_id` are the entity keys;
  `bid_time` is the time bucket and the partition column. A flight is a budget window of a campaign
  group, so `(campaign_group_id, flight_id)` together identify the delivery period.

## Column meanings (only the non-obvious ones)
- **`bid_time`** — TIMESTAMP truncated to the **minute** (the "agg_min" grain) and the DAY partition key.
  Not an epoch integer; `time_unit: timestamp`.
- **`total_bid_requests`** — bid requests seen for this campaign group in the minute. Empirically an exact
  identity holds: **`total_bid_requests = total_bids + total_204_bids`** (e.g. 44 + 1,837,918 = 1,837,962),
  so it is the denominator for bid-rate / no-bid-rate.
- **`total_bids`** — requests answered with an actual bid (HTTP 200). This is the column the prose oracle
  called `total_200_bids`; the live schema renamed it to `total_bids` (see Changelog drift note). Typically
  a tiny fraction of requests (targeting/pacing filters most out).
- **`total_204_bids`** — requests answered with **no bid** (HTTP 204 No Content) — dropped/skipped. Usually
  the bulk of `total_bid_requests`; a high 204 share is the throttling/eligibility signal.
- **`bid_price_per_hour`** — INT64 **per-minute, volume-proportional** figure — NOT a near-constant rate.
  Within a single flight it swings ~5 orders of magnitude tracking bid-request volume (verified cg 67765 /
  flight 1031143 on 2026-07-17: 1,347 distinct values over its 1,347 minutes, min 206,684 → max 15.97e9),
  while the per-request ratio `bid_price_per_hour / total_bid_requests` stays near-constant (~8,000) minute
  to minute — so it reads as an aggregate per-minute bid-price total (≈ per-request price × requests-this-
  minute), not the bidder's configured rate. Population is right-skewed: p50 ≈ 2.1e6, p95 ≈ 3.8e8,
  max ≈ 1.6e10, and only 35 of 4.2M rows reach 15–16e9 (the peak-volume minutes, not a typical value).
  Despite the `_per_hour` name it is a per-minute quantity.
- **`max_flight_campaign_group_spend` / `max_daily_campaign_group_spend`** — FLOAT64 **running cumulative**
  spend flight-to-date / day-to-date, snapshotted as the MAX seen within the minute (near-monotonic within
  the period — see Gotchas). Scaled integer/micro-currency: value / 1e6 ≈ USD (inferred from internal consistency — a daily
  cap of 8.98e7 → ~$89.81/day × ~29 flight days ≈ 2.58e9 flight cap ≈ the flight cap value).
- **`max_flight_campaign_group_spend_cap` / `max_daily_campaign_group_spend_cap`** — the flight / daily
  spend cap, **same scale** as the spend columns, so **spend / cap is the unit-free pacing %** (the ratio is
  what matters — you never need to resolve the absolute scale to compute pacing). Caps can drift minute to
  minute as pacing is re-tuned.
- **`max_flight_campaign_group_impression` / `max_daily_campaign_group_impression`** — FLOAT64 **running
  cumulative** impressions flight-to-date / day-to-date, MAX-within-minute, **near-monotonic** (~99.997% of
  minute-to-minute transitions non-decreasing; ~126 rare decreases per ~4.0M transitions on 2026-07-17).
  Plain impression **counts**, not scaled.
- **`max_flight_campaign_group_impression_cap` / `max_daily_campaign_group_impression_cap`** — impression
  caps; **`0.0` = uncapped** (common — many groups pace on spend only, so the impression cap is 0).

## Joins & relationships
All entity keys join to `bronze.integrationprod` dimension tables (query the `silver.core` thin views or the
bronze dims). In every case this table is the **N** side (many minute rows per entity) and the dim is the
**1** side, so joining to a properly-deduped dim does **not** fan out; filter dims with
`deleted = FALSE AND is_test = FALSE`.
- **`advertiser_id` → `advertisers`** (dim, unique per id → 1:N). Use `advertisers.company_name` for names.
- **`campaign_group_id` → `campaign_groups`** (dim, 1:N). `campaign_groups.product_id` = 1 PTV / 2 Select /
  3 QuickFrame. A campaign group has many flights and many minute rows.
- **`flight_id` → flight dim** (1:N) — the budget window; `(campaign_group_id, flight_id)` scopes a delivery
  period. Live-unverifiable here (dim not confirmed this pass) — treat as the safe fan-out-warning direction.
- **Sibling agg views (same minute grain):** `campaign_log_agg_min` (one grain finer — adds `campaign_id`)
  and `terms_log_agg_min` (per targeting term — adds term/dimension keys). These are **alternate grains, not
  join partners** — do not blindly join across them (row multiplicity differs) unless you first roll them to
  a common grain.
- **Not a minute-grain sibling:** `campaign_group_log_aggregation_mntn_bidder` belongs to the coarser
  `*_log_aggregation` family (per data_catalog.md: "same as `campaign_group_log_aggregation`", filtered to
  the MNTN bidder not Beeswax) — it lacks the `_agg_min` infix and is **not** the minute-grain analog of this
  table. The minute-grain MNTN-bidder variants carry the `_agg_min` infix (cf. `campaign_log_agg_min_mntn_bidder`).

## Gotchas
- **Prose→schema rename:** the catalog listed `total_200_bids`; the live column is **`total_bids`**. Same
  meaning (HTTP-200 bids), different name — reconciled below.
- **`max_*` = cumulative snapshot, not a per-minute delta.** Spend and impression columns are running
  flight-/day-to-date totals; to get a per-minute increment, diff consecutive minute rows within the same
  `(advertiser_id, campaign_group_id, flight_id)` — never sum them. The series is **near-monotonic, not
  strictly**: ~126–127 small decreases per ~4.0M transitions/day (flight spend, daily spend, flight
  impressions all show them on 2026-07-17), so a diff can occasionally go slightly negative — clamp at 0 if
  you need non-negative increments.
- **`bid_price_per_hour` is per-minute and volume-proportional, NOT a near-constant rate** — it swings ~5
  orders of magnitude across a flight tracking `total_bid_requests` (ratio ≈ 8,000/request stays roughly
  constant); the `~15–16e9` values are only the peak-volume minutes (35 of 4.2M rows), not typical
  (p50 ≈ 2.1e6). Do not filter on it as if `~15e9` were a normal value.
- **Impression `_cap = 0.0` means uncapped**, not "zero impressions allowed."
- **Scaled money:** spend/cap are micro-currency (÷1e6 ≈ USD, inferred). Prefer the spend/cap **ratio** for
  pacing rather than resolving absolutes.
- **No partition-filter enforcement:** `require_partition_filter = false`, so an accidental unfiltered query
  scans the whole ~53.9 GB table — always add a `bid_time` range yourself.
- **Partition timezone:** DAY partitioning is on the `bid_time` TIMESTAMP (UTC); day boundaries are UTC.

## Cost & partitioning notes
- **The one filter to always apply:** a `bid_time` range. Partition = `bid_time` (DAY); clustered by
  `bid_time, advertiser_id, campaign_group_id` (add advertiser/campaign-group predicates to prune further).
  `require_partition_filter` is **false**, so nothing stops a full scan — you must add the filter.
- Physical backing: `sqlmesh__aggregates.aggregates__campaign_group_log_agg_min__1828378980` — a real
  partitioned **TABLE** (~429.96M rows, numBytes 53,858,734,912). The clean name is a VIEW `SELECT *` over it.
- Dry-run figures (2026-07-19, labeled by column set — only compare like-for-like):
  - `SELECT *`, **one day** (2026-07-17): **525,026,608 B (~0.53 GB)**.
  - `SELECT *`, **no partition filter (all-time)**: **53,858,734,912 B (~53.86 GB)** — equals full storage;
    the day filter is **~102x** cheaper.
  - `SELECT bid_time` (one narrow col), one day: **33,671,936 B (~0.034 GB)** — **~15.6x** cheaper than
    `SELECT *` on the same day. Project only the columns you need; avoid `SELECT *`.

## Example queries
```sql
-- Pacing snapshot: bid rate + spend-cap utilization for one campaign group over a window
SELECT bid_time, campaign_group_id, flight_id,
       total_bids, total_204_bids, total_bid_requests,
       SAFE_DIVIDE(total_bids, total_bid_requests)                                  AS bid_rate,
       SAFE_DIVIDE(max_daily_campaign_group_spend,  max_daily_campaign_group_spend_cap)  AS daily_spend_pct,
       SAFE_DIVIDE(max_flight_campaign_group_spend, max_flight_campaign_group_spend_cap) AS flight_spend_pct
FROM `aggregates.campaign_group_log_agg_min`
WHERE bid_time >= TIMESTAMP('2026-07-17') AND bid_time < TIMESTAMP('2026-07-18')
  AND campaign_group_id = 67765
ORDER BY bid_time;
```
