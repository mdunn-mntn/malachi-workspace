# aggregates.campaign_log_agg_min

## Purpose
Minute-level bidder pacing summary at the **campaign** level. One row per campaign **per flight** per minute records
how many bid requests the campaign saw, how many turned into bids vs no-bids (204s), the summed bid price, and the running
spend / impression accumulators against their daily and flight caps. Reach for it to diagnose *why* a campaign is
under- or over-delivering — throttling, cap exhaustion, request starvation — without scanning raw bid logs. It is
the campaign-grain sibling of `campaign_group_log_agg_min` (group/flight grain) and a summarized rollup of the
per-decision detail in `campaign_group_log_aggregation` (which carries `terms` JSON + `threshold_failure_reasons`).

## Grain & keys
- **Grain:** one row per **campaign_id × flight_id × bid_time-minute**. A campaign can run under **two concurrent
  flights** in the same minute, so `campaign_id` + `bid_time` alone is **NOT** unique. Verified 2026-07-17:
  n_rows = 8,739,523; DISTINCT(`campaign_id`,`bid_time`) = 8,738,917 → **606 collisions/day (606 extra rows)**, all of
  which are one campaign under two `flight_id`s in the same minute (606 keys multi-flight, 0 multi-group, 0 multi-adv,
  max 2 rows/key). DISTINCT(`advertiser_id`|`flight_id`|`campaign_group_id`|`campaign_id`|`bid_time`) = 8,739,523 = n_rows.
- **Key(s):** the **minimal unique key is `campaign_id` + `flight_id` + `bid_time`** (adding `flight_id` resolves all 606
  collisions). `advertiser_id` and `campaign_group_id` are (redundant) parent dims — no dupe pair ever spans multiple
  of them, so the full 5-tuple is also unique but `flight_id` is the only discriminator needed beyond campaign+minute.
- **Bidder scope:** the queryable is a single-object VIEW over one physical TABLE and has **no bidder-identifier column**,
  so a Beeswax-vs-MNTN split cannot be confirmed from this table. The catalog header names a `campaign_log_agg_min_mntn_bidder`
  sibling (the `_mntn_bidder` convention elsewhere = MNTN-only, not Beeswax), but that table is **NOT materialized in live
  BQ** — `bq show aggregates.campaign_log_agg_min_mntn_bidder` → *Not found*; `bq ls aggregates` lists only the base VIEW.

## Column meanings (only the non-obvious ones)
- **bid_time** — TIMESTAMP truncated to the **minute** (seconds always 00; a day spans 00:00:00 → 23:59:00). UTC.
  This is the **partition column** (DAY granularity) and the lead cluster key.
- **total_bid_requests** — count of bid requests (auction opportunities) the campaign was eligible for in the minute.
  Verified identity on sample: `total_bid_requests = total_bids + total_204_bids` (exact, every sampled row).
- **total_bids** — count of responses that carried an actual bid (the bid-response leg of the request/204 partition;
  the "HTTP-200" framing is an inference — the complement of the explicit 204 no-bid counter, not a labeled column).
  **Right-skewed, not "tiny"**: 2026-07-17 median = 4, mean = 337.7, p90 ≈ 73, p99 ≈ 1,180, max = 809,867; 98,332
  rows/day exceed 1,000. The mean per-row bid fraction `total_bids / total_bid_requests` ≈ **0.36**, i.e. on the
  average row the bidder bids on ~36% of requests (do **not** read this as ~0.005% — that only holds on the very
  highest-volume/most-throttled minutes). 2,361,109 rows/day (~27%) have total_bids = 0.
- **total_204_bids** — count of **no-bid** responses (HTTP 204 = no content): eligible but the bidder chose not to
  bid. It is the complement `total_bid_requests − total_bids`, so it equals `total_bid_requests` **exactly only on the
  ~27% of rows where total_bids = 0**; on the average row 204s are ~64% of requests (mean bid fraction ≈ 0.36).
  NOTE: prose/data_catalog historically called the bid counter `total_200_bids`; the live column is `total_bids` —
  the "204" here is the *no-bid* count, not a typo for it.
- **bid_price_per_min** — INT64, per-minute **sum of computed bid prices in micros** (÷1e6 ≈ currency). It scales
  with request volume and is right-skewed (2026-07-17: p50 ≈ 4.68e5, p99 ≈ 1.59e9, max ≈ 1.59e10 — the ~1e10 values
  only appear on the highest-volume minutes). It aggregates the price across bid *opportunities*, not just placed
  bids. Sibling group table names its analogue `bid_price_per_hour`.
- **max_flight_campaign_spend / max_flight_campaign_spend_cap** — the flight-to-date **cumulative** spend
  accumulator (max = latest value seen in the minute) vs the flight budget cap. Micro-currency (÷1e6 ≈ dollars).
  Magnitudes span **~1e6 to ~1e12** across rows, not a narrow band: 2026-07-17 flight spend p50 ≈ 1.19e8,
  p99 ≈ 1.60e10, max ≈ 7.58e11; flight cap max ≈ 8.27e11 (daily counterparts run smaller — see below).
- **max_daily_campaign_spend / max_daily_campaign_spend_cap** — same, but the **daily** spend accumulator vs the
  daily budget cap (micros). 2026-07-17: daily spend p50 ≈ 3.72e6, p99 ≈ 4.36e8, max ≈ 8.58e9; daily cap p50 ≈ 1.01e7,
  max ≈ 9.59e9. Confirmed monotonically increasing across consecutive minutes within a day → it is a running
  cumulative counter, **not** a per-minute delta.
- **max_flight_campaign_impression / _cap, max_daily_campaign_impression / _cap** — cumulative delivered-impression
  accumulators vs impression caps (FLOAT64). The `*_impression_cap` columns are **commonly 0.0**, meaning *no
  impression cap configured* (the campaign paces on spend) — do not read 0.0 as "cap hit."

## Joins & relationships
- **→ `campaigns` / `silver.core` campaign dim** on `campaign_id` — dim is the **1** side, this table is the **N**
  side (many minute-rows per campaign). Joining dim→this **fans out** to every minute. Use `funnel_level` (on
  `campaigns`) for stage, not `objective_id`; `campaigns.name` for the label.
- **→ `campaign_groups`** on `campaign_group_id` (1:N same direction) — `product_id` 1=PTV / 2=Select / 3=QuickFrame.
- **→ `advertisers`** on `advertiser_id` (join `company_name`; `fpa_advertiser_verticals.advertiser_name` is unreliable).
- **→ flights** on `flight_id`.
- **Sibling `campaign_group_log_agg_min`** — same minute grain one level up (no `campaign_id`); this table rolls up
  to it by summing volumes across the campaigns within a `campaign_group`. Note the group table's price column is
  `bid_price_per_hour`, not `bid_price_per_min`, despite both being minute-grain.
- **Source detail `campaign_group_log_aggregation`** — the un-aggregated per-decision minute view (carries `terms`
  JSON, `threshold_failure_reasons`, `picked_term_id`); use it when you need *why* a bid was dropped, not just counts.
- **`*_mntn_bidder` variants** — the catalog documents a `_mntn_bidder` naming convention elsewhere (MNTN-bidder-only
  subset, excludes Beeswax; e.g. `campaign_group_log_aggregation_mntn_bidder`, `terms_log_agg_min_mntn_bidder`), but the
  specific `campaign_log_agg_min_mntn_bidder` is **not materialized** in live BQ (bq show → Not found).

## Gotchas
- **`campaign_id` + `bid_time` is NOT a unique key** — add `flight_id`. ~606 campaigns/day run two concurrent flights,
  so filtering one `campaign_id` and `ORDER BY bid_time` silently returns 2 rows/minute for those campaigns (doubling
  pace/spend/volume), and any 1:1 dedup or join on (`campaign_id`,`bid_time`) fans out. Use (`campaign_id`,`flight_id`,`bid_time`).
- **Accumulators, not deltas.** All `max_*_spend` / `max_*_impression` columns are running cumulative counters
  (verified monotonic within the day). To get spend/impressions *in* a minute, diff consecutive minutes — do not
  sum the raw columns.
- **Impression caps are usually 0.0** = no impression cap set; pacing is spend-based (`max_daily_campaign_impression_cap`
  = 0.0 on ~87% of rows, verified 2026-07-17). Filter/interpret accordingly.
- **`total_bids` vs prose `total_200_bids`.** Live column is `total_bids`; older catalog prose said `total_200_bids`.
- **No `_mntn_bidder` sibling and no bidder column.** The catalog header names `campaign_log_agg_min_mntn_bidder`, but it
  is not materialized (bq show → Not found; only the base VIEW exists) and the base table has no bidder-identifier column,
  so a Beeswax-vs-MNTN split cannot be sliced from this table.
- **bid_time is minute-truncated** (no sub-minute detail) and the partition is **DAY** — a `bid_time` filter is
  required for cost control but is **not enforced** (require_partition_filter = false), so it is easy to full-scan.
- **No soft-delete / no TTL** on the physical table; it is a full-history SQLMesh rebuild (~864M rows, back-filled).

## Cost & partitioning notes
- **Always filter `bid_time`** (partition, DAY granularity). It is **not** enforced (require_partition_filter = false),
  so an unfiltered query silently full-scans. Cluster keys `bid_time, advertiser_id, campaign_group_id` further prune
  advertiser/group-scoped slices.
- Dry-run figures (2026-07-19), labeled by column set:
  - `SELECT bid_time` **no filter** → **6.91 GB** (full scan of one column).
  - `SELECT bid_time` **one day** (`bid_time` in [2026-07-17, 2026-07-18)) → **0.070 GB** (~99% pruned — this is the
    empirical proof `bid_time` is the partition).
  - `SELECT *` **one day** → **1.13 GB** (all 16 columns; ~16x the single-column day).
- Backing physical storage: `numBytes` = **113.6 GB** (~113,610,070,760 B) across **~864M rows** (single physical
  table `aggregates__campaign_log_agg_min__3058104818`; no UNION).
- Avoid `SELECT *`; project only the volume/spend columns you need since the wide FLOAT64 accumulators dominate bytes.

## Example queries
```sql
-- Per-minute delivery pace for one campaign on one day (diff accumulators for in-minute spend).
-- Keep flight_id in SELECT/ORDER BY: ~606 campaigns/day run two concurrent flights, so a
-- campaign_id-only pull returns 2 rows/minute for them. 626171 is single-flight (masks this).
SELECT
  bid_time,
  flight_id,
  total_bid_requests,
  total_bids,
  total_204_bids,
  max_daily_campaign_spend / 1e6 AS daily_spend_cum_dollars,
  max_daily_campaign_spend_cap / 1e6 AS daily_cap_dollars
FROM `aggregates.campaign_log_agg_min`
WHERE bid_time >= TIMESTAMP('2026-07-17') AND bid_time < TIMESTAMP('2026-07-18')
  AND campaign_id = 626171
ORDER BY flight_id, bid_time
```
