# aggregates.agg__daily_sum_by_campaign

## Purpose
Pre-computed **daily campaign-level rollup** — the cheapest single table for campaign performance trend
analysis (impressions, spend, video-completion funnel, and multi-touch attribution, one row per campaign
per day). Reach for it when you want daily campaign totals over the **Sep 2025 – Apr 2026** window and do
NOT need sub-day granularity, geo/device dimensions, household reach counts, or recent data.

**Do NOT reach for it when:**
- You need history before 2025-09-01 or after 2026-04-30 → use `silver.summarydata.sum_by_campaign_by_day`
  (2024-01-01 → present, and its `uniques` HLL sketch actually works).
- You need current / trailing-30d data → this view is **frozen at 2026-04-30**; source the fact tables
  `silver.summarydata.{impression_facts, visit_facts, conversion_facts, spend_facts}` (hourly, stay fresh).
- You need household reach or unique-visitor counts → the entire reach/site-visitor family is **empty here**
  (see Column meanings + Gotchas).

## Grain & keys
- **Grain:** exactly one row per **(campaign_id, day)**. Verified April 2026: `COUNT(*)` = `COUNT(DISTINCT
  campaign_id||day)` = `COUNT(DISTINCT advertiser_id||campaign_id||day)` = 399,535. No duplicates.
- **Key(s):** `(campaign_id, day)`. `advertiser_id` is a redundant parent dimension (campaign_id →
  advertiser_id is deterministic); it does not refine the grain.
- **Partition key:** `day` (DATE, DAY-partitioned) — always filter on it.

## Column meanings (only the non-obvious ones)
All counts are integers; all `*_cost` / `*_spend` / `*_order_value` are NUMERIC dollars. MNTN convention:
`clicks`/`views` are **visit** counts (click-through vs view-through site visits), not ad-view counts —
`views` here is the headline view-through visit metric. `impressions` is the ad-serve count.

**EMPTY across ALL history (2025-09-01 → 2026-04-30) — the reach / site-visitor family is never populated
(0 positive rows verified over the full table):**
- `uniques` — HLL reach was never materialized in this table (0, always). *(Note: the same-named
  `uniques` in `summarydata.sum_by_campaign_by_day` IS a working HLL BYTES sketch — different table.)*
- `site_visitors`, `new_site_visitors`, `existing_site_visitors` — all 0.
- `new_users_reached`, `existing_users_reached` — all 0.
- `competing_site_visitors`, `competing_new_site_visitors`, `competing_existing_site_visitors` — all 0.
  *(But `competing_new_visitors` — a DISTINCT column — IS populated (~25%); see below. Do not confuse it
  with the empty `competing_new_site_visitors`.)*
- `view_untrackable` — 0 positive rows full-table (the viewability-untrackable count was never
  materialized here; do not derive a viewability-untrackable rate from this column).
- **Do not compute VVR, reach, or unique-visitor rates from this table.** Use these signals elsewhere.

**POPULATED / real (share of the 2.86M rows with a positive value):**
- Delivery / viewability: `impressions` (~88%), `view_impressions` (~88%), `view_viewed` (~88%, viewable
  impressions), `display_impressions` (17%), `video_impressions` (71%) — video/CTV is the dominant channel.
  (`view_untrackable` is the empty sibling — see the empty list above.)
- Spend: `media_spend` tracks `impressions` 1:1 (both positive on the same ~88% of rows). `media_cost`,
  `data_cost`/`data_spend`, `fee_cost`, `partner_cost`, `platform_spend`, `video_spend` are the cost vs
  spend lenses (cost = raw; spend = billed/marked-up — treat take-rate-derived splits as sensitive).
- Video funnel: `vast_start`/`vast_firstquartile`/`vast_midpoint`/`vast_thirdquartile`/`vast_complete`
  (~70% populated), `views` = completed view-through visits (50%).
- Visits/conversions: `clicks` (11%), `view_conversions` (26%), `click_conversions` (0.3%, sparse but
  real), with paired `*_order_value` NUMERIC revenue columns.
- Attribution families (all real): `last_touch_*` (last-touch, ~67%), `last_tv_touch_*` (TV last-touch,
  ~24%), `*_assist` (`visits_assist` ~10%, `conversions_assist_*`), and the `competing_*` attribution
  metrics — cross-advertiser competing credit: `competing_views`/`competing_last_touch_views` etc. (~51%),
  plus `competing_new_visitors` (~25%, MAX 86,065, SUM ~71.2M). `competing_new_visitors` is a REAL, distinct
  column — do NOT confuse it with the empty `competing_new_site_visitors`. Note
  `competing_last_tv_touch_view_conversions` is typed NUMERIC (not INT64) unlike its peers.

## Joins & relationships
- **`bronze.integrationprod.campaigns`** on `campaign_id` — partner grain 1 row per campaign (dim), so the
  join is **N:1** (many campaign-day rows → one campaign); no fan-out. Filter the dim
  `deleted=FALSE AND is_test=FALSE`. Use `campaigns.name` for the campaign label and `campaigns.funnel_level`
  for stage (objective_id is unreliable for stage).
- **`bronze.integrationprod.advertisers`** on `advertiser_id` — 1 row per advertiser (dim), **N:1**, no
  fan-out. Join for `advertisers.company_name` (the reliable advertiser label).
- **`silver.summarydata.sum_by_campaign_by_day`** — same campaign×day grain, its upstream sibling with
  longer history (2024-01-01→present) and a working `uniques` HLL. Prefer it for long pre-periods / reach.
  Roughly **1:1** on `(campaign_id, day)` within the overlapping window (both are daily campaign rollups).
- No raw-event / impression-grain joins needed — this is already a terminal aggregate.

## Gotchas
- **FROZEN / STALE — data stops at 2026-04-30.** Live max(day)=2026-04-30 (80+ days behind current date);
  effective start=2025-09-01 (241 distinct days, essentially contiguous). A trailing-window filter like
  `day >= last 7 days` returns **zero rows** (dry-run = 0 bytes). Pipeline appears to have stopped
  advancing. For anything "current," use the fresh fact tables (see Purpose). Acceptable only for
  historical Sep-2025→Apr-2026 patterns. Confirm `MAX(day)` before every use.
- **Effective start 2025-09-01**, despite the GCP data floor of 2025-01-01 — no rows before Sep 2025.
- **Reach/site-visitor family is entirely empty** (see Column meanings) — the biggest correctness trap.
  Older tribal notes flag only `uniques`; live data shows the whole family (site_visitors, *_users_reached,
  competing_site_visitors, …) is 0. Never derive reach/uniques/VVR from this table.
- No duplicate rows — grain is clean 1:(campaign×day).
- `day` is a plain DATE (no epoch, no timezone ambiguity in this view); no `time_unit` conversion needed.

## Cost & partitioning notes
- **Partition: DAY on `day`; no clustering; no TTL** (physical `...__11365516`: DAY-partitioned on `day`,
  clustering=None, no expirationMs). `require_partition_filter=false` — pruning is not enforced, so it is
  on YOU to add it. **The one filter to always apply: `WHERE day BETWEEN '<start>' AND '<end>'`.**
- Physical backing storage (numBytes, ≈ SELECT * logical size): **2,010,673,984 bytes (~1.87 GiB)** across
  2,856,071 rows. Whole table is small, but a `SELECT *` full scan still bills the full ~1.9 GiB — prune.
- Dry-run figures (labeled by exact column set, from `bq query --dry_run`, re-confirmed 2026-07-19):
  - `SELECT day` (1 narrow col), **no filter, full table** → **22,848,568 bytes (~21.8 MB)**.
  - `SELECT *`, **no filter, full table** → **2,010,673,984 bytes (~1.87 GiB)** — prune to avoid this.
  - `SELECT day` **WHERE day >= last 7 days** → **0 bytes** — perfect partition pruning (and 0 here also
    because the table is frozen at 2026-04-30, so recent windows hold no partitions).
  - (Scan cost is column-set dependent and scales roughly with the bytes of the columns selected, bracketed
    by the two figures above — name the exact `SELECT` list and `--dry_run` when a precise number matters.)
- Partition confirmed empirically: adding the `day` filter drops the byte estimate from 22.8 MB → 0, so
  `day` is the partition column (matches physical metadata).

## Example queries
```sql
-- Daily campaign spend + view-through visits over a bounded, in-range window (ALWAYS filter day).
SELECT day, campaign_id, advertiser_id, impressions, media_spend, views, view_conversions
FROM `dw-main-silver.aggregates.agg__daily_sum_by_campaign`
WHERE day BETWEEN '2026-03-01' AND '2026-04-30'   -- table is frozen at 2026-04-30
  AND campaign_id = <id>;

-- Always sanity-check freshness first — this table is stale:
SELECT MAX(day) AS max_day FROM `dw-main-silver.aggregates.agg__daily_sum_by_campaign`;
```
