# aggregates.terms_log_agg_min

## Purpose
Minute-grain aggregate of the bidder's **term-level pacing/throttle log**. Each row rolls up, for one
minute, the bid-side activity attributed to a single **targeting term** (a keyword/segment ID the bidder
scored the request against — BUK / behavior-keyword relevant) within a campaign, publisher, PMP deal and
inventory source: how many bid requests came in, how many became bids vs 204 no-bids, the average win
rate, and the pacing state (spend/impression caps, throttling %, in-flight spend). Reach for it to answer
"why is this term/campaign under- or over-delivering right now?" — throttling, spend-capping, rate-limiting,
and no-bid reasons at term granularity. Every row's `inventory_source` is `beeswax` (the only value
observed at 5-min, 1-hour and full-day scale) — this is effectively the Beeswax-integration term log, not
a multi-source superset. (`data_catalog.md` lists a sibling `terms_log_agg_min_mntn_bidder`; no such object
exists in the `aggregates` dataset as of 2026-07-19 — see Joins.)

## Grain & keys
- **Grain:** one row per **minute** (`bid_time` truncated to `:00` seconds) x the full bidding-decision
  dimension set: `advertiser_id`, `flight_id`, `campaign_group_id`, `campaign_id`, `eligible_term_id`,
  `picked_term_id`, `term_id`, `publisher`, `pmp_deal_ids`, `selected_pmp_deal_id`, `inventory_source`,
  `threshold_failure_reasons`, `dimension`. **Empirically verified unique** on a 5-minute slice
  (324,520 rows = 324,520 distinct combinations of those columns; measures aggregate within the combo).
  No single small subset is a key — e.g. a term repeats across publishers and picked-term outcomes.
- **Primary filter/query keys (cluster order):** `bid_time` (partition) → `campaign_id` → `term_id`.
- **A "term":** an individual targeting-term / keyword-segment ID the bidder evaluated (values like
  `90588`, `32557`). `eligible_term_id` is a **string-encoded array** of every candidate term for the
  underlying opportunity (e.g. `"[90588, 32557, 32558]"`); `picked_term_id` is the single term actually
  selected to bid under; `term_id` is the one term this row's metrics are attributed to (fans one bid
  opportunity into one row per active eligible term). **`term_id` and `picked_term_id` are NULL on most
  rows** (term_id ~92.6%, picked ~99.9%) — populated only on the pacing-meter subset; see Column meanings.

## Column meanings (only the non-obvious ones)
- **bid_time** — TIMESTAMP truncated to the **minute** (seconds always `:00`); this is the partition key
  and the aggregation bucket, not an event timestamp. UTC.
- **eligible_term_id** — STRING-encoded array of ALL candidate term IDs for the underlying bid
  opportunities, e.g. `"[90588, 32557, 32558]"`. Not a scalar ID; parse before joining.
- **picked_term_id** — the single term ID actually selected to bid under (scalar). Can differ from
  `term_id`, and is **NULL on ~99.9% of rows** (populated on only ~9.7K of 15.06M rows on the 2026-07-17
  12:00-12:05 slice, including on successful-bid rows) — do not rely on it as a populated key.
- **term_id** — the targeting term this row's metrics are attributed to (scalar, cluster key), but **NULL
  on the majority of rows** (~92.6% on the 2026-07-17 12:00-12:05 slice). It is non-NULL **exactly when
  `dimension` is non-NULL** (identical on all 15.06M slice rows) — i.e. only on the pacing-meter subset.
  NULL does **not** mean "no-bid": ~99.9% of all bids (8.31M of 8.32M on the slice) sit on NULL-`term_id`
  rows, and ~2.0M NULL-`term_id` rows carry `total_bids > 0`. Grouping by `term_id` buckets almost all bid
  volume under NULL.
- **dimension** — the pacing meter type: **`SPEND`** (budget pacing, ~1.07M rows) or **`COUNT`**
  (impression/count pacing, ~41K rows), else **NULL** (~92.6% of rows on the 2026-07-17 12:00-12:05 slice).
  NULL flags rows with no pacing-meter reading — but it is **not** a no-bid marker: NULL-`dimension` rows
  hold ~99.9% of all bids (8.31M of 8.32M on the slice; see Gotchas). `max_term_spend`/`max_term_spend_cap`
  populate only when `dimension='SPEND'`; `max_term_impressions`/`max_term_impression_cap` only when
  `dimension='COUNT'`; `avg_win_rate` and the other pacing floats are NULL on NULL-`dimension` rows. Use
  `total_bids`/`threshold_failure_reasons`, never `dimension`, to split bid vs no-bid.
- **threshold_failure_reasons** — reason(s) a request produced no bid, e.g. `invalidCampaignIntentScore`,
  `missingIntentScore`, `ghostBid` (camelCase — **not** the `ghost-bid` hyphenation used in
  `bid_logs_enriched`; `= 'ghost-bid'` matches 0 rows here). Often a **comma-joined multi-reason string**,
  e.g. `dailyTermSpendRateLimited, cappedOrPaced` or `dailySpendPacing, cappedOrPaced` — match a single
  reason with `LIKE`/`CONTAINS_SUBSTR`, not `=`. **Empty string `""`** (NOT null) on rows that bid
  successfully (`= ''` ⟺ `total_bids > 0`).
- **inventory_source** — the bidding integration/exchange. **Single value `beeswax`** at every scale tested
  (5-min, 1-hour, full day 2026-07-17) — not a multi-source column, so `WHERE inventory_source = '<other>'`
  returns zero rows.
- **publisher** — publisher/app label of the inventory (e.g. `paramountstreaming.reality`,
  `samsungtvplus.entertainment`), part of the grain.
- **pmp_deal_ids** / **selected_pmp_deal_id** — candidate PMP deal ID(s) and the one selected
  (e.g. `PMP-MNTN-Beeswax-Magnite-Centerstage`); NULL/empty on open-exchange rows.
- **total_bid_requests / total_bids / total_204_bids** — INT counts within the minute-combo: requests
  seen, bids submitted, and 204 no-bid responses. `total_204_bids > 0` with `total_bids = 0` is the
  no-bid case (paired with a `threshold_failure_reasons`).
- **total_spend_capped / total_rate_limited** — INT counts of requests dropped for hitting the spend cap
  or the rate limiter.
- **avg_win_rate / throttling_percentage / bid_volume_percentage** — FLOAT **fractions** (0-1), not
  percentages-as-100 (e.g. `avg_win_rate=0.693`, `throttling_percentage=0.01`).
- **max_term_spend / max_term_spend_cap / max_term_impressions / max_term_impression_cap /
  total_in_flight_spend / total_in_flight_bids** — bidder-internal **scaled** pacing values (observed in
  scientific notation, e.g. `max_term_spend_cap=4.53568E7`, `total_in_flight_spend=8690.0`). Treat as
  raw bidder units, **not plain dollars** — confirm the scale factor with the bidder team before
  reporting as currency. NULL when the row's `dimension` doesn't match the meter (see `dimension`).

## Joins & relationships
Dimension IDs join to the standard `bronze.integrationprod` dims — this table is **many rows per dim key**
(N:1 toward each dim), so enriching a slice of this table is safe, but joining a dim FORWARD into this
table fans out massively (billions of rows). Always pre-filter `bid_time` first.
- **campaign_id → `campaigns.id`** (dim 1 row/campaign; this table N:1). Use `campaigns.funnel_level` for
  stage, `campaigns.name` for label. Reverse = huge fan-out.
- **campaign_group_id → `campaign_groups.id`**; **advertiser_id → `advertisers.id`** (use
  `advertisers.company_name` — `fpa_advertiser_verticals.advertiser_name` is unreliable/empty).
- **flight_id → `flights.id`** (flight/budget window).
- **term_id / picked_term_id** — targeting-term IDs. Their exact dim mapping (BUK/DS19/DS38 keyword or
  `categories` space) is **not verified in this pass**; do not assume a `categories.id` join without
  confirming. `eligible_term_id` must be array-parsed before any term join.
- **No sibling view:** `data_catalog.md` (L1413) lists `aggregates.terms_log_agg_min_mntn_bidder`, but that
  object does **not exist** — `bq ls aggregates` returns only `terms_log_agg_min` (VIEW), and `bq show`/
  `SELECT` on the sibling errors `Not found` (checked 2026-07-19). Treat the catalog entry as stale.

## Gotchas
- **Split bid vs no-bid with `total_bids`, NOT `dimension`.** ~92.6% of rows are no-bid (`total_bids=0`,
  `total_204_bids>0`, non-empty `threshold_failure_reasons`) on the 2026-07-17 12:00-12:05 slice. But
  `dimension`/`term_id` are NULL on those same ~92.6% of rows **and on ~99.9% of all bids** — filtering
  `dimension IS NOT NULL` keeps only the ~7.4% pacing-meter subset and **drops ~99.9% of bids** (bids with
  `dimension IS NOT NULL` = 9,970 of 8,323,453). For actual bidding activity use `total_bids > 0`
  (⟺ `threshold_failure_reasons = ''`).
- **`threshold_failure_reasons` uses empty-string, not NULL, for success** — filter `= ''` for "bid OK",
  not `IS NULL`. Failure values are often **comma-joined multi-reason strings** (e.g.
  `dailyTermSpendRateLimited, cappedOrPaced`); use `LIKE '%reason%'`/`CONTAINS_SUBSTR`, not `=`, to catch a
  single reason. The ghost-bid literal here is **`ghostBid`** (camelCase), not `ghost-bid`.
- **Term fan-out (metered subset only):** where `term_id` is populated (the ~7.4% pacing-meter subset), one
  bid opportunity with N eligible terms can produce N rows (one per active `term_id`); do not sum
  `total_bids` across term rows to get campaign totals. The bulk of bids sit on NULL-`term_id` rows (see
  `term_id`), so per-`term_id` reads cover only the metered slice, not overall bid volume.
- **`eligible_term_id` is a STRING array literal**, not a native ARRAY — parse it, don't `UNNEST` directly.
- **Scaled pacing units** (see column notes) — `max_term_*` and `in_flight_*` are not dollars; the
  `E7`-magnitude values will mislead if summed as currency.
- **`bid_time` is minute-truncated UTC** — grouping by hour/day is exact; there is no sub-minute detail.

## Cost & partitioning notes
- **Always filter `bid_time`** (partition, DAY). It is not `require_partition_filter`-enforced, so an
  unfiltered query silently full-scans every column it selects: `SELECT *` unfiltered = ~113.5 TB, while a
  narrow unfiltered scan bills only the chosen columns (3 cols = 5.34 TB). Within a day, add `campaign_id`
  and/or `term_id` (cluster keys, in that order) to prune further. Avoid `SELECT *` — 28 columns, wide.
- Dry-run measured 2026-07-19 (3 cols: `campaign_id, term_id, total_bids`): **1-day `bid_time` filter =
  122.5 GB** (122,546,370,087 B) vs **unfiltered = 5.34 TB** (5,338,780,672,227 B) → partition prune ≈
  **43.6x** on that column set. `SELECT *`: **1-day = 1.83 TB**, unfiltered = 113.5 TB.
- Real backing storage `bq show numBytes` = **137,534,998,671,329 B (~137.5 TB)**, ~382B rows (re-checked
  2026-07-29; was ~113.5 TB / ~329B rows on 2026-07-19 — grows ~daily as partitions accrue).
- **Data floor:** the backing table has daily partitions from **2026-04-18** onward (103 partitions as of
  2026-07-29, floor unchanged since 2026-07-19; ~382B rows total) — `bid_time` before ~2026-04-18 returns
  zero rows. `ttl_days` is null (no partition expiration configured), but a SQLMesh physical rebuild can
  reset this floor (new hash).
- Actual runs (28 cols, tight filters): a 5-minute slice with LIMIT scanned **0.24 GB**; a
  full-column 5-minute grain check scanned **0.22 GB** (single partition; cluster pruning helps).

## Example queries
```sql
-- Per-term bidding activity for one campaign over one day (uses partition + both cluster keys)
SELECT term_id,
       SUM(total_bid_requests) AS reqs,
       SUM(total_bids)         AS bids,
       SUM(total_204_bids)     AS no_bids,
       AVG(avg_win_rate)       AS avg_win_rate
FROM `aggregates.terms_log_agg_min`
WHERE bid_time >= TIMESTAMP('2026-07-17') AND bid_time < TIMESTAMP('2026-07-18')
  AND campaign_id = 162502
  -- do NOT add `dimension IS NOT NULL`: it keeps only the ~7% pacing-meter subset and drops ~99.9% of
  -- bids. term_id is NULL on ~92.6% of rows (incl. most bids), so those bucket under term_id=NULL;
  -- add `AND total_bids > 0` for bids-only.
GROUP BY term_id
ORDER BY bids DESC;

-- No-bid reason breakdown for a campaign-minute window
SELECT threshold_failure_reasons, SUM(total_204_bids) AS n
FROM `aggregates.terms_log_agg_min`
WHERE bid_time >= TIMESTAMP('2026-07-17') AND bid_time < TIMESTAMP('2026-07-17 01:00:00')
  AND campaign_id = 133811 AND total_bids = 0
GROUP BY 1 ORDER BY n DESC;
```
