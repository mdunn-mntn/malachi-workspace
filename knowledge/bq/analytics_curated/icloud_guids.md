# analytics_curated.icloud_guids

## Purpose
Curated identity table for **Apple iCloud Private Relay** traffic. Private Relay proxies a user's connection through Apple/Cloudflare egress IPs, so the raw connection IP is a *shared relay address* — useless as a device/household identity key and misleading for geo. This table takes the full set of known Private Relay **IPv4 egress addresses** and assigns each one a stable synthetic **guid** (a name-based/version-3 UUID observed 1:1 with the IP). Downstream identity resolution and geo handling use the guid as the identity handle for relay traffic instead of trusting the raw IP.

Reach for it when you need to (a) detect that an IP is an iCloud Private Relay egress address, or (b) attach the stable relay-guid to a relay IP. It is the IPv4 companion to `icloud_ipv4` (same IP universe, plus the guid) and to `icloud_ipv6` (the IPv6 side, currently empty). Source layer: this is the CoreDW `icloud_guids` copy replicated into BQ (`dw-main-bronze.analytics_curated`); `silver.summarydata.icloud_guids` is the downstream silver view over the same data.

## Grain & keys
- **Grain:** one row per iCloud Private Relay **IPv4 address**. Verified strict 1:1 — 120,482 rows, 120,482 distinct `ip`, 120,482 distinct `guid`, zero NULLs (2026-07-19).
- **Key(s):** `ip` (natural key, unique) ↔ `guid` (also unique). Either column uniquely identifies the row. `ip` is the join key to log/event tables.

## Column meanings (only the non-obvious ones)
- **`ip`** — a single Apple iCloud Private Relay **IPv4 egress address** (e.g. `172.224.241.169`, `140.248.48.86`, `104.28.110.108`). These are individual addresses, **not CIDR ranges** (0 rows contain `/`) and **not IPv6** (0 rows contain `:`). NULL-free. This is the identical IP set as `analytics_curated.icloud_ipv4` (verified: 0 IPs in this table are absent from `icloud_ipv4`).
- **`guid`** — a stable synthetic identity string in UUID format (e.g. `72566cd7-2417-316c-8b30-bd21e05ed0b7`). Every sampled value is a **version-3 (name-based / MD5) UUID** (the version nibble is `3`), i.e. a deterministic hash-derived id rather than a random one, so the same relay IP yields the same guid across refreshes. NULL-free and unique 1:1 with `ip`. This is the identity handle used for relay traffic in place of the shared/rotating raw IP.

## Joins & relationships
- **`analytics_curated.icloud_ipv4`** (1:1) — same 120,482-row IPv4 universe; this table = that IP list **plus** the guid column. Semi-join / membership check: `WHERE ip IN (SELECT ip FROM icloud_ipv4)` is equivalent to `WHERE ip IN (SELECT ip FROM icloud_guids)`. No fan-out (both unique on `ip`).
- **`analytics_curated.icloud_ipv6`** (sibling) — the IPv6 companion, **currently empty (0 rows)**; columns `ip, prefix, first_8_bits, first_16_bits, network`. IPv6 relay coverage is not populated here, so this table covers only the IPv4 side of Private Relay.
- **Log/event tables keyed on `ip`** (e.g. `logdata.*`, `summarydata.*`, `icloud_vv_log`) — join `icloud_guids.ip = <table>.ip` to tag relay traffic or attach the relay-guid. **Fan-out risk is on the log side, not here:** icloud_guids is unique on `ip`, so a join can only match a log row at most once — but log tables have many rows per IP, so the *result* multiplies at the log grain, never at this table's grain. Use the enriched/preferred `ip` column (not `original_ip`, which is the pre-relay raw connection IP) when joining for relay identity.
- **`silver.summarydata.icloud_guids`** — downstream silver **view** over the same data; query whichever layer your pipeline standardizes on. This bronze `analytics_curated` copy is the CoreDW-replicated source layer.

## Gotchas
- **IPv4-only.** IPv6 Private Relay egress is *not* in this table (`icloud_ipv6` is empty), so relay traffic arriving over IPv6 will not match here — do not treat a non-match as "not Private Relay."
- **Static full-replace snapshot, not append/incremental.** `creationTime` and `lastModifiedTime` are ~50s apart, indicating the table is rebuilt by a full replace load rather than incrementally appended. There is **no timestamp/date column and no partition** — you cannot ask "when was this IP added" or filter by load date. Treat it as a point-in-time reference list that is periodically refreshed wholesale; the relay IP set drifts as Apple rotates egress ranges, so a stale copy will miss newer relay IPs.
- **Row-count drift vs CoreDW is expected and minor.** CoreDW `icloud_ipv4` had ~120,550 rows vs BQ's ~120,482 at migration audit (Ryan Kleck, 2026-04-01) — a small, known discrepancy, not a data-quality alarm.
- **guid is synthetic, not a real Apple/device identifier.** It is a hash-derived surrogate for the relay IP; it does not resolve to a household or a persistent user across relay-IP rotation. It is only as good an identity as the shared relay IP it is derived from.
- **Related-but-different use of iCloud IPs:** the legacy `logdata.icloud_ipv4_ips` external list (GCS `icloud_ips/all_ips/`) is used by Targeting to **exclude** relay IPs from bidding so they never enter MembershipDB. That exclusion role is separate from this table's identity-mapping role; don't conflate the two.

## Cost & partitioning notes
- **No partition and no clustering** (physical `BASE TABLE`, confirmed via `bq show`: `timePartitioning`/`rangePartitioning`/`clustering` all null). The "always filter the partition column" rule does not apply — there is no partition column and no date column to filter on.
- Tiny reference table (~6.5 MB, 120,482 rows) — a full scan is negligible. The only cost lever is **column pruning**:
  - `SELECT *` (ip + guid): **6,465,476 bytes** (dry-run; = full `numBytes`).
  - `SELECT guid` only: **4,578,316 bytes** (dry-run) — guid is the bulk of storage.
  - `SELECT ip` only: **1,887,160 bytes** (dry-run; = exactly `icloud_ipv4`'s full storage).
- For a pure membership test, select only `ip`; pull `guid` only when you actually need the identity handle.

## Example queries
```sql
-- Attach the stable relay-guid to a log's IPs (tag Private Relay traffic)
SELECT l.*, g.guid AS relay_guid
FROM `dw-main-silver.logdata.some_log` l
LEFT JOIN `dw-main-bronze.analytics_curated.icloud_guids` g
  ON l.ip = g.ip            -- unique on ip → no fan-out from this table
WHERE l.day = '2026-07-19';

-- Pure membership test (cheapest: reads the ip column only, ~1.9 MB)
SELECT COUNT(*) AS relay_impressions
FROM `dw-main-silver.logdata.some_log` l
WHERE l.day = '2026-07-19'
  AND l.ip IN (SELECT ip FROM `dw-main-bronze.analytics_curated.icloud_guids`);
```
