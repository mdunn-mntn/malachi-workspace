# analytics_curated.icloud_ipv6

## Purpose
Reference lookup of the **IPv6 egress CIDR ranges** that Apple iCloud Private Relay routes traffic
out of (Cloudflare / Akamai / Fastly second-hop egress blocks that Apple contracts). When an inbound
impression/visit arrives from one of these ranges, the source IP is a **relay egress IP — not the
device's real IP** — so geo and identity must be handled specially (see `original_ip` vs `ip` in
`data_knowledge.md` § IP columns: `original_ip` = pre-relay TCP IP, `ip` = MNTN-enriched device IP).
This table is the IPv6 half of the relay-detection set; `analytics_curated.icloud_ipv4` is the IPv4
half and `analytics_curated.icloud_guids` maps relay IPs to guids. Reach for it to (a) flag/exclude
relay traffic, or (b) test whether an observed IPv6 falls inside a known Apple relay range.

## Grain & keys
- **Grain:** one row per Apple Private Relay IPv6 **egress CIDR range** (e.g. `2606:54c0:820:21d0::/64`).
- **Key:** `ip` is the unique key — 406,799 rows, 406,799 distinct `ip`, 0 NULLs (verified).
- Every `ip` value carries a `/prefixlen` CIDR suffix (100% of rows). Prefix lengths observed: /64
  (63%), /48 (27%), /45 (5%), then /60, /52, /56, /58, /54, /41, /40 (long tail).
- **No time/date/partition column** — this is a full-replace snapshot, not an event log.

## Column meanings (only the non-obvious ones)
- **`ip`** — the full relay range in **CIDR notation with a `/prefixlen` suffix**, e.g.
  `2606:54c0:820:21d0::/64`. This is a RANGE, not a single address — you cannot equality-join an
  observed IPv6 to it (see Gotchas). Unique across the table.
- **`first_8_bits`** / **`first_16_bits`** — **misleadingly named** (the labels are inherited from the
  IPv4 sibling's octet convention). In IPv6 each group ("hextet") is 16 bits, so in practice
  `first_8_bits` holds the **first hextet** (e.g. `2606`) and `first_16_bits` the **first two hextets**
  (e.g. `2606:54c0`) — i.e. 16 and 32 bits, NOT 8 and 16. Only 4 distinct `first_8_bits`
  (`2606`, `2a02`, `2a04`, `2a09`) and 7 distinct `first_16_bits` values — these enumerate the Apple
  relay egress-provider blocks (largest: `2a02:26f7` = Cloudflare, 225K ranges). Use them as cheap
  coarse pre-filters before a full CIDR-containment test.
- **`network`** — the coarse **/48 aggregate**: the first ~3 hextets of `ip` (e.g. `2606:54c0:820`).
  Verified to be a leading substring-prefix of `ip` in 100% of rows and to hold exactly 3
  colon-groups. 120,932 distinct networks aggregate the 392,309 distinct prefixes — use `network` as
  a many-to-one coarse bucket for the range.
- **`prefix`** — the leading hextets that cover the CIDR's prefix length (`ip` minus the trailing
  `::/len` zeros): for /64 rows = 4 hextets (`2606:54c0:820:21d0`), for /48 and /45 rows = 3 hextets.
  Finer than `network`, coarser than the full `ip`; a convenience key that avoids re-parsing `ip`.

## Joins & relationships
This is a small **reference/dimension** table, not a fact table. Typical use is a containment/lookup
against observed IPv6 addresses, not an equi-join:
- **Observed-IPv6 (event/impression/visit tables) → icloud_ipv6:** relay detection. There is **no clean
  equi-join** because `ip` here is a CIDR range. Standard pattern: pre-filter candidates on
  `first_16_bits` or `network` (string-prefix of the observed address), then confirm with a
  CIDR-containment test on `ip`. Partner grain is 1:N (one range covers many device addresses); as a
  detection filter it is effectively N:1 (each observed IP matches at most one range). Fan-out risk is
  low as a boolean "is-relay" flag, but a naive `LIKE`/prefix join on `first_16_bits` alone would match
  the whole Cloudflare block — always narrow to `network`/CIDR before treating a row as identity.
- **icloud_ipv6 ↔ `analytics_curated.icloud_guids`:** guids maps relay `ip` → `guid`. Note guids'
  `ip` column and this table's `ip` are **different shapes** — guids may key individual/normalized IPs
  while this table keys CIDR ranges — so do not assume a direct string equality join; treat guid
  mapping and range detection as two separate steps. (Guid side not live-reconciled here.)
- **Downstream view:** `silver.summarydata.icloud_ipv6` (VIEW → `sqlmesh__summarydata`, per
  `data_catalog.md`) is the downstream/consumer copy of this curated external source. This
  analytics_curated table is the **source layer**; the summarydata view is what most silver pipelines
  read. (Downstream view not live-reconciled in this pass.)

## Gotchas
- **`ip` is a CIDR RANGE, not an address — never equality-join it to an observed IPv6.** You must do
  CIDR containment (or match the coarser `network`/`first_16_bits`/`prefix` helper columns, which exist
  precisely to make containment cheap). This is the key structural difference from the IPv4 sibling:
  `analytics_curated.icloud_ipv4` is a flat single-column (`ip`) list of individual addresses that CAN
  be equality-joined; IPv6 relay space is too large to enumerate, so it is stored as prefix ranges with
  helper decomposition columns instead.
- **`first_8_bits` / `first_16_bits` names lie about bit boundaries** (IPv4 octet naming carried onto
  IPv6 hextets) — see Column meanings. They are the first-1-hextet and first-2-hextet strings.
- **`network` is a coarse /48-ish bucket, not the CIDR's actual network address.** It is always the
  first ~3 hextets regardless of the row's real prefix length (a /45 or /64 both collapse to the same
  3-hextet `network`), and a few /45 rows render it as 2 hextets + trailing colon. Use it as a coarse
  pre-filter string, not as an authoritative subnet.
- **Full-replace snapshot, no as-of column.** There is no date/version column, so you cannot tell from
  within the table how stale it is; it is periodically regenerated by the coredw/summarydata curation
  job that writes the backing parquet. Freshness = whenever that job last ran.
- **All columns are STRING** — no INT epoch columns, so no unit/anchor question applies here
  (`time_unit: none`).

## Cost & partitioning notes
- **EXTERNAL table** over GCS parquet: `gs://mntn-analytics-curated/coredw/summarydata/icloud_ipv6/*.parquet`
  (autodetect schema, PARQUET). BQ storage metadata reads 0 (`numBytes`/`numRows`=0) because bytes live
  in GCS, not BQ — hence `approx_logical_bytes: null` (no BQ physical to sum).
- **No partition and no partition filter** (`requirePartitionFilter=false`; there is no date column to
  filter on). "Always filter the partition column" does not apply — instead keep scans cheap by
  **selecting only the columns you need** and pre-filtering on `first_16_bits`/`network`.
- **Dry-run cost is uninformative for this table.** `--dry_run` on both `SELECT ip, network` and
  `SELECT *` reports the external-table "lower bound of 0 bytes" — BQ cannot pre-estimate GCS parquet;
  billing is per-GiB actually read at run time. In practice the table is tiny (406,799 rows × 5 short
  strings), so even a full scan is negligible; there is no expensive-column trap here.
- **Job location:** external-table-only query (no BQ dataset input) → pass `--location=us-central1`
  explicitly so it lands on the org slot reservation instead of defaulting to US on-demand.

## Example queries
```sql
-- Enumerate the Apple relay egress blocks (provider-level buckets)
SELECT first_16_bits, COUNT(*) AS ranges
FROM `dw-main-bronze.analytics_curated.icloud_ipv6`
GROUP BY 1 ORDER BY ranges DESC;

-- Coarse relay-detection pre-filter for an observed IPv6 (confirm with real CIDR containment after)
SELECT ip, network
FROM `dw-main-bronze.analytics_curated.icloud_ipv6`
WHERE first_16_bits = '2606:54c0'
  AND network = '2606:54c0:820';
```
