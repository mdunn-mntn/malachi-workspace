# analytics_curated.icloud_ipv4

## Purpose
Static reference/lookup list of **Apple iCloud Private Relay egress IPv4 addresses**. When an Apple
device uses iCloud Private Relay, its real IP is hidden and traffic exits through a small pool of
relay egress IPs shared by many devices. Those IPs are geographically imprecise and identity-toxic
(one IP = many households). The **Targeting team uses this table to exclude these IPs from bidding**
so relay traffic never enters MembershipDB / the identity graph, and so relay IPs aren't treated as
stable household identifiers for geo-targeting (via Ryan Kleck, #chapter-data-engineering,
2026-04-01). Reach for it whenever you need to flag or filter iCloud Private Relay traffic out of an
IP-keyed analysis.

This is the **CoreDW-curated copy in BQ**. Lineage: GCS `pxf://mntn-data-curated-prod/icloud_ips/all_ips/`
(Parquet) → SQLMesh raw model `dw-main-bronze.sqlmesh__raw.raw__icloud_ips_raw` → this curated table.
Parallel copies: legacy CoreDW external table `logdata.icloud_ipv4_ips` (column `ip_address`) and the
migrated `dw-main-silver.summarydata.icloud_ipv4`. The `ipdsc` job depends on this table.

## Grain & keys
- **Grain:** one row per distinct Apple Private Relay egress **IPv4 address**. Verified empirically:
  `COUNT(*) = COUNT(DISTINCT ip) = 120,482` (equal ⇒ no duplicate IPs and no NULL `ip`).
- **Key / join column:** `ip` (the only column; the natural primary key). Join to any event/impression/
  visit table on its IP column via **exact string equality** — see Joins below.

## Column meanings (only the non-obvious ones)
- **`ip`** — a literal dotted-quad IPv4 string (e.g. `104.28.10.0`, `172.225.x.x`). **These are
  individually enumerated single IPs, NOT CIDR ranges** — verified: 0/120,482 rows contain a `/` mask
  and 0 contain a `:` (all IPv4, no IPv6). The upstream "IP ranges" are pre-expanded to individual
  addresses (GCS path `all_ips`). No port, no netmask, no numeric-integer form. Schema marks it
  nullable, but the table contains no NULLs in practice. Match it with `= '1.2.3.4'` string equality;
  do **not** attempt CIDR/netmask containment logic.

## Joins & relationships
This is a small **1:N lookup / exclusion list** — one `ip` row can match many rows in a large log
table that share that relay egress IP.
- **Partner tables (all keyed on an IP string, all one-row-per-event grain, huge):**
  `logdata.cost_impression_log` (`ip`, `bid_ip`, `original_ip`), `logdata.event_log`/`bid_logs`
  (`bid_ip`), `logdata.impression_log`, `logdata.ui_visits`/`visits` (`ip`, `impression_ip`).
- **Fan-out direction:** joining **event → icloud_ipv4** on `ip` **does not fan out** (this side is
  unique, ≤1 match per event row). The risk is the reverse: each relay IP corresponds to *many* device
  events, so never treat a matched `ip` as one household. **Use as a semi-join / filter**
  (`WHERE ip IN (SELECT ip FROM ...)` or `EXISTS`), not a metric-carrying INNER JOIN.
- **Which IP column to match:** relay hiding happens at the TCP layer, so `original_ip` (pre-relay raw
  connection IP) is the most literal target; MNTN's device-`ip` override may already differ. In
  practice targeting exclusion is applied on the bid/connection IP before MembershipDB entry. See
  `data_knowledge.md` "IP column reference" (`ip` vs `bid_ip` vs `original_ip` vs `impression_ip`).
- **Sibling relay tables (not joined here, but complete the picture):** `analytics_curated.icloud_ipv6`
  (IPv6 egress list), `analytics_curated.icloud_guids` (relay identity/guid mapping),
  `logdata.icloud_vv_log` (relay visit handling). **This table has no guid column** — the IP↔guid
  identity resolution lives in `icloud_guids`, not here.

## Gotchas
- **Column is `ip`, NOT `ip_address` (schema drift vs prose).** The legacy CoreDW external table
  `logdata.icloud_ipv4_ips` and the GCS source use `ip_address`; this curated BQ table (and the
  migrated `summarydata.icloud_ipv4`) expose it as **`ip`**. Reconciled 2026-07-19.
- **Individual IPs, not ranges.** Despite prose calling them "IP ranges," the values are fully
  enumerated single IPv4s — do exact-match, not CIDR containment.
- **Static snapshot, no time dimension.** No partition, no date, no `updated_at`, no TTL — it's a
  point-in-time reference list refreshed wholesale by the `ipdsc`/GCS pipeline. Apple rotates relay
  egress ranges over time, so a stale snapshot silently under-excludes. There's no in-table way to tell
  how fresh it is; check the upstream pipeline / GCS object if freshness matters.
- **Row-count drift across copies (expected):** CoreDW ~120,550 vs BQ ~120,482 — a minor, known
  discrepancy between the source and the migrated BQ copy (Ryan Kleck, 2026-04-01), not a data-quality
  bug.
- **Coverage is concentrated:** the 120,482 IPs live in ~8 `/16` blocks — `172.225` (48,388),
  `172.226` (24,892), `104.28` (22,903), `146.75` (15,428), `140.248` (5,654), `172.224` (3,174),
  `8.27` (42), `66.66` (1) — the Apple / Cloudflare / Fastly relay-egress partner ranges. If you need a
  cheap prefilter, gating on these `/16` prefixes captures ~everything before the exact-match join.

## Cost & partitioning notes
- **No partition and none needed** — single `STRING` column, ~120K rows, ~1.8 MB total. A full
  `SELECT *` (== `SELECT ip`, the only column) dry-runs at **1,887,160 bytes (~1.80 MiB)** — matches
  `approx_logical_bytes` exactly. There is nothing to prune and no expensive column set; scan freely.
- The real cost risk is on the **other** side: don't broadcast-join this against an unfiltered
  multi-TB log table. Semi-join with a date-filtered slice of the log table, or push the `/16` prefilter
  above, then exact-match `ip`.

## Example queries
```sql
-- Flag / exclude iCloud Private Relay traffic in an IP-keyed slice
SELECT e.*
FROM `dw-main-silver.logdata.cost_impression_log` e
WHERE e.load_date BETWEEN '2026-07-01' AND '2026-07-07'
  AND e.ip NOT IN (SELECT ip FROM `dw-main-bronze.analytics_curated.icloud_ipv4`);

-- Count how much of a slice is relay traffic
SELECT COUNTIF(r.ip IS NOT NULL) AS relay_rows, COUNT(*) AS total_rows
FROM `dw-main-silver.logdata.cost_impression_log` e
LEFT JOIN `dw-main-bronze.analytics_curated.icloud_ipv4` r USING (ip)
WHERE e.load_date BETWEEN '2026-07-01' AND '2026-07-07';
```
