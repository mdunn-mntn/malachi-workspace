# audience.mm_campaign_classifier

## Purpose
Per-campaign classification of how each **active (Live) Stage-1 prospecting campaign** is configured against
the MNTN Matched (MM) audience system. Built for AUDI-1083. One row per campaign labels: which MM version /
Fangorn cell it uses (`mm_class`), which scoring tiers its audience can reach (`tiers_reachable`), how narrowed
the targeting is (`restriction_level`), and a battery of feature flags for the underlying DS families
(DS13/DS19/DS38/DS46), Fangorn tier, HHST gate, geo restriction, and 3P/1P layering. Reach for it to
**segment or filter a campaign population by audience setup** — e.g. "give me all unmodified MM campaigns",
"which campaigns are Fangorn flagship", or "split spend by restriction_level" — by LEFT JOINing on
`campaign_id`. It is a labeling/dimension table, not an events table.

## Grain & keys
- **Grain:** one row per `campaign_id`. Confirmed 2026-07-29: 14,545 rows = 14,545 distinct `campaign_id` (1:1).
  Scope is active **Live** campaigns at `funnel_level = 1` (Stage-1 prospecting) — every row has
  `funnel_level = 1`. Row count and every per-value count below are **point-in-time from a regularly-rebuilt
  snapshot** (the earlier 2026-07-29 enrichment saw 14,573 rows; expect ±small drift each rebuild) — treat them
  as approximate, not exact.
- **Primary/natural key:** `campaign_id`.
- **Foreign keys / join columns:** `campaign_id` → the campaign dimension (e.g. `core.campaigns`) and any
  spend/impression fact keyed by campaign; `campaign_group_id` → campaign group (13,628 distinct — Stage-2/3
  rollups use the sibling `audience.mm_campaign_classifier_by_group` keyed on `campaign_group_id`);
  `advertiser_id` → advertiser (3,431 distinct).

## Column meanings (only the non-obvious ones)
> DS families (source: `ds_catalog.md`): DS13 = MNTN Vertical Categorization (bucket/vertical, also the PP tier);
> DS19 = MNTN Matched keywords (MM Core, largest MM signal); DS38 = BUK UI keywords (queued, augments DS19,
> not yet active); DS46 = Fangorn ML intent scoring (audience overlay — a DS46 campaign is still effectively MM).
- `mm_class` — the top-line label. Observed values (2026-07-29): `non_mm` (8,193, ~56% — no MM DS present),
  `mmv2` (3,602), `mm_flagship_fangorn` (1,584), `mmv3` (651), `fangorn_vertical_only` (373), `mmv1` (142).
  `mmv1/mmv2/mmv3` are team MM-version names; the two `fangorn_*` cells are DS46-overlaid campaigns.
- `mm_engine_rank` — integer ordering of the MM engine/version behind `mm_class` (higher = newer/more-capable
  engine cell). Used to rank/prefer one classification when a campaign qualifies for several.
- `has_ds13 / has_ds19 / has_ds38 / has_ds46` — the audience expression references that DS family. `has_mm` is
  the rollup (any MM-family DS present). Note DS38 (BUK) is not yet active in prod, so `has_ds38` is expected
  rare.
- `hhst_current` — current Household Score Threshold (HHST intent gate) value. Observed sentinels: `-1` and
  `NULL` both appear for "no/unknown threshold set"; `0` = gate present at 0; positive values (e.g. 9501) =
  active gate. HHST is a pacing lever thrashed daily — this is a point-in-time snapshot, not history.
- `hhst_gated` — whether the campaign has an effective HHST gate set (RTC/MM only bite when HHST is set; a
  score with no HHST is a no-op — see `ds_catalog.md`).
- `fangorn_tier` — Fangorn scoring cell (INT). ~6,752 rows NULL (non-Fangorn). Observed non-null: 5, 3, 4, 7,
  6, 2, 99, 1 (99 = sentinel/other). Fangorn runs two passes per IP (HI + PP) — this is the mapped tier.
- `is_express` — MNTN Express campaign flag (self-serve/express product path).
- `geo_reach_pct` — estimated fraction of the geo universe the campaign's geo targeting reaches (1.0 = national/
  unrestricted).
- `geo_narrowest_type` — narrowest geo-include level present: `country` (4,548), `dma` (3,176), `none` (2,513,
  no geo narrowing), `zip` (2,197), `city` (1,239), `state` (900).
- `has_geo_narrow_incl / has_geo_excl` — campaign has a narrowing geo include / a geo exclude clause.
- `three_p_semantics` — how 3rd-party (3P) audience data layers into the expression: `none` (8,652),
  `three_p_only` (2,847, 3P is the whole audience), `or_include` (2,779, 3P OR-added / additive),
  `and_include` (151, 3P AND-narrowed), `mixed` (144). `has_3p_incl`, `and_3p_narrowed`, `or_3p_additive`
  are the component flags feeding this.
- `and_1p_narrowed` — a 1P (first-party) segment AND-narrows the MM universe (1P/3P layer via AND-intersection
  narrow the scored universe; they do not bring unscored IPs into bidding — TI-999 Finding 14).
- `crm_excl_hygiene` — a CRM/suppression exclude is present (list-hygiene exclusion).
- `restriction_level` — rollup of how constrained targeting is (2026-07-29): `geo` (8,726), `none` (3,964),
  `geo+audience` (1,285), `audience` (570).
- `is_unmodified_mm` — TRUE = a "pure"/canonical MM campaign with no extra narrowing or layering (clean MM
  baseline). Useful for isolating a clean MM cohort.
- `is_flagship` — TRUE = flagship MM/Fangorn campaign (the reference/premier configuration).
- `tiers_reachable` — human-readable set of MM scoring tiers the audience can reach given its config. Observed:
  `unscored` (8,247, = the non_mm rows), `HI·MI·MaxReach (no PP)` (3,601), `HI·PP·MI·MaxReach` (2,100),
  `PP·MI (no HI)` (625). Tiers: HI = High Intent (10000), PP = Peak Performance (8000), MI = Mid Intent,
  MaxReach.
- `campaign_created` / `expression_updated_at` — native TIMESTAMPs (UTC): when the campaign was created and
  when its audience expression was last edited. Not epochs, not partition columns.

## Joins & relationships
- **LEFT JOIN on `campaign_id`** onto any campaign-keyed spend/impression/visit fact to tag rows by MM config.
  It is a dimension (1 row per campaign) so the join is safe (no fan-out) as long as the fact is also keyed at
  campaign grain. Campaigns absent from this view (non-Stage-1, non-Live) produce NULL labels — filter or
  COALESCE accordingly.
- **Stage-2/3 rollups:** this view only covers Stage-1 (funnel_level=1). For a whole campaign group across
  stages, roll up via the sibling `audience.mm_campaign_classifier_by_group` on `campaign_group_id` (per the
  view description).
- `advertiser_id` / `campaign_group_id` let you aggregate the classification up to advertiser or group level.

## Gotchas
- **`tiers_reachable LIKE '%PP%'` is NOT a Peak Performance filter.** The string `HI·MI·MaxReach (no PP)`
  contains the substring `PP`, so the LIKE matches 3,575 campaigns that reach no PP tier (verified 2026-08-19:
  LIKE returns 6,226 vs the true 2,651). **Peak Performance = `has_ds13 OR has_ds46`** (DS13 = PP v1 anchor,
  DS46 = PP v2 / Fangorn anchor). If you must use the string, use
  `tiers_reachable IN ('HI·PP·MI·MaxReach','PP·MI (no HI)')`.
- **`has_ds13` / `has_ds46` can be NULL**, not just TRUE/FALSE (2 rows on 2026-08-19: campaigns with no parsed
  DS rows). `has_ds13 OR has_ds46` returns NULL for those, so they fall out of both sides of a boolean GROUP BY.
  Wrap in `COALESCE(...,FALSE)` when the cut must be exhaustive.
- **VIEW over a snapshot table, not history.** Every column is point-in-time "current" state (Live campaigns
  only). HHST especially (`hhst_current`) is thrashed daily — do not treat it as the value in effect on some
  past date. For audience-config change history use `audience.campaign_segment_history`.
- **Scope filter is baked in:** only active/Live, `funnel_level = 1` prospecting campaigns appear. A campaign
  missing here is not "non-MM" — it may simply be paused, not Stage-1, or in a stage this view excludes.
- **`hhst_current` has two NULL-ish sentinels:** both `-1` and `NULL` mean no/unknown threshold; `0` is a real
  zero gate. Don't treat `-1` as a numeric threshold.
- **`fangorn_tier = 99`** is a sentinel/other bucket (124 rows), not a real tier-99.
- **A DS46/Fangorn campaign is still MM** (audience overlay replaces the scoring algorithm, not the audience
  config — Ryan Kleck, 2026-06-01). So `mm_flagship_fangorn` / `fangorn_vertical_only` count as MM-touching.
- **Stale physical metadata:** `bq show` of the sqlmesh physical table can report `numRows: 0` at times; the
  view returns ~14.6K rows. Trust a live `COUNT(*)`, not the physical table's cached stats.

## Cost & partitioning notes
- **Unpartitioned, unclustered VIEW** over a ~2 MB / ~14.6K-row physical table (`require_partition_filter:
  false`). There is nothing to prune and no partition filter to add. Every query full-scans the table, but the
  table is tiny (well under 0.01 GB billed for a full read), so cost is negligible.
- No epoch column; `time_unit: na`. `campaign_created` / `expression_updated_at` are native TIMESTAMPs.
- `SELECT *` is fine here (narrow, tiny). Prefer selecting only the flags you need for readability, not cost.

## Example queries
```sql
-- All "clean" unmodified MM campaigns and their reachable tiers
SELECT campaign_id, advertiser_id, mm_class, tiers_reachable, restriction_level, hhst_current
FROM `dw-main-silver.audience.mm_campaign_classifier`
WHERE is_unmodified_mm = TRUE
ORDER BY advertiser_id;

-- Tag a spend fact with MM configuration (LEFT JOIN, no fan-out — dimension is 1 row/campaign)
SELECT f.campaign_id, c.mm_class, c.restriction_level, SUM(f.spend) AS spend
FROM `dw-main-silver.<dataset>.<spend_fact>` f
LEFT JOIN `dw-main-silver.audience.mm_campaign_classifier` c USING (campaign_id)
GROUP BY 1, 2, 3;
```
