# audience.campaign_segment_history

## Purpose
Slowly-changing (valid-time) history of **which data-source keyword/category each campaign selected in its
audience expression, and when**. Every row is one selected leaf — a `(data_source_id, data_source_category_id)`
pair — pinned to its position in the campaign's AND/OR expression tree (`and_seq`, `or_seq`) and bounded by a
`[start_time, end_time)` validity interval. Reach for it to answer "what did this campaign's targeting look
like on date X" or "when did campaign C add/drop keyword K / data source DSxx". `end_time IS NULL` rows are the
**current** targeting state.

**Caveat up front (see Gotchas):** the prose docs flag this table for *contamination* — it blends template
(`audiences`) and targeting (`audience_segments`) objects, so it is unreliable as the authoritative "what
audience is this campaign using right now." For production audience-membership analysis use
`audience_segment_campaigns` + `audience_segments`. This table is best for *change history / timeline* work.

## Grain & keys
- **Grain:** one row per **campaign_id × audience_id × and_seq × or_seq × data_source_id × data_source_category_id × start_time**
  — i.e. one selected keyword/category leaf, at one expression position, for one validity interval.
  Verified effectively unique: 9,471,291 distinct combos vs 9,471,313 rows (only 22 near-simultaneous-write
  dup combos, max dup = 2). One campaign fans out to **many** rows (median ~13 active rows/campaign, p90 ~117,
  max 1,920).
- **Key(s) / join columns:**
  - `campaign_id` → the bidding campaign entity (`bronze.integrationprod.campaigns.id`; also the campaign side of `core.campaign_x_audiences`). 59,651 distinct campaigns; 56,907 have active (open) rows.
  - `audience_id` → the audience template (`core.audiences.id`). **Exactly one distinct audience_id per campaign among active rows** (56,907/56,907 → n_aud = 1).
  - `data_source_id` → DSxx data source (see domain below).
  - `data_source_category_id` → the keyword/category id *within* that data source (167,922 distinct). Same key as `integrationprod.archives_audience_keyword_state_archives.data_source_category_id`.

## Column meanings (only the non-obvious ones)
- **`start_time` / `end_time`** — valid-time interval `[start_time, end_time)` (native UTC TIMESTAMP, *not* epoch).
  `end_time IS NULL` = the selection is **currently active** (2,678,069 rows ≈ 28% of the table). When a
  selection is removed or the expression re-saved, the old row is closed with `end_time` and a new open row is
  written. Windows are non-overlapping per key (SCD-2 — verified 0 overlaps on the 5 busiest campaigns).
- **`start_time = 2000-01-01 00:00:00`** — **sentinel** for backfilled / pre-history initial state
  (271,283 rows). Not a real configuration date; don't chart it as one.
- **`and_seq`** (1–213) — index of the **AND clause** in the campaign's audience expression tree. The expression
  is an AND of clauses (mirrors the `audience_segments` expression JSON: selects / categories / geos / holdout
  AND blocks). A large `and_seq` just means many AND clauses.
- **`or_seq`** (1–7) — index of the **OR alternative** within that AND clause. Rows sharing
  `(campaign_id, and_seq, or_seq)` are OR-ed selections at the same expression slot (in the sample they share
  one `data_source_id`, e.g. and_seq=7/or_seq=1/DS=1 with ~40 category leaves OR-ed together).
  `and_seq`/`or_seq` are **1-based positions, not stable IDs** — they can shift when the expression is re-saved.
- **`data_source_category_id`** — the specific keyword/category selected inside `data_source_id`. For DS19 these
  are the MM keyword/segment ids; for DS1/DS14 the respective data-source category ids.

## Joins & relationships
- **`campaign_id` → campaigns** (`bronze.integrationprod.campaigns.id`, or the campaign side of
  `core.campaign_x_audiences`). Partner grain = one row per campaign. **Fan-out: 1-to-many** — a campaign has
  one row per selected leaf across all AND/OR positions (median ~13 active, up to 1,920). Always aggregate to
  campaign grain (e.g. `COUNT(DISTINCT campaign_id)`) before joining to campaign-level metrics, or you multiply.
- **`audience_id` → `core.audiences`** (template; partner grain one row per audience). 1:1 with campaign among
  active rows, so no extra fan-out from this side; but see the contamination caveat before treating audience_id
  as "the audience the campaign targets."
- **`data_source_category_id` → data-source-category / keyword dimension** (same id space as the archives table
  below and as `audience_segments` category selections).
- **Relation to `bronze.integrationprod.archives_audience_keyword_state_archives`:** that is the Postgres/Greenplum
  CDC **audience-keyword state archive**, keyed on `audience_id` with columns `keyword`, `keyword_type`,
  `selected`, `is_custom`, `is_magic`, `is_hidden`, `expanded_from`, `create_time`, `archive_time`,
  `data_source_id`, `data_source_category_id`. It is the *underlying keyword-state lineage* (per audience, with
  keyword text). `campaign_segment_history` is the **campaign-joined, expression-position-annotated**
  (`and_seq`/`or_seq`) valid-time projection of that lineage: it drops the keyword *text* and `selected/custom`
  flags, adds `campaign_id` + expression positions + `[start_time, end_time)` intervals. Join on
  `audience_id` + `data_source_id` + `data_source_category_id` to recover keyword text/flags for a selection.

## Gotchas
- **CONTAMINATION (authoritative — `data_knowledge.md`):** blends `audiences` (template) and `audience_segments`
  (targeting) objects, so it is **unreliable for "what audience is this campaign using."** Use
  `audience_segment_campaigns` + `audience_segments` for production audience-membership. BQ sibling
  `summarydata.v_campaign_group_segment_history` has the same issue. This table is fine for *change-history /
  timeline* questions, which is its real value.
- **No partition, no clustering** — the physical table (`sqlmesh__audience.audience__campaign_segment_history__2255962104`,
  9,471,313 rows / ~558 MB) is unpartitioned. No date filter can prune; every query full-scans. Aggregate,
  project only needed columns, never `SELECT *`.
- **`end_time IS NULL` = current state** — always filter it for "targeting as of now." Historical/closed rows
  greatly outnumber active ones (72% closed).
- **`start_time = 2000-01-01` sentinel** — backfill/initial-state marker, not a real edit time (271K rows).
- **`and_seq`/`or_seq` are positions, not identifiers** — re-saving the expression can renumber them; don't treat
  a given `(and_seq, or_seq)` as a durable slot key across time.
- **22 duplicate grain combos** (near-simultaneous writes) — dedup with `ROW_NUMBER()` if you need exact 1-row-per-key.

## Cost & partitioning notes
- **Unpartitioned VIEW** over a 9.47M-row / ~558 MB physical table. `partition_by: none`, `cluster_by: []` are
  confirmed facts (physical table has `timePartitioning: None`, `clustering: None`), not gaps. A full
  `GROUP BY data_source_id` scans the whole ~0.5 GB — there is no cheaper slice. Push filtering/aggregation into
  the query; the table is small enough that a full scan is ~0.5 GB but you cannot reduce it via partition pruning.

## Example queries
```sql
-- Current targeting of a campaign: which DSxx keywords are live now
SELECT and_seq, or_seq, data_source_id, data_source_category_id
FROM `audience.campaign_segment_history`
WHERE campaign_id = @campaign_id AND end_time IS NULL
ORDER BY and_seq, or_seq;

-- Timeline: when did campaign C add/drop DS19 (MM Core) categories
SELECT data_source_category_id, start_time, end_time
FROM `audience.campaign_segment_history`
WHERE campaign_id = @campaign_id AND data_source_id = 19
ORDER BY start_time;

-- Campaign-grain rollup (aggregate BEFORE joining to avoid fan-out)
SELECT campaign_id, COUNT(*) AS active_leaves, COUNT(DISTINCT data_source_id) AS n_data_sources
FROM `audience.campaign_segment_history`
WHERE end_time IS NULL
GROUP BY campaign_id;
```
