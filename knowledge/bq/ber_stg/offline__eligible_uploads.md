# ber_stg.offline__eligible_uploads

## Purpose
NON-CANONICAL BER staging worklist inside the offline-conversion ingestion pipeline
(`offline__uploads_processed` → `offline__hashed_value_x_ip` → **eligible_uploads** →
`offline__conversions_final`). Each row is one offline-conversion upload that is currently
**eligible** to be (re)processed for IP attribution: the row carries the date window the
matcher should scan, the conversion-attribution window, and a prep deadline. It is a
**full-refresh snapshot** (physical `creationTime == lastModifiedTime`; SQLMesh rebuilds it
every run), so it holds only the uploads eligible *right now* — 17 rows on 2026-07-20 — not
an append-only history. Reach for it to see which uploads the offline pipeline is working /
what window each is being attributed over. For the final attributed conversions use the
downstream canonical tables `summarydata.conversions` / `logdata.cost_impression_log`, not this.

## Grain & keys
- **Grain:** one row per `upload_id` (an eligible offline-conversion upload). Live-verified
  17 rows = 17 distinct `upload_id` = 17 distinct `advertiser_id` — in this snapshot each
  advertiser appears once, but the grain key is `upload_id` (one advertiser can have multiple
  uploads across snapshots).
- **Key(s) / join columns:** `upload_id` (primary), `advertiser_id`, `conversion_source_id`
  — the same trio threads every offline__ pipeline stage.

## Column meanings (only the non-obvious ones)
- **`conversion_window`** — INT64 **duration in MICROSECONDS**, NOT an epoch timestamp. The
  attribution window applied to this upload. Observed domain `{2592000000000, 5184000000000}`
  = exactly **30 days** (2.592e12 µs / 1e6 = 2,592,000 s = 30 d) and **60 days** (5.184e12 µs
  = 5,184,000 s = 60 d). This is the sole numeric time column and why front-matter
  `time_unit: microseconds`; the three `_date` columns below are native TIMESTAMP.
- **`start_date` / `end_date`** — native TIMESTAMP bounding the lookback window the matcher
  scans for this upload (`start_date` = window open, `end_date` ≈ snapshot/processing time).
- **`prep_end_date`** — native TIMESTAMP, observed to be exactly `end_date + 1 day` in every
  sampled row; the deadline by which prep/matching for this upload must complete.
- **`conversion_source_id`** — INT64 offline-conversion source id (same key used across the
  offline__ pipeline). Observed domain `{31, 37}` (37 dominant) in this snapshot.
- **`order_curr`** — currency code, **NOT case-normalized**: both `usd` and `USD` occur in the
  same snapshot. Lower-case before grouping/joining on it.
- **`time_zone`** — advertiser reporting timezone as an IANA string
  (`America/Chicago` / `America/New_York` / `America/Los_Angeles` observed); used to interpret
  the date window in the advertiser's local time.
- **`entry_count`** vs **`unique_uploaded_hashed_values`** — two DIFFERENT counts, not a
  before/after dedup of the same thing. `entry_count` = number of conversion/order entries in
  the upload; `unique_uploaded_hashed_values` = distinct hashed PII identifiers (emails/phones)
  eligible for IP matching. Either can exceed the other: a big upload dedups
  (entry 2627 → unique 2520), while a tiny order can carry multiple hashes per entry
  (entry 3 → unique 7). Do not treat one as a filtered subset of the other.
- **`upload_id`** — INT64 upload identifier; magnitudes vary wildly (5-digit to 10-digit) so
  do not assume monotonic/time-ordered ids.

## Joins & relationships
Join on `upload_id` (+ `advertiser_id`, `conversion_source_id`) to the other offline__ stages.
- `offline__hashed_value_x_ip` — **1:N** from this table (one eligible upload → many
  hashed_value×IP candidate rows). Fan-out risk: high; aggregate before joining.
- `offline__conversions_final` — **1:N** (one upload → many attributed offline conversions,
  each a hashed_value/ip pair). Fan-out risk: high.
- `offline__uploads_processed` — carries `run_ts`, so **1:N over processing runs** per
  `upload_id`; pick the latest `run_ts` (or a run window) before joining.
- `advertiser_id` → integrationprod `advertisers` dim (`deleted=FALSE AND is_test=FALSE`) —
  **N:1** (safe, no fan-out) for advertiser name/attributes.
(Partner cardinalities are from pipeline semantics + shared-key schema, not a live join on
this doc's tiny snapshot.)

## Gotchas
- **Snapshot, not history.** Full-refresh rebuild — only currently-eligible uploads are
  present (17 today). An upload disappearing from this table means it is no longer eligible,
  NOT that it was deleted. Don't build time series off it.
- **`conversion_window` is µs duration**, not a timestamp — dividing by 1e6 gives seconds.
- **`order_curr` case is dirty** (`usd`/`USD`) — normalize before use.
- **`entry_count` and `unique_uploaded_hashed_values` are independent counts** (see column
  meanings) — neither is a clean dedup of the other.
- Non-canonical intermediate — never report offline conversions from here; use
  `offline__conversions_final` / `summarydata.conversions`.

## Cost & partitioning notes
- **No partition, no clustering, no TTL** (physical: 17 rows, 1611 bytes, `timePartitioning`
  null, `clustering` null). It is a tiny full-refresh snapshot — there is no partition column
  to filter and none is needed.
- **`SELECT *` = 1611 bytes** (dry-run, all 11 columns / full table). Cost is negligible;
  scanning the whole table is fine. `approx_logical_bytes` = 1611 (physical `numBytes`).

## Example queries
```sql
-- Whole table is ~1.6 KB; just read it.
SELECT upload_id, advertiser_id, start_date, end_date, prep_end_date,
       conversion_window / 1e6 / 86400 AS conversion_window_days,  -- µs → days
       conversion_source_id, LOWER(order_curr) AS curr, time_zone,
       entry_count, unique_uploaded_hashed_values
FROM `ber_stg.offline__eligible_uploads`
ORDER BY entry_count DESC
```
