# ber_stg.offline_conversion_signal_log_processed_ingestion_time

## Purpose
Pipeline **control-plane checkpoint**, not analytical data. It stores a single high-water mark — the greatest `ingestion_time` already consumed from the offline conversion-signal log source — so the incremental offline-conversion-signal ingestion job can pick up only new rows (`source.ingestion_time > watermark`) on each run and never reprocess. Reach for it only to check pipeline freshness / whether ingestion has stalled; never for conversion counts. The canonical, queryable offline-conversion data lives downstream at `summarydata.offline_conversions` (the offline__* stage chain in this dataset — `offline__uploads_processed` → `offline__hashed_value_x_ip` → `offline__eligible_uploads` → `offline__conversions_final` — feeds it).

## Grain & keys
- **Grain:** exactly one row for the entire table (singleton). Verified: `numRows = 1`.
- **Key(s) / join columns:** none — it is a scalar state row, not an entity table. Do not join it into analytical queries.

## Column meanings (only the non-obvious ones)
- **`last_processed_ingestion_timestamp`** — native BigQuery `TIMESTAMP` (UTC), **not** an INT epoch. It is the high-water mark: the maximum source `ingestion_time` the last successful ingestion run consumed. It is a *pipeline* time (when the signal was ingested upstream), not a business/conversion event time. Overwritten in place on each run — the table holds only the current watermark, never history. Observed value `2026-07-20 09:00:00` UTC on a run whose `lastModifiedTime` was the same day, i.e. the mark tracks close to wall-clock and advances on clean hour boundaries (hourly-ish cadence). Nullable per schema, but expected non-NULL once the pipeline has run at least once.

## Joins & relationships
- **No analytical joins.** This is a bookmark table with no shared key; it is read/written by the ingestion job, not JOINed.
- **Conceptual partner:** the offline conversion-signal *log* source it watermarks (upstream ingestion feed) and the `ber_stg.offline__*` staging chain it gates. Those staging tables are SQLMesh VIEWs (physical `sqlmesh__ber_stg.*` hashes) and are the analytical grain (per upload / per hashed-value×IP / per conversion); this table is 1:whole-pipeline, so there is no fan-out to reason about.
- **Canonical downstream:** `summarydata.offline_conversions` (VIEW → `sqlmesh__summarydata.summarydata__offline_conversions__*`). Query that, not this, for offline conversions.

## Gotchas
- **Not data — control state.** Never `COUNT`, aggregate, or join this into reporting. It answers "how far has ingestion gotten?", nothing else.
- **Single mutable row, no history.** Each run overwrites the value; there is no audit trail of prior watermarks here.
- **Freshness signal.** If this timestamp stops advancing, the offline-conversion-signal ingestion has stalled and downstream `offline__*` / `summarydata.offline_conversions` will lag. A stale value here is the first place to look when offline conversions go missing.
- **UTC.** The `TIMESTAMP` is UTC; don't reinterpret in local time when comparing to source ingestion times.
- **No partition / no TTL.** Base table (`type = TABLE`), `timePartitioning = null`, `clustering = null`; it is not pruned or expired — it just gets overwritten.
