# ber_stg.unstable__budget_changes

## Purpose
BER (backend-reporting) **staging** table capturing **significant flight budget changes** — daily-budget and lifetime/flight-budget increases and decreases — for budget-change-impact analysis. `unstable__` marks it a **non-canonical pipeline intermediate**: it is a materialized SQLMesh snapshot, not a source of truth. Every row currently carries `sig_change = 1`, so the model has already filtered to "significant" changes only. Reach for it to answer *when did a flight's budget change and by how much*; for canonical spend/pacing use `logdata.spend_log` / `summarydata` rollups and the `campaigns`/`flights` dims. Data begins only ~2026-03-08 (recent-window pipeline), so it is unsuitable for historical trend work.

## Grain & keys
- **Grain:** one row per **significant budget change of a flight** at a given `change_time`.
- **Key(s):** `(flight_id, change_time)` is unique = row count (11,083). `(campaign_group_id, change_time)` and `(flight_id, change_epoch)` are equally unique. A flight recurs across rows when it has changes on multiple dates (10,555 distinct flights over 11,083 rows).
- **Join columns:** `flight_id`, `campaign_group_id` / `parent_campaign_group_id`, `advertiser_id`.

## Column meanings (only the non-obvious ones)
- **`change_time`** — canonical timestamp of the budget change; the **partition column** and the epoch anchor. Use this for all time filtering.
- **`change_epoch`** — `change_time` as an integer **UNIX_SECONDS** (verified `change_epoch = UNIX_SECONDS(change_time)` exactly; NOT millis/micros).
- **`batch_time`** — when the pipeline batch that recorded this change ran (always ≥ `change_time`; lag hours→days). **`batch_epoch`** = `UNIX_SECONDS(batch_time)` (verified; seconds, not millis/micros).
- **`change_min`** — minute-granularity change timestamp; equals `change_time` for ~85% of rows (9,430/11,083) and is earlier for the rest. **`start_time`** — flight/change start; also equals `change_time` in ~85% of rows. Prefer `change_time` as the authoritative event time.
- **`budget_change_type_id`** — direction of the **daily** budget change: **1 = increase** (100% of type-1 rows have `new_daily_budget > prior_daily_budget`), **2 = decrease** (100% `<`). Verified against the actual before/after values.
- **`new_daily_budget` / `prior_daily_budget`** — daily budget after/before the change, in dollars. `prior_daily_budget` is never NULL.
- **`flight_change_type_id`** — parallel classifier for the **lifetime/flight** budget, values {1, 2}. NOT a clean direction flag: type 1 (10,145 rows) always has `prior_flight_budget` NULL; type 2 (938 rows) mixes up/down/NULL. Treat with caution.
- **`new_flight_budget` / `prior_flight_budget`** — flight (lifetime) budget after/before. **`prior_flight_budget` is NULL in ~93% of rows** (10,352/11,083) — flight-budget deltas are largely uncomputable; rely on the daily-budget columns.
- **`attribution_window`** — `INTERVAL` (e.g. `0-0 44 0:0:0` = 44 days) — the attribution lookback window in effect.
- **`sig_change` / `sig_change_max`** — significant-change flags; **currently `1` for all rows** (the model pre-filters to significant changes) and `sig_change = sig_change_max` in 100% of rows. Do not rely on them to subset — they carry no discriminating signal in current data.
- **`multiple_changes`** — BOOL; TRUE (211 rows) when the flight had more than one change coalesced in the batch window.

## Joins & relationships
- **`flight_id` → `flights` / `campaigns` (1:1 per flight):** attach flight/campaign attributes. Low fan-out risk on the dim side; this table can hold multiple rows per flight (different `change_time`s), so joining a dim in is safe but the reverse (dim → this table) fans out to N change events.
- **`campaign_group_id` / `parent_campaign_group_id` → `campaign_groups` (1:1 on the group side):** MNTN Select product lives on `campaign_groups.product_id`. In sampled rows `campaign_group_id = parent_campaign_group_id`.
- **`advertiser_id` → `integrationprod.advertisers` (N:1):** many change rows per advertiser (1,513 advertisers over 11,083 rows). Filter dims `deleted=FALSE AND is_test=FALSE`.
- No spend/impression join is native here — to measure the *effect* of a change, join by `advertiser_id`/`flight`/`campaign_group_id` + a date window to canonical spend (`logdata.spend_log`, note ns epoch there) or summarydata rollups; expect heavy fan-out (one change row vs many spend rows).

## Gotchas
- **Non-canonical + `unstable__`:** a staging snapshot, not source of truth. Schema and semantics can shift without notice; do not build durable reporting on it.
- **Short history:** data starts ~**2026-03-08** (max ≈ current day). No pre-March-2026 rows — cannot support long lookbacks.
- **`sig_change`/`sig_change_max` are constant 1** — the view already filters to significant changes; these columns don't subset anything today.
- **`prior_flight_budget` NULL ~93%** and **`flight_change_type_id` is not a reliable up/down flag** — use `budget_change_type_id` + the daily-budget columns for change direction, which are clean.
- **Three near-duplicate timestamps** (`change_time`, `change_min`, `start_time`) agree ~85% of the time; standardize on `change_time` (partition + epoch anchor).
- **`batch_time` lags `change_time`** — late-arriving: a change appears only after the next batch run, so recent partitions may be incomplete until the batch catches up.

## Cost & partitioning notes
- **Partition = `change_time` (DAY), no clustering, no TTL** — confirmed off the physical table (`sqlmesh__ber_stg.ber_stg__unstable__budget_changes__348367159`, a real materialized TABLE, not a nested view) and by dry-run diff. Partition filter is **not required**, but always apply one.
- **The one filter to always apply:** `WHERE change_time >= '<start>'` (or a BETWEEN). Dry-run diff, single column `advertiser_id`: **full scan = 177,328 B** vs **one-day filter = 10,816 B** (~16x prune) — pruning works through the view.
- **`SELECT *` full scan = 1,701,547 B** (= physical `numBytes`); a single-column full scan is ~9.6x cheaper. Avoid `SELECT *`. The whole table is only ~1.6 MB / 11,083 rows, so cost is negligible either way, but keep the habit.
- `approx_logical_bytes` = 1,701,547 (physical `numBytes`); `approx_rows` = 11,083.

## Example queries
```sql
-- Significant daily-budget changes for an advertiser in a window
SELECT change_time, flight_id, campaign_group_id,
       budget_change_type_id,           -- 1 = increase, 2 = decrease (daily)
       prior_daily_budget, new_daily_budget
FROM `ber_stg.unstable__budget_changes`
WHERE change_time >= TIMESTAMP('2026-07-01')
  AND change_time <  TIMESTAMP('2026-07-08')
  AND advertiser_id = 41622
ORDER BY change_time DESC
```
