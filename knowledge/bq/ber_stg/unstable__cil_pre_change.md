# ber_stg.unstable__cil_pre_change

## Purpose
Pipeline-intermediate snapshot for the BER "unstable" budget-change impact study. It holds
`cost_impression_log` (CIL) impressions that fall in the **pre-period** (before-change) lookback
window of each advertiser daily-budget change, cross-joined against that change so a pre-vs-post
delivery/spend comparison can be run per change event. This is the pre-change leg; its post-change
twin is `ber_stg.unstable__cil_post_change` (identical schema, post-period window). The impression
payload is a projection of `silver.logdata.cost_impression_log`, and the change population lines up
with `ber_stg.unstable__budget_changes` (advertiser daily-budget changes).

**NON-CANONICAL staging.** Never use it for impression counts or spend totals — an impression is
duplicated once per overlapping change, so any SUM double-counts. For canonical impression/cost truth
use `silver.logdata.cost_impression_log`. Reach for this table only to reproduce or extend the
budget-change stability analysis (pre-period side).

## Grain & keys
- **Grain:** one row per **(change_id x impression)** — a pre-period CIL impression replicated once
  for each budget change whose pre-window it lands in. On 2026-06-01: 29.54M rows = 29.54M distinct
  (change_id, impression_id) pairs, but only 15.39M distinct `impression_id` (~1.9 changes per
  impression) across 2,332 `change_id` and 546 advertisers.
- **Key(s):** composite (`change_id`, `impression_id`). `change_id` = the budget-change event under
  study; `impression_id` = the CIL impression. Cluster keys are `advertiser_id`, `change_id`.
- **Partition:** `time` (impression timestamp), DAY. Data begins 2026-01-30 (study window, not full
  CIL history); ~173 day-partitions, 2.46B rows.

## Column meanings (only the non-obvious ones)
**Epoch units differ per column — do not mix (verified 2026-06-01 sample):**
- `epoch` — impression event time in **UNIX MICROSECONDS** at full sub-second precision (= `UNIX_MICROS(impression time)`; e.g. 1780310631058000 for `time` 2026-06-01 10:43:51.058). The `time` TIMESTAMP is the same instant and is the partition column.
- `change_epoch` — **UNIX SECONDS** (= `UNIX_SECONDS(change_time)`); when the budget change took effect.
- `batch_epoch` — **UNIX SECONDS**; when this snapshot batch ran. Constant across the snapshot (single build).
- `source_batch_epoch` — **UNIX SECONDS**; the upstream CIL ingestion batch that sourced each impression row (varies per row).

**Change / study columns:**
- `change_id` — identifier of the budget-change event under study (cluster key #2). Every impression is stamped with the change whose pre-window it falls in; the same impression carries multiple `change_id`s.
- `change_time` — timestamp the change took effect. In this (pre-change) table every row has `time < change_time` (0 violations observed).
- `new_daily_budget` / `prior_daily_budget` — daily budget after / before the change (NUMERIC dollars), constant per `change_id`.
- `pct_unstable` — fraction in [0,1], **constant per `change_id`** (e.g. 0.804 for change 65177): the share of the advertiser's delivery treated as "unstable"/affected by the change.
- `hash_pct` — deterministic per-impression hash in [0,1] (varies row-to-row); used for sampling/assignment against `pct_unstable`.
- `batch_source` — pipeline snapshot label; **always `"pre_change"`** in this table (its twin holds `"post_change"`).

**Impression payload (projected straight from `cost_impression_log`, same semantics as CIL):**
- `media_cost` (NUMERIC) and `media_spend`/`data_spend`/`platform_spend` (BIGNUMERIC) — cost breakdown carried from CIL.
- `household_score` (graduated), `advertiser_household_score` (binary 0/10000), `model_params` (RTC lives here as `realtime_conquest_score=10000`) — scoring fields carried from CIL.
- `is_new` — client-JS pixel new-user flag (carried from CIL; same 41-56% mismatch caveat as CIL).
- `recency_elapsed_time` — INTERVAL since prior exposure.
- `view_impression_raw`/`view_viewed_raw`/`view_untrackable` and `vast_start`/`vast_firstquartile`/`vast_midpoint`/`vast_thirdquartile`/`vast_complete` — viewability + VAST video-quartile counters carried from CIL.

## Joins & relationships
- **`ber_stg.unstable__cil_post_change`** — identical schema and grain, holding the **post-period**
  impressions (`time >= change_time`) for the same `change_id`s. Stack pre + post per `change_id` for
  the before/after comparison; do NOT join pre to post on `impression_id` (different impressions).
- **`ber_stg.unstable__budget_changes`** — the budget-change population (advertiser `new_daily_budget`
  / `prior_daily_budget`, change taxonomy). One change is **1:N** to impressions here; joining fans out.
  (Note: `unstable__budget_changes` has no `change_id` column in its schema, so the `change_id` key is
  synthesized in this pipeline — align on advertiser + change_time, not a shared surrogate.)
- **`silver.logdata.cost_impression_log`** — lineage/source. This table is a projection of CIL, so an
  `impression_id` join back to CIL is **1:N** here (impression duplicated per change). Dedup on
  `impression_id` first or you double-count impressions/spend.
- **Dims** (`advertisers`, `campaigns`, `campaign_groups`) via `advertiser_id`/`campaign_id`/`group_id`
  — **N:1** (safe direction), standard CIL join keys; filter dims `deleted=FALSE AND is_test=FALSE`.

## Gotchas
- **Fan-out double-counts spend/impressions.** Each impression appears once per overlapping `change_id`
  (~1.9x on 2026-06-01). `SUM(media_spend)` / `COUNT(*)` over-count — dedup on `impression_id`, or
  aggregate within a single `change_id`, before summing anything. This is the #1 trap.
- **Non-canonical staging** — not a source of impression/cost truth; use `logdata.cost_impression_log`.
- **Pre-period only.** Every row satisfies `time < change_time` (strict; 0 violations). The post side is
  the separate `unstable__cil_post_change` table — this one has no post-change rows.
- **Mixed epoch units** (see Column meanings): `epoch`=microseconds, `change_epoch`/`batch_epoch`/
  `source_batch_epoch`=seconds. Convert with the right multiplier.
- **Empty NULL partition.** INFORMATION_SCHEMA lists a `__NULL__` partition_id, but `WHERE time IS NULL`
  returns 0 rows — it is an empty placeholder, not late/unmatched data.
- **SQLMesh view.** Query the clean name `ber_stg.unstable__cil_pre_change`; the physical hash
  (`__2173039449`) changes on rebuild.
- **Window, not full history.** Data starts 2026-01-30 (the study window), not CIL's 2023-10-01 floor.

## Cost & partitioning notes
- **Partition:** `time` (DAY). **Cluster:** `advertiser_id`, `change_id`. `require_partition_filter` is
  **false**, but always add a `time` range — a full scan is ~2.5 TiB. Physical backing storage
  (`numBytes`) = 2.72 TB / 2.53 TiB; 2.46B rows.
- **The one filter to always apply:** `WHERE time >= 'D' AND time < 'D+1'`. Add `advertiser_id` and/or
  `change_id` predicates to exploit clustering.
- **Dry-run figures (2026-07-20, labeled by exact column set — only compare like with like):**
  - `SELECT *`, one day (time-filtered): **32.41 GiB**
  - `SELECT *`, full table (no filter): **2533 GiB (~2.53 TiB)** — partition filter prunes ~78x
  - `SELECT change_id, time`, one day: **0.44 GiB** — narrow columns prune ~74x vs `SELECT *` same day
  - `SELECT change_id, time`, full table: **36.72 GiB**
- Never `SELECT *`: the wide impression payload (VAST/view counters, spend BIGNUMERICs, user_agent)
  dominates the byte estimate.

## Example queries
```sql
-- Pre-vs-post daily delivery for one budget change (dedup impressions within the change_id).
SELECT
  DATE(time) AS day,
  COUNT(DISTINCT impression_id) AS impressions,   -- NOT COUNT(*): rows fan out per change_id
  SUM(media_spend)              AS media_spend      -- safe here: single change_id, one row per imp
FROM `ber_stg.unstable__cil_pre_change`
WHERE time >= '2026-06-01' AND time < '2026-07-01'   -- partition prune
  AND change_id = 65177                              -- cluster prune
GROUP BY day
ORDER BY day;
```
