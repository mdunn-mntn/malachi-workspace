# ber_stg.unstable__visits_pre_change

## Purpose
Non-canonical BER (backend-reporting) **staging / change-impact** snapshot. It holds row-level attributed
**visits as they looked BEFORE a re-attribution change** for a set of tracked "changes" (`change_id`).
Every row is stamped `batch_source = 'pre_change'`. It is the *before* side of a before/after pair against
its sibling view `ber_stg.unstable__visits_post_change` (the *after* snapshot); the parent QA view
`summarydata.unstable_ui_visits` is exactly the `UNION ALL` of these two physicals. BER uses the pre/post
diff to validate a re-attribution batch before promoting it to production. **Do not treat this as a source
of truth for visits.** The canonical visits table is `summarydata.visits` (alias `summarydata.ui_visits`),
which carries the same visit columns minus the five `change_*` / `batch_*` CDC audit columns. Reach for
this view only for change-impact / QA analysis, never for reporting visit totals.

## Grain & keys
- **Grain:** one row per **pre-change visit snapshot, per `change_id`**. Verified on the 2026-07-01→20
  slice: 1,290,925 rows vs 571,935 distinct `guid`, 857,848 distinct `ad_served_id`, 841,167 distinct
  `impression_id`, 992 distinct `change_id`, 1,801 campaigns, 352 advertisers.
- **No single unique key.** The same physical visit is duplicated across change batches and across
  attribution types (one `ad_served_id` can appear under multiple `attribution_model_type_id`), so
  `ad_served_id` (857K) < row count (1.29M) and `COUNT(*)` is **not** a visit count. Dedup on the full
  visit identity if you need one row per visit.
- **Visit identity:** `advertiser_id` + `ad_served_id` + `guid` + `time` (the underlying visit); join to
  dims via `advertiser_id`, `campaign_id`, `group_id`, `creative_id`.
- **Snapshot key:** `change_id` = the re-attribution batch id (scoped to exactly one advertiser — verified
  2026-07-19 on the parent view). `advertiser_id` + `change_id` are the physical cluster keys.

## Column meanings (only the non-obvious ones)
**Epoch units differ per column — verified against their TIMESTAMP anchors on the July slice:**
- `time` — TIMESTAMP the visit is attributed at; **partition column**. It is **second-granular**
  (`UNIX_MICROS(time)` ends in `000000`).
- `epoch` — the visit instant in **microseconds** (16-digit) and it carries **full µs precision**
  (e.g. `1784507012797382`, vs `UNIX_MICROS(time) = 1784507012000000`) — so `epoch` is the *higher-precision*
  version of `time`, not a copy of it.
- `impression_time` / `impression_epoch` — the credited-impression timestamp; `impression_epoch` is
  **microseconds but only millisecond precision** (value ends `000`, e.g. `1780959188678000`);
  `impression_time` is again truncated to the second.
- `change_time` / `change_epoch` — when the tracked re-attribution change was applied; `change_epoch` =
  `UNIX_SECONDS(change_time)` → **seconds** (10-digit, e.g. `1784517480`).
- `batch_epoch` — snapshot/batch build time, **seconds** (10-digit `UNIX_SECONDS`).
- `elapsed_time` (INTERVAL) = visit latency from the credited impression (`time − impression_time`);
  `recency_elapsed_time` (INTERVAL) = recency of the qualifying signal.
- `visit_day` — FLOAT64 but **integer-valued 1–14**: the **1-indexed attribution day** (day 1 = same-day
  visit), capped at the 14-day attribution window. NOT a date or epoch. Often **NULL** when not computed —
  NULL rate is much higher on `last_tv_touch_visits` rows than on `visits` rows.

**Encodings / NULL semantics:**
- `batch_source` — snapshot tag, uniformly `'pre_change'` in this view (the sibling post view carries `'post_change'`).
- `change_id` — INT id of the tracked re-attribution batch (992 distinct in the July slice); cluster key,
  scoped to one advertiser.
- `source_type` — attribution path: `'visits'` (standard display/CTV site visits) or `'last_tv_touch_visits'`
  (CTV last-touch path).
- `attribution_model_type_id` ∈ {1,2,3,4}: types **1 & 2 carry click-through visits** (`click` can be true,
  `is_competing`=false); types **3 & 4 are competing/view-type** (`is_competing`=true, `click`=false). In the
  slice `is_competing` is true **exactly** for type ∈ {3,4}. `attribution_model_id` = the specific model id.
- `is_competing` — competing/view-through visit flag (⟺ type 3/4). `click` — click-through visit flag
  (types 1/2 only). `visits_assist` and `efficient` were **all FALSE** across the slice.
- `from_verified_impression` — **TRUE for every row** in the slice (every visit ties to a verified impression).
- `is_new` — client-JS-pixel new-visitor flag (same semantics as elsewhere; do not treat as authoritative).
- `is_pa` / `pa_model_id` — post-attribution flags carried from the attribution engine (small counts).
- `ip` vs `ip_raw` vs `impression_ip` — resolved visit IP vs raw visit IP vs the IP on the credited
  impression (can differ on cross-device, `is_cross_device`).
- `ad_served_id` — the visit / ad-serve event id (repeats across change batches & attribution types, so not
  unique here); `first_touch_ad_served_id` — the first-touch event id; `impression_id` — credited impression id.
- `channel_id` — 8=CTV / 1=display (standard MNTN encoding); `device_type` STRING.

## Joins & relationships
- **`ber_stg.unstable__visits_post_change`** (sibling VIEW, same grain) — the *after* snapshot. Compare pre
  vs post on the same `change_id` **and the full visit identity** (`advertiser_id`+`ad_served_id`+`guid`+`time`)
  to measure change impact. Fan-out: joining on `change_id` alone is **N:N** (many visits per change) — always
  add the visit identity.
- **`summarydata.unstable_ui_visits`** (parent QA VIEW) — literally `UNION ALL` of this pre view + the post
  view; use it to diff both sides in one place. Non-canonical/QA-only.
- **`summarydata.visits`** (alias **`summarydata.ui_visits`**, VIEW) — the production source of truth for
  visits; shares the visit columns minus the `change_*`/`batch_*` CDC columns. Use it, not this staging view,
  for visit reporting.
- **Dims (all N:1, safe):** `campaigns`/`core_campaigns` via `campaign_id`; `advertisers`/`core_advertisers`
  via `advertiser_id`; `campaign_groups` via `group_id`; `creatives` via `creative_id`. Filter dims
  `deleted=FALSE AND is_test=FALSE`.

## Gotchas
- **Non-canonical / non-authoritative.** Intermediate change-impact snapshot — never report visit totals
  from it. Numbers here reflect *recomputed* pre-change attribution, not what was billed/reported.
- **No unique key; `COUNT(*)` ≠ visits.** The same visit is duplicated across change batches and across
  attribution types (one `ad_served_id` under multiple `attribution_model_type_id`). Dedup on the full
  visit identity if you need one row per visit.
- **`batch_source` is a constant** here (`'pre_change'`) — the pre/post distinction is the *view*, not a filter.
- **Mixed epoch units** — `epoch`/`impression_epoch` are microseconds; `change_epoch`/`batch_epoch` are
  seconds. Never assume a shared unit across the `*_epoch` columns.
- **`time` / `impression_time` are second-granular**; the µs-precise instant lives in `epoch` /
  `impression_epoch`. Use those if you need sub-second ordering.
- **`visit_day` is FLOAT64 but really an integer 1–14** (attribution day), and is frequently NULL (more so on
  `last_tv_touch_visits`) — do not treat it as a date.
- **Accumulating, no TTL.** Data spans **2026-01-30 → present** (42,820,677 rows on 2026-07-29) and keeps growing
  (expirationTime = none); an unfiltered scan grows over time.

## Cost & partitioning notes
- **Partition = `time` (DAY), not required but always filter it.** Cluster = `[advertiser_id, change_id]` —
  add `advertiser_id` / `change_id` predicates to prune within a day (runtime cluster pruning; a dry-run
  can't show it).
- Empirical partition proof (`SELECT time`, **one column**): no filter → **327,776,480 B (~327.8 MB)**;
  `WHERE time >= '2026-07-01'` (~20 days) → **10,327,400 B (~10.3 MB)**. Same column set, ~32x reduction —
  confirms `time` is the partition.
- `SELECT *` for `time >= '2026-07-01'` (~20 days, **all columns**) → **620,710,589 B (~620.7 MB)** — do not
  compare to the one-column numbers above.
- Physical backing: `numBytes` = 20,231,201,460 B (~**20.23 GB**), `numRows` = 42,820,677 (whole table, all columns; 2026-07-29).
- The one filter to always apply: `WHERE time BETWEEN <start> AND <end>` (+ `change_id` when analyzing a
  specific re-attribution batch).
