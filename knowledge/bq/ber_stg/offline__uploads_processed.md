# ber_stg.offline__uploads_processed

## Purpose
Per-upload processing/QA summary for the BER offline-conversion ingestion pipeline. Each row records the match statistics for one processed offline-conversion upload — how many entries and distinct hashed identities were uploaded, how many conversions matched (all partners vs Experian), and how many Experian-matched IPs hit the cross-device graph vs served impressions. It is an **observability / monitoring rollup, NOT the conversion records themselves and NOT a forward pipeline stage.** Reach for it to audit offline-upload match rates, spot uploads that produced zero matches, or confirm an upload was processed into ClickHouse. For the actual offline conversions, use the canonical downstream `summarydata.conversions` (BER-owned reporting) / the pipeline's own `ber_stg.offline__conversions_final`.

Pipeline context (dataset `dw-main-silver.ber_stg`, offline__* stages): uploads → `offline__hashed_value_x_ip` → `offline__eligible_uploads` → `offline__conversions_final`. This `offline__uploads_processed` view sits alongside those as the per-upload match-stats monitor.

## Grain & keys
- **Grain:** one row per **`upload_id`** (a single offline-conversion upload). `upload_id` is globally unique in the table (8,323 rows = 8,323 distinct upload_ids across 1,140 distinct `run_ts` values) — each upload is written exactly once, in the pipeline run that processed it. Append-per-run, not a per-run snapshot of all uploads.
- **Key(s) / join columns:** `upload_id` (grain key); `advertiser_id` (N:1 → advertisers); `conversion_source_id` (conversion-source lookup).

## Column meanings (only the non-obvious ones)
- **`run_ts`** (TIMESTAMP, UTC) — the pipeline run that processed this upload. Every upload processed in the same run shares one `run_ts`; it is a batch timestamp, not the upload's own creation time. Range observed 2024-04-02 → present. No epoch INT columns in this table — both timestamps are native TIMESTAMP.
- **`upload_id`** (INT64) — the offline-conversion upload identifier; the grain key (globally unique here).
- **`advertiser_id`** (INT64) — advertiser owning the upload; joins `advertisers.id`. 207 distinct advertisers observed.
- **`total_offline_conversions_all_partners`** (INT64) — total offline conversions matched for this upload across **all** match partners. Empirically `>= total_experian_offline_conversions` in 100% of rows (Experian is one partner, a subset).
- **`total_experian_offline_conversions`** (INT64) — the Experian-partner subset of the above.
- **`unique_experian_ip_matches_to_xdd`** (INT64) — distinct Experian-matched IPs that hit the cross-device (XDD) graph.
- **`unique_experian_ip_matches_to_impressions`** (INT64) — distinct Experian-matched IPs that matched a served impression (i.e. attributable to MNTN-served ads). NOT strictly nested with the XDD count: `xdd >= impressions` in only ~83% of rows, so treat the two as independent match targets, not a subset relationship.
- **`entry_count`** (INT64) — number of entries in the raw upload for this run. Observed max ~1,999,999 (near a ~2M cap). NOT a strict superset of distinct hashed values — per-row it can be above or below `unique_uploaded_hashed_values` (avg entry 8,384 vs avg unique 5,758).
- **`unique_uploaded_hashed_values`** (INT64) — distinct hashed identifiers (hashed PII / emails) present in the upload.
- **`processed_on_ch`** (BOOL) — whether this upload's conversions were processed/written into ClickHouse ("ch" = ClickHouse, the CHAPI/client-reporting store). Overwhelmingly `true`; a small tail is `false` (unprocessed / failed to reach CH).
- **`conversion_signal_max_ingestion_timestamp`** (TIMESTAMP) — high-watermark: the max ingestion timestamp of the conversion signals folded into this upload's processing.
- **`conversion_source_id`** (INT64) — conversion-source identifier. Observed domain: 37 (dominant), 31, 50, and **NULL**. NULL is a **backfill/version artifact**, not a live category: every NULL row has `run_ts` ≤ 2026-03-09; the column was added ~2026-03-10 and is populated on all rows since. Filter `run_ts >= '2026-03-10'` if you need a non-NULL source.

## Joins & relationships
- **`advertiser_id` → `advertisers.id`** (silver.core / bronze.integrationprod advertisers dimension). This table is **N:1** to advertisers (many uploads per advertiser). Dimension lookup — no fan-out. Advertiser display name via `advertisers.company_name` (per the fpa/advertiser-name gotcha, prefer `company_name`).
- **`upload_id` → sibling offline__ pipeline views** (`offline__hashed_value_x_ip`, `offline__eligible_uploads`, `offline__conversions_final`). One upload explodes to **many** hashed values / IPs / conversions downstream, so joining this per-upload summary to any per-hash or per-IP stage is **1:N with high fan-out** (an upload can carry up to ~1M distinct hashed values / ~2M entries). Aggregate the downstream side before joining. Those partners are SQLMesh VIEWs (physical metadata may read 0 rows / None partition even when populated) — grain not live-verified here; treat the fan-out warning as the safe direction.
- **`conversion_source_id`** → a conversion-source lookup (no verified dimension table located; 37 is the dominant offline/Experian-upload source). Left unresolved — see Gotchas.

## Gotchas
- **Append-per-run, never updated in place.** A given `upload_id` appears once. Do not expect a row to be revised on later runs; `run_ts` is fixed at first (only) processing.
- **`conversion_source_id` NULL = pre-2026-03-10 rows** (column added mid-life), not a real source category. Don't treat NULL as a distinct source.
- **`entry_count` vs `unique_uploaded_hashed_values` have no fixed ordering** — don't assume entries ≥ uniques (dedup) or vice-versa; both directions occur.
- **XDD-match and impression-match counts are independent**, not nested — an Experian IP can match impressions without appearing in the XDD graph.
- **Not canonical.** These are ingestion QA stats, not conversion facts. Do not sum `total_offline_conversions_*` here as a revenue/attribution source — use `summarydata.conversions`.
- **No partition / no TTL** — the physical table is unpartitioned and untruncated (full 2024-04 → present history retained). No date-filter safety requirement, but it also means filters don't cut bytes scanned (see below).

## Cost & partitioning notes
- **No partition, no clustering** (physical `TABLE`, 8,323 rows, 692,307 bytes ≈ 676 KB). The `partition_by: none` here is a verified fact, not a gap.
- Because it is unpartitioned, `WHERE run_ts …` filters **rows but not bytes billed** — cost is driven purely by columns selected. The whole table is tiny (below BQ's ~10 MB on-demand minimum), so scans are effectively free, but still prefer explicit columns over `SELECT *`.
- Dry-run byte estimates (labeled by column set): **`SELECT *` (all 12 cols) = 692,307 bytes**; **single column `upload_id` = 66,584 bytes**. Same-column-set comparisons only.

## Example queries
```sql
-- Recent uploads with low/zero Experian impression match (QA)
SELECT run_ts, upload_id, advertiser_id, entry_count, unique_uploaded_hashed_values,
       total_offline_conversions_all_partners, total_experian_offline_conversions,
       unique_experian_ip_matches_to_impressions, processed_on_ch
FROM `dw-main-silver.ber_stg.offline__uploads_processed`
WHERE run_ts >= TIMESTAMP('2026-07-01')          -- filters rows, not bytes (unpartitioned)
ORDER BY run_ts DESC
LIMIT 100;
```
