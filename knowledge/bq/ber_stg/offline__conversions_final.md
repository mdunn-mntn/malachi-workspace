# ber_stg.offline__conversions_final

## Purpose
Non-canonical **BER staging intermediate** — the FINAL stage of the offline-conversion ingestion
pipeline (`offline__uploads_processed` -> `offline__hashed_value_x_ip` -> `offline__eligible_uploads`
-> `offline__conversion_signal_orders` -> **`offline__conversions_final`**). Holds offline conversions
(in current data these are call-tracking events) that have been matched `hashed_value` -> IP -> ad
impression and attributed to a campaign/creative. Reach for it to see HOW an offline/call conversion
was attributed to a specific impression before it is rolled into canonical reporting. **Do NOT use for
canonical conversion counts** — the durable, deduped conversion of record lives downstream in
`summarydata.conversions`, and the impression/conversion event record in `logdata.cost_impression_log`.
Small full snapshot (~737K rows, ~0.32 GB as of 2026-07-29), recomputed by the pipeline (see `run_time`).

## Grain & keys
- **Grain:** one row per **attributed impression touchpoint** for an offline conversion — a conversion
  (identified by `guid`) matched to one ad impression. A single conversion/order **fans out** across every
  matched impression in its window: 337,052 distinct `guid`, avg 2.1 rows/guid, max ~1,898; 120,951 of
  337,052 guids have >1 row. **Not deduped** to one-row-per-conversion.
- **Keys / join columns:** `guid` = per-conversion identifier (UUID string; only ~3 rows NULL).
  `order_id` = advertiser's order/call id (623,141 distinct, **NULL for 77,039 rows / ~11%**, not unique).
  `upload_id` + `advertiser_id` = ingestion batch (301 uploads, 50 advertisers). Touchpoint identified by
  `impression_epoch` + `campaign_id` + `creative_id`. **No single column is a key** — even
  `guid`+`impression_epoch`+`campaign_id`+`creative_id` = 561,021 distinct < 707,977 rows.

## Column meanings (only the non-obvious ones)
- **`time` / `epoch`** — the CONVERSION (call/order) timestamp. `epoch = UNIX_SECONDS(time)` (**SECONDS**).
  `time` is always >= `impression_time` (conversion after the credited impression).
- **`event_time` / `event_epoch`** and **`impression_time` / `impression_epoch`** — the attributed AD
  IMPRESSION (the credited touchpoint). `event_*` **== `impression_*` for 100% of rows** — this is
  view-through attribution, the credited "event" IS the impression. The epoch columns are **MICROSECONDS**
  (`UNIX_MICROS`; they retain sub-second precision, e.g. `...615000`, while the TIMESTAMP columns are
  truncated to the whole second).
- **`hour`** — `time` truncated to the hour in the **advertiser's reporting timezone** (Eastern in sampled
  rows), NOT a UTC truncation of `time`. `DATE_TRUNC(time, HOUR)` in UTC will be off by the UTC offset.
- **`run_time`** — pipeline compute/batch timestamp (when this row was produced); varies per upload batch
  (2026-03-05 -> today). Use to pick the latest run; it is NOT an event time.
- **`conversion_type`** — STRING; observed domain is call-tracking labels: `Call`, `Answered Call`,
  `Missed Call`, `Voicemail`, `Abandoned Call`, plus numeric sentinel `-102`. Can be a label OR a code.
- **`channel_id`** — `1` = display, `8` = CTV.
- **`device_type`** — STRING (silver convention): `CONNECTED_TV`, `MOBILE`, `PC`, `TABLET`, `SET_TOP_BOX`,
  `GAMES_CONSOLE`, and `-1` = unknown.
- **`order_amt`** — NUMERIC conversion value in `order_curr`; always populated (0 NULL).
- **`order_curr`** — dirty: `USD`, `usd`, `''` (empty), and NULL all present; normalize case + empties.
- **`partner_id_list`** — stringified array of attribution partner ids, e.g. `[1,2,3]`, `[1]`; always populated.
- **`hashed_value`** — SHA-256 of the uploaded customer identifier (email); the join key back to
  `offline__hashed_value_x_ip`.
- **`hashed_values_key`** — ~99.99% NULL (78 non-null of 707,977) — effectively unused here.
- **`attribution_model_id`** — observed `{7, 8}`. **`conversion_source_id`** — observed `{31, 37}` (call-tracking source/partner).
- **`click`, `click_through`, `disputed`** — BOOL, **false for 100% of rows** (no click-based / disputed conversions in current data).
- **`is_cross_device`, `from_verified_impression`** — BOOL, **TRUE for 100% of current rows**.

## Joins & relationships
- **Upstream `ber_stg.offline__hashed_value_x_ip`** on `(upload_id, advertiser_id, hashed_value)` — that
  stage is the hashed_value->IP match (1:N); this final stage adds the impression match, so joining back is
  1:N -> further fan-out.
- **`bronze.integrationprod` dims** (each 1:1 on the id, fan-out is on THIS table's many-rows side):
  `advertiser_id` -> `advertisers`, `campaign_id` -> `campaigns`, `campaign_group_id` -> `campaign_groups`,
  `creative_id` -> `creatives`. Filter dims `deleted=FALSE AND is_test=FALSE`.
- **Downstream / canonical (inferred, not live-verified):** feeds the offline-conversion contribution to
  canonical `summarydata.conversions`; the durable conversion/impression record is
  `logdata.cost_impression_log`. Use those for reporting, not this staging view. (Canonical tables are
  separate SQLMesh views; lineage left prose-only, not confirmed against source.)
- No IP->IP bridging in BQ; treat `ip` as a match artifact, not a joinable identity.

## Gotchas
- **NON-CANONICAL staging intermediate** — pre-dedup; counts will NOT match canonical conversion totals.
  One conversion (`guid`) = many rows.
- **Fan-out:** joining on `advertiser_id` / `campaign_id` / `order_id` multiplies rows; dedup to `guid`
  (or `guid`+impression) first. One guid reaches up to ~1,898 rows.
- **`event_*` == `impression_*`** (view-through) — do not treat them as two separate touchpoints.
- **Two epoch scales in one row:** `epoch` is SECONDS, `event_epoch` / `impression_epoch` are MICROSECONDS.
  The TIMESTAMP columns drop the sub-second precision the microsecond epochs retain.
- **`hour` is timezone-localized (not UTC)** — reconstructing it from `time` in UTC will be off by the
  advertiser's UTC offset.
- `order_id` NULL for ~11% of rows and not unique; `hashed_values_key` ~all NULL — neither is a reliable key.
- `order_curr` casing/empties inconsistent.
- **Unpartitioned** — no partition filter can prune; cost is controlled only by column projection.
- Current contents are **call-tracking** conversions (see `conversion_type` domain). Treat "call-only" as an
  observed snapshot property, not a guaranteed schema constraint.

## Cost & partitioning notes
- **Unpartitioned, unclustered, no TTL.** Physical backing (bq show, 2026-07-29) = 338,184,960 bytes
  (~0.32 GB / ~323 MB), 736,896 rows.
- No partition to filter -> the only cost lever is **column projection**. Measured dry-runs (2026-07-29):
  `SELECT *` = **338.18 MB**; `SELECT order_id` (one narrow col) = **9.92 MB** (~34x cheaper). A
  `WHERE time >= '<date>'` filter does not reduce bytes (no partitioning). **Always list explicit
  columns; avoid `SELECT *`.**
- Whole table is small enough to full-scan cheaply, but still project only the columns you need.

## Example queries
```sql
-- Dedup to one row per offline conversion (guid) for one advertiser
SELECT guid,
       ANY_VALUE(advertiser_id) AS advertiser_id,
       ANY_VALUE(order_id)      AS order_id,
       ANY_VALUE(time)          AS conversion_time,
       ANY_VALUE(order_amt)     AS order_amt,
       ANY_VALUE(conversion_type) AS conversion_type
FROM `ber_stg.offline__conversions_final`
WHERE advertiser_id = <AID>
GROUP BY guid
```
