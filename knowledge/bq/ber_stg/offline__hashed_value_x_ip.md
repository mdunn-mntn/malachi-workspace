# ber_stg.offline__hashed_value_x_ip

## Purpose
Intermediate stage of the **offline-conversion ingestion pipeline** (`ber_stg.offline__*`). An advertiser uploads offline conversions (CRM orders, call-tracking events) keyed by a **hashed customer identifier** (`hashed_value`, e.g. SHA-256 of email/PII). This table takes each uploaded conversion event and **fans it out to every IP address the MNTN identity graph resolves that hashed value to** — the `hashed_value x IP` expansion the name refers to. Downstream stages then match those IPs against served impressions to attribute the offline conversion.

**Non-canonical / pipeline-internal** — a rebuilt rolling snapshot, not a system of record. For finished offline conversions use the terminal stage `ber_stg.offline__conversions_final` (adds `channel_id`, resolved `guid`/`event_time`) which flows into canonical `summarydata.conversions` / `logdata.conversion_log`. Reach for this table only to debug why a specific hashed value did/didn't resolve to an IP, or to inspect identity-partner coverage.

Pipeline neighbours: `offline__eligible_uploads` (per-upload config) -> `offline__conversion_signal_orders` (parsed orders, `hashed_values` ARRAY + one IP) -> **`offline__hashed_value_x_ip`** (IP fan-out, this table) -> `offline__impressions_unfiltered` (hashed_value -> served impressions) -> `offline__conversions_final` (attributed, with channel).

## Grain & keys
- **Grain:** one row per **offline-conversion event x identity-resolved IP**. A single conversion event (`upload_id` + `hashed_value` + `order_id` + `time`) produces one row for each IP the graph maps the hashed value to.
- **Effective key:** `(upload_id, hashed_value, order_id, time, ip)`. No single-column primary key; `hashed_value` and `ip` are both many-per-row-group.
- **Fan-out (2026-07-19 snapshot):** 11,238 rows from 1,840 distinct `hashed_value` (~6 IPs per customer) across 5,217 distinct IPs, 15 uploads, 15 advertisers. `ip IS NULL` count = 0 — only successfully-resolved rows survive this stage (unresolved hashed values are dropped here, not carried as NULL).

## Column meanings (only the non-obvious ones)
- **`hashed_value`** — the hashed customer identifier from the advertiser's upload (64-hex SHA-256 in samples). The join key into the identity graph; repeated across rows, one per resolved IP.
- **`ip`** — an IP address the identity graph maps `hashed_value` to. This is the fan-out column: multiple rows per hashed value. Never NULL in this stage.
- **`partner_id_list`** — a **STRING-encoded JSON array** (e.g. `"[2]"`, `"[2,3]"`, `"[1,2,3]"`), NOT a real ARRAY type. Lists the identity-resolution data-partner IDs that agreed on this hashed_value->IP mapping (partner 2 dominates; values seen 1/2/3). Parse the string before use.
- **`conversion_type`** — MIXED encoding, branch on `conversion_source_id`: an internal **numeric code as a string** (`"-102"`) for CRM/order conversions (source 31); **human-readable labels** (`"Answered Call"`, `"Missed Call"`, `"Voicemail w/ Transcript"`, `"Abandoned Call"`, or NULL) for call-tracking conversions (source 37).
- **`conversion_source_id`** — the offline conversion source/integration: `31` = CRM/order upload (dominant), `37` = call-tracking partner.
- **`conversion_window`** — INT64 **DURATION in MICROSECONDS**, NOT an epoch timestamp. `2592000000000` = 30 days (2,592,000 s x 1e6; the default); `5184000000000` = 60 days. Divide by 1e6 for seconds.
- **`order_amt`** — FLOAT64 conversion/order value expressed in `order_curr`, carried from the upload. Present even when `order_id = "0"`.
- **`order_id`** — advertiser's order identifier; `"0"` is a placeholder for conversions with no order id (e.g. call events).
- **`order_curr`** — currency code, `"usd"` for order conversions; empty string `""` for call conversions that carry no monetary value.
- **`time`** — TIMESTAMP of the conversion event (UTC). **`hour`** — DATETIME truncation of the event to the hour (tz-naive).
- **`start_date` / `end_date`** — the upload's lookback/conversion-window bounds (from `offline__eligible_uploads`), repeated on every row of the same upload — they describe the batch, not the individual event.
- **`customer_email_hashes`** — STRING; **entirely NULL** in current data. **`hashed_values_key`** — STRING grouping key for multi-hash records; NULL for ~99% of rows (77 / 11,238 populated). Don't rely on either.
- **`upload_id`** — the offline-conversion upload batch id (1:1 with an `offline__eligible_uploads` config row). **`advertiser_id`** — MNTN advertiser (each upload maps to one advertiser).

## Joins & relationships
- **`upload_id` -> `ber_stg.offline__eligible_uploads`** (partner grain: **1:1 per upload** — dates, window, source, currency, timezone) and **`offline__uploads_processed`** (1:1 per upload run — match counts). Safe, no fan-out.
- **`hashed_value` -> `ber_stg.offline__conversion_signal_orders.hashed_values`** (that column is an `ARRAY<STRING>`, so **UNNEST** it; upstream parsed-order rows — 1:N) and **`offline__impressions_unfiltered.hashed_value`** (**1:N** — a customer has many impressions). Fan-out on both sides.
- **`ip` -> attribution tables** (`logdata.cost_impression_log`, visits, bidder): **HIGH fan-out** — an IP maps to many impressions over any date range, and multiple households sit behind one IP. Never join on `ip` without a tight date + `advertiser_id` filter.
- **`advertiser_id` -> `bronze.integrationprod` advertisers/campaigns** (N:1). Filter `deleted=FALSE AND is_test=FALSE` on the dim side.
- **Feeds forward** -> `offline__conversions_final` (terminal staging: attributed offline conversions with `channel_id`), which is the input to canonical `summarydata.conversions` / `logdata.conversion_log`.

## Gotchas
- **Non-canonical intermediate.** Rebuilt each pipeline run; only a short rolling window is present (2026-07-13 -> 2026-07-20 in the snapshot, ~7 days) even though the physical table has **no TTL set**. Do NOT treat as a historical source — for durable offline conversions use `offline__conversions_final` -> `summarydata.conversions`.
- **Row count != conversion count.** Each event fans out to ~6 IPs — never `COUNT(*)` rows as conversions; dedupe to `(upload_id, hashed_value, order_id)` or aggregate before counting.
- **`partner_id_list` is a STRING**, not an ARRAY — parse it before filtering/unnesting.
- **`conversion_type` is polymorphic** (numeric code vs text label) — key off `conversion_source_id`.
- **`conversion_window` is microseconds** (a duration), easy to misread as an epoch.
- **`customer_email_hashes` fully NULL, `hashed_values_key` ~99% NULL** — don't build logic on them.
- Physical table is **not partitioned and not clustered**, so no partition pruning is possible — but it is tiny (~1.9 MB), so full scans are cheap.

## Cost & partitioning notes
- Physical (`sqlmesh__ber_stg.ber_stg__offline__hashed_value_x_ip__4213723168`) is a plain **non-partitioned, non-clustered TABLE**: `numRows` 11,238, `numBytes` 1,984,606 (~1.9 MB), no TTL. `timePartitioning` and `clustering` are both null on the real physical (not SQLMesh staleness — the byte/row counts are populated and consistent). There is **no partition column to filter**.
- **The one lever is column selection**, not partitioning. Dry-run figures (2026-07-19), labeled by column set:
  - `SELECT *` (all 17 cols): **1,984,606 bytes** (full table).
  - `SELECT ip` (one narrow col): **170,047 bytes** (~12x cheaper).
- To narrow logically (won't reduce bytes without clustering, but the table is tiny) filter on `advertiser_id` / `upload_id`.

## Example queries
```sql
-- Distinct offline conversions for an advertiser (dedupe the IP fan-out)
SELECT upload_id, hashed_value, order_id, ANY_VALUE(order_amt) AS order_amt,
       COUNT(DISTINCT ip) AS resolved_ips
FROM `ber_stg.offline__hashed_value_x_ip`
WHERE advertiser_id = 37085
GROUP BY upload_id, hashed_value, order_id;
```
