# ber_stg.unstable__conversions_pre_change

## Purpose
Non-canonical BER (backend-reporting) **staging / change-impact** snapshot. It holds attributed
conversions **recomputed under the PRE-change attribution logic** for a set of tracked "changes"
(`change_id`). Every row is stamped `batch_source = 'pre_change'`. It is the *before* side of a
before/after comparison against its sibling view `ber_stg.unstable__conversions_post_change` (the
*after* snapshot) — used to measure how an attribution/config change moves attributed conversions,
order counts, and revenue. **Do not treat this as a source of truth for conversions.** The canonical
attributed-conversion table is `summarydata.conversions` (this view shares nearly its entire schema,
adding only the `change_*` / `batch_*` snapshot columns). Reach for this table only for
change-impact / QA analysis, never for reporting conversion totals.

## Grain & keys
- **Grain:** one row per **pre-change attributed conversion, per `change_id`**. Verified on the
  2026-07-01→20 slice: 53,743 rows vs 37,941 distinct `guid`, 41,618 distinct `order_id`, 662
  distinct `change_id`. A user (`guid`) can convert multiple times, so no single column is a key.
- **No clean unique key.** Closest composite `(change_id, order_id)` = 52,244 distinct vs 53,743
  rows — still not unique (623 rows have NULL `order_id`; 42 have NULL `guid`). Dedup defensively if
  you need one row per conversion.
- **Snapshot key:** `change_id` groups the rows belonging to one tracked change; `advertiser_id` +
  `change_id` are the physical cluster keys.

## Column meanings (only the non-obvious ones)
**Epoch units differ per column — verified against their TIMESTAMP anchors:**
- `time` — TIMESTAMP the conversion is attributed at; **partition column**. `epoch` = `UNIX_MICROS(time)`
  → **microseconds** (verified: epoch 1784130588332975 = t_us 1784130588332975 exactly).
- `event_time` / `event_epoch` — the touch/qualifying event timestamp; `event_epoch` = `UNIX_MICROS(event_time)`
  → **microseconds** (full µs precision).
- `impression_time` / `impression_epoch` — impression timestamp; `impression_epoch` → **microseconds**
  but only millisecond precision (value = `UNIX_MILLIS(impression_time) * 1000`, trailing `000`).
- `change_time` / `change_epoch` — when the tracked change was applied; `change_epoch` = `UNIX_SECONDS(change_time)`
  → **seconds** (10-digit).
- `batch_epoch` — snapshot/batch build time, **seconds** (10-digit `UNIX_SECONDS`).
- `conversion_day` — INT, **1-indexed attribution day** = `floor(hours(time − event_time)/24) + 1`
  (day 1 = same-day conversion). NOT an epoch/date; small integer.
- `elapsed_time` (INTERVAL) = `time − event_time`; `impression_elapsed_time` = `time − impression_time`;
  `recency_elapsed_time` (INTERVAL) = recency of the qualifying signal.

**Encodings / NULL semantics:**
- `batch_source` — snapshot tag, uniformly `'pre_change'` in this view (the sibling post view carries `'post_change'`).
- `change_id` — INT id of the tracked change (662 distinct in the July slice; values ~65,000–66,600). Cluster key.
- `conversion_type` — **free-text advertiser-defined label** (e.g. `Purchase`, `Lead`, or raw URL paths),
  with dominant sentinel `'-101'` for unnamed/default conversions (40,770 of 53,743 in the slice).
- `conversion_source_id` — mostly `23` (dominant), also `61`. `attribution_model_id` ∈ {1..15};
  `attribution_model_type_id` ∈ {1,2,3,4}.
- `order_amt` (NUMERIC) — order value; never NULL (defaults to 0 when absent), median ≈ $69.71.
  `order_curr` — **dirty**: {`USD`, `usd`, `N/A`, empty}; normalize case and treat non-USD as unreliable.
- `is_pa` / `pa_model_id` / `is_competing` — post-attribution / competing-conversion flags carried from the
  attribution engine; `is_cross_device`, `click`, `click_through`, `disputed`, `conversion_assist`,
  `from_verified_impression` are the standard conversions booleans.
- `ip` vs `impression_ip` — resolved conversion IP vs the IP on the credited impression (can differ on cross-device).

## Joins & relationships
- **`ber_stg.unstable__conversions_post_change`** (sibling VIEW, same grain) — the *after* snapshot.
  Compare pre vs post on the same `change_id` (+ conversion identity) to measure change impact. Both are
  per-`change_id` snapshots; a `change_id` present in one should be present in the other. Fan-out: joining
  on `change_id` alone is **N:N** (many conversions per change) — join on the full conversion identity.
- **`summarydata.conversions`** (canonical conversions, VIEW) — shares nearly the entire schema; this is the
  production source of truth. Use it, not this staging view, for conversion reporting.
- **`bronze.integrationprod.core_campaigns` / `campaigns`** via `campaign_id` (N:1, safe), and
  `advertisers` / `core_advertisers` via `advertiser_id` (N:1, safe). `group_id` → campaign_groups,
  `creative_id` → creatives (N:1). Standard dim lookups; filter dims `deleted=FALSE AND is_test=FALSE`.

## Gotchas
- **Non-canonical / non-authoritative.** Intermediate change-impact snapshot — never report conversion
  totals from it. Numbers here reflect *recomputed* pre-change attribution, not what was billed/reported.
- **No unique key.** `guid` and `order_id` repeat; dedup on `(change_id, order_id, impression_id, event_epoch)`
  or similar if you need one row per conversion.
- **`batch_source` is a constant** here (`'pre_change'`) — the pre/post distinction is the *view*, not a filter.
- **Mixed epoch units** (µs on `epoch`/`event_epoch`/`impression_epoch`, seconds on `change_epoch`/`batch_epoch`) —
  never assume a shared unit across the `*_epoch` columns.
- **`order_curr` is dirty** and `conversion_type` is free-text — do not group on them without cleaning.
- **Accumulating, no TTL.** Data spans 2026-01-31 → present and keeps growing (expirationTime = none); an
  unfiltered scan grows over time.

## Cost & partitioning notes
- **Partition = `time` (DAY), not required but always filter it.** Cluster = `[advertiser_id, change_id]` —
  add `advertiser_id` / `change_id` predicates to prune within a day.
- Empirical partition proof (`SELECT time`, one column): no filter → **11,894,696 B (~11.9 MB)**;
  `WHERE time >= '2026-07-01'` → **429,944 B (~0.43 MB)**. Same column set, ~28x reduction — confirms `time` is the partition.
- `SELECT *` for `time >= '2026-07-01'` (~20 days) → **119,884,727 B (~120 MB)** (all-columns figure — do
  not compare to the one-column numbers above).
- Physical backing: `numBytes` = 3,357,989,781 B (~3.36 GB), `numRows` = 1,578,959 (whole table, all columns; 2026-07-29).
- The one filter to always apply: `WHERE time >= '2026-07-01' AND time < '2026-07-08'` (a bounded date range on the partition), plus a `change_id` predicate when analyzing a specific change.
