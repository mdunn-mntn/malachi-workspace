# logdata.impression_log

## Purpose
The impression-level serve log: one row per ad impression MNTN served/rendered, across
**both display and CTV**. Reach for it to trace an impression back to its bid/auction, to
recover the geo/device/IP context of a served ad, or as the **linkage source** that
`cost_impression_log` checks against (a CIL row is `unlinked=FALSE` only when its
`impression_id` is found here). It is also the counterpart to `event_log` for
**non-viewable display** impressions, which appear ONLY here (never in `event_log`).

Note the scope: it is served impressions, **not** "all bids won or lost." (An older
`data_knowledge.md` line calling it "all bids won or lost" describes the raw Greenplum
source semantics, not this served-impression silver view.)

## Grain & keys
- **Grain:** one row per served ad impression. `ad_served_id` is the ONLY 1:1 unique key —
  verified 203,528,125 distinct `ad_served_id` = 203,528,125 rows on 2026-07-15 (100%), and
  ~169.7M/169.7M on 2026-07-10. Exact counts drift day-to-day (3-hour lookback restate) —
  treat all row/distinct counts here as **approximate**.
- **Primary key / join column:** `ad_served_id` (STRING) — unique per impression; the key
  to `summarydata.visits` / `ui_visits` / conversions.
- **Auction/bid key:** `ttd_impression_id` (= `cost_impression_log.impression_id` = `bid_logs.auction_id`).
  **NOT unique here** — on 2026-07-15, 164,916,750 distinct values over 203,528,125 rows
  (~19% collision, 1.23 rows/value; ~1,357 NULL). It is a many-to-one bid key, not a PK, so
  any join keyed on `ttd_impression_id` fans out on the impression side (see Joins). Use
  `ad_served_id` when you need a 1:1 impression identity.

## Column meanings (only the non-obvious ones)
- **`epoch`** — **MICROSECONDS** since the Unix epoch, i.e. `epoch = UNIX_MICROS(time)`
  **exactly** (verified 2026-07-15: 0 rows where `epoch != UNIX_MICROS(time)`; identical µs
  unit in the pre-2026 history branch). `epoch` and `time` therefore carry **identical
  precision** — `epoch` is NOT finer. `time` itself retains sub-second precision on ~99.9% of
  rows (203,323,514 / 203,528,125 non-whole-second on 2026-07-15; e.g. `epoch =
  1783684801439000` ↔ `time = 2026-07-10 12:00:01.439`). Prefer `time` (it prunes the
  partition; `epoch` does not). **Prose drift:** `data_catalog.md`/`data_knowledge.md` call
  epoch "seconds" — WRONG for this silver view; `TIMESTAMP_SECONDS(epoch)` overflows. Divide
  by 1e6 for seconds, or use `TIMESTAMP_MICROS(epoch)`.
- **`time`** — impression TIMESTAMP in **UTC**. This is the **partition column** (see Cost).
- **`ip` vs `ip_raw`** — in the CURRENT silver view these are **identical**: the view maps
  `ip AS ip_raw` in both UNION branches, so `ip_raw` is a literal copy of `ip` (verified
  169,737,896/169,737,896 equal, 0 NULLs on 2026-07-10). Do NOT treat `ip_raw` as a distinct
  "pre-enrichment" IP here — that older `data_catalog.md` distinction is stale for this view.
  `ip` is never NULL, but **~13.9% are internal NAT (`10.x`) addresses** (display especially),
  which are useless for identity — for the public device IP use `bid_ip` (or join `bid_logs`).
- **`bid_ip`** — public IP at bid/auction time; the **gold IP-lineage column** (bare IP, no
  CIDR suffix, unlike `event_log.ip` pre-2026). ~2.1% NULL on 2026-07-10. One of four tables
  carrying denormalized `bid_ip` (`event_log`, `impression_log`, `viewability_log`, `click_log`);
  used in the COALESCE fallback when `bid_logs` (10-day TTL) is purged.
- **`original_ip`** — pre-proxy / pre-iCloud-Private-Relay raw TCP-connection IP (from the
  `x-forwarded-for` header). MNTN overrides it with the more accurate device IP in `ip`.
  Audit/debug only — use `ip`/`bid_ip` for analysis.
- **`original_aid` / `original_cid`** — the ORIGINAL (pre-remap) advertiser / campaign id.
  Equal to `advertiser_id` / `campaign_id` for 99.98% of rows; they differ only for the small
  remapped population (28,526 / 169.7M on 2026-07-10). **PSA impressions** are the canonical
  case: filter/inspect `original_cid` to confirm PSA volume for a campaign (PSAs are served
  when no paid ad is available and are excluded from `cost_impression_log`; advertiser_id 90
  is the PSA advertiser and PSAs are served to holdout IPs on purpose).
- **`advertiser_id`** — **populated** (100% non-null, 1,523 distinct AIDs on 2026-07-10).
  **Prose drift:** `data_knowledge.md` claims "impression_log does not [have advertiser_id]"
  — false for current data; it does. (CIL is still cheaper for single-advertiser pulls
  because it is a smaller table, but the "no advertiser_id" premise is wrong.)
- **`is_baseline`** — BOOL flag; empirically **FALSE for all** rows on 2026-07-10 (legacy /
  rarely set). Don't rely on it as a filter without confirming it's populated for your window.
- **`cache_buster`** — BOOL flag; likewise **FALSE for all** rows on 2026-07-10.
- **`user_agent`** — JSON (parsed UA), not a string. **`device`** — device string; `browser` — browser name.
- **`cpm`** BIGNUMERIC / **`cpi`** INT64 — cost per mille / per impression (cost fields;
  authoritative spend lives in `cost_impression_log`, which excludes PSAs).

## Joins & relationships
- **Impression → visit → conversion:** `ad_served_id` (unique here) → `summarydata.visits` /
  `ui_visits` / `ui_conversions`. Because it is unique, this side never fans out.
- **Impression → auction/bid:** `ttd_impression_id = cost_impression_log.impression_id`
  (100% match on `bid_ip`, per TI-650) `= bid_logs.auction_id`.
  **Fan-out warning (two sources):**
  1. `ttd_impression_id` is **non-unique within `impression_log` itself** (~19% collision,
     1.23 rows/value on 2026-07-15). A `cost_impression_log → impression_log` join on
     `impression_id = ttd_impression_id` (or any code that assumes 1:1 and dedups on that key)
     fans out ~15–19% on the impression side. If you need one impression row per CIL row,
     key/dedup on `ad_served_id`, not `ttd_impression_id`.
  2. `bid_logs` also has **multiple rows per `auction_id`** (one per eligible campaign). When
     joining `impression_log.ttd_impression_id = bid_logs.auction_id`, dedup:
     `QUALIFY ROW_NUMBER() OVER (PARTITION BY il.ad_served_id ORDER BY b.time ASC) = 1`.
- **CIL linkage:** `cost_impression_log.unlinked = FALSE` ⇔ the CIL row's `impression_id` was
  found in `impression_log`. Late/missing impressions here → CIL `unlinked = TRUE`, null `ad_served_id`.
- **Non-viewable display:** appears ONLY here, never in `event_log` (which holds only viewable
  CTV `vast_impression` events). For IP lineage use `COALESCE(event_log.bid_ip, impression_log.bid_ip)`.
- **Trace order** (Zach, confirmed): CTV `clickpass → event_log → win_logs → impression_log → bid_logs`;
  display non-viewable `clickpass → impression_log → win_logs → bid_logs` (impression_log comes
  BEFORE win_logs for display — opposite of CTV).
- Dimension joins: `advertiser_id → core.advertisers`, `campaign_id → core.campaigns`,
  `creative_id → core.creatives`, `metro_id` = Nielsen DMA code (bridge to `summarydata.metros`).

## Gotchas
- **`epoch` is microseconds, not seconds** (see column meanings) — the single most likely
  footgun. Divide by 1e6, or just use `time`.
- **`ip_raw` is a duplicate of `ip`** in this view — don't waste a column believing it holds
  the raw pre-enrichment IP.
- **~14% of `ip` are internal `10.x` NAT** — cross-table IP matching on `ip` silently loses
  those rows; prefer `bid_ip`.
- **`ttd_impression_id` is NOT a primary key** — it repeats (~15–19% of rows share a value).
  Only `ad_served_id` is 1:1. Joins/dedups that assume `ttd_impression_id` is unique fan out
  (see Grain & keys, Joins).
- **Late-arriving data:** the incremental pipeline uses a **3-hour lookback** on the source;
  rows arriving later need a manual restate and won't appear on normal runs.
- **UTC:** `time` is UTC — convert if comparing to Arizona-time (ATZ) UI/reporting numbers.
- **Not a spend source:** spend/PSA-exclusion logic lives in `cost_impression_log`; row counts
  here include PSAs and thus won't match customer-charged impression counts.
- **Two-branch UNION (split at 2026-01-01):** the view stitches a recent raw branch and a
  history branch (see below). A single `time` filter prunes both; querying `epoch` does not prune.
- **Future partition-hole risk:** the raw branch physical has a **365-day partition expiration**
  (`expirationMs 31536000000`); history is frozen at `date_column <= 2025-12-31` (permanent, no
  expiration). Around **2027-01** the earliest 2026 raw partitions begin expiring while history
  stays capped at 2025-12-31 → a **coverage gap** opens in early 2026 unless the history branch
  is extended forward. Watch for this before running long cross-year lookbacks in 2027+.

## Cost & partitioning notes
- **Partition column = `time`** (TIMESTAMP, day-partitioned), cluster = none.
- **Empirical dry-run estimates (2026-07-17; each figure labeled with its column set — they are
  NOT comparable across different column sets):**
  - Full view `SELECT *` (no filter): ≈ **115 TB**.
  - One day, `SELECT *`, filtered on `time`: ≈ **79 GB** (prunes to 1 partition).
  - One day, the 7-col example set below, filtered on `time`: ≈ **20 GB** (prunes).
  - One day, single narrow column (`epoch`), filtered on `time`: ≈ **3.3 GB** (prunes).
  - One day, the **same 7-col set** but filtered on `epoch` instead of `time`: ≈ **27 TB**
    (NO pruning — `epoch` is not the partition key, so it scans those 7 columns across every
    partition of both branches; ~1,300× worse than the identical 7-col `time`-filtered query).
  **Rule:** always bound on `time`, never on `epoch`. Use a **half-open** interval to avoid
  double-counting the boundary instant: `WHERE time >= TIMESTAMP('start') AND time < TIMESTAMP('end')`.
- `require_partition_filter` is **not enforced** at the view level (a no-filter dry run
  validates), so nothing stops an accidental ~115 TB full scan — discipline required.
- **The `physical_table` front-matter names the inner UNION view** (`sqlmesh__logdata.logdata__impression_log__1757027260`),
  which is a VIEW→VIEW→upstream chain — so SQLMesh/INFORMATION_SCHEMA report `partition:None`,
  `numRows:0`, `clustering:None` for it. Those are stale artifacts, not the truth; the partition
  was confirmed empirically. The **real backing physicals** (with actual rows/bytes/partitioning) are:
  - `dw-main-bronze.sqlmesh__raw.raw__impression_log__1161949256` — TABLE, partition `time` (DAY),
    **365-day expiration** (`expirationMs 31536000000`); ~31.7 TB, ~69.2B rows (2026-07-17).
  - `dw-main-bronze.history.impression_log_physical` — TABLE, partition `time` (DAY), **no
    expiration** (permanent); ~101.6 TB, ~215.7B rows (2026-07-17).
  Front-matter `approx_logical_bytes` (133 TB) = the sum of these two physicals' logical bytes.
- **View composition** (resolved 2026-07-17): `logdata.impression_log` = **UNION ALL of**
  - `raw__impression_log__1161949256` WHERE `CAST(time AS DATE) >= '2026-01-01'` (recent branch)
  - `history.impression_log_physical` WHERE `date_column <= '2025-12-31'` (history branch)
  Both physicals are partitioned on `time`, so a user-supplied `time` filter prunes **both**
  branches (the history branch's inner `date_column` predicate does not prune, but the outer
  `time` filter does). Both branches project `ip AS ip` and `ip AS ip_raw` (hence the duplicate).
  Cross-year queries span both branches transparently via `time`.
- Single-IP-across-history scans are extremely expensive (partitioned by time, not IP; no IP index).

## Example queries
```sql
-- always bound on the time partition (UTC); half-open interval (no boundary double-count)
SELECT ad_served_id, advertiser_id, campaign_id, ip, bid_ip, epoch, time
FROM `logdata.impression_log`
WHERE time >= TIMESTAMP('2026-07-10') AND time < TIMESTAMP('2026-07-11')
LIMIT 100;

-- epoch is MICROSECONDS: convert to a timestamp
SELECT ad_served_id, TIMESTAMP_MICROS(epoch) AS event_ts_us, time
FROM `logdata.impression_log`
WHERE time >= TIMESTAMP('2026-07-10') AND time < TIMESTAMP('2026-07-11')
LIMIT 100;
```
