# logdata.icloud_vv_log

## Purpose
The **iCloud Private Relay** verified-visit log — the `clickpass_log` analog for Apple iCloud Private Relay traffic (visits whose IP is an Apple relay egress IP, which need special handling for geo-targeting and IP lineage). Same VV shape as `clickpass_log`: MNTN served an impression → an Apple-relay user visited the advertiser site within the lookback window → the pixel matched the visit back to the impression (`ad_served_id`). Reach for it to count/trace iCloud-relay verified visits, or to isolate the relay-IP subset of attributed traffic. Small and self-contained: a single-source view over one bronze physical table, ~165K rows total (vs `clickpass_log`'s ~1.4B). This is **NOT** one of `clickpass_log`'s three UNION branches — iCloud-relay VVs are logged in a separate physical stream.

## Grain & keys
- **Grain:** one row per iCloud Private Relay verified-visit (view-through) event. Event-grain, same as `clickpass_log`. No column is a strict unique row id.
- **Key(s) / join columns:** `ad_served_id` (UUID → the winning ad impression, **last-touch**; always populated, ~25,198 distinct over 25,541 rows on 2026-07-05→19 → ~98.7% distinct, near-unique but NOT a strict row key; live table, absolute counts drift) is the primary join key back to impression tables. `guid` = the **page-view GUID** here (aliased from source `page_view_guid`, NOT the cookie GUID — see column meanings); `guid == page_view_guid` for 100% of rows. `original_guid` carries the source cookie GUID.

## Column meanings (only the non-obvious ones)
- **`guid`** — the **page-view GUID**, NOT the user cookie GUID. The view aliases source `page_view_guid AS guid` (and also `AS page_view_guid`), so **`guid == page_view_guid` for 100% of rows** (25,541/25,541 on 2026-07-05→19). This DIFFERS from `clickpass_log`, where `guid` = user cookie ID and `page_view_guid` is a distinct page-view signal GUID. ~6,628 distinct `guid` over 25,541 rows → several event rows per page view.
- **`original_guid`** — the **source cookie/event GUID** (the view aliases source `guid AS original_guid`). Always populated; differs from `guid` (page-view GUID) in ~61% of rows (10,005/25,541 equal). More granular than `guid`: ~13,822 distinct over 25,541 rows.
- **`time` / `epoch`** — VV redirect (attribution) timestamp. **`epoch` is MICROSECONDS**, and here `epoch = UNIX_MICROS(time)` holds **exactly, 100%** (25,541/25,541 on 2026-07-05→19) — unlike `clickpass_log`, where that identity is true only on one branch. `time` (= source `event_time`) is the partition column.
- **`impression_time` / `impression_epoch`** — impression that triggered this VV. **`impression_epoch` is MICROSECONDS**; the view derives `impression_time = TIMESTAMP_MICROS(impression_epoch)`, and `impression_epoch = UNIX_MICROS(impression_time)` holds 100%. Always populated. The `time − impression_time` gap is short for the vast majority (p50 ~0.4 day, p95 ~6.4 days, p99 ~12.3 days) with a very thin tail out to ~110 days (only 1/25,541 rows >90d, 9 rows >30d) — a lookback window, NOT capped at ≤30d, but long gaps are rare.
- **`ip` / `ip_raw`** — **identical by construction and 100% NON-NULL.** The view aliases the source `ip` column into BOTH `ip` and `ip_raw` (`icloud_vv.ip AS ip_raw`, `icloud_vv.ip AS ip`), so `ip == ip_raw` for every row. This is an **Apple iCloud Private Relay egress IP**, which needs special handling for geo-targeting (relay IPs geolocate to Apple's relay region, not the user). The `ui_visits` ip-vs-ip_raw split does NOT apply. (The bronze physical also has a separate `impression_ip` column, but the view does NOT surface it.)
- **`additional_parameters`** — **always NULL.** The view hardcodes `CAST(NULL AS STRING)` (25,541/25,541 NULL). Do not use.
- **`is_control_group`** — holdout/control flag; observed **all FALSE** in sampled windows (relay VVs not marked into holdout).
- **`is_new`** — new-to-brand flag set by the **client-side JS pixel** (same semantics as `clickpass_log`), not a DB lookup. ~55% true in sample.
- **`is_cross_device`** — ad served on one device, visit on another.
- **`first_touch_ad_served_id`** — first-touch impression UUID; **~66% NULL** (16,948/25,541) — same real-time-lookup gap as `clickpass_log`, populated at write time with no backfill.
- **`ga_tracking_ids` / `ga_client_ids`** — comma-joined STRINGS (the view `STRING_AGG`s the underlying repeated fields), not single values.
- **`click_elapsed`** — **MICROSECONDS since impression, NOT milliseconds.** Equals `TIMESTAMP_DIFF(time, impression_time, MICROSECOND)` exactly (25,541/25,541 on 2026-07-05→19). Treating it as ms (e.g. `/1000` → seconds) is 1000× wrong; its median (~8.6h) and max (~40 days) only make sense as microseconds.
- **`view_elapsed`** — **MICROSECONDS, not ms, and unreliable as a clean "since last view" duration.** Always ≤ `UNIX_MICROS(time)` (25,541/25,541); in ~51% of rows (12,981/25,541) it equals `UNIX_MICROS(time)` **exactly** — i.e. an absolute epoch-micros timestamp (no prior view / elapsed-since-epoch) — and is a smaller micros delta in the rest. Do not consume it as a plain elapsed-since-last-view value without handling the absolute-timestamp fallback.
- **`viewable`** — impression viewability. **`blocked_source`** — IVT/fraud block reason. **`attribution_model_id`** — attribution model used. **`user_agent`** = source `user_agent_string`.

## Joins & relationships
- **`ad_served_id` → `event_log` / `cost_impression_log`** (CAST to STRING) for the impression's `bid_ip` / VAST IP. Partner grain: `event_log` / `cost_impression_log` are impression-grain (one row per served impression); `ad_served_id` is near-unique here so the join is ≈1:1 in the safe direction. Size the lookback to the impression→visit gap: p99 is ~12 days, p95 ~6 days, so ~2 weeks covers the vast majority; the tail runs to ~110 days but is extremely thin (only 1/25,541 rows >90d), so only widen to that if you must capture the rare long-gap rows — do NOT default to a 110-day (or the old ≤30d) window. Fan-out risk low.
- **`ad_served_id` → `ui_visits`** (CAST STRING) / **`guid`/`page_view_guid` → page-view tables** as in `clickpass_log`. `ad_served_id` is not a strict unique key (a few impressions earn >1 visit row) → treat as low fan-out, not 1:1.
- **Relationship to `clickpass_log`:** this is a **separate, parallel VV stream**, not a subset that lives inside `clickpass_log`. `clickpass_log` UNIONs three physicals (`raw.clickpass_log` + `raw.competing_vv` + `history.clickpass_log_physical`); `icloud_vv_log` resolves to a **fourth** physical (`raw.icloud_vv`) that is NOT in that UNION. Do NOT assume iCloud-relay VVs are also present in `clickpass_log` without verifying; treat this as the relay-IP companion log.

## Gotchas
- **Single-source view, not a UNION.** Resolves `logdata.icloud_vv_log` → `sqlmesh__logdata.logdata__icloud_vv_log__1701206424` → **`dw-main-bronze.sqlmesh__raw.raw__icloud_vv__2252688389`** (one physical TABLE). Unlike `clickpass_log`, no history/competing branches.
- **`guid` is the page-view GUID, not the cookie GUID** (source columns are swapped relative to `clickpass_log`): `guid` = source `page_view_guid`, `original_guid` = source `guid`. Joining `guid` expecting a cookie ID will mis-match; use `original_guid` for the cookie GUID.
- **`ip` == `ip_raw`** (both aliased from source `ip`) and both are **Apple relay IPs** — special geo handling required; the physical's `impression_ip` is not exposed by the view.
- **`additional_parameters` is always NULL**; **`is_control_group`** observed always FALSE.
- **`epoch` and `impression_epoch` are MICROSECONDS**, not seconds. Here (unlike `clickpass_log`) `epoch = UNIX_MICROS(time)` is exact 100%.
- **View drops several physical columns:** the bronze physical also carries `impression_ip`, `publisher`, `app_bundle`, `first_touch_epoch`, `first_touch_campaign_id`, `is_tamp`, `url_prefix`, `url_suffix`, `x_device_map_size`, `campaign_channel_id`, `campaign_objective_id` — none surfaced by `logdata.icloud_vv_log`. Only document/query the AUTO:SCHEMA columns; drop to the physical if you need those.
- **90-day TTL** (`expirationMs=7776000000` on the physical, HOUR partitions on `event_time`) — no history beyond ~90 days; the whole view is only ~165K rows / ~512 MB.
- Partition filter is **not enforced** (`require_partition_filter=false`) but always filter `time` anyway.

## Cost & partitioning notes
- **Always filter `time`** (TIMESTAMP; = source `event_time`, HOUR-partitioned physical). Partition confirmed empirically by dry-run diff below.
- Labeled dry-run figures (2026-07-19):
  - `SELECT *` (all 33 cols), **no filter** (full view) → **486.7 MB** (464.2 MiB).
  - `SELECT *` (all 33 cols), **`time` ≥ last 7d** → **38.0 MB** — ~13× cheaper (partition prunes → `time` is the partition). (7-day figure varies with daily volume; the prune ratio is the stable fact.)
  - `SELECT ip` (1 narrow col), **`time` ≥ last 7d** → **0.30 MB** — ~127× cheaper than `SELECT *` same window (avoid `SELECT *`).
- Whole table is tiny (~165K rows, ~512 MB backing storage) so cost is never a concern here, but the partition-prune ratio and `SELECT *` penalty still hold.
- No clustering — an `advertiser_id` filter does not shrink the scan; only the `time` window does.
- Real backing storage (`bq show` numBytes of the single physical `raw__icloud_vv`): **511,593,507 bytes ≈ 0.51 GB**; ~164,590 rows.

## Example queries
```sql
-- One day of iCloud Private Relay VVs for an advertiser (always filter `time`)
SELECT ad_served_id, ip, guid, original_guid, is_cross_device, impression_time
FROM `logdata.icloud_vv_log`
WHERE time >= TIMESTAMP('2026-07-18') AND time < TIMESTAMP('2026-07-19')
  AND advertiser_id = 31921;

-- Count relay VVs per advertiser over a window (cost scales with the `time` window only)
SELECT advertiser_id, COUNT(*) AS icloud_relay_vvs
FROM `logdata.icloud_vv_log`
WHERE time >= TIMESTAMP('2026-07-01') AND time < TIMESTAMP('2026-07-19')
GROUP BY advertiser_id;
```
