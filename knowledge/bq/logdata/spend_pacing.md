# logdata.spend_pacing

## Purpose
Near-real-time, impression-grain spend feed used by the **BOS / pacing pipeline** to pace campaigns
against budget **before** the authoritative Cost Impression Log (CIL) is ready. The view self-scopes to
**yesterday + today only** (rows where `time >= CURRENT_DATE - 1 DAY`, scanning `dt >= CURRENT_DATE - 2 DAY`),
so it is a *live spend* surface — never a history table. Per Lizz (#data-platform, 2026-06-08): the
pacing pipeline reads `spend_pacing` on a ~24h live-spend lookback, then falls back to CIL; as long as
CIL issues resolve within 24h of onset, spend is unaffected. Reach for this table only for "how much has
campaign X spent in the last day"; for auditable or historical spend use `cost_impression_log`.

## Grain & keys
- **Grain:** one row per **won impression**. `impression_id` is unique across the whole view
  (verified 2026-07-19: `bwn` 72,459,571 rows = 72,459,571 distinct impression_id, exactly 1:1; `cil`
  5,902 rows = 5,902 distinct; the two sources are disjoint by construction — see `source`).
- **Key / join column:** `impression_id` (unique). Also joinable on `advertiser_id`, `campaign_id`,
  `creative_id`.
- **Two-source UNION (`source` column):**
  - `'bwn'` — near-real-time path built from bidder **win notifications** matched to impression logs
    (~72.5M rows/day, ~99.99% of the view).
  - `'cil'` — small backfill of impressions the live path missed, taken from `cost_impression_log`
    where the impression_id is `NOT EXISTS` in the `bwn` set (~5.9K rows/day).

## Column meanings (only the non-obvious ones)
- **`source`** — pipeline that produced the row: `'bwn'` (live bidder-win-notification path) or `'cil'`
  (gap-fill from `cost_impression_log`). Filter `source = 'bwn'` for the pure live meter; both together
  are the deduped total.
- **`time`** — impression/auction timestamp as a proper `TIMESTAMP` (no int epoch exposed). It is
  `COALESCE(impression-log time, bwn-derived time)`: **primarily the impression-log timestamp**
  (`impression__v1`/`vastimpression__v1`), falling back to the win notification's `auction_timestamp`
  only when the impression-log value is NULL; `cil`-source rows use `cost_impression_log.time`. The
  16-digit-values-are-microseconds / else-÷1000-from-nanoseconds unit-handling applies **only** to that
  `bwn` `auction_timestamp` fallback branch, inside the view; the surfaced column is a clean TIMESTAMP.
  Boundaries follow **CURRENT_DATE in UTC**: observed min = `CURRENT_DATE-1` 00:00 UTC.
- **`unlinked`** — BOOL, but **effectively always FALSE** here (0 of 72.5M rows on 2026-07-19). The `bwn`
  path INNER-JOINs impressions (so linked), and the `cil` path filters `unlinked IS FALSE`. The final
  `COALESCE(unlinked, TRUE)` fallback is defensive and does not trigger in practice. Do **not** add a
  `WHERE unlinked = FALSE` filter — it is redundant.
- **`media_cost`** — NUMERIC dollars, the un-marginned cost of the impression. On the `bwn` path
  (~99.99%) it is `SAFE_DIVIDE(win_price, 1,000,000)` — the /1e6 divisor implies `win_price` is in
  micro-dollars (inferred from the divisor, not from source-column metadata). On the `cil` path it is
  taken straight from `cost_impression_log.media_cost` (no division).
- **`media_spend` / `data_spend` / `platform_spend`** — BIGNUMERIC revenue components, each floored at
  `GREATEST(x, 0)`. Derived from `margin_history` (take_rate, partner_margin, data_margin) and CPM flags:
  - custom-margin (`has_cpm=FALSE`): media_cost is grossed up by `1/(1 - take_rate - partner_margin -
    data_margin)`, then split into the three components.
  - fixed-CPM (`has_cpm=TRUE`): `data_spend = target_cpi × data_margin` and `platform_spend =
    target_cpi × take_rate`, but `media_spend = target_cpi × (1 − take_rate − data_margin)` — the
    residual/complement, **not** `target_cpi` × a single rate.
  - **`data_spend` is nonzero only for CTV prospecting** (`has_tpa` = `channel_id = 8 AND objective_id = 1`);
    otherwise `data_margin` is forced to 0. Because these columns encode take-rate/margin math, treat
    them as **internal/sensitive** (see `feedback_take_rates_sensitive`).
- **`advertiser_id` / `campaign_id` / `creative_id`** — INT64. Defensive sentinels exist in the view
  (`-3`/`-4` for these ids, `'-4'` for impression_id) as `COALESCE` fallbacks when an id fails to resolve,
  but they were **not observed** in practice (0 negative advertiser_id on 2026-07-19). PSA advertiser
  **9090 is excluded** upstream, and win rows with `impression_timestamp = -1` are dropped.

## Joins & relationships
- **`cost_impression_log` (silver.logdata)** — same impression grain, join on `impression_id` (**1:1**).
  It is both the `'cil'` source rows *and* the historical/authoritative billing table. **Both sides are
  unique on `impression_id`** (spend_pacing verified 1:1; CIL verified unique too — 64,202,792 rows =
  64,202,792 distinct for 2026-07-17), so the join is genuinely 1:1 with no fan-out on either side.
  **Rule: for anything older than yesterday, join/query CIL, not spend_pacing.**
- **`bidder_win_notifications__v1` (dw-main-bronze.external, federated GCS)** — the `'bwn'` source. Raw
  wins are potentially many per impression; the view collapses to **1 row per impression_id** via an
  INNER JOIN to `DISTINCT ttd_impression_id` from the impression logs plus a `QUALIFY row_number()`
  dedup. Fan-out risk lives upstream; the published view is already deduped.
- **`impression__v1` / `vastimpression__v1` (bronze.external, federated)** — impression detail keyed by
  `ttd_impression_id`; used to confirm the win is *linked* (sets `unlinked = FALSE`) and to fill
  advertiser/campaign/creative.
- **`public_campaigns` (bronze.integrationprod)** — join on `campaign_id` (**1:1**) to read
  `channel_id`/`objective_id` and derive `has_tpa` (whether a 3P data margin applies).
- **`margins__margin_history` (silver.margins)** — time-ranged join on (advertiser_id, campaign_group_id,
  channel_id, partner_id) with `time_hr ∈ [start_hr, end_hr)`, deduped by `QUALIFY row_number()` per
  impression_id. Supplies take_rate/partner_margin/data_margin/has_cpm/target_cpi. **This is the main
  cost driver** — it resolves through a large stack of integrationprod margin/archive tables.
- **Downstream consumer:** the BOS / pacing service (24h live-spend lookback → CIL fallback).

## Gotchas
- **Only ever yesterday + today.** The view hard-codes `time >= CURRENT_DATE - 1 DAY`. A `WHERE time < …`
  clause can only narrow *within* that window; you cannot pull history from this view. Boundary rule (all
  UTC): min = `CURRENT_DATE-1` 00:00, max = now. Observed 2026-07-19 (run in the evening PT, when the UTC
  clock had already rolled to 2026-07-20): min_time `2026-07-19 00:00:00`, max_time `2026-07-20 01:15:08`
  — the dates are UTC boundaries, not the PT run-date.
- **Non-materialized VIEW.** Both `logdata.spend_pacing` and its physical
  `sqlmesh__logdata.logdata__spend_pacing__3576958514` are `type: VIEW` with `numRows: 0` /
  `numBytes: 0` — that is **true** (recomputed live each query), not stale SQLMesh metadata. There is no
  backing partitioned table, hence `partition_by: none`, no cluster keys, no TTL.
- **`unlinked` is always FALSE; PSA (adv 9090) already excluded** — don't re-filter for either.
- **`source` skew:** `'bwn'` ≈ 99.99%, `'cil'` ≈ tiny (5.9K/day). The `'bwn'` path is near-real-time
  (win notifications, ~1 min end-to-end); `'cil'` backfills stragglers not yet in the live path.
- **Spend columns are margin-derived and sensitive**; `data_spend` = 0 unless CTV prospecting
  (`has_tpa`). All three spend columns are floored at ≥ 0.
- **Slow AND expensive even for a COUNT:** the margin_history resolution makes this a join-heavy view — a
  simple `GROUP BY source` over ~72M rows burns **~17,500 slot-seconds (~5 slot-hours) and ~160 GiB
  billed** for ~2 min wall (measured 2026-07-19). Not a table to scan casually.

## Cost & partitioning notes
- **Dry-run drastically under-reads real cost here — do NOT budget from dry-run bytes.** The inputs are
  **federated external tables** (GCS parquet: `bidder_win_notifications__v1`, `impression__v1`,
  `vastimpression__v1`), so dry-run reports "accuracy unknown" and lands **~40x low**. Measured
  2026-07-19: the `source`-grouped `GROUP BY` **dry-runs at 4.03 GB but actually billed ~160 GiB
  (~172 GB) and burned ~17,500 slot-seconds (~4.9 slot-hours) / ~115 s wall — a ~42x under-read.** Use
  the dry-run figures below only as *relative* column-projection comparisons, never as an absolute budget.
- **No partition column to filter** — the view self-scopes to ~1–2 days, so the usual "always filter the
  partition" rule does not apply; there is nothing to add and no way to widen the window. The lever that
  *does* matter is **column projection** (avoid `SELECT *`) — dry-run figures (2026-07-19), *relative*
  only:
  - `SELECT *` (all 11 cols) → **12.46 GB** dry-run.
  - `advertiser_id, campaign_id, media_spend` (3 cols) → **6.67 GB** dry-run.
  - `source` only, grouped → **4.03 GB** dry-run (≈ **~160 GiB actually billed** — see above).
- `approx_logical_bytes` is `null`: no single backing storage (federated inputs + a live CIL scan), so a
  logical-bytes figure would be meaningless.
- **For historical / auditable spend, query `cost_impression_log`** (partitioned DAY on `time`), not this
  view.

## Example queries
```sql
-- Live spend by campaign for the current pacing window (yesterday + today only)
SELECT campaign_id,
       SUM(media_spend)    AS media_spend,
       SUM(data_spend)     AS data_spend,
       SUM(platform_spend) AS platform_spend
FROM `logdata.spend_pacing`
WHERE source = 'bwn'          -- pure live path; drop this to include the tiny cil gap-fill
  AND advertiser_id = @aid
GROUP BY campaign_id;
```
