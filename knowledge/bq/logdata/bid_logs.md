# logdata.bid_logs

## Purpose
Beeswax (external DSP) **per-bid decision log** — the record of every bid MNTN's Beeswax bidder made or considered, with the full RTB request context (geo, device, inventory, page, deal, floor) plus the bid economics (`bid_price_micros_usd`, `bid_floor_micros`, `bid_shade`, vendor fees). Reach for it to recover the **IP a bid was made against** (join key for TI-650-style VV/impression tracing), to audit bid pricing/shading, or to inspect what request signals the bidder saw at bid time. This is the Beeswax-native leg — distinct from the MNTN Rust-bidder tables (`bidder_bid_events`/`bid_logs_enriched`). For general advertiser bid-IP lookups this is the table to use; `bid_events_log` is near-empty (only adv 32167).

Live-verified 2026-07-19 (one recent day, 2026-07-10): 263.4M rows/day, epoch=microseconds, bid-grain confirmed.

## Grain & keys
- **Grain:** one row per **candidate campaign bid within an auction**. A single auction is eligible for multiple campaigns, so `auction_id` repeats — 2026-07-10 had 263.37M rows over 237.84M distinct `auction_id` (~1.11 rows/auction). **Bid-grain, NOT impression-grain** → it fans out against win_logs/impression_log (see Joins).
- **Key(s) / join columns:** `auction_id` (the RTB bid-request id; joins to `impression_log.ttd_impression_id`) + `campaign_id`/`line_item_id` to pin the specific candidate. `ip` is the bid IP (Beeswax `ip_address`). No natural single-column primary key; **dedup with ROW_NUMBER** (see Gotchas).

## Column meanings (only the non-obvious ones)
- **`epoch`** — bid time in **MICROSECONDS** since Unix epoch (view maps it from `bid_time_epoch_in_usecs`). Verified 2026-07-10: 16-digit values, `epoch ≈ UNIX_MICROS(time)` for 100% of rows (all within 1s). `time` (from `bid_time_utc`) is only **millisecond**-precision, so `epoch` carries the extra sub-ms digits and rarely equals `UNIX_MICROS(time)` exactly (only 0.1% exact-match) — use `epoch` when you need microsecond bid ordering; join on `time` for anything coarser. `time_of_week`/`user_time_of_week` are INT week-position codes, not epochs.
- **`time`** — bid timestamp (`bid_time_utc`), ms-precision. Effective co-prune column for the history leg (see Cost).
- **`ip` vs `ip_raw`** — in the **2026+ recent leg both are the SAME source column** (`ip_address`); verified equal on 98.7% of rows, the rest NULL (1.3%), and **zero `'0.0.0.0'` literals** on 2026-07-10. So the classic `NULLIF(ip,'0.0.0.0')` guard is defensive (for other tables/older data), not needed here. `ipv6_address` is the separate IPv6 field; hashed variants (`ip_address_hashed`, `ipv6_address_hashed`, `user_id_hashed`) are privacy hashes.
- **`bid_price_micros_usd` / `bid_price_micros`** — bid price in **micros** (1e-6 USD). `exchange_bid_price_micros_usd`, `bid_floor_micros`, `bid_shade_reduction_micros`, `campaign_revenue_amount_micros`, `line_item_revenue_amount_micros`, `total_cpm_vendor_fee_amount_micros`, `total_percent_vendor_fee_amount_micros` are all micros. `bid_shade` is a FLOAT multiplier (shade factor), `bid_modifier_multipliers_product` the product of applied bid modifiers.
- **`sent_to_exchange`** — BOOL, TRUE on ~100% of recent rows (263.37M/263.37M on 2026-07-10) — this leg effectively holds bids that were submitted; do not assume it's a discriminating filter.
- **`account_id` / `customer_id` / `buzz_key`** — Beeswax-internal account identifiers (Beeswax "buzz"), distinct from MNTN `advertiser_id`/`campaign_id`. `advertiser_id`, `campaign_id`, `line_item_id`, `creative_id`, `flight_id` are the MNTN-side ids (advertiser_id 100% populated on 2026-07-10).
- **`is_test`** — from Beeswax `test` flag (recent leg). **`continent`, `locale_code`, `time_zone`, `partner_id` are hard-`CAST(NULL)` in the 2026+ recent leg** — always NULL for current data (they carry real values only in the pre-2026 history leg). Don't build logic on them for recent dates.
- **`date_column`** — DATE, the view's prune handle for the recent leg (mapped from `dt`); see Cost.

## Joins & relationships
- **impression_log** (impression-grain, 1 row/served impression): join `impression_log.ttd_impression_id = bid_logs.auction_id`. bid_logs is **bid-grain → fans out** (auction eligible for many campaigns), so this is **N:1** into impression_log; **dedup bid_logs first** (`QUALIFY ROW_NUMBER() OVER (PARTITION BY il.ad_served_id ORDER BY b.time ASC)=1`, Zach 2026-03-24) or you multiply impression rows.
- **win_logs** (impression-grain): bid_logs → win_logs is **N:1** (bids ≫ wins). Partner-table key mapping (per tribal knowledge): win_logs `campaign_alt_id = campaign_group_id`, `line_item_alt_id = campaign_id`. Standard pipeline chains: CTV `clickpass → event_log → win_logs → impression_log → bid_logs`; display viewable `clickpass → viewability_log → win_logs → bid_logs`. Both win_logs/impression_log are downstream physicals not re-verified live in this pass — fan-out direction (bid_logs is the many side) is the safe claim.
- **bid_ip recovery fallback (TI-650, Zach 2026-03-24):** `event_log.bid_ip` was designed to equal `bid_logs.ip`. When bid_logs rows age out, recover the bid IP with `COALESCE(NULLIF(bid_logs.ip,'0.0.0.0'), impression_log.bid_ip, event_log.bid_ip, viewability_log.bid_ip)` (~50% recoverable; `clickpass_log` has no bid_ip). Note the view's history leg means bid_logs itself now reaches back further than the old 90-day belief (see Gotchas).

## Gotchas
- **VIEW = raw + history UNION on TWO different partition columns.** Physical resolves to `UNION ALL` of `dw-main-bronze.sqlmesh__raw.raw__bid_logs__3039662744` (2026+, partitioned **DAY on `dt`**, exposed as `date_column`, **365-day TTL**) and `dw-main-bronze.history.bid_logs_physical` (pre-2026, partitioned **HOUR on `time`**, no TTL). The cutover is a hardcoded `dt >= 2026-01-01` / `date_column <= 2025-12-31` split. **Consequence:** a filter on only ONE of the two columns prunes only ONE leg and full-scans the other (2–3 TB waste) — see Cost. **Filter BOTH `date_column` AND `time`.**
- **auction_id is not unique** — multiple candidate-campaign rows per auction (~1.11×). Always dedup before joining to impression/win logs.
- **Retention is NOT the old "90-day" belief — but the queryable span is ~10 months, NOT multi-year.** The history leg has no TTL, yet its data only reaches back to **~late-September 2025** (dry-run 2026-07-19: 0 bytes at 2024-06-15 / 2025-06-15 / 2025-08-15 / 2025-09-20; first non-zero at 2025-09-25). So the total queryable window is history **~2025-09-25 → 2025-12-31** + recent **2026-01-01 → now** — roughly 10 contiguous months. **Querying 2024 or Jan–Aug 2025 silently returns 0 rows** (the partition prunes to empty — a copy-paste user concludes the table is broken). The 90-day figure in `data_knowledge.md` L545 predates the raw+history restructure; TI-650's 2026-03 "records gone" finding reflects the recent-leg TTL, not the whole view. Forward watch-item: the recent leg's 365-day `dt` TTL vs the fixed 2026-01-01 cutover could open an early-2026 gap after ~2027-01 unless SQLMesh backfills history — not a problem today (2026-01-01 is ~200 days old, well inside 365d and contiguous with the history leg's 2025-12-31 tail).
- **NULL-filled columns in the recent leg:** `continent`, `locale_code`, `time_zone`, `partner_id` (see Column meanings). `ip` NULL on ~1.3% of recent rows.
- SQLMesh physical hash rotates on rebuild — the `data_catalog.md` prose named `...__932945987`; live physical is `...__2989555617`. Query the clean view name `logdata.bid_logs`, never a pinned hash.

## Cost & partitioning notes
- **THE filter to always apply: BOTH `date_column` AND a matching `time` range.** Because the view UNIONs two differently-partitioned legs, one column alone leaves the other leg fully scanned. Dry-run measured (all figures 2026-07-19, `--dry_run`):
  - **1 narrow column (`auction_id`), no filter:** 4.84 TB.
  - **1 col, `date_column='2026-07-10'` only:** 2.10 TB — recent leg pruned to 1 day, **history leg fully scanned** (date_column ≠ its `time` partition).
  - **1 col, `time` in [2026-07-10, 07-11) only:** 3.17 TB — history leg pruned, **recent leg fully scanned** (`time` ≠ its `dt` partition).
  - **1 col, BOTH `date_column='2026-07-10'` AND `time` in-day:** **15.7 GB** — both legs pruned to one day. ~134× cheaper than one-column-only.
  - **`SELECT *`, BOTH filters, one recent day:** **569.6 GB** (~36× the narrow-column same-day cost) — avoid `SELECT *`; one day is 263M rows.
  - Realistic 8-column verify aggregate, one day, both filters: **22.4 GB / 16s wall** (perf log 2026-07-19).
- No clustering on either physical — no cheaper sub-day predicate beyond the partition columns; project only the columns you need.
- Backing storage ≈ 255 TB (162 TB recent + 93 TB history physicals); ~94.6B rows total (53.5B + 41.2B — the 41.2B history rows are concentrated in ~3.5 high-volume months, ~2025-09-25 → 2025-12-31, not a multi-year archive; see Gotchas).

## Example queries
```sql
-- Recent-day bid-IP lookup, deduped, BOTH prune columns (≈26 GB/day for these 6 cols; dry-run 2026-07-19 = 25.94 GB):
SELECT auction_id, advertiser_id, campaign_id, ip, bid_price_micros_usd, time
FROM `dw-main-silver.logdata.bid_logs`
WHERE date_column = '2026-07-10'                 -- prunes the 2026+ recent leg (dt)
  AND time >= '2026-07-10' AND time < '2026-07-11'  -- prunes the pre-2026 history leg (time)
QUALIFY ROW_NUMBER() OVER (PARTITION BY auction_id ORDER BY time) = 1;

-- History leg (data spans ~2025-09-25 → 2025-12-31): time is the partition; date_column also bounds it.
-- Use an in-range date — e.g. 2025-06-15 returns 0 rows (history archive starts ~late-Sep 2025).
SELECT auction_id, ip, bid_price_micros_usd
FROM `dw-main-silver.logdata.bid_logs`
WHERE time >= '2025-11-15' AND time < '2025-11-16'
  AND date_column = '2025-11-15';
```
