# logdata.auction_log

## Purpose
Unified, IP-level view of pre-bid/auction traffic. It is a **`UNION ALL` of two distinct, still-live event streams**, stitched into one schema so downstream code can read "auctions" from one place:

1. **Augmentor arm** — the pre-bid augmentation service (`dw-main-bronze.raw.augmentor_log`, via `v_augmentor_log`). One row per augmented bid-request, carrying the MNTN segments / geo / PMP context computed at bid time. This is the arm whose derived features (`al_avg_segments`, `al_n_auctions`, …) feed IP-level targeting models.
2. **Bidder arm** — the bidder's auction log (`logdata.bidder_auction_events`). One row per auction the bidder processed, with the internal + exchange auction IDs, drop reason, publisher/app identifiers, and `is_test`.

Reach for it when you want IP-level bid-request context (segments, geo, inventory) across both services in one place. Do **not** treat it as a canonical "list of auctions" — the two arms cover overlapping traffic from different services and are **not** deduplicated. For clean auction-level analysis go straight to `logdata.bidder_auction_events` (the bidder arm alone).

## Grain & keys
- **Grain:** two grains unioned, NOT one. `auction_id IS NULL` → augmentor row (one per augmented bid-request, no auction key). `auction_id IS NOT NULL` → bidder row (one per bidder auction). Both arms are actively written **concurrently** — in a single 3-min window on 2026-07-18 the bidder arm produced ~82M rows and the augmentor arm ~66M. So `COUNT(*)` over `auction_log` is **not** a count of auctions.
- **Arm discriminator (reliable):** `auction_id IS NULL` ⟺ augmentor arm. Corroborating constants set by the view on the augmentor arm: `partner_id = 8` (hardcoded literal, not a real partner), `geo_type = 'IP'` (hardcoded), `is_test IS NULL`.
- **Keys:** `auction_id` = bidder internal auction id (`bidder_auction_events.mntn_auction_id`); `exchange_auction_id` = the exchange's auction id. **Both are NULL on the augmentor arm.** The augmentor arm has no auction key — its only useful join handle is `ip` (its physical is clustered on `ip`).

## Column meanings (only the non-obvious ones)
Most surprises come from the same column meaning different things (or being NULL) depending on which arm the row came from.

- **`epoch`** — event time in **MILLISECONDS** on **both** arms (verified same-row 2026-07-18: `epoch ≈ UNIX_MILLIS(time)`). Bidder arm: `epoch ≡ UNIX_MILLIS(time)` (max abs diff = 1 ms). Augmentor arm: `epoch` is full-precision ms, but its `time` is **floored to the whole second**, so `epoch - UNIX_MILLIS(time)` ranges 0-999 ms. Prefer `time` for filtering (it's the partition key); use `epoch` only when you need sub-second ms on augmentor rows. *(Drift note: the global memory gotcha "bidder_auction_events = µs" does NOT hold for the epoch exposed through this view — it is ms on both arms.)*
- **`auction_id`** — bidder internal auction id (`mntn_auction_id`); **NULL on augmentor arm**.
- **`exchange_auction_id`** — the exchange/SSP's auction id; **NULL on augmentor arm**.
- **`auction_dropped` / `auction_dropped_reason`** — bidder-only: whether/why the bidder dropped the auction; NULL on augmentor arm.
- **`partner_id`** — bidder arm = real partner id; augmentor arm = hardcoded literal `8` (meaningless as a value). Don't group by `partner_id` across arms.
- **`geo_type`** — bidder arm = real geo source; augmentor arm = hardcoded `'IP'`.
- **`is_test`** — bidder arm = real BOOL test flag; **augmentor arm = NULL** (see the filter gotcha below).
- **`network`** — semantic mismatch across arms: augmentor arm = `augmentor_log.network`; bidder arm = `publisher_name`. Same column name, different meaning.
- **`domain` vs `site_domain`** — augmentor arm sets both to the same value; bidder arm `domain` = `app_domain`, `site_domain` = `site_domain` (distinct).
- **`ifa`** — device advertising id (IDFA/AAID); augmentor arm from `augmentor_log.ifa`, bidder arm from `device_ifa`.
- **`mntn_segments`** — nested `STRUCT<list ARRAY<STRUCT<element INT64>>>`: the MNTN segment IDs attached to the IP at bid time. Read via `UNNEST(mntn_segments.list)` and access `.element` (Spark/Avro-style wrapper, not a plain ARRAY).
- **`pmp`** — nested `STRUCT<list ARRAY<STRUCT<element STRING>>>`: PMP deal-id strings; same `list`/`element` unnest pattern.
- **Bidder-only columns (NULL on augmentor arm):** `app_id`, `app_name`, `auction_type`, `geo_version`, `publisher_domain`, `publisher_id`, `region`, `site_id`.

## Joins & relationships
- **`logdata.bidder_auction_events` (1:1 with the bidder arm).** `bidder_auction_events` **IS** one arm of this UNION — every one of its rows appears here verbatim (just remapped column names). Joining `auction_log` back to it is circular; query `bidder_auction_events` directly instead. `auction_log` = `bidder_auction_events` **plus** the extra augmentor rows.
- **`dw-main-bronze.raw.augmentor_log` (1:1 with the augmentor arm), via `v_augmentor_log`.** The augmentor arm is a projection of this raw table with `geo` parsed into a struct. Bronze-only fields dropped by the silver view (`iab_categories`, `categories`, `isp`, `page`, `referrer`) are **not** in `auction_log` — go to `bronze.raw.augmentor_log` for those.
- **On `ip` → any IP-keyed table (`cost_impression_log`, `event_log`, feature tables): N:N, extreme fan-out.** An IP recurs across millions of rows; never join on `ip` without a tight `time` window on **both** sides. The augmentor physical is clustered on `ip`, so IP point-lookups within a narrow time range are the cheap access path. *(Cross-table cardinality not live-verified here — PB-scale partners; treat as fan-out warning.)*
- **On `auction_id` (bidder arm only) → win/impression/spend tables** keyed by the bidder auction id: augmentor rows (auction_id NULL) will never match, so such a join silently drops the entire augmentor arm. *(Partner grain not live-verified in this pass.)*

## Gotchas
- **Not single-grain / not deduplicated.** Two live streams unioned; `COUNT(*)` ≠ auctions. Split on `auction_id IS NULL` before counting anything.
- **`WHERE is_test = FALSE` silently deletes the entire augmentor arm.** `is_test` is NULL on augmentor rows, and `NULL = FALSE` is not TRUE, so the augmentor arm drops out. Use `WHERE COALESCE(is_test, FALSE) = FALSE` to keep both arms while excluding bidder test traffic.
- **Partition filter is mandatory.** A query with no `time` filter errors: `Cannot query over table 'dw-main-bronze.raw.augmentor_log' without a filter over column(s) 'time'` (require-partition-filter propagates from the augmentor arm). Always filter `time`.
- **Augmentor `time` is second-granularity;** don't expect sub-second ordering from `time` on augmentor rows — use `epoch` if you need ms there.
- **10-day TTL — no history.** Both physicals are HOUR-partitioned with a 10-day expiration; there is no long lookback. For anything older than ~10 days you need a downstream/derived store, not this view.
- **`partner_id = 8` and `geo_type = 'IP'` on augmentor rows are hardcoded constants**, not data — don't read meaning into them.

## Cost & partitioning notes
- **Partition:** `time`, **HOUR** granularity, `require_partition_filter = TRUE`. Confirmed empirically: `SELECT ip` for 24h scans ~24.5× a single-hour scan (linear in the time window). **The one filter to always apply: a tight `time` range** (an hour or a few hours, not a day).
- **Clustering:** none at the view level. The augmentor physical (`raw.augmentor_log`) is clustered on `ip`; the bidder physical is unclustered — so `ip` point-lookups prune only the augmentor arm.
- **Never `SELECT *`.** Dry-run figures (2026-07-18, both arms):
  - `SELECT ip`, 1 hour → **69.0 GB** (0.063 TiB)
  - `SELECT ip`, 24 hours → **1,693.6 GB** (1.54 TiB) — ~24.5× the 1-hour figure (HOUR-partition scaling)
  - `SELECT auction_id, epoch, time`, 1 hour → **148.4 GB** (a 5-min slice of the same hour → **107.5 GB**). Contrary to a naive "HOUR partition = whole hour always scanned" reading, a sub-hour `time` range prunes *below* the hour partition via block-level column metadata — so tightening past one hour still cuts bytes (`SELECT ip` behaves the same: 5-min 49.3 GB vs 1-hour 69.0 GB).
  - `SELECT *`, 1 hour → **10,156.5 GB** (9.24 TiB) — ~147× the single-column 1-hour scan, driven by the wide string columns + nested `mntn_segments`/`pmp` structs across both PB-scale arms.
- **Backing storage:** ~2.27 PB (2.02 PiB) total = augmentor physical 1.04 PB + bidder physical 1.23 PB (`bq show` numBytes summed across the two UNION physicals). ~737B rows total (~331B augmentor + ~406B bidder) within the rolling 10-day windows.

## Example queries
```sql
-- Bidder-arm auctions only, one hour, project just what you need:
SELECT auction_id, exchange_auction_id, ip, site_domain, auction_dropped_reason
FROM `logdata.auction_log`
WHERE time >= TIMESTAMP('2026-07-18 12:00:00') AND time < TIMESTAMP('2026-07-18 13:00:00')
  AND auction_id IS NOT NULL           -- exclude augmentor arm
  AND COALESCE(is_test, FALSE) = FALSE;

-- Augmentor-arm segment context for an IP (uses the ip cluster on the augmentor physical):
SELECT time, ip, seg.element AS segment_id
FROM `logdata.auction_log`, UNNEST(mntn_segments.list) AS seg
WHERE time >= TIMESTAMP('2026-07-18 12:00:00') AND time < TIMESTAMP('2026-07-18 13:00:00')
  AND auction_id IS NULL                -- augmentor arm
  AND ip = '<ip>';
```
