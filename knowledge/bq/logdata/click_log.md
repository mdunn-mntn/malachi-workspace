# logdata.click_log

## Purpose
Raw ad-click event log — one row per user click on a served ad, at the exchange level. This is the
**raw click firehose**, not attributed outcomes. It is **distinct from `clickpass_log`** (verified
visits / VVs, the MNTN-attributed clicks+visits log). Reach for `click_log` when you need every click
event with its serve id, click IP, geo, landing page, and referrer; reach for `clickpass_log` when you
need attributed verified visits. Upstream source is Postgres (coredw).

## Grain & keys
- **Grain:** one row per ad-click event. Not deduped; there is **no single-column primary key**.
- **`guid`** — device/user GUID. **Repeats** across clicks (30,132 distinct / 50,913 rows on
  2026-07-15 ≈ 1.7 rows per guid). It is NOT a row key — use `COUNT(*)` for click volume, never
  `COUNT(DISTINCT guid)`.
- **`ad_served_id`** — the impression/serve UUID and the main **join key** out of this table.
  Near-unique per row (49,955 distinct / 50,913 = 98.1% on 2026-07-15) but not a guaranteed PK.

## Column meanings (only the non-obvious ones)
- **`time`** — click event timestamp (UTC). **Truncated to the WHOLE SECOND on both branches**
  (sub-second dropped; `MOD(UNIX_MILLIS(time),1000)=0` for 100% of rows, verified 2026-07-15 recent &
  2025-06-15 history). This is the column to filter on (`DATE(time)` / `time` range).
- **`epoch`** — Unix timestamp in **MICROSECONDS** (16-digit; `TIMESTAMP_MICROS(epoch)` lands on the
  true wall clock). **NOT seconds** — the old prose said "Seconds" and is WRONG. `epoch` keeps the
  sub-second precision that `time` loses (99.9% of rows have non-zero micros). Because of that,
  **`epoch != UNIX_MICROS(time)` in general** — they coincide only on the ~0.1% of rows that landed
  exactly on a whole second (40/50,913 recent, 41/35,009 history) and otherwise differ by up to <1s.
  Use `epoch` for sub-second click ordering; never join/filter on `epoch = UNIX_MICROS(time)`.
- **`ip`** — click-time public IP of the clicking device.
- **`ip_raw`** — **identical to `ip`.** The view derives it as `ip AS ip_raw` (not a separate
  pre-enrichment IP), so `ip_raw == ip` for 100% of rows. Do not treat it as a distinct raw value
  (contrast `ui_visits`/`visits`, where `ip` and `ip_raw` genuinely differ).
- **`bid_ip`** — denormalized IP at bid/auction time for the impression this click belongs to.
  **~31% NULL** (15,990 / 50,913 on 2026-07-15); when non-null it equalled `ip` for 100% of that
  sample. This is one of the four denormalized `bid_ip` carriers used in the COALESCE fallback pattern
  (see Joins).
- **`original_ip`** — original IP before any rewrite/NAT resolution.
- **`ad_served_id`** — impression/serve UUID (STRING); primary join key to `impression_log`,
  `event_log`, `clickpass_log`.
- **`first_touch_ad_served_id`** — serve UUID of the user/advertiser's first-touch impression.
- **`advertiser_id` / `campaign_id` / `creative_id` / `exchange_id` / `group_id`** — INT dimension
  ids (advertisers, campaigns, creatives, exchange, campaign group). `group_id` = campaign_group id.
- **`country` / `region` / `postal_code` / `metro_id`** — geo enrichment of the click IP.
- **`landing_page` / `referrer`** — click destination URL and referring URL.
- **`app_bundle` / `publisher`** — in-app bundle id and publisher of the placement.

## Joins & relationships
- **`ad_served_id` -> `impression_log.ad_served_id`** — impression_log's `ad_served_id` is **unique
  per day** (verified 203,528,125 rows = 203,528,125 distinct, 0 NULL on 2026-07-15; and
  507,151,528 = distinct, 0 NULL on 2025-06-15), so a **date-bounded** join is effectively **1:1**
  (recover the impression that was clicked). Low fan-out. Cross-day serve-UUID recycling was not
  tested, so keep the join date-bounded.
- **`ad_served_id` -> `event_log.ad_served_id`** — event_log is the CTV VAST-beacon firehose with
  **~6 rows per CTV impression**, so this is **1:N (fan-out ~6x on CTV)**. Prefer reading `bid_ip`
  directly off `click_log` instead of joining to `event_log` for IP lineage.
- **`ad_served_id` -> `clickpass_log.ad_served_id`** — `clickpass_log` = MNTN-attributed **verified
  visits**; a raw click may or may not become a VV, so not every `click_log` row has a match. Use to
  bridge raw-click -> attributed-visit.
- **`bid_ip` COALESCE fallback** — `click_log` is one of four tables (with `event_log`,
  `impression_log`, `viewability_log`) that store a denormalized `bid_ip`. When `bid_logs.ip` is
  purged (90d TTL), recover it via
  `COALESCE(NULLIF(bid_logs.ip,'0.0.0.0'), impression_log.bid_ip, event_log.bid_ip, click_log.bid_ip)`.
  Note `clickpass_log` has NO `bid_ip` column (acknowledged gap).
- **Dimension lookups** — `advertiser_id`/`campaign_id`/`creative_id`/`group_id` join **N:1** to the
  integrationprod dims (`advertisers`, `campaigns`, `creatives`, `campaign_groups`); always filter
  `deleted=FALSE AND is_test=FALSE` on those dims.

## Gotchas
- **LIVE DATA GAP — 2026-01-01 through ~2026-04-20 returns ZERO rows** (verified 2026-01-05 and
  2026-02-15 both = 0 rows through the view). The view UNIONs a **recent branch** (`time >= 2026-01-01`
  off `raw.click_log`, which carries a **90-day partition TTL** so it physically holds only
  ~2026-04-21 -> today) with a **history branch** (`date_column <= 2025-12-31`, though that physical
  actually has data up to 2026-04-15). The 90-day raw TTL is far shorter than `clickpass_log`'s 365-day
  expiry, so this hole is **already open and widens forward daily** as the raw branch's min `dt`
  advances. Do NOT trust `click_log` for Jan -> mid-Apr 2026 until the model boundary is refreshed.
- **`epoch` is MICROSECONDS, not seconds** (prose was wrong), and **`epoch != UNIX_MICROS(time)`** —
  `time` is truncated to the whole second on both branches while `epoch` keeps sub-second precision;
  they match only ~0.1% of rows. Use `TIMESTAMP_MICROS(epoch)` for exact wall clock.
- **`ip_raw` is NOT a separate raw IP** — the view aliases `ip AS ip_raw`; `ip_raw == ip` always.
- **`bid_ip` is ~31% NULL.** For those rows fall back to `ip`/`original_ip` or other tables.
- **`guid` repeats** (device GUID) — not a row key; use `COUNT(*)` for click volume.
- **Two-physical UNION with different partition columns:** the recent raw physical is partitioned on a
  hidden `dt` column; the history physical is partitioned on `time`. A `DATE(time)` filter prunes the
  history branch but **not** the recent branch (see Cost).

## Cost & partitioning notes
- **Always filter `DATE(time)` (or a `time` range).** It prunes the **history branch** (~19.5 GB, the
  bulk of the table). For any bounded historical date range this is the one filter that matters.
- **But `DATE(time)` does NOT prune the recent raw branch** (partitioned by hidden `dt`, not exposed
  in the view): the recent branch is always fully scanned through the view. To actually prune recent
  data, query the raw physical `dw-main-bronze.sqlmesh__raw.raw__click_log__<hash>` **directly with
  `WHERE dt='YYYY-MM-DD'`** (0.8 MB/day for the `time` column — true partition prune).
- **The raw physical hash (`__2929351715`) is SQLMesh-model-versioned — it drifts on every model
  rebuild** (the same drift that left `data_catalog.md`'s silver hash `__3304395312` stale). A
  hardcoded hash fails with `Not found: Table` after the next re-version, so **re-resolve it before
  using the direct-raw workaround**: `bq show --format=prettyjson dw-main-silver:logdata.click_log`
  gives the silver→physical hash (`logdata__click_log__<hash>`), and that physical view's DDL gives the
  current `raw__click_log__<hash>` (as of 2026-07-19: silver→`__4053667325`, raw→`__2929351715`).
- **Never `SELECT *`** — project only the columns you need.
- Labeled dry-run figures (2026-07-19, via `bq --dry_run`):
  | query | column set | filter | bytes |
  |-------|-----------|--------|-------|
  | view | `time` only | none | 0.92 GB |
  | view | `time` only | `DATE(time)`=1 history day | 28.6 MB |
  | view | `time` only | `DATE(time)`=1 recent day | 28.0 MB (recent branch unpruned) |
  | view | `SELECT *` | none | 21.0 GB |
  | view | `SELECT *` | `DATE(time)`=1 recent day | 1.20 GB (recent branch unpruned; grows daily) |
  | raw physical | `time` only | `dt`=1 day | 0.8 MB (true prune) |
- **No clustering** on either physical.
- **Retention:** recent raw physical = **90-day** partition expiration (`expirationMs 7776000000`);
  history physical = **no expiration** (full history from 2024-01-01). `ttl_days: null` in front-matter
  refers to the view's history floor, NOT the recent branch (which ages out at 90d and drives the gap
  above).
- `approx_logical_bytes` = 22,508,588,830 = raw physical `numBytes` 1,593,988,612 + history physical
  `numBytes` 20,914,600,218 (summed across the 2 UNION physicals).

## Example queries
```sql
-- Historical date range (prunes the big history branch):
SELECT ad_served_id, ip, bid_ip, landing_page, referrer
FROM `dw-main-silver.logdata.click_log`
WHERE DATE(time) BETWEEN '2025-06-01' AND '2025-06-07';

-- Recent data with TRUE partition pruning — go direct to the raw physical on `dt`
-- (the silver view will not prune the recent branch on DATE(time)):
-- NB: the __2929351715 hash is SQLMesh-versioned and drifts on rebuild — re-resolve it from
--     `bq show dw-main-silver:logdata.click_log` (see Cost & partitioning notes) before running.
SELECT ad_served_id, ip, bid_ip, landing_page
FROM `dw-main-bronze.sqlmesh__raw.raw__click_log__2929351715`
WHERE dt = '2026-07-15';
-- NB: avoid dates 2026-01-01..~2026-04-20 through the view — it returns zero rows there.
```

## View definition
```sql
-- silver view resolves to a 2-branch UNION physical view:
SELECT guid, time, epoch, advertiser_id, exchange_id, campaign_id, creative_id, country, region,
       postal_code, metro_id, group_id, ad_served_id, ip, ip AS ip_raw, bid_ip, original_ip,
       first_touch_ad_served_id, landing_page, referrer, app_bundle, publisher
FROM `dw-main-bronze.sqlmesh__raw.raw__click_log__2929351715`   -- DAY on hidden `dt`, 90-day TTL
WHERE CAST(time AS DATE) >= CAST('2026-01-01' AS DATE)
UNION ALL
SELECT guid, time, epoch, advertiser_id, exchange_id, campaign_id, creative_id, country, region,
       postal_code, metro_id, group_id, ad_served_id, ip, ip AS ip_raw, bid_ip, original_ip,
       first_touch_ad_served_id, landing_page, referrer, app_bundle, publisher
FROM `dw-main-bronze.history.click_log_physical`               -- DAY on `time`, no expiry
WHERE date_column <= CAST('2025-12-31' AS DATE)
```
