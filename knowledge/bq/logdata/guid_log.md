# logdata.guid_log

## Purpose
MNTN's own first-party site pixel — the **"MNTN Pixel"**, registry `data_sources.id = 23` (DS23). It fires on
**every page view** on an advertiser's site by a tracked household, **regardless of whether MNTN ever served
that household an ad**. It is therefore the cause-agnostic record of *total* site traffic (direct + organic +
paid + view-through), and the honest denominator for incrementality: because holdout and targeted IPs appear
here at similar rates, guid_log measures the total traffic MNTN ads *barely move* (~0% lift), whereas
`clickpass_log` measures MNTN-*attributed* visits (2-8x lift). Reach for it for site-traffic / page-view
analysis and the "did this IP hit the advertiser site at all?" signal at IP-day grain (after dedup). It is also
one of the two **zero-cost** `site_visit_signal` feeds (DS23; the other is `augmentor_log` DS30), an input to
the Fangorn / feature-store pipelines, and the source of the DS14 4-day freshness/eligibility filter.

## Grain & keys
- **Grain:** one row per **page-view event** (individual pixel fire) — NOT one row per household or per IP.
  Verified 2026-07-15: **308.4M rows, ~51.2M distinct `guid`, ~32.3M distinct `ip`** in one day → ~6 page-views
  per household-cookie, ~9.5 rows per IP-day. **Dedup to DISTINCT (advertiser_id, ip[, day]) before any
  IP-level rate analysis or join.**
- **Identity key:** `guid` = the tracking-cookie GUID (a UUID, e.g. `34d126b9-7fe0-11f1-...`) — the
  household/device cookie identifier. Repeats across a household's page views, so it is **not** a per-row
  primary key and is **not** an IP.
- **Join columns:** `ip` (== `ip_raw`, see gotchas) and `advertiser_id` (~7,166 distinct advertisers/day).
  A row is uniquely a `(guid, epoch/time, advertiser_id)` pixel fire; there is no single natural PK.

## Column meanings (only the non-obvious ones)
- **`guid`** — cookie GUID (household/device tracking cookie), UUID string. The identity key; repeats per row; not an IP.
- **`epoch`** — **MICROSECONDS** since Unix epoch on current (recent/raw) data. Verified 2026-07-15:
  `epoch = 1784073636268999` vs `UNIX_SECONDS(time) = 1784073636` → ×10^6. **DRIFT: `data_catalog.md` says
  "Seconds" — wrong for live data.** Prefer the `time` TIMESTAMP for all filtering/bucketing.
- **`time`** — event TIMESTAMP; the **partition column of BOTH backing physicals**. Always filter on this.
- **`ip` / `ip_raw`** — **identical in this view** (recent branch maps both from the raw `ip`; history branch
  maps both to `split(ip,'/')[0]`). 100% `ip == ip_raw` on the sample day; `ip` never NULL. Unlike
  `ui_visits`/`visits` (where the two columns genuinely differ), do **not** treat them as two signals here.
- **`original_ip`** — pre-resolution IP; may differ from `ip`.
- **`is_new`** — first cookie seen for this advertiser (new-visitor flag). **Rate depends on the base
  (verified 2026-07-15):** ~18% of rows are **NULL** (55.5M/308.4M); `AVG(CAST(is_new AS INT64))=0.200`
  → **~20% true among non-NULL rows**, i.e. **~16% of all rows**. Quote which base you mean.
  **This is the client-JS pixel bit and it is guid/cookie-keyed** — one of five live NTB definitions,
  and NOT the one behind the customer-facing `visit_facts.new_visitors` (that is IP-keyed, via
  `ber_stg.visits__is_new_guid_flags`). Choosing guid vs IP moves the population count ~39%. See
  `knowledge/data_knowledge.md` § "NTB (New-to-Brand)". **`logdata.guid_log__v3` (Pixel 3) carries the
  column but it is 100% NULL** (177,944/177,944 rows on 2026-08-17) — Pixel 3 emits no NTB bit.
- **`is_cookied`** — whether a tracking cookie was successfully set. Same ~18% NULL; `AVG=0.491`
  → **~49% true among non-NULL rows**, i.e. **~40% of all rows**.
- **`is_control_group`** — holdout/PSA control flag; 0% true in the one-day sample (rarely set here).
- **`advertiser_id`** — advertiser whose pixel fired; populated ~100%. This is the column that makes DS23
  guid_log the *only* `site_visit_signal` source carrying `advertiser_id`.
- **`product` / `cart` / `user_agent`** — JSON type in the view, but **structurally different across the two
  UNION branches** (verified 2026-07-15 against the resolved view SQL + live samples):
  - **Recent branch (>=2026-01-01, `raw__guid_log__3436864589`)**: physical `product`/`user_agent` are RECORD,
    so the view's `TO_JSON(...)` yields **real JSON objects** — `JSON_VALUE(product,'$.CATEGORY')` works
    (uppercase fields: CATEGORY, BRAND, NAME, AMOUNT, SKU, INVENTORY_COUNT, CURRENCY, IMG_URL, REFERRER,
    AVAILABLE_UNTIL). `cart` = `JSON_OBJECT('PRODUCTS', cart_products, 'ITEMS', cart_items)` → keys
    **PRODUCTS**/**ITEMS**.
  - **History branch (<=2025-12-31, `guid_log_physical`)**: `product`/`cart`/`user_agent` are physically
    **STRING**, so the view does `TO_JSON(<STRING>)` → a **JSON-wrapped escaped string scalar, not an object**.
    `JSON_VALUE(product,'$.CATEGORY')` returns **NULL for every pre-2026 row** (verified 2025-06-01: `product`
    renders as `"\"{\\\"CURRENCY\\\":...}\""`). To read the JSON you must double-parse:
    `JSON_VALUE(PARSE_JSON(JSON_VALUE(product)),'$.CATEGORY')`.
  - **Cross-branch safe extraction:** use the flat `product_*` scalar columns
    (`product_currency`/`product_sku`/`product_name`/`product_inventory_count`/`product_referer`) — populated in
    both branches. These JSON columns are also the scan-cost hotspots (see Cost).
- **`query`** — `TO_JSON_STRING` of the raw `query_map` (recent) / raw `query` (history).
- **`email` / `phone`** — hashed PII.
- **`referer` / `parent_referer` / `product_referer`** — page URLs; `referer` is the visited page.

## Joins & relationships
- **guid_log vs clickpass_log** — guid_log = ALL visits (total traffic, honest incrementality denominator);
  clickpass_log = MNTN-attributed VV visits only. The wedge between them = visits MNTN claims that would have
  happened anyway (Zazzle HI ATT, TI-837: clickpass +1.49pp vs guid +1.30pp → ~78% happen anyway).
  clickpass_log **cannot** do holdout comparisons (its rows require an impression) — use guid_log for
  holdout / total-traffic lift.
- **site_visit_signal / DS23** — guid_log is the DS23 "MNTN Pixel" feed and one of two zero-cost svs sources
  (other = augmentor_log DS30). Feeds Fangorn (DS46, guid_log-only today) and the feature store (aug_log + guid_log).
- **DS14 freshness filter** — IPs seen in guid_log within a ~4-day window are the eligible pool for audience
  expressions (recency/eligibility filter at MembershipDB / audience-service level).
- **FAN-OUT WARNING** — joining raw guid_log to any per-IP or per-(advertiser,IP) table multiplies rows ~6-10x
  per IP-day (many page-view events per household). **Always pre-aggregate to DISTINCT (advertiser_id, ip[, day])
  before joining**, or the join explodes.
- **Feedback-feature leakage** — presence of a guid_log row implies a visit already happened (AUC ~0.999 but
  leaky). Never mix guid_log features with pre-visit bidstream features in a targeting model — they dominate and
  mask real predictive signal. Use for retraining / returning-visitor scoring / identity only.

## Gotchas
- **`time` is the only prune column** — always filter it (see Cost). No clustering on either physical.
- **`epoch` is MICROSECONDS, not seconds** (prose drift, corrected above). Use `time`.
- **`ip == ip_raw`** in this view (both derived from the same source column) — not two signals.
- **UNION ALL of two physicals, cutover 2026-01-01** — recent (>=2026-01-01) from
  `sqlmesh__raw.raw__guid_log__3436864589` (HOUR-partitioned, 546-day ≈ 18-mo TTL); history (<=2025-12-31) from
  `history.guid_log_physical` (DAY-partitioned, **permanent** archive). A query spanning the boundary reads both.
  The history branch's internal bound is on `date_column`, but the partition/pruning column is `time` — your
  filter must be on `time`.
- **`product`/`cart`/`user_agent` JSON is branch-dependent (silent NULLs pre-2026)** — the recent (>=2026)
  physicals are RECORD, so the view's `TO_JSON` gives real JSON objects and `JSON_VALUE` works; the history
  (<=2025) physicals are **STRING**, so `TO_JSON` gives a JSON *string scalar* and
  `JSON_VALUE(product,'$.CATEGORY')` is **NULL for every pre-2026 row**. Any extraction spanning or before the
  2026-01-01 cutover silently returns NULL on the history side — use the flat `product_*` columns for
  cross-branch work, or double-parse the history JSON (see Column meanings). Cannot compare to string `"null"` —
  use `IS NOT NULL`.
- **Physical carries far more columns than the view exposes** — `guid_log_physical` has geo
  (country/region/city/postal_code/geoname_id/metro_id), `user_segments`, `section_id`, `cookie_failure_id`,
  and `expansion_*` columns that the silver view drops. Need geo or segments? Go to the physical (or GCS parquet).
- **High-volume reads → GCS / Databricks** — archived to `gs://mntn-data-archive-prod/guid_log/`; for multi-day
  scans read the parquet directly via Spark on Databricks (no 6h wall, no BQ scan billing) — per Victor Savitskiy.
- **~0% ad-driven lift is expected** — guid_log measures total traffic, most of which MNTN doesn't cause; that's
  the point, not a bug.

## Cost & partitioning notes
- **ALWAYS filter `WHERE time >= '2026-07-15' AND time < '2026-07-16'`** — `time` is the partition column of both backing
  physicals and the single most important prune. `require_partition_filter` is **not enforced** by the tables, so
  an unfiltered query silently scans all-time (7.56 TB for one column).
- **Backing storage** (bq show `numBytes`, permanent figures): history `guid_log_physical` = **365.8 TB /
  107.47B rows** (DAY on `time`, no TTL); recent `raw__guid_log__3436864589` = **281.2 TB / 71.6B rows** (HOUR on
  `time`, 546-day TTL). Sum ≈ **647 TB / ~179B rows**. `guid_log_physical` is the perf-log cost hotspot: the
  careless **multi-day lift scans (TI-837) billed ~126 TB each** (a cluster of 3 queries), up to **495 TB** for
  one 7-day 4-segment scan — versus **~20 GB for a one-day narrow-column scan**. (The 126 TB figure is the
  multi-day-scan cluster, *not* a p50 — the median of all logged `guid_log_physical` scans is ≈20-35 GB, since
  most are single-day.)
- **Dry-run scan estimates** (each LABELED by exact column set — only same-label figures are comparable):
  - `SELECT guid` (1 col), **no filter / all-time**: **7.56 TB**
  - `SELECT guid` (1 col), **one recent day** (2026-07-15): **14.2 GB** → the `time` filter prunes ~530x
  - `SELECT guid` (1 col), **one history day** (2025-06-01): **10.7 GB** (history branch prunes too)
  - `SELECT *`, **one recent day**: **787 GB** → ~55x the one-column day; the wide JSON columns
    (`user_agent`/`product`/`cart`) + many strings dominate. **Never `SELECT *`.**
  - Actual billed: a ~6-narrow-column COUNT aggregate over one recent day billed **20.6 GB**.
- **Rule:** select only the columns you need (`guid`/`ip`/`advertiser_id`/`time` are cheap; the JSON columns are
  ~50x); for anything beyond a few days, dedup early and/or read the GCS parquet on Databricks.

## NTB / dedupe economics (measured 2026-08-19)

There is **no deduped `(advertiser_id, ip, visit_date)` table in BigQuery**. The dedupe already exists
outside BQ: `gs://mntn-data-archive-prod/feature_store/feature_group_1_source/guid_log_ip_advertiser_id/`
(airflow-ti, `models/feature_store/feature_group_1_source/guid_log_ip_advertiser_id.py`) is a daily
incremental Spark rollup at exactly `(ip, advertiser_id, dt)` — 293 unbroken partitions 2025-10-30 →
2026-08-18, verified one row per pair, **99.89% of guid_log rows** (the gap is `pixel_isolation`
advertisers: 6,874 vs 7,070). It drops `is_new`, and its `first_visit_time` is `min(time)` **within the
day only** — no cross-day state. No registered BQ external table over it (precedent for registering one:
`bronze.external.household_scoring__advertiser_intent__v1`).

**Dedupe ratio:** 2026-08-17 — 313,074,682 guid_log rows → **64,851,398 distinct (advertiser_id, ip)**,
i.e. **4.83x on rows, ~2 GB/day**. The saving is row count only; this query shape already touches 3 of 38
columns, so there is no width saving to capture.

**Scan cost of the NTB shape** (`SELECT DISTINCT advertiser_id, ip, DATE(time)`, dry-run):

| window | scan |
|---|---|
| 1 day | 9.08 GB |
| 30 day | 268 GB |
| 90 day | 798 GB |
| 365 day | 3.02 TiB |

The 90-day figure independently reproduces the in-repo `~856 GiB/run` comment at
`sqlmesh/models/dw-main-silver/enriched/lift__ghost_bid_visits.sql:89-93`. Against the existing parquet a
90-day distinct-pair query ran in **16 s / 132.5 GB** vs **856 GB** off `guid_log` — 6.46x cheaper.
Reservation capacity is prepaid, so quote slots, not dollars.

**Do not build a permanent "ever seen" first-seen table.** Measured over 30 days: 1,087,636,226 cumulative
distinct pairs, **74.2% appear on exactly one day**, p50 active days = 1, new-pair arrival flattening at
~28.8M/day — that is IP churn, not new households. Extrapolates to ~20.9B rows / ~648 GB at guid_log's full
717 days, and "have I ever seen this pair" has no pruning predicate, so a daily MERGE reads the whole
target (~237 TB/yr vs ~3.5 TB/yr for the visit-day table). Every NTB decision in the repo is windowed
anyway: `dw-main-silver.audience.advertiser_configurations.page_view_lookback_window` carries **11 distinct
values, 30 → 365 days, explicit for 4,241 advertisers** (default 30) and **806 configs changed in the last
90 days** — apply the window at read time, never bake it in.

**`history.guid_log_physical` is unmanaged.** 365.8 TB / 107.5B rows, hand-created BASE TABLE (2026-04-22),
read directly at `models/dw-main-silver/logdata/guid_log.sql:91`, produced by **no model in the repo**, and
holding 4 months more history (back to 2024-09-01) than the `history/guid_log.sql` model that nominally
covers it. Tech debt before anything durable depends on that leg.

**`guid_log` and `guid_log__v3` are deliberately NOT unioned** — `logdata/guid_log__v3.sql:3-6` says so
verbatim. Physical `raw__guid_log__v3` starts 2026-07-01. Any NTB model must union both and carry a
`pixel_version`, or a migrating advertiser's lookback silently collapses to weeks.

## Example queries
```sql
-- Distinct IP-day site traffic for an advertiser (dedup the page-view fan-out)
SELECT advertiser_id, DATE(time) AS d, COUNT(DISTINCT ip) AS visitors
FROM `logdata.guid_log`
WHERE time >= '2026-07-15' AND time < '2026-07-16'   -- ALWAYS filter time (the only prune)
  AND advertiser_id = 31357
GROUP BY advertiser_id, d
```
