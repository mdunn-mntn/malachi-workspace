# logdata.bidder_bid_events_test_optimized

## Purpose
A **one-shot, frozen physical BASE TABLE** (not a view, not SQLMesh-managed) holding a **~2-hour slice of `bidder_bid_events`** — every row's `time` falls in **2026-05-28 11:35:02 → 13:40:05 UTC** (live-verified MIN/MAX). It was materialized once on **2026-06-02** and never modified since (`creationTime == lastModifiedTime`). The name and provenance point to a **storage/query "optimized-layout" experiment** on `bidder_bid_events` (the base table was mid-repartition around this date — cf. its `_enriched_repartitioned…dev_schema_tmp`). The **schema is byte-identical to `bidder_bid_events`** (same 69 columns — 63 scalar + 6 STRUCT; live `bq show --schema`, 0 name diffs vs base).

Reach for it only to validate/benchmark that layout experiment. For any real analysis — ghost-bid/holdout incrementality, bid-eligibility diagnostics, current bidding behavior — **use the live `logdata.bidder_bid_events` view instead** (this copy is stale by design: a fixed 2-hour window of one day, will never update, and holds only **6 advertisers / 1 partner**). Full column semantics live in `knowledge/bq/logdata/bidder_bid_events.md`.

## Grain & keys
- **Grain:** identical to `bidder_bid_events` — one row per **bidder decision on an auction candidate**: a placed bid, or a no-bid/drop carrying a `threshold_failure_reasons`. NOT deduped to one-per-auction (a single `auction_id` can yield multiple rows per candidate campaign/line-item).
- **Row breakdown (live-verified over the full 883,635,756 rows):** `has_price = TRUE` **= 80,063** and no-failure rows (`threshold_failure_reasons` NULL/'') **= 80,063** (they match exactly → `has_price=TRUE` iff no failure reason). Everything else (~883.5M, >99.99%) is a dropped bid with a failure reason. `'ghost-bid'` rows = **23,072**. `is_test` rows = **0**.
- **Identifier columns:** `bid_id` (per-bid), `auction_id` (MNTN-side auction id), `exchange_auction_id` (raw exchange id). Cohort dims carried on the row (no dim-join needed): `advertiser_id`, `campaign_id`, `campaign_group_id`, `creative_id`, `line_item`, `objective_id`, `channel_id`, `ip`. Uniqueness of `bid_id`/`auction_id` not separately verified.

## Column meanings (only the non-obvious ones)
Semantics are inherited verbatim from `bidder_bid_events` — see that doc for the full column-by-column detail. Only the points **live-verified on THIS snapshot** (or worth repeating) are called out here:
- **`time`** — TIMESTAMP, the event (bid) time. **NOT a partition column here** (this table is unpartitioned — see Gotchas). All rows fall in 2026-05-28 11:35-13:40 UTC.
- **`epoch`** — bid time in **MILLISECONDS**. The unit (ms) is exact and load-bearing, but do NOT assume row-level identity with `UNIX_MILLIS(time)`: live-verified over all **883,635,756** rows, `epoch` = `UNIX_MILLIS(time)` for only **441,131,246** rows (49.9%) and `= UNIX_MILLIS(time)+1` for the other **442,504,510** (50.1%); never off by more than 1 ms (min/max diff 0/1). `epoch` is the bid time rounded up to ms and lands 0-1 ms after the auction, so a `WHERE epoch = UNIX_MILLIS(time)` join/filter would silently drop ~50% of rows — derive ms from `epoch` directly, not from `time`.
- **`auction_epoch`** — auction time in **MICROSECONDS**. Live-verified: `auction_epoch` = `UNIX_MICROS(time)` **exactly for 100% of rows** (all 883,635,756; e.g. row `auction_epoch=1779975204733837`, `UNIX_MICROS=1779975204733837`) — unlike `epoch`, this identity IS exact. A per-column trap: same row, `epoch`=ms but `auction_epoch`=µs (cf. `spend_log.auction_epoch` = ns).
- **`has_price`** — BOOL. `TRUE` = passed eligibility, price set (real ITT-treatment bid). On this snapshot `has_price=TRUE` count (80,063) equals the no-failure-reason count (80,063). **Ghost/drop rows carry `has_price=FALSE` but `price` is still populated** — use `has_price = TRUE`, never `price > 0`, to isolate real bids.
- **`price`** — bid price in **micros** (integer); logged even on ghost/no-price rows.
- **`threshold_failure_reasons`** — STRING drop reason; NULL/'' = no failure (real bid). `'ghost-bid'` (dashed, MNTN-bidder holdout marker) present here (23,072 rows).
- **`household_score`, `advertiser_household_score`, `conquest_score`, `household_score_threshold`** — applied bid-time scores; on the base table these are ~99.74% zero (real 0-10000 MM/Fangorn/RTC scores are consumed upstream, not logged here). NOT re-probed on this snapshot — assume base semantics.
- **`is_test`** — BOOL. **0 rows are `is_test=TRUE` on this snapshot** — it is already production-only, no test filter needed here.
- **`channel_id`** (8=CTV, 1=display), **`objective_id`** (1/5/6=prospecting, 4=retargeting), **`is_ctv`** (redundant STRING flag) — same as base.
- **Repeated STRUCT columns** (`campaign_impressions`, `campaign_group_impressions`, `targeted_segments`, `term_ids`, `pmp_deal_ids`, `tow_hours`) and blob strings (`agent_params`, `pacing_debug_data`) are heavy — never `SELECT *` when you only need scalars (esp. acute here — see Cost, no partition to save you).

## Joins & relationships
Same partner tables and fan-out profile as `bidder_bid_events`:
| To | Key(s) | Purpose / cardinality |
|----|--------|-----------------------|
| `logdata.spend_log` | `auction_id` / `bid_id` | Won impressions w/ cost. `spend_log.auction_epoch` = **ns** (this table's `auction_epoch` = µs). |
| `logdata.bidder_auction_events` | `auction_id` (confirm side) | Auction context. One auction → many bid rows here (**fan-out**); `bidder_auction_events` also has a distinct `mntn_auction_id`. |
| `logdata.win_logs` | `auction_id` / `exchange_auction_id` / `bid_id` | The only way to know a bid won. `win_logs.campaign_alt_id`=cg_id, `line_item_alt_id`=campaign_id. |
| `bronze.integrationprod.campaigns` | `campaign_id` | For `funnel_level` (not on the bid row). Filter dims `deleted=FALSE AND is_test=FALSE`. |

**Fan-out warnings:** multiple bid rows per `auction_id` → dedupe before counting auctions; join to `win_logs`/`spend_log` on `bid_id` (not `auction_id` alone) for one-to-one.

**⚠️ Time-overlap caveat unique to this snapshot (partner-by-partner, live-verified 2026-07-19):** the 2-hour window is 2026-05-28, ~52 days before this crawl, so partner availability is **mixed** — it is NOT fully self-contained:
- `spend_log` (**no expiry**, HOUR-partitioned) **still holds the window** — **5,988,956** rows in 2026-05-28 11:30–13:45 UTC. Joinable for won-impression cost.
- `win_logs` **still holds the window** — **6,020,654** rows in the same span. Joinable — the way to tell which of the 80,063 real bids won.
- `bidder_auction_events` returns **0 rows** for the window (partition already gone despite the nominal 90-day bronze.raw TTL) — not joinable.
- the base `bidder_bid_events` (**10-day TTL**) is **expired** for 2026-05-28 — not joinable.

So won-impression / cost / win enrichment IS possible via `spend_log` + `win_logs` (join on `bid_id` / `auction_id`); only auction-context enrichment (via `bidder_auction_events` or the base `bidder_bid_events`) is unavailable for this window.

## Gotchas
- **⚠️ UNPARTITIONED — a `WHERE time` filter does NOT prune; it makes cost WORSE.** No `timePartitioning`/`rangePartitioning`/`clustering` on the physical (live `bq show` 2026-07-19). Empirically proven (dry-runs, same column): `SELECT threshold_failure_reasons` with a `time` BETWEEN filter scanned **25.9 GB** vs **18.9 GB** without the filter — the filter *added* ~7 GB (reading the entire `time` column across all 884M rows) and pruned **nothing**. The only cost levers are **column projection** and **`TABLESAMPLE`/`LIMIT`**, not a date filter.
- **Frozen, one-shot snapshot — will NEVER update.** Created 2026-06-02, `lastModifiedTime == creationTime`, `expirationTime = null` (**no TTL** — unlike the base table's 10-day partition TTL, this copy persists indefinitely). Its data is a fixed 2-hour window of 2026-05-28 and does not track current bidding. Do not use for anything time-current.
- **Not representative.** Only **6 distinct advertisers, 1 partner, ~2 hours** of data. `bidder_bid_events` proper carries ~22 advertisers/day; the daily distribution differs. Do not generalize rates/mixes from this slice.
- **Even a `LIMIT` query is expensive.** A `LIMIT 5` over 3 columns billed **19.75 GB** (no partition to prune — the executor still reads full column stripes). Budget for GB-scale scans on any query here.
- **Not SQLMesh-managed / not a view.** `object_type = BASE TABLE`, lives directly in `logdata` (no `sqlmesh__` physical, no rotating hash). What you query is the storage — no view resolution needed.
- **Schema identical to base; score/HHST caveats inherited.** The 0-10000 MM/Fangorn/RTC scores are consumed upstream and surface here as ~0 (per base doc); not re-probed on this snapshot.

## Cost & partitioning notes
- **Partition `none`, cluster `[]`, no TTL (all live-confirmed).** The generic "always filter the partition column" advice is **inverted** for this table — there is no partition, so a `time` filter cannot help and actively adds the `time`-column scan. **The one lever: project only the scalar columns you need** (and `TABLESAMPLE SYSTEM (n PERCENT)` / `LIMIT` for exploration).
- **Labeled byte figures (each from `--dry_run` or an actual run; compare only same-column-set):**
  - `SELECT *` (all 69 cols): **4,059,479,268,693 B ≈ 4.06 TB** (dry-run 2026-07-19; equals `numBytes`/`approx_logical_bytes` — a full-table scan).
  - `threshold_failure_reasons` alone, **no** filter: **18,878,231,095 B ≈ 18.9 GB** (dry-run).
  - `threshold_failure_reasons` alone **WITH** `time` BETWEEN filter: **25,947,317,143 B ≈ 25.9 GB** (dry-run) — *larger*, proving no pruning (+~7 GB = the `time` column).
  - `time, epoch, auction_epoch` + `LIMIT 5`: **19.75 GB** billed (actual run, 1.4 s wall).
  - 6-col aggregate profile (`time, advertiser_id, partner_id, is_test, threshold_failure_reasons, has_price`): **38.97 GB** billed (actual run, 57.6 s wall, ~8,032 s slot).
- **`approx_logical_bytes` = 4,059,479,268,693** = real backing storage (`bq show` numBytes) = the `SELECT *` dry-run — a genuine 4.06 TB on disk (dense, ~884M rows).

## Example queries
```sql
-- CHEAP: project one scalar; do NOT add a WHERE time filter (no partition — it only costs more).
SELECT threshold_failure_reasons, COUNT(*) AS n
FROM `dw-main-silver.logdata.bidder_bid_events_test_optimized`
GROUP BY 1 ORDER BY n DESC;

-- Explore rows without a ~4 TB SELECT *: sample + narrow projection.
SELECT bid_id, advertiser_id, campaign_id, ip, has_price, price, threshold_failure_reasons, time
FROM `dw-main-silver.logdata.bidder_bid_events_test_optimized` TABLESAMPLE SYSTEM (1 PERCENT)
LIMIT 100;

-- Incrementality arms within this 2-hour snapshot (holdout vs ITT-treatment).
SELECT
  CASE WHEN threshold_failure_reasons = 'ghost-bid' THEN 'holdout'
       WHEN (threshold_failure_reasons IS NULL OR threshold_failure_reasons = '') AND has_price THEN 'itt_treatment'
       ELSE 'other' END AS arm,
  COUNT(*) AS rows, COUNT(DISTINCT ip) AS ips, COUNT(DISTINCT advertiser_id) AS advs
FROM `dw-main-silver.logdata.bidder_bid_events_test_optimized`
WHERE ip IS NOT NULL AND ip != '0.0.0.0'
GROUP BY 1;
```
