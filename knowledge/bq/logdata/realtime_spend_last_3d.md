# logdata.realtime_spend_last_3d

## Purpose
Near-realtime spend for **pacing / live dashboards** over the trailing ~3 days. It is a
computed-on-read view (no materialization) that stitches together two time windows:

- **Last 24h (hot window):** spend is recomputed *live* from raw auction wins (`spend_log`)
  joined to `impression_log`, then grossed up through the margin-history tables. This is the
  "realtime" part — `cost_impression_log` has not finalized these hours yet.
- **24h → ~3 days ago (warm window):** rows are read straight from the already-finalized
  `cost_impression_log`.

The two windows are `UNION ALL`-ed and are mutually exclusive at the `now_hour - 24h` boundary,
so an impression appears exactly once. Reach for this **only for pacing / operational "what have
we spent in the last few days" questions**. For anything historical or reconciled, use
`cost_impression_log` (source of truth) directly — this view is intentionally short-window and
recomputes on every query.

## Grain & keys
- **Grain:** one row per **impression** over a rolling ~3-day window. Not pre-aggregated — the
  "rollup" in the name refers to the 3-day *window*, not to any GROUP BY. To get pacing totals you
  still `SUM(...) ... GROUP BY advertiser_id/campaign_id/day` yourself.
- **Window bounds:** upper = now; lower = `timestamp(CURRENT_DATE - 3 days)` (midnight 3 calendar
  days ago). So it is really "since midnight 3 days ago," i.e. **3–4 days** of data depending on
  time of day — not a fixed 72h.
- **Key(s):** `impression_id` (STRING) uniquely identifies a row (deduped `QUALIFY row_number()=1`
  per impression in the hot branch; one-per-impression in the warm branch). `time` is the
  filter/window column.

## Column meanings (only the non-obvious ones)
- **`time`** — TIMESTAMP of the auction/impression (the window column). No integer-epoch column is
  exposed by this view (`time_unit: timestamp`); the internal `auction_epoch`/`epoch` are dropped
  before output.
- **`impression_id`** — the auction / TTD impression id (`spend_log.auction_id` =
  `impression_log.ttd_impression_id`). STRING. Sentinel `'-4'` when unresolved.
- **`unlinked`** — BOOL. `TRUE` = this is a won-impression **spend row whose `impression_id` was NOT
  found in `impression_log`** in the window (the win exists but no linked served impression). Derived
  as `IF(shi.ttd_impression_id IS NULL, TRUE, FALSE)` where `shi` is the
  `GROUP BY ttd_impression_id` existence-check subquery — i.e. the `GROUP BY` feeds **only this flag**,
  not the main win↔impression join (see Joins). `FALSE` = matched. Filter `unlinked = FALSE` when you
  only want fully-attributed impressions.
- **`media_cost`** — NUMERIC, USD. Raw media cost paid to the exchange for the win
  (`spend_log.win_cost_micros_usd / 1e6`). This is **MNTN's cost**, not the advertiser's bill.
- **`media_spend` / `data_spend` / `platform_spend`** — BIGNUMERIC, USD. The **advertiser-billed**
  spend decomposed by margin bucket. Non-CPM campaigns: `media_cost` is grossed up to
  `media_cost / (1 - take_rate - partner_margin - data_margin)` and split; CPM campaigns
  (`has_cpm`): derived from `target_cpi`. Their sum ≈ what the advertiser pays. **These embed
  take-rate / margin and are therefore INTERNAL-ONLY** — do not surface externally (see memory
  `feedback_take_rates_sensitive`).
- **`data_spend`** — is **forced to 0 unless the campaign has TPA** (`channel_id = 8` CTV **AND**
  `objective_id = 1` prospecting). Expect `data_spend = 0` for all non-CTV-prospecting rows; not a
  bug.
- **`partner_site`** — cleaned publisher domain / app bundle. For `VIDEO` placements it is the
  `app_bundle` (backslashes stripped); otherwise the site domain with the leading subdomain
  stripped (with a `co.uk` special-case). **Two junk sentinels, not one:** the internal `domain`
  coalesces to the literal string `'-9'` when both `site_domain` and `app_bundle` are NULL
  (non-VIDEO: `coalesce(site_domain, app_bundle, '-9')`); `'-9'` has ≤1 dot so it passes through the
  subdomain-strip `ELSE` branch unchanged and surfaces as `partner_site = '-9'`. The final
  `coalesce(partner_site, '-4')` only maps a NULL to `'-4'` — it does **not** catch `'-9'`. So a clean
  filter must exclude **both** `'-9'` and `'-4'` (e.g. `partner_site NOT IN ('-9','-4')`), not just
  `'-4'`. (The VIDEO branch reads `app_bundle` directly, not `domain`, so its unknown falls straight
  to `'-4'`; `'-9'` is a non-VIDEO artifact.)
- **`advertiser_id` / `campaign_id` / `creative_id`** — INT64. **Negative values are sentinels, not
  real ids;** filter them out (`> 0`) for clean pacing math. Two negative fallbacks with **different
  reach**: `-3` is the win↔impression coalesce fallback and `-4` is the final outer-coalesce fallback.
  `creative_id = coalesce(i.creative_id, -3)` is sourced **only** from `impression_log`, so it
  reliably becomes `-3` on an unlinked win. `advertiser_id`/`campaign_id` fall back to the **win
  (`spend_log`) side first** (`coalesce(i.advertiser_id, w.advertiser_id, -3)`), so they hit `-3` only
  when both the impression side and the spend_log side are NULL — rare, since `spend_log` almost
  always carries advertiser/campaign. So `creative_id = -3`, not `advertiser_id = -3`, is your
  practical "no impression match" signal (or just use the `unlinked` flag).

## Joins & relationships
This view is a **consumer** of the spend pipeline; its own output is impression-grain over ~3 days.

Upstream (what it reads FROM — all bounded to the ~3-day/24h windows internally):
- **`logdata.spend_log`** (hot branch) — grain **one row per auction win** (`auction_id`). The link
  is `clean_wins w LEFT JOIN impression_log i ON i.ttd_impression_id = w.impression_id` **gated by a
  9090/original_aid predicate** — `((i.advertiser_id<>9090 AND i.campaign_id=w.campaign_id AND
  i.original_aid<>9090) OR (i.advertiser_id=9090 AND i.original_aid<>9090))`. Wins with no matching
  impression survive as `unlinked = TRUE`.
- **`logdata.impression_log`** (hot branch) — one row per served impression (`ttd_impression_id`).
  **The join is NOT pre-deduped** — a stray duplicate `ttd_impression_id` would fan the pre-QUALIFY
  join out. One-row-per-`impression_id` is enforced **downstream** by
  `QUALIFY row_number() OVER (PARTITION BY impression_id ORDER BY …) = 1` in `ct_impression_info`
  (and again in `ct_stg_margins` for the margin pick), so the **output** grain is 1:1. The separate
  `GROUP BY ttd_impression_id` subquery (`shi`) is used **only** to compute the `unlinked` flag, not
  to dedup the link.
- **`logdata.cost_impression_log`** (warm branch) — one row per impression; the finalized-cost
  source of truth. This view is essentially "`cost_impression_log` semantics, with the most recent
  24h recomputed live." 1:1.
- **Margin history** (`margins.v_channel_margin_history`,
  `v_advertiser_channel_margin_history`, `v_campaign_group_channel_margin_history`) — time-ranged
  rows; joined then `QUALIFY row_number() ... ORDER BY priority = 1` so exactly one margin row wins.
  No fan-out.
- **Dimension lookups** — `integrationprod.public_campaigns` (channel/objective → `has_tpa`),
  `integrationprod.core_creatives`, `ctv.v_ctv_sites`, `mss.v_select_domains`. Dedup/`LEFT JOIN`;
  no fan-out.

Downstream (joining this view OUT):
- To **campaigns / advertisers** dims on `campaign_id` / `advertiser_id` — dim is 1:N but deduped
  → no fan-out; drop sentinel negatives first.
- To **visits / conversions** on `impression_id` — **1:N, fan-out risk** (one impression can have
  many visits). Aggregate the visit side or expect row multiplication.

## Gotchas
- **Computed on read — no materialization, no partition, no TTL of its own.** Every query
  re-evaluates the full pipeline (spend_log + impression_log + margin joins for 24h, plus
  cost_impression_log for the tail). A `WHERE time ...` clause can only **narrow within** the
  built-in ~3-day window; it cannot widen it and cannot prune the hot-branch recompute below 24h.
- **Not for historical analysis.** Anything older than ~3 days simply is not in the view. Use
  `cost_impression_log` for history/reconciliation.
- **~3 days ≠ 72h.** Lower bound is midnight 3 calendar days ago, so the window is 3–4 days wide
  depending on time of day.
- **Sentinels everywhere:** `advertiser_id/campaign_id/creative_id` `-3`/`-4`, `impression_id`
  `'-4'`, `partner_site` **both `'-9'` and `'-4'`** (`'-9'` is the non-VIDEO `domain` coalesce
  fallback that survives the final `coalesce(...,'-4')`). Exclude negatives before summing or
  grouping — for `partner_site` use `NOT IN ('-9','-4')`, not just `<> '-4'`.
- **`data_spend = 0` for non-CTV-prospecting** by design (data margin zeroed unless `has_tpa`).
- **`media_cost` (MNTN cost) ≠ `media_spend` (advertiser bill).** Do not add them. The advertiser
  bill is `media_spend + data_spend + platform_spend`.
- **Margin-bearing columns are internal-only** (embed take rate) — never expose externally.
- **SQLMesh hashes churn — do not pin them.** Always query the public name
  `` `logdata.realtime_spend_last_3d` ``. As of 2026-07-19 the whole `sqlmesh__logdata` layer was
  mid-rebuild: the public view resolved to a *missing* physical hash and the underlying spend_log /
  impression_log / cost_impression_log snapshots were also on new hashes — so this pass could not
  live-sample rows or pull dry-run byte figures (see Changelog). The transformation logic below is
  verified from the live view DDL.

## Cost & partitioning notes
- **No physical partition or cluster** — this is a view over views. `partition_by: none`. The
  effective cost governor is the **built-in ~3-day `time` window inside the view**, which bounds
  every scan to the last ~3 days of `spend_log`, `impression_log`, and `cost_impression_log`
  regardless of your `WHERE`.
- **The one filter to always apply:** add `WHERE time >= <as-recent-as-you-can>` to trim within the
  3-day window, and **project only the columns you need** — a `SELECT *` drags all four spend
  measures plus the full join tree. But understand the floor: you cannot get below the hot-branch
  24h recompute of `spend_log` + `impression_log` + margins.
- **No dry-run byte figures captured this pass** — the underlying SQLMesh physicals were on missing
  hashes (mid-rebuild), so no dry-run could resolve. `approx_logical_bytes: null` is correct: a
  view has no backing storage. When the layer settles, capture a labeled `SELECT *` vs
  single-column dry-run into `Observed cost`.

## Example queries
```sql
-- Pacing: last-24h advertiser spend (advertiser bill = media+data+platform), sentinels excluded
SELECT
  advertiser_id,
  SUM(media_spend + data_spend + platform_spend) AS advertiser_spend_usd,
  SUM(media_cost)                                AS mntn_media_cost_usd
FROM `logdata.realtime_spend_last_3d`
WHERE time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 24 HOUR)
  AND advertiser_id > 0            -- drop -3 / -4 sentinels
GROUP BY advertiser_id
ORDER BY advertiser_spend_usd DESC;
```
