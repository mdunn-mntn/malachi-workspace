# logdata.clickpass_log

## Purpose
The verified-visit (VV) log. **"clickpass" is the legacy internal name for a verified visit.** One row per MNTN-attributed visit: MNTN served an impression → the user visited the advertiser site within the lookback window → the MNTN pixel matched the visit back to the impression. Per Zach Schoenberger: **visits = clicks + VVs**, MNTN-attributed — NOT page views (that's `guid_log`). Contains ALL VV types: both **CTV and display** (VVs happen for display too). This is the real-time attribution log — "there is no post processing." Reach for it to count attributed visits, trace the winning impression (`ad_served_id`), or get the redirect IP for cross-stage IP work. `ui_visits` is the superset that adds display clicks and non-VV traffic.

## Grain & keys
- **Grain:** one row per attributed verified visit (a visit-touch). The MNTN UI "Total Verified Visits" = raw `COUNT(*)` of this table (~99% match, verified for Avon).
- **Key(s) / join columns:** `ad_served_id` (UUID → the winning ad impression, **last-touch**) is the primary join key. `guid` = user cookie ID. `page_view_guid` = the page-view signal GUID (several clickpass rows per page view). None is a unique row id — see fan-out below.

## Column meanings (only the non-obvious ones)
- **`time` / `epoch`** — VV redirect (attribution) timestamp. **`epoch` is MICROSECONDS** (16-digit; `TIMESTAMP_MICROS(epoch)` lands on the right wall clock; `UNIX_SECONDS(time)` matches 0 rows — so older docs saying "seconds" are WRONG). **But `epoch ≠ UNIX_MICROS(time)` in general — do NOT reconstruct or join on that identity.** It holds exactly ONLY on the `competing_vv` branch (594,520/594,520 on 2026-07-10); on the raw and history branches `time` is truncated to the whole second while `epoch` keeps sub-second precision, so they differ by up to <1s (raw branch 0/662,981 exact on 2026-07-10; history 114/1,551,108 on 2025-06-15). Filter/group on `DATE(time)` or a `time` range — never on `epoch = UNIX_MICROS(...)`.
- **`ip` / `ip_raw`** — **identical by construction.** The view aliases `ip AS ip_raw` in all three branches; 100% equal on sampled days. `ip` = enriched IP at redirect time (the VV/redirect IP). The `ui_visits` ip-vs-ip_raw split does **NOT** apply here — do not treat `ip_raw` as a distinct pre-enrichment value.
- **`ad_served_id`** — UUID of the ad impression that earned attribution; **always last-touch** (most recent impression). Near-unique but NOT a row key (~98.4% distinct per row on 2026-07-10 — one impression can earn multiple visit rows).
- **`first_touch_ad_served_id`** — UUID of the first impression for the user/advertiser. **~53% NULL** (661,959 / 1,257,501 on 2026-07-10). Populated at write time (real-time log, no backfill); the lookup requires a CTV S1 prospecting impression (`funnel_level=1`, `objective_id=1`) in the same campaign group. The high NULL rate is a known targeting/lookup gap, not a design choice. FT vs LT is **lens-invariant at the advertiser total** (one row per visit either way) — it only re-routes which campaign/funnel-stage gets credit.
- **`first_touch_time`** — unreliable. `CAST(NULL AS TIMESTAMP)` in the history and competing_vv branches (so always NULL for pre-2026 rows and competing rows); only the recent raw branch carries a real value. Do not rely on it.
- **`impression_time` / `impression_epoch`** — timestamp of the impression that triggered this VV. **`impression_epoch` is MICROSECONDS** and — unlike bare `epoch` — the view DOES derive it as `UNIX_MICROS(impression_time)` (holds 100%, both branches, 2026-07-10 and 2025-06-15; older docs saying "seconds" are WRONG). The `time − impression_time` gap was observed **0–113 days** on 2026-07-10 — the old "always ≤30 days" claim no longer holds (lookback window widened, ~10→90d+).
- **`is_new`** — new-to-brand (NTB) flag set by the **client-side JS pixel**, NOT a DB lookup. Disagrees with `ui_visits.is_new` **41–56%** of the time — architectural, expected, NOT a data bug.
- **`is_control_group`** — holdout/control-group exclusion flag.
- **`is_cross_device`** — ad served on one device, visit on another (~54% of rows on 2026-07-10). Primary driver of IP mutation between the impression bid IP and the redirect IP.
- **`original_guid`** — pre-reattribution / pre-cross-device guid; NULL in the competing_vv branch; differs from `guid` in ~16% of VVs.
- **`page_view_guid`** — GUID from the page-view signal. ~1.4–2.7 clickpass rows per `page_view_guid` (multiple attribution rows per page view; 798,194 distinct vs 1,257,501 rows on 2026-07-10).
- **`ga_tracking_ids` / `ga_client_ids`** — comma-joined STRINGS (the view does `array_to_string(...,',')` / `STRING_AGG` over the underlying arrays), not single values.
- **`click_elapsed` / `view_elapsed`** — ms since impression / since last view.
- **`viewable`** — was the impression viewable. **`blocked_source`** — IVT/fraud block reason. **`attribution_model_id`** — attribution model used. **`destination_click_url` / `destination_with_suffix`** — final landing URL / with tracking suffix.

## Joins & relationships
- **`ad_served_id` → `event_log` / `cost_impression_log`** (CAST to STRING) for the impression's `bid_ip` and VAST IP. Use a lookback window covering the impression→visit gap (historically ≤30d; now observed up to ~113d — widen accordingly).
- **`ad_served_id` → `CAST(ui_visits.ad_served_id AS STRING)`** with `from_verified_impression = true` for the visit IP.
- **`guid` ↔ `ui_visits.guid`** matches 99.99% (same session context); **`guid` ↔ `event_log.guid`** only ~60% (impression vs visit context differ).
- **Cross-stage IP trace:** S1/S2→S3 targeting uses **`clickpass_log.ip`** (the VV bridge), NOT impression tables — in cross-device cases the VV redirect IP ≠ the impression bid IP, and it is the VV IP that enters the next stage's segment. Fixed the old "92% S3 ceiling" (true ceiling ~99%). clickpass_log has **no `bid_ip` column** (acknowledged gap).
- **Fan-out warnings:** `ad_served_id` is NOT unique (one impression can produce multiple visit rows) and `page_view_guid` carries ~1.4–2.7 rows each. `COUNT(*)` = attributed visit-touch count (≈ the UI's "Total Verified Visits", ~99% match). `summarydata` `sum_by_advertiser` rollups apply tighter last-touch dedup (≈0.78× `COUNT(*)`); CHAPI/client UI adds `competing_*` credit (≈1.276× the rollup, stable across years so it cancels in YoY). Distinct `page_view_guid` undercounts.

## Gotchas
- **Now a 3-branch UNION** (re-versioned since the prose was written; live view def 2026-07-17): `raw.clickpass_log` (`time` ≥ 2026-01-01) **UNION ALL** `raw.competing_vv` (`event_time` ≥ 2026-01-01) **UNION ALL** `history.clickpass_log_physical` (`date_column` ≤ 2025-12-31). The **`competing_vv`** branch injects competitive-scenario VV rows (the `competing_*` credit) — the view is no longer a simple pass-through of one Postgres table.
- **`epoch` and `impression_epoch` are MICROSECONDS**, not seconds. `impression_epoch = UNIX_MICROS(impression_time)` exactly (100% both branches). But **`epoch ≠ UNIX_MICROS(time)` in general** — exact only on the `competing_vv` branch; on raw/history `time` is truncated to the second while `epoch` keeps sub-second precision (differ by <1s). Never join/filter on `epoch = UNIX_MICROS(time)`.
- **`ip_raw` == `ip`** (aliased in every branch) — no separate raw IP here.
- **`first_touch_time` is NULL for all pre-2026 and competing rows**; `first_touch_ad_served_id` is ~53% NULL.
- **No apples-to-apples holdout lift** from this table: a row requires a served impression, so per-advertiser holdout IPs (hash bucket 0–99) essentially can't generate rows for that advertiser → any clickpass "lift" is mechanically enormous. Use `guid_log` for causal (total-traffic) lift; use `clickpass_log` only to quantify **attribution capture** (the wedge = visits MNTN credits that would have happened anyway).
- **Bronze `raw.clickpass_log` holds only ~25% of silver volume** (upstream filter) — always use silver.
- No `dt` partition column — filter on **`time`** (TIMESTAMP).

## Cost & partitioning notes
- **Always filter `time`.** A `time` predicate prunes all three branches (verified: 63.6 GB → 58 MB below).
- Labeled dry-run figures (2026-07-17):
  - `SELECT ad_served_id` (1 narrow col), **no filter** → **63.58 GB** (59.2 GiB).
  - `SELECT ad_served_id` (1 narrow col), **1 day** → **57.8 MB** (55 MiB) — ~1,100× cheaper.
  - `SELECT *` (all 36 cols), **1 day** → **3.88 GB** (3.61 GiB).
- A **1-day** `time` filter scans **~25 partitions**, not 1: 1 DAY partition in the raw branch + 24 HOUR partitions in the `competing_vv` branch (it is HOUR-partitioned) + (0–1 in history if the day is pre-2026). Cost is still small, but partition count looks high.
- Physical partitioning: `raw.clickpass_log` = DAY on `time` (365-day partition expiration); `raw.competing_vv` = **HOUR on `event_time`** (365-day expiration); `history.clickpass_log_physical` = DAY on `time` (**no expiration**). None clustered.
- **Retention:** the history branch (≤2025-12-31) has **no TTL** → full history preserved; the two recent branches (≥2026-01-01) carry a real **365-day partition expiration** (confirmed `expirationMs=31536000000` on both `raw.clickpass_log` and `raw.competing_vv`; history physical `expirationMs=None`). Effective **bottom** floor = the history table's earliest partition. **Forward gap (not permanent):** the recent branches drop partitions older than 365 days and the history branch caps at 2025-12-31, so starting ~2027-01 the early-2026 partitions age out with **no** history coverage → a widening hole in 2026 data unless the pipeline backfills history or extends the model. `ttl_days: null` in front-matter refers only to the view's bottom floor, NOT the recent-branch data.
- Real backing storage (bq show numBytes, summed across the 3 physicals): raw 324 GB + competing_vv 464 GB + history 3.31 TB ≈ **4.10 TB**. Approx rows ≈ 1.38B (sum of physicals).
- GCS: no clean dump — the view is "complicated" (Victor). Read via the Spark BigQuery connector with `materializationDataset=external` + `viewsEnabled=true`; ~200M-row output cap on rows pulled to the driver, aggregations fine.

## Example queries
```sql
-- One day of VVs for an advertiser (always filter `time`)
SELECT ad_served_id, ip, guid, is_cross_device, impression_time
FROM `logdata.clickpass_log`
WHERE time >= TIMESTAMP('2026-07-10') AND time < TIMESTAMP('2026-07-11')
  AND advertiser_id = 31921;

-- Attributed-visit count reconciling to the UI "Total Verified Visits".
-- Cost scales with the `time` window ONLY — advertiser_id is NOT clustered, so an
-- advertiser filter does NOT shrink the scan (dry-run 2026-07-17: 1 month ≈ 0.67 GB;
-- the full Jan–Jun window ≈ 6.0 GB whether or not you add an advertiser_id filter).
-- Narrow `time` to control cost.
SELECT advertiser_id, COUNT(*) AS verified_visits
FROM `logdata.clickpass_log`
WHERE time >= TIMESTAMP('2026-05-01') AND time < TIMESTAMP('2026-06-01')  -- 1 month ≈ 0.67 GB
GROUP BY advertiser_id;
```
