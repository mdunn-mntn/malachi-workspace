# logdata.v_augmentor_log

## Purpose
Silver **VIEW** that thinly wraps the raw bidstream augmentation log
`dw-main-bronze.raw.augmentor_log` (written by the `rtb-augmentor-service`). Every incoming
bid/auction request the augmentor reviews produces one row: the augmentor responds to the exchange
(Beeswax/Magnite) with the applicable MNTN segment IDs + creative specs, and logs the IP, geo,
device, inventory, and segment context it saw. Reach for it to answer **"was this IP seen in the
bidstream recently (is it biddable/eligible)?"**, **"which MNTN segments evaluated this IP pre-bid?"**,
and to build **pre-visit IP features** (e.g. `al_avg_segments`, `al_n_auctions`). It is the pre-bid
side of the funnel — upstream of any bid/win/impression. This augmentor recency stream is one of the
two streams that feed the DS14 "MNTN Global Data" freshness/eligibility filter (the other is
`guid_log`). **The exact recency window is unsettled:** `data_catalog.md` records a **1-day** augmentor
window, while the audience-expression decode in `data_knowledge.md` reads it as **~7 days** — the
conflict is flagged open and AUDI-1117 resolves it empirically. Either way the qualitative role
(a short-lookback biddability/recency gate) holds.

The view is a passthrough of bronze columns **plus** one derivation: it parses the bronze raw `geo`
string into a structured `geo_parsed` STRUCT (see below). It does **not** dedup, re-key, or aggregate.

## Grain & keys
- **Grain:** one row per **upstream bid-request evaluation** (per augmentor auction eval). NOT per
  advertiser, NOT per impression, NOT per IP, and **not deduped**. A single IP produces many rows per
  hour (one per bid request it appeared in).
- **Key(s) / join columns:** no primary key. `ip` is the physical **cluster key** and the natural
  IP-level join column. `mntn_segments.list[].element` (INT64 segment IDs) is the only advertiser-
  relatable signal — join to `audience_segments.expression`/segment_id → advertiser.
- **No `advertiser_id` at the row level** — the augmentor log is per-bid-request, not per-advertiser.

## Column meanings (only the non-obvious ones)
- **`epoch`** — INT64 **milliseconds** since Unix epoch. Verified empirically: `epoch = 1784376233856`
  while `UNIX_MILLIS(time) = 1784376233000` for the same row (13-digit ms scale; `UNIX_MICROS` would be
  16 digits). Anchor: `epoch = UNIX_MILLIS(true event time)`. Note `epoch` actually carries **finer
  precision than `time`**, which is truncated to whole seconds — use `epoch` for sub-second math.
  (Corrects the stale bronze prose note that "augmentor uses microseconds" — it is ms.)
- **`time`** — TIMESTAMP, the **HOUR partition column** and the one filter you must always supply.
  Truncated to whole seconds (sub-second lives in `epoch`).
- **`geo_parsed`** — STRUCT **derived inside the view** by parsing the bronze raw `geo` string (the raw
  `geo` column itself is NOT exposed in silver). Fields: `geo_city`, `geo_country`, `geo_ip` (the geo
  service's echoed IP), `geo_latitude`/`geo_longitude` (FLOAT64 via SAFE_CAST — NULL when unparseable),
  `geo_metro`, `geo_region`, `geo_zip`. When `geo` is empty/short the whole struct comes back all-NULL.
  Because it re-reads the wide raw `geo` string, selecting `geo_parsed` is far more expensive than the
  scalar columns (see Cost notes).
- **`mntn_segments`** — parquet-legacy LIST: `STRUCT<list ARRAY<STRUCT<element INT64>>>`. Array of MNTN
  segment IDs that evaluated this IP pre-bid. **BQ access:** `ARRAY_LENGTH(mntn_segments.list)` and
  `UNNEST(mntn_segments.list) s → s.element` (INT64). Can be large (219 segments on a single row
  observed). **Holdout gotcha:** for a holdout IP the array does **NOT** contain the segment it is a
  holdout of (stripped at eval time) — so presence in the log proves biddability, but absence of a
  given segment ≠ "not targeted." The only path to an advertiser.
- **`pmp`** — parquet-legacy LIST: `STRUCT<list ARRAY<STRUCT<element STRING>>>`. PMP deal IDs on the
  request. Same `.list` / `.element` access.
- **`ip` vs `ipv6`** — separate STRING columns (IPv4 and IPv6). When `ip` is blank, `ipv6` is often
  populated; use `ipv6` as a fallback for blank-IP rows when building IP-level features. `ip` is the
  cluster key.
- **`ifa`** — device advertising identifier (IDFA / AAID) for mobile/CTV requests.
- **`app_bundle` / `site_name` / `domain` / `inventory_source` / `network` / `os` / `device_type` /
  `environment_type` / `placement_type` / `video_placement` / `user_agent`** — bid-request context
  passed straight through from the exchange; free-text, variable fill.

**Bronze-only columns dropped by this view** (must query `bronze.raw.augmentor_log` for them):
`iab_categories`, `categories`, `isp`, `page`, `referrer`, `is_blocked`, `blocking_site`, `hh`,
`time_stamp`, `publisher_id/name/domain`, `_source_file/_batch_id`, and the raw `geo` string.

## Joins & relationships
- **`ip` → any IP-keyed table** (`cost_impression_log.ip`, `guid_log`, `prospecting_scores`, holdout
  hash `MD5('{AID}:{IP}') mod 1000 ∈ 0-99`). **Fan-out: severe.** Grain is per-bid-request, so one IP
  has *many* rows/hour — a raw join on `ip` alone multiplies rows massively. **Dedup to distinct `ip`
  (or aggregate per IP) inside the partition window before joining.** Cluster-on-`ip` makes IP-filtered
  scans cheaper.
- **`mntn_segments.list[].element` → `audience_segments` (expression / segment_id) → advertiser.** The
  ONLY advertiser linkage. `audience_segments` is a small `bronze.integrationprod` dim (filter
  `deleted=FALSE AND is_test=FALSE`). Compound fan-out: many segments per row × many rows per IP —
  aggregate/dedup before joining. Canonical pattern: TI-837 `ti_837_lift_analysis_30adv_7day_v5_segments.sql`.
- **Not the same as `bidder_auction_events` / `logdata.auction_log`.** Those are the newer Rust-bidder
  "auction logs"; `v_augmentor_log` ← `bronze.raw.augmentor_log` is the legacy augmentor stream. (Note:
  `logdata.auction_log` is a *separate* SQLMesh view that references `v_augmentor_log`.)

## Gotchas
- **10-day BQ TTL** and **partition filter on `time` REQUIRED** — a query with no `time` filter errors
  (`Cannot query over table … without a filter over column(s) 'time'`).
- **`epoch` is milliseconds, not microseconds** (corrects stale prose).
- **Per-bid-request grain, not deduped, huge IP fan-out** — never join on `ip` without deduping first.
- **Silver drops bronze-only columns** (`iab_categories`, `categories`, `isp`, `page`, `referrer`,
  raw `geo`, …). Use `bronze.raw.augmentor_log` for IAB/vertical/page work. (IAB fill is only ~20% on
  CTV and generic — TI-791.)
- **Holdout segment-stripping** on `mntn_segments` (above) — biddability yes, targeting no.
- **LIST-struct access differs by engine:** BQ uses `mntn_segments.list` / `pmp.list` + `.element`;
  in Spark on the parquet archive `F.size(F.col("pmp.list"))` fails — use `F.col("pmp").isNotNull()`.
- **Volume (diurnal, period-dependent):** ~1.2-1.3B rows/hr and ~16-19M distinct IPs/hr — measured
  2026-07-18: **1.29B rows / 16.0M distinct IPs / ~81 rows-per-IP** at 12:00 UTC, ~19.2M distinct IPs
  at 00:00 UTC. (The older ~23.6M-IPs/hr figure is a 2026-03-29 reading — it runs high for current
  July hours; distinct-IP count swings with the hour.) `SELECT *` over even one day is ~92 TB — and
  `mntn_segments` is near-`SELECT *` cost — so always project the light columns you need.
- **GCS parquet archive** (~30 days, vs BQ's 10) at
  `gs://mntn-data-archive-prod/augmentor_log/region={east,west}/dt=YYYY-MM-DD/` — for multi-day / heavy
  lift scans read it via **Spark on Databricks** (no BQ 6-hour wall, no scan billing). Read BOTH
  `region=east` and `region=west` for a complete day.

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE time >= TIMESTAMP('…') AND time < TIMESTAMP('…')`
  (narrow to the hours you need), and **project only the columns you need**. Add `ip` predicates to
  exploit the `ip` clustering.
- **Physical partition/cluster/TTL** (from `bq show dw-main-bronze:raw.augmentor_log`): HOUR partition
  on `time`, `requirePartitionFilter=true`, cluster `[ip]`, partition `expirationMs=864000000` (**10
  days**). Physical size ≈ **330.9 B rows / 1.04 PB logical** (rolling 10-day window).
- **Dry-run scan estimates** (fresh dry-runs 2026-07-19 against the 2026-07-18 12:00 UTC hour / full
  day; **each labeled by its exact column set — only same-column-set rows are comparable**; figures
  drift ±5-10% hour-to-hour with diurnal bidstream volume):
  | query | column set | span | est scan |
  |-------|-----------|------|---------:|
  | narrow | `ip, time` | 1 hour | **27.7 GB** |
  | narrow | `ip, time` | 1 day | **666 GB** (≈ prose "~613 GB/day" bidstream read) |
  | geo | `geo_parsed, ip` | 1 hour | **164 GB** (~6× `ip,time`: re-reads the wide raw `geo` string) |
  | segments | `mntn_segments, ip` | 1 hour | **3.39 TB** (~120× `ip,time`, ~20× `geo_parsed`, **≈ `SELECT *`** — the wide array-of-structs is nearly the whole row) |
  | segments | `mntn_segments, ip` | 1 day | **78.9 TB** (= Example #1's day scan — see its warning) |
  | full | `SELECT *` | 1 hour | **3.94 TB** (~140× `ip,time` same span) |
  | full | `SELECT *` | 1 day | **92.6 TB** |
  | any | no `time` filter | — | **hard error** (requirePartitionFilter) |
- Takeaways: partition span moves cost by ~1-2 orders of magnitude, but **column projection only
  helps if you avoid the heavy columns.** The two heavy columns are **`mntn_segments`
  (near-`SELECT *` cost — the wide array-of-structs dominates the row) and `geo_parsed`.** Projecting
  `mntn_segments` does **NOT** keep you cheap, so the advertiser-linkage pattern (Example #1) is a
  full-scan-class query (~79 TB/day). `SELECT *` is never acceptable; multi-day or segment-level scans
  belong on the GCS/Spark path.

## Example queries
```sql
-- Distinct biddable IPs in a segment over a window (dedup FIRST to tame fan-out)
-- COST WARNING: touching mntn_segments is near-SELECT*-cost. This exact query over ONE day
-- scans ~79 TB in BQ (dry-run verified). Narrow the window to the hours you need, or run it on
-- the GCS/Spark path — TI-837 used GCS/Spark precisely to avoid this full-scan-class cost.
SELECT DISTINCT ip
FROM `logdata.v_augmentor_log`, UNNEST(mntn_segments.list) AS s
WHERE time >= TIMESTAMP('2026-07-18 00:00:00 UTC')
  AND time <  TIMESTAMP('2026-07-19 00:00:00 UTC')
  AND s.element = 62308;

-- Cheap "was this IP seen recently?" biddability check (cluster key + narrow window)
SELECT COUNT(*) AS n_bid_requests, MIN(time) AS first_seen, MAX(time) AS last_seen
FROM `logdata.v_augmentor_log`
WHERE time >= TIMESTAMP('2026-07-18 00:00:00 UTC')
  AND time <  TIMESTAMP('2026-07-19 00:00:00 UTC')
  AND ip = '146.71.31.6';
```

## View definition
```sql
-- dw-main-silver.logdata.v_augmentor_log → sqlmesh__logdata.logdata__v_augmentor_log__2626104662 (VIEW)
--   → passthrough of dw-main-bronze.raw.augmentor_log columns, plus geo_parsed derived by parsing
--     the raw `geo` string into STRUCT<geo_city, geo_country, geo_ip, geo_latitude, geo_longitude,
--     geo_metro, geo_region, geo_zip>. No dedup / re-key / aggregation.
SELECT
  app_bundle, device_type, domain, environment_type, epoch,
  /* geo_parsed = parse of raw `geo` string 'k=v,k=v,…' after substr(geo,5,len-5) */
  geo_parsed,
  ifa, inventory_source, ip, ipv6, mntn_segments, network, os,
  placement_type, pmp, site_name, time, user_agent, video_placement
FROM `dw-main-bronze`.`raw`.`augmentor_log`
```
