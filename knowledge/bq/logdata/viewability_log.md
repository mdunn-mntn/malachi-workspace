# logdata.viewability_log

## Purpose
IAB/MRC viewability measurement events for **display** impressions: each display impression that fires the viewability pixel produces a "measurable" event and, if it actually rendered in-view, a "viewable" event. It is the **display equivalent of `event_log`** — reach for it to trace a *viewable display* VV back to its impression (clickpass → viewability_log → win_logs → bid_logs). For *non-viewable* display impressions use `impression_log` instead. **CTV never appears here** — CTV viewability lives in `event_log` VAST events (vast_start / vast_impression). Earliest data 2025-04-08.

## Grain & keys
- **Grain:** one row per **raw viewability measurement event**. There is **no unique key** among the documented columns. A single display impression (`ad_served_id`) produces **~3 rows on the median** — max **65**, and **62.6% of impressions have >2 rows** (measured 2026-07-18 1-hr slice: 1,809,455 rows / 800,764 distinct `ad_served_id`). The measurable (`type=1`) event is logged **multiple times** (avg ~1.6, up to **61** rows/impression); the viewable (`type=2`) event is essentially 1 per impression (up to 4). So neither `ad_served_id` **nor** `(ad_served_id × viewability_type_id)` is unique — the pair had 1,307,019 distinct values over 1,809,455 rows (~1.4× duplication).
- **Impression key:** `ad_served_id` (the display impression id — joins to CIL / impression_log / event_log). **Heavily non-unique** here (median ~3, up to ~65 rows). **Only `GROUP BY ad_served_id` collapses to 1 row/impression** — filtering to a single `viewability_type_id` does **not** dedup (up to 61 type-1 rows survive).
- **`guid` is NOT a per-row/per-event key.** It is 1:1 with `ad_served_id` (every row of an impression shares one guid: distinct `(ad_served_id,guid)` = distinct `ad_served_id` = 800,764) but **coarser** than the impression id — one guid spans **many** `ad_served_id`s (up to **503** in the measured hour; 373,425 distinct guids < 800,764 distinct `ad_served_id`). It is a user/session-level id, useless for row dedup.
- **IP-lineage keys:** `bid_ip` → `bid_logs.ip`; `ip` for user-IP matching.

## Column meanings (only the non-obvious ones)
- **`viewability_type_id`** — the flag this table exists for. `1` = **measurable** (the viewability vendor could measure the impression), `2` = **viewable** (it actually rendered in the viewport per IAB/MRC). Only values are 1 and 2. Type 1 is **almost entirely** the superset of type 2, but not literally always: ~0.01% of impressions have a type-2 row with no type-1 row (70 of 800,764 in the measured hour). **Do NOT compute viewable rate as `COUNTIF(type=2)/COUNTIF(type=1)`** — type-1 rows are duplicated ~1.6× (up to 61× per impression), which deflates that row ratio to ~39-42% (a wrong number). The correct **impression-level** rate uses distinct impressions: `COUNT(DISTINCT IF(viewability_type_id=2, ad_served_id, NULL)) / COUNT(DISTINCT IF(viewability_type_id=1, ad_served_id, NULL))` ≈ **63%** in the measured hour (~63-72% across sampled days). Display-only encoding — CTV never populates it.
- **`epoch_time`** — **MILLISECONDS** since Unix epoch. Verified: sample `1783642767851` == `UNIX_MILLIS(time)` exactly (not seconds, not micros). `time` is the same instant as a TIMESTAMP and is the partition column — prefer `time` for filtering.
- **`ip` vs `ip_raw`** — in the current (2026+, raw-branch) data these are **identical** (100% in the measured slice): the SQLMesh view aliases `ip AS ip_raw`. Only in the pre-2026 history branch is `ip_raw` a genuinely distinct column. Do not treat `ip_raw` as a separate signal for recent data.
- **`bid_ip`** — bid/win-time IP, the denormalized fallback that matches `bid_logs.ip` (Zach-confirmed cross-table `bid_ip` design). Well-populated in current data (~0% NULL in the measured slice). Use in the COALESCE lineage chain when `bid_logs` rows are purged (90d TTL).
- **`original_ip` / `mntn_ip`** — additional IP variants carried through the pipeline (pre-resolution / MNTN-normalized). Present in both branches.
- **`publisher`** — populated in the **2026+ raw branch**; the pre-2026 history branch hard-codes it to `NULL` (the view selects `NULL AS publisher` for history). A NULL `publisher` **almost always** means "old row," not "no publisher" — but not universally: ~0.004% of recent raw rows also carry a NULL publisher (65 of 1,809,455 in the measured 2026 hour), and those same 65 rows also have NULL `bid_ip`.
- **`domain` / `subdomain`** — placement site of the display ad (where the creative rendered).
- **`group_id`** — MNTN campaign-group id; `campaign_id` = MNTN campaign; `advertiser_id` = MNTN advertiser (native MNTN ids here, unlike win_logs' Beeswax ids).
- **`device_type`** — STRING in silver (INT in bronze, per the standard bronze/silver device_type split).

## Joins & relationships
- **→ cost_impression_log / impression_log / event_log** on `ad_served_id` (impression id). Partner grain: those are **1 row per impression**; viewability_log is **median ~3, up to ~65 rows per impression** → joining fans out **~3× typical, up to ~65×** (NOT 2×). **Dedup with `GROUP BY ad_served_id` — the only method that collapses to 1 row.** Filtering to a single `viewability_type_id` does **not** dedup (up to 61 type-1 rows per impression survive). For S1 (CTV) resolution this table is useless — CTV isn't here (advertiser 37775 had zero S1 rows).
- **→ bid_logs** on `bid_ip = bid_logs.ip`. bid_logs is time-partitioned, 90d TTL; when purged, `viewability_log.bid_ip` is the fallback source. Fan-out: an IP is 1:N to bids — join on IP + narrow time window, never IP alone.
- **→ win_logs** (viewable-display lineage step). win_logs uses Beeswax ids with `_alt_id` bridges; join via the impression/auction path, not raw ids.
- **Cross-stage VV trace (display, viewable):** clickpass_log → **viewability_log** → win_logs → bid_logs. Query each table **individually**, not in one UNION ALL job (see Gotchas).

## Gotchas
- **Many rows per impression (not two).** Median ~3, up to ~65 rows per `ad_served_id` — the measurable (type=1) event is logged multiple times (avg ~1.6, up to 61/impression); viewable (type=2) is ~1/impression. Every join on `ad_served_id` risks a **~3×–65× fan-out**. **`GROUP BY ad_served_id` is the only reliable dedup** — filtering `viewability_type_id` does NOT collapse the duplicates.
- **Display only — no CTV.** If a trace returns 0 rows for a CTV advertiser/campaign, that's expected; go to `event_log` VAST events.
- **`ip_raw` is not independent** for 2026+ data (== `ip`). **`publisher` is NULL for all pre-2026 rows** by view construction — not a data-quality gap.
- **No CIDR suffix here.** Unlike `event_log.ip` (which carries `/32`/`/128` on pre-2026 data), viewability_log IPs are bare — exact `ip = 'x.x.x.x'` matching is safe. `bid_ip` is always bare too.
- **Fixed 2025/2026 cutover, not a rolling window.** The silver view is a UNION ALL: raw branch `WHERE time >= 2026-01-01`, history branch `WHERE date_column <= 2025-12-31`. The split is a hardcoded date in the current SQLMesh model (regenerates on rebuild), so the physical hashes rotate — don't hardcode a physical hash.
- **History branch filters on `date_column` (DATE) but the physical is partitioned by `time` (TIMESTAMP).** A user filter on `time` still prunes both branches (confirmed below); a filter on `date_column` would not prune the raw branch (which lacks that column). **Always filter `time`.**
- **`DATE(time)` defeats partition pruning** — use direct `time >= TIMESTAMP('…') AND time < TIMESTAMP('…')`.

## Cost & partitioning notes
- **Partition:** `time`, DAY granularity (both underlying physicals). No clustering on either physical. `require_partition_filter` is not enforced, but **always filter `time`** — the difference is ~1000×.
- **The one filter to always apply:** `WHERE time >= TIMESTAMP('<start>') AND time < TIMESTAMP('<end>')`.
- **Measured (dry-run, `dw-main-silver.logdata.viewability_log`, re-derived 2026-07-19 on the 2026-07-18 partition):**
  - `SELECT guid, time, ad_served_id, viewability_type_id` + **1-day** `time` filter → **3.94 GB** (3,935,992,476 B; day-dependent).
  - Same 4 columns, **no time filter** (full view) → **3.81 TB** (3,806,638,175,536 B, exact/stable). → ~967× penalty for dropping the partition filter; partition = `time` confirmed.
  - `SELECT *` + **1-day** filter → **15.1 GB** (15,146,809,136 B). → SELECT * costs ~3.85× the 4-column slice; project only what you need.
- **Backing storage (bq show numBytes, the two UNION physicals, 2026-07-19):** raw `dw-main-bronze.sqlmesh__raw.raw__viewability_log__2998484813` = ~5.3 TB / 8.13B rows, **365-day** partition TTL; history `dw-main-bronze.history.viewability_log_physical` = ~12.3 TB / 30.58B rows, **no TTL**. `approx_logical_bytes`/`approx_rows` front-matter = the arithmetic **sum** (~17.6 TB / 38.7B) of the two full physicals — an **upper bound on backing storage, not the view-readable count**: the view filters raw to `time>=2026-01-01` and history to `date_column<=2025-12-31`, yet each physical retains rows outside its branch window (raw keeps ~6mo of pre-2026 data under its 365-day TTL), so the overlap is not deduplicated and the view returns fewer rows than this sum.
- **Whole-history single-IP scans are expensive** (TI-650: full `DATE(time)` scan billed ~1.56 TB / 5 min). Narrow the date window and use `TIMESTAMP()`.

## Example queries
```sql
-- Viewable rate for a campaign group over one week (display only).
-- MUST count DISTINCT ad_served_id per type — raw COUNTIF ratios are inflated by
-- type-1 row duplication (~1.6×) and understate viewability by ~20 points.
SELECT
  COUNT(DISTINCT IF(viewability_type_id = 2, ad_served_id, NULL)) AS viewable_imps,
  COUNT(DISTINCT IF(viewability_type_id = 1, ad_served_id, NULL)) AS measurable_imps,
  SAFE_DIVIDE(
    COUNT(DISTINCT IF(viewability_type_id = 2, ad_served_id, NULL)),
    COUNT(DISTINCT IF(viewability_type_id = 1, ad_served_id, NULL))
  ) AS viewable_rate
FROM `dw-main-silver.logdata.viewability_log`
WHERE time >= TIMESTAMP('2026-07-10') AND time < TIMESTAMP('2026-07-17')
  AND group_id = <cg_id>;

-- Trace a viewable display impression's IP. GROUP BY ad_served_id is the only
-- reliable dedup (an impression can have many rows). Caveat: an ad_served_id may
-- carry multiple rows with differing ip/bid_ip — ANY_VALUE picks one arbitrarily.
-- If IP lineage must be exact, inspect all rows (below) instead of ANY_VALUE.
SELECT ad_served_id, ANY_VALUE(bid_ip) AS bid_ip, ANY_VALUE(ip) AS ip
FROM `dw-main-silver.logdata.viewability_log`
WHERE time >= TIMESTAMP('2026-07-10') AND time < TIMESTAMP('2026-07-11')
  AND viewability_type_id = 2
GROUP BY ad_served_id;
```
