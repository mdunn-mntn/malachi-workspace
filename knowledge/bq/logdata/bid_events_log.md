# logdata.bid_events_log

## Purpose
Analytics-friendly, typed view over the **Beeswax bid-price firehose** (`dw-main-bronze.raw.bid_price_log`, `partner_id`=8). Every candidate bid the Beeswax bidder *evaluated* is logged here — overwhelmingly (~98%) attempts that **failed a threshold** (e.g. `invalidCampaignIntentScore`, `ghost-bid`) and never went out, plus the ~1.8% that computed a price (`has_price=TRUE`). Reach for it to study **pre-auction bid behavior**: why bids were suppressed, threshold-failure reasons, ghost-bid holdout exposure, price computation, pacing/recency gates. It is **not** a won-impression log — for wins + cost use `spend_log` / `cost_impression_log`.

**Live-view drift (2026-07-19, this crawl):** the current view definition (hash `__3246330235`) is **`bid_price_log` ONLY**. Its own OPTIONS description states: *"view over bid_price_log (beeswax, partner_id=8). The bidder_bid_events (mntn bidder, partner_id=79) branch was removed because that source is disabled."* Older prose describing a `bidder_bid_events UNION ALL bid_price_log` (hash `__772626469`) and "nearly empty / only advertiser 32167" is **stale** — see Gotchas.

## Grain & keys
- **Grain:** one row per **Beeswax bid-price evaluation event** (one candidate bid the bidder considered). Not deduped; multiple rows per auction/advertiser/second are normal (one per candidate evaluated). **No row-unique key exists in this view.**
- **Key(s):** `auction_id` is the only real key — it **groups the candidates of one auction** (verified 2026-07-18 12:00–13:00 UTC: 670,746,046 distinct over 2.88B rows; a few are empty strings, no NULLs; it is 1:N, not a unique row id). **`bid_id` and `exchange_auction_id` are DEGENERATE — a constant empty string `""` on 100% of rows** (verified: 1 distinct value each, 0 NULLs). Both are leftovers of the removed Rust-bidder branch; the view computes `exchange_auction_id = COALESCE(bid_id, uuid)` but `bid_id=""` is never NULL so it never falls through to `uuid`. Never dedup on `bid_id` (no-op) and never join on `bid_id`/`exchange_auction_id` (matches all-to-all → catastrophic fan-out).
- **Verified scale (1-hour slice 2026-07-18 12:00–13:00 UTC):** 2,875,839,402 rows · **1,525 distinct advertisers** · `partner_id`=8 only · `has_price=TRUE` on 51,689,982 (~1.8%) · `threshold_failure_reasons` populated on 2,824,149,420 (~98.2%).

## Column meanings (only the non-obvious ones)
- **`time`** — event TIMESTAMP, the **partition column** (HOUR). Truncated to whole seconds; the sub-second precision lives in `epoch`/`auction_epoch`.
- **`epoch`** — bid-event time in **MILLISECONDS** since unix epoch (13 digits). Verified: `1784376046252` = `UNIX_MILLIS(time)` (1784376046000) + 252 ms.
- **`auction_epoch`** — auction time in **MICROSECONDS** (16 digits). Verified: `1784376046195173` ≈ `UNIX_MICROS(time)`; precedes `epoch` (auction fires, then the bid-price event is logged ~tens of ms later). **Different unit from `epoch` in the same row** — do not assume a shared unit.
- **`partner_id`** — **hardcoded constant 8** in the view (Beeswax). Never a discriminator here; the MNTN Rust-bidder (partner 79) leg is not present.
- **`has_price`** — BOOL. TRUE (~1.8%) = a bid price was computed / submitted; FALSE (~98%) = candidate was filtered before pricing.
- **`threshold_failure_reasons`** — STRING; the reason(s) the bid attempt was suppressed. **Can hold MULTIPLE comma-joined reasons** (verified: `dailySpendPacing, cappedOrPaced` = 348.5M rows/hr, `dailyTermSpendRateLimited, cappedOrPaced` = 157M, `dailyImpressionPacing, cappedOrPaced` = 76.9M, …) — so **exact-equality on a single component silently under-counts**; use `LIKE '%cappedOrPaced%'` / `CONTAINS_SUBSTR(...)` for compound reasons. Values are **camelCase**; the **ghost-bid holdout** marker is `threshold_failure_reasons = 'ghostBid'` — **NOT** `'ghost-bid'` (that literal returns ZERO rows). Verified 2026-07-18: `ghostBid` = 4,274,757 rows/hr; `ghost-bid` absent from the complete 21-value set. Empty string `""` (not NULL) on rows that passed all gates = exactly the `has_price=TRUE` rows (51,689,982/hr). This is the primary "why no bid" column.
- **`price`** — INT64 scaled bid price (integer micro-units, e.g. 8932); only meaningful when `has_price=TRUE`.
- **`campaign_id`** — view computes `COALESCE(campaign_id, alternative_line_item_id)` from the raw source.
- **`bid_id`** — **DEGENERATE: constant empty string `""` on 100% of rows** (verified: 1 distinct value, 0 NULLs, len 0) — a removed-Rust-branch leftover. Not a row id, not a key. Never dedup or join on it.
- **`exchange_auction_id`** — view computes `COALESCE(bid_id, uuid)`, but the OUTPUT is **degenerate**: `bid_id=""` is never NULL so `COALESCE` never falls through to `uuid` → constant empty string `""` on 100% of rows (verified: 1 distinct value, 0 NULLs). **Not a usable join key** — use `auction_id`.
- **`recency_threshold`** — sourced from `recency_threshold_millis` → value is in **milliseconds**.
- **`flight_end_timestamp`** — DERIVED: `flight_end_time` (ms) is regex-extracted from `agent_params`, ÷1000, `TIMESTAMP_SECONDS`. Convenience only.
- **`ip`** — enriched IP; also the **cluster key** of the physical table.
- **Structurally-ALWAYS-NULL columns** (hardcoded `CAST(NULL …)` in the view — they belonged to the removed bidder_bid_events branch or don't exist in bid_price_log): `app_bundle`, `app_id`, `app_name`, `auction_type`, `device_ua`, `ifa`, `impression_bid_floor`, `placement_type`, `pmp_deal_bid_floor`, `publisher_domain`, `publisher_id`, `publisher_name`, `region`, `segment_id`, `targeted_segments`, `term_id`, `term_ids`, `is_test`. They exist in the schema but carry no data — never filter/join on them.
- **Degenerate constant-empty-string columns (distinct from the NULL ones above):** `bid_id` and `exchange_auction_id` are the empty string `""` on 100% of rows (not NULL) — also removed-branch leftovers. Never dedup or join on them.

## Joins & relationships
- **Backing source — `dw-main-bronze.raw.bid_price_log` (1:1).** This view is a straight per-row projection of that physical TABLE (no UNION anymore), so there is no fan-out from the source; the view row count = the source row count for the same window.
- **`bidder_bid_events` / `bid_logs_enriched` (MNTN Rust-bidder leg, partner ~79) — SIBLING, NOT joined here.** Historically `bid_events_log` UNION-ALL'd this branch; it was **removed (source disabled)**. To analyze MNTN-bidder bid events, query `bidder_bid_events`/`bid_logs_enriched` directly — they are a separate physical with their own partition/TTL. The two logs are complementary halves of "all bid attempts", not duplicates.
- **`bid_attempted_log` — prose claims "same view as bid_events_log"; treat as STALE/unverified.** That alias resolves to a different sqlmesh hash; since this view was redefined to Beeswax-only, the parity claim needs re-checking (out of scope for this doc).
- **Won impressions + cost → `spend_log` / `cost_impression_log`.** `has_price=TRUE` marks a *submitted* bid, not a win. Link candidate → win/spend via **`auction_id`** (the only real key here — `exchange_auction_id` is a constant empty string, see Column meanings). **Caveat, but MISATTRIBUTED in older prose:** the "`auction_id` did not match `event_log.td_impression_id` (0/50)" forensic trace (data_catalog, adv 37775) was measured on the **now-removed Rust-bidder leg (`bidder_bid_events`)**, not on today's Beeswax-only `auction_id`, so it does not necessarily apply here. Still verify any `auction_id`→win join empirically before relying on it.
- **Ghost-bid lift (`silver.enriched.lift__ghost_bid_*`)** is built from this **same** Beeswax source (`bronze.raw.bid_price_log`); the ghost-bid holdout rows are exactly the `threshold_failure_reasons = 'ghostBid'` rows here (camelCase — see Column meanings).
- **Fan-out risk:** this is a ~2.9B-rows/hour firehose that is ~98% failed attempts. Any join on `ip` (the cluster key) or `auction_id` is **massively 1:N** — always pre-filter (`has_price`, a specific `threshold_failure_reasons`, a narrow `time` window, a specific `advertiser_id`) before joining.

## Gotchas
- **10-day TTL + `require_partition_filter=TRUE`.** Only the last ~10 days exist, and a query without a `time` filter **errors** (not just expensive). No long history — for anything older than 10 days this source is gone (use ghost-bid materialized tables or spend/impression logs).
- **Firehose — `SELECT *` for ONE hour = 3.21 TB.** Always project only the columns you need and keep the `time` window tight (one hour = ~2.9B rows).
- **~98% of rows are FAILED bid attempts** (`threshold_failure_reasons` populated, `has_price=FALSE`). This is an *attempt/evaluation* log, not a won-bid log — filter on `has_price` or a specific failure reason for whatever you actually want.
- **Beeswax-only now (`partner_id`≡8).** The MNTN Rust-bidder (partner 79 / `bidder_bid_events`) branch was removed as disabled. **STALE prose to ignore:** (a) "VIEW → bidder_bid_events UNION ALL bid_price_log"; (b) "nearly empty — only advertiser 32167" (live: 1,525 advertisers/hour, 32167 absent from the sampled hour).
- **`is_test` is always NULL** on this view → you **cannot** exclude test/QA auctions here.
- **Many columns are structurally NULL** (see Column meanings list) — they are schema placeholders from the removed branch, never populated.
- **`bid_id` and `exchange_auction_id` are a constant empty string `""`** (100% of rows, not NULL — removed-branch leftovers). `bid_id` is NOT a row-unique id and `exchange_auction_id` is NOT a join key; dedup on `bid_id` is a no-op and joining on either matches all-to-all → catastrophic fan-out. Use `auction_id` (the only real key).
- **`threshold_failure_reasons` is camelCase AND multi-valued.** The ghost-bid holdout marker is `'ghostBid'`, NOT `'ghost-bid'` (kebab-case `'ghost-bid'` matches zero rows). Pacing/cap reasons are comma-joined compounds (e.g. `'dailySpendPacing, cappedOrPaced'`) — exact-equality on a component under-counts; use `LIKE`/`CONTAINS_SUBSTR`.
- **Mixed epoch units in one row:** `epoch`=milliseconds, `auction_epoch`=microseconds; `time` is truncated to the second.
- **No row-unique key:** grain is per-candidate; `auction_id` (670M distinct/hr) groups the candidates of one auction (1:N), it is not a unique row id, and `bid_id` is a degenerate empty string (above).

## Cost & partitioning notes
- **Backing physical: `dw-main-bronze.raw.bid_price_log`** — HOUR partition on **`time`**, `require_partition_filter=TRUE`, clustered on **`ip`**, 10-day partition expiration. `bq show`: numRows ≈ **716,848,561,322** (~717B, 10-day rolling), numBytes ≈ **1,063,195,587,459,469** (~1.06 PB backing storage). Partition confirmed empirically: same 5-col query over 1h = 135 GB vs 2h = 268 GB (~linear in the `time` window).
- **The one filter to always apply:** a tight `time` range (hour or day). Then project only needed columns — SELECT-* penalty is ~24×.
- **Cost figures — 1-hour slice (2026-07-18 12:00–13:00 UTC), via `logdata.bid_events_log`, `--dry_run` unless noted:**
  - `SELECT *` → **3,212,589,747,512 B (~3.21 TB / 2.92 TiB)**
  - 5 narrow cols (`time, epoch, auction_epoch, advertiser_id, ip`) → **135,083,582,577 B (~135 GB)**; same cols over 2 hours → 268,257,818,843 B (~268 GB)
  - 1 col (`ip`) → **66,063,436,929 B (~66 GB)**
  - **actual run** (aggregate over `advertiser_id, partner_id, has_price, threshold_failure_reasons`, 1 hour) → **120 GB billed**, 7.4s wall, ~1,248 slot-s.
- `ip` clustering helps single-IP lookups within a partition (not measured here); it does **not** help time-range scans.

## Example queries
```sql
-- Ghost-bid holdout exposure for one advertiser, one hour (project narrow, filter time)
SELECT advertiser_id, campaign_group_id, ip, auction_id, household_score, price, has_price
FROM `logdata.bid_events_log`
WHERE time >= TIMESTAMP('2026-07-18 12:00:00') AND time < TIMESTAMP('2026-07-18 13:00:00')
  AND threshold_failure_reasons = 'ghostBid'   -- camelCase; 'ghost-bid' returns ZERO rows
  AND advertiser_id = <AID>;

-- Threshold-failure breakdown for one day-hour (why bids were suppressed)
SELECT threshold_failure_reasons, has_price, COUNT(*) n
FROM `logdata.bid_events_log`
WHERE time >= TIMESTAMP('2026-07-18 12:00:00') AND time < TIMESTAMP('2026-07-18 13:00:00')
GROUP BY 1,2 ORDER BY n DESC;
```
