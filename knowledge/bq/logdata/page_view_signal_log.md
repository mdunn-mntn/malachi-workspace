# logdata.page_view_signal_log

## Purpose
Structured page-view-signal events landed from a pixel vendor. Each row is one pixel fire on an
advertiser's site: which visitor cookie (`guid`), what page (`url`), for which advertiser, from which
data source. It is the silver-facing, column-projected view of the raw landing table.

**Do NOT confuse this with the MNTN first-party pixel (`guid_log`, DS23).** Empirically, the entire live
90-day window of this table is **DS41 = Freshpaint** (a third-party pixel vendor) — 20.1M rows, 0 rows of
any other data source. `guid_log` is a separate, far larger pipeline (107B rows, DS23). This table is a
`site_visit_signal`-style vendor landing, not the first-party click/visit log. Reach for it to inspect
Freshpaint page-view telemetry (visitor guid, landing url, occasional linked impression id); reach for
`guid_log` for MNTN's own pixel visits and for incrementality work.

## Grain & keys
- **Grain:** one row per page-view signal event (one pixel fire).
- **`event_id` is NOT unique** — on a recent 1.5-day slice, 10,975 rows carried only 8,788 distinct
  `event_id` (~20% repeats). Dedup on `event_id` (e.g. `ROW_NUMBER`) if you need one row per event.
- **Natural join keys:** `guid` (first-party visitor cookie, 100% populated, many rows per guid),
  `advertiser_id`, `data_source_id`, `ad_served_id` (impression id, sparse ~1.3%).

## Column meanings (only the non-obvious ones)
- **`time`** — derived in the view as `TIMESTAMP_MICROS(epoch)` off the raw `epoch` column, i.e. the raw
  `epoch` is **MICROSECONDS** (sample `epoch=1784398664309010` → `2026-07-18 18:17:44`). This is the event
  timestamp, NOT the partition (see Cost & partitioning).
- **`guid`** — the first-party visitor cookie, extracted by the view from `ids.list` where `element.name =
  'Guid'`. 100% populated. A visitor can fire many page views → many rows per `guid`.
- **`ip`** — extracted by the view from `ids.list` where `element.name = 'Ip'`. For DS41 this is the
  placeholder **`'0.0.0.0'` on 100% of rows** — there is no usable IP in this table. (The raw table has no
  top-level `ip` column at all; the view synthesizes it from the `ids` struct.) Do not use this column as
  an IP for joins/identity; use `guid`.
- **`ad_served_id`** — extracted from `ids.list` where `element.name = 'Impression'`; the MNTN served-
  impression id when the page view is tied to an ad. **Sparse — populated on only ~1.3% of rows.** NULL
  means the page view was not linked to an MNTN impression (organic / other-channel visit).
- **`ids`** — the raw untransformed struct the derived columns are pulled from: `ids.list[].element` =
  `{id, name, type}` name/value pairs (`Guid`, `Ip`, `Impression`, …). The view flattens the common three;
  read `ids` directly for anything else.
- **`url`** — the page the pixel fired on; 100% populated for DS41.
- **`referer`** — **always empty/NULL for DS41 (Freshpaint sends none).** Do not rely on it.
- **`query_str`** — url query string; sparse.
- **`user_agent`** — parsed struct (`browser`, `device_type`, `operating_system`, `raw`, `advanced`, …);
  fields are STRING (`is_mobile_device` is a STRING, not BOOL).
- **`data_source_id`** — pixel source. Live window is **100% `41` (Freshpaint)**; decode via
  `integrationprod.data_sources` (23=guid_log/"MNTN Pixel", 30=augmentor_log, 39=Klickly, 40=33Across API,
  41=Freshpaint, 42=MNTN Select).
- **`account_id`** (raw only, dropped by the view) — 100% NULL for DS41 despite prose calling it "present
  only at raw level"; the column exists but is unpopulated here.

## Joins & relationships
- **View → physical:** `logdata.page_view_signal_log` → SQLMesh view
  `sqlmesh__logdata.logdata__page_view_signal_log__461032789` (itself a VIEW, physical numRows 0) →
  **`dw-main-bronze.raw.page_view_signal_log`** (the real backing TABLE). Query the raw table directly when
  you need partition pruning (see below).
- **`guid` → `logdata.guid_log.guid`** — same first-party cookie space. Partner grain **1:N** (guid_log is
  ~107B rows total across all guids, many pageview rows per guid over time); fan-out is large — always
  window guid_log by `time` and/or aggregate before joining. These are two different tables: this one is a
  vendor (Freshpaint) signal, not guid_log's MNTN pixel stream.
- **`advertiser_id` → `integrationprod.advertisers.advertiser_id`** — dim lookup, **1:1**. Filter the dim
  `deleted=FALSE AND is_test=FALSE`; `company_name` lives there. The live 90-day window has **8 distinct
  `advertiser_id`s**: 7 are real advertisers (37963 growtherapy = 96.6% of rows, 38682 UnitedHealthcare,
  60093 Healthfirst, 58831 Holavida Health, 47487 UHC South Florida, 42473 FORHUMANITY, 68027 Bento) and
  **`advertiser_id=1` (59 rows) is NOT in the advertisers dim** (`company_name`/`deleted`/`is_test` all
  NULL) — an INNER join on this key silently drops those rows; LEFT-join if you need them.
- **`data_source_id` → `integrationprod.data_sources.data_source_id`** — dim lookup, 1:1.
- **`ad_served_id` → `logdata.cost_impression_log.ad_served_id`** — links a page view to its served MNTN
  impression when present (~1.3% of rows). Both sides carry the same UUID impression id (e.g.
  `5714f27a-249b-4cb7-b2da-02ee177dd110` → cost_impression_log advertiser 68027, campaign 643341); the
  `advertiser_id` matches across the join. Partner grain ~1:1 on the impression id but this side is mostly
  NULL, so an inner join keeps only the ~1.3% linked rows. (Live-spot-verified 2026-07-19: sampled populated
  ids joined with matching `advertiser_id`; filter cost_impression_log on `time` — it does not expose
  `_PARTITIONTIME`.)
- **`ip` is unusable for joins** (`'0.0.0.0'`). Identity must go through `guid`.

## Gotchas
- **`event_id` is not unique** (~20% duplicate rate on a recent slice) — dedup before counting distinct
  events.
- **`ip` is `'0.0.0.0'` on 100% of rows** — not a real IP. Use `guid`.
- **`referer` and `account_id` are empty/NULL** for the live DS41 data.
- **This is NOT `guid_log`.** The catalog/prose label "page view signals from MNTN pixel" is misleading:
  the live data is 100% DS41 Freshpaint (third-party vendor), 0 rows of DS23. The MNTN first-party pixel is
  `guid_log`. Don't use this table as a proxy for MNTN pixel visits or for incrementality.
- **90-day TTL** — only ~last 90 days exist (live: event min `2026-04-21`, max `2026-07-20`). No history
  beyond that in BQ.
- **`_PARTITIONTIME` is ingestion-time and ≥ event time** — the event lands in its ingestion-hour bucket, so
  `_PARTITIONTIME` runs slightly *after* the event (on the `_PARTITIONTIME`=2026-07-18 partition, event-time
  = `TIMESTAMP_MICROS(epoch)` spans `2026-07-17 23:19` → `2026-07-18 23:29`). A lower-bound
  `WHERE _PARTITIONTIME >= '<D>'` is a correct, safe **cost** prune (it never drops wanted rows), but it is
  **NOT an exact event-day selector**: a bounded `[D, D+1)` `_PARTITIONTIME` window over-includes ~the last
  hour of D-1's evening and can drop D's late-evening events whose ingestion pushed them into D+1's 00:00
  partition. For exact day-scoping add a companion filter on `time` (= `TIMESTAMP_MICROS(epoch)`).

## Cost & partitioning notes
- **Partition = ingestion-time `_PARTITIONTIME` (HOUR granularity) on the raw physical — there is NO named
  partition field.** The silver view exposes `time` (= `TIMESTAMP_MICROS(epoch)`) but does **NOT** expose
  `_PARTITIONTIME`, so **you cannot prune through the silver view.** No clustering. `require_partition_filter`
  is off (full scans are allowed — and easy to trigger by accident).
- **THE ONE FILTER TO ALWAYS APPLY:** query the raw table
  `dw-main-bronze.raw.page_view_signal_log` with **`WHERE _PARTITIONTIME >= TIMESTAMP('<date>')`**. That is
  the only way to prune this table.
- Measured (each labeled with its exact column set; only same-column-set rows are comparable):
  - `SELECT * FROM logdata.page_view_signal_log` (all cols, no filter): **7.44 GB** (dry-run) — the `ids`
    struct passthrough makes `SELECT *` heavy; avoid it.
  - `SELECT event_id FROM logdata.page_view_signal_log` (1 col, no filter): **2.48 GB** (dry-run).
  - `SELECT event_id … WHERE time >= '2026-07-18'` (1 col, filtered on view `time`): **2.64 GB** (dry-run)
    — **NOT smaller** than the unfiltered 1-col scan → confirms the view `time`/`epoch` filter does not
    prune (it even reads `epoch` on top).
  - `SELECT event_id FROM dw-main-bronze.raw.page_view_signal_log` (1 col, no filter): **1.33 GB** (dry-run).
  - `SELECT event_id … WHERE _PARTITIONTIME >= '2026-07-18'` (1 col, 1-day prune): **724 KB** (dry-run) —
    ~1800x smaller. This is the only filter that works.
- `approx_logical_bytes` = 10.56 GB = raw physical `numBytes` (real backing storage across the ~90-day TTL).

## Example queries
```sql
-- Correct: prune on the raw table via _PARTITIONTIME, then dedup event_id.
SELECT event_id, TIMESTAMP_MICROS(epoch) AS event_ts, advertiser_id, data_source_id,
       (SELECT e.element.id FROM UNNEST(ids.list) e WHERE e.element.name = 'Guid') AS guid,
       url
FROM `dw-main-bronze.raw.page_view_signal_log`
WHERE _PARTITIONTIME >= TIMESTAMP('2026-07-18')
QUALIFY ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY epoch) = 1
```
