# logdata.spend_log

## Purpose
Output of the MNTN bidder's spend/billing pipeline: one record per **won auction** with its realized cost. This is the **source of truth for spend** — reach for it for any spend-vs-budget question: step-9 pacing (`SUM(win_cost_micros_usd)/1e6 ÷ budget`), deliverability, spend by advertiser/campaign/flight, and won-impression volume. `win_cost_micros_usd` is the spend numerator. Along with `win_logs`, it is one of the two source tables that feed `cost_impression_log` (CIL), and the BOS pacing service reads live `spend_log` (24h lookback) before switching to CIL. For impression-level cost joined to geo/device/segment, prefer CIL; for the raw won-auction spend record, use this.

## Grain & keys
- **Grain:** one row per **won auction**. Empirically 1:1 with `auction_id` (2,893,237 rows == 2,893,237 distinct `auction_id` in a 1-hour slice, 2026-07-15).
- **Row / join key:** `auction_id` (= `<exchange_id>.<auction_id>`, aka mntn_auction_id) — the reliable 1:1 key **for spend_log itself**. Join **1:1 to `bidder_auction_events`** (verified 1:1 on `auction_id`). **`bidder_bid_events` is bid-decision grain (N rows per auction — one per bid + no-bid decision), NOT 1:1** — joining to it on `auction_id` alone fans out and multiplies spend; restrict to the winning bid or add `advertiser_id`/`campaign_id` (see Joins).
- **Do NOT key on `bid_id`** — NULL/empty on ~98.5% of rows in current data (2.85M of 2.89M in the sample), despite being a uuidv7 where present.
- **Do NOT key on `impression_id`** — it is a low-cardinality in-auction ordinal ("1","2","3"…), not a render-impression id (see Column meanings / Gotchas).

## Column meanings (only the non-obvious ones)
- **`win_cost_micros_usd`** — realized clearing cost in **micros USD**; `÷ 1e6 = dollars`. `SUM(...)/1e6` = total spend. Verified scale (2026-07-15 00h, 2.89M rows): range **309–50,000 micros**, quartiles 309 / 1,160 / **7,000 (median)** / 9,900 / 50,000 = **~$0.31–$50 CPM, median ~$7 CPM** — a wide envelope (sub-$0.40 floor wins up to $30–$50 CTV wins), so do not treat a narrow $1–$11 band as the bounds. Never NULL / never 0 and always `≤ bid_price_micros_usd` in the sampled hour. This is the spend numerator.
- **`bid_price_micros`** — bid price in micros, **local currency**. **`bid_price_micros_usd`** — same in USD; equal to `bid_price_micros` for US (USD) traffic. `win_cost_micros_usd ≤ bid_price` (win clears at/below bid).
- **`auction_epoch`** — **NANOSECONDS** (epoch). Verified: `1784076838024488000 / 1e9` → `2026-07-15 00:53:58` = `auction_timestamp` exactly. Per-table epoch units differ (bidder_bid_events.auction_epoch is micros) — prefer the TIMESTAMP columns for time math.
- **`auction_id`** — `<exchange_id>.<auction_id>`, aka mntn_auction_id (MNTN's composite id). **`exchange_auction_id`** — raw auction id from the exchange itself.
- **`auction_timestamp`** — UTC; auction receipt time (**the partition key**). **`impression_timestamp`** — UTC; time the impression rendered. **`creation_timestamp`** — UTC; win-notification receipt time, can lag the auction by hours (sampled 00:53 → 04:44, ~4h later).
- **`time`** — a byte-for-byte copy of `auction_timestamp` (silver naming convention). **It is NOT the partition** and filtering on it does not prune (see Cost notes) — always filter `auction_timestamp`.
- **`impression_id`** — a small **in-auction ordinal** ("1","2","3"…) = which impression slot in the multi-imp bid request was picked, NOT a globally-unique render-impression id. Populated on all rows but ~11,700 distinct/hour; value "1" alone is ~60.7% of rows. Do not use as a unique or join key.
- **`is_test`** — TRUE = test/QA auction, **not billable → exclude**. Almost always NULL in production (≈98.9% NULL, ~1.1% FALSE, TRUE rare); NULL/FALSE = production/billable. Filter `is_test IS NOT TRUE` (not `= FALSE`).
- **`auction_type`** — first-price vs second-price. **`partner_id`** — Beeswax vs MNTN bidder (→ `bronze.integrationprod.core_partners`). **`deal_id`** — aka `pmp_deal_id`. **`data_center`** — region the bidder ran in. **`bronze_ingestion_timestamp`** — when the bronze layer ingested the row.
- **`model_params`** — string blob of bidder scoring params built for the silver model; parse it for RTC detection (`model_params ~ 'realtime_conquest_score=10000'`).
- **`advertiser_intent_score` / `campaign_intent_score` / `segment_intent_score` / `segment_intent_score_ttl`** — per-win intent scores captured at bid time. **`term_id`** — targeting term picked when placing the bid. **`product_id`** — MNTN product (→ `bronze.integrationprod.core_products`; 1=PTV/2=Select/3=QuickFrame). **`device_type`** — already-joined STRING label (→ ENUM `bronze.integrationprod.device_type`).

## Joins & relationships
- **→ `bidder_auction_events`** on **`auction_id`** — genuinely **1:1** (verified 1:1 on `auction_id`), the safe join. **→ `bidder_bid_events`** is **bid-decision grain** (data_catalog: "all bid decisions … bid + no-bid", one row per bid decision) → **N rows per `auction_id`**, so joining on `auction_id` alone **fans out and inflates `SUM(win_cost_micros_usd)`** by the bid-multiplicity factor; restrict to the winning bid or add `advertiser_id`/`campaign_id`. `bid_id` (the true per-bid key) is empty on ~98.5% of spend_log rows and so cannot rescue the join from the spend_log side — aggregate spend first, or join on the auction table instead.
- **→ dims** on `advertiser_id`, `campaign_id`, `campaign_group_id`, `creative_id`, `flight_id`, `term_id`, `product_id`, `partner_id` → `bronze.integrationprod` (or `silver.core.*`). Any spend → flight on `flight_id` → `core_flights` (budget period). These are many-rows-to-one (each won auction carries the dims), so aggregate spend first, then join — joining raw rows to dims fans nothing out but scans the whole partition.
- **→ `cost_impression_log` (CIL):** spend_log is one of CIL's two source tables (with `win_logs`); CIL enriches impressions with geo/device/segment and is the better table for impression-level cost. **Do not try to join spend_log to `impression_log`/CIL on `impression_id`** — spend_log's `impression_id` is an in-auction ordinal, not the render-impression id CIL keys on.
- **Related tables:** `spend_log_tmp` (short-term staging in logdata), and the pacing/`spend_pacing` path (BOS reads live spend_log with a 24h lookback; `realtime_spend_last_3d`-style rollups derive from it). Compare with `win_logs` (Beeswax external win-notification perspective) and `cost_impression_log` (enriched, 90-day rolling).

## Gotchas
- **`time` is NOT the partition** — it duplicates `auction_timestamp`'s value but is a plain column; filtering it scans full history (dry-run proved a 1-day `time` filter costs *more* than no filter — see Cost). A prior prose note (data_catalog.md ~L1950, TI-1037) called `time` "the partition field" — that is wrong; the partition is `auction_timestamp`. Always date-filter `auction_timestamp`.
- **`impression_id` is an in-auction ordinal**, not a unique impression id — do not dedup on it or join it to impression_log/CIL.
- **`bid_id` is empty on ~98.5% of rows** — not a usable join/dedup key in current data; use `auction_id`.
- **`is_test` is almost always NULL** in production (not FALSE) — exclude with `is_test IS NOT TRUE`, never `is_test = FALSE` (that drops ~98.9% of real rows).
- **Late-arriving wins:** `creation_timestamp` (win-notification receipt) can trail `auction_timestamp` by hours, so a just-closed `auction_timestamp` hour partition can keep gaining rows; leave a small settle buffer for freshest-hour spend totals.
- **Epoch trap:** `auction_epoch` is **nanoseconds** here but microseconds in `bidder_bid_events` — don't reuse conversion constants across tables.
- **Spend history floor ≈ 2025-12-10:** the current physical (`__2162828994`) only holds partitions from `2025-12-10 22h` onward despite having **no configured TTL** — a pre-Dec-2025 `auction_timestamp` filter silently returns **zero rows, no error**. Long-lookback spend/pacing queries that assume multi-year history will under-report; for spend before 2025-12 use `cost_impression_log` (floor 2023-10-01).
- **`bidder_bid_events` fans out spend:** it is bid-decision grain (N rows/auction), so a `spend_log → bidder_bid_events` join on `auction_id` inflates `SUM(win_cost_micros_usd)`; use `bidder_auction_events` (1:1) or restrict to the winning bid.
- **Physical version bumps:** the view repoints to a new `sqlmesh__logdata.logdata__spend_log__<hash>` on each model rebuild (currently `__2162828994`; prose docs still cite the older `__4068879977`). Always query the clean alias `logdata.spend_log`, never the hashed physical.

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE auction_timestamp >= '…' AND auction_timestamp < '…'`. Partition = **HOUR on `auction_timestamp`**; no clustering; **no partition TTL configured** (`expirationMs`=None), **but the current physical only holds data from ~2025-12-10** — min partition `2025-12-10 22h`, max `2026-07-18 03h`, 4,484 hourly partitions, 10.26B rows. **A partition-filtered query for any date before ~2025-12-10 silently returns zero rows** (this model version was rebuilt then; it does NOT retain full spend history back to CIL's 2023-10-01 floor). `require_partition_filter` is NOT enforced, so an unfiltered scan silently costs full-table bytes — the filter is on you.
- **Dry-run diff (same 1 column, `win_cost_micros_usd`):** no filter = **82.1 GB**; 1-day `auction_timestamp` filter = **1.03 GB** (~80× prune → confirms the partition); 1-day `time` filter = **164 GB** (worse than no filter — `time` doesn't prune and adds a second scanned column). Never filter on `time`.
- **Actual billed (partition-filtered):** ~8 columns over one `auction_timestamp` hour = **0.151 GB**; a single narrow column over one hour ≈ **0.03–0.06 GB**. Column count dominates cost within a fixed slice — select only what you need, never `SELECT *` (full-`SELECT *` logical size ≈ **7.30 TB** / 10.26B rows; compressed physical ≈ 1.07 TB).

## Example queries
```sql
-- Total spend by advertiser for a day (partition-filtered, is_test excluded)
SELECT advertiser_id, SUM(win_cost_micros_usd)/1e6 AS spend_usd, COUNT(*) AS won_imps
FROM `logdata.spend_log`
WHERE auction_timestamp >= '2026-07-15' AND auction_timestamp < '2026-07-16'
  AND is_test IS NOT TRUE
GROUP BY advertiser_id
ORDER BY spend_usd DESC
```
