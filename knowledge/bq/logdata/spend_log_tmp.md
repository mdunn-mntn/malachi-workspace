# logdata.spend_log_tmp

## Purpose
A **frozen one-shot staging snapshot** — not a live pipeline table. It holds won-auction / spend rows in the same shape as `logdata.spend_log`, but restricted to a **single advertiser (advertiser_id = 32167)** and a fixed ~18-day window (auctions 2026-01-16 → 2026-02-02). Physical metadata confirms it was created **2026-02-03 01:11 UTC and never modified** (`creationTime == lastModifiedTime`; 100% of bytes are long-term / active bytes = 0). It is effectively an abandoned ad-hoc extract, most likely a pipeline test or backfill dry-run for the `spend_log` build.

**Do not reach for this table.** For any current spend / pacing / billing analysis use `logdata.spend_log` (HOUR-partitioned on `auction_timestamp`, full advertiser coverage, source of truth for spend). This doc exists so the table is not mistaken for a live rolling staging table.

## Grain & keys
- **Grain:** one row per **won auction** (≈ one row per `bid_id`). 99,387 distinct `bid_id` and 99,387 distinct `auction_id` across 99,395 rows → near-unique, 8 duplicate bid_ids. Mirrors `spend_log` grain (won auction records with cost).
- **Key(s) / join columns:** `bid_id` (uuidv7, effectively the row key), `auction_id` (`<exchange_id>.<auction_id>` = mntn_auction_id). `impression_id` is **NOT usable** here — it is the degenerate placeholder string `"1"` on every row (see Gotchas).

## Column meanings (only the non-obvious ones)
- **auction_epoch** — auction time in **NANOSECONDS** since Unix epoch (magnitude ~1.77e18; min `1768522331703211706`). It is **not** a clean 1000× of `auction_timestamp`: `auction_timestamp` is floored to whole seconds (all 99,395 rows have `UNIX_MICROS(auction_timestamp)` ending in `000000`), so the two differ by up to ~1 s (`MAX(ABS(auction_epoch − UNIX_MICROS(auction_timestamp)*1000)) = 999,992,723` ns). For sub-second timing use `auction_epoch` (÷1e9) — it is the only sub-second source; matches the `spend_log` epoch-unit gotcha.
- **win_cost_micros_usd** — actual win cost in **micros USD** (÷ 1e6 = dollars per impression; ×1000 for CPM). Populated on every row here (all rows are wins). Ranges MIN `1,308` → MAX `32,281` micros ≈ $1.31–$32.28 CPM (CTV RON/OTT deals). Equals the `spend=` field inside `model_params`.
- **bid_price_micros / bid_price_micros_usd** — bid price in micros (local currency / USD respectively).
- **impression_expiration** — a **duration in SECONDS**, not a timestamp; **not constant** — 3 values: `7200` (2 h, 97,788 rows), `1800` (30 min, 1,537), `3600` (1 h, 70). A `= 7200` filter silently drops 1,607 rows.
- **segment_intent_score_ttl** — a **Unix-SECONDS timestamp** (absolute expiry time, not a duration). On the 8,952 scored rows (`segment_intent_score = 10000`) it holds real future expiries (2026-01-16 → 2026-02-03, 6,092 distinct), so it is meaningful, **not** vestigial; on unscored rows it is often `0` (unset).
- **advertiser_intent_score / campaign_intent_score / segment_intent_score** — per-win intent scores; `-1` is the "unscored" sentinel. This snapshot **is** scored: `advertiser_intent_score` is populated on 60,549/99,395 rows (1,268 distinct, up to 10000; `-1` on 38,846); `segment_intent_score = 10000` on 8,952 rows (the RTC/DS19 rows, see `model_params`); only `campaign_intent_score` is genuinely all `-1`.
- **model_params** — a **comma-escaped `key=value` string** (`\,` delimiter) carrying the bidder's decision context: `advertiser_household_score` (populated — `10000` on 58,612 rows, 1,268 distinct, `-1` on 38,846), `household_score` (genuinely all `-1`), `realtime_conquest_score` (`10000` on 8,952 rows → **real RTC/DS19 wins**, `-1` on 90,443; the `=10000` set is exactly the `segment_intent_score = 10000` set), `campaign_group_id`, `flight_id`, `flight_end_time` (Unix seconds), `geo_version` (Unix seconds), `pmp_deal_id`, `term_id`, `device_type_group`, and `spend` (= `win_cost_micros_usd`). This is the widest column (see Cost notes).
- **impression_id** — degenerate placeholder `"1"` on all rows (not a real impression ID in this staging extract).
- **product_id** — populated on the majority of rows: `1` (PTV, per the `campaign_groups.product_id` taxonomy) on 84,908/99,395 rows (85.4%); `NULL` on 14,487 (14.6%). A single non-null value.
- **data_center** — all NULL in this snapshot.
- **is_test** — BOOL; never `TRUE` (0 test rows) — `FALSE` on 86,811 rows, `NULL` on 12,584; keep the `is_test = FALSE` / `IS NOT TRUE` exclusion habit for consistency with `spend_log`.

## Joins & relationships
This is a dead-end snapshot; there is no reason to join it in production (use `spend_log`). If needed for a one-off:
- **→ `logdata.spend_log`** on `bid_id` / `auction_id` — spend_log is the full won-auction table (HOUR-partitioned on `auction_timestamp`); grain 1:1 on `bid_id`. Always add a tight `auction_timestamp` date filter on the spend_log side (its partition column) or the join scans everything.
- **→ dim tables** `silver.core.advertisers` (advertiser_id, here always 32167), `campaigns` (campaign_id), `campaign_groups` (campaign_group_id) — many spend rows : 1 dim row (N:1, no fan-out from the dim side). Filter dims `deleted=FALSE AND is_test=FALSE`.
- **→ `impression_log`** — the usual `spend_log`→impression link is via impression-level keys, but `impression_id` here is the placeholder `"1"`, so this table **cannot** be joined to impression-grain tables. Use `spend_log` for that.

## Gotchas
- **Stale / abandoned:** created 2026-02-03 and never touched since (100% long-term bytes). It does **not** roll forward — treat it as a static historical curiosity, not a staging feed. `spend_log_tmp` in `data_catalog.md` previously said "likely transient / short-term staging"; live metadata shows it is a **one-shot frozen snapshot**, not a rolling stage.
- **Single advertiser only:** every row is `advertiser_id = 32167`. Any "totals" from this table describe one advertiser over ~18 days, nothing more. `data_center` is entirely NULL and `impression_id` is the placeholder `"1"`; `product_id` is `1` (PTV) on ~85% of rows and NULL on ~15% (not degenerate).
- **No partition / no clustering / no require-partition-filter** (verified via `bq show`: `timePartitioning`, `clustering`, `requirePartitionFilter` all None). Unlike `spend_log` (HOUR-partitioned on `auction_timestamp`), there is no partition column to filter — column pruning is the only cost lever.
- **8 duplicate bid_ids** (99,395 rows vs 99,387 distinct) — dedup with `ROW_NUMBER()` if exact uniqueness matters.
- **`auction_epoch` is nanoseconds** — a raw `TIMESTAMP_MICROS(auction_epoch)` would be off by 1000×. `auction_timestamp` is floored to whole seconds, so for sub-second timing use `auction_epoch` (÷1e9), the only sub-second source.
- **The snapshot IS scored (not unscored):** `advertiser_intent_score` / `advertiser_household_score` are populated on ~61% of rows, and `realtime_conquest_score = 10000` (= `segment_intent_score = 10000`) marks 8,952 **real RTC/DS19 wins**. Only `campaign_intent_score` and the standalone `household_score` are genuinely all `-1`. Do not describe this snapshot as unscored.

## Cost & partitioning notes
- **Real base TABLE** (not a view), **no partition, no clustering, no require-partition-filter.** There is no partition column to filter — the **only cost lever is column pruning** (never `SELECT *`).
- The table is tiny and static, so cost is a non-issue, but for reference (all figures from `bq query --dry_run`, us-central1, labeled by exact column set):
  - `SELECT *` (all 48 cols): **87,625,191 bytes ≈ 0.088 GB** (= `numTotalLogicalBytes`, the whole table).
  - `SELECT win_cost_micros_usd` (1 narrow col): **795,160 bytes ≈ 0.0008 GB** — ~110× less than `SELECT *`.
  - `SELECT model_params` (1 wide col): **30,491,321 bytes ≈ 0.031 GB** — this single column is ~35% of the whole table; avoid pulling it unless needed.
- `approx_logical_bytes` in front-matter (87,625,191) = real backing storage (`bq show` `numTotalLogicalBytes`), matching the `SELECT *` dry-run.
