# logdata.bidder_auction_events

## Purpose
The **auction firehose** written directly by the MNTN bidder: one row for **every auction the bidder saw**, including the overwhelming majority that were **dropped before ever bidding** (allow-list rejection, no-candidates-after-pacing, etc.). Reach for it to answer supply/inventory-side questions — what the exchanges are sending us, publisher/app/site/geo/device makeup of the request stream, why auctions were dropped, and PMP-deal / segment context on the request. It is the pre-bid counterpart to `bidder_bid_events` (bids we placed) and `spend_log` (impressions we won). Because ~99.99% of rows are dropped auctions, this is inventory-supply analytics, **not** a delivery/spend table.

## Grain & keys
- **Grain:** one row per **auction** — verified live 2026-07-17 (1h window): 2,327,422,278 rows vs 2,327,422,251 distinct `auction_id` (27 dupes / 2.3B ≈ noise), 0 NULL `auction_id`. Essentially unique per auction.
- **Key(s) / join columns:** two distinct id columns that are **NOT equal** — verified live 2026-07-18 12h (1,955,645,081 rows): `auction_id != mntn_auction_id` on **100%** of rows.
  - **`mntn_auction_id`** = MNTN's composite `<exchange_id>.<raw_auction_id>` (verified `mntn_auction_id = exchange_id || '.' || auction_id` on **100%** of rows; e.g. `152.b5ffb4c2-…_x11b_1`, exchange_id `152`). **This is the cross-family join key to `spend_log`** — it equals `spend_log.auction_id` (spend_log's composite, which its doc also calls the "mntn" id), verified 35,688 matches (see Joins). (`bidder_bid_events` carries its own MNTN-side `auction_id` and has no `mntn_auction_id`; which of this table's two id columns it matches is **not** live-verified — see that table's doc — so confirm before joining.)
  - **`auction_id`** = the **raw exchange auction id** (e.g. `b5ffb4c2-…_x11b_1`), i.e. the value the sibling tables store as `exchange_auction_id`. Do **not** join on it across tables — the composite-vs-raw join returns 0 rows (see Joins).

## Column meanings (only the non-obvious ones)
- **`epoch`** — event time in **milliseconds** since Unix epoch (unit verified live: `MIN(epoch) = 1784376000000` = `2026-07-18 12:00:00 UTC`). `epoch ≈ UNIX_MILLIS(time)` — matches on **~99.95%** of rows (996,432 / 1,955,645,081 ≈ 0.05% differ slightly, 2026-07-18 12h), so treat them as interchangeable for hour-grain time math but **not** a bit-exact identity. Units are per-table across the log family — do **not** reuse `spend_log`'s nanoseconds or `bidder_bid_events.auction_epoch`'s microseconds here.
- **`auction_dropped`** (BOOL) — TRUE when the bidder discarded the auction before/without bidding. **~99.99% of rows are TRUE** (1h live: 2,327,296,347 / 2,327,422,278). Filter `auction_dropped = FALSE` to get the ~0.005% of auctions that actually proceeded toward a bid.
- **`auction_dropped_reason`** (STRING) — why it was dropped: `global-allow-list-rejection`, `no-candidates-after-pacing-engine`, etc. **NOT a ghost-bid surface** — it carries zero `ghost`-matching values; do not use it for ghost-bid analysis (use the `lift__ghost_bid_*` tables).
- **`auction_id` vs `mntn_auction_id`** — **different values, not interchangeable** (100% mismatch, verified). `mntn_auction_id` is the composite `<exchange_id>.<raw_auction_id>` and is the cross-table join key (= `spend_log.auction_id`); `auction_id` is the raw exchange id (= the sibling tables' `exchange_auction_id`). See Grain & Joins.
- **`is_test`** (BOOL) — test/QA auction flag; **exclude `is_test = TRUE`** from production analysis. Live sample: 0 test rows in the hour, so production dominates, but the flag still exists and must be filtered.
- **`segment_ids`** — `STRUCT<list ARRAY<STRUCT<element INT64>>>` (BQ's repeated-field-as-struct encoding). Access with `UNNEST(segment_ids.list)` then read `.element` (the INT64 segment id). Not a flat array.
- **`pmp_deal_ids`** — same `STRUCT<list ARRAY<STRUCT<element STRING>>>` shape; `UNNEST(pmp_deal_ids.list).element` yields STRING PMP deal ids. Empty for open-market auctions.
- **`partner_id`** (INT64) — which bidder/exchange leg produced the row (Beeswax vs MNTN bidder), same meaning as in `spend_log`/`bidder_bid_events`.
- **`exchange_id`** (INT64) — numeric exchange partner id; the prefix embedded in `auction_id`.
- **`auction_type`** (INT64) — auction mechanism enum (e.g. first/second-price); exact code map not documented here — do not assume, join upstream config if you need labels.
- **`device_type`** (STRING) — human/label form in silver (INT in bronze); join `dw-main-bronze.integrationprod.device_type` for the canonical enum. `device_ip` vs `device_ipv6` are separate columns; `device_ifa` = device advertising id (IFA/IDFA, CTV/mobile).
- **`geo_region` vs `region`** — distinct columns: `geo_region` is the request's geographic region; `region` is a separate serving/partition region field (not the user's geo). `geo_type` / `geo_version` describe how geo was resolved.
- **`request_id`** (INT64) — bid-request id from the exchange; not a stable join key to other silver tables (use `auction_id`).

## Joins & relationships
Cross-table joins are on **`mntn_auction_id`** (the composite), **NOT** `auction_id` (raw). Verified live 2026-07-18 12h: `spend_log.auction_id = bidder_auction_events.mntn_auction_id` matched **35,688** wins, while the same join written on `bidder_auction_events.auction_id` matched **0** — a silent-empty trap (syntactically valid, always empty). This table is **not** a complete superset of MNTN's auctions/wins — see the coverage note below.

- **→ `spend_log` (won impressions)** — join `spend_log.auction_id = bidder_auction_events.mntn_auction_id`. Cardinality is **1:1 (no fan-out)** when a row matches, but **coverage is low — this is not a superset of wins**: in hour 2026-07-18 12h `spend_log` had **2,683,273** wins while this table held only **117,790** non-dropped auctions (~23x fewer), and only **35,688 (1.3%)** of those wins had a matching row here — so ~98.7% of won impressions have **no** row in this table. Do **not** use `bidder_auction_events` to enumerate all wins or every auction MNTN participated in; it captures only a fraction (whether that gap is sampling or a single bidder/exchange leg is not established here). Use `spend_log` for the population of wins/cost; use this table only for request-side context (publisher/app/geo/device/segments) on the subset of auctions it does contain.
- **→ `bidder_bid_events` (bids placed)** — partner grain: **potentially N bids per auction** (one per candidate line item). Joining `bidder_auction_events` (1/auction) to `bidder_bid_events` (N/auction) **fans out this table's rows** — pre-aggregate bids to one row per auction before joining, or expect row multiplication. The key correspondence — this table's composite `mntn_auction_id` vs raw `auction_id` against `bidder_bid_events.auction_id` — is **not** live-verified (that table's physical is currently empty; its own doc flags the same); confirm the matching column before relying on the join. (`bidder_bid_events` is itself mid-family with a Beeswax-vs-Rust leg split — see its own doc; the fan-out warning above is the safe, prose-verified direction.) Lineage: this table ← "auction" logs (fka augmentor logs); `bidder_bid_events` ← "bid" logs (fka bid price logs).
- **`device_type` → `dw-main-bronze.integrationprod.device_type`** — dimension lookup for human labels (filter `deleted=FALSE AND is_test=FALSE` on integrationprod dims).

## Gotchas
- **~99.99% of rows are `auction_dropped=TRUE`.** This is the raw firehose, not a delivery table. Almost every query wants `WHERE auction_dropped = FALSE` (or an explicit reason filter). Forgetting this makes any per-auction rate look ~20,000x too diluted.
- **Cross-table join key is `mntn_auction_id`, NOT `auction_id`.** `mntn_auction_id` is the composite `<exchange_id>.<raw>` (= `spend_log.auction_id`); `auction_id` is the raw exchange id (= the sibling tables' `exchange_auction_id`). Joining `auction_id = spend_log.auction_id` returns **0 rows** — a silent-empty trap. The two columns differ on 100% of rows (verified).
- **NOT the auction/win superset.** Only ~1.3% of `spend_log` wins have a row here (117,790 non-dropped auctions/hr vs 2.68M `spend_log` wins/hr, 2026-07-18 12h). Never count "all auctions" or "all won inventory" from this table — it is a partial capture.
- **Scale is ~2.3B rows/hour**, not the stale `112M/hr` figure in `data_knowledge.md`'s scale reference (~20x low — live COUNT 2026-07-17 = 2,327,422,278/hr). A single hour of `SELECT *` dry-runs to **6.81 TB**; a single hour of one narrow column ≈ 126 GB (see Cost).
- **`epoch` is milliseconds** (`≈ UNIX_MILLIS(time)`; same unit, matches ~99.95% of rows — ~0.05% differ slightly, not a bit-exact identity), verified. The `spend_log` catalog note that claims microseconds *for this table* is wrong — corrected here.
- **`content_genre` and `exchange_auction_id` do NOT exist in this silver view** (confirmed via INFORMATION_SCHEMA.COLUMNS 2026-07-19). Prose in `data_knowledge.md` ("content_genre in bidder_auction_events") and `data_catalog.md` (lists `exchange_auction_id`) is stale — those fields live only in a bronze/raw variant, if at all. Don't reference them off the silver view.
- **`auction_dropped_reason` is not the ghost-bid surface** (zero `ghost` values). Ghost-bid work uses `enriched.lift__ghost_bid_*`.
- **`segment_ids` / `pmp_deal_ids` are nested structs, not arrays** — `UNNEST(<col>.list).element`, not direct array access.
- **Partition key `time` is UTC**; the HOUR partition boundary is on UTC time. `epoch` and `time` share the same millisecond scale but are not bit-identical (~0.05% of rows differ slightly — see the `epoch` note above).
- **~10-day retention only** (see Cost) — no long historical backfills here; for anything older than ~10 days this data is gone from silver.

## Cost & partitioning notes
- **The one filter to always apply:** a narrow `time` range (HOUR-partitioned on `time`). No clustering exists, so `time` pruning is the only lever. `require_partition_filter` is **false** (BQ won't stop you) — but a full scan is enormous, so treat the filter as mandatory.
- **Physical (from `bq show` on the resolved table):** `sqlmesh__logdata.logdata__bidder_auction_events__3563801775`, HOUR partition on `time`, `expirationMs=864000000` = **10-day** partition TTL, **no clustering**. Live partitions 2026-07-10 01:00 → 2026-07-19 22:00 (238 hourly partitions ≈ 10 days). Physical `numRows` ≈ 406.0B, `numBytes` ≈ 1.228 PB (real backing storage).
- **Dry-run cost figures (us-central1, 2026-07-19), labeled by exact column set:**
  - `SELECT *`, 1 hour (time-pruned) → **6.81 TB** (6,813,515,100,264 B).
  - `SELECT auction_id`, 1 hour (time-pruned) → **125.6 GB** (125,648,527,797 B).
  - `SELECT auction_id`, **no time filter** (full ~10-day scan) → **18.78 TB** (18,779,511,226,592 B).
  - Same-column-set prune effect: `auction_id` full → 1 hour = 18.78 TB → 125.6 GB (**~149x**). Same-window column effect: `SELECT *` vs one column, 1 hour = 6.81 TB vs 125.6 GB (**~54x**) — always project only the columns you need.

## Example queries
```sql
-- Non-dropped auctions with request context, one hour, projected columns only
SELECT auction_id, exchange_id, publisher_domain, app_bundle, device_type,
       geo_country, geo_metro, auction_dropped_reason
FROM `logdata.bidder_auction_events`
WHERE time >= TIMESTAMP('2026-07-17 00:00:00') AND time < TIMESTAMP('2026-07-17 01:00:00')
  AND auction_dropped = FALSE
  AND is_test = FALSE
LIMIT 100;

-- Drop-reason breakdown for one hour (why we're discarding supply)
SELECT auction_dropped_reason, COUNT(*) AS n
FROM `logdata.bidder_auction_events`
WHERE time >= TIMESTAMP('2026-07-17 00:00:00') AND time < TIMESTAMP('2026-07-17 01:00:00')
GROUP BY auction_dropped_reason ORDER BY n DESC;

-- Unnest segment_ids (nested struct, not array)
SELECT auction_id, s.element AS segment_id
FROM `logdata.bidder_auction_events`, UNNEST(segment_ids.list) AS s
WHERE time >= TIMESTAMP('2026-07-17 00:00:00') AND time < TIMESTAMP('2026-07-17 01:00:00')
  AND auction_dropped = FALSE
LIMIT 100;
```
