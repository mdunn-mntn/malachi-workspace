# logdata.bidder_bid_events

## Purpose
Written directly by the **MNTN bidder** (the `rtb-campaign-service` Rust bidder), one record for every bid decision it makes: bids it placed *and* candidates it dropped, each tagged with a `threshold_failure_reasons`. Reach for it to answer "what did the bidder decide, and why":
- **Ghost-bid / holdout incrementality (BER-2250 / TI-886):** `threshold_failure_reasons = 'ghost-bid'` is the holdout arm; `has_price = TRUE` (no failure reason) is the ITT-treatment arm. Full attribution (advertiser, campaign, ip, objective, score) is on every row → cohorts build off this table alone. See `knowledge/experimentation.md` § "Bidder-Level Ghost Bids".
- **Bid-eligibility diagnostics:** distribution of drop reasons (pacing caps, block-lists, ghost bids) per campaign/advertiser.
- **Bid-time context join:** links auctions (`bidder_auction_events`) to wins (`win_logs`) and spend (`spend_log`).

Do **not** use it for won impressions/cost (→ `spend_log` / `cost_impression_log`) or for the 0–10000 MM/Fangorn scores (they live upstream — see Gotchas).

## Grain & keys
- **Grain:** one row per **bidder decision on an auction candidate** — a placed bid, or a no-bid/drop carrying a `threshold_failure_reasons`. Not deduped to one-per-auction; a single `auction_id` can yield multiple rows (per candidate campaign/line-item).
- **Identifier columns:** `bid_id` (per-bid), `auction_id` (MNTN-side auction id — this table has NO separate `mntn_auction_id` column; do not assume it equals `bidder_auction_events.mntn_auction_id`, which is a distinct column there), `exchange_auction_id` (raw exchange id). Join keys to spend/wins/auctions below. Uniqueness of `bid_id`/`auction_id` is NOT live-verified (physical currently empty — see Gotchas).
- **Cohort dimensions carried on the row (no dim-join needed):** `advertiser_id`, `campaign_id`, `campaign_group_id`, `creative_id`, `line_item`, `objective_id`, `channel_id`, `ip`.

## Column meanings (only the non-obvious ones)
- **`time`** — TIMESTAMP, the **partition key** (HOUR). Bid time. Use `time`/`DATE(time)` for all pruning.
- **`epoch`** — bid time in **MILLISECONDS** (verified against the epoch-units catalog). Not seconds.
- **`auction_epoch`** — auction time in **MICROSECONDS** (differs from `epoch`'s unit — a per-column trap; cf. `spend_log.auction_epoch` = nanoseconds).
- **`price`** — bid price in **micros** (integer). Present even on ghost/no-price rows.
- **`impression_bid_floor`, `pmp_deal_bid_floor`** — FLOAT bid floors.
- **`has_price`** — BOOL. `TRUE` = passed eligibility and a price was set (sent to exchange). **`FALSE` on every `'ghost-bid'` row** even though `price` is still logged → use `has_price = TRUE` (NOT `price > 0`) to isolate real ITT-treatment bids.
- **`threshold_failure_reasons`** — STRING drop reason; empty/NULL = no failure (real bid). Key values: **`'ghost-bid'`** (dashed — holdout/incrementality marker, the MNTN-bidder convention; NOT Beeswax's camelCase `'ghostBid'`), `'dailyTermImpressionRateLimited'` (pacing cap, ~1B/day), `'metadata:ctv-blocked-by-block-list'` (~711M/day). Ghost-bid is a small minority (~753K/day) of all dropped rows.
- **`household_score`, `advertiser_household_score`, `conquest_score`** — the applied bid-time scores. **Empirically ~99.74% = 0, ~0.26% negative, ZERO positive** on this table (probed 2026-05-28, 33.1B rows) — the real 0–10000 MM/Fangorn/RTC scores are consumed **upstream** and do NOT surface here (see Gotchas). `conquest_score` is the RTC/conquest field (upstream/`model_params` name is `realtime_conquest_score`). The ~0.26% negatives are likely a `-1` sentinel for explicitly-unscored IPs (unconfirmed).
- **`household_score_threshold` (HHST)** — the applied Household Score Threshold. **100% = 0** here — the *configured* HHST lives in campaign/advertiser config, not on the bid row. HHST is the master switch for whether the bidder uses scores at all (see `data_knowledge.md` § "HHST").
- **`objective_id`** — on the row directly: `IN (1,5,6)` = prospecting, `4` = retargeting. (`funnel_level` is NOT here — needs the campaigns dim.)
- **`channel_id`** — `8` = CTV, `1` = display. `is_ctv` is a redundant **STRING** flag (not BOOL) — prefer `channel_id`.
- **`is_test`** — BOOL; exclude `is_test = TRUE` for production analysis (test campaigns have structurally different behavior — TI-504).
- **`partner_id`** — which exchange partner / bidder path (Beeswax vs MNTN).
- **`beeswax_crid`** — Beeswax creative id (distinct from MNTN `creative_id`).
- **`campaign_impressions`, `campaign_group_impressions`, `targeted_segments`, `term_ids`, `pmp_deal_ids`, `tow_hours`** — repeated STRUCT<list ARRAY<...>> columns (frequency/impression counters, targeting arrays, time-of-week hours). Heavy — do not `SELECT *` when you need scalars.
- **`agent_params`, `pacing_debug_data`** — raw STRING bidding-agent / pacing debug blobs.

## Gotchas
- **MNTN-bidder ONLY (~22 advertisers).** Only ~22 distinct advertisers appear across the whole day (vs ~300–400 live MNTN advertisers) — this stream carries only the MNTN Rust bidder (`rtb-campaign-service`). The **Beeswax** bidder (`rtb-bidder-service`, camelCase `'ghostBid'`) lands in a different/not-yet-ingested surface. Any incrementality cohort off this table alone is capped at the MNTN-bidder advertiser set (a subset of TI-837 Phase-2). Confirmed Malachi 2026-06-02.
- **The 0–10000 MM/Fangorn/RTC scores are NOT here.** `household_score`/`advertiser_household_score`/`conquest_score` are ~99.74% zero (zero positives); `household_score_threshold` = 0 on every row. Scores are consumed upstream (IPDSC / scoring pipeline) and only a pass/fail propagates — the "applied" values logged here are 0. For real 0–10000 distributions use the IPDSC pipeline / GCS prospecting-scores monitor. (Probed 2026-05-28.)
- **Ghost bids have `has_price = FALSE` but `price` is still populated.** Never use `price > 0` to exclude ghosts — use `has_price = TRUE`. Ghost-bid rows carry full attribution (advertiser/campaign/objective/ip/price all 100% populated).
- **Ghost bids exist from 2026-05-27 forward only** (feature deploy; no backfill) — patient zero for any ghost-bid cohort. Sizing: ghost-bid adds **~753K rows/day** — that's **≈10% of the *successful/eligible* bid count** (~3.95M eligible-no-failure/day on 2026-05-30 per data_knowledge.md), NOT 10% of total drop-reason volume. Against the ~69B/day other-failure drops, ghost-bid is only ~0.001% of all dropped rows. (Ryan Kleck's "~10% increase in bid drop reasons" = ~10% of successful bids, an ambiguous phrasing — do not read it as a 10% rise in total drop volume.)
- **`bidder_auction_events.auction_dropped_reason` is NOT the ghost-bid surface** — it carries auction-level drops only (zero `ghost`-matching values). Ghost bids live in `threshold_failure_reasons` here.
- **Epoch-unit trap:** `epoch` = ms but `auction_epoch` = µs on the SAME row (and `spend_log.auction_epoch` = ns). Always confirm the unit per column before time math.
- **⚠️ Table is BROKEN / mid-repartition as of 2026-07-17 (unresolved this crawl):** the serving view `bidder_bid_events` resolves to `__2658829186`, which **does not exist** — a live `SELECT`/dry-run errors "Not found: ...__2658829186". The only existing physicals are `__3501696720` (**0 rows, empty**) and `logdata__bidder_bid_events_enriched_repartitioned__1769055992__dev_schema_tmp` (also 0 rows). **Nothing in this table is queryable right now** — every example query below currently errors. SQLMesh rotates the physical hash on every rebuild; always re-resolve from the live view (`INFORMATION_SCHEMA.VIEWS`), never hard-code it.
- **⚠️ TTL is 10 days, not 90.** The live physical `__3501696720` carries `partition_expiration_days=10.0` (DDL-confirmed 2026-07-17), and data_knowledge.md (TI-1044, Matt Brorby 2026-06-23) independently states these ghost-bidding tables have a **10-day TTL**. The old "90-day" figure appears only in stale prose (`data_catalog.md` §bidder_bid_events, memory) with no live support — treat it as WRONG until re-confirmed. **A TI-837 "90-day ghost-bid window" will silently lose everything older than 10 days.** `ttl_days` set to 10 to match live source.
- **`is_test = TRUE`** = QA/test auctions — exclude from production analysis.

## Cost & partitioning notes
- **Partition: HOUR on `time`** (confirmed live on the physical; `require_partition_filter=false`, no clustering — all DDL-confirmed 2026-07-17). Row volume is **tens of billions per day** and NOT stable: 33.1B rows on 2026-05-28 (score probe), but the drop-reason arm ALONE was **~69B on 2026-05-30** (data_knowledge.md arm table) — so a partition filter on `time` is effectively mandatory. Always bound `time` to the tightest window.
- **The one filter to always apply:** `WHERE time >= TIMESTAMP('…') AND time < TIMESTAMP('…')`.
- **Avoid `SELECT *`** — the repeated STRUCT/ARRAY columns (`campaign_impressions`, `campaign_group_impressions`, `targeted_segments`, `term_ids`, `pmp_deal_ids`, `tow_hours`) balloon bytes. Project only the scalars you need.
- **Observed billed cost (historical, from perf log 2026-06-01; billed bytes exact, but the per-column set is NOT recoverable — `sql_tables` is null in these records, so treat the column attribution as unknown, not "one column"):**
  - `distinct_failure_reasons_one_day` — **~2.86 TB** billed (2,857,988,259,840 B), **48 hourly partitions (~2 days, not one day)**, and it scanned **TWO tables** — `bidder_bid_events` AND `bidder_auction_events` — not a single narrow-column scan.
  - `ghost_bid_volume_by_day` — **~11.2 TB** billed (11,179,530,387,456 B), **318 hourly partitions (~13 days)**, also scanned `bidder_bid_events` + `bidder_auction_events`.
  - `ghost_vs_real_attribution_sample` — **~8.7 TB** billed (8,740,521,639,936 B), **24 hourly partitions (~1 day)**, `bidder_bid_events` only.
  - Takeaway: even ~1 day of this table is multi-TB — prefer aggregations, the tightest `time` window, project only scalars, and `TABLESAMPLE`/`LIMIT` when sampling. Watch for accidental joins to `bidder_auction_events` doubling the scan. Run large scans sequentially (adhoc slot contention).
- A fresh live dry-run for a labeled byte figure is **impossible as of 2026-07-17**: the serving view errors "Not found" and the only existing physical (`__3501696720`) is empty (a dry-run against it validates but processes **0 bytes** — confirmed 2026-07-17). The figures above are actual historical billed runs, not dry-runs; re-derive once the physical is repopulated.
- Physical/TTL/hash: see the mid-repartition gotcha — resolve the current physical from the live view definition (SQLMesh rotates the hash) rather than trusting the front-matter hash.

## Example queries
> ⚠️ **These currently ERROR** (2026-07-17): the serving view resolves to a missing physical (`__2658829186`) — see Gotchas. Also, under the live **10-day** partition TTL the 2026-05-27/30 windows below are already expired and would return zero rows even once the view is repaired. Re-point `time` to a window within the last 10 days after the repartition settles.
```sql
-- Ghost-bid (holdout) volume by day
SELECT DATE(time) AS dt, COUNT(*) AS ghost_bids
FROM `dw-main-silver.logdata.bidder_bid_events`
WHERE time >= TIMESTAMP('2026-05-27') AND time < TIMESTAMP('2026-05-28')
  AND threshold_failure_reasons = 'ghost-bid'
GROUP BY 1 ORDER BY 1;

-- Incrementality arms in one scan (holdout vs ITT-treatment)
SELECT
  CASE WHEN threshold_failure_reasons = 'ghost-bid' THEN 'holdout'
       WHEN (threshold_failure_reasons IS NULL OR threshold_failure_reasons = '') AND has_price THEN 'itt_treatment'
       ELSE 'other' END AS arm,
  COUNT(*) rows, COUNT(DISTINCT ip) ips, COUNT(DISTINCT advertiser_id) advs
FROM `dw-main-silver.logdata.bidder_bid_events`
WHERE time >= TIMESTAMP('2026-05-30') AND time < TIMESTAMP('2026-05-31')
  AND ip IS NOT NULL AND ip != '0.0.0.0'
GROUP BY 1;
```
