# logdata.win_logs

## Purpose
Beeswax **win-notification log** — one row per impression MNTN won at auction, seen from the external
DSP/exchange (Beeswax/Buzz) side. A very wide (207-column) Beeswax-native schema carrying win economics
(win_cost / clearing / bid prices in micros USD), served creative & inventory context, geo, device,
viewability, and full video-quartile telemetry. Reach for it to get exchange **clearing prices / win
cost**, to trace a won impression back to the bid, or to slice wins by inventory / placement / device /
CTV-vs-display. For MNTN-**native billing** use `spend_log`; for the rendered-impression record use
`cost_impression_log` (see data_catalog "spend_log vs win_logs vs cost_impression_log").

## Grain & keys
- **Grain:** one row per **won impression** (Beeswax win notification). Verified 2026-07-17 on a 30-min
  slice: 1,318,888 rows vs 1,315,829 distinct `auction_id` (99.77% unique) → ~0.2% duplicate win
  notifications. Dedup with `ROW_NUMBER() OVER (PARTITION BY auction_id ORDER BY time)` if exact win
  counts matter.
- **Primary key:** `auction_id` (Beeswax auction id). `exchange_auction_id` is the exchange-side id
  (near-1:1 with `auction_id`).
- **Join keys:** `auction_id = event_log.td_impression_id` (into the impression/VV pipeline).
  MNTN dims via the *_alt_id **remap** — see Joins (the id columns named `campaign_id`/`line_item_id`/
  `advertiser_id` are **Beeswax-internal**, not MNTN).

## Column meanings (only the non-obvious ones)
- **`epoch`** — **MICROSECONDS** since Unix epoch (16 digits; verified 2026-07-17, e.g. 1783641706642026 → 2026-07-10 00:01:46). NOT ms or ns. Contrast: `spend_log`=ns, `bidder_bid_events`=ms. Filter on the `time` TIMESTAMP (the partition), not `epoch`.
- **`win_cost_micros_usd` / `clearing_price_micros_usd` / `bid_price_micros_usd` / `pre_reduction_bid_price_micros_usd`** — micros USD **per impression** (÷1e6 → USD; ×1000 → CPM). E.g. 9000 micros = $0.009/imp = $9.00 CPM. `win_cost` = what MNTN paid; `clearing_price` = auction clearing price; `bid_price` = submitted bid.
- **`*_micros` (non-`usd`) twins** (`clearing_price_micros`, `win_cost_micros`, `bid_price_micros`, `vendor_fee_micros`, `bid_shading_fee_micros`) — **native-currency** micros; the `*_micros_usd` versions are USD-converted via `currency_rate` / `currency_code`.
- **Beeswax vs MNTN IDs** — `advertiser_id`, `campaign_id`, `line_item_id`, `creative_id` are **Beeswax-internal** ids, NOT MNTN. Map to MNTN via the `*_alt_id` columns (see Joins). This is the #1 trap.
- **`ip`** — bid/win **user** IP (= `event_log.bid_ip` at 99.9999%). **`impression_ip_address`** — infrastructure/CDN IP (68.67.x.x MNTN infra, AWS ranges), **NOT** the user IP. 8 IP columns total: `ip`, `ip_raw`, `ip_range`, `ipv6_address`, `ip_address_hashed`, `ipv6_address_hashed`, `clicks_ip_address`, `impression_ip_address`.
- **CTV vs display indicators** (validated 2026-03-13): `placement_type` VIDEO=CTV / BANNER=display; `environment_type` APP=CTV / WEB=display; `platform_device_type` SET_TOP_BOX|CONNECTED_TV=CTV, PC|MOBILE|TABLET=display; `banner_width`/`banner_height` = `-1` for CTV (no banner), real sizes (300x250, 728x90) = display.
- **`clicks` / `conversions` / `video_*`** (video_completes, video_q1s, video_midpoints, video_q3s, video_plays, video_skips, …) — per-win engagement counters folded onto the win row; mostly 0 (clicks>0 on ~0.03% of rows in-sample). `conversions` is backfilled later — see `conversion_update_time` / `conversion_order` / `conversion_value`.
- **`campaign_revenue_type` / `line_item_revenue_type`** — frequently `"UNKNOWN"`.
- **`is_test`** — BOOL test-traffic flag; filter `= FALSE` for real wins (0 in production slices).
- **Fee columns** — `beeswax_fee_rate_micros`, `vendor_fee_micros_usd`, `bid_shading_fee_micros_usd`, `total_cpm_vendor_fee_amount_micros`, `total_percent_vendor_fee_amount_micros` — exchange/vendor fee components (micros).

## Joins & relationships
**CRITICAL — Beeswax→MNTN id remap (VERIFIED 2026-07-17, 20,000/20,000 rows).** The `*_alt_id` columns map to a **different id level than their names imply**:
- **`campaign_alt_id`** (INT64) = MNTN **`campaign_group_id`** → `integrationprod.campaign_groups.campaign_group_id` (100% match).
- **`line_item_alt_id`** (STRING; `CAST(... AS INT64)`) = MNTN **`campaign_id`** → `integrationprod.campaigns.campaign_id` (100% match). Join: `CAST(w.line_item_alt_id AS INT64) = c.campaign_id`.
- Internally consistent: `campaigns.campaign_group_id = campaign_alt_id` (100%). The Beeswax hierarchy itself is inverted — Beeswax "campaign" ≈ MNTN **campaign_group**, Beeswax "line_item" ≈ MNTN **campaign**.
- `creative_alt_id` (STRING) = MNTN `creative_id` → `integrationprod.creatives.creative_id` (VERIFIED 2026-07-17, 25,848/25,848 = 100% on a 10-min slice). `creative_name` also carries the MNTN `campaign_id` as a string (redundant with `line_item_alt_id`).
- **To impression / VV pipeline:** `auction_id = event_log.td_impression_id`. Trace order differs by channel (Zach, 2026-03-13):
  - CTV: clickpass → event_log → **win_logs** → impression_log → bid_logs
  - Display viewable: clickpass → viewability_log → **win_logs** → bid_logs
  - Display non-viewable: clickpass → impression_log → **win_logs** → bid_logs
- **Fan-out:** win_logs (grain = won impression) → `campaign_groups` / `campaigns` dims is many-to-one (safe; filter dims `deleted=FALSE AND is_test=FALSE`). **`bid_logs` is bid-grain, NOT impression-grain** — on the same 30-min slice (2026-07-10 00:00–00:30, verified 2026-07-17) it has 5,280,644 rows / 4,816,380 distinct `auction_id` (~8.8% dup) vs win_logs' 1,318,886 rows (~4× more). Joining win_logs → `bid_logs` on `auction_id` therefore **fans out** win rows and over-counts wins / cost sums; **dedup `bid_logs` first** with `ROW_NUMBER() OVER (PARTITION BY auction_id ORDER BY time)` (matches the workspace `bid_logs: dedup ROW_NUMBER` rule). Do NOT join to `guid_log` / `augmentor_log` at their finer grain without aggregating first — win_logs is ~68M rows/day.

## Gotchas
- **Beeswax ids by default** — the biggest trap is treating `campaign_id` / `line_item_id` / `advertiser_id` as MNTN ids. Use `*_alt_id` with the remap above.
- **~0.2% duplicate `auction_id`** — dedup with ROW_NUMBER if exact win counts matter.
- **`epoch` is microseconds** (16 digits), not ms/ns — filter on `time` (partition), never `epoch`.
- **`impression_ip_address` = CDN/infra IP, not user** — use `ip` for the user IP.
- **UNION seam at 2026-01-01.** The view unions a **raw** physical (`time >= 2026-01-01`, 365-day partition TTL) with a **history** physical (`<= 2025-12-31`, no TTL). History is **contiguous 2025-01-01 → present today** (~562 daily partitions). Below the seam it is permanent — the history leg always retains `<= 2025-12-31`. Above the seam the raw leg's **365-day TTL is only conditionally harmless**: its oldest partition is `2026-01-01` (198 days old on 2026-07-17; `expirationMs = 31536000000`), so raw's 2026-H1 partitions begin **expiring ~2027-01-01**. Unless the pipeline advances the history seam or backfills 2026 into the no-TTL leg, a growing gap will open between `2026-01-01` and `(today − 365 d)` — a 2026-H1 lookback run in mid-2027 would silently miss data. Queries spanning the boundary read both physicals; the history leg filters internally on `date_column` but is partitioned on `time`, so a `time` filter still prunes it.
- **Wide table (207 columns)** — `SELECT *` is ~55× costlier than a few columns (see Cost). Never `SELECT *`.
- **No clustering** on either physical — only `time` prunes; a predicate on `advertiser_id` / `campaign_alt_id` alone still full-scans the selected columns.

## Cost & partitioning notes
- **Partition:** DAY on `time` (both physicals). **No clustering.** `require_partition_filter` is not enforced by the view, but **ALWAYS bound `time`** — an unfiltered query scans the full ~133 TB.
- **Dry-run figures (2026-07-17), each labeled by column set** (compare only same-column-set figures):
  - `SELECT auction_id` + 1-day `time` filter → **2.97 GB**.
  - `SELECT auction_id` + **no** time filter (`campaign_alt_id` predicate) → **2.56 TB** (~860× the one-day figure) — this diff **confirms `time` is the partition**.
  - `SELECT *` + 1-day `time` filter → **162 GB** (~55× the one-column one-day figure) — wide-table penalty; project only the columns you need.
- **Backing storage (real `numBytes`):** raw physical `dw-main-bronze.sqlmesh__raw.raw__win_logs__651277538` = 37.16 TB / 12.0 B rows (365-day TTL); history physical `dw-main-bronze.history.win_logs_physical` = 95.94 TB / 31.5 B rows (no TTL). View total ≈ **133.1 TB / ~43.5 B rows**.
- **Scale:** ~68 M rows/day, ~11.7 M distinct IPs/day (2026-03-29 reference).

## Example queries
```sql
-- Won impressions for a MNTN campaign (line_item_alt_id) with exchange clearing price, one day.
SELECT w.auction_id,
       w.time,
       w.win_cost_micros_usd / 1e6      AS win_cost_usd,
       w.clearing_price_micros_usd / 1e6 AS clearing_usd,
       w.placement_type,                -- VIDEO=CTV, BANNER=display
       w.ip                             -- user IP (impression_ip_address is CDN/infra)
FROM `logdata.win_logs` w
WHERE w.time BETWEEN TIMESTAMP('2026-07-10') AND TIMESTAMP('2026-07-11')
  AND w.is_test = FALSE
  AND CAST(w.line_item_alt_id AS INT64) = <mntn_campaign_id>   -- line_item_alt_id = MNTN campaign_id
LIMIT 100;

-- Join wins to MNTN dims via the alt_id remap.
SELECT cg.name AS campaign_group, c.name AS campaign, COUNT(*) wins,
       SUM(w.win_cost_micros_usd)/1e6 AS win_cost_usd
FROM `logdata.win_logs` w
JOIN `dw-main-bronze.integrationprod.campaign_groups` cg
  ON cg.campaign_group_id = w.campaign_alt_id            -- campaign_alt_id = MNTN campaign_group_id
JOIN `dw-main-bronze.integrationprod.campaigns` c
  ON c.campaign_id = SAFE_CAST(w.line_item_alt_id AS INT64)  -- line_item_alt_id = MNTN campaign_id
WHERE w.time BETWEEN TIMESTAMP('2026-07-10') AND TIMESTAMP('2026-07-11')
  AND w.is_test = FALSE
  AND cg.deleted = FALSE AND cg.is_test = FALSE   -- dims: deleted=FALSE AND is_test=FALSE
  AND c.deleted  = FALSE AND c.is_test  = FALSE
GROUP BY 1, 2 ORDER BY wins DESC LIMIT 50;
```
