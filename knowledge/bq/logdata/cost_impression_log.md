# logdata.cost_impression_log

## Purpose
Impression-level **customer-billed spend** (`media_cost` + the `media_spend`/`data_spend`/`platform_spend`
components) enriched with geo, device, publisher, and per-IP **score** fields. This is the go-to table for
per-impression delivery + spend analysis, per-DMA / per-device / per-advertiser reach, intent-tier (HHST)
distribution, and RTC/score analysis. It is also **the big history table**: ~76B rows / ~62 TB, a fixed
history floor of **2023-10-01** that GROWS one day per day (no TTL). It is **customer-centric**: PSAs
(unpaid impressions) are excluded, so totals will not match raw Beeswax/cache when PSAs are present.

## Grain & keys
- **Grain:** one row per **won / served, customer-charged impression**. Verified: `COUNT(*) == COUNT(DISTINCT impression_id)` on 2025-05-20, 2025-06-10, and 2026-07-10 (impression_id is **unique within CIL**).
- **Primary key:** `impression_id` (STRING). Also the second cluster key.
- **Join columns:** `impression_id` → `impression_log.ttd_impression_id` and `event_log.td_impression_id`; `advertiser_id` (present here, absent on impression_log); `metro_id` (Nielsen DMA code) → `geo.location_data.metro_id`; `ip` = bid IP.

## Column meanings (only the non-obvious ones)
- **`time`** — TIMESTAMP, **UTC**, and the **partition key** (DAY). Convert to Arizona time (ATZ) when reconciling against the MNTN UI / external reporting (via Pratik). `partner_time` = partner-reported timestamp.
- **`epoch` / `batch_epoch` / `source_batch_epoch`** — integer epochs, and they are **NOT the same unit**: **`epoch` = MICROSECONDS** (`= UNIX_MICROS(time)`; verified 2026-07-10: `epoch` 1783652691003000 = `UNIX_MICROS` 1783652691000000 + 3 ms sub-second), while **`batch_epoch` / `source_batch_epoch` = SECONDS** (`= UNIX_SECONDS`; 10-digit batch-write time, later than the event). Converting `epoch` as ms is off by 1000×; converting `batch_epoch` as µs is off by 1,000,000×. Prefer `time` (TIMESTAMP, the partition key) for all filtering.
- **`media_cost`** (NUMERIC) vs **`media_spend` / `data_spend` / `platform_spend`** (BIGNUMERIC) — the three customer-billed spend components; sum ≈ total charged. **Can be ~0 for some advertisers** (managed-service / agency / house billing) even with large real impression volume — never read `media_spend=0` as "no delivery."
- **`household_score`** (INT, −1/NULL = unscored) — the **general / main** per-IP scoring system, **graduated 0–10000** (~35% of impressions carry a positive score). Tiers: HI ≥6666 (in practice a flat 10000), MI 3333–6665, Max-Reach/PP 1–3332. **Typed column is 100% NULL before 2025-06** (logging onset, not a scoring onset — the bidder scored earlier upstream). Recover pre-2025-06 values from `model_params` back to 2025-05-06.
- **`advertiser_household_score`** (INT) — **per-advertiser (Mountain-Match-tuned)** score; in delivery effectively **binary** (scored ≈9900 vs unscored), so the signal is the *scored fraction*, not the level. `10000` = RTC conquest. **Retargeting/RT rows diverge from `household_score`: HS = −1 while AHS = 10000** (verified: 43.8M such rows on 2025-06-10, 3.59M on 2026-07-10). Same NULL-before-2025-06 caveat as `household_score`.
- **`model_params`** (STRING, kv pairs) — carries `household_score`, `advertiser_household_score`, `realtime_conquest_score`, plus `geo_version`, `device_type_group`, `flight_id`, `campaign_id`, `campaign_group_id`, `advertiser_id`, `pmp_deal_id`. **Contains NO segment/audience/upload identifiers.** `realtime_conquest_score=…` is logged on ~100% of rows regardless of whether RTC fired — **genuine RTC = `realtime_conquest_score=10000`** (−1 = not active); do NOT filter merely on the token's presence. Score recovery: `COALESCE(household_score, SAFE_CAST(REGEXP_EXTRACT(model_params, r'household_score=(-?\d+)') AS INT64))`. **This column is enormous and its scan cost scales with the partition's row count** — adding `model_params` to a 1-day scan bills ~17.3 GB alone / ~19.8 GB with `impression_id` on a recent day (2026-07-10, 58.6M rows) but ~39.9 GB on a larger 2025-05 partition (99M rows) = ~5.7–13× a narrow scan; avoid unless recovering pre-2025-06 scores.
- **`ip`** — the enriched **bid IP** used for all logic (= `event_log.bid_ip` = `win_log.ip` at 100%). Use for analysis. `partner_ip` = partner-reported IP. CIL has **only these two IP columns** (live schema is exactly 55 columns) — there is **no `original_ip`** on this table; do not SELECT it (it errors `Unrecognized name: original_ip`).
- **`metro_id`** — **Nielsen DMA code** (NOT the internal `location_id` used in audience expressions). CIL is the **only impression-grain source of DMA**. Join `geo.location_data.metro_id = cost_impression_log.metro_id = summarydata.metros.metro_id` (all Nielsen).
- **`device_type`** — Beeswax enum: `SET_TOP_BOX`, `CONNECTED_TV`, `MOBILE`, `PC`, `TABLET`, `GAMES_CONSOLE`. **`sh_device`** = MNTN device classification (often NULL for Beeswax impressions). **`ott_device`** = `bw_batch` (Beeswax batch) or `mb_rt` (real-time).
- **`partner_ad_format`** — authoritative **CTV vs display** indicator: `VIDEO` = CTV, `BANNER` = display, `BANNER_AND_VIDEO` = mixed. **`publisher_type_id`**: 1 = CTV/OTT, 2 = premium, 3 = web/display.
- **`unlinked`** (BOOL) — `FALSE` = `impression_id` was found in `impression_log` (valid linked impression, the standard filter); `TRUE` = no match (these rows always have NULL `ad_served_id`; ~140–185K/day vs ~55–61M/day linked).
- **`is_new`** (BOOL) — client-JS-pixel new-visitor flag (same semantics as elsewhere; 41–56% clickpass↔ui_visits mismatch is normal, do not treat as ground truth).
- **`geo_version`** (INT) — MaxMind IP-to-geo version used at targeting-cycle start (closes the loop so reporting geo = targeting geo). Can be NULL for World Cup inventory (bypasses the closed loop) without affecting spend.
- **`recency_elapsed_time`** (INTERVAL) — time since the IP's last impression. BQ does not support INTERVAL in all contexts, and the **Spark BigQuery connector's schema resolver fails on it** — exclude or cast when reading via Spark/Databricks.
- **`view_*` / `vast_*`** (INT counters) — viewability + VAST completion funnel (`vast_start` → `firstquartile` → `midpoint` → `thirdquartile` → `complete`) for CTV video.

## Joins & relationships
- **`impression_id` → `impression_log.ttd_impression_id`: FAN-OUT on the impression_log side.** `impression_log` has **1.178 rows per distinct `ttd_impression_id`** (169.74M rows / 144.08M distinct on 2026-07-10 ≈ **15–18% fan-out**). CIL.impression_id is unique, so this join multiplies CIL rows by ~1.18x — dedup (`ROW_NUMBER`) or aggregate the impression_log side. (Reconciles with the TI-650 "794,050/794,050 100% match": 100% of CIL rows find a match ≠ a 1:1 cardinality.)
- **`impression_id` → `event_log.td_impression_id`** — 100% populated in event_log; enriches *within a single impression event*, does NOT link across funnel stages.
- **`advertiser_id` lives on CIL but NOT on `impression_log`** — so CIL is far cheaper for single-advertiser work (filter `time`, exploit the `advertiser_id` cluster key).
- **IP lineage:** `ip` = `event_log.bid_ip` = `win_log.ip` = `ui_visits.impression_ip` (~96–100%). CIL is a one-stop shop for bid IP + advertiser_id.
- **Geo:** join on `metro_id` (Nielsen); `summarydata.metros` is the DMA dimension (name/country, no facts).
- **Upstream of `summarydata.impression_facts`** (WON/served subset: `unlinked = FALSE AND ad_served_id IS NOT NULL`, deduped 1-row-per impression_id) → feeds `all_facts.uniques` / graph "Households Reached".

## Gotchas
- **PSA exclusion (customer-centric view):** PSAs (unpaid impressions, e.g. **advertiser_id 90**) are excluded, so CIL spend/impressions will not match raw Beeswax/cache when PSAs were served. AID 90 PSAs *are* served to holdout IPs — exclude AID 90 from holdout-lift analysis.
- **Score typed-columns are NULL before 2025-06** (verified: 2025-05-20 = 100% NULL for both, 2025-06-10 = 0% NULL — a sharp platform-wide logging cutover, NOT a scoring event). Recoverable from `model_params` back to **2025-05-06**; **no CIL score history of any kind before 2025-05-06**. So "score distribution / scored-fraction over time" via typed columns only works from 2025-06; via `model_params` from 2025-05-06.
- **`realtime_conquest_score` token is on ~100% of rows** regardless of RTC firing — genuine RTC = value `10000`.
- **Timezone is UTC** — convert to Arizona time when matching the MNTN UI.
- **10% holdout** = `MD5('{AID}:{IP}') mod 1000` ∈ 0–99, per-advertiser per-IP (holdout IPs still appear via PSAs / cross-advertiser serving).
- **`require_partition_filter` is FALSE (not enforced)** — but a query without a `time` filter scans the whole ~62 TB. Always filter `time`.
- **Spark/Databricks:** the BQ connector schema resolver fails on `recency_elapsed_time` (INTERVAL) and one other source type — select explicit columns / cast. BQ-only table (no GCS archive); stream via the Spark BQ connector in table-only mode.

## Cost & partitioning notes
- **The one filter to always apply: `DATE(time) = …` (or a `time` BETWEEN range).** Partition is DAY on `time`, confirmed empirically by dry-run diff (same column set, `impression_id` only): **time-filtered 1 day = 3.04 GB** vs **advertiser_id-filtered, no time prune = 548.6 GB** (~180x). `advertiser_id` clustering further prunes *actual* scanned bytes at runtime (not the dry-run estimate) — combine both for cheap single-advertiser pulls.
- **Dry-run cost labels (all us-central1, per exact column set — only compare same-column-set figures):**
  - `SELECT *`, 1 day = **63.4 GB**
  - `impression_id` only, 1 day = **3.04 GB**
  - `impression_id` only, **no** time filter (advertiser_id filter) = **548.6 GB**
  - `household_score` + `advertiser_household_score` + `impression_id`, 1 day = **3.97 GB**
  - **adding `model_params`** (big STRING, partition-size dependent) = **~17.3 GB alone / ~19.8 GB with `impression_id`** on a recent day (2026-07-10), rising to **~39.9 GB** on a larger 2025-05 partition; the pre-2025-06 recovery-regex path is the expensive case (3-day 2025-05-18..20 dry-run = **102.4 GB**, ~34 GB/day). The single most expensive column — avoid unless recovering pre-2025-06 scores.
- **No TTL / fixed floor:** partitions run **20231001 → today**, **1022** daily partitions (verified 2026-07-17: MIN 20231001, MAX 20260718), 75.95B rows (was 1012 partitions on 2026-07-08 — grows +1/day). Physical backing store: `numBytes` = 61,810,191,009,584 (~62 TB), `numRows` = 75,950,052,647.
- Physical: TABLE `sqlmesh__logdata.logdata__cost_impression_log__2498930125`, partition DAY(`time`), cluster [advertiser_id, impression_id], `requirePartitionFilter` unset.

## Example queries
```sql
-- Single-advertiser delivery + score mix for a recent day (partition + cluster pruned, cheap)
SELECT advertiser_id,
       COUNT(*) AS imps,
       COUNTIF(household_score >= 6666) AS hi_imps,
       COUNTIF(household_score = -1)    AS unscored_imps,
       SUM(media_spend + data_spend + platform_spend) AS total_spend
FROM `logdata.cost_impression_log`
WHERE DATE(time) = '2026-07-10' AND advertiser_id = 31357
GROUP BY advertiser_id;

-- Recover a pre-2025-06 score from model_params (EXPENSIVE — model_params ~40 GB on a 2025-05 partition)
SELECT COALESCE(household_score,
                SAFE_CAST(REGEXP_EXTRACT(model_params, r'household_score=(-?\d+)') AS INT64)) AS hs
FROM `logdata.cost_impression_log`
WHERE DATE(time) = '2025-05-20' AND advertiser_id = 31357;
```
