# logdata.conversion_log

## Purpose
The receiving log of every advertiser **conversion pixel fire** (a purchase/lead/site-conversion event that
`px.mountain.com` records when the advertiser's on-site pixel fires). This is the **un-attributed firehose** —
one row per fire, before any last-touch / attribution join. Reach for it to: count conversion volume, read the
raw pixel payload (`query` JSON), investigate pixel/tag changes from our side, or pull local-currency order
amounts. For **attributed** conversions/revenue that match the client UI, use `summarydata.ui_conversions`
instead (attribution layer) — this table over-counts vs the UI (e.g. Avon raw ≈ 6.8× attributed).

## Grain & keys
- **Grain:** one row per **pixel conversion fire** (advertiser site conversion event). **NOT deduplicated** —
  refires (same order firing repeatedly) are real signal; raw `COUNT(*)` is the correct fire-volume metric
  (exact-identity collisions ≈ 0.04%, TI-1037).
- **Partition / time key:** `time` (TIMESTAMP) — the DAY partition on both UNION branches. Always filter
  `DATE(time) BETWEEN ...`. `epoch_time` is the same instant in **microseconds** since epoch (NOT
  seconds — `TIMESTAMP_MICROS(epoch_time)` reconstructs `time`; see Column meanings).
- **Identity / join columns:** `advertiser_id` (INT), `conversion_type` + `conversion_source_id` (event
  taxonomy), `guid` (user/cookie ID), `ip` / `ip_raw` (identical — see below), `order_id`, `ga_client_id`.
  **`guid` is NOT a row id** — on 2026-07-10 distinct `guid` was only 0.19× rows, so `COUNT(DISTINCT guid)`
  silently undercounts fires ~80% in the high-refire 2026 regime. Use `COUNT(*)` for fire volume.

## Column meanings (only the non-obvious ones)
- **`order_amt` (NUMERIC) — the conversion value to use; LOCAL currency (see `order_curr`).** Born from the
  `shoamt` pixel GET param, **digit-extracted** by the ingest parser *upstream of bronze* (`shoamt=1`→1;
  `"' and 6957=6964--"`→69,576,964; a no-digit string like an unreplaced `"ORDER AMOUNT"` macro → NULL). No
  validation — digits-in-garbage become plausible revenue. The silver view additionally wraps it:
  `SAFE_CAST(... AS NUMERIC)` (non-numeric → NULL) then `abs(...) >= 100000000 → NULL`, else `round(...,8)`.
  So **amounts ≥ $100M are NULLed but the ROW is KEPT** (a ≥$100M injected fire shows as an amount-coverage
  DROP, never a SUM spike). Coverage is regime-dependent: ~**90–93% of rows** in the 2026 raw branch,
  only ~**26–36%** in the pre-2026 history branch (verified 2026-07-17).
- **`order_amt_usd` (NUMERIC) — SPARSE; do NOT treat as total USD revenue.** Same $100M/SAFE_CAST wrapper as
  `order_amt`. Only ~**1–2% of rows** populated in the 2026 raw branch (~0.9M/day absolute regardless of total
  volume), ~**17–20%** in the pre-2026 history branch. This **corrects** the earlier prose claim ("coverage
  identical to order_amt") — it is NOT. It IS sometimes populated (unlike `ui_conversions`, where it is 100%
  NULL), but for USD revenue prefer `order_amt` filtered to `order_curr='USD'` (≈93–99% of rows are USD), or
  the `conv_log_ip` feature-store `usd_order_amount` rollup.
- **`order_curr` (STRING)** — currency code; defaults to `'USD'` even when no amount is sent. ~93–99% USD.
- **`ip` == `ip_raw`** — the view emits `ip AS ip_raw`, so they are **identical by construction** (verified
  100% equal on 2026-07-10). The ui_visits/visits "ip vs ip_raw diverge" gotcha does NOT apply here.
- **`original_ip` (STRING)** — a **separate** received-IP column, NOT identical-by-construction to
  `ip`/`ip_raw`. Populated (no NULL/empty in samples) and equals `ip` for ~**95%** of fires; on the ~**5%**
  that diverge it carries a **different** address (forwarded/proxy/egress cases, e.g. an AWS egress vs the
  client IP). Use `ip` (=`ip_raw`) as the canonical join key; treat `original_ip` as an alternate
  as-received value (the exact resolution direction is not documented upstream).
- **`guid` (STRING)** — user/cookie ID, not a row/transaction id (see Grain).
- **`order_id` (STRING)** — the `shoid` pixel param; advertisers often send a **page slug or a constant**
  (WGU: `lead`, `application-status`), NOT a transaction id — don't assume uniqueness.
- **`conversion_type` (STRING)** — the `type` pixel param; absent → NULL here. **Platform pseudo-types are
  string sentinels** `-100/-101/-102/-105/-106/-107` (six of them); when scanning genuine types exclude with
  `NOT REGEXP_CONTAINS(conversion_type, r'^-[0-9]+$')`. (In `ui_conversions`, NULL type is rendered as the
  string `'-101'` — but here in conversion_log NULL stays NULL.)
- **`conversion_source_id` (INT)** — conversion-source reference (e.g. WGU offline batch source = 23; NULL
  possible). A new (advertiser_id, conversion_type) auto-registers in `core_advertiser_conversion_types` at
  the FIRST fire.
- **`email`, `phone` (STRING)** — hashed PII (SHA256). Empty-string hash
  `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` = pixel fired with no email; exclude it
  when counting emailed conversions. Note: `email_data` is **NOT a top-level column in BQ silver** (Greenplum
  era only) — it lives inside the `query` JSON.
- **`query` (JSON)** — raw pixel GET params. Structure `{"key_value":[{"KEY":"shoid","value":"..."}, ...]}`;
  common keys `shoamt`(~75%), `shpt`(~74%), `ga_client_id`(~67%), `email_data`(~2.3%), device ids `idfa/adid`
  (~3%). Search with `TO_JSON_STRING(query)` + `REGEXP_CONTAINS`. Every param a pixel sends lands here, so tag
  changes are reconstructable from the receiving side even though we can't see the client's tag manager.
- **`user_agent` (JSON)** — the raw UA payload (`TO_JSON(user_agent)`). **This is the column the OLD prose
  called `_col_23`** (an unnamed Postgres-migration artifact); the re-versioned view now names it `user_agent`.
- **`epoch_time` (INT64) — conversion time in MICROSECONDS since epoch, NOT seconds.** Convert with
  `TIMESTAMP_MICROS(epoch_time)`; treating it as seconds (`TIMESTAMP_SECONDS`) overshoots by 1e6 (~56,000
  years / out-of-range error). On the **raw** branch (≥2026-01-01) `epoch_time = UNIX_MICROS(time)` for
  **100%** of rows (verified 63,142,868/63,142,868 on 2026-07-10). On the **history** branch (≤2025-12-31)
  `time` is truncated to whole seconds while `epoch_time` retains sub-second micros, so
  `epoch_time = UNIX_MICROS(time)` matches only ~11% *exactly* — but `TIMESTAMP_MICROS(epoch_time)` still
  lands in the same second as `time`, i.e. `epoch_time` is the higher-resolution timestamp there. This
  **corrects the prose oracle** (`data_catalog.md`: "epoch_time INTEGER Seconds"), which is wrong by 1e6.

## Joins & relationships
- **`advertiser_id` → `integrationprod.core.advertisers` / `advertisers.company_name`** for advertiser name
  (`fpa_advertiser_verticals.advertiser_name` is unreliable/empty).
- **(`advertiser_id`,`conversion_type`) → `core_advertiser_conversion_types`** — event-type registry; used to
  date the first fire of a new event type and to detect pixel/tag changes.
- **This table vs `summarydata.ui_conversions` (attribution layer):** conversion_log is the **un-attributed
  firehose**; `ui_conversions` is last-touch-attributed and matches the client UI. Raw fires ≈ **6.8× the
  attributed count** (Avon). Never compare conversion_log `COUNT(*)`/`SUM(order_amt)` to the client UI without
  an attribution join. `ui_conversions` also drops extreme amounts more aggressively (empirically between
  $590K kept and $5.7M dropped) and renders NULL `conversion_type` as `'-101'`.
- **Feature-store sinks:** GCS parquet `feature_group_1_source/conv_log_ip` (IP×day rollup; drops
  `pixel_isolation` advertisers + null/0.0.0.0/127.0.0.1 IPs) and `feature_group_2_derived/conv_log_derived_ip`
  (Fangorn V2 features). These read the **raw** amounts and WILL surface the corrupt values below — plan
  outlier trimming.
- **No IP→IP bridging in BQ.** `guid`/`ip`/`ga_client_id` are cookie/household-shared identifiers — high
  fan-out; treat as shared, not 1:1 to a person.

## Gotchas
- **Silver hides bronze amount corruption (TI-832).** Four advertisers wrote corrupt `order_amt` in the
  $1B–$7.4T range (34957 Harley ~$1.78T ≈ ms-epoch leak; 33903 Bioharvest ~$7.4T; 32023 Tarte ~$6.5T, 1
  order_id firing 759× across 64 IPs; 63746 Networking Today $1.21B). Silver **NULLs the amount, keeps the
  row** (Harley May–Jun 2026: bronze 8,619 = silver 8,619 rows, all silver `order_amt` NULL). So `COUNT(*)`
  is safe on silver; **amount-integrity investigations must query `dw-main-bronze.raw.conversion_log`**
  (≈9-month retention). Route pixel-integrity issues to **Pixel Ops → Ashley Pineda Varela**.
- **Pentest/scanner pollution.** Third-party security scans (e.g. Burp Suite against WGU, 2026-02-07, single
  IP 136.60.22.42) fuzz the pixel GET and land as real-looking conversions (WGU Feb'26 injected $222.9M in
  sub-$100M fakes that silver keeps). Watch single-IP floods and SQLi-string `conversion_type`s.
- **~10× fire-volume step at the 2026-01-01 branch boundary.** History branch (≤2025-12-31) ≈ **5M rows/day**;
  raw branch (≥2026-01-01) ≈ **47–68M rows/day** (verified 2026-07-17). `order_amt` fill rate also jumps
  (~30% → ~92%). Do **not** compare raw fire volumes across the boundary without accounting for this
  discontinuity (it straddles the two physical tables in the UNION).
- **Zero-fire months are invisible in a plain GROUP BY** — a total tag-stop emits no row. Scaffold months with
  `GENERATE_DATE_ARRAY` and month-truncate scan bounds (7.8% of advertisers have ≥1 mid-history zero-fire
  month).
- **Silver floor ≈ 2024-01** (no partitions before that); bronze.raw retention ≈ **9 months**. A bronze↔silver
  amount comparison older than ~9 months is impossible.

## Cost & partitioning notes
- **Always filter `DATE(time)`** — `time` is the DAY partition on BOTH UNION branches, and a plain `time`
  predicate **prunes both branches** (verified 2026-07-17, incl. the history branch even though its internal
  WHERE keys on `date_column`). Partition filter is **not enforced** (`require_partition_filter=false`) so an
  un-filtered query silently full-scans the full ~26 TB logical footprint. No clustering on either branch.
- **Dry-run figures (labeled by column set — `order_amt` only, one NUMERIC column):**
  - full union, no date filter: **361 GB** (360,993,806,195 B).
  - 1 week recent (raw branch, 2026-07-01…07): **6.88 GB** (52× prune).
  - 1 week old (history branch, 2025-06-01…07): **976 MB**.
- **Wider column sets scan far more** — an existing SELECT-*-scale measurement: one-advertiser 18-month window
  ≈ **831 GB** dry-run / ~774 GB billed / ~35 s; unbounded full-history (wide) ≈ 938 GB. Not comparable to the
  `order_amt`-only figures above (the `query`/`user_agent` JSON columns dominate a `SELECT *`).
- **Storage (INFORMATION_SCHEMA.TABLE_STORAGE, summed across the two UNION physicals):** **logical
  (uncompressed)** raw 12.80 TB / 10.73B rows (546-day = 18-month partition expiration) + history 13.21 TB /
  7.91B rows (**no expiration**) = **~26.0 TB logical / ~18.6B rows** — this is the `approx_logical_bytes`
  front-matter value (= sum of `total_logical_bytes` exactly) and what `bq show` reports as `numBytes`
  (`numBytes` is LOGICAL, not compressed). Actual **physical/compressed** storage is far smaller: raw 3.07 TB
  + history 1.78 TB = **~4.85 TB**. The union has no effective floor above the history branch (~2024-01).

## Example queries
```sql
-- Daily fire volume + local-currency revenue for one advertiser (partition-pruned)
SELECT DATE(time) AS d, COUNT(*) AS fires,
       COUNTIF(order_amt IS NOT NULL) AS n_amt,
       SUM(order_amt) AS local_amt          -- LOCAL currency; check order_curr
FROM `logdata.conversion_log`
WHERE DATE(time) BETWEEN '2026-07-01' AND '2026-07-10'
  AND advertiser_id = 31921
GROUP BY d ORDER BY d;

-- Genuine conversion types only (exclude the six platform sentinels)
SELECT conversion_type, COUNT(*) AS fires
FROM `logdata.conversion_log`
WHERE DATE(time) = '2026-07-10'
  AND advertiser_id = 31357
  AND NOT REGEXP_CONTAINS(conversion_type, r'^-[0-9]+$')
GROUP BY conversion_type ORDER BY fires DESC;
```
