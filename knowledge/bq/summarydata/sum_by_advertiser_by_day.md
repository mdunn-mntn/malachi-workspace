# summarydata.sum_by_advertiser_by_day

## Purpose
Daily **advertiser-level** KPI rollup: delivery (impressions, video/display split, VAST quartiles), attributed visits/conversions/order-value under **several attribution models**, spend, and HLL household reach — one pre-aggregated row per advertiser per day. This is the account-total sibling of `sum_by_campaign_by_day` (roll the campaign table up by `advertiser_id` and you get this). Reach for it for account-level VR/CVR/ROAS trends, advertiser YoY, reach analysis, and dashboards that need the **standard attribution model** (per data_knowledge, prefer these `sum_by_*` aggregates over log rebuilds for reporting). History runs back to **2024-01-01** and the `uniques` HLL sketch is populated and mergeable. It uniquely carries a block of `raw_*` un-attributed firehose columns plus `new_to_file` / `visitors` not present on the campaign / campaign_group siblings.

## Grain & keys
- **Grain:** exactly **one row per `advertiser_id` x `day`** (verified 2026-07-19 on 2026-04-01: 6,711 rows = 6,711 distinct advertisers = 6,711 distinct advertiser×day — no duplicates).
- **Key / join columns:** `advertiser_id` (+ `day`). There is **no `campaign_id` / `campaign_group_id`** here — this is the advertiser aggregate; drop to `sum_by_campaign_by_day` if you need stage/objective splits. Join `advertiser_id -> bronze.integrationprod.advertisers.advertiser_id` (filter `deleted=FALSE AND is_test=FALSE`) for `company_name`.

## Column meanings (only the non-obvious ones)
**Visits (VV) are not a single column — they are `views + clicks`** (view-through + click-through). There is **no `revenue` column** (revenue is the `*_order_value` NUMERIC-dollar family) and **no `conversions` column** (use `view_conversions + click_conversions`). There is **no first-touch column** at all in this table (AUDI-1070, §5c) — its headline cols ≈ the `last_touch_*` cols (verified 2026-07-19, one day: headline `views+clicks` = 664,550 vs `last_touch_views+last_touch_clicks` = 664,377, <0.03% diff). This table does **not** honor `reporting_style`; the client UI applies the `industry_standard` / first-touch lens via CHAPI (last-touch **+ `competing_*`**), so a naive pull here reproduces the client's YoY *direction* but not their *level* (~1.276× under the UI on visits/conv/rev). To rebuild the UI number, see `all_facts` (hour grain).

- **`day`** — DATE, the partition key. No epoch column exists in this table (`time_unit: date`); every measure is a same-day aggregate.
- **`raw_visits`, `raw_conversions`, `raw_order_value`, `raw_new_site_visitors`, `raw_existing_site_visitors`** — **un-attributed FIREHOSE counters, NOT a cleaner version of the attributed headline.** They are orders of magnitude larger than the attributed metrics — on 2026-04-01 `raw_visits` = **319,676,993** vs headline `views+clicks` = **664,550** (~481×), and `raw_conversions` = **66,905,778** vs headline `view_conversions+click_conversions` = **56,969** (~1,174×). These count raw pixel/event fires before attribution dedup — do **NOT** use them for reporting; use the attributed `views/clicks/*_conversions/*_order_value`. Present only on this advertiser view, not the campaign/campaign_group siblings.
- **`new_to_file`** (INT64) — new-to-file counter, also a large un-attributed count (49,594,793 on 2026-04-01), advertiser-view-only.
- **`impressions`** vs **`display_impressions` / `video_impressions`** — total vs the display/CTV split. `video_impressions` = CTV. VCR ≈ `vast_complete / vast_start`.
- **`view_impressions`, `view_viewed`, `view_untrackable`** — viewability accounting (impressions measured for viewability, measured-as-viewed, untrackable) — distinct from `views` (view-through visits).
- **`media_spend`, `data_spend`, `platform_spend`** (NUMERIC) — the three spend buckets. **Total spend = `media_spend + data_spend + platform_spend`.** Spend is lens-invariant and is the reliable fingerprint for identifying an advertiser/scope (AUDI-1070). `media_cost` (NUMERIC) and `video_spend` (BIGNUMERIC) are extra cost measures; the cost-side duplicates `data_cost`/`fee_cost`/`partner_cost` were **dropped in the BQ migration** (TI-832) — `SELECT * ` + explicit `*_cost` projection will crash.
- **`uniques`, `site_visitors`, `new_site_visitors`, `existing_site_visitors`, `new_users_reached`, `existing_users_reached`, `visitors`, and every `*_site_visitors`** (all **BYTES**) — **BQ-native HLL++ sketches, NOT integer counts.** Read distinct households with `HLL_COUNT.MERGE(uniques)`, never `SUM`. Verified 2026-07-19: 1,426/6,711 advertiser rows non-null on one day, MERGE ≈ **12.1M households** reached that day (many small/inactive advertisers carry a NULL sketch). `uniques ≈ new_users_reached + existing_users_reached`.
- **ATTRIBUTION-VARIANT FAMILIES — separate models, NOT additive buckets; NEVER SUM across families:**
  - **Default** (`views, clicks, view_conversions, click_conversions, view_order_value, click_order_value`) — **INCLUDES CTV** (a CTV view-conversion is a `view_conversion`).
  - **`last_touch_*` vs `last_tv_touch_*`** — two SEPARATE last-touch models (display/overall vs TV-only) that can credit the same conversion to different campaigns. Not subsets, not additive; coincide only at the account total. **Do NOT do `last_touch + last_tv_touch` (or `default + last_tv_touch`) to "add CTV back" — it double-counts.**
  - **`competing_*`** — the **`industry_standard`** variant (Prod-Ops shorthand "first-touch", a misnomer — `competing_last_touch_*` also exists, so it is a competitive-scenario credit orthogonal to touch-order; §5h). The client UI headline = default last-touch **+ `competing_*`**. `last_tv_touch` is NEVER in the UI headline.
  - **`conversions_assist_*` / `visits_assist`** — multi-touch assist credit. **`probattr_*`** — probabilistic attribution (right surface for ROAS/CPA modeling on probabilistically-attributed outcomes; TI-832). Each family has its own `competing_` sub-variant.

## Joins & relationships
- **`advertiser_id` -> `bronze.integrationprod.advertisers`** (partner grain: **1 row per advertiser**, join on `advertiser_id`, filter `deleted=FALSE AND is_test=FALSE`). Safe 1:1 lookup, **no fan-out** — recovers `company_name` and account attributes. Use `advertisers.company_name`, NOT `fpa_advertiser_verticals.advertiser_name` (unreliable, empty since 2025-12).
- **Sibling rollups at other grains (same core columns, same 2024-01-01 start):** `sum_by_campaign_by_day` (campaign grain — join `campaign_id -> campaigns` for `objective_id`/`funnel_level`/`campaign_group_id`), `sum_by_campaign_group_by_day` (group grain), `sum_by_creative_by_day` (creative grain), `sum_by_region_by_day` (STATE grain). The campaign/group siblings **lack** the `raw_*`, `new_to_file`, and `visitors` columns this advertiser view carries. Rolling `sum_by_campaign_by_day` up by `advertiser_id` reproduces this table's attributed measures.
- **Fresh underlying facts:** `silver.summarydata.{impression_facts, visit_facts, conversion_facts, spend_facts}` (and `all_facts`, time col `hour`) are the hour-grain sources this rollup is built from — use them if this view lags (see Gotchas) or to rebuild the UI `industry_standard` headline.
- **Downstream consumer:** `dw-main-gold.tableau.v_sum_by_advertiser_by_day` (gold tableau view) reads this table for BI/reporting.

## Gotchas
- **`require_partition_filter = TRUE` (enforced on the physical table).** Any query without a `day` filter hard-errors ("Cannot query over table ... without a filter over column(s) 'day'"). Always bound `day` — this also blocks `MIN/MAX(day)` scans (use `INFORMATION_SCHEMA.PARTITIONS` instead). Verified 2026-07-19: `SELECT * ` with no filter → hard error.
- **`raw_*` are a firehose, not attributed** — see Column meanings. `raw_visits`/`raw_conversions` run ~480×/~1,170× the attributed headline; using them as "visits"/"conversions" over-counts by ~2-3 orders of magnitude.
- **STALENESS — historically thrashy; verify `max(day)` before recent-window use.** Prose logged a ~17-day lag on 2026-05-01. **Re-checked 2026-07-29: fresh through the current day** (max dated partition `20260729`, min `20240101`, 941 dated partitions). Freshness has varied, so always check `max(day)`; if lagging, fall back to the hour-grain `*_facts` tables. The downstream `agg__daily_sum_by_campaign` lags worse (empty since 2026-03-31).
- **NO first-touch column, does NOT honor `reporting_style`** — cannot reproduce a client's UI/first-touch (`industry_standard`) number from this table alone; headline ≈ last-touch. Use `all_facts` + `competing_*` to rebuild the UI. Hold attribution lens AND window constant across both years of any client YoY.
- **Attribution variants are separate models — never SUM across families** (default / last_touch / last_tv_touch / competing / probattr / assist). Adding `last_tv_touch` to default/last_touch double-counts CTV-exposed conversions.
- **`uniques` et al. are HLL BYTES sketches**, not integers — `HLL_COUNT.MERGE(...)`, never `SUM`.
- **BQ-migration column drops (TI-832):** `data_cost`, `fee_cost`, `partner_cost` were removed; `*_spend` columns replace them. `SELECT * ` followed by an explicit `*_cost` projection crashes.
- **Empty `__NULL__` partition exists** (0 rows on 2026-07-19); a bounded `day` range predicate excludes any NULL-`day` rows anyway.

## Cost & partitioning notes
- **Partition:** DAY on `day`, `require_partition_filter = TRUE`. **Cluster:** none. **The one filter to always apply: a bounded `day` range** — it is mandatory and the only pruning lever (no cluster keys). Physical backing table (2026-07-29): **4,461,741 rows / 118,521,729,947 bytes (~110.4 GiB)**, **941 dated partitions** (2024-01-01 -> `20260729`) + 1 empty `__NULL__` partition. `numLongTermBytes = 0`.
- **SELECT only the columns you need — the row is very wide (90 cols) and the BYTES HLL sketches dominate, so `SELECT *` is ~613× costlier than a narrow projection.** Labeled dry-run figures (same partition = 1 day, 2026-04-01):
  - `SELECT *` (all 90 cols), 1 day: **142,526,144 bytes (~135.9 MB)**
  - 8 narrow cols (`advertiser_id, day, impressions, views, clicks, media_spend, data_spend, platform_spend`), 1 day: **232,512 bytes (~227 KB)** — ~613× cheaper than `SELECT *`
  - no `day` filter: **hard error** (partition-filter required)

## Example queries
```sql
-- Daily account-total VR + ROAS for one advertiser, long pre-period
SELECT day,
       SUM(views + clicks)                                            AS visits,
       SAFE_DIVIDE(SUM(views + clicks), SUM(impressions))             AS vr,
       SUM(media_spend + data_spend + platform_spend)                 AS spend,
       SAFE_DIVIDE(SUM(view_order_value + click_order_value),
                   SUM(media_spend + data_spend + platform_spend))    AS roas
FROM `summarydata.sum_by_advertiser_by_day`
WHERE day BETWEEN DATE '2024-06-01' AND DATE '2025-06-01'
  AND advertiser_id = 31921            -- Avon
GROUP BY day ORDER BY day;

-- Households reached in a window (HLL merge — never SUM(uniques))
SELECT HLL_COUNT.MERGE(uniques) AS households_reached
FROM `summarydata.sum_by_advertiser_by_day`
WHERE day BETWEEN DATE '2026-07-01' AND DATE '2026-07-10';
```
