# summarydata.pa_navigation_guide

## Purpose
Daily per-advertiser rollup that **calibrates / applies MNTN's probabilistic-attribution (PA) model** — the "navigation guide" the PA model reads. For each advertiser and each PA model version, it summarizes the day's raw page-view (`pv`) volume, the qualifying **PA-event** subset, the resulting **verified visits (VV)** and **conversions**, plus their distinct-IP counts and per-IP rates, and the model's estimated attributed visits (`pa_vv`). Reach for it when you need the advertiser x day inputs/outputs of the PA model in one compact table (2.2M rows, ~210 MB total) rather than reconstructing them from the much larger hourly `visit_facts` (18-key grain, ~135 GB). Net-new table — first partition 2026-02-11; no prose oracle existed in `data_catalog.md`/`data_knowledge.md` at enrichment.

`pa_model_id` = probabilistic-attribution model id (same id space as `visit_facts.pa_model_id` / `conversion_facts.pa_model_id`; see data_knowledge.md "pa_model_id"). Two versions observed live: **1001** and **1002** — for a given advertiser-day they carry identical PV/PA-event/VV/`pa_vv` inputs and differ only in whether the conversion columns are populated (in the sampled advertiser, only 1002 carried conversions). Derive the live domain with `SELECT DISTINCT pa_model_id`.

## Grain & keys
- **Grain:** one row per **(advertiser_id, pa_model_id, day)**. Verified 2026-07-10: 14,238 (advertiser, model, date) groups, every group exactly 1 row; 7,119 advertisers x 2 models (1001, 1002).
- **Key(s) / join columns:** `advertiser_id` + `pa_model_id` + the day. **`date` and `time` are redundant** — `time` is always the midnight-UTC TIMESTAMP of `date` (1 distinct `time` per `date`). Filter/partition on **`time`**; use `date` only for readability.
- **Sentinel advertiser_ids:** `-1` and `0` appear as non-real rollup/house buckets (`-1` = unattributed PV/PA-event aggregate, no VV/conv; `0` = tiny house bucket). Exclude `advertiser_id IN (-1, 0)` when aggregating real advertisers.

## Column meanings (only the non-obvious ones)
Naming convention: `num_*_filtered` = event count after the quality/bot filter; `num_*_ip_filtered` = **distinct IPs** behind those events; `*_per_ip_filtered` = a derived rate; `tot_*` = the day's un-filtered total. "pv" = raw pixel page-views; "pa" = probabilistic-attribution; "vv" = verified visits; "conv" = conversions.

- **`time`** — partition column. TIMESTAMP stamped at midnight UTC of the represented day (NOT an epoch int); equals `date` rendered as a timestamp. This is the column that prunes (see Cost).
- **`num_raw_pv_filtered` / `num_raw_pv_ip_filtered`** — raw page-view events / their distinct IPs (post-filter).
- **`num_pa_events_filtered` / `num_pa_event_ip_filtered`** — the qualifying PA-event subset of raw page-views / their distinct IPs. PA events are a small slice of raw PV (~3-6%).
- **`pa_event_pct`** — `num_pa_events_filtered / num_raw_pv_filtered` (verified: 28994/769319 = 0.03769). Fraction of raw page-views that qualified as PA events. NULL when no PV.
- **`raw_pv_per_ip_filtered`** — `num_raw_pv_filtered / num_raw_pv_ip_filtered` (verified 3.619). Page-views per unique IP (**self-normalized**).
- **`pa_event_per_ip_filtered`** — `num_pa_events_filtered / num_pa_event_ip_filtered` (verified 7.211). PA-events per unique IP (**self-normalized**).
- **`vv_per_ip_filtered`** — **cross-ratio**, NOT vv/vv_ip: `num_vv_ip_filtered / num_raw_pv_ip_filtered` (verified 69719/212584 = 0.328). Fraction of raw-PV IPs that became verified-visit IPs.
- **`conv_per_ip_filtered`** — **cross-ratio**: `num_conv_ip_filtered / num_raw_pv_ip_filtered` (verified 1775/212584 = 0.00835). Fraction of raw-PV IPs that converted. (Both `vv_per_ip` and `conv_per_ip` are normalized by the **raw-PV IP denominator**, unlike the two self-ratios above — do not assume numerator/own-IP.)
- **`tot_vv` / `tot_vv_ip`** — the advertiser-day's total verified visits and distinct-IP total (un-filtered totals; larger than `num_vv_filtered`).
- **`prev_day_vv`** — the prior day's `tot_vv`, carried forward as the base for the model projection.
- **`pa_vv`** — the PA model's estimated attributed verified visits: `pa_event_pct * prev_day_vv` (verified 0.03769 x 180077 = 6787.1 = 6787). Today's PA-event share applied to yesterday's VV total. This is the core "navigation guide" output.
- **`pa_vv_capped`** — `pa_vv` after a ceiling cap; equals `pa_vv` when the cap is not binding (equal in the sample).
- **`weighted_pa_vv`** — a weighted/smoothed variant of `pa_vv` (2627.56 vs pa_vv 6787 on the sample; < pa_vv).
- **`num_conv_filtered` / `num_conv_ip_filtered`** — conversion events / their distinct IPs. Frequently NULL (populated for ~28% of rows / the conversion-bearing model, mainly 1002).
- **`pa_conversions`** — the PA model's estimated attributed conversions (FLOAT; NULL when conversions absent).
- **NULL semantics:** VV/conv/`pa_vv` families are widely NULL — on 2026-07-10 of 14,238 rows only ~3,046 had `tot_vv`, ~2,784 had `pa_vv`, ~4,053 had `num_conv_filtered`. NULL = "no such activity / not computed," not zero.

## Joins & relationships
- **`advertiser_id` → `bronze.integrationprod.advertisers` (N:1, safe):** this table has 1 row per advertiser-model-day, so joining to the advertiser dim (1 row/advertiser) is N:1 with no fan-out. Filter the dim `deleted=FALSE AND is_test=FALSE`; use `advertisers.company_name` for labels. Remember to exclude sentinels `-1`/`0` first.
- **`pa_model_id` → probabilistic-attribution model id** — same id space as `visit_facts.pa_model_id` and `conversion_facts.pa_model_id`. No dedicated dim table observed; domain is small ({1001, 1002} live). Not a fan-out key here (part of the grain).
- **Companion `summarydata.advertiser_pa_toggle_change_log`** — CDC audit log of per-advertiser PA-toggle changes (sibling in the "pa" family; use it to see when an advertiser's PA setting flipped).
- **vs `summarydata.visit_facts` (do NOT join 1:1):** this table is a **daily advertiser x model rollup**; `visit_facts` is hourly at an 18-dimension-key grain (many rows per advertiser-day). Joining pa_navigation_guide to visit_facts on advertiser/day fans out massively. Treat pa_navigation_guide as its own pre-aggregated summary; go to `visit_facts` only when you need the geo/campaign/device breakdown.

## Gotchas
- **Partition is `time`, not `date`.** Filtering `WHERE date = '2026-07-10'` does NOT prune — it scans the whole table (verified: `date` filter → 220 MB full scan; `time` filter → 1.4 MB). Always filter `time` (a TIMESTAMP): `WHERE time >= TIMESTAMP('2026-07-10') AND time < TIMESTAMP('2026-07-11')`.
- **Newest partition can be dated "tomorrow."** MAX(`time`) = 2026-07-20 while today is 2026-07-19 — the daily job stamps a forward-dated partition. Don't assume the latest partition == today's date; range over `time` rather than pinning `= CURRENT_DATE`.
- **Two rows per advertiser per day** (models 1001 + 1002) — always constrain `pa_model_id` (or you double-count PV/VV, which are identical across the two models). Pick the conversion-bearing model (1002) when you need conversions.
- **Wide NULLs are normal.** VV / conversion / `pa_vv` columns are NULL for most rows (activity absent or not computed) — NULL ≠ 0. Guard ratios and SUMs accordingly.
- **`vv_per_ip` / `conv_per_ip` are cross-ratios** normalized by `num_raw_pv_ip_filtered`, not by their own numerator's IP count (see Column meanings). Don't reinterpret them as vv/vv_ip.
- **Sentinel advertisers `-1` and `0`** are non-real aggregate/house buckets — exclude before rolling up real advertisers.
- **History floor 2026-02-11** (~5 months; table created 2026-02-05). No data before that; no TTL/expiration observed (retains full history).

## Cost & partitioning notes
- **Partition = DAY on `time`; no clustering; `require_partition_filter = false`** (no-filter query is allowed but scans everything). Resolved physical: `sqlmesh__summarydata.summarydata__pa_navigation_guide__2755955306` (real TABLE, 2,181,844 rows, 220,576,936 bytes = `approx_logical_bytes`). View is a plain `SELECT *` over the single physical — no UNION.
- **The one filter to always apply:** `WHERE time >= TIMESTAMP('<start>') AND time < TIMESTAMP('<end>')` (on `time`, never `date`).
- **Dry-run figures (all `SELECT *`, i.e. all 23 columns — comparable set):**
  - no filter: **220,576,936 bytes** (~0.205 GiB, full table).
  - `WHERE time` one day: **1,433,872 bytes** (~1.37 MiB) — ~150x pruned.
  - `WHERE date = '<day>'` one day: **220,576,936 bytes** — **NOT pruned** (proves `date` is not the partition).
- Small table; even a full scan is only ~0.2 GB, but always range on `time` and select only needed columns.

## Example queries
```sql
-- PA-model estimated visits for real advertisers, one model, a day range.
-- Filter on `time` (partition), pick the conversion-bearing model, drop sentinels.
SELECT date, advertiser_id,
       num_raw_pv_filtered, pa_event_pct, prev_day_vv,
       pa_vv, pa_vv_capped, weighted_pa_vv,
       tot_vv, num_conv_filtered, pa_conversions
FROM `summarydata.pa_navigation_guide`
WHERE time >= TIMESTAMP('2026-07-10') AND time < TIMESTAMP('2026-07-11')
  AND pa_model_id = 1002
  AND advertiser_id NOT IN (-1, 0)
ORDER BY pa_vv DESC;
```
