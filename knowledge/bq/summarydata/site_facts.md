# summarydata.site_facts

## Purpose
Hourly, per-advertiser rollup of on-site activity captured by the MNTN conversion pixel: raw site-visit
volume, deduped distinct-visitor identity sets, a new-vs-returning ("new-to-file") split, and pixel
conversion events with order value. Reach for it when you need site-visit or conversion **counts and
distinct visitor reach by advertiser over time** without scanning row-level `summarydata.visits` /
`conversion_log`. The visitor arrays + HLL++ sketches let you compute or merge distinct-visitor reach
across hours/advertisers cheaply. It is a pre-aggregated layer, not the event source of truth.

## Grain & keys
- **Grain:** one row per **(advertiser_id, hour, conversion_source_id, conversion_type)**. Two row
  archetypes share the table (a UNION):
  - **Visit-aggregate rows** — `conversion_source_id IS NULL` and `conversion_type IS NULL`.
    Carry `raw_visits`, `new_to_file`, and all four visitor array/sketch columns.
    `raw_conversions` / `raw_order_value` are NULL. (~130K rows/day.)
  - **Conversion-aggregate rows** — `conversion_source_id` and `conversion_type` both set.
    Carry `raw_conversions` + `raw_order_value`; `raw_visits`, `new_to_file`, and the visitor
    arrays/sketches are NULL/empty.
- **`hour`** is a DATETIME truncated to the hour (`:00:00`, verified 24 distinct hour-aligned values per
  day, none off-boundary). Despite the name, the physical partition is **DAY** on `hour` — 24 rows per
  advertiser-archetype per day partition.
- **Key columns / typical joins:** `advertiser_id` (→ `integrationprod.advertisers`),
  `conversion_source_id` (→ pixel/conversion-source dim, conversion rows only).

## Column meanings (only the non-obvious ones)
- **`hour`** — DATETIME truncated to the hour; the row's aggregation window and the DAY partition key.
  No epoch/int time column exists in this table.
- **`conversion_type`** — free-text pixel event name as sent by the advertiser's tag; **not normalized**.
  Same semantic event appears under many spellings (`Purchase`/`purchase`, `SignUp`/`Signup`/`Sign Up`/
  `signup`, `Lead`/`lead`), plus numeric sentinel codes (e.g. `-101` — the most common value by **row**
  count, ~50K rows/day, though `Purchase` carries ~11× more actual conversion **volume**) and
  a literal string `<NIL>`. NULL only on visit-aggregate rows. Case-fold / map before grouping.
- **`raw_visits`** — raw (un-deduped) site-visit **event** count for the hour. Visit rows only.
  `raw_visits` ≠ distinct visitors: it exceeds `ARRAY_LENGTH(visitors_arr)` for ~89% of rows
  (e.g. 4.15M raw_visits vs 1.85M distinct visitors in one advertiser-hour).
- **`visitors_arr`** — deduped list of distinct visitor **GUIDs** (e.g.
  `9ac9e62e-9f0e-30f6-810d-3816da39d84b`). This is the distinct-visitor reach set, keyed by visitor GUID.
- **`visitors`** — BYTES, HLL++ serialized sketch of the same distinct-visitor (GUID) set; use
  `HLL_COUNT.EXTRACT` / `.MERGE` to count/union reach across rows without exploding the arrays.
- **`new_to_file`** — INT count of visitors new to the advertiser's file in the hour (typically tens to
  hundreds per row — median ~40, mean ~390; only large advertisers reach tens of thousands, max ~144K/row —
  and a per-day sum ≈ 50M across advertisers). It is **not** equal to
  `ARRAY_LENGTH(raw_new_site_visitors_arr)` — they diverge for ~88% of visit rows, so treat it as an
  independently-computed count, not the length of the new-visitor array. Visit rows only.
- **`raw_new_site_visitors_arr`** — array of **IP addresses** (e.g. `58.182.64.226`) for visitors new to
  file. **Different key space from `visitors_arr` (GUID)** — do not compare or intersect the two sets.
- **`raw_new_site_visitors`** — BYTES HLL++ sketch of the new-visitor IP set.
- **`raw_existing_site_visitors_arr`** — array of IP addresses for returning/on-file visitors
  (empty/NULL when there are none). IP-keyed, same caveat as above.
- **`raw_existing_site_visitors`** — BYTES HLL++ sketch of the existing-visitor IP set.
- **`raw_conversions`** — conversion event count for the (conversion_source_id, conversion_type) bucket.
  Conversion rows only.
- **`raw_order_value`** — FLOAT64 summed order/revenue value for that conversion bucket (prose called
  this NUMERIC — it is FLOAT64 live). Conversion rows only.

## Joins & relationships
- **`advertiser_id` → `bronze.integrationprod.advertisers` (1:N → 1)** — advertiser dim; filter
  `deleted=FALSE AND is_test=FALSE`. Many site_facts rows per advertiser (per hour × archetype); joining
  the dim is 1 advertiser row, no fan-out.
- **`conversion_source_id` → conversion-source / pixel dim (conversion rows only)** — NULL on visit rows,
  so any inner join on it silently drops all visit-aggregate rows.
- **Row-level sources it summarizes:** the view is a passthrough `SELECT *` of the physical hash, so the
  exact upstream SQLMesh model is not confirmed from the view definition — but it is a site-visit +
  pixel-conversion rollup (row-level equivalents live in `summarydata.visits` / the `conversion_log` /
  `ui_conversions` event streams). Do **not** join site_facts back to those row-grain event tables — it
  is the aggregate; you would double count. Use one or the other.
- **Mixed-key warning for reach math:** `visitors_arr`/`visitors` are GUID-keyed; the new/existing site-
  visitor arrays/sketches are IP-keyed. Distinct counts from the two families are not on the same
  identity space and must not be added or intersected. HLL++ merges are only valid **within** one family
  (GUID-with-GUID, new-IP-with-new-IP).

## Gotchas
- **Two archetypes in one table.** Visit metrics (`raw_visits`, `new_to_file`, visitor arrays) live only
  on `conversion_source_id IS NULL` rows; conversion metrics (`raw_conversions`, `raw_order_value`) live
  only on rows where it is set. Always filter to the archetype you want or you mix/NULL-poison sums.
- **`conversion_type` is dirty free text** — case variants, numeric sentinels (`-101`), and `<NIL>`.
  Normalize before grouping.
- **`raw_visits` is events, not visitors** — for distinct reach use `visitors_arr`/`visitors` (HLL++),
  not `raw_visits`.
- **`hour` is DATETIME (no timezone).** Timestamps are wall-clock in the pipeline's zone; treat as such.
- **History window is short and resets on rebuild.** Physical table holds only **141 dated daily
  partitions from 2026-03-01** (plus one empty `__NULL__` partition, 0 rows; verified via
  INFORMATION_SCHEMA.PARTITIONS; no partition-expiration is set — the
  window comes from the SQLMesh model). The physical hash rotates on each SQLMesh full rebuild
  (`…__2462066249` in stale prose → live `…__1619122006`), which resets available history — always
  resolve the view live, never hard-code the hash.
- **The `…_arr` array columns are enormous** (up to millions of IDs per row) — see cost note.

## Cost & partitioning notes
- **Always filter `hour`** (DAY partition). require_partition_filter is **false** on the physical, so an
  unfiltered query silently full-scans — the guardrail will not stop you.
- **The array + BYTES columns dominate cost.** Same 1-day slice, dry-run measured:
  - `SELECT advertiser_id … WHERE hour = 1 day` → **~3.0 MB** (labeled: 1 narrow INT column, 1 day).
  - `SELECT * … WHERE hour = 1 day` → **~6.17 GB** (labeled: all columns incl. arrays+sketches, 1 day)
    — ~2,000× the narrow-column scan. Never `SELECT *`; project only the columns you need and prefer
    the HLL++ BYTES sketches over exploding `…_arr` when you only need distinct counts.
  - Full-table `SELECT advertiser_id` (no filter) → ~208 MB (labeled: 1 narrow column, all 141 dated
    partitions) vs ~3.0 MB for 1 day → ~68× — confirms `hour` prunes.
- **Backing storage** ~825.6 GB (`numBytes` on the physical), ~26.06M rows across the 141 dated partitions.
- Clustered on `advertiser_id, conversion_source_id` — add an `advertiser_id` predicate to prune within
  the partition when targeting specific advertisers.

## Example queries
```sql
-- Distinct visitor reach (GUID) per advertiser for a day, via HLL++ (cheap, no array explode)
SELECT advertiser_id,
       HLL_COUNT.MERGE(visitors) AS distinct_visitors
FROM `summarydata.site_facts`
WHERE hour >= DATETIME('2026-07-15') AND hour < DATETIME('2026-07-16')
  AND conversion_source_id IS NULL          -- visit-aggregate rows only
GROUP BY advertiser_id
ORDER BY distinct_visitors DESC;

-- Conversions + order value by normalized event type for one advertiser
SELECT LOWER(conversion_type) AS conv_type,
       SUM(raw_conversions)   AS conversions,
       SUM(raw_order_value)   AS order_value
FROM `summarydata.site_facts`
WHERE hour >= DATETIME('2026-07-01') AND hour < DATETIME('2026-07-16')
  AND advertiser_id = <AID>
  AND conversion_source_id IS NOT NULL      -- conversion-aggregate rows only
GROUP BY conv_type
ORDER BY conversions DESC;
```
