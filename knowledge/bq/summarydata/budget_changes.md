# summarydata.budget_changes

## Purpose
Audit log of **budget edits** on campaign groups. Each row records one budget change — the prior and new
daily budget, the prior and new flight (total) budget, whether the change was an increase or a decrease,
and the effective time. Reach for it to answer "when/how did an advertiser's spend cap move?", to line up
budget edits against delivery/pacing shifts, or to reconstruct a campaign group's budget history. Small
table (~66K rows / ~9 MB total, history back to 2024-01-01). It is a SQLMesh-derived CDC rollup; the
upstream is the `dw-main-bronze.integrationprod.archives_campaign_group_*_budget_archives` change family.

## Grain & keys
- **Grain:** one row per budget-change event. `change_id` is the primary key — unique across the whole
  table (66,305 rows = 66,305 distinct `change_id`; verified 2026-07-19). `change_id` is a monotonic
  sequence assigned in change order.
- **Key(s) / join columns:** `change_id` (PK) · `advertiser_id` · `campaign_group_id` · `flight_id`.
  A single change carries all three foreign keys (never NULL).

## Column meanings (only the non-obvious ones)
- **change_time** (TIMESTAMP) — effective time of the budget change; this is the **partition column** (DAY).
  Values land on clean minute boundaries (e.g. `04:00:00`, `07:00:00`), often top-of-hour daily-pacing edits.
- **change_epoch** (INT64) — the same instant as `change_time` in **UNIX seconds** (verified:
  `change_epoch = UNIX_SECONDS(change_time)` for all sampled rows; NOT millis/micros). Redundant with
  `change_time`; prefer `change_time` for filtering (it is the partition key).
- **batch_epoch** (INT64) — **UNIX seconds** of `batch_time` (same anchor as change_epoch). Load/ETL time,
  not business time.
- **batch_time** (TIMESTAMP) — when the row was loaded by the CDC pipeline. **Not** the change time. The
  earliest history was bulk-backfilled: a single batch on **2025-02-12** loaded ~26.7K rows spanning
  change_time 2024-01-01 → 2025-02-12; incremental daily loads start 2025-02-13. So `batch_time` is only a
  meaningful "when we learned about it" signal for rows after ~2025-02-12.
- **budget_change_type_id** (INT64) — direction of the **daily** budget change. **1 = increase**
  (new_daily_budget > prior_daily_budget), **2 = decrease** (new_daily_budget < prior_daily_budget).
  Perfectly clean split (31,065 increases under type 1, 35,240 decreases under type 2, zero equals;
  verified 2026-07-19). Only two values observed.
- **flight_change_type_id** (INT64) — whether the **flight (total) budget** also moved. **1 = flight budget
  unchanged** (this was a daily-only edit → `prior_flight_budget` is NULL, `new_flight_budget` is a snapshot
  of the current flight budget). **2 = flight budget changed** (`prior_flight_budget` populated; direction
  is mixed here — 3,026 up / 2,813 down — so type 2 is *changed*, not a direction code). Only two values observed.
- **new_daily_budget / prior_daily_budget** (NUMERIC, USD) — the daily spend cap after / before the change;
  both always populated.
- **new_flight_budget / prior_flight_budget** (NUMERIC, USD) — the flight (total campaign-group) budget after
  / before. `new_flight_budget` is always populated. **`prior_flight_budget` is NULL ~91% of the time**
  (60,429 / 66,305) — specifically NULL whenever `flight_change_type_id = 1` (daily-only edit). Guard for NULL
  before differencing flight budgets.
- **attribution_window** (INTERVAL) — a day-valued interval carried from the flight/campaign-group config,
  populated on every row (mode 44 days, then 37, 60, 14, 30…; spread 0 → 135+). **Not budget-derived**:
  `new_flight_budget ÷ attribution_days ≠ new_daily_budget`, so it is not the pacing denominator. Read it as
  the flight's configured attribution/lookback window; exact semantic not independently confirmed — treat as
  a reference field, not a computed one.

## Joins & relationships
All foreign keys are non-NULL; every join below is **N budget-changes : 1 dimension row** (fan-out is on the
*dimension* side only — joining a dim to this table multiplies the dim row by its change count, which is the
intent for an audit log).
- **advertiser_id** → `dw-main-bronze.integrationprod.advertisers` (dim, 1 row per advertiser). N:1.
  Use `advertisers.company_name` for the label (`fpa_advertiser_verticals.advertiser_name` is unreliable —
  empty since 2025-12). Filter dims with `deleted = FALSE AND is_test = FALSE`.
- **campaign_group_id** → `campaign_groups` dim (1 row per campaign group). N:1. `campaign_groups.product_id`
  gives PTV(1)/Select(2)/QuickFrame(3). Many budget changes per campaign group.
- **flight_id** → the campaign-group **budget-flight** identifier (a flight = one budgeted flight period of a
  campaign group). N:1; many changes per flight. Upstream lineage is the
  `integrationprod.archives_campaign_group_flight_budget_archives` CDC family.
- **change_id** is unique here (PK) — never a join *fan-out* source.

## Gotchas
- **`prior_flight_budget` is NULL for ~91% of rows** (all `flight_change_type_id = 1` daily-only edits). Any
  flight-budget delta must guard NULL or filter `flight_change_type_id = 2`.
- **`budget_change_type_id` describes the DAILY budget only**, not the flight budget. Don't read it as the
  direction of `new_flight_budget`. `flight_change_type_id` is *changed vs unchanged*, not a direction.
- **`batch_time` ≠ `change_time`.** ~40% of rows (all history before 2025-02-12) share one backfill
  `batch_time` of 2025-02-12; do not use `batch_time` to bucket business activity — always use `change_time`.
- **Two redundant time representations** (`change_time`/`change_epoch`, `batch_time`/`batch_epoch`), both in
  **seconds** for the epoch columns. Filter on `change_time` (the partition), not the epoch, to prune bytes.
- **No `require_partition_filter`** — a bare `SELECT *` scans the whole (small) table; still filter
  `change_time` by habit.
- Only two enum values each observed for both type columns (1/2); treat 3+ as new and re-derive the domain.

## Cost & partitioning notes
- **Partition:** `change_time` (DAY), confirmed off the physical table
  (`sqlmesh__summarydata.summarydata__budget_changes__543345814`, `timePartitioning.field = change_time`).
  **No clustering. No `require_partition_filter`. No TTL** (full history retained since 2024-01-01).
- **The one filter to always apply:** `WHERE change_time >= TIMESTAMP('…')`. It prunes partitions; the epoch
  columns do not.
- Labeled dry-run figures (2026-07-19):
  - `SELECT *` whole table, no filter → **9,641,920 B (~9.2 MB)** — this equals the full backing storage
    (`numBytes`), so the whole table is ~9 MB. Cost is trivial regardless.
  - `SELECT *` one day (`change_time` in [2026-07-18, 2026-07-19)) → **2,448 B** (partition pruning works).
  - `SELECT change_id` only, full table → **530,440 B (~0.5 MB)** — column pruning alone cuts ~18x vs
    `SELECT *`. (Only same-column-set figures are comparable.)
- Practical guidance: the table is tiny, but select only needed columns and bound `change_time` out of habit;
  never rely on `batch_time`/`change_epoch` for pruning.

## Example queries
```sql
-- Budget edits for one advertiser in a window, newest first
SELECT change_time, campaign_group_id, flight_id,
       prior_daily_budget, new_daily_budget,
       CASE budget_change_type_id WHEN 1 THEN 'increase' WHEN 2 THEN 'decrease' END AS daily_dir,
       prior_flight_budget, new_flight_budget
FROM `summarydata.budget_changes`
WHERE change_time >= TIMESTAMP('2026-07-01')
  AND advertiser_id = 62427
ORDER BY change_time DESC;

-- Only flight-budget changes (guard the NULL prior)
SELECT change_time, campaign_group_id, prior_flight_budget, new_flight_budget
FROM `summarydata.budget_changes`
WHERE change_time >= TIMESTAMP('2026-07-01')
  AND flight_change_type_id = 2;   -- prior_flight_budget is populated only here
```
