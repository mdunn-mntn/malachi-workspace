# summarydata.sum_by_campaign_by_day

## Purpose
Daily campaign-level KPI rollup: delivery (impressions, video/display split, VAST quartiles), attributed visits/conversions/order-value under **several attribution models**, spend, and HLL household reach — one pre-aggregated row per campaign per day. This is the **go-to table for experiments needing long pre-periods** (52-week CausalImpact pre-windows): history runs back to **2024-01-01** and, unlike `silver.aggregates.agg__daily_sum_by_campaign` (starts Sep 2025, `uniques` ~0), the `uniques` HLL sketch here is populated and mergeable. Reach for it for daily VR/CVR/ROAS trends, tier YoY (group by `campaign_group_id` via `campaigns`), reach/overlap analysis, and delivery-gap detection.

## Grain & keys
- **Grain:** exactly **one row per `campaign_id` x `day`** (verified 2026-07-10: 12,154 rows = 12,154 distinct campaigns = 12,154 distinct campaign×day = 12,154 distinct advertiser×campaign — no duplicates). `campaign_id` is globally unique and maps to one advertiser, so `advertiser_id` is redundant within the key (never splits a row further).
- **Key / join columns:** `campaign_id` (+ `day`). `campaign_id` = the internal STAGE campaign (obj 1 = S1 prospecting / 4 = retargeting / 5,6 = MT-S2/S3 / 7 = Ego), **not** the client-facing campaign group. Join `campaign_id -> bronze.integrationprod.campaigns.campaign_id` (PK is `campaign_id`, NOT `id`) to recover `campaign_group_id`, `objective_id`, `funnel_level`.

## Column meanings (only the non-obvious ones)
**Visits (VV) are not a single column — they are `views + clicks`** (view-through + click-through). There is **no `revenue` column**; revenue is the `*_order_value` (NUMERIC dollars) family. There is **no `conversions` column**; use `view_conversions + click_conversions`.

- **`day`** — DATE, the partition key. No epoch column exists in this table (`time_unit: date`).
- **`impressions`** vs **`display_impressions` / `video_impressions`** — total vs the display/CTV split. `video_impressions` = CTV. VCR ≈ `vast_complete / vast_start`.
- **`view_impressions`, `view_viewed`, `view_untrackable`** — viewability accounting (impressions measured for viewability, measured-as-viewed, and untrackable), NOT the same as `views` (which is view-through visits).
- **`media_spend`, `data_spend`, `platform_spend`** (NUMERIC) — the three spend buckets. **Total spend = `media_spend + data_spend + platform_spend`** (verified prose). `media_cost` (NUMERIC) and `video_spend` (BIGNUMERIC) are additional cost measures present in the schema; the standard total-spend convention uses the three `*_spend` columns, not `media_cost`.
- **`uniques`, `site_visitors`, `new_site_visitors`, `existing_site_visitors`, `new_users_reached`, `existing_users_reached`** (all **BYTES**) — **BQ-native HLL++ sketches, NOT integer counts.** Read distinct households with `HLL_COUNT.MERGE(uniques)` (verified 2026-07-10: 10,232/12,154 rows non-null, MERGE across a day ≈ 12.4M households reached). `uniques ≈ new_users_reached + existing_users_reached`; prospecting is ~99% `new_users_reached`. Set overlap without a raw-IP scan via conditional-merge + inclusion-exclusion (see data_knowledge §HLL reach). **Unlike `agg__daily_sum_by_campaign.uniques` (~0, unreliable), this table's `uniques` works.**
- **ATTRIBUTION-VARIANT FAMILIES — separate models, NOT additive buckets; NEVER SUM across families:**
  - **Default** (`views, clicks, view_conversions, click_conversions, view_order_value, click_order_value`) — **INCLUDES CTV** (a CTV view-conversion is a `view_conversion`).
  - **`last_touch_*` vs `last_tv_touch_*`** — two SEPARATE last-touch models (display/overall vs TV-only) that can credit the same conversion to different campaigns. Not subsets, not additive; coincide only at the account total. **Do NOT do `last_touch + last_tv_touch` (or `default + last_tv_touch`) to "add CTV back" — it double-counts.**
  - **`competing_*`** — the **`industry_standard` (FIRST-TOUCH)** variant. The client UI headline = default last-touch **+ `competing_*`**: Verified Visits = `clicks + views + competing_views`; UI order-value adds `competing_view_order_value` (reproduced to the dollar, AUDI-1070). `last_tv_touch` is NEVER in the UI headline.
  - **`conversions_assist_*` / `visits_assist`** — multi-touch assist credit. **`probattr_*`** — probabilistic attribution. Each family has its own `competing_` (first-touch) sub-variant.

## Joins & relationships
- **`campaign_id` -> `bronze.integrationprod.campaigns`** (partner grain: **1 row per campaign, PK `campaign_id`** — filter `deleted=FALSE AND is_test=FALSE`). Safe 1:1 lookup, **no fan-out** — recovers `campaign_group_id`, `objective_id`, `funnel_level`, `channel_id`, `name`. There is no `silver.core.campaigns`; join the bronze dim.
- **`campaign_group_id` (via `campaigns`) -> `bronze.integrationprod.campaign_groups`** (1 row per group). Client "campaign" = the group; a group holds many stage campaigns, so grouping this table by `campaign_group_id` gives the client-visible rollup. `campaign_groups` is full of test/archived junk — filter.
- **`advertiser_id` -> `bronze.integrationprod.advertisers`** (1 row per advertiser, join on `advertiser_id`) for `company_name`. `fpa_advertiser_verticals.advertiser_name` is unreliable (empty since 2025-12) — use `advertisers.company_name`.
- **Sibling rollups at other grains (same columns, same 2024-01-01 start):** `sum_by_campaign_group_by_day` (group grain), `sum_by_advertiser_by_day` (advertiser grain), `sum_by_creative_by_day` (creative grain), `sum_by_region_by_day` (STATE grain, not DMA), `sum_by_ctv_network_by_day` (campaign×publisher×day, from 2025-01-01, lacks `competing_*`).
- **Fresh underlying facts:** `silver.summarydata.{impression_facts, visit_facts, conversion_facts, spend_facts}` (and `all_facts`, time col `hour`) are the hour-grain sources this rollup is built from — use them if this view lags (see Gotchas).

## Gotchas
- **`require_partition_filter = TRUE` (enforced on the physical table).** Any query without a `day` filter hard-errors ("Cannot query over table ... without a filter over column(s) 'day' that can be used for partition elimination"). Always bound `day` — this also blocks `MIN/MAX(day)` scans (use `INFORMATION_SCHEMA.PARTITIONS` instead).
- **STALENESS — historically thrashy; verify `max(day)` before recent-window use.** Prose logged a ~17-day lag on 2026-05-01. **Live 2026-07-19: resolved — data is fresh through the current day** (partition `20260719` had 11,280 rows; today's partition is naturally partial). Freshness has evidently varied, so always check `max(day)`; if lagging, fall back to the hour-grain `*_facts` tables. The downstream `agg__daily_sum_by_campaign` lags worse.
- **Attribution variants are separate models — never SUM across families** (default / last_touch / last_tv_touch / competing / probattr / assist). See Column meanings. Adding `last_tv_touch` to default/last_touch double-counts CTV-exposed conversions.
- **No `revenue` and no `conversions` column** — derive: visits = `views + clicks`, conversions = `view_conversions + click_conversions`, revenue = `*_order_value`.
- **`uniques` et al. are HLL BYTES sketches**, not integers — `HLL_COUNT.MERGE(...)`, never `SUM`. `uniques` is populated here (unlike `agg__daily_sum_by_campaign`).
- **`campaign_id` = stage campaign, not the client campaign group** — the client UI "Performance Report" chart scopes to the prospecting group (`objective_id != 4`); ROAS lift to the account total comes from the retargeting campaigns (`objective_id = 4`). Use `objective_id` (via `campaigns`), not `funnel_level` (messy separator).
- **`__NULL__` partition exists but is empty** (0 rows on 2026-07-19); require-partition-filter range predicates exclude any NULL-`day` rows anyway.

## Cost & partitioning notes
- **Partition:** DAY on `day`, `require_partition_filter = TRUE`. **Cluster:** none. **The one filter to always apply: a bounded `day` range** — it is mandatory and the only pruning lever (no cluster keys). Physical backing table: 8,801,789 rows / 87,634,277,248 bytes (~81.6 GiB), **931 date partitions** (2024-01-01 -> current day) + 1 empty `__NULL__` partition.
- **SELECT only the columns you need — the row is very wide (84 cols) so `SELECT *` is ~152x costlier than a narrow projection.** Labeled dry-run figures (same partition = 1 day, 2026-04-10):
  - `SELECT *` (all 84 cols), 1 day: **98,882,770 bytes (~94.3 MB)**
  - 6 narrow cols (`advertiser_id, campaign_id, day, impressions, views, clicks`), 1 day: **650,784 bytes (~635 KB)** — ~152x cheaper than `SELECT *`
  - same 6 narrow cols, 60-day window: **35,074,128 bytes (~33.4 MB)**
  - no `day` filter: **hard error** (partition-filter required)
- HLL reach/overlap over a multi-month window bills a few GB (the campaigns->group join over these rows), fine on reserved capacity.

## Example queries
```sql
-- Daily prospecting VR + ROAS for one advertiser, long pre-period
SELECT s.day,
       SUM(s.views + s.clicks) AS visits,
       SAFE_DIVIDE(SUM(s.views + s.clicks), SUM(s.impressions)) AS vr,
       SUM(s.media_spend + s.data_spend + s.platform_spend) AS spend,
       SAFE_DIVIDE(SUM(s.view_order_value + s.click_order_value),
                   SUM(s.media_spend + s.data_spend + s.platform_spend)) AS roas
FROM `summarydata.sum_by_campaign_by_day` s
JOIN `bronze.integrationprod.campaigns` c
  ON c.campaign_id = s.campaign_id AND c.deleted = FALSE AND c.is_test = FALSE
WHERE s.day BETWEEN DATE '2024-06-01' AND DATE '2025-06-01'
  AND c.objective_id IN (1,5,6)         -- prospecting stages
GROUP BY s.day ORDER BY s.day;

-- Households reached in a window (HLL merge — never SUM(uniques))
SELECT HLL_COUNT.MERGE(uniques) AS households_reached
FROM `summarydata.sum_by_campaign_by_day`
WHERE day BETWEEN DATE '2026-07-01' AND DATE '2026-07-10';
```
