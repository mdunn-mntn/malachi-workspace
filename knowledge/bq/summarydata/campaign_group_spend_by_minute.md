# summarydata.campaign_group_spend_by_minute

## Purpose
Intraday spend fact at **campaign-group × minute** grain. Reach for it when you need minute-resolution
spend for pacing analysis, intraday delivery curves, or the media/data/platform spend split for a
campaign group. For daily totals, roll this up (or use a daily campaign-grain table) — this table is
2.6B rows / ~444 GiB physical, so it is expensive to scan un-filtered. It is one level **above** campaign
in the MNTN hierarchy (advertiser → campaign_group → campaign); there is no line-item/campaign detail here.

## Grain & keys
- **Grain:** one row per **(campaign_group_id, minute)**. Verified on 2026-07-10: 3,124,899 rows =
  distinct (campaign_group_id, minute) = distinct (advertiser_id, campaign_group_id, minute) — no dupes,
  and `advertiser_id` is functionally determined by `campaign_group_id` (adding it does not split rows).
- **Key(s) / join columns:** `campaign_group_id` (+ `minute`/`hour` for the time slice); `advertiser_id`
  is the owning advertiser (redundant-but-carried); `parent_campaign_group_id` is the hierarchy parent.

## Column meanings (only the non-obvious ones)
- **`minute`** — DATETIME at **minute granularity** (seconds are always :00 — 0 non-zero-second rows on
  the sampled day). This is the true time key of the row. Timezone-naive (see Gotchas).
- **`hour`** — DATETIME = `DATETIME_TRUNC(minute, HOUR)` **exactly** (0 violations on the sampled day).
  Redundant with `minute`, but it is the physical **DAY partition column** — always date-filter on `hour`.
- **`parent_campaign_group_id`** — the parent in a campaign-group hierarchy. Mirrors `campaign_group_id`
  in recent data (100% equal on 2026-07-10) but genuinely diverges historically (~37% of rows differ on
  2023-10-01). Never assume it equals `campaign_group_id`; use it only if you need the rollup parent.
- **`total_spend`** — advertiser-billed spend for the minute. **Identity: `total_spend = media_spend +
  data_spend + platform_spend`** (0 violations on the sampled day). Do not add `media_cost` into this sum.
- **`media_spend` / `data_spend` / `platform_spend`** — the three billed components of `total_spend`
  (media, audience/3P-data, platform-fee). `platform_spend` is non-zero for ~96% of rows but is often 0
  for the largest-spend rows.
- **`media_cost`** — MNTN's **underlying cost** for the media (cost side, NOT billed spend). Always
  `<= media_spend` (0 rows with cost > spend). `media_spend − media_cost` ≈ media margin — sensitive
  (see Gotchas). It is a `NUMERIC`; the four spend columns are `BIGNUMERIC`.

## Joins & relationships
- **`campaign_group_id` → `campaign_groups.id`** (integrationprod dim; filter `deleted=FALSE AND
  is_test=FALSE`). Dim grain = 1 row per group, so this table → dim is **N:1 (safe, no fan-out)**.
  Joining the dim yields `product_id` (1=PTV / 2=Select / 3=QuickFrame) to split spend by product.
- **`parent_campaign_group_id` → `campaign_groups.id`** — same dim, the hierarchy parent (N:1).
- **`advertiser_id` → `advertisers.id`** — advertiser dim, **N:1 (safe)**; join `advertisers.company_name`
  for the name (`fpa_advertiser_verticals.advertiser_name` is unreliable/empty).
- **Fan-out warning:** this is a fact, not a dim — joining any per-minute row set to another minute-grain
  fact on `(campaign_group_id, minute)` is 1:1, but joining to a campaign-grain table is 1:N (a group
  contains many campaigns); aggregate one side first. No campaign_id here to bridge campaign-level tables.

## Gotchas
- **Huge minute-grain fact (2.59B rows / ~444 GiB physical).** Never scan without a `hour` date filter.
- **Filter `hour`, not `minute`.** `hour` is the declared DAY partition; a `hour` range is the guaranteed
  prune. (Empirically a `minute` range block-prunes to the same bytes because minute correlates with the
  hour partition, but `hour` is the contract — use it.)
- **DATETIME is timezone-naive.** `hour`/`minute` carry no zone; convention (UTC vs PST reporting tz) is
  unverified here — confirm before joining/aligning to TIMESTAMP or epoch-int tables.
- **`media_cost` is cost-side, sensitive.** `media_spend − media_cost` exposes media margin / take-rate.
  Per workspace policy, shareable cost work uses **media_spend / data_spend lenses only** — do not surface
  `media_cost` (or the spend−cost gap) in external/shareable artifacts.
- **`total_spend` already sums the three spend components** — don't re-add them; and don't fold in
  `media_cost` (would double-count on the cost side).
- **`parent_campaign_group_id` ≠ `campaign_group_id` historically** (~37% on 2023-10-01) even though they
  match in recent data — treat parent as a real hierarchy link.
- **Floor = 2023-10-01** (1.55M rows on the floor day; matches the cost_impression_log 2023-10-01 floor).
  No partition-expiration TTL — all 1,024 partitions from the floor forward are retained; volume grows
  over time (1.55M rows/day at floor → 3.12M rows/day in Jul 2026).

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE hour >= '<start>' AND hour < '<end>'` (DAY partition on `hour`).
  `require_partition_filter` is **false** (not enforced) — so an accidental un-filtered scan is possible;
  add the `hour` filter yourself.
- Dry-run figures (each labeled by the exact column set — do NOT compare across different sets):
  - `SELECT total_spend`, **no filter** (full scan, 1 BIGNUMERIC col): **82.9 GB** (82,906,629,024 B).
  - `SELECT total_spend`, **one day** `WHERE hour`: **125 MB** (124,995,960 B) — ~663× prune vs full.
  - `SELECT *`, **one day** `WHERE hour` (all 10 cols): **575 MB** (574,981,416 B); actual billed 0.535 GB.
  - `SELECT total_spend WHERE advertiser_id=31357`, **no date filter**: **14.6 GB** (14,646,809,320 B) —
    clustering block-prunes partially, but this is NOT a substitute for the `hour` date filter.
- `approx_logical_bytes` (476,713,116,888 B ≈ 444 GiB) is the physical `numBytes` of the full 10-column
  table; it is not comparable to the single-column dry-run figures above.
- Clustered by `(advertiser_id, campaign_group_id)` — a date-filtered query that also pins those columns
  is cheapest.

## Example queries
```sql
-- Intraday spend curve for one campaign group (minute grain), one day
SELECT minute, total_spend, media_spend, data_spend, platform_spend
FROM `summarydata.campaign_group_spend_by_minute`
WHERE hour >= '2026-07-10' AND hour < '2026-07-11'
  AND campaign_group_id = 129804
ORDER BY minute;

-- Daily spend split by advertiser, rolled up from minute grain
SELECT advertiser_id,
       SUM(total_spend)    AS total_spend,
       SUM(media_spend)    AS media_spend,
       SUM(data_spend)     AS data_spend,
       SUM(platform_spend) AS platform_spend
FROM `summarydata.campaign_group_spend_by_minute`
WHERE hour >= '2026-07-10' AND hour < '2026-07-11'
GROUP BY advertiser_id
ORDER BY total_spend DESC;
```
