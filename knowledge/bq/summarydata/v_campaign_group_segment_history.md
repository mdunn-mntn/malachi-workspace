# summarydata.v_campaign_group_segment_history

## Purpose
Segment-membership **history at the campaign-group level**: what audience / data source / category IDs a
campaign group was targeting, and over which time window. Reach for it to answer "which data sources and
category IDs did campaign group X target, and when did that change?" without joining per-campaign history
yourself. It is a pure **logical view** (no storage) that rolls the campaign-grain
`audience.campaign_segment_history` CDC table up to `campaign_group_id` and collapses the per-category rows
into arrays.

**Caveat (inherited contamination):** the source `campaign_segment_history` blends template `audiences`
objects with active `audience_segments` targeting, so this view is **not authoritative for "what was
actually bidding"** — verify against `audience.audience_segment_campaigns` (1:1 with `campaign_id`) +
`audience_segments` for production analysis. See Gotchas.

## Grain & keys
- **Grain:** one row per **(campaign_group_id, audience_id, start_time, end_time, data_source_id)** —
  a single time-bounded segment interval for a campaign group's audience + data source, with every
  `data_source_category_id` for that combination aggregated into `data_source_category_id` (array) and
  `category_info` (JSON). Live counts (2026-07-19): **542,598 rows, 59,632 distinct campaign_group_id**.
- **Key(s) / join columns:** `campaign_group_id` → `campaigns` / `campaign_groups`;
  `audience_id` → `audience.audiences`; `data_source_id` → `audience.data_sources`. There is no single
  surrogate key — the 5-tuple above is the composite grain (it is exactly the source view's `GROUP BY`).

## Column meanings (only the non-obvious ones)
- **`end_time`** — native `TIMESTAMP`, **never NULL in this view**. The source `end_time` is NULL for a
  still-open (currently-active) interval; the view `COALESCE`s that NULL to the sentinel
  **`9999-12-31 00:00:00`**. So `end_time = TIMESTAMP('9999-12-31 00:00:00')` = "interval still open /
  active"; filter on it to get the current segment state. Live: **147,583 open intervals, 0 NULL end_time**.
- **`start_time`** — native `TIMESTAMP`. Floor sentinel **`2000-01-01 00:00:00`** appears for "has always
  been in the segment" / open-start rows; `max_start` runs slightly into the future (`2026-07-20` observed
  on 2026-07-19) because these are scheduled/effective-from timestamps, not ingestion times. Not epoch ints —
  no unit decoding needed.
- **`data_source_id`** — the MNTN data-source ID (DS taxonomy): e.g. 19 = MNTN Matched, plus 14, 35, etc.
  Resolve names via `audience.data_sources`. One row per DS per interval.
- **`data_source_category_id`** — `ARRAY<INT64>`, **non-nullable** (it is an `ARRAY_AGG`, so at least one
  element). The full set of category IDs selected under this `data_source_id` for the interval, sorted
  ascending. Flattens the source's one-row-per-category into a single array — but **drops the AND/OR
  position** (use `category_info` if you need that).
- **`category_info`** — `STRING` holding a **JSON array** (via `TO_JSON_STRING`) of structs
  `{"data_source_category_id":<int>, "and_seq":<int>, "or_seq":<int>}`, one per category. `and_seq` = which
  AND clause of the audience expression the category sits in; `or_seq` = its OR position within that clause
  (per the expression structure: selects / categories / geos / holdout clauses). This is the richer form —
  it reconstructs the boolean nesting the flat array loses. Parse with `JSON_EXTRACT_ARRAY(category_info)`.
- **`campaign_group_id`** / **`audience_id`** — the group and audience-template IDs; the roll-up target and
  the audience each interval belongs to.

## Joins & relationships
- **`public.campaigns` (internal, 1:campaign_group_id → N campaign_id):** the view JOINs source
  `campaign_segment_history` (campaign-grained) to `campaigns` on `campaign_id` and then `GROUP BY
  campaign_group_id`, so one campaign group folds together the histories of all its campaigns. This is done
  *inside* the view — you never see `campaign_id`.
- **`campaign_group_id` → `public.campaigns` / `campaign_groups` (1:N / 1:1):** to attach advertiser or
  group metadata. Joining back to `campaigns` **fans out** (a group has many campaigns); join to
  `campaign_groups` (1:1 dim) instead for group attributes to avoid fan-out.
- **`data_source_id` → `audience.data_sources` (N:1, no fan-out):** DS registry for names/types.
- **`audience_id` → `audience.audiences` (N:1):** audience-template metadata (templates, not the active
  targeting expression — see contamination gotcha).
- **Production cross-check → `audience.audience_segment_campaigns` (1:1 with `campaign_id`) +
  `audience_segments`:** the authoritative "what was actually targeted/bidding" path. Prefer it over this
  view when correctness matters.

## Gotchas
- **Inherits `campaign_segment_history` contamination.** The source blends template `audiences` objects with
  active `audience_segments` targeting, so a row here does **not** guarantee the segment was live-targeting.
  For "what was campaign group X actually bidding," verify against `audience_segment_campaigns` +
  `audience_segments` (filter `expression_type_id = 2 AND is_targeted = TRUE`). Documented in
  `data_knowledge.md` (§ audience.campaign_segment_history contamination).
- **`end_time` sentinel, not NULL.** Do not test `end_time IS NULL` for active intervals — it is always the
  `9999-12-31` sentinel here (0 NULLs). Point-in-time filter: `WHERE start_time <= @t AND end_time > @t`.
- **`start_time` floor / future sentinels.** `2000-01-01` = open-start; `max_start` can be a day or two in
  the future (scheduled effective-from). Don't treat `start_time` as an event/ingestion timestamp.
- **Cross-campaign merge inside a group.** Because it groups by `campaign_group_id` (not `campaign_id`),
  identical (audience_id, start, end, data_source_id) tuples from different campaigns in the same group are
  merged and their category IDs unioned into one array — you cannot recover which campaign contributed which
  category from this view. Drop to source `campaign_segment_history` if you need campaign-level attribution.
- **`data_source_category_id` values span two ID spaces** — small canonical IDs (e.g. 1, 150) and large IDs
  (e.g. 1_007_008_551) coexist; the domain depends on `data_source_id`, so always pair category IDs with
  their DS.
- **No partition, no pruning.** Every query re-scans and re-aggregates the whole 9.47M-row source — a
  `campaign_group_id` predicate does **not** cut bytes (see Cost).

## Cost & partitioning notes
- **No partition, no clustering, no TTL.** The `sqlmesh__summarydata.…__1098153208` hash is itself a
  logical **VIEW** (numRows/numBytes = 0), resolving to `audience.campaign_segment_history` JOIN
  `public.campaigns` + `GROUP BY`. The real backing storage is the source table
  `sqlmesh__audience.audience__campaign_segment_history__2255962104`: **TABLE, 9,466,163 rows,
  584,422,728 bytes (~584 MB), unpartitioned, unclustered** (= `approx_logical_bytes`).
- **No filter prunes** — the view always re-scans and re-aggregates the whole source. Dry-run `SELECT *`
  with **and without** a `WHERE campaign_group_id = …` predicate both estimate **593,201,496 bytes**
  (identical). The only real cost lever is the **column set**, because the two aggregated columns force
  the array/JSON build:
  - **all columns / `SELECT *`** (includes `data_source_category_id` + `category_info`): **~0.55 GB**
    scanned/billed (measured).
  - **metadata columns only** (`campaign_group_id, audience_id, start_time, end_time, data_source_id`,
    no arrays): **~0.34 GB** scanned/billed (measured) — ~1.6x cheaper.
- Practical guidance: it's a small, cheap view (<1 GB full scan) — just **select only the columns you
  need** and skip `data_source_category_id` / `category_info` unless you actually need the category detail.
  A `campaign_group_id` / `data_source_id` predicate is fine for correctness but will not reduce bytes.

## Example queries
```sql
-- Current (open) segments for a campaign group, metadata only (~0.34 GB, no array build)
SELECT campaign_group_id, audience_id, data_source_id, start_time, end_time
FROM `summarydata.v_campaign_group_segment_history`
WHERE campaign_group_id = 128931
  AND end_time = TIMESTAMP('9999-12-31 00:00:00');   -- sentinel = still active

-- Point-in-time segment state with category detail (~0.55 GB, builds arrays/JSON)
SELECT campaign_group_id, data_source_id, data_source_category_id, category_info
FROM `summarydata.v_campaign_group_segment_history`
WHERE start_time <= TIMESTAMP('2026-06-01') AND end_time > TIMESTAMP('2026-06-01');
```
