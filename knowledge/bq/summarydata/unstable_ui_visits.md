# summarydata.unstable_ui_visits

## Purpose
**Non-canonical STAGING / QA table — do NOT use for reporting.** This view exists so BER can validate a
re-attribution change before it is promoted to the production `visits` / `ui_visits`. It is a `UNION ALL`
of two `ber_stg` physicals — the row-level visits *as they looked BEFORE* a change (`pre_change`) and
*as they look AFTER* it (`post_change`) — carrying the same visit columns as `ui_visits` plus five CDC
audit columns (`change_id`, `change_epoch`, `change_time`, `batch_epoch`, `batch_source`). Reach for it
only when diffing a specific re-attribution batch (compare a visit's `pre_change` vs `post_change` row for
a given `change_id`). For any production visit query, use the stable sibling **`summarydata.ui_visits`**
(→ `visits`) instead — see `knowledge/data_catalog.md` "silver.summarydata.ui_visits".

## Grain & keys
- **Grain:** one row per **(visit × `change_id` × `batch_source` side)** — a single visit snapshot as it
  appeared *before* (`batch_source='pre_change'`) or *after* (`batch_source='post_change'`) a specific
  re-attribution change. The **same physical visit is duplicated** across change batches and across the
  two sides, so `COUNT(*)` is NOT a visit count.
- **Change key:** `change_id` = the re-attribution batch id, **scoped to exactly one advertiser**
  (verified 2026-07-19: 0 change_ids span >1 advertiser on a sample day). A `change_id` may have rows on
  both the pre and post side (its comparison pair) or only one.
- **Visit identity:** `advertiser_id` + `ad_served_id` + `guid` + `time` (the underlying visit); join to
  dims via `advertiser_id`, `campaign_id`, `group_id`, `creative_id`.
- **Partition / cluster:** partitioned DAY on `time` (visit time); clustered `advertiser_id, change_id`.

## Column meanings (only the non-obvious ones)
**CDC / staging columns (what makes this table different from `ui_visits`):**
- `batch_source` — STRING, which UNION half the row came from: `'pre_change'` (visit state before the
  re-attribution change) or `'post_change'` (state after). This is the pre/post selector.
- `change_id` — INT64, the re-attribution batch id. **Per-advertiser** (never shared across advertisers).
  High-cardinality (thousands touch any given visit-day). It is a cluster key.
- `change_epoch` / `change_time` — when the change ran. **`change_epoch` is in SECONDS**
  (`change_epoch = UNIX_SECONDS(change_time)`, verified 2026-07-19); `change_time` is bucketed to the hour.
- `batch_epoch` — INT64, **SECONDS** since Unix epoch, when this comparison batch was materialized (no
  timestamp partner column; a few days later than `change_epoch` in the sample).

**Epoch units (differ per column — verified 2026-07-19 by anchoring to the paired TIMESTAMP):**
- `epoch` = **MICROSECONDS** (visit time; carries sub-second precision that the `time` column, which is
  truncated to the second, drops — so `epoch` is finer-grained than `UNIX_MICROS(time)`).
- `impression_epoch` = **MICROSECONDS** (`= UNIX_MICROS(impression_time)` exactly).
- `change_epoch`, `batch_epoch` = **SECONDS** (see above). Do not assume one unit across the four INT epochs.

**Carried-over visit columns (same semantics as `ui_visits`/`visits`):**
- `attribution_model_type_id` — **if `= 0`, treat as `1` (last-touch)** (same convention as `ui_visits`).
- `ip` vs `ip_raw` vs `impression_ip` — the known upstream dual-IP bug survives here: `ip` and `ip_raw`
  are both present temporarily; `impression_ip` is the bid IP carried forward from `impression_log`
  (mobile/CGNAT fallback). See `data_knowledge.md` "ui_visits.ip".
- `impression_time` / `impression_epoch` — the ORIGINAL impression timestamp, NOT the visit time
  (visit time = `time`/`epoch`). `elapsed_time` (INTERVAL) = impression → visit gap.
- `from_verified_impression` — TRUE = visit attributed via MNTN's verified-impression path (what the UI
  reports). `is_pa` = probabilistic-attribution flag; `is_competing` = competing attribution;
  `visits_assist` = assist (not last-touch) visit; `visit_day` = FLOAT day-number within the attribution
  window; `source_type` ∈ {`visits`, `last_tv_touch_visits`}; `is_new` = client-JS "new visitor" flag
  (known 41–56% disagreement with `clickpass_log.is_new` — normal).

## Joins & relationships
- **Stable sibling — `summarydata.ui_visits` (→ `visits`):** same visit columns minus the five CDC audit
  columns. `ui_visits` is the canonical production visit view; this table is its pre/post staging twin.
  Do not join the two — pick one. Grain of `ui_visits` = one row per attributed visit (this table fans
  that out ×(change batches × sides)).
- **Dimension joins (fan-out safe, N:1 from this table):** `advertiser_id` → `integrationprod.advertisers`
  (`company_name`; `fpa_advertiser_verticals.advertiser_name` is unreliable — join `advertisers`);
  `campaign_id` → `campaigns`, `group_id`/`creative_id` → their dims. All are many-visits-to-one-dim.
- **No safe row-level join to impression/event logs at this grain** — a visit is repeated per change batch,
  so any join multiplies. Deduplicate to one `change_id`/`batch_source` first.
- Physical sources (for lineage only, do not query directly): `sqlmesh__ber_stg.ber_stg__unstable__visits_pre_change__3983473504`
  (42.8M rows) and `...visits_post_change__1748979808` (25.3M rows, `requirePartitionFilter=TRUE`).

## Gotchas
- **NON-CANONICAL — never use for visit reporting or KPIs.** It is a BER re-attribution QA staging area;
  numbers will not match production. Use `ui_visits`/`visit_facts` for reporting.
- **`COUNT(*)` ≠ visit count.** The same visit is duplicated across `change_id`s and across the two
  `batch_source` sides. To count visits, pin one `change_id` + `batch_source`, or dedup on visit identity.
- **`time` filter is MANDATORY.** The `post_change` physical has `requirePartitionFilter=TRUE`, so the
  UNION view **errors** if queried without a `time` predicate (confirmed 2026-07-19: "Cannot query over
  table … without a filter over column(s) 'time'").
- **Asymmetric retention between the two halves:** `pre_change` holds `time` back to **2026-01-30**;
  `post_change` back to **2026-03-27** (verified 2026-07-19). So early-2026 days have a `pre_change` row
  with no `post_change` counterpart. No TTL / expiration is set — this staging data is not auto-pruned.
- Each physical also carries a `__NULL__` `time` partition (0 rows as of 2026-07-19) — harmless.
- Dual-IP upstream bug (`ip` + `ip_raw`) is inherited from `visits`; comment upstream says "revert once ip
  is fixed upstream." Prefer `ip` / `impression_ip` per the `ui_visits` guidance.

## Cost & partitioning notes
- **Always filter `time`** (required, see Gotchas) and select only needed columns — clustering is on
  `advertiser_id, change_id`, so narrowing the advertiser/change also prunes.
- Dry-run figures (2026-07-19, one visit-day `time >= '2026-07-10' AND < '2026-07-11'`):
  - `SELECT *` (all 48 cols, view) → **182.9 MB** (182,864,199 bytes).
  - `SELECT advertiser_id, change_id, batch_source` (3 narrow cols) → **14.0 MB** (13,999,054 bytes) — ~13×
    cheaper; SELECT * on this wide table is the main cost trap.
- `approx_logical_bytes` (32.4 GB) = sum of the two physicals' `numBytes` (20.23 GB pre + 12.12 GB post);
  `approx_rows` (68.17M) = 42.82M pre + 25.35M post.

## Example queries
```sql
-- Diff a single visit's attribution before vs after a re-attribution batch
SELECT batch_source, change_id, ad_served_id, guid, attribution_model_type_id, from_verified_impression
FROM `dw-main-silver.summarydata.unstable_ui_visits`
WHERE time >= '2026-07-10' AND time < '2026-07-11'   -- partition filter REQUIRED
  AND advertiser_id = <AID>
  AND change_id = <CHANGE_ID>
ORDER BY batch_source, time;
```
