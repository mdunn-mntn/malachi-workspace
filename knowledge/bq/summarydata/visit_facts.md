# summarydata.visit_facts

## Purpose
The pre-aggregated **fact table for visits** — attributed site-visit (view-through/click-through)
metrics rolled up to hourly campaign/geo/device grain. This is the primary reporting source for
"how many visits did this campaign drive." Reach for it (not row-level `visits`/`ui_visits`) whenever
you need visit counts by advertiser/campaign/day and don't need individual visit events. Inside
`all_facts` (a `UNION ALL` of row-types), `impression_facts` + `visit_facts` + `spend_facts` are FULL
OUTER JOINed on their **17 shared dimension keys**; `conversion_facts` and `site_facts` are appended as
their own union row-types (NOT dim-key-joined). **Stays fresh through the current hour** (verified
`MAX(hour) = 2026-07-19 22:00` on 2026-07-19) — prefer it over the `sum_by_*` rollup views, which lag
~2 weeks.

## Grain & keys
- **Grain:** exactly **one row per unique tuple of the 18 dimension keys** below. Verified 2026-07-19:
  for 2026-07-17, `COUNT(*)` = `COUNT(DISTINCT dim-tuple)` = 1,401,796 (no duplicates at grain).
- **Dimension keys (18):** `hour`, `advertiser_id`, `campaign_group_id`, `campaign_id`, `channel_id`,
  `objective_id`, `group_id`, `creative_id`, `private_marketplace_id`, `country`, `metro_id`, `region`,
  `city`, `postal_code`, `domain`, `supply_vendor`, `device_type`, `pa_model_id`. Of these, only the
  **first 17** (through `device_type`) are shared with `impression_facts`/`spend_facts`, so those are the
  keys `all_facts` FULL OUTER JOINs on; `pa_model_id` (the 18th) exists only on the visit/conversion side
  and adds negligible fan-out (verified 2026-07-17: 1,401,796 rows vs 1,401,783 distinct 17-key tuples, 2 pa_models).
- **No surrogate key / no row-level IDs** — this is a rollup, not an event log. To dedup a unique
  *visitor* count across hours you must HLL-merge the sketch or dedup the `*_arr` arrays; you cannot
  `SUM` the integer measures (see Gotchas).

## Column meanings (only the non-obvious ones)
**Dimensions**
- `hour` — **DATETIME** (partition key, DAY-truncated grain but stored at hour precision, e.g. `2026-07-17 23:00:00`). No timezone attached; it is the reporting hour. (Prose catalog called this TIMESTAMP — it is DATETIME; see Changelog.)
- `device_type` — **STRING** in silver (`MOBILE`, `SET_TOP_BOX`, `DESKTOP`, …), NOT the bronze INT code. Reconfirms the silver-STRING / bronze-INT split.
- `channel_id` — 8 = CTV, 1 = display (per the standard MNTN mapping). CTV `domain` values are rewritten via `public.to_domain()` upstream in `all_facts` when `channel_id = 8`.
- `objective_id` — **unreliable as a funnel-stage indicator**; use `campaigns.funnel_level` for stage. Prospecting ≈ `objective_id IN (1,5,6)`.
- `pa_model_id` — probabilistic-attribution model id (STRING here); part of visit_facts's 18-key grain but **NOT present in `impression_facts`/`spend_facts`**, so it is not one of the shared keys `all_facts` FULL OUTER JOINs on (see Joins).

**Count measures (INT64)** — these are event/visit counts, safe to `SUM` across rows (they are additive over the dimension grain):
- `views` — attributed **view-through site visits** (visits credited to this advertiser's impression as last touch). `clicks` — click-through visits.
- `efficient_views` — additive INT64 view count; its precise definition is **not documented in the prose oracle** (data_catalog.md leaves its Notes blank). Type is a plain INT64 (not HLL/array), so it is additive like the other count measures — but treat the exact semantics as unconfirmed.
- `competing_*` (e.g. `competing_views`, `competing_new_visitors`, `competing_visit_assists`) — the same metric but for impressions where this advertiser was **NOT** the attributed (last) touch — i.e. it was "competing" for credit. Used in incremental / multi-touch attribution.
- `last_touch_*` / `last_tv_touch_*` — attribution restricted to the final touch / final CTV touch.
- `probattr_*` — the metric under the **probabilistic-attribution** model (keyed by `pa_model_id`).
- `visits_assist` — assisted (non-final-touch) visits.
- Attribution-lag buckets: `first_day_visits` … `seventh_day_visits` + `visits_tail` bucket visits by **days elapsed between impression and visit**; `last_touch_visits_day0` … `last_touch_visits_day13` is the finer 14-day last-touch lag curve. `competing_first_day_views` … `competing_seventh_day_views` mirror for competing credit.
- `new_visitors` — count of first-time site visitors (no prior recorded pageview for that advertiser+visitor).

**Unique-visitor columns come in TWO physical forms for the SAME quantity — do NOT SUM either:**
- `*_arr` (e.g. `site_visitors_arr`, `new_site_visitors_arr`, `competing_site_visitors_arr`, `probattr_*_arr`, `first_day_visitors_arr`, `visitors_tail_arr`) — **ARRAY<STRING> of the raw visitor IDs** (resolved IP / guid) that visited in that row's hour. NON-NULL (empty array, never NULL). These are the arrays R2/CHAPI/ClickHouse dedups (`uniqArrayMerge`) to produce window-level unique reach.
- `site_visitors`, `new_site_visitors`, `existing_site_visitors`, plus the `competing_*`, `probattr_*`, `last_touch_*` variants — **BYTES = HLL++ serialized sketches** of the same visitor sets (verified present/non-null on sampled rows). **NOTE: the prose catalog lists `site_visitors`/`new_site_visitors`/`existing_site_visitors` as INTEGER — that is WRONG; they are BYTES HLL sketches** (see Changelog). To get a number from them use `HLL_COUNT.MERGE(site_visitors)` across rows, or `HLL_COUNT.EXTRACT` on a single row.
- Relationship (verified 2026-07-19 on 2026-07-17 rows): `ARRAY_LENGTH(new_site_visitors_arr)` = `new_visitors` **exactly** (that array is the raw NEW-visitor IDs), and `ARRAY_LENGTH(site_visitors_arr)` = new + existing visitor IDs (e.g. a row with 21 new + 1 existing has a 22-element `site_visitors_arr` while `new_visitors` = 21). Do **NOT** equate `ARRAY_LENGTH(site_visitors_arr)` with `new_visitors` — they coincide only when existing visitors = 0 (a row with 0 new / 24 existing still carries a 24-element `site_visitors_arr`). The unique-visitor-set size is independent of `views` (attributed view count): either can exceed the other.

## Joins & relationships
- **`spend_facts` / `impression_facts` (1:1-ish on the 17 shared dim keys):** these three are FULL OUTER JOINed on the **17 dimension keys shared by all three** (`hour` … `device_type`) inside `all_facts` (`SteelHouse/sqlmesh` `all_facts.sql`, owner BER). Grain matches, so it's roughly 1:1 per key tuple, but any single fact table may be missing a tuple the others have (that's why it's a FULL OUTER JOIN) — do not assume every visit row has a matching spend row. **Caveat:** `impression_facts` and `spend_facts` do NOT contain `pa_model_id` (verified — no `pa_model*` column in either); joining `visit_facts` to them on the full 18-key set (e.g. `USING (… pa_model_id)`) errors with `Unrecognized name: pa_model_id`. Join on the 17 shared keys — `pa_model_id` is contributed only by the visit/conversion side.
- **`conversion_facts` (many:many at coarse grain):** conversion_facts adds `conversion_type`/`conversion_source_id` to the grain, so it is **not** 1:1 with visit_facts — joining the two on advertiser+campaign+hour fans out. `all_facts` handles this by UNION-ing conversion rows as their own row-type, not by joining. Per-advertiser CVR from these facts can legitimately exceed 100% (multi-touch re-credits the same conversion across advertiser-visits) — not a bug.
- **`campaigns` dim (N:1):** join `campaign_id` → `campaigns` for `funnel_level` (authoritative stage; `objective_id` is unreliable). `campaigns` is a `silver.core` thin view over `bronze.integrationprod` — filter `deleted=FALSE AND is_test=FALSE`. Many fact rows per campaign.
- **`advertisers` dim (N:1):** `advertiser_id` → `advertisers.company_name` for names (`fpa_advertiser_verticals.advertiser_name` is unreliable/empty since 2025-12).
- **Reporting lineage (downstream):** `visit_facts.site_visitors` → `all_facts.site_visitors` → ClickHouse `all_facts_local_daily.site_visitors` → `graph.sitevisitors` (R2/CHAPI). This is a resolved-IP-grained metric — a *different grain* from `graph.usersreached` (which comes from `impression_facts.uniques`, a mixed IP/guid HLL). Do not equate the two.
- **No IP→IP bridging** available in BQ; the `*_arr` visitor IDs are already resolved — don't try to graph-join them.

## Gotchas
- **NEVER `SUM` a unique-visitor measure across hours/rows.** `site_visitors`/`new_site_visitors`/`existing_site_visitors` are HLL BYTES; the `*_arr` are raw ID arrays. A visitor who returns in multiple hours appears in multiple rows, so `SUM` over-counts. Use `HLL_COUNT.MERGE(site_visitors)` or dedup the concatenated `*_arr` arrays (`COUNT(DISTINCT id)` after `UNNEST`). Only the plain INT64 event counts (`views`, `clicks`, `competing_views`, day-buckets, `new_visitors`) are additive.
- **`site_visitors`/`new_site_visitors`/`existing_site_visitors` are BYTES, not INTEGER** — a raw `SELECT` returns a base64 sketch blob, and the prose catalog's INTEGER label is wrong. Wrap in `HLL_COUNT.*`.
- **`*_arr` columns are NON-NULL** (empty array when no visitors) — filter with `ARRAY_LENGTH(...) > 0`, not `IS NOT NULL`.
- **`competing_*` = NOT-last-touch credit**, not "a competitor's data." It's this advertiser's metric on impressions where someone else got last touch.
- **Attribution lag / late-arriving data:** because visits are bucketed by days-since-impression (`first_day…seventh_day…tail`, `last_touch_visits_day0..13`), a given `hour` partition keeps accruing visit credit for up to ~14 days after the impression hour. Recent partitions are *incomplete* — don't treat the last week as final for lag-sensitive metrics.
- **`hour` is DATETIME (no timezone).** Filter with `DATETIME` literals (`WHERE hour >= DATETIME "2026-07-01"`), not `TIMESTAMP`, to keep partition pruning.
- **`objective_id` is not the funnel stage** — join `campaigns.funnel_level`.
- **SQLMesh physical hash drifts.** The physical is `sqlmesh__summarydata.summarydata__visit_facts__918339743` today (prose catalog still says `__427634656`). Always query the clean view name `summarydata.visit_facts`; never hardcode the hash.
- **History floor is the physical build's retained window, not an absolute source floor:** current build starts `2026-03-01` (verified `MIN(hour)`). Older data is not in this physical table.

## Cost & partitioning notes
- **The one filter to always apply:** a `hour >= DATETIME "YYYY-MM-DD"` bound (DATETIME literal). Partition = DAY on `hour`; pruning works. Not required by the table (no `require_partition_filter`), but omitting it full-scans ~187M rows.
- **Physical backing:** `numRows` = 187,409,290; `numBytes` (real storage) = 135,529,769,275 (~126 GiB) — this is `approx_logical_bytes`, the whole physical table, NOT a query estimate.
- **Measured query estimates (all via `--dry_run`, 2026-07-19):**
  - `SELECT SUM(views)` (one narrow INT column), **no filter** → **1.39 GB**.
  - `SELECT SUM(views)`, **`WHERE hour >= "2026-07-01"`** (~18 days) → **0.379 GB**. Same column set as above → the 3.7x drop is pure partition pruning.
  - `SELECT *` (all ~150 cols incl. the fat `*_arr` ARRAY and BYTES HLL columns), `WHERE hour >= "2026-07-01"` → **17.56 GB** — **~46x** the one-column pruned scan. The `*_arr`/BYTES columns dominate width; never `SELECT *`.
- **Clustered on `advertiser_id, campaign_id`** — so, unlike `impression_facts` (unclustered), adding an `advertiser_id` / `campaign_id` predicate *does* prune bytes at runtime (cluster pruning; not visible in `--dry_run`, which reports the full-partition upper bound). Filter both date and advertiser when you can.
- Grain check itself (`COUNT(*)` + `COUNT(DISTINCT tuple)` over one day) processed 0.235 GB / 26s slot.

## Example queries
```sql
-- Additive event counts by campaign/day (safe to SUM):
SELECT DATE(hour) AS day, advertiser_id, campaign_id,
       SUM(views) AS view_visits, SUM(clicks) AS click_visits,
       SUM(competing_views) AS competing_visits
FROM `summarydata.visit_facts`
WHERE hour >= DATETIME "2026-07-01" AND hour < DATETIME "2026-07-08"
  AND advertiser_id = 31357            -- cluster prune
GROUP BY day, advertiser_id, campaign_id;

-- Unique site visitors over a window — HLL-MERGE the sketch, never SUM:
SELECT advertiser_id,
       HLL_COUNT.MERGE(site_visitors)     AS unique_site_visitors,
       HLL_COUNT.MERGE(new_site_visitors) AS unique_new_visitors
FROM `summarydata.visit_facts`
WHERE hour >= DATETIME "2026-07-01" AND hour < DATETIME "2026-07-08"
GROUP BY advertiser_id;
```
