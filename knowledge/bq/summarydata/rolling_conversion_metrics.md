# summarydata.rolling_conversion_metrics

## Purpose
Pre-canned "how many conversions did each advertiser get in the last 30 days" rollup. It saves you from
hand-writing the three-source UNION + trailing-window filter. Reach for it when you want a quick
per-advertiser conversion-volume snapshot; **do not** reach for it if you need a specific/other date range,
a historical snapshot, or a cheap query — the window is hard-coded and every call rescans ~113 GB.

It is an **aggregate VIEW**, not a stored table: nothing is materialized, and the physical
`sqlmesh__summarydata.summarydata__rolling_conversion_metrics__3972840797` is itself a VIEW
(numRows/numBytes = 0). Each query recomputes from scratch against the live source logs.

## Grain & keys
- **Grain:** one row per `advertiser_id`, aggregated over the trailing 30-day window. Verified 2026-07-19:
  7,422 rows = 7,422 distinct advertiser_ids (1:1). No time dimension in the output.
- **Key(s) / join columns:** `advertiser_id` (the only key; joins out to the `advertisers` dim).

## Column meanings (only the non-obvious ones)
- **`raw_conversion_rolling_30day`** — `COUNT(*)` of every conversion row across the three sources in the
  window. **NOT deduplicated**: an order that fires in more than one source (conversion_log +
  conversion_signal_log + offline_conversions) or fires multiple times is counted each time. Rows with a
  NULL `order_id` still count here. Use this only for raw volume / pixel-load, never as a conversion count.
  All-advertiser total ≈ 2.11 B (2026-07-19).
- **`unique_orderid_rolling_30day`** — `COUNT(DISTINCT order_id)` across the three sources for the
  advertiser. This is the **deduplicated conversion count**. NULL `order_id`s are dropped by COUNT DISTINCT,
  so they inflate `raw` but not this. Always ≤ `raw` (verified: 0 rows violate this). All-advertiser total
  ≈ 0.92 B — i.e. `raw` is ~2.3× `unique`, the measure of cross-source / repeat-fire duplication.
- **`advertiser_id`** — INT64; joins to the `advertisers` dim. (`advertiser_name` is not carried here;
  resolve names via `advertisers.company_name` — the vertical/name fields elsewhere are unreliable.)

## Joins & relationships
- **`advertiser_id` → `advertisers` (integrationprod dim)** — partner grain is 1 row per advertiser (1:1,
  no fan-out). Use `advertisers.company_name` for a display name; filter the dim `deleted=FALSE AND
  is_test=FALSE`. This view is already one row per advertiser, so joining out never multiplies rows.
- **Upstream sources (do not "join" — they are UNION-ed inside the view):**
  `logdata.conversion_log` (VIEW, `time` TIMESTAMP), `logdata.conversion_signal_log`
  (TABLE, DAY-partitioned on `time`), `summarydata.offline_conversions` (VIEW, `time` TIMESTAMP). Each is
  filtered `time >= CURRENT_DATE-30d AND time < CURRENT_DATE`, projected to (advertiser_id, order_id), then
  UNION ALL-ed and grouped. If you need a custom window/advertiser filter, query these sources directly.

## Gotchas
- **Fixed, non-parameterizable window.** The 30-day trailing range is hard-coded
  (`time >= timestamp(CURRENT_DATE - 30 DAY)` and `time < timestamp(CURRENT_DATE)`), evaluated in the
  session/UTC timezone. It **excludes today** (ends at yesterday 23:59:59). You cannot ask for a different
  range or a historical snapshot — the numbers slide forward every day and there is no stored history.
- **`raw` double-counts; `unique` is the real count.** ~2.3× gap comes from the same `order_id` appearing
  across the three UNION-ed sources and from repeat pixel/signal fires. Never present `raw` as "conversions."
- **No dedup except by `order_id`.** Two source rows with the same order_id collapse in `unique` but add 2
  to `raw`; a NULL order_id adds 1 to `raw` and 0 to `unique`.
- **Every call is a full recompute (~113 GB).** There is no partition column and no time column to filter on
  the view; a `WHERE advertiser_id = …` does not meaningfully prune (the UNION+aggregate scans the whole 30d
  window of all three sources first). For cost-sensitive or filtered work, hit the source tables directly.

## Cost & partitioning notes
- **No partition, no cluster, no filter to apply.** This is a computed aggregate view over a fixed window,
  so there is no partition column to prune on and `require_partition_filter` is N/A. You pay the full scan
  no matter what you SELECT or filter.
- **Measured cost (2026-07-19, us-central1 reservation):** running the full view (all-advertiser aggregate,
  reads advertiser_id+order_id+time across the three 30d source windows) = **112.8 GB billed** / 33.6 s wall.
  A `SELECT *` dry-run on the same 3-column set estimates **~121 GB**. These are the only comparable figures
  — both cover the identical column projection the view forces.
- **`approx_logical_bytes: null`** on purpose: the backing physical is itself a VIEW (numBytes 0); the real
  bytes live in the three source physicals and must not be hand-summed here.
- **Cheaper alternative:** if you only need one advertiser or a shorter window, query
  `logdata.conversion_signal_log` (DAY-partitioned) + the two conversion views directly with your own
  `time`/`advertiser_id` predicates instead of this view.

## Example queries
```sql
-- The whole view (there is no way to narrow the scan — ~113 GB every time):
SELECT advertiser_id, raw_conversion_rolling_30day, unique_orderid_rolling_30day
FROM `summarydata.rolling_conversion_metrics`
ORDER BY unique_orderid_rolling_30day DESC
LIMIT 100;   -- LIMIT does not reduce bytes scanned; aggregation runs over the full 30d window first
```
