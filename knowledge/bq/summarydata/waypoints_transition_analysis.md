# summarydata.waypoints_transition_analysis

## Purpose
Powers **Waypoints sequential-funnel analytics**: the stage-to-stage advancement fact. Each row is one user session that moved from funnel stage N (`source_event_*`) to the immediately-next stage N+1 (`target_event_*`) on a given `day`. Reach for it to compute funnel conversion / drop-off between consecutive stages, per advertiser/campaign, split by whether the session was ad-exposed (`from_verified_impression`). A Waypoint = an advertiser-defined pixel event (URL-match or delivered/custom); events are grouped into ordered funnel **stages** (`event_group` + `event_group_order`), and this view captures the *edges* between adjacent stages.

## Grain & keys
- **Grain:** one row per **consecutive funnel-stage transition instance** — (day, advertiser_id, campaign_id, GA session, source_event → target_event). The base `waypoints_fact` is filtered to `is_step_start = 1` and `has_target_transition = 1`, so each row already represents one session-step, not an aggregate.
- **Key(s) / join columns:** `advertiser_id`, `campaign_id` (MNTN hierarchy); `current_ga_client_id` / `current_session_key` (user/session); `current_ad_served_id` (served-ad UUID, when ad-attributed). No single primary key column.
- **Measure:** `COUNT(*)` = transition volume. `transition_count` is a constant 1 (see Gotchas) — do not SUM it expecting weights.

## Column meanings (only the non-obvious ones)
- **day** — DATE, the transition date and the **partition** column. View has a hardcoded floor `day >= 2026-02-10`; nothing earlier is returned even if `waypoints_fact` holds it.
- **from_verified_impression** — BOOL but observed only **TRUE or NULL** (never FALSE in sampled data). TRUE = the session's ad exposure was a verified/measurable impression; **NULL (~84% of rows) = not ad-attributed** (organic / GA-only session). Treat NULL as "no verified impression," not as unknown.
- **event_type** — the Waypoint definition type of the events on the edge. Two values observed: **`URL`** (event fired by page-URL match) and **`DLV`** (delivered/custom conversion event). Not a status flag.
- **source_event_group / target_event_group** — **advertiser-defined funnel STAGE names** (e.g. `Visitor → Intentful Visitor`, `Site Entry → Content Engagement`, `School and Program Selection → Primary Borrower Information`). These are NOT a global enum — each advertiser configures its own funnel taxonomy, so the string domain varies by advertiser.
- **source_event_group_order / target_event_group_order** — the stage ordinal (1 = top of funnel). **Invariant: `target_event_group_order = source_event_group_order + 1`** (verified 0 exceptions over 14 days) — the view keeps only strictly-consecutive-stage edges.
- **source_event_name / target_event_name** — the specific event within each stage (the endpoints of the edge). Non-NULL by construction (the view filters out NULL names).
- **current_ga_client_id** — Google Analytics client id, format `"<randomInt>.<firstVisitUnixSeconds>"` (e.g. `1005851163.1784144226`). The browser/user identifier; **populated on ~100% of rows** (0 NULL in sample). Best key for user-level dedup.
- **current_session_key** — composite session id `"<id>|<ga_client_id>|<sessionStartUnixSeconds>"` (e.g. `34114|1005851163.1784144226|1784144226`); the trailing component is a **Unix-seconds** session-start epoch. **~14.5% NULL** — use for session-level grouping when present.
- **current_ad_served_id** — UUID of the served ad/impression that drove the session (e.g. `5afe1e1d-...`). **NULL ~84%** (organic / non-ad transitions). When present, links a transition back to a specific served impression.
- **transition_count** — **constant 1** in this view (each row is one transition instance). `COUNT(*)`, not `SUM(transition_count)`, is the volume.
- **is_ordered** — **constant 1** (the outer view pre-filters `WHERE is_ordered = 1`). A dead column carrying no information here.
- **group_id** — observed **constant sentinel `0`** across all advertisers/campaigns on the sampled day (1 distinct value / 14 advertisers / 71 campaigns). **Not a usable campaign-group join key** in this view.
- **advertiser_id / campaign_id** — MNTN hierarchy ids; base-fact cluster keys. `campaign_id` is real and populated (71 distinct on one day); never NULL in sample.

## Joins & relationships
- **advertiser_id → `bronze.integrationprod.advertisers.id`** — dim, 1:1 on advertiser; many transition rows per advertiser (N:1). Filter `deleted=FALSE AND is_test=FALSE`. Use `advertisers.company_name` for names.
- **campaign_id → `campaigns.id`** — dim, 1:1 on campaign; N:1 from this fact. `campaigns.funnel_level` is authoritative for stage/objective (not `objective_id`).
- **current_ad_served_id → impression-level logs** (served-ad UUID) — N:1 (each served id is one impression; many transitions can reference the same served ad only if the ad drove multiple stage advances). ~84% NULL, so most rows do not join.
- **Event-group/name classification** derives from the Waypoints config dim `attr_advertiser_waypoints_event_mapping` (+ `attr_advertiser_selective_performance_config`), which maps event names → funnel groups/orders per advertiser (see `data_catalog.md` pixel-config section).
- **Base fact: `summarydata.waypoints_fact`** (physical `sqlmesh__summarydata.summarydata__waypoints_fact__2720337691`, day-partitioned, cluster `[advertiser_id, campaign_id, funnel_mode]`). This view = `waypoints_fact` filtered to `funnel_mode='sequential' AND has_target_transition=1 AND is_step_start=1 AND is_ordered=1`, keys non-NULL, source≠target — i.e. a projected ~4% subset. `current_user_key` is used as a filter in the base view but is **not** exposed as a column here.

## Gotchas
- **`is_ordered` ≡ 1 and `transition_count` ≡ 1 are dead constants.** The outer view already applies `WHERE is_ordered = 1`; there is no unordered/skip transition here. Use `COUNT(*)` for volume — `SUM(transition_count)` just re-counts rows.
- **`from_verified_impression` is never FALSE** — only TRUE (~16%) or NULL (~84%). NULL = organic / not-ad-attributed. A naïve `WHERE from_verified_impression = FALSE` returns nothing; use `IS NULL`.
- **No partition filter is *required* by the view.** The base fact sets `requirePartitionFilter=TRUE`, but the view bakes in `day >= 2026-02-10`, which satisfies it — so an unfiltered query **validates and silently scans all history from 2026-02-10** (~16 GB for 3 columns). Always add your own `day` predicate.
- **History floor 2026-02-10** is hardcoded in `waypoints_transition_daily`; no rows before it regardless of `waypoints_fact` depth.
- **`group_id` = 0 sentinel** — a single value across all advertisers; not a campaign-group key. Do not join on it.
- **`funnel_mode` is pinned to `'sequential'`** (filter, not a column). Non-sequential funnels are excluded, and only `advertiser_id`/`campaign_id` remain as useful cluster-pruning keys for view consumers.
- **Event-group names are advertiser-specific**, not a global enum — don't hardcode `Visitor`/`Site Entry` as a fixed domain.
- **`current_session_key` ~14.5% NULL** while `current_ga_client_id` is ~fully populated — prefer ga_client_id for user-level work, session_key for session-level.

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE day = '…'` (or a tight `day BETWEEN`). Partition = `day` (DATE).
- **Empirical partition proof (dry-run, same 3 columns `day, advertiser_id, transition_count`):** no filter = **16.05 GB** → `day = '2026-07-15'` = **172 MB** (~93× prune). Confirms `day` is the partition.
- **Column-set matters (dry-run, 1 day = 2026-07-15):** 3 narrow cols = **172 MB**; `SELECT *` = **330 MB** (~2×). Avoid `SELECT *`.
- **Actual billed (from perf log):** 14-day 8-col aggregate = **1.49 GB / 14 partitions**; single-day narrow aggregates ~**0.13–0.27 GB**.
- **Volume:** ~**46–48K rows/day** (2026-07-15 = 46,566; 2026-07-01..14 = 672,157). ~14 advertisers, ~71 campaigns per day in the sample.
- **Backing physical:** `waypoints_fact` = **54.1 GB / 232.6M rows** (2026-07-29; up from 42.5 GB/187M at enrichment; the FULL fact; this view reads a filtered ~4% projected subset — `approx_logical_bytes` above is that base-fact storage, not this view's footprint).

## Example queries
```sql
-- Stage drop-off for one advertiser/day: transitions into each target stage
SELECT source_event_group, target_event_group, target_event_group_order,
       COUNTIF(from_verified_impression) AS ad_exposed,
       COUNT(*)                          AS total_transitions
FROM `summarydata.waypoints_transition_analysis`
WHERE day BETWEEN '2026-07-01' AND '2026-07-15'
  AND advertiser_id = <AID>
GROUP BY 1,2,3
ORDER BY target_event_group_order, total_transitions DESC;
```
