# summarydata.campaign_group_audience_association_change_log

## Purpose
Audit / CDC trail of **which audience got associated with (or swapped onto) a campaign group**, by whom, and when. Reach for it to reconstruct the audience-assignment history of a campaign group or advertiser — e.g. "when did CG 129345 switch from `ABM_EcomPersona_5k-202606` to `ABM_EcomPersona_202607_7k`, and which user made the change?" It is a self-service-UI change feed, not a delivery/rollup fact table. Tiny (~39K rows / ~5.5 MB, data from 2025-01-01 → present).

## Grain & keys
- **Grain:** one row per audience-association change event on a campaign group. When an audience is first attached, one row is written (`prior_value` NULL); when an existing audience is replaced, one row is written with the old name in `prior_value` and the new name in `current_value`.
- **No single-column primary key.** `change_id` is a constant type-code (see below), NOT a surrogate row id. The natural composite key is roughly `(campaign_group_id, entity_id, time)`.
- **Join columns:** `campaign_group_id` (→ campaign_groups), `entity_id` (= audience_id → audience_audiences), `advertiser_id` (→ advertisers), `user_id` (→ users). This table is always the **many** side.

## Column meanings (only the non-obvious ones)
- **time** — native `TIMESTAMP` (UTC), the moment of the change. NOT an epoch int — no unit resolution needed. Sampled max `2026-07-20 01:25` = evening of 2026-07-19 PT, confirming UTC.
- **change_id** — constant `20` across **all** 39,190 rows. It is the numeric code for the "Audience Association" change type, **not** a per-row id. Do not treat as a unique key or filter on it expecting variety.
- **change_type** — constant `'Audience Association'`. This log currently records only that one kind of change.
- **entity_type** — constant `'audience_id'`; declares that `entity_id` holds an audience id.
- **entity_id** — the **audience_id** (INT stored as STRING) now associated with the campaign group. `SAFE_CAST(entity_id AS INT64)` joins 1:1 to `audience_audiences.audience_id`.
- **entity_text** — the audience **name** at change time; equals `current_value` in all sampled rows.
- **current_value** — the **new** (post-change) audience name.
- **prior_value** — the **previous** audience's **name**, `NULL` in ~81% of rows (7,328 of 39,190 populated). NULL means an **initial / first** audience association (no prior audience) — it is not missing data. Only the prior **name** is stored; there is **no** prior audience_id column, so the "from" audience cannot be joined by id.
- **entity_id_2 / entity_text_2 / entity_type_2** — **always NULL** for this change type (0 of 39,190 populated). Schema reserves a second-entity slot that this event type does not use.
- **user_id** — the user who made the change (self-service UI actor).

## Joins & relationships
This table is always the **N** side; joining out to the dims below is safe 1:1 (no fan-out from those partners).
- **campaign_group_id → `bronze.integrationprod.campaign_groups.campaign_group_id`** — partner grain 1 row per campaign group (1:1); this log is N:1 to it. Verified 199/200 on a recent slice (the 1 miss = a deleted/test/very-recent CG). Note the PK is `campaign_group_id`, **not** `id`. `campaign_groups` carries `product_id` (1=PTV / 2=Select / 3=QuickFrame) and `advertiser_id`.
- **entity_id (cast INT64) → `bronze.integrationprod.audience_audiences.audience_id`** — partner grain 1 row per audience (1:1); N:1. Verified **200/200**. Prefer this **raw** table over `silver.core.audiences`, which is a filtered/curated view where only ~20% (39/200) of `entity_id`s resolve — historical/deleted audiences are dropped there.
- **advertiser_id → `bronze.integrationprod.advertisers`** (1:1; N:1). Equivalently `campaign_groups.advertiser_id`.
- **user_id → `bronze.integrationprod` users dim** (1:1; N:1) — the change author.
- Remember `integrationprod` dims should generally filter `deleted=FALSE AND is_test=FALSE`, which is partly why the curated `core.audiences` view under-resolves historical `entity_id`s.

## Gotchas
- **No partition, no cluster.** A `time`/date filter does **NOT** prune — a `WHERE time >= '2026-07-01'` scan reads the same 5,504,200 bytes as `SELECT *` (dry-run confirmed). The table is tiny so it's cheap, but do not expect partition pruning.
- **change_id / change_type / entity_type are constants** — the feed presently records ONLY audience-association events. Do not treat `change_id=20` as a row key, and don't filter on these expecting multiple values.
- **entity_2 columns are entirely NULL** — reserved schema, unused for this change type.
- **`prior_value` NULL = initial association**, not missing data. Only the prior audience **name** is captured (no prior audience_id) — you cannot join the "from" audience by id.
- **Name snapshots at change time.** `entity_text` / `current_value` / `prior_value` freeze the audience name as of the change; if an audience was later renamed, these will not match the current dim name.
- **time is UTC** — convert before comparing to PT-based business days.
- **Join to raw `audience_audiences`, not `core.audiences`** for full `entity_id` resolution (see Joins).

## Cost & partitioning notes
- No partition column exists to filter — the one lever is **column selection**, not a partition filter. Avoid `SELECT *`; the table is columnar so fewer columns = fewer bytes.
- **SELECT \* full scan = 5,504,200 bytes (~5.5 MB)** (dry-run, all 14 columns). **Identical figure with `WHERE time >= '2026-07-01'`** — no pruning. Physical backing storage = 5,504,200 bytes across 39,190 rows (`bq show numBytes`).

## Example queries
```sql
-- Audience-swap history for one campaign group (only real swaps, not initial attach)
SELECT time, entity_id AS audience_id, prior_value AS from_audience,
       current_value AS to_audience, user_id
FROM `summarydata.campaign_group_audience_association_change_log`
WHERE campaign_group_id = 129345
  AND prior_value IS NOT NULL
ORDER BY time DESC;
```
