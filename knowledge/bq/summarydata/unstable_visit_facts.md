# summarydata.unstable_visit_facts

## Purpose
**NON-CANONICAL staging / experimental copy of `summarydata.visit_facts`.** Same pre-aggregated
view-through / click-through **visit** attribution content (attributed site visits, competing credit,
probabilistic attribution, HLL unique-visitor sketches) at the same hourly campaign/geo/device grain,
but with two staging-specific twists: (1) it carries a **`change_id`** column — a per-advertiser
recompute/reprocess **batch stamp** — and clusters on it; (2) it currently covers only a **subset of
advertisers** (663 distinct, vs the full advertiser universe in `visit_facts`). The `unstable_` prefix
marks it as a staging/experimental materialization whose rows are subject to being superseded by later
recompute batches — do **not** use it as a reporting source. For "how many visits did this campaign
drive," use the verified stable sibling **`summarydata.visit_facts`** (partition DAY on `hour`,
clustered `advertiser_id, campaign_id`). Reach for `unstable_visit_facts` only to inspect the
change-tracked staging output or to trace how a given advertiser's recompute batch (`change_id`) is
reflected in the facts. **No prose oracle exists for this table** (not in `data_catalog.md` /
`data_knowledge.md`); the shared-column semantics below are inherited from the verified `visit_facts`
doc, and the staging-specific claims are all live-verified (2026-07-19).

## Grain & keys
- **Grain:** exactly **one row per unique tuple of the 18 dimension keys** (same as `visit_facts`).
  Verified 2026-07-19 on the 2026-07-17 partition: `COUNT(*)` = `COUNT(DISTINCT 18-dim-tuple)` =
  `COUNT(DISTINCT 18-dim-tuple + change_id)` = **99,251** — no duplicates at grain, and adding
  `change_id` does **not** split the grain further (it is functionally determined by the row).
- **Dimension keys (18):** `hour`, `advertiser_id`, `campaign_group_id`, `campaign_id`, `channel_id`,
  `objective_id`, `group_id`, `creative_id`, `private_marketplace_id`, `country`, `metro_id`, `region`,
  `city`, `postal_code`, `domain`, `supply_vendor`, `device_type`, `pa_model_id`.
- **`change_id` is NOT a grain key** — it is a per-row **recompute-batch identifier** (see Column
  meanings). It is a cluster key, not a grain key.
- **No surrogate/event-level key** — this is a rollup. To count unique *visitors* across rows, HLL-merge
  the BYTES sketches or dedup the `*_arr` arrays; never `SUM` an integer measure across hours to get uniques.

## Column meanings (only the non-obvious ones)
**Staging-specific columns (what makes this differ from `visit_facts`):**
- `change_id` — **INT64 per-advertiser recompute/reprocess batch identifier** (a monotonically
  increasing sequence). Verified 2026-07-19: **every one of the 1,663 distinct `change_id` values maps
  to exactly ONE `advertiser_id`** (0 change_ids span multiple advertisers), and a single `change_id`
  stamps a *range* of hours/days for that advertiser (e.g. `change_id=66628` covers 45 days,
  2026-06-05→2026-07-19, 20,164 rows, 1 advertiser). So when an advertiser's attribution is
  recomputed, the affected rows across its whole date window are re-stamped with a new (higher)
  `change_id`. Higher `change_id` = more recent recompute. This is the same change-tracking concept as
  the `unstable_ui_visits` sibling's `change_id`/`change_epoch`/`change_time`/`batch_*` CDC columns,
  but the aggregated fact table keeps only the id. (The exact upstream process that assigns `change_id`
  is not documented in any prose oracle — no SQLMesh source was read; the per-advertiser-batch behavior
  above is empirical.)
- `pa_model_id` — probabilistic-attribution model id, **INT64 here** with observed values `{-6, 1001}`
  (`-6` is a sentinel/default; `1001` a real PA model). **Schema drift vs `visit_facts`, where
  `pa_model_id` is STRING.** Part of the 18-key grain but not shared with `impression_facts`/`spend_facts`.

**Shared columns — semantics inherited from the verified `visit_facts` doc:**
- `hour` — **DATETIME** partition key at hour precision (e.g. `2026-07-17 23:00:00`), no timezone. Filter
  with DATETIME literals to keep partition pruning. (`hour` here reads slightly ahead of local "now",
  e.g. MAX = `2026-07-20 09:00` on 2026-07-19 — it is UTC-based reporting hour; treat as fresh-through-now.)
- `device_type` — silver STRING (`MOBILE`, `SET_TOP_BOX`, `DESKTOP`, …), not the bronze INT code.
- `channel_id` — 8 = CTV, 1 = display. `objective_id` — **not** the funnel stage; use `campaigns.funnel_level`.
- **Additive INT64 count measures (safe to `SUM`):** `views` (attributed view-through visits), `clicks`,
  `efficient_views`, `new_visitors`, `visits_assist`, the `competing_*` counts (credit on impressions
  where this advertiser was NOT last touch), `last_touch_*`/`last_tv_touch_*`, the attribution-lag
  buckets `first_day_visits`…`seventh_day_visits` + `visits_tail` (bucketed by days between impression
  and visit), `last_touch_visits_day0`…`last_touch_visits_day13` (14-day last-touch lag curve),
  `competing_first_day_views`…`competing_seventh_day_views`, and the `probattr_*` count variants.
- **Unique-visitor columns come in TWO physical forms for the SAME set — NEVER `SUM` either:**
  - `*_arr` (e.g. `site_visitors_arr`, `new_site_visitors_arr`, `competing_site_visitors_arr`,
    `probattr_*_arr`, `first_day_visitors_arr`, `visitors_tail_arr`) — **ARRAY<STRING> of raw resolved
    visitor IDs**, NON-NULL (empty array, never NULL).
  - `site_visitors`, `new_site_visitors`, `existing_site_visitors`, and the `competing_*`/`probattr_*`
    variants — **BYTES = HLL++ serialized sketches** of the same visitor sets. Read with
    `HLL_COUNT.MERGE(col)` across rows or `HLL_COUNT.EXTRACT(col)` on one row — never `SUM`.
- **This table LACKS the `last_touch_site_visitors*` set** that `visit_facts` has: no
  `last_touch_site_visitors_arr` / `last_touch_new_site_visitors_arr` /
  `last_touch_existing_site_visitors_arr` and no BYTES `last_touch_site_visitors` /
  `last_touch_new_site_visitors` / `last_touch_existing_site_visitors`. (Only column meanings for columns
  present in this doc's AUTO:SCHEMA are given above.)

## Joins & relationships
- **`summarydata.visit_facts` (stable sibling — the canonical version, ~1:1 on the 18 dim keys for the
  covered advertiser subset):** `unstable_visit_facts` is a staging copy of the same fact. Its 663
  advertisers are a subset of `visit_facts`'s full universe, so a join is at best 1:1 per dim-tuple for
  those advertisers and empty elsewhere. **Prefer `visit_facts` outright** — do not join the two for
  reporting.
- **`impression_facts` / `spend_facts` (FULL OUTER JOIN on the 17 shared dim keys):** as with
  `visit_facts`, only the **first 17** dim keys (`hour`…`device_type`) are shared; `pa_model_id` (and
  `change_id`) exist only on this side. Joining on the full 18-key set with `USING (… pa_model_id)` errors
  (`Unrecognized name: pa_model_id`) because those tables have no `pa_model*` column. This staging table
  is NOT part of the canonical `all_facts` UNION — `all_facts` reads `visit_facts`, not this.
- **`campaigns` dim (N:1):** `campaign_id` → `campaigns` for `funnel_level` (authoritative stage;
  `objective_id` unreliable). `campaigns` = `silver.core` thin view over `bronze.integrationprod` — filter
  `deleted=FALSE AND is_test=FALSE`. Many fact rows per campaign.
- **`advertisers` dim (N:1):** `advertiser_id` → `advertisers.company_name` for names
  (`fpa_advertiser_verticals.advertiser_name` is unreliable/empty since 2025-12).
- **No IP→IP bridging** in BQ; the `*_arr` visitor IDs are already resolved — don't graph-join them.

## Gotchas
- **NON-CANONICAL / staging — do not report from this table.** Use `summarydata.visit_facts`. Rows here
  can be superseded by later recompute batches (a higher `change_id` for the same advertiser), so a
  point-in-time read is not a stable source of truth. It also covers only **663 advertisers**, not all.
- **NEVER `SUM` a unique-visitor measure across rows.** `site_visitors`/`new_site_visitors`/
  `existing_site_visitors` (+ `competing_*`/`probattr_*` variants) are **BYTES HLL sketches**; the `*_arr`
  are raw ID arrays. A returning visitor appears in multiple hourly rows → `SUM` over-counts. Use
  `HLL_COUNT.MERGE(...)` or dedup the concatenated `*_arr` via `COUNT(DISTINCT id)` after `UNNEST`. Only
  the plain INT64 event counts are additive.
- **`*_arr` columns are NON-NULL** (empty array when no visitors) — filter with `ARRAY_LENGTH(...) > 0`,
  not `IS NOT NULL`.
- **`change_id` is NOT time-ordered within a partition.** A single `hour` day holds hundreds of different
  `change_id` values (694 distinct on 2026-07-17, ranging 61,867–66,628) because each advertiser's rows
  carry that advertiser's own last-recompute batch id, and one batch spans many days. Do not treat
  `change_id` as a row timestamp — it is a per-advertiser batch sequence.
- **`pa_model_id` is INT64 here (STRING in `visit_facts`)** — cast accordingly when comparing across the
  two tables.
- **Attribution lag / late-arriving data:** visits are bucketed by days-since-impression
  (`first_day…seventh_day…tail`, `last_touch_visits_day0..13`), so a given `hour` partition keeps
  accruing credit for ~14 days after the impression hour — recent partitions are *incomplete* for
  lag-sensitive metrics.
- **`hour` is DATETIME (no timezone)** — filter with DATETIME literals to keep partition pruning.
- **History floor = the physical build's retained window, not an absolute source floor.** Current build
  starts `MIN(hour) = 2026-03-22 07:00` (verified) and is fresh through `MAX(hour) = 2026-07-20 09:00`
  (UTC). Older data is not in this physical table.
- **SQLMesh physical hash drifts.** Physical is `sqlmesh__summarydata.summarydata__unstable_visit_facts__2012328492`
  today (was `__1678881492` on 2026-07-19 — the hash rebuilt). Always query the clean view name
  `summarydata.unstable_visit_facts`; never hardcode the hash.

## Cost & partitioning notes
- **The one filter to always apply:** a `hour >= DATETIME "YYYY-MM-DD"` bound (DATETIME literal).
  Partition = **DAY on `hour`**; pruning works. Not required by the table (no `require_partition_filter`
  — a no-filter dry-run validated fine), but omitting it scans all partitions / ~8.7M rows.
- **Physical backing (real storage, resolved via `bq show` on the physical TABLE):** `numRows` =
  **8,657,469**; `numBytes` = **6,298,072,050** (~5.87 GiB) = `approx_logical_bytes`, the whole physical
  table — NOT a query estimate. This is a small staging table (~20x smaller than `visit_facts`'s ~126 GiB).
- **Measured query estimates (all via `--dry_run`, 2026-07-19; labeled by exact column set):**
  - `SELECT SUM(views)` (one narrow INT col), **no filter** → **63.4 MB** (63,384,376 bytes).
  - `SELECT SUM(views)` (same one col), **`WHERE hour >= "2026-07-10"`** (~10 days) → **14.7 MB**
    (14,650,736 bytes). Same column set → the ~4.3x drop is pure **partition pruning** (this is the
    empirical proof `hour` is the partition column).
  - `SELECT *` (all ~106 cols incl. the fat `*_arr` ARRAY and BYTES HLL columns), **`WHERE hour >=
    "2026-07-10"`** → **666.3 MB** (666,333,695 bytes) — **~45x** the pruned one-column scan. The
    `*_arr`/BYTES columns dominate width; never `SELECT *`.
- **Clustered on `advertiser_id, change_id`** (NOT `campaign_id` like `visit_facts`) — an `advertiser_id`
  predicate prunes bytes at runtime (cluster pruning; not visible in `--dry_run`, which reports the
  full-partition upper bound). Adding a `change_id` predicate also prunes. Filter date + advertiser when
  you can; note the cluster key differs from the stable sibling.
- Observed real-query costs (via `bq_run.sh`): whole-table `MIN/MAX/COUNT` over narrow cols = 0.236 GB /
  7.3s slot; one-day grain check = 0.018 GB; whole-table `change_id`-by-advertiser aggregate = 0.177 GB.

## Example queries
```sql
-- Additive event counts by advertiser/day (safe to SUM) — filter date + advertiser (cluster prune):
SELECT DATE(hour) AS day, advertiser_id, campaign_id,
       SUM(views) AS view_visits, SUM(clicks) AS click_visits,
       SUM(competing_views) AS competing_visits
FROM `summarydata.unstable_visit_facts`
WHERE hour >= DATETIME "2026-07-10" AND hour < DATETIME "2026-07-18"
  AND advertiser_id = 31357            -- cluster prune on advertiser_id
GROUP BY day, advertiser_id, campaign_id;

-- Unique site visitors over a window — HLL-MERGE the BYTES sketch, never SUM:
SELECT advertiser_id,
       HLL_COUNT.MERGE(site_visitors)     AS unique_site_visitors,
       HLL_COUNT.MERGE(new_site_visitors) AS unique_new_visitors
FROM `summarydata.unstable_visit_facts`
WHERE hour >= DATETIME "2026-07-10" AND hour < DATETIME "2026-07-18"
GROUP BY advertiser_id;

-- Inspect a recompute batch: which advertiser + date window a change_id stamped:
SELECT change_id, advertiser_id, MIN(hour) AS min_hour, MAX(hour) AS max_hour, COUNT(*) AS n_rows
FROM `summarydata.unstable_visit_facts`
WHERE hour >= DATETIME "2026-07-01"
GROUP BY change_id, advertiser_id
ORDER BY change_id DESC;
```
