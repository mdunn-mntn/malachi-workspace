# summarydata.unstable_impression_facts

## Purpose
**Non-canonical STAGING/experimental twin of `summarydata.impression_facts`** (the `unstable_*` prefix in this dataset marks a working copy of the SQLMesh model, not a table to report from). It carries the **same hourly impressions grain and the same measures** as `impression_facts` (served/won impressions only, sliced by campaign × geo × device × domain × supply), with two schema differences: it **adds** a `change_id` column (a per-advertiser CDC change-set / load marker) and it **omits** the `users_reached_ip_arr` array that the stable table has. **For all reporting use `summarydata.impression_facts`** (verified/canonical — see `knowledge/bq/summarydata/impression_facts.md`) and its rollup `all_facts`. Reach for this table only when you specifically need the `change_id` batch/version lineage, or are debugging the staging layer. It is fresh (data through the current day) and is clustered (unlike the stable table), so advertiser-scoped debugging queries are cheap here.

## Grain & keys
- **Grain:** one row per unique **(hour, advertiser_id, campaign_group_id, campaign_id, channel_id, objective_id, group_id, creative_id, private_marketplace_id, country, metro_id, region, city, postal_code, domain, unlinked, supply_vendor, device_type)** tuple — the identical 18-column grain as `impression_facts`. Verified 2026-07-19 on 2026-07-15: `COUNT(*)` = `COUNT(DISTINCT 18-col tuple)` = `COUNT(DISTINCT tuple+change_id)` = **3,753,618** (all three equal → the 18-col tuple is the key and `change_id` adds nothing). `hour` is truncated to the hour.
- **`change_id` is NOT part of the key** — it is functionally determined by the dimension tuple (an attribute). It is advertiser-scoped: on 2026-07-15 all 479 distinct `change_id`s mapped to exactly **one** `advertiser_id` each (290 advertisers, ~1.65 change_ids/advertiser/day). Values recur across dates (range ~61264-66628 seen on both 2026-05-15 and 2026-07-15) — it is **not** a per-day monotonic counter but a per-advertiser CDC change-set / load identifier.
- **Measures (additive across the grain):** `display_impressions`, `ctv_impressions`, `media_cost`, `vast_start`/`vast_firstquartile`/`vast_midpoint`/`vast_thirdquartile`/`vast_complete`, `view_impression_raw`/`view_viewed_raw`/`view_untrackable`. HLL sketches (`uniques`, `existing_users_reached`, `new_users_reached`) + their `_arr` twins are reach, not additive.

## Column meanings (only the non-obvious ones)
- **`change_id`** — INT64, the **distinguishing column vs the stable `impression_facts`** (which has no `change_id`). A per-advertiser **CDC change-set / load-batch marker** carried in this staging layer and dropped when merged into the canonical table. Empirically (2026-07-15): each `change_id` belongs to exactly one `advertiser_id`; an advertiser typically has 1-2 `change_id`s per day; values recur across days (not a monotonic per-day counter). It is the **second clustering key** (`advertiser_id, change_id`), so filtering by it prunes. Functionally determined by the dimension tuple — never needed to make a row unique.
- **`hour`** — `DATETIME` truncated to the hour; this is the **DAY partition key**. Wall-clock DATETIME (no INT epoch, no unit conversion) — filter as `WHERE hour >= DATETIME("...")`. Per the stable sibling's live column description the wall-clock is in the **advertiser's local timezone** (no stored offset), so `DATE(hour)` is a per-advertiser local day. Note the observed `MAX(hour)` can sit slightly ahead of "today" (2026-07-20T07:00 while today is 2026-07-19) — a consequence of the per-advertiser local-tz stamping / near-real-time loading.
- **`display_impressions` vs `ctv_impressions`** — impression count split by channel, not summed. Verified 2026-07-15: `channel_id = 8` (CTV) rows populate `ctv_impressions` (with only trivial `display_impressions` leakage), `channel_id = 1` (display) rows populate `display_impressions` and leave `ctv_impressions = 0`. **Total impressions per row = `display_impressions + ctv_impressions`.**
- **`unlinked`** — `BOOL` dimension, empirically **constant FALSE** (all sampled rows 2026-07-15 were FALSE), same as the stable sibling — the source keeps only linked/served/won impressions. Treat as a passthrough that never varies, not a live slicer.
- **`media_cost`** — `NUMERIC` raw media cost for the slice (not client billing / not margin-adjusted). CTV cost-per-impression is roughly an order of magnitude higher than display (same behavior as the stable table).
- **`vast_*`** — VAST video-quartile completion counts (CTV/video); monotonically non-increasing `vast_start ≥ … ≥ vast_complete`.
- **`view_impression_raw` / `view_viewed_raw` / `view_untrackable`** — raw viewability counters (measured / of-those-viewable / unmeasurable). Note this table uses the `_raw` variants (like the stable `impression_facts`); the `unstable_all_facts` twin instead exposes the un-suffixed `view_impression`/`view_viewed`.
- **`uniques` / `existing_users_reached` / `new_users_reached` (BYTES) + their `_arr` twins** — reach, **not** additive. Column names/types are identical to the stable `impression_facts`, and this is the same SQLMesh model's staging output, so the semantics carry over: the **BYTES** columns are HLL++ sketches (combine with `HLL_COUNT.MERGE`, read cardinality with `HLL_COUNT.EXTRACT` — never SUM); the **`_arr`** columns are **raw `ARRAY<STRING>` of the distinct key values** (count with `UNNEST` + `COUNT(DISTINCT)`, not `HLL_COUNT`). `uniques` uses the **MIXED channel-conditional key** — CTV/video legs key on served IP, display legs key on guid — so it over-counts the served-IP universe ~2× (TI-1019). See `impression_facts.md` for the authoritative treatment. NOTE: this staging table does **not** have the `users_reached_ip_arr` column the stable table has, so there is no raw IP-only reach array here.

## Joins & relationships
- **`summarydata.impression_facts` (stable canonical twin)** — same hourly impressions grain and measures; this staging copy adds `change_id` and drops `users_reached_ip_arr`. ⚠️ **Do NOT UNION or join this against `impression_facts` / `all_facts`** — they represent the **same** underlying served impressions (staging vs merged), so combining them double-counts. Pick one; for reporting pick the stable table.
- **`bronze.integrationprod` dimensions** — `advertiser_id`→`advertisers`, `campaign_id`→`campaigns` (use `funnel_level` for stage; `objective_id` is unreliable for stage), `creative_id`→`creatives`, `campaign_group_id`→`campaign_groups` (has `product_id` 1=PTV/2=Select/3=QuickFrame). Each is **N:1** (many fact rows per dim row) — safe (no fan-out) provided you filter the dims `deleted=FALSE AND is_test=FALSE`.
- **`logdata.cost_impression_log`** — the ultimate physical upstream (served/won rows, `unlinked=FALSE AND ad_served_id IS NOT NULL`). This staging fact is an hourly aggregate of it; do not join them (double-count).
- **Fan-out note:** this table is itself unique on the 18-col tuple (and on tuple+change_id), so as a join *left* side it does not fan out on its own key; fan-out risk comes only from N:1 dimension joins done incorrectly (unfiltered soft-deleted/test dims) or from accidentally combining it with the canonical siblings.

## Gotchas
- **Non-canonical — do not report from it.** The `unstable_` prefix marks a SQLMesh staging/experimental copy. Reporting numbers come from `impression_facts` / `all_facts` (and downstream ClickHouse `all_facts_local_daily` → CHAPI → R2 `graph.*`). This table can be rebuilt/repartitioned without notice (physical `creationTime` == `lastModifiedTime`, i.e. freshly materialized).
- **`change_id` is a staging artifact, not a business dimension.** It exists only here (the canonical table drops it). Don't group reporting metrics by it. It's advertiser-scoped and recurs across days — treat it as CDC/load lineage, not a slicer.
- **`uniques` is a MIXED IP/GUID key** — do not read it as "households/IPs reached" (~2× over-count vs served IPs, TI-1019). For a served-IP denominator use `COUNT(DISTINCT ip)` on `cost_impression_log` (this staging table lacks the `users_reached_ip_arr` fallback the stable table offers).
- **Impressions split across two columns** — always `display_impressions + ctv_impressions`; summing only one silently drops a channel.
- **`hour` is a DATETIME in the advertiser's local timezone** — compare against `DATETIME(...)` not `TIMESTAMP(...)`; `DATE(hour)` is a per-advertiser local day, so a fixed `hour` window mixes absolute instants across advertisers and is off by each advertiser's offset when joined to UTC-stamped tables.
- **HLL BYTES columns are not summable; the `_arr` twins are not sketches** (`MERGE`/`EXTRACT` on BYTES; `UNNEST`+`COUNT(DISTINCT)` on the arrays).
- **~120-day rolling window** — observed data spans 2026-03-22 → present (121 distinct days). No partition-expiration is set on the physical, but the window is bounded in practice; verify `MIN(hour)` before assuming deep history (the stable `impression_facts` goes back much further).

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE hour >= DATETIME("...") AND hour < DATETIME("...")`. `hour` is the DAY partition (confirmed empirically 2026-07-19). `require_partition_filter = false`, so a missing date filter silently full-scans.
- **Bonus lever (unlike the stable table):** this physical **IS clustered on `(advertiser_id, change_id)`** (`bq show`, 2026-07-19), so an `advertiser_id` (or `change_id`) filter prunes at **runtime** — the stable `impression_facts` is unclustered and gains nothing from an advertiser filter. Note dry-run estimates do **not** reflect cluster pruning; you only see the benefit in actual billed bytes.
- **Physical:** `sqlmesh__summarydata.summarydata__unstable_impression_facts__3085155177` — TABLE, **455,895,586 rows**, **168.1 GB** backing storage (`bq show` numBytes = 168,138,951,183 B, 2026-07-19). Partition DAY on `hour`; clustering `(advertiser_id, change_id)`; no partition expiration set. (This is ~6% the size of the 2.89 TB stable `impression_facts` — it holds a shorter window.)
- **Dry-run cost figures** (decimal GB = bytes ÷ 1e9; labeled by exact column set — do NOT cross-compare different column sets):
  - `SELECT hour`, **no** date filter → **3.65 GB** (3,647,164,688 B — scans `hour` across all 121 partitions).
  - `SELECT hour`, 2-day `hour` filter → **0.062 GB** (62,005,416 B; ~59× prune → confirms `hour` is the DAY partition).
- **Actual-run figures** (billed bytes — these DO reflect runtime cluster pruning):
  - `COUNT(*) + SUM(media_cost)`, 1 day, no advertiser filter → **0.084 GB** billed (3,753,618 rows).
  - same + `advertiser_id = 31357` → **0.008 GB** billed (27,984 rows; ~10× less → confirms clustering on `advertiser_id` prunes).
- **Rule of thumb:** narrow the `hour` window first (only prune lever that shows in dry-run), then add an `advertiser_id`/`change_id` filter to cut runtime bytes further, and select only needed columns.

## Example queries
```sql
-- Debug a single advertiser's staging impressions for one day (date + clustered advertiser filter)
SELECT DATE(hour) AS day,
       SUM(display_impressions + ctv_impressions) AS impressions,
       SUM(media_cost) AS media_cost,
       COUNT(DISTINCT change_id) AS change_batches
FROM `summarydata.unstable_impression_facts`
WHERE hour >= DATETIME("2026-07-15") AND hour < DATETIME("2026-07-16")
  AND advertiser_id = 31357
GROUP BY day;

-- Reach from the scalar HLL sketch (BYTES) — MERGE, never SUM.
-- NOTE: `uniques` is the MIXED IP(CTV)/GUID(display) key — over-counts served IPs (~2x).
SELECT HLL_COUNT.MERGE(uniques) AS reach_mixed_key
FROM `summarydata.unstable_impression_facts`
WHERE hour >= DATETIME("2026-07-15") AND hour < DATETIME("2026-07-16")
  AND advertiser_id = 31357;
```
For canonical reporting, run the equivalent query against `summarydata.impression_facts` instead.
