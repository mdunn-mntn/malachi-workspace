# summarydata.last_tv_touch_visits

## Purpose
Row-level site visits attributed to the **last CTV / TV ad touch** in a user's path. This is one **attribution-model variant** of the site-visit stream: it credits each visit to the most recent *CTV* impression the user saw (channel_id ≈ 8), separate from the display/overall `last_touch` model and from the `default` (view+click) counts. Reach for it when you specifically need TV-driven visit credit — e.g. isolating CTV prospecting's contribution — and NEVER as a general "all visits" table (that is `visits` / `ui_visits` / `clickpass_log`). `last_tv_touch` revenue/visits concentrate in the **CTV prospecting stage** and go to ~0 at mid-funnel (fl=2). Sibling: `last_tv_touch_conversions` (same idea for conversions).

## Grain & keys
- **Grain:** one row per TV-last-touch-attributed visit event. On 2026-07-10, 627,222 rows vs 626,056 distinct `(advertiser_id, guid, epoch)` → **~99.8% unique** on that natural key. Unlike `ui_visits` (which fans the same visit out across 15+ attribution-model rows), this table does **NOT** fan out per model — each visit appears once, carrying the single winning `attribution_model_id`.
- **Natural key:** `(advertiser_id, guid, epoch)` — dedupe/join on `epoch`, **NOT** `time`. `epoch` is microseconds and the **higher-fidelity** timestamp; `time` is stored second-truncated for ~51% of rows, so `epoch = UNIX_MICROS(time)` holds for only ~49% (307,572/627,222 on 2026-07-10). See Column meanings.
- **Join keys:** `ad_served_id` (→ impression/event logs), `impression_id`, `campaign_id`, `advertiser_id`.

## Column meanings (only the non-obvious ones)
- **`time` / `epoch`** — the *visit* time. `epoch` is **microseconds** and the higher-fidelity value; `time` (the partition column) is **second-truncated for ~51% of rows**. So `epoch = UNIX_MICROS(time)` holds for only **~49%** (307,572/627,222 on 2026-07-10); in the rest `UNIX_MICROS(time)` ends in `000000` while `epoch` keeps the sub-second micros (max gap ≈ 0.999998s). Worked row: `TIMESTAMP_MICROS(1783646664911935)` = `2026-07-10 01:24:24.911935`, whereas `UNIX_MICROS(TIMESTAMP('2026-07-10 01:24:24'))` = `1783646664000000` (911,935µs lower — the whole-second literal ≠ the sub-second epoch). **Derive/dedupe on `epoch`; do not assume `epoch = UNIX_MICROS(time)`.**
- **`impression_time` / `impression_epoch`** — the *attributed (last-TV) impression* time. `impression_epoch` is also **microseconds** (millisecond precision; e.g. `1783026111974000`). Note `impression_time` TIMESTAMP is truncated to whole seconds while `impression_epoch` keeps the ms.
- **`elapsed_time`** (INTERVAL) — impression→visit gap (e.g. `0-0 0 172:22:33` = ~172h). Attribution windows for TV are long, so multi-day gaps are normal.
- **`recency_elapsed_time`** (INTERVAL) — usually **NULL** in this table (0 populated in the 2026-07-10 sample rows).
- **`channel_id`** — channel of the *attributed impression*. Overwhelmingly **8 = CTV** (this is TV-last-touch); a small display (`1`) and NULL residual. (1=display, 8=CTV per catalog.)
- **`attribution_model_id`** — the attribution model that produced this last-TV-touch credit. **Multiple ids coexist across rows** (sample day: 12, 5, 4, 13, 6, 14, 0, 32, 34, 26 …), but each row carries exactly one — it is **not** a fan-out key. `attribution_model_type_id` (present in `ui_visits`) does **not** exist here.
- **`pa_model_id`** — probabilistic-attribution model id; effectively single-valued in-sample (1 distinct on 2026-07-10).
- **`ad_served_id`** — UUID of the attributed CTV impression; primary join to impression/event logs. **`first_touch_ad_served_id`** — the first impression in the path (for first-touch comparison).
- **IP columns (four of them):** `ip` = visit-time IP. **`ip_raw` ≡ `ip` by construction** (100% equal in-sample) — the `ui_visits` ip-vs-ip_raw ambiguity does NOT apply here. **`last_touch_ip`** ≈ `ip` (99.97% equal, never NULL). **`impression_ip`** = IP at the attributed CTV impression — differs from `ip` in ~24% of rows (cross-device) and is NULL in ~0.85%.
- **`is_cross_device`** — impression device ≠ visit device; ~**48%** TRUE (high, expected for CTV: ad on the TV, visit on phone/laptop).
- **`click`** — TRUE = click-through visit (~3% in-sample); the rest are view-through.
- **`from_verified_impression`** — attributed via MNTN's verified-impression attribution (UI-facing). ~**98%** TRUE. Filter `= TRUE` to match what the UI reports.
- **`is_new`** — first visit for this advertiser (NTB flag); ~75% TRUE in-sample.
- **`efficient`** — efficient-attribution flag. **`guid`** — visitor cookie/device id, NOT a row id.

## Joins & relationships
- **`ad_served_id` → impression/event logs** (`logdata.cost_impression_log`, `logdata.event_log`, `summarydata.clickpass_log`). Partner grain: one impression can drive several visits. In-sample `COUNT(DISTINCT ad_served_id)` = 613,465 vs 627,222 rows, so ad_served_id repeats modestly. **Fan-out:** joining impression→this table can fan out; visit→impression is ~1:1. Use a ≤30-day impression lookback (impression_time ≤ ~30d before visit, though TV windows run longer than display).
- **`campaign_id` → `bronze.integrationprod.campaigns`** (PK is `campaign_id`, **NOT** `id`; there is no `silver.core.campaigns`) for `objective_id` / `funnel_level` / `campaign_group_id`. Partner grain 1:N (one campaign → many visits). Filter `deleted=FALSE AND is_test=FALSE`.
- **`advertiser_id` → `bronze.integrationprod.advertisers.company_name`** (1:N).
- **Relationship to the visit stream:** this is the **last-TV-touch attribution VARIANT** of the same visits carried in `visits` / `ui_visits`. It is a **separate model** from the display/overall `last_touch` and from `default` — the three can credit the *same* visit to *different* campaigns. They coincide only at the account total and diverge per stage. **⛔ Do NOT sum `last_touch + last_tv_touch` (or `default + last_tv_touch`) to "add CTV back" — that double-counts** any visit exposed to both a display and a TV touch. Sibling `last_tv_touch_conversions` is the conversion analog.

## Gotchas
- **Attribution-variant, not additive.** Never add these counts to `last_touch`/`default` visit counts — double-count. See `data_catalog.md` § `sum_by_campaign_by_day` attribution-variant warning (verified AUDI-1070, Avon AID 31921).
- **NOT a per-model fan-out** (contrast `ui_visits`, which repeats each visit across 15+ model rows). Here `(advertiser_id, guid, epoch)` is ~99.8% unique, so a plain `COUNT(*)` ≈ visit count. But `ad_served_id`/`impression_id` repeat modestly, so `COUNT(DISTINCT ad_served_id)` **undercounts** visits by ~2%.
- **Predominantly CTV credit.** `channel_id` is **~97% CTV(8)**, with a residual **~2% display(1)** and **~1% NULL** (2026-07-10: 608,437 / 13,459 / 5,326) — not literally CTV-only. Its revenue is ~0 at mid-funnel (fl=2) and concentrates in CTV prospecting; don't read it as an account-wide visit source.
- **`ip_raw` ≡ `ip`** here (no ip-vs-ip_raw ambiguity). If you want the impression-side IP use `impression_ip` (differs ~24% on cross-device); `last_touch_ip` tracks `ip`.
- **No rolling TTL.** Full daily history from **2023-08-15** through current day (unlike `conversions`' 60-day window). Physical is a **materialized TABLE** (not a view-on-visits like `ui_visits`), so its freshness is independent and current (max `time` = 2026-07-19 same-day in-sample). The `__NULL__` partition exists but holds **0 rows** — no NULL-`time` rows to worry about.
- **Cross-device is high (~48%)**, by design — do not treat impression IP/geo as the visit's IP/geo.

## Cost & partitioning notes
- **Partition:** DAY on **`time`** (TIMESTAMP), confirmed empirically. **Cluster:** `[advertiser_id, time]`. `require_partition_filter = false` (full-table dry-run succeeds without a filter) — but **always add a `time` range anyway**.
- **The one filter to always apply:** `WHERE time >= TIMESTAMP('<start>') AND time < TIMESTAMP('<end>')`. Then narrow `advertiser_id` (leading cluster key) to prune further within the day.
- **Dry-run figures (labeled by column set):**
  - 1 column (`advertiser_id`), **no filter** → **5.23 GB** (upper bound 5,228,248,616 B).
  - 1 column (`advertiser_id`), **1 day** → **10.0 MB** (10,035,552 B) — partition prune ≈ **521×**.
  - `SELECT *`, **1 day** → **270 MB** (269,791,214 B).
  - `SELECT *`, **whole table** → **269 GB** (269,089,878,815 B) = `numTotalLogicalBytes` (the `approx_logical_bytes` for the physical). ~653.5M rows across **1,070 dated daily partitions** (+1 `__NULL__` partition holding 0 rows; 1,071 total in `INFORMATION_SCHEMA.PARTITIONS`; floor 2023-08-15).
- Avoid `SELECT *` — pick columns; the wide row (four IP columns + intervals) makes full-row scans ~27× the single-column cost per day.

## Example queries
```sql
-- TV-last-touch visits for an advertiser over a window (UI-matching, verified only)
SELECT time, advertiser_id, campaign_id, guid, ad_served_id, ip, click, is_new
FROM `summarydata.last_tv_touch_visits`
WHERE time >= TIMESTAMP('2026-07-10') AND time < TIMESTAMP('2026-07-17')
  AND advertiser_id = <AID>
  AND from_verified_impression = TRUE;

-- Daily TV-attributed visit volume (one row per visit → plain COUNT is safe)
SELECT DATE(time) AS d, COUNT(*) AS tv_visits, COUNTIF(click) AS click_visits
FROM `summarydata.last_tv_touch_visits`
WHERE time >= TIMESTAMP('2026-07-01') AND time < TIMESTAMP('2026-07-11')
GROUP BY d ORDER BY d;
```

## Observed facts
- **CIL attribution join key = `impression_id` (the `.steelhouse` composite, e.g. `1783542586487865.3413280614.142.steelhouse`), NOT `ad_served_id`.** `ad_served_id` is a different UUID (`fc632b4c-...`); it differs from `impression_id` on **100%** of rows and would return ~0 matches against `cost_impression_log.impression_id`. Join `cost_impression_log.impression_id = last_tv_touch_visits.impression_id` (1:1; CIL PK unique; ~99.99% of prospecting visits match a CIL impression). Every visit event maps to exactly one impression_id (no multi-count). Verified `hhst_efficiency_sizing` 2026-07-28.
- **Attribution tail runs LONG: 21.6% of visits land >14 days after the attributed impression, 15.6% >20d, p90 = 28d, p99 = 74d (median 5d).** A +14d visit window truncates ~15-22% of a cohort's visits (understates IVR, inflates CPV) and can be band-differential — size the visit window **≥30-45d past the last impression day** for stable IVR/CPV. Verified `hhst_efficiency_sizing` 2026-07-28.
