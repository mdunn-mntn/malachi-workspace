# summarydata.unstable_ui_conversions

## Purpose
**Non-canonical STAGING / experimental table — do NOT use for conversion or revenue reporting.** This is an
attribution-audit snapshot maintained in the BER staging area (`sqlmesh__ber_stg`). For each attribution-change
event (`change_id`, one per advertiser per change), it captures that advertiser's attributed conversion set as it
looked **before** the change (`batch_source = 'pre_change'`) and **after** it (`batch_source = 'post_change'`), so the
delta in attributed conversions / revenue caused by the change can be measured. The `unstable_` prefix and `ber_stg`
backing both mark it as experimental and subject to schema/definition churn.

**Reach for the canonical sibling `summarydata.ui_conversions` for any real attribution, conversion-count, or revenue
work.** Only touch this table when specifically auditing an attribution change (pre-vs-post conversion diff).

## Grain & keys
- **Grain:** one row per **(conversion event × `change_id` × `source_type` × pre/post snapshot)**. A single
  conversion is re-emitted once for every `change_id` that touched its advertiser, separately for each `source_type`,
  and separately in the pre_change and post_change snapshots — so one physical conversion produces many rows.
- **Uniqueness (verified):** within a fixed (`source_type`, `batch_source`), the tuple
  (`epoch`, `advertiser_id`, `change_id`) is effectively unique (rows_per_key = 1.000; residual dup ≈0.02–0.03%).
- **Conversion identity:** `epoch` (= conversion micros) + `advertiser_id` (+ `order_id`/`ip`) identifies the
  underlying conversion; `change_id` + `batch_source` identify the audit snapshot it belongs to.
- **`change_id` is 1:1 with `advertiser_id`** — verified 0 change_ids span >1 advertiser (5,917 change_ids over
  ~672 advertisers → many change_ids per advertiser). This is why the physicals cluster on (advertiser_id, change_id).
- **View = UNION ALL of two physicals** (both `TABLE`, partitioned on `time` DAY, clustered advertiser_id+change_id):
  `sqlmesh__ber_stg.ber_stg__unstable__conversions_pre_change__1453283275` (1,480,129 rows, 3.12 GB, tagged
  `batch_source='pre_change'`) + `..._post_change__2857904261` (1,093,936 rows, 2.45 GB,
  **requirePartitionFilter=TRUE**, `batch_source='post_change'`). Full view = 2,574,065 rows.

## Column meanings (only the non-obvious ones)
**Epoch units are MIXED — do not apply a single divisor (all verified against the paired TIMESTAMP columns):**
- `epoch` = **MICROSECONDS** = `UNIX_MICROS(time)` (exact match). `time` is the partition column and = the
  **conversion** timestamp.
- `event_epoch` = **MICROSECONDS**, anchored to `event_time` (`event_time` is truncated to seconds; `event_epoch`
  carries the sub-second micros — e.g. 1779536744538207 vs `UNIX_MICROS(event_time)` 1779536744000000). `event_time`
  is the underlying pixel/event fire — chronologically **before** `time`.
- `impression_epoch` = **MICROSECONDS** (millisecond resolution: 1779447639281000, trailing 000). `impression_time`
  is the winning impression — chronologically first (`impression_time` < `event_time` < `time`).
- `change_epoch` = **SECONDS** = `UNIX_SECONDS(change_time)` (1780500600 = `UNIX_SECONDS`; `UNIX_MICROS(change_time)`
  = 1780500600000000). Timestamp of the attribution-change event this snapshot belongs to.
- `batch_epoch` = **SECONDS**, no paired TIMESTAMP column — `TIMESTAMP_SECONDS(batch_epoch)` = when the ETL batch
  that wrote the row ran (pre_change batches run up to "today"; the table is actively appended).
- `batch_source` = which physical / snapshot side the row came from: exactly `'pre_change'` or `'post_change'`
  (verified domain). This is the primary discriminator for the audit.
- `source_type` = attribution lineage, exactly two values (verified): `'conversions'` (general/display) and
  `'last_tv_touch_conversions'` (CTV last-TV-touch). Both are present in each snapshot side.
- `change_id` = attribution-change event id (1:1 with `advertiser_id`); the cluster key. It is an internal
  experiment key, not a FK to a documented dim.
- `conversion_type` = STRING; NULL/untyped conversions render as the string sentinel `'-101'` (plus the wider
  six-sentinel family `-100/-101/-102/-105/-106/-107`) — same rendering as canonical `ui_conversions`. Never filter
  `conversion_type IS NULL`; use `REGEXP_CONTAINS(conversion_type, r'^-[0-9]+$')` to exclude sentinels. (558 distinct
  values observed over the window.)
- `order_amt` = order value in **local currency** (`order_curr`). **There is NO `order_amt_usd` column here**
  (unlike some sibling views) — use `order_amt` + `order_curr`.
- `conversion_day` = INT day-offset (lookback bucket), not a date; `impression_id`/`ad_served_id` link to the
  attributed impression; `is_pa` / `is_competing` / `conversion_assist` are attribution-role booleans;
  `from_verified_impression` flags conversions tied to a verified impression.

## Joins & relationships
- **`advertiser_id` → `bronze.integrationprod.advertisers`** (dim, 1 row/advertiser → **1:N safe**, this table is the
  N side). Join on `advertiser_id`, filter `deleted=FALSE AND is_test=FALSE`; use `company_name` for the label.
- **`campaign_id` / `group_id` / `creative_id` → `campaigns` / `campaign_groups` / `creatives` dims** (each 1 row per
  entity → safe fan-out from this side).
- **`change_id` → 1:1 with `advertiser_id` here**; it is an internal BER-staging change-event key with no documented
  partner dim to join. Do not treat as a global conversion id.
- **Self-pairing (pre↔post):** join pre_change to post_change on
  (`epoch`, `advertiser_id`, `change_id`, `source_type`) for a **1:1** before/after comparison of the same
  conversion under the same change — that is the intended analytical join.
- **DANGER — do NOT join this to any per-conversion table (e.g. `ui_conversions`, `impression_log`) on conversion
  keys expecting 1:1.** One conversion is duplicated across many `change_id`s (up to hundreds per advertiser) × 2
  `source_type`s × 2 snapshots, so such a join multiplies rows massively. Always pin `batch_source` **and** a single
  `change_id` (or dedup) first.

## Gotchas
- **NON-CANONICAL / experimental.** `unstable_` + `ber_stg` backing. Never use for conversion counts or revenue —
  those belong to `summarydata.ui_conversions`. Definition/schema can churn without notice.
- **Massive intentional duplication.** `COUNT(*)` over-counts conversions ~1.9x (pre) / ~1.25x (post) *within a
  single snapshot family*, and far more across `change_id`s. To count conversions: filter to one `batch_source`, one
  `source_type`, one `change_id` — or `COUNT(DISTINCT (epoch, advertiser_id, ...))`.
- **Mixed epoch units** (see Column meanings): micros for `epoch`/`event_epoch`/`impression_epoch`, seconds for
  `change_epoch`/`batch_epoch`.
- **The view is UNQUERYABLE without a `time` filter** — the post_change physical has requirePartitionFilter=TRUE, so
  a bare `SELECT ... FROM unstable_ui_conversions` **errors** (not just costs more): "Cannot query over table ...
  without a filter over column(s) 'time'." Always `WHERE time >= ... AND time < ...`.
- **Bounded, batch-appended window.** `time` spans ~2026-01-31 → 2026-07-20 (verified); it is not a continuous live
  feed for arbitrary dates. `batch_epoch` shows pre_change is still being appended.
- **`conversion_type` NULL sentinel `'-101'`** (and the six-sentinel family) — same as `ui_conversions`.
- `time` (partition) = conversion time, which is chronologically **after** `impression_time` and `event_time`;
  filtering on `time` bounds the conversion date, not the impression date.

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE time >= TIMESTAMP('…') AND time < TIMESTAMP('…')`. It is **mandatory**
  (the view errors without it) and it is the partition (`time`, DAY) — verified: a bare scan errors on
  requirePartitionFilter; a one-day `time` filter prunes to 89-ish partitions cleanly. Secondary prune:
  `advertiser_id` then `change_id` (cluster order).
- **Cost figures (all `--dry_run`, labeled by exact column set — only same-column-set figures are comparable):**
  - one day (`WHERE time` in [2026-06-01, 2026-06-02)), **`SELECT *`** (all 56 columns): **≈74.2 MB** (74,217,354 bytes).
  - one day, **single `time` column only**: **≈0.26 MB** (264,616 bytes) — ~280× cheaper than `SELECT *`; always
    project only needed columns.
- **approx_logical_bytes = 5,570,843,147** (real backing storage, summed across the two UNION physicals:
  3,124,537,416 pre + 2,446,305,731 post; from `bq show` numBytes). No TTL / expiration on either physical.

## Example queries
```sql
-- Before/after conversion diff for one attribution change (the intended use)
SELECT pre.advertiser_id, pre.change_id, pre.source_type,
       COUNT(*)               AS n_conversions,
       SUM(post.order_amt) - SUM(pre.order_amt) AS revenue_delta
FROM `summarydata.unstable_ui_conversions` pre
JOIN `summarydata.unstable_ui_conversions` post
  USING (epoch, advertiser_id, change_id, source_type)
WHERE pre.batch_source  = 'pre_change'
  AND post.batch_source = 'post_change'
  AND pre.time  >= TIMESTAMP('2026-06-01') AND pre.time  < TIMESTAMP('2026-06-15')
  AND post.time >= TIMESTAMP('2026-06-01') AND post.time < TIMESTAMP('2026-06-15')
GROUP BY 1,2,3;
```
