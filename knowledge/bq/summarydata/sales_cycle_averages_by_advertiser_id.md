# summarydata.sales_cycle_averages_by_advertiser_id

## Purpose
Pre-aggregated "how long is this advertiser's sales cycle" rollup. For each advertiser and each `day` it stores the average **sales-cycle time** — seconds elapsed from a visitor's first page view to their conversion — smoothed over trailing 1-day, 7-day, and 30-day windows. Reach for it instead of the raw per-conversion source (`advertiser_sales_cycle_by_day`, ~50M–1.9B rows/day) whenever you need a stable advertiser-level cycle-length metric, e.g. attribution-window sizing, pacing, or benchmarking time-to-convert. It is **fresh through the current day** (unlike the `sum_by_*` rollups, which lag ~17 days).

## Grain & keys
- **Grain:** one row per **(day, advertiser_id)** — verified 1:1 (462,873 rows = 462,873 distinct day×advertiser pairs; zero duplicates).
- **Key(s) / join columns:** `day` (DATE, partition) + `advertiser_id` (INT64). `advertiser_id` joins to the `advertisers` dim; `day`+`advertiser_id` line up with other daily advertiser rollups.

## Column meanings (only the non-obvious ones)
- **`avg_sales_cycle_time_30_day` / `_7_day`** — mean `sales_cycle_time` in **SECONDS** (fractional) over conversions in the **trailing N calendar days ending on `day` (inclusive)**, pooled across all qualifying conversions. Verified exact against the source: for advertiser 12373 on 2026-07-19 the 30-day column = 9731.51563973437 and the source pooled mean over `day BETWEEN 2026-06-20 AND 2026-07-19` = 9731.515639734376; the 7-day column = 8523.982556552633 matches `day BETWEEN 2026-07-13 AND 2026-07-19`. Divide by 86,400 for **days** (median 30-day value ≈ 852,104 s ≈ 9.9 days; mean ≈ 12 days on 2026-07-19).
- **`avg_sales_cycle_time_1_day`** — nominal trailing 1-day average, in seconds. **Does NOT equal the same-day pooled mean** and its exact windowing is unverified: for adv 12373 on 2026-07-19 this column = 12,106.7 s while the source pooled mean of conversions dated 2026-07-19 is only 0.19 s, and the column exceeds both the 7-day and 30-day columns. It behaves like a recency-weighted / most-recent-active construction rather than a literal one-calendar-day pooled mean. NULL on ~16% of rows (no qualifying recent conversion). **Prefer the 7-day or 30-day column** for stable use.
- **NULL semantics:** a window is NULL when no conversion in that window has a non-NULL `sales_cycle_time` (i.e. no conversion could be matched back to a first page view). NULL rate rises as the window shrinks: 30-day = 0% (462,873/462,873 populated), 7-day = 6.3% (29,075 NULL), 1-day = 16.0% (73,915 NULL). The 30-day column is effectively always populated for any advertiser active in the trailing month.
- **`day`** — the as-of / compute date and DATE partition key (the right edge of each trailing window), NOT a conversion timestamp.

## Joins & relationships
- **Source (upstream):** `summarydata.advertiser_sales_cycle_by_day` — raw, one row per conversion (cols: guid, ip, conversion_time/epoch, first_page_view_time/epoch, `sales_cycle_time` seconds, is_new), partitioned by `day`. That table is **1:N per (day, advertiser_id)** (tens of millions to ~1.9B rows/day). This averages table is its pre-aggregated rollup — do NOT re-join to the source to "recompute," it fans out massively and scans tens of GB; this table already is the aggregate.
- **`advertiser_id` → `bronze.integrationprod.advertisers`** (also `silver.core`) — dim is **1 row per advertiser** (1:1, no fan-out; filter `deleted=FALSE AND is_test=FALSE`). Join for `company_name` (the `advertiser_name` in vertical tables is unreliable/empty since 2025-12).
- **(day, advertiser_id) → other daily advertiser rollups** (e.g. `summarydata.sum_by_advertiser_by_day`) — partner grain 1 row per (day, advertiser_id), **1:1, safe** to co-join for a wide advertiser-day fact row. (Note the `sum_by_*` rollups lag ~17 days; this table does not.)

## Gotchas
- **Unit is SECONDS, fractional.** Divide by 86,400 for days. Values span from ~1e-4 s (near-instant) to ~7.77M s (≈90 days).
- **Near-zero averages are real, not errors.** Down to ~0.0001 s — these are returning / already-known visitors whose first page view ≈ conversion event (same session). They drag some advertisers' averages toward zero. Not a data-quality bug.
- **1-day column is not a literal one-day pooled mean** and is unverified (see Column meanings); prefer 7/30-day.
- **Rolling ~3-month retention, no long history.** Observed range 2026-04-15 → 2026-07-28 (105 distinct dated partitions on 2026-07-29); the retention floor has stayed fixed at 2026-04-15 while the window accumulates forward, so it is not a fixed 96-day window. Enforced upstream by the SQLMesh model (there is **no BQ partition-expiration TTL** on the physical table — `ttl_days: null`). For long pre-periods (e.g. 52-week CausalImpact) this table will not reach back far enough.
- **Fresh through current day** — max(day) = 2026-07-28 on 2026-07-29 (computed a day in arrears), unlike `sum_by_campaign/advertiser_by_day` which have historically lagged.
- **Source `sales_cycle_time` is often NULL** (conversion not matched to a first page view); those rows are excluded from the average, which is why the shorter windows go NULL.

## Cost & partitioning notes
- Physical is a **real TABLE** (`sqlmesh__summarydata.summarydata__…__1181683363`), DAY-partitioned on `day`, **no clustering**, `require_partition_filter=false`. Tiny: 507,368 rows / **19,381,928 bytes (~18.5 MiB)** total backing storage (`bq show` numBytes, 2026-07-29; 105 dated partitions + 1 empty `__NULL__`).
- **Always filter `day`.** Labeled dry-run (same `SELECT *` column set): one day (`day = '2026-07-19'`) = **185,960 bytes**, ~100× less than the ~19 MB full-table scan. Even a full scan is cheap here, but keep the day filter as habit.
- Prefer selecting only the window column you need over `SELECT *` (5 columns, all narrow).

## Example queries
```sql
-- Latest sales-cycle length per advertiser, in days (stable 30-day window)
SELECT advertiser_id, ROUND(avg_sales_cycle_time_30_day / 86400, 2) AS cycle_days
FROM `summarydata.sales_cycle_averages_by_advertiser_id`
WHERE day = (SELECT MAX(day) FROM `summarydata.sales_cycle_averages_by_advertiser_id`)
  AND avg_sales_cycle_time_30_day IS NOT NULL
ORDER BY cycle_days DESC;
```
