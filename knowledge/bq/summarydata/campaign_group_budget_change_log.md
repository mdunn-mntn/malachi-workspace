# summarydata.campaign_group_budget_change_log

## Purpose
Audit trail of budget-related edits to campaign groups. Each row records a single change event: the campaign group and flight(s) affected, the budgeting mode ("Flighted" vs "Monthly"), the resulting budget amount, a change-reason code, the user who made it, and — for changes that have a directional before/after (amount edits, flight date shifts, mode switches) — the `prior_value`→`current_value` pair. Reach for it to answer "when/who/why did this campaign group's budget or flight schedule change," to build budget-change timelines, or to correlate delivery/pacing anomalies with manual budget edits. Not a current-state table — it is an append-only event log; the live budget lives on the `campaign_groups` / flight dims.

## Grain & keys
- **Grain:** one row per budget-change event on a campaign group — effectively unique on `(time, campaign_group_id, entity_id, change_id)` (243,760 distinct of 243,776 rows; 16 near-dups, ~0.007%).
- **Key(s) / join columns:** `campaign_group_id` (→ campaign_groups), `advertiser_id` (→ advertisers), `user_id` (→ users / who edited), `entity_id` (brace-wrapped flight-id array → flight dim). No single surrogate PK — `change_id` is a categorical reason code, NOT a row key.

## Column meanings (only the non-obvious ones)
- **`time`** — native TIMESTAMP of the change, stored in **UTC** (not an epoch int). Because business ops are US-local, the max value can sit "ahead" of the US-local clock (e.g. `2026-07-20 00:56 UTC` = `2026-07-19 17:56 PDT`). No partition is built on it (see Cost).
- **`change_id`** — a **change-reason CODE** (categorical 1–6), NOT a surrogate key. Verified domain and semantics:
  - `1` = **Monthly budget INCREASE** (8,054 rows; `prior_value`/`current_value` = dollar strings, current > prior for all).
  - `2` = **Monthly budget DECREASE** (7,599 rows; current < prior for all).
  - `3` = **Flighted budget set** (113,635 rows, largest bucket; `prior`/`current` NULL — resulting amount is in `entity_text_2`; typically the flight's initial/created budget).
  - `4` = **Flighted flight date change** (14,894 rows; `prior`/`current` are DATE-timestamp strings, e.g. `2026-07-31 23:59:59`→`2026-07-19 09:57:59` — a flight end/schedule shift).
  - `5` = **Flighted budget recalculated** (97,706 rows, 2nd largest; `prior`/`current` NULL — amount in `entity_text_2`; observed on edits / early-ends / reflights). *(3 vs 5 distinction inferred from event ordering — both are Flighted budget-set events with the amount carried in `entity_text_2`, not in prior/current.)*
  - `6` = **Pacing-mode switch** (1,888 rows; `prior`/`current` = mode labels, e.g. `Monthly`→`Flighted`).
- **`prior_value` / `current_value`** — before/after values whose **datatype depends on `change_id`**: dollar strings (1/2), NULL (3/5), date-timestamp strings (4), mode labels (6). Both are NULL together in ~87% of rows (all of change_id 3 & 5). Dollar values are formatted strings (`$7,257.26`) — parse with `SAFE_CAST(REPLACE(REPLACE(v,'$',''),',','') AS FLOAT64)`.
- **`entity_text`** — the campaign group's **budget mode** for this event: `Flighted` or `Monthly`. (Not the changed value.)
- **`entity_id`** — brace-wrapped Postgres **text array of flight_id(s)**, e.g. `{346486}` or `{346603,346604}`. ~4.3% (10,396 rows) contain multiple flights (commas). Extract numeric id(s) with `REGEXP_EXTRACT_ALL(entity_id, r'\d+')` or `TRIM(entity_id,'{}')` before joining.
- **`entity_text_2`** — the **budget AMOUNT** as a formatted dollar string (`$39,657.00`); never NULL. This is where the amount lives for change_id 3/5 (which leave prior/current NULL). Not numeric.
- **`entity_type`** — constant `flight_id_array` (1 distinct value); describes `entity_id`'s encoding. Pure label, not a variable.
- **`entity_type_2`** — constant `Budget Amount` (1 distinct value); label for `entity_text_2`.
- **`entity_id_2`** — **always NULL** (0/243,776 populated); the secondary-entity id slot is unused for this log.
- **`change_type`** — constant `Budget` (all rows); this log only carries budget-family changes.
- **`advertiser_id` / `campaign_group_id` / `user_id`** — INT64 FKs (advertiser owner, the campaign group, the editing user). 10,447 advertisers / 39,183 campaign groups / 6,842 users represented.

## Joins & relationships
- **`campaign_group_id` → campaign_groups dim** (integrationprod / silver.core) — partner grain **1 CG : N change rows**; this table → campaign_groups is **N:1 (safe, no fan-out)**. campaign_groups carries `product_id` (1=PTV/2=Select/3=QuickFrame). Reverse (campaign_groups → this log) fans out.
- **`advertiser_id` → advertisers.id** — N:1 safe; use `advertisers.company_name` for a label (the `advertiser_name` fields elsewhere are unreliable). One advertiser : many change rows.
- **`user_id` → users dim** — N:1 safe; who performed the edit. Many changes per user.
- **`entity_id` → flight dim (by flight_id)** — must strip braces / unnest first. A single row can list several flights (~4.3%); `UNNEST`-ing the extracted array fans a row **1:N** by flight, so aggregate carefully.

## Gotchas
- **`time` is UTC**, so it can read "in the future" versus a US-local now, and the flight `prior`/`current` timestamps (e.g. `23:59:59`) are UTC end-of-day markers — offset before comparing to local pacing windows.
- **`change_id` is a reason code, not a key** — do not treat it as an incrementing PK or count "distinct change_id" as a change count.
- **`prior_value`/`current_value` semantics vary by `change_id`** (dollars / NULL / dates / mode labels). Never parse them as one uniform type. For change_id 3 & 5 they are NULL by design — the amount is in `entity_text_2`.
- **Amounts and the flight list are strings**, not numbers/arrays — dollar values need `$`/`,` stripping; `entity_id` needs regex extraction and may hold multiple flights.
- **`entity_id_2`, `entity_type`, `entity_type_2`, `change_type` are constant/empty** (unused secondary slot + fixed labels) — carry no information to filter on.
- **Append-only event log, not current state** — the same campaign group appears many times; for the live budget/schedule join to the dims, don't reconstruct it from the latest row unless you confirm event completeness.
- **History floor = 2024-01-01** (SQLMesh model start), max ≈ now (UTC). No earlier history exists in this view.

## Cost & partitioning notes
- **Unpartitioned, unclustered physical table** (bq show: `timePartitioning: None`, `clustering: None`). Empirically confirmed: `SELECT * WHERE time >= '2026-07-01'` dry-runs to the **same** 28,002,520 bytes as unfiltered `SELECT *` — a `time` filter does **not** prune. There is no partition column to filter.
- **The only cost lever is column pruning** (avoid `SELECT *`). Dry-run figures:
  - `SELECT *` (all 14 columns), full table → **28,002,520 bytes (~0.026 GB)**.
  - one narrow column (`campaign_group_id`), full table → **1,950,208 bytes (~0.0019 GB)** — ~14x cheaper.
- Whole table is only ~28 MB / ~243,776 rows, so even a full scan is tier-1 cheap; select just the columns you need and let BigQuery cache handle repeats.
- `approx_logical_bytes` = 28,002,520 (bq show `numBytes`, single physical table — not a UNION view).

## Example queries
```sql
-- Budget-change timeline for one campaign group (all columns needed; small table)
SELECT time, change_id, entity_text AS mode, entity_text_2 AS amount, prior_value, current_value, user_id
FROM `summarydata.campaign_group_budget_change_log`
WHERE campaign_group_id = 118970
ORDER BY time;

-- Net budget edits (Monthly increases/decreases) with parsed dollar deltas
SELECT campaign_group_id, time,
       SAFE_CAST(REPLACE(REPLACE(current_value,'$',''),',','') AS FLOAT64)
       - SAFE_CAST(REPLACE(REPLACE(prior_value,'$',''),',','') AS FLOAT64) AS delta
FROM `summarydata.campaign_group_budget_change_log`
WHERE change_id IN (1, 2)          -- 1=increase, 2=decrease
ORDER BY time DESC
LIMIT 100;
```
