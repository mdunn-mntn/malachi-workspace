# summarydata.waypoints_sp_aggregation

## Purpose
Daily SQLMesh fact that computes MNTN's **Selective Performance (SP)** product metrics from Waypoint
events. Physical description string: *"Calculate Selective Performance (SP) using Waypoints."* Reach for
it when you need per-day, per-campaign SP delivery vs standard delivery: how many of an advertiser's
designated *optimizable event* fired, how many impressions/users/sessions were involved, and the spend
split between the SP companion campaign group and the standard campaign groups feeding it.

Selective Performance = an advertiser designates one optimizable site event (here **"Viewed
Recommendations Page"**); MNTN runs a dedicated **SP companion campaign group** that optimizes bidding
toward that event, alongside the advertiser's standard campaign groups. This table is the daily
aggregation of the per-event `waypoints__selective_performance` view — it collapses individual waypoint
events (ad_served_id / user_key / session_key grain) into daily counts and fractional-spend sums.

**Scope caveat (verified 2026-07-19):** this is a narrow pilot — a single advertiser (34114), a single
optimizable event, 4 campaign groups (1 SP + 3 standard), 60 days present. Do **not** read volumes as
platform-wide; treat every enum domain below as open and re-derive via `SELECT DISTINCT` as SP rolls out.

## Grain & keys
- **Grain:** **one row per `day` × `campaign_id`** (× the event-classification tuple `raw_event_name`,
  `event_name`, `event_type`, `optimizable_event_name`, `is_optimizable_event`, `from_verified_impression`).
  Verified: 477 rows = 477 distinct `(day, campaign_id)` = 477 distinct full-key tuples — so with today's
  single optimizable event, `(day, campaign_id)` is the effective unique key. When multiple optimizable
  events per advertiser exist, the event tuple becomes part of the grain.
- **Key / join columns:** `day`, `advertiser_id`, `campaign_id`, `campaign_group_id`,
  `sp_campaign_group_id`. Each advertiser has exactly one SP campaign group; standard campaign groups link
  to it via `sp_campaign_group_id`.

## Column meanings (only the non-obvious ones)
- **`day`** — DATE partition; the event/delivery day. Only a rolling ~60-day window is present
  (`2026-05-21` → today) even though the partition TTL is 90 days.
- **`campaign_group_id` vs `sp_campaign_group_id`** — `campaign_group_id` is the group the row's
  `campaign_id` belongs to. `sp_campaign_group_id` is the **linked SP companion campaign group**. Two row
  archetypes result (verified):
  - **SP-group row** — `campaign_group_id` = the SP group (e.g. `67999`), `sp_campaign_group_id` **NULL**.
    Carries the SP group's own delivery in the **base** measures; all `sp_*` measures = 0.
  - **Standard-group row** — `campaign_group_id` = a standard group (`78204`, `79558`, `127534`),
    `sp_campaign_group_id` = its SP group (`67999`). Carries SP-attributed metrics in the `sp_*` measures;
    `event_count` / `user_count` / `total_spend` = 0.
- **`raw_event_name`** — event name exactly as fired by the pixel ("Viewed Recommendations Page").
- **`event_name`** — normalized lowercase form of `raw_event_name` ("viewed recommendations page").
- **`event_type`** — waypoint event class. Only `"DLV"` (delivery) observed so far; domain is open.
- **`optimizable_event_name`** — display name of the SP-optimizable event this group targets (mirrors
  `raw_event_name` in the pilot).
- **`is_optimizable_event`** — TRUE when this event is the advertiser's designated SP optimizable event;
  every current row is TRUE.
- **`from_verified_impression`** — TRUE when the waypoint event is tied to a verified impression; every
  current row is TRUE.
- **Base ↔ `sp_` measure pairs** — each `sp_`-prefixed column is the Selective-Performance counterpart of
  its base column, and (except the two impression/session columns) the two are **mutually exclusive by
  row archetype**:
  - `event_count` / `selective_performance_event_count` — count of the waypoint event. Base populated only
    on SP-group rows; `selective_performance_event_count` populated only on standard-group rows (event
    volume credited to the SP group).
  - `ad_served_id_count` / `sp_ad_served_id_count` — distinct impressions (ad_served_id). `ad_served_id_count`
    populates on **both** archetypes; `sp_ad_served_id_count` only on standard rows. On a standard row
    `ad_served_id_count` is much smaller than `sp_ad_served_id_count` (e.g. 39 vs 339).
  - `user_count` / `sp_user_count` — distinct users. Base only on SP-group rows, `sp_` only on standard rows.
  - `session_count` — distinct sessions; single column, populated on **both** archetypes (no `sp_` twin).
  - `total_spend` / `sp_spend` — **BIGNUMERIC dollars with ~37-decimal fractional precision** =
    fractionally-attributed spend, NOT integer cents. `total_spend` on SP-group rows, `sp_spend` on
    standard rows. `ROUND(...,2)` for any reporting.

## Joins & relationships
- **Source (upstream):** this is the daily GROUP BY of **`summarydata.waypoints__selective_performance`**
  (per-event grain: `ad_served_id`, `user_key`, `session_key`, `guid`). `*_count` columns are
  `COUNT(DISTINCT ...)` of those keys; `total_spend`/`sp_spend` are sums of its spend columns. That view is
  itself a SQLMesh passthrough → resolve to its own physical if you need event-level detail. Joining this
  rollup back to the per-event view is **1:N** (one agg row → many raw events) — don't.
- **`campaign_id`** → `campaigns` dim (1:1 on campaign; a campaign group has **N** campaigns, so
  campaign_group → campaign is 1:N). `campaigns.funnel_level` is authoritative for stage, not objective_id.
- **`campaign_group_id` / `sp_campaign_group_id`** → `campaign_groups` dim. `sp_campaign_group_id` is a
  **self-referential** link inside `campaign_groups` (points at the SP companion group). Do not conflate SP
  with `campaign_groups.product_id=2` ("MNTN Select") — different concept.
- **`advertiser_id`** → advertisers dim (1:N advertiser → campaigns). Direct query of
  `bronze.integrationprod.advertisers` was access-denied under this catalog account (company_name
  unresolved here) — join via a permitted advertiser view if you need the name.

## Gotchas
- **Narrow pilot (verified 2026-07-19):** only advertiser **34114**, one optimizable event, and 4 campaign
  groups exist. Volumes are not representative of the platform.
- **`require_partition_filter = true`:** every query MUST filter `day` or it errors.
- **Base vs SP measures don't add:** `event_count` (SP-group rows only) and
  `selective_performance_event_count` (standard rows only) count different populations. Summing both, or
  summing `total_spend`+`sp_spend`, double-mixes the SP group with its feeder groups — decide which side
  you want and filter on `sp_campaign_group_id IS NULL` (SP group) vs `IS NOT NULL` (standard).
- **Rolling window ≠ TTL:** only ~60 days are materialized (`2026-05-21`→today) despite the 90-day
  partition expiration. Physical table was (re)materialized 2026-07-19; its `numRows`/`numBytes` reflect
  the whole current table (~477 rows / ~117 KB), not a stale 0.
- **Spend is fractional BIGNUMERIC** (~37 decimals) — never treat as cents; ROUND for display.
- **Open enum domains:** `event_type` shows only `"DLV"` today — re-derive with `SELECT DISTINCT` before
  relying on it.
- **VIEW → versioned physical:** the clean name is a passthrough to
  `sqlmesh__summarydata.summarydata__waypoints_sp_aggregation__<hash>`; the hash rotates on model rebuild.
  Always query `summarydata.waypoints_sp_aggregation`.

## Cost & partitioning notes
- Partition **`day`** (DAY granularity), cluster **(advertiser_id, campaign_group_id)**, TTL **90 days**,
  `require_partition_filter = true`. Always filter `day`. The whole table is tiny today.
- Dry-run byte estimates (each labeled by exact column set — only compare same-column-set figures):
  - `SELECT *` WHERE `day='2026-07-15'` (1 partition, all 20 cols): **2,016 bytes**.
  - `SELECT *` WHERE `day>='2026-05-21'` (all 60 partitions, 20 cols): **120,198 bytes** (= full backing
    storage, matches `bq show` numBytes).
  - `SELECT day, sp_spend` WHERE `day>='2026-05-21'` (2 narrow cols, 60 partitions): **19,080 bytes**.
- Clustering on `advertiser_id` gives no pruning benefit today (single advertiser); it will matter once SP
  expands to more advertisers.

## Example queries
```sql
-- SP companion group's own daily delivery (base measures)
SELECT day, campaign_group_id, SUM(event_count) AS sp_group_events,
       ROUND(SUM(total_spend), 2) AS sp_group_spend
FROM `summarydata.waypoints_sp_aggregation`
WHERE day BETWEEN '2026-07-01' AND '2026-07-15'
  AND sp_campaign_group_id IS NULL      -- SP-group rows only
GROUP BY day, campaign_group_id ORDER BY day;

-- SP-attributed event volume + spend from the standard feeder groups
SELECT day, campaign_group_id, sp_campaign_group_id,
       SUM(selective_performance_event_count) AS sp_events,
       ROUND(SUM(sp_spend), 2) AS sp_spend
FROM `summarydata.waypoints_sp_aggregation`
WHERE day BETWEEN '2026-07-01' AND '2026-07-15'
  AND sp_campaign_group_id IS NOT NULL  -- standard-group rows only
GROUP BY day, campaign_group_id, sp_campaign_group_id ORDER BY day;
```
