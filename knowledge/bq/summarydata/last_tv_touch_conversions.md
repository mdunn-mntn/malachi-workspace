# summarydata.last_tv_touch_conversions

## Purpose
Row-level conversion events **attributed to the advertiser's LAST TV (CTV) touch**. Reach for it when you need per-conversion detail under the *last-TV-touch* attribution model specifically — the crediting TV impression (its id / IP / time / supply path), the conversion event, the dollar value, and the touch-to-conversion latency. It is one of several parallel attribution variants of the same underlying conversions (see the rollup note in `data_catalog.md` under `sum_by_campaign_by_day`): `last_tv_touch_*` credits the last **TV** touch, `last_touch_*` credits the overall/display last touch, `competing_*` is first-touch, `probattr_*` is probabilistic. These are **separate models, not additive buckets** — a single conversion can be credited to different campaigns by different models.

Data is fresh (max `time` = current day) and goes back to **2023-10-01** (same floor as `cost_impression_log`) — unlike the staleness-prone daily rollups, so this is a viable source for row-level TV-attributed conversion history.

## Grain & keys
- **Grain:** one row per **last-TV-touch-attributed conversion event**. NOT a clean 1:1 on any single column.
- **`order_id` is advertiser-supplied and NOT unique** — it repeats across separate conversion events (a session can fire "Home Page", "Lead", "Purchase"), across attribution models, and across touches. On a single day (2026-07-10): 44,292 rows vs 37,561 distinct `order_id`; even a rich composite `(advertiser_id, order_id, attribution_model_id, ad_served_id)` leaves ~5.7% residual duplication (41,783 distinct, NULL-preserving; 933 rows have NULL `order_id`, so a raw `CONCAT` collapses them and misleadingly reports 41,130). **There is no verified primary key — dedup before COUNT/SUM.**
- **Practical keys:** `advertiser_id` + `campaign_id` / `group_id` (join to dims); `impression_id` / `impression_ip` (the crediting CTV impression, join back to `cost_impression_log`); `guid` (user/device); `order_id` (advertiser transaction/session label, non-unique).

## Column meanings (only the non-obvious ones)
**Three timestamps + three epochs — all epochs are MICROSECONDS (verified 2026-07-19):**
- `time` (partition) — the **attribution/write row timestamp**, i.e. when this attributed row was materialized. It trails `event_time` by a **highly variable** lag (median ~31.6 h, p10 ~1 min, p90 ~23 days, up to weeks on the sample day) — NOT a short processing lag — so the partition date is generally later than the conversion date (see the late-data gotcha). This is the DAY partition column. `epoch` = `UNIX_MICROS(time)` **exactly** (16-digit micros; `time` itself carries sub-second micros — only 239/44,292 land on a whole second).
- `event_time` / `event_epoch` — the actual **conversion event** time. `event_time` is mostly truncated to whole seconds (29,454/44,292); `event_epoch` carries the sub-second micros the timestamp drops (e.g. `event_epoch`=1783690482513558 while `event_time`=…482 sec). `event_epoch` is MICROSECONDS.
- `impression_time` / `impression_epoch` — the **crediting last-TV-touch impression** time. Like the event pair, `impression_time` is second-truncated (42,997/44,292 land on whole seconds) while `impression_epoch` carries the sub-second **ms** precision the timestamp drops — so `impression_epoch` ≠ `UNIX_MICROS(impression_time)` for ~97% of rows (equal for only 1,332/44,292; `impression_epoch` > `UNIX_MICROS(impression_time)` for 42,960). `impression_epoch` is MICROSECONDS stored at ms precision (all values end in `000`).
- `elapsed_time` (INTERVAL) = `time − event_time` (lag between the conversion event and the row write) — **wide, not minutes**: median ~31.6 h, p10 ~1 min, p90 ~561 h (~23 days) on the sample day; 52% of rows (23,063/44,292) exceed 1 day, only 38% within 1 hour. `impression_elapsed_time` (INTERVAL) = `time − impression_time` (recency of the TV touch relative to the row; hours–weeks). `recency_elapsed_time` (INTERVAL) is **almost always NULL** (1 of 44,292 on the sample day).

**Attribution / conversion columns:**
- `attribution_model_id` (INT) — attribution-model variant id; observed values {4,5,6,12,13,14,16,30}. Rarely splits an order (adding it barely raises distinct-order counts).
- `conversion_type` (STRING) — the **advertiser-defined pixel event label**, free text: business names ("Purchase", "Lead", "Home Page"), URLs, or numeric codes like `-101`. Advertiser-supplied, not a controlled vocabulary.
- `conversion_source_id` (INT) — conversion source id (observed {23, 41, 61, 328496}). `pa_model_id` (INT) — probabilistic-attribution model id, mostly NULL (observed 1002).
- `conversion_source_id` NOTE: appears once in schema; don't confuse the sibling `pa_model_id`.
- `order_id` (STRING) — advertiser transaction/session identifier; **non-unique** (see Grain). Format varies by advertiser pixel (UUIDs vs numeric ids).
- `order_amt` (NUMERIC) / `order_curr` (STRING) — conversion value and currency. **~41% of rows are `order_amt = 0`** (26,214/44,292 > 0 on the sample day) — the zero rows are non-revenue conversions (leads, page views). `order_curr` is mixed-case ("usd"/"USD"). Use `summarydata` `order_amt`, not a `_usd` variant.
- `click` vs `click_through` (BOOL) — click-through-vs-view-through flags; the CTV rows sampled are `click=false, click_through=true` (view-through). `disputed` (BOOL) — dispute flag. `from_verified_impression` (BOOL) — nearly always TRUE (44,208/44,292); the credited impression was a verified impression.
- `is_cross_device` (BOOL) — conversion matched to the TV touch across devices.

**Impression / supply-path columns (describe the crediting TV impression, not the conversion):**
- `impression_id` (STRING) — id of the crediting last-TV-touch impression; nullable (86/44,292 NULL). Repeats — one impression can be last-touch for many conversions.
- `impression_ip` (STRING) — IP of the crediting impression (converted from the Postgres `inet` type → STRING). `ip` — the conversion-event IP.
- `ad_served_id` — the crediting (last-touch) ad-serve id; `first_touch_ad_served_id` — the first-touch ad-serve id for the same path.
- `channel_id` (INT) — 8 = CTV, 1 = display, and **can be NULL** (26/44,292 on the sample day, ~0.06%). **~98% CTV** (43,343 ch8, 923 ch1, 26 NULL on the sample day), consistent with attribution to a TV touch; the small display share carries impression ids too. `{8,1}` is not exhaustive — a `channel_id = 8` TV-only filter silently drops the NULL rows.
- `exchange_id`, `section_id`, `supply_vendor`, `private_marketplace_id`, `domain`, `subdomain` — supply-path of the crediting impression.
- `device_type` (STRING) — silver STRING encoding (bronze is INT); mostly non-NULL.
- `group_id` = campaign **group** id (join to `campaign_groups` for product_id 1=PTV/2=Select/3=QuickFrame); `campaign_id` = line/campaign; `creative_id`; `advertiser_id`.
- `query` (STRING) — referrer/query context field, typically empty.

## Joins & relationships
- `advertiser_id` → `bronze.integrationprod.advertisers.advertiser_id` — dim is **1 row/advertiser**; join facts→dim is **N:1 (safe)**. Filter `deleted=FALSE AND is_test=FALSE`. Use `company_name` for the label (`fpa_advertiser_verticals.advertiser_name` is unreliable/empty).
- `campaign_id` → `bronze.integrationprod.campaigns.campaign_id` — **PK is `campaign_id`, NOT `id`; there is no `silver.core.campaigns`**. **N:1 (safe)**. Join for `objective_id` / `funnel_level` (use `funnel_level` for stage; `objective_id`=4 marks TV-retargeting). `group_id` → `campaign_groups`, `creative_id` → `creatives` — both **N:1 (safe)**.
- `impression_id` / `impression_ip` → `silver.logdata.cost_impression_log` (the crediting CTV impression; same 2023-10-01 floor). **1:N the other way — one impression can credit many conversions**, so joining impressions→this table fans out. `impression_ip` is a STRING IP (no BQ IP→IP bridging).
- **Sibling attribution variants** — `summarydata.last_touch_conversions` (overall/display last touch), `summarydata.last_tv_touch_visits` (TV-touch site visits). **Do NOT `UNION`/sum `last_touch + last_tv_touch`** — a conversion exposed to both a display and a TV touch is credited by each model → **double count** (documented in `data_catalog.md`: the lt+tv sum overshoots the UI 22.1× ROAS to 23.5× by coincidence). The client-UI headline uses `last_touch (default) + competing_*`, and `last_tv_touch` is **never** in that headline.

## Gotchas
- **`order_id` is not a primary key** — advertiser-supplied, repeats across conversion events, models, and touches; also NULL on ~2% of rows (933/44,292). ~5.7% residual row duplication even on a rich composite (NULL-preserving distinct). **Dedup before COUNT(DISTINCT order_id) / SUM(order_amt)** or you over-count conversions and revenue.
- **These are one of several parallel attribution models** — never add `last_tv_touch_*` to `last_touch_*`/`default`/`competing_*`; they re-credit the same conversions (double count). See the `sum_by_campaign_by_day` note in `data_catalog.md`.
- **Partition `time` ≠ conversion date (late data).** `time` (the partition/write timestamp) trails `event_time` by a highly variable lag — median ~31.6 h, p90 ~23 days on the sample day, 52% of rows > 1 day. Filtering the `time` partition for a date range does **not** return the conversions whose *events* fell in that range; a "daily conversions" series built by partitioning on `time` is shifted/smeared vs actual conversion dates. Partition on `time` for cost, but bucket by `event_time` (or `event_epoch`) when you need conversions by their true date — and widen the `time` lookback to capture late-attributed events.
- **Three timestamps, don't mix them.** `time` (partition) ≠ `event_time` (conversion) ≠ `impression_time` (TV touch). Filter/partition on `time`; report the conversion at `event_time`; measure touch recency with `impression_elapsed_time`.
- **All `*_epoch` columns are MICROSECONDS** (not ms/ns). `event_time` is second-truncated — use `event_epoch` for sub-second precision.
- **`order_amt = 0` for ~41% of rows** — non-revenue conversions (leads/pageviews). Filter `order_amt > 0` for revenue-only analysis.
- **`recency_elapsed_time` is effectively always NULL** — don't build on it; use `impression_elapsed_time`.
- **~98% CTV, ~2% display, ~0.06% NULL** — `channel_id` can be NULL (26/44,292), so `{8,1}` is not exhaustive; a `channel_id = 8` TV-only filter drops the NULL rows. Don't assume the table is 100% CTV.
- **Physical hash drift:** `data_catalog.md` records physical `…__1806020579`; the live view now resolves to `…__3221502556` (normal SQLMesh rehash — query the clean view name, never the hash).
- **`require_partition_filter` is NOT enforced** (`None`) — the partition filter is not mandatory, so it's on the query author to always add it or pay a full-column scan.

## Cost & partitioning notes
**The one filter to always apply:** `WHERE time >= 'YYYY-MM-DD' AND time < 'YYYY-MM-DD'` (partition = `time`, DAY). No clustering. No TTL (full history 2023-10-01 → current day). `require_partition_filter` is **not** enforced, so an unfiltered query silently full-scans.

Physical: `TABLE` (not a passthrough view) `sqlmesh__summarydata.summarydata__last_tv_touch_conversions__3221502556` — numRows **58,214,376**, numBytes **114,310,194,820** (~114.3 GB logical, `bq show`, single physical table).

Dry-run byte estimates (2026-07-19), **labeled by column set** (only same-column-set figures are comparable):

|---|---|---|---|

## Example queries
```sql
-- Revenue attributed to the last TV (CTV) touch, one advertiser, one month — deduped
SELECT advertiser_id,
       COUNT(DISTINCT order_id)              AS conversions,   -- order_id is non-unique: DISTINCT
       SUM(order_amt)                         AS attributed_rev -- caveat: dedup dups first for exactness
FROM `summarydata.last_tv_touch_conversions`
WHERE time >= '2026-07-01' AND time < '2026-08-01'   -- partition filter, always
  AND advertiser_id = <AID>
  AND order_amt > 0                                    -- revenue-only; drop for lead/pageview counts
GROUP BY advertiser_id;
```
