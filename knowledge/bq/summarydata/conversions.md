# summarydata.conversions

## Purpose
Row-level conversion (pixel-fire) events, each already **attribution-credited to the verified impression that earned it**. This is the granular source behind conversion/revenue/ROAS reporting — reach for it when you need per-conversion detail (order value, conversion type, timing chain, geo, the matched impression) rather than the pre-aggregated `summarydata.conversion_facts` / `sum_by_*` rollups (use those for reporting; they are cheaper). `order_amt` is the revenue column. Full history is retained back to 2022-01-01 (see Gotchas — the older "60-day retention" note is stale).

## Grain & keys
- **Grain:** **one row per attributed conversion credit**, NOT strictly one row per conversion event. Multi-touch attribution credits a single underlying conversion to multiple impressions/advertisers/models, so one `order_id` can appear on several rows (empirically on 2026-07-15: 87,640 rows but only 67,964 distinct `order_id` + 3,341 NULL `order_id`; even `advertiser_id|order_id|ad_served_id` = 82,059 distinct < 87,640). This is the same MTA mechanism that makes per-advertiser CVR exceed 100% (see data_knowledge.md).
- **Key(s) / join columns:** no single unique key. `order_id` is advertiser-supplied (from the pixel `shoid` param) and unreliable — it can be a transaction id, a base64 hash, a page slug, a constant (e.g. WGU `lead`), or NULL. Attribution identity is `advertiser_id` + the matched impression (`ad_served_id` / `impression_id`). Coarse dedup/join to visits uses `guid + advertiser_id`.

## Column meanings (only the non-obvious ones)
- **`time`** — conversion time; the **DAY partition key**. Never NULL (the `__NULL__` partition holds 0 rows).
- **`epoch`** — `time` as **UNIX_MICROS** (microseconds). Verified: `epoch = UNIX_MICROS(time)` exactly.
- **`event_time` / `event_epoch`** — the pixel-fire event. `event_epoch` = **UNIX_MICROS** (microseconds). `event_time` is stored at coarser (second) precision so it can lag `event_epoch` by sub-second; trust `event_epoch` for exact timing. Populated for ~99.99% of rows (rare conversion sources leave it NULL).
- **`impression_time` / `impression_epoch` / `impression_ip` / `impression_id` / `ad_served_id`** — attributes of the **matched verified impression** that earned the credit. `impression_epoch` = **UNIX_MICROS** (values carry ms precision -> trailing `000`). Populated on ~99.2% of rows (the verified rows). Two directions hold exactly on the sampled day (2026-07-15): every `from_verified_impression = TRUE` row has these populated (0 verified-but-null), and every NULL `impression_time` row is non-verified — so **a NULL `impression_time` reliably means "no verified impression matched," not missing data.** The reverse is *not* strict, though: **~25 rows/day (~0.03%) have `from_verified_impression = FALSE` yet a populated `impression_*`** (687 NULL vs 712 fvi=FALSE), so don't use `impression_time IS NOT NULL` as an exact proxy for `from_verified_impression = TRUE` — filter on the flag itself.
- **`order_amt`** (NUMERIC) — the **revenue / order value column**. **There is NO `order_amt_usd` column in this table** (that NULL-column caveat belongs to `ui_conversions`). When the advertiser's pixel passes no dollar value, `order_amt` is **`0`, not NULL** (0 NULLs observed on a full day; ~40% of rows are `0` for lead-gen/education advertisers). Upstream the value is digit-extracted from the pixel `shoamt` string with no validation, so garbage-with-digits can become plausible-looking revenue (WGU pentest, Feb 2026).
- **`order_curr`** — currency, but a **dirty free-text field**: on 2026-07-15 it held `USD` (62,984), `usd` (23,360), the literal `N/A` (1,278), and `''` empty-string (18). `UPPER()` collapses the `USD`/`usd` case split but **leaves `N/A` and `''` as spurious non-currency buckets** — coalesce/filter those out too (e.g. `NULLIF(UPPER(order_curr) IN ('N/A','') → drop`) before treating it as a currency dimension.
- **`conversion_type`** — advertiser-defined type string, BUT platform **sentinels** appear here: numeric pseudo-types `-100/-101/-102/-105/-106/-107` (e.g. `-101` = untyped) and the literal string `<NIL>`. To keep only genuine types filter `NOT REGEXP_CONTAINS(conversion_type, r'^-[0-9]+$') AND conversion_type != '<NIL>'`.
- **`click` vs `click_through`** — `click` (sparse, ~0.4%) = the conversion was on an ad click. `click_through` is observed **constant TRUE** across a full day (100%) so it is not a useful click-vs-view discriminator — use `click` for that.
- **`from_verified_impression`** (BOOL) — TRUE = credited via MNTN's verified-impression attribution (what the UI reports). Filter `= TRUE` to match UI conversions.
- **`conversion_assist`** (BOOL, ~10%) — assist (non-final-touch) credit. **`disputed`** — observed all FALSE.
- **`elapsed_time` / `impression_elapsed_time` / `recency_elapsed_time`** — native **INTERVAL** durations along the attribution chain (impression -> event -> conversion), not epochs/numbers; do not treat as counts.
- **`attribution_model_id` / `pa_model_id` / `conversion_source_id`** — attribution-model & conversion-source identifiers. (There is **no `attribution_model_type_id` column** in this table — the 45-col live schema has only `attribution_model_id` and `pa_model_id`; don't reference a `_type_id`.) `conversion_source_id` -> `integrationprod.data_sources`.
- **`channel_id`** (INT64) — delivery channel of the credited impression: **8 = CTV, 1 = display** (2026-07-15: 8 -> 59,830, 1 -> 25,124, plus ~2,686 NULL). This is the load-bearing knob for any CTV-vs-display conversion split (workspace-wide `channel_id` gotcha).
- **`query`** (STRING) — the pixel query-string param captured at fire time. **Live type is STRING, not JSON** — the stale `data_catalog.md` entry types it `JSON`, which is wrong; treat it as an opaque string.

## Joins & relationships
- **-> `summarydata.visits`** on **`guid + advertiser_id`** (data_knowledge Join Keys). Partner grain = one row per visit; **`guid` persists across many visits**, so this is **N:M / high fan-out** — a conversion can multiply against every visit sharing that guid+advertiser. Prefer the impression-level match (`ad_served_id` / `impression_id`) when you need a 1:1 anchor.
- **-> `logdata.impression_log` / `logdata.cost_impression_log`** on **`ad_served_id`** (or `impression_id`) = the verified impression. Partner grain = one row per impression; ~1:1 when `from_verified_impression = TRUE`, low fan-out.
- **-> `integrationprod.data_sources`** on **`conversion_source_id`** — dim lookup, **1:1**, no fan-out.
- **-> `integrationprod.campaigns`** on `campaign_id`, **-> `campaign_groups`** on `group_id`, **-> `advertisers`** on `advertiser_id`, **-> `core_creatives`** on `creative_id` — dim lookups, 1:1 (filter dims `deleted=FALSE AND is_test=FALSE`).
- **Fan-out warning:** because one conversion can occupy multiple rows (MTA), any `SUM(order_amt)` / `COUNT(*)` at advertiser grain already reflects multi-touch crediting — that is intended for ROAS but will double-count if you also join to another 1:N table. De-dup to `from_verified_impression = TRUE` and/or a single attribution model first.

## Gotchas
- **STALE PROSE — retention is NOT 60 days.** data_catalog.md ("60-day TTL") and data_knowledge.md ("conversions | 60 days") are wrong for this physical table. INFORMATION_SCHEMA.PARTITIONS shows **1,661 populated daily partitions from 2022-01-01 (25,306 rows) through today** (the `__NULL__` partition also appears but holds 0 rows, so the raw partition-row count of 1,662 overstates it by one), ~130.7M rows total, and the physical table has **no partition expiration** (`requirePartitionFilter` unset, no `expirationMs`). Treat retention as **full history back to 2022-01-01**, TTL = none.
- **Grain is per-credit, not per-conversion** — `order_id` is not unique (MTA + advertiser-supplied). Don't `COUNT(DISTINCT order_id)` expecting a clean conversion count; scope to one attribution model / `from_verified_impression = TRUE` first.
- **`order_amt = 0` != no conversion** and **!= NULL** — 0 is the zero-value fill for value-less (lead-gen) conversions. Filter `order_amt > 0` before any revenue/ROAS readout, and expect whole verticals (education, lead-gen, services) to report `0`.
- **Revenue can be poisoned by unvalidated pixel input** — digit-extracted `shoamt` means SQLi/pentest/garbage strings can inject fake dollar amounts (WGU Feb 2026). Sanity-cap extreme `order_amt`.
- **`order_curr` is dirty free text** — beyond the `USD`/`usd` case split it also carries `N/A` and `''`; `UPPER()` alone won't give clean currency buckets (drop the non-currency values too).
- **`conversion_type` sentinels** — never treat `-101` (or the `-1xx` family / `<NIL>`) as a real conversion type.
- **`impression_*` NULLs are meaningful** — absent verified-impression match, not missing data.

## Cost & partitioning notes
- **Partition = `time` (DAY); no clustering; partition filter NOT required but ALWAYS apply `DATE(time)` / a `time` range** — the one filter to always add. Empirically confirmed: adding `DATE(time)` collapses the byte estimate ~1000x for a single day.
- Dry-run byte estimates (2026-07-19, labeled by exact column set — only same-column-set figures are comparable):
  - `SELECT order_amt`, **no filter (full table)** -> **2,091,903,856 B (~1.95 GiB)**
  - `SELECT order_amt`, **1 day** (`DATE(time)="2026-07-15"`) -> **2,103,360 B (~2.0 MiB)**  <- partition prune, ~1000x cheaper
  - `SELECT *`, **1 day** -> **197,770,408 B (~188.6 MiB)** — ~94x the single-column 1-day pull, so **avoid `SELECT *`**; project only needed columns.
- Storage (INFORMATION_SCHEMA.TABLE_STORAGE, 2026-07-19): **`total_logical_bytes` = 228,441,731,988 B (~212.75 GiB)** — this is what `approx_logical_bytes` tracks. The **physical/on-disk footprint is far smaller: `total_physical_bytes` = 46,934,023,378 B (~43.7 GiB)**, ~4.9x compressed. ~130.7M rows. (Neither figure is the query-scan cost — see the dry-run numbers above for that.)

## Example queries
```sql
-- UI-matching revenue for one advertiser, one day (partition-pruned, verified only, value>0)
SELECT advertiser_id,
       COUNT(*)          AS credited_conversions,
       SUM(order_amt)    AS revenue
FROM `summarydata.conversions`
WHERE DATE(time) = '2026-07-15'
  AND advertiser_id = <AID>
  AND from_verified_impression = TRUE
  AND order_amt > 0
GROUP BY advertiser_id;
```
