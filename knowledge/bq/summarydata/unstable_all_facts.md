# summarydata.unstable_all_facts

## Purpose
**NON-CANONICAL staging / experimental table — do not use for reporting.** The `unstable_` prefix marks
a SQLMesh staging/experimental copy in the `all_facts` family; the stable, authoritative sibling is
**`summarydata.all_facts`** (and its export view `summarydata.v_all_facts` → ClickHouse/CHAPI, which
drives `graph.usersreached`/`graph.sitevisitors` and the exact BQ↔UI ROAS/visit reproduction). For any
spend / impression / visit / conversion / reach reporting, reach for `all_facts`, **not** this table.

What this table actually holds (verified 2026-07-19): a **recent ~4-month rolling window** of
**conversion / pixel-attribution restatements**. It is NOT a full copy of `all_facts` — on 2026-07-10 it
had **4.17M rows vs `all_facts`'s 55.69M** (7.5%) and **$35.9K media_spend vs $513.4K** (7%). Every row
carries a **`change_id`** (a column `all_facts` does **not** have), plus `conversion_source_id` +
`conversion_type` + `pa_model_id` all NOT NULL — i.e. this is the subset of facts broken out by
conversion source / pixel event and tagged with a change/reprocessing batch id. Best read as the
attribution-restatement staging feed for entities whose conversions/pixels were (re)processed under a
given `change_id`; the settled, merged result lands in `all_facts`. (Inference from the schema +
one-day profile — there is **no prose oracle** for this table; treat the exact SQLMesh model role as
unverified.) When in doubt, use `all_facts`.

## Grain & keys
- **Grain:** one row per the **all_facts 18-column grain (hour + 17 dims: advertiser_id,
  campaign_group_id, campaign_id, channel_id, objective_id, group_id, creative_id,
  private_marketplace_id, country, metro_id, region, city, postal_code, domain, supply_vendor,
  device_type)** — note this schema **drops** `all_facts`'s `pa_model` grain slot into a populated
  measure column — **× `change_id` × `conversion_source_id` × `conversion_type`**. Unlike `all_facts`
  (where `conversion_source_id`/`conversion_type` are NULL on ~99.7% of rows), here **100% of rows** have
  `change_id`, `conversion_source_id`, `conversion_type`, and `pa_model_id` NOT NULL (one day, 4.17M rows).
- **Key / join columns:** FK dims are the same as `all_facts` — `advertiser_id`, `campaign_id`,
  `campaign_group_id`, `channel_id`, `objective_id`, `creative_id`. **No `ip`/`guid` scalar** — identity
  lives only in the HLL `BYTES` sketches (`uniques`, `site_visitors`, …) and the `*_arr` ID arrays.
- **Schema drift vs `all_facts` (why this is a distinct model, not a mirror):** this table **adds
  `change_id`** and **omits** `all_facts`'s `legacy_spend`, `raw_visits`, `raw_conversions`,
  `raw_order_value`, `new_to_file`, `first_touch_visits`, `visitors`(+`_arr`),
  `raw_new/existing_site_visitors`(+`_arr`), `last_touch_*_site_visitors_arr`, and `users_reached_ip_arr`.
  So it is a leaner, change-tracked column set — consistent with an experimental/staging model.

## Column meanings (only the non-obvious ones)
Columns shared with `all_facts` keep the same meaning — see `knowledge/bq/summarydata/all_facts.md` for
the full set. This table's **distinctive** columns:
- **`change_id`** (INT64, **always populated here**; absent from `all_facts`) — an integer change /
  reprocessing batch id. Rolling, roughly monotonic sequence: values ~61,442–66,630 over the current
  window, **~830–980 distinct per day**, with the low bound (~61,442) roughly **stable across days** —
  i.e. `change_id` is a **global** sequence and the table retains a rolling window of ids, not a per-day
  counter. Best understood as the identifier of the conversion/pixel change or restatement batch that
  produced the row (SQLMesh model role unverified — no prose oracle).
- **`conversion_source_id`** (INT64, **always NOT NULL here**, 3 distinct/day) — the conversion/pixel
  source. Heavily skewed: one dominant source ≈ **99.86%** of rows on 2026-07-10, then id `23` (~5.6K rows)
  and id `61` (~129 rows). In `all_facts` this column is the conversion/site-leg discriminator (NULL
  elsewhere); **here it is NOT a discriminator** — it is a mandatory grain dim.
- **`conversion_type`** (STRING, always NOT NULL here, **50 distinct/day**) — the **advertiser pixel-event
  name**, not a fixed enum: e.g. `OwnerRentedProperty`, `RenterBooking`, `quoteStarted`,
  `MembershipPurchase`, `Engagement`, `Labor`, `Junk`. Advertiser-defined labels, so the domain is open
  and per-advertiser.
- **`pa_model_id`** (INT64) — probabilistic-attribution model id; **NOT NULL on 100% of rows here**
  (contrast `all_facts`, where it is NULL on many rows across both legs and is explicitly *not* a leg
  discriminator).
- **Measures are genuinely populated, not conversion-only:** on 2026-07-10, **97%** of rows had
  `media_spend > 0`, **27%** had `display_impressions > 0`, but only **~0.09%** had a non-zero
  `view/click_conversions`. So despite the conversion grain, this carries full spend/impression facts —
  it is a fact restatement broken out by conversion source/pixel, not a pure conversion table.
- **`hour`** — DATETIME (tz-naive), truncated to the hour; the DAY **partition column** (same as
  `all_facts`; timezone not independently confirmed). Not epoch-encoded.
- **Spend/HLL/`competing_*`/`*_arr` columns** — same semantics as `all_facts`: spend (`media_spend`,
  `data_spend`, `platform_spend`, `ctv_spend`, `unlinked_spend`, `media_cost`) is **whole USD, do not
  ÷1e6**; reach/unique columns (`uniques`, `site_visitors`, …) are **`BYTES` HLL++ sketches** →
  `HLL_COUNT.MERGE(col)`, never `SUM()`; `*_arr` are the raw-ID array twins; `competing_*` is the
  industry_standard competitive-scenario credit (a misnomer for "first-touch").

## Joins & relationships
- **Canonical sibling:** `summarydata.all_facts` — the stable, reporting-authoritative version.
  `unstable_all_facts` is **not** its physical source and **not** a 1:1 mirror (different, leaner column
  set + `change_id`; ~7% of the daily rows/spend). Do not substitute one for the other in a query.
- **Base fact tables (same family as `all_facts`):** `summarydata.impression_facts`, `visit_facts`,
  `spend_facts`, `conversion_facts`, `site_facts` — all hour-partitioned summarydata facts. For a single
  metric, query one of those (narrower/cheaper).
- **Dimension joins (all 1:1, safe — no fan-out; filter `deleted=FALSE AND is_test=FALSE`):**
  `advertiser_id` → `integrationprod.advertisers` (use `company_name`); `campaign_id` → `campaigns`
  (use `funnel_level` for stage, not `objective_id`); `campaign_group_id` → `campaign_groups`
  (`product_id` 1=PTV/2=Select/3=QuickFrame); `creative_id`/`group_id`/`metro_id`/`pa_model_id` → their
  dims. `channel_id` 8=CTV / 1=display; prospecting scope = `objective_id IN (1,5,6)`.
- **`change_id` has no confirmed partner table here** — likely joins a conversion/pixel change-log
  upstream, but the partner and its grain are **unverified** (no prose oracle; not resolvable in this
  pass). Do not assume a join target.
- **Fan-out warnings:** (1) No `ip`/`guid` scalar — never join to raw event/log tables on identity.
  (2) Because this table is **already exploded by `conversion_source_id` × `conversion_type` × `change_id`**,
  a naive join to `all_facts` or a base fact on the shared 18 dims will **multiply** rows (many
  conversion/pixel rows per dim-tuple) — aggregate first, and do not treat the 18-dim tuple as unique here.

## Gotchas
- **NON-CANONICAL — never report from this table.** The `unstable_` prefix = SQLMesh staging/experimental.
  Any spend/visit/ROAS/reach number pulled from here will disagree with the client UI and with
  `all_facts` (7% of the volume on a sample day). Use `all_facts` / `v_all_facts`.
- **Rolling ~4-month window — not full history.** Partitions span only **2026-03-22 → 2026-07-20** (121
  daily partitions); older data is dropped by the model (no BQ partition/table TTL is set — the retention
  is model-enforced). Do NOT use this table for anything before ~2026-03-22; `all_facts` covers 2020→now.
- **`conversion_source_id`/`conversion_type` are NOT NULL here and are grain dims** — the exact opposite
  of `all_facts`, where they are the conversion/site-leg discriminator (mostly NULL). Do not port a
  discriminator pattern between the two tables.
- **`conversion_type` is an open, advertiser-defined string domain** (pixel-event names), not an enum —
  a `SELECT DISTINCT` on one day (~50 values) does not enumerate all advertisers/events.
- **`hour` is a tz-naive DATETIME** — timezone not independently confirmed (same caveat as `all_facts`).
- **Spend is whole USD (no ÷1e6); HLL columns are `BYTES`** (`SUM()` throws "cannot coerce BYTES" — use
  `HLL_COUNT.MERGE`). Same as `all_facts`.
- **Owner = Backend Reporting (`ber`)** by family convention (same as `all_facts`); route model-role /
  definition questions there. The precise SQLMesh model behind `unstable_all_facts` was not read in this
  pass — its exact semantics are inferred from schema + a one-day profile.

## Cost & partitioning notes
- **Partition:** DAY on **`hour`** (DATETIME). **Clustering:** `advertiser_id`, `campaign_id`.
  `require_partition_filter` is **NOT enforced** — but ALWAYS filter `hour`; a missing filter full-scans.
  The physical is a real materialized TABLE (numRows 464,567,098; not a stale SQLMesh 0-row placeholder).
- **The one filter to always apply:** an `hour` range. Confirmed empirically (dry-run, `SUM(media_spend)`
  = one BIGNUMERIC column): **no filter = 14,866,147,136 B ≈ 14.87 GB / 13.85 GiB** vs **one day
  `hour ∈ [2026-07-10, 2026-07-11) = 166,983,320 B ≈ 0.167 GB / 159 MiB`** — the `hour` filter prunes
  **~89×**. Add an `advertiser_id` predicate to also exploit clustering.
- **Never `SELECT *`** — ~150 columns, many wide `ARRAY<STRING>` / `BYTES`. Same-column-set actuals (all
  one-day, `hour ∈ [2026-07-10, 2026-07-11)`): a 9-scalar-column profile (`change_id`,
  `conversion_source_id`, `pa_model_id`, `media_spend`, `display_impressions`, `ctv_impressions`) billed
  **0.312 GB**; a `conversion_source_id` + `pa_model_id` + `conversion_type` group-by billed **0.109 GB**;
  a grain probe with a 7-column `FORMAT("%T", (...))` tuple billed **0.451 GB**. Scan the fewest columns
  you need.
- **Physical size:** 464,567,098 rows, numBytes 450,791,639,343 (~450.8 GB / 419.8 GiB backing storage),
  **121 daily partitions** spanning **2026-03-22 → 2026-07-20** (a rolling ~4-month window; no NULL
  partition). Far smaller than `all_facts` (107.1B rows / ~76.2 TB / 2,111 partitions since 2020).

## Example queries
```sql
-- Always filter hour. This is a STAGING table — for real reporting use summarydata.all_facts instead.
SELECT CAST(hour AS DATE) AS day,
       COUNT(*)                        AS rows,
       COUNT(DISTINCT change_id)       AS change_batches,
       SUM(media_spend + data_spend + platform_spend) AS spend_usd
FROM `dw-main-silver.summarydata.unstable_all_facts`
WHERE hour >= '2026-07-14' AND hour < '2026-07-20'
GROUP BY 1 ORDER BY 1;

-- Restatement rows for one advertiser, broken out by conversion source/pixel (exploits clustering)
SELECT conversion_source_id, conversion_type, COUNT(*) AS rows, SUM(media_spend) AS spend_usd
FROM `dw-main-silver.summarydata.unstable_all_facts`
WHERE hour >= '2026-07-10' AND hour < '2026-07-11'
  AND advertiser_id = 31921
GROUP BY 1, 2 ORDER BY rows DESC;
```
