# summarydata.tvo_prospecting_campaign_groups

## Purpose
A small, fully-derived **config/routing VIEW** that enumerates the set of **Prospecting, PTV campaign groups that qualify as "TVO."** The SQLMesh physical carries the description: *"Prospecting campaign groups that are TVO — used to disable ltvt for these campaign groups."*

Its only real consumer is **`summarydata.ui_visits`**, which LEFT JOINs this list on `campaign_group_id` to branch attribution: a prospecting group that appears here gets **standard `visits` (retargeting-style, credited to the impression)** attribution; a prospecting group NOT here falls through to **`last_tv_touch_visits` (ltvt / last-TV-touch)** attribution. So this table is the switch that decides "which prospecting groups skip last-TV-touch."

Reach for it to answer: *which prospecting groups are running in TVO mode / get standard-visit attribution instead of TV-last-touch.* It is a **membership flag list, not a fact table** — no measures, no time series.

## Grain & keys
- **Grain:** one row per qualifying **`campaign_group_id`**. Verified unique: 41,954 rows = 41,954 distinct `campaign_group_id` (across 11,899 advertisers), because the view `GROUP BY advertiser_id, campaign_group_id` collapses the fan-out from its two internal `campaigns` self-joins.
- **Key / join column:** `campaign_group_id` (the unique key; join target for consumers). `advertiser_id` is a carried attribute (the group's owner), not part of the grain.

## Column meanings (only the non-obvious ones)
- **`campaign_group_id`** — the qualifying group; the unique key. This is what downstream code joins on.
- **`advertiser_id`** — the group's owner (`campaign_groups.advertiser_id`). Carried for convenience; **not** the grain (one advertiser can own many qualifying groups).
- **`start_dt`** — **NOT an event date and NOT a partition column.** It is a hardcoded constant literal baked into the view SQL — `DATE('2026-03-17')` — so **every row has the identical value `2026-03-17`** (verified: `COUNT(DISTINCT start_dt)=1`). It marks when the TVO-routing logic was cut in, not any per-group timestamp. Never filter or range-scan it as if it were real data.

### Membership rule (the view's WHERE — what makes a group "TVO")
A group qualifies iff **all** of the following hold (derived from `public.campaign_groups vcg` + two self-joins of `public.campaigns`):
- `campaign_groups.objective_id = 1` → **Prospecting** (per the objective taxonomy: Prospecting = obj IN (1,5,6); 1 is the base Prospecting objective).
- `campaign_groups.product_id = 1` → **PTV** (product_id 1=PTV / 2=Select / 3=QuickFrame).
- The group contains **both** of these campaigns, and **both** must be `campaign_status_id = 7`:
  - a `campaign_template_id = 15` campaign — template name **"Multi-Touch"** (channel_id=1, display), AND
  - a `campaign_template_id = 23` campaign — template name **"Multi-Touch - Plus"** (channel_id=1, display).
- **`campaign_status_id = 7` = "Inactive" (ended/off)** per `integrationprod.core_campaign_statuses` — NOT Live (=3). This is counterintuitive but it is the TVO signature: a pair of *Inactive* Multi-Touch / Multi-Touch-Plus legs. Do not "correct" it to Live.

## Joins & relationships
- **`summarydata.ui_visits` (downstream consumer, the important one):** `ui_visits` **LEFT JOINs** this view on `campaign_group_id` to branch its attribution (TVO prospecting groups → `'visits'` branch; other prospecting → `'last_tv_touch_visits'` branch). **1:1 on `campaign_group_id`** (this side is unique) → **no fan-out**; it acts as a presence/flag lookup. This is an internal wiring join, not a user-facing one.
- **`public.campaign_groups` (1 row per group):** join on `campaign_group_id`. 1:1 from this table's side (unique key) → no fan-out. Use it to pull group name/flight/budget for a qualifying group.
- **`public.campaigns` (N rows per group):** the view self-joins it twice internally (once for the template-15 leg, once for template-23). That internal join **fans out** (a group can have many campaigns), but the view's `GROUP BY` collapses it back to one row per group. If you re-derive membership yourself, you must dedupe the same way (`GROUP BY campaign_group_id` or `EXISTS` per leg).
- **`advertisers` / `public.campaign_groups` on `advertiser_id`:** 1:N from this table (an advertiser owns many groups); safe to enrich with `company_name` (1:1 the other direction).

## Gotchas
- **`start_dt` is a constant, not a date.** Same literal (`2026-03-17`) on every row. Do not partition-filter, range-scan, or trend on it. There is no real time dimension in this table.
- **Live view, recomputed on every query — not a snapshot.** Membership drifts as campaign statuses/templates change in `public.campaigns`. Two reads on different days can differ. There is no history table and no as-of snapshot; if you need point-in-time membership, materialize your own.
- **Status 7 = "Inactive" is required, not "Live."** The signature is a pair of *inactive* Multi-Touch legs; a group whose Multi-Touch campaigns are Live (3) will **not** appear.
- **Both legs required.** A group with only the "Multi-Touch" (15) leg or only the "Multi-Touch - Plus" (23) leg is excluded — the double self-join demands both.
- **View-over-views: `numRows=0`, `numBytes=0` on the SQLMesh physical** (`__1901231145`) because it has no backing storage of its own; it resolves live to `public.campaign_groups` + `public.campaigns` (themselves views over `bronze.integrationprod` raw). Don't read the 0s as "empty" — the live view returns ~42K rows.
- **Membership/flag list, not a fact table.** No measures, no impressions/spend/visits here — only which groups qualify.

## Cost & partitioning notes
- **No partition column and no clustering** — this is a fully-derived view, so there is nothing to prune; the cost floor is the scan of the underlying `public.campaigns` + `public.campaign_groups` dims. "Always filter the partition" does **not** apply here.
- **Dry-run figures (full view, no filter possible):** `SELECT *` (all 3 cols) = **26.66 MB** (26,664,704 B); `SELECT campaign_group_id` (one col) = **25.63 MB** (25,629,816 B). Nearly identical — column choice barely matters because the dim scan dominates. Cheap either way (~25 MB); real COUNT ran at 0.025 GB processed.
- **`approx_logical_bytes = null`** — a view-over-views owns no storage (`bq show numBytes = 0`); the backing bytes live in the `campaigns`/`campaign_groups` physicals and are not attributed here.
- **Guidance:** it's tiny, so just `SELECT *` when you need the list. The only real cost trap is joining it into a large fact scan expecting partition pruning — there is none; treat it as a small broadcast lookup on `campaign_group_id`.

## Example queries
```sql
-- The full TVO prospecting-group membership list (it's tiny; no filter needed)
SELECT advertiser_id, campaign_group_id
FROM `summarydata.tvo_prospecting_campaign_groups`;

-- Is a given prospecting group routed as TVO (standard visits) rather than last-TV-touch?
SELECT COUNT(*) > 0 AS is_tvo
FROM `summarydata.tvo_prospecting_campaign_groups`
WHERE campaign_group_id = @cg_id;

-- Enrich the membership list with group + advertiser names
SELECT t.campaign_group_id, cg.name AS group_name, a.company_name
FROM `summarydata.tvo_prospecting_campaign_groups` t
JOIN `public.campaign_groups` cg USING (campaign_group_id)
JOIN `public.advertisers`      a  ON a.advertiser_id = t.advertiser_id;
```
