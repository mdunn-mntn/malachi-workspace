# summarydata.campaign_group_status_change_log

## Purpose
Audit trail of every change to a campaign group's **status** (its lifecycle state — Ready / Live / Pause By Advertisers / Pause By MNTN / Deleted). Reach for it to answer "when did this campaign group go live, get paused, and who/what paused it, and when was it deleted" — e.g. to align a delivery gap or spend drop with a pause, distinguish an **advertiser-initiated** pause from an **MNTN-side** (platform/billing/policy) pause, or reconstruct a campaign group's up/down timeline for an incrementality or pacing analysis. It is a slice of a generic per-entity change-log source, pre-filtered to status changes on campaign groups (`change_type='Status'`, `change_id=50`). The physical table description confirms it: *"Activity timeline campaign group status changes (Postgres parity)."*

## Grain & keys
- **Grain:** one row per campaign-group status change **event** (a transition). 147,027 rows over 68,864 distinct campaign groups — 30,623 groups have exactly one status row (created → Ready and never touched again), the rest have 2–15+ successive transitions.
- **Key(s) / join columns:** `campaign_group_id` (the entity that changed), `advertiser_id` (owner, 16,008 distinct), `user_id` (who made the change). There is **no per-row surrogate key** — `change_id` is a constant type-code (=50, "Status"), not a row id. Identify a specific transition by `(campaign_group_id, time)`.

## Column meanings (only the non-obvious ones)
- **`time`** — when the status change was recorded. Native `TIMESTAMP` stored in **UTC** (max value = 2026-07-20 04:49 while Pacific "today" is 2026-07-19, i.e. ~a day ahead — confirms UTC, not local). De-facto event/sort key; the table is **not** partitioned on it.
- **`prior_value` / `current_value`** — the status label before and after the transition, as human-readable strings: `Ready`, `Live`, `Pause By Advertisers`, `Pause By MNTN`, `Deleted` (and a rare `Inactive`, 6 rows, as a prior value). **`prior_value IS NULL`** (63,137 rows — never an empty string) marks the **initial** status assignment when the campaign group is first created (almost always `current_value='Ready'`). Semantically: `Pause By Advertisers` = client-initiated pause; `Pause By MNTN` = platform-side pause (budget/billing/policy/automated); `Deleted` is terminal.
- **`entity_type`** — **constant `"campaign_group_status_id"`** for every row; it labels what `entity_id`/`entity_text` describe (the changed field is the campaign group's status id). Not a discriminator here.
- **`entity_id` / `entity_text`** — the **numeric status code and label of the new (current) status** — the id counterpart of `current_value`. Observed mapping: **1=Ready, 3=Live, 4=Pause By Advertisers, 5=Pause By MNTN, 8=Deleted**. `entity_text` duplicates `current_value`'s label; `entity_id` is the only place the numeric status code appears (there is **no** id for `prior_value`). Never NULL.
- **`entity_id_2` / `entity_text_2` / `entity_type_2`** — **always NULL** (147,027/147,027). Generic second-entity slots inherited from the shared change-log schema; unused for status changes. Ignore them.
- **`change_type`** — **constant `"Status"`** (this view is pre-filtered to status changes). Not a discriminator here.
- **`change_id`** — **constant `50`** (the source change-log's type code for "Status"), NOT a row identifier. Do not use it as a key or join column.
- **`user_id`** — the user who made the change; **NULL in 2,407 rows** (~1.6%) = system/automated transitions (e.g. MNTN-side auto-pauses, lifecycle automation) rather than a human edit.

## Joins & relationships
- **`campaign_group_id` → `campaign_groups`** (bronze.integrationprod / silver.core dim; grain = 1 row per campaign group). Relationship is **N:1 from this log to the dim** — a single group has many status rows, so joining the dim onto this log **fans out** to N rows per group (up to 15+). `campaign_groups.product_id` distinguishes PTV(1)/Select(2)/QuickFrame(3) if you need product context. Filter dims `deleted=FALSE AND is_test=FALSE`.
- **`advertiser_id` → `advertisers`** (dim; grain = 1 per advertiser). 1 advertiser : N change rows (16,008 distinct advertisers here). Join for `company_name` (`fpa_advertiser_verticals.advertiser_name` is unreliable/empty — use `advertisers.company_name`).
- **`user_id` → users dim** (bronze.integrationprod users). 1 user : N change rows; NULL = automated/system. Use only for attribution of who changed the status.
- No natural join to fact/delivery tables — to correlate a status change (e.g. a pause) with delivery, window facts (`summarydata.sum_by_campaign*`) on `campaign_group_id` around `time`.

## Gotchas
- **This is a pre-filtered slice, not the full change-log.** Only status changes (`change_type='Status'` / `change_id=50`) are present; those two columns plus `entity_type` are constants, and the three `entity_*_2` columns are entirely NULL. Sibling views (`campaign_group_goal_change_log`, `campaign_group_budget_change_log`, `..._creative_change_log`, etc.) carry the other change types.
- **`prior_value IS NULL` ≠ empty string.** It marks the first-ever status (creation → Ready), not a missing value. There are zero empty-string prior_values; test with `IS NULL`, not `= ''`.
- **Status code lives only in `entity_id`.** `current_value` gives the label; if you need the numeric code, read `entity_id` (1/3/4/5/8). There is no numeric code for `prior_value`.
- **No surrogate row key.** `change_id` is a type code (50), not a unique id. De-dup / identify a transition by `(campaign_group_id, time)`.
- **`time` is UTC.** Convert (`DATETIME(time, "America/Los_Angeles")`) before aligning to Pacific business days, or recent changes appear on "tomorrow."
- **History floor 2024-01-01** (min `time` = 2024-01-01 01:41 UTC, matching the SQLMesh summarydata build floor); no rows before that even though real status changes predate it.
- **No TTL** — rows are retained (physical `expirationTime` unset); the table only grows and is tiny.
- **Rare states:** `Inactive` appears only as a prior value (6 rows → Deleted); `Deleted` is generally terminal but 4 rows show a reactivation out of Deleted — treat Deleted-as-terminal as ~always, not absolute.

## Cost & partitioning notes
- **No partition, no clustering, no TTL** (confirmed on the physical `...__3366278031`: no `timePartitioning`/`rangePartitioning`/`clustering` block, `expirationTime` null). The whole table is ~**14.2 MiB** / 147,027 rows, so scans are effectively free and there is **no partition column to prune on** — a `WHERE time BETWEEN …` filter is semantic only (does not reduce bytes scanned).
- **The one filter to always apply:** none is needed for cost; add a `time` range only to bound the result set. Prefer named columns over `SELECT *` out of habit, but the difference is small here.
- **Measured (dry-run, 2026-07-19):** `SELECT *` (all 14 columns) = 14,852,461 bytes (~14.2 MiB); `SELECT time` alone (1 column) = 1,176,216 bytes (~1.1 MiB). `approx_logical_bytes` (14,852,461) = physical `numBytes` from `bq show` (= `numActiveLogicalBytes`).

## Example queries
```sql
-- Status timeline for one campaign group, oldest → newest (labels + new-status id)
SELECT DATETIME(time, "America/Los_Angeles") AS pt_time,
       prior_value, current_value, entity_id AS new_status_id, user_id
FROM `summarydata.campaign_group_status_change_log`
WHERE campaign_group_id = 130967
ORDER BY time;

-- Advertiser-initiated vs MNTN-side pauses per day
SELECT DATE(time) AS d, current_value AS pause_type, COUNT(*) n
FROM `summarydata.campaign_group_status_change_log`
WHERE current_value IN ('Pause By Advertisers', 'Pause By MNTN')
GROUP BY 1, 2
ORDER BY 1 DESC, 3 DESC;

-- Current (latest) status per campaign group
SELECT campaign_group_id,
       ARRAY_AGG(current_value ORDER BY time DESC LIMIT 1)[OFFSET(0)] AS latest_status
FROM `summarydata.campaign_group_status_change_log`
GROUP BY campaign_group_id;
```
