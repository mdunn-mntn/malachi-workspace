# summarydata.sum_by_creative_by_day

## Purpose
Daily **ad-creative-level** KPI rollup: delivery (impressions, video/display split, VAST quartiles), attributed visits / conversions / order-value under **several attribution models**, spend, and HLL household reach — one pre-aggregated row per creative per advertiser per day. It is the creative-grain sibling of `sum_by_campaign_by_day` with the **identical column set** (84 columns); the only structural difference is the entity key (`creative_id` here vs `campaign_id` there). Reach for it to compare creative variants (A/B creative tests), find the top/bottom creatives by VR/CVR/ROAS, track VAST completion by asset, or roll delivery up to the creative-group level. History runs back to **2024-01-01** and `uniques` (HLL) is populated and mergeable.

## Grain & keys
- **Grain:** one row per **`advertiser_id` x `creative_id` x `day`** (verified 2026-07-17: 55,839 rows = 55,839 distinct advertiser×creative pairs = the row count exactly — no duplicates). **`advertiser_id` is part of the key here — it is NOT redundant** (drift from the campaign sibling): the same `creative_id` can appear under two advertisers on one day (55,838 distinct `creative_id` vs 55,839 rows — one shared creative). Group / join on `(advertiser_id, creative_id)` to be exact; keying on `creative_id` alone very rarely collapses two advertisers' rows for a shared/copied creative.
- **Key / join columns:** `creative_id` (+ `advertiser_id`, + `day`). `creative_id` -> `silver.core.creatives.creative_id` recovers the creative's name, size, media type, and owning advertiser. No `campaign_id` column exists on this table — you cannot pin a row to a stage/campaign or funnel_level from here (use `sum_by_campaign_by_day` for that).

## Column meanings (only the non-obvious ones)
Column semantics are **identical to `sum_by_campaign_by_day`** (same builder, same measures) — see that doc for the full attribution treatment; the essentials:

**Visits (VV) are not a single column — they are `views + clicks`** (view-through + click-through). There is **no `revenue` column** (revenue is the `*_order_value` NUMERIC-dollars family) and **no `conversions` column** (use `view_conversions + click_conversions`).

- **`day`** — DATE, the partition key. No epoch column exists (`time_unit: date`).
- **`impressions`** vs **`display_impressions` / `video_impressions`** — total vs display/CTV split; `video_impressions` = CTV. VCR ≈ `vast_complete / vast_start` — the VAST quartile columns (`vast_start/firstquartile/midpoint/thirdquartile/complete`) are per-creative video-completion counts, the main reason to reach for this creative-grain table.
- **`view_impressions`, `view_viewed`, `view_untrackable`** — viewability accounting (measured / measured-as-viewed / untrackable), distinct from `views` (view-through visits).
- **`media_spend`, `data_spend`, `platform_spend`** (NUMERIC) — the three spend buckets; **total spend = their sum**. `media_cost` (NUMERIC) and `video_spend` (BIGNUMERIC) are additional cost measures; the standard total uses the three `*_spend` columns.
- **`uniques`, `site_visitors`, `new_site_visitors`, `existing_site_visitors`, `new_users_reached`, `existing_users_reached`** (all **BYTES**) — **BQ-native HLL++ sketches, NOT integer counts.** Read distinct households with `HLL_COUNT.MERGE(uniques)`; **never `SUM`**. Per-creative reach is lower than per-campaign, so single-creative sketches are noisier at the HLL floor.
- **ATTRIBUTION-VARIANT FAMILIES — separate models, NOT additive buckets; NEVER SUM across families:**
  - **Default** (`views, clicks, view_conversions, click_conversions, *_order_value`) — **INCLUDES CTV** (a CTV view-conversion is a `view_conversion`).
  - **`last_touch_*` vs `last_tv_touch_*`** — two SEPARATE last-touch models (display/overall vs TV-only) that can credit the same conversion to different creatives. Not subsets, not additive. **Do NOT do `last_touch + last_tv_touch` (or `default + last_tv_touch`) — it double-counts CTV-exposed conversions.**
  - **`competing_*`** — the **`industry_standard` (FIRST-TOUCH)** variant. The client-UI headline = default last-touch **+ `competing_*`** (Verified Visits = `clicks + views + competing_views`; order-value adds `competing_view_order_value`). `last_tv_touch` is never in the UI headline.
  - **`conversions_assist_*` / `visits_assist`** — multi-touch assist credit; **`probattr_*`** — probabilistic attribution. Each family has its own `competing_` (first-touch) sub-variant.

## Joins & relationships
- **`creative_id` -> `silver.core.creatives`** (partner grain: **exactly 1 row per `creative_id`** — verified 2026-07-19: 5,722,718 rows = 5,722,718 distinct `creative_id`; thin view over `bronze.integrationprod.core_creatives`). Safe **1:1** lookup, **no fan-out** — recovers `name`, `creative_size_id`, `media_type_id`, `creative_location`, `active`, `approved`, and the dim-side `advertiser_id`. Filter `deleted = FALSE` for live creatives. Caveat: for the rare `creative_id` served under two advertisers, the dim's single `advertiser_id` may not match one of the fact rows — trust the fact row's `advertiser_id` for spend/delivery attribution.
- **`creative_id` -> `silver.core.creative_groups_x_creatives` -> `silver.core.creative_groups`** — creative->group is a **bridge (potential N:M)**, so this join can **fan out** a creative into multiple groups; for pre-aggregated group KPIs prefer the ready-made `sum_by_creative_group_by_day` rollup instead of rolling up through the bridge.
- **`advertiser_id` -> `bronze.integrationprod.advertisers`** (1 row per advertiser) for `company_name`. `fpa_advertiser_verticals.advertiser_name` is unreliable (empty since 2025-12) — use `advertisers.company_name`.
- **No `campaign_id` on this table.** To attribute a creative's delivery to a stage/campaign, funnel_level, or objective, you must go through impression-level facts (`impression_facts` / `cost_impression_log`) — this rollup cannot be joined to `campaigns`.
- **Sibling rollups (identical columns, same 2024-01-01 start):** `sum_by_campaign_by_day` (campaign grain), `sum_by_campaign_group_by_day`, `sum_by_advertiser_by_day`, `sum_by_creative_group_by_day` (creative-group grain), `sum_by_region_by_day`, `sum_by_ctv_network_by_day` (lacks `competing_*`).
- **Fresh underlying facts:** `silver.summarydata.{impression_facts, visit_facts, conversion_facts, spend_facts}` (and `all_facts`, time col `hour`) are the hour-grain sources this rollup is built from — use them if this view ever lags.

## Gotchas
- **`require_partition_filter = TRUE` (enforced on the physical table).** Any query without a `day` filter hard-errors ("Cannot query over table ... without a filter over column(s) 'day' that can be used for partition elimination"). Always bound `day` — this also blocks bare `MIN/MAX(day)` scans (use `INFORMATION_SCHEMA.PARTITIONS`, or bound the range as in the freshness query below).
- **`advertiser_id` is part of the grain (unlike the campaign sibling).** Group/join on `(advertiser_id, creative_id)`; a shared `creative_id` across advertisers will otherwise collapse two rows.
- **Attribution variants are separate models — never SUM across families** (default / last_touch / last_tv_touch / competing / probattr / assist). Adding `last_tv_touch` to default/last_touch double-counts CTV-exposed conversions.
- **No `revenue`, no `conversions`, and no `campaign_id`** — derive visits = `views + clicks`, conversions = `view_conversions + click_conversions`, revenue = `*_order_value`; there is no path to campaign/funnel from this table.
- **`uniques` et al. are HLL BYTES sketches**, not integers — `HLL_COUNT.MERGE(...)`, never `SUM`. Per-creative reach is small, so treat single-creative HLL counts as approximate.
- **Freshness — verify `max(day)` before recent-window use.** Live 2026-07-19: **fresh through the current day** (max(day) = current UTC day; the leading partition is naturally partial). Prose logged a ~17-day lag on the campaign/advertiser siblings on 2026-05-01, so freshness has varied across this family — always check `max(day)`; if lagging, fall back to the hour-grain `*_facts` tables.
- **`__NULL__` partition exists but is empty** (0 rows on 2026-07-19); range predicates on `day` exclude any NULL-`day` rows anyway.

## Cost & partitioning notes
- **Partition:** DAY on `day`, `require_partition_filter = TRUE`. **Cluster:** none. **The one filter to always apply: a bounded `day` range** — mandatory and the only pruning lever (no cluster keys). Physical backing table: **46,622,834 rows / 156,608,293,143 bytes (~145.9 GiB)**, **932 date partitions** (2024-01-01 -> current day) + 1 empty `__NULL__` partition. Roughly 5x wider row-volume than `sum_by_campaign_by_day` (~55.8K rows/day vs ~12K) because there are far more creatives than campaigns.
- **SELECT only the columns you need — the row is very wide (84 cols) so `SELECT *` is ~66x costlier than a narrow projection.** Labeled dry-run figures (same partition = 1 day, 2026-07-17):
  - `SELECT *` (all 84 cols), 1 day: **176,536,244 bytes (~168.4 MB)**
  - 6 narrow cols (`advertiser_id, creative_id, day, impressions, views, clicks`), 1 day: **2,680,272 bytes (~2.56 MB)** — ~65.9x cheaper than `SELECT *`
  - no `day` filter: **hard error** (partition-filter required)

## Example queries
```sql
-- Top creatives by VR + ROAS for one advertiser over a window
SELECT s.creative_id, cr.name,
       SUM(s.views + s.clicks)                                   AS visits,
       SAFE_DIVIDE(SUM(s.views + s.clicks), SUM(s.impressions))  AS vr,
       SAFE_DIVIDE(SUM(s.vast_complete), SUM(s.vast_start))      AS vcr,
       SUM(s.media_spend + s.data_spend + s.platform_spend)      AS spend,
       SAFE_DIVIDE(SUM(s.view_order_value + s.click_order_value),
                   SUM(s.media_spend + s.data_spend + s.platform_spend)) AS roas
FROM `summarydata.sum_by_creative_by_day` s
LEFT JOIN `dw-main-silver.core.creatives` cr
  ON cr.creative_id = s.creative_id
WHERE s.day BETWEEN DATE '2026-06-01' AND DATE '2026-06-30'
  AND s.advertiser_id = 31357
GROUP BY s.creative_id, cr.name
ORDER BY visits DESC;

-- Freshness check (bounded so partition-filter is satisfied)
SELECT MAX(day) AS max_day
FROM `summarydata.sum_by_creative_by_day`
WHERE day BETWEEN DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY) AND CURRENT_DATE();
```
