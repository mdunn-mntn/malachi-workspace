# summarydata.conversion_sources

## Purpose
Row-level conversion-attribution fact for **verified-impression** conversions, with each conversion's
landing-page marketing parameters (`utm_*`, `gclid`, `gbraid`, `wbraid`, ...) broken out into their own
rows. Reach for it when you need to tie an attributed conversion to (a) the marketing/paid-search
query-string that came in on the referer, (b) the specific impression that got credit (`ad_served_id`,
`impression_ip`, `impression_time`, ad-network `domain`), and (c) the attribution model / source that
credited it. It is the exploded, event-grain source that feeds the pre-aggregated `conversion_facts` /
`sum_by_*` rollups — use those rollups for counts/revenue; use this table when you need per-event
attribution detail or the UTM/click-id breakdown.

## Grain & keys
- **Grain:** one row per **conversion event (`uuid`) x marketing query-param `key`** parsed out of the
  conversion's landing-page `referer` URL. Verified on 2026-07-10: `COUNT(DISTINCT uuid||'|'||key)` =
  81,076 = `COUNT(*)` exactly; the same day had only 22,313 distinct `uuid`, so each conversion is
  repeated ~3.6x (once per UTM/click parameter). **`uuid` is the conversion-event key; it is NOT unique
  in this table.**
- **Key(s) / join columns:** `uuid` (conversion event), `advertiser_id`, `campaign_id`/`group_id`/
  `creative_id`, `ad_served_id` (attributed impression), `attribution_model_id`, `conversion_source_id`,
  `visit_uuid` (attributed site visit). `order_id` identifies the order (NULL ~1.4% of rows — untyped
  conversions).

## Column meanings (only the non-obvious ones)
- **`time`** (TIMESTAMP, partition) = the **conversion timestamp**, not the impression time. Verified:
  `impression_elapsed_time` = `time` − `impression_time` on sampled rows (e.g. impression 2026-06-12
  20:05 + 651h54m ≈ `time` 2026-07-10). A conversion attributed to an impression from days/weeks earlier
  lands in the partition of its *conversion* date — filtering `time` selects by conversion date.
- **`key` / `value`** = one marketing/click-tracking parameter parsed from the `referer` landing-URL
  query string. This is the column that explodes the grain. Observed keys (2026-07-10): `utm_source`,
  `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gclid`, `gbraid`, `wbraid`, `cid`, `cm_mmc`.
  `value` = the param's value; **`value = '-1'` is the empty/sentinel value** (param present but blank).
- **`referer`** = the full conversion landing-page URL including query string. **`parent_referer`** = the
  page that referred to it (e.g. `https://www.google.com/`) or `'-1'` sentinel when unknown.
- **`domain` / `subdomain`** = the **ad-impression publisher/network** the credited impression ran on
  (values like `NBC`, `Disney+`, `TBS` — CTV app names), **NOT the conversion website**. `subdomain` is
  frequently `com`/NULL (looks like a TLD mis-split — low signal).
- **`order_amt`** (NUMERIC) = conversion revenue in `order_curr`. **There is NO `order_amt_usd` column —
  this is native currency, not USD-normalized** (same convention as `ui_conversions`). `order_curr` has a
  **case-inconsistency gotcha: both `USD` and `usd` appear** — normalize with `UPPER()`.
- **`event_epoch`** (INT64) = **microseconds** (magnitude ~1.78e15 in 2026 = UNIX_MICROS scale). It is an
  underlying event epoch that is generally **≤ `time`** and does **not** equal `UNIX_MICROS(time)`;
  prefer `time` for the conversion moment.
- **`impression_epoch`** (INT64) = **microseconds** = `UNIX_MICROS(impression_time)` at full precision;
  `impression_time` is the same instant **truncated to the whole second** (so `impression_epoch` carries
  the sub-second ms and matched `UNIX_MICROS(impression_time)` on the 78% of rows with a whole-second
  impression). Anchor: `impression_epoch = UNIX_MICROS(impression_time)` (micros).
- **`recency_elapsed_time` / `impression_elapsed_time`** (INTERVAL) — `impression_elapsed_time` = elapsed
  from the credited impression to the conversion (= `time` − `impression_time`, verified).
  `recency_elapsed_time` is often NULL (elapsed since a more-recent touch/visit).
- **`source_type`** (STRING) = attribution family: `conversions` (~80% of uuids) vs
  `last_tv_touch_conversions` (~20%). The two are **disjoint uuid populations** (17,511 + 4,802 = 22,313
  total on 2026-07-10), not the same conversion doubled. `conversion_assist` is populated (`false`) for
  `conversions` rows and **NULL exactly for `last_tv_touch_conversions`** rows.
- **`conversion_source_id`** (INT64) = data-source FK. ~99.99% = **`23`** (`guid_log`, display "MNTN
  Pixel"/"Website Event" — the post-2025-01-10 website-pixel standard); rare `41`. Decode via
  `data_sources` (see data_catalog.md § core_advertiser_conversion_types: `-1`=MNTN Pixel, `23`=guid_log,
  `21`=MNTN Conversion).
- **`conversion_type`** (STRING) = client-tag event name. Dominated by the **`-101` sentinel** (~88% =
  untyped/default pixel conversion, same sentinel `ui_conversions` renders); named types (`Lead`,
  `Purchase`, `SignUp`, `app_submitted`, ...) plus **junk client values** (`[object Object]`, pentest
  payloads) also appear.
- **`attribution_model_id`** (INT64) = attribution-model FK (dim `core_attribution_models`). Observed
  9 (dominant), 10, 11, 12, 13, 14, 29 — **one model per `uuid`** (does not fan out the grain).
- **`pa_model_id`** (INT64) = probabilistic-attribution model id; NULL for ~98% of rows, `1002` when set.
- **`from_verified_impression`** (BOOL) = **TRUE for every row** — this view is already scoped to
  verified-impression attribution (no filter needed; it also excludes disputed/click rows in practice:
  sampled `disputed`=false, `click`=false, `click_through`=true throughout).
- **`ip` vs `impression_ip`** = conversion-event IP vs the credited impression's IP. They **differ on
  ~37% of rows** (cross-device / IP drift); `is_cross_device` is TRUE on ~30%.
- **`ad_served_id`** = the credited impression's ad-served UUID (non-null on all rows).
  **`first_touch_ad_served_id`** = first-impression UUID (~80% NULL — populated at write time, no
  backfill). **`visit_uuid`** = the attributed site-visit id.

## Joins & relationships
- **`attribution_model_id` → `core_attribution_models` / `silver.core.attribution_models`** (PK
  `attribution_model_id`) — **1:1 dim, no fan-out**. `attribution_model_type_id` there splits last-touch
  vs probabilistic.
- **`conversion_source_id` → `audience.data_sources`** (PK `data_source_id`) — **1:1 dim** decode.
- **`advertiser_id` → `integrationprod.advertisers`** (`company_name`) — 1:1 dim. Use `advertisers` for
  the name; `fpa_advertiser_verticals.advertiser_name` is unreliable (empty since 2025-12).
- **`campaign_id` / `group_id` / `creative_id` → campaign/creative dims** — 1:1 dims.
- **`ad_served_id` (+ `impression_ip`, `impression_time`) → `logdata.cost_impression_log`** — the credited
  served impression. `ad_served_id` is per-impression → effectively **1:1** back to the impression (a
  conversion crediting many impressions is not the pattern here; one credited impression per row).
- **`uuid` → conversion event** (relates to `logdata.conversion_log` / `ui_conversions`). **FAN-OUT
  WARNING: this table is already exploded one-row-per-marketing-param, so joining any other table ON
  `uuid` multiplies the partner rows by the number of UTM/click params (~3.6x).** Dedup to `uuid` (or
  filter to a single `key`) *before* joining.

## Gotchas
- **The #1 trap — never `SUM(order_amt)`/`COUNT(*)` raw.** Each conversion is repeated once per marketing
  param, so raw sums/counts multiply revenue and conversion counts by ~3.6x (varies by how many UTM/click
  params were on the referer). Aggregate over `COUNT(DISTINCT uuid)` and dedup revenue to one row per
  `uuid` (e.g. `MAX(order_amt)` within `uuid`, or filter `key = 'utm_source'` / a single key) first.
- **`source_type` splits into two disjoint uuid sets** (`conversions` vs `last_tv_touch_conversions`).
  They are NOT the same conversion twice — but if you want only standard attribution, filter
  `source_type = 'conversions'`; last-TV-touch is a separate credited population.
- **`order_curr` case inconsistency** (`USD` vs `usd`) — `UPPER()` before grouping.
- **`conversion_type` pollution** — `-101` sentinel (untyped) dominates; client-side junk
  (`[object Object]`, SQLi/XSS pentest strings) and fabricated `order_amt` values leak in the same way as
  `conversion_log` (see data_knowledge.md § "Pentest / scanner pollution", WGU 31357 case). Treat
  `order_amt` as native, un-scrubbed revenue.
- **`time` = conversion date, not impression date.** Filtering `time` to a window can pull conversions
  whose credited impression is far outside that window (`impression_elapsed_time` reached ~650h in the
  sample). Filter on `impression_time` too if you need impression-date alignment.
- **`domain` is the ad network, not the conversion site** — don't read it as the advertiser's website.
- **History starts 2026-03-01** (`MIN(time)` = 2026-03-01 00:00:01, fixed backfill floor). No earlier
  data; ~4.5 months present as of 2026-07. `time` runs slightly into the future edge (`MAX` 2026-07-20
  03:59, near-real-time write).

## Cost & partitioning notes
- **Partition: `time` (DAY). No clustering. No `require_partition_filter` (full scans allowed but avoid).
  No partition expiration set on the physical table.** Physical: ~11.1M rows, ~30.6 GB
  (`bq show` numBytes = 30,617,601,777; single physical table, not a UNION).
- **Always filter `time`.** Dry-run, identical column set (`SELECT order_id`): **full scan = 212 MB**;
  **one day (`time` in [2026-07-10, 2026-07-11)) = 2.23 MB (~95x less)**. Because there is **no
  clustering, filtering `advertiser_id` prunes nothing** — only a `time` range prunes bytes.
- **Avoid `SELECT *`** — the wide STRING columns (`referer`, `value`, `query`, `parent_referer`) dominate
  width, so `SELECT *` costs many multiples of a few-column projection (the 212 MB / 2.23 MB figures above
  are the narrow one-column `order_id` set; do not compare them to a `SELECT *` figure).
- `MIN/MAX(time)` over full history scanned 0.083 GB (two TIMESTAMP columns only) — cheap because it
  reads just the timestamp columns.

## Example queries
```sql
-- Dedup to conversion grain, then aggregate revenue/counts (avoids the ~3.6x param explosion)
SELECT
  advertiser_id,
  COUNT(DISTINCT uuid)                       AS conversions,
  SUM(order_amt)                             AS revenue_native_curr   -- one row per uuid after dedup
FROM (
  SELECT advertiser_id, uuid, ANY_VALUE(order_amt) AS order_amt
  FROM `summarydata.conversion_sources`
  WHERE time >= '2026-07-10' AND time < '2026-07-11'
    AND source_type = 'conversions'
  GROUP BY advertiser_id, uuid
)
GROUP BY advertiser_id
ORDER BY conversions DESC;

-- UTM/click-id breakdown for a conversion window (the reason to use this table over conversion_facts)
SELECT key, value, COUNT(DISTINCT uuid) AS conversions
FROM `summarydata.conversion_sources`
WHERE time >= '2026-07-10' AND time < '2026-07-11'
  AND key IN ('utm_source','utm_medium','gclid')
  AND value != '-1'
GROUP BY key, value
ORDER BY conversions DESC;
```
