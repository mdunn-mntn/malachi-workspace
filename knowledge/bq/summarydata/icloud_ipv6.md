# summarydata.icloud_ipv6

## Purpose
A reference/dimension list of the **IPv6 CIDR blocks that Apple iCloud Private Relay uses for egress**. Private Relay is Apple's pseudo-VPN: it hides a device's real IP behind a rotating pool of Apple/Cloudflare/Akamai/Fastly egress ranges, so any observed IPv6 that falls inside one of these blocks cannot be trusted for geo-targeting or identity resolution. Reach for this table when you need to **identify, filter, or exclude** iCloud Private Relay IPv6 traffic. The documented usage of the IPv4 sibling (`summarydata.icloud_ipv4`, which shares the same raw source `raw__icloud_ips_raw`) is that targeting/bidder **excludes these IPs from bidding so they never enter MembershipDB** (data_catalog.md, via Ryan Kleck 2026-04-01); and per the prose oracle, IPs from iCloud relay **require special treatment for geo-targeting**. It is the IPv6 sibling of `summarydata.icloud_ipv4` and `summarydata.icloud_guids`.

## Grain & keys
- **Grain:** one row per **distinct IPv6 CIDR network block** (e.g. `2606:54c0:1000::/45`). Verified 406,865 rows = 406,865 distinct `ip` (1:1).
- **Key / join column:** `ip` is the natural unique key, **but it is a network prefix in CIDR notation, not a host address.** You do not equi-join observed traffic to `ip`; you test subnet membership via the coarser prefix columns (`first_8_bits` / `first_16_bits` / `network`) or IPv6 range logic.

## Column meanings (only the non-obvious ones)
All five columns are derived from a single source `ip` string by the view (see View definition). None is NULL in practice (0 NULLs over 406,865 rows). Every `ip` carries a `::` and a `/NN` CIDR mask.

- **`ip`** — the full iCloud Private Relay IPv6 **CIDR block** as published by Apple, e.g. `2606:54c0:1000::/45` or `2606:54c0:1000:10::/64`. Always a network block (`::/NN`), never a single host. The same base prefix can appear at several mask lengths (e.g. `.../45` and `.../64`), so blocks **overlap** — one observed address can sit inside multiple rows.
- **`prefix`** — `ip` with everything from the first `::` onward stripped off (`REGEXP_REPLACE(ip, '::.*$', '')`), so the `/NN` mask is also removed. E.g. `2606:54c0:1000`. 392,375 distinct values (slightly fewer than `ip` because different masks on the same base collapse together).
- **`first_8_bits`** — the **first hextet** only: `SPLIT(ip, ':')[0]`, e.g. `2606`. **Name is a misnomer** — one IPv6 hextet is 16 bits, so this is the first 16 bits, not 8. Only **4 distinct values** exist (`2606`, `2a02`, `2a04`, `2a09`) — the four leading blocks Apple/its CDN partners allocate to Private Relay.
- **`first_16_bits`** — the **first two hextets** joined by `:`, e.g. `2606:54c0`. Again a misnomer (this is 32 bits). Only **7 distinct values** exist: `2a02:26f7`, `2a09:bac2`, `2a09:bac3`, `2606:54c0`, `2a04:4e41`, `2606:54c3`, `2a09:bac4`.
- **`network`** — the **first three hextets** joined by `:`, e.g. `2606:54c0:1000`. 120,940 distinct values. It is the **narrowest** of the three prefix keys (48 bits), but that makes it **unsafe as a pre-filter for blocks coarser than /48**: 21,050 rows (5.17% — all the `/40`, `/41`, `/45` blocks; verified live 2026-07-19) have masks shorter than 48, so their 3rd hextet is not fully fixed by the mask and a true member address can compute a *different* `network` value → it is silently dropped by an equi-join on `network`. Use `first_16_bits` (32 bits) as the lossless coarse key instead (see Joins / Gotchas).

The three `first_8_bits` → `first_16_bits` → `network` columns are **progressively-narrower prefix keys** provided so a consumer can cheaply pre-filter observed IPv6 traffic to the candidate iCloud blocks before doing exact subnet math. **A prefix key is only a safe (lossless) pre-filter when its width ≤ the block's mask** — otherwise it drops true members of coarser blocks. The coarsest block here is `/40`, so `first_16_bits` (32 bits) is safe for *every* row, while `network` (48 bits) is safe only for `/48`-or-finer blocks. Prefer the coarsest key that is still selective enough, and let the exact subnet-math step reject the extra false-positive candidates it admits.

## Joins & relationships
- **How it is used (not an equi-join):** to test whether an observed IPv6 belongs to iCloud, extract the first two hextets of the (canonicalized) observed address and equi-join them to **`first_16_bits`** to cheaply pre-filter to candidate iCloud blocks, then confirm exact subnet membership with CIDR range logic. **Do NOT pre-filter on `network`** (48 bits) — it silently drops the 21,050 sub-/48 blocks (`/40`/`/41`/`/45`), letting real Private Relay IPs pass through as "real". `first_8_bits` (16 bits) is also lossless but less selective. Matching directly on `ip` (the CIDR string) will almost never hit.
- **Fan-out risk:** this is the small (dimension) side (~407K rows). Because CIDR blocks **overlap** (multiple mask lengths per base prefix), a single observed address can match **several rows** — a prefix/subnet join against a large event or impression table can fan out multiplicatively. Dedup to the single best (coarsest or longest-prefix) match, or `SELECT DISTINCT` the network keys before joining.
- **Sibling reference lists:** `summarydata.icloud_ipv4` (IPv4 equivalent — same underlying raw source, the rows *without* a colon) and `summarydata.icloud_guids`. All three are reference/dimension lists, not fact tables — no timestamps, no partition to prune.
- **Upstream partner grains:**
  - `dw-main-bronze.analytics_curated.icloud_ipv6` — EXTERNAL table, ~406,799 rows, **already carries all 5 columns**. This is the **dominant/curated source** (contributes essentially the whole list).
  - `dw-main-bronze.sqlmesh__raw.raw__icloud_ips_raw__1716913687` — physical TABLE, partitioned `DAY` on `ds`, 49.3M rows across **172 daily snapshots** (2026-01-05 → 2026-07-18, one `version` per day). It holds **both IPv4 and IPv6**; this view filters to rows whose `ip` contains `':'` (IPv6) and re-derives the 5 columns. It is **1:N** (many daily snapshots per ip); the view collapses it to 1 row per ip via `DISTINCT`. It adds only ~66 net-new distinct IPs on top of the external set.

## Gotchas
- **Not a point-in-time snapshot — it accumulates.** The physical view `SELECT DISTINCT`-unions the curated external table with **every** daily raw snapshot since 2026-01-05. A range Apple published once and later withdrew still appears. You **cannot** recover "today's" iCloud list from this view; if you need the current published set, query `raw__icloud_ips_raw` at the latest `ds`.
- **`ip` is a CIDR block, never a host.** Do not join event IPs to `ip` with `=`. Use prefix/subnet matching (see Joins).
- **Overlapping masks.** The same base prefix appears at multiple `/NN` lengths (`.../45`, `.../64`, …), so rows overlap and an address can match many rows → dedup before joining (fan-out).
- **`network` (48-bit key) under-selects → false negatives.** 21,050 rows (5.17%: masks `/40`=37, `/41`=52, `/45`=20,961) are **coarser than /48**, so their 3rd hextet is not fully fixed by the mask. Pre-filtering observed traffic by equi-joining on `network` drops true members of those blocks (their computed 3-hextet prefix differs from the stored base) → Private Relay IPs slip past the exclusion, and the "confirm subnet math" step never runs on the already-dropped row. Pre-filter on **`first_16_bits`** (32 bits ≤ the coarsest `/40` mask, so lossless), then confirm exact CIDR membership. Full mask distribution (verified live 2026-07-19): `/40`=37, `/41`=52, `/45`=20,961, `/48`=109,583, `/52`=7,006, `/54`=747, `/56`=1,606, `/58`=1,470, `/60`=7,671, `/64`=257,732 (Σ=406,865).
- **Observed IPs must be canonicalized before SPLIT extraction.** The prefix columns are built by `SPLIT(ip, ':')`, which assumes an expanded address. On RFC-5952 **compressed** forms (e.g. `2606:54c0::1` → `['2606','54c0','','1']`) the offsets shift and the match fails. iCloud's leading two hextets are always present and non-zero, so `first_16_bits` survives compression in practice, but any deeper (`network`) or observed-side extraction should expand the address first.
- **Column names lie about bit widths.** `first_8_bits` = first hextet (16 bits), `first_16_bits` = first two hextets (32 bits). Treat them as "first / first-two / first-three colon groups", not literal bit counts.
- **Two-source merge.** Curated external is the bulk; the raw daily-snapshot union is a thin delta. If the external table is unavailable the list still populates from raw (and vice versa), but counts may shift by the ~66-row delta.
- **No date/epoch column at all.** `time_unit` is N/A here — the silver view exposes only the 5 string columns. (The underlying raw `ds` is a DATE snapshot key, not an epoch integer, and it is not surfaced.)

## Cost & partitioning notes
- **No partition to filter — every query scans the whole list.** The silver view is not partitioned/prunable: it unions all 172 raw daily snapshots and `DISTINCT`s them, so there is no `ds` to push down. The underlying raw table *is* `DAY`-partitioned on `ds`, but you cannot reach it through this view. It is a small reference list (~407K rows); if you use it repeatedly in joins, **materialize it once** into a CTE/temp table (optionally clustered on `network`) rather than re-scanning.
- **Cost is fixed regardless of columns selected.** All output columns derive from the raw `ip` column, so pruning columns saves nothing:
  - `SELECT *` — dry-run **1,204,072,479 B (1.20 GB)** [measured 2026-07-19].
  - `SELECT ip` only — dry-run **1,204,072,479 B (1.20 GB)**, identical [measured 2026-07-19].
  - `SELECT COUNT(*)` etc. — actual run billed **1.15 GB** (tier 1) [measured 2026-07-19].
  - The estimate is dominated by the raw `ip` column across 172 partitions; the EXTERNAL `analytics_curated.icloud_ipv6` contributes ~0 to the on-demand byte estimate despite supplying most rows.
- `approx_logical_bytes` left `null`: the silver view has `numBytes 0`; the raw physical is 1.99 GB but that is the full IPv4+IPv6, all-columns, all-172-snapshots superset (not this view's slice), and the external partner reports 0 bytes — there is no clean per-view backing figure to sum.

## Example queries
```sql
-- Coarse pre-filter of observed IPv6 traffic to candidate iCloud blocks (then confirm subnet math).
-- Pre-filter on first_16_bits (32 bits), NOT network (48 bits): network silently drops the ~5% of
-- blocks coarser than /48 (/40,/41,/45) — a false negative that lets Private Relay IPs pass through.
-- first_16_bits is lossless (32 <= the coarsest /40 mask). Cost is identical (whole-view scan either
-- way, ~1.20 GB). Dedup the reference side to avoid overlapping-CIDR fan-out.
WITH icloud AS (
  SELECT DISTINCT first_16_bits FROM `summarydata.icloud_ipv6`
)
SELECT e.ip                                 -- select only the columns you need, never SELECT *
FROM `logdata.some_event_log` e
JOIN icloud i
  -- e.ip must be canonicalized/expanded first; on RFC-5952 compressed forms (e.g. 2606:54c0::1)
  -- SPLIT-by-':' offsets shift. iCloud's leading two hextets are always present/non-zero, so
  -- first_16_bits survives compression in practice.
  ON CONCAT(SPLIT(e.ip, ':')[SAFE_OFFSET(0)], ':',
            SPLIT(e.ip, ':')[SAFE_OFFSET(1)]) = i.first_16_bits
WHERE e.ds = CURRENT_DATE()   -- always date-filter the LARGE side (event log), not the ref list
-- then confirm exact CIDR membership of e.ip against the matched icloud_ipv6 blocks.
;
```

## View definition
```sql
SELECT * FROM `dw-main-silver`.`sqlmesh__summarydata`.`summarydata__icloud_ipv6__2946731607`

-- resolves to (physical SQLMesh view):
SELECT DISTINCT ip, prefix, first_8_bits, first_16_bits, network
FROM (
  -- (a) raw daily snapshots, IPv6 subset, 5 cols re-derived from ip
  SELECT ip,
         REGEXP_REPLACE(ip, '::.*$', '')                         AS prefix,
         SPLIT(ip, ':')[SAFE_OFFSET(0)]                          AS first_8_bits,
         CONCAT(SPLIT(ip,':')[SAFE_OFFSET(0)],':',SPLIT(ip,':')[SAFE_OFFSET(1)]) AS first_16_bits,
         CONCAT(SPLIT(ip,':')[SAFE_OFFSET(0)],':',SPLIT(ip,':')[SAFE_OFFSET(1)],':',SPLIT(ip,':')[SAFE_OFFSET(2)]) AS network
  FROM `dw-main-bronze`.`sqlmesh__raw`.`raw__icloud_ips_raw__1716913687`
  WHERE REGEXP_CONTAINS(ip, ':')
  UNION ALL
  -- (b) curated external table, already carries all 5 cols
  SELECT ip, prefix, first_8_bits, first_16_bits, network
  FROM `dw-main-bronze`.`analytics_curated`.`icloud_ipv6`
) AS combined_ips
ORDER BY ip, first_8_bits, first_16_bits
```
