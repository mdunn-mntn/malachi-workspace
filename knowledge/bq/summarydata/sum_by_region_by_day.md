# summarydata.sum_by_region_by_day

## Purpose
The **US-state geographic breakout** of the daily campaign rollup. It carries the *identical* measure set to `sum_by_campaign_by_day` (delivery, VAST quartiles, multi-model attributed visits/conversions/order-value, spend, HLL household reach) with one extra dimension: `region` = the delivery **state**. Reach for it for **state-level geo-mix and YoY geo-share** analysis, per-state VR/CVR/ROAS, and "where is delivery concentrated" questions. History runs back to **2024-01-01** and is **fresh through the current day**.

**It is STATE grain, NOT DMA.** There is no DMA-grain fact table with history — for per-DMA (Nielsen metro) delivery use `logdata.cost_impression_log` (`metro_id`, filter `DATE(time)`); see the geo-bridge gotcha in `data_knowledge.md`. Use this table for state-level geo-mix only.

## Grain & keys
- **Grain:** exactly **one row per `campaign_id` x `region` x `day`** (verified 2026-07-10: 202,040 rows = 202,040 distinct campaign×region = 202,040 distinct advertiser×campaign×region — no duplicates, no NULL region). That day held 12,154 distinct campaigns × 52 regions. `campaign_id` maps to one advertiser, so `advertiser_id` is redundant within the key.
- **Key / join columns:** `campaign_id` + `region` (+ `day`). `campaign_id` = the internal STAGE campaign (obj 1 = S1 prospecting / 4 = retargeting / 5,6 = MT-S2/S3 / 7 = Ego), **not** the client-facing group. Join `campaign_id -> bronze.integrationprod.campaigns.campaign_id` for `campaign_group_id`, `objective_id`, `funnel_level`.
- **Row grain is finer than "state"** — a state total requires `GROUP BY region` and `SUM` across the ~12K campaigns that delivered there; a single row is one campaign's contribution to one state on one day.

## Column meanings (only the non-obvious ones)
The measure set is **identical to `summarydata.sum_by_campaign_by_day`** — the full column semantics (attribution families, HLL sketches, spend buckets, VAST/viewability) live in that doc and apply here 1:1. Only the geo-specific and gotcha-worthy columns are restated below.

- **`region`** (STRING) — the delivery **US state NAME**, spelled out: `"Texas"`, `"California"`, `"New York"`, plus `"District of Columbia"`. **52 distinct values** on a full day = 50 states + DC + a **`"-1"` sentinel** for unresolved / unknown geo (tiny: 167 rows / 6,552 impressions on 2026-07-10 — exclude it for clean state analysis). It is **NOT** a DMA/Nielsen `metro_id`, **NOT** an internal `location_id`, and **NOT** a 2-letter abbreviation. There is no numeric geo key — join to other geo systems is by name only. The sample is US-only (no international regions).
- **`day`** — DATE, the partition key. No epoch column exists (`time_unit: date`).
- **Visits (VV) = `views + clicks`** (view-through + click-through). There is **no `revenue` column** (use the `*_order_value` NUMERIC family) and **no `conversions` column** (use `view_conversions + click_conversions`).
- **`media_spend`, `data_spend`, `platform_spend`** (NUMERIC) — **Total spend = the sum of these three.** `media_cost` and `video_spend` (both NUMERIC here) are additional cost measures; the standard total-spend convention uses the three `*_spend` columns, not `media_cost` (e.g. 2026-07-10: total spend $1,211,877 vs `media_cost` $422,520).
- **`uniques`, `site_visitors`, `new_site_visitors`, `existing_site_visitors`, `new_users_reached`, `existing_users_reached`** and the `competing_*`/`probattr_*` `_visitors` variants (all **BYTES**) — **BQ-native HLL++ sketches, NOT integer counts.** Read distinct households with `HLL_COUNT.MERGE(uniques)`, never `SUM` (verified 2026-07-10: 191,454/202,040 rows non-null; `HLL_COUNT.MERGE(uniques)` across all campaign×region rows = **12,357,261 households — an EXACT match to the sibling `sum_by_campaign_by_day` same-day reach**, confirming this table is a state breakout of the *same* underlying sketches). Merging across regions/campaigns dedupes correctly; summing the sketch bytes does not.
- **ATTRIBUTION-VARIANT FAMILIES — separate models, NOT additive buckets; NEVER SUM across families** (same as the campaign rollup): **Default** (`views/clicks/*_conversions/*_order_value`, includes CTV) · **`last_touch_*`** vs **`last_tv_touch_*`** (two separate last-touch models — never add `last_tv_touch` to default/last_touch, it double-counts CTV-exposed conversions) · **`competing_*`** = the **`industry_standard` (FIRST-TOUCH)** variant the client UI headline adds to default last-touch · **`conversions_assist_*`/`visits_assist`** = multi-touch assist · **`probattr_*`** = probabilistic. Each family carries its own `competing_` sub-variant.

## Joins & relationships
- **`campaign_id` -> `bronze.integrationprod.campaigns`** — partner grain **1 row per campaign, PK `campaign_id`** (filter `deleted=FALSE AND is_test=FALSE`). Safe 1:1 lookup, **no fan-out**; recovers `campaign_group_id`, `objective_id`, `funnel_level`, `channel_id`, `name`. There is no `silver.core.campaigns`.
- **`campaign_group_id` (via `campaigns`) -> `bronze.integrationprod.campaign_groups`** — 1 row per group; the client-visible "campaign." Group is full of test/archived junk — filter.
- **`advertiser_id` -> `bronze.integrationprod.advertisers`** — 1 row per advertiser, join on `advertiser_id` for `company_name` (`fpa_advertiser_verticals.advertiser_name` is unreliable / empty since 2025-12). `advertiser_id` is also present natively on this table, so most advertiser filtering needs no join.
- **`region` has NO numeric geo partner** — it is a state name string. It does **not** join to `summarydata.metros` (that dim is `metro_id` = Nielsen DMA code, a different geo level), nor to `geo.location_data.location_id`. Map to other geo systems by name if needed. **No DMA in this table.**
- **Sibling `sum_by_campaign_by_day`** (same measures, no `region`): summing this table's rows across `region` for a given `campaign_id`×`day` reproduces the campaign row — cross-validated on HLL reach (12,357,261 households both ways, 2026-07-10). Other same-column siblings: `sum_by_campaign_group_by_day`, `sum_by_advertiser_by_day`, `sum_by_creative_by_day` (all from 2024-01-01).

## Gotchas
- **`require_partition_filter = TRUE` (enforced on the physical table).** Any query without a `day` filter hard-errors. Always bound `day` — this also blocks `MIN/MAX(day)` scans (use `INFORMATION_SCHEMA.PARTITIONS` instead).
- **Row grain is campaign×region×day, NOT region×day** — ~200K rows/day (~17x the ~12K/day of `sum_by_campaign_by_day`, since each campaign fans across ~52 states). State-level numbers require `GROUP BY region` + `SUM` across campaigns, and `SELECT *` here is correspondingly ~3x costlier per day than the campaign rollup.
- **STATE, not DMA.** For per-DMA (Nielsen metro) delivery use `logdata.cost_impression_log.metro_id` (see the geo-bridge gotcha in `data_knowledge.md`); no DMA-grain fact table with history exists.
- **`region = '-1'`** is an unresolved-geo sentinel (167 rows / 6,552 imps on 2026-07-10) — exclude for clean state analysis.
- **Attribution variants are separate models — never SUM across families** (default / last_touch / last_tv_touch / competing / probattr / assist). Adding `last_tv_touch` to default/last_touch double-counts CTV-exposed conversions.
- **No `revenue` and no `conversions` column** — derive: visits = `views + clicks`, conversions = `view_conversions + click_conversions`, revenue = `*_order_value`.
- **HLL columns are BYTES sketches**, not integers — `HLL_COUNT.MERGE(...)`, never `SUM`.
- **Freshness — historically thrashy for the sum_by_* family; verify `max(day)`.** Prose logged a ~17-day lag on the campaign-family rollups (2026-05-01). **Live 2026-07-19: this table is fresh through the current day** (partition `20260719` had 199,167 rows; `20260720` is a small partial from the UTC/PST day boundary). Freshness has varied, so check `max(day)` before recent-window use; if lagging, fall back to the hour-grain `*_facts` tables.
- **`__NULL__` partition exists but is empty** (0 rows on 2026-07-19); range predicates on `day` exclude it anyway.

## Cost & partitioning notes
- **Partition:** DAY on `day`, `require_partition_filter = TRUE`. **Cluster:** none. **The one filter to always apply: a bounded `day` range** — it is mandatory and the only pruning lever. Physical backing table (2026-07-29): **176,379,036 rows / 276,371,728,861 bytes (~257.4 GiB)** (~188 GiB long-term), **941 dated partitions** (2024-01-01 -> 2026-07-29) + 1 empty `__NULL__` partition.
- **SELECT only the columns you need, and GROUP BY region for state rollups — the wide row + high row count make `SELECT *` ~26x costlier than a narrow projection.** Labeled dry-run figures (partition = 1 day, 2026-07-10, unless noted):
  - `SELECT *` (all 85 cols), 1 day: **306,750,403 bytes (~292.5 MB)**
  - 7 narrow cols (`advertiser_id, campaign_id, region, day, impressions, views, clicks`), 1 day: **11,847,900 bytes (~11.3 MB)** — ~25.9x cheaper than `SELECT *`
  - same 7 narrow cols, 60-day window (2026-05-11 -> 2026-07-10): **720,036,451 bytes (~686.7 MB)**
  - no `day` filter: **hard error** (partition-filter required)
- HLL reach/overlap over a multi-month window bills a few GB (the extra `region` fan-out means more BYTES sketch columns scanned than the campaign rollup); fine on reserved capacity.

## Example queries
```sql
-- State-level geo-mix for one advertiser over a YoY window (exclude '-1' unresolved)
SELECT s.region,
       SUM(s.impressions)                AS imps,
       SUM(s.views + s.clicks)           AS visits,
       SUM(s.media_spend + s.data_spend + s.platform_spend) AS spend,
       SAFE_DIVIDE(SUM(s.view_order_value + s.click_order_value),
                   SUM(s.media_spend + s.data_spend + s.platform_spend)) AS roas
FROM `summarydata.sum_by_region_by_day` s
WHERE s.day BETWEEN DATE '2025-01-01' AND DATE '2025-06-01'
  AND s.advertiser_id = <AID>
  AND s.region != '-1'
GROUP BY s.region
ORDER BY spend DESC;

-- Households reached per state in a window (HLL merge — never SUM(uniques))
SELECT region, HLL_COUNT.MERGE(uniques) AS households
FROM `summarydata.sum_by_region_by_day`
WHERE day BETWEEN DATE '2026-07-01' AND DATE '2026-07-10'
  AND region != '-1'
GROUP BY region
ORDER BY households DESC;
```
