# summarydata.ga_client_id_x_ip_map

## Purpose
Identity-resolution / IP-enrichment map bridging an advertiser's **first-party Google Analytics client_id** (the `_ga` cookie their GA/GA4 tag writes on their own site) to the **IP addresses MNTN observed** for that client_id. Given a `ga_client_id` (e.g. from advertiser-side GA conversion/measurement data) you recover the IP(s); given an IP you recover the GA client_ids seen on it. This is the join surface between the advertiser's own GA identity and MNTN's IP-keyed graph/serving world. Retains a **rolling ~90-day window** (see Gotchas).

## Grain & keys
- **Grain:** one row per **(advertiser_id, ga_client_id, ip)** — the triple is fully deduped. Verified on a 1% base-table sample: `COUNT(*)` = `COUNT(DISTINCT triple)` = 55,451,217 (exactly equal). `time` is therefore **not** part of the key — it is a single value carried per triple.
- **Key / join columns:** `(advertiser_id, ga_client_id)` is the advertiser-scoped GA identity; `ip` is the observed network address. A given `(advertiser_id, ga_client_id)` maps to ~1.009 IPs on average (55.45M triples vs 54.97M distinct (adv,cid) pairs in the sample → ~0.9% of client_ids have ≥2 IPs).

## Column meanings (only the non-obvious ones)
- **`advertiser_id`** — MNTN advertiser id (matches `advertisers.id` / integrationprod dims). Sample IDs (44112, 38695, 40887, 31357-range) are ordinary MNTN advertiser ids. 6,502 distinct advertisers in the 1% sample.
- **`ga_client_id`** — the advertiser's Google Analytics **client_id**, classic `_ga`-cookie format `{random}.{firstVisitEpochSeconds}` (e.g. `993157858.1780615881`). The suffix after the dot is **Unix SECONDS** of GA cookie creation / first visit — verified: `993157858.1780615881` → suffix decodes to 2026-06-04, matching that row's `time` of `2026-06-04 23:31:24`; `873490941.1784397195` → 2026-07-16, ~2 days before its `time` of `2026-07-18`. This id is **scoped to the advertiser's GA property**, so always key on `(advertiser_id, ga_client_id)`, never `ga_client_id` alone (2.88M client_ids in the sample appear under >1 advertiser).
- **`ip`** — IPv4 dotted-quad string (all sample rows IPv4). 23.9M distinct IPs in the 1% sample → heavily shared (households / CGNAT), so it is a low-cardinality-per-value join key. Not normalized; raw as observed.
- **`time`** — TIMESTAMP of the sighting recorded for that triple (native TIMESTAMP, **not** an epoch int; `time_unit: timestamp`). Because the triple is unique, `time` is a single aggregate value per (advertiser_id, ga_client_id, ip). Full range in the view is `2026-04-20 00:00:00` → `2026-07-18 23:59:59` (span 89 days); the floor sits on an exact midnight ~90 days before "today", i.e. a rolling-window cutoff, not a true data start.

## Joins & relationships
- **`advertiser_id` → `advertisers.id`** (integrationprod / `core` advertiser dim). Partner grain: **1 row per advertiser (dim)** → join is **N:1**, no fan-out. Filter the dim `deleted=FALSE AND is_test=FALSE`.
- **`ip` → any IP-keyed table** (visits / ui_visits `ip`, bidder events, graph_ips, cost/impression logs). Partner grain: those tables are **many rows per IP**, and this table is also **many rows per IP** → joining on `ip` alone is **N:N = severe fan-out**. Always constrain with `advertiser_id` (and ideally a `time` window on both sides) before an IP join, and pre-aggregate.
- **`ga_client_id` → advertiser first-party GA/GA4 data** (advertiser-side conversion/measurement carrying the `_ga` client_id). This is the intended bridge: resolve a GA client_id to MNTN IPs for measurement/attribution reconciliation. No single canonical BQ partner table confirmed live from this doc — join on `(advertiser_id, ga_client_id)`; partner grain depends on the source (typically N:N at raw event grain, so aggregate first).

## Gotchas
- **NO partition, NO clustering.** The physical table (`...__616882325`) has `timePartitioning=null`, `rangePartitioning=null`, `clustering=null`. A `time` filter does **not** prune bytes — verified: `SELECT time … WHERE time` for one day scans the **same 45.24 GB** as `SELECT time` with no filter. Every query full-scans the referenced columns; the only real cost lever is **column projection** (never `SELECT *`).
- **Rolling ~90-day window, not a table TTL.** `expirationTime` is null (no BQ TTL), but the data floor is a clean rolling ~90-day cutoff enforced by the SQLMesh model. Triples fall out of the window; do not treat the min `time` as an all-time history start.
- **`ga_client_id` is GA-property-scoped**, not a global person id. Key on `(advertiser_id, ga_client_id)`. Same physical browser on two advertisers' sites has two different client_ids; a client_id shared across advertisers is a collision / shared property, not the same user.
- **`ip` is shared** (households/CGNAT) — one IP → many client_ids, one client_id → occasionally many IPs. Treat as a fuzzy many-to-many bridge, never a 1:1 identity key.
- **`time` is a single carried timestamp per triple** (last/first sighting within the window), not an event log — you cannot count sightings from this table; it is deduped to the mapping grain.
- **View over a materialized physical table** — the SQLMesh physical is real here (numRows/numBytes populated, not the usual stale 0), so `bq show` metadata on `...__616882325` is trustworthy.

## Cost & partitioning notes
- **No partition to filter — projection is the only lever.** All GB figures below are `--dry_run` estimates, labeled by exact column set (bytes differ 3-7x by column):
  - `SELECT *` (all 4 cols): **304.9 GB** (= physical `numBytes` exactly; 283.999 GiB).
  - `SELECT ga_client_id` only: **129.0 GB** (largest column — long strings).
  - `SELECT ip` only: **85.4 GB**.
  - `SELECT time` only: **45.24 GB**; `SELECT advertiser_id` only: **45.24 GB** (both fixed 8-byte).
  - `SELECT time … WHERE time` for one day: **45.24 GB** — identical to no-filter → **confirms no partition pruning**.
- **Rule:** select only the columns you need; a `time` predicate reduces the *result rows* but not bytes scanned. To sample cheaply, `LIMIT` short-circuits reads (a `SELECT * LIMIT 15` read only 1.38M of 5.66B rows in S00) but on-demand *billed* bytes still report full — fine under the us-central1 reservation.
- **Scale:** ~5.66B rows / ~305 GB backing storage; runs on the `dw-main-bronze:us-central1.background-jobs` reservation (no on-demand dollars), but full-column scans still burn slot-time.

## Example queries
```sql
-- IPs MNTN observed for a specific advertiser's GA client_id (project only needed cols)
SELECT ip, `time`
FROM `summarydata.ga_client_id_x_ip_map`
WHERE advertiser_id = 44112
  AND ga_client_id = '993157858.1780615881';

-- Reverse: GA client_ids seen on an IP for one advertiser (constrain adv to bound fan-out)
SELECT ga_client_id, `time`
FROM `summarydata.ga_client_id_x_ip_map`
WHERE advertiser_id = 44112
  AND ip = '172.59.185.121';
```
