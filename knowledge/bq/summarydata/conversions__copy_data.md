# summarydata.conversions__copy_data

## Purpose
NOT a conversions fact table despite the name. This is the **audit/heartbeat row for a SQLMesh export job**. The physical model's own description: *"Exports the last 3 days of conversions to GCS as Parquet using an atomic staging-prefix swap."* Each time the model runs it writes the last 3 days of `summarydata.conversions` out to `gs://mntn-analytics-curated/bq-export/summarydata/conversions/` and stamps a single row here recording when it last ran and a human-readable status. Reach for it only to answer "did the conversions GCS export run, and when?" — never to read conversion events. For conversion data, query `summarydata.conversions` (or `ui_conversions`).

The `__copy_data` suffix is a naming convention for these GCS-export models: `summarydata.last_tv_touch_conversions__copy_data` is the identical pattern for the `last_tv_touch_conversions` export.

## Grain & keys
- **Grain:** one row, full stop. The physical table holds exactly one row that is overwritten each run (verified: `numRows = 1`).
- **Key(s) / join columns:** none. There is no entity key, no date partition, no join column — this is a status singleton, not a keyed fact. Do not join it to anything.

## Column meanings (only the non-obvious ones)
- **`last_run`** — native BigQuery `TIMESTAMP` (UTC), the wall-clock time the export model last completed. Verified value on 2026-07-19: `2026-07-20 05:25:19` UTC (the daily run had already fired for the UTC day). It is NOT an epoch integer — no UNIX_MICROS/MILLIS conversion needed; read it directly. Represents job completion time, not a data-coverage watermark (the data window is "last 3 days of conversions", computed at run time, not stored here).
- **`status`** — free-text human-readable status string, not an enum. Verified value: `"conversions exported to gs://mntn-analytics-curated/bq-export/summarydata/conversions/"`. It embeds the GCS destination prefix. Because it is a plain success sentence (not a code), do not parse it as a status enum; treat a fresh `last_run` + this string as "last export succeeded." There is no observed failure-code vocabulary — with a single overwritten row the domain is whatever the model last wrote.

## Joins & relationships
- **Source of the export:** `summarydata.conversions` (1:N conceptually — this heartbeat summarizes an export of many conversion rows). This table does NOT contain those rows; it only records that they were shipped. No key links the two.
- **Sibling pattern:** `summarydata.last_tv_touch_conversions__copy_data` — same single-row export-heartbeat shape for a different source view.
- **Fan-out risk:** none — it is a single row, so no join can fan out. The trap is the opposite: someone reads the *name* and joins it expecting conversion facts, getting one meaningless row.

## Gotchas
- **The name lies.** `conversions__copy_data` sounds like a staging copy of conversion events. It is an ops heartbeat with two columns and one row. The stable/source table is `summarydata.conversions`.
- **`last_run` is UTC and can read "ahead" of local date.** On a Pacific evening the value shows the next UTC calendar day (verified `2026-07-20 05:25` UTC while local date was 2026-07-19). Not a data error.
- **Single overwritten row = no history.** You cannot see prior runs or a run log here; only the most recent run survives. For run history use Airflow/SQLMesh run metadata, not this table.
- **`status` is prose, not a code.** Do not build alerting that string-equals a status enum; match on freshness of `last_run` plus substring, or move upstream to the orchestrator.
- Both columns are nullable in schema, but in practice both are populated after a successful run.
