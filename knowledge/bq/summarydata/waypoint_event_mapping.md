# summarydata.waypoint_event_mapping

## Purpose
Configuration/lookup for the **Waypoint** funnel product: per advertiser, it defines which visited-page **URL patterns** or **dataLayer variables** count as a named funnel **event**, and which ordered **stage group** that event sits in. Downstream Waypoint reporting matches a visit's URL / dataLayer against these `pattern` rows to tag the visit with `event_name` / `event_group`, giving each advertiser a custom multi-stage funnel (Site Entry -> ... -> Purchase). Reach for it when you need to know how an advertiser's on-site events map into funnel stages, or to enumerate which advertisers have Waypoint configured (only 15 do as of 2026-07-19).

Not a fact/log table — it is a small CDC-mirrored **dimension**. The silver view is a 1:1 rename+filter of the bronze Postgres-CDC source `bronze.integrationprod.attr_advertiser_waypoints_event_mapping` (note the dropped `attr_advertiser_` prefix and singularized `waypoint`), keeping only `deleted=FALSE` rows.

## Grain & keys
- **Grain:** one row per **waypoint pattern rule** = (advertiser_id, pattern) matched to an `event_name` within an ordered `event_group`. `deleted=FALSE` rows only.
- **Primary key:** `id` (source Postgres row id; 337 rows == 337 distinct `id`, verified 2026-07-19).
- **Natural key:** ~(advertiser_id, pattern) but NOT unique — 337 rows vs 328 distinct (advertiser_id,pattern) pairs; the same URL pattern can map to two event_names. `event_name` is many-patterns-to-one (304 distinct adv+event_name over 337 rows — e.g. "Campaign Used" is fed by `/campaign/*`, `/campaign/*/edit`, `/campaign/*/goalbudget`).
- **Join column:** `advertiser_id` -> advertiser dim (N pattern-rules per advertiser; ~22 avg, up to hundreds).

## Column meanings (only the non-obvious ones)
- **`pattern`** — the match string. When `pattern_type='url'` it is a **URL path glob** with `*` wildcards (e.g. `/campaign/*/edit`, `/myaccount/*`, `/sign-up`). When `pattern_type='dlv'` it is a **dataLayer variable** spec (GTM `dataLayer` key/value). maxLength 255 on source.
- **`pattern_type`** — detection method, ONLY two values (verified): `url` (match the visited page URL path; 304/337 rows, 14 advertisers) or `dlv` = **dataLayer variable** (GTM dataLayer match; 33/337 rows, 9 advertisers). maxLength 12.
- **`event_name`** — human label a matching visit is tagged as (e.g. "Login", "Campaign Used", "Purchase"). Always populated (0 NULL). Multiple `pattern` rows can share one `event_name`.
- **`event_group`** — the **funnel stage bucket** the event rolls into (e.g. "Site Entry", "Campaign Management", "Application Start", "Purchase"). Advertiser-specific free-text taxonomy — group labels are NOT a shared enum across advertisers. Always populated (0 NULL).
- **`event_group_order`** — ordinal **funnel depth** of the group: 1 = entry / top-of-funnel, larger = deeper toward conversion (observed 1..5). Assigned per advertiser, so the same-looking label can carry a different order across advertisers (e.g. "Application Started" seen at order 2, "Application Start" at 3).
- **`pattern_count`** — **ALWAYS NULL in this view.** The silver view hardcodes `CAST(NULL AS INT64)`; there is no matching column on the bronze source. Do not use it — it is a placeholder, not a match tally (0/337 non-null, verified).
- **`created_at`** — = source `inserted_at` (row insert TIMESTAMP). Renamed by the view.
- **`run_date`** — MISLEADING NAME: = source `updated_at` (last CDC row-update TIMESTAMP), NOT a batch/pipeline run date. Renamed by the view. Both `created_at` and `run_date` are true TIMESTAMPs (not epoch ints).

## Joins & relationships
- **`advertiser_id` -> `bronze.integrationprod.advertisers.id`** (or `silver.core.advertisers`) — dim is 1 row per advertiser; this table is **N:1** to advertiser. Joining advertisers -> waypoint_event_mapping **fans out ~22x** (avg pattern-rules per configured advertiser), up to hundreds for advertisers like 30506. Filter `advertisers.deleted=FALSE AND is_test=FALSE` on the dim side. Only 15 advertisers appear here.
- **Consumption side (Waypoint funnel product):** this is the config that classifies visits into funnel events. A visit's URL / dataLayer is matched against `pattern` (glob for `url`, key match for `dlv`) to assign `event_name` + `event_group` + `event_group_order`. Match is many-to-one per visit-path is possible (a URL can hit multiple patterns) — the mapping does not guarantee a single event per visit.
- **Sibling config:** `bronze.integrationprod.attr_advertiser_selective_performance_config` (per data_catalog.md) governs selective-performance event classification alongside this table. Both are advertiser-keyed pixel/event config, not fact tables.

## Gotchas
- **Not partitioned, not a log.** 337 rows total (view) / 473 in bronze; the ~136 hidden rows are `deleted=TRUE` soft-deletes the view drops via `coalesce(deleted,FALSE)=FALSE`. To audit deletes, query the bronze source directly.
- **`pattern_count` is a dead column** — always NULL (see column meanings). Never filter or aggregate on it.
- **`run_date` is `updated_at`, not a run date** — do not treat it as a batch anchor or partition proxy.
- **`event_group` / `event_group_order` are per-advertiser free text**, not a global funnel enum. Do not aggregate stage counts across advertisers assuming a shared taxonomy; the same order number means different things per advertiser.
- **(advertiser_id, pattern) is not unique** — dedup on `id` if you need a true PK; 9 duplicate adv+pattern pairs exist (same URL -> two event_names).
- **Tiny, low-coverage table** — only 15 advertisers configured. Absence of an advertiser here means Waypoint is unconfigured for them, not that they have no events.

## Cost & partitioning notes
- **No partition, no date filter needed** — the whole object is trivially small. Backing bronze storage is **70,858 bytes** (`bq show numBytes`, real logical storage). The silver physical is itself a VIEW (0 bytes) over the bronze TABLE.
- **`SELECT *` dry-run: 49,100 bytes** (~0.05 MB, all 10 cols; measured 2026-07-19). **Narrow `SELECT advertiser_id, event_name` dry-run: 14,126 bytes** (~0.014 MB, 2 cols). Both are far below the 10 MB billing floor — every query bills the ~0.01 GB minimum regardless.
- **One filter to apply:** `advertiser_id = <id>` (the only meaningful selector). Not for cost — for correctness/scope. Full scans are fine here.
- **cluster_by [id]** reflects the bronze physical clustering on `id`; irrelevant for pruning a 337-row view. `require_partition_filter=false`; no TTL (CDC-mirrored dim).

## Example queries
```sql
-- Full funnel config for one advertiser, in stage order
SELECT advertiser_id, event_group_order, event_group, event_name, pattern, pattern_type
FROM `summarydata.waypoint_event_mapping`
WHERE advertiser_id = 30506
ORDER BY event_group_order, event_group, event_name;

-- Which advertisers have Waypoint configured, and how deep their funnel goes
SELECT advertiser_id,
       COUNT(*) AS pattern_rules,
       COUNT(DISTINCT event_name) AS events,
       MAX(event_group_order) AS deepest_stage
FROM `summarydata.waypoint_event_mapping`
GROUP BY advertiser_id
ORDER BY pattern_rules DESC;
```
