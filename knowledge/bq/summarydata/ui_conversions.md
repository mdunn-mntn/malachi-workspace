# summarydata.ui_conversions

## Purpose
The canonical **post-attribution** conversion fact. Each row is one conversion that MNTN's
attribution logic credited to a campaign/impression. It is the table client-facing conversion &
revenue reporting is built on (e.g. `sum_by_campaign_by_day` conversion/revenue columns derive from
it). Reach for it when you need *attributed* conversions with the crediting impression, attribution
model, and dollar amount already joined — not raw pixel fires (that is `logdata.conversion_log` /
`bronze.raw`, which are un-attributed and un-filtered).

It is a pure VIEW (no physical rows of its own). Resolution chain:
`summarydata.ui_conversions` → hash view `summarydata__ui_conversions__1431780340` (the UNION+join
logic below) → two DAY-partitioned base TABLEs `summarydata__conversions__2893062813` (130.8M rows,
228.5 GB) and `summarydata__last_tv_touch_conversions__3221502556` (58.2M rows, 114.3 GB).

## Grain & keys
- **Grain:** one row per **attributed conversion event** (attribution output, not raw fire). The two
  UNION arms are **mutually exclusive** (see `source_type`), so a conversion appears in exactly one arm.
- **No single surrogate PK.** Identify a conversion by (`advertiser_id`, `guid`, `event_epoch`,
  `campaign_id`, `impression_id`). `order_id` is advertiser-supplied and often a constant/slug — not a
  unique transaction key.
- **Join columns:** `campaign_id`, `advertiser_id`, `impression_id` / `ad_served_id`,
  `attribution_model_id`, `guid`, `ip`.

## Column meanings (only the non-obvious ones)
- **`source_type`** — which attribution arm produced the row, **mutually exclusive**:
  - `'conversions'` — pixel/site conversions from campaigns that are **retargeting (`objective_id = 4`)
    OR prospecting campaign-groups enrolled in TVO prospecting attribution** (`tvo_prospecting_campaign_groups`).
  - `'last_tv_touch_conversions'` — **prospecting** conversions (`objective_id IN (1,5,6)`, NOT in a TVO
    group), credited via **CTV last-touch**.
- **`time` / `epoch`** — conversion attribution timestamp and its epoch. **`epoch = UNIX_MICROS(time)`
  exactly (microseconds; verified 100% on a 1-day sample).** `time` is the DAY **partition column**.
- **`event_time` / `event_epoch`** — the conversion event's own timestamp; `event_epoch` is its
  **microsecond** epoch (exact where `event_time` is non-null).
- **`impression_time` / `impression_epoch`** — the **crediting impression's** timestamp; `impression_epoch`
  is its **microsecond** epoch (exact where `impression_time` non-null; NULL when no crediting impression).
- **`elapsed_time`** (INTERVAL) — impression/touch → conversion **attribution lag**. It is the basis for
  `conversion_day` (view formula rounds it to whole days). `recency_elapsed_time` and
  `impression_elapsed_time` are related INTERVAL lags.
- **`conversion_day`** — attribution lag **in whole days**, `GREATEST(ceil(elapsed_time), 1)`, **clamped
  to 1–14; NULL when the lag exceeds the 14-day attribution window** (~22% NULL on the sampled day). Use it
  as the conversion-latency bucket, not a calendar day.
- **`attribution_model_type_id`** — domain observed `{1,2,3,4}`. Derived: when `attribution_model_id = 0`
  it is overridden to the **arm default** (`1` for the conversions arm, `2` for the TV-touch arm), else it
  comes from `core.attribution_models`. **`3`/`4` = competing** models.
- **`is_competing`** = `attribution_model_type_id IN (3,4)` (someone else also touched the user).
- **`is_pa`** = `pa_model_id IS NOT NULL` (probabilistic / predictive attribution row).
- **`conversion_assist`** — populated **only in the `'conversions'` arm**; **NULL** for every
  `'last_tv_touch_conversions'` row (set to NULL by the view). Do not read it as false on TV rows.
- **`first_touch_ad_served_id`** — populated **only in the `'last_tv_touch_conversions'` arm**; **always
  NULL in the `'conversions'` arm** (`CAST(NULL AS STRING)` in the view).
- **`conversion_type`** — STRING. **Raw NULL type is rendered as the string sentinel `'-101'`** — never
  filter `conversion_type IS NULL` here. Six platform sentinels exist (`-100/-101/-102/-105/-106/-107`);
  exclude them with `NOT REGEXP_CONTAINS(conversion_type, r'^-[0-9]+$')`. On the sampled day 87.5% of rows
  carried `'-101'`.
- **`order_amt`** (NUMERIC) — purchase amount, digit-extracted from the pixel `shoamt` param. **`0` OR
  `NULL` when the advertiser's pixel carries no dollar value** (~36% of top-50 advertisers report no
  revenue; on the sampled day zeros dominated with 0 nulls). There is **NO `order_amt_usd` column** in
  this view — use `order_amt` directly and gate revenue reads on `order_amt > 0`.
- **`channel_id` / `objective_id`** — pulled from the **`campaigns` join**, not the conversion row.
  `channel_id` 8 = CTV, 1 = display; `objective_id` 1/5/6 = prospecting, 4 = retargeting.
- **`from_verified_impression`** — **always TRUE** (view filter); **`domain`** — **always non-null** (view
  filter). Filtering on either inside ui_conversions is redundant.
- **`guid`** — user/device cookie ID (NOT a row id). **`ip`** = conversion IP; **`impression_ip`** = IP of
  the crediting impression.

## Joins & relationships
- **`campaigns` (via `campaign_id`)** — N:1 (many conversions : 1 campaign). `channel_id`, `objective_id`
  are **already embedded** from this join; re-joining `campaigns` adds nothing new and risks a dim mismatch.
- **`advertisers` (via `advertiser_id`)** — N:1. `advertiser_id` is trustworthy; join to
  `advertisers.company_name` for names.
- **`cost_impression_log` / `impression_log` (via `impression_id` or `ad_served_id`)** — the **crediting
  impression**, N:1, low fan-out (one credited impression per conversion). Filter both sides by their own
  partition.
- **`core.attribution_models` (via `attribution_model_id`)** — N:1, **already embedded** as
  `attribution_model_type_id` / `is_competing`.
- **`guid` / `ip` → log tables** — **high fan-out**, avoid; a user has many impressions/visits.

## Gotchas
- **This is a VIEW, not a table.** The hash physical is itself a view; partition/cluster/TTL live on the
  two base tables (`summarydata__conversions`, `summarydata__last_tv_touch_conversions`), both DAY-
  partitioned on `time`, unclustered, no TTL. Always `WHERE time BETWEEN ...`.
- **`order_amt`, never `order_amt_usd`** — the USD column does not exist here (prose said "NULL"; more
  precisely it is absent from this view). `0`/`NULL` both mean "no revenue"; filter `order_amt > 0`.
- **`conversion_type = '-101'` sentinel** = untyped conversion; six sentinels total — use the
  `^-[0-9]+$` regex, never a hard-coded pair, and never `IS NULL`.
- **`conversion_day` is NULL beyond 14 days** (~22% of rows) — a lag bucket, not a date.
- **Arm-specific NULLs:** `conversion_assist` is NULL on all TV-touch rows; `first_touch_ad_served_id` is
  NULL on all pixel-conversion rows. Split by `source_type` before reading either.
- **`attribution_model_id = 0` is treated as the arm default type** (1 or 2), a known business rule baked
  into the view.
- **Extreme `order_amt` is capped/dropped.** The attribution layer drops amounts somewhere between
  \$590,132 (kept) and \$5,736,771 (dropped) on top of silver's ~\$100M strip, so bronze ⊃ silver ⊃
  ui_conversions on extreme amounts (WGU Feb-2026 pentest lineage). Reconciling a revenue delta to bronze
  will not tie without accounting for both strips.
- **Late-arriving attribution:** a conversion can attribute to an impression up to 14 days earlier, so a
  `time`-partition slice can gain rows for prior days as attribution completes — the row's `time` is the
  attribution time, not the impression time.

## Cost & partitioning notes
- **The one filter to always apply: `WHERE time BETWEEN <start> AND <end>`** (DAY partition on both base
  tables). Not `require_partition_filter`, but omitting it full-scans both physicals.
- Dry-run, **same column set (`SELECT *`)**: full view **342.35 GB**; **1 day `2026-07-15` → 340.26 MB**
  (~1000x prune). Confirms `time` is the pruning column; `event_time`/`impression_time` do **not** prune.
- **View is join-heavy** (campaigns + tvo groups + attribution_models + a UNION): even a 1-day scan burns
  ~29–62 slot-seconds and reads far more rows than it returns. **Select only the columns you need**;
  avoid `SELECT *`.
- `approx_logical_bytes` **342.84 GB** = sum of the two base physicals (`numBytes`, all columns, pre-
  filter), **not** the filtered view output.

## Example queries
```sql
-- Attributed revenue by advertiser for a day, revenue-safe
SELECT advertiser_id, source_type,
       COUNT(*) AS conversions,
       COUNTIF(order_amt > 0) AS revenue_conversions,
       SUM(IF(order_amt > 0, order_amt, 0)) AS revenue
FROM `dw-main-silver.summarydata.ui_conversions`
WHERE time >= TIMESTAMP('2026-07-15') AND time < TIMESTAMP('2026-07-16')
GROUP BY 1, 2
ORDER BY revenue DESC;
```
