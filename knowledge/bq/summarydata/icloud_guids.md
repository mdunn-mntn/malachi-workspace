# summarydata.icloud_guids

## Purpose
The canonical reference map of Apple **iCloud Private Relay** egress IPv4 addresses to a stable
MNTN-derived GUID token. iCloud Private Relay is Apple's pseudo-VPN: it hides the real device IP
behind a rotating pool of shared egress IPs (Apple / Cloudflare / Fastly infrastructure). This view
gives each known relay egress IP a deterministic GUID so relay traffic can be identified and handled
consistently across the identity/attribution path. Reach for it to (a) enumerate the set of relay
egress IPv4s MNTN currently recognizes, or (b) translate a relay IP to its paired GUID (or vice
versa). It is a small, static lookup — not an event log.

## Grain & keys
- **Grain:** one row per `(guid, ip)` pair. Empirically a **strict 1:1 bijection** — distinct `guid`
  count == distinct `ip` count == row count (120,667). Verified over the full 164-day raw history:
  `max_guids_per_ip = 1` and `max_ips_per_guid = 1`. Every relay IP has exactly one GUID and every
  GUID has exactly one relay IP.
- **Key(s) / join columns:** either column is a unique key. Join on `ip` (relay egress IPv4) to
  reach event/log tables; `guid` is the GUID-keyed identifier used on the deterministic
  attribution path (GUID match / GUID blocklist).

## Column meanings (only the non-obvious ones)
- **`guid`** — an MNTN-derived identifier for the relay IP. Sampled values are all **UUID version 3**
  (name-based MD5; the 3rd group's leading nibble is `3`, e.g. `79c4b189-ccd4-3357-a0bb-7f3201f12d7a`),
  which is why it is a deterministic 1:1 function of the relay IP rather than a device/household GUID
  observed in traffic. Treat it as a pseudonymized token for the relay egress IP, **not** as a real
  per-device or per-household graph GUID.
- **`ip`** — the iCloud Private Relay **egress** IPv4 (shared infrastructure, e.g. `172.224–226.x`
  Apple, `104.28.x` Cloudflare, `146.75.x` Fastly). 100% IPv4 in the view (0 IPv6 rows, despite the
  sibling `icloud_ipv6` table existing). This is the relay's public-facing IP, **not** the end user's
  device IP — the real device IP is never exposed by Private Relay.

## Joins & relationships
- **`summarydata.icloud_ipv4` / `icloud_ipv6`** (sibling reference tables): the raw relay IP lists.
  `icloud_ipv4` is a **flat single-column (`ip`) list — 120,667 rows / 120,667 distinct IPs, exactly
  this view's IP set** (verified live 2026-07-19), *not* an IP-range list. `icloud_ipv6` is the
  range-carrying sibling (columns `ip`, `prefix`, `first_8_bits`, `first_16_bits`, `network`); this
  view is 100% IPv4, so ipv6 is not part of its content. Those lists are used by Targeting to
  **exclude iCloud relay IPs from bidding so they never enter MembershipDB** (see `data_catalog.md`
  §`icloud_ipv4_ips`). This table adds the GUID pairing on top of the IP list.
- **`logdata.icloud_vv_log`** (→ `icloud_vv`): the separate view-through event stream for iCloud
  relay traffic (Comprehensive Reporting / Probabilistic Attribution). Join `icloud_guids.ip` to a VV
  table's relay IP is 1:N (one relay IP → many events) — **fan-out on the event side**, never on this
  side (this table is unique per ip and per guid, so it can only de-duplicate a join, never multiply).
- **Deterministic attribution path** (`data_knowledge.md` VVS decision tree): GUID match
  (`attribution_model_id=1`) and GUID blocklist (`segmentation.guid_blocklist`) operate on GUID-keyed
  identifiers; the IP-match step includes an "iCloud IPv4 filter." This view is the reference that
  ties those two keys (relay IP ↔ GUID) together.
- **Fan-out summary:** joining FROM this table is safe (unique on both columns). Any multiplication in
  a join comes entirely from the partner (event/log) side.

## Gotchas
- **NOT the "guids per iCloud IP" weighting source.** Comprehensive Reporting estimates iCloud
  attributable volume by weighting on *how many device GUIDs sit behind a relay IP* observed in
  traffic (`data_knowledge.md`, ~1% lift post-fix). This table is **1:1** (one GUID per relay IP), so
  that per-IP GUID count must come from observed VV traffic, **not** from here. Do not use this table
  to count devices behind a relay IP.
- **`guid` is synthetic, not a graph/household GUID.** It is a v3 hash tied to the relay IP. Do not
  join it to real device/household GUIDs expecting a match, and do not treat two rows sharing nothing
  as "different households" — the whole table is one relay-IP↔token map.
- **Raw daily snapshots barely change over time, but a snapshot is NOT the full mapping.** Each daily
  raw snapshot is ~105.8K rows and drifts only ~178 rows over ~6 months (105,638 on 2026-01-28 →
  105,816 on 2026-07-18). *However*, the all-time distinct set (120,667) is ~14% larger than one
  snapshot (105,816), and that surplus is a **source-composition gap, not time drift**: the legacy
  curated union source (`analytics_curated.icloud_guids`, 120,482 distinct pairs) contributes **14,851
  pairs absent from the current raw snapshot**, while raw adds only **185** pairs beyond curated
  (verified live 2026-07-19). So `MAX(ds)` staleness is genuinely irrelevant, but a single `ds`
  snapshot silently omits ~12% of the pairs the view recognizes — see the Cost section for which
  source reproduces the full set.
- **Two-source view.** The view is `SELECT DISTINCT guid, ip` over a `UNION ALL` of the SQLMesh raw
  model (`raw__icloud_guids_raw`, 17.3M rows across 164 daily `ds` snapshots) and a legacy curated
  table (`analytics_curated.icloud_guids`, 120,482 rows). DISTINCT collapses all of that to 120,667
  pairs. Physical `numRows` on the SQLMesh wrapper reads 0 (view) — ignore it.

## Cost & partitioning notes
- **The view has no usable partition filter.** `summarydata.icloud_guids` does **not** expose `ds` —
  it is `SELECT DISTINCT` over the full raw history, so any query against the view scans the whole
  thing. Dry-run **SELECT * (guid+ip): 937,497,166 bytes ≈ 894 MiB** — and selecting a single column
  is the *same* 894 MiB because the DISTINCT must read both columns regardless. There is no cheaper
  column projection at the view level.
- **To prune, hit the raw physical directly with `ds`.** On
  `dw-main-bronze.sqlmesh__raw.raw__icloud_guids_raw__3794008824`:
  - no filter, `guid+ip`: 931,031,690 bytes ≈ **888 MiB** (dry-run).
  - `WHERE ds = '2026-07-15'`, `guid` only: 4,867,536 bytes ≈ **4.64 MiB** (dry-run) — one full daily
    snapshot. Filtering `ds` prunes ~888 MiB → ~5 MiB.
  - `ds` (DATE, DAY partition) spans 2026-01-28 → 2026-07-18, 164 partitions = 164 `version` values
    (1:1 ds↔version, one full snapshot per day). Use `ds = 'YYYY-MM-DD'` for a single snapshot.
- **Choosing a cheap source — and what each one omits.** No cheap path reproduces the view's full
  120,667 pairs exactly (all dry-runs 2026-07-19):
  - **View** (`summarydata.icloud_guids`) — the only exact full set (120,667) but always ~894 MiB
    (cannot prune). Use only when you truly need every pair and cost is not a concern.
  - **Legacy curated table** `dw-main-bronze.analytics_curated.icloud_guids` (120,482 distinct pairs,
    **6,465,476 bytes ≈ 6.17 MiB** full scan) — the **near-complete, cheapest** source, only **185
    pairs short** of the view. Best default for "current mapping" work.
  - **A single `ds` raw snapshot** (~105.8K rows; guid+ip 6,528,779 bytes ≈ 6.23 MiB, guid-only
    4,867,536 bytes ≈ 4.64 MiB) — **omits ~14,851 pairs (~12%)** of the view's set (they live only in
    the curated source). Do **not** treat a lone snapshot as the full mapping; use it only when a
    partial, freshest-day list is acceptable.
  - **Avoid the view for large/repeated jobs** since it cannot prune; prefer the curated table.
- `approx_logical_bytes` (1,214,901,726) = sum of the two UNION-source physical `numBytes`
  (raw 1,208,436,250 + curated 6,465,476). Cluster: none on either source.

## Example queries
```sql
-- Near-complete current mapping, cheapest (~6.2 MiB): the legacy curated table.
-- 120,482 pairs — 185 short of the view; best default (see Cost notes).
SELECT guid, ip FROM `dw-main-bronze.analytics_curated.icloud_guids`

-- Complete set: all 120,667 pairs via the view — scans ~894 MiB, cannot prune.
SELECT guid, ip FROM `summarydata.icloud_guids`

-- One freshest-day raw snapshot (~6.2 MiB) — PARTIAL: ~106K of the 120.7K pairs (~12% omitted).
-- Use a LITERAL ds (bump the date). A dynamic MAX(ds) subquery does NOT prune — it scans ~1.02 GiB.
SELECT guid, ip
FROM `dw-main-bronze.sqlmesh__raw.raw__icloud_guids_raw__3794008824`
WHERE ds = '2026-07-18'

-- Is a given IP an iCloud Private Relay egress IP? (returns its token if so)
-- Query the view (or curated table) — a single snapshot misses ~12% of relay IPs.
SELECT guid FROM `summarydata.icloud_guids` WHERE ip = '172.225.12.50'
```

## View definition
```sql
-- summarydata.icloud_guids  →  physical wrapper resolves to:
SELECT DISTINCT combined_guids.guid AS guid, combined_guids.ip AS ip
FROM (
  SELECT guid, ip FROM `dw-main-bronze`.`sqlmesh__raw`.`raw__icloud_guids_raw__3794008824`
  UNION ALL
  SELECT guid, ip FROM `dw-main-bronze`.`analytics_curated`.`icloud_guids`
) AS combined_guids
```
