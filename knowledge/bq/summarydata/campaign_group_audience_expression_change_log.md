# summarydata.campaign_group_audience_expression_change_log

## Purpose
Audit/change log that captures **every save of a campaign group's audience expression** — the targeting definition (interest data sources + category ids, plus geo include/exclude/radii). Reach for it to reconstruct the targeting-edit history of a campaign group: *when* the audience was changed, *by whom* (`user_id`), and the *exact* targeting JSON *before* and *after* the change. Typical uses: auditing who narrowed/expanded targeting, correlating a delivery or performance shift with a targeting edit, and reconstructing what a campaign group's audience expression was at a point in time.

## Grain & keys
- **Grain:** one row per **saved audience-expression edit event** for a campaign group. Every row in this view is `change_id = 25` / `change_type = "Audience Expression"` — this view carries only that one change type (the generic change-log schema's other slots are unused here).
- **No surrogate primary key.** `change_id` is a constant *type code* (25), **not** a per-row id. `(time, campaign_group_id, entity_id)` is **not unique**: 63,985 rows vs 48,733 distinct tuples (~24% share a tuple — multiple saves within the same one-second `time` resolution, or repeated saves). De-dup on `(time, campaign_group_id, entity_id, current_value)` if you need distinct states.
- **Natural keys / FKs:** `advertiser_id`, `campaign_group_id`, `entity_id` (the audience), `user_id`. Distinct counts: 5,440 advertisers · 17,067 campaign groups · 3,476 users.

## Column meanings (only the non-obvious ones)
- **time** — TIMESTAMP (UTC — native BQ timestamp, *not* an INT epoch) of the save. History floor = `2025-01-01 00:56:38` (backfill start, not the true beginning of targeting edits); max tracks ~now. Second-level resolution.
- **entity_type** — always `"audience_id"` in this view (single-valued). **entity_id** — the audience identifier being edited (STRING). **entity_text** — the human-readable audience/campaign name (e.g. `"TELEVISION Campaign"`, `"Safe driving campaign"`). See Joins for a caveat on resolving `entity_id`.
- **entity_id_2 / entity_text_2 / entity_type_2** — **100% NULL** in this view. Secondary-entity slots from the generic change-log schema; unused for audience-expression changes. Don't write logic expecting them.
- **change_id** — constant `25` = the code for "Audience Expression". **change_type** — its label. Both are single-valued across all 63,985 rows; they identify the change *type*, not the row.
- **prior_value / current_value** — the audience expression JSON **before / after** the edit. Shape: `{"interest":{"include":[{"or":[{"data_source_id":N,"cats":[...]}]}],"exclude":[]},"geo":{"include":[...],"exclude":[],"radii_include":[],"radii_exclude":[]}}`. `data_source_id` values observed: 9, 13, 19, 35 (DS13/DS19 = MNTN Match components; DS9, DS35 = others). `geo.include` = DMA/geo-segment ids. **prior_value is always populated** (0 NULLs) and **never equals current_value** (0 unchanged rows) — every row is a genuine state change. These two JSON blobs are ~99.8% of the table's bytes.
- **user_id** — the platform user who saved the edit. **NULL for 6,664 rows (~10.4%)** = system/automated edits not attributed to a UI user.
- **advertiser_id / campaign_group_id** — owning advertiser and campaign group (INT64).

## Joins & relationships
This change log is the **MANY side** of every relationship — joining it to a dimension is **N:1** (no fan-out from the dim side; fan-out risk arises only if you join it to another log/fact).
- **campaign_group_id → campaign_group dim** (1 row per campaign group): **N:1, safe.** There is no `core.campaign_groups` view; use the integrationprod campaign_group dimension (filter `deleted=FALSE AND is_test=FALSE`).
- **advertiser_id → advertisers dim:** **N:1, safe.**
- **user_id → users dim:** **N:1**; the ~10% NULL (system edits) won't join.
- **entity_id (entity_type='audience_id') → an audience** — nominally `core.audiences.audience_id`, **BUT a live spot-check did not cleanly resolve**: advertiser 69062 is entirely absent from `core.audiences`, and only 1/15 recent `entity_id`s matched. Likely a product / id-space difference (e.g. Select / self-serve auto-generated campaigns — names like "TELEVISION Campaign") or `is_test`/`deleted` filtering on the `core.audiences` view. **Verify the id-space before relying on this join.** You usually don't need it: `entity_text` already carries the audience name, and `current_value` carries the full expression JSON (mirrors `audiences.expression`), so a change is fully readable without any join.

## Gotchas
- **No partition — filtering `time` does NOT prune** (full 325 MB scan either way; confirmed by dry-run diff below). The table is small (~0.3 GB) so full scans are cheap, but the cost lever is **column projection, not a WHERE**: `prior_value`/`current_value` are ~99.8% of the bytes (one narrow column = 0.5 MB vs 325 MB for `SELECT *`).
- **Not deduplicated** on `(time, campaign_group_id, entity_id)` — ~24% of rows share a tuple. Dedupe if you need one row per distinct state.
- **Single-valued columns:** `change_id`(=25), `change_type`(="Audience Expression"), `entity_type`(="audience_id") are constants; the `*_2` columns are all NULL. Don't build branching logic expecting variety.
- **SQLMesh full-refresh table:** the physical resolves to a single TABLE (not a UNION), `creationTime == lastModifiedTime`, and `numRows`/`numBytes` are **real here** (63,985 / 325,050,014 B) — not the SQLMesh 0 placeholder. No TTL.
- **time is UTC**; the max value runs ahead of local wall-clock.
- **No prose oracle** existed in `data_catalog.md` / `data_knowledge.md` — this doc was enriched from the live schema + sampled data alone.

## Cost & partitioning notes
- **Partition: none. Cluster: none. TTL: none** (full-refresh). Confirmed via `bq show` (timePartitioning/rangePartitioning/clustering all null) and a dry-run diff.
- **The one thing to always do:** since there is no partition to prune, avoid `SELECT *` — project only the columns you need (skip `prior_value`/`current_value` unless you need the JSON). A `time` range bounds rows logically but does **not** reduce bytes scanned.
- **Byte figures — all from `bq query --dry_run`, labeled by column set (only same-column-set figures are comparable):**
  - `SELECT *` (all 14 cols), full table → **325,050,014 B (~0.303 GiB)** — equals backing `numBytes`.
  - `SELECT * WHERE time >= '2026-07-18'` → **325,050,014 B** — *identical* to full → confirms **no partition pruning**.
  - `SELECT change_id` only, full table → **511,880 B (~0.5 MB)** → the two JSON value columns dominate table size.

## Example queries
```sql
-- Full targeting-edit history for one campaign group (project only what you need)
SELECT time, user_id, entity_text, prior_value, current_value
FROM `summarydata.campaign_group_audience_expression_change_log`
WHERE campaign_group_id = 130517
ORDER BY time;

-- Most recent audience-expression change per campaign group (deduped)
SELECT campaign_group_id, entity_id, current_value, time
FROM (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY campaign_group_id, entity_id ORDER BY time DESC
  ) rn
  FROM `summarydata.campaign_group_audience_expression_change_log`
  WHERE time >= TIMESTAMP('2026-07-01')
)
WHERE rn = 1;
```
