# summarydata.spend_facts

## Purpose
The hourly spend fact table — pre-aggregated ad spend broken out by campaign, geo, device, domain,
and supply vendor. Reach for it whenever you need spend (media / data / platform / advertiser-billed
CTV) sliced below the day, or by geo/device/domain/supply_vendor dimensions that the daily agg tables
(`aggregates.agg__daily_sum_by_campaign`, `summarydata.sum_by_campaign_by_day`) don't carry. For plain
daily campaign totals the agg tables are cheaper; use `spend_facts` for sub-day granularity or the extra
dimensions. It is one of the three fact tables (`impression_facts` + `visit_facts` + `spend_facts`) that
the SQLMesh `all_facts` model FULL-OUTER-JOINs on 18 dimension keys — so for spend *alongside*
impressions/visits/conversions, query `all_facts`, not a hand-rolled join of the fact tables.

## Grain & keys
- **Grain:** one row per **hour × the full 17-dimension tuple** (verified 2026-07-19: for 2026-07-10,
  `COUNT(*)` = `COUNT(DISTINCT <all 17 dims>)` = 54,037,713 exactly — no duplicate dimension combos).
  The 17 grain columns are: `hour`, `advertiser_id`, `campaign_group_id`, `campaign_id`, `channel_id`,
  `objective_id`, `group_id`, `creative_id`, `private_marketplace_id`, `country`, `metro_id`, `region`,
  `city`, `postal_code`, `domain`, `supply_vendor`, `device_type`. The remaining 5 columns
  (`media_spend`, `data_spend`, `platform_spend`, `ctv_spend`, `unlinked_spend`) are the additive
  measures.
- **Partition/cluster keys:** partitioned DAY on `hour`; clustered on `advertiser_id`, `campaign_id`.
- **Join columns:** `advertiser_id` → advertisers, `campaign_id` → campaigns, `campaign_group_id` →
  campaign_groups, `creative_id` → creatives, `group_id` → creative_groups (all N:1 into the dim, safe).

## Column meanings (only the non-obvious ones)
- **`hour`** — DATETIME (NOT TIMESTAMP; prose in `data_catalog.md` said TIMESTAMP — live wins, it is
  DATETIME with no timezone offset, e.g. `2026-07-10T13:00:00`). It is the **hour bucket** (top of the
  hour), and it is the DAY partition key. Because it is a bare DATETIME there is no tz on the value —
  treat it as the reporting-layer wall-clock hour, don't apply a tz conversion blindly.
- **The five spend measures are all whole USD, NOT micros** (verified 2026-07-19: sample rows show
  `media_spend` ≈ 58.27, `ctv_spend` ≈ 61.47 — dollars-and-cents, never ÷1e6). Stored BIGNUMERIC. All
  five are additive across rows (safe to `SUM`). No negative `media_spend` observed.
- **`media_spend`** — raw media cost (paid to the supply vendor for the impression), USD.
- **`data_spend`** — 3P data/audience cost, USD. Effectively **CTV-only**: ~0 on display rows
  (channel_id=1). On CTV it runs ~10% of `media_spend`.
- **`platform_spend`** — MNTN platform fee, USD. Non-zero on both CTV and display.
- **`ctv_spend`** — the **advertiser-billed CTV total = `media_spend` + `data_spend` + `platform_spend`**
  (verified 2026-07-19: the identity is exact — for 2026-07-10 CTV rows, `SUM(media+data+platform)` =
  `SUM(ctv_spend)` = 1,114,646.43 to the cent, 0 rows break it). It is the full CPM the advertiser pays
  for a CTV impression. **Zero for all display rows** — it is not a generic "billed" column, it is the
  CTV rollup only.
- **`unlinked_spend`** — spend not linked to a served/attributed unit. **Empirically ~always 0**
  (0 non-zero rows across all of 2026-07-10). Treat as a legacy/edge measure; don't build logic on it.
- **`channel_id`** — 8 = CTV (Beeswax Television), 1 = display. CTV rows carry `ctv_spend`/`data_spend`;
  display rows do not.
- **`objective_id`** — UNRELIABLE as a funnel-stage indicator (workspace-wide gotcha); for stage use
  `campaigns.funnel_level`, not this column.
- **`device_type`** — STRING enum already resolved (e.g. `MOBILE`, `SET_TOP_BOX`) — the silver layer
  joins the bronze INT code to the label. **Two wrinkles a naive `GROUP BY device_type` must handle
  (verified 2026-07-10):** (1) redundant near-duplicate labels for the same device — `PC` (7.96M rows)
  alongside `PERSONAL_COMPUTER` (85), and `MOBILE` (9.42M) alongside `PHONE` (5,645) — collapse these
  before bucketing or they split into separate rows; (2) a rare unresolved sentinel `-1` (77 rows) when
  the bronze code didn't map. CTV itself splits across `SET_TOP_BOX` (22.1M) and `CONNECTED_TV` (13.1M).
- **Geo dims** (`country`, `metro_id`, `region`, `city`, `postal_code`) — human-readable strings
  (`country` = "United States", not a code) except `metro_id` (INT). **Not always resolved:** the same
  77 unresolved-sentinel rows carry `country` = "-4" (verified 2026-07-10 — the `-4`/`device_type=-1`
  cohort is a single group; prevalence is trivial, 77/54M, but guard against numeric-string geo values).

## Joins & relationships
- **`all_facts` (`summarydata.all_facts`) is built FROM this table** — it FULL-OUTER-JOINs
  `impression_facts` + `visit_facts` + `spend_facts` on **18 dimension keys** (the 17 grain dims here +
  `pa_model_id`, which spend_facts lacks — it enters as a constant `-1` on the spend side), then UNIONs
  conversion/site rows. Verified 2026-07-19 against the SQLMesh `all_facts` model source
  (`models/dw-main-silver/summarydata/all_facts.sql`, owner `ber`): the `FULL OUTER JOIN` ON clause
  enumerates exactly these 18 keys — `hour`, `advertiser_id`, `campaign_group_id`, `campaign_id`,
  `channel_id`, `objective_id`, `group_id`, `creative_id`, `private_marketplace_id`, `country`,
  `metro_id`, `region`, `city`, `postal_code`, `domain`, `supply_vendor`, `device_type`, `pa_model_id`.
  (The model's own header comment and `data_catalog.md` say "19 keys" — an off-by-one; the SQL ON clause
  is 18.) If you need spend next to reach/visits/conversions, query `all_facts` — do NOT hand-join the
  fact tables yourself.
- **Dim joins are N:1 (safe, no fan-out):** `advertiser_id` → `bronze.integrationprod.advertisers`
  (grain: 1 row/advertiser), `campaign_id` → `campaigns`, `campaign_group_id` → `campaign_groups`,
  `creative_id` → `core_creatives`, `group_id` → `core_creative_groups`. Each partner is one row per
  entity, so a lookup join does not multiply spend rows. Filter dims `deleted=FALSE AND is_test=FALSE`.
- **Fan-out WARNING — never join spend_facts directly to `visit_facts`/`conversion_facts`/
  `impression_facts` on a *partial* key.** Those are sibling hourly fact tables at the same grain
  (spend_facts on 17 dims; the join adds `pa_model_id`); a join on fewer than all 18 keys fans out
  combinatorially (many-to-many within an hour × advertiser). The correct pre-joined artifact is
  `all_facts` (joined on all 18 keys — the key set is verified from the model source, see Joins above).
  Use `all_facts`; don't partial-join the fact tables yourself.

## Gotchas
- **`hour` is DATETIME, not TIMESTAMP** — prose in `data_catalog.md` was stale (said TIMESTAMP). Bare
  DATETIME = no timezone; don't `TIMESTAMP_*`-convert it. Partition filters are plain DATETIME/date
  string comparisons: `WHERE hour >= '2026-07-10' AND hour < '2026-07-11'`.
- **Physical retains only ~4.5 months** (verified 2026-07-19 via INFORMATION_SCHEMA.PARTITIONS: 141
  partitions, `2026-03-01` → `2026-07-19`), even though there is **no BQ partition-expiration TTL**
  (`expirationMs = null`, `require_partition_filter = false`). This is the SQLMesh incremental window,
  not a fixed TTL. For spend history older than that window, use the daily agg tables
  (`summarydata.sum_by_campaign_by_day` goes back to 2024-01-01).
- **The physical hash rotates on every SQLMesh rebuild.** `data_catalog.md` recorded
  `...__1266598596`; the live view now resolves to `...__1528080727`. **Always query the stable view name
  `summarydata.spend_facts`** — never hardcode a `sqlmesh__summarydata.summarydata__spend_facts__<hash>`
  reference, it will 404 after the next rebuild.
- **`ctv_spend` is CTV-only** — 0 for display. Don't treat it as a universal "amount billed"; the
  display advertiser-billed total is not carried as a single rollup column here.
- **`data_spend`/`ctv_spend` ≈ 0 on display**, `unlinked_spend` ≈ 0 everywhere — guard against dividing
  by these or reading meaning into their zeros.
- Spend is **whole USD** — do not ÷1e6 (a recurring mistake because many raw MNTN cost columns are
  micros; these facts are not).

## Cost & partitioning notes
- **The one filter to always apply: a `hour` range.** It is the DAY partition column, confirmed
  empirically (2026-07-19, all figures via `bq_run.sh --dry_run`):
  - `SELECT media_spend` (1 narrow col), **hour-filtered to 1 day**: **2.16 GB** (2,161,508,520 bytes).
  - `SELECT media_spend` (same 1 col), **all-time, no hour filter**: **253.3 GB** (253,320,098,080 bytes)
    — the hour filter prunes ~117×. → **`hour` is the partition.**
  - `SELECT media_spend` (same 1 col), filter on `advertiser_id` only (a cluster key, **no** hour
    filter): **60.66 GB** (60,656,174,960 bytes) — clustering alone only cuts ~4× off the 253 GB
    all-time scan; it does NOT substitute for the partition filter.
  - `SELECT *` (all 22 cols), **1 day**: **18.17 GB** (18,173,609,514 bytes) — ~8.4× the single-column
    day (2.16 GB). **Avoid `SELECT *`; project only the columns you need.**
- Actual billed (post-run, for reference): a 10-column channel aggregate over 1 day billed **8.86 GB**;
  a full-row-width single-day scan (`SELECT *` + FARM_FINGERPRINT grain check) billed **16.93 GB**.
- Physical backing = a single TABLE (no UNION): 7,916,253,065 rows / 2,651,157,636,275 bytes (2.65 TB
  logical) via `bq show`.

## Example queries
```sql
-- Daily media/data/platform/ctv spend for one advertiser (always range-filter hour, project columns)
SELECT DATE(hour) AS d,
       SUM(media_spend)    AS media,
       SUM(data_spend)     AS data,
       SUM(platform_spend) AS platform,
       SUM(ctv_spend)      AS ctv_billed   -- advertiser-billed CTV = media+data+platform (CTV rows only)
FROM `dw-main-silver.summarydata.spend_facts`
WHERE hour >= '2026-07-01' AND hour < '2026-07-11'
  AND advertiser_id = 31357            -- cluster key: further prunes within the partitions
GROUP BY d
ORDER BY d;
```
