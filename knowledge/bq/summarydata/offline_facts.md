# summarydata.offline_facts

## Purpose
Hourly, fully-dimensioned aggregate of **offline / uploaded (CRM) conversions** — conversions that arrive in batch uploads (order files, CRM matches) rather than through the pixel. Reach for it to get offline-conversion counts and revenue (`order_amt`) sliced by advertiser / campaign / geo / creative / supply, at hour grain. It is the offline-conversion counterpart to the pixel-based `conversion_facts` / `all_facts` fact tables.

It is a pure **VIEW** (no physical rows of its own) built as a `UNION ALL` of two aggregation branches over the same source `summarydata.offline_conversions`:
- **primary branch** — buckets each conversion by its **conversion time** (`hourtz(l.time, advertiser.time_zone)`); populates `offline_primary_*`, zeros the cohort/secondary columns.
- **cohort branch** — buckets the **same conversions** by their **impression time** (`hourtz(l.impression_time, advertiser.time_zone)`); populates `cohort_offline_primary_*`, zeros the primary/secondary columns.

Both branches only keep rows where `partner_id_list LIKE '%1%'` and `domain IS NOT NULL`. Note `LIKE '%1%'` is a raw **substring** match on the list-valued `partner_id_list` string — it retains any row whose partner-id list *contains the character* `1` anywhere (`1`, `10`, `11`, `21`, `100`, …), not strictly partner id 1; do not read it as a partner-id = 1 selector.

## Grain & keys
- **Grain:** one row per **branch** (conversion-time vs impression-time) × `hour` × the full dimension tuple: `advertiser_id, campaign_group_id, campaign_id, channel_id, objective_id, group_id, creative_id, private_marketplace_id, country, metro_id, region, city, postal_code, domain, supply_vendor, device_type, conversion_type, conversion_source_id, upload_id` (`run_time` and the CTV-join key `s.publisher_type_id` also flow through the GROUP BY — both branches' outer `GROUP BY` end `..., l.upload_id, s.publisher_type_id`). `publisher_type_id` is functionally determined by `domain` (0 domains map to >1 publisher_type_id in the deduped `v_ctv_sites` subquery), so it adds no rows and the LEFT JOIN never fans out. ~2.59M rows total; hour range 2023-04-12 → 2026-07-17.
- **Key(s) / join columns:** no surrogate key — the composite of the dimensions above (plus the branch discriminator) is the natural key. Join to dims via `advertiser_id`, `campaign_id`, `campaign_group_id`, `creative_id`.
- **Branch discriminator:** a row is a **primary** row iff `offline_primary_conversions > 0`, a **cohort** row iff `cohort_offline_primary_conversions > 0`. The two are mutually exclusive per row (verified: 0 rows have both populated).

## Column meanings (only the non-obvious ones)
- **`hour`** (DATETIME) — the aggregation bucket, in the **advertiser's local wall clock** (`hourtz(time, advertisers.time_zone)`), truncated to the hour — **NOT UTC**. Its meaning depends on the branch: on primary rows it is the **conversion** hour; on cohort rows it is the **impression/exposure** hour. It is a computed column, **not a physical partition** (see Cost).
- **`run_time`** (TIMESTAMP) — the ETL batch run/load timestamp for the offline-conversion feed. Processing metadata, **not** the conversion event time; tracks to ~now (max 2026-07-17 18:39). It is in the GROUP BY, so the same conversion reloaded in a later batch can produce distinct `run_time` rows.
- **`-1` / `'-1'` sentinels** — `advertiser_id, campaign_group_id, campaign_id, channel_id, objective_id, group_id, creative_id, private_marketplace_id, country, metro_id, region, city, postal_code, supply_vendor, device_type, upload_id` are all `COALESCE(..., -1 / '-1')` — a value of `-1` (INT dims) or `'-1'` (STRING dims: `private_marketplace_id, country, region, city, postal_code, supply_vendor, device_type`) means **unknown / unmatched**, not a real id. (In current data these sentinels are not materializing — every row has real ids — but the logic is live.)
- **`device_type`** — STRING here (silver-side), not the bronze INT encoding.
- **`domain`** — for CTV (`channel_id = 8`) it is normalized through `to_domain()` using the CTV publisher type; otherwise the raw domain. Source rows with `domain IS NULL` are **dropped entirely** by the view's WHERE clause.
- **`conversion_type`** (STRING) — offline conversion event-type label (10 distinct values observed). **Not** coalesced → can be NULL.
- **`conversion_source_id`** (INT) — source-system id for the offline conversion. **Not** coalesced → can be NULL.
- **`upload_id`** — identifies the **batch upload** the conversion arrived in; this is the mechanism by which offline data enters (1,518 distinct uploads observed). Coalesced to `-1` when unknown.
- **`offline_primary_conversions` / `offline_primary_order_value`** — `COUNT(1)` and `SUM(order_amt)` of offline conversions bucketed by **conversion hour**. Populated **only on primary-branch rows**; hardcoded 0 on cohort rows. `order_value` is NUMERIC in the conversion's `order_curr` (order currency — not guaranteed USD-normalized).
- **`cohort_offline_primary_conversions` / `cohort_offline_primary_order_value`** — the **same conversions and revenue**, bucketed by **impression hour** instead. Populated **only on cohort-branch rows**. Grand totals are identical to the primary columns (both = 1,523,003 conversions / $681,475,316.7) — this is by construction, NOT additive.
- **`offline_secondary_conversions` / `offline_secondary_order_value`** — **hardcoded 0 in the current view; always zero.** Reserved/unused columns; do not treat a 0 as "no secondary conversions" — the view never populates them.

## Joins & relationships
Base lineage: `offline_facts` (VIEW) → `summarydata.offline_conversions` (VIEW = `summarydata_archive.offline_conversions` archive TABLE `UNION ALL` `sqlmesh__ber_stg.ber_stg__offline__conversions_final` staging TABLE, anti-joined for dedup). Offline conversions land through the **BER (backend-reporting) offline pipeline** plus a historical archive.

Dimension joins baked into the view:
- **`advertiser_id` → `silver.public.advertisers`** — 1:1; **INNER JOIN** (conversions for an unknown advertiser are dropped). Supplies `time_zone` for the `hourtz()` bucketing.
- **`campaign_id` → campaigns** — many-rows:1 dim, no fan-out. Supplies `campaign_group_id`, `channel_id`, `objective_id`. NOTE: the primary branch joins `silver.public.campaigns`, the cohort branch joins `bronze.integrationprod.public_campaigns` — a minor source difference between branches.
- **`domain` → `sqlmesh__ctv.v_ctv_sites`** (block IS FALSE, deduped) — supplies `publisher_type_id` for CTV domain normalization; LEFT JOIN, no fan-out.

Consuming / sibling tables: this is the offline-conversion sibling of the pixel fact tables (`conversion_facts`, `visit_facts`, `impression_facts`, `spend_facts`, `all_facts`). When you **union or join offline_facts to any other fact table, first restrict to ONE branch** (`WHERE offline_primary_conversions > 0` OR the cohort predicate) — otherwise every conversion is counted twice. Joins on `advertiser_id` / `campaign_id` to dimension tables are 1:1-safe and do not fan out.

## Gotchas
- **DOUBLE-COUNTED BY DESIGN — never sum primary + cohort.** Every conversion appears in two rows: a primary row (bucketed by conversion time) and a cohort row (bucketed by impression time). Verified: `SUM(offline_primary_conversions) = SUM(cohort_offline_primary_conversions) = 1,523,003` and the order values match to the cent. Pick exactly one branch for any total.
- **`offline_secondary_*` are always 0** — hardcoded in the view; not a data-quality signal, just unused columns.
- **`hour` is advertiser-local wall clock, not UTC** — it is `hourtz(time, advertiser.time_zone)`. Do not assume UTC and do not compare it hour-for-hour against a UTC-bucketed table.
- **`hour` is computed, not a partition** — filtering `WHERE hour >= '...'` does **not** reduce bytes scanned (see Cost). It also cannot be predicate-pushed to the base tables (timezone offset), so the whole base is scanned regardless.
- **`run_time` in the grain** — a re-run/re-load of the same source conversions with a new `run_time` yields distinct rows; aggregate away `run_time` if you want a stable per-conversion total across loads.
- **`order_value` currency** — `order_amt` is summed in the conversion's own `order_curr`; treat as reported currency, not guaranteed USD.
- **INNER JOIN on advertisers** — conversions whose `advertiser_id` is missing from `public.advertisers` never appear. Also `partner_id_list LIKE '%1%'` and `domain IS NOT NULL` silently drop source rows.

## Cost & partitioning notes
- **No partition, no cluster, no TTL.** The physical resolves to a VIEW over two **unpartitioned** physical TABLEs: `summarydata_archive.offline_conversions` (2,959,066 rows / 1,374,170,480 bytes) and `sqlmesh__ber_stg.ber_stg__offline__conversions_final` (707,427 rows / 324,591,765 bytes). `approx_logical_bytes` = their sum = **1,698,762,245 bytes (~1.70 GB)**.
- **Cost is fixed at ~1.05 GB per query regardless of filter or column projection.** Verified by `--dry_run` (all three shapes measured 2026-07-19, each identical to the byte). The exact figure **drifts upward daily** as the two unpartitioned base tables grow — read it as approximate (was 1,127,353,569 B on 2026-07-19 skeleton pass; 1,127,354,912 B on the same day's re-run):
  - `SELECT advertiser_id, offline_primary_conversions` — no filter → **~1,127,354,912 bytes** upper bound.
  - Same two cols **`WHERE hour >= DATETIME '2026-07-01'`** → **~1,127,354,912 bytes** — the `hour` filter prunes **nothing** (unpartitioned + computed column).
  - `SELECT *` no filter → **~1,127,354,912 bytes** — identical (the view's base scan is fixed by its GROUP BY, so top-level projection doesn't change it). Actual run: 1.05 GB processed / 1.05 GB billed, ~3.7s wall.
- **There is no cost lever inside this view** — you cannot cheapen it with a WHERE clause. It is small (~1 GB), so this is usually fine. **Do NOT try to save bytes by hitting the base staging table `ber_stg.offline__conversions_final` directly as if it were a smaller slice of the same data — it is not.** Staging is only the live BER-pipeline feed (707,427 rows, `time` 2024-08 → present) and **omits the entire archive** `summarydata_archive.offline_conversions` (2,959,066 rows, `time` 2023-04 → 2026-03 — the bulk of offline-conversion history). Because `offline_conversions` = archive `UNION ALL` staging(`NOT EXISTS` anti-join dedup), querying staging alone silently returns recent-only, incomplete results (≈19% of the pre-dedup source), not a cheaper slice of the same population.
- **The one filter to always apply is a CORRECTNESS filter, not a cost filter:** restrict to a single branch — `WHERE offline_primary_conversions > 0` (conversion-time view) or the cohort predicate — to avoid the built-in double count.

## Example queries
```sql
-- Offline conversions + revenue by advertiser, CONVERSION-TIME view (primary branch)
SELECT advertiser_id,
       SUM(offline_primary_conversions)  AS offline_conversions,
       SUM(offline_primary_order_value)  AS offline_order_value
FROM `summarydata.offline_facts`
WHERE offline_primary_conversions > 0            -- pick ONE branch; hour filter does not prune
  AND hour >= DATETIME '2026-01-01'
GROUP BY advertiser_id
ORDER BY offline_order_value DESC;

-- Same conversions bucketed by IMPRESSION hour (cohort branch) — do NOT add to the above
SELECT hour,
       SUM(cohort_offline_primary_conversions) AS conversions
FROM `summarydata.offline_facts`
WHERE cohort_offline_primary_conversions > 0
GROUP BY hour
ORDER BY hour DESC;
```
