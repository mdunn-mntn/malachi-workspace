# summarydata.guid_ip_log_visitors

## Purpose
Distilled **guid <-> ip visitor mapping**, scoped per advertiser, derived from `logdata.guid_log`
page-view events. Reach for it to answer "which IPs did this visitor GUID appear on for advertiser X?"
(or the reverse) at a cookie/device grain — it is the identity-bridge layer between the raw page-view
log (`guid_log`) and the IP identity graph (`tpa.graph_ips*`). One row per visitor sighting: an advertiser's
pixel/site was hit by a tracked GUID resolving to an IP. Same column shape as `guid_log` but slimmed to the
identity-relevant fields (time, epoch, advertiser_id, ip, guid) plus two first-seen flags. Fresh through the
current day (max `time` = 2026-07-19 22:59:59 at sync); ~120-day TTL means no history beyond ~4 months —
reach for `guid_log` (or its GCS archive) for longer lookback.

## Grain & keys
- **Grain:** event-grain — 1 row per **advertiser_id x ip x guid** sighting, NOT deduped. On 2026-07-15:
  308.4M rows but only **84.2M distinct `(advertiser_id, ip, guid)` tuples (27%)** → avg **~3.7 rows per
  tuple per day**; **~73% of rows are intra-day duplicate tuples**, so `(advertiser_id, ip, guid)` is NOT a
  unique key. `COUNT(*)` over-counts distinct visitor mappings ~3.7x — always `DISTINCT` / `ROW_NUMBER` when
  you need one row per visitor. Same day: 7,166 distinct advertisers, 51.2M distinct guids, 32.3M distinct ips.
- **Key(s) / join columns:** `guid` (browser-cookie id, device-level — not household) and `ip` bridge identity; `advertiser_id` scopes
  the mapping (a GUID<->IP pair is recorded per advertiser). `time` is the partition key.

## Column meanings (only the non-obvious ones)
- **time** — event (page-view) timestamp; the DAY partition key. Fresh through the current day.
- **epoch** — INT64, **MICROSECONDS**: `epoch = UNIX_MICROS(time)` exactly, full sub-second precision
  (verified 2026-07-15: epoch `1784089276966000` = `UNIX_MICROS('2026-07-15 04:21:16.966')`). The parent
  `logdata.guid_log.epoch` is **also microseconds** (verified: guid_log `epoch = UNIX_MICROS(time)`, sub-second
  precision, `eq_secs=false` — the `data_catalog.md` guid_log entry labeling it "Seconds" is wrong; there is
  no seconds-vs-micros drift). `TIMESTAMP_SECONDS(epoch)` overflows (the micros value is far past
  `TIMESTAMP_SECONDS`'s year-9999 range) — never use it; just use `time`.
- **advertiser_id** — the advertiser whose pixel/site the sighting belongs to; the GUID<->IP mapping is
  recorded per advertiser (join to `advertisers.id`).
- **ip** — resolved visitor IP (STRING, IPv4/IPv6). No separate `ip_raw`/`original_ip` here (unlike
  `guid_log`), so this is already the resolved IP.
- **guid** — browser-cookie id (device-level), UUID-formatted. ~60% are RFC-4122 **version-3**
  (MD5-namespaced) UUIDs (185.7M / 308.4M on 2026-07-15 carry the `3` version nibble); the rest are other
  UUID versions, so "MD5-derived" is not universal. The **blank / no-cookie sentinel** is the v3 UUID
  `d41d8cd9-8f00-3204-a980-0998ecf8427e` (28,151 rows on 2026-07-15) — the empty-string MD5 with the version
  nibble forced to `3` and the variant nibble to `a`; treat it as "no/blank cookie." Note: the **raw**
  empty-string MD5 `d41d8cd9-8f00-b204-e980-0998ecf8427e` returns **0 rows** — do not filter on it.
- **is_new** — BOOL, **never NULL** (0 nulls on the sample day). First cookie/first sighting of this GUID
  for this advertiser (client-JS-pixel first-seen flag, same semantics as `guid_log.is_new`). ~9% true
  (28.8M / 308M on 2026-07-15).
- **is_new_gl** — BOOL, **nullable**. `_gl` = guid_log: whether this is a *new* GUID in `guid_log`
  (first-page-view lineage). Distribution 2026-07-15: false 202M (66%), true 50.7M (16%), **NULL 55.5M (18%)**.
  Treat NULL as "lineage undeterminable / no guid_log match," NOT as false.

## Joins & relationships
- **`logdata.guid_log` (source / parent, 1:N)** — this table is distilled from guid_log page-view events.
  guid_log is the fuller event log (much larger — ~471 TiB, DAY-partitioned on `time`, `epoch` also
  **microseconds** = `UNIX_MICROS(time)`, same unit as here). Join on
  `guid` + `ip` + `advertiser_id` (+ date). guid_log fans out (multiple page views per GUID/day); for
  identity mapping prefer this table. Do not expect a clean 1:1 either direction.
- **`tpa.graph_ips*` (IP identity graph, IP-keyed, heavy fan-out)** — join `guid_ip_log_visitors.ip` →
  the graph's IP key to expand IP -> household / co-located IPs. Self-joins and IP->IP bridging are
  expensive and CGNAT-limited; there is **no IP->IP bridging in BQ** for general use (external only).
- **`bronze.integrationprod.advertisers` (dim, 1 row per advertiser)** — `advertiser_id` -> `advertisers.id`;
  filter `deleted=FALSE AND is_test=FALSE`. This is the fan-out dimension (~7.2K advertisers/day).
- **Fan-out warning:** joining to any per-IP or per-guid table multiplies against ~32M distinct IPs / ~51M
  distinct GUIDs *per day*. Always filter `time` to a narrow window first, and dedup `(advertiser_id, ip,
  guid)` before joining if you need one row per visitor.

## Gotchas
- **epoch is MICROSECONDS** (`= UNIX_MICROS(time)`) — and so is the parent `guid_log` (both micros; the
  `data_catalog.md` guid_log entry labeling epoch "Seconds" is wrong). Just use `time`.
- **Not deduped (event-grain):** only ~27% of daily rows are distinct `(advertiser_id, ip, guid)` tuples —
  ~73% are intra-day duplicates (avg ~3.7 rows/tuple on 2026-07-15). `COUNT(*)` over-counts distinct visitor
  mappings ~3.7x; `DISTINCT`/`ROW_NUMBER` when you need a unique key.
- **`is_new_gl` is nullable (~18% NULL)** — NULL means lineage unknown, not "not new." `is_new` is never NULL.
- **120-day TTL** (partition expiration 10,368,000,000 ms). No history beyond ~120 days (floor ~2026-03-21 at
  sync). For longer lookback use `logdata.guid_log` or the `gs://mntn-data-archive-prod/guid_log/` GCS archive.
- **Huge:** ~30B rows / 2.37 TB. A one-day filter is mandatory; even single-partition `COUNT(DISTINCT ...)`
  is slot-heavy — a one-day 5-way `COUNT(DISTINCT)` measured **5.2K slot-seconds / 20.4 GB** (2026-07-15; see
  Observed cost). A single `COUNT(DISTINCT)` runs a few thousand slot-seconds.
- **Stale physical hash in prose:** `data_catalog.md` lists the physical as
  `...__guid_ip_log_visitors__2172532229`; the live view resolves to `...__51612752` (SQLMesh rebuilt).

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE time >= 'YYYY-MM-DD' AND time < 'YYYY-MM-DD'` (DAY partition on
  `time`). `require_partition_filter` is not enforced, but never omit it.
- Dry-run figures (each labeled with its column set — only same-column-set figures are comparable):
  - `SELECT ip, guid` **one day** = **18.85 GB** vs **no filter** same 2 cols = **1595.6 GB** → the `time`
    filter prunes ~85x (empirical partition confirmation).
  - `SELECT *` **one day** = **24.3 GB**.
  - `approx_logical_bytes` (full physical, all 7 cols) = **2.37 TB** (`bq show` numBytes = 2,369,984,051,773).
- Cluster: none — no secondary pruning; a `guid`/`ip`/`advertiser_id` predicate still scans the whole
  day partition.
