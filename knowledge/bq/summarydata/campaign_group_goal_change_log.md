# summarydata.campaign_group_goal_change_log

## Purpose
Audit trail of every change to a campaign group's **performance goal** (the bid-optimization target — CPV / CPA / ROAS / CostPerCompletedView). Reach for it to answer "when did this campaign group's goal change, from what to what, and who changed it" — e.g. to align a goal edit with a delivery/pacing/ROAS shift, or to detect goal churn ahead of an incrementality/pacing analysis. It is a slice of a generic per-entity change-log source, pre-filtered to goal changes on campaign groups (`change_type='Goal'`, `change_id=36`).

## Grain & keys
- **Grain:** one row per campaign-group goal change **event** (an edit). 61,514 rows over 49,428 distinct campaign groups — most (40,981) have exactly one goal set; a long tail have 2-15+ successive changes.
- **Key(s) / join columns:** `campaign_group_id` (the entity that changed), `advertiser_id` (owner), `user_id` (who made the change). There is **no per-row surrogate key** — `change_id` is a constant type-code (=36), not a row id. Identify a specific change by `(campaign_group_id, time)`.

## Column meanings (only the non-obvious ones)
- **`time`** — when the goal change was recorded. Native `TIMESTAMP` stored in **UTC** (max value runs ~a day ahead of Pacific "today", confirming UTC, not local). This is the de-facto event/sort key; the table is **not** partitioned on it.
- **`prior_value` / `current_value`** — the goal before and after the edit, as human-readable strings of the form `"<GoalType>: <numeric target>"`, e.g. `"CostPerCompletedView: 0.03"`, `"CostPerVisit: 12.5"`, `"CPA: 40"`, `"ROAS: 3"`. The sentinel **`"No Goal"`** means no goal was set — as `prior_value` it marks a first-time goal (most common prior), as `current_value` it marks a goal being cleared (718 rows). `prior_value` is never NULL. Goal-type distribution in `current_value`: CostPerVisit 22,203 · CostPerCompletedView 16,871 · CPA 11,889 · ROAS 9,833 · No Goal 718.
- **`user_id`** — the user who made the change; NULL in only 6 rows (system/automated edits).
- **`change_type`** — **constant `"Goal"`** for every row in this view (it is pre-filtered to goal changes). Not a discriminator here.
- **`change_id`** — **constant `36`** (the source change-log's type code for "Goal"), NOT a row identifier. Do not use it as a key or a join column.
- **`entity_id`, `entity_text`, `entity_type`, `entity_id_2`, `entity_text_2`, `entity_type_2`** — **always NULL** in this view (61,514/61,514). They are generic slots inherited from the shared change-log schema and carry no data for goal changes; the changed entity is `campaign_group_id` and the payload is `prior_value`/`current_value`. Ignore them.

## Joins & relationships
- **`campaign_group_id` → `campaign_groups`** (bronze.integrationprod / silver.core dim; grain = 1 row per campaign group). Relationship is **N:1 from this log to the dim** — a single campaign group can have many goal-change rows, so joining the dim onto this log **fans out** to N rows per group. `campaign_groups.product_id` distinguishes PTV(1)/Select(2)/QuickFrame(3) if you need product context. Filter dims `deleted=FALSE AND is_test=FALSE`.
- **`advertiser_id` → `advertisers`** (dim; grain = 1 per advertiser). 1 advertiser : N change rows (14,261 distinct advertisers). Join for `company_name` (note `fpa_advertiser_verticals.advertiser_name` is unreliable/empty — use `advertisers.company_name`).
- **`user_id` → users dim** (bronze.integrationprod users). 1 user : N change rows. Use only for attribution of who edited the goal.
- No natural join to fact/delivery tables — to correlate a goal change with performance, window facts (e.g. `summarydata.sum_by_campaign*`) on `campaign_group_id` around `time`.

## Gotchas
- **This is a pre-filtered slice, not the full change-log.** Only goal changes (`change_type='Goal'` / `change_id=36`) are present; those two columns are constants and the six `entity_*` columns are entirely NULL. Don't expect other change types here.
- **No surrogate row key.** `change_id` is a type code (36), not a unique id. De-dup / identify by `(campaign_group_id, time)`.
- **Goal values are strings, not numbers.** Parse `current_value` as `SPLIT(current_value, ": ")` → `[type, target]` and `SAFE_CAST` the target; watch the `"No Goal"` sentinel (no colon).
- **`time` is UTC.** Convert (`DATETIME(time, "America/Los_Angeles")`) before aligning to Pacific business days, or recent edits appear on "tomorrow."
- **History floor 2024-01-01** (matches the SQLMesh summarydata build floor); no rows before that even though real goal edits predate it.
- **No TTL** — rows are retained (physical `expirationTime` unset); the table only grows and is tiny.

## Cost & partitioning notes
- **No partition, no clustering, no TTL** (confirmed on the physical `...__1718841263`: `timePartitioning`/`rangePartitioning`/`clustering` all null, `expirationTime` null). The whole table is ~**4.5 MiB** / 61,514 rows, so scans are effectively free and there is **no partition column to prune on** — a `WHERE time BETWEEN …` filter is semantic only (does not reduce bytes scanned).
- **The one filter to always apply:** none is needed for cost; add a `time` range only to bound the result set. Prefer selecting named columns over `SELECT *` out of habit, but the difference is small here.
- **Measured (dry-run, 2026-07-19):** `SELECT *` = 4,695,267 bytes (~4.48 MiB, all 14 columns); `SELECT time` alone = 492,112 bytes (~0.47 MiB, one column). `approx_logical_bytes` (4,695,267) = physical `numBytes` from `bq show`.

## Example queries
```sql
-- Goal history for one campaign group, oldest → newest
SELECT time, prior_value, current_value, user_id
FROM `summarydata.campaign_group_goal_change_log`
WHERE campaign_group_id = 130967
ORDER BY time;

-- Parse the goal type + numeric target of the latest goal per campaign group
SELECT campaign_group_id,
       ARRAY_AGG(STRUCT(time, current_value) ORDER BY time DESC LIMIT 1)[OFFSET(0)].* 
FROM `summarydata.campaign_group_goal_change_log`
WHERE current_value != 'No Goal'
GROUP BY campaign_group_id;
```
