# summarydata.budget_changes_in_ramp

## Purpose
A live snapshot of every campaign group that is **currently in a budget ramp** — i.e. its most recent budget change is still inside the change's attribution window. For each such campaign group it exposes the single latest change plus the ramp window `[budget_ramp_start_time, budget_ramp_end_time]` and the daily/flight budget before and after. Reach for it to answer "which campaign groups changed budget recently and are still ramping" and "when does this group's ramp end" — pacing / delivery-monitoring, not full audit history. For the complete change log use the base `summarydata.budget_changes`.

## Grain & keys
- **Grain:** one row per `campaign_group_id` — the single most-recent budget change (`ROW_NUMBER() OVER (PARTITION BY campaign_group_id ORDER BY change_time DESC) = 1`) that still falls inside the ramp window. Verified live: `n_rows = n_distinct(campaign_group_id) = n_distinct(change_id) = 1778`.
- **Key(s) / join columns:** `campaign_group_id` (grain key), `change_id` (equally unique here — PK of the underlying change event), `advertiser_id`, `flight_id`.

## Column meanings (only the non-obvious ones)
- **change_time** — TIMESTAMP, **UTC**, when the budget change was made. This is the partition column of the base table.
- **change_epoch** — INT64, **SECONDS** since Unix epoch. Resolved: `change_epoch = UNIX_SECONDS(change_time)` exactly (diff = 0). Redundant numeric form of `change_time`; carries no extra information.
- **budget_change_time_local** / **budget_ramp_start_time** — DATETIME, `change_time` converted to the **advertiser's local timezone** (`public.timetz(change_time, advertisers.time_zone)`). The two columns are identical (the ramp starts at the moment of the change). Wall-clock local time with **no tz offset stored** — do not treat as UTC.
- **budget_ramp_end_time** — DATETIME, `(change_time + attribution_window)` in advertiser-local time. End of the ramp / attribution window.
- **new_daily_budget** / **prior_daily_budget** — NUMERIC, daily budget after / before the change (account currency).
- **budget_change_percentage** — NUMERIC, a **FRACTION, not a percent**, despite the name: `SAFE_DIVIDE(new_daily_budget - prior_daily_budget, prior_daily_budget)`. e.g. `0.677` = +67.7%, `-0.95` = -95%, `10.4` = +1044%. **NULL when `prior_daily_budget = 0`** (SAFE_DIVIDE); currently 0 NULLs in live data. Multiply by 100 for a percent.
- **budget_change_type_id** / **budget_change_type** — enum from `integrationprod.core_budget_change_types`. Full live domain: **1 = increase, 2 = decrease** (only two values).
- **flight_change_type_id** — INT64 raw id, **no lookup table exists**. Empirically: **1 = new flight** (`prior_flight_budget` always NULL, 1604 rows), **2 = flight budget modification** (`prior_flight_budget` usually populated, 174 rows). `new_flight_budget` is always populated for both.
- **new_flight_budget** / **prior_flight_budget** — NUMERIC, flight-level (whole-flight) budget after / before. `prior_flight_budget` is NULL for `flight_change_type_id = 1` (a newly created flight has no prior).
- **attribution_window** — INTERVAL, Postgres-style rendering (`"0-0 44 0:0:0"` = 44 days). The advertiser/campaign attribution window that defines the ramp length. Varies **~10 to ~135 days** across campaign groups (58 distinct values live).
- **attribution_window_text** — STRING cast of `attribution_window` (same rendering).
- **attribution_window_seconds** — INT64 length of the window in seconds (44 days = 3,801,600).
- **batch_time** — TIMESTAMP, the **ETL batch load time**, not the change time. Can be **after** `change_time` (pipeline lag — e.g. change at 07-19 13:58, batch at 07-20 00:11). Do not use for time windowing.

## Joins & relationships
This view is a 3-table join already resolved inside the view definition:
- **Base `summarydata.budget_changes`** (physical TABLE, partitioned `change_time` DAY, ~66,305 rows) — **1:N** historically (many changes per campaign group over time); this view collapses it to **1 row per campaign_group_id** via the QUALIFY, keeping only the latest change inside the ramp window.
- **`public.advertisers`** — **INNER JOIN on `advertiser_id`**, 1:1 dim (one row per advertiser). Supplies `time_zone` for the local-time columns. No fan-out. Because it is an INNER join, a change whose `advertiser_id` is absent from `advertisers` is **silently dropped**.
- **`integrationprod.core_budget_change_types`** — **INNER JOIN on `budget_change_type_id`**, 1:1 lookup (2 rows). Supplies the `budget_change_type` name. Also an INNER join.
- **Downstream keys for your own joins:** `campaign_group_id` → `public.campaign_groups` (1:1 dim), `flight_id` → flights dim (1:1), `advertiser_id` → `public.advertisers` (1:1). All dim joins — no fan-out from this side.

## Gotchas
- **Not a history table — a rolling live snapshot.** Only the *latest* change per campaign group, and only if it is still inside its ramp window: base filter is `change_time >= GREATEST(CURRENT_DATE - 61 days, CURRENT_DATE - attribution_window - 1 day)`. Superseded / older changes and expired ramps are excluded. For full audit history use `summarydata.budget_changes`.
- **61-day hard floor:** no row can be older than 61 days regardless of a longer attribution window — the `GREATEST(..., -61 DAY)` caps lookback.
- **`budget_change_percentage` is a fraction, not a percent** (see column meanings) — a classic off-by-100 trap.
- **Two INNER joins** (`advertisers`, `core_budget_change_types`) can silently drop rows if the dimension is missing the key. Row counts here may be lower than in the base.
- **Local-time columns are DATETIME wall-clock in the advertiser's tz**, no offset stored — never compare them to a UTC `change_time` without accounting for the tz.
- **`batch_time` reflects pipeline load, not the change**, and can post-date `change_time`; do not window on it.
- `budget_change_type` domain is only `increase`/`decrease`; `flight_change_type_id` (1=new flight, 2=modified) has **no name column** in the view.

## Cost & partitioning notes
- Object is a VIEW → base physical `summarydata.budget_changes` is partitioned by **`change_time` DAY**, **no clustering, no TTL, no require-partition-filter** (base ~66,305 rows / ~9,641,920 bytes = ~9.6 MB backing storage).
- **Partition pruning does NOT help this view:** its internal `WHERE` uses a dynamic `change_time` predicate, so BigQuery reads the **full base every time** (932 partitions, 66,305 rows scanned). Filtering `change_time` on the outer query does not reduce the scan.
- Cost is trivial regardless. Dry-run (labeled by column set): **`SELECT *` (all 21 cols) = 10,120,245 bytes (~10.1 MB; 0.009 GB processed / 0.029 GB billed tier 1)**; **one narrow column `campaign_group_id` = 3,490,136 bytes (~3.5 MB)**. The two figures share no column set beyond the join overhead, so treat them as separate baselines, not a prune diff.
- **The one filter to always apply:** none is required here (whole thing is <11 MB) — just `SELECT` only the columns you need. If you need large historical scans, query the base `summarydata.budget_changes` instead and filter its `change_time` partition.

## Example queries
```sql
-- campaign groups currently ramping a budget increase, soonest-ending ramp first
SELECT campaign_group_id, advertiser_id, budget_change_type,
       prior_daily_budget, new_daily_budget,
       ROUND(budget_change_percentage * 100, 1) AS pct_change,
       budget_ramp_start_time, budget_ramp_end_time
FROM `summarydata.budget_changes_in_ramp`
WHERE budget_change_type = 'increase'
ORDER BY budget_ramp_end_time ASC
```
