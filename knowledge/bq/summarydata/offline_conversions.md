# summarydata.offline_conversions

## Purpose
Offline / CRM-uploaded conversion events (e.g. in-store purchases, phone-call conversions, CRM order feeds an advertiser uploads) that have been **matched back to a MNTN ad exposure**. Reach for this when a conversion did **not** fire the web pixel — it happened offline and was reconciled to an impression/click via an identity match (`guid` / `ip` / hashed PII key). Complements the online pixel tables (`summarydata.visits` / `ui_conversions`). Only **161 advertisers** currently use it. Data is fresh — max `time`/`run_time` = 2026-07-17 (a normal ~1-2 day ETL lag behind today); the April-2026 staleness once noted in `data_knowledge.md` is now RESOLVED by the live pipeline (see Gotchas).

## Grain & keys
- **Grain:** one row per matched offline conversion event, but **no column tuple is unique.** `COUNT(DISTINCT (advertiser_id, COALESCE(hashed_values_key,hashed_value), time, order_id, order_amt))` ≈ **3.0–3.2M** (depends on NULL handling) vs `COUNT(*)` = **3,640,756** — i.e. ~11–17% of rows share a composite tuple, because the view's `NOT EXISTS` only dedups live-vs-archive, not within either branch. Do **not** treat any tuple as a primary key; joins on it can fan out and double-count.
- **Timestamps do NOT collapse.** `time` = the conversion moment; `event_time`/`impression_time` = the attributed **exposure**, which is earlier than `time` by hours to weeks (e.g. conversion 2026-07-17 15:09 attributed to impression 2026-05-27 08:59). `time = event_time` on only 2,333 rows (0.06% — the 2023 micros sliver); the two exposure timestamps equal each other (`event_time = impression_time` on 100% of rows). Use `time` (not `event_time`) as the conversion instant, and `time − impression_time` for exposure-to-conversion latency.
- **Dedup predicate (from the view's own `NOT EXISTS`; live `bq` branch anti-joined against `arch`ive):** `arch.advertiser_id = bq.advertiser_id AND arch.hashed_value = COALESCE(bq.hashed_values_key, bq.hashed_value) AND arch.time = bq.time AND COALESCE(arch.order_id,'') = COALESCE(bq.order_id,'') AND COALESCE(CAST(arch.order_amt AS NUMERIC),0) = COALESCE(CAST(bq.order_amt AS NUMERIC),0)`. Note the archive side matches **plain `hashed_value`** (the archive branch hardcodes `hashed_values_key = CAST(NULL AS STRING)`); the `COALESCE(hashed_values_key, hashed_value)` is only on the live side, and `order_id`/`order_amt` are NULL-coalesced (to `''` / `0`) on both sides.
- **Join columns:** `advertiser_id` (→ advertisers), `campaign_id` / `campaign_group_id` / `group_id` / `creative_id` (→ campaign hierarchy), `guid` / `ip` (identity). `upload_id` = the offline-upload batch a row arrived in.

## Column meanings (only the non-obvious ones)
- **`epoch` (INT64) = SECONDS** since Unix epoch for **99.94%** of rows (`epoch = UNIX_SECONDS(time)` on 3,638,078 / 3,640,756). It is technically **mixed-unit**: 3,638,423 rows are 10-digit seconds and only **2,333 rows (0.06%, a 2023 sliver)** are 16-digit microseconds (`max(epoch)=1706002551732000`). **Do NOT `TIMESTAMP_MICROS(epoch)`** — for ~99.9% of rows that yields a 1970 timestamp. Use the `time` TIMESTAMP directly (or `TIMESTAMP_SECONDS(epoch)`).
- **`event_epoch`, `impression_epoch` (INT64) = MICROSECONDS** since Unix epoch — 100% micros-scale (0 seconds-scale rows). These hold the **exposure** instant, **not** the conversion: `epoch != event_epoch` on 99.94% of rows, while `event_epoch = impression_epoch` on 100%. Anchor: `event_epoch=1781750872146000` → `TIMESTAMP_MICROS` = 2026-06-17 (the attributed impression), while the paired conversion `time` is weeks later. (The prior "all three = micros, all equal" note generalized from one unrepresentative 2023 outlier row — corrected 2026-07-19.)
- **`time`** = conversion timestamp (the conversion moment); `epoch` = its Unix-**seconds** form (`epoch = UNIX_SECONDS(time)`), **not** a truncation of a micros value. **`event_time`** / **`impression_time`** = the attributed **exposure** (earlier than `time` by hours to weeks — do not use as the conversion moment; see Grain & keys). **`run_time`** = the ETL/attribution run that produced the row (max `run_time` ≈ today = freshness signal, not a business event). **`hour`** (DATETIME) = hour-bucket of the event.
- **`order_amt` (NUMERIC)** = conversion order value in `order_curr`. Non-null on **100%** of current rows (3,640,756/3,640,756). Note the online rollups use `order_amt` here (unlike `ui_conversions` where `order_amt_usd` is NULL).
- **`conversion_type` (STRING)** = human label, usually `"Offline Event"` (majority) or `"Call"`; but sometimes an **unmapped raw numeric code as a string, e.g. `"-102"`** (~1.5M rows) — treat it as an event-type code that never got a label, not a real category.
- **`conversion_source_id` (INT64)** = the offline integration/source. **31** = the main offline-upload source (dominant, 3,640,101 rows), **37** = call-tracking (619 rows, pairs with `conversion_type="Call"`), **32** = Showroom Up/Visit activity (36 rows, rare).
- **`attribution_model_id` (INT64)** = attribution model applied (5, 7, 8 observed). **`channel_id`** follows the workspace convention: **8 = CTV, 1 = display** — offline conversions attribute across both.
- **`hashed_value` / `hashed_values_key` (STRING)** = hashed PII match keys (email/phone). **`hashed_value` is the actually-populated key** — NULL on only 5,657 rows (0.16%). **`hashed_values_key` is NULL on 3,640,678 / 3,640,756 rows (99.998%)** — the archive branch hardcodes it to NULL and only a handful of live rows carry it, so the dedup's `COALESCE(hashed_values_key, hashed_value)` is effectively just `hashed_value`. Group/join on `hashed_value`, not `hashed_values_key`.
- **`disputed` (BOOL)** = FALSE on 100% of current rows (0 disputed). **`is_cross_device`** and **`from_verified_impression`** = TRUE on 100% of current rows. As of the 2026-07-19 scan these three flags carry no discriminating signal — do not filter on them expecting a subset.
- **`partner_id_list` (STRING)** = delimited list of data-partner IDs involved in the match. **`ad_served_id`** = the served-ad reference id. **`private_marketplace_id` / `supply_vendor`** = supply-path metadata.

## Joins & relationships
- **`advertiser_id` → `advertisers` (id) — N:1.** Many conversions per advertiser (only 161 distinct advertisers here); joining to the advertiser dim does not fan out. Filter the dim with `deleted=FALSE AND is_test=FALSE`.
- **`campaign_id` → `campaigns`; `campaign_group_id` → `campaign_groups`; `group_id` → line-item/group; `creative_id` → creatives — each N:1.** Safe from this side (many conversions per campaign object).
- **`guid` / `ip` → identity tables (`guid_ip_log_visitors`, graph) — N:N**, fan-out risk if joined loosely; these are the match keys, not clean FKs. IP-to-IP bridging is not available in BQ.
- **Self-relationship:** the view is already the deduped UNION of `summarydata_archive.offline_conversions` (2.96M rows, history) and the live BQ pipeline (707K rows). The live source's **hash-stable clean name is `ber_stg.offline__conversions_final`** (dataset `ber_stg`, no `ber_stg__` prefix); it currently resolves to physical `sqlmesh__ber_stg.ber_stg__offline__conversions_final__2948769173` (the unhashed `sqlmesh__ber_stg.ber_stg__offline__conversions_final` does **not** exist). You almost never need the physicals directly — query the top-level view.

## Gotchas
- **UNPARTITIONED.** Both backing physicals have `timePartitioning: None`. A `WHERE time >= …` filter does **NOT** prune bytes — dry-run of `SELECT time` was byte-identical (418,949,997 B) with and without a date filter, and `Partitions: 0` on every run. There is no partition column to lean on.
- **Elevated per-column cost floor from the dedup join.** Even `SELECT time` scans ~0.42 GB (not a few MB) because the view's `NOT EXISTS` anti-join must read the archive + live key columns (`advertiser_id, hashed_value/hashed_values_key, time, order_id, order_amt`) to dedup. You cannot get "cheap" by selecting one column.
- **Freshness (drift vs prose):** `data_knowledge.md` (2026-04-16) said the BQ table was current only to ~2026-04-14. That is now **stale/RESOLVED** — max `time` = 2026-07-17, max `run_time` = 2026-07-17, i.e. fresh to within a ~1-2 day ETL lag (scan date 2026-07-19). The live `ber_stg` branch keeps it fresh; the archive branch is the frozen CoreDW-migration history (min `time` 2023-04-13).
- **Catalog hash drift:** `data_catalog.md` still lists physical hash `…__292378007`; the live view is `…__3013632845` (a UNION view, not a plain passthrough). SQLMesh re-hashes on rebuild — trust AUTO:SCHEMA / the live `bq show`, not the prose hash.
- **`numRows:0 / timePartitioning:None` on the top-level view is expected** (it's a VIEW); the truth lives in the two physical TABLEs, which report real stats.
- **Always-true / always-null flags** (`disputed`=0, `is_cross_device`/`from_verified_impression`=TRUE, `order_amt` never null) — see Column meanings; treat as constants in current data.

## Cost & partitioning notes
- **No partition to filter — the table is just small.** Full `SELECT *` (all 42 cols) = **1,698,762,245 B (~1.70 GB)**, which equals the summed backing storage exactly. There is no cheaper "recent slice"; reduce cost only by selecting fewer columns.
- **The one rule:** project only the columns you need. Column-set cost (dry-run, labeled):
  - `SELECT *` (42 cols), any/no filter → **1,698,762,245 B (~1.70 GB)**.
  - `SELECT time` (1 col), with OR without a `time` filter → **418,949,997 B (~0.42 GB)** — identical (proves no pruning; floor is the dedup join).
- **`approx_logical_bytes` = 1,698,762,245** = `numBytes(summarydata_archive.offline_conversions)` 1,374,170,480 + `numBytes(ber_stg__offline__conversions_final)` 324,591,765.
- If you only need **recent BQ-native** conversions, querying `ber_stg.offline__conversions_final` (the clean SQLMesh view, ~325 MB, 707,427 rows) directly skips the archive scan and the dedup anti-join; for **pre-2026 history** use `summarydata_archive.offline_conversions`. Otherwise use the top-level view for a complete, deduped picture. (Do **not** use `sqlmesh__ber_stg.ber_stg__offline__conversions_final` — that unhashed name 404s; only the hash-suffixed physical `…__2948769173` exists and its hash churns on rebuild.)

## Example queries
```sql
-- Offline conversion volume & value per advertiser, last 90 days
-- (no partition filter helps cost; the WHERE just scopes rows, whole table is scanned regardless)
SELECT advertiser_id,
       COUNT(*)                         AS offline_convs,
       SUM(order_amt)                   AS offline_value,
       COUNTIF(conversion_type='Call')  AS call_convs
FROM `summarydata.offline_conversions`
WHERE time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 90 DAY)
GROUP BY advertiser_id
ORDER BY offline_value DESC;
```
