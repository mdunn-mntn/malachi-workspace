# summarydata.advertiser_pa_toggle_change_log

## Purpose
CDC / audit log of when **Probabilistic Attribution (PA)** — MNTN's statistical-modeling attribution feature, where visit and conversion metrics include modeled (not just deterministic) events — was turned on or off for an advertiser, who did it, and from what effective date. Reach for it to answer "which advertisers have PA enabled, and since when?" and to reconstruct the PA-adoption timeline. It is a small reference/flag table (128 distinct advertisers, log starts 2025-10-19), not a fact table.

## Grain & keys
- **Grain:** one row per **advertiser x change event**. `change_id` enumerates the event type (only two values live):
  - `change_id = 71` — the **PA toggle** itself: `Toggled Off -> Toggled On` (120 rows / 120 advertisers) or `Toggled On -> Toggled Off` (8 rows / 8 advertisers).
  - `change_id = 70` — the paired **"Statistical Modeling Data Enabled"** record (`... Disabled -> ... Enabled`), auto-emitted alongside every On toggle (120 rows / 120 advertisers).
- An advertiser turning PA **on** produces **2 rows** (a `70` data-enabled + a `71` toggled-on); an **off** event is a **single** `71` row. Max 2 rows per advertiser in current data; no advertiser has repeated the same-direction toggle.
- **No single natural PK.** `(advertiser_id, change_id, time)` uniquely identifies a row. `advertiser_id` is the real entity key.

## Column meanings (only the non-obvious ones)
- **time** — event timestamp, native `TIMESTAMP` (no epoch decoding; `time_unit: timestamp`). Second-level precision (166/248 rows carry a nonzero seconds part; some land on an exact minute). Never NULL. Treat as UTC (SQLMesh convention).
- **advertiser_id** — the advertiser whose PA setting changed. This is the join key, NOT `entity_id`.
- **campaign_group_id** — constant `1` in every row. PA is an advertiser-level setting, not per-campaign-group; this column is scaffolding — ignore it.
- **change_id** — enum `{70, 71}` identifying *which* change (see Grain). `70` = the "data enabled" side, `71` = the user-facing toggle.
- **change_type** — constant `"Probabilistic Attribution"` for all rows (the only feature this log covers today).
- **prior_value / current_value** — human-readable before/after *display strings*, not booleans. For `71`: `"Toggled Off"`/`"Toggled On"`. For `70`: `"Statistical Modeling Data Disabled"`/`"Statistical Modeling Data Enabled"`.
- **entity_text** — human-readable description. For a `71` Toggled-On row it embeds the **per-advertiser effective date**: `"Visit and conversion metrics include statistical modeling starting YYYY-MM-DD"` — the date PA modeling begins for that advertiser (varies row to row). For Toggled-Off it reads `"... now exclude statistical modeling"`; for `70` it is static (`"... now include statistical modeling in calculations"`).
- **entity_id / entity_type** — constant `"1"` / `"advertiser_id"` scaffolding, not a usable entity key.
- **entity_id_2 / entity_text_2 / entity_type_2** — always NULL (unused second-entity slot).
- **user_id** — internal MNTN user who made the change. **NULL on 170/248 rows (~69%)** — system/automated or bulk-backfilled changes (notably the `change_id = 70` data-enabled records) carry no actor. 48 distinct users among the non-null rows. Do not treat NULL as a data bug.

## Joins & relationships
- **advertiser_id -> `integrationprod.advertisers.id`** (or `core` advertisers) — partner grain 1 row per advertiser; this log is **N:1** into it (up to 2 rows here per advertiser). Low fan-out; join to recover `company_name` (per catalog gotcha, prefer `advertisers.company_name` over `fpa_advertiser_verticals.advertiser_name`).
- **user_id -> internal users dim** (`integrationprod` users) — 1:1 lookup; **nullable**, so use `LEFT JOIN`.
- **campaign_group_id** — do NOT join; constant `1`, carries no campaign-group meaning here.
- Usage pattern: this is a reference/flag table. Use it as a filter or a derived per-advertiser PA-state lookup; do not fan it into large fact scans.

## Gotchas
- **Log starts 2025-10-19** — PA enablement before that is NOT captured. The 8 `Toggled Off` rows have no matching in-log `Toggled On` (they were on before the window); no advertiser has both an On and an Off row. **Absence of an "On" row does not mean PA was never on.**
- **Current PA state = latest `change_id = 71` row by `time`** per advertiser — not merely "has any row." An advertiser can appear with only an Off (predating On) row.
- **Do not double-count advertisers by counting rows** — an On event is 2 rows (`70` + `71`). Count `DISTINCT advertiser_id`, or filter `change_id = 71`.
- **`user_id` NULL ~69%** — system/automated changes, expected.
- **Constant scaffolding columns** — `campaign_group_id = 1`, `entity_id = "1"`, `entity_type = "advertiser_id"`, `change_type = "Probabilistic Attribution"`, `entity_*_2 = NULL`. Don't mistake `entity_id` for a real key.
- Tiny, slowly-growing table (248 rows / ~50 KB); grows only as advertisers toggle PA.

## Cost & partitioning notes
- **No partition, no clustering, no TTL** — the physical is a plain `TABLE` (`timePartitioning: None`, `clustering: None`, 248 rows / 50,904 bytes).
- `SELECT *` over the full table = **50,904 bytes** (all 14 columns, full table, dry-run 2026-07-19) — billed at the 10 MB tier-1 floor. Full scans are negligible; **no partition filter is needed or possible.** Filter by `advertiser_id` / `change_id` / `time` for readability, not cost.

## Example queries
```sql
-- Current PA state per advertiser (latest toggle wins; ignores the paired change_id=70 record)
SELECT advertiser_id,
       ARRAY_AGG(current_value ORDER BY time DESC LIMIT 1)[OFFSET(0)] AS latest_state,
       MAX(time) AS last_change
FROM `summarydata.advertiser_pa_toggle_change_log`
WHERE change_id = 71
GROUP BY advertiser_id;

-- Advertisers currently ON, with modeling effective date
SELECT advertiser_id, time, entity_text
FROM `summarydata.advertiser_pa_toggle_change_log`
WHERE change_id = 71 AND current_value = 'Toggled On';
```
