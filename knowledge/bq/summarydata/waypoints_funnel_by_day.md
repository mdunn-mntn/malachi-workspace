# summarydata.waypoints_funnel_by_day

## Purpose
Serving view for the **Waypoints sequential-funnel** product. A "waypoint" is a defined funnel stage (an ordered `event_group`, e.g. *Platform Entry → … → Purchase*) configured per advertiser. This view exposes, per day, the raw building blocks needed to render a sequential funnel: how many distinct users/sessions/ad-exposures reached each stage, and how many transitioned from the prior stage. Reach for it when building or diagnosing a **sequential** funnel chart / step-conversion rate; it is the daily, sequential-only slice of the underlying `waypoints_fact`.

## Grain & keys
- **Grain:** one **contribution row**, not one row per stage. Dimensions: `day` × `advertiser_id` × `campaign_id` × `from_verified_impression` × funnel stage (`event_group` / `event_group_order`) × **contribution-row archetype**. Four archetypes coexist for the same stage (verified on 2026-07-10, adv 37056, stage "Platform Entry"):
  1. **Zero-scaffold** — all identity columns NULL, `transition_count`=`current_event_count_flag`=0. Guarantees every defined stage appears even with zero activity.
  2. **Per-user presence** — `current_ga_client_id` / `current_session_key` / `current_ad_served_id` populated, counts 0. `COUNT(DISTINCT …)` these to get users / sessions / ad-served **reaching** a stage.
  3. **Previous-stage transition** — `previous_ga_client_id` / `previous_session_key` populated, counts 0. `COUNT(DISTINCT …)` these to get distinct users **transitioning** from the prior stage into this one.
  4. **Aggregated event-count** — identity columns NULL, `current_event_count_flag` / `transition_count` > 0, `from_verified_impression` set. Pre-summed event volume for the stage.
- **Analytical keys:** `day, advertiser_id, campaign_id, event_group_order` (stage) + `from_verified_impression`. `funnel_mode` is a constant here (`'sequential'`).
- **There is no single-row-per-stage rollup** — a naive `COUNT(*)` or `SUM()` over the raw view mixes archetypes and over-counts. Aggregate deliberately per the archetype you want.

## Column meanings (only the non-obvious ones)
- **funnel_mode** — constant `'sequential'` in this view (it hard-filters `WHERE funnel_mode='sequential'`). The source `waypoints_fact` also carries `'full_volume'`, which is excluded here. Verified: `COUNT(DISTINCT funnel_mode)=1` on 2026-07-10.
- **event_group / event_group_order** — the funnel **stage** name and its 1-based ordinal position within the advertiser's configured funnel. Ordering/`previous_*`/`source_*`/`target_*` sequencing is derived from the advertiser's waypoint stage definitions (see Joins). Max observed order = 5 on the sample day; 44 distinct `event_group`s across 12 advertisers.
- **event_type, event_name** — **ALWAYS NULL in this view** (the sequential transform sets them to `CAST(NULL AS STRING)`). On `waypoints_fact` both are 100% populated — go there (or `full_volume` mode) if you need the actual pixel/event name. Verified: 0 non-null of 392,501 rows on 2026-07-10.
- **current_event_count_flag** — despite the "flag" name this is a **summed event count** for the stage (0 on scaffold/user-presence rows, up to tens of thousands on aggregated event-count rows — 37,660 max on the sample day). Not a 0/1 boolean.
- **transition_count** — summed count of transitions **into** the target stage, populated only on aggregated event-count rows (0 elsewhere; 37,660 max observed).
- **has_target_transition** — `1` if the stage has a defined predecessor (a real step edge exists), `0` for the first stage / a stage with no prior (i.e. `previous_event_group_order IS NULL`). INT flag, not the transition count.
- **current_ga_client_id / current_session_key / current_ad_served_id** — Google-Analytics-derived identity, present **only on per-user-presence rows** (NULL on scaffold and aggregate rows). `current_ga_client_id` = GA client id (`"<random>.<creation_unix_seconds>"`); `current_session_key` = `"<advertiser_id>|<ga_client_id>|<session_start_unix_seconds>"`; `current_ad_served_id` = the ad-exposure id. `COUNT(DISTINCT)` each for the users / sessions / ad-served meter at a stage. On 2026-07-10: 199,022 rows had ga_client_id, 165,275 had session_key, 19,807 had ad_served_id.
- **previous_ga_client_id / previous_session_key** — same GA identity but populated on **previous-stage transition rows** (the user arriving from the prior stage). `COUNT(DISTINCT)` for step-to-step distinct-user transitions.
- **source_event_group/_order vs target_event_group/_order** — the from→to stage pair for a transition edge: `source_*` = predecessor stage (mirrors `previous_event_group/_order`), `target_*` = the current stage (mirrors `event_group/_order`). `*_event_name` are always NULL (as with `event_name`).
- **from_verified_impression** — BOOL; where populated it was **TRUE** (38,875 rows on 2026-07-10) and NULL elsewhere (per-user-presence rows). Flags that the underlying activity came from an MNTN-verified impression (source `is_mntn_visit`); it is a dimension of the aggregated measure rows, not a per-user column here.
- **campaign_id** — `0` means the waypoint event is **not attributed to a specific campaign** (advertiser-level / organic) — ~89% of rows (247,846 of 278,113 sequential fact rows on 2026-07-10). `>0` = a specific campaign. This is the fact's own `campaign_id` (each event sits in exactly one bucket), **not** a GROUPING rollup, so summing across all `campaign_id` values does not double-count.

## Joins & relationships
- **advertiser_id → `integrationprod.advertisers.id`** — dim, **1:1**. Join for `company_name` (do not trust `fpa_advertiser_verticals.advertiser_name`). Fan-out risk: none (dim side unique).
- **campaign_id → `integrationprod.campaigns.id`** — dim, **1:1**, except `campaign_id=0` which has no match (unattributed). Fan-out risk: none.
- **Stage definitions (lineage, already baked in):** the view joins `waypoints_fact` to per-advertiser funnel-stage definitions sourced from `integrationprod.attr_advertiser_waypoints_event_mapping` via `ber_stg.waypoints__event_mapping_prepared`, keyed by `advertiser_id` + `event_group` / `event_group_order`. That mapping is what makes the funnel ordered (`event_group_order`, `previous_*`, `next→target_*`). Relationship advertiser→stages is **1:N**. You normally don't re-join it; documented for provenance and because it explains where the stage ordering comes from.
- **current_ga_client_id / current_session_key** are client-side GA identifiers from the Waypoints/GA pixel — **no FK to a BQ dim**; treat as opaque identity strings for `COUNT(DISTINCT)`.
- **Fan-out warning:** this is already a multi-row-per-entity contribution table (four archetypes × many stages/users per advertiser-day). Joining it to any per-event / per-impression table on `advertiser_id`/`campaign_id` explodes rows — **aggregate this view down to the grain you need first**, then join.

## Gotchas
- **Not a clean rollup.** Four contribution-row archetypes are UNION-ed together. Naive `COUNT(*)`/`SUM()` mixes them. Use `COUNT(DISTINCT current_ga_client_id)` (filter to presence rows) for stage reach; `COUNT(DISTINCT previous_ga_client_id)` for step transitions; `SUM(transition_count)`/`SUM(current_event_count_flag)` (only aggregate rows are non-zero) for event volume.
- **event_type & event_name are always NULL here** — sequential transform nulls them. Use `waypoints_fact` (or full_volume mode) for real event names.
- **Only `funnel_mode='sequential'`** — the `full_volume` funnel lives in `waypoints_fact`, not in this view.
- **Compute-heavy, not scan-heavy.** Bytes are tiny (~0.18 GB/day) but slot time explodes on sorting: an ordered wide pull of one day burned **399s slot** vs **4.8s slot** for an aggregate of the same day. Avoid `ORDER BY` over wide windows; pre-aggregate; never pull raw rows unfiltered.
- **Column projection does NOT prune cost.** `SELECT <one col>` and `SELECT *` for one day both dry-run at **189 MB** — the multi-CTE transform reads the whole day-partition of `waypoints_fact` regardless of projection. Only the `day` filter prunes.
- **`day` filter is mandatory** — the backing fact has `requirePartitionFilter=true`; a query without a `day` predicate ERRORS: *"Cannot query over table … without a filter over column(s) 'day' that can be used for partition elimination."*
- **campaign_id=0 dominates** (~89%) and means unattributed-to-campaign (advertiser-level), a real partition of the data — safe to sum across campaign_ids, but don't mistake `0` for a specific campaign.
- **History from 2026-02-10** (161 daily partitions through 2026-07-19). A `__NULL__` day partition exists but is empty (0 rows).
- **SQLMesh view — query the clean name.** `waypoints_funnel_by_day` → view `…__waypoints_funnel_by_day__3666253074` → view `…__waypoints_stage_daily__4175487051` → physical TABLE `…__waypoints_fact__2720337691`. The hashes change on model redeploy; never hardcode a hash. All storage is short-term (`numLongTermBytes=0`) because SQLMesh rewrites partitions — no `last_modified` age you can rely on for TTL.

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE day = '<date>'` (DATE partition, required). Cluster keys are `advertiser_id, campaign_id, funnel_mode` on the physical fact — add an `advertiser_id` (and/or `campaign_id`) predicate to prune further.
- **Measured figures (each labeled with its column set):**
  - View `waypoints_funnel_by_day`, **one day, ANY projection incl `SELECT *`**: 189 MB dry-run est / 0.177 GB billed. (Column projection does **not** reduce this.)
  - View, one day, **aggregate-only**: 4.8s slot / 0.177 GB.
  - View, one day, **ordered wide pull (`ORDER BY …`)**: 399s slot — avoid.
  - Fact `waypoints_fact`, one day, **4 narrow cols** (`funnel_mode, campaign_id, event_group, event_name`): 69.67 MB dry-run / 0.07 GB billed.
- **`approx_logical_bytes` = 54,098,086,880 B (~54.1 GB, 2026-07-29; up from 42.54 GB at enrichment)** — real backing storage of the physical `waypoints_fact` (`bq show numBytes`), which holds **both** funnel_modes; the sequential view is a compute-time subset of it. Fact holds 232,613,083 rows.

## Example queries
```sql
-- Users reaching each sequential funnel stage for one advertiser on one day
SELECT event_group_order, event_group,
       COUNT(DISTINCT current_ga_client_id) AS users_reached
FROM `dw-main-silver.summarydata.waypoints_funnel_by_day`
WHERE day = '2026-07-10'
  AND advertiser_id = 37056
  AND current_ga_client_id IS NOT NULL      -- presence rows only
GROUP BY event_group_order, event_group
ORDER BY event_group_order;

-- Step-to-step distinct-user transitions (source -> target)
SELECT source_event_group_order, source_event_group,
       target_event_group_order, target_event_group,
       COUNT(DISTINCT previous_ga_client_id) AS users_transitioned
FROM `dw-main-silver.summarydata.waypoints_funnel_by_day`
WHERE day = '2026-07-10'
  AND advertiser_id = 37056
  AND previous_ga_client_id IS NOT NULL     -- transition rows only
GROUP BY 1,2,3,4
ORDER BY target_event_group_order;
```
