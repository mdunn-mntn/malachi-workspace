# summarydata.cohort_conversion_facts_pivoted

## Purpose
Cohort-lag attribution facts. Each row is attributed conversions (and their order value) landing on a
given `conversion_date`, bucketed by which **exposure-cohort `hour`** they trace back to and how many
days later (`day_number`) the conversion happened. It is the **"pivoted"** (wide) shape of the conversion
facts: the same conversions are spread across many columns, one per **attribution model** (default /
last_touch / last_tv_touch / assist, each also in `competing` = industry-standard-first-touch and
`probattr` = probabilistic variants). Reach for it to study **conversion latency / attribution curves**
(how conversions accrue over days since exposure) at advertiser/campaign/creative grain. For a plain
"conversions by hour, no day-lag decomposition" total, use `summarydata.all_facts` (sister table, same
attribution-variant columns) instead — this table multiplies rows by the `hour x day_number` cohort matrix.

## Grain & keys
- **Grain:** one row per `conversion_date` x `hour` (exposure-cohort hour) x `advertiser_id` x
  `campaign_group_id` x `campaign_id` x `creative_id` x `conversion_type` x `conversion_source_id` x
  `day_number`. **Verified unique** (2026-07-01 partition: 72,947 rows = 72,947 distinct grain groups,
  0 dups). Dropping `hour` from the key produces duplicates (one `day_number` spans several exposure
  hours) — `hour` is a mandatory grain column, not descriptive.
- **Key(s) / join columns:** `advertiser_id`, `campaign_group_id`, `campaign_id`, `creative_id`
  (→ dims); `conversion_type` + `conversion_source_id` (→ conversion/pixel identity, see below).

## Column meanings (only the non-obvious ones)
- **`conversion_date`** (DATE, partition) — calendar date the **conversion** landed (the day the credit is
  booked). Range observed 2025-01-01 → present (+1 future day from tz/rollup edge).
- **`hour`** (DATETIME) — the **exposure-cohort hour**: the hour of the ad impression/touch that the
  conversion is attributed back to, NOT the conversion time. Always `<= conversion_date`; goes back to
  2024-08-23 (~132 days before the earliest conversion_date) because of the max attribution window. This
  is the cohort anchor.
- **`day_number`** (INT64) — 1-indexed **days-since-exposure lag** (conversion happened `day_number` days
  after the `hour` cohort). Observed range 1–132 (~4.4-month attribution window). It is derived from the
  hour-level exposure→conversion timestamps, so it is NOT exactly `DATE_DIFF(conversion_date, DATE(hour))`
  — a single `DATE(hour)` maps to two adjacent `day_number` values depending on within-day timing.
- **`conversion_type`** (STRING) — the advertiser's pixel event name (free text: `Purchase`, `Lead`,
  `Install`, `app_submitted`, and much long-tail/dirty text incl. URLs and `[object Object]`). The value
  **`'-101'` is a sentinel for NULL/untyped conversion** (the default site-visit conversion with no named
  event) — same convention as `summarydata.ui_conversions`; NEVER filter `conversion_type IS NULL`, filter
  `= '-101'`. `'-101'` dominates volume (~90% of conversions on 2026-07-01: 52,903 of 58,974). Named types
  and `'-101'` are **disjoint rows** in the grain — `'-101'` is its own bucket, not a rollup total.
- **`conversion_source_id`** (INT64) — the conversion/pixel source registry id (join to `data_sources`).
  Decode (per catalog): `23` = `guid_log` / "Website Event" — the standard post-2025-01 website pixel,
  hence dominant; `-1` = MNTN Pixel; `21` = MNTN Conversion; larger ids (e.g. `61`=Install,
  `328496`=Mobile App Install) are e-commerce/app integrations.
- **Measure columns come in `<model>_conversions` + `<model>_..._order_value` pairs.** `*_conversions` =
  count of attributed conversions; `*_order_value` (NUMERIC) = summed order/revenue value for that same
  model. The models are: **default** (`cohort_conversions` / `cohort_order_value` — view+click, INCLUDES
  CTV); **`last_touch`** (display/overall last-touch); **`last_tv_touch`** (TV last-touch); **assist**
  (`cohort_conversions_assist*` — multi-touch assist credit); each also carried in a **`competing`**
  variant (industry-standard / first-touch — what the client UI's "Verified Visits" adds on top of default)
  and a **`probattr`** variant (probabilistic attribution), including combined `probattr_competing_*`.
  See `data_catalog.md` §`sum_by_campaign_by_day` / `all_facts` for the vetted attribution-variant notes.

## Joins & relationships
- **`campaign_id` → `bronze.integrationprod.campaigns.campaign_id`** (PK is `campaign_id`, NOT `id`; there
  is no `silver.core.campaigns`) for `objective_id` / `funnel_level` / `campaign_group_id`. Partner grain
  1 campaign : N fact rows — safe (many facts per campaign), no fan-out on the dim side.
- **`advertiser_id` → `bronze.integrationprod.advertisers`** (filter `deleted=FALSE AND is_test=FALSE`),
  `campaign_group_id` → `campaign_groups`, `creative_id` → `creatives`. All dim joins are N:1 (many fact
  rows per dim) → no fan-out from the dim.
- **`conversion_type` + `conversion_source_id` → `integrationprod` conversion-type registry**
  (`advertiser_conversion_types`, one row per advertiser × conversion_type × conversion_source_id) and
  `data_sources` for the source decode.
- **Sister fact:** `summarydata.all_facts` (advertiser × campaign × `hour` grain, same attribution-variant
  columns, reproduces the client UI to the dollar). This table = the cohort-lag decomposition of the same
  conversions; **do NOT join and add them** — they overlap.
- **Fan-out warning (internal):** the `hour x day_number` cohort matrix multiplies rows. Any aggregate that
  ignores this (e.g. counting rows, or summing a measure without collapsing day_number/hour first) will
  over-inflate. Aggregate the measure columns with `SUM(...)` — they are additive **within one model** —
  but never mix rows across `conversion_type='-101'` and named types unless you intend the union.

## Gotchas
- **Attribution-variant columns are SEPARATE models of the SAME conversions — never SUM across them.** A
  conversion can appear in `cohort_conversions`, `cohort_last_touch_conversions`,
  `cohort_competing_view_conversions`, etc. simultaneously. Summing families double/triple-counts. To
  reproduce the client-UI "industry_standard" figure use **default + `competing`** (mirrors the verified
  `all_facts` result: visits = clicks+views+`competing_views`); do NOT add `last_tv_touch` to "add CTV
  back" — default already includes CTV and the sum overshoots (see `data_catalog.md`).
- **`conversion_type='-101'` is the untyped/default conversion, not "all types".** It is one value in the
  grain alongside named types; `SUM(cohort_conversions)` over the whole table counts `-101` **plus** named
  events (no double-count across types, but `-101` is the bulk). Filter deliberately.
- **`hour` is exposure time, `conversion_date` is conversion time** — do not treat `hour` as when the
  conversion happened. Cohort curves need both.
- **Late/backfilling data:** because `day_number` runs to ~132, recent `conversion_date` partitions keep
  gaining rows for older cohort hours as attribution matures; a fresh partition is not "final."
- **`conversion_type` is dirty free text** (URLs, `[object Object]`, casing variants like
  `Purchase`/`purchase`) — normalize before grouping by event name.
- No `require_partition_filter` and no partition TTL — full-history scans are allowed (and expensive); the
  guardrail is convention, not enforced.

## Cost & partitioning notes
- **Always filter `conversion_date`** (DAY partition). Cluster keys `advertiser_id, campaign_group_id,
  campaign_id, day_number` prune further when filtered/grouped in that order.
- Dry-run figures (labeled by column set, 2026-07-19):
  - `SELECT *` **full table** (all 33 cols) → **22.27 GB** (= backing `numBytes`, single physical table).
  - `SELECT *` **one day** (`conversion_date='2026-07-01'`, all cols) → **26.2 MB** (~0.026 GB) — partition
    pruning ≈ 850x reduction.
  - `SELECT advertiser_id, campaign_group_id, campaign_id, day_number, cohort_conversions` **full table**
    (5 narrow cols) → **2.51 GB** — column pruning ≈ 9x vs `SELECT *` on the same full scan.
- ~62.7M rows, 566 daily partitions; backing storage ~22.3 GB.

## Example queries
```sql
-- Attribution-latency curve for one advertiser (default model), a single conversion month
SELECT day_number,
       SUM(cohort_conversions)  AS conversions,
       SUM(cohort_order_value)  AS order_value
FROM `summarydata.cohort_conversion_facts_pivoted`
WHERE conversion_date BETWEEN '2026-06-01' AND '2026-06-30'
  AND advertiser_id = <AID>
GROUP BY day_number
ORDER BY day_number;

-- Industry-standard (client UI) conversions = default + competing, one day, named events only
SELECT SUM(cohort_conversions + cohort_competing_view_conversions) AS ui_conversions
FROM `summarydata.cohort_conversion_facts_pivoted`
WHERE conversion_date = '2026-07-01'
  AND conversion_type <> '-101';
```
