# summarydata.unstable_spend_facts

## Purpose
**NON-CANONICAL / experimental — do NOT use for spend reporting.** This is the *budget-cohort
"in-ramp" spend* table: it holds hourly ad spend attributed to **campaign-group budget changes that
are still ramping**, keeping only the impressions that fall inside each change's **attribution window**
(±`attribution_window` around the change time). It exists to measure how spend responds to a recent
budget change while the change is settling — the "unstable" name means the spend is still in flux, not
final. It is a small subset of overall spend (verified 2026-07-10: **293 advertisers / $35.9K media**
here vs **1,517 advertisers / $513.4K media** in the stable `spend_facts` for the same day). For any
real / total spend question, reach for **`summarydata.spend_facts`** (the canonical hourly spend fact) —
not this. The upstream SQLMesh model header even says: *"This model can be deleted after CoreDW is
turned off — no longer relevant."*

Lineage (verified from source, 2026-07-19): Greenplum function
`lds.budget_cohort_populate_unstable_spend_facts()` (`SteelHouse/db_repo`) reads
`logdata.unstable_cost_impression_log` JOINed to `core.v_budget_changes_in_ramp` on
`advertiser_id AND change_id`, filters to the per-change attribution window, aggregates by hour ×
dims × `change_id`, `TRUNCATE`+`INSERT`s `summarydata.unstable_spend_facts` → external parquet
`dw-main-bronze.external.unstable_spend_facts__v1` → SQLMesh `FULL` model (cron every 6h) → this view.

## Grain & keys
- **Grain:** one row per **hour × 17-dimension tuple × `change_id`** (verified 2026-07-10: for that day
  `COUNT(*)` = `COUNT(DISTINCT <17 dims + change_id>)` = 4,067,809 exactly — no dup combos). The 17 grain
  dims are the same as `spend_facts`: `hour`, `advertiser_id`, `campaign_group_id`, `campaign_id`,
  `channel_id`, `objective_id`, `group_id`, `creative_id`, `private_marketplace_id`, `country`,
  `metro_id`, `region`, `city`, `postal_code`, `domain`, `supply_vendor`, `device_type`.
- **`change_id` is 1:1 and stable with `campaign_group_id`** (verified 2026-07-10: 497 change_ids =
  497 campaign_groups, each change_id maps to exactly 1 advertiser + 1 campaign_group; and it is
  functionally determined by the 17 dims — `COUNT(DISTINCT 17-dim tuple)` = `COUNT(*)`, so it never
  multiplies the grain). It is **stable across days** (all 464 campaign_groups present on both 2026-07-09
  and 2026-07-10 kept the identical change_id) — it is not a per-day restatement version, it is the
  budget-change record the row belongs to.
- **Partition/cluster keys:** partitioned DAY on `hour`; clustered on **`advertiser_id`, `change_id`**
  (note: `change_id`, NOT `campaign_id` — this differs from `spend_facts` which clusters on
  `advertiser_id, campaign_id`).
- **Measures (additive):** `media_spend`, `data_spend`, `platform_spend`, `ctv_spend`, `unlinked_spend`.

## Column meanings (only the non-obvious ones)
- **`change_id`** — the **budget-change identifier** the spend is attributed to; FK to the budget-changes
  registry (`core.v_budget_changes_in_ramp` / the `budget_changes` dim), joined in the populate function
  on `advertiser_id AND change_id`. Only changes still "in ramp" are present. It is 1:1 and stable with
  `campaign_group_id` (see Grain), and is a cluster key. It does NOT multiply the grain.
- **`hour`** — DATETIME (no timezone; e.g. `2026-07-10T13:00:00`), the hour bucket **already adjusted to
  the advertiser's local timezone** by the populate function (`hourtz(l.time, a.time_zone)`). It is the
  DAY partition key. Don't apply another tz conversion.
- **The five spend measures are whole USD, NOT micros** (BIGNUMERIC; verified 2026-07-10 sample — dollars
  and cents, never ÷1e6). All additive.
- **`unlinked_spend` — SEMANTIC DIFFERS FROM `spend_facts`.** Here it = **`SUM(media+data+platform)` across
  ALL channels** i.e. the full billed total per row (verified 2026-07-10: `unlinked_spend` = media+data+
  platform on every row, 0 exceptions; SUM = $90,489.27). In the stable `spend_facts` `unlinked_spend`
  is ≈0. **Do not carry the stable table's "unlinked ≈ 0" assumption here.**
- **`ctv_spend`** — the CTV subset of the billed total: `SUM(media+data+platform)` filtered to
  `channel_id = 8` (verified 2026-07-10: SUM = $84,207.00 = the CTV-only media+data+platform; 0 non-CTV
  rows carry it). CTV dominates this table (~93% of total billed on 2026-07-10). Same CTV-only semantic
  as `spend_facts`.
- **`media_spend` / `data_spend` / `platform_spend`** — raw media cost / 3P-data cost / MNTN platform fee,
  USD (same meaning as `spend_facts`).
- **`objective_id`** — UNRELIABLE as a funnel-stage indicator (workspace-wide gotcha); use
  `campaigns.funnel_level` for stage.
- **`-8` sentinel** — the coredw populate function coalesces NULL dims to `-8` (INT dims) / `'-8'`
  (STRING dims), including `advertiser_id`/`campaign_group_id`. None observed on 2026-07-10 (0 sentinel
  rows), so it's rare, but guard numeric-string geo/id comparisons against `-8`/`'-8'`.

## Joins & relationships
- **`change_id` → budget-changes registry (`core.v_budget_changes_in_ramp` / `budget_changes`).** Partner
  grain: one row per budget change (per `advertiser_id` + `change_id`); this table is **N:1** into it
  (many hourly spend rows per change_id) — safe lookup, no fan-out. That registry is a coredw/Greenplum
  view and is **not live-queryable in BQ** (documented from the populate-function source, not live-verified
  here).
- **Dim joins are N:1 (safe):** `advertiser_id` → `bronze.integrationprod.advertisers` (1 row/advertiser),
  `campaign_id` → `campaigns`, `campaign_group_id` → `campaign_groups`, `creative_id` → `core_creatives`,
  `group_id` → `core_creative_groups`. Filter dims `deleted=FALSE AND is_test=FALSE`.
- **NEVER union/add this to `spend_facts` or `all_facts`.** They are different populations and different
  filters: this table is (a) a small budget-cohort subset (293 vs 1,517 advertisers on 2026-07-10) and
  (b) attribution-window-filtered (only impressions within ±window of a budget change), so it is neither a
  subset-sum nor a superset of `spend_facts` — mixing them double-counts or mismatches. Use `spend_facts`
  for real spend; use this only for budget-change ramp analysis.
- **Downstream:** consumed by `summarydata.unstable_all_facts` (the budget-cohort analogue of `all_facts`).

## Gotchas
- **NON-CANONICAL / flagged for deletion.** Upstream SQLMesh model header: *"can be deleted after CoreDW
  is turned off — no longer relevant. replaced by summarydata version."* Owner `ber`. Treat as
  experimental/staging; default to `summarydata.spend_facts`.
- **Partial, change-scoped population — never a spend total.** Only campaign-groups whose budget changes
  are currently "in ramp", and only the impressions inside each change's attribution window. 2026-07-10:
  4.07M rows / $35.9K media / 293 advertisers here vs 54.0M rows / $513.4K media / 1,517 advertisers in
  `spend_facts`.
- **`unlinked_spend` means the full billed total here, not ≈0** (see Column meanings) — the single most
  likely cross-table mistake.
- **FULL-refresh rolling window, not accumulating history.** The model is `kind FULL`, TRUNCATE+INSERT
  every 6h with a ~122-day lookback in the populate function. The live partition window is
  **2026-03-22 → 2026-07-20** (121 partitions, ~120 days — matches the lookback, NOT table history).
  Settled/old changes drop out on refresh. There is **no BQ partition-expiration TTL** (`expirationMs`
  null); the window is the refresh lookback.
- **`change_id` is a cluster key here (with `advertiser_id`), not `campaign_id`** — asymmetric with
  `spend_facts`. Filtering by `change_id` (or `advertiser_id`) prunes via clustering.
- **`hour` is DATETIME (tz-adjusted to advertiser local), not TIMESTAMP.** Partition filters are plain
  date-string comparisons: `WHERE hour >= '2026-07-10' AND hour < '2026-07-11'`.
- **Physical hash rotates on every SQLMesh rebuild.** Query the stable view name
  `summarydata.unstable_spend_facts`; never hardcode `...__unstable_spend_facts__594209343`.

## Cost & partitioning notes
- **The one filter to always apply: a `hour` range** (DAY partition), confirmed empirically 2026-07-19,
  all figures via `bq_run.sh`/`bq --dry_run` and labeled by exact column set:
  - `SELECT media_spend` (1 narrow col), **hour-filtered to 1 day**: **0.163 GB** (162,712,360 bytes).
  - `SELECT media_spend` (same 1 col), **all-time, no hour filter**: **14.60 GB** (14,599,721,664 bytes)
    — the hour filter prunes **~90×**. → **`hour` is the partition.**
  - `SELECT media_spend` (same 1 col), `advertiser_id` filter only (a cluster key, **no** hour filter):
    **4.94 GB** (4,935,014,720 bytes) — clustering alone cuts only ~3× off the 14.60 GB all-time scan; it
    does NOT substitute for the partition filter.
  - `SELECT *` (all 22 cols), **1 day**: **1.40 GB** (1,401,233,946 bytes) — ~8.6× the single-column day
    (0.163 GB). **Avoid `SELECT *`; project only the columns you need.**
- Actual billed (post-run, for reference): a 2-column `change_id`-distribution over 1 day billed
  **0.062 GB**; a wide grain-check over 1 day (many cols + FARM_FINGERPRINT) billed **0.699 GB**.
- Physical backing = a single TABLE (no UNION): **471,266,799 rows / 161,846,546,417 bytes (161.8 GB /
  0.162 TB logical)** via `bq show`. ~17× smaller than `spend_facts` (7.9B rows / 2.65 TB).

## Example queries
```sql
-- In-ramp spend by budget change for one advertiser (always range-filter hour, project columns)
SELECT change_id,
       campaign_group_id,
       SUM(media_spend)     AS media,
       SUM(ctv_spend)       AS ctv_billed,     -- CTV-only media+data+platform
       SUM(unlinked_spend)  AS total_billed     -- ALL-channel media+data+platform (NOT ~0 here)
FROM `dw-main-silver.summarydata.unstable_spend_facts`
WHERE hour >= '2026-07-10' AND hour < '2026-07-11'
  AND advertiser_id = 32527          -- cluster key: prunes within the partitions
GROUP BY change_id, campaign_group_id
ORDER BY total_billed DESC;
```
