# summarydata.visit_sources

## Purpose
The **referral-source / UTM tamp-detection detail** behind verified visits. Each verified visit is **exploded into one row per referer query-string parameter** that VVS extracts and evaluates for **referral blocking / tamp (tampering) detection** — the mechanism that identifies visits carrying a *competing* paid-source marker (a Google Ads `gclid`/`gbraid`/`wbraid`, a `utm_*` tag, `cm_mmc`, `&cid`) so they can be classified as competing attribution rather than credited to the MNTN ad.

Reach for it when you need to know **which referral/UTM signals a visit arrived with** — e.g. "how many verified visits came in tagged with a Google Ads `gclid`", auditing MNTN's competing-source blocking, or reconstructing the full referer URL per visit. It is the detail companion to `ui_visits`/`visits` (which carry `source_type`/`competing_source` at one-row-per-visit); `visit_sources` is the *unrolled* key/value form and is **not** a visit-count table without deduping.

This maps directly to the VVS "referral blocking / tamp detection (utm_source, utm_medium, utm_campaign, utm_content, gclid, cid, cmmmc)" step documented in `data_knowledge.md` (Nimeshi Fernando's VVS decision tree).

## Grain & keys
- **Grain:** one row per **(verified visit × detected referer source-parameter)**. A visit with 5 tracked params → 5 rows. Observed **1–14 rows per visit** in one day (mode = 5); average ≈ 4 (2,503,933 rows over 626,947 distinct visits on 2026-07-15).
- **Per-visit key:** `uuid` — one UUID per verified visit, repeated across all of that visit's rows. `distinct uuid` = 626,947 vs `distinct (advertiser_id, guid, epoch)` = 626,862 in the sampled day (≈1:1; `uuid` is the slightly finer/safer visit key). **To get one row per visit, dedup on `uuid`** (or `(advertiser_id, guid, epoch)`).
- **Source-param key within a visit:** `key` (normalized param name) — unique per visit-row.
- **Join keys to other tables:** `(advertiser_id, guid, epoch)` → `ui_visits`/`visits`/`clickpass_log`; `ad_served_id` → impression_log / event_log; `campaign_id` → campaigns.

## Column meanings (only the non-obvious ones)
The last nine columns (`uuid` … `blocked_value`) are what make this table distinct from `visits`/`ui_visits`; the rest are the standard visit dimensions (see `visits`/`ui_visits` docs). All figures below are from one advertiser-day sample (2026-07-15, 2,503,933 rows).

- **`uuid`** — per-**visit** UUID (e.g. `d2d7da5b-0d40-4939-8f0e-f9f26500ee6e`), **repeated on every source-row of the same visit**. This is the fan-out key; it is *not* per-row-unique. `guid` is the device/cookie id (browser-level), so `uuid` (visit) ≠ `guid` (device). Never NULL in-sample.
- **`key`** — the **normalized** referer source-parameter name. Domain in one day: `utm_source, utm_medium, utm_campaign, utm_content, utm_term, gclid, gbraid, wbraid, cm_mmc, %26cid` (top 10; `%26cid` = URL-encoded `&cid`). This is the tracked competing-paid-source vocabulary.
- **`raw_key`** — the raw matched token as it appeared in the referer / blocked-source pattern, sometimes carrying a trailing `=` or a URL-encoded `%26` (`&`) prefix — e.g. `gclid=`, `%26cid=`, or plain `utm_medium`. Equals `competing_source` in-sample; `key` is its cleaned form.
- **`value`** — the extracted value of that parameter from the referer URL (e.g. `Google` for `utm_source`, `Paid` for `utm_medium`, the gclid token for `gclid`). **`value = '-1'` is the sentinel for "parameter present but empty"** (e.g. an empty `utm_term`). **Never NULL** (0/2.5M) — empty is `'-1'`, not NULL.
- **`competing_source`** — the specific competing-source pattern this row matched (≈ `raw_key`). Names *which* param made the visit competing on this row.
- **`blocked_source`** — the **full comma-separated list of ALL competing/blocked source patterns detected on this visit**, repeated identically on every row of the visit (e.g. `gclid=, utm_source, utm_medium, utm_campaign, utm_term, %26cid=`). It is the visit-level union; `competing_source`/`raw_key` is the single per-row member of it.
- **`blocked_value`** — the value that was blocked/stripped. **Empty string `''` for 100% of the sampled day** (0 non-empty). In current data the blocking is expressed via `competing_source`/`blocked_source`, not via a populated `blocked_value`.
- **`referer`** — the **full referring URL including its query string** (which contains the raw source params). Repeated across the visit's rows. NULL for only 145/2.5M rows (~0.006%).
- **`parent_referer`** — the parent/root referring site (e.g. `https://www.lendio.com/`) vs the full deep-link `referer`.
- **`source_type`** — two-value branch tag, identical to `ui_visits`: **`'visits'`** (retargeting / TVO branch, 1.98M/day) or **`'last_tv_touch_visits'`** (prospecting / TV-last-touch branch, 0.52M/day). NOT free text.
- **`from_verified_impression`** — **constant TRUE** here (2,503,933/2,503,933). Like `ui_visits`, this view is restricted to verified impressions; do not re-filter on it, it never distinguishes rows. (In base `visits` it varies.)
- **`epoch`** — **microseconds** since Unix epoch = `UNIX_MICROS(time)`, and here the identity is **exact for 100%** of rows (2,503,933/2,503,933) — unlike `ui_visits`, `time` is NOT second-truncated in this table. Anchor: `epoch = UNIX_MICROS(visit time)`. Example: `1784159999881322`.
- **`impression_epoch`** — **microseconds** = `UNIX_MICROS(impression instant)`. `impression_epoch = UNIX_MICROS(impression_time)` holds for **79.7%** (1,995,598/2,503,933); the ~20% miss is essentially the `last_tv_touch_visits` branch (0.52M rows), where the impression timestamp is truncated/absent. Use `impression_epoch` for full precision.
- **`is_new`** — client-JS pixel NTB flag (same caveat as everywhere: not reproducible in SQL, ~41–56% disagreement with `clickpass_log.is_new`).
- **`ip` vs `ip_raw`** — enriched vs raw IP; identical for the sampled rows.

## Joins & relationships
- **`summarydata.ui_visits` / `summarydata.visits`** (partner grain: **1 row per verified visit**) — `visit_sources` is **N:1 against them** (~4 source-rows per visit, up to 14). Join on `(advertiser_id, guid, epoch)` (both are μs `epoch`); `ui_visits` has no `uuid` column, so `(advertiser_id, guid, epoch)` is the bridge. **Fan-out risk: joining ui_visits → visit_sources multiplies visit rows ~4x** — dedup `visit_sources` on `uuid` first if you want visit grain. Same two-branch `source_type` universe, so it covers the same verified-visit population.
- **`logdata.clickpass_log`** (partner grain: 1 row per VV redirect — VV source-of-truth) via `(advertiser_id, guid, epoch)` / `guid` — 1:1 at visit grain *after* deduping `visit_sources` on `uuid`; raw-to-raw it is N:1.
- **`logdata.impression_log` / `cost_impression_log` / `event_log`** via `ad_served_id` — **1:N** per `ad_served_id` (multiple VAST/viewability rows); dedup the log side before joining, and multiply by this table's own visit-level fan-out.
- **`integrationprod.public_campaigns`** via `campaign_id` (PK `campaign_id`, unique → 1:1 dim, no fan-out) — for `objective_id` / `campaign_group_id`.
- Dimension joins (`exchange_id`, `metro_id`, `creative_id`, `supply_vendor`) behave as in `visits` — all safe 1:1 dims.

## Gotchas
- **This is NOT a visit-count table.** Naively `COUNT(*)` counts *(visit × source-param)* pairs, ~4x the visit count. Always `COUNT(DISTINCT uuid)` (or dedup on `uuid`) for verified-visit counts.
- **`blocked_value` is empty `''` for the entire sampled day** — the "blocked" signal lives in `competing_source`/`blocked_source`, not in a populated `blocked_value`. Don't build logic expecting `blocked_value` to carry the stripped value.
- **`value = '-1'` means "param present but empty", not a real value.** `value` is never NULL — filter `value NOT IN ('-1','')` for genuinely populated params.
- **`from_verified_impression` is constant TRUE** and rows are already verified-visit-restricted — don't re-apply it as a selector.
- **`key` vs `raw_key` vs `competing_source`:** `key` is normalized (`gclid`), `raw_key`/`competing_source` carry the matched pattern with `=`/`%26` artifacts (`gclid=`, `%26cid=`). Join/group on `key` for clean param names.
- **`epoch` here equals `UNIX_MICROS(time)` exactly (100%)**, but `impression_epoch = UNIX_MICROS(impression_time)` only ~80% (misses concentrated in the `last_tv_touch_visits` branch). Use the epoch columns, not the truncated-elsewhere timestamps, for ordering/dedup.
- **Long impression→visit gaps exist** (same long-cycle advertisers as `ui_visits`, e.g. WGU/31357). Size any `ad_served_id` lookback to the advertiser's attribution window, not a flat 30 days.
- Underlying physical can carry a `__NULL__` partition (streaming/late buffer) — normal; filtered out when computing history below.

## Cost & partitioning notes
- **Partition: DAY on `time`** — confirmed by `bq show` on the physical (`timePartitioning.field = time`, no `requirePartitionFilter`) AND a dry-run diff. **No clustering** (`clustering: null`).
- **The one filter to always apply:** a `time` (or `DATE(time)`) range. Filtering `impression_time` does **not** prune (it is not the partition key).
- **Cost figures (each labeled by exact column set, from `--dry_run`, 2026-07-19):**
  - `SELECT time` · 1 day (`DATE(time)=…`): **20,031,464 B (~20.0 MB)** — one narrow col, one partition.
  - `SELECT time, source_type, competing_source` · 1 day: **76,656,198 B (~76.7 MB)** — three cols, one partition.
  - `SELECT time, source_type, competing_source` · all partitions (no filter): **11,425,360,261 B (~11.43 GB)** — same three cols, full view → **~149x prune** from the `time` filter (same column set — comparable).
  - `SELECT *` · 1 day: **2,744,362,989 B (~2.74 GB)** — all 47 cols, one partition (the wide `referer` URL dominates; avoid `SELECT *`).
  - `SELECT time WHERE DATE(impression_time)=…`: **5,916,077,264 B (~5.92 GB)** — proves `impression_time` does NOT partition-prune (≈296x more than the 20 MB `time`-filtered read of the same `SELECT time`).
- **History:** physical partitions span **2026-02-24 → 2026-07-20** (147 daily partitions), **no partition-expiration TTL** (`expirationTime: null`). This is a relatively new model — no long pre-2026 history available, unlike `visits`/`ui_visits` (back to 2023).
- `approx_logical_bytes` = physical `numBytes` of the single backing table `summarydata__visit_sources__2853818179` = **407,338,394,403 B (~407 GB)**; `numRows` ≈ **369,754,829** (~370M, consistent with ~2.5M/day × 147 days). Single physical — no UNION to sum.

## Example queries
```sql
-- Verified visits tagged with a Google Ads gclid, one advertiser, one week (dedup to visit grain)
SELECT COUNT(DISTINCT uuid) AS visits_with_gclid
FROM `summarydata.visit_sources`
WHERE DATE(time) BETWEEN '2026-07-08' AND '2026-07-15'
  AND advertiser_id = 31357
  AND key = 'gclid'
  AND value NOT IN ('-1','');

-- Distribution of competing referral params across verified visits (one day)
SELECT key, COUNT(*) AS param_rows, COUNT(DISTINCT uuid) AS visits
FROM `summarydata.visit_sources`
WHERE DATE(time) = '2026-07-15'
GROUP BY key ORDER BY visits DESC;

-- Per-visit source rollup (collapse the fan-out back to one row per visit)
SELECT uuid, ANY_VALUE(advertiser_id) advertiser_id, ANY_VALUE(source_type) source_type,
       ANY_VALUE(parent_referer) parent_referer,
       STRING_AGG(key, ',' ORDER BY key) source_params
FROM `summarydata.visit_sources`
WHERE DATE(time) = '2026-07-15' AND advertiser_id = 31357
GROUP BY uuid;
```
