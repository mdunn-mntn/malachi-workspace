# summarydata.waypoints__selective_performance

## Purpose
Event-grain fact for the **Waypoint** product — MNTN-pixel site events that were attributed to a served
impression. Physical-table description (verbatim): *"Waypoint events with selective-performance reassigned
ad served id and spend using campaign-group optimizable event config."*

A **waypoint** is a tracked on-site event fired by the advertiser's MNTN pixel. Two observed `event_type`
values (2026-07-15): `URL` (page-view / URL-match events; ~50%) and `DLV` (data-layer / e-commerce events;
~50%). Every row here already carries a non-null `ad_served_id`, i.e. this table holds only events that
matched a served ad.

The table's reason to exist is the **selective-performance (SP) reassignment**: alongside the naive
last-touch attribution (`ad_served_id` / `campaign_group_id` / `total_spend`), it computes a *reassigned*
attribution (`sp_ad_served_id` / `sp_campaign_group_id` / `sp_spend`) that credits the event to the
campaign group whose **optimizable-event config** matches the event, rather than to the most-recent
impression. Reach for it when you need SP-attributed event/spend at raw event grain; for daily rollups use
`summarydata.waypoints_sp_aggregation` instead (do not aggregate this table by hand unless you need a cut
the rollup doesn't provide).

## Grain & keys
- **Grain:** one row per **waypoint event × attributed impression (`ad_served_id`)**. The table is **NOT
  deduplicated** — on 2026-07-15, 1,279,852 rows collapsed to 968,758 distinct
  `guid|epoch|raw_event_name|ad_served_id` signatures (~1.32 rows/signature; byte-identical duplicate rows
  observed). Always `COUNT(DISTINCT …)` or dedup before counting events.
- **Identity keys:**
  - `user_key` = `{advertiser_id}|{ga_client_id}` — per-advertiser resolved user identity (matched
    `CONCAT(advertiser_id,'|',ga_client_id)` on 100% of rows). A cluster key.
  - `session_key` = `{advertiser_id}|{ga_client_id}|{ga_session_id}` — per-advertiser resolved session.
  - `guid` = MNTN pixel visitor GUID (UUID); `ga_client_id` / `ga_session_id` = Google-Analytics client &
    session ids the pixel captured.
- **Join columns:** `advertiser_id`, `campaign_id`, `campaign_group_id` (naive) / `sp_campaign_group_id`
  (reassigned), `ad_served_id` (naive) / `sp_ad_served_id` (reassigned).

## Column meanings (only the non-obvious ones)
- **`time` / `epoch`** — same instant. `epoch = UNIX_MICROS(time)` (**microseconds** since Unix epoch;
  verified `epoch` == `UNIX_MICROS(time)` exactly, e.g. `1784121504979474` = `2026-07-15 13:18:24` UTC).
  Not ms, not ns — this table is µs, unlike `bidder_bid_events` (ms) / `spend_log` (ns).
- **`event_type`** — coarse event class. Observed domain (2026-07-15): `URL` (page-view / URL-match event)
  and `DLV` (data-layer / e-commerce event). Only `DLV` events ever receive SP reassignment or become
  optimizable; `URL` events never do (n_opt=0, n_sp=0 for URL).
- **`raw_event_name`** — the event's display name as fired by the pixel (e.g. `"Viewed Recommendations
  Page"`). Free-text, advertiser-defined.
- **`optimizable_event_name` / `is_optimizable_event`** — set by the campaign group's optimizable-event
  config. `optimizable_event_name` is non-null **iff** `is_optimizable_event = TRUE` (18,828/18,828 on
  2026-07-15; zero non-optimizable rows carried a name). Only ~1.5% of rows are optimizable.
- **`from_verified_impression`** — TRUE when the attributing impression is a *verified* impression (~99.2%
  of rows on 2026-07-15). Distinguishes verified vs unverified impression attribution.
- **`ad_served_id`** — UUID (36-char) of the **naive last-touch** served ad/impression this event was
  matched to. Non-null on **every** row (empty-string count = 0); this table only holds ad-matched events.
- **`campaign_group_id` / `campaign_id`** — the campaign group / campaign of the naive last-touch impression.
- **SP-reassignment trio — `sp_ad_served_id` / `sp_campaign_group_id` / `sp_spend`:** the
  selective-performance **reassigned** attribution. Populated together (all three non-null or all null) on a
  minority of rows (24,845 of 1,279,852 ≈ 1.9% on 2026-07-15) — mostly the 18,828 optimizable events plus
  ~6,099 non-optimizable ones. When populated they may point at a **different** impression/campaign group
  than the naive columns (observed base `cg 78204 / ad_served_id A` reassigned to `sp_cg 67999 /
  sp_ad_served_id B`). `NULL` sp_* = no reassignment (fall back to the naive `ad_served_id` / `total_spend`).
- **`total_spend` vs `sp_spend`** (both `BIGNUMERIC`, currency) — `total_spend` is the naive impression's
  spend, non-null on all rows (day sum ≈ \$1,082.68 on 2026-07-15). `sp_spend` is the SP-reassigned spend,
  non-null only where reassignment fired (day sum ≈ \$67.61). Do **not** assume `sp_spend ≈ total_spend`;
  they are independent measures and most rows have `sp_spend = NULL`.

## Joins & relationships
- **`summarydata.waypoints_sp_aggregation`** — the **daily rollup of this table** (grain
  day × advertiser × campaign × campaign_group × sp_campaign_group × event). This table is the event-grain
  source; that one carries `event_count`, `selective_performance_event_count`, `sp_ad_served_id_count`,
  `sp_user_count`, `total_spend`, `sp_spend`. **This→aggregate is 1:N** (many events per aggregate row);
  prefer the aggregate for reporting to avoid re-summing duplicate event rows.
- **Upstream lineage (column-superset chain, same event grain):** `waypoints` / `waypoints_fact` (base
  events) → `waypoints__optimizable_event_mapping` (adds `optimizable_event_name`, `is_optimizable_event`)
  → `waypoints__optimizable_events_with_spend` (adds `total_spend`) → **this table** (adds the SP trio
  `sp_ad_served_id` / `sp_campaign_group_id` / `sp_spend`). Each stage is 1:1 with its predecessor on event
  grain.
- **Dimension lookups (1:1, no fan-out when joined to PK):** `advertiser_id` →
  `integrationprod.advertisers.id` (`company_name`; filter `deleted=FALSE AND is_test=FALSE`);
  `campaign_id` → `campaigns.id`; `campaign_group_id` / `sp_campaign_group_id` → `campaign_groups.id`.
- **Config source (prose oracle, not live-verified here):** the optimizable / selective-performance
  classification originates from `attr_advertiser_waypoints_event_mapping` +
  `attr_advertiser_selective_performance_config` (per data_catalog "pixel-config tables" note) — these carry
  the event-name → optimizable/SP mapping that populates `is_optimizable_event` and drives the reassignment.
- **`ad_served_id` / `sp_ad_served_id` → impression-level tables:** these UUIDs identify served impressions;
  joining to any impression/served-ad log is **1:N and high fan-out** (many site events per impression) —
  aggregate the event side first. The exact partner impression table is not live-verified in this pass.

## Gotchas
- **Not deduplicated.** Byte-identical duplicate rows exist (~24% row inflation vs distinct event
  signature). `COUNT(*)` over-counts events; dedup or use `waypoints_sp_aggregation`.
- **`epoch` is microseconds** (= `UNIX_MICROS(time)`), not ms/ns. Wrong unit → dates in the wrong millennium.
- **sp_* are sparse and all-or-nothing.** ~98% of rows have `sp_ad_served_id / sp_campaign_group_id /
  sp_spend = NULL`. Filtering `WHERE sp_spend IS NOT NULL` keeps only reassigned events; for total SP
  behavior you must `COALESCE`/fall back to the naive columns yourself — the view does not merge them.
- **Only `DLV` events are ever optimizable / reassigned.** `URL` events never carry SP or optimizable flags.
- **Rolling ~90-day window.** Observed `day` range 2026-05-01 → 2026-07-29 (~90 distinct days, ~91 physical
  partitions). No partition-expiration TTL is set on the physical table; the window is maintained by the
  SQLMesh full-refresh, so older days silently drop off — don't expect deep history here.
- **SQLMesh view.** `summarydata.waypoints__selective_performance` resolves to
  `sqlmesh__summarydata.summarydata__waypoints__selective_performance__3155232050`; the hash changes on
  model rebuild. Query the clean `summarydata.…` name, never the hashed physical.
- **`user_key` / `session_key` are advertiser-prefixed composites**, not bare GA ids. To compare against a
  raw `ga_client_id` you must strip the `{advertiser_id}|` prefix (or rebuild it).

## Cost & partitioning notes
- **Partition = `day` (DATE, DAY grain), `require_partition_filter = TRUE`** — a query with no `day` filter
  is **rejected** ("Cannot query … without a filter over column(s) 'day'"). Always add
  `WHERE day BETWEEN … AND …`. Cluster keys `advertiser_id, campaign_group_id, user_key` further prune when
  filtered.
- **Dry-run figures (labeled by column set), single partition `day = 2026-07-15`:**
  - `SELECT *` (all 22 cols, 1 day) → **389.6 MB** (389,556,517 B).
  - `SELECT sp_spend` (1 col, 1 day) → **11.0 MB** (11,033,856 B) — ~35× cheaper than `SELECT *`. Project
    only the columns you need.
  - `SELECT *` with no `day` filter → **rejected** (require_partition_filter).
- Physical backing storage (bq show): `numRows` ≈ 112.7M, `numTotalLogicalBytes` ≈ 34.07 GB
  (34,074,230,148); the daily SQLMesh full-refresh also holds time-travel physical bytes that are not query-billed.

## Example queries
```sql
-- SP-reassigned events for one advertiser, one day (uses partition + cluster prune)
SELECT raw_event_name, campaign_group_id, sp_campaign_group_id,
       total_spend, sp_spend, from_verified_impression
FROM `summarydata.waypoints__selective_performance`
WHERE day = DATE '2026-07-15'
  AND advertiser_id = 40673
  AND sp_ad_served_id IS NOT NULL;

-- Distinct optimizable events (dedup — table is not deduplicated)
SELECT optimizable_event_name, COUNT(DISTINCT CONCAT(guid,'|',CAST(epoch AS STRING),'|',ad_served_id)) AS events
FROM `summarydata.waypoints__selective_performance`
WHERE day BETWEEN DATE '2026-07-01' AND DATE '2026-07-15'
  AND is_optimizable_event
GROUP BY optimizable_event_name ORDER BY events DESC;
```
