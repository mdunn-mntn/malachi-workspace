# summarydata.waypoints_transitions

## Purpose
The **funnel step-to-step transition rollup** for the Waypoints product — the aggregated, dashboard-ready
layer that answers "of the visitors who reached funnel step A, what fraction went on to step B, and how
many dropped off?" It rolls the raw per-event Waypoints stream up to **one row per source→target step
pair**, per advertiser × campaign × day, and computes the forward-conversion (`pct_to_next_*`) and
drop-off (`dropoff_*`) rates on three denominators: distinct visitors (users), sessions, and served ads.

Reach for it to build funnel / Sankey / drop-off reporting. It is derived (via `waypoints_transition_daily`)
from the canonical `waypoints_fact`, **filtered to `funnel_mode='sequential'`** (ordered-funnel completion,
not raw event volume) and to rows that are a step start with a forward transition. It is **not** the raw
event detail — for that use `waypoints_transition_daily` / `waypoints_transition_analysis` (one row per
user event with transition context); this view is the pre-aggregated funnel-rate summary on top of them.

## Grain & keys
- **Grain:** one row per **source→target funnel-step pair**, dimensioned by
  `day × advertiser_id × campaign_id × from_verified_impression × event_type × source_event_(group,order,name) × target_event_(group,order,name)`.
  The 11-column tuple is a **unique key** — verified `COUNT(*) = COUNT(DISTINCT 11-tuple) = 1659` on
  2026-07-17. (`group_id` is used internally by the view but collapsed out of the output; it is `0` for
  100% of rows so the collapse never creates duplicates.)
- **Scaffolded matrix, not just observed transitions.** For each source step the view cross-joins **every
  target that ever appeared for that advertiser+source** (a per-advertiser DISTINCT catalog), so rows exist
  for source→target pairs that had **zero** transitions on that day/campaign (full drop-off placeholders).
  On 2026-07-17, **969 of 1659 rows (58%) had `transition_count = 0`**; only 690 were realized transitions.
- **Small, config-gated population.** Only advertisers with a configured **sequential** Waypoints funnel
  appear — 14 advertisers / 91 campaigns / 1,659 rows on 2026-07-17.
- **Join columns:** `advertiser_id`, `campaign_id` (0 = organic), and the source/target event-group +
  event-name dimensions (advertiser-authored funnel stages).

## Column meanings (only the non-obvious ones)
- **`day`** — DATE, the only temporal column (from `waypoints_fact.day`, the backing partition). No integer
  epoch column exists here. **NOTE:** filtering `day` does **not** reduce scan cost (see Cost & partitioning).
- **`event_type`** — how the events in this transition were captured: `URL` (page-URL match) or `DLV` (GA4
  dataLayer variable). Only these two values (verified 2026-07-17). Applies to the whole source→target row.
- **`source_event_group` / `source_event_group_order` / `source_event_name`** — the **from-side** step of the
  transition: advertiser-defined funnel **stage** name, its 1-based ordinal in the funnel, and the specific
  event within the stage. `event_name='*'` is a group-level (any-event-in-stage) wildcard. Labels are
  advertiser-authored free text (expect typos / no controlled vocabulary across advertisers).
- **`target_event_group` / `target_event_group_order` / `target_event_name`** — the **to-side** step the
  visitor transitioned forward into. Same encoding as the source triplet.
- **`source_users` / `source_sessions` / `source_ad_served_count`** — the **denominator**: distinct
  visitors (`current_ga_client_id`), distinct sessions (`current_session_key`), and distinct MNTN ad-serves
  (`current_ad_served_id`) that were **at the source step**. **These are repeated identically across every
  target row that shares the same source** (the scaffold pairs one source against many targets) — treat them
  as the source-step total, never `SUM` them across rows.
- **`transition_count`** — raw count of transition-detail rows for this exact source→target pair
  (`COUNT(*)`, not distinct); `COALESCE`d to 0 when the pair did not occur. Not a distinct-visitor count.
- **`transition_users` / `transition_sessions` / `transition_ad_served_count`** — the **numerator**: distinct
  visitors / sessions / ad-serves that actually made the source→target transition; `COALESCE`d to 0.
- **`dropoff_users` / `dropoff_sessions` / `dropoff_ad_served_count`** — `GREATEST(source_* − transition_*, 0)`:
  who reached the source step but did **not** take this specific target. Clamped at 0, so never negative
  (verified: 0 rows with `source_users < transition_users`).
- **`pct_to_next_users` / `pct_to_next_sessions`** — forward conversion rate for this pair =
  `transition_* / source_*`. **NULL when the source denominator is 0.** Bounded [0, 1] (verified min 0.0,
  max 1.0). Because a single source fans out to multiple targets, `pct_to_next_*` across a source's target
  rows can sum to > 1 (a visitor may progress to several targets).
- **`dropoff_pct_users` / `dropoff_pct_sessions`** — `dropoff_* / source_*` = `1 − pct_to_next_*`; NULL when
  the source denominator is 0.
- **`from_verified_impression`** — BOOL that is only ever `TRUE` or `NULL` (never `FALSE`; verified
  fvi_false=0, fvi_true=1051, fvi_null=608 on 2026-07-17). `TRUE` = the funnel path tied to a **verified**
  MNTN ad impression; `NULL` mixes organic + unverified-ad paths. Splits ad-verified vs. non-verified funnels.
- **`campaign_id`** — MNTN campaign; **`0` = organic** (no ad). 414 organic rows on 2026-07-17.

## Joins & relationships
This view is already aggregated, so joins to dimensions are **N:1 and safe** (no fan-out out of the view).
- **`advertiser_id` → `advertisers.id`** (silver dim / `bronze.integrationprod.core_advertisers`). Partner
  grain 1 row/advertiser; **N:1**. Filter `deleted=FALSE AND is_test=FALSE`; join for `company_name` (the
  reliable advertiser label).
- **`campaign_id` → `campaigns.id`** (dim, 1 row/campaign; **N:1**) — meaningful only for `campaign_id > 0`;
  use `campaigns.funnel_level` (not `objective_id`) for stage. Organic rows (`campaign_id = 0`) won't match.
- **`source_event_group` / `source_event_name` (+ `advertiser_id`) → `attr_advertiser_waypoints_event_mapping`**
  (companion `attr_advertiser_selective_performance_config`) — the per-advertiser Waypoints pixel config that
  defines the funnel stages & event-name classification (carries a `deleted` flag). This is the origin of the
  stage/event labels. Config dim, **N:1**.
- **Lineage / sibling views:** derived from **`waypoints_fact`** (physical TABLE, 232.6M rows / 54.1 GB as
  of 2026-07-29, partition `day`) via **`waypoints_transition_daily`** (SQLMesh view `…__1934107001`, the
  per-user-event transition detail: one row per source→target user event, carries `group_id`, `is_ordered`,
  `current_ga_client_id`,
  `current_session_key`, `current_ad_served_id`). `waypoints_transition_analysis` is a near-passthrough of
  `waypoints_transition_daily` at that same detail grain. **`waypoints_transitions` (this view) is the
  aggregated funnel-rate rollup** of that detail — use it for rates; use the daily/analysis views for the
  underlying per-event rows.
- **Internal self fan-out (not a partner join, but a hazard):** `source_users/sessions/ad_served_count` are
  duplicated across a source's target rows — pre-aggregate at the source grain before combining source-step
  totals, or you multiply the denominator by the number of targets.

## Gotchas
- **`day` does NOT prune scan cost.** Because the view's `source_target_catalog` CTE does `SELECT DISTINCT`
  across **all history**, a `WHERE day = '…'` predicate scans the full backing table anyway — 18.24 GB with
  **and** without the day filter (identical, `SELECT day` dry-run). The prune lever is **`advertiser_id`**
  (cluster), ~6.8×. Always add `advertiser_id`; add `day` too for correctness but it saves nothing.
- **Scaffolded zero rows.** ~58% of rows (969/1659 on 2026-07-17) have `transition_count = 0` /
  `transition_users = 0` — placeholder drop-off pairs for targets that didn't occur that day/campaign. Add
  `WHERE transition_count > 0` (or `transition_users > 0`) when you only want realized transitions.
- **Never `SUM(source_users)` (or source_sessions / source_ad_served_count) across rows.** They repeat across
  every target row of the same source. Take the source total once per source key.
- **Sequential mode only.** This is ordered-funnel drop-off analysis, not raw event volume. `full_volume`
  events are excluded upstream; do not expect total-event counts here.
- **`from_verified_impression` is TRUE-or-NULL** (never FALSE). `WHERE from_verified_impression` = verified
  paths only; `IS NULL` mixes organic + unverified. The view's internal joins use `IS NOT DISTINCT FROM` so
  NULLs match correctly on both sides.
- **`pct_*` columns are NULL when the source denominator is 0** — filter or `COALESCE` before averaging.
- **Young, sparse table.** Data starts **2026-02-10**; only advertisers with a configured sequential
  Waypoints funnel appear (14 advertisers on a sampled day). Not for long pre-period baselines.
- **No `require_partition_filter` at the view surface** — you *can* query without a `day` predicate (the
  inner view supplies `day >= '2026-02-10'`), but doing so changes nothing cost-wise (still a full scan).

## Cost & partitioning notes
- **The one filter to always apply: `advertiser_id`** (the cluster key that actually prunes), plus a `day`
  range for correctness. Backing partition is `waypoints_fact.day` (DATE, DAY) but the outer `day` filter is
  a no-op for cost (see Gotchas).
- **Labeled dry-run figures (same column set within each comparison):**
  - `SELECT day`, **no** day filter: **18.24 GB**.
  - `SELECT day`, `WHERE day = '2026-07-17'`: **18.24 GB** — identical → `day` does not prune.
  - `SELECT day`, `day = '2026-07-17' AND advertiser_id = 36583`: **2.68 GB** — ~6.8× prune from the
    `advertiser_id` cluster.
  - `SELECT *`, one day: **28.17 GB** (dry-run) — ~1.5× the 1-column day scan.
  - `SELECT *`, `advertiser_id = 36583` (no day): **4.18 GB** (dry-run).
- **Actual full-day aggregate** (grain/domain probe, `WHERE day = '2026-07-17'`, all advertisers): **15.28 GB
  billed / 167.9 s slot / 1.5 s wall**, 160 partitions scanned, 166M+ base rows read — confirms the
  full-history scan even for one output day.
- **`approx_logical_bytes` = null** (derived aggregation view; no single stored byte count). Real backing
  storage lives in `waypoints_fact` (54,098,086,880 bytes / 232,613,083 rows, 2026-07-29; up from 42.5 GB/187M
  at enrichment) which this view filters + aggregates — do not treat the view's scan estimate as logical bytes.

## Example queries
```sql
-- Realized funnel transitions for one advertiser, one day.
-- advertiser_id prunes (~6.8x); day is for correctness (does NOT reduce cost).
SELECT source_event_group, source_event_name, target_event_group, target_event_name,
       source_users, transition_users, dropoff_users, pct_to_next_users
FROM `summarydata.waypoints_transitions`
WHERE day = '2026-07-17'
  AND advertiser_id = 36583
  AND from_verified_impression IS TRUE   -- verified-impression funnel only
  AND transition_count > 0               -- drop the ~58% zero scaffold rows
ORDER BY source_event_group_order, target_event_group_order, transition_users DESC
```
