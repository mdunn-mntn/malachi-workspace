# summarydata.audience_keyword_state_history

## Purpose
Full temporal history of which keywords are associated with each audience. It answers "what keywords did audience X target, and how did that set change over time." Physically a `UNION ALL` view over the **live** current-state table (`ui.audience_keyword_state`) and the **archive** of superseded versions (`archives.audience_keyword_state_archives`), so one query sees both the present set and every prior edit.

Reach for it when you need the *history* (audit trail of keyword edits, as-of-a-date reconstruction). For the plain **current** keyword set, query `ui.audience_keyword_state` (a.k.a. bronze `integrationprod.ui_audience_keyword_state`) directly — it is smaller and, crucially, exposes columns this view drops (see Gotchas).

## Grain & keys
- **Grain:** one row per **keyword-state version** — a snapshot of a single keyword's association to one audience at a point in time. The live half contributes the current version (archive_time NULL); the archive half contributes every superseded version (archive_time set).
- **Key(s):** `id` = the keyword-state row PK (INT64). It is *near*-unique in the view (7.81M distinct of 7.97M CHILD rows; PARENT rows are ~all distinct) but **not a guaranteed unique key** — a small fraction of ids recur, and the archive's own PK (`audience_keyword_state_archives_id`) that would disambiguate is **dropped by the view**. For a truly unique version key use `(id, create_time, archive_time)`.
- **Join columns:** `audience_id` (→ audiences / audience_segments), `id`. `data_source_id` = 19 (DS19 / MNTN-Matched) for the overwhelming majority.

## Column meanings (only the non-obvious ones)
- **`archive_time`** — the linchpin of the "history" semantics. `NULL` ⇒ the row came from the **live** half (`ui.audience_keyword_state`), i.e. the **current** state of that keyword association. `NOT NULL` ⇒ the row came from the **archive** half and is a **superseded** version, timestamped when it was retired. Filter `archive_time IS NULL` to collapse to today's live set; use `archive_time` + `create_time` to reconstruct as-of-date.
- **`create_time`** — TIMESTAMP (not an epoch int) when this keyword-state version was written. Use with `archive_time` to bound a version's validity window.
- **`keyword_type`** — enum `{PARENT, CHILD}` (verified live; only these two values). **PARENT** = the ~20 customer-visible seed terms shown in the UI audience builder. **CHILD** = the system/LLM-expanded terms grouped under a parent — the CHILD rows with `selected=true` are what actually populate the DS19 targeting expression. UI shows only PARENTs; DS19 targets the selected CHILDren.
- **`selected`** — BOOL; `true` = this keyword is included in the audience expression. `selected=true AND keyword_type='CHILD'` ≈ the real DS19 targeting set (but see the is_magic caveat in Gotchas).
- **`is_custom`** — customer-entered vs system-generated. Empirically **only PARENT rows are ever custom** (251K custom PARENTs; 0 custom CHILDren) — customers seed parents, the system expands children.
- **`is_hidden`** — empirically **only CHILD rows are ever hidden** (1.37M hidden CHILDren; 0 hidden PARENTs); PARENT seeds are always visible.
- **`data_source_id`** — near-always `19` (DS19 = MNTN-Matched keyword segments). Treat non-19 as rare/edge.
- **`data_source_category_id`** — high-cardinality INT (the specific keyword-segment/category id within DS19, e.g. 940735). Not a small enum — do not treat as a type code.
- **`keyword`** — the keyword text itself.
- **`expanded_from`** — JSON; for a CHILD, the PARENT seed it was embedding-expanded from. NULL/empty for PARENTs. JSON type — extract with `JSON_VALUE`/`JSON_QUERY`, do not string-compare raw.
- **`id`** / **`audience_id`** — keyword-state row id and its owning audience id (see Grain & keys for uniqueness caveat).

## Joins & relationships
- **`audience_id` → `audience.audiences` / `ui.audience_segments`** — partner grain is 1 row per audience (dim). This view is **N:1** into audiences (many keyword versions per audience), so joining audiences→this view **fans out ~9.9M ways total** (~thousands of keyword-versions per large audience). Aggregate or filter `archive_time IS NULL` before joining back to a per-audience metric.
- **`data_source_id` = 19** ties these rows to the DS19 / MNTN-Matched targeting path; the selected CHILD keywords here are the source-of-truth for the DS19 audience expression (preferred over parsing the JSON expression blob in `audience.audiences`).
- No direct join to impression/bid logs — this is a config/dimension history, not an event log. To connect keywords to delivery you go audience → campaign → bid/impression, not from this table directly.

## Gotchas
- **The view DROPS columns the prose oracle depends on.** The bronze source tables carry `is_magic`, `model_version`, `description`, `feedback`, and `datastream_metadata` (plus the archive's own PK `audience_keyword_state_archives_id`), but this history view **exposes none of them** — it projects only 12 columns. In particular **`is_magic` is NOT available here**, so you **cannot** filter out untargetable "magic" keywords from this view. For `is_magic` / `model_version` work (e.g. separating real DS19 targeting from magic UI-only keywords), query `ui.audience_keyword_state` (bronze `integrationprod.ui_audience_keyword_state`) directly. This is the main reason to prefer the base table over the history view unless you specifically need archived versions.
- **`archive_time IS NULL` ≠ deleted vs kept** — NULL simply marks the row as sourced from the live table (current). A keyword that was *removed* from an audience appears only as an archived row (archive_time set) with no matching live row.
- **`id` is not a safe unique key** in the view (the disambiguating archive PK is dropped). De-dupe on `(id, create_time, archive_time)` if you need one row per version.
- **No partition column, no date filter possible.** Both physical tables are unpartitioned (clustered only). You cannot restrict by a partition date — every query reads the whole ~9.9M-row / ~1.16 GB (SELECT *) view. Keep queries to aggregates or narrow column projections; the cost lever is column count, not a date filter.
- **CoreDB CDC via Datastream** — rows reflect Postgres CDC snapshots; `datastream_metadata` (which would carry CDC op/soft-delete info) is dropped here, so you cannot see CDC deletes from this view.
- **is_custom/is_hidden are polarity-locked to keyword_type** (custom⇒PARENT only, hidden⇒CHILD only) — filtering `is_custom=true` implicitly restricts to PARENTs, `is_hidden=true` to CHILDren.

## Cost & partitioning notes
- **No partition filter exists** (both physicals unpartitioned) — the one lever is **column projection**. Dry-run figures: `SELECT *` (all 12 cols) = **1.161 GB** upper bound; `SELECT create_time` (one TIMESTAMP col) = **79.3 MB** — a ~15x spread. A typical 6-column aggregate over the full view billed **0.205 GB**. Never `SELECT *` for exploration; project only the columns you need.
- **Clustering:** the live half clusters on `id`, the archive half on its own (dropped) PK — so a filter on **`id`** prunes the live side at runtime (dry-run estimates do not reflect cluster pruning); a filter on `audience_id` prunes nothing. There is no clustering benefit for `audience_id`-scoped queries.
- **Backing storage (real):** live `ui_audience_keyword_state` = 791.8 MB / 5.01M rows; archive `audience_keyword_state_archives` = 874.3 MB / 4.90M rows; combined ≈ **1.666 GB / 9.91M rows** (approx_logical_bytes above).
- No TTL / partition expiration on either bronze table — full history is retained.

## Example queries
```sql
-- Current (live) DS19 targeting set for one audience — collapse history to today
SELECT keyword, keyword_type, selected, data_source_category_id
FROM `summarydata.audience_keyword_state_history`
WHERE audience_id = @audience_id
  AND archive_time IS NULL          -- live rows only
  AND keyword_type = 'CHILD' AND selected = TRUE;

-- Audit trail: every version of an audience's keywords, newest first
SELECT id, keyword, keyword_type, selected, create_time, archive_time
FROM `summarydata.audience_keyword_state_history`
WHERE audience_id = @audience_id
ORDER BY COALESCE(archive_time, TIMESTAMP '9999-12-31') DESC, create_time DESC;
```
> Need `is_magic` / `model_version` / `feedback`? This view does not expose them — query `dw-main-silver.ui.audience_keyword_state` instead.
