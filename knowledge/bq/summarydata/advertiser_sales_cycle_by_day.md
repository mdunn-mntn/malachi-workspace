# summarydata.advertiser_sales_cycle_by_day

## Purpose
Measures the **sales cycle / consideration window** for MNTN-tracked conversions: the elapsed time between a visitor's **first page view** (first observed site touch) and their **conversion**. Reach for it when you need per-conversion time-to-conversion latency (e.g. "how long between first touch and purchase for advertiser X?"), distributions of consideration windows, or new-visitor-vs-returning conversion behavior. It is **event-level**, not a daily rollup — the name's `by_day` refers only to the `day` DAY-partition, not the aggregation grain.

Do NOT reach for this to count conversions or compute advertiser daily totals — `sum_by_advertiser_by_day` / `visit_facts` / `conversion_facts` are the fact tables for that. This table's headline measure (`sales_cycle_time`) is populated for only ~3% of rows (new visitors with a matched first page view), so it is a **latency** source, not a volume source.

## Grain & keys
- **Grain:** one row per **conversion event x matched visitor identity**. The tightest empirical key is `(advertiser_id, ip, conversion_epoch)` — 62,505,757 distinct tuples in 62,505,764 rows for 2026-07-10 (only **7 duplicate rows**, ~0.00001%). `(advertiser_id, guid, conversion_epoch)` is also effectively unique but slightly looser (62,502,819 distinct, ~0.005% dups). The fan-out from `(advertiser_id, conversion_epoch)` to the row grain is over the visitor **ip/guid identity pair**, not guid alone. ~62M rows/day across 4,114 advertisers.
- **Finer than one-row-per-conversion — but key on `(advertiser_id, conversion_epoch)`, never `conversion_epoch` alone.** Raw `conversion_epoch` is NOT a conversion identity: for 2026-07-10 there are 39,997,940 distinct `conversion_epoch` but 48,039,899 distinct `(advertiser_id, conversion_epoch)` — the same microsecond is shared across **different advertisers** for ~8.0M/48.0M (**~17%**) of tuples. Collapsing on `conversion_epoch` alone merges conversions belonging to different advertisers (~17% undercount). Keyed correctly there are 62,505,764 / 48,039,899 ≈ **1.30 rows per per-advertiser conversion instant** (identity fan-out over ip/guid), not 1.56. Always dedup to at least `(advertiser_id, conversion_epoch)` before counting.
- **Key / join columns:** `advertiser_id` (→ advertisers dim), `guid` + `ip` + `ga_client_id` (visitor identity), `conversion_epoch` (the event instant, microseconds). `day` is the partition, not a key.

## Column meanings (only the non-obvious ones)
- **day** — DATE partition key. Buckets the conversion event; ~62M rows per day. This is the ONLY thing "by_day" in the name refers to (partition, not grain).
- **conversion_epoch** — the precise conversion instant in **MICROSECONDS** since Unix epoch. `conversion_epoch = UNIX_MICROS(true conversion time)`; e.g. `1783658653328841` µs = 2026-07-10 04:44:13 UTC. This, not `conversion_time`, is the authoritative sub-day timestamp.
- **conversion_time** — TIMESTAMP, but **coarsened/truncated** — do NOT trust for sub-day precision. On 2026-07-10 only 4.5% of rows had `conversion_time = TIMESTAMP(day)` and `TIMESTAMP_DIFF` between the two `_time` columns does NOT reproduce `sales_cycle_time`. Use the `_epoch` columns for any timing math.
- **first_page_view_epoch** — first observed page-view instant in **MICROSECONDS** (same anchor as `conversion_epoch`). NULL when no first page view is matched to the conversion (~97% of rows).
- **first_page_view_time** — TIMESTAMP, coarsened like `conversion_time`; use `first_page_view_epoch` for precision. NULL exactly when `first_page_view_epoch` is NULL.
- **sales_cycle_time** — FLOAT64 **seconds** (fractional, microsecond resolution) = `(conversion_epoch - first_page_view_epoch) / 1e6`. Verified: 72917184 µs diff → 72.917184 s; 986325563052 µs → 986325.563052 s (~11.4 days). **NULL for ~97% of rows** (whenever `first_page_view_epoch` is NULL). Range observed on one day: 1e-6 s to ~7.78M s (~90 days). **PROSE-DRIFT: data_catalog.md called this INTEGER seconds — live is FLOAT64 fractional seconds.**
- **is_new** — client-JS-pixel new-visitor flag (same semantics as `visits.is_new`). **Every row with a non-NULL `sales_cycle_time` has `is_new = true`** (verified: 1,820,145 non-NULL sct rows = exactly the is_new-with-sct count). So the sales-cycle measure is effectively a **new-visitor-only** metric; returning-visitor conversions carry NULL.
- **guid** — visitor GUID (same identity space as `visits.guid` / `guid_ip_log_visitors.guid`).
- **ip** — visitor IP; placeholder `0.0.0.0` appears (~0.1% of rows) for unknown IPs — filter it out for identity work.
- **ga_client_id** — Google Analytics client id; **~95% NULL** (only ~5% of rows are GA-tracked). Usable only for that GA subset.

## Joins & relationships
- **advertiser_id → `bronze.integrationprod.advertisers`** (filter `deleted=FALSE AND is_test=FALSE`). Partner grain: **1 row per advertiser (dimension)** → this side is **N:1**, fan-in safe, no fan-out. Join for `company_name` (the standard advertiser-name source; `fpa_advertiser_verticals.advertiser_name` is unreliable).
- **guid / ip → visitor fact tables** (`summarydata.visits`, `ui_visits`, `guid_ip_log_visitors`): partner side is **1:N** (a visitor GUID/IP appears in many visits/conversions) → **fan-out risk**; aggregate to visitor grain before joining. `guid_ip_log_visitors` is a GUID×IP **bridge** (many:many) — expect multiplicative fan-out; not live-verified here (prose fallback for the fan-out warning).
- **ga_client_id → GA4 client identifier** — only meaningful for the ~5% non-NULL GA subset.
- Within one advertiser the same `conversion_epoch` recurs across visitor identities (~1.30 rows per `(advertiser_id, conversion_epoch)`) — a **self fan-out**; dedup on `(advertiser_id, ip, conversion_epoch)` (tightest, 7 dup rows/62.5M) or `(advertiser_id, guid, conversion_epoch)`. **Never collapse on `conversion_epoch` alone** — it collides across advertisers (~17% of tuples share a microsecond with a different advertiser), so a bare-epoch dedup silently merges other advertisers' conversions.

## Gotchas
- **Name is misleading — NOT advertiser x day.** 8.5B rows total / ~62M per day. It is per conversion-event x visitor identity. Aggregate yourself for advertiser-daily figures.
- **~97% of rows have NULL `sales_cycle_time` and NULL `first_page_view_*`** (60,685,619 / 62,505,764 on 2026-07-10). The metric exists only for **new-visitor** conversions with a matched first page view. Never treat row count as "conversions with a sales cycle."
- **Use the `_epoch` (microsecond) columns, not the `_time` TIMESTAMP columns, for any timing.** The `_time` columns are coarsened/truncated and `TIMESTAMP_DIFF` on them does not reproduce `sales_cycle_time`.
- **Rolling ~125-day window.** Empirical range 2026-03-16 → 2026-07-18 (fresh through yesterday; today 2026-07-19) = 125 partitions. No table-level partition expiration is configured (`expirationTime` = None), so this window is a SQLMesh model artifact, not a TTL — but do not assume deep history exists.
- **SQLMesh hash rotates.** Live view currently resolves to physical `...__77792519`; `data_catalog.md` still cited `...__969350298` (stale after a rebuild). Query the clean view name `summarydata.advertiser_sales_cycle_by_day`, never a pinned hash.
- **`sales_cycle_time` type drift:** FLOAT64 fractional seconds live (prose said INTEGER).

## Cost & partitioning notes
- **Physical:** `sqlmesh__summarydata.summarydata__advertiser_sales_cycle_by_day__77792519`, TABLE, DAY-partitioned on `day`, **no clustering**, `require_partition_filter = false` (NOT enforced — easy to accidentally full-scan). numRows 8,547,250,066; numBytes 751,815,908,146 (~700 GiB backing storage).
- **THE filter to always apply:** `WHERE day BETWEEN DATE '2026-07-01' AND DATE '2026-07-10'` (bound `day`). Because the partition filter is not required, forgetting it scans all 125 partitions.
- **Dry-run cost figures (labeled by exact column set — only same-column-set figures are comparable):**
  - `SELECT day` **no filter** (day-only, all partitions): **68,378,000,528 B ≈ 63.7 GiB**.
  - `SELECT day WHERE day = '2026-07-10'` (day-only, 1 partition): **500,046,112 B ≈ 0.47 GiB** — ~137x prune vs the no-filter day-only scan (this is what confirms `day` is the partition).
  - `SELECT * WHERE day = '2026-07-10'` (all 11 cols, 1 partition): **5,502,974,457 B ≈ 5.12 GiB** — ~11x the day-only 1-partition scan; select only the columns you need.
- Avoid `SELECT *` across a wide date range (a full-table `SELECT *` would touch the full ~700 GiB backing store). Project the 2-3 columns you need and always bound `day`.

## Example queries
```sql
-- New-visitor sales-cycle distribution (days) for an advertiser over a bounded window
SELECT
  APPROX_QUANTILES(sales_cycle_time / 86400.0, 100)[OFFSET(50)] AS median_days,
  APPROX_QUANTILES(sales_cycle_time / 86400.0, 100)[OFFSET(90)] AS p90_days,
  COUNT(*) AS n_new_visitor_conversions
FROM `summarydata.advertiser_sales_cycle_by_day`
WHERE day BETWEEN '2026-07-01' AND '2026-07-10'
  AND advertiser_id = 31357
  AND sales_cycle_time IS NOT NULL;   -- ~97% of rows are NULL; this is the ~3% new-visitor set
```
