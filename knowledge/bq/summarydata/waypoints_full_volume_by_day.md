# summarydata.waypoints_full_volume_by_day

## Purpose
The Waypoints product tracks advertiser-defined multi-step conversion funnels (site/pixel events grouped
into named funnel **stages**). This view is the **full-volume** lens: it counts **every** qualifying event a
site visitor fires, not just the ones that advance a sequential funnel step. Reach for it to answer "how many
events (and how many distinct visitors/sessions) hit each funnel stage per advertiser/campaign per day" — total
volume at every stage, including ad-attributed vs organic. Use the sibling `sequential` funnel_mode slice (a
different view over the same fact) when you need step-to-step **transition** counts instead.

## Grain & keys
- **Grain:** one row per `day` × `advertiser_id` × `campaign_id` × `event_group`+`event_name` ×
  `from_verified_impression` × `current_ga_client_id` × `current_session_key` × `current_ad_served_id`. The
  row retains the visitor identity (GA client id + session), so you can compute unique visitors/sessions vs
  total events. `current_event_count_flag` is the **measure** = SUM of raw event occurrences collapsed into
  that cell (min 1, up to thousands).
- **Effective join keys:** `advertiser_id`, `campaign_id`; `(advertiser_id, event_name)` → the Waypoints
  event-mapping registry; `current_ga_client_id`/`current_session_key` = visitor identity; `current_ad_served_id`
  = served-ad impression id (populated only for ad-attributed rows).
- This view is one funnel_mode slice: a chain of SQLMesh views over base fact `waypoints_fact`, filtered
  `funnel_mode = 'full_volume'`. `funnel_mode` is therefore **constant** = `'full_volume'` here.

## Column meanings (only the non-obvious ones)
- **`current_event_count_flag`** — the volume MEASURE (misleadingly named "flag"): SUM of raw event
  occurrences for this cell, not a 0/1 boolean. Sample day 2026-07-15: min 1, max 8,765, ~2.06M total events
  across 632K rows. Sum this column, don't `COUNT(*)`, to get event volume.
- **`funnel_mode`** — constant `'full_volume'` in this view (the view hard-filters it). The base fact also
  holds a `'sequential'` mode surfaced by a sibling view.
- **`event_group` / `event_group_order` / `event_name`** — the advertiser's own funnel taxonomy, defined in
  `attr_advertiser_waypoints_event_mapping`. `event_group` = named stage ("Site Entry", "Application
  Started", "Enrollment", "Application Submitted"…); `event_group_order` = ordinal position in that
  advertiser's funnel (1 = top-of-funnel/site entry, ascending toward conversion); `event_name` = the specific
  event within the group (multiple names per group). Names are per-advertiser, so the DISTINCT set varies by
  advertiser.
- **`from_verified_impression`** — effectively **TRUE-or-NULL** (never FALSE observed). TRUE = event
  attributed to a verified MNTN ad impression (and `current_ad_served_id` is populated); NULL = not tied to a
  verified impression (organic / pixel-only site event, no served-ad id). Sample day: NULL 578,839 rows /
  1.79M events (~87%), TRUE 53,718 rows / 267K events (~13%). Because NULL dominates, use
  `from_verified_impression IS TRUE` to isolate ad-attributed volume, not `= FALSE`.
- **`current_ga_client_id`** — the site visitor's Google-Analytics / pixel client id (visitor identity), NOT a
  MNTN IP. Populated on ~99.98% of rows. **`current_session_key`** = per-session id (~81% populated).
- **`current_ad_served_id`** — the served-ad impression id; populated only where `from_verified_impression`
  IS TRUE (~8.6% of rows on the sample day). Links an event back to the ad that drove it.
- **`event_type`** — always **NULL** in this view (CAST(NULL) by construction); it only carries values in the
  sequential funnel_mode slice.
- **`previous_*`, `source_*`, `target_*` (ga_client_id, session_key, event_group, event_group_order,
  event_name), `has_target_transition`, `transition_count`** — all **constant NULL / 0** in the full-volume
  view. These are transition columns that only carry data in the `sequential` funnel_mode. Do not use them
  here; go to the sequential view for step-to-step transitions.

## Joins & relationships
- **`advertiser_id` → `bronze.integrationprod.advertisers.advertiser_id`** — dim, partner grain 1 row per
  advertiser. This view is N:1 into the dim → no fan-out. Filter `deleted=FALSE AND is_test=FALSE`; join
  `company_name` for a reliable name. Waypoints is a limited-adoption product: only ~15 advertisers appear on
  the 2026-07-15 partition (only advertisers with configured event mappings emit rows).
- **`campaign_id` → `bronze.integrationprod.campaigns.id`** — dim, 1 row per campaign. N:1 → no fan-out. Use
  `funnel_level` (not `objective_id`) for stage. Sample day: 133 distinct campaigns.
- **`(advertiser_id, event_name)` → `bronze.integrationprod.attr_advertiser_waypoints_event_mapping`** — the
  registry that DEFINES `event_group` / `event_group_order` / `event_name` per advertiser (has a `deleted`
  flag). Partner grain = 1 row per advertiser × event mapping. This view → mapping is N:1 (many event rows per
  mapping def). Fan-out risk if you don't filter `deleted=FALSE` (deleted+live versions of a mapping can both
  match) — always filter it. The view already reads this table to resolve the taxonomy.
- **`current_ad_served_id`** joins back to ad-serving/impression logs (served-ad id) for ad-attributed events
  only; **`current_ga_client_id`/`current_session_key`** are the client-side pixel identity, not joinable to
  MNTN IP-keyed tables.

## Gotchas
- **`funnel_mode` is pinned to `'full_volume'`** — filtering on it is a no-op; funnel transitions live in the
  sibling `sequential` view, not here.
- **`current_event_count_flag` is a SUM, not a flag** — SUM it for event volume; `COUNT(*)` counts identity
  cells (distinct visitor-session-event combos), not events.
- **Transition/previous/source/target columns are NULL/0 by construction** in this view — schema shows 26
  columns but ~11 of them (event_type + all previous_*/source_*/target_* + has_target_transition +
  transition_count) never carry data in the full-volume slice.
- **`from_verified_impression` is never FALSE** — it's TRUE or NULL. NULL ≠ "unverified event that was
  checked and failed"; it means "not tied to a verified impression at all" (organic/pixel). Treat NULL as the
  non-ad-attributed bucket.
- **Rolling retention window** — the base fact `waypoints_fact` currently holds only 2026-02-10 → 2026-07-19
  (160 daily partitions, ~5 months). Older days are not queryable; no long historical backfill. (No BQ
  partition-expiration TTL is set — expirationMs is None; the window is SQLMesh incremental retention.)
- **View chain** — `waypoints_full_volume_by_day` (view) → `waypoints_stage_daily` (view, aggregates &
  filters `funnel_mode`) → base fact `waypoints_fact`. SQLMesh physical metadata on the intermediate views
  reads numRows:0 / partition:None because they are views; the real partition/cluster/TTL live on
  `waypoints_fact` only.

## Cost & partitioning notes
- **Always filter `day`** (DATE, `require_partition_filter=TRUE` — propagates from the base fact; an unfiltered
  query errors "Cannot query over table … without a filter over column(s) 'day'"). `day` is the sole
  partition; confirmed empirically (dry-run bytes scale linearly with the day range).
- **Backing physical:** base fact `sqlmesh__summarydata.summarydata__waypoints_fact__2720337691` = **~42.5 GB /
  187,051,929 rows** (bq show numBytes, ALL funnel_modes + all base columns + 160 partitions). Clustered on
  `advertiser_id, campaign_id, funnel_mode` — so within this view (funnel_mode pinned), the useful cluster
  keys are `advertiser_id` then `campaign_id`; add them to prune further.
- **Dry-run cost, labeled by column set (2026-07-15 one partition):**
  - `SELECT *` (all 26 cols), 1 day → **359.0 MB** upper bound; 3 days (07-13..07-15) → **996.4 MB** (~332
    MB/day, linear).
  - `SELECT day` only, 1 day → **339.7 MB** — column pruning barely helps (~5% off SELECT *) because the view
    must scan most base-fact columns to run its aggregation. **The `day` filter is the dominant cost lever,
    not the column list.**
  - Representative slice size: ~632K rows / ~2.06M events for one day across ~15 advertisers.

## Example queries
```sql
-- Daily event volume + distinct visitors per funnel stage for one advertiser
SELECT day, advertiser_id, event_group, event_group_order,
       SUM(current_event_count_flag)         AS events,
       COUNT(DISTINCT current_ga_client_id)  AS visitors,
       COUNTIF(from_verified_impression IS TRUE) AS ad_attributed_rows
FROM `summarydata.waypoints_full_volume_by_day`
WHERE day BETWEEN '2026-07-13' AND '2026-07-15'
  AND advertiser_id = 31357         -- also filters the cluster key
GROUP BY 1,2,3,4
ORDER BY day, event_group_order;
```
