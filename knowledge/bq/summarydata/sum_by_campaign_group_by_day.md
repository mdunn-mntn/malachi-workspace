# summarydata.sum_by_campaign_group_by_day

## Purpose
Daily pre-aggregated KPI rollup at **campaign-group** grain — impressions, media cost/spend, VAST/video engagement, conversions and order value under **multiple attribution models**, plus HLL uniques/reach sketches. SQLMesh-derived VIEW over a single day-partitioned physical table; full history back to **2024-01-01**. Reach for it for campaign-group daily reporting, budget pacing ("% to cap"), ROAS/CPA, and pre/post experiments that need a long pre-period. It is the campaign-group sibling of `sum_by_campaign_by_day` (campaign grain) and `sum_by_advertiser_by_day` (advertiser grain, which additionally exposes `raw_*` un-attributed metrics) — all three carry the same measure column set and go back to 2024-01-01.

## Grain & keys
- **Grain:** one row per **(campaign_group_id, day)**. Verified 2026-07-15: 4,134 rows = 4,134 distinct `campaign_group_id` = 4,134 distinct `(advertiser_id, campaign_group_id)` pairs, and every `campaign_group_id` maps to exactly one `advertiser_id` (max advertisers per CG = 1).
- **Natural key:** `campaign_group_id` + `day`. `advertiser_id` is a **denormalized attribute** (functionally determined by `campaign_group_id`) — convenient for filtering, not part of the key.
- **Scale:** 3,150,811 rows / 29,860 distinct campaign groups across full history (2024-01-01 → present).
- **No `campaign_id` / `funnel_level` here** — already collapsed to the group. For stage (funnel_level) splits use the sibling `sum_by_campaign_by_day` (campaign_id → `campaigns`).

## Column meanings (only the non-obvious ones)

**HLL sketches — NOT integer counts.** `uniques`, `site_visitors`, `new_site_visitors`, `existing_site_visitors`, `new_users_reached`, `existing_users_reached`, and the `competing_*_site_visitors` / `probattr_*_site_visitors` mirrors are **BYTES HLL++ sketches** (~23–33 KB per row; verified 2026-07-15: `uniques` = 32,791 bytes, `site_visitors` = 23,286 bytes on a top-impression row). Never CAST or SUM them as numbers — merge/estimate with `HLL_COUNT.MERGE` / `HLL_COUNT.EXTRACT`. These BYTES columns dominate the row's storage and are the reason `SELECT *` costs ~855x a narrow scalar column for the same day (see Cost notes).

**`day`** — DATE partition column and the **only** time column. Native DATE, no epoch decoding; there are **no INT epoch columns** in this table.

**Cost vs spend.** `media_cost` is the **cost-side** figure used for budget pacing — "CGID Daily % to Cap" = `media_cost` ÷ DSO daily budget cap (AUDI-1070). `media_spend` / `data_spend` / `platform_spend` are the **spend-side**; total spend = the sum of those three. `video_spend` is BIGNUMERIC.

**Attribution-variant column families — separate models, NOT additive buckets; never SUM across families** (verified AUDI-1070, Avon AID 31921):
- **Default** (`views, clicks, view_conversions, click_conversions, view_order_value, click_order_value`) — **INCLUDES CTV** (a CTV view-conversion is a `view_conversion`).
- **`last_touch_*` vs `last_tv_touch_*`** — two SEPARATE last-touch models (overall/display vs TV). They can credit the same conversion to different groups; they coincide only at the account total and **diverge per stage**. Not subsets, not additive.
- **`competing_*`** — the industry_standard (**first-touch**) attribution variant.
- **`probattr_*`** — the **probabilistically-attributed** variant (full mirror of the deterministic outcome columns incl. `competing` mirrors); the right surface for ROAS/CPA modeling on non-last-touch signal.
- **`conversions_assist_*` / `visits_assist`** — multi-touch **assist** credit.

**Impression / video splits.** `display_impressions` vs `video_impressions` = display vs CTV/video split of `impressions`. `vast_start / vast_firstquartile / vast_midpoint / vast_thirdquartile / vast_complete` = VAST quartile completion counts (VCR = `vast_complete / vast_start`). `view_impressions` / `view_viewed` / `view_untrackable` = viewability instrumentation counts for view-through.

**Dropped in the BQ migration (TI-832, 2026-05-05):** `data_cost`, `fee_cost`, `partner_cost`, and `legacy_spend` were **removed** from this view (the `*_spend` columns replace them). Any `SELECT *` followed by an explicit `*_cost` / `legacy_spend` projection will crash.

## Joins & relationships
This is a **terminal rollup** — it does not fan out into event/fact tables. Join it to dimensions on its two keys:
- **`campaign_group_id` → `bronze.integrationprod.campaign_groups`** — dim, **1:1** per group (filter `deleted=FALSE AND is_test=FALSE`). Gives `product_id` (1=PTV / 2=Select / 3=QuickFrame) and nominal `budget`. No fan-out (dim side unique).
- **`advertiser_id` → `advertisers`** (`company_id`/`company_name`) — **1:1** for names. Prefer `advertisers.company_name`; `fpa_advertiser_verticals.advertiser_name` is unreliable (empty since 2025-12).
- **Campaign / stage detail:** this view has no `campaign_id` or `funnel_level`. To split by campaign or funnel stage, use the sibling `sum_by_campaign_by_day` (`campaign_id` → `campaigns` for `campaign_group_id` + `funnel_level`). That sibling is **1:N** to this one (many campaigns per group).
- **DSO pacing:** `campaign_group_id` → `bronze.integrationprod.dso_campaign_group_daily_budgets.budget` (latest per CG by `update_time`; current-row-only table, no history) for "% to cap". **Filter to active CGs** — paused groups carry a stale tiny daily cap ($8–38) with 0 delivery and drag the ratio down.
- **Fresher / finer source:** the underlying hour-grain facts `silver.summarydata.{impression_facts, visit_facts, conversion_facts, spend_facts}` stay fresh through the current day (use these when this rollup lags or you need sub-day grain).

## Gotchas
- **HLL BYTES columns are not integers** (`uniques`, `site_visitors`, `*_users_reached`, `competing_*_site_visitors`, `probattr_*_site_visitors`) — see Column meanings. `HLL_COUNT.MERGE` to combine, never SUM.
- **Attribution variants are NOT additive** — never SUM across default / `last_touch_*` / `last_tv_touch_*` / `competing_*` / `probattr_*` / `*_assist_*`. They are alternative models of the same conversions.
- **`media_cost` ≠ `media_spend`** — pacing "% to cap" is in **media-cost** terms; total delivered spend is `media_spend + data_spend + platform_spend` (AUDI-1070/1089).
- **Dropped `*_cost` / `legacy_spend` columns** (TI-832) — `SELECT *` + explicit `*_cost` projection crashes.
- **Staleness — re-checked fresh as of 2026-07-29.** The 2026-05-01 note ("~17-day lag; max=2026-04-14") no longer holds: `max(day) = 2026-07-29` = current day (941 dated partitions). The latest partition may be a partial/UTC-forward day. Still `MAX(day)` before recent-window use and treat the newest day as possibly incomplete; for guaranteed same-day/hour-grain freshness use the `*_facts` tables.
- **`require_partition_filter=True`** — a query with no `day` filter **errors** ("Cannot query over table ... without a filter over column(s) 'day'"); this propagates through the view.
- **BQ view vs deprecated Greenplum table.** A same-named Greenplum coreDW table exists but coreDW is EOL **2026-04-30** — use this BQ SQLMesh view.

## Cost & partitioning notes
- **Partition:** `day` (DATE, **DAY** grain), `require_partition_filter=True`. **No clustering. No partition-expiration TTL** — full history retained back to 2024-01-01.
- **THE one filter to always apply:** `WHERE day BETWEEN <start> AND <end>` (required — unfiltered queries error).
- **Physical backing storage (2026-07-29):** 3,191,724 rows / **65,852,160,329 bytes (~61.3 GiB)** — `bq show` numBytes on physical `sqlmesh__summarydata.summarydata__sum_by_campaign_group_by_day__272419159` (a real TABLE, not a nested view); 941 dated partitions + 1 empty `__NULL__`.
- **Dry-run scan estimates (labeled by column set — only same-column-set figures are comparable):**
  - 1 day, one narrow scalar col (`advertiser_id`): **73,120 bytes (~73 KB)**.
  - 1 day, `SELECT *`: **62,538,859 bytes (~62.5 MB)** — **~855x** the narrow col; the BYTES HLL columns are the entire difference.
  - 30 days, `SELECT *`: **2,177,351,212 bytes (~2.18 GB)**.
- **Prune hard:** filter `day` AND project only the columns you need. Never `SELECT *` unless you actually need the HLL sketches — selecting scalar measures instead cuts scan by ~3 orders of magnitude.

## Example queries
```sql
-- Campaign-group daily KPIs (project scalars only; day filter mandatory)
SELECT advertiser_id, campaign_group_id, day,
       impressions, display_impressions, video_impressions,
       media_cost, media_spend + data_spend + platform_spend AS total_spend,
       views, view_conversions, view_order_value               -- DEFAULT attribution (incl. CTV)
FROM `dw-main-silver.summarydata.sum_by_campaign_group_by_day`
WHERE day BETWEEN DATE '2026-06-01' AND DATE '2026-06-30'
  AND campaign_group_id = <cg_id>;

-- Unique reach across a window: HLL merge, never SUM the BYTES column
SELECT campaign_group_id,
       HLL_COUNT.MERGE(site_visitors) AS site_visitors_est
FROM `dw-main-silver.summarydata.sum_by_campaign_group_by_day`
WHERE day BETWEEN DATE '2026-06-01' AND DATE '2026-06-30'
GROUP BY campaign_group_id;
```
