# summarydata.waypoints_fact

## Purpose
The canonical fact for **Waypoints** — MNTN's configurable on-site conversion-funnel / multi-step
event product. An advertiser defines a funnel as an ordered set of **stages** (`event_group` +
`event_group_order`), each stage containing named **events** (`event_name`) that fire either on a URL
match (`event_type='URL'`) or a GA4 dataLayer event (`event_type='DLV'`). This view is the flattened,
day-partitioned fact behind stage-completion, event-volume, and step-to-step **transition** (funnel-drop)
reporting.

Each row is one waypoint event occurrence carried with three temporal contexts around the current step:
the **previous step** the user came from (`previous_event_*`), the **current step**
(`event_*` = `source_event_*`), and the **next step** they transitioned to (`target_event_*`). Reach for
it to build funnel/stage dashboards, compute step conversion & transition rates, and split organic vs.
ad-driven (MNTN-served) funnel activity. It is an **additive** fact — SUM the count flags; never COUNT rows.

## Grain & keys
- **Grain:** one **additive** row per waypoint event occurrence, dimensioned by
  `day × advertiser_id × campaign_id × funnel_mode × event_type × current step × transition-context`.
  There is **no unique key** — on 2026-07-17 the full dimension tuple collapsed to 887,086 distinct
  combos across 4,626,305 rows (~5.2x repetition, e.g. a session re-firing the same step). Treat it as
  an additive fact: `SUM(current_event_count_flag)` to count events, `SUM(transition_count)` to count
  step transitions. **Never `COUNT(*)` for volume.**
- **Identity keys (user/session):**
  - `current_user_key` = `'{advertiser_id}|{ga_client_id}'` (1:1 with `current_ga_client_id` within an advertiser).
  - `current_session_key` = `'{advertiser_id}|{ga_client_id}|{session_epoch_seconds}'` — one browsing session.
  - `current_ad_served_id` = the MNTN ad-serve UUID when the waypoint is ad-attributed (else NULL).
- **Reporting dimensions:** `advertiser_id`, `campaign_id` (0 when organic), `funnel_mode`, `event_type`,
  `event_group` + `event_group_order` (stage), `event_name` (event within stage; `'*'` = group-level/any).
- **Always filter `day`** (partition, `require_partition_filter=true`).

## Column meanings (only the non-obvious ones)
- **`day`** — DATE partition column (the only temporal column; there is **no integer epoch column** in this
  table — the unix-seconds timestamp visible inside `current_session_key` is embedded in a STRING, not a typed field).
- **`funnel_mode`** — reporting mode of the row: `'full_volume'` (every occurrence of the event is counted,
  regardless of funnel order) vs `'sequential'` (the occurrence is counted only when it happened in the
  configured stage order). The **same** physical event can appear under both modes → do not sum across modes.
- **`event_type`** — how the event was captured: `'URL'` (page-URL match) or `'DLV'` (GA4 dataLayer variable).
- **`event_group` / `event_group_order`** — the advertiser-defined funnel **stage** name and its 1-based ordinal
  position in the funnel. `event_group_order` is per-advertiser (small ints, e.g. 1..5).
- **`event_name`** — the specific event inside the stage; `'*'` is a **wildcard** meaning "any event in this group"
  (group-level rollup rows).
- **`is_step_start`** — 1 when this row marks the start/entry of a step occurrence (used to count step entries),
  else 0.
- **`current_event_count_flag`** — the **additive count measure**; SUM it to count events. Observed always `1`
  on the sampled day (each row = one counted event).
- **`has_target_transition` / `transition_count`** — a forward step-to-step transition indicator. On the sampled
  day `has_target_transition = 1` **iff** `transition_count > 0`, and `transition_count ∈ {0,1}`. SUM
  `transition_count` to count transitions from the current/source step to the `target_*` step.
- **Source vs. current vs. previous vs. target (the four step-contexts):**
  - `event_*` = **current** step of this row.
  - `source_event_*` = the **from-side** of the transition; equals the current step (`source_event_group` ==
    `event_group`, etc.). `source_event_name='*'` = group-level.
  - `target_event_*` = the **next** step the user transitioned **to** (forward). NULL when no transition
    (`has_target_transition=0`).
  - `previous_event_*` = the step the user came **from before** arriving at the current step (backward context).
    Independent of `source/target`; can be NULL (session start / first step).
- **`previous_ga_client_id` / `previous_session_key`** — identity of the prior step's session; frequently NULL
  (the previous step is often same-session, so these carry cross-session lineage only when it applies).
- **`campaign_id`** — MNTN campaign the waypoint is attributed to, **0 when organic** (no ad). Present
  (`>0`) **exactly** when `current_ad_served_id IS NOT NULL` (see Joins).
- **`group_id`** — campaign-group id; observed **0 for 100% of rows** on the sampled day (effectively
  unpopulated in current data — do not rely on it as a filter).
- **`from_verified_impression`** — BOOL that is only ever `TRUE` or `NULL` (never `FALSE`). `TRUE` marks a
  waypoint tied to a **verified** MNTN ad impression; it is a strict subset of ad-served rows (6,865 ad-served
  rows on the sampled day had `campaign_id>0` but `from_verified_impression` NULL).

## Joins & relationships
- **`advertiser_id` → `integrationprod.advertisers.id`** (dim, 1:1 from the fact side; filter
  `deleted=FALSE AND is_test=FALSE`). Join for `company_name` (the reliable advertiser label). Safe.
- **`campaign_id` → `integrationprod.campaigns.id`** (dim, 1:1 from the fact side) — only meaningful for
  ad-attributed rows (`campaign_id>0`). ~86% of rows are organic (`campaign_id=0`) and will not match a
  real campaign. `campaign_id>0` ⟺ `current_ad_served_id IS NOT NULL` **exactly** (verified 2026-07-17:
  0 rows with campaign>0 & ad_served NULL, 0 rows with campaign=0 & ad_served non-NULL).
- **`current_ad_served_id`** — the MNTN ad-serve UUID; the linkage to the served-impression / attribution
  side (ad-served waypoints only). Populated on ~14% of rows.
- **Funnel/event-mapping config:** stage & event definitions here originate from the advertiser's Waypoints
  pixel config — see `attr_advertiser_waypoints_event_mapping` + `attr_advertiser_selective_performance_config`
  (event-name classification; carry a `deleted` flag) and `core_pixel_integrations` for the pixel wiring.
- **Fan-out warning:** this fact is **not** 1:1 with any session/user/event — a single session yields many
  rows and dimension tuples repeat (~5x). Any join to it fans out on the fact side; always **pre-aggregate**
  (SUM the count flags at your reporting grain) *before* joining to a per-session or per-user dim to avoid
  double-counting. Joining the same physical event across both `funnel_mode` values also double-counts.

## Gotchas
- **Additive, not unique — never `COUNT(*)`.** Dimension tuples repeat ~5x. Volume = `SUM(current_event_count_flag)`;
  transitions = `SUM(transition_count)`. `COUNT(*)` overstates everything.
- **`funnel_mode` double-counts if summed together.** `full_volume` and `sequential` are two views of the
  same events. Pick one (`sequential` for ordered-funnel completion; `full_volume` for raw event volume) —
  never aggregate across both.
- **`campaign_id=0` / `group_id=0` are sentinels, not real ids.** `campaign_id=0` = organic (no MNTN ad).
  `group_id` was `0` for 100% of sampled rows — treat as unpopulated.
- **`from_verified_impression` is TRUE-or-NULL** (never FALSE). `WHERE from_verified_impression` keeps only
  verified-impression rows; `IS NULL` mixes organic + unverified-ad rows. It is stricter than "has a
  `campaign_id`".
- **`event_name='*'` are group-level wildcard rows.** Including them alongside named-event rows can
  double-count if you're rolling up by stage — decide whether you want per-event or per-stage granularity.
- **Young table:** partitions run **2026-02-10 → present** (160 daily partitions as of 2026-07-19). No history
  before Feb 2026 — do not use it for long pre-period baselines.
- **No partition TTL** (`expirationTime` null) — but the partition filter is **mandatory** (query errors
  without a `day` predicate).
- **Advertiser-authored labels are messy** — `event_group` values are free-text from the advertiser (e.g.
  the literal typo "Application & Credit Verifcation"); don't assume a clean controlled vocabulary across advertisers.

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE day = '<date>'` (or a tight `BETWEEN`). Partition = `day` (DATE,
  DAY), `require_partition_filter=true` — a query with **no** `day` predicate hard-errors (verified: "Cannot
  query over table … without a filter over column(s) 'day'").
- **Cluster** = `advertiser_id, campaign_id, funnel_mode`. Add an `advertiser_id` (and `funnel_mode`) predicate
  to prune within a partition.
- **Labeled dry-run figures (all same-partition unless noted):**
  - `SELECT *`, one day (`day='2026-07-17'`): **1.169 GB** (dry-run) / 1.089 GB billed (actual).
  - 4 narrow cols (`advertiser_id, campaign_id, funnel_mode, current_event_count_flag`), one day: **0.207 GB**
    — ~5.6x cheaper than `SELECT *` on the same partition. Select only the columns you need.
  - `SELECT *`, 7-day range (`2026-07-11..17`): **3.769 GB** (dry-run) — days vary in size; not a flat 7x.
- **Physical backing:** 187,051,929 rows / 42,537,927,068 bytes (~39.6 GiB) across 160 daily partitions
  (single physical `sqlmesh__summarydata` table; not a UNION view).

## Example queries
```sql
-- Stage-completion volume for one advertiser, sequential funnel, one day (additive: SUM the flag)
SELECT event_group_order, event_group,
       SUM(current_event_count_flag) AS events,
       SUM(transition_count)         AS transitions_out
FROM `summarydata.waypoints_fact`
WHERE day = '2026-07-17'
  AND advertiser_id = 38710
  AND funnel_mode = 'sequential'
GROUP BY 1, 2
ORDER BY event_group_order;

-- Step-to-step transition (drop) matrix for one advertiser-day
SELECT source_event_group, target_event_group, SUM(transition_count) AS n
FROM `summarydata.waypoints_fact`
WHERE day = '2026-07-17' AND advertiser_id = 38710
  AND funnel_mode = 'sequential' AND has_target_transition = 1
GROUP BY 1, 2 ORDER BY n DESC;

-- Ad-attributed vs organic funnel activity (campaign_id>0 <=> ad-served)
SELECT IF(campaign_id > 0, 'ad_served', 'organic') AS attribution,
       SUM(current_event_count_flag) AS events
FROM `summarydata.waypoints_fact`
WHERE day = '2026-07-17' AND advertiser_id = 38710
GROUP BY 1;
```
