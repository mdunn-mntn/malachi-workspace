# summarydata.unstable_conversion_facts

## Purpose
**NON-canonical staging / experimental copy of `conversion_facts`.** Same hourly conversion-metric
grain and the identical measure set as the stable `summarydata.conversion_facts`, plus one extra
column — `change_id` — which it also clusters on. It is **not** a full parallel copy: for a given
day it holds a small *subset* of the stable table's rows (2026-07-15: **5,592 rows here vs 85,616 in
stable `conversion_facts`**, ~6.5%; ~7.7% of the day's `view_order_value`). Treat it as SQLMesh
change-tracking scratch — do **not** use it for reporting, ROAS, CVR, or any advertiser-facing
number. **Reach for `summarydata.conversion_facts` (or `all_facts`) instead.** The only reason to
open this table is to inspect the `change_id` CDC batch mechanics or debug the unstable/staging model
itself. (No prose oracle existed for this table in `data_catalog.md` / `data_knowledge.md` — this doc
is enriched from the live schema + empirical sampling and the stable-sibling prose.)

## Grain & keys
- **Grain:** one row per **`hour` (DATETIME, hour-truncated) × full dimension tuple**. The dimension
  tuple = the 20 leading dims: `hour, advertiser_id, campaign_group_id, campaign_id, channel_id,
  objective_id, group_id, creative_id, private_marketplace_id, country, metro_id, region, city,
  postal_code, domain, supply_vendor, device_type, conversion_type, conversion_source_id, pa_model_id`.
  Everything after `pa_model_id` is a measure; `change_id` is a per-row stamp (see below).
- **Verified unique (2026-07-15):** rows for the day = `5,592` = distinct dimension tuples = `5,592`.
  So **each dimension tuple appears exactly once — `change_id` does NOT version/duplicate rows.** No
  "take latest change_id" dedup is needed; the tuple is the natural key.
- **Key(s) / join columns:** the dimension tuple. For joins, the practical keys are
  `hour + advertiser_id + campaign_id (+ finer geo/creative dims)` and `conversion_source_id` /
  `pa_model_id` (attribution config). No surrogate PK column.

## Column meanings (only the non-obvious ones)
- **`hour`** — DATETIME (civil time, no zone), truncated to the hour; this is the **partition column**.
  Not an epoch INT, so no unit anchor applies (front-matter `time_unit: datetime`). NOTE: the AUTO:SCHEMA
  here is DATETIME; the stable-sibling prose in `data_catalog.md` still says `conversion_facts.hour` is
  TIMESTAMP, but the live schema of BOTH is now **DATETIME** (drift reconciled — see Changelog).
- **`change_id`** — INT64 **CDC/incremental batch-sequence stamp** identifying the SQLMesh load batch
  that emitted the row (also the second cluster key). Monotonic-ish: observed range `61,264 → 66,629`
  with `1,363` distinct values over the ~110-day span; on a single day 5,592 rows carry `462` distinct
  change_ids. It is a *stamp*, not a version — it does not create duplicate rows per dimension tuple
  (see Grain). Present here but **absent from stable `conversion_facts`** — it is the one column that
  makes this the "unstable" copy. Do not treat it as a business dimension.
- **`conversion_source_id`** — pixel/source registry id (joins to `bronze.integrationprod.conversion_sources`
  / `advertiser_conversion_types`). Empirically small domain here — 3 distinct all-time; July-2026 window
  dominated by `23` (guid_log "Website Event", the post-2025 standard pixel), with `61` (only ~3
  advertisers) also present.
- **`conversion_type`** — advertiser-defined free-string conversion label (246 distinct values), NOT an
  enum. `conversion_source_id` is the stable numeric key; `conversion_type` is the human name.
- **`pa_model_id`** — probabilistic-attribution model id; uses **sentinel/negative** values here
  (`-7` dominant, `1002` secondary) — do not assume positive ids. Only the `probattr_*` measures are
  keyed to it.
- **Measure families (identical to stable `conversion_facts`; all conversion counts are scalar INT,
  all `*_order_value` are NUMERIC in whole USD — NOT micros, do not ÷1e6):**
  - `click_conversions` / `view_conversions` (+ `_order_value`) — default (last-touch) click/view credit.
  - `last_touch_*` — display/overall last-touch attribution model.
  - `last_tv_touch_*` — **separate** TV-last-touch model; NOT a subset of `last_touch_*` and **not
    additive with it** (adding them double-counts conversions exposed to both a display and a TV touch).
  - `conversions_assist_*` — multi-touch assist credit.
  - `competing_*` — the **first-touch / `industry_standard`** variant (CHAPI labels these
    FirstTouch\*); rows where the advertiser was NOT the attributed touch. Adding `competing_view_*`
    onto the default cols is how the client-UI `industry_standard` number is reconstructed.
  - `probattr_*` — probabilistic-attribution variant (keyed to `pa_model_id`).
- **NULL semantics:** any measure can be NULL/0 for a tuple where that attribution flavor produced no
  credit; finer geo dims (`metro_id`, `city`, `postal_code`, `region`) can be NULL for coarse rows.

## Joins & relationships
- **Stable sibling `summarydata.conversion_facts`** (the canonical version): same dimension + measure
  columns (stable = 52 cols, this = 53 = the 52 + `change_id`). Relationship is **subset**, not 1:1 —
  this table holds only a fraction of stable's rows per day, so do NOT join/union them expecting
  coverage; prefer stable outright. (Stable clusters on `advertiser_id, campaign_id`; this one swaps
  `campaign_id → change_id` in the cluster.)
- **`advertisers` / `campaigns` / `campaign_groups`** (`bronze.integrationprod`, dims are 1:N parent →
  many fact rows) — join `advertiser_id` / `campaign_id` / `campaign_group_id` for names/verticals.
  Filter dims `deleted=FALSE AND is_test=FALSE`. Fan-out is on the dim side (one advertiser → many
  fact rows); joining the dim onto the fact does not multiply fact rows.
- **`conversion_sources` / `advertiser_conversion_types`** (`bronze.integrationprod`) — decode
  `conversion_source_id` (1:N registry → facts; safe direction).
- **`geo_*` / metro dims** — `metro_id`, `country`, `region`, `city`, `postal_code` are already
  denormalized on the row; usually no join needed.
- **Fan-out warning:** because a given day is a *partial subset* of stable conversion_facts, any
  reconciliation join against `conversion_facts`, `visit_facts`, `spend_facts`, or `all_facts` will
  silently under-report. Never treat this table as a complete conversion source in a multi-fact join.

## Gotchas
- **NON-CANONICAL — do not report from it.** It is a staging/experimental partial copy (~6.5% of
  stable `conversion_facts` rows for a sampled day). Advertiser-facing metrics from here will be wrong
  (too low). Use `conversion_facts` / `all_facts`.
- **`change_id` is a stamp, not a version** — grain is already unique per dimension tuple (verified),
  so there is no `QUALIFY ROW_NUMBER()`/latest-change_id dedup to perform. Do not GROUP BY or filter on
  `change_id` expecting it to disambiguate duplicate business rows.
- **`last_touch_*` + `last_tv_touch_*` are NOT additive** — summing them double-counts any conversion
  seen on both a display and a TV touch (each model credits it separately). Same trap documented for
  stable `conversion_facts`.
- **`competing_*` = first-touch / industry_standard**, not "extra" conversions — needed to rebuild the
  client-UI `industry_standard` figure, but only for advertisers on that reporting style.
- **`*_order_value` are whole USD (NUMERIC), not micros** — do not divide by 1e6.
- **Retention observed ~110 days** (min `hour` = 2026-04-01, max = 2026-07-19 = current hour) — no TTL
  is set in the physical table metadata, so the ~110-day floor is an *observed rolling window*, not a
  guaranteed contract; re-check `MIN(hour)` before relying on any older date.
- **Fresh, unlike the sum_by_* rollups** — this table tracks through the current hour (not lagged).
- **`hour` is DATETIME (no timezone)** — treat as the pipeline's civil hour; do not apply a TZ offset.
- **Physical hash churns** — `bq show --schema` on the versioned physical
  (`sqlmesh__summarydata.summarydata__unstable_conversion_facts__<hash>`) can 404 after a SQLMesh
  rebuild; always inspect via the clean view name `summarydata.unstable_conversion_facts`.

## Cost & partitioning notes
- **Partition = `hour` (DATETIME, DAY granularity); cluster = `advertiser_id, change_id`;
  `require_partition_filter = false`** (not enforced — but always filter anyway). Resolved from the
  physical table `sqlmesh__summarydata.summarydata__unstable_conversion_facts__4183553511`
  (TABLE; `numRows` 351,067; `numBytes` 207,309,382).
- **The one filter to always apply:** `WHERE hour >= DATETIME('start') AND hour < DATETIME('end')`.
  Add `advertiser_id IN (...)` to lean on clustering.
- **Dry-run figures (each labeled by column set — only compare same-column-set):**
  - `SELECT *`, no filter → **207.3 MB** (207,309,382 B — equals full `numBytes`, whole table).
  - `SELECT *`, one day (`hour` 2026-07-15) → **3.31 MB** (3,309,613 B) — partition pruning **~63×**,
    confirms `hour` is the partition column.
  - `SELECT hour, advertiser_id, change_id` (3 narrow cols), no filter → **8.43 MB** (8,425,608 B) —
    column pruning ~24.6× vs `SELECT *`.
- **This is a tiny table (~207 MB total)** so even a full scan is cheap, but keep the `hour` filter and
  a narrow column list as habit; `SELECT *` over the whole table is ~25× more bytes than a 3-column read.
- `approx_logical_bytes` = 207,309,382 (single physical table `numBytes` — real backing storage).

## Example queries
```sql
-- NOTE: staging/non-canonical. For real reporting use summarydata.conversion_facts instead.
-- Inspect the change_id batch mechanics for one day (partition-pruned, narrow cols):
SELECT hour, advertiser_id, change_id, conversion_source_id, pa_model_id,
       click_conversions, view_conversions, competing_view_conversions, view_order_value
FROM `summarydata.unstable_conversion_facts`
WHERE hour >= DATETIME('2026-07-15') AND hour < DATETIME('2026-07-16')
  AND advertiser_id = 12345          -- leans on clustering
ORDER BY change_id DESC
LIMIT 100;
```
