# summarydata.visits

## Purpose
The row-level log of **Verified Visits (VVs)** — a user who saw/clicked an MNTN ad and later visited the
advertiser's site, with the visit attributed back to a served impression. This is the **source of truth for
the headline visit-rate KPI** (visits ÷ impressions) and the raw input behind the `sum_by_*` visit rollups
and `visit_facts`. Reach for it when you need per-visit detail: the served ad (`ad_served_id`), the visit vs
impression IP, cross-device flags, click-vs-view, new-to-brand, and the impression→visit latency. For
client-UI-matching visit counts, filter `from_verified_impression = TRUE`. **`ui_visits` is NOT the same
rows as `visits`** — it is a filtered `UNION ALL` of two sources (verified 2026-07-19 from the live view
DDL): branch 1 = `visits` restricted to `(campaigns.objective_id = 4 OR a prospecting campaign group) AND
from_verified_impression IS TRUE AND domain IS NOT NULL`; branch 2 draws from a **different** table,
`summarydata.last_tv_touch_visits` (last-TV-touch rows absent from `visits`). It also CIDR-strips
`ip`/`impression_ip` (`split(x,'/')[OFFSET(0)]`) and adds computed columns (`visit_day`, `source_type`,
`is_competing`, `is_pa`, `attribution_model_type_id`). Counts differ: on 2026-07-10 `visits` = 1,301,811 vs
`ui_visits` = 1,266,584. Do not treat them as interchangeable — see Joins.

## Grain & keys
- **Grain:** one row per **attributed site visit (VV)**. Every row carries a non-null `ad_served_id`
  (100% on 2026-07-10), i.e. a visit is always tied to a served impression. A single served impression can
  produce **more than one** visit row, so the grain is "attributed visit event", not "impression".
- **Key(s) / join columns:** No single clean primary key. On 2026-07-10 (1,301,811 rows):
  `ad_served_id` is **98.1%** unique (1,277,944 distinct), `impression_id` is unique among the ~97% of rows
  that have it but is **NULL on ~2.6%** (34,491 rows ≈ the non-verified subset), and the composite
  `(advertiser_id, ad_served_id, time)` is **~99.0%** unique (1,288,831 distinct). Treat `ad_served_id` as
  the join key to impressions and dedup on `(advertiser_id, ad_served_id, time)` if you need row uniqueness.
- **Join columns:** `ad_served_id` → `logdata.impression_log`; `guid` + `advertiser_id` → visitor/conversion
  matching.

## Column meanings (only the non-obvious ones)
- **`time`** — visit timestamp (TIMESTAMP, UTC); the **partition key** (DAY on `DATE(time)`).
- **`epoch`** — visit time in **MICROSECONDS** since Unix epoch (magnitude ~1.78e15; not ms, not ns). It is
  the **higher-precision** of the two visit-time columns: `epoch` keeps full sub-second µs, but `time` is
  floored to the whole second on ~54% of rows, so **`epoch != UNIX_MICROS(time)` on the majority**
  (2026-07-10: 705,275/1,301,811 = 54.2% mismatch, MAX(ABS(diff)) = 999,998 µs ≈ 1s; only 45.8% equal). Use
  `epoch` (not `time`) for sub-second ordering/dedup, and never assume `epoch = UNIX_MICROS(time)`.
- **`impression_time` / `impression_epoch`** — the *attributed* impression's timestamp. `impression_epoch`
  is also **MICROSECONDS**, and here the equality **does** hold: `impression_epoch = UNIX_MICROS(impression_time)`
  on 99.99% of non-null rows (2026-07-10: 1,267,320 equal vs 163 off; NULL on the ~2.6% non-verified subset).
  This is the asymmetry with `epoch` above — `impression_time` keeps sub-second precision, plain `time` does
  not. `impression_time` precedes `time` — often by hours (CTV, same-day) up to **2–4 weeks** (display; see
  Gotchas).
- **`elapsed_time`** (INTERVAL) — impression→visit latency (`time − impression_time`).
- **`recency_elapsed_time`** (INTERVAL) — recency window measure; separate from `elapsed_time`.
- **`ad_served_id`** — the **served impression** this visit is attributed to (last-touch). Join key to
  `logdata.impression_log`. Non-null on 100% of rows.
- **`first_touch_ad_served_id`** — the *first-touch* impression's ad_served_id in the journey (vs
  `ad_served_id` = last-touch). **NULL on ~53% of rows** (2026-07-10: 689,754/1,301,811) — first-touch
  coverage collapsed platform-wide in 2024-Q3→Q4 (FT-null jumped to ~65–75%; see data_knowledge §5d/§5f). A
  first-touch analysis on this column silently drops the majority of visits; usable only at the **visit**
  level and only for the non-null minority.
- **`impression_id`** — impression identifier; NULL on the ~2.6% non-verified rows (≈ the
  `from_verified_impression = FALSE` set).
- **`ip`** — IP observed at **visit** time (page-view IP). **`impression_ip`** — IP carried forward from the
  attributed **impression**; **NULL on ~2.6% of rows** (2026-07-10: 34,328 — the same non-verified subset
  that carries NULL `impression_id`). It differs from `ip` on **304,660/1,301,811 = 23.4%** of rows
  (= 24.0% of the non-NULL rows; IP changed / cross-device between impression and visit). **`ip_raw`** — a
  second copy of the visit IP: empirically **byte-identical to `ip` on 100%** of a full recent day
  (0 divergence, 0 NULLs / 1.3M rows) — see Gotchas re: the historical two-column bug.
- **`from_verified_impression`** (BOOL) — TRUE ⇒ visit attributed via MNTN's verified-impression logic
  (what the client UI counts). TRUE on ~97% of rows. **Filter `= TRUE` to match UI visit counts.**
- **`click`** (BOOL) — TRUE = click-through visit (~3.3%); FALSE = view-through visit (the majority).
- **`is_new`** (BOOL) — new-to-brand: first visit for this advertiser (~30%). NOTE: this is the visit-side
  is_new; it disagrees with `clickpass_log.is_new` by 41–56% across advertisers — that mismatch is NORMAL
  (see Gotchas), driven by cross-device visits.
- **`is_cross_device`** (BOOL) — attributed across devices (IP/GA-Client-ID graph expansion); TRUE on ~52%.
- **`visits_assist`** (BOOL) — multi-touch **assist** credit flag (~13%).
- **`efficient`** (BOOL) — "efficient attribution" flag; empirically **never TRUE** on recent data
  (0 of 1.3M on 2026-07-10) — effectively unused; do not filter on it.
- **`attribution_model_id`** — attribution model id (last-touch, etc.).
- **`pa_model_id`** — probabilistic-attribution model id.

## Joins & relationships
- **`visits.ad_served_id` → `logdata.impression_log.ad_served_id`** — impression grain (≈1 row per served
  impression). Direction matters: `impression_log → visits` is **1:N and sparse** (only the small fraction
  of impressions that led to a visit appear, and one impression can yield >1 visit row); `visits →
  impression_log` is ~N:1 (near-1:1). **Fan-out/timing warning:** display impressions can precede the visit
  by 2–4 weeks — a ±7d join window misses ~35% of display impressions; use **±30d** when display is in
  scope (CTV is same-day). See TI-650.
- **`summarydata.conversions → visits` on `guid` + `advertiser_id`** — a conversion's visitor can match
  **multiple** visits (a guid has many visits): **1:N fan-out**. Computing per-advertiser
  `conversions / visits` naively over-counts if a conversion attributes across multiple funnel visits;
  count visits once per advertiser-visit. See data_knowledge on CVR reconstruction.
- **`ui_visits` is a filtered `UNION ALL` derivative of `visits` — NOT 1:1 rows** (live view DDL, verified
  2026-07-19). Branch 1 = `visits` INNER JOIN `integrationprod.public_campaigns` filtered to
  `(objective_id = 4 OR the campaign group is a prospecting group) AND from_verified_impression IS TRUE AND
  domain IS NOT NULL`; branch 2 = a **different table**, `summarydata.last_tv_touch_visits` (rows absent from
  `visits`). Consequences: the ~2.6% `from_verified_impression = FALSE` rows and any `domain`-NULL rows in
  `visits` are **absent** from `ui_visits`; the last-TV-touch rows in `ui_visits` are **absent** from
  `visits`; and `ui_visits.ip`/`impression_ip` are CIDR-stripped (`split(x,'/')[OFFSET(0)]`), not
  byte-identical to `visits.ip`. Different SETS, different counts (2026-07-10: `visits` 1,301,811 vs
  `ui_visits` 1,266,584). It also adds computed columns (`visit_day`, `source_type`, `is_competing`, `is_pa`,
  `attribution_model_type_id`; the last = 0 should be treated as 1/last-touch). Query `ui_visits` only when
  you specifically want that UI-scoped, campaign-group-restricted population; for the full raw visit set (and
  cheapest access) query `visits`.
- **`guid` + `advertiser_id`** also links to visitor-identity tables (`guid_ip_log_visitors`,
  `advertiser_sales_cycle_by_day`). `guid` persists across a user's visits/sessions (a browser-level id).

## Gotchas
- **`ip` vs `ip_raw` — currently identical (drift vs tribal).** Tribal knowledge (from `ui_visits`) says two
  IP columns exist because of an upstream bug ("revert once ip is fixed upstream"). Empirically, at the
  `visits` physical level `ip` and `ip_raw` are **byte-identical on 100%** of a full recent day (2026-07-10:
  0 rows differ, 0 NULLs, 1.3M rows). Treat them as interchangeable for the visit IP today; the duplicate
  column persists in the schema but no longer diverges. Do NOT confuse either with `impression_ip` (the
  impression-time IP), which is NULL on ~2.6% of rows and differs from `ip` on ~23% of all rows.
- **`is_new` disagrees with `clickpass_log.is_new` by 41–56% — NORMAL.** `is_new` here is derived from the
  attribution pipeline; `clickpass_log.is_new` is the client-JS pixel value. Cross-device visits are the
  primary driver of the mismatch (61% mutation rate). Do not treat the disagreement as a data bug.
- **Not one row per impression.** A served impression can generate multiple visit rows (multi page-view
  sessions, cross-device expansion, view+click). If you need unique rows dedup on
  `(advertiser_id, ad_served_id, time)` (~99% already unique) — never assume `ad_served_id` alone is a PK.
- **`from_verified_impression = FALSE` rows (~2.6%) carry NULL `impression_id`.** Filter to
  `from_verified_impression = TRUE` for UI-matching visit counts and to keep `impression_id` non-null.
- **`efficient` is dead** — never TRUE on recent data; do not build filters on it.
- **Partition is UTC.** `time` is a UTC TIMESTAMP; `DATE(time)` (the partition) buckets by UTC day — a
  local-time analysis needs an explicit timezone shift.
- **NULL partition slot exists but is currently empty.** `INFORMATION_SCHEMA.PARTITIONS` lists a `__NULL__`
  partition alongside the dated ones, but it holds **0 rows** today (verified 2026-07-19) — the slot exists
  to catch any NULL-`time` row, though none are present now. A `WHERE time BETWEEN` bound excludes it
  regardless (usually desired).
- **`visit_day` / `source_type` / attribution-variant columns live on `ui_visits`, not here.** If a query
  references those, point it at `ui_visits` — but remember `ui_visits` is a filtered `UNION ALL` population
  (visits ∩ UI-scope, plus last-TV-touch rows), **not** the same rows as `visits` (see Joins & Purpose).

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE time BETWEEN TIMESTAMP('2026-07-01') AND TIMESTAMP('2026-07-08')` (or `DATE(time) = '2026-07-10'`).
  Partition = DAY on `time`; cluster = `advertiser_id, ad_served_id, time`. `require_partition_filter` is
  **false** (BQ will NOT stop a full-table scan) so the date bound is on you.
- **Physical backing:** VIEW resolves to a single physical TABLE
  `sqlmesh__summarydata.summarydata__visits__2108051348` — ~1.455B rows / ~518 GiB (numBytes
  556,258,232,941). Partitions span **2023-01-01 → present** (2026-07-19: 1,296 dated partitions + 1 empty
  `__NULL__` slot, 0 rows; dated count drifts +1/day); **no short TTL** — full history is retained.
- **Partition prune, measured (dry-run, 4 cols `epoch, impression_epoch, time, impression_time`):**
  `WHERE DATE(time) = '2026-07-15'` → **43.4 MB**; same 4 cols with **no** date filter (all partitions) →
  **45.58 GB**. ~1,050× reduction — confirms `time` is the partition.
- **Actual scans (partition-pruned, one day 2026-07-10):** 8-row sample of 16 mixed cols → **0.188 GB**
  billed; full-day aggregate over ~16 boolean/id cols → **0.224 GB**; 5-col grain aggregate → **0.117 GB**.
  Cost scales with the **column set × days**, not row count — clustering on `advertiser_id` further prunes
  single-advertiser slices. Avoid `SELECT *` (all **38** columns) — a one-day `SELECT *` dry-runs at
  **551.8 MB** vs **43.4 MB** for the 4 time columns (`epoch, impression_epoch, time, impression_time`).

## Example queries
```sql
-- Verified visits for one advertiser, UI-matching, one week (partition + cluster pruned):
SELECT advertiser_id, ad_served_id, time, ip, click, is_new
FROM `summarydata.visits`
WHERE time BETWEEN TIMESTAMP('2026-07-01') AND TIMESTAMP('2026-07-08')
  AND advertiser_id = 31921
  AND from_verified_impression = TRUE;
```
