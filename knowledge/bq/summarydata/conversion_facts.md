# summarydata.conversion_facts

## Purpose
Pre-aggregated **conversion** reporting rollup — one of the four sibling hourly fact tables
(`impression_facts` / `visit_facts` / `conversion_facts` / `spend_facts`) that the SQLMesh
`all_facts` model UNIONs into the R2/CHAPI reporting graph. Reach for it when you need
conversion counts and order value sliced by campaign/geo/device/creative **and by attribution
model** (click vs view, last-touch, last-TV-touch, assist, competing, probabilistic) without
scanning the row-level `summarydata.conversions` table. It is the pre-aggregated counterpart to
`conversions` (row-level, one row per conversion event, 60-day retention); this table is the
rollup you use for reporting/trend work. Stays **fresh through the current hour** (unlike the
stale `sum_by_*` daily rollups), so it is a good source for recent-window conversion analysis.

## Grain & keys
- **Grain:** one row per **`hour`** × the 16 targeting/geo dimensions (advertiser_id,
  campaign_group_id, campaign_id, channel_id, objective_id, group_id, creative_id,
  private_marketplace_id, country, metro_id, region, city, postal_code, domain, supply_vendor,
  device_type) × **conversion_type** × **conversion_source_id** × **pa_model_id**.
  Verified: for 2026-07-10, total_rows = distinct full-key = **85,493** (no duplicate rows).
- **Partition/pruning key:** `hour` (DATETIME, DAY partition).
- **Cluster / join columns:** `advertiser_id`, `campaign_id` (physical cluster keys). All the
  dimension columns above are foreign keys into the bronze integration dims.
- **No single surrogate key** — the composite dimension tuple above IS the key.

## Column meanings (only the non-obvious ones)

**Dimension / key columns**
- `hour` — DATETIME (naive, no timezone), truncated to the hour; the DAY partition key. This is
  the reporting hour of the conversion, not an epoch integer. (Drift note: prose catalog called
  it TIMESTAMP; the live physical column is **DATETIME**.)
- `channel_id` — `8` = CTV (Beeswax Television), `1` = display. View-through conversions dominate
  CTV inventory (see measures).
- `objective_id` — funnel objective, but **unreliable for stage** org-wide; use `campaigns.funnel_level`.
- `conversion_type` — **free-text pixel event name** (STRING), not an enum, and **NOT a rollup
  value**. Real values include `Purchase`, `Lead`, `Confirmation`, `app_submitted`, `Install`,
  `Job Booked`, and junk the pixel emitted verbatim (`[object Object]`, `SignUp`, `funded`,
  `sold`). The dominant value is the **sentinel `-101`**, a per-advertiser **untyped/default
  bucket** (the pixel fired without a named event) — **not** an all-conversions rollup. On
  2026-07-10 it held 54,630 of 60,723 view_conversions (89.97%), but the named pixel-event types
  add **6,093 view_conversions ON TOP of `-101`, not inside it**, and they come from a largely
  **disjoint** advertiser population: that day 139 advertisers had named-type conversions with
  **zero** `-101` rows, 790 had only `-101`, and just 18 had both. **Total conversion volume =
  `SUM` across ALL `conversion_type` values — never `-101` alone** (using `-101` as the total
  undercounts by ~10% and silently drops the 139 named-only advertisers). Filter on a specific
  `conversion_type` only when you want that named pixel event.
- `conversion_source_id` — the conversion **source / pixel id** (INT). `23` is by far the most
  common; other real ids seen: `61`, `328496`. NULL/large ids appear for app-install partners.
- `pa_model_id` — probabilistic-attribution model id (part of the grain key). Also present in
  `visit_facts`, `visits`, `ui_visits`.
- `private_marketplace_id` — STRING; NULL for open-market inventory.

**Measure columns — all `*_conversions` are scalar INT64 counts; all `*_order_value` are NUMERIC
in WHOLE USD (do NOT ÷1e6)**. Verified by magnitude: e.g. `hard_pull_approved` = 8 conversions →
$104,750 order value (~$13k each, plausible loan value); `funded` = 31 conv → $10,000.
- `click_conversions` / `click_order_value` — click-through attributed conversions + revenue.
- `view_conversions` / `view_order_value` — view-through attributed conversions + revenue. On CTV
  this dwarfs click (CTV has no clickable surface).
- `last_touch_{click,view}_{conversions,order_value}` — last-touch attribution variant (this
  advertiser was the LAST touch before conversion). Close to but a subset of the base counts.
- `last_tv_touch_{click,view}_{conversions,order_value}` — last **TV/CTV** touch attribution.
- `conversions_assist_{click,view}` (+ `_order_value`) — assist attribution (advertiser assisted
  but was not the credited last touch).
- `competing_*` — VIEW-ONLY family (`competing_view_conversions`,
  `competing_last_touch_view_conversions`, `competing_last_tv_touch_view_conversions`,
  `competing_conversions_assist_view` + each `_order_value`). "Competing" = the advertiser was
  **NOT** the attributed touch — they competed for the credit. Used for incremental-attribution
  analysis. **No `competing_click_*` columns exist** — competing is measured view-side only.
- `probattr_*` — VIEW-ONLY probabilistic-attribution family (`probattr_view_conversions`,
  `probattr_last_touch_view_conversions`, `probattr_competing_view_conversions`,
  `probattr_competing_last_touch_view_conversions` + each `_order_value`). These are the
  probabilistic-model counterparts of the deterministic last-touch/competing view metrics. Again
  **view-side only** — no `probattr_click_*`.

## Joins & relationships
- **→ dimension tables (fact-side fan-out is 0; dims are the "1"):** all are `bronze.integrationprod`
  dims and take the standard `deleted=FALSE AND is_test=FALSE` hygiene filter (else test/deleted
  dim rows leak into aggregates). `advertiser_id` → `advertisers` (1:1; filter
  `deleted=FALSE AND is_test=FALSE`; use `company_name`); `campaign_id` → `campaigns` (1:1; filter
  `deleted=FALSE AND is_test=FALSE`; `funnel_level` is stage-authoritative, not `objective_id`;
  `campaigns.name` not `campaign_name`); `campaign_group_id` → `campaign_groups` (1:1; filter
  `deleted=FALSE AND is_test=FALSE`; `product_id` 1=PTV / 2=Select / 3=QuickFrame); `creative_id`
  → `creatives` (1:1; filter `deleted=FALSE` — `creatives` has **no `is_test` column**, verified
  via schema). Joining these dims does NOT fan out the fact rows (each fact row maps to one dim row).
- **↔ sibling fact tables (`visit_facts`, `spend_facts`, `impression_facts`):** same `hour` + the
  16 shared dimension keys, BUT `conversion_facts` adds **`conversion_type` + `conversion_source_id`**
  to its grain (the sibling facts have neither). So a direct join on the shared dim key is
  **N:1 (conversion_facts → visit/spend)** and will **fan out**: one visit-fact row matches many
  conversion-fact rows (one per conversion_type/source). **Pre-aggregate `conversion_facts` up to
  the shared dim grain** (`GROUP BY` and drop conversion_type/source/pa_model) before joining, or
  just query `summarydata.all_facts`, which already UNION-reconciles the four facts (conversions
  arrive as conversion-only UNION rows there — see the `all_facts` doc). `pa_model_id` is shared
  with `visit_facts` but not with `spend_facts`/`impression_facts`.
- **↔ `summarydata.conversions` (row-level):** `conversion_facts` is the pre-aggregated rollup of
  the row-level `conversions` table (one row per conversion event, 60-day retention). Use
  `conversions` for event-level detail, `conversion_facts` for reporting aggregates.

## Gotchas
- **`hour` is DATETIME (naive, no timezone)** — the physical column is DATETIME, not TIMESTAMP.
  Compare against `DATETIME(...)` literals, not `TIMESTAMP(...)`. Same convention as the sibling
  fact tables (the SQLMesh `all_facts` pipeline keys everything on this DATETIME `hour`).
- **`*_order_value` is whole USD, NOT micros** — do not ÷1e6 (verified by magnitude). Matches the
  `all_facts` TI-1044 finding.
- **`conversion_type` is dirty free text** — the `-101` sentinel is a per-advertiser
  untyped/default bucket (~90% of daily volume), **not an all-conversions rollup**: total
  conversions = `SUM` across ALL `conversion_type`, never `-101` alone (named pixel types add
  ~10% on top, from a mostly disjoint advertiser set). It also contains literal junk the pixel
  emitted (`[object Object]`). Never assume it is a clean enum.
- **`competing_*` and `probattr_*` are view-side only** — no click variants exist in the schema.
  Don't look for `competing_click_conversions`; it isn't there.
- **Per-advertiser CVR can legitimately exceed 100%** when dividing these conversion counts
  (incl. `competing_view_conversions`) by `visit_facts` visits — a multi-touch-attribution
  artifact, not a bug (see `data_knowledge.md` "Per-advertiser CVR can exceed 100%"; winsorize
  before variance-reduction / leave-one-out analyses).
- **History starts 2026-03-01** (min `hour` = 2026-03-01T00:00, max = current hour;
  141 partitions, ~11.4M rows on 2026-07-19). No formal partition-expiration TTL is set
  (`expirationMs` = None), so the floor is the model backfill start, not a rolling window — but
  don't assume data older than 2026-03-01 exists here.
- **Owner = Backend Reporting squad (`ber`)** (SteelHouse/sqlmesh `all_facts.sql`); route
  reporting-metric change requests to a BER Jira ticket.

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE hour >= DATETIME('...') AND hour < DATETIME('...')`.
  `hour` is the DAY partition key and pruning works. `require_partition_filter` is **false** (not
  enforced), so an unfiltered query silently full-scans — always add the filter yourself.
- **Physical:** VIEW → TABLE `sqlmesh__summarydata.summarydata__conversion_facts__2982367969`
  (`bq show`: DAY partition on `hour`, cluster `[advertiser_id, campaign_id]`, no
  expiration/TTL). `approx_logical_bytes` = **6,621,068,619** (bq show `numBytes`), ~11.4M rows.
- **Measured dry-run costs (all labeled `SELECT *`, so same column set — directly comparable):**
  - `SELECT *`, no filter (full view): **6.62 GB** (6,621,068,619 B).
  - `SELECT *`, 7-day `hour` filter (2026-07-01→07-08): **0.319 GB** (319,323,123 B) — **~20x
    prune** from partition pruning alone.
  - Narrower column sets are far cheaper (a single-column aggregate over one day billed ~0.01 GB).
    Column-set sizes are NOT comparable to the SELECT * figures above — measure with `--dry_run`
    for the exact columns you pull.
- **Clustering caveat:** `advertiser_id`/`campaign_id` clustering reduces the *actually scanned*
  bytes when you filter on those columns, but `--dry_run` reports the partition upper bound and
  will NOT show the clustering savings — the real bill can be well under the dry-run estimate.

## Example queries
```sql
-- Total + view-through conversions and revenue for a campaign over a date window
SELECT
  DATE(hour)                         AS day,
  SUM(view_conversions)              AS view_conv,
  SUM(click_conversions)            AS click_conv,
  SUM(view_order_value)              AS view_revenue_usd,   -- whole USD, no /1e6
  SUM(competing_view_conversions)    AS competing_view_conv
FROM `summarydata.conversion_facts`
WHERE hour >= DATETIME('2026-07-01') AND hour < DATETIME('2026-07-08')  -- ALWAYS filter hour
  AND advertiser_id = 31357                                             -- clustered: cuts real scan
GROUP BY day
ORDER BY day;
```
