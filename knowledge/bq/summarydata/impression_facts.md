# summarydata.impression_facts

## Purpose
Primary **impressions** reporting fact in the star schema (siblings: `visit_facts`, `conversion_facts`, `spend_facts`; the FULL-OUTER-JOIN rollup of all four is `all_facts`). Pre-aggregated hourly impression delivery by campaign × geo × device × domain × supply. Reach for it when you need served/won impression counts, media cost, VAST video-quartile completion, viewability, or unique reach (HLL) sliced by any of the dimension columns. Unlike the `sum_by_campaign_by_day` rollups it **stays fresh through the current day/hour**. Physical source is `logdata.cost_impression_log` restricted to served/won rows (`unlinked = FALSE AND ad_served_id IS NOT NULL`), deduped to one row per impression, then aggregated — so it is the SAME won/served universe as the impression log, not a pre-bid/augmentor/all-seen stream.

## Grain & keys
- **Grain:** one row per unique **(hour, advertiser_id, campaign_group_id, campaign_id, channel_id, objective_id, group_id, creative_id, private_marketplace_id, country, metro_id, region, city, postal_code, domain, unlinked, supply_vendor, device_type)** tuple. Verified 2026-07-19 on 2026-07-15: `COUNT(*)` = `COUNT(DISTINCT dim-tuple)` = 57,344,758 (exactly equal → the 18-column tuple is the key). `hour` is truncated to the hour (24 distinct values/day, 00:00…23:00).
- **Key(s) / join columns:** the 18-column tuple above is the compound key. The keys **shared** with the sibling facts are the **17** columns other than `unlinked` (the siblings have no `unlinked`); `impression_facts` is unique on those 17 because `unlinked` is constant FALSE. The SQLMesh `all_facts` model FULL OUTER JOINs the siblings on a **19-key union** — the 17 shared dims + `unlinked` (impression side) + `pa_model_id` (visit/conversion side) — so `impression_facts` supplies 18 of the 19 (it has no `pa_model_id`) and its `uniques`/`uniques_arr` pass through untouched. No surrogate PK; there is no single-column unique id.
- **Measures (additive across the grain):** `display_impressions`, `ctv_impressions`, `media_cost`, `vast_start`/`vast_firstquartile`/`vast_midpoint`/`vast_thirdquartile`/`vast_complete`, `view_impression_raw`/`view_viewed_raw`/`view_untrackable`. Everything else is a dimension or an HLL sketch.

## Column meanings (only the non-obvious ones)
- **`hour`** — `DATETIME`, truncated to the hour; this is the DAY **partition key**. It is a wall-clock DATETIME, not an INT epoch — no unit conversion needed, filter it as `WHERE hour >= DATETIME("...")`. Per the live column description the wall-clock is **in the advertiser's local timezone** (no offset is stored on the value), so `DATE(hour)` is a per-advertiser local day — see Gotchas before aggregating a fixed `hour` window across advertisers or joining `hour` to a UTC-stamped table.
- **`display_impressions` vs `ctv_impressions`** — the impression count is split by channel, not summed into one column. Verified 2026-07-15: `channel_id = 8` (CTV) rows populate `ctv_impressions` and leave `display_impressions` ≈ 0; `channel_id = 1` (display) rows populate `display_impressions` and leave `ctv_impressions = 0`. **Total impressions per row = `display_impressions + ctv_impressions`.** (`channel_id` 8=CTV, 1=display.)
- **`unlinked`** — `BOOL` dimension, but empirically **constant FALSE** (all rows on 2026-07-15 were `unlinked = FALSE`). The source model already filters `unlinked = FALSE`, so this table holds only linked/served/won impressions; treat `unlinked` as a passthrough that never varies here, not a real slicer.
- **`media_cost`** — `NUMERIC`, the raw media cost for the slice (not client billing / not margin-adjusted). CTV cost per impression is roughly an order of magnitude higher than display — ~11× (2026-07-15: $570K over 46.6M CTV imps ≈ $12.2 CPM vs $19K over 17.7M display imps ≈ $1.10 CPM).
- **`vast_*`** (`vast_start`, `vast_firstquartile`, `vast_midpoint`, `vast_thirdquartile`, `vast_complete`) — VAST video-quartile completion counts (CTV/video); each is a count of impressions that reached that playback milestone. Monotonically non-increasing across the funnel (`vast_start` ≥ … ≥ `vast_complete`).
- **`view_impression_raw` / `view_viewed_raw` / `view_untrackable`** — raw viewability counters: measured impressions, of-those viewable, and impressions on inventory that couldn't be measured. `_raw` = un-normalized counts (viewability rate = `view_viewed_raw / view_impression_raw`).
- **`uniques` (BYTES) + `uniques_arr` (ARRAY<STRING>)** — HLL++ reach sketch, **channel-conditional key** (verified against the SQLMesh model, TI-1019): `HLL_COUNT.INIT(CASE WHEN channel_id = 8 OR objective_id IN (5,6) THEN ip ELSE guid END)`. So CTV/video legs count distinct **served IP**; display legs count distinct **guid** (cookie). This is a MIXED-key blend — see Gotchas. `uniques` (BYTES) is the serialized HLL sketch (combine across rows with `HLL_COUNT.MERGE`, read cardinality with `HLL_COUNT.EXTRACT`). `uniques_arr` (`ARRAY<STRING>`) is **not** a sketch — it is the raw array of the distinct key values the sketch is built from (verified 2026-07-19: `uniques_arr[0]` = a raw GUID like `d342bcc5-2fdd-11f1-…` on a display row); count it with `UNNEST` + `COUNT(DISTINCT ...)`, never `HLL_COUNT` (which errors on `ARRAY<STRING>`).
- **`existing_users_reached` / `new_users_reached` (BYTES, + `_arr`)** — the same channel-conditional key as `uniques`, split by the impression's `is_new` flag (repeat vs first-seen); together they partition `uniques`. As with `uniques`, the **BYTES** columns are HLL sketches (`MERGE`/`EXTRACT`) and the `_arr` columns are raw `ARRAY<STRING>` of the key values (`UNNEST` + `COUNT(DISTINCT)`).
- **`users_reached_ip_arr` (ARRAY<STRING>)** — **not** a sketch: a raw array of the impression **IPs**, keyed on IP regardless of channel (the IP-only reach variant, no guid substitution; verified 2026-07-19: element 0 = a raw IP like `209.181.18.217`). For a pure served-IP reach number use `COUNT(DISTINCT ...)` over `UNNEST(users_reached_ip_arr)` — not `uniques` (mixed key) and not `HLL_COUNT` (there is **no** `users_reached_ip` BYTES/HLL companion; only this raw `_arr` form is materialized).
- **`private_marketplace_id`** — `STRING` deal id; NULL/empty for open-exchange inventory.
- **`domain`** — publisher/app domain of the inventory; **not** the advertiser's site. Distinct from the `advertiser_id` dimension.

## Joins & relationships
- **`summarydata.all_facts`** — the canonical consumer. `all_facts` FULL OUTER JOINs `impression_facts` + `visit_facts` + `spend_facts` (there is **no** `bid_facts` in SQLMesh) on a **19-key union** of the siblings' dimensions — the 17 keys shared by all + `unlinked` (from `impression_facts`) + `pa_model_id` (from visit/conversion), so the 19 are **not** all present here (`impression_facts` has 18 of them, no `pa_model_id`). It passes `uniques`/`uniques_arr` straight through with no re-keying — so the mixed-key reach behavior is inherited verbatim. This BQ `all_facts` view is the source for ClickHouse `all_facts_local_daily` → CHAPI → R2 `graph.usersreached` / `graph.sitevisitors`. Fan-out risk: none for the direct sibling join (matched grain); but because it is a FULL OUTER JOIN, rows present in `visit_facts`/`spend_facts` but absent here (and vice-versa) yield NULL measures — coalesce before summing.
- **`summarydata.visit_facts` / `conversion_facts` / `spend_facts`** — siblings at ~the same hour × dimension grain, but **not exactly 1:1**: `visit_facts`/`conversion_facts` carry an extra grain column `pa_model_id` (and lack `unlinked`), so a direct join on the 17 shared keys can fan out slightly on the sibling side (verified WGU 2026-07-15: 228,219 `visit_facts` rows vs 228,212 distinct shared tuples — 7 collisions across 2 `pa_model_id` values). `impression_facts` itself stays unique on the 17 shared keys. ⚠️ **Asymmetry:** those three are **clustered on (advertiser_id, campaign_id)**; `impression_facts` is **NOT clustered** (verified: filtering to an advertiser prunes nothing here — see Cost). Joining across them, only `hour` partition-prunes `impression_facts`; advertiser/campaign filters help the siblings but not this table.
- **`bronze.integrationprod` dimensions** — `advertiser_id`→`advertisers`, `campaign_id`→`campaigns` (use `funnel_level` for stage, `objective_id` is unreliable for stage), `creative_id`→`creatives`, `campaign_group_id`→`campaign_groups` (has `product_id` 1=PTV/2=Select/3=QuickFrame). Each is **N:1** (many fact rows per dimension row) — join is safe (no fan-out) as long as you filter the dims `deleted=FALSE AND is_test=FALSE`.
- **`logdata.cost_impression_log`** — the physical upstream (served/won rows, `unlinked=FALSE AND ad_served_id IS NOT NULL`). `impression_facts` is the hourly aggregate of it; do not join them (double-count) — pick one grain.

## Gotchas
- **`uniques` is a MIXED IP/GUID key — do NOT treat it as "households/IPs reached" (TI-1019).** CTV/video legs key on served IP, display legs key on guid; guids fan out ~2.4× per household, so `uniques` over-counts the served universe (WGU 30d: `uniques` ≈ 32.1M vs distinct served IP ≈ 15.7M, a ~2× gap driven entirely by the display GUID leg). For a served-IP denominator (MDE/IVR) use `COUNT(DISTINCT ip)` from `cost_impression_log`, or here `COUNT(DISTINCT ...)` over `UNNEST(users_reached_ip_arr)` (the raw IP array) — never `uniques` (mixed key).
- **Impressions are split across two columns.** Anyone summing only `display_impressions` (or only `ctv_impressions`) silently drops the other channel. Always `display_impressions + ctv_impressions`.
- **Not clustered.** Filtering to a small advertiser/campaign list does **not** reduce bytes scanned (it actually scans an extra column). The only prune lever is the `hour` partition. Asymmetric with the sibling facts, which ARE clustered on advertiser/campaign.
- **`hour` is a DATETIME in the advertiser's local timezone** (per the live column description). Compare against `DATETIME(...)`, not `TIMESTAMP(...)`. The value carries no stored offset, so `DATE(hour)` is a **per-advertiser local day**: a fixed `hour` window is a different absolute instant per advertiser, cross-advertiser day-level aggregation silently mixes timezones, and joining `hour` to a UTC-stamped table (e.g. `cost_impression_log` epoch timestamps) is off by each advertiser's offset.
- **`unlinked` never varies** (always FALSE) — grouping by it is a no-op; it exists for schema parity with the log, not as a live slicer.
- **HLL columns are not summable — and the `_arr` twins are not sketches.** The **BYTES** columns `uniques`, `existing_users_reached`, `new_users_reached` are serialized HLL sketches; combine with `HLL_COUNT.MERGE(...)` and read cardinality with `HLL_COUNT.EXTRACT(...)` (summing the BYTES is meaningless). Their `*_arr` twins (and `users_reached_ip_arr`) are **raw `ARRAY<STRING>` of identifiers, not sketches** — count with `UNNEST` + `COUNT(DISTINCT)`; `HLL_COUNT` errors on `ARRAY<STRING>`.
- **No `site_visitors` here** — that metric lives in `visit_facts`; `all_facts` is where impressions and visits meet.

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE hour >= DATETIME("...") AND hour < DATETIME("...")`. `hour` is the DAY partition (confirmed empirically 2026-07-19) — it is the ONLY prune lever (no clustering). `require_partition_filter = false`, so a missing date filter silently full-scans all 2.89 TB.
- **Physical:** `sqlmesh__summarydata.summarydata__impression_facts__3555911259` — TABLE, 7.94B rows, **2.886 TB** backing storage (`bq show` numBytes, 2026-07-19). No partition expiration (no TTL). Clustering = `null` (verified).
- **Dry-run cost figures** — all `bq --dry_run` estimates in **decimal GB** (bytes ÷ 1e9), re-derived 2026-07-19; labeled by exact column set, do NOT cross-compare different column sets. (Unit note: `bq_run.sh` reports **GiB** = bytes ÷ 2³⁰, ~7% lower for the same query — e.g. the 18-col 1-day scan is 10.2 GB decimal ≈ 9.46 GiB billed.)
  - `SELECT hour`, **no** date filter → **63.5 GB** (63,548,380,656 B — scans the `hour` column across every partition).
  - `SELECT hour`, 2-day `hour` filter → **0.90 GB** (903,049,632 B; ~70× prune → confirms `hour` is the partition).
  - `SELECT hour WHERE advertiser_id = X` (no date filter) → **127 GB** (127,096,761,312 B) — *more* than the no-filter `hour` scan, because it must also read `advertiser_id` and prunes nothing → confirms **no clustering on advertiser**.
  - 18 dimension columns, 1 day → **10.2 GB** (10,152,789,710 B).
  - 6 columns incl. `media_cost`, 1 day → **3.2 GB** (3,211,306,448 B).
- **Rule of thumb:** cost scales with (days in range) × (columns selected). Narrow the date window first, then select only needed columns; advertiser/campaign filters buy nothing here. Per data_catalog (TI-961): a multi-column 60-day pull across all prospecting advertisers ≈ 206 GB; 14 days ≈ 50 GB.

## Example queries
```sql
-- Total impressions + media cost by day for one advertiser (date filter is the only prune)
SELECT DATE(hour) AS day,
       SUM(display_impressions + ctv_impressions) AS impressions,
       SUM(media_cost) AS media_cost
FROM `summarydata.impression_facts`
WHERE hour >= DATETIME("2026-07-01") AND hour < DATETIME("2026-07-15")
  AND advertiser_id = 31357
GROUP BY day
ORDER BY day;

-- Reach from the scalar HLL sketch (BYTES) — MERGE, never SUM.
-- NOTE: `uniques` is the MIXED IP(CTV)/GUID(display) key — it over-counts served IPs
-- (~2x). For a pure served-IP denominator use COUNT(DISTINCT ip) on cost_impression_log.
SELECT HLL_COUNT.MERGE(uniques) AS reach_mixed_key
FROM `summarydata.impression_facts`
WHERE hour >= DATETIME("2026-07-01") AND hour < DATETIME("2026-08-01")
  AND advertiser_id = 31357;
```
