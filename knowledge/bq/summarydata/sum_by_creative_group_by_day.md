# summarydata.sum_by_creative_group_by_day

## Purpose
Daily **creative-group**-level KPI rollup: delivery (impressions, video/display split, VAST quartiles), attributed visits/conversions/order-value under **several attribution models**, spend, and HLL household reach — one pre-aggregated row per creative group per day. This is the **finest-grain sibling** in the `sum_by_*` family that still carries the full attribution + reach measure set: it is `sum_by_campaign_by_day` sliced one level deeper, by the creative group (the ad-rotation unit a campaign delivers through) rather than the campaign. Reach for it to compare **creative-group performance** (which creative variant / rotation drove visits, CVR, ROAS, reach) within a campaign or advertiser, and for long pre-periods — history runs back to **2024-01-01** and, like the campaign sibling (and unlike `silver.aggregates.agg__daily_sum_by_campaign`), the `uniques` HLL sketch here is populated and mergeable. For campaign/advertiser-level trends use the coarser siblings — this table's extra `group_id` dimension multiplies row count (~32K rows/day vs ~12K in the campaign table) with no benefit unless you actually need the creative-group cut.

## Grain & keys
- **Grain:** exactly **one row per `advertiser_id` x `group_id` x `day`** (verified 2026-07-15: 32,085 rows = 32,085 distinct advertiser×group pairs — no duplicates). `group_id` = the **creative group** (`bronze.integrationprod.core_creative_groups.group_id`), not the campaign or campaign-group.
- **Key / join columns:** the **composite `(advertiser_id, group_id)`** (+ `day`). `group_id` is *nearly* globally unique but **NOT fully** — the sentinel **`group_id = -1`** (delivery not attributable to a real creative group) recurs across advertisers, so on 2026-07-15 there were 32,085 rows but only 32,084 distinct `group_id` (advertisers 31357 and 63642 both had a `-1` row). **Always key on `(advertiser_id, group_id)`, never `group_id` alone.** `group_id` -> `core_creative_groups.group_id` recovers `name`, the owning `campaign_id`, `active`, `is_control`, `parent_group_id`.

## Column meanings (only the non-obvious ones)
The measure set is **column-for-column identical to `sum_by_campaign_by_day`** — only the entity key differs (`group_id` here vs `campaign_id` there). Same conventions apply:

**Visits (VV) are not a single column — they are `views + clicks`** (view-through + click-through). There is **no `revenue` column** — revenue is the `*_order_value` (NUMERIC dollars) family. There is **no `conversions` column** — use `view_conversions + click_conversions`.

- **`group_id`** — the creative group id. Sentinel **`-1`** = delivery not tied to a specific creative group (recurs per advertiser; see Grain & keys). Positive values join to `core_creative_groups`.
- **`day`** — DATE, the partition key. No epoch column exists in this table (`time_unit: date`).
- **`impressions`** vs **`display_impressions` / `video_impressions`** — total vs the display/CTV split. `video_impressions` = CTV. VCR ≈ `vast_complete / vast_start`.
- **`view_impressions`, `view_viewed`, `view_untrackable`** — viewability accounting (impressions measured for viewability, measured-as-viewed, untrackable), NOT the same as `views` (which is view-through visits).
- **`media_spend`, `data_spend`, `platform_spend`** (NUMERIC) — the three spend buckets. **Total spend = `media_spend + data_spend + platform_spend`**. `media_cost` (NUMERIC) and `video_spend` (BIGNUMERIC) are additional cost measures in the schema; the standard total-spend convention uses the three `*_spend` columns, not `media_cost`.
- **`uniques`, `site_visitors`, `new_site_visitors`, `existing_site_visitors`, `new_users_reached`, `existing_users_reached`** (all **BYTES**) — **BQ-native HLL++ sketches, NOT integer counts.** Read distinct households with `HLL_COUNT.MERGE(uniques)` (verified populated + mergeable here 2026-07-15 — top creative group reached ~312K households). Never `SUM`. Merge across rows/days for a window reach without a raw-IP scan.
- **ATTRIBUTION-VARIANT FAMILIES — separate models, NOT additive buckets; NEVER SUM across families:**
  - **Default** (`views, clicks, view_conversions, click_conversions, view_order_value, click_order_value`) — **INCLUDES CTV** (a CTV view-conversion is a `view_conversion`).
  - **`last_touch_*` vs `last_tv_touch_*`** — two SEPARATE last-touch models (display/overall vs TV-only) that can credit the same conversion to different creative groups. Not subsets, not additive. **Do NOT add `last_tv_touch` to default/last_touch to "add CTV back" — it double-counts.**
  - **`competing_*`** — the **`industry_standard` (FIRST-TOUCH)** variant; the client UI headline Verified Visits = `clicks + views + competing_views`. `last_tv_touch` is NEVER in the UI headline.
  - **`conversions_assist_*` / `visits_assist`** — multi-touch assist credit. **`probattr_*`** — probabilistic attribution. Each family has its own `competing_` (first-touch) sub-variant.

## Joins & relationships
- **`group_id` -> `bronze.integrationprod.core_creative_groups`** (partner grain: **1 row per creative group, PK `group_id`** — filter `active = TRUE` to drop inactive groups). Safe 1:1 lookup, **no fan-out** — recovers `name`, the owning `campaign_id`, `is_control`, `parent_group_id`, `weight`, `ui_creative_group_id`. Join on the composite `(advertiser_id, group_id)` is unnecessary against this dim because `group_id` is the dim PK, but keep `advertiser_id` in this table's GROUP BY to avoid collapsing distinct `-1` sentinel rows.
- **`core_creative_groups.campaign_id` -> `bronze.integrationprod.campaigns`** — a creative group belongs to exactly one **stage campaign**, so join through the dim to recover `objective_id` (obj 1=S1 prospecting / 4=retargeting / 5,6=MT-S2/S3 / 7=Ego), `funnel_level`, `campaign_group_id`, `channel_id`. This is how you roll a creative group up to campaign / campaign-group / stage.
- **`group_id` -> `bronze.integrationprod.core_creative_groups_x_creatives`** — **1:N (fan-out)**: a creative group holds many `creative_id`s. Use only to enumerate a group's individual creatives; **never as a 1:1 lookup** (it multiplies rows). For per-creative metrics use the sibling `sum_by_creative_by_day` instead of exploding this table.
- **`advertiser_id` -> `bronze.integrationprod.advertisers`** (1 row per advertiser, join on `advertiser_id`) for `company_name`. `fpa_advertiser_verticals.advertiser_name` is unreliable (empty since 2025-12) — use `advertisers.company_name`.
- **Sibling rollups (same columns, same 2024-01-01 start):** `sum_by_campaign_by_day` (campaign grain), `sum_by_campaign_group_by_day` (client-campaign/group grain), `sum_by_advertiser_by_day` (advertiser grain), `sum_by_creative_by_day` (individual-creative grain), `sum_by_region_by_day` (STATE grain), `sum_by_ctv_network_by_day` (campaign×publisher×day). Aggregating this table by campaign/advertiser reproduces the coarser siblings.

## Gotchas
- **`require_partition_filter = TRUE` (enforced on the physical table).** Any query without a `day` filter hard-errors. Always bound `day` — this also blocks `MIN/MAX(day)` scans (use `INFORMATION_SCHEMA.PARTITIONS` instead).
- **`group_id` is NOT globally unique — key on `(advertiser_id, group_id)`.** The `-1` sentinel (unattributed delivery) recurs across advertisers; grouping by `group_id` alone silently merges different advertisers' `-1` rows.
- **Attribution variants are separate models — never SUM across families** (default / last_touch / last_tv_touch / competing / probattr / assist). Adding `last_tv_touch` to default/last_touch double-counts CTV-exposed conversions.
- **No `revenue` and no `conversions` column** — derive: visits = `views + clicks`, conversions = `view_conversions + click_conversions`, revenue = `*_order_value`.
- **`uniques` et al. are HLL BYTES sketches**, not integers — `HLL_COUNT.MERGE(...)`, never `SUM`.
- **Fresh through the current day** (re-checked 2026-07-29: max dated partition `20260729`), unlike the historically-thrashy campaign sibling — but freshness across the `sum_by_*` family has varied, so check `max(day)` (via PARTITIONS) before recent-window use and fall back to the hour-grain `silver.summarydata.*_facts` tables if lagging.
- **`__NULL__` partition exists but is empty** (0 rows on 2026-07-19); range predicates over `day` exclude any NULL-`day` rows anyway.

## Cost & partitioning notes
- **Partition:** DAY on `day`, `require_partition_filter = TRUE`. **Cluster:** none. **The one filter to always apply: a bounded `day` range** — mandatory and the only pruning lever (no cluster keys). Physical backing table (2026-07-29): **23,708,431 rows / 125,581,541,488 bytes (~117.0 GiB)**, **941 dated partitions** (`20240101` -> `20260729`) + 1 empty `__NULL__` partition (942 total).
- **SELECT only the columns you need — the row is very wide (84 cols) so `SELECT *` is ~140x costlier than a narrow projection.** Labeled dry-run figures (same partition = 1 day, 2026-07-15):
  - `SELECT *` (all 84 cols), 1 day: **144,175,971 bytes (~137.5 MB)**
  - 4 narrow cols (`advertiser_id, group_id, day, impressions`), 1 day: **1,026,720 bytes (~1.00 MB)** — ~140x cheaper than `SELECT *`
  - no `day` filter: **hard error** (partition-filter required)

## Example queries
```sql
-- Creative-group prospecting VR + ROAS for one advertiser, bounded window
SELECT s.group_id, cg.name,
       SUM(s.views + s.clicks) AS visits,
       SAFE_DIVIDE(SUM(s.views + s.clicks), SUM(s.impressions)) AS vr,
       SUM(s.media_spend + s.data_spend + s.platform_spend) AS spend,
       SAFE_DIVIDE(SUM(s.view_order_value + s.click_order_value),
                   SUM(s.media_spend + s.data_spend + s.platform_spend)) AS roas
FROM `summarydata.sum_by_creative_group_by_day` s
JOIN `bronze.integrationprod.core_creative_groups` cg
  ON cg.group_id = s.group_id AND cg.active = TRUE
WHERE s.day BETWEEN DATE '2026-06-01' AND DATE '2026-07-01'
  AND s.advertiser_id = 31357
GROUP BY s.group_id, cg.name ORDER BY visits DESC;

-- Households reached by a creative group in a window (HLL merge — never SUM(uniques))
SELECT group_id, HLL_COUNT.MERGE(uniques) AS households_reached
FROM `summarydata.sum_by_creative_group_by_day`
WHERE advertiser_id = 31357 AND day BETWEEN DATE '2026-07-01' AND DATE '2026-07-10'
GROUP BY group_id ORDER BY households_reached DESC;
```
