# summarydata.ui_visits

## Purpose
The row-level, UI-facing verified-visit log — the table the client dashboard reads to report **Verified Visits (VV)**. Reach for it when you need per-visit rows *as the UI attributes them*, including the UI's split attribution logic (retargeting vs prospecting) and the UI-only computed columns (`visit_day`, `source_type`, `is_competing`, `is_pa`, `attribution_model_type_id`).

It is **not** the raw visit table. `summarydata.visits` is the unfiltered row-level visit fact; `ui_visits` is a curated VIEW on top that (a) restricts to verified impressions, (b) applies the UI's per-campaign-type attribution routing, and (c) adds computed columns. For raw/all attribution paths use `visits`; for "what the UI shows" use `ui_visits`.

## Grain & keys
- **Grain:** one row per **verified visit event**. Empirically ~1:1 on `(advertiser_id, guid, epoch)` — 185,537 distinct keys across 186,155 rows in a sampled advertiser-day (99.7% unique). Deduped it lines up ~1:1 with `logdata.clickpass_log` (+~0.5%; `clickpass_log` is the VV source-of-truth at event grain).
- **Natural key / dedup key:** `(advertiser_id, guid, epoch)`. In the sampled advertiser-day 618 of 185,537 keys carry a duplicate (max **2 rows/key**). These are **near-exact duplicate rows, NOT an `attribution_model_id` fan-out**: 612/618 are identical on `attribution_model_id`, `ad_served_id` AND `campaign_id`; only ~6 differ by `ad_served_id`, ~5 by `campaign_id`, and 2 span both `source_type` branches; **0/618 differ by `attribution_model_id`** (15 distinct model ids exist across the whole day, but none co-occur within a duplicate key). So dedup with a plain `DISTINCT` / `ROW_NUMBER() OVER (PARTITION BY advertiser_id, guid, epoch)` — a "lowest `attribution_model_id`" tiebreaker disambiguates none of them.
- **Join keys to other tables:** `ad_served_id` (→ event_log / impression_log / clickpass_log), `guid` (→ clickpass_log), `campaign_id` (→ campaigns).

## Column meanings (only the non-obvious ones)
The live view DDL (verified 2026-07-19) is a **UNION ALL of two branches** — this drives most of the column semantics below.

- **`source_type`** — a two-value branch tag, NOT free text. Exactly `'visits'` (retargeting / TVO branch, sourced from `summarydata.visits`) or `'last_tv_touch_visits'` (prospecting branch, sourced from `summarydata.last_tv_touch_visits`). Confirmed both literals present in one advertiser-day.
- **`from_verified_impression`** — **always TRUE** in this view. Both branches hard-filter `from_verified_impression IS TRUE`, so it is a constant here, not a selector. Do not re-filter on it; it never distinguishes rows. (In the base `visits` table it *does* vary.)
- **`domain`** — **never NULL** in this view (both branches filter `domain IS NOT NULL`).
- **`epoch`** — **microseconds** since Unix epoch = `UNIX_MICROS(actual visit instant)`. Example row: `epoch=1783649174642120`. It does NOT equal `UNIX_MICROS(time)` for most rows only because `time` is often truncated to whole seconds while `epoch` keeps sub-second μs (e.g. `UNIX_MICROS(time)=1783649174000000` vs `epoch=…174642120`, a 0.64 s difference). Anchor: `epoch = UNIX_MICROS(visit time)`.
- **`impression_epoch`** — **microseconds** since Unix epoch = `UNIX_MICROS(impression instant)`, the attributed *impression* instant (not the visit). Like `epoch` vs `time`, it does NOT equal `UNIX_MICROS(impression_time)` for most rows, because `impression_time` is second-truncated while `impression_epoch` keeps sub-second μs — the identity `impression_epoch = UNIX_MICROS(impression_time)` holds for only **96,035/186,155 (51.6%)** of the sampled advertiser-day. Use `impression_epoch` (full precision), not `impression_time`, for impression ordering/dedup.
- **`impression_time`** — timestamp of the **original attributed impression**, NOT the visit. Filter on this when you want "visits attributed to ads served during period X". `time` is the visit timestamp (and the partition column).
- **`elapsed_time`** (INTERVAL) — impression → visit gap = `time − impression_time`.
- **`visit_day`** (FLOAT64) — day-number within the attribution window. DDL: `round(datetime_diff(time, impression_time, MICROSECOND)/1e6/86400 + 0.5, 0)`, floored at 1, and **populated only when that rounded value ≤ 14** — otherwise **NULL**. So `visit_day ∈ {1..14}` or NULL for visits landing >14 days after the impression.
- **`attribution_model_type_id`** — the **type** rollup from the `core_attribution_models` dim (LEFT-joined inside the view on `attribution_model_id`). It takes exactly **four values** (verified against the live 30-row dim, and all four appear in one advertiser-day): **1 = Last Touch, 2 = Last TV Touch, 3 = Last Touch Competing, 4 = Last TV Touch Competing**. Do NOT confuse it with the finer `attribution_model_id` (the 1-34 guid/ip/ga_client_id/offline/impression/winlogs/household variants that roll up into these four types) — an earlier version of this doc mislabeled the `attribution_model_id` ranges as the `type_id` domain. When the raw `attribution_model_id = 0` (unmatched), the type is coalesced to **1 in the `'visits'` branch** and **2 in the `'last_tv_touch_visits'` branch** (the "treat 0 as last-touch" rule is branch-dependent). To select competing visits use `attribution_model_type_id IN (3,4)`.
- **`is_competing`** — computed in the DDL as `m.attribution_model_type_id IN (3,4)` on the **raw joined dim value** `m` (before the 0→1/0→2 coalesce that produces the output `attribution_model_type_id`). Immaterial in practice: when `attribution_model_id = 0` the output type is 1/2, never in (3,4), so `is_competing` is FALSE under either reading. Semantically it flags the two competing types (3 = Last Touch Competing, 4 = Last TV Touch Competing).
- **`is_pa`** — computed = `pa_model_id IS NOT NULL` (probabilistic-attribution flag).
- **`visits_assist`** — carried from `visits` in the `'visits'` branch, but **hard-set to NULL for every `'last_tv_touch_visits'` row** (DDL `CAST(NULL AS BOOL)`). So a NULL here means "prospecting/TV-last-touch branch", not "no assist".
- **`ip`** — the enriched IP with the CIDR suffix stripped: DDL `split(v.ip, '/')[OFFSET(0)]` (the base `visits.ip` is INET-style `x.x.x.x/32`). Use `ip` for analysis.
- **`ip_raw`** — the raw pre-enrichment IP, passed through unchanged (NOT split). Empirically `ip = ip_raw` for 100% of a sampled advertiser-day (186,155/186,155), so the long-standing "two IP columns / upstream bug" note is cosmetic in practice — they agree.
- **`impression_ip`** — bid-time IP carried from the impression, also CIDR-stripped (`split(...)[OFFSET(0)]`). Non-CTV fallback IP; matches `event_log.bid_ip` ~95.8–100%.
- **`is_new`** — NTB (new-to-brand) flag set by the **client-side JavaScript pixel**, not a DB lookup. Not reproducible in SQL; disagrees with `clickpass_log.is_new` 41–56% (expected, architectural — cross-device drives most of the mismatch).
- **`click`** — TRUE = click-through visit; FALSE = view-through.

## Joins & relationships
- **`logdata.clickpass_log`** (partner grain: one row per VV redirect) — ~**1:1** with deduped `ui_visits` (+~0.5%). `clickpass_log.guid ↔ ui_visits.guid` 99.99%. Low fan-out; clickpass is the VV source-of-truth at event grain. Dedup `ui_visits` on `(advertiser_id, guid, epoch)` first.
- **`logdata.event_log`** via `ad_served_id` (CAST `ui_visits.ad_served_id AS STRING`) — for bid_ip / VAST IP lineage. **Partner grain 1:N** (multiple VAST/viewability rows per `ad_served_id`) → fan-out risk; GROUP BY / dedup event_log before joining. **Size the lookback to the advertiser's attribution window, not a flat 30 days:** the impression→visit gap is ≤30 days for most advertisers, but **8.7% (16,139/186,155) of this sample — WGU/31357, a long-cycle advertiser with a ~120-day production lookback — exceed 30 days, up to 148 days**. A 30-day event_log lookback silently drops those impressions; extend to the advertiser's configured window for long-cycle advertisers.
- **`logdata.impression_log` / `cost_impression_log`** via `ad_served_id` — impression details; 1:N possible per ad_served_id, dedup first.
- **`integrationprod.public_campaigns`** via `campaign_id` (PK `campaign_id`, **not** `id`; unique 548,629/548,629 → **1:1**, no fan-out) — this is the dim the view actually joins (alias `c`), to route by `objective_id` (=4 retargeting, IN (1,5,6) prospecting) and `campaign_group_id`. Note `integrationprod.campaigns` is a *different* dim keyed differently — not what the view uses; don't treat the two as interchangeable.
- **`integrationprod.core_attribution_models`** via `attribution_model_id` — dim (30 rows, unique on `attribution_model_id`), 1:1, already LEFT-joined for `attribution_model_type_id` / `is_competing`.
- The view also LEFT JOINs `summarydata.tvo_prospecting_campaign_groups` (to route TVO prospecting groups into the `'visits'` branch) — internal, not a user join target.

## Gotchas
- **Not "visits + a few columns."** The prose oracle (data_catalog / data_knowledge) described `ui_visits` as the `visits` schema plus computed fields. The **live view is a UNION ALL of two disjoint branches**: `'visits'` (retargeting `objective_id=4` OR TVO prospecting groups) and `'last_tv_touch_visits'` (prospecting `objective_id IN (1,5,6)`, not in a TVO group). Retargeting is credited via standard visits; prospecting via **TV-last-touch**. This is the UI's headline VV attribution.
- **`from_verified_impression` is constant TRUE** and **`domain` is never NULL** — both are WHERE filters baked into the view. Don't re-apply them; don't treat them as selectors.
- **`visits_assist` is NULL for the entire prospecting branch** — a NULL is a branch marker, not "no assist credit."
- **`epoch`/`impression_epoch` are microseconds**, but `time`/`impression_time` are often stored to whole-second precision, so `epoch = UNIX_MICROS(time)` fails for ~84% of rows (only 30,112/186,155 equal) AND `impression_epoch = UNIX_MICROS(impression_time)` fails for ~48% (only 96,035/186,155 equal) — even though the unit is correct. Use the `epoch` / `impression_epoch` columns (full μs precision) for tie-breaking / dedup / ordering, never the truncated `time` / `impression_time`.
- **`is_new` is a client-JS pixel value** — un-auditable in SQL, ~41–56% disagreement with `clickpass_log.is_new`. Expected.
- **`attribution_model_type_id` 0→1 rule is branch-specific** (0→2 in the prospecting branch). Don't hard-code "0 means 1".
- **`ip` vs `ip_raw`:** semantically distinct (enriched-CIDR-stripped vs raw) but empirically identical in-sample; the "upstream bug / two IP columns" note is benign.
- Underlying physicals can carry a `__NULL__` partition (streaming/late buffer) — normal.

## Cost & partitioning notes
- **Partition: DAY on `time`** — confirmed by `bq show` on both physicals AND a dry-run diff: `SELECT time WHERE DATE(time)='2026-07-10'` estimated **97,998,032 bytes (~98 MB)** vs `SELECT time` unfiltered **67,670,240,459 bytes (~67.67 GB)** — a ~690x prune. **Always filter `time`.** Filtering `impression_time` does NOT prune the partition (it's not the partition key) and spans a range of visit-days.
- **The one filter to always apply:** a `time` (or `DATE(time)`) range. Add `advertiser_id` to exploit clustering.
- **No partition TTL** — full history retained: `visits` partitions back to **2023-01-01**, `last_tv_touch_visits` to **2023-08-15** (from INFORMATION_SCHEMA.PARTITIONS). Unlike `conversions` (60-day TTL), `ui_visits` supports long pre-periods.
- **Clustering (on the physicals, benefits `advertiser_id` filters):** `visits` clusters `[advertiser_id, ad_served_id, time]`; `last_tv_touch_visits` clusters `[advertiser_id, time]`. The view itself declares no clustering.
- **Cost figures (each labeled by exact column set, from `--dry_run`, 2026-07-19):**
  - `SELECT time` · 1 day (`DATE(time)=…`): **~98 MB** (97,998,032 B) — one narrow column, one partition.
  - `SELECT time` · all partitions (no filter): **~67.67 GB** (67,670,240,459 B) — one narrow column, full view.
  - `SELECT *` · 1 day: **~818 MB** (818,351,466 B) — all 43 columns, one partition.
- `approx_logical_bytes` = summed backing storage of the two UNION physicals: `visits` 556,258,232,941 B + `last_tv_touch_visits` 269,089,878,815 B = **825,348,111,756 B** (~825 GB). Small dims (campaigns, attribution_models, tvo groups) excluded.

## Example queries
```sql
-- Verified visits for one advertiser over a window (always filter time; add advertiser_id for clustering)
SELECT advertiser_id, guid, time, ip, source_type, attribution_model_type_id, is_competing, click, is_new
FROM `summarydata.ui_visits`
WHERE DATE(time) BETWEEN '2026-07-01' AND '2026-07-10'
  AND advertiser_id = 31357;

-- Split retargeting vs prospecting attribution branch
SELECT source_type, COUNT(*) visits
FROM `summarydata.ui_visits`
WHERE DATE(time) BETWEEN '2026-07-01' AND '2026-07-10'
GROUP BY source_type;
```
