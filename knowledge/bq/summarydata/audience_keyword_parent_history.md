# summarydata.audience_keyword_parent_history

## Purpose
Reconstructs the **parent→child keyword expansion lineage** for every audience, across its full edit
history. For a given audience snapshot, it pairs each **selected DS38 PARENT keyword** (the UI-visible
seed term) with each **selected DS19 CHILD keyword** (MNTN-Matched / "MM Core" auto-expansion) that was
expanded from it. Reach for it when you need "which seed keyword did this targetable DS19 keyword come
from?" over time — e.g. auditing MNTN-Matched expansion drift, or attributing DS19 targeting back to the
customer's original seeds. For **current** state only, prefer the simpler `ui.audience_keyword_state`;
this view adds the archived-snapshot history and the parent↔child edge resolution.

Description on the physical view: *"Full history of audience keyword state matched w/ parent keyword state history."*

## Grain & keys
- **Grain:** one row per **(audience snapshot × selected DS38 parent keyword × selected DS19 child keyword expanded from that parent)**. This is a **many-to-many edge list** — a single child appears once for *every* matching parent whose keyword is in the child's `expanded_from` array, and every historical snapshot repeats the edges. **Not one row per keyword.**
- **Keys / join columns:** `audience_id` (scopes to one audience), `parent_id` + `child_id` (source `audience_keyword_state.id` of each side, per-snapshot), and the `*_archive_time` pair (identifies which historical snapshot the edge belongs to).
- **Observed scale (2026-07-19):** 12,089,021 rows · 36,199 distinct audiences · 1,307,885 distinct parent_id · 5,445,677 distinct child_id · ~6.64M live-snapshot rows (archive_time NULL) + ~5.45M archived-snapshot rows.

## Column meanings (only the non-obvious ones)
- **`parent_archive_time` / `child_archive_time`** — snapshot markers. **NULL = the current, live state** (row came from `ui.audience_keyword_state`). **Non-NULL = an archived historical version** (row came from `archives.audience_keyword_state_archives`); the timestamp is when that state was superseded. The view matches parent to child only within the **same** snapshot (`parent.archive_time IS NOT DISTINCT FROM child.archive_time`, so live-NULL matches live-NULL). All four `*_time` columns are true `TIMESTAMP` values — **no epoch conversion needed**.
- **`parent_create_time` / `child_create_time`** — when each side's keyword-state row was created (start of that snapshot version).
- **`parent_type` / `child_type`** — constant `'PARENT'` and `'CHILD'` respectively (hard-coded in the join). Useless as filters — they never vary.
- **`parent_data_source_id`** — constant **38** (DS38 = the seed / parent-keyword taxonomy). Comes from the internal `tpa.categories` join (`data_source_id = 38`), not from the parent row itself.
- **`parent_data_source_category_id`** — the DS38 category id matched to the parent. By view construction `= parent_id` (join key is `categories.data_source_category_id = parent.id`); confirmed empirically identical (e.g. 2643190 = 2643190). Redundant with `parent_id`.
- **`child_data_source_id`** — **19** (DS19 = MNTN-Matched "MM Core", the targetable auto-expanded keywords). A small residue (484 of 12.09M rows) is NULL.
- **`child_data_source_category_id`** — the DS19 keyword's real targeting category id (e.g. 908431). **Distinct from `child_id`** (which is the `audience_keyword_state` row PK).
- **`parent_keyword` / `child_keyword`** — human-readable keyword text. Parent = the UI-visible seed term (~20 per audience); child = a DS19 targetable term (e.g. parent "Cardio Training" → children "Fitness Training", "Cardio Equipment", "Hydration Gear").
- **`expanded_from`** — JSON **array on the CHILD** listing the parent seed keywords the child was expanded from. The view emits one row per child × parent where `parent.keyword IN UNNEST(JSON_VALUE_ARRAY(expanded_from))` **and both sides `selected = TRUE`**. This array is the **fan-out driver** (a single child lists dozens of parents). It may contain duplicate strings (e.g. "Whoop" twice) — harmless to the `IN UNNEST` match.

## Joins & relationships
- **Built from** `summarydata.audience_keyword_state_history` self-joined (parent alias `keyword_type='PARENT'`, child alias `keyword_type='CHILD'`), which is itself `ui.audience_keyword_state` (live) **UNION ALL** `archives.audience_keyword_state_archives` (history) → ultimately `dw-main-bronze.integrationprod.ui_audience_keyword_state` (5.01M rows, ~792 MB) + `...archives_audience_keyword_state_archives` (4.90M rows, ~874 MB). Plus `tpa.categories` filtered to `data_source_id = 38` (supplies the parent DS38 category columns and restricts parents to those with a DS38 category match).
- **`audience_id` → `audience.audiences` / `audiences` (audience dim):** the dim is 1 row per audience, but **this view is N rows per audience** (~334 avg; hundreds of parent×child edges × multiple snapshots). Joining on `audience_id` fans out hard — aggregate this side first.
- **`child_data_source_category_id` → DS19 targeting category:** the selected CHILD keywords are the DS19 expression set; this ties expansion lineage to actual targeting. Cross-reference `ui.audience_keyword_state` (data_catalog.md) for the current-state, is_magic-aware view of the same DS19 set.
- **Fan-out warning:** never `COUNT(*)` to count keywords — a child is repeated once per matching parent and once per snapshot. Use `COUNT(DISTINCT child_id)` / `COUNT(DISTINCT parent_id)`, and pin a single snapshot (e.g. `child_archive_time IS NULL`) before counting.

## Gotchas
- **It is an edge list, not one-row-per-keyword.** Row count (12.09M) ≫ distinct children (5.45M) ≫ real keyword count, because of the parent×child many-to-many AND the snapshot repetition. De-dupe with `DISTINCT` and pin a snapshot.
- **History duplication:** without a snapshot filter you get *every* historical version of the audience. For **current state**, filter `parent_archive_time IS NULL AND child_archive_time IS NULL` (the live UNION branch). Archived rows have both set.
- **Snapshot alignment:** parent↔child are matched only within the same version via `archive_time IS NOT DISTINCT FROM` — a parent from one edit will never pair with a child from another.
- **Both sides pre-filtered to `selected = TRUE`** — only keywords actually included in the DS19 expression appear; unselected keywords are absent.
- **`is_magic` is NOT filtered here.** The view never references `is_magic`, so untargetable magic children *can* appear. To exclude them, join back to `ui.audience_keyword_state` and drop `is_magic = TRUE` (see data_catalog.md § `ui.audience_keyword_state`).
- **Parents constrained to DS38 categories:** the `tpa.categories` (data_source_id=38) join can silently drop parents lacking a DS38 category match.
- **484 rows have `child_data_source_id` NULL** — minor data quirk; filter if you require DS19.
- **No partition column** — every query full-scans the backing dimension tables; filters do **not** prune bytes (see below).

## Cost & partitioning notes
- **No partition, no view-level clustering.** `require_partition_filter = false`. Backing physical tables are unpartitioned dimension tables clustered by their PK `id` (not by `audience_id`), so there is **nothing to prune on**. Real backing storage ≈ **1.67 GB** (ui_audience_keyword_state ~792 MB + archives ~874 MB); the `tpa.categories` chain adds a little more.
- **Measured (all labeled by column set, 2026-07-19):**
  - `SELECT *` whole view (16 cols) — **dry-run 2.16 GB**.
  - `SELECT audience_id, parent_keyword, child_keyword ... WHERE audience_id = 34668` (3 cols) — **dry-run 1.95 GB**.
  - Aggregate `COUNT`/`COUNTIF` over the view — **1.88 GB billed** (actual).
  - `SELECT` 16 cols `WHERE audience_id = 34668` — **2.01 GB billed** (actual).
- **The WHERE does not cut bytes.** 3-col filtered (1.95 GB) vs 16-col full (2.16 GB) differ only by column set — the `audience_id` predicate prunes nothing (no partition/cluster on it). Cost is roughly **fixed at ~1.9–2.2 GB per query**.
- **The one filter to always apply is semantic, not for cost:** `parent_archive_time IS NULL AND child_archive_time IS NULL` for current state, plus `audience_id` to scope results. To actually reduce bytes, **select fewer columns** — avoid `SELECT *`; the `expanded_from` JSON and the two `*_keyword` strings are the heaviest columns.

## Example queries
```sql
-- Current parent→child expansion lineage for one audience (live snapshot only)
SELECT parent_keyword, child_keyword, child_data_source_category_id
FROM `summarydata.audience_keyword_parent_history`
WHERE audience_id = 34668
  AND parent_archive_time IS NULL
  AND child_archive_time IS NULL;

-- Count distinct current DS19 children per parent seed (de-duped, one snapshot)
SELECT parent_keyword, COUNT(DISTINCT child_id) AS n_children
FROM `summarydata.audience_keyword_parent_history`
WHERE audience_id = 34668 AND child_archive_time IS NULL
GROUP BY parent_keyword
ORDER BY n_children DESC;
```
