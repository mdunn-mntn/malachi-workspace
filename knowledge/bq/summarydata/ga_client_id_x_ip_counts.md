# summarydata.ga_client_id_x_ip_counts

## Purpose
A **high-fanout / toxic GA-cookie detector**. For each MNTN advertiser, it counts how many *distinct IPs* a single Google Analytics client ID (browser cookie) was seen from, and keeps **only cookies with >=45 distinct IPs** (a HAVING threshold — see Gotchas). A real GA cookie legitimately maps to a handful of IPs (home / work / mobile); >=45 (and up to 122,457 here) means the cookie is shared (household/kiosk), behind a proxy/VPN/CGNAT, a bot, or the product of ID collision / an unset default. Reach for it as a **lookup / exclusion list** to strip these non-user cookies before attributing conversions or building the identity graph, so one toxic cookie doesn't over-link IPs or inflate an advertiser's attributed unique users. Directly supports the "shared identifier" hygiene rule in `data_knowledge.md` (an ID connected to many other IDs = likely shared) and the `ga_client_ids`-per-IP volume driver noted there.

## Grain & keys
- **Grain:** one row per **(advertiser_id, ga_client_id)** pair, filtered to unique_ips >= 45. Verified: total_rows (614,636) == COUNT(DISTINCT advertiser_id||ga_client_id) (614,636).
- **NOT unique on ga_client_id alone:** 553,902 distinct GA cookies across 614,636 rows — the *same* cookie appears under multiple advertisers (separate rows), and its IP count is scoped **per advertiser**, not global.
- **Key(s) / join columns:** composite `(advertiser_id, ga_client_id)`. No surrogate key, no time column.

## Column meanings (only the non-obvious ones)
- **ga_client_id** (STRING) — the Google Analytics **client ID**, a browser-scoped cookie, format `<random32>.<first-visit-unix-seconds>` e.g. `1429918182.1781259737`. Browser-specific and only present when GA is installed and fires (~74-77% population on visits per `data_knowledge.md`), so it is NOT a universal identity key. **Sentinel `"false"` appears** as a literal value = GA cookie unset / not captured; it is a catch-all bucket (one such row carried 29,240 IPs) and is NOT a real user — exclude it from any per-user logic.
- **unique_ips** (INT64) — count of **DISTINCT IPs** the cookie was seen from, scoped to that advertiser. Not impressions, not visits, not conversions — a distinct-IP fan-out. **Hard floor = 45** (the retention threshold, not the true minimum), median 65, p90 152, max 122,457. No NULLs.
- **advertiser_id** (INT64) — MNTN advertiser whose conversion/visit tracking produced the rows. Never NULL. 3,295 distinct advertisers present.

## Joins & relationships
Composite key `(advertiser_id, ga_client_id)`. Use this table as a **semi-join / anti-join filter list**, never as a fact to fan out:
- **`logdata.conversion_log`** (the upstream source — carries advertiser_id + ga_client_id + ip): grain = **one row per conversion pixel fire (1:N)**, many events per GA cookie. Joining ON `(advertiser_id, ga_client_id)` fans out hard. Use `WHERE (advertiser_id, ga_client_id) IN (...)` / anti-join to EXCLUDE toxic cookies before attribution.
- **`logdata.guid_log`** — has ga_client_id; **1:N** (many rows per cookie). Same fan-out warning.
- **`aggregates.guid_identity_daily`** — the daily identity graph (guid → ip, ga_client_id, …); grain = **one row per (day, guid) (1:N)**. This table is effectively the per-advertiser aggregate of the same ga_client_id↔ip relationship; join only as a lookup.

## Gotchas
- **No time column at all.** This is a point-in-time **full-refresh snapshot** (physical `creationTime == lastModifiedTime` — SQLMesh rebuilds the whole table each run). There is no history and no date filter is possible; the IP counts reflect whatever lookback the upstream model uses (window not exposed in the schema).
- **min=45 is a retention threshold, NOT the real minimum.** Cookies with <45 IPs are simply absent. **Presence ⇒ flagged high-fanout; absence ⇒ "not flagged", NOT "clean/verified."** Never treat this as a complete cookie inventory.
- **`ga_client_id = "false"`** (and any other non-`<num>.<num>` sentinel) is not a real cookie — drop it before per-user reasoning.
- **Per-advertiser scoping:** the same cookie under two advertisers = two rows with independent counts; there is no global-across-advertisers count in this table.
- Values are effectively a small denormalized flag list — safe to load entirely into memory (~615K rows).

## Cost & partitioning notes
- **Unpartitioned, unclustered, no TTL** — confirmed off the physical (`timePartitioning: null`, `clustering: null`). There is **no partition column to prune**; every query scans the whole table. That is fine because it is tiny.
- **The whole table = 24,592,800 bytes (~0.023 GB) for `SELECT *` (all 3 columns)** — dry-run verified. A narrower column set scans proportionally less but the table is already trivial. There is no date/partition filter to add; instead push `advertiser_id = ...` and/or a `unique_ips >=` cutoff into the WHERE to trim **output rows** (not bytes).

## Example queries
```sql
-- The toxic-cookie exclusion list for one advertiser (highest fan-out first)
SELECT advertiser_id, ga_client_id, unique_ips
FROM `summarydata.ga_client_id_x_ip_counts`
WHERE advertiser_id = 35237
  AND ga_client_id != 'false'
ORDER BY unique_ips DESC;

-- Anti-join: keep only conversions NOT tied to a flagged high-fanout cookie
SELECT c.*
FROM `logdata.conversion_log` c
LEFT JOIN `summarydata.ga_client_id_x_ip_counts` t
  ON c.advertiser_id = t.advertiser_id AND c.ga_client_id = t.ga_client_id
WHERE c.time >= '2026-07-01'          -- REQUIRED: conversion_log is 25TB, prune it
  AND t.ga_client_id IS NULL;          -- cookie is not on the toxic list
```
