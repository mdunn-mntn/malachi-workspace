# summarydata.waypoints_transition_daily

## Purpose
Powers the **Waypoints** funnel/journey-analytics product. Each advertiser configures its own **ordered
funnel** — a set of named stages ("event groups"), each with an integer order, and named events inside
them. This view reports, per day, the **adjacent-stage transitions** its site visitors made: a user in a
session moved from a stage at order `N` (source) to the next stage at order `N+1` (target). Reach for it
to answer "how many sessions stepped from stage A to the next stage B for advertiser X" — i.e. funnel
step-through / drop-off analysis.

It is a **filtered projection** (no aggregation) of the base fact `summarydata.waypoints_fact`, keeping
only rows where `funnel_mode='sequential'`, `is_step_start=1`, `has_target_transition=1`, a non-null user
key, and the source/target actually differ. The final `is_ordered=1` filter keeps only **strictly
adjacent** forward steps (target order = source order + 1) — non-adjacent jumps and backward moves are
dropped. Data floor is hardcoded at **2026-02-10** (view WHERE clause); nothing earlier is returned.

## Grain & keys
- **Grain:** one row per qualifying **user-session step-transition** (source stage order N → target stage
  order N+1) per advertiser per day. Inherited straight from `waypoints_fact` — this view does NOT
  GROUP BY, so it is one output row per one fact row.
- **Identifying columns:** `day` + `advertiser_id` + `current_session_key` (+ `current_ga_client_id`) +
  `source_event_name` + `target_event_name` + `event_type` + `from_verified_impression`. The
  (adv, campaign, group, session, ad_served, source_name, target_name) tuple is **not unique** — on
  2026-07-10, 55,413 rows vs 31,986 distinct such tuples — because a session can log the same transition
  via more than one `event_type` (URL vs DLV) or ad-linkage state.
- **Analytic keys:** `advertiser_id`, `day`; funnel structure keyed by
  `source_event_group_order` / `target_event_group_order` (integers) and the group/event name strings.

## Column meanings (only the non-obvious ones)
- **`day`** — native DATE, the partition column (not an epoch). One transition's day.
- **`campaign_id`, `group_id`** — observed **0 for every row** on the sampled day (2026-07-10: all 55,413
  rows have `campaign_id=0` and `group_id=0`). Waypoints transitions here are funnel-/account-level, not
  tied to a specific campaign or creative group. Do not join these to `campaigns`/`campaign_groups`
  expecting a match; treat 0 as "unattributed / rollup" sentinel.
- **`from_verified_impression`** — BOOL, tri-state: `TRUE` = the session's journey is attributable to a
  MNTN **verified ad impression**; `NULL` = no ad linkage (organic / site-direct traffic); `FALSE`
  possible but **not observed** on the sampled day. 2026-07-10 mix: ~84% NULL, ~16% TRUE, 0 FALSE.
- **`event_type`** — capture mechanism of the underlying event. Domain (2026-07-10): **`URL`** (page-view
  URL match, ~55%) and **`DLV`** (dataLayer / GTM event push, ~45%). Same session-transition can appear
  under both types → a source of the row-vs-tuple multiplicity noted above.
- **`source_event_group` / `target_event_group`** — advertiser-defined **stage names**; each advertiser
  has its own vocabulary (e.g. 32603: Site Entry → Authentication → Lead Funnel → Revenue Operations →
  Active Customer; 34114: Visitor → Intentful Visitor → Job Booked). Not a shared enum.
- **`source_event_group_order` / `target_event_group_order`** — INT stage position within that
  advertiser's funnel (1-based). This view guarantees `target_order = source_order + 1`.
- **`source_event_name` / `target_event_name`** — the specific named event within the stage that fired.
- **`current_ga_client_id`** — GA-style client id, format `"<randomInt>.<epoch-seconds>"`; identifies the
  visitor's browser/device.
- **`current_session_key`** — composite session id, format `"<advertiser_id>|<ga_client_id>|<session_ts>"`.
- **`current_ad_served_id`** — the served-ad identifier when the transition is tied to a MNTN ad; **NULL
  for ~83%** of rows (2026-07-10) — populated only for ad-attributable journeys (tracks
  `from_verified_impression=TRUE`).
- **`transition_count`** — number of times this exact transition occurred for the row's key. **Observed =
  1 for every row** on the sampled day (fact appears to emit one row per traversal instance). Use
  `SUM(transition_count)`, not `COUNT(*)`, if you want to be robust to future >1 collapsing.
- **`is_ordered`** — INT flag, **always 1 in this view** (the view's final WHERE is `is_ordered = 1`). A
  dead/constant column here; it only varies in the parent fact. Do not filter or group on it.

## Joins & relationships
- **`summarydata.waypoints_fact`** (parent) — 1:1; this view is a filtered projection of it. Fact is the
  physical table (`sqlmesh__summarydata.summarydata__waypoints_fact__2720337691`): ~187M rows, ~42.5 GB,
  partition `day` (DAY, require_partition_filter=TRUE), cluster `[advertiser_id, campaign_id,
  funnel_mode]`. Go to the fact for `funnel_mode` values other than `sequential`, non-adjacent
  transitions, `is_step_start=0` rows, or the extra fact columns not projected here.
- **`bronze.integrationprod.advertisers`** — `advertiser_id` → `advertisers.id`; partner grain 1 row per
  advertiser (filter `deleted=FALSE AND is_test=FALSE`). Safe many-to-one; no fan-out from the advertiser
  side. Use `advertisers.company_name` for labels.
- **Do NOT join `campaign_id`/`group_id`** to campaign/group dims — they are 0 here (see Column meanings).
- **No IP / conversion_log join** — journeys are keyed by GA client id + session, not IP. Stage/event
  naming is advertiser-configured (cf. `attr_advertiser_waypoints_event_mapping` in
  `bronze.integrationprod`, which classifies advertiser event names), not a platform enum.

## Gotchas
- **`is_ordered` is a constant 1** — filtering/grouping on it does nothing; the parent fact carries the
  0/1 variation.
- **`campaign_id` and `group_id` are 0** on observed data — don't treat them as real FKs.
- **Row count ≠ transition count of distinct sessions** — the same session-transition appears once per
  `event_type` (URL and DLV) and per ad-linkage state, so `COUNT(*)` double-counts if you want unique
  session steps. De-dup on `current_session_key` + source/target names, or pick a single `event_type`.
- **Small product footprint** — only **11 advertisers** on 2026-07-10. Aggregate metrics are dominated by
  a handful of accounts; don't read platform-wide trends from it.
- **Hardcoded floor 2026-02-10** — the view returns nothing before this date even though the parent fact
  may hold earlier partitions.
- **Only forward-adjacent, sequential-mode steps survive** — backward moves, skips (order N → N+2), and
  non-sequential funnel modes are filtered out upstream; this is a step-through view, not a full path log.

## Cost & partitioning notes
- **The one filter to always apply: `WHERE day = '<date>'`** (or a tight `day BETWEEN`). Partition is
  `day` (DATE, DAY granularity), inherited from the parent fact. `advertiser_id` is the leading cluster
  key — add `AND advertiser_id = …` to prune further within a day.
- Cluster keys inherited from the fact are `[advertiser_id, campaign_id, funnel_mode]`, but on this view
  `funnel_mode` is pinned to `'sequential'` (not projected) and `campaign_id` is 0 — so `advertiser_id`
  is the only cluster key that actually prunes here.
- **require_partition_filter = false on the view** (the parent fact enforces it, but the view's embedded
  `day >= '2026-02-10'` satisfies that requirement) — so an un-filtered query does NOT error, it just
  scans everything. Filter `day` anyway.
- Dry-run byte estimates (upper bound), labeled by column set:
  - `SELECT *`, **no** day filter → **29.50 GB** (full view scan; ~27.5 GiB).
  - `SELECT *`, **one** day (`day='2026-07-10'`) → **0.205 GB** (204.6 MB) — the day filter cuts ~144x.
  - `SELECT advertiser_id, transition_count`, one day → **0.112 GB** (111.8 MB) — column pruning cuts
    a further ~1.8x vs `SELECT *` on the same day.
- Backing physical `waypoints_fact` storage = 42.53 GB / 187M rows (whole fact, all funnel modes — this
  view exposes only a filtered subset, so no clean per-view `approx_logical_bytes`; left null).

## Example queries
```sql
-- Step-through counts between adjacent funnel stages for one advertiser on one day
SELECT source_event_group, target_event_group,
       COUNT(DISTINCT current_session_key)  AS sessions,
       SUM(transition_count)                AS transitions
FROM `summarydata.waypoints_transition_daily`
WHERE day = '2026-07-10' AND advertiser_id = 32603
GROUP BY 1, 2
ORDER BY MIN(source_event_group_order);
```
