# summarydata.waypoints_stage_daily

## Purpose
The **daily Waypoint funnel-stage rollup**. A "waypoint" is a tracked site event (see
`summarydata.waypoints`); this view turns the raw event fact (`waypoints_fact`) into a per-day,
per-advertiser **funnel** by joining each advertiser's **stage definitions** (event → ordered stage,
from `attr_advertiser_waypoints_event_mapping` via `ber_stg.waypoints__event_mapping_prepared`). Reach
for it to build funnel-stage dashboards: how many users/sessions reached each stage on a given day, how
many transitioned from the previous stage, and total event volume per stage. It is a **long
"contributions" table** (one physical query that `UNION ALL`s four row-kinds), so it is NOT a clean
one-row-per-stage rollup — you must aggregate it yourself (`COUNT(DISTINCT current_ga_client_id)` for
stage users, etc.). It is upstream of `waypoints_by_day`, `waypoints_funnel_by_day`,
`waypoints_full_volume_by_day`, `waypoints_transition_daily`, and the `waypoints` UI product.

## Grain & keys
- **Grain:** one **contribution row** per `day` x `advertiser_id` x `campaign_id` x `funnel_mode` x
  `from_verified_impression` x stage (`event_group` / `event_group_order`), where the contribution kind is
  one of four (unioned): **zero-scaffold** (every defined stage emitted with zero counts so funnels always
  render all steps), **current-user** (one row per distinct user present AT a stage — `current_ga_client_id`
  / `current_session_key` / `current_ad_served_id` set), **previous-user transition** (one row per distinct
  user who arrived at a stage FROM the prior stage — `previous_ga_client_id` / `previous_session_key` set,
  `current_*` NULL), and **event-count** (aggregated `current_event_count_flag` / `transition_count` per
  stage). Because current-user and previous-user rows are one-per-distinct-identity, **DO NOT `COUNT(*)`** —
  `COUNT(DISTINCT current_ga_client_id)` = stage users, `COUNT(DISTINCT previous_ga_client_id)` = users who
  entered from the prior stage, `SUM(current_event_count_flag)` / `SUM(transition_count)` = event volume.
- **No primary key.** Dimensional keys: `day`, `advertiser_id`, `campaign_id`, `funnel_mode`,
  `from_verified_impression`, `event_group`, `event_group_order`. Identity keys used only for distinct
  counting: `current_ga_client_id`, `current_session_key`, `current_ad_served_id`, `previous_ga_client_id`,
  `previous_session_key`.
- **`funnel_mode` domain (verified 2026-07-15):** `sequential` (a staged funnel with ordered
  `event_group_order` stages and prev→current transitions) and `full_volume` (a flat per-event volume
  rollup — no transition topology). Only these two values.

## Column meanings (only the non-obvious ones)
- **`day`** — DATE, the partition column and require-partition-filter key. UTC event day (inherited from
  `waypoints_fact.day`). Always filter it.
- **`funnel_mode`** — `sequential` vs `full_volume` (see Grain). Filter it to pick a funnel type; it is also
  a cluster key on the backing fact, so filtering prunes.
- **`from_verified_impression`** — BOOL. `TRUE` = the stage/event contribution is tied to a **view-verified
  MNTN impression** (the "MNTN-influenced" funnel); `NULL` = not tied to a verified impression (the full /
  all-site funnel). Observed domain on 2026-07-15 = `{NULL, TRUE}` only — there is **no `FALSE`**. To get
  the MNTN-attributed funnel filter `from_verified_impression = TRUE`; the `NULL` rows are the broader
  all-volume funnel. (In the view SQL this is aliased `is_mntn_visit`.)
- **`event_group` / `event_group_order`** — the **stage** label and its 1-based ordinal within the
  advertiser's funnel (observed 1–5). `event_group_order` = the stage index; the same pair defines a stage.
- **`event_name`** — **populated ONLY for `full_volume` rows** (the specific event name); **always NULL for
  `sequential` rows** (the sequential rollup carries stages, not raw event names). Verified 2026-07-15.
- **`event_type`** — **always NULL in this view** (the contributions `CAST(NULL AS STRING)`); the URL/DLV
  distinction lives in `waypoints_fact` / `waypoints`, not here.
- **`current_event_count_flag`** — event-volume measure. For `full_volume` rows it is the summed count of
  that event for that user/session/ad_served (all rows > 0). For `sequential` rows it is populated only on
  the aggregated **event-count** contribution rows (a small subset — 417 of 530K on 2026-07-15) and 0
  elsewhere; on those rows it equals `transition_count`.
- **`transition_count`** — for `sequential`, the summed event count on the event-count contribution rows
  (equals `current_event_count_flag` there); 0 on scaffold/current/previous rows. Always 0 for `full_volume`.
  This is a raw event count, NOT a distinct-user transition — for transition *users* count DISTINCT
  `previous_ga_client_id`.
- **`has_target_transition`** — INT flag (0/1). 1 = this contribution represents an inter-stage transition
  edge (a stage that has a predecessor / a previous-user contribution); 0 = a terminal/first-stage or
  zero-scaffold row. On 2026-07-15, 1 on ~312K of 530K sequential rows; always 0 for `full_volume`.
- **`current_*` vs `previous_*` identity columns** — `current_ga_client_id` / `current_session_key` /
  `current_ad_served_id` identify the user AT the stage (populated on current-user and full_volume rows);
  `previous_ga_client_id` / `previous_session_key` identify the same user's presence at the PRIOR stage
  (populated only on previous-user transition rows, where `current_*` are NULL). They are mutually exclusive
  per row — the ~1K rows with both NULL are the zero-scaffold / aggregated event-count contributions.
- **`source_event_group` / `source_event_group_order`** — the **previous** stage in the funnel (predecessor
  edge); NULL for the first stage (no predecessor). Populated on ~59% of sequential rows.
- **`target_event_group` / `target_event_group_order`** — the **current/destination** stage of the
  contribution; populated on ~100% of sequential rows. Together source→target describes the funnel edge.
- **`previous_event_group` / `previous_event_group_order`** — the prior stage carried from the stage
  definition (mirrors `source_event_*` on most sequential rows).
- **`source_event_name` / `target_event_name` / `previous_event_name`** — **always NULL in this view** (the
  contributions null them out; only the `*_group`/`*_order` topology survives).
- **`campaign_id`** — advertiser campaign; also a backing-fact cluster key. `advertiser_id` = the
  advertiser. Only advertisers with a configured Waypoint stage mapping appear (15 on 2026-07-15).

## Joins & relationships
- **`waypoints_fact`** (`summarydata`, physical TABLE, partitioned `day`, clustered
  advertiser_id/campaign_id/funnel_mode; ~187M rows, ~42.5 GB) — the sole event source. This view IS the
  daily stage-shaped projection of it. Grain of the fact = one row per waypoint event (with the same
  `current_*`/`previous_*`/stage columns pre-computed). Join back to it only for raw-event detail; expect
  large fan-out (the fact is the granular layer under this rollup).
- **`attr_advertiser_waypoints_event_mapping`** (bronze `integrationprod`, per-advertiser dim) via
  **`ber_stg.waypoints__event_mapping_prepared`** — supplies the **stage definitions** (advertiser_id →
  event_group → event_group_order, deduped 1-per-(advertiser, event_group_order)). Grain = one row per
  advertiser per stage; **1:N** into this fact (one stage definition scaffolds many daily contribution
  rows). This is where the funnel's stage set / order / prev-next topology comes from. `event_mapping_prepared`
  resolves to a VIEW (SQLMesh metadata shows 0 rows — stale; it is not empty). Filter deleted mappings at
  source (`deleted` flag on the mapping table) if joining directly.
- **Downstream consumers** (this view is their input, 1:N): `waypoints_by_day`, `waypoints_funnel_by_day`,
  `waypoints_full_volume_by_day`, `waypoints_transition_daily`, `waypoints_transition_analysis` — each
  aggregates the contribution rows (DISTINCT identity counts) into stage/transition metrics.

## Gotchas
- **Never `COUNT(*)` or `SUM` naively across the whole view** — it mixes four contribution kinds
  (zero-scaffold, current-user, previous-user, event-count). Counting rows double-counts. Use
  `COUNT(DISTINCT current_ga_client_id)` for stage users, `COUNT(DISTINCT previous_ga_client_id)` for
  entered-from-prior-stage, and `SUM(current_event_count_flag)` / `SUM(transition_count)` for event volume —
  and filter to the row-kind you want.
- **Zero-scaffold rows are intentional** — every defined stage emits a row with NULL identities and zero
  counts so a funnel renders all steps even on days with no traffic. They inflate `COUNT(*)` (~1K/day) and
  must be excluded from any user/event aggregate (they naturally drop out of DISTINCT identity counts).
- **`from_verified_impression` is `{NULL, TRUE}`, never `FALSE`.** "MNTN funnel" = `= TRUE`; "all-volume
  funnel" = the NULL rows (or all rows). Do not write `= FALSE` (matches nothing) or assume NULL means
  "non-verified only" in a way that lets you add it to TRUE — the two partitions are the verified subset
  vs. the broader set, defined by the fact.
- **`event_name` NULL for `sequential`; `event_type` always NULL.** If you need the raw event label/URL/DLV,
  go to `waypoints` / `waypoints_fact`, not this rollup.
- **Small advertiser footprint.** Only advertisers who configured a Waypoint stage mapping appear (15 on
  2026-07-15) — this is a niche funnel product, not all MNTN advertisers. Don't treat coverage as universal.
- **Projection does NOT reduce cost** (see Cost) — the multi-CTE reads the whole `day` partition regardless
  of selected columns; the only lever is the `day` (and secondarily `funnel_mode`/`advertiser_id`) filter.
- **SQLMesh view chain:** query the clean name `summarydata.waypoints_stage_daily`; it resolves to a
  versioned `sqlmesh__summarydata.…__4175487051` view over the physical `waypoints_fact` table. The physical
  `numRows`/`numBytes` on the view objects show 0 (stale metadata) — they are views, not empty.

## Cost & partitioning notes
- **The one filter to always apply: `WHERE day = <date>` (or a tight range).** The view **enforces** a
  partition filter on `day` — omitting it errors ("Cannot query … requires a filter over column(s) 'day'
  that can be used for partition elimination"), which is how partition = `day` (DAY-granularity) was
  confirmed. Backing fact `waypoints_fact` has `requirePartitionFilter=true`.
- **Projection is NOT a cost lever.** Dry-run of one day (2026-07-15): `SELECT *` and a 4-column select
  both estimate **446 MB** — identical, because the CTEs (joins + window functions over `waypoints_fact`)
  read the full day partition regardless of the outer column list. Only narrowing `day` (and secondarily
  `funnel_mode` / `advertiser_id`, the backing-fact cluster keys) reduces bytes.
- **Observed actual (one full day, aggregation over all columns):** ~0.40–0.42 GB billed per day
  (0.416 GB and 0.398 GB on two 2026-07-15 aggregations); ~120–140 slot-seconds, ~4 s wall. Budget roughly
  **~0.4 GB per day** scanned.
- **Effective cluster keys** (inherited from `waypoints_fact`): `advertiser_id`, `campaign_id`,
  `funnel_mode`. Adding these to `WHERE` prunes the backing-fact scan further.
- **`approx_logical_bytes` (42,537,927,068 ≈ 42.5 GB)** = the backing physical `waypoints_fact` `numBytes`
  (187,051,929 rows). This view has no storage of its own; that fact is the dominant physical it reads.

## Example queries
```sql
-- Daily stage funnel: users reaching each sequential stage (MNTN-verified funnel only)
SELECT
  event_group_order AS stage,
  ANY_VALUE(event_group)                 AS stage_name,
  COUNT(DISTINCT current_ga_client_id)   AS stage_users,
  COUNT(DISTINCT previous_ga_client_id)  AS entered_from_prior_stage,
  SUM(transition_count)                  AS event_volume
FROM `summarydata.waypoints_stage_daily`
WHERE day = DATE '2026-07-15'
  AND advertiser_id = <AID>
  AND funnel_mode = 'sequential'
  AND from_verified_impression = TRUE      -- drop this line for the all-volume funnel
GROUP BY stage
ORDER BY stage;
```
