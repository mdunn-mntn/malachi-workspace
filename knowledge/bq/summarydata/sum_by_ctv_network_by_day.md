# summarydata.sum_by_ctv_network_by_day

## Purpose
Publisher/network-level (CTV) daily performance rollup. Reach for it to attribute impressions, spend, video-completion (VAST) events, and conversions/order-value to the **CTV network the impression served on** (Peacock, Tubi, HBO Max, NBC, "Paramount Streaming - Comedy", …). It is the network-grain sibling of `sum_by_campaign_by_day`: same daily fact family, but broken out by `domain` (network) instead of rolled to campaign. Use it for publisher-mix analysis, media-plan-vs-delivery comparison, and per-network attribution across the several attribution methods this table carries side by side.

## Grain & keys
- **Grain:** one row per `advertiser_id` x `campaign_id` x `domain` (CTV network) x `day`. **Verified unique** — on 2026-07-10, `COUNT(*)` = `COUNT(DISTINCT advertiser_id|campaign_id|domain)` = 550,610, no NULL keys.
- **Key(s):** the composite (`advertiser_id`, `campaign_id`, `domain`, `day`). `day` is the DATE partition key.
- **Scale:** ~456.2M rows total; ~2,211 distinct `domain` values on a single recent day; each advertiser x campaign fans out across the networks it delivered on that day.

## Column meanings (only the non-obvious ones)
- **`domain`** — the **human-readable CTV network / streaming-service name**, NOT a URL domain. Values are curated network labels, sometimes genre-split ("Paramount Streaming - Comedy", "Paramount Streaming - Drama"). **Matches `core.media_plan_publishers.name` exactly** (cross-validated TI-748), so it joins the planned publisher list to actual delivery.
- **Spend decomposition (all NUMERIC, USD)** — `media_cost` (raw cost paid for media), `media_spend` (billed media), `data_spend` (3P/data cost), `platform_spend` (platform fee). On the top network (Peacock, 2026-07-10) `media_spend` $113K > `platform_spend` $93.4K > `media_cost` $92.5K > `data_spend` $9.9K. `legacy_spend` is **FLOAT64** (older spend field) and `video_spend` is **BIGNUMERIC** — different types from the four core spend columns; cast carefully when summing across.
- **Attribution measure families** — the same metrics repeat under several attribution methods; pick ONE family, do not add them together:
  - *default* (no prefix): `views`, `clicks`, `view_conversions`, `click_conversions`, `view_order_value`, `click_order_value`, plus assist cols (`visits_assist`, `conversions_assist_click/view`, `conversions_assist_*_order_value`).
  - `last_touch_*` — last-touch attribution variant of the same measures.
  - `last_tv_touch_*` — last-TV-touch attribution variant.
  - `competing_*` — competing/industry-standard attribution variant (`competing_views`, `competing_view_conversions`, `competing_view_order_value`, `competing_last_touch_*`, `competing_last_tv_touch_*`, …). Populated (summed 472,201 competing_views on 2026-07-10). `industry_standard` reporting ≈ last-touch + competing (see `reference_chapi_ui`).
  - `probattr_*` and `probattr_competing_*` — probabilistic-attribution variants (small volumes; probattr_views summed 729 on 2026-07-10).
- **VAST quartiles (INT64)** — `vast_start`, `vast_firstquartile`, `vast_midpoint`, `vast_thirdquartile`, `vast_complete`: video-player completion funnel counts. `view_impressions` / `view_viewed` / `view_untrackable` describe viewability.
- **`display_impressions` vs `video_impressions`** — split of `impressions` by creative format; this is a CTV table so `video_impressions` dominates.
- **HLL++ BYTES columns** — `uniques`, `site_visitors`, `new_site_visitors`, `existing_site_visitors`, `new_users_reached`, `existing_users_reached`, and the `competing_*`/`probattr_*` `*_site_visitors` variants are **HyperLogLog++ sketches**, NOT integers. Read with `HLL_COUNT.EXTRACT(col)` for a single row or `HLL_COUNT.MERGE(col)` to aggregate across rows — a plain `SUM` is meaningless. (`competing_new_visitors`, `probattr_new_visitors`, etc. that are INT64 are plain counts.)

## Joins & relationships
- **`domain` → `core.media_plan_publishers.name`** (string equality; cross-validated TI-748). Partner grain: one row per (media_plan_id, publisher) — a **1:N** relationship both ways (a plan lists many publishers; a network appears across many plans), so join through a specific `media_plan_id` (via `core.media_plan` on `advertiser_id`/`campaign_group_id`) or aggregate first. Naive join network→publisher-list fans out.
- **`advertiser_id` → `core.advertisers`** (many rows here : 1 advertiser). **`campaign_id` → `core.campaigns`** (many : 1). Both are safe dimension lookups (filter dims `deleted=FALSE AND is_test=FALSE`).
- **Cross-validated against `logdata.cost_impression_log`** — same top-5 publishers in the same rank order (TI-748 / CWRV Sales Feb 2026). Counts differ slightly due to campaign-level filtering, but proportions hold; this table is a valid, far cheaper proxy for publisher-level analysis than scanning the impression log.
- **Sibling `summarydata.sum_by_campaign_by_day`** — same daily fact family rolled to campaign (no `domain`). Use it when you need campaign totals without the network breakout; use THIS table when you need the network split. Do not join the two on measures (double-counts) — pick the grain you need.

## Gotchas
- **DRIFT — competing_* / probattr_* columns now EXIST and are populated.** The `data_catalog.md` prose said this table "does NOT have competing_views/conversions columns … use sum_by_campaign_by_day instead." That is **stale**: as of 2026-07-19 the full `competing_*`, `last_touch_*`, `last_tv_touch_*`, and `probattr_*` attribution families are present and populated, so network-grain industry-standard (competing) attribution CAN be computed here directly.
- **DRIFT — data starts 2024-01-01, not 2025-01-01.** Partition metadata: `min_partition = 20240101`, `max = 20260719` (today). Prose said "2025-01-01 to present."
- **Empty `__NULL__` partition.** INFORMATION_SCHEMA lists a `__NULL__` partition but it holds **0 rows** — no rows have NULL `day`. (It sorts lexically after real dates, so a naive `MAX(partition_id)` returns "__NULL__"; exclude it.)
- **Pick ONE attribution family.** default / last_touch / last_tv_touch / competing / probattr all coexist as separate columns — summing across families double-counts the same conversions.
- **HLL++ BYTES visitor/unique columns** — never `SUM`; use `HLL_COUNT.MERGE` / `HLL_COUNT.EXTRACT`.
- **`require_partition_filter = TRUE`** — every query MUST filter `day` or it errors before running.
- **Mixed spend types** — `legacy_spend` FLOAT64, `video_spend` BIGNUMERIC, the four core spend cols NUMERIC; watch type coercion.

## Cost & partitioning notes
- **The one filter to always apply:** `WHERE day = / BETWEEN …` — DAY-partitioned on `day`, `require_partition_filter = TRUE` (query errors without it). No clustering, no TTL (full history retained from 2024-01-01).
- Physical: resolves directly to `sqlmesh__summarydata.summarydata__sum_by_ctv_network_by_day__211569296` (a real TABLE, not a chained view). ~456.2M rows, ~386.7 GiB logical (`numBytes` 415.2 GB), 901 populated day partitions (902 total incl. an empty `__NULL__`).
- **Dry-run figures (columns `advertiser_id, impressions` only):** 1 day = **13.2 MB**; 30 days = **364 MB** — linear in day count, confirming `day` prunes. Full-table SELECT of these 2 narrow cols would be ~30x the 30-day figure. Wide `SELECT *` (86 columns, many NUMERIC/BIGNUMERIC/BYTES) is far more expensive — a 1-day `SELECT *` dry-runs at ~550 MB, ~42x the 13.2 MB narrow-column 1-day scan. Project only the columns you need.

## Example queries
```sql
-- Per-network delivery + spend for one advertiser, one day
SELECT domain, SUM(impressions) imps, SUM(views) views,
       SUM(media_spend) media_spend, SUM(data_spend) data_spend,
       SUM(view_conversions) view_conv, SUM(view_order_value) view_ov
FROM `summarydata.sum_by_ctv_network_by_day`
WHERE day = DATE '2026-07-10' AND advertiser_id = <aid>
GROUP BY domain ORDER BY imps DESC;

-- Unique site visitors per network (HLL++ — MERGE, never SUM)
SELECT domain, HLL_COUNT.MERGE(site_visitors) AS unique_visitors
FROM `summarydata.sum_by_ctv_network_by_day`
WHERE day BETWEEN DATE '2026-06-11' AND DATE '2026-07-10'
GROUP BY domain ORDER BY unique_visitors DESC;
```
