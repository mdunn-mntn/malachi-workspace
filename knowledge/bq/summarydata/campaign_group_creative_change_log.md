# summarydata.campaign_group_creative_change_log

## Purpose
Append-only CDC audit log recording every edit made to a **creative** inside a campaign group in the MNTN UI. Reach for it to answer "who changed this creative, when, and what was the value before/after" — click-through URL changes, rotation-weight changes, active/paused flips, and creative-name renames. It is a change-history log, **not** a current-state table: to know a creative's *current* setting you take the latest `time` per (entity, change_id), or join to the live creative dim. `change_type` is always `Creative` and `entity_type` is always `ui_creative_group_id`, so despite the generic column names this table only ever logs one entity kind.

## Grain & keys
- **Grain:** one row per logged creative-attribute **change event** — i.e. one edit to one field of one `ui_creative_group_id`. 516,270 rows spanning 2024-01-01 → present (2026-07-19), 149,078 distinct creatives, 6,221 distinct editing users.
- **Natural key (near-unique, not enforced):** `(advertiser_id, campaign_group_id, entity_id, change_id, time)` → 513,751 distinct of 516,270 rows (~0.5% collide because `time` is second-granularity and two edits to the same field in the same second are indistinguishable). There is **no** guaranteed unique row id — `change_id` is a change-*type* code, not a row id.
- **Entity being changed:** `entity_id` = the `ui_creative_group_id`; `entity_text` = that creative's display name/filename at edit time.

## Column meanings (only the non-obvious ones)
- **`time`** — native BigQuery `TIMESTAMP` (UTC-normalized), **not** an epoch integer, so no unit conversion needed. Second-granularity as stored (sub-second is 0). This is the edit timestamp.
- **`change_id`** — a change-**type** code identifying *which* creative attribute was edited (NOT a per-row surrogate key). Empirically only 4 values exist:
  - `43` (117,805 rows) — **click-through / landing-page URL** (`current_value` = a URL; also seen blank/whitespace).
  - `45` (219,875 rows) — **rotation weight percentage** (`current_value` in `"0%"`…`"99%"`/`"100%"`).
  - `47` (167,863 rows) — **active/enabled flag** (`current_value` ∈ {`true`,`false`}).
  - `65` (10,727 rows) — **creative name/label** (free text, e.g. `"Standard ranch 2"`, emoji-prefixed names; 10,216 distinct).
- **`change_type`** — always the literal `Creative` (single-valued across all 516K rows). This log is creative-only; the column exists for schema-parity with other change logs.
- **`entity_type`** — always `ui_creative_group_id`; **`entity_id`** is that id, **`entity_text`** its name at edit time.
- **`entity_id_2` / `entity_text_2` / `entity_type_2`** — **entirely NULL** in this table (100% of rows). Reserved for a secondary entity used by other change-log tables; unused for creative changes. Do not attempt to join on them.
- **`prior_value` / `current_value`** — before/after string values of the edited field (all values stringified regardless of underlying type). **`prior_value` is NULL in ~51% of rows (265,070)** — these are creation / first-set events (no prior state). `current_value` NULL/blank = field cleared.
- **`user_id`** — the user who made the edit. **NULL in ~3.6% of rows (18,639)** — system/automated or unattributed changes.
- **`advertiser_id` / `campaign_group_id`** — the advertiser and parent campaign group owning the creative.

## Joins & relationships
All joins from this log go to a **1** on the partner side (each dim keyed by its id), so joins are **N:1 — no fan-out from the dim**. The fan-out risk runs the other way: this is a many-row-per-entity history, so joining a current-state fact/dim to this log **multiplies** rows (one per historical edit) — dedup to the latest `time` per key first.
- **`advertiser_id`** → `integrationprod` advertisers dim (1:1 on advertiser; join `advertisers.company_name`, since `fpa_advertiser_verticals.advertiser_name` is empty). Filter dims `deleted=FALSE AND is_test=FALSE`.
- **`campaign_group_id`** → `campaign_groups` (1:1 on the group; `product_id` 1=PTV / 2=Select / 3=QuickFrame lives here).
- **`entity_id`** (= `ui_creative_group_id`) → the UI creative-group dim (1:1 on creative group). This log holds the audit history; the dim holds current state.
- **`user_id`** → users dim (1:1 on user). NULL for system changes — use a LEFT join.

## Gotchas
- **Not a snapshot / current-state table.** It is an event log. A creative appears once per *edit*; to reconstruct current state take `ARRAY_AGG(... ORDER BY time DESC LIMIT 1)` per `(entity_id, change_id)`.
- **Generic column names, single-valued in practice.** `change_type='Creative'` and `entity_type='ui_creative_group_id'` for **every** row; the `*_2` entity columns are 100% NULL. Don't filter on them expecting variety.
- **`change_id` is a type code, not a key.** Only {43,45,47,65} occur; there is no unique row id, and the near-key collides at second granularity (~0.5%).
- **`prior_value` NULL = creation, not missing data** (~51% of rows). Don't treat these as data-quality gaps.
- **All values are strings** — `"100%"`, `"true"`, URLs, names all come back as STRING in `prior_value`/`current_value`; cast/parse per `change_id`.
- **No TTL / full history** from 2024-01-01 (typical SQLMesh backfill floor); the table only grows.
- **View → single physical table.** `summarydata.campaign_group_creative_change_log` is `SELECT *` over `sqlmesh__summarydata.summarydata__campaign_group_creative_change_log__<hash>`; the hash rotates on rebuild — always query the clean view name.

## Cost & partitioning notes
- **NOT partitioned, NOT clustered** (physical `timePartitioning`/`rangePartitioning`/`clustering` all null; confirmed empirically — a `WHERE time >= '2026-07-01'` dry-run returns the **same** 72,248,278 bytes as unfiltered `SELECT *`, i.e. **no partition pruning**). A `time` filter does **not** reduce scan cost here.
- **The lever is column projection, not a partition filter.** The table is tiny (~72 MB / 516K rows); BQ columnar pruning is the only cost knob. Dry-run figures (labeled by column set):
  - `SELECT *` (all 14 cols): **72,248,278 bytes** (~68.9 MiB) — this equals the full backing storage (`numBytes`).
  - `SELECT change_type` (one narrow col): **5,162,700 bytes** (~4.9 MiB) — ~14× cheaper.
- So: **avoid `SELECT *`; project only the columns you need.** Even a full scan is <0.1 GB, so this table is cheap regardless.

## Example queries
```sql
-- Latest value of each creative attribute for a campaign group (reconstruct current state)
SELECT entity_id, change_id,
       ARRAY_AGG(current_value ORDER BY time DESC LIMIT 1)[OFFSET(0)] AS current_value,
       MAX(time) AS last_changed
FROM `summarydata.campaign_group_creative_change_log`
WHERE campaign_group_id = 130952
GROUP BY entity_id, change_id;

-- Who paused (change_id 47 → false) which creatives, most recent first
SELECT time, advertiser_id, campaign_group_id, entity_id, entity_text, user_id
FROM `summarydata.campaign_group_creative_change_log`
WHERE change_id = 47 AND current_value = 'false'
ORDER BY time DESC
LIMIT 100;
```
