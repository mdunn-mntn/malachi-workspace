# summarydata.waypoints_by_day

## Purpose
The Waypoint funnel product — a daily rollup of on-site event/funnel activity per advertiser × campaign. A "waypoint" is a named funnel **stage** an advertiser defines from its pixel events (e.g. `Landing → Quote → Product Interest → Purchase`, or `Site Entry → Eligibility & Loan Purpose → …`). This view powers funnel / customer-journey reporting in the client UI. Reach for it to answer "how many users reached each funnel stage" and "how many transitioned from stage N to stage N+1," split by whether the activity was driven by a verified MNTN ad impression. It is a **heavily-computed rollup view** built over the base fact `waypoints_fact` plus advertiser stage definitions (`attr_advertiser_waypoints_event_mapping`).

## Grain & keys
- **Grain:** one row per `day × advertiser_id × campaign_id × funnel_mode × from_verified_impression × stage descriptor (event_group / event_group_order / event_name) × transition edge (source_* / target_*) × identity tuple (current_ga_client_id / current_session_key / current_ad_served_id) × previous-identity`. `current_event_count_flag` and `transition_count` are the **pre-summed measures** at that grain. This is a **mixed grain**: some rows are user/session-level detail, some are stage-scaffold zeros, some are aggregate — see Gotchas.
- **Empirical (day 2026-07-15):** 1,162,616 rows; 15 advertisers; 133 campaigns. `full_volume` = 632,557 rows, `sequential` = 530,059 rows. My partial-key distinct count (14 cols) = 1,120,821 (~96% of rows) — the true grain also includes `event_name` + all `previous_*`/`target_*` columns.
- **Natural keys / join columns:** `advertiser_id`, `campaign_id` (+ `event_group`/`event_group_order` for the stage). `day` is the required partition filter.

## Column meanings (only the non-obvious ones)
- **`funnel_mode`** (STRING, cluster #3) — determines the entire row semantics. Live domain (`SELECT DISTINCT`, 2026-07-15) = **{`full_volume`, `sequential`}**:
  - **`full_volume`** — raw per-event-name volume. Every tracked event counted, keyed by `event_group` (stage) + `event_name` (the specific pixel event). `current_event_count_flag` holds the event count. **No** transition tracking (`transition_count`=0, `has_target_transition`=0).
  - **`sequential`** — the ordered funnel. Stage-to-stage transitions with **zero-scaffolding**: every defined stage is emitted even with zero activity. On 2026-07-15, 529,642 of 530,059 sequential rows were scaffold zeros (`current_event_count_flag`=0); only 417 carried a real `transition_count`. `source_event_group → target_event_group` encode the transition edge (e.g. `Landing → Quote`).
- **`current_event_count_flag`** (INT64) — **misleading name: this is a SUMMED COUNT, not a 0/1 flag.** Range 0–73,265 in the sample. In `full_volume` = count of that event; in `sequential` = count contributing to that stage (0 on scaffold rows).
- **`transition_count`** (INT64) — count of stage-to-stage transitions. Nonzero only in `sequential` mode; 0 in `full_volume` and on scaffold rows.
- **`has_target_transition`** (INT64) — 0/1 flag: whether the row represents a valid transition into `target_event_group` (a real funnel edge).
- **`event_group`** (STRING) — the named funnel **STAGE / waypoint** (advertiser-defined), e.g. `Landing`, `Quote`, `Product Interest`, `Purchase`, `Site Entry`, `Eligibility & Loan Purpose`.
- **`event_group_order`** (INT64) — the stage's ordinal position in the funnel (1, 2, 3, …).
- **`event_name`** (STRING) — the specific event within a stage. Populated in `full_volume` (e.g. `Home/Landing`, `conversion`, `Auto`, `eligibility`, `Loan Details`); **NULL in `sequential`** rows.
- **`event_type`** (STRING) — **entirely NULL** (1,162,616 / 1,162,616 rows on 2026-07-15). Reserved/unused in current data — do not rely on it.
- **`from_verified_impression`** (BOOL) — whether the waypoint activity is attributed to a **verified MNTN ad impression** (an ad-driven "MNTN visit"). Observed values: **TRUE or NULL — FALSE never appeared** in the sample. NULL on scaffold and non-impression-keyed aggregate rows. Aliased `is_mntn_visit` in the underlying view. Splitting on it separates ad-attributed activity from total.
- **`current_ga_client_id` / `current_session_key` / `current_ad_served_id`** (STRING) — identity of the "current" event: Google Analytics client id, web session key, and the served-ad id it is attributed to. Populated on user-presence/detail rows, **NULL on scaffold and aggregate rows**. `current_ad_served_id` is ~94% NULL (only impression-linked rows carry it); `current_ga_client_id` ~77% populated.
- **`previous_ga_client_id` / `previous_session_key` / `previous_event_group` / `previous_event_group_order` / `previous_event_name`** — the PRIOR stage/event the user came from in the sequence (the source side of a transition).
- **`source_event_*` vs `target_event_*`** — the FROM (source) and TO (target) endpoints of a funnel transition edge. In `sequential` mode: source = previous stage, target = current stage.

## Joins & relationships
- **`advertiser_id` → `advertisers.id`** (silver.core / `integrationprod.advertisers`) — N:1, dim lookup. Join for `company_name` (note: `fpa_advertiser_verticals.advertiser_name` is unreliable/empty since 2025-12 — use `advertisers.company_name`). Fan-out safe (many waypoint rows per advertiser; dim side is 1).
- **`campaign_id` → `campaigns.id`** — N:1 dim lookup; cluster key #2. Fan-out safe from the dim side.
- **Stage definitions** (the funnel stage list that drives the sequential zero-scaffold): `integrationprod.attr_advertiser_waypoints_event_mapping` (grain ≈ one row per advertiser × `event_group` × `event_group_order`, with a `deleted` flag classifying event names into stages), consumed via `sqlmesh__ber_stg.ber_stg__waypoints__event_mapping_prepared`. Related config: `attr_advertiser_selective_performance_config`. 1 stage-definition row per (advertiser, event_group_order) after the view's `QUALIFY row_number()=1` dedup.
- **Base fact `sqlmesh__summarydata.summarydata__waypoints_fact__2720337691`** (physical TABLE: 232,613,083 rows, ~54.1 GB as of 2026-07-29 — up from 187M/42.5 GB at enrichment; rolling retention, partition `day` DAY require-filter, cluster `advertiser_id, campaign_id, funnel_mode`) — `waypoints_by_day` is the computed rollup over this fact + stage definitions. Lineage: `waypoints_by_day` → `waypoints_stage_daily` (view) → `waypoints_fact` (fact) ⋈ `waypoints__event_mapping_prepared` (stage defs).
- **`current_ad_served_id`** could in principle link to ad-served/impression logs, but it is ~94% NULL — not a reliable join key.

## Gotchas
- **Column pruning does NOT reduce cost.** This is a scaffold/self-join-heavy computed view: `SELECT day, advertiser_id, transition_count` scans the **same 446 MB/day** as `SELECT *`. The whole day's base fact must be read regardless of projection.
- **Mixed grain / scaffold rows.** `sequential` mode is ~99.9% zero-scaffold rows (every defined stage emitted with count 0). **Never treat `COUNT(*)` as "events."** Filter `current_event_count_flag > 0` (activity) or `transition_count > 0` (transitions) for real signal.
- **`current_event_count_flag` is a COUNT, not a flag** (name is misleading) — safe to `SUM`, but only within a single `funnel_mode`.
- **Never sum across `funnel_mode`.** `full_volume` and `sequential` are two different models over the same events; adding them double-counts.
- **`event_type` is entirely NULL** — do not use it.
- **`event_name` is NULL in `sequential`** — only populated in `full_volume`.
- **`from_verified_impression` is TRUE or NULL (never FALSE seen)** — NULL marks scaffold/aggregate rows, so `WHERE from_verified_impression` (TRUE only) isolates ad-attributed activity and drops everything else.
- **Small opt-in product** — only ~15 advertisers, ~133 campaigns/day. Not representative of the full MNTN advertiser base.
- **`require_partition_filter = TRUE`** — any query without a `day` filter **errors** ("Cannot query over table … without a filter over column(s) 'day'").

## Cost & partitioning notes
- **Always filter `day`** — it is required; a no-filter query errors.
- Partition = `day` (DATE, DAY granularity, require-filter). Physical clustering = `advertiser_id, campaign_id, funnel_mode` — filtering these prunes the base-fact scan.
- Dry-run upper bounds (`bq_run.sh --dry_run`, labeled by column set):
  - **1 day, `SELECT *`** → 446,103,688 bytes (~0.42 GiB). Actual scanned ~0.40 GB.
  - **1 day, 3 narrow cols** (`day, advertiser_id, transition_count`) → **446,103,688 bytes — identical** to `SELECT *` (view forces full scan; pruning ineffective).
  - **7 days, `SELECT *`** → 2,053,220,795 bytes (~1.9 GiB) — scales ~linearly with day count, confirming `day` is the partition.
  - **No filter** → ERROR (require_partition_filter on `day`).
- `approx_logical_bytes` (54.1 GB, 2026-07-29) = the base physical fact `waypoints_fact.numBytes`; the view is non-materialized (physical row/byte counts are 0).

## Example queries
```sql
-- Sequential funnel: real stage-to-stage transitions for one advertiser
SELECT event_group, event_group_order, source_event_group, target_event_group,
       SUM(transition_count) AS transitions
FROM `summarydata.waypoints_by_day`
WHERE day BETWEEN DATE '2026-07-09' AND DATE '2026-07-15'
  AND funnel_mode = 'sequential'
  AND advertiser_id = 45458
  AND transition_count > 0
GROUP BY 1,2,3,4
ORDER BY event_group_order;

-- Full-volume event counts by stage/event, ad-attributed only
SELECT event_group, event_name, SUM(current_event_count_flag) AS events
FROM `summarydata.waypoints_by_day`
WHERE day = DATE '2026-07-15'
  AND funnel_mode = 'full_volume'
  AND from_verified_impression   -- TRUE only; NULL rows dropped
GROUP BY 1,2
ORDER BY events DESC;
```
