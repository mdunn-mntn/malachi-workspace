# summarydata.unstable_cost_impression_log

## Purpose
NON-canonical **staging / CDC audit** view — do not use it as an impression fact table. It captures the
before/after states of cost-impression rows that get **corrected and restated** down the CIL pipeline
(`raw → spend_log → cil__impression_info → cost_impression_log`; e.g. the geo_version / uniques patch in
PR #1033). Reach for it only when you need to **audit a specific correction batch** (what changed, when,
for which impressions). For any actual served-impression / spend / reach / score analysis use the stable
canonical sibling **`logdata.cost_impression_log`** (deduped, one row per served impression, carries the
score columns this view lacks).

The `summarydata.unstable_cost_impression_log` view is a thin `SELECT *` over the SQLMesh physical view
`sqlmesh__summarydata.summarydata__unstable_cost_impression_log__3037319118`, which resolves to a
**`UNION ALL` of two BER-staging physical TABLEs** in `sqlmesh__ber_stg`:
- `ber_stg__unstable__cil_post_change__3518197138` — TABLE, ~930M rows, ~1.04 TB, part `time` DAY, cluster [advertiser_id, change_id]
- `ber_stg__unstable__cil_pre_change__2173039449` — TABLE, ~2.45B rows, ~2.71 TB, part `time` DAY, cluster [advertiser_id, change_id]

## Grain & keys
- **Grain:** one row per **(impression × correction-batch × pre/post snapshot)** — i.e. one row per
  impression **per `change_id` batch that touched it, in each `batch_source` state**. This is NOT one row
  per impression: an impression restated by a correction appears multiple times (old value under
  `pre_change`, new value under `post_change`, once per batch). Measured 2026-07-10: **14.56M rows over
  10.27M distinct `impression_id` (~1.42x)**, spanning 1,291 distinct `change_id` batches.
- **Natural key of the impression:** `impression_id` (= the served impression). **Correction-batch key:**
  `change_id` (INT surrogate, 1:1 with `change_time`). **Snapshot state:** `batch_source` ∈ {`pre_change`,
  `post_change`}. To collapse to one row per impression, take `batch_source='post_change'` and the latest
  `change_id` per `impression_id` — or just query `logdata.cost_impression_log`.

## Column meanings (only the non-obvious ones)
CDC / staging bookkeeping columns (these are what make this view different from the stable CIL):
- **`change_id`** (INT) — surrogate key of the **correction/restatement batch** that produced this row.
  **1:1 with `change_time`** (verified: every `change_id` has a single min=max `change_time`). Groups all
  impressions restated together (one row per impression per batch). NULL/absent on rows that were never
  part of a correction. Also a **cluster key** on the physicals.
- **`batch_source`** (STRING) — snapshot state; **only two values: `pre_change` / `post_change`**. Tells you
  which UNION leg (which physical) the row came from: `pre_change` = the row's value BEFORE the correction
  (superseded), `post_change` = the value AFTER (current/corrected). Use it to pick the state you want.
- **`change_time`** (TIMESTAMP) — when the correction batch's change was recorded. **Can be AFTER the
  impression `time`** (corrections land days later — e.g. impression 2026-07-10 corrected by a batch dated
  2026-07-14). Late-arriving.
- **`change_epoch`** (INT) — **SECONDS** since Unix epoch = `UNIX_SECONDS(change_time)` (verified
  `1784049000` ↔ `2026-07-14 17:10:00 UTC`).
- **`batch_epoch`** (INT) — **SECONDS** since Unix epoch; when the staging batch was processed/loaded (no
  paired TIMESTAMP column; magnitude ~1.784e9 confirms seconds, e.g. `1784230640` ≈ 2026-07-16).

Impression columns (same meanings as the stable `logdata.cost_impression_log`):
- **`epoch`** (INT) — impression event time in **MICROSECONDS** since Unix epoch (`= UNIX_MICROS`), and it
  carries **sub-second (ms) precision** (verified `1783646611103000` µs ↔ `2026-07-10 01:23:31 UTC`). The
  `time` column is that same instant **truncated to the whole second** (`UNIX_MICROS(time)` = `...611000000`).
  Three epoch columns here, three different units: `epoch`=µs, `change_epoch`=s, `batch_epoch`=s.
- **`time`** (TIMESTAMP) — impression served time, **UTC**, second-truncated. **PARTITION column (DAY).**
- **`partner_time`** (TIMESTAMP) — partner/exchange-reported impression time.
- **`ip`** — resolved device IP (= `bid_ip`); **`partner_ip`** — partner-reported IP; **`guid`** — cookie/device id.
- **`media_cost`** (NUMERIC) = raw media cost; **`media_spend` / `data_spend` / `platform_spend`** (BIGNUMERIC)
  = the customer-facing spend split. **These are per-row spend — over-counted if you don't dedup (see Gotchas).**
- **`unlinked`** (BOOL) — TRUE = no `impression_id` match in `impression_log` (then `ad_served_id` is NULL);
  FALSE = linked/won impression.
- **`is_new`** (BOOL) — client-JS "new user" flag (same caveats as elsewhere: JS-pixel derived, noisy).
- **`geo_version`** (INT) — geo-enrichment version; this is the column whose empty-string/cast bug was
  fixed in PR #1033 (a correction restated through exactly this pipeline).
- **`recency_elapsed_time`** (INTERVAL) — BQ `INTERVAL` type; not usable in all SQL contexts / some
  connectors (e.g. Spark BQ connector) fail to resolve it.
- Viewability: **`view_impression_raw` / `view_viewed_raw` / `view_untrackable`** (viewability counters) and
  **`vast_start … vast_complete`** (VAST video-quartile counters).
- **Absent vs stable CIL:** no `household_score`, `advertiser_household_score`, or `model_params` — this
  staging view **cannot answer scoring / HI / RTC questions**; go to `logdata.cost_impression_log`.

## Joins & relationships
- **Canonical sibling — `logdata.cost_impression_log`** (different dataset): the stable, deduped served-
  impression fact (1 row per impression), grain = one impression. This `unstable` view is its **upstream
  CDC/correction staging** and is 1:N against it. Prefer the stable table for everything except correction audits.
- **`impression_id` → `logdata.impression_log.ttd_impression_id`** and **`event_log.td_impression_id`**
  (confirmed join keys in the prose). Partner grain there is 1 row per impression, but **this view is 1:N on
  `impression_id`** (N = correction batches × pre/post states), so a direct join **fans out** — collapse to
  one row per impression first (`post_change` + latest `change_id`).
- **`advertiser_id` → `advertisers` / dims** (many:1); **`metro_id` → `summarydata.metros.metro_id`**
  (Nielsen DMA code, many:1); **`campaign_id` / `group_id` / `creative_id`** → the campaign dims (many:1).
  All of these fan out the SAME way — never join this view to a 1-row-per-entity dim without first
  deduping to one row per impression.

## Gotchas
- **NON-canonical staging/CDC view — not an impression fact.** Use `logdata.cost_impression_log` for real
  impression/spend/reach/score work. (No prose oracle existed for this table; enriched from live schema.)
- **Duplicates by design.** Rows:impressions ≈ **1.42x** on 2026-07-10 (14.56M rows / 10.27M distinct
  `impression_id`). Naive `COUNT(*)` or `SUM(media_spend)` **over-counts** — always dedup by
  `impression_id` (keep `post_change`, latest `change_id`) before aggregating.
- **`pre_change` AND `post_change` both present.** `batch_source` discriminates; `post_change` = corrected
  current value, `pre_change` = superseded prior value. For this impression day both legs appear but for
  different `change_id`s (post_rows 12.06M >> pre_rows 2.51M on 2026-07-10).
- **Three epoch columns, three units** — `epoch` µs, `change_epoch` s, `batch_epoch` s. Don't assume one unit.
- **Partition `time` is second-truncated (UTC);** `epoch` keeps the sub-second precision. All timestamps UTC.
- **Late-arriving / mutable partitions.** `change_time` can post-date the impression by days; an impression-`time`
  partition keeps gaining pre/post rows as new correction batches run, so historical partitions are not stable.
- **No score columns** (`household_score` / `model_params` absent) — can't do HI/RTC/scored-fraction analysis here.

## Cost & partitioning notes
- **The one filter to always apply: `WHERE time >= '<start>' AND time < '<end>'`** (partition = `time`, DAY).
  `require_partition_filter` is **not** enforced, but backing storage is **~3.75 TB** (real: 1.04 TB
  post_change + 2.71 TB pre_change, `bq show numBytes` summed across the two UNION physicals) so an
  unfiltered scan is very expensive. Cluster keys `[advertiser_id, change_id]` further prune when you also
  filter an advertiser or a specific correction batch.
- **Dry-run, `SELECT change_id` only:** full-table **27.07 GB** vs **one day 0.233 GB** — the `time` filter
  prunes ~116x (this is the empirical partition confirmation; same one-column set both sides).
- **Real one-day query costs (labeled by column set):** 5-col epoch sample (`epoch,time,change_epoch,
  change_time,batch_epoch,batch_source,change_id`) = 0.031 GB; 3-col dup check (`impression_id,change_id,
  batch_source`) = 0.985 GB; group-by (`batch_source,change_id,change_time,batch_epoch,impression_id`) =
  1.094 GB. Cost scales with the number of columns referenced — select only what you need and avoid `SELECT *`.

## Example queries
```sql
-- Canonical-ish impression slice from the staging view (dedup pre/post): one row per impression, corrected state
SELECT * EXCEPT(rn) FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY impression_id ORDER BY change_id DESC) AS rn
  FROM `summarydata.unstable_cost_impression_log`
  WHERE time >= TIMESTAMP('2026-07-10') AND time < TIMESTAMP('2026-07-11')
    AND batch_source = 'post_change'
) WHERE rn = 1;

-- Audit a single correction batch: what changed for change_id X (pre vs post)
SELECT batch_source, COUNT(*) AS n, COUNT(DISTINCT impression_id) AS imps, ANY_VALUE(change_time) AS change_time
FROM `summarydata.unstable_cost_impression_log`
WHERE time >= TIMESTAMP('2026-07-10') AND time < TIMESTAMP('2026-07-11') AND change_id = <X>
GROUP BY batch_source;
```
