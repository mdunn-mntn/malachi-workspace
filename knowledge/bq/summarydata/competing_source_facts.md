# summarydata.competing_source_facts

## Purpose
Records, hour by hour, the **site-visitors of an MNTN advertiser who arrived carrying a *competing* marketing source's tracking tag** — i.e. a visitor who converted/visited the advertiser's site with a landing-page URL parameter that belongs to some other channel (Google Ads `gclid`/`gbraid`/`wbraid`, TikTok/paid `utm_source`/`utm_medium`/`utm_campaign`, `cid`, `cm_mmc`, …). This is the raw fact behind MNTN's **"competing" / industry-standard last-touch attribution** surfaced in the client UI (CHAPI) — it answers "which of this advertiser's converters were *also* driven by a competing channel, and how much revenue did that competing source touch?" Reach for it when you need competing-source view/conversion/revenue counts sliced by the tracking parameter, geo, creative, or supply path. **View is a thin `SELECT *` passthrough** over the physical SQLMesh table `sqlmesh__summarydata.summarydata__competing_source_facts__411286732` — query the clean name `summarydata.competing_source_facts`.

## Grain & keys
- **Grain:** one row per `hour` × full ad-serving dimension tuple (advertiser/campaign_group/campaign/channel/objective/group/creative/private_marketplace + geo `country`/`metro_id`/`region`/`city`/`postal_code` + `domain`/`supply_vendor`/`device_type`) × **`(key, value)` tracking-parameter pair**. Verified **unique**: for one hour, `COUNT(*) − COUNT(DISTINCT tuple) = 0` (0 dup rows across all 19 dimension columns + key + value).
- **Exploded by tracking key — the defining structural fact:** the SAME set of visitors appears in *multiple rows*, one per tracking key present on their URLs. A single competing-source slice (e.g. a TikTok campaign) emits separate `utm_source`, `utm_medium`, `utm_campaign` rows that each carry the **same** `site_visitors_arr` / `competing_views` / `competing_view_conversions`. See Gotchas — never `SUM` measures across `key`.
- **No single surrogate key.** Join columns are the dimension IDs (`advertiser_id`, `campaign_id`, `campaign_group_id`, `creative_id`, `channel_id`, `objective_id`, `metro_id`).

## Column meanings (only the non-obvious ones)
- **`hour`** — DATETIME, **hourly-truncated** (24 distinct values per calendar day: `…T00:00:00` … `…T23:00:00`). This is the **partition column** but the physical partitioning granularity is **DAY** (not HOUR). No epoch/int time column exists — all time is this wall-clock DATETIME (assume UTC per DW convention; `time_unit: datetime`).
- **`key`** — the *name* of the tracking parameter found on the competing-source landing URL. Observed domain (one day): `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gclid` (Google Ads click id), `gbraid`/`wbraid` (Google app/web click ids), `&cid`/`?cid`/`%26cid`/`&amp;cid` (raw-encoded cid variants), `cm_mmc`, and `-1` (sentinel = no/undecodable parameter). Not an ID — a raw querystring key.
- **`value`** — the observed *value* of that `key` (e.g. `utm_source`→`tiktok`, `utm_medium`→`paid`, `utm_campaign`→a campaign name string). Free-text; identifies the specific competing source/channel.
- **`site_visitors_arr`** — `ARRAY<STRING>` of the **distinct visitor IPs** (e.g. `166.199.8.73`) counted for this row. Verified deduped: `ARRAY_LENGTH` == distinct-length in 100% of matched rows. NOT NULL (empty array when zero).
- **`competing_views`** — `= ARRAY_LENGTH(site_visitors_arr)` (holds in 148,624/150,127 one-hour rows; the ~1% gap is empty-array rows where the count is NULL). So it is the **count of distinct competing-source visitor IPs**, not an impression count.
- **`competing_view_conversions`** / **`competing_view_order_value`** — conversions and order revenue (NUMERIC) attributed to those competing-source visitors. `order_value` is 0 for lead/no-revenue advertisers (positive in ~3.1K/150K rows sampled); it is a raw order value, not USD-normalized.
- **`probattr_*` (4 columns)** — the **probabilistic-attribution** variant of the same four measures (`probattr_site_visitors_arr`, `probattr_competing_views`, `probattr_competing_view_conversions`, `probattr_competing_view_order_value`). **Very sparsely populated** — `probattr_competing_views > 0` in only 91/150,127 sampled rows. Treat the deterministic (IP-array) columns as the primary signal; probattr is a secondary lens that is empty on most rows.
- **`domain`** — the site/app where the competing view occurred; for CTV (`channel_id=8`) this is an **app name** (e.g. `Peacock`), not a web domain.
- **`supply_vendor`** — SSP/exchange **name string** (e.g. `STICKYADS`), not an id.
- **`device_type`** — STRING enum: `SET_TOP_BOX`, `CONNECTED_TV`, `MOBILE`, `PC`, `TABLET`, `GAMES_CONSOLE`, `PHONE`, `-1` (sentinel/unknown).
- **`channel_id`** — `8` = CTV (dominant), `1` = display. **`objective_id`** — `1` Prospecting, `4` Retargeting, `5` MT-S2, `6` MT-S3 (per DW objective domain; use `campaigns.funnel_level` for authoritative stage).
- **Geo sentinels** — `city`/`region`/`postal_code` are STRING and carry `-4` / `-1` for unknown geo; `metro_id` uses **negative values** for unknown (~0.15% of rows). Filter these out for clean geo rollups.
- **`private_marketplace_id`** — STRING, **effectively always populated** (0 empty, only ~9/150K = `-1`); real PMP/deal id on nearly every row (CTV supply is deal-heavy).

## Joins & relationships
All joins are **fact → dimension** lookups (this table is the many side): 1 dim row : N fact rows, so the dim side is fan-out-safe; the risk is on THIS table's key-explosion (below), not the dims.
- **`advertiser_id`** → `bronze.integrationprod.advertisers` (1 advertiser : N rows). Use `advertisers.company_name` for names (`fpa_advertiser_verticals.advertiser_name` is empty since 2025-12). Filter dim `deleted=FALSE AND is_test=FALSE`.
- **`campaign_id`** → `campaigns` (use `funnel_level` for stage, not `objective_id`); **`campaign_group_id`** → `campaign_groups` (`product_id` 1=PTV/2=Select/3=QuickFrame); **`creative_id`** → `creatives`; **`group_id`** → ad-group / line-item dim (id, not resolved here).
- **`metro_id`** → geo/DMA dim. `supply_vendor`/`domain`/`device_type` are already denormalized strings — no join needed.
- **Fan-out warning:** joining this table to any per-visit or per-conversion fact will **multiply by the number of tracking keys** on each slice (a 41-visitor slice = 3+ rows). Restrict to a single `key` before joining, or the join inherits the key-explosion multiplier.
- **`site_visitors_arr` IPs** are join-able to IP-keyed data only via UNNEST + external IP bridge — **no in-BQ IP→IP bridging** (external only); avoid graph_ips self-joins.

## Gotchas
- **NEVER `SUM` a measure across `key`.** Because the grain is exploded per tracking parameter, the identical `site_visitors_arr` / `competing_views` / `competing_view_conversions` / `competing_view_order_value` repeat under `utm_source`, `utm_medium`, `utm_campaign`, `gclid`, … for the same slice. Summing over all keys **double/triple-counts** the same visitors and conversions. To get unique competing visitors: pick ONE `key` (e.g. `key='utm_source'`), or `UNNEST(site_visitors_arr)` and `COUNT(DISTINCT ip)`. Verified in-sample: one 41-visitor / 7-conversion Peacock slice appeared identically across three `utm_*` rows.
- **`competing_views` is a visitor (distinct-IP) count, not an impression/view-event count** — despite the name. Same for `probattr_competing_views`.
- **`probattr_*` columns are ~empty** (>0 on <0.1% of rows). Do not report probattr metrics as populated without checking; the IP-array path is the real signal.
- **`hour` looks hourly but partitions are DAY** — you still only prune to whole days; an hour-range filter reads the full day's partition(s).
- **Geo/device sentinels** (`-4`, `-1`, negative `metro_id`) must be excluded for clean geo/device rollups.
- **`competing_view_order_value` is a raw order value (NUMERIC), not USD-normalized** — mixed-currency advertisers not reconciled here.

## Cost & partitioning notes
- **Partition = `hour` (DATETIME, DAY granularity); no clustering; no partition TTL** (`require_partition_filter=false`, so an unfiltered scan is *allowed* — and will read all 333 GB. Always add a `hour` range filter anyway).
- **The two `ARRAY<STRING>` visitor columns dominate storage** — a `SELECT *` costs ~12× a narrow-column read of the same rows. Project only the columns you need.
- Dry-run figures (labeled by column set):
  - `SELECT *`, **full table**: **333.1 GB** (= physical `numBytes`, all partitions).
  - `SELECT *`, **one day**: **0.75 GB** (arrays included).
  - `SELECT advertiser_id, competing_views` (2 narrow cols), **full table**: **19.33 GB**.
  - Same 2 narrow cols, **one day**: **0.061 GB** — one-day + narrow-cols filter prunes ~319× vs the 2-col full scan (19.33 GB → 0.061 GB), confirming `hour` is the partition.
- **Always filter `hour`**; add specific columns; if you only need counts, avoid the two `*_site_visitors_arr` arrays entirely.

## Example queries
```sql
-- Unique competing-source visitors + conversions per advertiser for one day.
-- Pin to a SINGLE key to avoid the cross-key double-count.
SELECT advertiser_id,
       SUM(competing_views)              AS competing_visitors,
       SUM(competing_view_conversions)   AS competing_conversions,
       SUM(competing_view_order_value)   AS competing_order_value
FROM `summarydata.competing_source_facts`
WHERE hour >= DATETIME('2026-07-15') AND hour < DATETIME('2026-07-16')
  AND key = 'utm_source'          -- one key only; never SUM across keys
GROUP BY advertiser_id
ORDER BY competing_conversions DESC
LIMIT 100;

-- Which competing sources touched an advertiser's converters (by utm_source value).
SELECT value AS competing_source,
       SUM(competing_view_conversions) AS conversions
FROM `summarydata.competing_source_facts`
WHERE hour >= DATETIME('2026-07-15') AND hour < DATETIME('2026-07-16')
  AND advertiser_id = 50195 AND key = 'utm_source'
GROUP BY value ORDER BY conversions DESC LIMIT 50;
```
