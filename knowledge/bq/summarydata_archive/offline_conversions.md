# summarydata_archive.offline_conversions

## Purpose
**ARCHIVE / NON-CANONICAL.** This is the **frozen historical snapshot** of offline / CRM-uploaded conversion events (in-store purchases, phone-call conversions, CRM order feeds) that were **matched back to a MNTN ad exposure** via an identity match (`guid` / `ip` / hashed PII). It is a static copy of the old **CoreDW (Postgres)** `summarydata.offline_conversions` taken at the BQ cutover, frozen at **max `time` = 2026-03-05** (created ~2026-03-05; min `time` = 2023-04-13).

**Do NOT query this table for current data.** The live, canonical table is `summarydata.offline_conversions` (a VIEW), which is a **deduped UNION ALL of THIS archive (history) + the live BQ-native `ber_stg.offline__conversions_final` pipeline** (fresh to ~today). Reach for this archive directly only when you (a) want **pre-2026-03-05 history and want to skip the live view's dedup anti-join cost**, or (b) are reconciling what the archive branch contributes to the live view. For any "what are offline conversions today" question, use the live view. See `knowledge/bq/summarydata/offline_conversions.md` (verified) for the full live-view treatment.

## Grain & keys
- **Grain:** one row per matched offline conversion event, **history only** (through 2026-03-05). `COUNT(*)` = **2,959,066** across **143 distinct advertisers**. **No column tuple is unique** — same as the live view, the archive branch is not internally deduped, so `(advertiser_id, hashed_value, time, order_id, order_amt)` can repeat; do not treat any tuple as a primary key or joins can fan out and double-count.
- **Timestamps do NOT collapse.** `time` = the conversion moment; `event_time` / `impression_time` = the attributed **exposure** (earlier than `time` by hours to weeks). `event_time = impression_time` on **100%** of rows; `time = event_time` on only **2,333** rows (0.08% — the 2023 micros sliver). Use `time` as the conversion instant and `time − impression_time` for exposure-to-conversion latency.
- **Key(s) / join columns:** `advertiser_id` (→ advertisers), `campaign_id` / `campaign_group_id` / `group_id` / `creative_id` (→ campaign hierarchy), `guid` / `ip` (identity match keys, never NULL here), `hashed_value` (hashed PII key). `upload_id` = the offline-upload batch a row arrived in. **NOTE: no `hashed_values_key` column** (41 cols here vs 42 in the live view — the view adds `hashed_values_key`, hardcoded NULL for archive rows) and **no `order_amt_usd`** (the value column is `order_amt`; see below).

## Column meanings (only the non-obvious ones)
- **`order_amt` (NUMERIC)** = conversion order value in `order_curr`. **Non-null on 100%** of rows (2,959,066/2,959,066). This is the value column — **there is no `order_amt_usd` column here** (unlike some rollups; and unlike `ui_conversions` where `order_amt_usd` is NULL and you must use `order_amt`). Sum `order_amt` for offline revenue.
- **`epoch` (INT64) = SECONDS** since Unix epoch for **99.9%** of rows (`epoch = UNIX_SECONDS(time)` on 2,956,388/2,959,066). It is **mixed-unit**: only **2,333 rows (0.08%, a 2023 sliver)** are 16-digit microseconds. **Do NOT `TIMESTAMP_MICROS(epoch)`** — for ~99.9% of rows that yields a 1970 timestamp. Use the `time` TIMESTAMP directly (or `TIMESTAMP_SECONDS(epoch)`).
- **`event_epoch`, `impression_epoch` (INT64) = MICROSECONDS** since Unix epoch — **100%** micros-scale. They hold the **exposure** instant (the attributed impression/click), **not** the conversion. `event_epoch = impression_epoch` on 100% of rows. Convert with `TIMESTAMP_MICROS`.
- **`time`** = conversion timestamp; **`event_time`/`impression_time`** = attributed exposure (earlier — see Grain & keys). **`run_time`** = the ETL/attribution run that produced the row; here it is **also frozen** (max = 2026-03-05 15:17:59) — it is NOT a freshness signal in the archive. **`hour`** (TIMESTAMP here — the live view casts it to DATETIME) = hour-bucket of the event.
- **`conversion_source_id` (INT64)** = offline integration/source. **31** = main offline-upload source (dominant, 2,958,571 rows), **37** = call-tracking (459 rows, pairs with `conversion_type` `"Call"`/`"Text"`), **32** = Showroom activity (36 rows, `conversion_type` = the raw `"activity_type = Showroom Up"` / `"activity_type = Showroom Visit"`).
- **`conversion_type` (STRING)** = human label, usually `"Offline Event"` (majority) or `"Call"`; but often an **unmapped raw numeric code as a string, e.g. `"-102"`** (~868,870 rows) — an event-type code that never got a label, not a real category. Source-32 rows carry the raw `"activity_type = …"` string (the live view keeps the same raw text).
- **`attribution_model_id` (INT64)** = attribution model applied — only **5, 7, 8** observed (7 dominant, 8 next, 5 = exactly the 5,657 rows whose `hashed_value` is NULL). Per `data_knowledge.md` the offline-attribution models are 7-8; 5 is a competing/edge variant here. **`channel_id`** = **8 CTV** (dominant) / **1 display** — offline conversions attribute across both.
- **`hashed_value` (STRING)** = hashed PII match key (email/phone). NULL on only **5,657 rows (0.19%)**. This is the offline-match key; group/join on it (there is no `hashed_values_key` in the archive).
- **`disputed` (BOOL)** = FALSE on 100% of rows. **`is_cross_device`** and **`from_verified_impression`** = TRUE on 100% of rows. **`guid`/`ip`** = never NULL. As of the 2026-07-20 scan these flags carry no discriminating signal — do not filter on them expecting a subset.
- **`partner_id_list` (STRING)** = delimited data-partner IDs involved in the match. **`ad_served_id`** = served-ad reference. **`private_marketplace_id` / `supply_vendor`** = supply-path metadata. **`upload_id`** = offline-upload batch id.

## Joins & relationships
- **`advertiser_id` → `advertisers` (id) — N:1.** Many conversions per advertiser (only **143** distinct here); joining the advertiser dim does not fan out. Filter the dim with `deleted=FALSE AND is_test=FALSE`.
- **`campaign_id` → `campaigns`; `campaign_group_id` → `campaign_groups`; `group_id` → line-item/group; `creative_id` → creatives — each N:1.** Safe from this side (many conversions per campaign object).
- **`guid` / `ip` → identity tables (`guid_ip_log_visitors`, graph) — N:N**, fan-out risk if joined loosely; these are match keys, not clean FKs. No IP-to-IP bridging in BQ.
- **Parent relationship (the important one):** this table **is the history branch** of the live `summarydata.offline_conversions` VIEW. That view = `UNION ALL` of `summarydata_archive.offline_conversions` (this table, 2.96M rows / 1.37 GB) **+** the live `ber_stg.offline__conversions_final` pipeline (~707K rows / ~325 MB), with a `NOT EXISTS` dedup anti-joining the live branch against this archive on `(advertiser_id, hashed_value, time, order_id, order_amt)`. So rows here can be re-surfaced (deduped) in the live view; do not sum archive + view (double-counts).

## Gotchas
- **FROZEN SNAPSHOT — non-canonical.** max `time` = **2026-03-05 03:08:14**, max `run_time` = 2026-03-05 15:17:59, and `numRows` has not grown. This is the CoreDW→BQ migration cutover copy; it will never advance. The prose in `data_knowledge.md` (2026-04-16, via Lilit) that "CoreDW is stale, use the BQ table" refers to the **live view**, not this archive — this archive IS the frozen CoreDW history. For anything ≥ 2026-03-05, use the live view or `ber_stg.offline__conversions_final`.
- **UNPARTITIONED, unclustered.** `timePartitioning: None`, `clustering: None` (confirmed via `bq show`). A `WHERE time >= …` filter does **NOT** prune bytes — dry-run of `SELECT time` was byte-identical (23,672,528 B) with and without a date filter. There is no partition column to lean on; scope cost by **column projection**, not date filters.
- **No unique key / not internally deduped** — same tuple can repeat within the archive (see Grain & keys). Fan-out risk on tuple joins.
- **`epoch` is mixed-unit** (seconds for 99.9%, micros for a 2,333-row 2023 sliver) — use `time`, never `TIMESTAMP_MICROS(epoch)`. Only `event_epoch`/`impression_epoch` are micros.
- **`hashed_values_key` and `order_amt_usd` do not exist here** — the live view adds `hashed_values_key` (NULL for archive rows) and there is no USD-normalized amount column; use `hashed_value` and `order_amt`.
- **Always-true / always-null flags** (`disputed`=0, `is_cross_device`/`from_verified_impression`=TRUE, `order_amt`/`guid`/`ip` never null) — treat as constants in this frozen data.

## Cost & partitioning notes
- **Plain BASE TABLE (not a view) — column projection prunes normally, unlike the live view.** Because there is no dedup anti-join, selecting one column really is cheap here:
  - `SELECT *` (41 cols) = **1,374,170,480 B (~1.37 GB)** = `numBytes`.
  - `SELECT time` (1 col), with OR without a `time` filter = **23,672,528 B (~24 MB)** — identical (proves no partition pruning; the cost driver is which columns, not the date range).
  - Contrast: the live `summarydata.offline_conversions` view has a ~419 MB floor even for one column because its `NOT EXISTS` dedup must read the archive + live key columns. Querying this archive directly avoids that floor.
- **The one rule:** project only the columns you need; do not rely on `WHERE time` to reduce bytes.

## Example queries
```sql
-- Offline conversion volume & value per advertiser from the FROZEN history (through 2026-03-05).
-- For current data query the live view `summarydata.offline_conversions` instead.
-- (time filter does NOT reduce bytes here — the table is unpartitioned — it only scopes rows.)
SELECT advertiser_id,
       COUNT(*)                              AS offline_convs,
       SUM(order_amt)                        AS offline_value,
       COUNTIF(conversion_type = 'Call')     AS call_convs
FROM `summarydata_archive.offline_conversions`
WHERE time >= '2025-01-01'
GROUP BY advertiser_id
ORDER BY offline_value DESC;
```
