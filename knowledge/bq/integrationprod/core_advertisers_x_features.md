# integrationprod.core_advertisers_x_features

## Purpose
The advertiser ↔ feature junction: which features are enabled/disabled for each advertiser (a
per-advertiser feature-flag / entitlement table). Postgres CDC dim landed via Datastream. Reach for it
to check whether an advertiser has a given feature turned on (`active = TRUE`). `feature_id` decodes via
`core_features`. Exposed as the `silver.core.advertisers_x_features` view (`SELECT * FROM` this table,
verified 2026-07-29).

## Grain & keys
- **Grain:** one row per `(advertiser_id, feature_id)` assignment. ~213,714 rows, 34,586 advertisers,
  83 distinct feature_ids present; `(advertiser_id, feature_id)` is unique (verified 2026-07-29).
- **Primary key:** `advertisers_x_features_id` (unique; sole cluster key).
- **Natural key:** `(advertiser_id, feature_id)`.
- **Foreign keys:** `advertiser_id` → `advertisers.advertiser_id`; `feature_id` →
  `core_features.feature_id`.

## Column meanings (only the non-obvious ones)
- **`feature_id`** — FK to `core_features` (90-row feature dim). Sample decode (verified 2026-07-29):
  4=LEGACY_BUDGET_MINIMUMS, 9=CAMPAIGN_GROUP_FREQUENCY_CAPS_ENABLED, 18=CONFIGURABLE_BLOCKING,
  1024=DELIVERABILITY_WIDGET, 1025=PA_M1_DATA_GENERATION_EXCLUSION, 1036=UseTargetingMfe,
  1040=CreativeDeliveryMFE, 1050=TPAExpressionV2. **Always decode against `core_features`, never assume.**
- **`active`** — the on/off toggle. **A row existing does not mean the feature is enabled** — check
  `active = TRUE`. ~137,743 of ~213,714 rows are active (~64%). Some features are present-but-disabled
  for most advertisers (e.g. feature 1039 is `active = FALSE` on all rows).
- **`create_time` / `update_time`** — CDC write/update timestamps in source Postgres.
- **`datastream_metadata`** — Datastream CDC lineage RECORD; not business data.

## Joins & relationships
- **`advertiser_id` → `advertisers.advertiser_id`** — N:1 into this table. Joining advertisers to this
  table **fans out heavily** (~6 feature rows per advertiser on average, more for some). **Always filter
  `feature_id = <id> AND active = TRUE`** (or pivot) before joining to a fact/advertiser table, or the
  join multiplies rows.
- **`feature_id` → `core_features.feature_id`** — N:1 decode; cannot fan out.
- `silver.core.advertisers_x_features` is a `SELECT *` view over this table.

## Gotchas
- **Row presence ≠ feature on.** The flag is `active`; a `(advertiser, feature)` row can be
  `active = FALSE`. Filter `active = TRUE` for "is this feature enabled."
- **Massive fan-out** — never join advertiser→this table without pinning `feature_id` (and usually
  `active`). This is the single biggest trap on this table.
- **No `deleted`/`is_test` columns** — standard bronze soft-delete filter does not apply; the disable
  mechanism is `active = FALSE`, not a delete flag.

## Cost & partitioning notes
- **Non-partitioned dim: ~214K rows / ~18 MB.** No partition, no TTL, no `require_partition_filter`.
  Clustered on the surrogate `advertisers_x_features_id` — **that clustering does not help
  advertiser/feature lookups** (leading key is the surrogate id, not advertiser_id/feature_id).
- A full scan is ~18 MB → tier-1 10 MB minimum-ish; cheap, but prefer selecting
  `advertiser_id, feature_id, active` and filtering `feature_id`.

## Example queries
```sql
-- Advertisers with a specific feature ENABLED
SELECT advertiser_id
FROM `dw-main-bronze.integrationprod.core_advertisers_x_features`
WHERE feature_id = @feature_id AND active = TRUE;

-- Enabled features for one advertiser (decoded)
SELECT f.feature_id, f.name AS feature
FROM `dw-main-bronze.integrationprod.core_advertisers_x_features` xf
JOIN `dw-main-bronze.integrationprod.core_features` f USING (feature_id)
WHERE xf.advertiser_id = @advertiser_id AND xf.active = TRUE;
```
