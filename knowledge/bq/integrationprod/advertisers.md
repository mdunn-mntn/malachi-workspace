# integrationprod.advertisers

## Purpose
The canonical MNTN advertiser (account) dimension — the master record for every advertiser account and its
per-account configuration (attribution/conversion windows, control-group %, clickpass/pixel settings, billing,
locale). This is a Postgres BASE table replicated via Datastream CDC into `dw-main-bronze.integrationprod`; it is
the **source of truth** for the advertiser label and supersedes proxies. Reach for it whenever you need the
current company name for an `advertiser_id`, or to filter a cohort to live production accounts. `company_name`
here is the reliable name label — **`fpa_advertiser_verticals.advertiser_name` is empty since 2025-12 and stale
for older rows, so always join back to this table for the name.**

## Grain & keys
- **Grain:** one row per `advertiser_id` (one advertiser account). Verified 2026-07-19: `COUNT(*) = COUNT(DISTINCT advertiser_id) = 38,440`, zero NULL `advertiser_id`. No history/SCD — this is a current-state snapshot dim, not append-only.
- **Primary key:** `advertiser_id` (INT64, unique, non-null).
- **Live-row filter (always):** `deleted = FALSE AND is_test = FALSE` → 35,558 live rows.
- **Foreign keys OUT:** `account_manager_user_id`, `user_id` → users; `pixel_id` / `pixel_id_conversion` → pixel; `client_id` → client/parent account; `advertiser_vertical_id` → vertical lookup (**100% NULL / vestigial**, see below); `billing_type_id` / `status_id` / `product_version_id` → small lookups.
- **Referenced BY (advertiser_id is the parent key):** `campaign_groups`, `campaigns`, `core_creatives`, `fpa_advertiser_verticals`, `beeswax_advertiser_mappings`, and essentially every advertiser-scoped fact/dim.

## Column meanings (only the non-obvious ones)
- **`company_name`** — the reliable current advertiser name. Empty (NULL/`''`) for **6,668 live rows (~19%)**, and every one of those was **created on/after 2025-12-23** (min create_time = 2025-12-23) — the same date as the FPA empty-name regression. These empty-name rows are essentially **dormant self-serve signups**: only **2 of the 6,668 have any campaign_group**. So `company_name` is reliably populated for advertisers that actually run campaigns; treat an empty name as "unlaunched account," not "missing data." Prefer this over `fpa_advertiser_verticals.advertiser_name` (empty since 2025-12 AND stale).
- **`deleted`** (BOOL) — soft-delete flag; filter `= FALSE` for live accounts. Rows are not physically removed.
- **`is_test`** (BOOL) — test-account flag; filter `= FALSE` for production. **Caveat:** `is_test=TRUE` accounts can carry **real production spend** (verified 2026-06-03: 8 such advertisers spent $459K of media in 30 days). For spend/billing/scoring cohorts, key off spend or campaign-liveness rather than blindly dropping `is_test=TRUE`.
- **`active`** (BOOL) — near-constant TRUE for live rows (35,550 of 35,558 true) → almost redundant with `deleted`; low discriminating signal.
- **`account_health`** (STRING) — only value present on live rows is `"Normal"` → effectively constant, no signal today.
- **`status_id`** (INT) — **~76% NULL** on live rows (values seen: 1, 3, 5). Sparsely populated; do NOT use as a status filter — use `deleted`/`is_test`/`active`.
- **`tier`** (INT) — vestigial: NULL on essentially all rows (only 5 rows = 2). Not the advertiser "tier" you want.
- **`data_tier_id`** (INT) — near-constant `1` (one row = 4). Low signal.
- **`advertiser_vertical_id`** (INT) — **100% NULL / entirely unpopulated** (verified 2026-07-19: 0 non-null across all 38,440 rows and all 35,558 live rows). Vestigial column carrying zero data; do NOT source vertical from here — use `fpa_advertiser_verticals WHERE type = 1` (and join `advertisers.company_name` for the name).
- **`*_conversion_window` / `click_conversion_window` / `view_conversion_window` / `conversion_window` / `invoice_conversion_window` / `abandon_window` / `slingshot_window`** — attribution/window config stored as **STRING interval text** (e.g. "30 days"), not integers. For historical/point-in-time VV windows use `archives_advertiser_archives`; the live column reflects only the current setting.
- **`control_group_percentage`** (NUMERIC) — % of traffic held in the advertiser's control/holdout group.
- **`create_time`** (TIMESTAMP) — genuine account creation; ranges back to 2010-11. Use this for account age.
- **`update_time`** (TIMESTAMP) — last-modified, but its **floor is artificially 2023-10-13** (the Datastream backfill onset): rows not touched since before CDC began read as ~2023-10-13. Do NOT use `update_time` to infer account age (use `create_time`). This table has **no `datastream_metadata` column**, so `update_time` is the only freshness signal.
- **`currency` / `display_currency`** (STRING) — USD-dominant (US-only advertiser base). **`country_iso_code`** (STRING) is 98.7% `US`; the long tail of tiny non-US counts is largely signup-form noise (most have no campaigns).

## Joins & relationships
- `advertiser_id` is **unique here**, so joining any child table's `advertiser_id` **into** `advertisers` is a safe **N:1 lookup** (one label/config row per advertiser — no fan-out). This is the standard way to attach a name to spend/impression/visit rows.
- Joining `advertisers` **out** to child tables fans out **1:N** — one advertiser has many:
  - **`campaign_groups`** (`advertiser_id`, 1:N) — 18,176 of 28,890 named live advertisers have ≥1 **live** campaign_group (both sides filtered `deleted=FALSE AND is_test=FALSE`, verified 2026-07-19; the count rises to 18,600 if `campaign_groups` is left unfiltered, 18,279 with `deleted=FALSE` only).
  - **`campaigns`** (`advertiser_id`, 1:N; `campaigns` also carries `advertiser_id` directly).
  - **`core_creatives`** (`advertiser_id`, 1:N).
  - **`fpa_advertiser_verticals`** (`advertiser_id`) — vertical lives here (`type=1`); take the **name from `advertisers.company_name`**, not fpa's stale/empty `advertiser_name`.
  - **`beeswax_advertiser_mappings`** (`advertiser_id`) — MNTN→Beeswax advertiser bridge for bidder-side joins.
- Never `SELECT *` and join blindly for a label — pull `advertiser_id, company_name` only (≈23x cheaper here, see Cost).

## Gotchas
- **Empty-name regression is upstream, not just FPA (drift vs prose):** the "empty advertiser name since 2025-12-23" documented for `fpa_advertiser_verticals` is present in the **base dim itself** — `advertisers.company_name` is empty for all 6,668 live post-2025-12-23 self-serve signups. So the root cause is upstream in the source Postgres, and FPA merely mirrors it. Practical effect is small because those accounts don't run campaigns (2/6,668 have a group).
- **`is_test=TRUE` ≠ no spend** — see the $459K caveat above; don't silently drop for spend/billing/scoring workflows.
- **Soft-delete + test rows inflate counts** — always `deleted=FALSE AND is_test=FALSE`. Without it, counts include internal test and deleted accounts.
- **`update_time` floor is a replication artifact** (2023-10-13 = Datastream onset) — not a real edit date; use `create_time` for age.
- **Don't trust `status_id`/`tier`/`account_health`/`data_tier_id` as signals** — status_id ~76% NULL, tier ~all NULL, account_health constant, data_tier_id constant on live rows.

## Cost & partitioning notes
- **BASE TABLE (not a view), unpartitioned, no clustering, no TTL.** Full snapshot of ~38K rows / ~19 MB backing storage. There is no partition column and none is needed — the only cost lever is **column selection**.
- **The one filter to always apply is not a partition, it's `deleted = FALSE AND is_test = FALSE`** (correctness, not cost) to get live rows.
- Labeled dry-run figures (project `dw-main-bronze`, 2026-07-19):
  - `SELECT *` (all 118 columns): **20,092,672 bytes ≈ 19.2 MB** — equals the full backing storage (`approx_logical_bytes`).
  - `SELECT advertiser_id, company_name` (2 columns): **883,408 bytes ≈ 0.86 MB** — ~23x cheaper than `SELECT *`.
- Practically free either way, but for label-join usage pull only `advertiser_id, company_name`. Query as `dw-main-bronze.integrationprod.advertisers` (the default `dw-main-silver` project will NOT find it).

## Example queries
```sql
-- Live advertiser label lookup (the common case) — cheapest column set
SELECT advertiser_id, company_name
FROM `dw-main-bronze.integrationprod.advertisers`
WHERE deleted = FALSE AND is_test = FALSE;

-- Attach current advertiser name to an advertiser-scoped fact (safe N:1, no fan-out)
-- Pull only the fact columns you need (not f.*), and keep the fact table's own partition/date filter.
SELECT f.advertiser_id, f.media_spend, a.company_name
FROM `some_partitioned_fact_table` f
LEFT JOIN `dw-main-bronze.integrationprod.advertisers` a USING (advertiser_id)
WHERE f.event_date BETWEEN '2026-07-01' AND '2026-07-19';
```
