# integrationprod.categories

## Purpose
Raw Postgres CDC mirror (Datastream) of the master **category / taxonomy** dimension for MNTN's *internal* audience data sources. Each row is a node in a hierarchical tree. Reach for it to decode a `data_source_category_id` seen in an audience expression into a human-readable name/path for one of the four internal data sources it carries: **DS13** (MNTN vertical buckets), **DS16** (per-advertiser funnel-state taxonomy tree), **DS21** (per-advertiser converters), **DS14** (global root only).

It does **not** carry 3P / LiveRamp (**DS35**) or MNTN Matched keyword (**DS19**) names — those live elsewhere (see Joins). For audience-decode workflows the team usually reads the curated sibling views `silver.fpa.categories` (→ `bronze.integrationprod.fpa_categories`, same DS13/14/16/21 set) or `dw-main-bronze.tpa.categories` (DS35/DS11/DS9/DS42); this raw table is the underlying CDC source.

## Grain & keys
- **Grain:** one row per **(data_source_id, data_source_category_id)** node. Verified: `COUNT(*) = COUNT(DISTINCT dsid:dscid) = 2,020,272`, whereas `COUNT(DISTINCT data_source_category_id) = 2,017,293` — so **dscid alone is NOT unique** (~2,979 collisions across data sources). Always key/join on the **pair**.
- **PK:** (`data_source_id`, `data_source_category_id`).
- **Self-FK:** `parent_id` → `data_source_category_id` of the parent node **within the same data_source_id** (builds the tree; ROOT has `parent_id IS NULL`).
- **Per-source row split** (2026-07-19): DS16 = 1,930,831 · DS21 = 89,254 · DS13 = 186 · DS14 = 1.

## Column meanings (only the non-obvious ones)
- **data_source_id** — the DS taxonomy this node belongs to. Live domain in THIS table is only {13, 14, 16, 21} (not DS19/DS35/DS38). See `data_sources` for the full DSxx map.
- **data_source_category_id** — the node id, unique only *within* its data_source_id (part of the composite PK). For DS16/DS21 the ids are globally sequential across advertisers (first advertiser loaded gets low ids 1–5; later advertisers get large ids, e.g. Kindred CampaignGroupID `1783281`).
- **parent_id** — self-referential FK to the parent's `data_source_category_id` (same DS). `NULL` at ROOT.
- **name / description** — human label. DS13: vertical name ("Apparel"); DS16: funnel-node label ("AdvertiserID - Eat Clean Bro", "Impressions", "Prospecting", "CampaignGroupID"); DS21: literally "Conversion".
- **path** — ` > `-delimited human ancestry, e.g. `AdvertiserID > Impressions > Prospecting`.
- **names** — JSON `{"names":[...]}` array of the ancestor *labels* (same chain as `path`).
- **path_from_root** — JSON `{"pathFromRoot":[dscid,...]}` array of ancestor **dscids** from ROOT to this node.
- **path_from_root_types** — JSON `{"pathFromRootTypes":[mntn_id_type,...]}` array of the ancestor **node-type codes**; only populated for DS16 (NULL for DS13/14/21).
- **mntn_id_type** — the **funnel node-type code** for DS16 (drives the tree shape). Verified domain: `0`=ROOT · `1`=AdvertiserID · `2`=PageViews · `3`=Conversions · `4`=Impressions · `5`=VV · `6`=Prospecting · `7`=MultiTouch · `8`=Retargeting · `9`=CampaignGroupID · `10`=CampaignID · `11`=Wins. Matches the documented DS16 tree exactly. Mostly `NULL` for DS13; `1` for DS21.
- **mntn_id** — the MNTN entity id the node *references*, whose kind is given by `mntn_id_type` (advertiser_id at AdvertiserID/DS21 nodes; campaign-group / campaign id at CampaignGroupID / CampaignID nodes). `NULL` (~513K rows) on pure funnel-state leaves (PageViews/Conversions/Impressions/VV/Wins/Prospecting/MultiTouch/Retargeting) which reference no entity.
- **advertiser_id** — the **owning advertiser** on *every* DS16 and DS21 node (funnel leaves included). This is the filter for isolating one advertiser's DS16 tree: `WHERE data_source_id=16 AND advertiser_id=<AID>`. `NULL` only for the global DS13 (186) + DS14 (1) taxonomy roots (187 nulls total).
- **partner_id** — data owner/partner id; `1` = MNTN-internal (DS13/16/21), `0` on the DS14 ROOT.
- **is_leaf_node** — TRUE = terminal/targetable node; FALSE = navigational parent.
- **navigation_only** — 0 rows TRUE here (would flag nav-only, non-targetable nodes).
- **public** — TRUE on exactly **1** row (effectively unused in this table).
- **deprecated** — **0 rows TRUE** in this table (no soft-deletes present).
- **created_date / updated_date** — DATE (business date from source Postgres, **not epoch** → `time_unit: none`). `updated_date` is **100% NULL** (never populated in this CDC mirror); `created_date` populated on all but 24,732 rows.
- **sort_order** — UI display-order hint; NULL across sampled rows.

## Joins & relationships
- **`data_sources`** (dim, 1 row per data_source_id): `categories.data_source_id → data_sources.id`. Many categories : 1 data_source. No fan-out risk (dim lookup). Gives the DSxx name (DS13=MNTN Vertical Categorization, DS16=MNTN Taxonomy Data, DS21=own converters, DS14=MNTN Global Data).
- **`advertisers`** (dim, 1:1 on advertiser_id): `categories.advertiser_id → advertisers.id` for DS16/DS21 nodes. Many nodes : 1 advertiser (a single advertiser owns its whole DS16 subtree ≈ up to dozens of nodes) → **fan-out N:1 the safe direction**; joining advertisers→categories multiplies advertiser rows by tree size, so aggregate/`DISTINCT advertiser_id` when sizing.
- **Audience expressions** (`audience_segment_campaigns.expression`, `archives_*` templates): expression `data_source_id` + `category_ids` reference `(data_source_id, data_source_category_id)` here. Decode DS13/16/21 leaves against this table (or `fpa.categories`). Fan-out: one expression cites many category_ids.
- **Sibling category tables (NOT this table):**
  - `silver.fpa.categories` → `bronze.integrationprod.fpa_categories` — curated copy, same **DS13/14/16/21** set; the usual read for DS16 funnel-tag decoding.
  - `dw-main-bronze.tpa.categories` — SQLMesh-built; carries **DS35 (LiveRamp/3P), DS11 (legacy LiveRamp, deprecated), DS9, DS42 (MNTN Select)**. DS35 names are ONLY here, not in this table.
  - `external.tpa__mntn_matched_taxonomy__v2` — **DS19** keyword names (`>=900000` id space). **DS19 has zero rows in this table**; do not try to decode DS19 names here.

## Gotchas
- **DS35 / DS19 / DS38 are absent.** This raw table holds only DS13/14/16/21. A DS35 or DS19 id will return empty — use `tpa.categories` / `tpa__mntn_matched_taxonomy__v2` respectively.
- **dscid is not globally unique** — always join on the (data_source_id, data_source_category_id) pair, never on dscid alone (2,979 cross-DS collisions).
- **`updated_date` is 100% NULL and `deprecated` is 0% TRUE** — this mirror has no working recency or soft-delete signal; do not filter on them. There is also **no `deleted` / `is_test`** column, so the dataset-wide `deleted=FALSE AND is_test=FALSE` hygiene filter does **not** apply here.
- **DS14 = ROOT only (1 row)** in this raw table. Prose that lists DS14 as 5 categories (Beeswax Bidder / Magnite / Index Exchange / IP Ends In .0 / ROOT) describes the **audience-expression / fpa-tpa** view, not this CDC source — reconciled drift, see Changelog.
- **DS16 is the bulk (~1.93M rows, 95%)** — a per-advertiser funnel tree (38,368 advertisers with an `AdvertiserID` node; ~1.13M `CampaignID` leaves). A DS16 leaf inside an audience expression is the advertiser's *own funnel state*, not interest/breadth — decode via `mntn_id_type` + `advertiser_id`, don't count it as 3P reach (TI-1037 module 12c).
- **No partition column** (BASE TABLE) — you cannot prune by date; the only cost lever is column projection (see below).

## Cost & partitioning notes
- **BASE TABLE, no partition, no clustering** — `require_partition_filter: false`; there is nothing to prune. Small dim (~2.0M rows, ~591 MiB logical). "Always filter the partition column" does not apply; instead **project only the columns you need and filter `data_source_id`** to the DS you're decoding.
- Dry-run figures (2026-07-19, whole-table scan since no partition):
  - `SELECT *` (all 20 cols): **619,636,313 B (~591 MiB)** — equals `approx_logical_bytes`.
  - `SELECT data_source_id, data_source_category_id, name`: **57,890,061 B (~55 MiB)** — ~11x cheaper.
  - `SELECT name` (1 col): **25,565,709 B (~24 MiB)** — ~24x cheaper than `SELECT *`.
- Takeaway: avoid `SELECT *`; the wide JSON/STRING columns (`names`, `path_from_root`, `path_from_root_types`, `description`) dominate. Adding a `WHERE data_source_id=<n>` cuts rows returned but not bytes scanned (no partition), so it is hygiene, not a cost prune.

## Example queries
```sql
-- DS13 vertical name for a category id
SELECT name, path
FROM `dw-main-bronze.integrationprod.categories`
WHERE data_source_id = 13 AND data_source_category_id = 101;   -- Apparel

-- One advertiser's whole DS16 funnel tree (decode a funnel leaf)
SELECT data_source_category_id, name, mntn_id_type, path
FROM `dw-main-bronze.integrationprod.categories`
WHERE data_source_id = 16 AND advertiser_id = 36532
ORDER BY data_source_category_id;
```
