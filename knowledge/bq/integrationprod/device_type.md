# integrationprod.device_type

## Purpose
Canonical device-type ENUM reference dim. Reach for it to turn an INT64 `device_type` code into a
human-readable device label. The INT64 `device_type` code lives on **exactly three** bronze.raw event
tables — `bidder_bid_events`, `bidder_auction_events`, `bidder_win_notifications` (verified via
`raw.INFORMATION_SCHEMA.COLUMNS`, 2026-07-19). Most other bronze.raw event tables do **not** carry an
INT device_type: `impression_log` and `bid_price_log` expose only a `device` STRING (no device_type
column at all), and `event_log`, `cost_impression_log`, `conversion_log` (18 more) store `device_type`
as a STRING already — none of those int-join to this dim. This is the source-of-truth ENUM: all valid
`device_type` codes are defined here (data_knowledge.md § "device_type ENUM"). Silver `logdata` tables
have already joined this dim and store a STRING device_type, so you only need this table when working
from the bidder_* INT64 codes.

## Grain & keys
- **Grain:** one row per device_type ENUM value — 8 rows total (id 1-8, dense, no gaps).
- **Key(s) / join columns:** `id` = primary key (the INTEGER code); `name` = the STRING label.
  Join `id` on the INT64 `device_type` column of a bronze.raw **bidder_* event table**
  (`bidder_bid_events` / `bidder_auction_events` / `bidder_win_notifications` — the only three raw
  tables whose `device_type` is INT64). Do NOT try to int-join `impression_log`/`bid_price_log`
  (they have no `device_type`, only `device` STRING) or `event_log`/`cost_impression_log` (their
  `device_type` is already STRING — a STRING = INT type mismatch).
- **No soft-delete / test columns:** this table has ONLY `id` + `name` — there is no `deleted`,
  `is_test`, `create_time`, `update_time`, or `datastream_metadata` column. The dataset-wide
  `deleted=FALSE AND is_test=FALSE` filter does NOT apply here (verified: schema is 2 columns).

## Column meanings (only the non-obvious ones)
- **id** — the INTEGER device-type code. This is the value stored (as INT64) on the bronze.raw
  bidder_* event tables. Full live domain (SELECT DISTINCT, 2026-07-19):

  | id | name |
  |----|------|
  | 1 | MOBILE |
  | 2 | PERSONAL_COMPUTER |
  | 3 | CONNECTED_TV |
  | 4 | PHONE |
  | 5 | TABLET |
  | 6 | CONNECTED_DEVICE |
  | 7 | SET_TOP_BOX |
  | 8 | GAMES_CONSOLE |

- **name** — the STRING label. NOTE these are the canonical UPPERCASE ENUM names — they are NOT the
  same strings silver stores. Silver `logdata` tables store friendlier values like `"CTV"` / `"Mobile"`
  (data_catalog.md), and Beeswax/bidstream tables (e.g. `bid_logs_enriched`) use a slightly different
  vocabulary (`PC` rather than `PERSONAL_COMPUTER`; no `PHONE`/`CONNECTED_DEVICE`). Do not assume the
  three vocabularies are string-identical — this table's `name` is the bronze.raw INTEGER-join label only.

## Joins & relationships
- **Partner = a bronze.raw bidder_* event table with an INT64 `device_type` column** — exactly three
  qualify: `bidder_bid_events`, `bidder_auction_events`, `bidder_win_notifications` (verified via
  `raw.INFORMATION_SCHEMA.COLUMNS` GROUP BY data_type, 2026-07-19: INT64 device_type = 3 tables,
  STRING device_type = 21 tables). Join `raw.device_type = device_type.id`. This dim is the "one" side:
  **1:N** (one ENUM row → many event rows). Joining event → dim is a label lookup with **no fan-out
  risk** (each event maps to at most one id; id is unique here). Fan-out only if you accidentally joined
  the dim to a non-unique key — not possible on `id`.
- **Coverage gap — out-of-domain sentinels; use LEFT JOIN.** bidder_* rows carry an out-of-ENUM
  `device_type = -1` (unknown/unset) that is NOT in this dim's 1-8 domain, so an INNER JOIN **silently
  drops** those rows. Verified on `raw.bidder_bid_events` for the hour 2026-07-19 12:00-13:00:
  `device_type = -1` had 291,581 rows alongside ids 2-7 (ids 1 MOBILE and 8 GAMES_CONSOLE were absent
  in that sample — expected sparsity). Prefer `LEFT JOIN ... ON b.device_type = dt.id` with a
  `COALESCE(dt.name, CAST(b.device_type AS STRING))` guard, or explicitly filter `device_type > 0`.
- **NOT a partner:** `impression_log`, `bid_price_log` (only `device` STRING, no device_type column);
  `event_log`, `cost_impression_log`, `conversion_log` and 18 other raw tables (21 raw tables total
  carry `device_type` as STRING). None int-join to this dim.
- **Silver already-joined:** `silver.logdata.*` tables store STRING `device_type` (already resolved from
  this ENUM), so you do NOT re-join this dim there — see data_catalog.md (`device_type STRING` in silver
  vs INTEGER in bronze.raw).
- **CTV vs display split:** classification splits on device_type first (data_knowledge.md), but the
  authoritative CTV delimiter at MNTN is `channels.channel_id` (8=CTV / 1=display), not this dim. This
  table only supplies the id→name label; any CTV grouping of these 8 names is applied downstream.

## Gotchas
- **INNER JOIN drops `-1` sentinel rows** — bidder_* event tables carry `device_type = -1`
  (unknown/unset), outside this dim's 1-8 domain, so an INNER JOIN discards them with no warning
  (291,581 rows in a single 1h sample of `bidder_bid_events`). LEFT JOIN + COALESCE, or filter
  `device_type > 0` deliberately.
- **Only bidder_* raw tables int-join here** — `impression_log`/`bid_price_log` have no `device_type`
  (just `device` STRING) and `event_log`/`cost_impression_log`/`conversion_log` store `device_type` as
  STRING; joining any of them to this INT dim errors or type-mismatches. See Joins section.
- **Uppercase ENUM names ≠ silver strings** — joining bronze INTEGER here yields `CONNECTED_TV`/`MOBILE`,
  not the `CTV`/`Mobile` that silver.logdata stores. Reconcile vocabularies before comparing across layers.
- **No soft-delete/test filter** — unlike most integrationprod dims, there is no `deleted`/`is_test`
  column; every one of the 8 rows is live. Applying `WHERE deleted=FALSE` would error.
- **Tiny static ENUM** — 8 rows, effectively immutable. Safe to broadcast-join / read in full.

## Cost & partitioning notes
- **No partition, no cluster, no TTL** — this is an 8-row static ENUM dim. There is no partition column
  to filter and no cost trap; scan it freely.
- **Full-scan cost (dry-run, 2026-07-19):** **166 bytes** processed for both `SELECT id, name` and

## Example queries
```sql
-- label bronze.raw bidder bids with device names (INT64 device_type → dim)
-- LEFT JOIN + COALESCE keeps the -1 (unknown) sentinel rows an INNER JOIN would silently drop.
SELECT COALESCE(dt.name, CAST(b.device_type AS STRING)) AS device, COUNT(*) AS bids
FROM `dw-main-bronze.raw.bidder_bid_events` b            -- HOUR-partitioned on _PARTITIONTIME, 90-day TTL
LEFT JOIN `dw-main-bronze.integrationprod.device_type` dt ON b.device_type = dt.id
WHERE b._PARTITIONTIME >= TIMESTAMP('2026-07-19')        -- always date-filter the EVENT table, not the dim
GROUP BY device ORDER BY bids DESC

-- just read the full ENUM (trivial cost — 166 bytes)
SELECT id, name FROM `dw-main-bronze.integrationprod.device_type` ORDER BY id
```
