# integrationprod.audience_uploads

## Purpose
Metadata catalog for every audience list an advertiser uploads for targeting or exclusion — CRM email/phone lists, direct IP lists, MNTN campaign/geo files, and offline-attribution conversion files. One row per upload batch. Holds the file-level facts (name, record count, HEM→IP match rate, content hash, lifecycle status) but **not** the resolved IPs themselves — those live in `external.ipdsc__v1` (email→IP) or `audience_upload_ips` (direct IP uploads). Reach for it to size a CRM audience (`match_rate * entry_count`), to find the `data_source_category_id` needed to pull an upload's IPs out of ipdsc, or to audit which advertisers uploaded what and when.

## Grain & keys
- **Grain:** one row per **`audience_upload_id`** (a single upload batch). Confirmed unique: 21,236 rows / 21,236 distinct ids.
- **PK:** `audience_upload_id`.
- **FKs:** `advertiser_id` → advertisers, `data_source_id` → data_sources, `user_id` → users.
- **Membership join key:** `data_source_category_id` (see Column meanings — this is NOT always the PK).

## Column meanings (only the non-obvious ones)
- **`data_source_category_id`** — the **join key to IP membership**, not a category taxonomy id. It equals `audience_upload_id` for recent uploads (the id sequences were unified), but **diverges for legacy 2023–2024 rows** which carry a separate category-id sequence (e.g. id `4300` → dsc `2218793`; id `5332` → dsc `5041`). This value = `external.ipdsc__v1.category_id` = `tpa.audience_upload_hashed_emails.audience_upload_id`. It is **not unique** (20,013 distinct of 21,236) and is **NULL for 1,167 rows**. Always join membership tables on `data_source_category_id`, never on the PK.
- **`data_source_id`** — DSxx taxonomy FK. Observed domain here: **4 = CRM** (18,911 rows, dominant), **8 = IP List** (1,466), **9 = MNTN Campaigns** (857), **10 = MNTN Geo File** (2).
- **`audience_upload_type_id`** — upload mechanism/type. No lookup table exists in integrationprod; observed behavior: **1 = standard CRM email list** (dominant), **3 = IP list/pool** (huge `entry_count` up to ~30M, `match_rate` always NULL), **5 = offline-attribution conversion file** (`entry_count` often 1, `match_rate` a default 0.5). Also seen: 2, 4, 7, 8, 9, 11, 12, 13, 23. NULL for the oldest rows.
- **`entry_count`** — count of **source records** in the file (HEMs for email uploads, IPs for IP uploads) — NOT the resolved IP count. Use `match_rate * entry_count` for an estimate, or query ipdsc for the exact IP count.
- **`match_rate`** — fraction of email/phone records resolved to IP addresses (HEM→IP), typically **0.55–0.63**. Computed by the Spark pipeline `crm_match_rate_gcp.py` (DAG `crm_match_rate_dag.py`). **NULL by design for IP-type (type 3) uploads** (no conversion step) and also NULL for many pending/failed/legacy rows — 7,779 NULL total (~37%). Null ≠ bug.
- **`deprecated`** — BOOL soft-delete / retired flag (3,240 TRUE). **This is the live-row filter for this table** — there is no `deleted` or `is_test` column here, so exclude retired uploads with `deprecated = FALSE`.
- **`status`** — upload lifecycle: `completed` / `uploading` / NULL. ~85% NULL (18,141 rows) because it is a newer column and historical rows predate it — do not treat NULL as "not completed".
- **`crm_attribution_start_date` / `crm_attribution_end_date`** — offline-attribution measurement window; rarely populated (only 53 rows have a start date).
- **`crm_attribution_matches`** — **100% NULL in this table** (0 populated). Effectively unused — do not rely on it.
- **`md5_hash`** — content hash of the uploaded file (dedup / change detection). Populated for ~82% (17,465 rows).
- **`signed_url` / `signed_url_expiration_date`** — short-lived GCS signed URL for the source file; only populated for recent uploads (3,095 rows) and expires ~7 days after `upload_start_date`.
- **`user_id`** — FK to the user who created the upload; NULL for system/legacy uploads (2,470 NULL).
- **`name` / `description`** — advertiser-supplied label. `name` often encodes a **geographic partition** ("TX test", "FL control") — advertisers routinely split a national campaign into ~10 geo-partition uploads.
- **`create_time` / `update_time` / `upload_start_date`** — native `TIMESTAMP` (Datastream CDC), **not** integer epochs. History runs from 2020-11-05 to present.

## Joins & relationships
- **`advertiser_id` → `integrationprod.advertisers.advertiser_id`** — N:1 (each upload belongs to one advertiser; 3,177 distinct advertisers here). No fan-out risk from this table's side.
- **`data_source_id` → `integrationprod.data_sources.data_source_id`** — N:1 (DSxx name lookup).
- **`user_id` → `integrationprod.users.user_id`** — N:1.
- **`data_source_category_id` → `external.ipdsc__v1.category_id`** — **1:N** (one upload → many IP rows). This is where the targetable IPs live for email uploads. Join on `data_source_category_id`, and always filter ipdsc by `dt` + `data_source_id` (unnest `data_source_category_ids.list`). Fan-out is the point here — expect millions of IP rows per large upload.
- **`data_source_category_id` → `tpa.audience_upload_hashed_emails.audience_upload_id`** — **1:N** HEMs. ⚠️ naming trap: the partner column is called `audience_upload_id` but it holds **this table's `data_source_category_id`**, not this table's PK. Dedup HEMs with `pre_hash_case = 'UPPERCASE'`.
- **`audience_upload_id` → `integrationprod.audience_upload_ips.audience_upload_id`** — 1:N, but **populated only for direct IP-type uploads; empty for email uploads** (those resolve through ipdsc instead).
- **`audience_upload_id` → `integrationprod.ui_audience_uploads.audience_upload_id`** — UI-layer mirror of the same batches (~1:1).

## Gotchas
- **No `deleted` / `is_test` columns.** The standard `deleted=FALSE AND is_test=FALSE` filter does not apply — use **`deprecated = FALSE`** to drop retired uploads.
- **`data_source_category_id` ≠ `audience_upload_id` for legacy rows.** The prose shorthand "same value" holds for recent uploads only (16,915 of 21,236 equal; 1,167 NULL; ~3,154 genuinely differ, concentrated in older type-1 rows). Always join IP/HEM membership on `data_source_category_id`.
- **`match_rate` NULL is expected**, not an error, for type-3 IP uploads (by design) and for pending/failed/legacy rows.
- **`crm_attribution_matches` is always NULL** in this table — never use it as a metric.
- **`entry_count` is source-record count, not IP count.** Multiply by `match_rate` (or query ipdsc) for IPs.
- **`status` is ~85% NULL** because it is a newer column — NULL does not mean incomplete.
- **`audience_upload_ips` is empty for email uploads** — do not expect email-upload IPs there; they are in ipdsc.
- Full history back to 2020; no TTL, no partition — the table only grows.

## Cost & partitioning notes
- **No partition column** (base TABLE, not partitioned; `bq show` → `timePartitioning: None`, `clustering: None`, `requirePartitionFilter: None`). The only cost lever is **column pruning** — always `SELECT` the few columns you need, never `SELECT *`.
- **Trivially cheap** — the whole table is ~5.6 MiB, so every query bills a fraction of a cent regardless.
- Dry-run figures (labeled by column set):
  - `SELECT *` (all 21 cols): **≈ 5,879,976 bytes ≈ 5.61 MiB** (= full backing storage; scanned every query since there is no partition).
  - `SELECT audience_upload_id, data_source_category_id, data_source_id` (3 narrow cols): **≈ 500,328 bytes ≈ 489 KiB** (~11× cheaper than `SELECT *`).

## Example queries
```sql
-- Live CRM email uploads for an advertiser, with estimated IP count
SELECT audience_upload_id, data_source_category_id, name, entry_count, match_rate,
       ROUND(match_rate * entry_count) AS est_ips, status, create_time
FROM `dw-main-bronze.integrationprod.audience_uploads`
WHERE advertiser_id = <ADV>
  AND data_source_id = 4          -- CRM
  AND audience_upload_type_id = 1 -- email list
  AND deprecated = FALSE
ORDER BY create_time DESC;

-- Resolve an upload's targetable IPs (join on data_source_category_id, NOT the PK)
SELECT DISTINCT ip
FROM `dw-main-bronze.external.ipdsc__v1` t, UNNEST(t.data_source_category_ids.list) dscid
WHERE t.data_source_id = 4
  AND t.dt = '<flight_date>'
  AND dscid.element = (SELECT data_source_category_id
                       FROM `dw-main-bronze.integrationprod.audience_uploads`
                       WHERE audience_upload_id = <UPLOAD_ID>);
```
