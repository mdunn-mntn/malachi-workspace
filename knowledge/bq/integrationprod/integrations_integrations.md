# integrationprod.integrations_integrations

## Purpose
The catalog dim of third-party integrations/connectors MNTN offers — one row per integration
*partner* (CallRail, Google Analytics, Rockerbox, Kochava, AppsFlyer, Triple Whale, HubSpot,
DoubleVerify, mParticle, Klaviyo, MNTN Audience, …). It is the UI/config source of truth for
"what integrations exist," their display metadata (name, description, logo), and whether each is
visible in the platform catalog. It does **not** record which advertiser has connected what — that
per-advertiser instance lives in `integrations_advertiser_integrations` (this table's `id` is its FK).
Reach for this when you need the human-readable name/slug behind an `integration_id`, or the mapping
from an integration to its `data_source_id` (DSxx) when the integration feeds an audience/measurement
data source.

Postgres dim mirrored into BigQuery via Datastream CDC (a true BASE TABLE, not a SQLMesh view).

## Grain & keys
- **Grain:** one row per integration partner/connector definition. 34 rows live as of 2026-07-19.
- **Primary key:** `id` (INT64, Postgres serial — **non-monotonic with gaps**: ids 16–18 absent,
  jumps 15→19 and 33→1015; do not assume dense/sequential). Clustering key.
- **Stable business key:** `key` (STRING slug, e.g. `callrail`, `google_analytics`, `mntn-audience`) —
  the programmatic identifier; prefer it over `name` for joins to app config. `key` is a SQL reserved
  word — backtick it (`` `key` ``).
- **Outbound FK:** `data_source_id` → `data_sources.data_source_id` (mostly NULL, see below).
- **Inbound FK:** `integrations_advertiser_integrations.integration_id` → this table's `id`.

## Column meanings (only the non-obvious ones)
- **`key`** — machine slug / programmatic identifier (`callrail`, `google_analytics`, `mntn-audience`,
  `mparticle`, `klaviyo`). Stable across renames of `name`; this is the safe join/lookup key. Reserved
  word → backtick.
- **`integration_type_id`** — categorizes the integration (values seen: 1–25, then 1004–1012). **Soft FK
  with no partner table in `integrationprod`** — there is no `integrations_integration_types` table, and
  `core_pixel_integration_types` is a different (pixel) domain. The type→label lookup is app-side. **Not
  1:1 with `id`** — many integrations share a type (e.g. ids 2/4/5 all type 2; ids 6/7/8/9 all type 5).
- **`visible`** — whether the integration is exposed in the UI catalog. Several are `false`
  (Google Analytics id=2, CDK Global id=4, Adjust id=9, MNTN Audience id=1017) = hidden / internal /
  beta / deprecated-in-UI. Filter `visible = TRUE` for the customer-facing list.
- **`hotel_manageable`** — whether a hotel-scoped advertiser can self-manage this integration; ties to
  `hotel_id` / `hotel_integration_id` on the child table. **Only CallRail (id=1) is `true`**; all other
  33 rows `false`. Niche flag — usually ignorable.
- **`data_source_id`** — FK to the DSxx taxonomy (`data_sources.data_source_id`), populated **only when
  the integration feeds an audience/measurement data source; NULL for most rows (27 of 34 NULL)**.
  Populated examples: AppsFlyer=61, Upwave=62, Tealium=48, mParticle=60, OursPrivacy=57, Klaviyo=55.
  **Gotcha:** MNTN Audience (id=1017) carries `data_source_id = 3986845`, a 7-digit outlier far outside
  the normal ≤~100 DSxx range — treat as a different id space / placeholder, not a real DSxx; verify
  before joining.
- **`create_time`** — business creation timestamp (TIMESTAMP, UTC).
- **`update_time`** — business update timestamp; **NULL for all 34 rows** (column is unused — do not rely
  on it for change detection; use `t_updated_ns` instead).
- **`t_created_ns` / `t_updated_ns` / `t_deleted_ns`** — Datastream/CDC row-materialization epochs in
  **UNIX NANOSECONDS** (verified: `t_created_ns / 1e9` = `create_time` to the second for most rows,
  e.g. id=1 `1748432602354000000` → 2025-05-28 11:43:22 = `create_time`). `t_deleted_ns` is the
  **soft-delete tombstone**; **all NULL currently** (no deleted rows). These are pipeline/materialization
  times, not strictly business time — they usually track `create_time` but **diverge on backfill/re-sync**
  (id=14 LiftLab: `create_time` 2025-11-19 vs `t_created_ns` 2025-12-03; ids 31/32 also diverge).
- **`datastream_metadata`** — Datastream CDC envelope. `.source_timestamp` = **MILLISECONDS** CDC-capture
  epoch (not business time; note the unit differs from the `t_*_ns` nanosecond columns). `.uuid` = CDC
  change-event id.

## Joins & relationships
- **`id` ← `integrations_advertiser_integrations.integration_id`** — the primary fan-out. **1 integration
  definition : N per-advertiser connections** (one row there per advertiser × connection). Joining this
  dim to that table multiplies rows by the number of advertiser connections; aggregate the child side or
  join dim→child only to decorate connections with `name`/`key`, never child→dim expecting 1:1.
- **`data_source_id` → `data_sources.data_source_id`** — N:1 lookup into the DSxx taxonomy, but **mostly
  NULL here**, so most integrations won't join (inner join silently drops ~27/34 rows). Left-join if you
  need the DS label. `data_sources` is itself a small dim (safe, no fan-out).
- **`integration_type_id` → (no BQ partner table)** — app-side enum; unresolved in `integrationprod`.
  Live-unverifiable against a lookup table; treat the numeric type as opaque.

## Gotchas
- **No `deleted` / `is_test` columns.** The standard `integrationprod` live-row filter
  (`deleted=FALSE AND is_test=FALSE`) does **not** apply here. Soft-delete is via **`t_deleted_ns IS NULL`**
  (currently all 34 rows are live). Use that for "active integrations."
- **`id` is sparse/non-monotonic** — gaps (16–18 missing) and a jump to the 1000s. Never assume
  contiguous ids or use `MAX(id)` as a count.
- **`update_time` is always NULL** — dead column. Use `t_updated_ns` (nanoseconds) for change tracking.
- **`data_source_id` mostly NULL** — inner-joining to `data_sources` drops most integrations; and
  id=1017 holds a non-DSxx outlier value (3986845). Left-join and validate.
- **`t_*_ns` are nanoseconds**, while `datastream_metadata.source_timestamp` is milliseconds — do not
  reuse one divisor for both.
- **`key` is a reserved word** — must be backticked in Standard SQL.

## Cost & partitioning notes
- **No partition** (BASE TABLE, 34 rows / 7,019 bytes). `require_partition_filter = false`; clustered by
  `id`. There is no partition column to filter — the whole table is a rounding error to scan.
- **Cost (dry-run, labeled by column set):** `SELECT *` over the full table = **7,019 bytes** processed
  (BQ 10 MB on-demand billing floor applies regardless). No pruning is possible or needed; select only the

## Example queries
```sql
-- Live, customer-visible integrations with their DSxx (if any)
SELECT i.id, i.`key`, i.name, i.integration_type_id, i.data_source_id
FROM `dw-main-bronze.integrationprod.integrations_integrations` AS i
WHERE i.t_deleted_ns IS NULL      -- live rows (no deleted/is_test cols here)
  AND i.visible = TRUE            -- shown in the UI catalog
ORDER BY i.id;

-- Decorate per-advertiser connections with the integration name (dim → child, 1:N)
SELECT ai.advertiser_id, ai.integration_id, i.`key`, i.name, ai.active
FROM `dw-main-bronze.integrationprod.integrations_advertiser_integrations` AS ai
JOIN `dw-main-bronze.integrationprod.integrations_integrations` AS i
  ON i.id = ai.integration_id
WHERE ai.t_deleted_ns IS NULL;
```
