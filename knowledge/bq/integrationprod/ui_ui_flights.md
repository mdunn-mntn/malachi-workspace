# integrationprod.ui_ui_flights

## Purpose
The **UI-layer flight** table: one row per flight the user created or edited in the MNTN UI for a
campaign_group — a scheduling/budget record carrying a start/end window, a budget, and a budget type.
This is the *UI representation* of a flight; the operational, bidder-facing expansion lives in
`core_flights` (one UI flight fans out to ~3 core flights, linked via `core_flights.ui_flight_id → ui_ui_flights.flight_id`).
A flight's `update_time` propagates up into `campaign_groups.update_time` via the Postgres view's
`GREATEST(ui_ui_flights.update_time, campaign_groups_raw.update_time)` formula, so this table is what makes
a "campaign was modified" check fire on a child-flight edit. Reach for it to see a campaign_group's
schedule/budget edit history, or to bridge a UI `flight_id` to the operational `core_flights` rows.

## Grain & keys
- **Grain:** one row per **`flight_id`** — unique (354,832 rows = 354,832 distinct flight_id). Primary key + cluster key.
- **`campaign_group_id`** is **1:N** from the CG side: 89,768 distinct CGs across the table → ~4 flights per CG.
  Every budget/schedule edit (start/end shift, budget change, status flip) spawns a **new** flight row rather
  than mutating the old one, so a CG accumulates a stack of flight rows over its life. `campaign_group_id` is never NULL.
- **Join columns:** `flight_id` (out to `core_flights.ui_flight_id`), `campaign_group_id` (out to `campaign_groups` / `core_flights`),
  `budget_type_id` (→ `core_budget_types`), `user_id` (→ users dim).

## Column meanings (only the non-obvious ones)
- **`flight_id`** — PK, unique per row, and the cluster key. This is the value `core_flights.ui_flight_id` points back to.
- **`campaign_group_id`** — FK → `campaign_groups.campaign_group_id`. A flight belongs to exactly one CG; a CG has many flights (edit history + sequential flighted windows).
- **`create_time` / `update_time`** — TIMESTAMP (UTC). `update_time` bumps on any edit and is the value that
  propagates into `campaign_groups.update_time` via `GREATEST(...)`. Use `update_time` (not a raw cg-level column)
  for freshness/"was modified" logic.
- **`start_time` / `end_time`** — the flight's scheduled window (UTC). **Sentinel values present:** observed
  `start_time` as low as `1969-12-31 23:00:00` (epoch-0 placeholder) and `end_time` as high as `2074-07-01`
  (far-future "no end" sentinel). Do not assume clean, real-world bounds; guard against sentinels before doing date math.
- **`budget_type_id`** — FK → `core_budget_types`: **1 = Monthly, 2 = Daily, 3 = Flighted**. Only 1 (Monthly) and 3 (Flighted) actually appear here; Daily is unused in this table.
- **`budget`** — NUMERIC(12,2), the UI-entered flight budget in dollars. **This is the static UI budget, not the operative pacing budget** — for the real current allocation use the DSO tables (`dso_campaign_group_flight_budgets`), per the campaign_groups gotchas.
- **`user_id`** — the UI user who owns/created the flight (8,180 distinct; fully non-null). FK → a users dim.
- **`status_id`** — flight lifecycle, **flight-level semantics (not `core_campaign_statuses`)**: `3` = active/kept
  (a valid schedule — past, current, or future), `8` = **superseded/deleted** (replaced by a later edit), `2` = rare
  anomaly (1 row). Matches the `core_flights` convention (3 = active/completed, 8 = superseded). Multiple status-3
  flights can coexist in one CG (48.9K CGs have exactly one, but many have several; 8.0K CGs have zero live flights).
- **`datastream_metadata.source_timestamp`** — INT64 **milliseconds** CDC-capture epoch: `TIMESTAMP_MILLIS(source_timestamp)`
  reproduces `update_time` exactly (micros interpretation lands in 1970). This is Datastream capture time, **not** business
  time — do not use it as an edit timestamp; use `update_time`. `datastream_metadata.uuid` = the Datastream row identifier.

## Joins & relationships
- **→ `core_flights`** on `core_flights.ui_flight_id = ui_ui_flights.flight_id`: **N:1** (core is the child).
  ~1.00M core rows / 339K distinct `ui_flight_id` ≈ **3 operational flights per UI flight** (1,004,824 of 1,004,826
  core rows matched a UI flight). **Fan-out risk:** joining ui→core multiplies UI-flight rows ~3x. `core_flights`
  (a.k.a. `silver.core.flights`) is the authoritative operational schedule (start/end times used for the short-flight <72h HHST check).
- **→ `campaign_groups`** on `campaign_group_id`: **N:1** from the flights side (a CG has ~4 flights). **Fan-out risk:**
  joining `campaign_groups` → this table multiplies each CG ~4x. `ui_ui_flights.update_time` is a component of the CG's computed `update_time`.
- **→ `core_budget_types`** on `budget_type_id`: N:1 reference dim (safe, no fan-out).
- **→ users dim** on `user_id`: N:1 (safe).
- **`archives_ui_flight_archives`** — versioned CDC history snapshots of this table; order by `create_time`
  (archive `version` is often non-monotonic). Use for as-of reconstruction.
- **`core_ui_flight_x_media_plan`** — junction linking a UI flight to a media plan.

## Gotchas
- **No `deleted` / `is_test` columns** — the standard integrationprod live-row filter (`deleted=FALSE AND is_test=FALSE`)
  does **not** apply here (those columns don't exist). Use `status_id` instead: exclude `status_id = 8` (superseded/deleted)
  and, for the current schedule, keep `status_id = 3` then pick by `start_time`/`end_time` window.
- **This is the UI flight, not the operational flight.** Do not confuse `ui_ui_flights` with `core_flights` — the latter
  is the bidder-facing expansion (~3x rows) and is what bidding/pacing reads. `active_flight_id` on `campaign_groups`
  points into `core_flights` and is known to be stale (TI-1037).
- **`status_id = 8` rows are edit history, not garbage** — they are superseded prior versions; the live schedule is a status-3 row.
- **Sentinel start/end dates** (`1969-12-31`, `2074-07-01`) — filter/guard before date arithmetic.
- **`budget` is static UI budget, not the pacing budget** — for the real current cap/allocation use `dso_campaign_group_flight_budgets`.
- **`update_time` is load-bearing upstream:** it feeds `campaign_groups.update_time` via `GREATEST()`, so a flight
  edit is what makes a CG look "modified."

## Cost & partitioning notes
- **No partition** (physical `timePartitioning` is null; `require_partition_filter=false`); **clustered on `flight_id`**.
  Whole table is tiny (~46.7 MB / ~352.9K rows) — full scans are cheap, so there is no partition to filter.
- **The real cost lever is column projection, not row filtering.** Dry-run, all-column set `SELECT *` on the full table
  = **46.73 MB**; two-column `SELECT flight_id, campaign_group_id` = **5.65 MB** (~8x cheaper, same rows). A
  `flight_id BETWEEN …` filter on `SELECT *` still dry-runs at **46.73 MB** — clustering does not reduce the dry-run
  upper bound, it only speeds point-lookup bytes-scanned at runtime.
- **Always:** select only the columns you need; look up by `flight_id` (the cluster key) for point access. Given the
  table's size, an unfiltered scan is acceptable when you genuinely need all rows.

## Example queries
```sql
-- Current (live) flights for a campaign_group, newest first
SELECT flight_id, start_time, end_time, budget, budget_type_id, status_id, update_time
FROM `dw-main-bronze.integrationprod.ui_ui_flights`
WHERE campaign_group_id = @cg_id
  AND status_id = 3            -- exclude superseded (8)
ORDER BY update_time DESC;

-- Bridge a UI flight to its operational core_flights rows (N:1, ~3x fan-out)
SELECT u.flight_id AS ui_flight_id, c.flight_id AS core_flight_id, c.start_time, c.end_time
FROM `dw-main-bronze.integrationprod.ui_ui_flights` u
JOIN `dw-main-bronze.integrationprod.core_flights` c
  ON c.ui_flight_id = u.flight_id
WHERE u.campaign_group_id = @cg_id;
```
