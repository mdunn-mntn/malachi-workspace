# integrationprod.public_advertisers

## Purpose
The master **advertiser account dimension** — one row per advertiser holding account config, contact/billing info, attribution windows, control-group (holdout) settings, and dozens of product/feature flags. This is the `public` Postgres-schema mirror of the same underlying `advertisers` table (Datastream CDC into `integrationprod`). Reach for it to resolve an `advertiser_id` → **authoritative current `company_name`**, timezone, currency, or account status, and to enrich any fact table keyed on `advertiser_id`. It is a **strict superset** of `integrationprod.advertisers` (see Joins), so prefer it as the most complete advertiser lookup.

## Grain & keys
- **Grain:** one row per `advertiser_id` — verified 1:1 (total 39,213 = distinct advertiser_id 39,213, 0 NULLs, re-verified live 2026-07-29).
- **Key(s) / join columns:** `advertiser_id` (PK, cluster key). Foreign refs: `account_manager_user_id`, `user_id` → users; `advertiser_vertical_id` → vertical lookup (often NULL — see Gotchas); `currency`/`display_currency`/`country_iso_code` → `core.currency_codes`; `pixel_id`/`pixel_id_conversion` → pixel config.

## Column meanings (only the non-obvious ones)
Detailed value distributions below are the dated 2026-07-20 snapshot (n=38,461); totals re-verified 2026-07-29 (n=39,213, grain still 1:1; is_test 2,918; company_name empty 6,945; exclusion_reason_id NULL 36,295 = deleted=FALSE AND is_test=FALSE live population).

- **`company_name`** — authoritative, current advertiser display name. **Can be empty** (`''`): 6,868 rows / 17.9%, concentrated in test/excluded accounts. Still the SoT name (prefer over `fpa_advertiser_verticals.advertiser_name`, which has a 79-82% empty-string regression since 2025-12).
- **`deleted`** — soft-delete flag, but **always FALSE in this mirror** (0 deleted rows). The CDC replica only carries live (non-deleted) rows, so `deleted=FALSE` is effectively a **no-op filter** here. The meaningful production filter is `is_test=FALSE`.
- **`is_test`** — internal/test account flag; 2,882 rows TRUE. **Caveat:** `is_test=TRUE` accounts can still carry real production spend (data_knowledge, 2026-06-03) — for spend/scoring/billing workflows key off spend or campaign-liveness, not this flag.
- **`exclusion_reason_id`** — **NULL for 35,579 rows, which exactly equals the `deleted=FALSE AND is_test=FALSE` live population.** Populated only for test/excluded accounts (value 1 = 2,873, 2 = 4, 3 = 5). Effectively a "live-account" sentinel: `exclusion_reason_id IS NULL` ≈ production advertiser.
- **`cs_exception_reason_id`** — INT64 (added since the 2026-07-20 crawl; live-confirmed 2026-07-29). Customer-success exception-reason FK, **sparse: 1,109 non-NULL of 39,213 (~2.8%), 5 distinct values.** Populated only on flagged accounts; NULL for the vast majority. Do not build broad logic on it.
- **`active`** — near-constant TRUE (38,382 of 38,461); only ~79 FALSE. Not a useful discriminator.
- **`tier`** — effectively **dead column**: 38,455 of 38,461 NULL (only 5 rows =2, 1 row =3). Do NOT use for advertiser tiering.
- **`account_health`** — free-text/enum, but **constant `"Normal"`** across the whole table in this snapshot — no discriminating power currently.
- **`data_tier_id`** — data-tier assignment; ~all `1` (38,459), only 2 rows `4`.
- **`product_version_id`** — product generation: `6` = current (34,819 / 90.5%), `5` = legacy (3,642). No other values.
- **`billing_type_id`** — FK to billing-type lookup: `1` dominant (37,962 / 98.7%), `2` (274), NULL (225).
- **`status_id`** — FK to advertiser-status lookup; mostly NULL (29,438 / 76.5%), then `5` (7,068), `3` (1,546), `1` (409).
- **`control_group_percentage`** — NUMERIC(2,2) fraction (0.00-0.99) of traffic held out as control; paired with `strict_control_group` / `strict_control_group_requests` / `min_control_*` config.
- **Attribution/TTL windows** — `conversion_window`, `click_conversion_window`, `view_conversion_window`, `abandon_window`, `invoice_conversion_window`, `clickpass_click_ttl`, `clickpass_view_ttl`, `clickpass_window`, `clickpass_acquisition_ttl`, `clickpass_facebook_ttl` are all native **`INTERVAL`** here (not STRING — see Gotchas). `clickpass_iframe_ttl`, `slingshot_window`, `just_registered_clickpass_ttl`, etc. are INT64 (raw second/ms counts).
- **`create_time` / `update_time`** — business timestamps (min create 2010-11-12, table live-updated). Use these for the business timeline, NOT `datastream_metadata.source_timestamp`.
- **`datastream_metadata.source_timestamp`** — INT64 **milliseconds** CDC-capture epoch (= `UNIX_MILLIS` at replication). Confirmed ~4-11 ms *after* `update_time` per row (CDC lag): e.g. src_ts 1784562524907 vs UNIX_MILLIS(update_time) 1784562524902 = +5 ms. Not business time.
- **External platform IDs** — `appnexus_segment_id`, `coremetrics_id`, `google_audience_id`, `fb_ad_account_id`, `facebook_page_id`, `api_key`, `trpx_endpoint` map to third-party/integration systems.

## Joins & relationships
- **`advertiser_id` ↔ `integrationprod.advertisers` (1:1, but public_advertisers is a strict SUPERSET).** Anti-join verified: 12 advertiser_ids in `public_advertisers` are NOT in `advertisers`; 0 the other way (public 38,461 vs advertisers 38,449). Both mirror the same Postgres table; **prefer `public_advertisers` as the more complete lookup**. They can diverge by a handful of rows due to sync timing.
- **`advertiser_id` ← fact/config tables (1:N — advertiser is the "one" side).** `campaigns.advertiser_id`, `campaign_groups.advertiser_id`, `core_creatives.advertiser_id` all fan out N:1 to this dim. Using `public_advertisers` as the **right/dimension side** of a join is a safe enrichment (no fan-out). Do NOT join it as the driving/left table to a per-campaign fact and expect one row — you get one dim row per fact row (correct, but the count is the fact's, not 38k).
- **`advertiser_id` → `fpa_advertiser_verticals` (1:N — exactly 2 rows/advertiser: type=0 parent + type=1 sub-vertical).** For an advertiser's vertical, join `WHERE type=1` there — do NOT trust `public_advertisers.advertiser_vertical_id` (frequently NULL even when a vertical exists).
- **`advertiser_id` → `beeswax_advertiser_mappings`** (MNTN→Beeswax advertiser id map).
- **`advertiser_id` → `core.v_icloud_blacklist` (1:1).** That view is driven by a LEFT JOIN against `public_advertisers`, so it emits exactly one row per advertiser here.
- **`account_manager_user_id`, `user_id` → users (N:1).** `currency`/`display_currency` → `core.currency_codes` (N:1, many-fact:1-dim).

## Gotchas
- **`deleted` is a no-op filter here** — 0 deleted rows in the mirror. The real production gate is `is_test=FALSE` (or `exclusion_reason_id IS NULL`, which selects exactly the 35,579 live rows). Still, `is_test=TRUE` can carry real spend — see the `is_test` column note.
- **Attribution windows are native `INTERVAL`, not STRING.** Older `advertisers`-table prose (data_knowledge) calls `conversion_window` a STRING — that describes a different mirror / a silver view; in `public_advertisers` these columns are true INTERVAL. Compare/cast them as INTERVAL, don't string-parse.
- **`public_advertisers` is a strict superset of `advertisers`** (12 extra advertiser_ids) — the two mirrors are near-identical but not byte-identical; don't assume a row present in one is in the other.
- **`company_name` can be empty** (~18%, concentrated in test/excluded) — filter to the live population before treating it as a guaranteed name.
- **Dead / constant columns:** `tier` (>99.98% NULL), `account_health` (constant "Normal"), `data_tier_id` (~all 1), `active` (~all TRUE) carry no signal in the current snapshot — don't build logic on them.
- **`datastream_metadata.source_timestamp` is CDC-capture time (ms), not business time** — ~4-11 ms after `update_time`. Use `create_time`/`update_time` for advertiser-lifecycle timelines.
- **No partition column** — this is a small clustered base dim; every read scans the full selected columns. Cost is governed entirely by column selection (see below).

## Cost & partitioning notes
- **Base TABLE, no time/range partition, clustered on `advertiser_id`** (confirmed via `bq show` 2026-07-29: numRows 39,213, numBytes 25,252,175, timePartitioning None). `require_partition_filter=false` — there is no partition column to filter; the only cost lever is **column selection**.
- Dry-run figures (labeled by column set; column bytes are the dated 2026-07-20 snapshot):
  - `SELECT *` (all 120 cols) → **~25,252,175 B (25.25 MB)** (= live numBytes 2026-07-29; was 24,768,976 B at the 2026-07-20 crawl).
  - `SELECT advertiser_id, company_name` (2 cols) → **883,923 B (0.88 MB)** — ~28x cheaper.
  - Point lookup `SELECT company_name WHERE advertiser_id=<id>` → **883,923 B** dry-run upper bound (same column set). Clustering on `advertiser_id` prunes at *execution*, not in the dry-run estimate, so a point lookup bills less at runtime but the estimate matches the column-only scan.
- **Always:** select only the columns you need (never `SELECT *`); add `is_test=FALSE` (and optionally `exclusion_reason_id IS NULL`) for the production advertiser population. `deleted=FALSE` is harmless but redundant here.

## Example queries
```sql
-- Authoritative current advertiser name for the production population
SELECT advertiser_id, company_name, time_zone, currency, country_iso_code
FROM `dw-main-bronze.integrationprod.public_advertisers`
WHERE is_test = FALSE          -- deleted is always FALSE here; exclusion_reason_id IS NULL is equivalent
  AND company_name != '';

-- Enrich a fact table (public_advertisers as the dimension/right side — no fan-out)
SELECT f.campaign_id, f.advertiser_id, a.company_name
FROM `dw-main-bronze.integrationprod.campaigns` f
LEFT JOIN `dw-main-bronze.integrationprod.public_advertisers` a USING (advertiser_id);
```
