# integrationprod.core_flights

## Purpose
The **operational flight dimension** — one row per flight, a financial commitment period (a `budget` over a
`start_time`→`end_time` window) for a `campaign_group`. This is the **full flight history**: every flight
ever set, not just the current one. Reach for it to pull a campaign group's flight timeline (start/end/
budget/status) — join spend on `flight_id`. Datastream-CDC replica of Postgres `core.flights`, exposed as
`silver.core.flights`.

## Grain & keys
- **Grain:** one row per `flight_id`. 1:1 — 1,008,556 rows == distinct `flight_id` (verified 2026-07-29).
- **Primary key:** `flight_id` (INT, sole cluster key).
- **Foreign keys:** `campaign_group_id` → `campaign_groups.campaign_group_id` (89,768 distinct groups — the
  group is 1:N over flights); `ui_flight_id` → `ui_ui_flights.flight_id` (341,063 distinct — the UI flight is
  the parent, and `core_flights` is its operational expansion, so ~3 core flights per UI flight); `user_id`
  → creating user; `budget_type_id` → `core_budget_types`; `status_id` (no bronze lookup table).

## Column meanings (only the non-obvious ones)
- **`start_time` / `end_time`** — the flight window (TIMESTAMP). **Contains placeholder extremes** — live
  MIN(start)=1969-12-31 and MAX(end)=2074-08-01 exist (sentinel/open-ended values). Filter/guard for
  implausible dates when computing durations.
- **`budget`** — NUMERIC(12,2) flight budget allocation for the window.
- **`budget_type_id`** — decoded via `core_budget_types`: `1` = Monthly, `2` = Daily, `3` = Flighted. Live
  distribution (2026-07-29): `1` (Monthly) = 724,663, `3` (Flighted) = 283,893; Daily (2) not observed.
- **`status_id`** — flight status code. Live distribution (2026-07-29): `3` = 724,307, `8` = 284,249 (both
  real per data_knowledge.md). **No bronze lookup table** (`core_flight_statuses` does not exist) — labels
  are not confirmed here; `3` behaves like an active/live status and `8` like ended/deleted, but do not
  assert exact labels from this table.
- **`ui_flight_id`** — the parent UI flight (`ui_ui_flights.flight_id`); one UI flight expands to several
  core flights.
- **`datastream_metadata.source_timestamp`** — INT64 **milliseconds** CDC-capture epoch, not business time.
  Use `create_time`/`update_time` for row timing, `start_time`/`end_time` for the flight window.

## Joins & relationships
- **`campaign_group_id` → `campaign_groups`** (N:1): the group is the parent; a group has many flights.
  **Pull flight timelines by `campaign_group_id` directly** — a group can deliver continuously yet be
  composed of many short back-to-back flights.
- **`ui_flight_id` → `ui_ui_flights.flight_id`** (N:1): `core_flights` is the operational expansion of the
  UI-layer flight.
- **Spend join:** `spend_log.flight_id = core_flights.flight_id` for pacing/deliverability.
- Exposed as `silver.core.flights`.

## Gotchas
- **`campaign_groups.active_flight_id` is often STALE** — do NOT use it to find the current flight (verified
  TI-1037: it can point to a 2022-era flight with budget 2.5 while the real current flight is a recent
  70k-budget one). For the operative current flight, read the latest
  `dso_campaign_group_flight_budgets.flight_id` and join THAT to `core_flights`; for a historical as-of
  window, pick the `core_flights` row whose `start_time`/`end_time` covers the date (not `active_flight_id`).
- **Flights are set MANUALLY by Prod Ops** (officially since early 2025, informally before) — **coverage may
  be partial for older campaigns**, and short flights (≤3d / <72h) auto-set HHST=0.
- **Placeholder `start_time`/`end_time`** (1969 / 2074 sentinels) — guard before computing durations.
- **`status_id` has no bronze lookup** — only `3` and `8` occur; treat labels as inferred, not verified.
- **No `deleted`/`is_test` columns** — the soft-delete dim filter does not apply.

## Cost & partitioning notes
- **Non-partitioned dim: 1,008,556 rows / ~142.9 MB.** No partition, no TTL, `require_partition_filter=false`.
  Clustered on `flight_id` — filtering/joining on `flight_id` prunes blocks; for group-level pulls, scanning
  is cheap (~143 MB whole table). Project only needed columns.

## Example queries
```sql
-- Flight timeline for a campaign group (join by campaign_group_id directly, not active_flight_id)
SELECT flight_id, start_time, end_time, budget, budget_type_id, status_id
FROM `dw-main-bronze.integrationprod.core_flights`
WHERE campaign_group_id = @cg
ORDER BY start_time;

-- Decode budget type
SELECT f.flight_id, f.budget, bt.name AS budget_type
FROM `dw-main-bronze.integrationprod.core_flights` f
LEFT JOIN `dw-main-bronze.integrationprod.core_budget_types` bt USING (budget_type_id)
WHERE f.campaign_group_id = @cg;
```
