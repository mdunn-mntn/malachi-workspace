# integrationprod.billing_billing_type_change_requests

## Purpose
Datastream CDC mirror of the Postgres `billing.billing_type_change_requests` table. Records advertiser requests to switch billing **method** between `STRIPE` (card / auto-charge) and `INVOICE` (net-terms invoicing), plus the internal approve/reject workflow processed by operators in MNTN **Command Center**. Reach for it to see which advertisers asked to change billing type, when, who actioned it, and the outcome. It is a billing/admin config table — no spend or event data.

## Grain & keys
- **Grain:** one row per billing-type change request. Current-state CDC mirror — Datastream keeps only the latest version per PK (651 rows = 651 distinct `request_id` = 651 distinct `hash`), so there are no per-request version duplicates.
- **Primary key:** `request_id` (clustered). Sparse serial — max = 1651 with only 651 rows.
- **Join columns:** `advertiser_id` -> `advertisers.advertiser_id` (N requests : 1 advertiser; 622 advertisers across 651 requests). `requested_by` / `approved_by` / `rejected_by` / `acknowledged_by` -> internal operator/user IDs.

## Column meanings (only the non-obvious ones)
- **current_billing_type / requested_billing_type** — the FROM and TO billing methods. Observed domain: `STRIPE`, `INVOICE`. They are always **opposites** (a request flips one to the other), so they are not independent dimensions. 614 requests are STRIPE->INVOICE, 37 are INVOICE->STRIPE.
- **request_status** — outcome state. Observed domain: `APPROVED` (493), `REJECTED` (82), `PENDING` (76). No other values observed.
- **rejection_reason** — intended free-text reason, but **always NULL** (0/651 non-null, including all 82 REJECTED rows). The reason is not captured here — do not rely on this column.
- **created_at / updated_at** — business timestamps from the source Postgres row (request creation / last mutation). Use `created_at` for request time.
- **approved_at / approved_by** and **rejected_at / rejected_by** — populated only on the matching terminal outcome; both NULL while `PENDING`. The `*_by` fields are internal operator user IDs (e.g. 116508 actions most requests).
- **acknowledged_at / acknowledged_by** — acknowledgement of the request; sparsely used (42/651 have `acknowledged_at`).
- **notified** — BOOL, whether a notification was sent (533/651 true).
- **webhook_approval_url / webhook_rejection_url** — Command Center deep-links to action the request; format `https://command-center.mountain.com/advertisers/{advertiser_id}?billing_type_change_request_id={request_id}&...`. Always populated.
- **hash** — opaque 5-6 char request token embedded in the webhook URLs (651/651 distinct). Not a content hash. (`hash` is a reserved word — backtick it in SQL.)
- **datastream_metadata.source_timestamp** — INT64 = **milliseconds** since Unix epoch of the CDC capture (= `UNIX_MILLIS` of the **latest** source mutation, e.g. for a rejected row it equals `rejected_at`, not `created_at`). Decode with `TIMESTAMP_MILLIS()`. `.uuid` = Datastream change UUID.

## Joins & relationships
- **advertiser_id -> `integrationprod.advertisers` (advertiser_id).** Partner grain: 1 advertiser per row here, but **N requests : 1 advertiser** overall (622 advertisers / 651 requests). Fan-out: joining `advertisers` -> this table yields multiple rows for repeat requesters; dedup to latest by `created_at`/`request_id` if you need one row per advertiser.
- **requested_by / approved_by / rejected_by / acknowledged_by -> internal user/operator dim.** 1 operator actions many requests (1:N); no fan-out from this table's side.
- No campaign, spend, or event linkage — this is an admin/billing-config table.

## Gotchas
- **`rejection_reason` is always NULL** (verified 0/651, incl. all REJECTED). The rejection reason is not stored here.
- **`request_id` is sparse / non-contiguous** — max = 1651 but only 651 rows (~1000 gaps). Postgres serial with gaps (source deletes / sequence skips); never treat `max(request_id)` as a row count.
- **No `deleted` / `is_test` columns** — the standard integrationprod `deleted=FALSE AND is_test=FALSE` filter does NOT apply here (would error). This CDC mirror already holds current-state rows only, deduped to one per `request_id`.
- **current/requested billing types are mirror opposites** — don't treat them as two independent facts.
- **`datastream_metadata.source_timestamp` tracks the latest mutation, not creation** — use `created_at` for request time.

## Cost & partitioning notes
- Tiny table: **no partition** (physical BASE TABLE, `require_partition_filter=false`), clustered by `request_id`, 651 rows / ~237 KB. `SELECT *` dry-run = **242678 bytes (0.23 MB, full-scan)** = the full physical size (matches `bq show` numBytes) — full scans are trivially cheap; no partition filter to apply.
- Clustering on `request_id` helps only point lookups by request_id. No always-apply filter is needed for cost on this table.

## Example queries
```sql
-- All change requests for one advertiser, newest first
SELECT request_id, current_billing_type, requested_billing_type, request_status,
       created_at, approved_at, rejected_at
FROM `dw-main-bronze.integrationprod.billing_billing_type_change_requests`
WHERE advertiser_id = 64465
ORDER BY created_at DESC;

-- Pending requests awaiting a Command Center decision
SELECT request_id, advertiser_id, current_billing_type, requested_billing_type, created_at
FROM `dw-main-bronze.integrationprod.billing_billing_type_change_requests`
WHERE request_status = 'PENDING'
ORDER BY created_at;
```
