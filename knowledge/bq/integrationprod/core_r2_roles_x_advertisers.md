# integrationprod.core_r2_roles_x_advertisers

## Purpose
R2 (RBAC-v2) **role×advertiser grant** junction — records which platform roles are enabled for which advertisers. ~234K rows, one per (role_id, advertiser_id) pair. Reach for it to find the advertisers a given role applies to, or the role set granted on an advertiser. Referenced by the `roles` / `ui_roles` dim doc as the heavy-fan-out role junction; join `role_id` to the roles dim for names.

## Grain & keys
- **Grain:** one row per (role, advertiser) grant. 234,705 rows = 234,705 distinct pairs (verified — no duplicate pairs).
- **Primary/natural key:** composite `(role_id, advertiser_id)`, which is also the cluster key.
- **Foreign keys / join columns:** `role_id` → `roles.roles_id` / `ui_roles.roles_id` · `advertiser_id` → `advertisers.advertiser_id` (39,237 distinct advertisers).

## Column meanings (only the non-obvious ones)
- **role_id** — FK to the role dim; cluster key #1. Observed domain = **{1, 9, 10, 11, 14, 15}** (6 roles). `11` is an **orphan** — it is absent from the `roles`/`ui_roles` dim (ids skip 11/12/13), so it will NOT resolve; LEFT JOIN and expect misses.
- **advertiser_id** — FK to `advertisers`; cluster key #2. 39,237 distinct.
- **create_time** — native TIMESTAMP (UTC) when the grant was written. **There is no `update_time` column** — grants are effectively insert-only here.
- **datastream_metadata.source_timestamp** — Datastream CDC snapshot epoch in **milliseconds** (replication time). `.uuid` = CDC event id.

## Joins & relationships
- **M:N grant bridge.** Each of the 6 role_ids is granted to ~39K advertisers (role 15→39,226; 9→39,217; 10→39,142; 14→39,135; 1→38,993; 11→38,992) — i.e. essentially every advertiser carries the full R2 role set. **Heavy fan-out (~39K rows per role_id).** Always aggregate/DISTINCT before joining into advertiser- or role-grain analyses.
- `role_id` → `roles.roles_id` (or `ui_roles.roles_id`) for the role name/scope — but `role_id = 11` won't resolve (orphan).
- `advertiser_id` → `advertisers.advertiser_id`.

## Gotchas
- **`role_id = 11` is an orphan** (not in the roles dim); ~39K rows carry it and won't join to a name.
- **Fan-out ~39K rows per role_id** — never join role→advertiser without collapsing to the grain you need first.
- **No `update_time`, no `deleted` / `is_test` columns** — the standard live-row filter does not apply; use `create_time` for the grant time and treat rows as insert-only.
- `datastream_metadata.source_timestamp` is ms and reflects CDC replication, not a business edit time.

## Cost & partitioning notes
- **BASE TABLE**, no partition, no TTL; **clustered on `(role_id, advertiser_id)`** (numRows 234,705, numBytes 16,429,350 via `bq show`). Filtering `role_id` (leading key), then `advertiser_id`, prunes blocks within the ~16 MB table.
- **No partition column to filter.** ~16 MB total — a full scan is cheap; prefer clustered filters (`WHERE role_id = …`) over `SELECT *` on the whole thing.

## Example queries
```sql
-- advertisers granted a given role, with the role name
SELECT rxa.advertiser_id, r.name AS role_name
FROM `dw-main-bronze.integrationprod.core_r2_roles_x_advertisers` rxa
LEFT JOIN `dw-main-bronze.integrationprod.roles` r   -- LEFT: role_id 11 is an orphan
  ON rxa.role_id = r.roles_id
WHERE rxa.role_id = 15;

-- role grant counts (fan-out shape)
SELECT role_id, COUNT(DISTINCT advertiser_id) n_advertisers
FROM `dw-main-bronze.integrationprod.core_r2_roles_x_advertisers`
GROUP BY role_id ORDER BY n_advertisers DESC;
```
