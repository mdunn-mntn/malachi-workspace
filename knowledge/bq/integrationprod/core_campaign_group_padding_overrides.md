# integrationprod.core_campaign_group_padding_overrides

## Purpose
Manual override table (bronze Postgres-CDC dim, replicated via Datastream): for the small set of campaign groups that need a non-default **padding multiplier**, one row records the override factor plus a free-text `notes` string pointing at the PER Jira ticket that requested it. It is an exceptions / allow-list — only 31 campaign groups of the many thousands in the system have a row. A campaign group with **no** row uses the default padding (no override). Reach for it to see which campaign groups were manually padded, by how much, and why (the PER ticket). The thin silver view `silver.core.campaign_group_padding_overrides` is a `SELECT *` over this table.

## Grain & keys
- **Grain:** one row per `campaign_group_id` that has an override. Verified 2026-07-29: `COUNT(*) = COUNT(DISTINCT campaign_group_id) = 31`, so `campaign_group_id` is unique.
- **Primary key / join column:** `campaign_group_id` (unique here; the physical table is clustered on it).
- **No surrogate id / version column** — one current row per campaign group (CDC current state, not history).

## Column meanings (only the non-obvious ones)
- **padding** — the override multiplier, stored as **text**, not a number. Distinct observed values (2026-07-29): `"5"` (10), `"1.05"` (9), `"1.01"` (8), `"1.1"` (2), `"1.10"` (1), `"1"` (1). Older rows read as small multipliers (1.01–1.10 = a 1–10% pad); a cluster of recent rows use bare `"5"`, and one is `"1"` — so the formatting/scale is **not internally consistent**. Always `CAST(padding AS FLOAT64)` and treat the exact quantity the factor multiplies (budget vs bid vs pacing target) as set by the consuming pacing/bidder service — it is not determinable from this dimension alone.
- **notes** — free text; in practice the PER Jira ticket(s) that authorized the override (observed `"PER-1918"`, `"PER-1922"`, `"PER-2399"`). Provenance, not a machine field.
- **create_time / update_time** — Postgres business TIMESTAMPs (UTC). `update_time` > `create_time` when a row was later re-padded; use `update_time` for "last changed."
- **datastream_metadata.source_timestamp** — Datastream **CDC-capture** epoch in **MILLISECONDS** (`= UNIX_MILLIS(capture_time)`; the family-wide convention, verified on the silver sibling). This is replication time, **not** business time — most rows share the one-time backfill timestamp. Prefer `create_time`/`update_time`. `datastream_metadata.uuid` = the CDC row-change id.

## Joins & relationships
- **`campaign_group_id` → `dw-main-bronze.integrationprod.campaign_groups.campaign_group_id`** — the campaign-group dim. Partner grain 1 row per campaign group → **1:1** join, **no fan-out**. This table is a **sparse subset**, so `LEFT JOIN` *from* `campaign_groups` and coalesce a missing `padding` to the default. Apply `deleted=FALSE AND is_test=FALSE` on the `campaign_groups` side (those columns live there, not here).
- **Sibling override family:** `core_campaign_padding_overrides` (campaign grain), `core_advertiser_padding_overrides` (advertiser grain) — same schema/mechanism at different grains.

## Gotchas
- **No `deleted` / `is_test` columns here.** Do not add the standard live-row filter to *this* table (it will error); apply it on the joined `campaign_groups`.
- **`padding` is a STRING with mixed formatting** (`"1.10"` vs `"1.1"`, bare `"5"`/`"1"`). Never compare/aggregate it as text; `CAST(... AS FLOAT64)`. The numeric scale/unit is not self-describing — confirm against the consuming service.
- **Not history.** One current row per campaign group; for as-of/version history use the archives family, not this table.
- **`datastream_metadata.source_timestamp` is CDC-capture time, not edit time** — most rows carry the one-time backfill timestamp. Don't use it as "when the override was set."

## Cost & partitioning notes
- **Genuine BASE TABLE** (`physical_table: self`), **no partition, no cluster-based cost, no TTL** — confirmed via `bq show` (timePartitioning None, clustered on `campaign_group_id`, 31 rows, 2,744 bytes).
- **No partition column to filter.** At 31 rows / 2.7 KB there is no cost trap; a full `SELECT *` is a rounding error and bills the 10 MB tier-1 minimum regardless. Clustering on `campaign_group_id` helps the 1:1 join point-lookup only.

## Example queries
```sql
-- Current padding overrides with their authorizing PER ticket, live campaign groups only
SELECT p.campaign_group_id, CAST(p.padding AS FLOAT64) AS padding_factor, p.notes, p.update_time
FROM `dw-main-bronze.integrationprod.core_campaign_group_padding_overrides` p
JOIN `dw-main-bronze.integrationprod.campaign_groups` g
  ON p.campaign_group_id = g.campaign_group_id
WHERE g.deleted = FALSE AND g.is_test = FALSE
ORDER BY p.update_time DESC;
```
