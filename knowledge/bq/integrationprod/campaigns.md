# integrationprod.campaigns

## Purpose
THE canonical campaign dimension — a Postgres replica (Datastream CDC) with one row per campaign. Reach for it to resolve a `campaign_id` to its advertiser, campaign group, funnel stage, objective, channel (CTV vs display), delivery status, budget, and flight window. It is the "1" side that nearly every log/fact table joins to on `campaign_id` (cost_impression_log, sum_by_campaign_by_day, bid/win logs via `line_item_alt_id`, creative groups). Use it to scope reporting (prospecting vs retargeting), filter to currently-delivering campaigns, and determine campaign stage. There is **no** `silver.core.campaigns` view — query `dw-main-bronze.integrationprod.campaigns` directly.

## Grain & keys
- **Grain:** one row per campaign. `campaign_id` is unique (548,673 rows = 548,673 distinct `campaign_id`, 0 NULL PK). After the liveness filter `deleted=FALSE AND is_test=FALSE`, 474,021 rows remain.
- **`deleted` is three-valued:** 6,327 rows have `deleted IS NULL` (all non-test), so the filter `deleted=FALSE` / `NOT deleted` silently drops those 6,327. `is_test` is never NULL. If you need every non-deleted row, use `deleted IS NOT TRUE`; to audit deletions, `deleted=TRUE` misses the NULL population.
- **Primary key:** `campaign_id`. (There is **no** `id` column — any "`id` (PK)" shorthand is wrong; the PK is `campaign_id`.)
- **Foreign keys / join columns:** `campaign_group_id` → campaign_groups (N:1), `advertiser_id` → advertisers (N:1), `objective_id` → core_objectives (N:1), `campaign_status_id` → core_campaign_statuses (N:1), `channel_id` → channels (N:1), `partner_id` → core_partners (N:1).

## Column meanings (only the non-obvious ones)
- **`funnel_level`** — **AUTHORITATIVE stage indicator.** Live-row distribution: `1`=Prospecting/S1 (88,668), `2`=Multi-Touch/S2 (150,845), `3`=MT Plus/S3 (142,050), `4`=Ego (51,922), `NULL` (40,536, ~8.5%). More reliable than `objective_id` for what stage a campaign actually is (see Gotchas for the crosstab proof).
- **`objective_id`** — campaign objective, join `core_objectives(objective_id).name`. Live-row domain (`deleted=FALSE AND is_test=FALSE`): `1`=Prospecting (168,691), `2`=Onsite (27), `3`=Prospecting (a second Prospecting objective, 5,200), `4`=Retargeting (94,083), `5`=Multi-Touch (75,171), `6`=Multi-Touch Full Funnel (73,571), `7`=Ego (57,064); `NULL` (214). **Not a clean stage key** — a single objective spans multiple `funnel_level`s. **Three different objective sets are used for three different purposes — do not swap them:**
  - **True stage** = `funnel_level` (stage-1 prospecting = `funnel_level=1`), NOT any objective set.
  - **CHAPI / client "Performance Report" reporting scope:** prospecting = `objective_id IN (1,5,6)`. Note this scope **excludes** the 5,200 live `objective_id=3` "Prospecting" campaigns and **includes** `5`/`6` Multi-Touch campaigns (which are not stage-1). It is a reporting convention, not a stage filter.
  - **Rankability universe** (elsewhere in the corpus, data_catalog §prospecting): `objective_id IN (1,3,5)` — a different set again; here `3` IS counted and `6` is not.
- **`channel_id`** — **authoritative CTV-vs-display flag**, join `channels(channel_id).name`. Live domain: `8`=Television/CTV (264,387), `1`=Multi-Touch/display (198,812), `7`=Social (10,170), `4`=Mobile Web (378), `3`=In-App (34), `10`=Onsite Offers (27), `NULL` (213). (The CTV product subtype PTV/Select/QuickFrame is `product_id` on `campaign_groups`, **not** here.)
- **`campaign_status_id`** — delivery/lifecycle status, join `core_campaign_statuses(campaign_status_id).name`. Live domain: `7`=Inactive (150,403), `1`=Ready (91,913), `8`=Deleted (70,248), `3`=Live (59,718), `4`=Pause By Advertisers (39,592), `5`=Pause By MNTN (31,386), `9`=Legacy Archived (30,568), plus `0`/`NULL` orphans. **`=3` (Live) = currently delivering.** Note status `8`="Deleted" is independent of the row-level `deleted` boolean (these 70K rows are `deleted=FALSE`).
- **`deleted` / `is_test`** — soft-delete + test-campaign flags. Filter `deleted=FALSE AND is_test=FALSE` for production rows (`deleted` is three-valued — 6,327 NULLs that this filter drops; see Grain & keys). `is_test` campaigns have structurally lower IVR (TI-504) — never compare test vs non-test performance directly.
- **`audience_type_id` / `audience_source_id`** — sparse legacy first-party-audience linkage. `audience_type_id` joins `core_audience_types(audience_type_id).name`; on live rows the only non-NULL value is `1`="First Party Audience" (177,479 rows; 296,542 NULL). `audience_source_id` is a bare int (values `1`/`2`/`3`, mostly NULL) with **no** integrationprod lookup table. Both are largely unpopulated — do not treat them as the audience→segment→DS graph (that lives in the `audience_*` tables, keyed off `campaign_group_id`, not these columns).
- **`control_percentage`** — INTEGER 0–100 campaign-config holdout %; ~99.98% are `0`. This is a per-campaign control-group config, **distinct from** the org-wide 10% `MD5('{AID}:{IP}') mod 1000` holdout applied downstream in the log data.
- **`start_time` / `end_time`** — campaign flight-window config (TIMESTAMP, UTC). Full flight *history* lives in `core_flights` (keyed by `campaign_group_id`), not here.
- **`create_time` / `update_time`** — CDC row timestamps (TIMESTAMP, UTC). This table has **no `datastream_metadata` column**, so use these as the business-time proxy.
- **`budget_floor` / `budget_ceiling`** — NUMERIC budget bounds; **`dso_manage_budget`** BOOL = DSO auto-manages budget.
- **`clickpass_click_ttl`** — click attribution TTL stored as STRING (not an interval/int).

## Joins & relationships
- **`campaign_id` (PK) ← fact/log tables:** the relationship is **N:1** (many fact/log rows per one campaign, e.g. cost_impression_log). Joining a fact table → campaigns on `campaign_id` **never fans out** because `campaign_id` is unique here (campaigns is the "1" side) — but it does not preserve the fact table's row count 1:1 either; each fact row simply picks up its one campaign's attributes. In bid/win logs the campaign is `win_logs.line_item_alt_id = campaign_id` (and `campaign_alt_id = campaign_group_id`).
- **`campaign_group_id` → campaign_groups** (N campaigns : 1 group). Joining campaigns→campaign_groups is **N:1 (safe)**; the reverse fans out. `product_id` (1=PTV / 2=Select / 3=QuickFrame) lives only on the **group** — join up to get it.
- **`advertiser_id` → advertisers** (N:1). Use `advertisers.company_name` for the advertiser name — `fpa_advertiser_verticals.advertiser_name` is unreliable/empty.
- **Lookup dims** `objective_id`→core_objectives, `campaign_status_id`→core_campaign_statuses, `channel_id`→channels, `partner_id`→core_partners — all small N:1 integrationprod dims (safe, no fan-out).
- **MNTN → Beeswax:** `campaign_id` → `beeswax_line_item_mappings.campaign_id` for the bidder line-item mapping.

## Gotchas
- **`objective_id` is unreliable for stage — `funnel_level` is authoritative.** Crosstab (live rows): `objective_id=1` (Prospecting) appears at funnel_level 1 (65,575) / 2 (51,331) / 3 (51,307) / NULL (478); `objective_id=4` (Retargeting) at funnel_level 1 (23,093) / 2 (22,352) / 3 (22,352) / NULL (26,286). So a single objective spans every stage — objective_id does not encode stage. The one exception: **CHAPI reporting scope literally filters on `objective_id` (prospecting = `IN (1,5,6)`)** — don't swap the two by context (see the objective bullet above for all three objective sets).
- **Live `core_objectives` names drift from tribal shorthand:** `5`="Multi-Touch" (not "MT-S2"), `6`="Multi-Touch Full Funnel" (not "MT-S3"); `3` is a **second** "Prospecting" objective; `2`="Onsite". Always join the lookup, don't hardcode memorized labels.
- **NULLs:** `funnel_level` NULL for ~8.5% of live rows (40,536); `objective_id` NULL for 214.
- **"Live" ≠ `deleted=FALSE`.** Paused (4/5), Inactive (7), status-Deleted (8), and Legacy Archived (9) rows are all `deleted=FALSE`. Use `campaign_status_id=3`, or confirm delivery via recent impressions. Two independent "deleted" notions exist: the row-level `deleted` boolean vs `campaign_status_id=8`.
- **No `datastream_metadata` column** on this table → no CDC `source_timestamp`; use `create_time`/`update_time`.
- **No `id` column and no `silver.core.campaigns` view** — PK is `campaign_id`; join `dw-main-bronze.integrationprod.campaigns` directly.

## Cost & partitioning notes
- **BASE TABLE (Postgres CDC replica), NOT partitioned, NOT clustered, no TTL** — confirmed via `bq show` (timePartitioning None, clustering None). ~548,673 rows / ~111 MB (`numBytes` 110,887,363) backing storage. There is no partition column to filter and no cost trap; a full aggregate scan is cheap.
- **The one filter to always apply is liveness, not partition:** `deleted=FALSE AND is_test=FALSE` (add `campaign_status_id=3` for currently-delivering).
- Measured via `--dry_run`, labeled by exact column set (2026-07-19): PK/liveness aggregate (`campaign_id`, `deleted`, `is_test`) = **1,091,019 bytes ≈ 0.001 GB**; domain resolution (`funnel_level` + 2 lookup joins on `campaign_status_id`, `channel_id`) = **13,860,936 bytes ≈ 0.014 GB** (add the `objective_id`→core_objectives join → 18,248,730 bytes ≈ 0.018 GB); funnel×objective crosstab (`funnel_level`, `objective_id`) = **9,472,475 bytes ≈ 0.009 GB**. A `SELECT *` (all 32 cols) scans the full **110,887,363 bytes ≈ 0.11 GB** logical. Cost scales with the columns touched, not row filters (no partition); all are trivially cheap.

## Example queries
```sql
-- Live prospecting CTV campaigns for an advertiser (stage via funnel_level, CTV via channel_id)
SELECT campaign_id, name, campaign_group_id, funnel_level, objective_id
FROM `dw-main-bronze.integrationprod.campaigns`
WHERE NOT deleted AND NOT is_test
  AND campaign_status_id = 3          -- currently delivering
  AND channel_id = 8                  -- CTV (8=Television, 1=display)
  AND funnel_level = 1                -- Prospecting/S1 (authoritative stage)
  AND advertiser_id = <AID>
```
