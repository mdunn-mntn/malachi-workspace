# integrationprod.creatives

## Purpose
Canonical MNTN **creative dimension** — one row per built creative (ad unit) across every advertiser: the ad tag / adcode served, its format (display vs video), the destination/asset locations, Facebook-ad copy fields, and video metadata. This is the base Postgres-CDC replica dim (`dw-main-bronze.integrationprod.creatives`). Reach for it to resolve a `creative_id` (from impression / win / spend logs and `sum_by_creative_by_day`) to its advertiser, format, size, video length, and control-creative flag. Full history from 2010-08-08 to present.

Note it is a **near-identical sibling of `integrationprod.core_creatives`** (the `core_*` replica exposed as `silver.core.creatives`, documented separately in data_catalog.md). Both carry the same business columns — including the two large blob columns `adcode` / `adserver_payload`, the `fb_*` copy fields, `static_image_location`, and `caas_video_id` (verified present in BOTH, 2026-07-19). The only schema difference is that `core_creatives` additionally carries a `datastream_metadata` CDC column (32 cols vs this table's 31); it is NOT thinner. The documented creative→advertiser join path in data_knowledge.md uses `core_creatives`.

## Grain & keys
- **Grain:** one row per **`creative_id`** — verified 1:1 (total rows 5,722,718 == COUNT(DISTINCT creative_id), 2026-07-19). No duplicates.
- **Primary key:** `creative_id` (INT64).
- **Foreign keys / join columns:** `advertiser_id` → `advertisers.advertiser_id` (0 NULL, 10,158 distinct advertisers); `creative_size_id` → `core_creative_sizes.creative_size_id` (0 NULL, width×height + `video`/`ctv` flags; bare `creative_sizes` does NOT exist in this dataset); `user_id` → creating user (~75% NULL, sparse). `creative_hash_id` is present in schema but **all-NULL / 0-populated** — do not join on it.

## Column meanings (only the non-obvious ones)
- **`media_type_id`** (INT64) — creative format code. Live distribution (2026-07-19, all rows since `deleted` is never set — see gotchas): `2` = 5,049,128 (**88%**, display/banner — `length` almost always absent), `9` = 591,088 (**video** — `length` populated ~99%, dominated by 30s (383,679) and 15s (198,601) = 98.7% of populated video; 60s exists but is rare (134 rows, 0.02%); the only type with `caas_video_id`), `0` = 41,563, `NULL` = 28,891, `8` = 10,963, then a long tail (`3`,`1`,`7`,`6`,`10`,`4`,`5`). No `media_types` lookup was resolved — `2`=display / `9`=video is empirically inferred from the `length`+`caas_video_id` correlation, not a verified enum.
- **`length`** (INT64) — video spot length in **seconds** — almost entirely 30 or 15 (60 exists but is rare, ~0.02% of video), populated only for video-type creatives; NULL/0 for display. Not a byte size.
- **`caas_video_id`** (STRING) — Creative-as-a-Service video asset id; populated only on `media_type_id=9` (6,164 rows), else NULL/empty.
- **`active`** (BOOL) — the meaningful **liveness** flag: only ~50% TRUE (2,845,139 / 5.72M). Use this, not `deleted`, to filter to serviceable creatives.
- **`approved`** (BOOL) — moderation state; ~99.96% TRUE (5,720,474). Rarely discriminating.
- **`deleted`** (BOOL) — **always FALSE** in this table (0 TRUE rows). Deletions appear to hard-drop the row via CDC rather than soft-delete, so a `deleted=FALSE` filter is currently a no-op (still safe to include for forward-compat).
- **`is_adcode`** (BOOL) — creative is served via a raw ad tag; ~99.5% TRUE. **`adcode`** (STRING) holds that tag markup and **`adserver_payload`** (STRING) the ad-server VAST/config blob — both large (see cost notes).
- **`is_control_creative`** (BOOL) — control/holdout creative; rare (2,424 rows).
- **`fb_*`** (`fb_headline`, `fb_text`, `fb_description`, `fb_cta`, `fb_social`, `fb_display_url`, `fb_click_url`, `fb_url_prefix`, `fb_url_suffix`) — Facebook/social ad copy + link fields; only relevant to social creatives.
- **`creative_location`** (STRING, ~90% populated) / **`static_image_location`** (STRING, ~9.5%) — asset URLs (rendered creative vs static fallback image).
- **`create_time` / `update_time`** — TIMESTAMP (not epoch INT); application-layer times, span 2010-08-08 → present. There is **no `datastream_metadata`** column on this table, so no CDC `source_timestamp` alternative exists — use `update_time`.
- **`user_id`** (INT64) — creating user; ~75% NULL. **`a2_version`** — only 2 distinct values (ad-builder generation flag). **`creative_hash_id`** — all NULL/0, unused.

## Joins & relationships
- **`advertiser_id` → `advertisers`** (`advertiser_id`): N:1. Every creative has exactly one advertiser (0 NULL). Safe from `creatives` (many creatives per advertiser); joining the other way fans out.
- **`creative_size_id` → `core_creative_sizes`** (`creative_size_id`): N:1. The size lookup is `core_creative_sizes` — bare `creative_sizes` does **NOT** exist in this dataset (also exposed as the VIEW `silver.core.creative_sizes`). PK `creative_size_id`; cols `width`/`height`/`description` + `video`/`web`/`mobile`/`ctv` BOOL flags. Sizes 39 (Vertical HD Video 1080×1920) and 93 (HD Video 1920×1080) are both `video=true, ctv=true` (verified 2026-07-19). Safe lookup, no fan-out.
- **`creative_id` is the parent (1) side of every log/fact table** keyed on creative: impression/win/spend logs, `all_facts` (creative dim key), and `silver.aggregates.sum_by_creative_by_day` are the N side — one creative row, many events. Joining creatives→logs is a 1:N fan-out; always aggregate the log side first.
- **Creative ↔ creative group** is a **many-to-many via the junction table** `core_creative_groups_x_creatives` (PK `group_id, creative_id`; bare `creative_groups_x_creatives` does **NOT** exist in this dataset). There is **no `creative_group_id` column on this table** — the group link is only through that junction. Go `creatives.creative_id → core_creative_groups_x_creatives.creative_id`, then `.group_id → core_creative_groups.group_id` (target PK is `group_id`, not `creative_group_id`).
- **Beeswax crid bridge (verified):** `integrationprod.beeswax_creative_mappings` maps this MNTN `creative_id` → `beeswax_creative_id` **1:1** (PK `creative_id`; 1,585,234 rows, 0 NULL `beeswax_creative_id`, verified 2026-07-19); it also carries `advertiser_id`, `campaign_id`, `height`/`width`/`duration`. Use it to get the Beeswax crid. `sync_beeswax_creative_mapping` (PK `beeswax_creative_mapping_id`) is the sync-state sibling. Separately, `win_logs.creative_alt_id` (STRING) is *believed* to equal this `creative_id` (data_knowledge.md notes it "from integrationprod.creatives? — unverified") — a secondary, still-unverified path.
- **Sibling replica:** `integrationprod.core_creatives` (exposed as `silver.core.creatives`) is a parallel `core_*` replica with the same `creative_id` PK and the **same** business columns — `adcode`/`adserver_payload`/`fb_*`/`static_image_location`/`caas_video_id` are present in BOTH, so it is **not** thinner. It is one column larger (32 vs 31: it adds `datastream_metadata`); the documented creative→advertiser join path (data_knowledge.md) uses `core_creatives`.

## Gotchas
- **`deleted` is never TRUE here** — do not rely on it to find retired creatives; use `active=FALSE` (~50% of rows are inactive). Hard-deletes remove the row entirely.
- **No `is_test` column** — the standard `deleted=FALSE AND is_test=FALSE` dim filter does **not** apply verbatim; there is no test flag on creatives. Filter liveness via `active` (and reach the advertiser's `is_test` through the `advertisers` join if you must exclude test accounts).
- **`SELECT *` is a ~19 GB trap:** two STRING blob columns dominate storage — `adserver_payload` = 12.2 GB (63% of the table) and `adcode` = 5.75 GB (30%); together 93% of a full scan. See cost notes for column-pruned figures.
- **`creative_hash_id` all-NULL** and **`caas_video_id`/`length` populated only for video** — guard for NULL rather than assuming population.
- **`media_type_id` enum is empirically inferred**, not from a verified lookup — treat `2`=display / `9`=video as strong-but-unconfirmed.

## Cost & partitioning notes
- **No partition, no cluster** (base dim table). There is no partition column to filter — the lever here is **column pruning**: never `SELECT *`; the two blob columns are the entire cost.
- Labeled dry-run figures (full-table, 2026-07-19, `dw-main-bronze`):
  - `SELECT *` → **19.29 GB** (== `approx_logical_bytes`, real backing storage)
  - `SELECT adserver_payload` → **12.20 GB** (single blob, 63%)
  - `SELECT adcode` → **5.75 GB** (single blob, 30%)
  - `SELECT creative_id, advertiser_id, name, media_type_id, creative_size_id, active, approved` (7 dim cols) → **0.259 GB**
  - `SELECT creative_id` → **0.046 GB**
  - Same-column-set comparison: pulling the 7 useful dim columns costs **~75x less** than `SELECT *`. Only select `adcode`/`adserver_payload` when you actually need the tag markup.

## Example queries
```sql
-- Resolve creative_ids to advertiser/format/size (cheap — avoids the blob columns)
SELECT creative_id, advertiser_id, name, media_type_id, creative_size_id, length, active, approved
FROM `dw-main-bronze.integrationprod.creatives`
WHERE creative_id IN (/* ids from a log/fact table */);

-- Live video creatives for an advertiser
SELECT creative_id, name, length, caas_video_id
FROM `dw-main-bronze.integrationprod.creatives`
WHERE advertiser_id = @adv AND active = TRUE AND media_type_id = 9;
```
