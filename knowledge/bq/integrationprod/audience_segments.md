# integrationprod.audience_segments

## Purpose
The core-platform (integrationprod Postgres, Datastream CDC) registry of **OPM / first-party (FPA)
retargeting SEGMENT definitions**. One row = one reusable OPM audience segment, keyed by `segment_id`
and owned by an advertiser. Every `expression` is a **text-format user-attribute predicate**
(`UserNumPageViews >= 1`, `UserLastVisitTime >= 30,day`, `UserNumConversions >= 1 AND UserNumPageViews >= 1`,
`UserPageViews contains "/cart"`, `UserCustomIdentifiers contains "ego_ads=1"`) that matches site
visitors/converters by MNTN pixel attributes. This is the substrate for retargeting and ego audiences.

Reach for it when you need: the canonical OPM/type-1 retargeting segment text, `segment_id → advertiser`
ownership, or the `segment_id` join key for audience sizing.

**Do NOT** reach for it for prospecting / TPA targeting or DS13/DS19/DS46 (Mountain Match / Fangorn)
analysis — see the disambiguation below; that lives in a *different* object.

## Grain & keys
- **Grain:** one row per `segment_id`. Verified: 112,836 rows = 112,836 distinct `segment_id`.
- **Primary key:** `segment_id`.
- **`advertiser_id` is 1:N** — 14,322 advertisers own the 112,836 segments (~7.9 segments/advertiser). Never NULL.
- **All rows are `expression_type_id = 1` (OPM)** — 112,836 / 112,836. Zero type-2/type-3 rows live here.

## Column meanings (only the non-obvious ones)
- **`segment_id`** — PK, the OPM segment identity. Referenced by `audience_audience_segments.segment_id`
  (the audience↔segment bridge — partial: only 20,871 of 112,836 are currently bridged) and by
  `aggregates.audience_hll_by_day` for audience sizing.
- **`advertiser_id`** — owning advertiser (`integrationprod.advertisers.advertiser_id`). Never NULL.
- **`expression`** — **TEXT-format OPM predicate, NOT JSON.** Grammar: `User*` pixel-attributes vs
  thresholds, with `day`/`min` unit suffixes, joined by `AND`/`OR`/parens — e.g. `UserNumPageViews >= 5`,
  `UserLastVisitTime >= 30,day`, `UserCartQuantity >= 1 OR UserPageViews contains "cart"`,
  `UserCustomIdentifiers contains "ego_ads=1"` (ego campaigns). Only ~0.07% (75 rows) look JSON-like —
  a TPA-shaped `{"interest":{...},"geo":{...}}` tail, 74 of which carry `data_source_id` leaves (only
  DS2=1P / DS4=CRM observed; NO DS13/DS19/DS46), yet all still stored as `expression_type_id=1`. Treat
  the column as text; do not JSON-parse. This is the type-1 source form the bidder wraps into a
  TPA/type-2 expression at evaluation time (see data_knowledge.md "audience.audiences vs audience_segments"
  → OPM↔TPA wrapping).
- **`expression_type_id`** — always `1` (OPM) in this table. Enum (`audience.expression_types`):
  1=opm, 2=tpa, 3=sga. Type-2 (TPA prospecting JSON) and type-3 do NOT appear here.
- **`create_time`** — native TIMESTAMP (UTC), business creation time. Reliable; spans 2024-07-09 → present
  (actively written — max create_time = today).
- **`update_time`** — native TIMESTAMP (UTC), last modification. **NULL for 68% of rows (77,184)** that
  were never updated post-create; the non-null values **span 2024-07-16 → 2025-04-21 and never advance
  past that 2025-04-21 backfill ceiling** (MAX(update_time) = 2025-04-21 even for rows created in 2026).
  **Not reliable for recency — use `create_time`.** Never < `create_time`.
- **`datastream_metadata.source_timestamp`** — INT64 CDC-capture epoch in **MILLISECONDS** (per-capture,
  **NOT constant across rows**: 5,850 distinct values; one value `1768324406832` = `TIMESTAMP_MILLIS(...)`
  → 2026-01-13 dominates ~94% of rows — the Datastream initial backfill — while newer captures advance to
  the present). This is the Datastream pipeline capture time, **NOT business time** — never use it for
  business dates.
- **`datastream_metadata.uuid`** — Datastream row-version UUID.

## Joins & relationships
- **`advertisers` via `advertiser_id`** — partner grain 1 row/advertiser (`advertisers.advertiser_id` PK).
  This table is **N:1 → advertisers** (no fan-out joining up). Apply the live-row filter
  `deleted=FALSE AND is_test=FALSE` **on `advertisers`** (those columns do not exist on this table).
- **`audience_audience_segments` (audience↔segment / campaign bridge) via `segment_id`** — partner grain
  445,983 rows / 351,372 distinct `segment_id` (PK `audience_segment_id`). Join is **1:N (one OPM
  definition → many bridge attachments)** — **fan-out risk: de-dup or aggregate.** Only **20,871 of this
  table's 112,836** `segment_id`s appear in the bridge (~18.5%); the rest are unattached/historical OPM
  defs. The bridge's `segment_id` space (351K) is far larger and mostly references non-OPM segments
  defined elsewhere.
- **`aggregates.audience_hll_by_day` via `segment_id`** — audience-size HLL sketches keyed by `segment_id`
  (data_catalog §"Audience size"); that table's grain is `segment_id × day`.

### ⚠️ Disambiguation — this is NOT the silver `audience.audience_segments` view
The silver VIEW `dw-main-silver.audience.audience_segments` (the bidder-facing object all the tribal
knowledge is about — `campaign_id`, `is_targeted`, `expression_type_id=2 AND is_targeted=TRUE`, the 10%
holdout clause, DS13/DS19/DS46 MM & Fangorn overlay) is a **DIFFERENT table**. Its column set
(`audience_segment_id, audience_id, campaign_id, segment_id, expression, expression_type_id, is_targeted,
update_time, create_time, datastream_metadata`) matches bronze **`integrationprod.audience_audience_segments`**
exactly — that bridge, not this table, is what the silver view resolves to. This bronze
`audience_segments` table has no `campaign_id`, no `is_targeted`, and no TPA/DS-id JSON.

## Gotchas
- **Naming collision (biggest trap):** `integrationprod.audience_segments` (this table, OPM defs by
  `segment_id`) vs the silver `audience.audience_segments` view (campaign-level TPA/MM, = bronze
  `audience_audience_segments`). See disambiguation above.
- **100% `expression_type_id = 1` (OPM):** essentially all rows are OPM user-attribute text. A tiny
  74-row (0.066%) tail carries TPA-shaped JSON with `data_source_id` leaves (only DS2=1P / DS4=CRM
  observed) — still stored as type-1. **No DS13/DS19/DS46 leaf appears anywhere** (regex counts = 0), so
  this table is still useless for MM/Fangorn analysis.
- **`update_time` unreliable:** 68% NULL; non-null values span 2024-07-16 → a 2025-04-21 backfill ceiling
  (never newer, even for 2026-created rows) — use `create_time` for recency.
- **No `deleted` / `is_test` columns.** The standard integrationprod live-row filter does NOT apply — do
  not add `deleted=FALSE AND is_test=FALSE` (the query will error); every row is present as-is. Ownership
  test filtering (if needed) is done on the joined `advertisers` row.
- **`datastream_metadata.source_timestamp` = ms CDC capture, not business time.**
- **`expression` is TEXT, not JSON** — parse the `User*` grammar, don't JSON-decode.

## Cost & partitioning notes
- **No partition** (small dim BASE TABLE, `physical_table: self`). No date filter is possible or needed —
  every query scans the whole table (~22.8 MB), which is trivially cheap.
- The one discipline: **avoid `SELECT *` / avoid pulling the wide `expression` column** unless you need
  it — it dominates storage. Labeled dry-run figures (2026-07-19):
  - `SELECT *` (all 7 cols, incl. `expression`): **22,809,821 bytes (~0.0218 GiB)** — equals full logical size.
  - `SELECT segment_id` (one narrow INT): **902,688 bytes (~0.86 MB)** — ~25× cheaper.
- Clustered on `segment_id` → point lookups / `segment_id`-range filters are efficient.

## Example queries
```sql
-- OPM/type-1 retargeting segment definitions for one advertiser
SELECT segment_id, expression, create_time
FROM `dw-main-bronze.integrationprod.audience_segments`
WHERE advertiser_id = 34991
ORDER BY create_time DESC;

-- Segment ownership + count per advertiser (narrow, cheap)
SELECT advertiser_id, COUNT(*) AS n_segments
FROM `dw-main-bronze.integrationprod.audience_segments`
GROUP BY advertiser_id
ORDER BY n_segments DESC;
```
