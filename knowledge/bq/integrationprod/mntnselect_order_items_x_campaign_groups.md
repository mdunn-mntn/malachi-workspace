# integrationprod.mntnselect_order_items_x_campaign_groups

## Purpose
Junction (bridge) table linking an MNTN Select **order item** to the **campaign_group(s)** that fulfill it. A single Select order item (a purchased offering line on a Select order) is delivered by one or more campaign_groups; this table records that membership. Reach for it to cross the boundary between the Select order/billing side (`mntnselect_order_items`) and the delivery/campaign side (`campaign_groups`). Every campaign_group referenced here is `product_id = 2` (MNTN Select) — verified: all 516 live links resolve to product_id=2.

## Grain & keys
- **Grain:** one row per `(order_item_id, campaign_group_id)` association. The pair is unique — 590 rows = 590 distinct pairs (verified).
- **Key(s) / join columns:** composite `(order_item_id, campaign_group_id)` is the de-facto PK and the clustering key.
  - `order_item_id` → FK to `mntnselect_order_items.order_item_id`.
  - `campaign_group_id` → FK to `campaign_groups.campaign_group_id`.
- **Live-row filter:** no `deleted` / `is_test` columns — soft-deletes are recorded via `delete_time`. Filter `delete_time IS NULL` for the live mapping (74 of 590 rows soft-deleted → 516 live).

## Column meanings (only the non-obvious ones)
- **order_item_id** — FK to `mntnselect_order_items.order_item_id` (the Select order line). NOT unique within this table: one order item links to up to 16 campaign_groups (mean ~1.7 live).
- **campaign_group_id** — FK to `campaign_groups.campaign_group_id`. Nearly unique here: a campaign_group links to at most 3 order items (mostly 1).
- **create_time / update_time / delete_time** — TIMESTAMP (UTC) of the association row's Postgres lifecycle. `delete_time IS NOT NULL` = the link was soft-removed. Earliest `create_time` is 2025-07-31 — the MNTN Select product launch epoch (matches the `campaign_groups.product_id` Select go-live date).
- **datastream_metadata.source_timestamp** — INT64 **milliseconds** CDC-capture epoch (Datastream). Verified ≈ `UNIX_MILLIS(update_time)` (e.g. 1784223688891 vs update 1784223688850, ~41 ms apart). This is pipeline capture time, **not** business time.
- **datastream_metadata.uuid** — Datastream CDC change-event id, not a business key.

## Joins & relationships
- **→ `mntnselect_order_items`** on `order_item_id = mntnselect_order_items.order_item_id`. Partner PK = `order_item_id`; junction→order_items is **1:1** (all 516 live links matched exactly one order item — safe, no fan-out). Reverse (order_items→junction) fans out up to **16:1**.
- **→ `campaign_groups`** on `campaign_group_id = campaign_groups.campaign_group_id`. Partner PK = `campaign_group_id`; junction→campaign_groups is **1:1** (all 516 matched; all `product_id = 2` = MNTN Select — safe). Reverse (campaign_groups→junction) fans out up to **3:1**.
- **Overall many-to-many, order-item-dominant.** Full path from a Select order to delivery campaigns: `mntnselect_orders → mntnselect_order_items → THIS → campaign_groups`.

## Gotchas
- **Soft delete via delete_time, not flags.** This table has NO `deleted`/`is_test` columns (unlike `campaign_groups`). Always add `WHERE delete_time IS NULL` for the current mapping; 74/590 rows are stale links.
- **Fan-out both directions.** Joining through this junction multiplies rows (one order_item → up to 16 CGs; one CG → up to 3 order_items). Dedup or aggregate before summing order-item impressions/spend or CG delivery, or you will double count.
- **datastream_metadata.source_timestamp is CDC capture ms, not an event clock** — don't use it as business time.
- **Tiny slow-growing CDC mirror** (590 rows, ~46 KB). One row appears per new Select order-item↔CG link; no bulk churn.

## Cost & partitioning notes
- **Unpartitioned base TABLE** (confirmed `bq show`: `timePartitioning: None`, `type: TABLE`). No date filter is possible or needed; `require_partition_filter = false`.
- **SELECT * dry-run = 46,612 bytes** (~46 KB — the entire table; matches physical `numBytes`). Cost is negligible at any column set.
- Clustered `[order_item_id, campaign_group_id]` — join/filter on those keys for cluster pruning, though at this size pruning saves nothing meaningful.

## Example queries
```sql
-- Live Select order-item → campaign_group mapping, enriched with both sides
SELECT j.order_item_id, j.campaign_group_id,
       oi.advertiser_id, oi.offering_version_id, oi.impressions,
       cg.name AS campaign_group_name, cg.product_id
FROM `dw-main-bronze.integrationprod.mntnselect_order_items_x_campaign_groups` j
JOIN `dw-main-bronze.integrationprod.mntnselect_order_items` oi
  ON j.order_item_id = oi.order_item_id
JOIN `dw-main-bronze.integrationprod.campaign_groups` cg
  ON j.campaign_group_id = cg.campaign_group_id
WHERE j.delete_time IS NULL
```
