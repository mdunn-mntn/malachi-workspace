# integrationprod.core_campaign_x_audiences

## Purpose
Junction / bridge table (bronze Postgres-CDC replica) mapping a **campaign** to the **audience(s)** it targets. Reach for it to answer "which audience(s) is this campaign attached to?" or the reverse. The thin silver view `silver.core.campaign_x_audiences` is a `SELECT *` over this table. This is the campaign-grain analog of `core_campaign_group_x_audiences` (campaign-group grain).

**Legacy / frozen — read before using.** Business writes stopped: newest `create_time` is 2023-12-15 (per the silver-sibling analysis, the same freeze as `core.audiences`). This is the old core-schema audience-attachment model; the **live** per-campaign targeting mechanism is the `audience_audience_segments` expression. Treat this table as a historical record for campaigns created on or before Dec 2023 — do not use it for current targeting.

## Grain & keys
- **Grain:** one row per `campaign_x_audience_id` (surrogate PK). Verified 2026-07-29: 76,498 rows = 76,498 distinct PKs.
- **Natural key:** `(campaign_id, audience_id)` — a campaign attaches an audience at most once.
- **Foreign keys:** `campaign_id` → `campaigns.campaign_id`; `audience_id` → `audience_audiences` / `core.audiences`; `segment_id` → core-era audience segment (nullable).

## Column meanings (only the non-obvious ones)
- **campaign_x_audience_id** — surrogate PK; also the cluster key. Unique per row.
- **campaign_id** — FK → `campaigns.campaign_id`. 76,490 distinct across 76,498 rows (2026-07-29) → a handful (8) of campaigns carry more than one audience row.
- **audience_id** — FK → `audience_audiences.audience_id` (silver `core.audiences`); reused across many campaigns.
- **segment_id** — core-era audience-segment reference, nullable (present only when the attachment carried a specific segment). Treat as a historical core-schema id, not a live `audience_segments` targeting id.
- **user_id** — column present but **unused in this replica** (NULL throughout on the silver sibling); do not rely on it for who-created attribution.
- **create_time** — business creation TIMESTAMP of the attachment (there is **no `update_time`** on this table). Frozen after 2023-12-15. Use this for business time.
- **datastream_metadata.source_timestamp** — CDC-capture epoch in **MILLISECONDS** (family-wide convention). Datastream snapshot/replication time, **not** business time — can be years after `create_time`. Prefer `create_time`. `.uuid` = the CDC row id.

## Joins & relationships
- **`campaign_id` → `dw-main-bronze.integrationprod.campaigns.campaign_id`** (PK is `campaign_id`, **not** `id`; partner grain 1 row per campaign, ~548.7K rows). Junction→campaigns is **N:1, no fan-out** (safe). Reverse fans out only slightly (8 campaigns have >1 audience row); most campaigns have 0 rows here since the table is frozen.
- **`audience_id` → `audience_audiences` (silver `core.audiences`)** (partner grain 1 row per audience; also legacy/frozen). Junction→audiences is **N:1, no fan-out**. Because many campaigns share an audience, audiences→junction is 1:N (fan-out).
- **`segment_id` → segment dimension** — the core-era segment physical is not co-located in this dataset region; treat as live-unverifiable. The live targeting-expression tables (`audience_segments` / `audience_audience_segments`) are a different lineage, not the parent of this `segment_id`.
- **Sibling:** `core_campaign_group_x_audiences` — the campaign-group-level analog.

## Gotchas
- **Frozen since 2023-12-15** — no rows for any campaign created after that. Do not use for current targeting; use the live `audience_audience_segments` expression instead.
- **`user_id` unusable; `segment_id` frequently NULL** — use a LEFT join, not INNER, if you need every attachment.
- **No `deleted` / `is_test` and no `update_time`** — cannot filter test / soft-deleted rows or detect edits here; apply hygiene on the joined `campaigns`/`audiences`.
- **`datastream_metadata.source_timestamp` is CDC time (ms), not business time** — use `create_time`.
- **`campaign_id` PK is `campaign_id` not `id`** on the `campaigns` partner — a common wrong-key join.

## Cost & partitioning notes
- **Genuine BASE TABLE**, unpartitioned, clustered on `campaign_x_audience_id`, no TTL — `bq show`: 76,498 rows / 6,486,220 bytes (~6.19 MiB). No partition column to filter; `require_partition_filter=false`.
- The one lever is **project only the columns you need** (avoid `SELECT *`, which drags in `datastream_metadata`). Clustering on the PK prunes point-lookups by `campaign_x_audience_id` only; filtering by `campaign_id` still scans the full (small) table. Cost is negligible at this size regardless.
