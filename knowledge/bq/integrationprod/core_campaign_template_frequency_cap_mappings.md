# integrationprod.core_campaign_template_frequency_cap_mappings

## Purpose
Small config dimension (bronze Postgres-CDC via Datastream) storing the frequency-cap definition for each **campaign template**, broken out by the three cap-optimization modes (AUTOMATED / AGGRESSIVE / MANUAL). A campaign inherits its template's cap config; this table is where you look up "for template X in mode Y, how many impressions are allowed per how many seconds." Reach for it to explain or reconstruct the frequency-capping applied to a campaign's delivery. The thin silver view `silver.core.campaign_template_frequency_cap_mappings` is a `SELECT *` over this table.

## Grain & keys
- **Grain:** one row per `(campaign_template_id, frequency_cap_optimized)` — each template has exactly one row per optimization mode. Verified 2026-07-29: 21 distinct templates × 3 modes = 63 rows, 0 duplicate (template_id, mode) pairs.
- **Composite primary key:** `(campaign_template_id, frequency_cap_optimized)` (also the physical clustering key, in that source order).
- **Foreign key:** `campaign_template_id` → the campaign-template entity (consumers reach it via `campaigns.campaign_template_id`; there is no dedicated `campaign_templates` dim CDC'd into `integrationprod`).

## Column meanings (only the non-obvious ones)
- **frequency_cap_optimized** — the cap-optimization mode; enum domain (live `SELECT DISTINCT`, 2026-07-29, 21 rows each): `AUTOMATED`, `AGGRESSIVE`, `MANUAL`. Part of the composite key; a template has one config row per mode.
- **primary_impressions / primary_duration** — the primary (usually short-window) cap: allow at most `primary_impressions` impressions per `primary_duration` **seconds**. **Populated only for AUTOMATED and MANUAL (6 of 21 each); NEVER for AGGRESSIVE (0/21)**. NULL primary = no primary-tier cap, only the secondary cap applies.
- **secondary_impressions / secondary_duration** — the secondary (usually long-window) cap, same units: `secondary_impressions` per `secondary_duration` **seconds** (observed 43200=12h, 86400=1d, 259200=3d, 1209600=14d, 1296000=15d). Populated on 19/21 rows per mode. A template can thus enforce a two-tier cap.
- **create_time / update_time** — business TIMESTAMPs (UTC). Rows were seeded in batches when each mode was introduced (per the silver-sibling analysis), so `create_time` clusters by mode; `update_time` reflects the last edit of that specific template-mode config.
- **datastream_metadata.source_timestamp** — Datastream **CDC-capture** epoch in **MILLISECONDS**; identical across all rows = a single snapshot/backfill load, NOT per-row business time. Use `create_time`/`update_time` for change tracking. `.uuid` = CDC bookkeeping id.

## Joins & relationships
- **`campaigns.campaign_template_id` → this.`campaign_template_id`** — the consumer path. `campaigns` is one row per campaign (many campaigns share a template). **Fan-out warning:** joining on `campaign_template_id` alone multiplies each campaign by **3** (AGGRESSIVE/AUTOMATED/MANUAL). Consumers must additionally filter `frequency_cap_optimized` to the intended mode. `campaigns` carries `frequency_cap_type_id` (INT) but **no** `frequency_cap_optimized` STRING column, so the mode selection must come from business logic, not a direct equi-join.
- **No `campaign_templates` dimension exists in `integrationprod`** — the parent template entity is not CDC'd under that name; `campaign_template_id` resolves only through the tables that carry it as a column (`campaigns`, `public_campaigns`, `archives_campaign_archives`, `valid_campaigns`, etc.).

## Gotchas
- **No `deleted` / `is_test` columns** — the standard dimension filter does not apply (columns absent). Treat all 63 rows as live config.
- **1:3 fan-out on the campaign join** (see Joins) — the single most common mistake. Always constrain `frequency_cap_optimized`.
- **NULL primary tier is normal**, not missing data — it means "no primary cap, secondary only." Don't `COALESCE` it to 0 (0 impressions would mean "cap everything").
- **Durations are seconds**, not ms/minutes — convert with `/86400` for days.
- **`datastream_metadata.source_timestamp` is one snapshot instant repeated on every row** — useless for detecting which config changed when; use `update_time`.

## Cost & partitioning notes
- **Genuine BASE TABLE**, unpartitioned, clustered on `(campaign_template_id, frequency_cap_optimized)`, no TTL — `bq show`: 63 rows / 6,165 bytes. Clustering is immaterial at this size. There is no partition column to filter and no cost trap; a full `SELECT *` bills the 10 MB tier-1 minimum.
- The one thing to always do is **filter `frequency_cap_optimized`** — not for cost, but to avoid the 3× row fan-out on joins.

## Example queries
```sql
-- Cap config for one template in its AUTOMATED mode
SELECT campaign_template_id, frequency_cap_optimized,
       primary_impressions, primary_duration, secondary_impressions, secondary_duration
FROM `dw-main-bronze.integrationprod.core_campaign_template_frequency_cap_mappings`
WHERE campaign_template_id = 27 AND frequency_cap_optimized = 'AUTOMATED';
```
