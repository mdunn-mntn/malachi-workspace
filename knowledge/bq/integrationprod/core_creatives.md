# integrationprod.core_creatives

## Purpose
Canonical MNTN **creative dimension** — one row per built creative (ad unit) across every advertiser: the
served ad tag / adcode, its format (display vs video), asset/destination locations, Facebook-ad copy
fields, and video metadata. Reach for it to resolve a `creative_id` (from impression / win / spend logs
and `sum_by_creative_by_day`) to its advertiser, format, size, video length, and control-creative flag.
This is the `core_*` Postgres-CDC replica exposed as the `silver.core.creatives` view; it is the
creative→advertiser join path documented in data_knowledge.md.

## Grain & keys
- **Grain:** one row per `creative_id`. 1:1 — 5,730,607 rows == distinct `creative_id` (verified 2026-07-29).
- **Primary key:** `creative_id` (INT, sole cluster key).
- **Foreign keys / join columns:** `advertiser_id` → `advertisers.advertiser_id` (10,260 distinct, 0 NULL);
  `creative_size_id` → `core_creative_sizes.creative_size_id`; `user_id` → creating user (sparse). No
  `media_types` lookup table exists in bronze — `media_type_id` is decoded empirically (below).

## Column meanings (only the non-obvious ones)
- **`media_type_id`** — creative format code. Live distribution (2026-07-29): `2` = 5,052,683 (**88%**,
  display/banner — `length` almost always absent), `9` = 595,422 (**video** — the only type with
  `caas_video_id`), `0` = 41,563, `NULL` = 28,891, `8` = 10,963, then a long tail (`3`,`1`,`7`,`6`,`10`,
  `4`,`5`, each ≤465 rows). **`2`=display / `9`=video is empirically inferred** from the
  `length`+`caas_video_id` correlation, NOT a verified enum — no `core_media_types` table exists in bronze.
- **`caas_video_id`** — Creative-as-a-Service video asset id; populated only on `media_type_id=9`, else NULL.
- **`length`** — video length in seconds; populated for video, absent for display.
- **`is_adcode`** / **`adcode`** / **`adserver_payload`** — `adcode` holds the raw ad-tag markup and
  `adserver_payload` the ad-server VAST/config blob. Both are large STRING blobs (see cost notes).
- **`is_control_creative`** — control/holdout creative flag; rare.
- **`fb_*`** — Facebook-ad copy fields (headline / text / description / cta / display+click URLs).
- **`deleted`** — soft-delete BOOLEAN but **always FALSE** on this table (0 rows deleted, 2026-07-29). Use
  `active` for liveness, not `deleted`. There is no `is_test` column.
- **`creative_hash_id`** — present in schema but all-NULL / unused; do not join on it.
- **`datastream_metadata.source_timestamp`** — INT64 **milliseconds** CDC-capture epoch (`TIMESTAMP_MILLIS`
  → 2026; `TIMESTAMP_MICROS` → 1970), NOT business time. Use `create_time`/`update_time` for creative age.

## Joins & relationships
- **1-side of a 1:N decode.** Joining a fact table (impression/win/spend log, `sum_by_creative_by_day`)
  onto `core_creatives` on `creative_id` attaches advertiser/format/size and **never fans out** the fact.
- `advertiser_id` → `advertisers` (N:1); `creative_size_id` → `core_creative_sizes` (N:1, carries
  width/height + `video`/`ctv` flags).
- **`silver.core.creatives`** is the view over this base table. **Sibling `integrationprod.creatives`**
  (see creatives.md) carries the same business columns but lacks `datastream_metadata` (31 vs 32 cols).

## Gotchas
- **`SELECT *` is a ~19.6 GB trap** — the two blob columns `adserver_payload` + `adcode` are 17.96 GB
  (92% of a full scan). Always project the dim columns you need.
- **`deleted` is always FALSE** and there is no `is_test` — the dataset-wide `deleted=FALSE AND
  is_test=FALSE` filter is a no-op here; gate liveness on `active` / `approved`.
- **`media_type_id` enum is empirical** (2=display / 9=video), not a verified lookup — treat as strong-but-
  unconfirmed.
- **`creative_hash_id` all-NULL**; `caas_video_id`/`length` populated only for video — guard for NULL.

## Cost & partitioning notes
- **BASE TABLE, physical self:** `numRows=5,730,607`, `numBytes≈19.57 GB`, `timePartitioning=None`,
  `requirePartitionFilter=None`, `clustering=[creative_id]`. No partition, no TTL.
- **Column pruning is essential:** `SELECT adserver_payload, adcode` = **17.96 GB**; the 8-dim projection
  `creative_id, advertiser_id, name, media_type_id, creative_size_id, active, approved, deleted` = **0.265
  GB** (~74x cheaper). Clustering on `creative_id` prunes when you filter/join on it.

## Example queries
```sql
-- Resolve creatives to advertiser/format (cheap dim projection; never fans out the fact)
SELECT creative_id, advertiser_id, name, media_type_id, creative_size_id, length, active, approved
FROM `dw-main-bronze.integrationprod.core_creatives`
WHERE advertiser_id = @adv AND active = TRUE;

-- Active video creatives for an advertiser
SELECT creative_id, name, length, caas_video_id
FROM `dw-main-bronze.integrationprod.core_creatives`
WHERE advertiser_id = @adv AND active = TRUE AND media_type_id = 9;
```
