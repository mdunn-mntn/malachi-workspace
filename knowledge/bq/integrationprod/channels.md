# integrationprod.channels

## Purpose
Tiny static ENUM lookup that maps a `channel_id` integer to a human-readable marketing
channel name. Reach for it to label the `channel_id` foreign key that appears on
`campaigns` (and downstream event/log tables) — e.g. to split reporting into
CTV (Television) vs display (Multi-Touch). A tiny static Postgres reference/seed table in
`dw-main-bronze.integrationprod`; unlike the CDC-replicated dims in this dataset it carries
no `datastream_metadata` column (verified 2026-07-19) — it behaves as a fixed ENUM seed, not
a change-tracked stream.

## Grain & keys
- **Grain:** one row per `channel_id` (10 rows total — the complete channel ENUM).
- **Primary key / join column:** `channel_id`.

## Joins & relationships
- **`campaigns.channel_id` (N campaigns : 1 channel).** `channels` is the dim, `campaigns`
  is the fact-ish side. Joining `channels` onto `campaigns` (dim lookup) is safe — 1:N, no
  fan-out. Going the other way (`campaigns` → `channels`) never multiplies rows because
  `channel_id` is unique here. Nearly all live campaigns carry `channel_id` 1 (display /
  Multi-Touch) or 8 (CTV / Television) — together ~97.7% (463,199 of 474,021 live campaigns,
  `deleted=FALSE AND is_test=FALSE`, 2026-07-19). Note 213 live campaigns carry
  `channel_id IS NULL`; an `INNER JOIN`/`USING (channel_id)` silently drops them, so use a
  `LEFT JOIN` when you need a full campaign census.
- The same `channel_id` code appears on many `bronze.raw` event and `silver` log/summary
  tables, and this dim is the usual label source for them (exact downstream coverage not
  enumerated here). Because it is a broadcast-sized 10-row lookup, any such join is free.

## Gotchas
- **The dataset-wide `deleted=FALSE AND is_test=FALSE` filter does NOT apply here** — this
  table has ONLY `channel_id` and `name` (verified live 2026-07-19). No soft-delete flag,
  no `is_test`, no `create_time`/`update_time`, no `datastream_metadata`. It is a pure
  static ENUM; every row is live.
- **`channel_id` label ≠ the "display/CTV" shorthand.** Codebase/memory shorthand is
  "channel_id 1=display, 8=CTV", but the dim's own `name` for 1 is `Multi-Touch` and for 8
  is `Television`. Map through this table for the canonical string; use the shorthand only
  when reasoning about CTV-vs-display splits.
- **`channel_id` can be NULL on the fact side.** 213 live `campaigns` rows carry no
  `channel_id` (2026-07-19). Any `INNER JOIN`/`USING (channel_id)` back to this dim silently
  drops those rows — reach for `LEFT JOIN` when the count must be complete.
- Static and small — do not expect it to change; it has no versioning/archive sister table.

## Cost & partitioning notes
- No partition, no clustering, no TTL. It is a 10-row / 199-byte BASE TABLE — the entire
  table is `numBytes` = 199 B (`bq show`, 2026-07-19). `SELECT channel_id, name` dry-run =
  0 GB processed / 0.01 GB billed (min tier-1 rounding), 0.6s wall (2026-07-19). There is
  no filter to "always apply" — full scans are effectively free. `SELECT *` and a
  two-column select are identical cost here (both columns are the whole table).

## Example queries
```sql
-- Label LIVE campaigns by channel (safe dim lookup, no fan-out).
-- The deleted/is_test filter is REQUIRED on campaigns to count only live rows.
-- NOTE: 213 live campaigns have channel_id IS NULL (2026-07-19); this INNER JOIN
-- drops them — switch to LEFT JOIN if you need a full campaign census.
SELECT ch.name AS channel, COUNT(*) AS n_campaigns
FROM `dw-main-bronze.integrationprod.campaigns` c
JOIN `dw-main-bronze.integrationprod.channels` ch USING (channel_id)
WHERE c.deleted = FALSE AND c.is_test = FALSE
GROUP BY channel
ORDER BY n_campaigns DESC
```
