# integrationprod.core_blocked_ip_addresses

## Purpose
Bronze CDC replica of the per-advertiser **IP blocklist / suppression list**: each row says "advertiser X
has blocked IP Y" (e.g. the advertiser's own office IPs, internal traffic, or IPs flagged invalid).
Reach for it to know which IPs an advertiser has excluded from targeting/attribution. Exposed as the
`silver.core.blocked_ip_addresses` view (a plain `SELECT * FROM` this bronze table). As of 2026-07-29 it
holds ~657K rows across only **330 distinct advertisers** — so a small set of advertisers carry very
large blocklists (often bulk-uploaded).

## Grain & keys
- **Grain:** one row per **(advertiser_id, ip)** pair (verified: 657,387 rows = 657,387 distinct
  `advertiser_id|ip`, 2026-07-29 — the pair is unique).
- **Natural/composite key:** (`advertiser_id`, `ip`). There is no surrogate id column.
- **Foreign keys:** `advertiser_id` → `advertisers.advertiser_id`; `audience_upload_id` →
  `audience_uploads.audience_upload_id` (provenance of a bulk upload); `user_id` → the user who added it.
- **No `deleted` / `is_test` columns** — presence of a row = the IP is blocked for that advertiser.

## Column meanings (only the non-obvious ones)
- **`ip`** — the blocked IP as a **STRING** (IPv4 dotted-quad in the sample, e.g. `65.55.65.190`).
  **Leading cluster key** (source order is `[ip, advertiser_id]`), so filtering by `ip` prunes best.
  Not normalized to an integer; compare as text.
- **`advertiser_id`** — the advertiser that owns this block. Second cluster key. Only ~330 advertisers
  appear, so the list is concentrated.
- **`description`** — free-text note on why the IP is blocked (e.g. "RGE Office", "Invalid"); frequently
  NULL. Not structured; do not parse for logic.
- **`audience_upload_id`** — links the row to the bulk `audience_uploads` job that added it (NULL when
  added ad hoc / not via upload). Provenance, not required for the block to apply.
- **`create_time` / `update_time`** — often **NULL** in this table (many legacy rows carry no timestamps).
  Do not rely on them to date a block; absence of a timestamp does not mean the block is inactive.
- **`datastream_metadata`** — Datastream CDC lineage RECORD (`uuid`, `source_timestamp`).
  `source_timestamp` is a **millisecond** epoch (CDC-capture time), not business time.

## Joins & relationships
- **`core_blocked_ip_addresses.advertiser_id` → `advertisers.advertiser_id`** — **N:1** (this table is
  the many-side: many blocked IPs per advertiser). Aggregating blocked-IP counts up to the advertiser is
  a safe group-by; joining this table to an advertiser dim **fans out** to blocklist cardinality — never
  join it in without aggregating first.
- **`audience_upload_id` → `audience_uploads`** — **N:1** provenance link (one upload → many blocked IPs).
- **`silver.core.blocked_ip_addresses`** is a VIEW = `SELECT * FROM dw-main-bronze.integrationprod.core_blocked_ip_addresses`
  (verified 2026-07-29). Content-identical.
- **IP↔IP bridging caveat:** this is a raw string IP list scoped to an advertiser. Do not attempt to
  bridge these IPs against log-table IPs across the warehouse beyond an exact string match on `ip`
  (consistent with the workspace "no IP→IP bridging in BQ" rule).

## Gotchas
- **Big table, one advertiser = huge blocklist.** ~657K rows / ~81 MB across only ~330 advertisers; a
  join without a per-advertiser filter or a pre-aggregation fans out hard. Filter on `ip` (leading
  cluster key) or `advertiser_id` first.
- **`create_time`/`update_time` are frequently NULL** — not usable as a reliable "when blocked" signal.
- **`ip` is a STRING** — no IPv4 integer, no CIDR ranges observed (individual addresses). Match exactly.
- **No soft-delete.** A row's presence is the block; there is no `deleted` flag to filter on.

## Cost & partitioning notes
- **BASE TABLE, physical `self`** (the silver `core.blocked_ip_addresses` view reads it directly).
  `bq show`: `type=TABLE`, `numRows=657387`, `numBytes≈81.5 MB`, `timePartitioning=None`,
  `clustering.fields=[ip, advertiser_id]`, no `expirationTime` (no TTL).
- **Partition: none** (`require_partition_filter=false`) — but the table is **clustered on
  `[ip, advertiser_id]`**. Filter on `ip` first (leading key), then `advertiser_id`, to prune blocks
  within the scan.
- **Cost:** a full scan is ~81 MB. Cheap in absolute terms, but avoid `SELECT *` inside large joins —
  pre-filter by advertiser or aggregate to a per-advertiser count first.

## Example queries
```sql
-- IPs an advertiser has blocked (partition/cluster-friendly: filter advertiser_id)
SELECT ip, description, audience_upload_id
FROM `dw-main-bronze.integrationprod.core_blocked_ip_addresses`
WHERE advertiser_id = 32178
LIMIT 100;

-- how concentrated are blocklists? (per-advertiser counts, aggregate before joining)
SELECT advertiser_id, COUNT(*) AS blocked_ips
FROM `dw-main-bronze.integrationprod.core_blocked_ip_addresses`
GROUP BY advertiser_id
ORDER BY blocked_ips DESC
LIMIT 100;
```
