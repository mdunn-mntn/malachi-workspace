# integrationprod.audience_audiences

## Purpose
The LIVE, mutable registry of named **audience objects** in MNTN's audience service — one per advertiser-created audience, carrying an audience-level targeting `expression` (JSON with `data_source_id` / MM references). This is the current successor to the FROZEN `silver.core.audiences` snapshot (that snapshot stops at create_time 2023-12-15 01:22:02; this table is live to now). Reach for it to look up an audience's owning advertiser, name, or top-level expression, and as the parent of the `audience_audience_segments` bridge. **Caveat:** this is a template/definition table, not what the bidder evaluates per campaign — for "what a campaign actually targets" use `silver.audience.audience_segments` (campaign-level, `is_targeted`).

## Grain & keys
- **Grain:** one row per `audience_id` (verified: 64,495 rows = 64,495 distinct `audience_id`).
- **PK:** `audience_id` (also the sole cluster key).
- **FKs:** `advertiser_id` → `advertisers.advertiser_id` (N:1, never NULL); `expression_type_id` → `audience.expression_types`; `user_id` → audience-service user; parent of `audience_audience_segments.audience_id` (1:N).

## Column meanings (only the non-obvious ones)
- **audience_id** — PK on the audience-service auto-increment sequence. Its FK partner is `audience_audience_segments.audience_id`. **This sequence is NOT the same as `core.audiences.audience_id`** — the two tables share ~59K numerically-overlapping ids but 0/59,240 share create_time and only 10/59,240 share name, i.e. the same integer points at different audiences. Never join the two on `audience_id` (see Gotchas).
- **advertiser_id** — owning advertiser (FK → `advertisers`). Never NULL (0/64,495).
- **expression** — the **audience-level** targeting expression, a JSON string carrying the top-level MM / data-source leaves (e.g. `"data_source_id":13/19`). Extract DS ids with `REGEXP_EXTRACT_ALL(expression, r'"data_source_id":([0-9]+)')`. This is the fat column: ~63.9 MiB of the table's 71 MiB (~90%). NOT the per-campaign/per-segment expression the bidder evaluates — the Fangorn overlay adds DS46 to `audience_audience_segments.expression` while leaving DS13/DS19 in THIS base expression, so read segments, not this, for Fangorn-on detection.
- **expression_type_id** — FK → `audience.expression_types`; domain (verified live) **1=opm (95 rows), 2=tpa (64,398, dominant), 3=sga (2 rows)**. Matches `audience.audience_segments` convention (2=tpa is the bidder-evaluated form).
- **is_test** — TRUE = test/QA audience (1,797 rows). **Never NULL.** Filter `is_test=FALSE` for real audiences. (See Gotchas: there is NO `deleted` column on this table.)
- **is_hidden** — soft-hide flag; almost always NULL (64,424 NULL, 71 TRUE, 0 FALSE). Treat NULL as visible; add `is_hidden IS NOT TRUE` if you need to drop hidden audiences.
- **create_time / update_time** — business TIMESTAMPs. **`create_time` is never NULL** (0/64,495), spans 2011-07-11 → live — use it for the audience's business time. **`update_time` is NULL for 18,625 rows (28.9%)**; non-null values span 2020-08-28 → now. Prefer `create_time` (or `update_time` when present) over `datastream_metadata.source_timestamp`.
- **user_id** — audience-service user who owns/created the audience (nullable).
- **datastream_metadata.source_timestamp** — INT64 **milliseconds** Datastream CDC-**capture** epoch (decode with `TIMESTAMP_MILLIS()`; `TIMESTAMP_MICROS()` decodes the same raw to 1970, proving ms not µs). Never NULL (0/64,495). **This is capture time, NOT business time, and is NOT equal to `update_time`** — only 5/64,495 rows match `UNIX_MILLIS(update_time)` exactly; 45,865 rows have source_timestamp **greater** (capture lag of ms→seconds for rows updated after Datastream went live, up to **5.31 years** later for older/backfilled rows); 0 rows less; the rest have NULL `update_time`. Earliest capture = 2025-12-19, so a row last updated in 2011 still gets a 2025 source_timestamp. For a business timestamp use `create_time`. `datastream_metadata.uuid` = CDC row uuid.

## Joins & relationships
- **→ `audience_audience_segments` on `audience_id`** — **1:N (fan-out up to 887×).** Only 41,427 / 64,495 audiences (64%) have any segment rows; median 7 segments/audience, max 887. Aggregate the segment side (e.g. array-agg or DISTINCT DS ids) before joining, or you multiply the audience row.
- **→ `advertisers` on `advertiser_id`** — **N:1** (many audiences per advertiser; 14,970 distinct advertisers own type-2 audiences). Filter the partner `deleted=FALSE AND is_test=FALSE`.
- **→ `audience.expression_types` on `expression_type_id`** — N:1 decode (1=opm/2=tpa/3=sga).
- **✗ `core.audiences` on `audience_id` — DO NOT.** Separate id sequences; the join is meaningless (identity mismatch verified above). `core.audiences` is the frozen legacy snapshot (79,874 rows, max create 2023-12-15); this table is its live audience-service replacement, not a renumbered copy.

## Gotchas
- **No `deleted` column.** The dataset-wide `deleted=FALSE AND is_test=FALSE` hygiene filter does NOT fully apply here — this table exposes only `is_test` (+ the mostly-NULL `is_hidden`). Live-row filter is **`is_test=FALSE`** (optionally `AND is_hidden IS NOT TRUE`).
- **Templates ≠ targeting.** These are audience-level definitions. Counting MM (DS19) off `audience_audiences` over-counts by ~5 pts vs the true per-campaign figure from live `audience.audience_segments` (~88% vs ~83%). For "what is actually targeted," use `audience.audience_segments` with `expression_type_id=2 AND is_targeted=TRUE`.
- **Fangorn is invisible here.** The Fangorn DS13→DS46 swap is applied in `audience_audience_segments.expression`, not in this table's `expression`. Base expression still shows DS13/DS19 for Fangorn-on advertisers — do not infer Fangorn state from this table.
- **audience_id numeric overlap with core.audiences is a trap** (see Joins). Same integer, different entity.
- **datastream_metadata.source_timestamp is Datastream CDC-CAPTURE time**, ms epoch (earliest capture 2025-12-19) — NOT the audience's business time and NOT equal to `update_time` (5/64,495 exact, up to 5.31 yrs off). For "when was this audience made/changed," use `create_time` (never NULL); `update_time` is present but NULL for ~29% of rows.

## Cost & partitioning notes
- **Small dim, no partition** (64,495 rows, ~71 MiB backing storage; `numBytes=74,499,505`). No date filter needed; full scans are cheap. Clustered on `audience_id` — point lookups by id prune.
- **The one thing to always do: avoid `SELECT *` and don't pull `expression` unless you need it.** Dry-run upper bounds (labeled by column set): `SELECT *` = 74,499,505 B (71.0 MiB) · `SELECT expression` = 67,018,472 B (63.9 MiB, ~90% of the table) · `SELECT audience_id` = 515,960 B (0.49 MiB). The `expression` STRING dominates cost by ~130×.
- **Live-row filter to always apply:** `WHERE is_test=FALSE` (there is no `deleted` column).

## Example queries
```sql
-- Live audiences for an advertiser, with the DS leaves in their audience-level expression
SELECT audience_id, name, expression_type_id,
       REGEXP_EXTRACT_ALL(expression, r'"data_source_id":([0-9]+)') AS ds_ids,
       update_time
FROM `dw-main-bronze.integrationprod.audience_audiences`
WHERE advertiser_id = <AID>
  AND is_test = FALSE
ORDER BY update_time DESC;

-- Audience → segment fan-out (aggregate the child before joining)
SELECT a.audience_id, a.name, s.n_segments
FROM `dw-main-bronze.integrationprod.audience_audiences` a
JOIN (
  SELECT audience_id, COUNT(*) AS n_segments
  FROM `dw-main-bronze.integrationprod.audience_audience_segments`
  GROUP BY audience_id
) s USING (audience_id)
WHERE a.is_test = FALSE;
```
