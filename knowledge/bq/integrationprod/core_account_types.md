# integrationprod.core_account_types

## Purpose
Tiny CDC reference dimension that decodes the surrogate `account_type_id` into the human-readable name
of an advertiser's **account type** (business vertical/classification: Ecommerce, B2B, Mobile, etc.).
Reach for it only to attach a name to an `account_type_id` carried by the advertiser↔account-type
bridge. Sourced from the Postgres `core.account_types` table via Datastream CDC into bronze; it has been
effectively static since seed (7 rows in 2023, one added in 2024).

## Grain & keys
- **Grain:** one row per advertiser account type. Exactly 8 rows (ids 1–8).
- **Primary key:** `account_type_id` (surrogate INT; declared PK in `tableConstraints`, also the sole
  cluster key).
- **Natural key:** `name` (title-case label: `Ecommerce`, `B2B`, `Mobile`, `Gaming`,
  `Transparent Pricing`, `Agency`, `Local`, `Mobile With Conversions`).
- **Foreign-key target:** `account_type_id` is referenced by the bridge
  `integrationprod.core_advertiser_account_types` (`advertiser_id`, `account_type_id`).

## Column meanings (only the non-obvious ones)
- `account_type_id` — surrogate id; FK target for the advertiser bridge. Live domain = {1..8}:
  `1=Ecommerce`, `2=B2B`, `3=Mobile`, `4=Gaming`, `5=Transparent Pricing`, `6=Agency`, `7=Local`,
  `8=Mobile With Conversions`. Clustered, but clustering is cosmetic on an 8-row table.
- `name` — title-case label as above. Match case-insensitively if joining to prose/UI strings.
- `create_time` — business insert time in Postgres. Ids 1–7 = `2023-09-26 21:55:50` (original seed);
  id 8 (`Mobile With Conversions`) = `2024-09-11 16:49:28` (added later). Use this for age, not
  the CDC timestamp below.
- `datastream_metadata.source_timestamp` — INT64 **milliseconds** CDC-capture epoch, NOT business time.
  Anchor: `TIMESTAMP_MILLIS(source_timestamp)` = `2026-04-22 17:14:42` for every row (a full-table CDC
  re-snapshot); `TIMESTAMP_MICROS` gives 1970 = wrong. `datastream_metadata.uuid` is the Datastream
  event id.

## Joins & relationships
This is the **"1" side** of a 1:N lookup — 8 rows fanning out to many advertiser rows via a bridge.
- `core_advertiser_account_types` (`advertiser_id`, `account_type_id`) is the **many-to-many bridge**:
  `account_types.account_type_id` ← `core_advertiser_account_types.account_type_id` (N:1), and
  `core_advertiser_account_types.advertiser_id` → `advertisers.advertiser_id`. An advertiser can carry
  multiple account types (bridge grain), so **`advertisers` does NOT carry `account_type_id` directly** —
  go through the bridge.
- Joining `core_account_types` onto the bridge on `account_type_id` is a **safe name-enrichment**: it
  adds one string and never fans out the bridge (each bridge row matches exactly one dim row). The
  fan-out risk lives in the bridge (advertiser × account-type), not here.

## Gotchas
- **No `deleted` / `is_test` columns** — the dataset-wide `deleted=FALSE AND is_test=FALSE` live filter
  does NOT apply here (and isn't needed; all 8 rows are canonical seed rows).
- **No `update_time`** — the schema is just `account_type_id, name, create_time, datastream_metadata`.
  Use `create_time` for business age; use `datastream_metadata.source_timestamp` (ms) for CDC freshness.
- **`source_timestamp` is ms CDC-capture, not business time** (all rows re-snapshotted 2026-04-22).
- **Effectively static** — 7 rows since 2023, +1 in 2024. Analysts typically hard-code the map rather
  than join. Confirm against source before assuming no new type has appeared.

## Example queries
```sql
-- Full dim dump
SELECT account_type_id, name
FROM `dw-main-bronze.integrationprod.core_account_types`
ORDER BY account_type_id;

-- Decode account type for advertisers via the bridge
SELECT at.name AS account_type, COUNT(DISTINCT b.advertiser_id) AS n_advertisers
FROM `dw-main-bronze.integrationprod.core_advertiser_account_types` b
JOIN `dw-main-bronze.integrationprod.core_account_types` at
  ON b.account_type_id = at.account_type_id
GROUP BY 1 ORDER BY 2 DESC;
```
