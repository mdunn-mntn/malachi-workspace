# integrationprod.core_flight_billing_types

## Purpose
**Source-of-truth mapping of a flight to its billing type.** One row per `core_flight_id` giving the
`billing_type_id` used to bill that flight. This table **supersedes the legacy `advertisers.billing_type_id`
column** — the reporting team (BAE) uses `core.flight_billing_types` as authoritative for spend/billing
logic. Values are derived and upserted by the Gary (gary-ql) service after budget processing (it maps the
billing type from the campaign group's `product_id`; the SELECT/Premier UI does not pass it directly).

## Grain & keys
- **Grain:** one row per `core_flight_id`. 74,769 rows == 74,769 distinct `core_flight_id` (1:1 — one billing
  type per flight, verified 2026-07-29).
- **Primary key:** `core_flight_id` (INT, sole cluster key).
- **Foreign key:** `core_flight_id` → `core_flights.flight_id` (N:1 into flights; 74,768 of 74,769 match — 1
  orphan). Note the FK column is named `core_flight_id`, not `flight_id`.

## Column meanings (only the non-obvious ones)
- **`core_flight_id`** — the flight this billing type applies to; joins to `core_flights.flight_id`.
- **`billing_type_id`** — the billing-type code. Live distribution (2026-07-29): `1` = 61,859 (dominant),
  `2` = 12,910. Confirmed labels (Slack, PER-6526, 2026-06-02): **`2` = PTV Fixed CPM** (currently also used
  for MNTN SELECT campaigns, slated to split to a new `3`); `3` = proposed MNTN SELECT / native impression-cap
  (not yet live). **The label for the dominant `1` is not confirmed** in bronze — the full enum lives in
  `core.billing_types` (there is no `integrationprod.core_billing_types` replica). Decode there before
  asserting `1`'s meaning.
- **`create_time` / `update_time`** — TIMESTAMPs of the mapping row (Gary upsert times), not flight timing.
- **`datastream_metadata.source_timestamp`** — INT64 **milliseconds** CDC-capture epoch, not business time.

## Joins & relationships
- **N:1 into `core_flights`:** `core_flight_billing_types.core_flight_id = core_flights.flight_id`. As a
  billing-type lookup keyed 1:1 on the flight, it does not fan out flights.
- **Label lookup is external:** `billing_type_id` → `core.billing_types` (definition/reference table for
  billing types; new ids are added there). Not catalogued here.
- Exposed as `silver.core.flight_billing_types`.

## Gotchas
- **Sparse coverage:** only 74,769 flights have a billing-type row vs ~1,008,556 in `core_flights` (~7%).
  Gary only writes newer/eligible flights — expect NULL on a LEFT JOIN for most flights. Do not assume every
  flight is present.
- **FK column is `core_flight_id`, not `flight_id`** — join `core_flight_id = core_flights.flight_id`.
- **`billing_type_id=2` currently conflates PTV Fixed CPM and MNTN SELECT** (PER-6526 tracks splitting SELECT
  to a new id `3`) — treat `2` as ambiguous between those two until the split ships.
- **`1`'s label is unconfirmed** in bronze — resolve via `core.billing_types`, do not guess.
- **No `deleted`/`is_test` columns** — the soft-delete dim filter does not apply.

## Cost & partitioning notes
- **Non-partitioned mapping table: 74,769 rows / ~5.8 MB.** No partition, no TTL,
  `require_partition_filter=false`. Clustered on `core_flight_id` — filtering/joining on it prunes blocks.
  Cheap to scan whole; still project only the columns needed.

## Example queries
```sql
-- Attach the source-of-truth billing type to flights (LEFT JOIN — most flights are absent)
SELECT f.flight_id, f.campaign_group_id, b.billing_type_id
FROM `dw-main-bronze.integrationprod.core_flights` f
LEFT JOIN `dw-main-bronze.integrationprod.core_flight_billing_types` b
  ON f.flight_id = b.core_flight_id;

-- Billing-type distribution
SELECT billing_type_id, COUNT(*) n
FROM `dw-main-bronze.integrationprod.core_flight_billing_types`
GROUP BY billing_type_id ORDER BY n DESC;
```
