# integrationprod.core_pixel_integrations

## Purpose
Configuration dimension recording each advertiser's e-commerce / conversion-pixel integration — which
platform it uses (Shopify, GTM, manual, etc.), the shop URL, and its tracking/conversion setup status.
Reach for it to answer "how is advertiser X's pixel installed?" and "when was that integration set up /
last touched?" **~12.3K rows.** Exposed as the `silver.core.pixel_integrations` view. (One of the
pixel-config tables; there is no separate `conversion_sources` table — see also `ui_advertiser_pixel_infos`,
`attr_advertiser_waypoints_event_mapping`, and advertiser pixel flags on `advertisers`.)

## Grain & keys
- **Grain:** one row per pixel integration instance. 12,270 rows (verified 2026-07-29). An advertiser can
  hold **multiple** integrations — 10,439 distinct advertisers over 12,270 rows; most (9,446) have exactly
  one, but a few have dozens (max seen: 39). So `advertiser_id` is **NOT** unique here.
- **Primary key:** `pixel_integration_id` (INT). Unique (12,270 distinct = row count). Also cluster key.
- **Foreign keys:** `advertiser_id` → `advertisers.advertiser_id` (N:1); `pixel_integration_type_id` →
  `core_pixel_integration_types.pixel_integration_type_id` (N:1); `user_id` → the setting user (often NULL).

## Column meanings (only the non-obvious ones)
- **`pixel_integration_id`** — PK and cluster key; a per-integration surrogate id, not the advertiser.
- **`advertiser_id`** — the advertiser this integration belongs to. **Fans out** — one advertiser may
  have many integration rows (see Grain). Join back to `advertisers` for company_name.
- **`pixel_integration_type_id`** — platform FK → `core_pixel_integration_types`. Live distribution
  (2026-07-29): manual (4) = 7,297; gtm (6) = 2,064; shopify (1) = 1,342; sans-pixel (7) = 1,046;
  reset (8) = 521. Manual is the default/dominant install method.
- **`access_token`** — integration credential; **effectively always NULL/blank in bronze** (0 of 12,270
  rows populated, 2026-07-29) — treat as redacted/unavailable, do not rely on it.
- **`shop_base_url`** — the advertiser's shop URL (populated mainly for Shopify/plugin integrations;
  blank for most manual rows).
- **`tracking_status` / `conversion_status`** — free-text setup-state STRINGs (not INT enums). Dominant
  value is `"Not Done"` (11,582 of 12,270 rows are `Not Done`/`Not Done`; 688 rows have both blank).
  Non-empty values seen are "Not Done" (and "Done" where progressed). Treat blank vs "Not Done" as
  distinct states.
- **`create_time` / `update_time`** — TIMESTAMPs the integration row was created / last modified in source
  Postgres; on most rows they are equal (set-once). Use `update_time` to find recently-touched pixels
  (this table's `update_time` is used in on-call triage to rule out MNTN-side pixel config changes).
- **`user_id`** — id of the user who configured it; frequently NULL.
- **`datastream_metadata`** — Datastream CDC lineage RECORD; not business data.

## Joins & relationships
- **`advertiser_id` → `advertisers.advertiser_id`** — **N:1** from this table's side, but because an
  advertiser can hold several integrations, joining `core_pixel_integrations` INTO an advertiser-grain
  query **fans out** (up to ~39x). Aggregate or pick one row per advertiser first if you need advertiser grain.
- **`pixel_integration_type_id` → `core_pixel_integration_types`** — **N:1** platform decode; never fans out.
- **`silver.core.pixel_integrations`** is a VIEW over this table.

## Gotchas
- **`advertiser_id` is not unique** — do not treat this as an advertiser-grain dim (see fan-out above).
- **`access_token` is empty across all rows** — never use it as a signal.
- **`tracking_status`/`conversion_status` are free-text STRINGs, not coded enums** — compare on literal
  values ("Not Done", "Done", blank), and note blank ≠ "Not Done".
- **No `deleted`/`is_test` columns** — standard integrationprod soft-delete dim filter does not apply here.
- **Slowly-changing / mostly-static** — bulk of the table was written 2020–2023; the corpus notes
  "pixel_integrations untouched since 2020" for many advertisers. `update_time` tells you the last change.

## Cost & partitioning notes
- **Non-partitioned config dim: 12,270 rows / ~1.15 MB.** No partition, no TTL, no `require_partition_filter`.
  Clustered on `pixel_integration_id` — helpful only for point lookups by that id.
- Full `SELECT *` bills roughly the tier-1 10 MB minimum (table is ~1.15 MB). Cheap; scan freely, but
  prefer selecting the columns you need (skip the CDC RECORD and the always-empty `access_token`).

## Example queries
```sql
-- All pixel integrations for an advertiser, with platform decode
SELECT pi.pixel_integration_id, t.name AS platform, pi.shop_base_url,
       pi.tracking_status, pi.conversion_status, pi.create_time, pi.update_time
FROM `dw-main-bronze.integrationprod.core_pixel_integrations` pi
LEFT JOIN `dw-main-bronze.integrationprod.core_pixel_integration_types` t USING (pixel_integration_type_id)
WHERE pi.advertiser_id = @advertiser_id
ORDER BY pi.update_time DESC;

-- Platform mix across all advertisers
SELECT t.name AS platform, COUNT(*) n
FROM `dw-main-bronze.integrationprod.core_pixel_integrations` pi
JOIN `dw-main-bronze.integrationprod.core_pixel_integration_types` t USING (pixel_integration_type_id)
GROUP BY 1 ORDER BY n DESC;
```
