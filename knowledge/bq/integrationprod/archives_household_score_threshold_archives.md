# integrationprod.archives_household_score_threshold_archives

## Purpose
Datastream (Postgres CDC) mirror of the app's `archives.household_score_threshold_archives` table — the append-only history of household-score-**threshold** values written for each campaign. A campaign targets/serves against a household only if the household's score clears its configured threshold; every time that threshold is (re)written the row is archived here. Reach for it to reconstruct **what a campaign's household-score gate was as-of a historical date**, or to trace how RTC (Real-Time Conquest) conquest-score thresholds moved over time. The `archives` prefix is the Postgres schema name (BQ names integrationprod tables `<schema>_<table>`), not a version-suffix — the PK is unique, one row per write.

## Grain & keys
- **Grain:** one row per `household_score_threshold_archives_id` — a single archived threshold write. **Verified unique:** 61,507,781 rows = 61,507,781 distinct PK (2026-07-29).
- **Surrogate PK:** `household_score_threshold_archives_id` (the sole cluster key).
- **Natural grouping key:** `(advertiser_id, campaign_group_id, campaign_id)` — every row carries all three (0 nulls). This is **many-rows-per-campaign**, not one: 42,947 distinct campaigns / 18,480 campaign_groups / 5,041 advertisers across 61.5M rows (~1.4k archived writes per campaign, accumulated over `create_time` 2024-06-12 → present). Order the history by `create_time`.

## Column meanings (only the non-obvious ones)
- **`household_score_threshold_archives_id`** — surrogate PK of the archive row (cluster key, unique). NOT a base-record id to join on.
- **`advertiser_id` / `campaign_group_id` / `campaign_id`** — FKs to `advertisers` / `campaign_groups` / `campaigns`. All three present on every row (0 nulls); together they identify which campaign the threshold applies to.
- **`threshold`** — the household-score gate for the campaign: the minimum household score required to serve/target. Recent rows sit on the **RTC conquest-score scale 0–10,000** (matches the `realtime_conquest_score=10000` seen in RTC `model_params`). Distribution across the full table: **67% are exactly 0** (median 0), Q3 ≈ 3,800; full-table extremes are **-100** (sentinel / "unset") and **7,776,000** (= 90 days × 86,400 s — a legacy/alternate encoding, likely a recency window in seconds rather than a 0–10k score). Treat non-`[0,10000]` values as a different encoding era; do not assume one unit across all history.
- **`transaction_id`** — per-write UUID (the app/CDC write-transaction id); near-1:1 with rows (every sampled row distinct). Use as an idempotency/dedup key, not a business key.
- **`create_time`** — business time the threshold record was created (2024-06-12 → present). This is the as-of / ordering column. Recent `create_time` days are **sparse** (dozens–hundreds of rows/day); the bulk of the 61.5M rows is historical — the table is skewed, not evenly daily.
- **`update_time`** — last-modified time of the record; equals `create_time` when never updated (table min of both = 2024-06-12). On recently re-captured rows it reflects the **CDC snapshot/refresh time** (clusters at "today"), not a business edit — do not read it as a business update.
- **`datastream_metadata.source_timestamp`** — INT64 = **UNIX_MILLIS** of CDC capture (verified: `TIMESTAMP_MILLIS(1785362724191)` ≈ `update_time` to the second). `datastream_metadata.uuid` = CDC event id. CDC-capture time, not business time.

## Joins & relationships
- **`campaign_id` → `campaigns`**, **`campaign_group_id` → `campaign_groups`**, **`advertiser_id` → `advertisers`** — all N:1 (many archived threshold writes per campaign). Get advertiser name from `advertisers.company_name` (advertiser_name fields are unreliable elsewhere in the stack).
- **Fan-out warning:** this table is the *many* side of every one of those FKs — joining a campaign/advertiser dim straight to it explodes to the full threshold history. To get the current/as-of threshold, first dedupe: `QUALIFY ROW_NUMBER() OVER (PARTITION BY campaign_id ORDER BY create_time DESC) = 1`.
- **No `deleted` / `is_test`** columns — the standard bronze `deleted=FALSE AND is_test=FALSE` hygiene filter cannot be applied here; apply it on the joined `campaigns` / `advertisers` if you need it.

## Gotchas
- **`archives_` is the Postgres schema, not a versioning suffix.** Unlike the `archives_*_archives` version-history tables (which carry a `version` column), this one has **no `version` and no `archive_time`** column — PK is unique, one row per write. Order history by `create_time`.
- **`threshold` is not single-unit across history** — recent rows are 0–10,000 (RTC score), but the full table holds -100 and 7,776,000 (=90 days in seconds). Filter/interpret by era; don't assume every value is a 0–10k score.
- **67% of thresholds are exactly 0** — a 0 gate is the common/default case; non-zero rows are where a real conquest-score floor was set.
- **`update_time` on recently-captured rows = CDC refresh time (today), not a business edit.** Use `create_time` for business timing.
- **`create_time` is heavily skewed** — recent days are sparse; the 61.5M rows are dominated by historical writes. Sizing a "per day" scan off recent volume will under-estimate historical density.

## Cost & partitioning notes
- **Genuinely unpartitioned** (bq show: `timePartitioning` null, `rangePartitioning` null), clustered on `household_score_threshold_archives_id` only. **No partition to prune** and the cluster key is a surrogate id, so filtering by `campaign_id` / `create_time` does **not** prune blocks — a scoped query still touches the whole column. 61,507,823 rows / **8.61 GB** logical (bq show `numBytes`). No TTL — the archive grows.
- **Column pruning is the main lever.** Dry-run (2026-07-29): a 15-col-equivalent multi-`COUNT(DISTINCT)` incl. `transaction_id` (STRING) estimated **5.78 GB**; the same aggregate without the `transaction_id` distinct billed **3.21 GB**. `SELECT *` drags in the STRING + STRUCT and is the expensive shape — project only the ids/threshold/create_time you need.
- A `create_time` filter does NOT reduce bytes (no partition) but is still correct for scoping results; expect ~1 GB per column-set even for a 3-day window.

## Example queries
```sql
-- Current household-score threshold per campaign (latest write), non-string cols only
SELECT campaign_id, campaign_group_id, advertiser_id, threshold, create_time
FROM `dw-main-bronze.integrationprod.archives_household_score_threshold_archives`
QUALIFY ROW_NUMBER() OVER (
          PARTITION BY campaign_id
          ORDER BY create_time DESC) = 1
```
