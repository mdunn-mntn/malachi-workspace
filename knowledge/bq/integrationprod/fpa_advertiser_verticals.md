# integrationprod.fpa_advertiser_verticals

## Purpose
Datastream CDC mirror of the Postgres `fpa.advertiser_verticals` table: the advertiser → industry-vertical
classification. **This is the source of truth for an advertiser's vertical** — reach for it (WHERE `type=1`) when
you need an advertiser's sub-vertical for RTC / Fangorn scoring, bucket lookups, or industry cuts. It is
authoritative over `advertisers.advertiser_vertical_id`, which is frequently NULL even when a vertical exists here.
Small dim (~7 MB, ~57.8K rows) — cheap to full-scan.

## Grain & keys
- **Grain:** two rows per `advertiser_id` — one `type=0` (parent vertical) + one `type=1` (sub-vertical).
  Verified 2026-07-20: 57,772 rows / 28,886 advertisers = exactly 2× (28,886 rows at each `type`).
- **PK:** `id` (surrogate row id, clustered). One `id` per (advertiser × type) row.
- **Business key:** `advertiser_id` + `type`. FK: `advertiser_id` → `advertisers.advertiser_id` (N:1).
- **Vertical dims:** `vertical_id` (+ denormalized `vertical_name`); 37 distinct parent verticals (`type=0`),
  148 distinct sub-verticals (`type=1`) = 185 total (verified 2026-07-20).

## Column meanings (only the non-obvious ones)
- **`type`** — vertical level, NOT a soft-delete flag. `0` = parent vertical (broad industry), `1` = sub-vertical
  (specific; this is the one used for scoring/filtering). Every advertiser has exactly one row of each. **Filter
  `type=1`** for the primary vertical used by RTC/Fangorn. (Verified domain 2026-07-20: only values 0 and 1 exist.)
- **`vertical_id`** — the vertical category id (6-digit, e.g. parent `116` "Gifts", sub `116001` "Gifts & Specialty
  Stores"). The `type=1` `vertical_id` **matches** the `score.types[].id` (RTC vertical) in the audience expression
  and the `category_ids` leaf in live DS13/DS46 prospecting config (see data_knowledge). This is the join anchor to
  scoring, not just a label.
- **`vertical_name`** — denormalized name for `vertical_id`; never NULL (verified 2026-07-20).
- **`advertiser_name`** — **UNRELIABLE, do not use.** Denormalized, effectively write-once. 21,052 of 57,772 rows
  (~36%) are empty string (verified 2026-07-20) — an empty-name insert regression that began 2025-12-23 (see
  Gotchas). Even populated values go stale vs the advertiser's current name. Always join to
  `advertisers.company_name` for the current name.
- **`created_time`** — native TIMESTAMP (UTC), row insert time. Range 2024-01-09 → present (verified 2026-07-20).
- **`updated_time`** — native TIMESTAMP (UTC). **Never NULL** — it defaults to `created_time` on insert and is only
  advanced on a genuine update. Only 107 of 57,772 rows have `updated_time > created_time` (verified 2026-07-20), so
  the field is a poor freshness signal: 99.8% of rows have never been genuinely updated. (Reconciles legacy prose
  that called it "nearly all NULL" — the current bronze table populates it, but the intent — "almost nothing is ever
  updated" — still holds.)
- **`datastream_metadata.source_timestamp`** — CDC-capture epoch in **MILLISECONDS** (not business time). Anchor:
  `TIMESTAMP_MILLIS(source_timestamp)` ≈ 2026-07-20 08:14 UTC matches same-day `created_time` (verified 2026-07-20).
  `datastream_metadata.uuid` = per-change CDC row uuid.
- **`id`** — surrogate PK / cluster key. No business meaning beyond row identity.

## Joins & relationships
- **`advertiser_id` → `advertisers.advertiser_id`** (partner grain: 1 row per advertiser_id, PK). This table is the
  **N side** (2 rows per advertiser). Filtering `type=1` first makes the join effectively **1:1** — no fan-out. Join
  WITHOUT a `type` filter DOUBLES advertiser rows (fan-out ×2). Always join to `advertisers.company_name` (never this
  table's `advertiser_name`) for the current name. ~49 `advertiser_id`s are orphans not present in `advertisers`
  (pre-existing upstream source issue, prose oracle — not re-verified live).
- **`type=1` `vertical_id` → RTC / Fangorn scoring** — matches the campaign's `score_type:rtc` id and the DS13/DS46
  `category_ids` vertical leaf in live prospecting expressions (data_knowledge §Fangorn config grid). Use this table
  as the authoritative vertical, not `advertisers.advertiser_vertical_id` (often NULL).
- **Bucket shortcut:** for vertical→bucket mappings, prefer `tpa.dim_vertical` (coredb, PK `vertical_id`, pre-joined
  with `bucket_id`/`bucket_name`) instead of self-joining `type=0`+`type=1` here.
- **`silver.fpa.advertiser_verticals`** is a thin VIEW over this bronze table (parity confirmed TI-737).

## Gotchas
- **`advertiser_name` is unreliable** — ~36% empty (regression since 2025-12-23; 79–82% of *new* advertisers inserted
  with empty string), and populated values go stale when customers rename. Join `advertisers.company_name` instead.
- **`type` is a level, not a delete flag** — 0=parent, 1=sub-vertical. Forgetting a `type=1` filter fans advertiser
  joins out ×2 and mixes parent+sub verticals into the same result.
- **No `deleted` / `is_test` columns** on this table (unlike most integrationprod dims) — the standard
  `deleted=FALSE AND is_test=FALSE` live-row filter does NOT apply here; there is no soft-delete to filter.
- **`updated_time` is not a freshness signal** — defaults to `created_time`, so `WHERE updated_time > X` mostly
  returns nothing (only 107 rows ever genuinely updated). Use `created_time` for recency.
- **`source_timestamp` is milliseconds** — a common wrong assumption is microseconds; `TIMESTAMP_MICROS` would place
  it ~55,000 AD. Use `TIMESTAMP_MILLIS`.
- **Orphan advertiser_ids** (~49) won't match `advertisers` — use LEFT JOIN if you need every vertical row.

## Cost & partitioning notes
- **No partition** (confirmed physical BASE TABLE: `timePartitioning=None`, `rangePartitioning=None`), clustered by
  `id` only. There is no partition column to filter, and none is needed — the whole table is tiny.
- **The one lever is column projection, not row pruning.** Dry-run figures (verified 2026-07-20):
  - `SELECT *` (all 9 columns): **7,310,285 bytes (~7.0 MB)** — full table (no pruning possible).
  - `SELECT advertiser_id, vertical_id, type WHERE type=1`: **1,386,528 bytes (~1.32 MB)** — the ~81% saving is
    entirely from projecting 3 columns; the `WHERE type=1` prunes 0 bytes (unpartitioned, and `type` is not a cluster
    key). Only same-column-set figures are comparable.
- Clustering on `id` only helps point lookups by `id`; it does not accelerate `advertiser_id` / `type` scans.

## Example queries
```sql
-- Authoritative current vertical per advertiser (type=1), with the CURRENT name.
SELECT v.advertiser_id, a.company_name, v.vertical_id, v.vertical_name
FROM `dw-main-bronze.integrationprod.fpa_advertiser_verticals` v
JOIN `dw-main-bronze.integrationprod.advertisers` a
  ON a.advertiser_id = v.advertiser_id
WHERE v.type = 1;   -- omit type filter and advertiser rows fan out ×2
```
