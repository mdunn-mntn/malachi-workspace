# integrationprod.core_creative_sizes

## Purpose
Static reference enum that maps `creative_size_id` → ad dimensions (`width` × `height`), a human `description`,
and the surface flags `video` / `web` / `mobile` / `ctv`. Reach for it to decode
`creatives.creative_size_id` (and `core_creatives.creative_size_id`) into a readable size / format and to
tell whether a creative is video vs display and CTV-eligible. **29 rows, effectively constant.** Exposed as
the `silver.core.creative_sizes` VIEW (a plain `SELECT *` over this table).

## Grain & keys
- **Grain:** one row per creative size. Static enum, 29 rows (full dump 2026-07-29).
- **Primary key:** `creative_size_id` (INT64). Unique, sole cluster key. **Sparse, non-contiguous ids** — a
  mix of small ints (1,2,8,20,24,39,40,44,…) and large power-of-two-like legacy codes
  (16384, 24576, 32768, 34048, 49152, 65536, 98304, 131072, 524288). Never assume a range.
- **Join column:** `creative_size_id` — FK target for `creatives.creative_size_id` /
  `core_creatives.creative_size_id`. Always the **1-side**; used as a decode lookup it cannot fan out.

## Column meanings (only the non-obvious ones)
- **`width` / `height`** — pixel dimensions. Note `description` sometimes reads `WxH` in the OTHER order
  than width/height (e.g. id 39 "Vertical HD Video" is width=1080, height=1920; id 93 "HD Video" is
  width=1920, height=1080) — trust the numeric columns, not the label's digit order.
- **`video`** (BOOL) — TRUE only for the video sizes. Live video rows (2026-07-29): **39** Vertical HD Video
  (1080×1920), **80** 640×360 Landscape Video, **93** HD Video (1920×1080). All other 26 sizes are display.
- **`ctv`** (BOOL) — TRUE only for **39 and 93** (both also `video=true`). Size 80 is `video=true` but
  `ctv=false` (a non-CTV landscape video). So CTV-eligible ⊂ video, not equal.
- **`web` / `mobile`** — surface-eligibility flags (a size can be both, either, or neither — e.g. the
  "Onsite Offer" and interstitial sizes are web-only or neither).
- **`approve`** (BOOL) — **TRUE for all 29 rows** — currently non-discriminating.
- **`description`** — free-text label; some are named ("Medium Rectangle", "Leaderboard", "Facebook Ad"),
  others are just the raw `WxH` string ("1800x1000", "720x480").
- **`datastream_metadata`** — Datastream CDC lineage RECORD (`uuid`, `source_timestamp`); not business data.

## Joins & relationships
- **`creatives.creative_size_id` → `core_creative_sizes.creative_size_id`** — **N:1** (creatives is the
  many-side). Same for `core_creatives`. Broadcast/lookup join; never fans out (1 row per id).
- **`silver.core.creative_sizes`** is a VIEW = `SELECT *` over this table (verified present 2026-07-29).
  Content-identical; use whichever project you are already in.

## Gotchas
- **Sparse, non-contiguous ids** including large legacy bitmask-style codes (524288 etc.) — decode on the
  literal id, never generate a numeric range.
- **`description` digit order ≠ width/height order** for the vertical video size (id 39) — use the numeric
  `width`/`height` columns for orientation, not the label.
- **`approve` is all TRUE** — do not treat it as a live/eligible filter; it discriminates nothing here.
- **No `deleted` / `is_test` columns** — the standard soft-delete dim filter does not apply; read all rows.

## Cost & partitioning notes
- **Non-partitioned static enum: 29 rows / ~2.6 KB.** No partition, no TTL, no `require_partition_filter`.
  Clustered on `creative_size_id` (no-op at this size). Full `SELECT *` bills the tier-1 10 MB minimum
  (~0 real bytes). Broadcast-join it freely.

## Example queries
```sql
-- Decode creative sizes (N:1 lookup; never fans out)
SELECT c.creative_id, c.creative_size_id, s.description, s.width, s.height, s.video, s.ctv
FROM `dw-main-bronze.integrationprod.creatives` c
LEFT JOIN `dw-main-bronze.integrationprod.core_creative_sizes` s USING (creative_size_id);

-- CTV-eligible sizes only
SELECT creative_size_id, description, width, height
FROM `dw-main-bronze.integrationprod.core_creative_sizes`
WHERE ctv = TRUE;
```
