# integrationprod.integrations_sync_targets

## Purpose
Postgres CDC mirror (via Datastream) of the integrations sync-target registry: each row is one **external destination** that an advertiser's installed integration connection syncs an audience/segment to. 96% are HubSpot lists (`hubspot:list/N`); the rest are Upwave audiences, MNTN audiences, and QA/automation test targets. Reach for it to answer "which HubSpot lists (or other external audiences) is this advertiser's integration wired to sync into?" and to trace an audience-export/CRM-sync destination back to the connection and integration type. Small config dim (2,987 rows) — not an event log.

## Grain & keys
- **Grain:** one row per (advertiser-integration connection x external sync target). A single connection fans out to many targets (137 connections carry 2,987 rows, ~22 avg; max in the hundreds for large HubSpot accounts).
- **Primary key:** `id` (Postgres row id; 2,987 distinct = unique).
- **Natural key:** `(connection_id, target_key)` — unique among **live** rows only (`t_deleted_ns IS NULL`). Soft-deleted history repeats the same pair up to 7 times (create → delete → re-create lifecycle); 165 pairs have >1 version but 0 live pairs are duplicated.
- **Join columns:** `connection_id` (FK, see Joins).

## Column meanings (only the non-obvious ones)
- **connection_id** — FK to `integrations_advertiser_integrations.id` (the per-advertiser *installed connection instance*), all 137 distinct values match, 0 orphans. **Naming trap:** it does *not* map to `integrations_integrations` (the type catalog), and it does *not* map to the like-named `connection_id` column that also exists inside `integrations_advertiser_integrations` — it maps to that table's `id`.
- **target_key** — the external system's identifier for the sync destination, format `<provider>:<resource>/<external_id>`. Distribution: `hubspot:list/N` = 2,854 rows / 104 conns (96%), `upwave:*` = 18, `mntn:*` = 8; the long tail is bare UUIDs, `test_aud_creation*`, `codex-prod-*`, `demo-*` — QA/automation audience-creation rows where the key is the raw external id with no `provider:` prefix.
- **synchronization** — JSON sync-state blob, `null` (JSON null) for most rows. When populated it holds `{"name": <display name>, "t_creation_journaled_ns": <ns>, "t_deletion_journaled_ns": <ns>}` — the target's display name plus journaled nanosecond lifecycle timestamps recorded by the sync engine (distinct from the row's own `t_*_ns` CDC timestamps).
- **t_created_ns / t_updated_ns / t_deleted_ns** — UNIX **nanoseconds** (confirmed: `TIMESTAMP_MICROS(t_created_ns/1000)` = valid 2026 business time; MAX = 2026-07-16). `t_deleted_ns IS NOT NULL` = soft-deleted (340 of 2,987 rows). There is **no** `deleted`/`is_test` boolean on this table — soft-delete lives entirely in `t_deleted_ns`.
- **datastream_metadata.source_timestamp** — CDC change-capture time in **milliseconds** (confirmed: `TIMESTAMP_MILLIS(...)` = valid time, matches row create time), NOT business time — it's when Datastream captured the change. `datastream_metadata.uuid` = the Datastream change event id (shared across a batch, so not row-unique).

## Joins & relationships
- **connection_id -> `integrations_advertiser_integrations.id`** (N:1, this table is the child). Safe direction child->parent (each target has exactly one connection). Parent->child fan-out: one connection expands to many targets (~22 avg, hundreds for big HubSpot accounts) — dedup/aggregate before joining upward if counting connections.
- From the parent you reach the integration type and advertiser:
  - `integrations_advertiser_integrations.integration_id -> integrations_integrations.id` (1:1 lookup) — the integration-type catalog (name = hubspot/tealium/upwave/..., carries `data_source_id`).
  - `integrations_advertiser_integrations.advertiser_id -> advertisers.id` (N:1) — which advertiser owns the connection.
- Do not join `connection_id` to `integrations_integrations.id` — verified 0 matches (that table is the type catalog, not connection instances).

## Gotchas
- **No `deleted`/`is_test` columns** (unlike most integrationprod dims). Use `t_deleted_ns IS NULL` for live rows; the dataset-wide `deleted=FALSE AND is_test=FALSE` filter does not apply here.
- **connection_id naming trap** — maps to `integrations_advertiser_integrations.id`, not to `integrations_integrations` and not to that table's own `connection_id` column.
- **target_key repeats across soft-delete lifecycle** — `(connection_id, target_key)` is unique only among live rows; 165 pairs have up to 7 historical versions. Filter to `t_deleted_ns IS NULL` before treating it as a key.
- **Test/automation noise** — a meaningful share of rows are `test_aud_creation*`, `codex-prod-*`, `demo-*`, and bare-UUID targets from QA/audience-creation automation. Filter to `target_key LIKE 'hubspot:%'` (or the provider you care about) for real integration analysis.
- **Two epoch conventions in one table** — `t_*_ns` are nanoseconds; `datastream_metadata.source_timestamp` is milliseconds; the `t_*_journaled_ns` inside the `synchronization` JSON are nanoseconds.
- **datastream_metadata.source_timestamp is capture time, not business time** — for when a target was actually created/updated use `t_created_ns` / `t_updated_ns`.

## Cost & partitioning notes
- **BASE TABLE, unpartitioned** (physical = self; `numRows` 2,987 / `numBytes` 300,668 confirmed via `bq show`). No partition filter is required or possible — it's a tiny config dim; there is no partition column to filter on.
- Labeled dry-run figures (2026-07-19, same-table): `SELECT *` = 300,668 B (~294 KB, equals full physical bytes); `SELECT id` = 23,896 B; `SELECT synchronization` = 6,785 B. Column pruning still helps proportionally, but total cost is negligible.
- Cluster key `[id]` is cosmetic at this size; no scan concern. Prefer selecting only `id, connection_id, target_key` (and parse `synchronization` only when you need the display name) rather than `SELECT *`.

## Example queries
```sql
-- Live HubSpot list targets per advertiser + integration type
SELECT
  a.advertiser_id,
  ii.name        AS integration_type,
  s.connection_id,
  s.target_key,
  JSON_VALUE(s.synchronization, '$.name') AS target_name
FROM `dw-main-bronze.integrationprod.integrations_sync_targets` s
JOIN `dw-main-bronze.integrationprod.integrations_advertiser_integrations` a
  ON s.connection_id = a.id
JOIN `dw-main-bronze.integrationprod.integrations_integrations` ii
  ON a.integration_id = ii.id
WHERE s.t_deleted_ns IS NULL          -- live only (no deleted/is_test flags on this table)
  AND s.target_key LIKE 'hubspot:%'   -- drop test/automation noise
LIMIT 100;
```
