# integrationprod.campaign_groups

## Purpose
Canonical coredb (Postgres, via Datastream CDC) dimension for **campaign groups** — the budget-allocation / flight-container unit that sits **above** `campaigns` (the actual bidding line items) and **below** `advertisers`. This is where the **product line** (`product_id`: PTV / Select / QuickFrame), the **campaign objective** (`objective_id`), the **group lifecycle status**, and the nominal **budget/goal** are stamped. Reach for it whenever you need to slice campaigns by product (e.g. MNTN Select), filter to prospecting vs retargeting groups, or resolve a `campaign_group_id` seen in logs/`*_alt_id` remaps back to an advertiser and a name.

This is the SQLMesh-derived **analytical** variant (cleaner column set with `_raw` companions). Three sibling BQ replicas exist of the same coredb source — use `public_campaign_groups_raw` for CDC/incremental pipelines (has `datastream_metadata`, `max_staleness=15min`), `public_campaign_groups` for the SQLMesh view over raw, and `campaign_groups_raw` as internal staging. All four agree on `product_id` for shared rows (zero per-row disagreement, verified 2026-05-05); the analytical variant carries **slightly fewer rows** than the CDC raw due to SQLMesh filters, so they are not row-identical. Despite the "SQLMesh-derived" prose framing, live INFORMATION_SCHEMA shows this object is a **materialized physical `TABLE`** (not a view), so there is no view to resolve and no partition trap.

## Grain & keys
- **Grain:** exactly one row per **`campaign_group_id`** — 129,367 rows = 129,367 distinct ids, zero NULLs (verified 2026-07-19). No dedup needed.
- **PK:** `campaign_group_id`.
- **FKs:** `advertiser_id` → `advertisers` (N groups : 1 advertiser), `active_flight_id` → `core_flights`, `product_id` → `core_products`, `objective_id` → `core_objectives`, `budget_type_id` → `core_budget_types`, `goal_type_id` → goal-type lookup, `parent_campaign_group_id` → self (nesting).
- **Live filter:** `WHERE deleted = FALSE AND is_test = FALSE` → 107,203 live rows. Non-live rows: `deleted=TRUE` (1,993), `deleted IS NULL` (2,647 — `deleted` is nullable, so `deleted=FALSE` silently drops these too), `is_test=TRUE` (17,565; `is_test` has zero NULLs). **Do not** confuse this filter with the business status `campaign_group_status = 'DELETED'` (see Gotchas).

## Column meanings (only the non-obvious ones)
All `*_time` columns are true `TIMESTAMP` (no INT epoch on this table; `time_unit: timestamp`). This analytical variant has **no `datastream_metadata`** column — use `public_campaign_groups_raw` if you need `source_timestamp` for CDC-incremental reads.

- **`product_id`** — the MNTN product line, **immutable** and set at creation by the UI. Live domain: `1`=PTV (106,738 live), `2`=Select (465 live); `3`=QuickFrame is defined in `core_products` but has **no** live groups. **This is the only place the product line is stamped — it is NOT on `campaigns`.** Select groups first appeared 2025-07-31; any pre-that analysis returns zero Select rows. Canonical Select filter: `product_id = 2 AND deleted = FALSE AND is_test = FALSE`.
- **`objective_id`** — the group's campaign **objective** (join `core_objectives`). Live distribution + names: `1`=Prospecting (65,493), `5`=Multi-Touch (21,690), `4`=Retargeting (19,095), `3`=Prospecting (925 — a second, mostly-legacy prospecting id); `core_objectives` also defines `2`=Onsite, `6`=Multi-Touch Full Funnel, `7`=Ego, but those three have **zero live groups** here. **This is NOT the funnel stage** — `campaign_groups` has no `funnel_level` column; funnel stage (S1/S2/S3) lives on `campaigns.funnel_level`, which is authoritative for stage. **Prospecting groups = the workspace-canonical `objective_id IN (1,5,6)`** (matches CLAUDE.md and `data_knowledge.md`; note `6` has no live groups so it resolves to `1,5` in practice). A second id `3` is also named "Prospecting" in `core_objectives` (925 live groups) but is **excluded** by the canonical filter — add it only deliberately, and expect a ~925-group divergence against any other workspace analysis if you do.
- **`campaign_group_status_id` / `campaign_group_status`** — group lifecycle status (id + denormalized name). The **id↔name pairing is loosely coupled / drifted** (the same problem flagged for `goal_type` below) — do NOT treat it as 1:1. Clean pairings (live rows): `1`=NOT_LIVE (26,293), `5`=SH_PAUSED (8,093), `8`=DELETED (34,573), `9`=LEGACY_ARCHIVED (12,753). **Split ids:** `3` → mostly ENDED (11,910), then LIVE (3,418), SCHEDULED (56), NULL (11) = 15,395 total; `4` → mostly PAUSED (6,977), then ENDED (3,119). Distinct live status **names**: DELETED, NOT_LIVE, LEGACY_ARCHIVED, ENDED, SH_PAUSED, PAUSED, LIVE, SCHEDULED. **Filter on the string `campaign_group_status`, never on `campaign_group_status_id`, when you want a business status** — `campaign_group_status_id=3` returns 15,395 rows that are ~77% ENDED and only 3,418 actually LIVE, and a name-whitelist that omits `PAUSED` silently drops ~6,977 live groups. **`campaign_group_status='DELETED'` is a business status, NOT the `deleted` soft-delete flag** — 34,573 rows carry status DELETED while surviving the live filter (`deleted=FALSE AND is_test=FALSE`).
- **`client_launch_status`** — a **separate** STRING launch state, distinct from `campaign_group_status`. Domain (live rows): NOT_LIVE (57,716), LIVE (29,122), PAUSED_OR_ISSUE (20,307), NULL (58). Its `LIVE` count (29,122) differs from `campaign_group_status='LIVE'` (**3,418**) — the two are different concepts; do not treat them as synonyms. (Do not confuse the 3,418 `campaign_group_status='LIVE'` rows with the 15,395 rows where `campaign_group_status_id=3`, which are mostly ENDED — see above.)
- **`deleted` / `is_test`** — CDC soft-delete + test-campaign flags. Always filter both `FALSE` for live analysis.
- **`update_time`** — computed = `GREATEST(ui_flights.update_time, campaign_groups_raw.update_time)`; propagates child-flight edits (start/end shifts, budget/status flips) up to the group row (verified via Postgres view def, Victor Savitskiy 2026-06-03; 98.8% follow GREATEST across 17,499 cgs/90d; status transitions always bump it). **Use `update_time` for any "was this modified?" check.**
- **`update_time_raw`** — the group row's own update_time only (excludes flight edits). Use only when you specifically want direct cg-level changes.
- **`budget` / `budget_type_id` / `active_flight_id`** — these three **co-NULL** (68,047 live rows) when the group has no active flight — budget lives on the flight, not the group. `budget` is the **nominal** amount and can be far above the effective DSO flight budget (observed: nominal $20,455 → DSO flight $7,747). `active_flight_id` is **stale** — use `core_flights` (keyed by `campaign_group_id`) for the real flight timeline/budget.
- **`goal_type_id` / `goal_type_name` / `goal_value`** — the group's optimization goal. Dominant id→name map: `13`=CostPerVisit, `14`=CostPerCompletedView, `1`=ROAS, `16`=CPA; `goal_value` = the target. The id↔name pairing is **loosely coupled** — legacy rows show drift (e.g. id `9` and `3` map to several/NULL names); trust `goal_type_name` as the label but expect noise on rare ids.
- **`parent_campaign_group_id`** — nesting pointer; populated on ~21,667 live rows (~20%), never self-referential (0 self-parents). Fangorn/audience bridge joins must match on `campaign_group_id` **OR** `parent_campaign_group_id`.
- **`first_launch_time`** — first time the group launched; NULL for never-launched groups (55,281 live).
- **`name`** — free-text, carries strategic intent (query it to read campaign strategy) but is **polluted with junk**: `test - *`, `* Copy 0X`, `archived`, `paused`. Filter accordingly.
- **`has_audience` / `has_audience_raw`** — audience-attached flag (enriched vs raw). **`ctv_creatives_status_id` / `display_creatives_status_id` / `ui_creatives_status_id`** (+ `_raw`) = per-channel creative-approval status. **`testing_type`** — A/B test type: mostly NULL (104,605), else NONE/AB/MULTIVARIATE/PSA_CONTROL. **`delivery_mode_id`** {2 default, 1, 3}, **`platform_id`** {1 dominant, 2}, `budget_lock`/`restricted_edits`/`config_override_id`/`cgid_link_id`/`campaign_goal_id` are edit-control / config pointers.

## Joins & relationships
- **`campaigns.campaign_group_id` → this** — **1 group : N campaigns** (fan-out). Campaigns are the actual bidding line items; `product_id`/`objective_id` sit on the group, `funnel_level` (stage) on the campaign. Join down to campaigns for stage/bidding analysis.
- **`advertisers.advertiser_id` ← `advertiser_id`** — **1 advertiser : N groups** (~5.5 live groups/advertiser; 19,635 distinct advertisers). Fan-out risk when going advertiser→group; dedup or aggregate.
- **`core_flights.campaign_group_id` = `campaign_group_id`** — **1 group : N flights** (full flight history; heavy fan-out — e.g. Kindred High Pop = 114 flights). Use `core_flights` for the flight timeline/budget, **not** `active_flight_id` (stale) or `dso_campaign_group_flight_budgets` (current-only).
- **`core_products` / `core_objectives` / `core_budget_types`** — **1:1 lookups** on `product_id` / `objective_id` / `budget_type_id` (the latter often NULL). No fan-out.
- **`audience_audience_x_campaign_groups.campaign_group_id`** — bridge to `audience_audiences`→`audience_audience_segments`→`audience_segments` (the audience→segment→DS graph; Fangorn DS46 detection). Match on `campaign_group_id` **OR** `parent_campaign_group_id`.
- **`archives_campaign_group_archives`** — version history, **1 group : N versions** (~7/90d). Use `MAX(version)`/`MAX(update_time)` for as-of state.
- **Downstream `*_alt_id` remaps:** logs remap `campaign_group_id` — e.g. `win_logs.campaign_alt_id` = campaign_group_id (and `line_item_alt_id` = campaign_id). Resolve alt-ids back through this dim.

## Gotchas
- **`campaign_group_status_id` is NOT a 1:1 map to `campaign_group_status`.** id `3` is mostly ENDED (11,910) — only 3,418 of its 15,395 rows are actually LIVE; id `4` is mostly PAUSED (6,977), not ENDED. **Filter the string name, not the id, for a business status.** (See Column meanings for the full drift table.)
- **`campaign_group_status='DELETED'` (status_id 8) ≠ the `deleted` boolean.** 34,573 rows survive the full live filter (`deleted=FALSE AND is_test=FALSE`) while carrying status DELETED (44,761 under `deleted=FALSE` alone). Always filter `deleted=FALSE AND is_test=FALSE` for live rows; don't rely on the status string.
- **`product_id` only on the group, never on `campaigns`** — always filter product at group level and join down. It is immutable (verified: zero changes across 735K archive versions). Don't use `camperbid_mmm_training_data.is_select_cid` as source of truth — use `product_id=2`.
- **`objective_id` is NOT the funnel stage.** No `funnel_level` column here; stage is on `campaigns.funnel_level`. `objective_id` unreliability warnings elsewhere are about stage, not the objective itself.
- **`budget`/`active_flight_id` are group-level and often stale/NULL.** Budget lives on flights; nominal `budget` ≠ effective DSO flight budget. Pull flight history from `core_flights`.
- **Four BQ variants of this table** (`campaign_groups`, `campaign_groups_raw`, `public_campaign_groups`, `public_campaign_groups_raw`) — this is the analytical one, **no `datastream_metadata`**. Use `public_campaign_groups_raw` for CDC/incremental.
- **`name` is full of test/archived junk** — filter `test - *`, `* Copy 0X`, `archived`, `paused` when mining names for strategy.
- **Select (`product_id=2`) starts 2025-07-31** — zero rows before that date.

## Cost & partitioning notes
- Small dimension: `TABLE`, no partition, no clustering, no TTL. `approx_logical_bytes` = 30,855,939 (`bq show` numBytes = full-table `SELECT *` dry-run, both 30,855,939 B ≈ 0.029 GB, 2026-07-19). There is nothing to prune — the "one filter to always apply" is a **correctness** filter (`deleted=FALSE AND is_test=FALSE`), not a cost filter.
- Column-set-labeled dry/observed figures (2026-07-19): full-table `SELECT *` = 0.029 GB; a 6-column boolean/count aggregate = 0.001 GB billed 0.01 GB (tier-1 floor); a ~3-column DISTINCT aggregate = 0.004–0.006 GB. All well under any concern threshold — SELECT * is cheap here, but still prefer explicit columns.

## Example queries
```sql
-- Live MNTN Select groups (product line lives ONLY on the group)
SELECT campaign_group_id, advertiser_id, name, campaign_group_status
FROM `dw-main-bronze.integrationprod.campaign_groups`
WHERE product_id = 2 AND deleted = FALSE AND is_test = FALSE;

-- Live prospecting groups for an advertiser, with objective + status names
SELECT cg.campaign_group_id, cg.name, o.name AS objective, cg.campaign_group_status
FROM `dw-main-bronze.integrationprod.campaign_groups` cg
LEFT JOIN `dw-main-bronze.integrationprod.core_objectives` o USING (objective_id)
WHERE cg.deleted = FALSE AND cg.is_test = FALSE
  AND cg.objective_id IN (1,5,6)        -- canonical prospecting set (id 3 = 2nd 'Prospecting', excluded by convention)
  AND cg.advertiser_id = <advertiser_id>;
```
