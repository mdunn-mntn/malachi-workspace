# integrationprod.keyword_categories

## Purpose
The keyword-string + hierarchy dimension for **data source 38 = "MNTN UI Audience Keywords"** (verified against `data_sources`: `data_source_id=38`, `name='MNTN UI Audience Keywords'`, `visible=false` → internal). **100% of rows are DS38** — no other `data_source_id` is present. Reach for it to resolve a `data_source_category_id` → its human-readable keyword string (`name`) and its category breadcrumb (`path`, `names`, `path_from_root`), and to walk the keyword → parent-category hierarchy that backs the MNTN UI audience-keyword picker. It is the DS38 analogue of `categories` (which holds DS13/DS16/etc.), split out into its own table because of its size (~6.8M ids).

## Grain & keys
- **Grain:** one row per **(data_source_category_id, parent_id) taxonomy edge**. `COUNT(DISTINCT (data_source_category_id, parent_id)) = 61,492,744 = total rows` (verified) → this pair is the unique key.
- **`data_source_category_id` alone is NOT unique** — 6,812,809 distinct ids across 61.5M rows (~9 edges per id). The taxonomy is a **DAG, not a tree**: one keyword id hangs under many parent categories. Any join keyed on `data_source_category_id` alone fans out ~9x — dedup first.
- **Key / join columns:** `data_source_category_id` (the keyword id; joins outward), `parent_id` (self-referential to `data_source_category_id`), `data_source_id` (constant 38).

## Column meanings (only the non-obvious ones)
- **data_source_id** — always `38` (MNTN UI Audience Keywords). A constant, not a filter dimension; no other value exists in the table.
- **data_source_category_id** — the keyword/category id. This is the id that joins outward (e.g. into DS38 arrays in `external.ipdsc__v1`). **Not unique per row** (see Grain).
- **parent_id** — id of the parent node (self-reference to `data_source_category_id`). `NULL` = top-level node hanging directly off the implicit `ROOT` (id `0`); 1,343,220 rows are NULL. `path_from_root` always begins with `0` (ROOT), which is *not* a physical row.
- **partner_id** — **100% NULL** in the live table; unused.
- **advertiser_id** — **100% NULL**; this taxonomy is global, not per-advertiser (do not expect advertiser scoping here).
- **name** / **description** — the keyword string; `description` mirrors `name` (duplicative). Only **157,460 distinct `name` values** across 61.5M rows — the same string maps to many ids and many edges.
- **path** — human breadcrumb: `"Category > Keyword"` for a leaf, or just the node's own name for a top-level node.
- **names** — JSON string `{"names": ["ROOT", <parent name>, <leaf name>]}` — the name chain from ROOT to this node. Stored as text; `JSON_EXTRACT`/`PARSE_JSON` to use.
- **path_from_root** — JSON string `{"pathFromRoot": [0, <parent_id>, <id>]}` — the id chain from ROOT (`0`) to this node.
- **is_leaf_node** — `true` = terminal keyword (60,170,243 rows); `false` = intermediate/parent category node (~1.32M).
- **navigation_only**, **deprecated**, **public** — all **100% `false`** in the live table; no filtering value.
- **sort_order** — NULL in all sampled rows.
- **created_date** / **updated_date** — `DATE`. **NOT per-row provenance** — every one of the 61.5M rows shows the *same* value = the snapshot/reload date (all `2026-07-20` on the verify run). The table is fully truncate-and-reloaded, so these track the CDC snapshot day, not when a keyword was actually created or changed. Do not use them to find "new" keywords.

## Joins & relationships
- **`data_source_id` (=38) → `data_sources.data_source_id`** — many:1 to the DS dimension (here effectively a constant lookup; DS38 = "MNTN UI Audience Keywords", internal). No fan-out.
- **`parent_id` → self.`data_source_category_id`** — hierarchy self-join. DAG, so a child can resolve to a parent that itself has multiple parents; not a clean tree walk.
- **`data_source_category_id` → `external.ipdsc__v1` DS38 category-id arrays** — this table is the *name resolver* for DS38 ids that an IP carries. **1:N from this side** (id not unique) → dedup this table on `data_source_category_id` (e.g. `ANY_VALUE(name)`) before joining or you multiply the ipsdc side ~9x. (ipdsc gotchas — hive `dt` STRING partition, bursty delivery — are in `data_knowledge.md`.)
- **DS38 vs DS19 namespace warning (from `data_knowledge.md`):** DS38 keyword ids live in a **different id namespace than DS19** ("MNTN Matched"). Do NOT cross-map a `data_source_category_id` here to DS19/DS16 category ids — they are not the same space.

## Gotchas
- **Full daily truncate-reload.** `created_date`/`updated_date` are all identical (= today's snapshot). Row count and id membership can shift day to day; there is no history in this table (see `archives_*` if versioned history is ever needed).
- **`data_source_category_id` fans out ~9x.** It is not a primary key — the PK is (id, parent_id). Joins keyed on the bare id must dedup first.
- **No `deleted` / `is_test` columns** (unlike most `integrationprod` dims) — the standard `deleted=FALSE AND is_test=FALSE` live-row filter does NOT apply and would error; the whole table is the live DS38 snapshot.
- **Dead columns:** `partner_id`, `advertiser_id`, `sort_order` are all NULL; `navigation_only`, `deprecated`, `public` are all `false`. Don't design filters around them.
- **Noisy hierarchy.** Leaf keywords frequently sit under unrelated parents (e.g. leaf `"2024 Vehicles For Sale"` under parent `"Wellness"`; `"Web services"` / GTM pollution noted in `data_knowledge.md`). Treat `path`/`names` as descriptive, not an authoritative clean taxonomy.
- **Grown past prose.** `data_catalog.md`/`data_knowledge.md` still say "~40M rows"; the live table is **~63.0M rows** as of 2026-07-29 (was 61.5M on 2026-07-20) — treat 40M as stale, and the exact count as volatile (full daily truncate-reload).

## Cost & partitioning notes
- **No partition, no clustering** (plain BASE TABLE, physical `self`). A WHERE filter does **not** prune — cost is **100% column-driven**. There is no "partition filter to apply"; the one rule is **select only the columns you need, never `SELECT *`**, and don't bother filtering `data_source_id` (constant 38).
- Dry-run figures (labeled by exact column set, all full-scan since unpartitioned):
  - `SELECT *` (all 17 cols): **14,154,977,474 B ≈ 13.2 GiB** (= physical `numBytes`).
  - `data_source_category_id` only (1 INT col): **491,941,952 B ≈ 469 MiB**.
  - `WHERE name = '…'` returning `(id, parent_id)` (touches the `name` STRING col): **2,139,244,597 B ≈ 2.0 GiB** — the STRING columns (`name`/`description`/`path`/`names`/`path_from_root`) dominate cost; pull them only when needed.

## Example queries
```sql
-- Resolve a batch of DS38 keyword ids to their (deduped) keyword string
SELECT data_source_category_id, ANY_VALUE(name) AS keyword
FROM `dw-main-bronze.integrationprod.keyword_categories`
WHERE data_source_category_id IN (8267065, 9671561)
GROUP BY data_source_category_id;

-- Look up ids + parents for a keyword string (STRING scan ~2 GiB)
SELECT data_source_category_id, parent_id, path
FROM `dw-main-bronze.integrationprod.keyword_categories`
WHERE name = 'AG 1';
```
