# integrationprod.core_audiences

## Purpose
Bronze CDC replica of the core **audience definitions** — one row per audience an advertiser has built
for targeting. Each row carries the audience's name, its **type** (`audience_type_id` → First/Third
Party / Control Group / Extension), and a JSON **`expression`** encoding the actual targeting logic
(interest/data-source/age/gender includes and excludes). Reach for it to enumerate an advertiser's
audiences and inspect how each is defined. Exposed as the `silver.core.audiences` view (a plain
`SELECT * FROM` this bronze table).

**Disambiguation — this is NOT `audience.audiences`.** `silver.audience.audiences` is a different view
over `integrationprod.audience_audiences` (a distinct physical table). `core_audiences` (this table,
behind `silver.core.audiences`) and `audience_audiences` are two separate audience tables — confirm which
one a query needs before joining.

## Grain & keys
- **Grain:** one row per audience definition (verified: 79,874 rows = 79,874 distinct `audience_id`,
  2026-07-29 — `audience_id` is unique).
- **Primary key:** `audience_id` (INT64, unique; the sole cluster key).
- **Foreign keys:** `advertiser_id` → `advertisers`; `audience_type_id` → `core_audience_types`;
  `geo_segment_id` → geo segment dim; `opportunity_id` → sales opportunity; `user_id` → creating user;
  `external_audience_id` (STRING) → the external/DSP audience id (79,769 distinct — a few dups/NULLs, not
  strictly unique).
- **Has `is_test` but NO `deleted` column** — the usual `deleted=FALSE AND is_test=FALSE` live filter is
  only **half** applicable here: filter `is_test = FALSE`, but there is no `deleted` column to add.

## Column meanings (only the non-obvious ones)
- **`audience_id`** — PK / cluster key. Unique across the table; the canonical join key.
- **`audience_type_id`** — FK to `core_audience_types` ({1 First Party, 2 Third Party, 3 Control Group,
  4 Extension}). In the sample, most rows are type 2 (Third Party).
- **`external_audience_id`** — **STRING** id of the audience in the external/DSP system; near-unique but
  not strictly 1:1 with `audience_id` (79,769 distinct vs 79,874 rows). Do not assume uniqueness.
- **`expression`** — **JSON string** encoding the targeting definition (observed keys: `interest`
  {`include`/`exclude` with `data_source_id`/`cats`}, `age`, `gender`). This is the audience's actual
  targeting logic; parse as JSON, not free text. Can be large — exclude it from wide scans you don't need.
- **`geo_segment_id`** — FK to a geo segment (NULL when the audience is not geo-scoped).
- **`opportunity_id`** — FK to the originating sales opportunity (present on most rows in the sample).
- **`segment_type_id` / `segmentation_default_id`** — segment classification FKs (by name/values;
  confirm target dims before relying on their semantics). `segment_type_id` was 2 across the sample.
- **`auto_append`** — BOOL; whether the audience auto-appends (e.g. new matching members added
  automatically). All sampled rows `false`.
- **`is_test`** — BOOL test-row flag; filter `is_test = FALSE` for real audiences.
- **`create_time` / `update_time`** — TIMESTAMPs of audience creation / last edit in source Postgres
  (business timestamps here, unlike the enum dims).
- **`datastream_metadata`** — Datastream CDC lineage RECORD (`uuid`, `source_timestamp`).
  `source_timestamp` is a **millisecond** epoch (CDC-capture time), NOT business time — verified:
  `TIMESTAMP_MILLIS(source_timestamp)` gives a 2025 snapshot datetime while `create_time` is the real
  audience creation time.

## Joins & relationships
- **`core_audiences.audience_type_id` → `core_audience_types.audience_type_id`** — **N:1** decode (no
  fan-out; that dim is the 1-side).
- **`core_audiences.advertiser_id` → `advertisers.advertiser_id`** — **N:1** (many audiences per
  advertiser). Joining audiences to the advertiser dim fans out to audience cardinality — aggregate first.
- **`silver.core.audiences`** is a VIEW = `SELECT * FROM dw-main-bronze.integrationprod.core_audiences`
  (verified 2026-07-29). Content-identical.
- **Not `audience.audiences`.** See the Disambiguation note in Purpose — `silver.audience.audiences`
  resolves to `integrationprod.audience_audiences`, a different physical table.

## Gotchas
- **Two different "audiences" tables.** `core_audiences` (this, silver.core.audiences) vs
  `audience_audiences` (silver.audience.audiences) are distinct physical tables — a wrong pick silently
  returns a different row set. Confirm which one upstream queries use.
- **No `deleted` column** — only `is_test`. Do not write `deleted = FALSE` against this table (it will
  error); filter `is_test = FALSE` and treat every non-test row as present.
- **`expression` is JSON and can be wide** — the table is ~41 MB largely because of it. Don't `SELECT *`
  when you only need ids/name; parse `expression` with JSON functions when you do need targeting logic.
- **`external_audience_id` is a STRING and not strictly unique** — do not use it as a PK.
- **`datastream_metadata.source_timestamp` is ms CDC-capture time, not business time** — use
  `create_time`/`update_time` for audience timing.

## Cost & partitioning notes
- **BASE TABLE, physical `self`** (the silver `core.audiences` view reads it directly). `bq show`:
  `type=TABLE`, `numRows=79874`, `numBytes≈40.9 MB`, `timePartitioning=None`,
  `clustering.fields=[audience_id]`, no `expirationTime` (no TTL).
- **Partition: none** (`require_partition_filter=false`). Clustered on `audience_id` — helps point
  lookups by audience id. A full scan is ~41 MB; the `expression` column dominates the bytes, so
  projecting away `expression` cuts cost materially.
- Prefer selecting the ids/name/type you need over `SELECT *` on this (moderately wide) table.

## Example queries
```sql
-- an advertiser's non-test audiences with decoded type (no deleted col here)
SELECT a.audience_id, a.name, a.audience_type_id, t.name AS audience_type, a.create_time
FROM `dw-main-silver.core.audiences` a
LEFT JOIN `dw-main-bronze.integrationprod.core_audience_types` t USING (audience_type_id)
WHERE a.advertiser_id = 33613 AND a.is_test = FALSE
LIMIT 100;

-- inspect the JSON targeting expression for one audience
SELECT audience_id, name, expression
FROM `dw-main-bronze.integrationprod.core_audiences`
WHERE audience_id = 80297;
```
