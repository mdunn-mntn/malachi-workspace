# Ticket-Context — 5 → 90 Scale Plan

> Companion to `ticket_context_pilot.md`. The pilot is validated (5/5 cards, eval green, gate
> recalibrated). This plan takes the same pipeline to the remaining 84 cards. **Do not run until
> the human says go.** Same prime directive: minimize tokens a task must load, maximize P(loaded
> context is sufficient). Cards = compression; the retrieval eval = fitness function.

## 1. What the pilot proved (carry forward, don't relitigate)
- Pipeline works end-to-end and is resumable (`resumeFromRunId` cached the eval + unchanged agents across 3 runs).
- The verify gate needed calibration, now fixed in `ticket_context_pilot.js`:
  - Tables-field dataset/project qualifier = normalization, NOT fabrication → non-blocking.
  - Reject only BLOCKING problems: unsupported fact/number/outcome, hedge upgraded to certainty,
    plan reported as done, inflated scope, or a table the summary never names.
- Extractor no longer emits qualified table names (routing qualification lives in the catalog).
- Result of recalibration: yield went 3/5 (stochastic) → **5/5, 0 rejected**.

## 2. Current state (measured 2026-07-23)
- 90 ticket cards total (incl. epic children). **6 carded, 84 remaining.**
- 3 epics (nested children, full structure each): `audi_1089_ddp_vendor_evaluations`,
  `audi_1111_vendor_quality`, `ber_2250_incrementality_overhaul`.
- 2 structural lint violations (missing front-matter, safe to auto-fix during scale):

## 3. Three changes the script needs before scaling (all in `ticket_context_pilot.js`)
1. **Batch input + skip-done.** Accept `args.tickets` (already supported) AND read a coverage
   ledger so a ticket already `carded` is skipped on re-run. Idempotent across batches.
2. **Nested-path handling.** Pilot slugs are flat (`tickets/<slug>/summary.md`). Epic children are
   `tickets/<epic>/<child>/summary.md`. Extract/verify/land must accept a full relative card path,
   not assume flat. Enumerate cards via `find tickets -name summary.md` minus `_template`.
3. **Optional fixer loop (yield insurance).** For a card rejected on a *correctable* discrepancy,
   one `fixer` agent (the agent already exists) edits only the flagged claims against source and
   re-verifies once. Converts binary-reject → converge; keeps the strict bar on real fabrication.
   Cap at 1 fixer pass per card so cost stays bounded.

## 4. The coverage ledger — `tickets/_CONTEXT_COVERAGE.md` (mirror of `bq/_COVERAGE.md`)
One row per card, worst-first = the work queue. Regenerated by `build_index.sh` (add a small
walker) or written by the Land phase. Columns:

| ticket | state | card | facts_staged | last_run | notes |
|--------|-------|------|--------------|----------|-------|

- `state`: `pending` → `carded` (card landed, verified) → `verified` (card + delta facts human-reviewed).
- Resumability: a batch reads this, skips `carded`/`verified`, processes only `pending`.
- Commit per batch so a killed run loses at most one batch.

## 5. Batching (9 batches × ~10 cards; cluster by domain so each batch has a meaningful eval)
Order by leverage + eval-cohesion, not folder name:
1. **MM / audience** (audi_1083 done; audi_1141 done) → remaining MM/DS/scoring tickets.
2. **Incrementality / experiments** (ber_2250 epic + children, INCR-*, ghost-bid).
3. **DDP / vendor valuation** (audi_1089 epic, audi_1111 epic, 1027).
4. **Performance / reporting** (perf_report, Mode dashboards, goal-attainment — clears 1 lint).
5. **Pixel / attribution / CHAPI**.
6. **Bidder / serving / pacing**.
7. **Pre/post & method tickets** (ti_221 done; ti_270, ti_391, ti_849 …).
8. **Bidstream / augmentor** (audi_1091 — clears the 2nd lint).
9. **Tail / housekeeping / thin tickets.**

Each batch: extract → verify (recalibrated gate) → optional fixer → land → commit → append ledger.
Run one batch, read the result, then launch the next (stay in the loop; don't fire all 9 blind).

## 6. Eval grows into a regression suite (the §10 self-learning loop)
- Keep the canonical MM pre/post probe as regression case #1.
- After each domain batch, add ONE cold-start probe for that domain (e.g. "value a 3P vendor —
  method, tables, prior verdicts"; "did feature X move visit rate — cohort, control, method").
- Store probes as a small list the eval agent iterates. Every real cold-start miss → a new probe →
  fix routing → it stays fixed. Misses are logged, never silently dropped.

## 7. Safe-vs-gated (unchanged from §6 of the pilot)
- **Auto-apply (safe):** add missing front-matter (the 2 lint fixes), insert/replace TL;DR card,
  add `keywords:`, fill an empty `result:`, stage delta facts, rebuild index, commit.
- **Propose only (gated, batched at end, separate commit, human-approved):**
  - `build_index.sh` extension to walk `tickets/` so ticket `keywords:` fold into `_ROUTING.md`
    (finishes gap #2 — cards are already keyword-tagged and forward-compatible).
  - Any ticket move / de-nesting / renumber (ref-check first, archive over delete).
  - Merging staged delta facts into `knowledge/*.md`.

## 8. Cheap routing wins to apply first (from the pilot eval's soft gaps — no big run)
- Add `pre/post` / `pre-post analysis` keyword → `experimentation.md` § Standard Analysis Protocol.
- One cross-link in that protocol: "long pre-period → `sum_by_campaign_by_day`" so the Sep-2025
  `agg__daily_sum_by_campaign` truncation gotcha is unmissable from the method path, not only the table doc.

## 9. Cost & cadence
- Pilot: ~1.0–1.1M subagent tokens per 5-ticket run (extract 5 + verify 10 + land ~6 + eval 1).
- 84 remaining ≈ 9 batches → order-of-magnitude ~9–11M subagent tokens total if run fully, less
  with the fixer avoiding re-runs. Commit-per-batch; resumable; can pause between any two batches.
- Recommendation: apply §8 first (cheap), then run batches 1–3 (highest leverage), re-check the
  eval suite, and only then decide whether the long tail (batches 7–9, thin/housekeeping) is worth it.

## 10. Definition of done for the scale-up
- Every non-trivial ticket has a verified TL;DR card; `_CONTEXT_COVERAGE.md` shows 0 `pending`.
- Lint: 0 violations.
- Eval regression suite passes on every domain probe.
- Staged facts reviewed; gated proposals (esp. the `build_index.sh` ticket-routing extension)
  presented for approval. Thin/housekeeping tickets may stay card-less by explicit decision (logged, not silent).
